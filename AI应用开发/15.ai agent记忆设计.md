# AI Agent 记忆设计

> Agent 记忆（Memory）不是简单的「存历史对话」，而是让 Agent 跨会话保持上下文、积累经验、个性化交互的核心机制。本文系统总结记忆分层、生命周期、实现方案与工程实践。

---

## 一、为什么需要记忆

### 1.1 无记忆 Agent 的痛点

```
用户：我刚才说的项目叫什么？
Agent：抱歉，我无法记住之前的对话。

用户：帮我继续上次的需求
Agent：请问你上次的需求是什么？
```

LLM 本身是**无状态**的（stateless），每次推理只看当前输入。要让 Agent 具备连续性，必须在外部构建记忆系统。

### 1.2 记忆系统要解决的三个核心问题

| 问题 | 说明 |
|:---|:---|
| **存什么** | 全量对话太占 token，需要选择性保留 |
| **怎么取** | 相关记忆要能在正确时机被检索出来 |
| **怎么忘** | 过期/错误记忆不能永远污染后续推理 |

---

## 二、记忆分层架构（经典三层）

参考认知科学的记忆模型，工业界 Agent 普遍采用**分层记忆架构**：

```
┌─────────────────────────────────────────────────────────┐
│                    Agent Memory System                   │
├─────────────────────────────────────────────────────────┤
│  工作记忆 Working Memory（上下文窗口内）                   │
│  ├─ 当前对话历史                                         │
│  ├─ LLM 推理 scratchpad（ReAct 的 Thought/Action）        │
│  └─ 临时变量（工具调用结果）                              │
│  特点：高可访问、低容量、会被压缩/截断                     │
├─────────────────────────────────────────────────────────┤
│  情景记忆 Episodic Memory（会话级/任务级）                 │
│  ├─ 某次任务的完整执行轨迹                               │
│  ├─ 用户某次会话的偏好表达                               │
│  └─ Agent 某次失败的教训                                 │
│  特点：中等容量、按时间/主题组织、可摘要                   │
├─────────────────────────────────────────────────────────┤
│  语义记忆 Semantic Memory（长期知识）                     │
│  ├─ 用户画像（偏好、习惯、角色）                          │
│  ├─ 领域知识库（RAG 检索的文档）                          │
│  ├─ 经验规则（"用户喜欢简洁的回答"）                       │
│  └─ 技能/过程知识（SOP）                                 │
│  特点：大容量、持久化、可跨会话复用                         │
└─────────────────────────────────────────────────────────┘
```

### 2.1 三层记忆的对比

| 维度 | 工作记忆 | 情景记忆 | 语义记忆 |
|:---|:---|:---|:---|
| **对应人脑** | 短期记忆/注意力 | 情节记忆 | 长期记忆 |
| **存储位置** | LLM context window | 短期存储（Redis/缓存）| 向量数据库 + 元数据 |
| **容量** | 4k-128k tokens | 几千条事件 | 无限（取决于存储）|
| **生命周期** | 单次推理 | 单次会话/任务 | 永久/长期 |
| **检索方式** | 全量可见 | 时间序列 + 摘要 | 向量相似度 + 元数据过滤 |
| **典型技术** | 上下文工程（压缩）| Session Manager | RAG + Memory Graph |

## 三、各层记忆的实现机制

### 3.1 工作记忆：上下文窗口内的管理

工作记忆就是当前送入 LLM 的 context window。核心挑战是**在有限窗口内最大化信息密度**。

**关键技术**：

1. **滑动窗口**：保留最近 N 轮对话，旧的丢弃
2. **摘要压缩**：旧对话用 LLM 摘要后替换（见 [[AI应用开发/2.5 上下文工程]]）
3. **重要性过滤**：根据 relevance score 选择性保留
4. ** scratchpad**：ReAct 模式下，Agent 的推理过程（Thought）作为临时工作记忆

```typescript
// 工作记忆的压缩策略（伪代码）
interface WorkingMemory {
  messages: Message[];
  maxTokens: number;

  async pack(): Promise<Message[]> {
    if (this.tokenCount() <= this.maxTokens) {
      return this.messages;
    }
    // 策略 1: 保留 system prompt + 最近 K 轮
    const recent = this.messages.slice(-this.keepRecentTurns);
    // 策略 2: 旧消息摘要
    const old = this.messages.slice(0, -this.keepRecentTurns);
    const summary = await this.summarize(old);
    return [this.systemPrompt, summary, ...recent];
  }
}
```

### 3.2 情景记忆：会话级存储

情景记忆记录「发生过什么事」，按时间/会话组织。

**核心设计**：

```
Session（会话）
  ├─ Turn 1（用户消息 + Agent 响应 + 工具调用）
  ├─ Turn 2
  └─ ...
Event（事件粒度）
  ├─ type: "tool_call" | "user_message" | "agent_action"
  ├─ timestamp
  ├─ content
  └─ metadata
```

**实现方案**：

| 方案 | 存储 | 适用场景 |
|:---|:---|:---|
| Redis List | 内存 | 热会话，需要快速读取 |
| PostgreSQL | 关系库 | 需要复杂查询（按时间/用户/标签）|
| MongoDB | 文档库 | 事件结构多变 |
| SQLite | 文件 | 本地优先（OpenClaw 采用）|

```sql
-- 情景记忆表结构（PostgreSQL 示例）
CREATE TABLE agent_episodes (
  id BIGSERIAL PRIMARY KEY,
  session_id VARCHAR(64) NOT NULL,
  user_id VARCHAR(64),
  episode_type VARCHAR(32),  -- task_start / tool_call / task_complete
  content JSONB,
  metadata JSONB,
  created_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_session ON agent_episodes(session_id, created_at);
```

**情景记忆的摘要**：每 N 个 turn 或会话结束时，用 LLM 生成结构化摘要，压缩存入长期记忆：

```python
EPISODE_SUMMARY_PROMPT = """
请总结以下对话片段，提取：
1. 用户的核心意图（1 句话）
2. 关键事实/决策（列表）
3. 未完成的任务（列表）
4. 用户表达的偏好（如有）

对话：
{messages}

输出 JSON 格式。
"""
```

### 3.3 语义记忆：长期知识存储

语义记忆是 Agent 的「大脑皮层」，存储跨会话的持久知识。

#### 3.3.1 用户画像（User Profile）

```json
{
  "user_id": "u123",
  "profile": {
    "name": "张三",
    "role": "Java 后端工程师",
    "preferences": {
      "language": "中文",
      "code_style": "简洁，少注释",
      "response_format": "先给结论再展开"
    },
    "expertise_level": {
      "java": "expert",
      "python": "intermediate",
      "ml": "beginner"
    },
    "projects": ["EasyBI", "APASS"],
    "interaction_patterns": {
      "timezone": "Asia/Shanghai",
      "active_hours": ["9:00-12:00", "14:00-18:00"]
    }
  },
  "updated_at": "2026-09-06T10:00:00Z"
}
```

#### 3.3.2 经验规则（Procedural Memory）

从历史交互中提取的「如果...那么...」规则：

```
IF 用户问 "xxx 怎么实现" THEN 先给架构图，再给代码
IF 用户说 "太快了" THEN 放慢节奏，增加解释
IF 涉及 Java 并发 THEN 主动提醒线程安全
```

提取方式：
- **显式提取**：LLM 从会话摘要中提取规则（每周批量）
- **隐式学习**：通过强化学习（AgentMate 的双引擎回归守门）
- **人工标注**：用户反馈直接写入

#### 3.3.3 领域知识（RAG 知识库）

见 [[AI应用开发/3. 检索增强生成(RAG)]]，核心是向量数据库 + 混合检索。

## 四、记忆生命周期四阶段

```
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│  写入     │ ──→ │  巩固     │ ──→ │  检索     │ ──→ │  遗忘     │
│ Encode   │     │ Consolidate│    │ Retrieve │     │ Forget   │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
```

### 4.1 写入（Encode）：存什么，不存什么

**决策树**：

```
新信息到来
  ├─ 是当前对话必需的？→ 进入工作记忆
  ├─ 是一次性任务的细节？→ 写入情景记忆（短期）
  ├─ 是用户偏好/事实？→ 提取后写入语义记忆
  ├─ 是可复用的知识？→ 向量化写入知识库
  └─ 是噪声/临时信息？→ 丢弃
```

**关键原则**：不是所有对话都值得记住。写入前要做**重要性评分**（importance score）。

### 4.2 巩固（Consolidate）：从短期到长期

类似人脑的睡眠巩固，Agent 也需要定期把情景记忆提炼成语义记忆：

```
每 24 小时 / 会话结束时：
  1. 收集过期的情景记忆
  2. LLM 提取关键事实/偏好/规则
  3. 去重 + 冲突检测
  4. 写入语义记忆库
  5. 原情景记忆归档/删除
```

```python
# 记忆巩固（伪代码）
async def consolidate_memories():
    episodes = await episode_store.get_expired(hours=24)
    for episode in episodes:
        facts = await llm.extract_facts(episode.summary)
        for fact in facts:
            # 去重检查
            if not await semantic_memory.exists(fact.content):
                # 冲突检测
                conflict = await semantic_memory.find_conflict(fact)
                if conflict:
                    await resolve_conflict(conflict, fact)
                else:
                    await semantic_memory.write(fact)
        await episode_store.archive(episode.id)
```

### 4.3 检索（Retrieve）：在正确时机取出正确记忆

记忆检索是**多路召回** + **重排序**的过程：

```
用户当前输入
  ├─ 关键词匹配（BM25）→ 召回关键词相关记忆
  ├─ 向量相似度（embedding）→ 召回语义相关记忆
  ├─ 时间衰减（最近的记忆权重更高）
  ├─ 用户画像注入（profile 始终可见）
  └─ 元数据过滤（按场景/标签/重要性）
          ↓
     Reranker 重排序
          ↓
     Top-K 注入 context window
```

**记忆检索的上下文注入**：

```typescript
// 将检索到的记忆注入 system prompt
function buildMemoryContext(query: string): string {
  const memories = memorySystem.search(query, { topK: 5 });
  const profile = userProfile.get();
  
  return `
# 用户画像
${formatProfile(profile)}

# 相关记忆（按相关性排序）
${memories.map((m, i) => `${i+1}. [${m.type}] ${m.content}`).join('\n')}

# 当前对话
${query}
`;
}
```

### 4.4 遗忘（Forget）：防止记忆污染

没有遗忘的记忆系统会逐渐被噪声淹没。遗忘策略：

| 策略 | 机制 | 适用场景 |
|:---|:---|:---|
| **时间衰减** | 超过 N 天未访问 → 降低权重 | 通用 |
| **容量上限** | LRU/LFU 淘汰最冷记忆 | 内存有限 |
| **置信度衰减** | 低置信度记忆逐渐遗忘 | 推测性记忆 |
| **冲突解决** | 新事实覆盖旧事实 | 用户偏好变更 |
| **主动遗忘** | 用户明确要求删除 | 隐私合规（GDPR）|

```python
# 时间衰减遗忘
def forget_old_memories(memories, days=30):
    cutoff = datetime.now() - timedelta(days=days)
    return [m for m in memories if m.last_accessed > cutoff]
```

## 五、主流开源方案对比

| 方案 | 核心思路 | 存储 | 特色 | 不足 |
|:---|:---|:---|:---|:---|
| **Mem0** | 三层记忆 + 自适应提取 | 向量库（可插拔） | 自动 fact extraction + 冲突解决 | 相对较新，生态小 |
| **Letta**（原 MemGPT） | 虚拟上下文 + 内存分页 | PostgreSQL | 操作系统式内存管理，Agent 自己决定何时 recall | 架构重，部署复杂 |
| **LangGraph** | StateGraph + Checkpoint | 多后端 | 状态机 + 持久化 + Human-in-the-loop | 记忆需自己实现 |
| **CrewAI** | 共享 Memory + Entity Memory | ChromaDB | 简单易用，开箱即用 | 灵活性低 |
| **OpenClaw** | Session Manager + Local-First | SQLite | 会话持久化 + 配置驱动人格 | 长期记忆较弱 |
| **DeepSeek-Harness** | Log + Surface 投影 + Compaction | 事件日志 | 压缩不删 log，可重建历史 | 侧重上下文，非长期记忆 |

### 5.1 Mem0 的三层记忆设计

```
Mem0 Memory
├─ Core Memory（核心记忆）
│  └─ 用户画像 + 关键事实（始终可见）
├─ Recall Memory（召回记忆）
│  └─ 历史对话的向量索引（按需检索）
└─ Archival Memory（档案记忆）
   └─ 长期归档，低频访问
```

### 5.2 Letta 的 OS 式内存管理

Letta 把记忆当作操作系统的内存管理：

```
Context Window（RAM）        External Storage（磁盘）
├─ System Prompt             ├─ Archival Memory（向量库）
├─ Conversation History      ├─ Recall Memory（对话日志）
└─ Scratchpad               └─ Core Memory（可修改的事实）
         ↑                          ↓
         └──── Agent 自主调用 ──────┘
            memory_insert / memory_search
```

Agent 可以通过工具调用自己管理记忆（写入/检索/更新），而不是由框架自动注入。

## 六、AgentMate 的记忆设计（项目实践）

### 6.1 架构

```
AgentMate Memory
├─ 短期记忆（Redis）
│  ├─ 当前会话上下文（TTL 1h）
│  └─ 工具调用结果缓存
├─ 中期记忆（PostgreSQL）
│  ├─ 会话历史（按用户/时间索引）
│  └─ 任务执行轨迹
├─ 长期记忆（Elasticsearch + 向量库）
│  ├─ 用户画像
│  ├─ 经验规则库
│  └─ 领域知识库（RAG）
└─ 记忆检索层
   ├─ 多路召回（BM25 + Vector + 元数据）
   ├─ Reranker 重排
   └─ Token 预算控制
```

### 6.2 记忆提取流程

```
用户会话结束
    ↓
LLM 结构化摘要（意图 + 关键事实 + 偏好 + 未完成任务）
    ↓
重要性评分（importance_score）
    ↓
阈值过滤（score > 0.6 才写入）
    ↓
分类存储：
  ├─ 事实 → 用户画像（KV）
  ├─ 偏好 → 偏好库（标签）
  ├─ 经验 → 规则库（向量化）
  └─ 知识 → 知识库（向量化 + 全文索引）
    ↓
冲突检测 → 人工审核（高风险规则）→ 写入
```

### 6.3 差异化优势

| 特性 | AgentMate | 通用方案 |
|:---|:---|:---|
| 记忆提取 | 双引擎回归守门（LLM 提取 + 规则校验）| 纯 LLM 自动提取 |
| 冲突处理 | 人工审核 + 版本控制 | 静默覆盖 |
| 可观测性 | 每次记忆写入/读取可追溯 | 黑盒 |
| 质量保障 | 记忆变更需测试用例覆盖 | 无 |

## 七、工程实践要点

### 7.1 记忆设计的五个关键决策

| 决策 | 选项 | 推荐 |
|:---|:---|:---|
| 存储后端 | Redis / PG / Mongo / 向量库 | 分层组合，不追求单一 |
| 写入时机 | 实时 / 批量 | 实时存原始，批量提炼 |
| 检索策略 | 纯向量 / 混合 / 图谱 | 混合检索（BM25 + Vector）|
| 遗忘机制 | 时间 / 容量 / 主动 | 组合策略 |
| 可观测性 | 日志 / 指标 / Trace | 全链路可追溯 |

### 7.2 常见陷阱

1. **过度记忆**：什么都存 → 检索噪声大，token 浪费。**解法**：重要性评分 + 阈值过滤
2. **记忆不一致**：同一事实多个版本。**解法**：冲突检测 + 版本控制
3. **检索不相关**：向量检索召回语义相似但不相关的内容。**解法**：混合检索 + Reranker
4. **记忆膨胀**：用户画像无限增长。**解法**：结构化 + 容量上限 + 定期整理
5. **隐私泄露**：敏感信息被注入 prompt。**解法**：PII 检测 + 脱敏 + 访问控制

### 7.3 记忆设计 Checklist

- [ ] 是否区分了工作/情景/语义三层记忆？
- [ ] 是否有清晰的写入决策（存什么、不存什么）？
- [ ] 检索是否支持多路召回 + 重排序？
- [ ] 是否有遗忘/淘汰机制？
- [ ] 记忆变更是否可追溯（audit log）？
- [ ] 是否有冲突检测与解决？
- [ ] 用户能否查看/删除自己的记忆？（合规）

## 八、面试问答

### Q1：Agent 的记忆系统和 RAG 有什么区别？

A：RAG 是**单向检索**（知识库 → LLM），记忆系统是**双向闭环**（对话 → 提炼 → 存储 → 检索 → 注入）。RAG 的知识是静态的（人工灌入），记忆是动态生长的（从交互中学习）。RAG 解决「外部知识不足」，记忆解决「Agent 无状态」。

### Q2：如何让 Agent 记住用户偏好，又不占用太多 context？

A：分层注入。用户画像（结构化）始终注入（~200 tokens），历史偏好按需检索（vector search），不全量塞入。每次只注入当前任务相关的 Top-K 偏好。

### Q3：记忆冲突怎么处理？比如用户先说「我喜欢简洁」，后来说「详细解释」。

A：1）时间优先：新记忆覆盖旧记忆；2）置信度优先：明确表达 > 推测；3）上下文优先：偏好可能是场景相关的（写代码简洁，讲概念详细），需要带场景标签存储。

### Q4：Letta 的 OS 式内存管理和传统记忆分层有什么区别？

A：传统分层是框架自动管理（自动写入/检索/遗忘），Letta 是**Agent 自主管理**（Agent 通过 tool call 决定何时写入/检索/淘汰）。Letta 更灵活但更难控制，传统方案更简单但可能不够智能。

### Q5：如何评估记忆系统的效果？

A：三个维度：1）**召回率**：相关记忆是否被检索出来（离线评测）；2）**命中率**：注入的记忆是否被 LLM 实际使用；3）**任务效果**：有记忆 vs 无记忆的任务完成率差异。
