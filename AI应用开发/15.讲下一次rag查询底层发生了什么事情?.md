# 讲下一次 RAG 查询底层发生了什么事情？

> 面试高频问题：用户问了一个问题，RAG 系统在底层做了什么才生成最终回答？本文从一次查询的完整生命周期出发，逐阶段剖析底层原理。
> 前置阅读：[3. RAG检索增强生成.md](3.%20RAG检索增强生成.md)、[4. rag如何与大模型集成.md](4.%20rag如何与大模型集成.md)

---

## 一句话回答

> 一次 RAG 查询经历 **6 个阶段**：查询处理 → 查询向量化 → 向量检索 → 重排序 → 上下文组装 → LLM 生成。每个阶段都有工程优化空间，检索质量决定上限，生成质量决定下限。

## 二、完整链路总览

```
用户提问: "如何用 Redis 实现分布式锁？"
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 1: Query Processing（查询处理）                              │
│  ├─ 查询改写（让问题更适合检索）                                   │
│  ├─ HyDE（假设性回答，丰富查询语义）                               │
│  ├─ 多查询扩展（生成多个子查询提升召回）                           │
│  └─ 意图识别（分类到不同知识库/检索策略）                          │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 改写后的 query
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 2: Query Embedding（查询向量化）                             │
│  ├─ Embedding 模型（text-embedding-3 / bge-m3 / gte）            │
│  ├─ 文本 → 高维向量（1536/1024/768 维）                           │
│  └─ 归一化（cosine similarity 所需）                              │
└──────────────────────────┬──────────────────────────────────────┘
                           │ query vector
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 3: Vector Retrieval（向量检索）                              │
│  ├─ ANN 算法（HNSW / IVF-PQ / DiskANN）                          │
│  ├─ Top-K 粗召回（K=20~100，高召回低精度）                        │
│  ├─ Metadata Filtering（按租户/时间/权限过滤）                    │
│  └─ 可选：混合检索（BM25 + 向量，RRF 融合）                       │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 候选文档（Top-K）
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 4: Reranking（重排序）                                       │
│  ├─ Cross-Encoder 精排（bge-reranker / Cohere Rerank）           │
│  ├─ Query-Document 交互特征（比双塔更准）                         │
│  └─ Top-N 精选（N=3~10，高精度）                                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 精选文档（Top-N）
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 5: Context Assembly（上下文组装）                            │
│  ├─ Chunk 去重（重叠窗口去重）                                     │
│  ├─ 元数据附标（标题/来源/页码）                                   │
│  ├─ 上下文压缩（只保留相关片段）                                   │
│  └─ Token 预算控制（不超 LLM context window）                     │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 组装后的 context
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 6: LLM Generation（生成回答）                               │
│  ├─ Prompt 组装（System + Context + Question）                   │
│  ├─ LLM 推理（DeepSeek / GPT-4o / Claude）                       │
│  ├─ 流式输出（SSE）                                               │
│  └─ 可选：引用标注 / 幻觉检测 / 安全过滤                          │
└─────────────────────────────────────────────────────────────────┘
                           │
                           ▼
                    "Redis 分布式锁通过 SETNX..."
```

## 三、阶段深度剖析

### 阶段 1：Query Processing（查询处理）

#### 3.1.1 为什么需要查询改写？

用户的原始问题往往**不适合直接检索**：
- 太简短：「Redis 锁」→ 缺上下文
- 太口语化：「redis 咋搞分布式锁啊」→ 噪音多
- 有歧义：「锁」→ 可能是数据库锁/分布式锁/乐观锁

#### 3.1.2 常用改写策略

| 策略 | 原理 | 适用场景 | 代价 |
|:---|:---|:---|:---|
| **简单改写** | LLM 改写为更规范的检索语句 | 口语化/简短问题 | 1 次 LLM 调用 |
| **HyDE** | 先生成假设性回答，用回答去检索 | 技术文档/专业领域 | 1 次 LLM 调用 |
| **多查询扩展** | 生成 3-5 个子查询，分别检索后合并 | 复杂/多面问题 | N 次检索 |
| **查询分解** | 拆成多个子问题分别检索 | 多跳推理问题 | 多次检索 |

#### 3.1.3 HyDE 示例

```
原始 query: "Redis 分布式锁怎么实现？"
                │
                ▼
LLM 生成假设性回答（HyDE）:
  "Redis 分布式锁通常使用 SETNX 命令实现，即 SET key value NX EX seconds。
   加锁时设置唯一 value（UUID），解锁时用 Lua 脚本校验 value 后删除..."
                │
                ▼
用假设性回答去检索 → 匹配到的 chunk 更可能包含正确答案
```

**原理**：假设性回答包含了答案的关键词和语义，比原始问题更接近正确文档的 embedding。

#### 3.1.4 多查询扩展示例

```
原始 query: "Redis 分布式锁怎么实现？"
                │
                ▼ LLM 生成 3 个子查询
  ├─ "Redis SETNX 实现分布式锁的原理"
  ├─ "Redisson RLock 可重入锁源码"
  └─ "Redis 分布式锁的续期机制 watchdog"
                │
                ▼ 分别检索 + 合并去重 → 召回率提升 30%+
```

### 阶段 2：Query Embedding（查询向量化）

#### 3.2.1 Embedding 的本质

```
文本 "Redis 分布式锁" → Embedding 模型 → [0.023, -0.145, 0.891, ...] (1536 维)

语义空间：
  "Redis 分布式锁" 与 "SETNX 实现锁" 距离近 ✓
  "Redis 分布式锁" 与 "MySQL 行锁" 距离远 ✗
```

#### 3.2.2 常用 Embedding 模型对比

| 模型 | 维度 | 中文效果 | 多语言 | 成本 | 适用场景 |
|:---|:---:|:---|:---:|:---:|:---|
| text-embedding-3-large | 3072 | 优 | 是 | $$$ | 英文为主/高精度 |
| text-embedding-3-small | 1536 | 良 | 是 | $ | 通用场景 |
| bge-m3 | 1024 | 优 | 是 | 免费 | 中文/多语言 |
| bge-large-zh | 1024 | 优 | 否 | 免费 | 中文为主 |
| gte-large-zh | 1024 | 优 | 否 | 免费 | 中文开源 |

#### 3.2.3 关键工程细节

```python
# ❌ 错误：查询和文档用不同的 embedding 模型
query_vec = openai_embed("Redis 锁")
doc_vec = bge_embed("Redis 分布式锁实现")

# ✅ 正确：查询和文档必须用同一个模型 + 同一预处理
query_vec = bge_m3.encode("Redis 锁", normalize_embeddings=True)
doc_vec = bge_m3.encode("Redis 分布式锁实现", normalize_embeddings=True)
```

**归一化**：`normalize_embeddings=True` 让向量模长为 1，cosine similarity 等价于 dot product，计算更快。

#### 3.2.4 批处理优化

```
1000 个查询逐个 embedding → 1000 次 API 调用 → 慢 + 限流
  ↓
1000 个查询批量 embedding → 1 次 API 调用 → 快 10x
```

### 阶段 3：Vector Retrieval（向量检索）

#### 3.3.1 ANN 算法：为什么不用暴力检索？

```
暴力检索（精确但慢）：
  query_vec vs 100万 doc_vec → 100万次 cosine 计算 → ~50ms

ANN 近似最近邻（快且准）：
  HNSW → ~5ms（10x 加速，精度损失 < 1%）
```

#### 3.3.2 三大 ANN 算法对比

| 算法 | 原理 | 构建速度 | 查询速度 | 内存 | 适用场景 |
|:---|:---|:---:|:---:|:---:|:---|
| **HNSW** | 分层图，高层粗筛低层精搜 | 中 | 极快 | 高 | 100万以下，实时查询 |
| **IVF-PQ** | 倒排索引 + 乘积量化 | 快 | 快 | 低 | 1000万+，内存敏感 |
| **DiskANN** | 图索引 + 磁盘存储 | 中 | 中 | 低 | 亿级，SSD 场景 |

#### 3.3.3 HNSW 工作原理

```
HNSW 分层图（以 5 层为例）：

Layer 4（最稀疏）：  A ──── B
                     │      │
Layer 3：           A ── C ── B ── D
                     │  ╱  │  ╱  │
Layer 2：           A ─ C ─ E ─ B ─ D ─ F
                     │ ╱ │ ╱ │ ╱ │ ╱ │
Layer 1（最密）：   全部节点，每层 1/10 节点

查询过程：
  1. 从最高层入口点开始
  2. 在当前层贪心搜索最近邻
  3. 下降到下一层，从上次的最近邻继续
  4. 到最底层，搜索 ef 个最近邻
  5. 返回 Top-K
```

**关键参数**：
- `M`：每个节点的邻居数（默认 16，越大越准越慢）
- `efConstruction`：构建时的搜索宽度（默认 200）
- `efSearch`：查询时的搜索宽度（默认 50，越大越准越慢）

#### 3.3.4 Metadata Filtering（元数据过滤）

```python
# 场景：企业知识库，不同租户/部门只能看自己的文档
query_vec = embed("Redis 锁")
results = vector_store.search(
    query_vec,
    filter={
        "tenant_id": "acme",      # 租户隔离
        "department": "backend",   # 部门权限
        "updated_at": {"$gte": "2024-01-01"}  # 时效性
    },
    limit=20
)
```

**两种过滤策略**：
- **Pre-filter**：先过滤再检索（快，但过滤后数据少时召回低）
- **Post-filter**：先检索再过滤（召回高，但可能过滤完不够数）

#### 3.3.5 混合检索（BM25 + 向量）

```
用户查询: "Redis SETNX 锁"
    │
    ├─ BM25 检索（关键词精确匹配）→ chunk A (score 0.95)
    ├─ 向量检索（语义匹配）       → chunk B (score 0.88)
    │
    ▼ RRF（Reciprocal Rank Fusion）融合
    最终排名: chunk A (BM25 rank 1) + chunk B (vector rank 2)
```

**RRF 公式**：`score = Σ 1/(k + rank)`，k 通常=60

**适用场景**：技术术语/错误码/专有名词，BM25 比向量更准；日常问答，向量更优。

### 阶段 4：Reranking（重排序）

#### 3.4.1 为什么需要 Reranking？

```
向量检索（双塔模型）：
  query ──encode──→ q_vec
  doc   ──encode──→ d_vec    （独立编码，无法交互）
  相似度 = cosine(q_vec, d_vec)

问题：双塔编码时 query 和 doc 看不到对方，细粒度匹配丢失
  query: "Redis 分布式锁"  doc: "SETNX 实现互斥锁"
  向量相似度: 0.75（还行）
  但 Cross-Encoder 看两者交互后: 0.92（更准）
```

#### 3.4.2 Cross-Encoder 原理

```
Cross-Encoder（交叉编码器）：
  [query] [SEP] [doc] → BERT/RoBERTa → score (0~1)
  
  query 和 doc 拼接后一起过 Transformer，能看到交互特征：
  - "分布式锁" 和 "互斥锁" 的语义关联
  - "Redis" 和 "SETNX" 的共现关系
  - 否定词/转折词的影响

缺点：慢！每个 query-doc 对都要过一次模型
  100 个候选 → 100 次模型推理
```

#### 3.4.3 两阶段检索架构

```
Stage 1: 向量检索（快，粗召回）
  100万 docs → Top-100 candidates (~5ms)
                    │
                    ▼
Stage 2: Reranking（慢，精排）
  Top-100 → Cross-Encoder → Top-10 (~50ms)
                    │
                    ▼
最终结果: Top-10 (高精度)
```

**权衡**：K 太大 → rerank 慢；K 太小 → 可能漏掉好结果。经验值 K=20~50。

#### 3.4.4 常用 Reranker

| 模型 | 类型 | 中文效果 | 速度 | 适用场景 |
|:---|:---|:---|:---:|:---|
| bge-reranker-v2-m3 | Cross-Encoder | 优 | 中 | 中文为主 |
| Cohere Rerank v3 | API | 优 | 快（API） | 不愿自部署 |
| gte-reranker | Cross-Encoder | 优 | 中 | 中文开源 |

### 阶段 5：Context Assembly（上下文组装）

#### 3.5.1 Token 预算分配

```
LLM Context Window: 128K tokens
  ├─ System Prompt:         ~500 tokens
  ├─ Few-shot Examples:     ~1000 tokens
  ├─ Retrieved Context:      ~100K tokens（可压缩到 20K）
  ├─ User Question:         ~200 tokens
  ├─ LLM 输出预留:          ~8K tokens
  └─ 安全余量:              ~19K tokens
```

#### 3.5.2 Chunk 去重与合并

```
检索到的 chunks（有重叠）：
  chunk_3: "...SETNX 实现锁，设置过期时间..."
  chunk_4: "...设置过期时间防止死锁，value 用 UUID..."  ← 重叠
  chunk_7: "...UUID 防止误删，Lua 脚本保证原子..."

去重合并后：
  "...SETNX 实现锁，设置过期时间防止死锁，value 用 UUID 防止误删，
   Lua 脚本保证原子性..."
```

#### 3.5.3 上下文压缩

```python
# ❌ 把所有检索到的 chunk 塞进去
context = "\n\n".join([c.text for c in top_chunks])

# ✅ 只保留与问题最相关的句子
compressed_context = []
for chunk in top_chunks:
    sentences = split_sentences(chunk.text)
    relevant = [s for s in sentences if is_relevant(s, query)]
    compressed_context.append({"source": chunk.source, "text": " ".join(relevant)})
```

#### 3.5.4 引用标注

```
组装后的 context：
  [来源: redis-doc.md#12] Redis 分布式锁通过 SET key value NX EX seconds 实现...
  [来源: redisson-wiki.md#5] Redisson RLock 提供可重入锁，基于 Lua 脚本...

LLM 生成时可引用来源:
  根据 [1]，Redis 分布式锁通过 SETNX 实现...
  根据 [2]，Redisson 提供可重入锁...
```

### 阶段 6：LLM Generation（生成回答）

#### 3.6.1 Prompt 组装

```markdown
## System Prompt
你是一个技术问答助手。请严格基于以下检索到的上下文回答问题。
如果上下文中没有相关信息，请回答"我不知道"。
回答时请标注引用来源，格式为 [来源编号]。

## Retrieved Context
[1] [来源: redis-doc.md] Redis SETNX 实现分布式锁...
[2] [来源: redisson-wiki.md] Redisson RLock 可重入锁...
[3] [来源: blog.md] 分布式锁的续期机制...

## User Question
如何用 Redis 实现分布式锁？

## Answer
```

#### 3.6.2 生成时的约束

```
关键约束：
  1. Groundedness（扎根性）：答案必须基于 context，不能幻觉
  2. Citation（引用）：每个论断标注来源
  3. Conciseness（简洁性）：不啰嗦
  4. Format（格式）：代码块/列表/表格

工程手段：
  - System prompt 明确要求"基于上下文回答"
  - 加 "如果不知道就说不知道" 防止编造
  - 用 LLM-as-Judge 事后检测幻觉（见 [6. 幻觉治理](6.%20幻觉，幻觉审计，幻觉治理，幻觉评测.md)）
```

#### 3.6.3 流式输出

```
SSE 流式响应：
  data: {"delta": "Redis"}
  data: {"delta": " 分布式"}
  data: {"delta": "锁通过"}
  data: {"delta": " SETNX "}
  data: {"delta": "实现..."}
  data: [DONE]

用户感知：打字机效果，首 token 延迟 < 500ms
```

## 五、常见问题排查

### 5.1 检索不到相关内容

| 可能原因 | 排查方法 | 解决方案 |
|:---|:---|:---|
| Chunk 太大/太小 | 打印 chunk 长度分布 | 调整 chunk_size（200-500 tokens） |
| Embedding 模型不匹配 | 对比 query/doc embedding 是否同模型 | 统一模型 |
| 元数据过滤太严 | 去掉 filter 测试 | 放宽过滤条件 |
| Top-K 太小 | K=10 → K=50 测试 | 增大 K |
| 没有 BM25 兜底 | 加 BM25 混合检索 | 关键词匹配补充 |

### 5.2 检索到但 LLM 没用

| 可能原因 | 解决方案 |
|:---|:---|
| Context 太长被淹没 | 压缩 + 精排 Top-N |
| Prompt 没明确要求用 context | System prompt 加约束 |
| 检索内容与问题不相关 | 调优检索 + reranking |
| LLM 能力不足 | 换更强模型 |

### 5.3 幻觉严重

| 可能原因 | 解决方案 |
|:---|:---|
| Context 不足 | 增大 Top-K + 加 rerank |
| Prompt 约束不够 | 加"不知道就说不知道" |
| LLM 不遵守约束 | 用 LLM-as-Judge 检测 + 重试 |
| 检索内容质量差 | 优化 chunking + 去噪 |

## 六、面试高频问答

**Q1：一次 RAG 查询底层经历了哪些阶段？**

A：6 个阶段：(1) Query Processing（查询改写/HyDE/多查询）；(2) Query Embedding（向量化）；(3) Vector Retrieval（ANN 检索 + 元数据过滤 + 可选 BM25 混合）；(4) Reranking（Cross-Encoder 精排）；(5) Context Assembly（去重/压缩/Token 控制）；(6) LLM Generation（Prompt 组装 + 流式生成 + 引用标注）。

**Q2：为什么需要 Reranking？向量检索不行吗？**

A：向量检索用双塔模型，query 和 doc 独立编码，无法做细粒度交互匹配。Reranking 用 Cross-Encoder，query 和 doc 拼接后一起过 Transformer，能捕捉交互特征（如否定词/转折词/术语关联）。两阶段架构：向量检索快但粗召回 Top-K，reranking 慢但精排 Top-N，兼顾速度和精度。

**Q3：HNSW 是什么？为什么比暴力检索快？**

A：HNSW（Hierarchical Navigable Small World）是分层图索引。从最稀疏的高层开始贪心搜索，逐层下降到最密的底层，复杂度从 O(N) 降到 O(log N)。比暴力检索快 10-100 倍，精度损失 < 1%。关键参数 M（邻居数）和 efSearch（搜索宽度）控制精度/速度权衡。

**Q4：HyDE 是什么？为什么能提升检索效果？**

A：HyDE（Hypothetical Document Embeddings）是先生成假设性回答，用假设性回答去检索而不是用原始问题。原理是假设性回答包含了答案的关键词和语义，比简短/口语化的原始问题更接近正确文档的 embedding，能显著提升召回率。代价是多一次 LLM 调用。

**Q5：RAG 的延迟瓶颈在哪里？怎么优化？**

A：LLM 生成占 80%+ 延迟。优化手段：(1) 流式输出（SSE）降低首 token 延迟感知；(2) 模型选择（小模型快）；(3) 检索侧优化（ANN 参数调优 + 批处理 embedding）；(4) 缓存（相同 query 直接返回）；(5) 投机解码（speculative decoding）加速生成。

**Q6：怎么判断 RAG 系统的好坏？**

A：两个维度：(1) 检索质量——Recall@K（召回率）、MRR（平均倒数排名）、NDCG（归一化折损累计增益）；(2) 生成质量——Faithfulness（忠实度/无幻觉）、Answer Relevancy（答案相关性）、Context Relevancy（上下文相关性）。常用 RAGAS 框架自动评测。

## 七、易错点

1. **查询和文档用不同 Embedding 模型**：向量空间不一致，检索完全失效
2. **Chunk 太大**：一个 chunk 包含多个主题，检索到但不相关
3. **Top-K 太小没有 rerank**：粗召回精度低，最终答案差
4. **Context 不加 Token 控制**：超出 LLM 窗口直接报错或截断丢失
5. **Prompt 不约束 LLM 用 context**：LLM 用预训练知识回答，不基于检索内容
6. **没有 BM25 兜底**：技术术语/错误码/专有名词向量匹配差
7. **忽略元数据过滤**：不同租户数据混在一起，安全风险
8. **不做流式输出**：用户等待 3 秒才看到第一个字，体验差

## 九、一句话总结

> 一次 RAG 查询的本质：**把用户问题翻译成向量，在百万级文档库中用 ANN 算法快速找到最相关的 Top-K，用 Cross-Encoder 精排到 Top-N，组装成受控上下文塞进 LLM，让 LLM 基于检索内容生成有引用的回答**——检索质量决定上限，生成质量决定下限，工程优化贯穿全链路。
