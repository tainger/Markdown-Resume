# 从对话框输入问题到回复答案，大模型底层发生了什么

> 面试高频问题：你在 DeepSeek 对话框输入一个问题，到答案逐字蹦出，底层经历了哪些阶段？本文按 **用户侧 → 网络 → 服务端 → 模型推理 → 流式返回** 的顺序逐阶段拆解。
> 前置阅读：[1. 大模型工程基础.md](1.%20大模型工程基础.md)、[6.1 讲下一次RAG查询底层发生了什么事情.md](6.1%20讲下一次RAG查询底层发生了什么事情.md)

---

## 一句话回答

> 一次对话 = **5 个阶段**：前端打包请求 → 网络传输（DNS/TLS/LB/排队）→ 服务端预处理（鉴权/审核/组装 Prompt/分词）→ **模型自回归逐 token 生成**（Embedding + Transformer + KV Cache/MoE 加速）→ SSE 流式返回渲染。核心耗时在 GPU 上的自回归矩阵运算，体验关键在**首字延迟 TTFT**。

## 二、完整链路总览

```
你输入问题
  │
  ▼
┌─────────────────────────────────────────────────────┐
│ 1. 前端处理                                          │
│   收集输入 + 会话历史 + 系统提示 + 参数（模型/联网开关）│
│   封装 JSON → HTTPS 请求                             │
└─────────────────┬───────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────┐
│ 2. 网络传输                                          │
│   DNS 解析 → TCP/TLS 握手 → 负载均衡 → 排队调度       │
└─────────────────┬───────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────┐
│ 3. 服务端预处理                                      │
│   鉴权/限流 → 安全审核 → 组装 Prompt → Tokenization   │
└─────────────────┬───────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────┐
│ 4. 模型推理（核心）                                   │
│   Embedding + 位置编码 → Transformer Block × N 层    │
│   → 输出词表概率分布 → 采样解码出 1 个 token          │
│   → 追加到序列，循环（自回归）                        │
│   加速：KV Cache / 批处理 / 量化 / 并行 / MoE         │
└─────────────────┬───────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────┐
│ 5. 流式返回与渲染                                    │
│   每 token 经 SSE/WebSocket 推送 → 前端解码          │
│   → Markdown/代码高亮渲染 → 敏感词过滤 → 展示         │
└─────────────────────────────────────────────────────┘
```

## 三、阶段深度剖析

### 阶段 1：输入与前端处理

点击发送后，前端要做三件事：

| 步骤 | 内容 | 说明 |
|:---|:---|:---|
| 收集上下文 | 输入文本 + 会话历史 + 系统提示 + 参数 | 模型选择、温度、是否联网等 |
| Tokenization（可选在服务端） | 文本 → token | 中文一个汉字可能是 1~2 个 token；英文长单词会被拆成子词（subword） |
| 打包请求 | JSON → HTTPS POST | 携带会话 ID、鉴权凭证 |

> 💡 Tokenization 在客户端还是服务端做，取决于产品架构；**发给 API 的是文本，分词最终以服务端 tokenizer 为准**（同一段文本的 token 数决定计费和上下文占用）。

### 阶段 2：网络传输

```
域名 → DNS 解析出 IP → TCP 三次握手 → TLS 握手（HTTPS 加密）
     → 机房负载均衡器（LB）分配到某台推理网关
     → 高峰期进入队列，等待 GPU 资源（排队与调度）
```

- **负载均衡**：按负载/地域把请求分发到可用推理服务器
- **排队调度**：推理资源是稀缺的，调度器决定请求何时进入 GPU batch（直接影响 TTFT）

### 阶段 3：服务端预处理

| 步骤 | 内容 |
|:---|:---|
| 身份与权限校验 | 账号/API Key、额度、频率限制（Rate Limit） |
| 安全审核（输入侧） | 敏感内容过滤、Prompt 注入检测 |
| 组装 Prompt | 系统指令 + 历史对话 + 当前问题，按对话模板拼成完整输入序列 |
| Tokenization | 文本 → token ID 序列（模型只认 ID，不认文字） |

### 阶段 4：模型推理（核心）

#### 4.1 编码输入：一次前向传播

```
token ID 序列
  │
  ▼
Embedding 层：ID → 高维向量
  │
  ▼
+ 位置编码（让模型知道 token 的顺序）
  │
  ▼
Transformer Block × N 层，每层：
  ├─ 自注意力 Self-Attention：每个 token 关注其他 token，理解上下文
  ├─ 前馈网络 FFN：对特征做非线性变换（MoE 模型这里是专家网络）
  └─ 残差连接 + 归一化：稳定训练与推理
```

#### 4.2 生成输出：自回归（Autoregressive）

模型最后一层输出**词表上的概率分布** → 解码策略选出下一个 token → **追加到输入序列** → 再跑一次前向 → 再选一个 token……直到生成结束符（EOS）或达到最大长度。

**这就是"一个 token 一个 token 往外吐"的自回归生成——模型不是检索现成答案，而是逐 token 计算"下一个字是什么"。**

常见解码策略：

| 策略 | 做法 | 特点 |
|:---|:---|:---|
| Greedy（贪心） | 每次取概率最高的 token | 稳定但呆板，可能重复 |
| Top-k | 只在概率前 k 个 token 中采样 | 兼顾质量与多样性 |
| Top-p（核采样） | 只在累计概率达 p 的候选中采样 | 更自适应的候选集 |
| Temperature | 温度 T 缩放分布：T<0 更确定，T>1 更发散 | 控制随机性 |

> 💡 这解释了"**同一个问题每次回答不一样**"——采样有随机性，温度等参数不同，结果就不同。

#### 4.3 关键加速技术

实际推理**不会每次重算整个序列**，核心优化：

| 技术 | 原理 | 作用 |
|:---|:---|:---|
| **KV Cache** | 缓存历史 token 的 Key/Value，新增 token 只算增量 | 把每步复杂度从"全序列重算"降为"只算新 token"，**流式生成的基石** |
| **批处理 Batching** | 多用户请求合成 batch 共享一次 GPU 前向 | 提高 GPU 利用率（Continuous Batching 进一步动态插队） |
| **量化 Quantization** | FP16 → INT8/INT4 等低精度 | 减显存、提吞吐，精度轻微损失 |
| **张量/流水线并行** | 一层内切多卡（TP）/ 按层切多卡（PP） | 大模型单卡装不下时的协同推理 |
| **MoE 混合专家** | FFN 换成多个"专家"，路由器每 token 只激活少数专家 | 参数量大但计算量小 |

**DeepSeek 的特色技术**（面试加分项）：

- **MoE 架构**：总参数量很大，但每个 token 只激活其中一小部分专家网络——"容量大、算得省"
- **MLA（多头潜在注意力）**：把 KV 压缩成低维潜在向量再缓存，**KV Cache 体积大幅缩小**，显存省、吞吐高（对比传统 MHA 的完整 KV 缓存）
- **MTP（多 Token 预测）**：训练时教模型一次预测多个位置，推理时可做投机解码式的加速

#### 4.4 两个延迟指标

```
TTFT（Time To First Token）首字延迟：排队 + Prefill（一次性编码全部输入）
TPOT（Time Per Output Token）      ：Decode 阶段每吐一个 token 的时间

Prefill 是"读题"（并行，算力密集）→ 决定多快看到第一个字
Decode  是"答题"（自回归，访存密集）→ 决定字蹦得多快
```

### 阶段 5：流式返回与前端渲染

- **流式输出**：每生成一个/几个 token，立即通过 **SSE（Server-Sent Events）** 或 WebSocket 推给前端——首字延迟低，体验是"打字机效果"
- 前端处理：token ID → 文本（detokenize）→ **Markdown 渲染 / 代码高亮 / 公式渲染** → 输出侧敏感词过滤 → 逐字显示

> 💡 SSE vs WebSocket：单向推送用 SSE（HTTP 语义、自动重连、实现简单）；双向通信用 WebSocket。对话场景的主流选择是 SSE。

## 四、容易忽略的点（面试辨析）

1. **不是检索答案**：模型不从数据库里"找"现成答案，而是基于参数化知识逐 token 生成；"看起来像检索"是因为训练时记住了模式。（RAG 才是"检索 + 生成"，见 [3. RAG检索增强生成.md](3.%20RAG检索增强生成.md)）
2. **随机性来源**：不是模型"想"了不同答案，而是采样策略的随机性 + 温度参数。
3. **上下文长度限制**：模型只能看到有限窗口，超长对话会被截断或压缩——这就是为什么聊久了它会"忘事"（治理方案见 [Rag知识库/知识库如何做防腐治理.md](../Rag知识库/知识库如何做防腐治理.md) 与 [15.ai agent记忆设计.md](15.ai%20agent记忆设计.md)）。
4. **联网搜索 = 多了一步 RAG**：开启联网后链路变成"搜索 → 抓网页 → 相关内容拼进 Prompt → 再推理"，本质是外挂检索，不是模型自己会联网。
5. **成本大头**：GPU 上的矩阵运算，尤其自注意力的 QK^T 与 Decode 阶段的访存；所以 KV Cache、MLA 这类"省显存/省访存"的技术直接决定服务成本。
6. **Prompt 组装发生在服务端**：你看到的对话 ≠ 模型看到的输入——系统指令、注入的上下文、格式模板都在服务端拼接。

## 五、面试高频 Q&A

**Q1：为什么大模型生成是一个字一个字蹦，而不是整段一起出？**
> 自回归架构决定了"下一个 token 依赖前面所有 token"，必须逐个生成；配合 KV Cache 与流式传输，既保证因果正确又降低首字延迟。

**Q2：KV Cache 为什么能加速？代价是什么？**
> Attention 中历史 token 的 K/V 在生成过程中不变，缓存后每步只需计算新 token 的 Q/K/V，避免全序列重算。代价是显存占用随序列长度线性增长——这正是 MLA（压缩 KV）和 PagedAttention（分页管理 KV）要解决的问题。

**Q3：MoE 为什么"大而不贵"？**
> 总参数决定模型容量，路由器让每个 token 只激活少数专家（如 256 选 8），单 token 的实际计算量只相当于一个小得多的稠密模型；代价是显存仍需装下全部专家，需要并行与负载均衡。

**Q4：从输入 URL 到看到第一个字，延迟花在哪了？**
> DNS/TLS（网络）→ 排队（调度）→ Prefill 全量编码输入（算力）→ 首 token Decode。优化手段分别是：连接复用、持续批处理、Prefix Cache（命中相同前缀跳过重算）、投机解码。

## 六、易错点

1. **把推理当成"查库"**：生成 ≠ 检索，模型没有"答案表"可查。
2. **认为 Tokenization 一定在客户端**：以服务端 tokenizer 为准，token 数决定计费与上下文占用。
3. **混淆 Prefill 与 Decode**：首字延迟主要由 Prefill + 排队决定，"打字速度"由 Decode 决定。
4. **以为上下文无限**：超出窗口的早期对话会被截断/压缩，不是模型"记性差"，是架构约束。
5. **把联网搜索当模型内建**：那是外挂 RAG 管道，中间多了检索与拼接环节。
6. **忽略输出侧过滤**：输入和输出两侧都有安全审核，输出侧过滤发生在渲染前。

## 一句话总结

> **从输入到回答 = 一次"排队 → 读题 → 逐字答题"的 GPU 流水线**：前端打包、网络传输、服务端鉴权审核并组装 Prompt，模型用 Embedding + Transformer 编码全部输入（Prefill 定首字延迟），再自回归逐 token 生成（Decode 定打字速度），KV Cache/MoE/MLA 决定这件事多快多便宜，SSE 流式让你看到"打字机"效果——**模型不是在找答案，而是在算下一个字**。
