# 上下文工程（Context Engineering）

> 已有 [2. 提示词工程](2.%20提示词工程.md) 讲「怎么写指令」，[4. rag如何与大模型集成](4.%20rag如何与大模型集成.md) 讲「检索结果怎么注入」，本篇讲**上下文工程**——管理整个 context window 的**生命周期**（Packing → Compression → Caching → Eviction），从「调 Prompt」升级到「管理模型环境」。
> P7 分水岭：提示词工程是「写好指令」，上下文工程是「管理模型看到的一切」。

---

## 一、什么是上下文工程

### 1.1 定义

**上下文工程（Context Engineering）**：工程化管理**放进 LLM context window 的一切内容**，包括 system prompt、用户 query、历史对话、检索片段、工具 schema、工具执行结果、few-shot 示例等。

```
Prompt Engineering（提示词工程）= 写好「指令性文本」（system + user）
Context Engineering（上下文工程）= 管理「模型看到的一切」
  ├─ System Prompt（指令层）← 提示词工程的地盘
  ├─ User Query + History（对话层）
  ├─ Retrieved Context（检索层）← RAG 的地盘
  ├─ Tool Schema + Tool Results（工具层）
  ├─ Few-shot Examples（示例层）
  └─ Memory（记忆层：短期+长期）
```

**核心认知**：Prompt 是变量，上下文是环境。改 Prompt 是调参，改上下文是改环境——环境决定模型表现的上限。

### 1.2 为什么上下文工程比提示词工程更重要

| 维度 | 提示词工程 | 上下文工程 |
|:---|:---|:---|
| 优化对象 | 指令文本 | 整个 context window |
| 优化手段 | 措辞/结构/格式 | Packing/压缩/缓存/淘汰/布局 |
| 影响范围 | 单次调用的质量 | 成本 + 延迟 + 质量 + 可扩展性 |
| 上限 | 好指令能提升 20-30% | 好上下文工程能决定成败（长对话/Agent 场景） |
| 面试层级 | P5/P6 问的 | P7 问的 |

> **一句话**：P5 问「Prompt 怎么写」，P7 问「上下文怎么管」——管理模型看到的一切，才是工程化落地者的护城河。

## 二、Context Window 生命周期管理

上下文工程的核心是管理内容在 context window 中的**完整生命周期**：

```
┌─────────────────────────────────────────────────────────────┐
│              Context Window 生命周期管理                       │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  [1] Packing（装填）                                         │
│      ├─ 决定放什么：system / query / history / 检索 / 工具   │
│      ├─ 决定放多少：Token 预算分配                           │
│      └─ 决定怎么排：布局顺序（防 lost-in-the-middle）         │
│         │                                                    │
│         ▼                                                    │
│  [2] Compression（压缩）                                     │
│      ├─ 信息无损压缩（去重/去格式/去冗余）                    │
│      ├─ 信息有损压缩（摘要/LLMLingua 提示压缩）               │
│      └─ 外置存储（RAG：不塞 context，检索时再取）             │
│         │                                                    │
│         ▼                                                    │
│  [3] Caching（缓存）                                         │
│      ├─ Prompt Caching（前缀缓存）：固定前缀命中价 1/10      │
│      ├─ 检索结果缓存：相同 query 不重复检索                   │
│      └─ LLM 输出缓存：相同输入直接返回                        │
│         │                                                    │
│         ▼                                                    │
│  [4] Eviction（淘汰）                                        │
│      ├─ 多轮对话历史淘汰：滚动摘要 + 截断                      │
│      ├─ 工具结果淘汰：只保留相关的，旧的压缩                   │
│      └─ 长期记忆召回：相关记忆注入，不相关不塞                 │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 三、Packing：怎么放上下文

### 3.1 Token 预算的分层分配

> 基础预算计算见 [rag如何与大模型集成 §2.2](4.%20rag如何与大模型集成.md)，这里讲**动态分层预算**。

静态预算 vs 动态预算：

| 策略 | 说明 | 适用场景 |
|:---|:---|:---|
| **静态预算** | 每层固定 token 上限（system 500 + context 8K + history 2K） | 简单场景 |
| **动态预算** | 根据当前 query 复杂度动态调整各层预算 | 生产级系统 |

```java
public class DynamicContextPacker {
    public PackedContext pack(UserQuery query, ConversationHistory history,
                              List<Document> retrieved, ToolSchema toolSchema) {
        int totalBudget = model.getContextWindow() - maxOutputTokens;

        // 1. System Prompt 固定（必须留）
        int systemTokens = tokenize(systemPrompt);

        // 2. 根据 query 复杂度动态分配
        int queryComplexity = estimateComplexity(query);  // 1-10
        int retrievalBudget = (int) (totalBudget * (0.2 + queryComplexity * 0.05));
        int historyBudget = (int) (totalBudget * 0.15);
        int toolBudget = hasTools ? (int) (totalBudget * 0.1) : 0;

        // 3. 剩余给 query + few-shot
        int remaining = totalBudget - systemTokens - retrievalBudget - historyBudget - toolBudget;

        return PackedContext.builder()
            .system(systemPrompt)
            .retrieved(truncateToBudget(retrieved, retrievalBudget))
            .history(compressHistory(history, historyBudget))
            .toolSchema(toolSchema ? truncateToBudget(toolSchema, toolBudget) : null)
            .query(query)
            .build();
    }
}
```

### 3.2 布局策略：防 Lost-in-the-Middle

**Lost-in-the-Middle 问题**：LLM 对 context window 中间位置的信息关注度最低，头尾信息关注度最高。

```
LLM 注意力分布：
  [最关注] ←────────────────────────────────────────────→ [最关注]
    head                    middle                        tail
    ↑                        ↑                              ↑
System Prompt         检索片段/历史对话              User Query
(规则约束)           (最容易被忽略的内容)           (当前问题)
```

**布局策略**：

| 策略 | 说明 | 示例 |
|:---|:---|:---|
| **头尾关键信息** | 把最重要的约束放 head，当前 query 放 tail | System 规则放最前，User Query 放最后 |
| **检索结果重排** | 最相关的放最前/最后，不相关的放中间 | Top-1 放 head，Top-2 放 tail，Top-3 放中间 |
| **分块 + 分隔符** | 不同类型上下文用分隔符明确标记 | `<system>...</system>\n<context>...</context>\n<user>...</user>` |
| **滚动位置** | 多轮对话中定期把关键结论「滚到」tail | 每 5 轮把当前结论重新插入到 query 前 |

### 3.3 AgentMate 实战：上下文布局

```
AgentMate RAG 上下文布局（防 lost-in-the-middle）：

[HEAD] System Prompt（角色 + 幻觉防线规则 + 引用格式）
  ├─ 规则：只用 context 回答，不知道就拒答
  └─ 格式：引用 [doc:id]

[MID] 检索结果（按相关度排序）
  ├─ doc:1（最相关，放 mid 偏前）
  ├─ doc:2（次相关，放 mid）
  └─ doc:3（辅助，放 mid 偏后）

[MID] 历史对话（最近 3 轮，压缩后）
  └─ 旧的压缩成滚动摘要，新的保留原文

[TAIL] User Query（当前问题，放最前）
  └─ "MSE 网关支持哪些协议？"
```

## 四、Compression：怎么压缩上下文

### 4.1 压缩技术分类

```
上下文压缩技术
│
├─ [无损压缩] 不丢失信息
│   ├─ 去重：重复 chunk 只留一份（SimHash）
│   ├─ 去格式：去掉 Markdown/HTML 标签（保留纯文本）
│   ├─ 去冗余：去掉无关的样板文本（如"点击这里"等）
│   └─ 结构压缩：JSON 只保留关键字段
│
├─ [有损压缩] 丢失部分信息
│   ├─ 摘要压缩：用小模型对长文档摘要
│   ├─ 关键句提取：只保留包含关键实体/数值的句子
│   ├─ LLMLingua 提示压缩：BERT 级别的提示压缩
│   └─ Map-Reduce 总结：先逐个 chunk 总结，再汇总
│
└─ [外置存储] 不压缩，直接不放 context
    ├─ RAG：检索时才取，不预先塞入
    ├─ 数据库：只查需要的字段
    └─ 文件系统：按需读取片段
```

### 4.2 LLMLingua 提示压缩

**LLMLingua** 是微软开源的提示压缩技术，用 BERT 级别的小模型在 token 级别压缩提示，保持语义的同时减少 60-80% token。

```
原始提示（1000 tokens）：
  "MSE 网关是阿里云微服务引擎的组件，支持 HTTP、gRPC、Dubbo 三种协议。
   其中 HTTP 协议适用于...gRPC 适用于...Dubbo 适用于...
   Dubbo 协议需要在配置中开启 rpc-mode 参数..."

LLMLingua 压缩后（~250 tokens）：
  "MSE 网关支持 HTTP/gRPC/Dubbo 协议，Dubbo 需开 rpc-mode"
```

**工程价值**：
- 长文档 RAG 场景：10K tokens 的检索结果压缩到 2K，节省 80% 成本
- Agent 工具结果：大段 API 响应压缩到关键信息
- 多轮对话历史：旧对话压缩成关键结论

### 4.3 滚动摘要（多轮对话核心策略）

多轮对话中，历史会不断增长，**滚动摘要**是最常用的压缩策略：

```
滚动摘要机制：

第 1 轮：用户问 A → 助手答 A
第 2 轮：用户问 B → 助手答 B
...
第 5 轮触发摘要：
  历史（前 4 轮）→ 小模型摘要 → "用户问了 A 关于网关协议，又问了 B 关于配置"
  当前第 5 轮：[滚动摘要] + [最近 1 轮原文] + [当前 query]
第 10 轮再次触发摘要：
  [滚动摘要 v2（基于 v1 + 中间对话）] + [最近 1 轮原文] + [当前 query]
```

**摘要触发时机**：
- 历史 token 超过阈值（如 4K）
- 每 N 轮（如每 5 轮）
- 切换话题时（检测到语义变化）

### 4.4 压缩 vs 不压缩的 trade-off

| 策略 | 成本 | 延迟 | 信息保留 | 适用场景 |
|:---|:---:|:---:|:---:|:---|
| 不压缩（全塞） | 高 | 高 | 完整 | 关键决策、需要完整上下文 |
| 无损压缩 | 低 | 低 | 完整 | 有冗余但不能丢信息 |
| 摘要压缩 | 中 | 中 | 部分 | 长对话、文档总结 |
| LLMLingua | 低 | 中 | 大部分 | 大批量 RAG、工具结果 |
| 外置 RAG | 低 | 中 | 按需 | 知识库问答 |

## 五、Caching：怎么缓存上下文

### 5.1 Prompt Caching（前缀缓存）

主流 LLM API（OpenAI / Anthropic / DashScope）都支持 **Prompt Caching**：相同前缀的 prompt 第二次调用时，前缀部分按 1/10 价格计费，且跳过 prefill 阶段。

```
首次调用：
  [System: 2000 tokens] [Context: 5000 tokens] [Query: 100 tokens]
  → 全量计费（7100 tokens）+ prefill 延迟

二次调用（相同前缀）：
  [System: 2000 tokens ✅ 命中缓存] [Context: 5000 tokens ✅ 命中缓存] [Query: 100 tokens]
  → 只对 Query 计费（100 tokens）→ 成本降 98%，延迟降 80%
```

### 5.2 提高缓存命中率的工程策略

| 策略 | 说明 | AgentMate 实践 |
|:---|:---|:---|
| **System Prompt 稳定** | 不改 System Prompt，一旦改了缓存全灭 | System 版本化，改动走灰度 |
| **Context 排序稳定** | 检索结果每次按相同规则排序（如按 doc id） | 按相关度排序后固定顺序 |
| **公共前缀前置** | 把所有请求都有的内容放最前 | 产品介绍 + 通用规则放 System |
| **动态内容后置** | 把每次不同的内容（query、个性化上下文）放最后 | User Query 放 tail |
| **缓存版本控制** | Prompt 版本号变了才重新构建缓存 | System 带 version 标记 |

### 5.3 多层缓存架构

```
AgentMate 缓存架构（三层）：

├─ L1：LLM Prompt Caching（API 层）
│   └─ 相同前缀 1/10 价格，跳过 prefill
│
├─ L2：检索结果缓存（应用层）
│   └─ 相同 query 的检索结果缓存 5 min（Redis）
│   └─ 热点产品文档 embedding 缓存（不用每次计算）
│
└─ L3：LLM 输出缓存（应用层）
    └─ 相同 query + 相同 context 的输出缓存 10 min
    └─ 适用于高频重复问题（如"网关支持什么协议"）
```

## 六、Eviction：怎么淘汰上下文

### 6.1 多轮对话淘汰策略

| 策略 | 说明 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **FIFO 截断** | 超过预算时删掉最早的对话 | 简单 | 早期关键信息丢失 |
| **滚动摘要** | 旧对话摘要成滚动摘要 | 保留关键信息 | 摘要可能失真 |
| **语义相关性保留** | 只保留与当前 query 语义相关的历史 | 精准 | 需要额外 embedding 计算 |
| **结构化记忆** | 关键信息提取到结构化记忆（如 JSON），不保留原文 | 节省 token | 需要维护记忆结构 |

### 6.2 工具结果淘汰

Agent 场景中，工具执行结果可能很长（如 SQL 查询返回 1000 行），需要特殊处理：

```
工具结果处理策略：

1. 结果截断：只保留前 N 行 + 统计信息（"共 1000 行，显示前 10 行"）
2. 结果摘要：用小模型对结果摘要（"查询到 5 个异常实例，CPU 均超过 80%"）
3. 外置存储：结果存 Redis，context 里只放引用 ID，需要时再取
4. 按需保留：只保留当前对话仍在讨论的工具结果，旧的压缩
```

### 6.3 长期记忆管理

AgentMate 的记忆分层：

```
记忆分层（类似计算机存储层级）：

├─ L1：工作记忆（当前对话 context window）
│   └─ 当前 query + 最近 3 轮对话 + 当前检索结果
│
├─ L2：短期记忆（会话级，Redis）
│   └─ 本次会话的历史对话（压缩前），TTL 2 小时
│   └─ 切换页面/刷新后恢复对话
│
├─ L3：长期记忆（用户级，MySQL + 向量库）
│   └─ 用户偏好、历史工单、常用产品（结构化存储）
│   └─ 检索时按相关性召回注入 context
│
└─ L4：知识库记忆（产品文档，向量库）
    └─ RAG 检索的来源，不按用户区分
```

## 七、AgentMate 实战：上下文工程全链路

### 7.1 整体架构

```
用户请求
    │
    ▼
[Packing] 动态预算分配
    ├─ System Prompt（固定，缓存友好）
    ├─ Tool Schema（按需注入，不相关工具不塞）
    ├─ 检索结果（动态预算，按 query 复杂度）
    ├─ 历史对话（滚动摘要 + 最近 1 轮）
    └─ User Query（放 tail，防 lost-in-the-middle）
    │
    ▼
[Compression] 多级压缩
    ├─ 检索结果：去重 + SimHash + LLMLingua 压缩
    ├─ 历史对话：超过 4K token 触发滚动摘要
    └─ 工具结果：SQL 结果截断 + 统计摘要
    │
    ▼
[Caching] 三层缓存
    ├─ L1：Prompt Caching（System + 公共 Context 命中）
    ├─ L2：检索结果缓存（相同 query 5 min）
    └─ L3：LLM 输出缓存（高频问题 10 min）
    │
    ▼
[LLM 调用]
    │
    ▼
[Eviction] 后处理淘汰
    ├─ 历史对话写入 L2 短期记忆
    ├─ 关键结论提取到 L3 长期记忆
    └─ 当前 context 清空，准备下一轮
```

### 7.2 Agent 场景的上下文管理

AutoDev 多智能体流水线中的上下文传递：

```
AutoDev 五阶段状态机：

[阶段1] 建工单 → 输出：issue_spec.json（结构化，~500 tokens）
  │ 只把 issue_spec 传给下一个 Agent，不传完整对话历史
  ▼
[阶段2] SpecAgent → 输出：spec.md（结构化，~2000 tokens）
  │ 只把 spec.md + issue_spec 传给下一个 Agent
  ▼
[阶段3] CodingAgent → 输出：diff.patch（结构化，~5000 tokens）
  │ 只把 diff.patch + spec.md 传给下一个 Agent
  ▼
[阶段4] 单测 → 输出：test_result.json（结构化，~300 tokens）
  ▼
[阶段5] DeployAgent → 输出：deploy_report（结构化，~200 tokens）

关键设计：每个阶段只传「当前阶段的结构化产物」，不传完整对话历史
→ 避免 context 爆炸 + 缓存友好 + 状态清晰
```

## 八、面试高频问答

### Q1：什么是上下文工程？和提示词工程什么关系？

上下文工程是管理**放进 LLM context window 的一切内容**（system/query/history/检索/工具/记忆）的工程化方法论。提示词工程只管其中「指令性文本」这一层。关系：**提示词是变量，上下文是环境**。

### Q2：上下文工程的核心工作有哪些？

四件事（生命周期管理）：
1. **Packing 装填**：决定放什么、放多少、怎么排（防 lost-in-the-middle）
2. **Compression 压缩**：去重/摘要/LLMLingua/外置 RAG
3. **Caching 缓存**：Prompt Caching 前缀命中（1/10 价）+ 检索/输出缓存
4. **Eviction 淘汰**：多轮对话滚动摘要 + 工具结果截断 + 长期记忆分层

### Q3：什么是 lost-in-the-middle？怎么解决？

LLM 对 context window 中间位置的信息关注度最低，头尾关注度最高。解决：
- 关键信息放头尾（System 放 head，Query 放 tail）
- 检索结果重排（最相关的放前/后）
- 分块 + 明确分隔符
- 多轮对话定期把关键结论「滚到」tail

### Q4：Prompt Caching 是什么？怎么提高命中率？

主流 LLM API 的前缀缓存机制：相同前缀第二次调用时，前缀按 1/10 价格计费，跳过 prefill。提高命中率：
- System Prompt 保持稳定（改了缓存全灭）
- 公共内容放前缀，动态内容放后缀
- Context 排序稳定
- Prompt 版本化

### Q5：多轮对话历史怎么管理？

分层策略：
1. **滚动摘要**：旧对话摘要成滚动摘要，保留最近 1-2 轮原文
2. **FIFO 截断**：简单但会丢早期关键信息
3. **语义相关性保留**：只保留与当前 query 相关的历史（需要额外 embedding）
4. **结构化记忆**：关键信息提取到 JSON 记忆，不保留原文

AgentMate 用滚动摘要 + 4K token 触发阈值。

### Q6：Agent 工具结果太长怎么办？

四种策略：
1. **截断**：只保留前 N 行 + 统计信息
2. **摘要**：小模型对结果摘要（"5 个异常实例"）
3. **外置**：结果存 Redis，context 只放引用 ID
4. **按需保留**：只保留当前仍在讨论的工具结果

### Q7：你在项目中怎么做上下文工程的？

AgentMate 全链路：
1. **动态预算**：根据 query 复杂度动态分配 system/检索/历史/工具的 token 预算
2. **防 lost-in-the-middle**：System 放 head，Query 放 tail，检索结果按相关度排序
3. **三级压缩**：检索结果去重 + SimHash + LLMLingua 压缩；历史对话 4K 触发滚动摘要
4. **三层缓存**：Prompt Caching（System 稳定）+ 检索结果缓存 + 输出缓存
5. **Agent 结构化传递**：AutoDev 五阶段只传当前阶段结构化产物，不传完整对话

### Q8：上下文工程和 RAG 是什么关系？

RAG 是上下文工程的一个**子模块**——RAG 负责「检索什么内容放进 context」，上下文工程还包括「怎么压缩、怎么缓存、怎么淘汰、怎么布局」。RAG 解决「放什么」，上下文工程解决「放多少、怎么放、放完怎么管」。

## 九、易错点

1. **❌ 上下文工程就是 RAG** → ✅ RAG 只是检索层，上下文工程覆盖整个 context window 生命周期
2. **❌ 上下文越长越好** → ✅ 长上下文有 lost-in-the-middle 问题，且成本高延迟大，要精简
3. **❌ Prompt Caching 只要开了就行** → ✅ System Prompt 一改缓存全灭，需要版本化 + 灰度
4. **❌ 多轮对话全保留历史** → ✅ 历史会指数增长，必须滚动摘要 + 淘汰策略
5. **❌ 工具结果全塞进 context** → ✅ 大结果要截断/摘要/外置，否则 context 爆炸
6. **❌ 上下文工程是调参** → ✅ 是系统工程：Packing + Compression + Caching + Eviction 四件事
