# LLM Wiki 如何优化传统 RAG

> 已有 [3. RAG检索增强生成.md](3. RAG检索增强生成.md) 讲「怎么搜到对的内容」，[4. rag如何与大模型集成.md](4. rag如何与大模型集成.md) 讲「搜到后怎么喂给大模型」，本篇讲**优化演进层**——传统 RAG 的五大痛点 → 四种高级 RAG 范式（Agentic / Self / Corrective / Graph）→ LLM Wiki 模式（Karpathy）如何系统性地解决传统 RAG 的知识碎片化问题，并结合本仓库 [AGENTS.md](../AGENTS.md) 的 LLM Wiki Schema 实践。

---

## 一、传统 RAG 的五大痛点

传统 RAG（Naive RAG）的流程是固定的单步流水线：

```
Query → Embedding → Vector Search → Top-K → 拼 Prompt → LLM → Answer
```

这个流程简单有效，但有五个**结构性缺陷**：

| # | 痛点 | 根因 | 后果 |
|:---|:---|:---|:---|
| 1 | **检索与生成割裂** | 检索结果不可控，生成无法反馈检索 | 检索错了，LLM 基于错误片段生成，越答越偏 |
| 2 | **单轮检索不够** | 复杂问题需要多步推理才能确定检索方向 | 「MSE 网关和 Nacos 的服务发现有什么区别」需要先查两者各自文档再对比 |
| 3 | **知识碎片化** | 文档切 chunk 后丢失全局结构，表格/代码块被切断 | LLM 看到的是碎片，无法理解完整知识体系 |
| 4 | **无自我纠错** | LLM 生成后没有验证环节，幻觉直接输出 | 错误答案直达用户，无法检测和修正 |
| 5 | **静态知识库** | 知识库是一次性导入，不会自动维护和更新 | 新知识进不来，旧知识过期了没人管 |

**传统 RAG 的天花板**：检索质量决定一切，而检索是静态单轮的，无法应对复杂问题。

## 二、四种高级 RAG 范式

为了解决传统 RAG 的痛点，业界演进了四种高级范式：

```
传统 RAG 演进路线
│
├─ [1] Agentic RAG（代理式 RAG）
│   痛点：检索与生成割裂、单轮不够
│   思路：Agent 自主决定要不要检索、检索几次、检索什么
│
├─ [2] Self-RAG（自反思 RAG）
│   痛点：无自我纠错
│   思路：LLM 自己判断是否需要检索、生成后自我反思是否准确
│
├─ [3] Corrective RAG（纠错式 RAG）
│   痛点：检索错了就全错
│   思路：先评估检索质量，差了就换策略或走 Web 搜索兜底
│
└─ [4] Graph RAG（图谱 RAG）
    痛点：知识碎片化
    思路：用知识图谱/关系图谱替代纯向量检索，保留实体间关系
```

### 2.1 Agentic RAG（代理式 RAG）

**核心思想**：把 RAG 检索从「固定步骤」变成「Agent 可以自主调用的工具」，Agent 用 ReAct 循环决定何时检索、检索什么、检索几次。

```
传统 RAG：Query → 强制检索一次 → LLM → Answer
Agentic RAG：
  Query → Agent 思考
      ├─ 需要检索？→ 调用 search_tool("MSE 网关协议")
      │    ├─ 结果不够？→ 再调用 search_tool("MSE 网关 Dubbo 配置")
      │    └─ 结果够了 → 继续
      ├─ 需要查代码？→ 调用 code_tool("GatewayConfig.java")
      └─ 生成 Answer → 反思是否完整 → 不完整继续检索
```

**Agentic RAG 的三个关键能力**：

| 能力 | 说明 | 实现 |
|:---|:---|:---|
| **检索决策** | Agent 自主判断「是否需要检索」 | ReAct 循环 + 工具调用 |
| **迭代检索** | 一次检索不够可以多次，每次基于上一次结果调整 | 多轮 Tool Calling |
| **多工具编排** | 除了向量检索，还可以查代码/查数据库/调 API | 工具注册 + 路由 |

**AgentMate 实战**：AutoDev 流水线中的 SpecAgent / CodingAgent / DeployAgent 分工协作，就是 Agentic RAG 的变体——每个 Agent 自主检索所需上下文，而不是一次性把所有知识塞进去。

### 2.2 Self-RAG（自反思 RAG）

**核心思想**：LLM 在生成过程中**自我反思**，三个问题：

1. **Need Retrieval?**：这个问题需要检索吗？（简单常识题不需要）
2. **Is Retrieved Relevant?**：检索结果和问题相关吗？（不相关重新检索）
3. **Is Generated Correct?**：我的回答有依据吗？（没依据重新生成或拒答）

```
Query
  │
  ▼
LLM 自我判断：需要检索吗？
  ├─ 不需要 → 直接回答
  └─ 需要 → 检索
        │
        ▼
LLM 自我判断：检索结果相关吗？
  ├─ 不相关 → 改写 query 重新检索
  └─ 相关 → 生成回答
        │
        ▼
LLM 自我判断：回答有依据吗？
  ├─ 没依据 → 拒答 / 重新生成
  └─ 有依据 → 输出
```

**Self-RAG 的核心是把「是否检索、检索是否相关、生成是否正确」的判断权交给 LLM 自己**，而不是固定流程。

### 2.3 Corrective RAG（纠错式 RAG）

**核心思想**：在检索和生成之间加一个**评估器**，先评估检索质量，质量差就换策略。

```
Query → 检索
            │
            ▼
      检索质量评估器
            │
            ├─ 质量好 → 正常生成
            │
            └─ 质量差
                 ├─ 改写 query 重新检索
                 ├─ 换检索策略（向量→关键词→混合）
                 └─ 走 Web 搜索兜底（如果允许联网）
```

**评估指标**：
- 相关度分数低于阈值？
- 检索结果之间是否矛盾？
- 检索结果是否覆盖问题的所有方面？

### 2.4 Graph RAG（图谱 RAG）

**核心思想**：传统 RAG 把文档切成 chunk 做向量检索，**丢失了知识结构**。Graph RAG 用**知识图谱**保留实体间关系，检索时可以遍历图谱找到关联知识。

```
传统 RAG 知识表示：
  [chunk1: MSE 网关支持 HTTP] [chunk2: 网关支持 gRPC] [chunk3: Nacos 服务发现]
  → 三个孤立向量，不知道它们之间的关系

Graph RAG 知识表示：
  MSE 网关 ──支持──▶ HTTP
  MSE 网关 ──支持──▶ gRPC
  MSE 网关 ──依赖──▶ Nacos
  Nacos ──提供──▶ 服务发现
  → 图谱保留了关系，可以多跳遍历
```

**Graph RAG 的优势**：
- 多跳推理（「MSE 网关依赖什么？」→ 查图谱 → Nacos → 再查 Nacos 作用）
- 保留知识结构（实体-关系-实体）
- 解决知识碎片化问题

## 三、LLM Wiki 模式：系统性优化传统 RAG

> Karpathy 提出的 LLM Wiki 模式是对 RAG 的**系统性优化**，不是单一技术，而是一套知识管理方法论。本仓库 [AGENTS.md](../AGENTS.md) 就是这个模式的实践。

### 3.1 传统 RAG vs LLM Wiki 模式

| 维度 | 传统 RAG | LLM Wiki 模式 |
|:---|:---|:---|
| **知识组织** | 文档切 chunk，扁平向量库 | 结构化 Wiki（concept/entity/comparison/synthesis 分类） |
| **知识编译** | 每次查询从零检索 | 知识**编译一次、持续积累**（LLM 维护 Wiki） |
| **知识更新** | 全量重新导入 | 增量更新（git diff 找变更，只消化变更部分） |
| **知识质量** | 依赖检索召回 | Agent 审核维护（Ingest/Lint/Output 工作流） |
| **知识关联** | chunk 间无关联 | 双链 `[[concept/xxx]]` 串联知识 |
| **可追溯** | 无溯源 | 每个结论带双链指回 raw 笔记 |

### 3.2 LLM Wiki 的核心机制

```
┌─────────────────────────────────────────────────────────────┐
│                   LLM Wiki 知识循环                            │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  [Raw 层] 人类原始笔记（只读）                                 │
│      │                                                       │
│      │ Ingest 工作流（Agent 读 raw → 编译到 wiki）            │
│      ▼                                                       │
│  [Wiki 层] LLM 维护的结构化知识库                              │
│      │  ├─ concepts/     概念页（一个思想的总结+例题+易错点）  │
│      │  ├─ entities/     实体页（组件定位+导航+追问链）        │
│      │  ├─ comparisons/  对比页（横向对比+选型结论）          │
│      │  └─ synthesis/    综合页（跨目录串联面试主线）         │
│      │                                                       │
│      │ Query 工作流（向 Agent 提问）                          │
│      ▼                                                       │
│  [Answer] 基于 wiki 已编译知识回答，引用来源页                 │
│      │                                                       │
│      │ 有价值的结论 → 落回 wiki（对应页面 +1 条）             │
│      ▼                                                       │
│  Wiki 持续积累，越用越准                                      │
│                                                              │
│  Lint 工作流（定期检查）                                      │
│  ├─ 死链检查（双链指向不存在的页面）                           │
│  ├─ 矛盾检查（新旧条目冲突 → 更新/合并/标过期）               │
│  ├─ 孤立页检查（无入链无出链）                                 │
│  └─ 过期检查（raw 已删除 → wiki 对应标过期）                  │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 LLM Wiki 如何解决传统 RAG 的五大痛点

| 传统 RAG 痛点 | LLM Wiki 的解法 |
|:---|:---|
| 检索与生成割裂 | Wiki 是 LLM 自己维护的，知识已经被「编译」过一次，检索时直接用结构化知识而非原始碎片 |
| 单轮检索不够 | synthesis 综合页已经预先串联了跨目录知识（如「MySQL 事务 + Redis 缓存 + 分布式锁」的面试主线），一次检索就能拿到完整链路 |
| 知识碎片化 | Wiki 按 concept/entity/comparison/synthesis 分类，每篇都是完整主题，不是 chunk 碎片 |
| 无自我纠错 | Lint 工作流定期检查矛盾/死链/过期，相当于知识库的自我纠错 |
| 静态知识库 | Ingest 增量更新 + Query 结果回写，知识库持续积累 |

### 3.4 LLM Wiki 的知识编译原理

传统 RAG 是「**查询时编译**」（Query time compilation）：

```
每次查询：Query → 检索 chunks → 拼接 context → LLM 理解 → 生成
（每次都要从零理解原始文档碎片）
```

LLM Wiki 是「**预编译**」（Pre-compilation）：

```
Ingest 时：读 raw 笔记 → LLM 理解 → 编译成结构化 wiki 页面 → 写入
查询时：Query → 检索 wiki 页面（已编译）→ LLM 直接用 → 生成
（wiki 已经是 LLM 理解后的结构化知识，不用重新理解）
```

**类比**：传统 RAG 像每次考试都翻原书找知识点，LLM Wiki 像提前做好了结构化笔记——考试时直接看笔记，效率和准确性都更高。

### 3.5 本仓库的 LLM Wiki 实践（AGENTS.md）

本仓库 [AGENTS.md](../AGENTS.md) 定义了完整的 LLM Wiki Schema：

```
Markdown-Resume/
├── wiki/                    ← LLM 维护的 Wiki 层（读写）
│   ├── index.md             ← 全局索引
│   ├── log.md               ← 操作日志
│   ├── concepts/            ← 概念页（如 MySQL事务隔离级别）
│   ├── entities/            ← 实体页（如 Redis、HashMap）
│   ├── comparisons/         ← 对比页（如 Redis vs Memcached）
│   └── synthesis/           ← 综合页（如 Java后端面试主线）
├── mysql/                   ← raw 层（人类原始笔记，只读）
├── redis/                   ← raw 层
├── java/                    ← raw 层
└── AI应用开发/              ← raw 层
```

**四个工作流**：

| 工作流 | 触发 | Agent 动作 |
|:---|:---|:---|
| **Ingest** | `消化 <路径>` | 读 raw → 编译 wiki 页 → 维护双链 → 更新 index → log |
| **Query** | 向 Agent 提问 | 优先用 wiki 回答，有价值结论落回 wiki |
| **Lint** | `lint wiki` | 检查死链/矛盾/孤立页/过期 → 三动作 → log |
| **Output** | `从 wiki 出草稿` | 从 synthesis 提炼文章草稿到 output 层 |

## 四、四种范式 + LLM Wiki 的组合策略

实际工程中不是二选一，而是**组合使用**：

```
企业级 AI 知识库架构（演进方向）
│
├─ 基础层：LLM Wiki（知识预编译 + 双链 + Lint 自检）
│   └─ 解决知识碎片化、静态更新、质量不可控
│
├─ 检索层：混合检索 + Graph RAG
│   └─ 向量检索 + 关键词检索 + 图谱遍历（多跳）
│
├─ 生成层：Self-RAG + Corrective RAG
│   └─ 自反思判断 + 检索质量评估 + 纠错兜底
│
└─ 编排层：Agentic RAG
    └─ Agent 自主决定检索策略，多工具编排
```

**AgentMate 实战的演进路径**：

```
Phase 1（当前）：传统 RAG + P0-P4 分级检索
    └─ 解决「不相关不检索」问题

Phase 2（规划）：Corrective RAG
    └─ 加检索质量评估，差了自动改写 query 重检

Phase 3（规划）：Agentic RAG
    └─ AutoDev Agent 自主检索代码+文档+API，多工具编排

Phase 4（远期）：LLM Wiki 模式
    └─ 产品知识预编译成结构化 wiki，持续积累
```

## 五、面试高频问答

### Q1：传统 RAG 有什么问题？

五大痛点：
1. **检索与生成割裂**：检索错了 LLM 基于错误生成
2. **单轮检索不够**：复杂问题需要多步推理
3. **知识碎片化**：chunk 丢失全局结构
4. **无自我纠错**：幻觉直接输出
5. **静态知识库**：不会自动维护更新

### Q2：Agentic RAG 和传统 RAG 有什么区别？

传统 RAG 是固定流水线（Query→检索→生成），Agentic RAG 把检索变成 Agent 可自主调用的工具：
- Agent 自主决定**要不要检索**
- Agent 自主决定**检索几次**（迭代检索）
- Agent 可以**多工具编排**（向量检索+代码查询+API 调用）
- 适合复杂多步问题

### Q3：Self-RAG 的核心是什么？

LLM 在生成过程中自我反思三个问题：
1. Need Retrieval?（需要检索吗）
2. Is Retrieved Relevant?（检索结果相关吗）
3. Is Generated Correct?（生成内容有依据吗）

把判断权交给 LLM 自己，而不是固定流程。

### Q4：Graph RAG 解决什么问题？

解决传统 RAG 的**知识碎片化**问题。传统 RAG 把文档切 chunk 做向量检索，丢失了实体间关系。Graph RAG 用知识图谱保留关系，支持多跳推理（「A 依赖什么 → B → B 的作用是什么」）。

### Q5：LLM Wiki 和传统 RAG 有什么区别？

核心区别是**知识编译时机**：
- 传统 RAG：查询时编译（每次检索 chunks 重新理解）
- LLM Wiki：预编译（Ingest 时 LLM 理解 raw → 写成结构化 wiki，查询时直接用）

LLM Wiki 的优势：知识持续积累、双链关联、Lint 自检、增量更新、可追溯。

### Q6：四种 RAG 范式能组合用吗？

能，企业级架构是组合的：
- 基础层：LLM Wiki（知识预编译）
- 检索层：混合检索 + Graph RAG
- 生成层：Self-RAG + Corrective RAG
- 编排层：Agentic RAG

### Q7：你在项目中怎么优化 RAG 的？

AgentMate 的演进路径：
1. **当前**：传统 RAG + P0-P4 分级检索（命中关键词才检索，不相关拒答）
2. **两阶段召回**：向量粗排 Top-20 → Cross-Encoder 重排 Top-3，提升检索质量
3. **规划 Corrective RAG**：加检索质量评估，差了自动改写 query 重检
4. **规划 Agentic RAG**：AutoDev Agent 自主检索代码+文档，多工具编排
5. **远期 LLM Wiki**：产品知识预编译成结构化 wiki，持续积累

### Q8：为什么 LLM Wiki 比传统 RAG 更适合企业知识？

因为企业知识有三个特点：
1. **持续更新**：新产品、新接口不断出现，需要增量维护
2. **关联性强**：概念间有引用关系，需要双链串联
3. **质量要求高**：不能有过期/矛盾/死链，需要 Lint 自检

传统 RAG 是一次性导入+静态检索，LLM Wiki 是持续编译+动态积累+质量自检，更适合企业场景。

## 六、易错点

1. **❌ Agentic RAG 就是加个 Agent** → ✅ 核心是把检索变成工具 + Agent 自主决策，不是简单套壳
2. **❌ Self-RAG 一定更准** → ✅ LLM 自我反思也可能判断错，需要配合外部校验
3. **❌ Graph RAG 替代向量检索** → ✅ 是补充关系信息，实际用向量+图谱混合
4. **❌ LLM Wiki 就是做个知识库网站** → ✅ 核心是「预编译+持续积累+质量自检」的知识循环，不是静态站点
5. **❌ 越复杂的 RAG 越好** → ✅ 简单场景传统 RAG 就够，复杂问题才需要 Agentic/Graph，过度设计增加延迟和成本
6. **❌ 四种范式互斥** → ✅ 实际工程组合使用，分层互补

## 八、一句话总结

> 传统 RAG 的五大痛点（检索生成割裂/单轮不够/知识碎片/无纠错/静态）催生了四种高级范式（Agentic 自主编排 / Self-RAG 自反思 / Corrective 质量评估 / Graph 关系图谱），而 LLM Wiki 模式通过「知识预编译 + 双链关联 + Lint 自检 + 增量更新」从系统性层面优化传统 RAG，企业级实践应该分层组合：LLM Wiki 打底 + 混合/Graph 检索 + Self/Corrective 生成 + Agentic 编排。
