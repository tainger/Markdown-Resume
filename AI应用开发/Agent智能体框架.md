# Agent 智能体框架

> **P7 面试的深度区分题**：「你做的 Agent 是 ReAct 吗？遇到过什么问题？怎么优化？」。AgentMate 里从「双层 ReAct 推理发散到链路超时」踩坑 → 重构为「过程式状态机流水线」的真实 trade-off，是区分「只会写 LangChain Demo」和「真做过生产 Agent」的试金石。

## 一、Agent 是什么？和「LLM 直接调」有什么区别？

纯 LLM = 你问一句我答一句，什么都只能靠模型自己**想**（参数知识 + RAG 上下文）。
Agent = LLM + **工具使用能力**（能查 DB、调 API、跑脚本、发消息、改代码……）+ **自主规划能力**（知道该调用哪个工具、哪一步做完了下一步该干嘛）。

```
纯 LLM 回答：
  Q：帮我查下 MSE 网关杭州机房的 503 错误率最近一天趋势？
  A：（尴尬）我是一个语言模型，没有办法访问实时监控数据……

Agent 回答：
  Thought：用户要杭州机房 MSE 网关最近一天 503 错误率趋势
    → Action：调用【SLB监控查询工具】参数：region=杭州, product=MSE网关, metric=503错误率, time=1d
    → Observation：工具返回数据，9:00~12:00 错误率从 0.1% 飙升到 12%，对应 3 台实例 CPU 80%+
    → Thought：找到异常原因了，CPU 飙升导致 503
    → Action：再调用【网关实例列表工具】查这 3 台实例配置
    → Observation：实例是 2C4G，阈值配置成 CPU > 75% 触发限流
    → Thought：信息齐了，可以给用户总结根因 + 处理建议
    → Answer：「最近一天 503 错误率飙升时段为 9-12 点，根因是 3 台 2C4G 网关实例 CPU 持续>75% 触发限流阈值；建议：① 临时扩容到 4C8G ② 限流阈值调整到 85% ③ 排查 9 点突增流量来源」
```

## 二、Agent 经典框架对比：ReAct ⚔️ Plan-and-Execute ⚔️ 过程式状态机

### 2.1 三种模式全景对比表

| 维度 | **ReAct（思考行动循环）** | **Plan-and-Execute（先规划后执行）** | **⭐ 过程式状态机流水线（AutoDev 重构后）** |
|:---|:---|:---|:---|
| **核心思想** | Thought（想）→ Action（做）→ Observation（看结果）→ 下一轮 Thought…… 自由循环，直到得出答案 | 第一步：先列完整 Plan（①…②…③…N 步）→ 第二步按 Plan 顺序逐个执行 → 第三步根据结果反思要不要改 Plan | 固定五阶段状态机：建工单 → 写 Spec → 编码 → 单测 → 部署，每个阶段内部是确定性代码调用，只有必要环节用 LLM 做判断 |
| **灵活性** | ⭐⭐⭐⭐⭐ 极高（想到哪做到哪，能应对完全开放问题）| ⭐⭐⭐⭐ 中等（Plan 能改，但要先规划）| ⭐⭐ 低（流程固定，只能在状态转换点加分支）|
| **结果可控性** | ⭐⭐ 极差（推理发散、无限循环、链路超时、做着做着忘了原目标）| ⭐⭐⭐ 中等（Plan 约束了方向，但执行中还是可能发散）| ⭐⭐⭐⭐⭐ 极强（流程确定性，每一步输入输出严格定义）|
| **Token/时间消耗** | ⭐⭐ 极差（N 轮 LLM 调用，越跑越贵越慢）| ⭐⭐⭐ 中等（规划 1 次 + 执行 N 次）| ⭐⭐⭐⭐⭐ 极优（只有 5 个关键决策点用 LLM，其余全是代码直接调，LLM 调用量降 80%）|
| **幂等/可重跑** | ⭐ 不可能（每次 LLM 推理结果都不一样，重跑一遍完全不同路径）| ⭐⭐ 困难（Plan 每次都可能变）| ⭐⭐⭐⭐⭐ 完美支持（状态机每个状态都有幂等判定：如「分支上是否已存在本任务的 commit」）|
| **适用场景** | 完全开放域问答 / 对话式自由探索（用户问：我遇到个奇怪的报错，帮我排查……这种没法预定义流程）| 半结构化任务：「给 Aone 所有未关闭工单写周报」（步骤可预见但细节要 LLM 规划）| **生产级固定流程任务**（AutoDev 自动开发流水线、周报生成、排障诊断、工单流转这类有固定 SOP 的场景）|

### 2.2 ReAct ASCII 流程 & 典型坑（AgentMate 踩过）

```
ReAct 轮次循环：
  轮 1:  Thought: 用户要我帮他写个 HelloWorld SpringBoot 项目
         Action:  调用【代码生成 Skill】参数：语言=Java, 框架=SpringBoot, 需求=HelloWorld REST
         Observation: 生成了 HelloController.java + pom.xml  ✅ OK
  轮 2:  Thought: 有了代码，接下来应该建 Git 分支然后提交
         Action:  调用【Git CLI】参数：checkout -b feature/helloworld-20250825
         Observation: 分支创建成功                           ✅ OK
  轮 3:  Thought: 接下来应该 git add + commit，commit message 应该用 Conventional Commits 风格
         Action:  调用【Git CLI】参数：add . ; commit -m "feat: add HelloWorld REST endpoint"
         Observation: 提交成功，commit-id=abc123                   ✅ OK
  轮 4:  Thought: 好了，代码提交完了要不要调 OP2 部署？不过用户没说要部署……
         Action:  调用【Aone工单查询】查一下用户是谁？→ 不对，应该问用户要不要部署？
                    → 又调用了 LLM 推理一轮：要不要部署？→ 结论：可能需要……
         😱 😱 😱 推理发散开始：LLM 越想越偏，原任务是写代码提交，结果开始自说自话查用户信息、
              做产品推荐……轮次从 5 轮跑到 20 轮还没停，最终触发 10 分钟超时阈值被系统 kill。
```

**我们 AutoDev 早期踩的 ReAct 三大灾难级问题**：
| # | 灾难 | 发生频率 | 影响 |
|:---:|:---|:---:|:---|
| 1 | **推理发散（忘了原目标）** | ~30% 任务 | 做着做着跑到不相关的事上，用户要 A 他去做了 B 还自以为对 |
| 2 | **无限循环死磕** | ~15% 任务 | 同一个工具连续调 N 次返回同样错误，LLM 还不死心反复调，直到超时 |
| 3 | **链路超时（10 分钟 kill）** | ~25% 任务 | 轮次太多 LLM 调用累积时间 + 工具执行时间 > 10 分钟硬超时 → 全部作废 |

### 2.3 ⭐⭐⭐⭐⭐ 重构：过程式状态机流水线（P7 必讲亮点）

**核心思想**：把「主管 Agent + 执行 Agent 双层 ReAct 无限循环」的不确定性，降维为「5 阶段确定性状态机」。只有每个阶段的**关键决策点**才调用 LLM，流程本身用 Java 代码硬编码控制。

```
AutoDev 五阶段状态机 ASCII 图：
     ┌──────────────────────────────────────────────────────────────────────────┐
     │  ⭐ 状态机每一步都可幂等重跑（先 check 该步是否已完成 → 是则 skip）⭐  │
     └──────────────────────────────────────────────────────────────────────────┘

  (创建任务)
      │
      ▼
┌──────────────┐   成功     ┌──────────────┐   成功     ┌──────────────┐
│  ① 建工单    │──────────▶│  ② 写 Spec   │──────────▶│  ③ 编码      │
│  (Jira/Aone) │            │  (SpecAgent)│            │ (CodingAgent)│
│  幂等检查：   │            │  幂等检查：  │            │  幂等检查：   │
│  该需求是否已 │            │  Spec.md 是否│            │ 分支上是否已  │
│  有对应工单？ │◀────────── │  已生成并落库│◀────────── │ 有本任务提交？│
└──────┬───────┘  失败      └──────┬───────┘  失败      └──────┬───────┘
       │ 回滚                     │ 回滚                      │ 回滚
       │ （删工单）                │ （清 Spec 标记）            │ （reset branch）
       ▼                          ▼                           ▼
    [失败终态]                  [失败终态]                    [失败终态]

                                 │ 编码成功
                                 ▼
                        ┌──────────────┐   成功     ┌──────────────┐
                        │  ④ 跑单测    │──────────▶│  ⑤ 部署发布   │
                        │ (Qoder CLI) │            │ (OP2 流水线) │
                        │  幂等检查：  │            │  幂等检查：   │
                        │  该 commit ID│            │ 流水线是否已  │
                        │  是否已测通过│◀────────── │ 针对该 commit │
                        └──────┬───────┘  失败      │  有成功部署？ │
                               │ 回滚               └──────┬───────┘
                               ▼                         │ 部署成功
                            [失败终态]                    ▼
                                                        [成功终态]
                                                        钉钉卡片通知用户
```

**关键设计要点**：
1. **LLM 只在必要环节出场**：② Spec 生成（必须 LLM 写 Spec.md）、③ 编码（必须 LLM 按 Spec 写代码）。其他 ① 建工单、④ 单测、⑤ 部署全是纯 Java 代码调 API，零 LLM 调用。
2. **每步必做幂等检查**：这是「支持安全重跑」的基石——用户点错重复触发、前次跑一半挂了重提任务，都不会产生重复工单/重复 commit/重复部署。
3. **超时/失败状态可追溯**：每个阶段入参/出参/耗时持久化，失败时可以直接把某阶段「手动标记成功」从断点继续跑，不用重头来。
4. **异步推送结果**：整个流水线可能 5~15 分钟，同步等用户早烦死了 → 立即返回「任务已受理，预计 10 分钟后钉钉卡片通知结果」，完成后钉钉私信+群卡片双推送。

## 三、Skill 体系：把 Agent 能力做成可复用积木

ReAct/状态机是「怎么组织执行」，Skill 是「执行单元」——就像 Android 开发里 Activity 是框架，SDK 库是可复用能力。

### 3.1 Skill 的定义与四件套

```
一个合格的 Skill = 「四件套齐全」
  ① meta.json（定义元信息）
     {
       "name": "gateway_info_query",
       "displayName": "MSE 网关信息查询",
       "description": "查询云原生网关实例配置、路由规则、限流阈值、SLB 信息。参数：instanceId（网关实例ID，必填）、region（地域，可选）",
       "author": "贾志远",
       "category": "MSE运维",
       "version": "1.2.0"
     }
  ② Skill.java / Skill.py（实现代码）
     入参校验 → 调阿里云 OpenAPI / 查 DB → 结构化结果返回
  ③ 单测套件（JUnit 5 + Mock）
     正常场景 3 条 + 边界/异常场景 5 条 = 8 条单测覆盖率 ≥ 80%
  ④ 使用示例文档（README.md）
     3 个真实调用样例 + 常见报错说明

Agent LLM 在思考阶段怎么选 Skill？
  → 把所有已启用 Skill 的 meta.json description 拼起来当 System Prompt 给 LLM：
    「你可以调用以下工具，每个工具的功能和参数说明如下：
     1. gateway_info_query：功能……参数：instanceId,region
     2. aone_ticket_query：功能……参数：ticketId,status
     ……
     请根据用户问题，选择最合适的工具和参数，用指定 JSON 格式返回 action 和 parameters。」
```

## 四、Git WorktreeManager：多任务并发操作同一仓库的并发隔离（⭐ P7 工程亮点）

### 4.1 问题场景：为什么共享工作树会炸？

```
早期 AutoDev：多个任务并发操作同一个 Git 仓库，共享同一个 working tree
  任务 A：在 feature/branch-1 分支上，改 HelloController.java → git add → 正要 commit
  任务 B：并发进来，git checkout feature/branch-2 → 把工作区切走了！
  → 任务 A 此时 commit：commit 里居然包含了任务 B 分支上的文件 ❌
  或者更糟：两个任务同时 git add / git commit，Index.lock 文件冲突 → 双双失败
  或者：任务 A 生成的 Model.java 被任务 B 同名文件覆盖 → 互相覆盖写文件 ❌
```

### 4.2 解法：git worktree + 仓库级细粒度锁

Git 有个神器命令 `git worktree add <path> <branch>`：**同一个裸仓库可以「挂」多个独立工作树目录**，每个工作树有自己的分支/文件/Index，互不干扰：

```
┌─────────────────────────────────────────────────────────────────┐
│  同一个裸仓库 repo.git（objects 共享，省磁盘省 clone 时间）       │
└────┬───────────────┬───────────────┬───────────────┬────────────┘
     │               │               │               │
     ▼ worktree1     ▼ worktree2     ▼ worktree3     ▼ worktreeN
 /worktrees/       /worktrees/      /worktrees/      /worktrees/
  task-123/        task-124/        task-125/        task-xxx/
  branch: A1       branch: A2       branch: A3       branch: Ax
  任务 A 写文件     任务 B 写文件     任务 C 写文件    任务 N 写文件
  互不影响！每个    完全独立的        Checkout/Add/    从根上就隔离了，
  任务有自己的      工作树和 Index    Commit 互不干扰  不可能互相覆盖
  HEAD 和 Index
```

### 4.3 WorktreeManager 设计 ASCII

```
WorktreeManager.lockAndBorrow(repoUrl, taskId) 调用流程：

  ① repo 是否已本地 clone？无 → git clone --bare repo.git（只做一次，objects 共享）
  ② ┌─ 仓库级锁：synchronized(repoUrl.intern()) ─┐（只在「元数据操作」加锁，快：20ms）
     │   worktree 是否已存在(task-123)？是 → 直接复用
     │   不存在 → git worktree add worktrees/task-123 <branch>（真正 worktree 创建）
     └─ 释放仓库级锁 ─────────────────────────────────────────────────────────┘
         ↑ 仓库级锁范围只有 20ms，不阻塞「编码过程」（耗时的编码几分钟都在锁外跑）

  ③ 返回 Worktree 对象：任务 A 就拿这个 worktree 的绝对路径去读/写/编译/git 命令

使用完归还：returnWorktree(taskId, keepOrClean)
  keep = 后续还要用（如部署阶段） → 保留 worktree
  clean = 用完了 → git worktree remove worktrees/task-123（删除独立工作树，不影响其他）
  
异常兜底策略：
  如果配置文件里 `worktree.enabled=false`（如单测环境没 git）→ 降级回共享工作树
  如果并发冲突超过阈值自动降级；worktree 创建失败也自动降级
  → 保证「系统不会因为并发隔离失败而挂掉」，最多退化成串行执行
```

> 面试话术：「并发隔离这块我做了两层设计——第一层是 git worktree 硬隔离从根上避免互相覆盖，第二层是仓库级细粒度锁 + 开关降级兜底机制，既保证了并发性能（编码过程锁外并行，吞吐量比串行提升 N 倍，N=并发任务数），又保证了异常情况下系统可用不崩。」

## 五、钉钉异步推送模式：「立即受理 + 后台生成 + 完成通知」

长耗时 AI 任务（周报 4 分钟、AutoDev 10 分钟、排障 2 分钟）不能同步阻塞 HTTP 响应（HTTP 一般 60s 就超时）。我们用异步三步走：

```
1. 用户请求入口（HTTP / 钉钉对话）：
   立即校验参数 → 任务入库 status=PENDING → 返回用户「已受理，完成后钉钉通知」
   ↑ 这一步同步返回，保证不超时（100ms 内响应）

2. 后台虚拟线程异步执行：
   任务调度器从队列拿 PENDING 任务 → fork 虚拟线程（Java 21 + 不会占平台线程）→ 跑长流程
   → 每 30s 更新一次 DB 进度 status=RUNNING, progress=40%
   → 遇到幂等（同仓库 + 同任务已有 commit）→ 标记 SKIP，不重复执行

3. 完成后双渠道通知：
   status=SUCCESS/FAILED → 钉钉机器人私信用户 + 群卡片 @ 责任人
   → 卡片里附：任务详情页链接 + 一键重试按钮 + 失败原因堆栈（仅自己可见）

4. 防重复触发兜底：同人同仓库分布式锁
   前 5 分钟同一个人 + 同一个仓库 = 相同任务 → 用 Redisson 分布式锁「task:weekly:userId:repoUrl」TTL=5 分钟
   防止用户连续点 3 次导致后台跑 3 份（4 分钟 × 3 = 12 分钟浪费 + 3 条重复推送骚扰用户）
```

## 六、常见 Agent 模式（面试讲广度）

| 模式 | 核心思想 | 典型应用 |
|:---|:---|:---|
| **ReAct** | Thought-Action-Observation 循环 | 开放域对话 Agent（如普通聊天 + 工具调用）|
| **Plan-and-Execute** | 先写 Plan 再按 Plan 执行 | 复杂任务拆解（写周报、多步排障）|
| **过程式状态机** | 确定性状态机 + 关键节点 LLM | ⭐ AutoDev 流水线类（固定流程生产级任务）|
| **Multi-Agent 多智能体协作** | 多个 Agent 分工：Product/Dev/Test 各一个，协作完成 | 复杂软件开发（MetaGPT / AutoDev 早期 SpecAgent+CodingAgent+DeployAgent）|
| **Router + Expert** | 路由 Agent 先判断意图 → 转发给专门领域的 Expert Agent | 客服系统：路由到退款/物流/售后各专属 Agent |
| **Reflexion 反思型** | 任务完成后自己 Review 反思一遍 → 改不好 → 循环优化 | 代码生成：生成 → 单测不过 → 反思错误原因 → 改代码 → 再测 |

## 七、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「做 Agent 就是 ReAct，用 LangChain 调就完事」 | ❌ 错！ReAct 是开放域的好方案，但对「固定流程任务」来说，结果不可控、超时率 30%+、还没法重跑。P7 要讲「ReAct 在对话入口保留，但执行链路必须用过程式状态机控住」的折中方案。 |
| 2 | 「多智能体 = 越多越好」 | ❌ 错！多个 Agent 协调会带来「Agent 之间沟通歧义 + 推理发散叠加 + LLM 调用成本 N 倍增长」问题。AutoDev 早期双层 Agent 就是反例，后来改成「一个状态机 + 三个 Agent 角色固定分工」才稳定。 |
| 3 | 「并发操作 Git 加个全局锁就完事了」 | ❌ 错！全局大锁会把所有任务都串行化，吞吐量暴跌到 1/N。工程上正确做法是 worktree 硬隔离 + 元数据操作细粒度锁 + 兜底开关，把锁范围压缩到 20ms 级别。 |
| 4 | 「Skill 只要能跑就行，不需要单测和文档」 | ❌ 错！Agent 平台的 Skill 是给 LLM 调用的——LLM 选工具靠的是 Skill.description 的描述质量，没有示例 LLM 很容易传错参数；没有单测 Skill 改一下就可能把整个平台的调用全搞崩。 |
| 5 | 「HTTP 同步等待长任务完成没问题，前端加 loading 动画就行」 | ❌ 错！HTTP 网关超时 60s~300s，长任务 5 分钟起，前端 loading 转圈圈 5 分钟用户大概率以为挂了。必须走「立即受理 + 异步通知」模式。 |

---

## 八、一句话总结

> Agent 框架的本质不是「让 LLM 自由地想干嘛干嘛」，而是**在「LLM 的创造性」和「工程的可控性」之间找平衡**——对话入口保留 ReAct 的灵活性让用户爽，执行链路锁死过程式状态机保证结果可控不超时；Skill 做成可复用积木而不是一次性脚本；并发任务靠 Worktree 硬隔离而不是全局大锁。P7 面试考察的不是会调 LangChain，而是**讲清楚从双层 ReAct 失控到重构过程式状态机这段踩坑的心路历程，以及每一步 trade-off 后效果指标的变化（如超时率从 30% 降到 <5%）**。
