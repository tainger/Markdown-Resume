# RAG 检索增强生成

> **AI 应用面试 80% 开场白**：「你项目里的 RAG 是怎么做的？」。AgentMate 双混合检索架构 + Markdown 标题切片 + Cross-Encoder 重排 + P0-P4 分级 = 一套完整可落地的生产级 RAG 方案，讲出来秒杀纯 Demo 选手。

---

## 一、为什么需要 RAG？纯 LLM 为什么不行？

| 纯 LLM（参数化知识） | RAG + LLM（外挂知识库） |
|:---|:---|
| 知识截止训练时间，**新文档/内部文档不知道** | 检索最新文档/内部 Wiki，**实时知识** |
| 幻觉严重，一本正经胡说八道（参数化记忆不可控） | 有**源文档片段做事实依据**，引用溯源 |
| 想更新知识 → **重新微调/继续训练（成本几十万）** | 想更新知识 → **往知识库加一篇 Markdown（0 成本）** |
| 企业内部私有知识不可能靠微调（涉密+改不起） | 私有知识直接入库，完全隔离外网 |
| 问「咱们产品 MSE 网关最近那个限流 bug 怎么解？」 → 瞎猜 | 从最近技术方案/Wiki/工单里查真实答案 → 基于事实回答 |

```
RAG 全流程（R=Retrieve 检索 + A=Augment 增强 + G=Generate 生成）
  用户提问 → ①Query 预处理（改写/同义词映射/分词）
            → ②检索召回（向量/关键词/混合 → N 个候选 Doc Chunk）
            → ③重排排序（Cross-Encoder/规则打分 → Top-K 最相关）
            → ④Prompt 组装（「请基于以下参考资料回答：{Top-K Chunk} 问：{用户问题}」）
            → ⑤LLM 生成答案（基于 Prompt 里的参考资料，不再靠参数记忆）
            → ⑥后置处理（答案里引用来源跳转 + 脱敏 + 格式渲染）
```

## 二、AgentMate RAG 架构：Dual 双混合检索（⭐⭐⭐⭐⭐ 面试核心亮点）

很多人做 RAG 就是「纯向量检索」一条路走到黑，我们在 AgentMate 里做了 **双层双策略混合检索**，解决了三个典型问题：
- 产品黑话/英文缩写向量召回丢（「MSE」「网关熔断」这类内部词 Embedding 语义被稀释）
- 纯 Wiki 关键词找不到同义表达（「限流怎么开」↔「熔断降级配置」）
- 非本产品问题模型硬答（用户问「SpringBoot 事务」，产品知识库没有，模型照抄参数知识瞎扯产品能力）

### 2.1 架构 ASCII 图

```

## 三、P0-P4 分级检索策略（⭐⭐⭐ 防「模型硬答」的杀招）

纯 RAG 有个经典坑：知识库没有的问题，LLM 还是会拿参数知识硬扯一个「看起来很真」的答案，用户以为是产品能力结果用不了 → 投诉。我们分级兜底：

| 级别 | 判定条件 | 检索策略 | 回答策略 |
|:---:|:---|:---|:---|
| **P0 命中** | Query 命中产品专有名词（MSE/云原生网关/Nacos/Sentinel 等词库）且知识库召回 Top-1 置信度 ≥ 0.85 | 混合检索全量打开 | 正常基于召回回答 + 引用溯源 |
| **P1 半命中** | 命中产品词但 Top-1 置信度 0.6~0.85（可能是边角料问题）| 混合检索 + 放宽召回阈值到 Top-30 | 回答完明确标注「置信度中等，建议再查官方文档」|
| **P2 非本产品** | 没有命中产品词，但命中通用技术词（SpringBoot/JVM/MySQL） | **不检索本产品知识库**，把问题导向「官方文档链接聚合页」 | 回答「这是通用技术问题，不在本产品知识库范围内，官方文档参考：{Spring 事务官方文档}」，绝不拿参数知识硬说产品支持 |
| **P3 闲聊/开放式** | 既没产品词也没技术词（「今天天气？」「你是谁」）| 直接跳过 RAG | 走预设 Prompt 闲聊分支，回答「我是 MSE 智能助手，只回答产品技术问题」|
| **P4 无法判断** | Top-1 置信度 < 0.5 三路都不沾 | **反向提问澄清** | 回答「我可能没完全理解你的问题，你想问的是 MSE 微服务引擎哪方面呢？A. 网关限流 B. 注册配置中心 C. 智能体平台 D. 其他」 |

> 💡 面试话术：「P2 级别的兜底帮我们避免了至少 40% 的无效投诉——用户常问 Spring 事务这类通用问题，如果 RAG 照召回答，会被误以为是我们 MSE 产品支持的功能，最后找过来发现是误会，体验极差。分级后直接给官方链接，用户也不懵。」

## 四、切片策略（Chunker）：90% 的 RAG 效果差都栽在这一步

**为什么切片这么重要？** 切片切得稀碎，召回来的是半句话，模型读不懂；切片切得太大，上下文被无关内容占满，真正有用的信息被稀释，注意力分散。AgentMate 面对的是**内部技术 Wiki（大量 Markdown + 表格 + 代码块）**，普通的「固定长度 500 字符一刀切」效果很差。

### 4.1 我们的切片规则：Markdown 标题优先 + 结构完整保证

```
一篇 Markdown 文档结构：
# MSE 网关 503 熔断排查手册          ← H1：文档根节点
## 一、问题现象                       ← H2：章节
### 1.1 典型报错日志                  ← H3：小节（切片单位 #1 边界）
```java
2024-01-15 ERROR: Rate limit exceeded, threshold=1000
```                                    ← ⭐ 代码块：要么整块放一个切片，要么不切，绝对不能在代码中间切！
### 1.2 定位步骤
| 步骤 | 命令 | 预期输出 |            ← ⭐ 表格：同样不能把表头和内容拆散！
|------|------|----------|
| 1 | kubectl get pods | Running |
## 二、解决方案
### 2.1 临时恢复（应急）
...

切片算法（按递归优先级）：
  ① 先按 H2/H3 标题边界切 → 天然语义对齐，每个切片讲一个小主题
  ② 但如果某个 H3 超过 800 字符 → 看能不能在 H4/列表项边界切
  ③ 如果切完会穿过「代码块围栏 ``` / 表格 |---|---|」 → 推迟到结构结束再切
  ④ 最小切片单元：保留 Markdown 层级结构（每块 Chunk 带上文 H1/H2 标题作为前缀，避免语义漂移）
```

### 4.2 切片效果对比

| 切片策略 | 召回命中率 | 模型回答准确率 | 典型坑 |
|:---|:---:|:---:|:---|
| 固定长度 500 字符（一刀切）| 62% | 58% | 表格被砍一半 → 模型看到的是残缺列，乱答；代码块半截报错 |
| 纯 H1 大章节切（1 章 1 块）| 75% | 65% | 每块 3000+ 字符 → 上下文噪音太多，模型注意力被稀释 |
| ⭐ **AgentMate 标题+结构保护切片** | **89%** | **84%** | 极少出现结构残缺；每块 Chunk 自带 H1/H2 标题 → 上下文不漂移 |

## 五、召回层深入：向量相似度 vs Cross-Encoder 重排

### 5.1 向量相似度（ANN 检索）：快但不准（适合粗排）

**Embedding 模型**把一段文本变成 1024/1536 维的向量，查询向量和库向量**余弦相似度**越高就越相关：
```
余弦相似度 = cos(θ) = (A · B) / (|A| × |B|)  → 范围 [-1, 1]，越大越相关
  Q（查询向量）  ╲
                 ╲ θ=20°  → 相似度 0.94 ✅ 很相关
  C1（候选向量）──╯
                 ╱ θ=70°  → 相似度 0.34 ❌ 不相关
  C2（候选向量）─╯
```

为什么只能做粗排？**Bi-Encoder 的先天缺陷**：查询和文档各自独立做 Embedding，没有做「交叉注意力」，只能捕捉粗粒度语义，像「苹果 公司」vs「苹果 水果」这种 polysemy 就分不清楚。

### 5.2 Cross-Encoder 重排：慢但准（适合精排 Top-N）

Cross-Encoder 把「查询 + 候选 Chunk」**拼成一对**送进 Transformer，做完整的交叉注意力计算，输出一个 0~1 的「相关性分数」：

```
 Bi-Encoder（粗排向量召回）          Cross-Encoder（精排重排）
 ┌────────┐   ┌────────┐            ┌───────────────────────┐
 │ Query  │   │  Doc   │            │ <[BOS_never_used_51bce0c785ca2f68081bfa7d91973934]> Query </s> Doc
 │ Emb.   │   │  Emb.  │            │   完整 Transformer    │
 └───┬────┘   └───┬────┘            │   （双向交叉注意力）  │
     │            │                 └───────────┬───────────┘
     └─── 点积 ───┘ ← 独立编码后才比               │
           ▼                                      ▼
        相似度 0.89                            相关性得分 0.943
        （快，1ms/万条）                       （慢，10~30ms/条）
```

**为什么重排效果好 30%+？** Cross-Encoder 能看「查询里的关键词在 Doc 里的上下文」——比如用户查「限流 bug 503」，Bi-Encoder 只看语义接近；Cross-Encoder 能发现 Doc 里「503 = 服务不可用 = 触发限流阈值 = bug 已在 V1.2.3 修复」这条推理链，打分自然更准。

> 💡 **成本优化策略**：粗排（向量 + Wiki）召回 20 条，这 20 条里已经包含了正确答案（只是排序不对）；再拿 Cross-Encoder 只重排这 20 条 → **10~30ms × 20 = 最多 600ms 延迟**，用户无感，但准确率飙升。

## 六、向量数据库原理（简单讲清楚 HNSW 就够 P7）

| 向量检索方式 | 原理 | 召回率 | QPS | 适用 |
|:---|:---|:---:|:---:|:---|
| **暴力搜索（Flat）** | 拿查询向量和库中每一条算余弦距离，Top-K | 100% 精确 | 极低（1w 条都要 10ms） | 小数据集 < 10w 条 / 离线评测 |
| **IVF（倒排索引）** | K-Means 聚类 N 个中心点 → 先找最近的几个中心点簇 → 只在簇内暴力搜 | ~95% | 高 | 中数据集 10w~100w 条 |
| **⭐ HNSW（分层小世界图） ⭐ 主流默认** | 像跳表一样建 3~5 层图：上层稀疏散布点，下层稠密连接；先从上粗找接近，再下沉细搜 | ~98% | 极高（10w QPS） | **百万级以上数据集首选**（FaISS/Milvus/Elasticsearch 默认都是 HNSW）|

### HNSW ASCII 原理（跳表的图版本）

```
层 3（最稀疏，跳得远）：  A ─────────────────────────────────────── F
                        │                                         │
层 2（中等稀疏）：       A ──────── C ────────────── E ────────── F
                        │          │                │            │
层 1（最稠密，细搜）：   A ── B ──── C ─── D ──────── E ──────── F
                        ↑ 目标：从 A 出发找最近的 G（在 C 附近）
                             
搜索路径：A → 层3看A邻居是F(太远) → 回层2，A邻居是C(更近，跳到C) → 层1，C邻居里找G ✅
```

> 💡 面试不用讲太深，能说「向量库不是暴力比，用 HNSW 图索引近似检索，快几十倍，召回率 98%+」就够了。如果你用的是阿里云百炼 RAG 或 DashVector，这些底层全托管不用自己操心。

## 七、同义词与查询改写（Query Transformation）

内部产品 RAG 的**第一大敌人**：同一概念有 N 种说法。

```
例子：用户想查「MSE 网关的限流配置」
  实际文档标题是「云原生网关流量控制规则配置」
  用户说法：限流 / 流控 / 熔断 / 防刷 / QPS 控制 / 限速  ← 6 种说法，文档只用了「流量控制」
  如果不做同义词映射：用户查「限流」→ 向量相似度不够 → 召回失败 ❌
  做了同义词映射：Query 改写为「MSE 网关 限流 OR 流控 OR 熔断 OR QPS控制 OR 限速 配置」
              → 两种说法都去检索，召回命中 ✅
```

### 同义词映射的三种来源（P7 落地细节）

| 来源 | 举例 | 更新频率 |
|:---|:---|:---|
| **① 人工维护黑话词库（核心种子）** | MSE=微服务引擎；网关=云原生网关；熔断=限流降级；503=服务不可用 | 产品大版本迭代一次 |
| **② 点赞点踩自动挖掘（自动迭代）** | 用户问「xx」踩了 → 补充「正确答案应该是 yy」→ 自动把 xx ↔ yy 加到候选映射 → 人工审核入库 | 每周批量跑一次 |
| **③ LLM 做查询扩写（在线动态）** | 把用户问题丢给 LLM：「请把这个问题扩写成 5 种不同说法，包含缩写、别名、行业黑话」→ 6 个 Query 并行召回再合并去重 | 高优先级问题实时开，普通问题默认不开（省钱）|

## 八、常见 RAG 坑 & 解决方案（面试加分）

| # | 常见坑 | 现象 | 解法 |
|:---:|:---|:---|:---|
| 1 | **知识库污染** | 一篇错误文档被召回 → 模型照错文档回答错 | 知识库入库前审核 + 文档版本号 + 点赞点踩标记低质量文档降权 |
| 2 | **召回率还行但精确率差** | 10 条召回只中 2 条，Top-3 里经常没正确答案 → 模型看不对的上下文就胡扯 | 加 Cross-Encoder 重排 + 同义词映射 + 切片策略优化 |
| 3 | **表格/代码块召回残缺** | 表格召回到一半列 → 模型看到残缺信息就瞎猜 | 切片时严格保证结构完整，表格/代码块必须整块切；召回后按文档位置回调父段落 |
| 4 | **长上下文窗口注意力稀释** | 128K 窗口塞满 10 篇 Chunk → 模型其实只看前半部分 | Lost in the Middle 效应：把最高置信度 Chunk 放 Prompt 最前+最后（中间注意力最弱）|
| 5 | **Hallucination 幻觉** | 模型基于上下文添油加醋、编造不存在的参数 | System Prompt 里加「如果参考资料里没有明确答案，请直接回答『知识库暂无此问题答案，请联系技术支持』」+ 严格引用溯源 |

## 九、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「RAG 就是把文档切片存向量库，查的时候 Cosine 找相似」 | ❌ 这是最低级 Demo RAG。生产级 RAG 至少要包含：**查询改写 + 混合检索 + Cross-Encoder 重排 + 分级策略 + 反馈闭环**。只说切片向量的，面试官直接判定 Demo 水平。 |
| 2 | 「切片越大越好，上下文越完整」 | ❌ 太大的切片：① 噪声多稀释有用信息 ② 召回成本高（Embedding 长文本贵） ③ Lost in the Middle 中段模型根本不看。**目标是每个切片讲一个独立小主题**，不是越大越完整。 |
| 3 | 「Cross-Encoder 重排比向量好，所以直接用 Cross-Encoder 检索全库」 | ❌ 慢 100 倍！100w 条库，Cross-Encoder 要 3000 秒，用户早走了。**必须是「向量粗排 Top-20 → 重排 Top-3」两级结构**，兼顾速度与精度。 |
| 4 | 「只要 Embedding 模型用最新最大的，召回就好」 | ❌ 80% 的召回问题不是模型差，是**切片策略烂 + 没有同义词映射 + 没有做混合检索**。Embedding 从 1.5 亿参数换到 30 亿参数，提升不到 5%；切片策略优化一下可以提升 20%。 |
| 5 | 「RAG 用了就不会幻觉」 | ❌ RAG 大幅降低幻觉但**不能彻底杜绝**。要配合：严格 System Prompt（不许用知识库外内容）+ 引用溯源（用户点引用能跳原文）+ 分级策略（知识库没有就反向澄清）三重兜底。 |

---

## 十、一句话总结

> RAG 的本质不是「切片 + 向量」的玩具 Demo，而是**检索策略（混合/分级）、数据预处理（切片/结构保护）、排序算法（粗排+重排）、在线迭代（同义词/反馈闭环）** 四层工程化体系的结合。P7 面试考察的不是讲 RAG 全流程，而是**能说清「为什么我们选双混合检索而不是纯向量？为什么 Cross-Encoder 只重排 20 条？切片策略怎么保证表格代码不被切断？P2 级别兜底是怎么防止模型硬答的？」这类具体的工程 trade-off 和落地效果**。
