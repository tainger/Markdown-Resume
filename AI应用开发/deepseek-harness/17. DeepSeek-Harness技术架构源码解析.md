# DeepSeek-Harness 技术架构源码解析

> DeepSeek Harness（`dsh`）是 DeepSeek AI 开发的开源 Agent Harness，基于 Cordis 插件架构，核心设计哲学是 **"everything is a plugin"**——包括 Agent Loop 本身。本文基于源码 `repo/AI-project/deepseek-harness` 深度解析，并与 [OpenClaw 笔记](../openclaw/15.%20OpenClaw技术架构与AI%20Agent技术解析.md) 对比。

---

## 一、项目定位

### 1.1 什么是 DeepSeek-Harness

```
传统 Agent 框架：
  Agent 循环写死在核心代码里 → 换模型/换工具/换策略都要改核心

DeepSeek-Harness：
  Cordis 插件架构 → 一切皆插件（模型适配器/工具注册表/会话日志/Agent Loop）
  → 每个部分都可从配置替换
```

**核心理念**：没有特权核心（privileged core）需要打补丁。扩展 dsh 的方式是在其他插件旁边挂载一个新插件，注册是可逆的 effect——插件卸载时自动回滚。

### 1.2 与 OpenClaw 的定位差异

| 维度 | OpenClaw | DeepSeek-Harness |
|:---|:---|:---|
| 运行形态 | 本地后台服务（常驻） | 可组合插件树（CLI/Web/ACP） |
| 架构基础 | 自研微内核网关 | Cordis 插件框架 |
| 可扩展性 | ContextEngine 可插拔 | **Everything 可插拔**（含 Agent Loop） |
| 设计哲学 | 配置优先（SOUL.md） | **日志优先（Session Log as Truth）** |
| 成熟度 | 145k stars 爆火 | 预发布阶段（foundation over blast radius） |

### 2.2 Profiles 和 Bundles

```
Profile（配置组合）：
  命名组合，存储在 Harness home
  ├─ 列出堆叠的 bundles
  ├─ 安装的 out-of-tree 插件
  └─ 用户自己的 cordis.patch.yml

Bundle（分发格式）：
  Cordis 配置行 + 它们挂载的代码
  └─ 插入的内容可被上层 patch

加载顺序（空 entry list 开始）：
  bundle1 → bundle2 → ... → profile patch → home patch → --patch overlay
```

**设计亮点**：任何一行配置都可被你的 patch 替换。`dsh --profile web --dump-config` 能看到实际启动的插件树。

## 三、核心设计原则：Model-visible ⟺ Logged

这是 dsh 最核心的设计铁律：

> **任何到达模型请求的内容，必须能从 session log 重建。**
> 一个新的模型可见输入，必须对应一个新的 session event。

### 3.1 Session Log 是唯一事实源

```
Session Event Log（append-only，不可变）：
  ├─ turn/start
  ├─ user/message
  ├─ assistant/chunk*（流式保真，可重放）
  ├─ assistant/message
  ├─ tool/call*
  ├─ tool/result*
  ├─ step/start
  ├─ step/end
  ├─ turn/end
  ├─ compaction/start
  ├─ compaction/summary
  └─ compaction/end
        │
        │ deriveMessages()
        ▼
  Model Request（从日志派生，不存原始消息）
```

### 3.2 请求重建不变量（Request-Reconstruction Invariant）

每次 LLM 调用前，dsh 会**运行时断言**请求可从 session log 重建：

```typescript
// packages/core/agent-loop/src/invariant.ts
ctx.on('llm/stream', (options: GenerateOptions, next) => {
  // 1. 请求必须 frozen（不可变）
  if (!Object.isFrozen(options)) fail('a loop-built request must be frozen')
  // 2. 必须带 sessionId
  if (options.sessionId === undefined) fail('a loop-built request must carry a session id')
  // 3. messages 必须从 session log 派生
  const expected = session.deriveMessages()
  if (JSON.stringify(options.messages) !== JSON.stringify(expected)) {
    fail(`llm request diverges from durable derivation (log-reconstruction desync)`)
  }
  // 4. 配置必须与 request header 匹配
  const headerMatches = options.model === header.config.model
    && JSON.stringify(options.tools ?? []) === JSON.stringify(header.tools ?? [])
  if (!headerMatches) fail(`llm request diverges from folded request header`)
  return next()
})
```

**设计意义**：
- 防止插件在消息发送后、LLM 调用前偷偷篡改（安全红线）
- 保证可重放（replay）、可分支（fork）、可持久化
- 这是 dsh 与 OpenClaw 最大的设计差异——OpenClaw 组装完消息直接发，dsh 强制验证一致性

## 四、Agent Loop：Turn / Step 模型

### 4.1 Turn 与 Step

```
Step = 一次模型请求 + 它调用的工具
Turn = 零或多个 step（从第一个输入被 claim 到没有 owed）

  turn/start
    │
    ├─ claim next-step input + one queued message
    │
    ├─ assemble prompt sections + tool schemas
    │
    ├─ agent/pre-step（waterfall，可 reject/rewrite）
    │     │
    │     ├─ reject 或空 → 关闭 turn，无 step
    │     │
    │     └─ enter(messages) → step/start
    │           │
    │           ├─ append user/message
    │           ├─ derive model history from log
    │           ├─ agent/request → llm/stream
    │           ├─ assistant/chunk* → assistant/message
    │           ├─ tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
    │           └─ step/end
    │
    ├─ 还有工具要调用 / 有新输入 → 下一个 step
    │
    └─ agent/turn-stopping（serial，无 next()）
  turn/end
```

### 4.2 ReactLoopAgent 源码结构

```typescript
// packages/core/agent-loop/src/agent.ts
export class ReactLoopAgent implements Agent {
  private phase: Phase  // idle | maintenance | running
  readonly inbox: Inbox  // 输入队列
  
  // 状态机驱动 turn/step 边界
  // 每个请求都从 session log deriveMessages()
}
```

### 4.3 事件分类（三个域）

| 域 | 事件 | 特点 |
|:---|:---|:---|
| **Session Events** | turn/*, step/*, user/message, assistant/*, tool/* | 持久化事实，append-only |
| **Agent Events** | agent/inbox/*, agent/pre-step, agent/request, agent/status | 实时扩展点，waterfall |
| **Capability Events** | fs/*, tools/*, telemetry/* | 策略和适配器 |

**Waterfall 语义**：`agent/pre-step`、`agent/request`、`llm/stream`、`tools/*` 是 waterfall，监听器必须调用 `next()` 委托；`agent/turn-stopping` 是 serial，无 `next()`。

## 五、能力缝（Capability Seams）：三角色模式

### 5.1 定义

```
Capability Seam = Service Definition（接口）
                + Service Provider（实现）
                + Consumer（使用，通常是模型可见工具）

一个能力缝必须包含三个角色，缺一不可。
```

### 5.2 示例：文件系统能力缝

```
┌─────────────────────────────────────────────┐
│ Service Definition: ctx.fs                  │
│   定义接口：read(path), write(path, content) │
└────────────────────┬────────────────────────┘
                     │ implements
         ┌───────────┴───────────┐
         ▼                       ▼
  ┌─────────────┐          ┌─────────────┐
  │ Local FS    │          │ Remote Sandbox│
  │ Provider    │          │ Provider     │
  │ 本地文件系统 │          │ 远程沙箱文件系统│
  └─────────────┘          └─────────────┘
         │                       │
         └───────────┬───────────┘
                     │ consumed
                     ▼
  ┌─────────────────────────────────────────┐
  │ Consumer: dsh-tool-read / dsh-tool-write│
  │   模型可见工具，调用 ctx.fs.read()       │
  └─────────────────────────────────────────┘
```

**设计意义**：切换 Provider 不需要改 Consumer——把 `ctx.fs` 从 Local 换成 Remote Sandbox，所有基于它的工具自动切换到沙箱执行。

### 5.3 常见能力缝

| 能力缝 | Service | Providers | Consumers |
|:---|:---|:---|:---|
| 文件系统 | `ctx.fs` | local / remote sandbox | read_file, write_file |
| Shell 执行 | `ctx.shell` | local / pwsh | bash 工具 |
| 子进程 | `ctx.subprocess` | local process-tree | shell 底层 |

## 六、基于 Surface 的上下文压缩

### 6.1 Surface 模型

dsh 不直接对原始消息做压缩，而是对 **Surface（可见节点序列）** 操作：

```
Session Event Log（完整历史，不可变）：
  [seq0, seq1, seq2, seq3, seq4, seq5, seq6, seq7, seq8, seq9]
                          │
                          │ surfaceOp: replace [seq0, seq4]
                          ▼
Surface（当前模型可见的节点序列）：
  [shadowed_summary, seq5, seq6, seq7, seq8, seq9]
  ↑ 新的 summary 节点   ↑ 保留的近期原文

Surface 是 Log 的投影——压缩不删除 log，只改变 surface 可见性
```

**设计意义**：压缩是逻辑操作（改变投影），不是物理删除；fork/resume/replay 都能从 log 重建任意历史 surface。

### 6.2 压缩区域选择算法

```typescript
// packages/compaction/compaction-basic/src/region.ts
function selectCompactableRange(session, measurement, retainTokens):
  // 1. 从后往前累加 token，保留 retainTokens 的近期 tail
  let accumulated = 0
  let keepFromIdx = pricedNodes.length
  for (let i = pricedNodes.length - 1; i >= 0; i--) {
    accumulated += pricedNodes[i].tokens
    keepFromIdx = i
    if (accumulated >= retainTokens) break
  }
  if (keepFromIdx === 0) return null  // 没有可压缩的

  // 2. ⭐ 工具调用对平衡检查：向前找到第一个平衡切点
  while (keepFromIdx > 0) {
    if (toolPairingBalancedBefore(session, surfaceNodes[keepFromIdx])) break
    keepFromIdx -= 1
  }
  if (keepFromIdx === 0) return null

  // 3. 返回 head-anchored 压缩范围
  return { start: surfaceNodes[0], end: surfaceNodes[keepFromIdx - 1] }
```

### 6.3 工具调用对平衡算法（增量缓存）

```typescript
// packages/compaction/compaction/src/tool-pairing.ts
interface BalanceCache {
  generation: number           // surface 重写代际
  cutBalanced: boolean[]      // N+1 个切点的平衡状态
  indexBySeq: Map<number, number>  // seq → 切点索引
  inProgressToolCalls: number      // 未完成工具调用数
}

// 增量扩展：只 fold 新增的 surface 节点
function extendCache(session, cache, seqs): BalanceCache {
  const tail = seqs.slice(processed)
  let inProgressToolCalls = cache.inProgressToolCalls
  for (const seq of tail) {
    inProgressToolCalls += eventDelta(event)  // tool-call +1, tool-result -1
    if (inProgressToolCalls < 0) throw 'corrupt surface'
    pendingCuts.push(inProgressToolCalls === 0)  // 0 = 平衡
  }
}

// 切点平衡检查
function toolPairingBalancedBefore(session, seq): boolean {
  return cutBalance(balanceCache(session), seq, 0)  // seq 之前的切点
}
function toolPairingBalancedAfter(session, seq): boolean {
  return cutBalance(balanceCache(session), seq, 1)  // seq 之后的切点
}
```

**与 OpenClaw 对比**：

| 维度 | OpenClaw | DeepSeek-Harness |
|:---|:---|:---|
| 保护粒度 | 按消息分组（pendingToolCalls 队列） | 按 surface 切点（N+1 个 cut） |
| 缓存策略 | 每次重新分组 | **增量缓存**（按 surface generation） |
| 检查时机 | 压缩分组时 | 区域选择 + 压缩提交前双重校验 |
| 平衡定义 | 队列空 | inProgressToolCalls === 0 |

### 6.4 压缩事务生命周期

```
Compaction Transaction（事务性压缩）：

  compaction/start（获取锁，log-only）
       │
       ▼
  ┌──────────────────────────────────────┐
  │ 1. validateSurfaceRegion             │  验证范围 + tool-pairing 平衡
  │ 2. prepareCompaction                 │  快照定价 + 摘要输入
  │ 3. summarizeCompaction（LLM 摘要）    │  ⭐ 异步，surface 可能变化
  │ 4. assertStable（稳定性校验）          │  防止压缩期间 surface 变了
  │ 5. commitCompactionBody              │  同步提交（无 yield）
  │    ├─ append compaction/summary      │  摘要 + 元数据（provider/model/usage）
  │    └─ append user/message            │  surface replace 操作
  └──────────────┬───────────────────────┘
                 │
                 ▼
  compaction/end（释放锁，记录成功/失败）
```

**关键设计**：
1. **锁机制**：`compaction/start` 是日志锁，未闭合的 start 可检测 busy
2. **稳定性校验**：摘要异步生成期间 surface 可能变化，提交前必须重新校验
3. **同步提交**：`commitCompactionBody` 不 yield，summary + replacement 原子追加
4. **KV Cache 优化**：摘要输入复用 conversation prefix（system prompt + tools + 区域消息），是真实请求的前缀，复用 provider KV cache

### 6.5 Shadow Price 协议

```
压缩替换的定价协议：
  compaction/summary（metering event，记录被替换内容的 token 价）
       │ 紧接其后
       ▼
  user/message（surface replace 操作）

消费者只需读 metering event 就能减去被替换内容的 token 计数，
不需要保留每个 surface 节点的价格。
```

## 七、RuntimeContextProjection：动态上下文投影

### 7.1 设计

dsh 的动态上下文（如当前工作目录、git 状态、运行时信息）不是每轮都注入，而是**只在变化时注入**：

```typescript
// packages/core/agent-loop/src/runtime-context.ts
class RuntimeContextProjection {
  private retained: { seq: number; text: string | undefined } | null | undefined

  project(current: string, sections: ContextSnapshotSection[]): UserMessage | undefined {
    // 首次 + 当前为空 → 不注入
    if (this.retained === undefined && current.length === 0) return
    const snapshot = current.length === 0 ? CLEARED : current
    // 与上次相同 → 不注入（避免冗余）
    if (this.retained?.text === snapshot) return
    // 变化了 → 生成新的 user message 注入
    return createUserMessage({
      content: [{ type: 'text', text: snapshot }],
      source: { kind: 'plugin', plugin: SOURCE, form: 'snapshot', sections },
    })
  }
}
```

### 7.2 恢复机制

```typescript
// 构造时从 session log 恢复投影状态
constructor(ctx: Context, session: Session) {
  const surface = new Set(session.surface.nodes)
  for (let i = session.events.length - 1; i >= 0; i--) {
    const event = session.events[i]
    // 找到最后一个属于 system-prompt 的 user/message
    if (event?.type !== 'user/message' || !isOwned(event.data)) continue
    this.retained ??= null
    if (surface.has(event.seq)) {  // 且在当前 surface 上
      this.retained = { seq: event.seq, text: textOf(event.data) }
      break
    }
  }
  // 监听 session event 实时跟踪
  ctx.on('session/event', ...)
}
```

**设计意义**：动态上下文变化频率低，每轮注入浪费 token。只在变化时注入 + 从 log 恢复状态，既省 token 又可持久化。

## 十、面试高频问答

**Q1：DeepSeek-Harness 的核心设计原则是什么？**

A：两个核心原则：
1. **Everything is a plugin**：基于 Cordis 插件架构，包括 Agent Loop、LLM 适配器、会话日志都可从配置替换。没有特权核心。
2. **Model-visible ⟺ Logged**：任何到达模型请求的内容必须能从 session log 重建。运行时有 Request-Reconstruction Invariant 强制断言。

**Q2：什么是 Surface 模型？压缩为什么基于 Surface 而不是原始消息？**

A：Surface 是 session log 的当前可见节点序列。压缩是改变 surface 的投影（replace 操作），不是物理删除 log。好处：(1) fork/resume/replay 可从 log 重建任意历史 surface；(2) 压缩是逻辑操作，可回滚；(3) 多个压缩操作的叠加可预测。

**Q3：工具调用对保护为什么要用增量 BalanceCache？**

A：压缩需要频繁检查 surface 切点是否平衡。每次重新 fold 整个 surface 成本 O(n)。增量 BalanceCache 按 surface generation 缓存，只 fold 新增节点，均摊 O(1)。当 surface 重写（generation 变化）时才全量重建。

**Q4：Request-Reconstruction Invariant 解决什么问题？**

A：防止插件在消息组装后、LLM 调用前偷偷篡改内容。每次 `llm/stream` 事件触发时，dsh 会验证 `options.messages === session.deriveMessages()`，且配置与 request header 匹配。不匹配则 fail。这是安全红线 + 可重放性保证。

**Q5：能力缝（Capability Seam）的三角色是什么？**

A：Service Definition（声明接口）+ Service Provider（实现）+ Consumer（使用，通常是模型可见工具）。一个能力缝必须包含三个角色。好处：切换 Provider 不需要改 Consumer，比如把 fs 从本地换成远程沙箱，所有 read/write 工具自动切换。

## 十一、易错点

1. **混淆 log 和 surface**：log 是完整历史（不可变），surface 是当前可见投影（可变）。压缩改 surface 不改 log。
2. **压缩不在平衡切点切**：会拆断 tool-call/result 对，provider 返回 400。dsh 用 `toolPairingBalancedBefore/After` 双重校验。
3. **压缩期间 surface 变化**：摘要异步生成时 surface 可能被其他操作改变。提交前必须 `assertStable` 重新校验，否则用旧摘要替换了新内容。
4. **跳过 Request-Reconstruction Invariant**：任何绕过 invariant 的路径（直接调 adapter）都破坏可重放性和安全性。所有模型可见输入必须走 session event。
5. **Waterfall 不调 next()**：`agent/pre-step` 等 waterfall 监听器必须调用 `next()` 委托，不调用会短路整个链条。
