## 经验 1：日志优先——Log as Source of Truth

### 问题描述

Agent 的上下文管理面临一个根本问题：**模型看到的消息序列从哪里来？**
- 如果从内存状态来 → 进程崩溃就丢失、无法重放、无法分支
- 如果从外部存储来 → 需要额外同步、可能不一致

### dsh 方案

dsh 的答案是：**Session Event Log 是唯一事实源，模型可见消息必须从 log 派生。**

```typescript
// 铁律：Model-visible ⟺ Logged
// 任何到达模型请求的内容，必须能从 session log 重建
// 一个新的模型可见输入，必须对应一个新的 session event

// agent-loop 每次请求都从 log deriveMessages()
const messages = session.deriveMessages()  // 从事件日志投影
```

**关键设计**：
- Log 是 append-only 的不可变事件流
- `deriveMessages()` 是纯投影函数（相同 log → 相同消息）
- UI、fork、resume、replay 都从同一 log 派生

### 可复用模式：Event Sourcing + Projection

```
Event Log（append-only，不可变）
    │
    ├─ deriveMessages() → Model Request  ← 上下文来源
    ├─ renderUI() → Chat UI               ← 展示来源
    ├─ fork() → 子会话分支                 ← 分支来源
    └─ replay() → 确定性重放               ← 调试来源

所有消费者从同一 log 投影，杜绝多源不一致。
```

### 理论提炼

对应 **Event Sourcing（事件溯源）** 模式 + **CQRS（命令查询职责分离）**。上下文不是存储的数据，而是事件流的投影。**适用边界**：当系统需要可重放、可分支、可审计时，事件溯源是最优解；如果只是简单的单轮对话持久化，过度设计反而增加复杂度。

## 经验 2：运行时不变量断言——Request-Reconstruction Invariant

### 问题描述

即使设计了日志优先，仍有插件可能在消息组装后、LLM 调用前偷偷篡改内容。如何**运行时强制**模型请求与日志一致？

### dsh 方案

dsh 用**运行时不变量（Runtime Invariant）**在每次 LLM 调用前断言一致性：

```typescript
// packages/core/agent-loop/src/invariant.ts
ctx.on('llm/stream', (options: GenerateOptions, next) => {
  if (!isAgentLoopRequest(options)) return next()
  
  // 1. 请求必须 frozen（不可变）
  if (!Object.isFrozen(options)) fail('a loop-built request must be frozen')
  
  // 2. 必须带 sessionId
  if (options.sessionId === undefined) fail('must carry a session id')
  
  // 3. messages 必须从 session log 派生（核心断言）
  const expected = session.deriveMessages()
  if (JSON.stringify(options.messages) !== JSON.stringify(expected)) {
    fail(`llm request diverges from durable derivation (log-reconstruction desync)`)
  }
  
  // 4. 配置必须与 request header 匹配
  const headerMatches = options.model === header.config.model
    && JSON.stringify(options.tools ?? []) === JSON.stringify(header.tools ?? [])
  if (!headerMatches) fail(`llm request diverges from folded request header`)
  
  return next()
})
```

**设计亮点**：
- Invariant 通过 `ctx.invariants.register()` 注册，是插件化的
- `prepend: true` 保证在其他监听器之前执行，防止短路
- 失败时调用 `fail()` 直接中断，不只是告警

### 可复用模式：运行时不变量 + 断言驱动

```
正常路径：assemble → freeze → llm/stream → invariant 检查 → 发请求
违规路径：assemble → freeze → llm/stream → invariant 失败 → fail() 中断
```

### 理论提炼

对应 Design by Contract 的 **运行时断言** + **fail-fast** 原则。不变量不是文档约定，而是代码强制。**适用边界**：任何安全关键或一致性关键的操作，都应在边界处设置运行时断言；断言失败必须中断，不能仅告警。

## 经验 3：Surface 投影模型——压缩是改变可见性，不是删除

### 问题描述

压缩历史时，如果直接删除旧消息会丢失信息（无法恢复）；如果保留所有消息又浪费 token。如何两全？

### dsh 方案

dsh 区分 **Log（完整历史）** 和 **Surface（当前可见投影）**：

```
Session Event Log（完整历史，不可变，永不删除）：
  [seq0, seq1, seq2, seq3, seq4, seq5, seq6, seq7, seq8, seq9]
                          │
                          │ surfaceOp: replace [seq0, seq4]
                          ▼
Surface（当前模型可见的节点序列，可变投影）：
  [new_summary, seq5, seq6, seq7, seq8, seq9]

压缩 = 改变 surface 的投影操作，不是物理删除 log
```

**关键设计**：
- 压缩操作记录在 log 中（`compaction/start` → `compaction/summary` → `compaction/end`）
- Surface 有 `replaceGeneration` 代际标识，每次重写递增
- 从 log 可重建任意历史 surface 状态

### 可复用模式：不可变源 + 可变投影

```
Immutable Source（Log，永不修改/删除）
    │
    │ projection rules（compaction ops, surface ops）
    ▼
Mutable View（Surface，当前可见）
    │
    ├─ deriveMessages() → 模型请求
    ├─ renderUI() → 界面展示
    └─ fork(boundary) → 分支会话
```

### 理论提炼

对应数据库的 **MVCC（多版本并发控制）** 模式 + **事件溯源投影**。源数据不可变，视图可变。**适用边界**：任何需要「删除旧数据但保留恢复能力」的场景（压缩/软删除/版本回滚），投影模型都优于物理删除。

## 经验 4：增量平衡缓存——工具调用对保护的 O(1) 均摊

### 问题描述

压缩需要频繁检查 surface 切点是否在工具调用对之间（平衡切点）。每次从头 fold 整个 surface 是 O(n)，高频检查成本太高。

### dsh 方案

dsh 用 **按 surface generation 缓存的增量 BalanceCache**：

```typescript
// packages/compaction/compaction/src/tool-pairing.ts
interface BalanceCache {
  generation: number           // surface 重写代际
  cutBalanced: boolean[]      // N+1 个切点的平衡状态（0=不平衡，1=平衡）
  indexBySeq: Map<number, number>  // seq → 切点索引
  inProgressToolCalls: number      // 当前未完成的工具调用数
}

// 增量扩展：只 fold 新增的 surface 节点
function extendCache(session, cache, seqs): BalanceCache {
  const tail = seqs.slice(processed)  // 只处理新增部分
  let inProgressToolCalls = cache.inProgressToolCalls
  for (const seq of tail) {
    inProgressToolCalls += eventDelta(event)  // tool-call +1, tool-result -1
    pendingCuts.push(inProgressToolCalls === 0)  // 0 = 平衡切点
  }
  // ...更新缓存
}

// 检查切点平衡 — O(1)
function toolPairingBalancedBefore(session, seq): boolean {
  return cutBalance(balanceCache(session), seq, 0)
}
```

**代际失效**：当 surface 重写（`replaceGeneration` 变化），缓存全量重建；否则只增量扩展。

### 可复用模式：代际感知的增量缓存

```
读路径：cache 有效 → O(1) 查切点平衡
写路径：新增节点 → O(新增量) fold → 更新缓存
失效：generation 变化 → 全量重建 O(n)

均摊 O(1)，最坏 O(n) 但低频。
```

### 理论提炼

对应 **Incremental Computation（增量计算）** 模式 + **Generation-based Invalidation（代际失效）**。缓存绑定到数据的代际，数据变化时精确失效。**适用边界**：任何需要对序列数据做重复查询的场景（平衡检查/前缀和/窗口统计），增量缓存都能显著降低成本。

## 经验 5：Change-Only Injection——动态上下文只在变化时注入

### 问题描述

动态上下文（如当前工作目录、git 状态、运行时信息）如果每轮都注入，既浪费 token 又增加干扰。但如果不注入，模型又缺少环境感知。

### dsh 方案

dsh 的 `RuntimeContextProjection` 只在动态上下文**变化时**才注入，且能从 log 恢复状态：

```typescript
// packages/core/agent-loop/src/runtime-context.ts
class RuntimeContextProjection {
  private retained: { seq: number; text: string | undefined } | null | undefined

  project(current: string, sections: ContextSnapshotSection[]): UserMessage | undefined {
    // 首次 + 当前为空 → 不注入
    if (this.retained === undefined && current.length === 0) return
    const snapshot = current.length === 0 ? CLEARED : current
    // ⭐ 与上次相同 → 不注入（避免冗余）
    if (this.retained?.text === snapshot) return
    // 变化了 → 生成新的 user message 注入
    return createUserMessage({ content: [{ type: 'text', text: snapshot }] })
  }
}
```

**恢复机制**：构造时从 session log 倒序找最后一个属于 system-prompt 的 user/message，恢复 `retained` 状态。

### 可复用模式：状态投影 + 差量注入

```
每轮流程：
  1. 计算当前动态上下文 current
  2. 与 retained（上次注入的）对比
  3. 相同 → 跳过（节省 token）
  4. 不同 → 注入新快照 + 更新 retained

持久化：retained 状态从 session log 恢复（不单独存）
```

### 理论提炼

对应 **Change Data Capture（CDC）** 模式 + **差量同步**。只传输变化的数据，不变的部分不重复注入。**适用边界**：任何有状态的上下文注入（环境信息/用户偏好/系统状态），变化频率低且对比成本低时，差量注入能显著节省 token。

## 经验 6：KV Cache 前缀复用——摘要即真实请求前缀

### 问题描述

摘要压缩需要调用 LLM 生成摘要。如果用独立的 system prompt + 独立的对话内容，会导致 provider 的 KV cache 完全不命中，成本高、速度慢。

### dsh 方案

dsh 让摘要请求**复用真实对话的前缀**——system prompt + tools + 对话区域原样放在前面，压缩指令作为最后一条 user message：

```typescript
// packages/compaction/compaction-basic/src/summarizer.ts
const messages: Message[] = [
  ...input.messages,           // 真实对话区域（原样）
  createUserMessage({          // 压缩指令作为最后一条
    content: [{ type: 'text', text: COMPACTION_INSTRUCTION }],
    source: { kind: 'plugin', plugin: 'dsh-compaction-basic' },
  }),
]
const options: GenerateOptions = {
  ...input.system === undefined ? {} : { system: input.system },  // 复用真实 system
  ...input.tools === undefined ? {} : { tools: [...input.tools] }, // 复用真实 tools
  messages,
  purpose: 'compaction',
}
```

**关键注释**：
> Keeping the conversation's own system prompt, tools, and message prefix in front of it makes the auxiliary call a genuine prefix of the last routed request, so the provider's KV cache is reused instead of invalidated.

### 可复用模式：Cache-Aware Prompt Construction

```
传统摘要请求：[system: 你是摘要器] + [摘要内容] → KV cache 不命中
dsh 摘要请求：[真实 system] + [真实 tools] + [真实对话] + [压缩指令]
             ↑ 与真实请求的前缀完全一致 ↑ → KV cache 命中
```

### 理论提炼

对应 **Prefix Caching（前缀缓存优化）** 模式。Provider 的 KV cache 按 prompt 前缀匹配，让辅助调用的前缀与主调用一致就能复用缓存。**适用边界**：任何在主请求旁边发起的辅助 LLM 调用（摘要/评判/改写），都应尽量复用主请求的前缀以降低成本。

## 经验 7：结构化摘要 + 标识符保持 + 历史合并

### 问题描述

摘要如果让 LLM 自由发挥，会出现：格式不可控、丢失关键信息、改写标识符、多次摘要后信息漂移。

### dsh 方案

dsh 的压缩指令强制**固定 8 段结构 + MUST PRESERVE 规则 + 历史合并**：

```typescript
// packages/compaction/compaction-basic/src/summarizer.ts
const COMPACTION_INSTRUCTION = [
  'You are now acting as a compaction engine...',
  'Output EXACTLY the Markdown structure below: keep every section, in order.',
  '',
  '## Primary Request and Intent',     // 用户原始目标
  '## Key Technical Concepts',         // 技术栈
  '## Files and Code',                 // 文件路径 + 变更
  '## Errors and Fixes',               // 错误 + 修复
  '## Pending Jobs',                   // 未完成工作
  '## Current Work',                   // 当前进度
  '## Next Step',                      // 下一步
  '## Critical Context',               // 决策 + 约束
  '',
  'Rules:',
  '- Preserve exact file paths, commands, error strings, identifiers...',
  `- If the conversation already contains a ${SUMMARY_OPEN_TAG} block, it is a PRIOR checkpoint.`,
  '  Do not copy it forward verbatim: preserve still-true facts, drop stale ones, and merge.',
].join('\n')
```

**Checkpoint Framing**：摘要替换原消息时加 preamble + tags，让模型知道这是自动生成的检查点：

```
This is an automatically generated checkpoint condensing an earlier span...
Treat the captured context as established background and build on it without restating it.

<compacted-summary>
  ## Primary Request and Intent
  ...
</compacted-summary>
```

### 可复用模式：Constrained Summarization + Checkpoint Framing

```
摘要输入：[真实对话] + [压缩指令]
              │
              ▼
LLM 输出：严格 8 段 Markdown + 标识符保持 + 历史合并
              │
              ▼
Checkpoint Framing：preamble + tags + 摘要内容 → 注入为 user message
```

### 理论提炼

对应 **结构化输出约束（Structured Output Constraint）** + **Checkpoint 模式**。摘要不是自由文本，而是有 schema 的检查点。**适用边界**：任何需要 LLM 摘要的场景，固定结构 + 标识符保持 + 历史合并能显著提升摘要质量和可控性。

## 经验 8：压缩事务 + 稳定性校验 + 同步提交

### 问题描述

压缩是多步异步操作（选择范围 → 定价 → LLM 摘要 → 替换 surface）。任何一步失败或期间 surface 变化，都可能导致数据不一致。

### dsh 方案

dsh 把压缩实现为**完整事务**，有锁、有稳定性校验、同步提交：

```typescript
// packages/compaction/compaction-basic/src/region.ts
async function compactSurfaceRegion(...): Promise<CompactionResult> {
  // 1. 验证范围 + 工具调用对平衡
  const selection = validateSurfaceRegion(session, start, end)
  
  // 2. 获取压缩锁（compaction/start 是日志锁）
  session.append('compaction/start', lifecycle)
  
  try {
    // 3. 快照定价 + 摘要输入
    const prepared = prepareCompaction(dependencies, session, selection)
    
    // 4. 异步 LLM 摘要（surface 可能在此期间变化）
    const summarized = await summarizeCompaction(...)
    
    // ⭐ 5. 稳定性校验：摘要期间 surface 没变才能提交
    assertStable(dependencies, session, summarized)
    
    // 6. 同步提交（不 yield，原子追加 summary + replacement）
    stage = 'commit'
    const pending = commitCompactionBody(session, startEvent, summarized)
    const endEvent = session.append('compaction/end', lifecycle)
  } catch (error) {
    // 7. 失败也必须闭合事务（compaction/end with error）
    session.append('compaction/end', { ...lifecycle, error: errorChain(error) })
  }
}
```

**双重稳定性校验**：
- `assertWholeSurfaceUnchanged`：整个 surface 没变（manual 模式）
- `assertSelectedSpanStable`：只校验被压缩的区域没变（auto 模式，允许区域外变化）

### 可复用模式：异步事务 + 乐观锁 + 稳定校验

```
事务生命周期：
  START（锁）→ PREPARE（快照）→ ASYNC WORK（摘要）→ VALIDATE（稳定校验）
                                                    │
                                          ┌──────────┴──────────┐
                                          ▼                     ▼
                                    稳定 → COMMIT          不稳定 → ABORT
                                    （同步提交）            （丢弃，不更新）
```

### 理论提炼

对应数据库的 **Optimistic Concurrency Control（乐观并发控制）** + **两阶段提交（2PC）** 的简化版。异步工作后校验状态是否变化，变化则放弃。**适用边界**：任何「先读数据 → 异步处理 → 写回」的操作（缓存更新/索引重建/批处理），都应加稳定性校验。

## 经验 9：分层配置 + 模型级策略覆盖

### 问题描述

不同模型的上下文窗口差异巨大（4K vs 200K），压缩阈值和保留策略不能一刀切。如何设计可扩展的配置？

### dsh 方案

dsh 用**全局默认 + 模型级精确覆盖 + 运行时解析**的三层配置：

```typescript
// packages/compaction/compaction-basic/src/config.ts

// 1. 全局默认
const DEFAULT_THRESHOLD_RATIO = 0.8   // 80% 触发压缩
const DEFAULT_RETAIN_RATIO = 0.16    // 保留 16% 近期原文

// 2. 模型级覆盖（精确匹配 provider/model）
const modelPolicies = [
  { provider: 'deepseek', model: 'deepseek-chat', thresholdRatio: 0.75 },
  { provider: 'openai', model: 'gpt-4o', thresholdRatio: 0.85, retainTokens: 8000 },
]

// 3. 运行时解析为具体 token 预算
function resolveCompactSpec(policy, contextWindow): ResolvedCompactSpec {
  const thresholdTokens = Math.floor(contextWindow * policy.thresholdRatio)
  const retainTokens = policy.retainTokens ?? Math.floor(contextWindow * policy.retainRatio)
  return deepFreeze({ thresholdTokens, retainTokens, ... })
}
```

**加载时校验**（fail loud）：
- 未知 key 报错（防止拼写错误）
- retainRatio < thresholdRatio（否则压缩后比阈值还大）
- retainRatio 和 retainTokens 互斥
- summarizationProvider 和 summarizationModel 必须成对

### 可复用模式：分层配置 + 运行时解析 + 加载时校验

```
配置层级：
  全局默认（DEFAULT_*）→ 模型级覆盖（modelPolicies）→ 运行时解析（resolveCompactSpec）
                              │
                              └─ 精确匹配 provider/model

校验时机：load-time（fail loud，不静默跳过）
不可变：resolve 后 deepFreeze（防止运行时篡改）
```

### 理论提炼

对应 **Configuration Override Chain（配置覆盖链）** 模式 + **Fail-Loud Configuration Validation**。**适用边界**：任何需要按环境/模型/租户差异化配置的场景，分层覆盖 + 加载时校验比运行时 fallback 更安全。

## 经验 10：Waterfall 事件语义 + 显式扩展点

### 问题描述

Agent Loop 需要支持插件在不同阶段介入（pre-step 改写、pre-tool 鉴权、post-llm 校验）。如何设计既能拦截又能委托的扩展机制？

### dsh 方案

dsh 用 **Waterfall 事件**——监听器必须调用 `next()` 委托下一个监听器，不调用则短路链条：

```typescript
// Turn Flow 中的 waterfall 事件：
agent/pre-step      // 可拒绝/改写输入
agent/request       // 可修改请求配置
llm/stream          // 可拦截/修改 LLM 流
tools/pre-execute   // 可鉴权/改写工具参数
tools/post-execute  // 可过滤/记录结果

// Waterfall 语义：
ctx.on('agent/pre-step', (input, next) => {
  if (shouldReject(input)) return reject()  // 短路，不调 next()
  const modified = transform(input)
  return next(modified)  // 委托下一个
})
```

**扩展点映射**（源码架构文档）：

| 目标 | 机制 |
|:---|:---|
| 加模型 provider | 注册 adapter 到 `ctx.llm` |
| 加工具 | 注册到 `ctx.tools`，schema 自动加入 prompt |
| 拦截请求/工具/turn | 用 `agent/*` 或 `tools/*` 事件 |
| 加模型可见上下文 | `agent.inject()` 注入下一轮 |
| 加持久化状态 | 扩展 `SessionEventMap` |

### 理论提炼

对应 **Chain of Responsibility（责任链）** 模式 + **Middleware Pipeline（中间件管道）**。Waterfall 比普通事件更强大——可以拦截、改写、短路、委托。**适用边界**：任何需要多阶段可拦截的请求处理流水线（HTTP 中间件/Agent Loop/工具执行），Waterfall 语义是最佳实践。

## 面试高频问答

**Q1：dsh 的 "Model-visible ⟺ Logged" 原则解决什么问题？**

A：解决多源不一致和安全问题。所有到达模型的内容必须能从 session log 重建，运行时有 Request-Reconstruction Invariant 强制断言。好处：(1) 可重放/可分支/可审计；(2) 防止插件在消息发送后偷偷篡改；(3) UI 和模型请求从同一源派生，不会出现「界面显示的和模型看到的不一样」。

**Q2：Surface 模型和直接删消息压缩有什么区别？**

A：Surface 是 log 的投影，压缩改变投影（replace 操作），不物理删除 log。区别：(1) 可恢复——从 log 重建任意历史 surface；(2) 可分支——fork 时选择任意边界；(3) 可重放——replay 不依赖当时的 surface 状态。直接删消息则永久丢失。

**Q3：dsh 怎么保证压缩的原子性和一致性？**

A：三层保障：(1) **事务锁**——`compaction/start` 获取日志锁，未闭合的 start 可检测 busy；(2) **稳定性校验**——摘要异步生成后，提交前重新校验 surface 是否变化，变了则放弃；(3) **同步提交**——summary + replacement 原子追加，不 yield。失败也必须闭合事务（`compaction/end` with error）。

**Q4：KV Cache 前缀复用是怎么实现的？**

A：摘要请求的 system prompt + tools + 对话区域与真实请求完全一致，压缩指令作为最后一条 user message。这样 provider 的 KV cache 命中真实请求的前缀，只有压缩指令是新输入。比独立 system prompt 的摘要请求成本低得多。

**Q5：dsh 的压缩配置为什么要分层 + 加载时校验？**

A：不同模型上下文窗口差异大，需要全局默认 + 模型级精确覆盖。加载时校验（fail loud）防止拼写错误、逻辑矛盾（retain >= threshold）、互斥字段同时设置。resolve 后 deepFreeze 防止运行时篡改。比运行时 fallback 更安全可预测。
