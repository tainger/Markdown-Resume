# OpenClaw 技术架构与 AI Agent 技术解析

> OpenClaw 是 2025 年底爆火的开源个人 AI Agent 运行时（GitHub 145k+ stars，MIT 协议，TypeScript），它不是给开发者构建 Agent 的框架，而是**Agent 本身**——本地运行的后台服务，连接 WhatsApp/Telegram/Discord/Slack 等 20+ 渠道，7×24 小时自动执行任务。
> 本文解析 OpenClaw 用到的 AI Agent 技术，并与本仓库 [AgentMate 项目](../../简历/resume.md#L61-L81) 对比，提炼可复用的工程经验。

---

## 一、OpenClaw 是什么

### 1.1 定位

```
传统 AI 聊天机器人：
  浏览器打开网页 → 手动输入 → 获得回答 → 关闭页面 → 结束

OpenClaw：
  后台服务常驻运行 → 监听消息渠道 → 自动响应 → 自动执行工具 → 持久记忆 → 永不停止
```

**核心理念**：从「云端 AI 对话」向「本地 AI 行动」的范式转变。

| 维度 | 传统 AI 助手 | OpenClaw |
|:---|:---|:---|
| 运行方式 | 浏览器/SaaS | 本地后台服务 |
| 交互方式 | 主动打开网页 | 消息渠道自动推送 |
| 数据位置 | 云端 | 本地优先（Local-First） |
| 执行能力 | 仅文本生成 | 工具执行 + 自动化任务 |
| 记忆 | 单会话 | 跨会话持久记忆 |
| 定义方式 | 写代码/调 API | 写 Markdown 配置（SOUL.md） |

### 1.2 两个核心配置文件

OpenClaw 的 Agent 定义是**配置优先**的，不用写代码：

```markdown
# SOUL.md（Agent 的人格、规则、行为）
你是一个软件团队的项目经理。
你每天早上通过 Slack 检查团队状态。
你跟踪阻塞问题并向团队负责人汇报。
未经人工确认，你不会批准预算变更。

# AGENTS.md（多 Agent 定义，可选）
## Agent: research-bot
你负责市场调研，使用 search 工具收集竞品信息。
## Agent: code-bot
你负责代码审查，使用 git diff 工具分析变更。
```

> **设计哲学**：Agent 行为是配置，不是代码。改行为只需编辑 Markdown，重新对话即生效，无需重新编译部署。

### 2.2 完整消息流

```
入站消息处理：
  Channel SDK（Baileys/Grammy/Carbon 等）
    → Channel Monitor（渠道监控）
    → Inbound Debouncer（消息防抖，批量处理快速连续消息）
    → Allowlist Check（白名单检查）
    → Mention/Command Gating（@提及/命令门控）
    → Message Deduplication（LRU 去重）
    → Route Resolution（路由解析：哪个 Agent 处理）
    → Session Key Construction（会话键构建）

Agent 处理：
  Session Manager（加载/创建会话）
    → Pi Embedded Runner（Agent 执行器）
    → System Prompt Construction（SOUL.md → System Prompt）
    → Model Selection + Failover（选模型）
    → Tool Registration + Policy（注册工具）
    → LLM API 调用（anthropic/openai/google/deepseek）
    → Tool Execution Loop（工具执行循环 = Agentic Loop）
    → Response Streaming（流式响应）

出站投递：
  Block Stream Coalescer（流式块合并）
    → Message Chunking（消息分块，避免超长）
    → Markdown Formatting（格式化）
    → Outbound Delivery（投递）
    → Channel Send Adapter（渠道发送适配）
    → Gateway Broadcast（WebSocket 广播到所有客户端）
```

## 三、核心 AI Agent 技术

### 3.1 Agentic Loop（ReAct 工具调用循环）

OpenClaw 的核心是 **Agentic Loop**——LLM 自主决定调用工具、观察结果、继续推理的循环：

```
Agentic Loop（ReAct 模式）：

  ┌──────────┐
  │  用户消息 │
  └────┬─────┘
       ▼
  ┌─────────────────┐     否
  │ LLM 是否需要工具?│─────────→ 直接生成响应
  └────────┬────────┘
           │ 是
           ▼
  ┌─────────────────┐
  │ 选择工具 + 参数  │
  └────────┬────────┘
           ▼
  ┌─────────────────┐
  │ 工具执行 + 结果  │
  └────────┬────────┘
           ▼
  ┌─────────────────┐     否
  │ 结果是否满足需求?│─────────→ 回到 LLM 推理（带上工具结果）
  └────────┬────────┘
           │ 是
           ▼
  ┌─────────────────┐
  │ 生成最终响应     │
  └─────────────────┘
```

**关键技术点**：
- 工具调用采用 **JSON Schema** 定义（函数名 + 参数类型 + 描述）
- 支持**多工具并行调用**（一次 LLM 输出多个 tool_call）
- 工具结果注入回对话历史，LLM 基于结果继续推理
- 循环有**最大步数限制**（防止无限循环）+ **超时熔断**

**与 AgentMate 对比**：
- OpenClaw：对话入口保留 ReAct 循环（自由探索）
- AgentMate：对话入口保留 ReAct，执行链路（AutoDev）用过程式状态机（可控性优先）

### 3.2 LLM Provider 抽象层（模型无关）

OpenClaw 是**模型无关**的，通过统一接口抽象不同 LLM 提供商：

| 提供商 | 定位 | 特点 |
|:---|:---|:---|
| Anthropic Claude | 默认首选 | 优化 Agentic 任务，长上下文 |
| OpenAI GPT-4o+ | 全支持 | 生态成熟，工具调用稳定 |
| Google Gemini | 全支持 | 多模态能力强 |
| DeepSeek | 中国社区适配 | 性价比高，中文好 |
| Ollama | 本地部署 | 完全离线，隐私优先 |

```
统一抽象接口：
  interface LLMProvider {
    chat(messages: Message[], tools?: Tool[]): ChatResponse
    stream(messages: Message[], tools?: Tool[]): AsyncStream<Chunk>
    embed(text: string): number[]
  }

  实现：AnthropicProvider | OpenAIProvider | DeepSeekProvider | OllamaProvider
```

**Model Selection + Failover**：支持主备模型自动切换（如 Claude 限流时自动切到 GPT-4o）。

### 3.4 Session Manager（持久会话管理）

OpenClaw 的 Session Manager 管理跨会话的持久上下文：

```
Session 层级：

├─ Channel Session（渠道会话）
│   └─ 每个渠道（WhatsApp/Telegram）的消息历史
│
├─ Agent Session（Agent 会话）
│   └─ 每个 Agent 的对话上下文（可跨渠道）
│
├─ User Session（用户会话）
│   └─ 用户级偏好设置（长期记忆）
│
└─ Memory Store（记忆存储）
    ├─ 短期记忆（当前对话 context window）
    ├─ 中期记忆（会话历史，可摘要压缩）
    └─ 长期记忆（用户偏好、事实、知识）
```

**上下文管理策略**（与 [2.5 上下文工程](../2.5%20上下文工程.md) 一致）：
- 超过 token 预算时**滚动摘要**（旧对话压缩成摘要）
- 关键事实提取到**结构化记忆**（不保留原文）
- 按相关性召回历史对话注入当前 context

### 3.5 Hooks System（生命周期钩子）

类似 AgentMate 的 pre/do/post 三态 Hook，OpenClaw 也有钩子系统：

```
Hook 类型：
  ├─ pre-message：消息到达时（可拦截/修改）
  ├─ pre-llm：LLM 调用前（可修改 prompt）
  ├─ post-llm：LLM 调用后（可校验输出）
  ├─ pre-tool：工具执行前（可鉴权/审计）
  ├─ post-tool：工具执行后（可过滤结果）
  └─ post-message：消息发送后（可记录/通知）
```

**安全策略**：工具执行前可以通过 Hook 做权限检查（如危险操作需要人工确认）。

### 3.6 多 Agent 协作（AGENTS.md）

OpenClaw 通过 AGENTS.md 支持多 Agent：

```markdown
# AGENTS.md
## Agent: researcher
角色：市场研究员
工具：search, web_fetch
## Agent: analyst
角色：数据分析师
工具：python_exec, chart_gen
## Agent: writer
角色：报告撰写
工具：markdown_render, email_send
```

**路由策略**：
- 关键词路由（包含"调研"→researcher）
- Mention 路由（@researcher → 直接指定）
- 默认路由（无法判断→默认 Agent）

**与 AgentMate 对比**：
- OpenClaw：多 Agent 是配置式的（Markdown 定义），路由是简单关键词匹配
- AgentMate：多 Agent 是过程式的（AutoDev 五阶段状态机），每个 Agent 有明确的输入输出契约

### 3.7 上下文工程（Context Engineering）

> 基于 OpenClaw 源码 `src/context-engine/` + `src/agents/compaction-*.ts` 的深度解析。这是 OpenClaw 最硬核的工程模块，也是与本仓库 [2.5 上下文工程](../2.5%20上下文工程.md) 笔记最直接的对照。

#### 3.7.1 核心设计：可插拔 ContextEngine 接口

OpenClaw 把上下文管理抽象成一个**插件接口**（而非硬编码策略），第三方可以实现自己的 ContextEngine 替换默认实现：

```typescript
// src/context-engine/types.ts — ContextEngine 接口（简化）
interface ContextEngine {
  readonly info: ContextEngineInfo;

  // 生命周期
  bootstrap?(params: {...}): Promise<BootstrapResult>;     // 会话初始化
  ingest(params: {...}): Promise<IngestResult>;            // 摄入单条消息
  ingestBatch?(params: {...}): Promise<IngestBatchResult>; // 批量摄入
  assemble(params: {...}): Promise<AssembleResult>;        // ⭐ 组装模型上下文
  compact(params: {...}): Promise<CompactResult>;           // ⭐ 压缩历史
  afterTurn?(params: {...}): Promise<void>;                 // 每轮结束后
  maintain?(params: {...}): Promise<...>;                   // 维护（清理/重写）
  dispose?(): Promise<void>;                                // 释放资源
}
```

**设计亮点**：`assemble()` 是核心方法——在 token 预算内返回有序的模型可见消息列表，引擎可以自由实现召回/压缩/排序策略。

```
ContextEngine 生命周期：

  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ bootstrap│────▶│  ingest  │────▶│ assemble │
  │ 初始化会话 │     │ 摄入消息  │     │ 组装上下文 │
  └──────────┘     └────┬─────┘     └────┬─────┘
                         │                │
                    持续摄入          返回模型可见消息
                         │                │
                         ▼                ▼
                   ┌──────────┐     ┌──────────┐
                   │ afterTurn│────▶│ compact  │
                   │ 轮后处理  │     │ 超预算压缩 │
                   └──────────┘     └──────────┘
                         │                │
                         └────────┬───────┘
                                  ▼
                           ┌──────────┐
                           │ maintain │
                           │ 维护清理  │
                           └──────────┘
```

#### 3.7.2 Context Window Guard：预算解析 + 安全阈值

OpenClaw 不会盲目发送消息，每次调用前都会**解析模型上下文窗口**并做安全检查：

```typescript
// src/agents/context-window-guard.ts — 预算解析优先级
resolveContextWindowInfo({ cfg, provider, modelId, ... }):
  1. modelsConfig 中显式配置的 contextTokens（最高优先级）
  2. 模型元数据 modelContextTokens / modelContextWindow
  3. 默认值 8000 tokens
```

**三级安全阈值**：

| 阈值 | 计算方式 | 行为 |
|:---|:---|:---|
| Hard Min | max(4000, 上下文窗口 × 10%) | 低于此值**阻断运行** |
| Warn Below | max(8000, 上下文窗口 × 20%) | 低于此值**发出警告** |
| Normal | 上下文窗口 × 100% | 正常运行 |

```typescript
// 核心判断逻辑
shouldWarn: tokens < warnBelowTokens    // 上下文太小，工具调用可能不稳定
shouldBlock: tokens < hardMinTokens     // 上下文太小，直接拒绝运行
```

**源码细节**：对本地自托管模型（Ollama 等）会给出更友好的修复建议——"raise the server/model context limit"，而不是简单报错。

#### 3.7.3 Context Window Cache：进程级全局缓存

为避免每次请求都查模型元数据，OpenClaw 用 `Symbol.for` 做了进程级全局缓存：

```typescript
// src/agents/context-cache.ts
const CONTEXT_WINDOW_CACHE_STATE = Symbol.for("openclaw.contextWindowCacheState");

// 三个缓存 Map：
//   configuredTokenCache  — 用户显式配置的 contextTokens
//   discoveredTokenCache  — 从模型目录发现的 token 数
//   contextWindowCache    — 原生上下文窗口（不作为运行时上限）

// 原子替换（不复制整个 Map，直接引用替换）
replaceContextWindowCaches(newState);

// 查找优先级：configured > discovered
lookupCachedContextTokens(modelId)
```

**设计亮点**：用 `globalThis + Symbol.for` 跨模块共享，不用依赖 DI 容器；缓存替换是**代际替换**（reference swap），不是逐条更新，避免并发问题。

#### 3.7.4 Compaction Pipeline：上下文压缩流水线

这是 OpenClaw 上下文工程最核心的部分。当历史消息超过 token 预算时，触发压缩：

```
Compaction Pipeline（src/agents/compaction-planning.ts + compaction.ts）：

  原始消息历史
       │
       ▼
  ┌─────────────────────┐
  │ 1. Sanitize（净化）  │  ← 必须先做，安全红线
  │  - 剥离 toolResult   │
  │    .details（敏感）   │
  │  - 剥离 runtime-     │
  │    context 内部消息  │
  └─────────┬───────────┘
            │
            ▼
  ┌─────────────────────┐
  │ 2. Estimate（估算）  │  ← estimateTokens() + 安全边距
  │  SAFETY_MARGIN=1.2   │     （防止估算偏低）
  └─────────┬───────────┘
            │
            ▼
  ┌─────────────────────┐
  │ 3. Group（分组）      │  ← ⭐ 工具调用对保护
  │  assistant(toolCall) │     永远不拆 call 和 result
  │  + toolResult 原子组 │     否则 provider 会拒绝
  └─────────┬───────────┘
            │
            ▼
  ┌─────────────────────┐
  │ 4. Adaptive Chunk    │  ← 自适应分块
  │  BASE_CHUNK_RATIO=0.4│     （默认每块占窗口 40%）
  │  MIN_CHUNK_RATIO=0.15│     （大消息时缩小到 15%）
  │  SUMMARIZATION_      │     （预留 4096 tokens 给摘要 prompt）
  │  OVERHEAD=4096       │
  └─────────┬───────────┘
            │
            ▼
  ┌─────────────────────┐
  │ 5. Summarize（摘要） │  ← 多轮 LLM 摘要
  │  - 每块独立摘要       │
  │  - 标识符保持指令     │     UUID/IP/URL 原样保留
  │  - 合并摘要           │     保留活跃任务/进度/TODO
  └─────────┬───────────┘
            │
            ▼
  ┌─────────────────────┐
  │ 6. Oversized Fallback│  ← 超大消息降级
  │  > 50% 窗口的消息     │     不摘要，替换为占位说明
  │  "Large msg omitted" │     （避免单条撑爆摘要请求）
  └─────────────────────┘
            │
            ▼
  压缩后的历史（摘要 + 近期原文）
```

**关键常量**（源码实测）：

| 常量 | 值 | 作用 |
|:---|:---:|:---|
| `BASE_CHUNK_RATIO` | 0.4 | 默认每块占上下文窗口 40% |
| `MIN_CHUNK_RATIO` | 0.15 | 大消息时每块最小占 15% |
| `SAFETY_MARGIN` | 1.2 | token 估算安全边距（防止偏低） |
| `SUMMARIZATION_OVERHEAD_TOKENS` | 4096 | 摘要 prompt + 系统 prompt 预留 |

**自适应分块算法**：

```typescript
// src/agents/compaction-planning.ts
function computeAdaptiveChunkRatio(messages, contextWindow): number {
  const avgRatio = (estimateMessagesTokens(messages) / messages.length * SAFETY_MARGIN)
                   / contextWindow;
  // 平均消息 > 窗口 10% → 缩小分块，避免超模型限制
  if (avgRatio > 0.1) {
    const reduction = Math.min(avgRatio * 2, BASE_CHUNK_RATIO - MIN_CHUNK_RATIO);
    return Math.max(MIN_CHUNK_RATIO, BASE_CHUNK_RATIO - reduction);
  }
  return BASE_CHUNK_RATIO;  // 默认 0.4
}
```

1. **压缩前必须净化**：toolResult.details 可能包含敏感数据，绝不能进入摘要 prompt

#### 3.7.7 面试高频问答

**Q1：OpenClaw 的 ContextEngine 接口有哪些核心方法？**

A：核心是 `assemble()` 和 `compact()`。`assemble()` 在 token 预算内组装模型可见消息；`compact()` 压缩历史（摘要/裁剪）。其他生命周期方法：`bootstrap`（初始化）、`ingest`（摄入消息）、`afterTurn`（轮后处理）、`maintain`（维护清理）。

**Q2：Compaction Pipeline 的六个步骤是什么？**

A：Sanitize（净化）→ Estimate（估算 + 1.2 安全边距）→ Group（工具调用对原子分组）→ Adaptive Chunk（自适应分块 0.4→0.15）→ Summarize（多轮 LLM 摘要 + 合并）→ Oversized Fallback（超大消息降级占位）。

**Q3：为什么不能拆断工具调用对？**

A：LLM provider（Anthropic/OpenAI）的 API 协议要求 `toolUse` 和 `toolResult` 必须配对出现在同一次请求中。如果压缩时把 call 分到 A 块、result 分到 B 块，摘要后的历史会出现 orphan toolResult，provider 会返回 400 错误。OpenClaw 用 `pendingToolCalls` 队列跟踪配对状态，只有队列为空时才允许切分。

**Q4：自适应分块策略是怎么工作的？**

A：默认每块占上下文窗口的 40%（BASE_CHUNK_RATIO）。当检测到平均消息 > 窗口 10% 时，说明消息普遍较大，自动缩小分块比例（最低 15%），避免单块超过模型摘要请求的限制。同时预留 4096 tokens 给摘要 prompt 和系统 prompt。

**Q5：Context Window Guard 的三级阈值是什么？**

A：Hard Min = max(4000, 窗口×10%)，低于此值阻断运行；Warn Below = max(8000, 窗口×20%)，低于此值发出警告；正常区间内正常运行。对本地自托管模型会给出针对性修复建议。

#### 3.7.8 易错点

1. **忘记净化就压缩**：toolResult.details 可能包含 API key、用户数据等敏感信息，必须先剥离再送摘要
2. **估算不带安全边距**：estimateTokens 对 Unicode/代码 token 估算偏低，必须乘 1.2 系数
3. **摘要丢失标识符**：LLM 可能把 UUID 缩写或改写，必须在 prompt 中明确要求保持原样
4. **压缩后不校验**：摘要合并后要检查是否丢失了活跃任务状态，否则 Agent 会"忘记"正在做什么
5. **超大消息直接摘要**：单条超过窗口 50% 的消息送摘要会撑爆请求，应该降级为占位说明

## 七、面试高频问答

### Q1：OpenClaw 是什么？

开源个人 AI Agent 运行时（TypeScript，MIT，145k stars），本地运行的后台服务，连接 20+ 消息渠道，7×24 小时自动响应消息、执行工具、持久记忆。核心理念是从「云端 AI 对话」到「本地 AI 行动」。

### Q2：OpenClaw 的核心架构是什么？

四层微内核架构：
1. **Gateway 控制平面**：WebSocket + HTTP API + 路由引擎 + 会话管理 + Hooks
2. **Agent Runtime**：Pi Embedded Runner（Agentic Loop + 模型选择 + 工具注册 + System Prompt 构建）
3. **Channel Adapters**：WhatsApp/Telegram/Discord/Slack 等渠道插件
4. **Persistent Memory**：Local-First 加密存储

### Q3：OpenClaw 怎么定义 Agent？

配置优先——两个 Markdown 文件：
- **SOUL.md**：Agent 的人格、规则、行为（自然语言描述）
- **AGENTS.md**：多 Agent 定义（可选）

改行为只需编辑 Markdown，重新对话即生效，无需重新编译部署。

### Q4：OpenClaw 的 Agentic Loop 怎么工作？

标准 ReAct 循环：
1. LLM 判断是否需要工具
2. 需要→选择工具+参数→执行→结果注入对话历史
3. LLM 基于结果继续推理，直到不需要工具
4. 生成最终响应

有最大步数限制 + 超时熔断防止无限循环。

### Q5：OpenClaw 的 Skills 系统和 MCP 有什么关系？

两者理念一致——**工具标准化接入**：
- OpenClaw Skills：本地插件 + ClawHub 市场，TypeScript 实现
- MCP 协议：跨语言的工具接入标准（见 [11. MCP协议](../11.%20MCP协议.md)）

未来 OpenClaw 可能原生支持 MCP，让第三方 MCP Server 直接作为工具接入。

### Q6：OpenClaw 和你的 AgentMate 有什么区别？

定位不同：OpenClaw 是个人 Agent 运行时（配置优先、本地优先、消息优先），AgentMate 是企业平台（代码+Prompt、云端、Web+钉钉、过程式状态机、双引擎回归守门）。AgentMate 在**可控性**（过程式状态机 vs 自由 ReAct）和**质量保障**（双引擎回归 vs 无系统评测）上更有优势。

### Q7：从 OpenClaw 能学到什么工程经验？

1. **配置优先**：Agent 行为是配置不是代码，改 Markdown 即生效
2. **Local-First**：数据不离开本地，隐私安全
3. **模型无关**：Provider 抽象 + Failover，不绑定单一厂商
4. **微内核 + 插件**：小核心 + 大生态，渠道/工具都通过插件扩展
5. **Hooks 生命周期**：pre/post 钩子实现安全拦截和可观测性
