# OpenClaw 上下文工程设计经验

## 经验 1：把上下文管理抽象成可插拔接口，不要硬编码策略

### 问题描述

上下文管理没有银弹——RAG 召回、滚动摘要、全量向量检索、滑动窗口……不同场景最优策略不同。如果把策略硬编码在 Agent Runtime 里，换策略就要改核心代码。

### OpenClaw 方案

定义 `ContextEngine` 接口，把整个上下文生命周期抽象成插件：

```typescript
// src/context-engine/types.ts
interface ContextEngine {
  readonly info: ContextEngineInfo;
  bootstrap?({ sessionId, ... }): Promise<BootstrapResult>;
  ingest({ sessionId, message, ... }): Promise<IngestResult>;
  assemble({ sessionId, messages, tokenBudget, prompt, ... }): Promise<AssembleResult>;
  compact({ sessionId, tokenBudget, force, ... }): Promise<CompactResult>;
  afterTurn?({ sessionId, messages, tokenBudget, ... }): Promise<void>;
  maintain?({ sessionId, ... }): Promise<ContextEngineMaintenanceResult>;
  dispose?(): Promise<void>;
}
```

核心是 `assemble()`——在 token 预算内返回有序的模型可见消息列表。引擎内部可以自由实现召回/压缩/排序。

### 可复用模式：策略接口 + 默认实现

```
┌─────────────────────────────────────────┐
│         Agent Runtime（核心）            │
│  只依赖 ContextEngine 接口，不关心实现    │
└────────────────────┬────────────────────┘
                     │ interface
         ┌───────────┼───────────┐
         ▼           ▼           ▼
  ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ 默认引擎  │ │ RAG 引擎 │ │ 向量引擎 │
  │ Compaction│ │ 召回优先 │ │ 全量检索 │
  └──────────┘ └──────────┘ └──────────┘
```

### 反面案例

某 Agent 框架把「滑动窗口 + 摘要」写死在 `Agent.run()` 里，后来想加 RAG 召回，只能 fork 核心代码改，导致升级上游困难。

### 理论提炼

对应经典**策略模式（Strategy Pattern）**，但比标准策略模式更进一步——不仅替换算法，还抽象了完整生命周期（bootstrap/ingest/assemble/compact/maintain/dispose）。**适用边界**：当上下文管理策略需要在运行时切换、或需要第三方扩展时，生命周期接口比单一策略接口更健壮；如果策略固定不变，过度抽象反而增加复杂度。

## 经验 2：安全净化必须是压缩流水线的第一步

### 问题描述

工具调用结果（toolResult）的 `.details` 字段可能包含 API key、用户数据、内部配置等敏感信息。如果直接送进 LLM 摘要 prompt，会导致：
1. 敏感数据泄露给 LLM provider
2. 摘要本身可能被后续会话保留，扩大泄露面

### OpenClaw 方案

压缩流水线第一步强制净化，且用 `SECURITY` 注释标记为安全红线：

```typescript
// src/agents/compaction-planning.ts
function sanitizeCompactionMessages(messages: AgentMessage[]): AgentMessage[] {
  // SECURITY: toolResult.details and runtime-context transcript entries
  // must never enter LLM-facing compaction.
  return stripToolResultDetails(stripRuntimeContextCustomMessages(messages));
}
```

净化在**所有** token 估算和摘要之前执行，且每个入口都重复调用（不假设上游已净化）：

```typescript
function estimateMessagesTokens(messages: AgentMessage[]): number {
  const safe = sanitizeCompactionMessages(messages);  // 再次净化
  return safe.reduce(...);
}
```

### 可复用模式：安全边界前置 + 不信任上游

```
原始消息 → [净化层] → 估算 → 分组 → 摘要 → ...
              ↑
        安全红线，不可跳过
```

**原则**：每个可能接触 LLM 的入口都独立净化，不假设上游已处理。纵深防御。

### 反面案例

某 Agent 框架压缩时直接把 toolResult 原文送摘要，导致用户的 API key 出现在摘要里，后续会话被发送给 LLM provider，触发安全审计告警。

### 理论提炼

对应安全工程的**纵深防御（Defense in Depth）**原则 + **零信任（Zero Trust）**架构。安全净化不假设上游已处理，每个入口独立校验；并且净化层放在流水线最前端，让后续所有环节（估算/分组/摘要）接触的都是净化后的数据。**适用边界**：任何涉及外部数据（toolResult/用户输入/文件内容）进入 LLM 之前的场景，都应设独立净化层；净化策略应可配置（不同数据类型不同规则）。

## 经验 3：工具调用对不能拆断——原子分组保护

### 问题描述

LLM provider（Anthropic/OpenAI）的 API 协议要求 `toolUse` 和 `toolResult` 必须配对出现在同一次请求中。如果压缩时把 call 分到 A 块、result 分到 B 块，摘要后的历史会出现 orphan toolResult，provider 返回 400 错误。

### OpenClaw 方案

用 `pendingToolCalls` 队列跟踪配对状态，只有队列为空时才允许切分：

```typescript
// src/agents/compaction-planning.ts — groupCompactionMessages()
let pendingToolCalls = createToolCallOccurrenceQueue();

for (const message of messages) {
  // assistant 发出 toolCall → 记录 pending
  if (message.role === "assistant") {
    const toolCalls = extractToolCallsFromAssistant(message);
    pendingToolCalls = createToolCallOccurrenceQueue();
    for (const toolCall of toolCalls) {
      pendingToolCalls.add(toolCall.id, true);
    }
  }
  // toolResult 到达 → claim pending
  else if (message.role === "toolResult" && pendingToolCalls.size > 0) {
    pendingToolCalls.claim(resultId);
  }
  // ⭐ 只有队列空时才允许切分
  if (pendingToolCalls.size === 0) {
    groups.push({ messages: current, tokens: currentTokens });
    current = [];
  }
}
```

### 可复用模式：协议感知的分组边界

```
消息序列：
  user → assistant(toolCall A) → toolResult A → assistant(toolCall B) → toolResult B → user
         └────── 原子组 1 ──────┘                └────── 原子组 2 ──────┘

切分点只能在 ⭐ 处（pendingToolCalls.size === 0）：
  user → assistant(toolCall A) → toolResult A  ⭐  assistant(toolCall B) → toolResult B → user
```

**原则**：任何需要分块/裁剪历史的操作，必须先识别 provider 协议的原子单元（call/result 对），不能在原子单元中间切分。

### 反面案例

某 Agent 框架按固定条数切分历史（每 10 条一块），某次切分正好把 toolCall 和 toolResult 分到不同块，压缩后 provider 返回 `tool_use ids were found without tool_result blocks`，整个会话崩溃。

### 理论提炼

对应分布式系统的**原子性（Atomicity）**原则 + 网络协议的**消息完整性（Message Integrity）**。在 LLM 消息流中，toolCall + toolResult 构成一个逻辑事务单元，必须作为整体切分或保留。切分算法必须**协议感知（Protocol-Aware）**——理解 provider 协议的配对约束，而非机械按条数/字数切分。**适用边界**：任何需要对消息历史做分块/裁剪/重排的操作，都必须先识别协议原子单元（call/result 对、thinking/response 对等）。

## 经验 4：token 估算要有安全边距，不要相信精确值

### 问题描述

`estimateTokens()` 对 Unicode（中文/emoji）、代码、特殊字符的估算往往偏低。如果按精确估算值切分，实际发送时会超上下文窗口，导致 provider 400 错误。

### OpenClaw 方案

引入 `SAFETY_MARGIN = 1.2` 系数，所有估算值都乘 1.2：

```typescript
// src/agents/compaction-planning.ts
export const SAFETY_MARGIN = 1.2;

// 自适应分块时用安全边距调整
const avgRatio = (estimateMessagesTokens(messages) / messages.length * SAFETY_MARGIN)
                 / contextWindow;

// 分块上限也用安全边距
const effectiveMax = Math.max(1, Math.floor(params.maxChunkTokens / SAFETY_MARGIN));
```

### 可复用模式：悲观估算 + 动态调整

```
实际 token 数 = estimateTokens() × SAFETY_MARGIN

切分判断：currentTokens + group.tokens > maxTokens（用悲观值）
切分上限：maxChunkTokens / SAFETY_MARGIN（留余量）
```

**原则**：估算用于切分决策时要悲观（宁可多切一块），用于报告时可以乐观。1.2 是经验值，代码密集型场景可以调到 1.3-1.5。

### 反面案例

某 Agent 框架按精确估算值切分，中文代码注释多时估算偏低 20%+，频繁触发 provider 400，用户体验差。

## 经验 5：多源预算解析 + 降级链，不要单一依赖

### 问题描述

模型上下文窗口信息可能来自多个源：用户配置、模型元数据、provider 文档、默认值。如果只信一个源，配置错误时会运行在错误预算下。

### OpenClaw 方案

定义清晰的解析优先级链，逐级降级：

```typescript
// src/agents/context-window-guard.ts
resolveContextWindowInfo({ cfg, provider, modelId, ... }):
  // 1. 用户显式配置（最高优先级，覆盖一切）
  const fromModelsConfig = modelsConfig.find(m => m.id === modelId)?.contextTokens;
  // 2. 模型元数据（从模型目录发现）
  const fromModel = modelContextTokens ?? modelContextWindow;
  // 3. 默认值 8000 tokens
  const defaultTokens = CONTEXT_WINDOW_WARN_BELOW_TOKENS;

  return fromModelsConfig
    ? { tokens: fromModelsConfig, source: "modelsConfig" }
    : fromModel
      ? { tokens: fromModel, source: "model" }
      : { tokens: defaultTokens, source: "default" };
```

### 可复用模式：配置优先级链 + 来源标记

```
优先级：用户配置 > 模型元数据 > 默认值
标记来源：source = "modelsConfig" | "model" | "default"
```

**关键**：返回值带 `source` 字段，调试时能看到预算来自哪里，排查配置问题。

### 三级安全阈值

| 阈值 | 计算 | 行为 |
|:---|:---|:---|
| Hard Min | max(4000, 窗口 × 10%) | 阻断运行 |
| Warn Below | max(8000, 窗口 × 20%) | 发出警告 |
| Normal | 窗口 × 100% | 正常 |

### 理论提炼

对应**配置优先级链（Configuration Precedence Chain）**模式 + **多级熔断（Multi-Level Circuit Breaker）**。预算解析按优先级逐级降级（用户配置 > 元数据 > 默认值），保证总有值可用；三级阈值对应熔断的三个状态（正常/警告/阻断）。返回值带 `source` 字段是**可观测性（Observability）**设计——预算来源可追溯，便于排查配置问题。**适用边界**：任何外部依赖的配置值（模型能力/API 限额/超时阈值）都应设计多源降级链 + 来源标记，避免单点配置错误导致系统不可用。

## 经验 6：进程级缓存用 Symbol.for + 代际替换，不依赖 DI 容器

### 问题描述

模型元数据（上下文窗口、token 数）是高频读、低频写的数据。如果每次都查配置文件或模型目录，性能差；如果用 DI 容器管理，增加启动复杂度。

### OpenClaw 方案

用 `globalThis + Symbol.for` 做进程级全局缓存，替换时用代际替换（reference swap）：

```typescript
// src/agents/context-cache.ts
const CONTEXT_WINDOW_CACHE_STATE = Symbol.for("openclaw.contextWindowCacheState");

const CONTEXT_WINDOW_CACHE_STATE = (contextWindowCacheGlobal[CONTEXT_WINDOW_CACHE_STATE] ??= {
  configuredTokenCache: new Map(),
  discoveredTokenCache: new Map(),
  contextWindowCache: new Map(),
});

// 代际替换：直接引用替换，不逐条更新
export function replaceContextWindowCaches(newState: ContextWindowCacheState): void {
  CONTEXT_WINDOW_CACHE_STATE.configuredTokenCache = newState.configuredTokenCache;
  CONTEXT_WINDOW_CACHE_STATE.discoveredTokenCache = newState.discoveredTokenCache;
  CONTEXT_WINDOW_CACHE_STATE.contextWindowCache = newState.contextWindowCache;
}
```

### 可复用模式：全局单例 + 不可变代际替换

```
读：直接读当前代际（无锁，快）
写：构造新 Map → 原子替换引用（无锁，O(1)）
旧代际：自然 GC（无锁，无并发问题）
```

**原则**：高频读低频写的缓存，用不可变代际替换代替加锁更新。`Symbol.for` 保证跨模块/跨 chunk 共享同一个实例，不依赖 DI。

### 反面案例

某框架每次查模型上下文窗口都读 YAML 配置文件，每次 Agent run 多 5-10ms IO 开销，高并发时明显。

## 经验 7：超大消息优雅降级，不要让单条消息撑爆摘要

### 问题描述

单条消息（如大文件读取、长命令输出）可能超过上下文窗口的 50%。如果直接送摘要，会撑爆摘要请求；如果直接保留，又占用太多预算。

### OpenClaw 方案

超大消息降级为占位说明，不送摘要：

```typescript
// src/agents/compaction-planning.ts — buildOversizedFallbackPlan()
const oversizedThreshold = params.contextWindow * 0.5;

for (const group of groupCompactionMessages(params.messages, perMessageTokens)) {
  for (const message of group.messages) {
    if (tokens * SAFETY_MARGIN > oversizedThreshold) {
      oversizedNotes.push(
        `[Large ${message.role} (~${Math.round(tokens / 1000)}K tokens) omitted from summary]`
      );
      omitToolBatch = true;  // 标记整个工具批次省略
    } else {
      retainedMessages.push(message);
    }
  }
}
```

### 可复用模式：分级降级策略

```
消息大小 vs 上下文窗口：
  < 10%  → 正常摘要
  10%-50% → 自适应分块 + 安全边距
  > 50%  → 降级占位（"Large msg omitted"）
```

**原则**：不是所有消息都值得摘要。超大消息降级为占位说明，保留「这里曾有大内容」的事实，比强行摘要撑爆请求更好。

### 反面案例

某 Agent 框架尝试摘要 200K tokens 的文件读取结果，摘要请求本身超过模型 128K 上下文，provider 返回 400，整个压缩流程失败，会话无法继续。

## 经验 8：LLM 行为控制要显式写进 prompt，不要假设模型会遵守

### 问题描述

摘要时 LLM 可能：丢失 UUID/IP/URL 等标识符、改写关键决策、遗漏活跃任务状态。如果不明确控制，摘要质量不可控。

### OpenClaw 方案

在摘要 prompt 中显式写入行为控制指令：

```
# 标识符保持指令
Preserve all opaque identifiers exactly as written (no shortening or reconstruction),
including UUIDs, hashes, IDs, hostnames, IPs, ports, URLs, and file names.

# 合并摘要指令（MUST PRESERVE 列表）
MUST PRESERVE:
- Active tasks and their current status (in-progress, blocked, pending)
- Batch operation progress (e.g., '5/17 items completed')
- The last thing the user requested and what was being done about it
- Decisions made and their rationale
- TODOs, open questions, and constraints
```

### 可复用模式：结构化行为控制 + MUST PRESERVE 列表

```
普通 prompt："请总结以下对话"
↓ 改为
受控 prompt：
  ## 标识符保持
  Preserve UUIDs/IPs/URLs verbatim.
  ## MUST PRESERVE
  - Active tasks + status
  - Last user request
  - Decisions + rationale
  ## 摘要正文
  {messages}
```

**原则**：不要假设 LLM 会「自然地」保留关键信息。用结构化指令 + MUST PRESERVE 列表显式约束。

### 反面案例

某 Agent 框架摘要后 UUID 被缩写为 "abc..."，导致后续工具调用找不到资源，排查困难。加了标识符保持指令后问题消失。

### 理论提炼

对应**指令约束生成（Instruction-Constrained Generation）**模式 + **防御性 Prompt Engineering**。不假设 LLM 会「自然地」保留关键信息，而是用结构化指令（MUST PRESERVE 列表 + 显式禁止项）在生成阶段前置约束。这比事后评测修正更高效——一次生成正确 vs 生成后检测再重试。**适用边界**：任何需要 LLM 输出满足特定约束的场景（格式/标识符/关键事实），都应设计显式约束指令；约束项应结构化、可枚举，避免模糊表述。

## 经验 9：压缩与重试策略分离——overflow 才自动重试，threshold 不重试

### 问题描述

压缩有两种触发场景：
1. **Overflow**：LLM 返回上下文超限错误，必须压缩后重试
2. **Threshold**：上下文接近阈值，预防性压缩，不需要立即重试

如果两种场景都自动重试，会导致不必要的 LLM 调用；如果都不重试，overflow 场景用户体验差。

### OpenClaw 方案

在 `checkCompaction()` 中明确区分：

```typescript
// src/agents/sessions/agent-session-compaction.ts

// Case 1: Overflow — compact and auto-retry
if (isContextOverflow(assistantMessage, contextWindow)) {
  // 删除失败的 assistant 消息
  this.agent.state.messages = messages.slice(0, -1);
  return await this.runAutoCompaction("overflow", true);  // willRetry = true
}

// Case 2: Threshold — compact but NO auto-retry
if (shouldCompact(contextTokens, contextWindow, settings)) {
  return await this.runAutoCompaction("threshold", false);  // willRetry = false
}
```

并且限制 overflow 恢复最大次数（防止无限循环）：

```typescript
if (this.overflowRecoveryAttempts >= MAX_OVERFLOW_COMPACTION_ATTEMPTS) {
  // 放弃，提示用户换模型或减少上下文
  return false;
}
```

### 可复用模式：场景化触发 + 有限重试

```
触发场景：
  Overflow（错误）→ 压缩 + 自动重试（最多 N 次）
  Threshold（预防性）→ 压缩，不重试
  Manual（用户手动）→ 压缩，按用户指令

重试上限：MAX_OVERFLOW_COMPACTION_ATTEMPTS（防止无限循环）
```

### 额外细节：压缩边界检查

```typescript
// 如果 assistant 消息早于上次压缩，不触发（防止 stale 触发）
const assistantIsFromBeforeCompaction =
  compactionEntry !== null &&
  assistantMessage.timestamp <= new Date(compactionEntry.timestamp).getTime();
if (assistantIsFromBeforeCompaction) {
  return false;
}
```

**原则**：压缩触发要基于当前状态，不能用 stale 的历史消息触发。

## 经验 10：压缩生命周期要可中止、可观测、可扩展

### 问题描述

压缩是耗时操作（多次 LLM 调用），可能需要中止（用户取消/超时）、需要观测（知道压缩了多少 token）、需要扩展（第三方想在压缩前后插入逻辑）。

### OpenClaw 方案

完整的生命周期管理：

```typescript
// 1. 可中止：AbortController 贯穿整个压缩流程
const abortController = new AbortController();
this.compactionAbortController = abortController;
outcome = await this.runCompactionWork({ signal: abortController.signal, ... });
// 用户取消时
abortCompaction(): void {
  this.compactionAbortController?.abort();
}

// 2. 可观测：事件流
this.emit({ type: "compaction_start", reason: "manual", itemId });
this.emit({
  type: "compaction_end",
  reason: "manual",
  itemId,
  outcome: { status: "completed", tokensBefore, tokensAfter, willRetry }
});

// 3. 可扩展：extension hook
if (this.currentExtensionRunner.hasHandlers("session_before_compact")) {
  const extensionResult = await this.currentExtensionRunner.emit({
    type: "session_before_compact",
    preparation,
    ...
  });
  if (extensionResult?.cancel) return { status: "aborted" };  // 扩展可以取消
  if (extensionResult?.compaction) {                          // 扩展可以接管
    compactionResult = extensionResult.compaction;
    fromExtension = true;
  }
}
// 压缩完成后通知扩展
await this.currentExtensionRunner.emit({ type: "session_compact", ... });

// 4. 压缩前断开 agent，压缩后重连（避免并发冲突）
this.disconnectFromAgent();
await this.abort();
// ... 压缩工作 ...
finally {
  this.reconnectToAgent();
}
```

### 可复用模式：完整生命周期四要素

| 要素 | 实现 |
|:---|:---|
| 可中止 | AbortController 贯穿，每个 LLM 调用都传 signal |
| 可观测 | start/end 事件流，带 tokensBefore/tokensAfter |
| 可扩展 | before/after hook，扩展可取消或接管 |
| 无冲突 | 压缩前断开 agent，压缩后重连 |

**原则**：任何涉及 LLM 多次调用的操作，都要设计完整的生命周期——能停、能看、能扩展、不冲突。

## 面试高频问答

**Q1：如果让你设计一个 Agent 的上下文管理系统，你会怎么做？**

A：参考 OpenClaw 的 ContextEngine 接口设计：
1. 定义可插拔接口（bootstrap/ingest/assemble/compact/maintain），不硬编码策略
2. assemble() 是核心——在 token 预算内组装模型可见消息
3. 压缩流水线六步：净化→估算（带安全边距）→原子分组→自适应分块→摘要→超大降级
4. 三级预算阈值（Hard Min 阻断 / Warn Below 警告 / Normal 正常）
5. 压缩生命周期可中止、可观测、可扩展

**Q2：压缩时最容易踩的坑是什么？**

A：三个坑：
1. **拆断工具调用对**：provider 协议要求 call/result 配对，拆断会 400。用 pendingToolCalls 队列跟踪，只有队列空才切分。
2. **估算不带安全边距**：estimateTokens 对中文/代码偏低，必须乘 1.2。
3. **忘记净化**：toolResult.details 可能含敏感数据，必须先剥离再送摘要。

**Q3：OpenClaw 的预算解析为什么要多源降级？**

A：模型上下文窗口信息来自多个源（用户配置、模型元数据、默认值），单一依赖会在配置错误时运行在错误预算下。多源降级链 + source 标记，既能容错又能调试。

**Q4：overflow 和 threshold 压缩为什么要区别对待？**

A：overflow 是错误场景（LLM 返回超限），必须压缩后自动重试；threshold 是预防性场景（接近阈值），压缩后不需要立即重试。两者混为一谈会导致不必要的 LLM 调用或用户体验差。
