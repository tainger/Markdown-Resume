# 幻觉、幻觉审计、幻觉治理、幻觉评测

> LLM 幻觉（Hallucination）是大模型应用落地的**头号杀手**——一本正经胡说八道的答案比没有答案更危险。
> 本文结合 AgentMate 项目实战，系统讲透**幻觉成因 → 审计发现 → 治理体系 → 评测守门**全链路，对应简历「P0-P4 分级检索策略杜绝 LLM 幻觉」「pre/do/post 三态 Hook 后置过滤」「双引擎回归测试」三条核心职责。

---

## 一、什么是幻觉

### 1.1 定义

**幻觉（Hallucination）**：LLM 生成的内容**看似合理但与事实不符**，或**与上下文/知识库不一致**的现象。

幻觉分两类：

| 类型 | 定义 | 示例 |
|:---|:---|:---|
| **内在幻觉（Intrinsic Hallucination）** | 生成内容与输入上下文矛盾 | RAG 知识库说 A 功能在 2024.1 上线，LLM 回答说 2023.12 上线 |
| **外在幻觉（Extrinsic Hallucination）** | 生成内容在输入上下文中找不到依据（编造） | 编造不存在的 API、参数、错误码、文档链接 |

### 1.2 幻觉的四大成因

```
┌─────────────────────────────────────────────────────────┐
│                  幻觉四大成因                              │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  [1] 训练数据问题                                         │
│      ├─ 数据有噪声/错误（标注错误、过期信息）               │
│      ├─ 数据分布偏差（某些领域样本少）                     │
│      └─ 数据截止（知识有截止日期，训练后世界变了）          │
│                                                          │
│  [2] 生成机制本质                                         │
│      ├─ 自回归生成：下一个 token 基于概率分布，不是事实     │
│      ├─ 采样随机性：temperature/top-p 引入不确定性         │
│      └─ 模型倾向"续写"而非"查证"，即使不确定也要生成         │
│                                                          │
│  [3] 上下文限制                                           │
│      ├─ 上下文窗口有限，长文档被截断丢失关键信息             │
│      ├─ 检索召回不精准，给到错误的片段                     │
│      └─ 多轮对话历史过长，早期约束被稀释                    │
│                                                          │
│  [4] 对齐不足                                             │
│      ├─ RLHF/DPO 对齐不充分，模型优先"流畅"而非"准确"       │
│      ├─ Prompt 约束弱，模型自由发挥过度                    │
│      └─ 没有 Grounding（接地），模型用参数化记忆硬答         │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 1.3 幻觉为什么不能根除

> 面试必问：「幻觉能消除吗？」——不能，这是生成机制决定的。

LLM 的本质是**基于概率分布的自回归生成**，不是数据库查询。即使事实在训练数据中出现过，模型也只是学到了「这种 token 序列的概率分布」，不是「事实本身」。模型的目标是**生成最可能的下一个 token**，而不是**验证事实正确性**。

所以工程目标不是「消除幻觉」，而是：

```
✅ 正确目标：可检测（能发现幻觉）+ 可归因（知道为什么幻觉）+ 可兜底（幻觉时有降级方案）
❌ 错误目标：彻底消除幻觉（不可能）
```

## 二、幻觉审计

> 幻觉审计 = **输入侧审计 + 生成侧审计 + 输出侧审计**，在三个关口拦截幻觉。

### 2.1 审计三道关口

```
用户 Query ──→ [输入侧审计] ──→ 检索/RAG ──→ [生成侧审计] ──→ LLM 生成 ──→ [输出侧审计] ──→ 返回用户
                    │                          │                          │
                    │ 检查 Query 是否          │ 检查检索结果是否          │ 检查生成结果是否
                    │ 会诱导幻觉               │ 充分、准确               │ 有依据、一致
                    ▼                          ▼                          ▼
                 Query 分类                检索质量评估               事实一致性校验
                 P0-P4 分级               召回率/相关度               引用溯源率
```

### 2.2 输入侧审计：Query 分级（AgentMate 实战）

AgentMate 的 P0-P4 分级检索策略就是**输入侧幻觉审计**：

| 级别 | 触发条件 | 检索策略 | 幻觉风险 |
|:---|:---|:---|:---|
| **P0** | 命中产品关键词（如「MSE 微服务」「网关」） | 强制检索知识库，不命中则拒答 | 低（有 grounding） |
| **P1** | 命中通用技术词（如「JVM」「Redis」） | 检索知识库 + 允许模型补充 | 中（需引用校验） |
| **P2** | 命中非本产品但相关 | 走官方文档检索，标注来源 | 中（来源明确） |
| **P3** | 命中无关话题 | 拒绝回答（不在业务范围） | 极低（直接拒答） |
| **P4** | 无法判断 | 反向提问澄清，不直接回答 | 极低（不生成） |

**核心逻辑**：**通过 Query 分类决定是否需要检索、检索什么、能不能答**，从源头减少幻觉机会。P0/P3/P4 都是「不依赖模型自由发挥」的刚性策略。

### 2.3 生成侧审计：检索质量评估

RAG 系统中，**检索质量直接决定幻觉率**——检索错了，LLM 再好也会基于错误信息生成。

审计指标：

| 指标 | 含义 | 阈值建议 |
|:---|:---|:---|
| **召回率（Recall@K）** | 正确文档是否在 Top-K 中 | >85% |
| **准确率（Precision@K）** | Top-K 中有多少是相关的 | >70% |
| **MRR（Mean Reciprocal Rank）** | 第一个相关文档的排名倒数 | >0.6 |
| **nDCG@K** | 考虑等级的排序质量 | >0.7 |
| **引用覆盖率** | LLM 输出中有多少内容能被检索片段支撑 | >90% |

**AgentMate 实战**：两阶段召回（向量粗排 Top-20 → Cross-Encoder 重排 Top-3）就是为了提升 Top-3 准确率，给 LLM 高质量的上下文。

### 2.4 输出侧审计：事实一致性校验

LLM 生成后，对输出做事实校验：

```
LLM 输出: "MSE 微服务的 Sentinel 组件在 2024 年 3 月发布"
                    │
                    ▼
事实一致性校验：
  ├─ 引用溯源：这句话对应哪个检索片段？
  │    → 检索片段说 "Sentinel 在 2024 年 1 月发布"
  │    → ❌ 不一致，内在幻觉
  │
  ├─ 实体校验：Sentinel 是 MSE 的组件吗？
  │    → 检索结果确认存在
  │    → ✅ 实体正确
  │
  └─ 数值校验：时间/版本号/配置项等关键数值
       → 与知识库对比
       → ❌ 数值错误，需修正或拒答
```

### 2.5 pre/do/post 三态 Hook（AgentMate 实战）

AgentMate 的三态 Hook 是**全链路幻觉审计的工程化实现**：

```
用户请求 → [pre Hook] → LLM 调用 → [do Hook] → 工具调用 → [post Hook] → 返回
              │                      │                      │
              │ 前置审计             │ 执行监控             │ 后置过滤
              │                      │                      │
              ├─ Query 分级（P0-P4）  ├─ 工具调用参数校验     ├─ 输出事实校验
              ├─ 敏感词/越权检测      ├─ 工具调用结果校验     ├─ 引用溯源检查
              ├─ Prompt 注入检测     ├─ 超时/失败降级         ├─ PII 脱敏
              └─ 决定是否检索         └─ 执行日志记录         └─ 幻觉拦截/降级
```

**pre Hook**（前置）：在 LLM 调用前做 Query 分级和安全检查，决定检索策略
**do Hook**（执行中）：监控工具调用，校验参数和结果，超时降级
**post Hook**（后置）：对 LLM 输出做事实校验、引用检查、脱敏，拦截幻觉输出

## 三、幻觉治理

> 幻觉治理 = **预防（Prompt + Grounding）+ 检测（审计 + 校验）+ 兜底（拒答 + 降级）** 三层防线。

### 3.1 治理体系总览

```
┌─────────────────────────────────────────────────────────────┐
│                   幻觉治理三层防线                             │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  第一层：预防（减少幻觉机会）                                   │
│  ├─ RAG Grounding：用检索结果约束 LLM，不许用参数化记忆        │
│  ├─ P0-P4 分级：不同 Query 用不同检索策略，不相关直接拒答      │
│  ├─ System Prompt 强约束：「知识库没有就说不知道」              │
│  └─ 降低随机性：temperature=0~0.3，top-p 受限                 │
│                                                              │
│  第二层：检测（发现幻觉）                                      │
│  ├─ 引用溯源：输出必须带来源，无来源内容标红                    │
│  ├─ 事实校验：关键数值/实体与知识库比对                        │
│  ├─ LLM-as-Judge：用另一个 LLM 做裁判检查一致性                │
│  └─ 用户反馈：点赞点踩收集 badcase                             │
│                                                              │
│  第三层：兜底（幻觉发生时降级）                                │
│  ├─ 拒答策略：知识库没有明确答案时直接说「暂无此问题答案」      │
│  ├─ 降级回复：不确定时返回「可能是...建议查看文档/联系人工」     │
│  ├─ 人工接管：高风险场景（生产故障/支付）转人工                 │
│  └─ 记录 badcase：幻觉样本进评测集，下次回归检测               │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 治理手段详解

#### 手段 1：RAG Grounding（最核心）

RAG 是幻觉治理的**第一道防线**，给 LLM 提供事实依据：

```
❌ 无 RAG：用户问"MSE 网关支持哪些协议？"
    LLM 用参数化记忆回答（可能是其他网关的协议，幻觉）

✅ 有 RAG：
    1. 检索 MSE 网关文档 → 得到支持 HTTP/gRPC/ Dubbo 的片段
    2. Prompt 注入：「基于以下参考资料回答：{检索片段}」
    3. LLM 基于片段生成，大幅降低幻觉
```

但 RAG 不是万能的，会有**检索幻觉**（检索错了或切片断章取义），需要配合其他手段。

#### 手段 2：System Prompt 强约束

```markdown
# System Prompt 幻觉防线模板

你是产品知识助手，必须严格遵守以下规则：

1. 只允许使用「参考资料」中的内容回答，禁止使用你自己的知识
2. 如果参考资料中没有明确答案，必须回答：「知识库暂无此问题答案，请联系技术支持」
3. 回答必须标注引用来源（文档名 + 章节）
4. 不允许编造 API、参数、错误码、链接
5. 如果用户问题不是关于本产品的，回答：「我只能回答产品相关问题」

# 参考资料
{retrieved_context}
```

#### 手段 3：引用溯源（可检测）

要求 LLM 输出必须标注引用：

```
✅ 带引用的回答：
"MSE 网关支持 HTTP、gRPC、Dubbo 三种协议[文档1 §3.2]，
其中 Dubbo 协议需要在配置中开启 rpc-mode[文档1 §3.4]。"

❌ 无引用的回答：
"MSE 网关支持 HTTP、gRPC、Dubbo、WebSocket 四种协议。"
（WebSocket 可能是编造的，无法验证）
```

引用溯源让用户和系统都能验证事实，**引用覆盖率**是核心指标。

#### 手段 4：LLM-as-Judge 自动校验

用另一个 LLM 做裁判，检查生成内容与检索结果的一致性：

```java
public class HallucinationChecker {
    private final ChatClient judgeClient;

    public HallucinationCheckResult check(String userQuery, String context, String llmOutput) {
        String judgePrompt = """
            请判断以下回答是否与参考资料一致。

            用户问题: %s
            参考资料: %s
            AI回答: %s

            判断标准:
            1. 回答中的每个事实是否都能在参考资料中找到依据？
            2. 回答是否与参考资料矛盾？
            3. 回答是否编造了参考资料中没有的内容？

            输出 JSON: {"consistent": true/false, "violations": [...], "confidence": 0.0-1.0}
            """.formatted(userQuery, context, llmOutput);

        String result = judgeClient.prompt(judgePrompt).call().content();
        return parseResult(result);
    }
}
```

**AgentMate 实战**：简历中的「LLM-as-Judge 语义评判 + 接口真实校验」双引擎就是这个思路——LLM 做语义一致性判断，再用真实接口做硬校验。

#### 手段 5：temperature 调优

| temperature | 适用场景 | 幻觉风险 |
|:---:|:---|:---:|
| 0 ~ 0.3 | 事实问答、RAG grounding、代码生成 | 低 |
| 0.3 ~ 0.7 | 对话、总结、写作 | 中 |
| 0.7 ~ 1.0 | 创意生成、头脑风暴 | 高 |

**幻觉治理场景统一用 temperature=0~0.3**，降低采样随机性。

### 3.3 不同场景的治理策略

| 场景 | 幻觉容忍度 | 核心策略 |
|:---|:---:|:---|
| 产品知识问答 | 极低 | RAG + 引用溯源 + 无依据拒答 |
| 故障排查 | 极低 | RAG + 工具真查 + 关键步骤人工确认 |
| 代码生成 | 低 | RAG + 单测验证 + 静态分析 |
| 数据分析 | 低 | SQL 真查 + 结果校验 + 指标定义对齐 |
| 创意写作 | 高 | 允许发挥，但事实部分需标注 |

## 四、幻觉评测

> 没有评测就没有治理——你不知道幻觉率是多少，就无法判断治理效果。

### 4.1 评测体系总览

```
┌─────────────────────────────────────────────────────────┐
│                   幻觉评测体系                             │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  [1] 评测集构建                                           │
│      ├─ 人工标注集：黄金问答对（问题 + 标准答案 + 依据）   │
│      ├─ 线上 badcase 集：从用户反馈收集的幻觉样本          │
│      └─ 对抗集：故意诱导幻觉的问题（知识截止/边界/诱导）   │
│                                                          │
│  [2] 自动化评测                                           │
│      ├─ LLM-as-Judge：自动判断一致性/相关性/完整性        │
│      ├─ 引用覆盖率：有多少内容能溯源                       │
│      ├─ 拒答准确率：该拒答时是否拒答了                     │
│      └─ 接口真查：关键输出与真实接口/数据库比对            │
│                                                          │
│  [3] 人工抽检                                             │
│      ├─ 每日抽检 Top 高频问题                             │
│      ├─ 高风险场景全检（支付/故障/安全）                   │
│      └─ 评分标准：事实准确/引用正确/表达清晰/无幻觉        │
│                                                          │
│  [4] 回归测试守门                                         │
│      ├─ 每次 Prompt/模型/检索策略变更 → 跑评测集           │
│      ├─ 幻觉率劣化 >阈值 → 阻断发布                        │
│      └─ badcase 修复进评测集 → 下次自动检测               │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 4.2 核心评测指标

| 指标 | 定义 | 计算方式 | 目标值 |
|:---|:---|:---|:---:|
| **幻觉率** | 输出中有幻觉的比例 | 幻觉样本数 / 总样本数 | <5% |
| **引用覆盖率** | 输出中能溯源内容的比例 | 可溯源 token 数 / 总 token 数 | >90% |
| **拒答准确率** | 该拒答时拒答的比例 | 正确拒答数 / 应拒答总数 | >95% |
| **误拒率** | 不该拒答时拒答的比例 | 错误拒答数 / 应回答总数 | <5% |
| **事实准确率** | 事实性回答正确的比例 | 正确事实数 / 总事实数 | >95% |
| **一致性得分** | LLM-as-Judge 给出的一致性分 | Judge 评分均值 | >4.0/5.0 |

### 4.3 评测集构建实战

AgentMate 的评测集来源：

```
评测集 = 黄金集 + Badcase 集 + 对抗集

黄金集（1000+ 条）：
  ├─ 产品文档覆盖问题（每个核心功能 5-10 问）
  ├─ 历史工单真实问题（脱敏后）
  └─ 标注：问题 + 标准答案 + 依据文档

Badcase 集（持续增长）：
  ├─ 用户点踩反馈（自动收集）
  ├─ 人工抽检发现的幻觉
  ├─ 线上监控告警的异常输出
  └─ 修复后加入回归集

对抗集（200+ 条）：
  ├─ 知识截止问题（"2025 年最新功能"→ 应拒答）
  ├─ 边界问题（"其他产品怎么用"→ 应拒答）
  ├─ 诱导问题（"你是不是万能的"→ 应拒绝越界）
  └─ 模糊问题（"那个功能"→ 应反向澄清）
```

### 4.4 双引擎回归测试（AgentMate 实战）

简历中提到的「LLM-as-Judge 语义评判 + 接口真实校验」双引擎评测：

```
评测样本: {query, expected_answer, golden_context, api_validation_rules}
    │
    ▼
被测系统生成 answer
    │
    ├─────────────────────────────────────────┐
    ▼                                         ▼
[引擎1: LLM-as-Judge]                  [引擎2: 接口真实校验]
    │                                         │
    ├─ 语义一致性：answer vs expected        ├─ 硬校验：关键数值/状态码
    ├─ 引用覆盖率：answer 溯源到 context       │   调用真实接口比对
    ├─ 幻觉检测：是否有 context 外的事实       ├─ 数据校验：SQL 查询结果比对
    └─ 拒答判断：该拒答是否拒答了               └─ 权限校验：越权调用拦截检测
    │                                         │
    └──────────────┬──────────────────────────┘
                   ▼
            综合评分 + 失败归因
                   │
                   ├─ 通过 → 允许发布
                   └─ 失败 → 阻断发布 + badcase 自动收集
```

**执行方式**：虚拟线程异步批量执行（JDK21），实时回写进度，大规模评测不阻塞流水线。

### 4.5 回归测试守门机制

```
变更触发（Prompt/模型/检索策略/知识库更新）
    │
    ▼
自动触发回归测试
    │
    ▼
执行评测集（黄金集 + Badcase 集 + 对抗集）
    │
    ▼
幻觉率 / 引用覆盖率 / 拒答准确率 三项核心指标
    │
    ├─ 全部达标（幻觉率 <5%, 引用覆盖 >90%, 拒答准确 >95%）
    │    → ✅ 允许发布
    │
    └─ 任一劣化超阈值
         → ❌ 阻断发布 + 告警
         → 自动收集失败样本
         → 人工归因（检索错/生成错/Prompt 错/模型降级）
         → 修复后重跑
```

**与 Aone 流水线集成**（简历实战）：

```
Aone 流水线自定义组件
├─ EXECUTE：触发评测，返回 executionId
├─ STATUS：轮询执行状态和进度
├─ ABORT：取消执行
└─ 回调凭证未配置时 → 降级为同步执行，避免流水线永久等待
```

## 五、面试高频问答

### Q1：什么是 LLM 幻觉？有哪几种？

幻觉是 LLM 生成的看似合理但与事实不符或无依据的内容。分两类：
- **内在幻觉**：与输入上下文/参考资料矛盾
- **外在幻觉**：编造上下文中不存在的内容（API、参数、链接）

### Q2：幻觉能消除吗？

不能。幻觉是 LLM 自回归生成机制的本质决定的——模型生成的是「最可能的下一个 token」，不是「事实查询结果」。工程目标是**可检测、可归因、可兜底**，不是消除。

### Q3：幻觉有哪些治理手段？

三层防线：
1. **预防**：RAG Grounding + System Prompt 强约束 + P0-P4 分级检索 + 低 temperature
2. **检测**：引用溯源 + 事实校验 + LLM-as-Judge + 用户反馈
3. **兜底**：无依据拒答 + 不确定降级 + 高风险人工接管 + badcase 进评测集

### Q4：RAG 能彻底解决幻觉吗？

不能。RAG 大幅降低幻觉但**不能彻底杜绝**：
- 检索幻觉：检索错了或切片断章取义，LLM 基于错误片段生成
- 生成幻觉：LLM 即使有正确上下文也可能添油加醋
- 所以要配合：严格 Prompt 约束 + 引用溯源 + 分级拒答 + 输出校验

### Q5：怎么评测幻觉率？

四步：
1. **建评测集**：黄金问答对 + 线上 badcase + 对抗样本
2. **自动评测**：LLM-as-Judge 判一致性 + 引用覆盖率计算 + 接口真查
3. **人工抽检**：高风险场景全检，高频问题抽检
4. **回归守门**：每次变更跑评测集，幻觉率劣化超阈值阻断发布

### Q6：你在 AgentMate 项目中怎么治理幻觉的？

四招组合：
1. **P0-P4 分级检索**：命中关键词才检索，不相关直接拒答，无法判断反向问——从源头减少幻觉机会
2. **pre/do/post 三态 Hook**：前置 Query 分级 + 后置输出校验，全链路拦截
3. **严格引用溯源**：输出必须带来源，无来源内容标红或拒答
4. **双引擎回归测试守门**：LLM-as-Judge 语义评判 + 接口真查，幻觉率劣化阻断发布

### Q7：幻觉治理中最难的是什么？

**归因难**：发现幻觉容易，难的是定位根因——是检索错了？切片断了？Prompt 约束弱？模型能力不够？需要建立「badcase → 归因分层（检索错/生成错/工具错）→ 修复 → 回归」的数据飞轮。AgentMate 就是通过线上反馈收集 badcase，自动归因分层，修复后加进回归集，形成闭环。

### Q8：temperature 对幻觉有影响吗？

有。temperature 越高采样随机性越大，幻觉风险越高。事实问答/RAG 场景用 0~0.3，创意场景可以 0.7+。幻觉治理场景统一低 temperature。

## 六、易错点

1. **❌ RAG 用了就不会幻觉** → ✅ RAG 大幅降低幻觉但不能杜绝，检索错/生成添油加醋仍会幻觉
2. **❌ 幻觉可以彻底消除** → ✅ 幻觉是生成机制本质决定的，目标是可检测可兜底
3. **❌ 幻觉评测靠人工就行** → ✅ 人工抽检覆盖率低，必须自动化评测 + 回归守门
4. **❌ System Prompt 写了约束就会遵守** → ✅ 模型会遵循大多数情况但不绝对，需要后置校验兜底
5. **❌ 幻觉率越低越好** → ✅ 过度追求零幻觉会导致误拒率飙升，要平衡准确率和召回率
6. **❌ 治理幻觉只需要改 Prompt** → ✅ 需要全链路：输入分级 + 检索质量 + Prompt 约束 + 输出校验 + 评测回归
