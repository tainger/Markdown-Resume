# 沙箱机制

> AI应用开发 · 面试题集

围绕「沙箱（Sandbox）」整理的面试题，覆盖基础概念、实现方式、AI Agent 语境下的应用与边界踩坑。每题附参考答案要点。

## 一、基础概念

### Q1 什么是沙箱？为什么 AI 应用需要沙箱？

**沙箱**是一种受控的隔离执行环境，让不可信代码/程序在受限空间内运行，即便其恶意或出错，也无法波及宿主系统。

AI 应用尤其需要沙箱，因为：

- **执行不可信代码**：LLM 生成的代码可能含 bug 或恶意行为，不能直接在宿主跑；
- **工具调用风险**：Agent 调用的工具（shell、文件操作）可能被提示注入劫持；
- **多租户隔离**：不同用户的执行要互不可见、互不可干扰。

> 一句话：沙箱把「执行不可信内容」的风险，圈在一个炸了也不波及宿主的笼子里。

### Q2 沙箱、隔离、虚拟化是什么关系？

| 概念 | 含义 | 关系 |
|:---|:---|:---|
| 隔离 | 把不同执行体分开的总目标 | 上位概念 |
| 沙箱 | 实现隔离的一种受控环境 | 隔离的具体形态 |
| 虚拟化 | 实现隔离/沙箱的底层技术 | 沙箱的构建手段 |

隔离是目标，沙箱是形态，虚拟化是手段——三者层层落地。

## 二、实现方式

### Q3 沙箱有哪几种实现方式？对比一下

主流四种：

| 方式 | 隔离强度 | 性能开销 | 启动速度 | 典型代表 |
|:---|:---|:---|:---|:---|
| **语言级**（解释器限制） | 弱 | 极低 | 极快 | Python `RestrictedPython`、JS 沙箱 |
| **进程级**（系统调用过滤） | 中 | 低 | 快 | seccomp / namespaces / gVisor |
| **容器** | 中高 | 低 | 秒级 | Docker / Firecracker microVM |
| **虚拟机** | 高 | 高 | 分钟级 | KVM / 传统 VM |

AI 代码执行通常选**容器 + microVM**（Firecracker）——隔离够强、启动够快、开销可控。

### Q4 为什么 AI Agent 执行代码常用容器沙箱，而不是直接解释器沙箱？

解释器沙箱（如限制 Python 内置）只能防「语言层」攻击，防不住：

- 调系统调用读 `/etc/passwd`；
- fork 子进程绕过限制；
- 触发解释器自身的 C 层漏洞。

容器沙箱在**操作系统层**隔离（独立文件系统/网络/进程空间），即使代码想调系统调用，看到的也是沙箱内的伪环境。**对不可信代码，OS 层隔离比语言层可靠得多。**

## 三、AI Agent 语境

### Q5 AI Agent 为什么要给工具调用加沙箱？

Agent 的工具一旦能碰真实世界（shell、文件、网络），风险来自两头：

- **模型想错了**：调错工具、传错参数；
- **模型被骗了**：提示注入让它去执行恶意操作。

沙箱的作用是「**兜底**」——即使上面两种情况发生，炸的也只是沙箱，不波及宿主和真实环境。

> 模型被骗不可完全防，但「被骗之后干不成坏事」是可以靠沙箱保证的。

### Q6 沙箱和权限模型怎么配合？

两者互补，不是二选一：

- **权限模型**决定「**能不能做**」——高危操作拦截、人工确认；
- **沙箱**决定「**做了能炸多大**」——即便放行也限范围。

```
模型想调 rm -rf /data
    ↓
[权限] 高危 → 拦截/人工确认
    ↓
[沙箱] 即便放行，/data 只是沙箱内挂载，炸不到宿主
```

权限是「事前拦」，沙箱是「事后兜」，两层叠加才敢让 Agent 上生产。

### Q7 提示注入与沙箱的关系？

提示注入（prompt injection）骗模型去调危险工具，沙箱是它最后的防线：

- 输入净化、权限确认能**降低**注入成功率，但防不住隐蔽的间接注入；
- 沙箱**保证**即使注入成功、模型真的去调危险工具，爆炸半径被圈住。

> 提示注入防不住，但后果能兜住——靠的就是沙箱。

## 四、边界与踩坑

### Q8 沙箱的局限是什么？能防住什么、防不住什么？

| 能防住 | 防不住 |
|:---|:---|
| 文件越权访问（隔离 FS） | 模型输出泄露敏感信息 |
| 网络外联（禁网/白名单） | 提示注入本身（只能兜后果） |
| 资源耗尽（限额 CPU/内存） | 业务逻辑错误（代码写对了但逻辑错） |
| 进程逃逸（namespace） | 侧信道攻击（高级） |

沙箱是「**物理隔离 + 资源限额**」，不是「**逻辑正确性保证**」。

### Q9 设计一个 AI 代码执行沙箱要考虑哪些维度？

至少六点：

1. **文件系统**：独立 FS，只挂载必要目录，禁读宿主敏感路径；
2. **网络**：默认禁外联，白名单放行；
3. **资源限额**：CPU / 内存 / 执行时长上限，防死循环耗尽；
4. **权限降级**：以非 root 用户运行，最小权限；
5. **一次性**：每次执行用全新沙箱，用完即弃，防状态污染；
6. **可观测**：沙箱内行为全记录，出事能追溯。

> 好沙箱不只「隔离」，还要「**限额 + 一次性 + 可观测**」。

### Q10 什么是沙箱逃逸？怎么防？

沙箱逃逸 = 沙箱内代码利用漏洞突破隔离，访问到宿主。常见路径：

- 容器配置不当（过度挂载、特权模式）；
- 内核漏洞（namespace 突破）；
- 共享资源侧信道。

防护：

- **最小挂载**：不挂 `/`、不挂敏感目录，只挂工作目录；
- **禁特权**：不用 `--privileged`，降权运行；
- **用 microVM**：Firecracker 这类强隔离方案，逃逸难度远高于普通容器；
- **及时打补丁**：内核和运行时漏洞跟进。

> 对真正不可信代码（用户上传脚本），microVM 级隔离是更稳的选择。

---

## 速记三条

1. **隔离是目标，沙箱是形态，虚拟化是手段。**
2. **AI 代码执行选容器/microVM，不选语言级沙箱。**
3. **权限事前拦，沙箱事后兜，两层叠加才上生产。**
