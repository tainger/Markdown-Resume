# ✅AI Agent 的运行指标与容量规划

> 适用对象：gogo-agent / know-engine 这类「多智能体 + ReAct + 工具调用 + RAG + SSE 流式」的企业级 Agent。
>
> 一句话总结：**Agent 系统入口 QPS 很低（1000 DAU 仅 ≈2 QPS），但容量模型与传统 Web 完全不同——真正的压力是「长事务并发 × LLM 调用放大 × Provider 配额 × Token 成本」，规划要按并发数和 RPM/TPM，而不是按 QPS 加机器。**

---

## 一、Agent 与传统 Web 服务的指标差异

| 维度 | 传统 Web（CRUD） | AI Agent |
|:---|:---|:---|
| 请求持续时间 | 50~500 ms | **15~120 s**（多轮 ReAct + 工具） |
| QPS 量级 | 高（百~万） | **低（个位数）** |
| 关键容量指标 | QPS、连接池 | **在途并发数、LLM RPM/TPM** |
| 下游依赖 | DB / Cache | DB / Cache / **LLM Provider / 向量库 / 第三方 API** |
| 成本结构 | 服务器为主 | **Token 费用占大头**（常 > 基础设施 10 倍） |
| 响应方式 | 同步返回 | SSE 流式 + Human-in-the-Loop 挂起 |
| 错误来源 | 代码 bug 为主 | 模型漂移、限流、超时、幻觉、工具级联失败 |
| 容量定律关注 | QPS × RT | **到达率 × 持续时间 = 在途并发（Little 定律）** |

核心认知：**不要拿"QPS 高不高"判断系统压力，要看"同时有多少个几十秒的长任务在跑"。**

---

## 二、指标全景（四层）

```
┌──────────────────────────────────────────────────────────┐
│ L4 业务效果层   DAU/留存/任务完成率/重试率/点踩率           │
├──────────────────────────────────────────────────────────┤
│ L3 质量层       意图准确率/工具选择正确率/幻觉率/拒答率     │
├──────────────────────────────────────────────────────────┤
│ L2 成本性能层   Token/会话、RPM、首token延迟、P95、命中率  │
├──────────────────────────────────────────────────────────┤
│ L1 系统稳定层   在途并发/QPS/错误率/熔断率/SSE连接数/资源   │
└──────────────────────────────────────────────────────────┘
```

| 层 | 指标 | 说明 |
|:---|:---|:---|
| **L1 系统** | 入口 turn QPS、在途任务并发、SSE 长连接数 | 容量规划核心 |
| | LLM RPM / TPM 峰值 | **决定是否被 Provider 限流** |
| | 错误率、超时率、限流(429)率、熔断触发次数 | 稳定性 |
| | CPU / 内存 / 线程池 / 连接池 | Agent 普遍 IO 密集，CPU 常 <30% |
| **L2 成本性能** | 首 token 延迟（TTFT）P50/P95 | 用户体感第一指标 |
| | 单 turn 耗时、单任务总耗时 | |
| | Token/turn、Token/任务、prompt cache 命中率 | 成本闸 |
| | 意图 L1/L2 短路命中率、工具平均调用次数 | 架构优化效果 |
| **L3 质量** | 意图识别准确率、工具选择正确率、参数正确率 | 见 RAG评测/Agent评测系列 |
| | Faithfulness、幻觉率、拒答率 | |
| **L4 业务** | DAU、人均会话/轮次、任务完成率 | 容量推算输入 |
| | 重试率、追问率、放弃率、点赞点踩 | 隐式质量反馈 |

## 三、1000 DAU 容量推算（含可调公式）

### 3.1 推算链路（从 DAU 到机器规格）

```
DAU
 └─× 人均会话数 × 每会话轮次 = 日 turn 数（用户消息数）
      └─÷ 活跃窗口秒数 × 峰谷系数 = 峰值 turn QPS
           ├─× 单turn内部LLM调用次数 = LLM 峰值 QPS → RPM
           ├─× 单turn耗时（Little定律）= 在途任务并发
           └─× 平均 token = TPM 峰值 / 日成本
```

### 3.2 输入参数三档（按业务活跃度替换）

| 参数 | 保守 | 中等 | 积极 |
|:---|:---|:---|:---|
| DAU | 1000 | 1000 | 1000 |
| 人均会话数/天 | 2 | 3 | 5 |
| 每会话轮次 turn | 4 | 6 | 8 |
| **日 turn 数** | **8,000** | **18,000** | **40,000** |
| 每 turn 内部 LLM 调用次数 | 3 | 5 | 8 |
| 每 turn 工具调用次数 | 2 | 5 | 10 |
| 单 turn 端到端耗时 | 15~30s | 20~60s | 30~120s |
| 活跃窗口 | 10h（工作时间集中） | 同左 | 同左 |
| 峰谷系数 | ×3 | ×4 | ×5 |

> 企业内部系统（差旅/审批）峰谷比高于 toC 产品，早 9 点、午后 2 点明显尖峰。

### 3.3 入口 QPS（中等档，18,000 turn/天）

| 口径 | 公式 | 结果 |
|:---|:---|:---|
| 全天平均 | $18000/86400$ | ≈ **0.2 QPS** |
| 10h 活跃窗口平均 | $18000/36000$ | ≈ **0.5 QPS** |
| **峰值** | $0.5\times 4$ | **≈ 2 turn/s（按 3 预留）** |

### 3.4 内部放大后的下游负载（峰值 2~3 turn/s）

Agent 每收 1 条用户消息，内部扇出大量调用（三层意图识别 + Master + 子 Agent ReAct + 总结）：

| 下游 | 放大倍数 | 峰值量级 |
|:---|:---|:---|
| **LLM 接口** | ×5 | **8~15 QPS ≈ 500~900 RPM** |
| **MySQL**（会话/消息/订单/Hook 落库） | ×15~30 | **40~80 QPS** |
| **Redis**（session/熔断/TTL 上下文/缓存） | ×20~50 | 100~200 QPS（无压力） |
| **Embedding**（L1 miss 才走 L2） | ×0.5 | ≈1 QPS |
| **向量库 / RAG**（信息类 turn 占 20~40%） | ×0.3 | 0.5~1 QPS |
| **外部业务 API**（机票/酒店/天气） | ×0.5~1 | 0.5~2 QPS（受第三方限流） |

> 经验法则：**入口 1 QPS ≈ LLM 5~8 QPS（300~500 RPM）**，这是与 Provider 谈配额的核心换算。

## 四、并发模型：Little 定律（面试高频）

$$L = \lambda \times W$$

- $L$：系统中平均在途任务数（并发）
- $\lambda$：任务到达率
- $W$：单个任务平均停留时间

代入中等档（峰值 2 turn/s，单 turn 30s）：

$$L = 2 \times 30 = \textbf{60 个在途任务}$$

| 并发资源 | 估算 | 量级 |
|:---|:---|:---|
| 在途 turn 任务 | 2/s × 30s | **40~80** |
| 在途 LLM 请求（每 turn 瞬时 0.3~0.8 个） | 60 × 0.5 | **20~50 并发** |
| SSE 长连接（同时在线 = DAU×5~15%） | 1000×10% | **50~150 条** |
| 出口带宽 | 60 连接 × 1~5KB/s | 2~4 Mbps（可忽略） |

**结论**：单台 4C8G 在 QPS 意义上极闲，但它扛的是几十条持续几十秒的流式长事务——**线程模型（响应式/异步）和上下文内存比 CPU 重要**。

## 五、Token 与成本（1000 DAU 的真正大头）

假设（多智能体上下文 + 工具结果经压缩后）：每 turn 输入 20k token、输出 1k。

| 口径 | 输入 | 输出 |
|:---|:---|:---|
| 日（18,000 turn） | **3.6 亿** | 0.18 亿 |
| 月 | **≈ 100 亿** | ≈ 5 亿 |
| 月费用（混部粗估） | — | **¥1 万 ~ 5 万** |

成本杠杆（按收益排序）：

1. 意图 L1/L2 短路命中率（40~70%）——命中即省一次问题改写/路由 LLM；
2. prompt cache 命中率（30~60%）——system prompt + 历史前缀按缓存价计费；
3. 工具结果压缩 + Redis 中转，禁止把 10K+ JSON 回灌上下文；
4. 模型分档——查询用小模型，规划/下单才用强模型；
5. 规划阶段开深度思考、执行阶段关思考（PlanAwareThinking 思路）。

## 六、延迟与质量目标（可写进 SLO）

| 指标 | 建议目标 |
|:---|:---|
| 首 token（TTFT）P50 / P95 | 1~3s / 5~8s |
| 完整 turn P50 / P95 | 15~40s / 60~120s |
| 端到端错误率（含 LLM 超时/限流） | < 1~2% |
| L1+L2 意图短路命中率 | 40~70% |
| Prompt cache 命中率 | 30~60% |
| 可用性 | 99.5~99.9%（上限受 LLM Provider 牵制） |

## 七、容量配置建议（1000 DAU）

| 组件 | 配置 | 说明 |
|:---|:---|:---|
| 应用服务 | **2 实例 × 4C8G** | IO 密集；调大 HTTP 连接池(50~100)、boundedElastic 线程数；WebFlux 适配长事务 |
| MySQL | 2C4G 云 RDS 基础版 | 40~80 QPS 远未到瓶颈，盯慢查询/长事务即可 |
| Redis | 1G 标准版 | 价值在中断广播、熔断共享状态、会话续跑 |
| 向量库 | 入门规格 | 个位数 QPS |
| 聊天记录 | ≈ 8KB/turn → 150MB/天 → **4~5GB/月，半年≈25GB** | 含 timeline/plan 等 extra JSON |

### 上线前必须处理的三件事（按踩坑概率排序）

1. **LLM Provider 提额**：峰值 500~900 RPM、TPM 峰值约 20~30 万；很多默认配额只有 60~600 RPM，**不提额上线必被限流**，比加机器重要。
2. **第三方工具限流**：机票/酒店 API 普遍 5~20 QPS 且按账号限流 → 多租户 API Key 注入 + 工具熔断/退避必需。
3. **SSE 与内存治理**：100+ 长连接 + 会话级 prototype Bean/历史缓存 → emitter 超时、断连清理、挂起任务恢复（Human-in-the-Loop）。

## 八、面试问题（运行指标方向）

> 答题骨架遵循：**先纠正认知（QPS 不重要）→ 给推算链路（DAU→turn→放大→并发）→ 给数字 → 落回工程手段**。

### Q1：1000 DAU 的 Agent，QPS 大概多少？需要什么配置？

**答题骨架**：
1. 先算 turn：1000 DAU × 3 会话 × 6 轮 ≈ 1.8 万 turn/天，10h 活跃窗口平均 0.5 QPS，峰值 ×4 ≈ **2 QPS**；
2. 强调 QPS 有迷惑性——Agent 单 turn 30s，用 Little 定律 $L=\lambda W$ 得 **60 个左右在途任务**、20~50 个在途 LLM 请求、50~150 条 SSE 连接；
3. 内部放大：LLM ≈ 500~900 RPM、MySQL 40~80 QPS；
4. 配置：2×4C8G 足够，**瓶颈是 LLM 配额（RPM/TPM 提额）和长事务治理，不是机器**。

### Q2：Agent 系统和传统 Web 服务做容量规划最大的区别是什么？

**答题骨架**：传统是 $QPS \times RT$（毫秒级、无状态短请求），按 QPS 水平扩机器；Agent 是**到达率 × 几十秒持续时间 = 高在途并发**，瓶颈在 LLM Provider 配额、Token 成本、第三方限流；成本主体从服务器变成 Token 费；必须 SSE 流式 + 异步响应式线程模型。

### Q3：首条消息返回很慢（30s 才出字），怎么优化？

**分层答**：
- 体感层：SSE **首 token 先推 thinking/progress**，把 TTFT 压到 1~3s，完整结果后台流；
- 路由层：意图 L1 规则/L2 向量短路（<100ms），高置信直跳子 Agent，省掉问题改写和 Master 路由（1~3s）；
- 模型层：规划才开深度思考，执行/查询关思考；模型分档；
- 检索层：并行工具调用、缓存（政策/偏好/API Key）、embedding 预计算；
- 基础设施：连接池预热、就近区域 endpoint、prompt cache。

### Q4：怎么估算一个 Agent 功能上线后的 Token 成本？

**骨架**：DAU → 日 turn → 每 turn 平均输入/输出 token（区分不同意图类型加权）→ 日/月量 × 分档单价；再给优化杠杆（短路率、cache 命中率、工具结果压缩、模型分档），强调"**省一次 LLM 调用比优化单次 token 更有效**"。

### Q5：LLM Provider 返回 429 限流，系统会怎样？怎么设计？

1. 现象：峰值 RPM 超配额、TPM 打满、突发并发；
2. 客户端：**指数退避 + 抖动重试**、请求级超时、信号量/令牌桶做客户端限流削峰；
3. 架构层：意图短路减少调用、结果缓存、非关键路径（标题/推荐问题）异步化降级、多模型/多 Key 容灾；
4. 运营层：按峰值 RPM/TPM **提前提额**，监控 429 率与排队时长；
5. 用户层：流式进度提示，而非超时白屏。

### Q6：SSE 长连接很多时服务端要注意什么？

- 响应式/异步（WebFlux）避免一个连接占一个 Servlet 线程；
- TTL/Reactor Context 在 `boundedElastic` 与 SDK 回调线程间的传播（TransmittableThreadLocal）；
- emitter 超时与断连检测（客户端关闭要能取消上游任务，避免空跑烧 Token）；
- 集群下停止/续跑用 Redis Pub/Sub 广播；挂起（ask_user）状态持久化可跨节点恢复；
- 反向代理（Nginx/网关）的 `proxy_read_timeout`、buffering 关闭。

### Q7：Agent 的"慢"定位在哪一层？怎么做可观测？

**分层埋点**：意图识别耗时（L1/L2/L3 各一段）、问题改写、Master 路由、每次工具调用、每次 LLM 请求（TTFT + 总耗时 + token 数）、rerank、总结。用 trace 串起整条 turn，形成"慢查询"视图（类似 TruLens/Phoenix）。指标：各层 P95、工具调用次数、cache 命中率、429/熔断率。**没有分阶段耗时，Agent 的慢无法归因。**

### Q8：DAU 涨 10 倍（1 万），系统最先挂的是哪里？

按顺序：① LLM Provider RPM/TPM 配额（最先）；② 第三方工具按账号限流；③ SSE 长连接/内存与单实例线程池；④ MySQL 写入（消息表，先到几百 QPS）；⑤ Redis（通常最晚）。应对：无状态水平扩展应用层 + 配额扩容/多供应商 + 消息存储分表/冷热分离，而不是盲目升配。

### Q9：怎么衡量 Agent 系统"跑得好不好"？（指标体系）

四层作答：L1 系统（并发/RPM/错误率/熔断）、L2 成本性能（TTFT、P95、token/turn、cache 命中率）、L3 质量（意图准确率、Faithfulness、幻觉率）、L4 业务（完成率、重试率、点踩率）。强调**业务指标 + 成本指标必须和质量指标一起看**，否则会出现"延迟降了但任务完成率也降了"。

### Q10：第三方工具（机票/酒店 API）不稳定怎么办？

超时 + 重试（仅网络类错误、指数退避）+ **熔断器三态（关闭/打开/半开，Redis 共享集群状态）** + 降级（换备用 Skill/数据源/告知稍后重试）+ 结果缓存；写操作（下单）必须幂等键 + 写后查库验证，不能盲目重试。

## 九、易错点

1. **用 QPS 衡量 Agent 容量**——错，应用 Little 定律看在途并发与 RPM。
2. 只算平均不算峰值——企业应用峰谷系数 3~5，配额按峰值报。
3. **把 LLM 当无限容量内部服务**——RPM/TPM 是硬约束，不提额必挂。
4. 只盯 P50 不盯 P95——Agent P95 常是 P50 的 3~5 倍（工具重试/限流退避）。
5. Token 成本只看输出——多智能体输入（上下文+工具结果）往往是输出的 10~20 倍。
6. 客户端断连不取消任务——后台继续空跑烧 Token，是隐性成本黑洞。
7. 把"准确率"当唯一质量指标——忽略成本、延迟、工具安全。
8. SSE 网关用默认超时（常 60s）——长任务被网关静默掐断。

---

## 十、一句话总结

**入口按 QPS 算账（≈2）、容量按并发算账（≈60 在途）、配额按 RPM 算账（≈900）、成本按 Token 算账（月万元级）、体验按 TTFT 算账（<3s）**——五个账本分开，才是 Agent 运行指标的正确打开方式。
