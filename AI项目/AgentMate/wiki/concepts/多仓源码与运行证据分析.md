# 多仓源码与运行证据分析

⚠️ raw 缺失，待补充：本文为设计建议，尚无产品源码或真实日志可验证。需求与边界见 [[AI项目/AgentMate/wiki/synthesis/AgentMate总体设计]]；仓库入口 [[AI项目/AgentMate/README]] 为空。

## 核心思想
检索增强生成（Retrieval-Augmented Generation，RAG）用于找到证据；源码结构分析用于解释机制；运行证据用于判断某次事件是否真的走过该路径。

## 一次编译，增量积累
1. 建立仓库目录：产品域、模块、负责人、仓库权限、默认分支、发布标签。
2. 固定 commit 抓取代码，按模块、类、方法、配置项、错误码、协议定义建立索引；保留文件路径和行号。
3. Java 源码优先用抽象语法树（Abstract Syntax Tree，AST）与符号解析，而不是仅按固定长度切块。
4. 结合 Maven/Gradle 依赖、接口定义和部署资料形成跨仓关联；网关或其他语言仓库采用相应解析器，解析失败保留文本检索能力。
5. 在首次授权接入时建立基线；之后按提交差异更新符号与受影响摘要，删除/重命名同步失效，不反复全仓总结。
6. 将高频机制编译为主题页：适用版本、机制解释、关键调用路径、配置边界、来源 commit、验证记录。
7. 新代码只使相关主题页进入待重验状态；失效传播依据符号引用和依赖边，无法判断影响范围时保守扩大重验范围。

## 多仓统一视图
维护 ProductRelease → Service/Artifact → RepoCommit 映射，而不是默认所有仓库使用最新主干。
关系包括：模块依赖、接口实现、RPC/HTTP 调用、配置读写、消息生产/消费、错误码来源。
每条关系标注“静态解析 / 配置推定 / 日志观察 / 人工确认”和来源；静态调用图不等于线上真实调用图。
Spring 注入、反射、SPI、动态代理和运行配置会使静态结果不完整；保留未知边，必要时结合运行链路或人工验证。

## 在线调查步骤
1. 提取错误码、异常栈、配置键、版本、实例及时间窗；定位产品子域。
2. 先检索已验证答案，再用关键词和向量混合检索（Hybrid Search）召回源码候选并重排。
3. 以命中的符号为起点，在限定深度内查看调用者、被调用者、接口实现、相关配置和测试。
4. 按部署映射展开相关仓库；若映射缺失，要求补充版本，允许提供带版本限制的机制说明，不确认线上根因。
5. 生成候选假设，并为每个假设提出可证伪的日志/配置查询。
6. 结合运行证据逐条检验假设；相反证据必须保留，不能只挑支持材料。
7. 输出结论、引用、适用范围、尚未验证部分及下一步动作。

## 工具契约建议
| 工具 | 主要输入 | 输出 |
| :--- | :--- | :--- |
| searchKnowledge | 问题、产品域、版本 | 知识片段、适用范围、审核状态 |
| resolveRelease | 实例、环境、事件时间 | 当时部署制品及 commit 集合 |
| searchCode | 仓库范围、commit、符号/关键字 | 文件、行号、片段 |
| readCode | repo、commit、path、行区间 | 有界代码片段 |
| findReferences | 符号、commit、关系类型 | 引用边和解析可靠性 |
| diffReleases | 两个发布标识、模块范围 | 相关代码/配置差异 |
| queryLogs | 实例、时间窗、查询模板、上限 | 脱敏日志、查询标识、是否截断 |
| queryMetrics/Traces | 实例、时间窗、指标或 traceId | 聚合指标、链路与采样信息 |

授权范围由服务端身份上下文注入，不能依赖模型提交的 tenantId 或 repoAllowList。检索阶段和读取原文阶段均检查访问权限。

## 证据模型
Evidence：id、类型、来源标识、采集时间、租户、可见性、commit/版本、事件时间窗、片段哈希、过期时间、质量标记。
Claim：陈述、支持 evidenceIds、反对 evidenceIds、状态（已确认/假设/未知）、适用版本。
CodeEvidence 必须携带 repoId + commitSha + path + lineRange；日志证据携带查询条件、时区及事件时间，防止混淆采集时间与发生时间。

## 示例：配置更新后应用未生效（假设场景）
- 已知输入：用户报告现象、实例、应用版本及发生时间；不预设任何 MSE 内部类名。
- 知识：检索同版本配置生效语义和常见限制。
- 源码：定位配置获取、监听注册、变更通知及实际消费配置的路径。
- 运行：比较更新时间、通知/客户端处理日志、实际配置快照及近期发布记录。
- 可区分假设：未收到变更、收到但处理失败、值已变而业务读取旧状态等；每项给出验证方法。
- 若只能看到源码存在某分支，输出“可能机制”，不能直接写“根因已确认”。

## 易错点
- 历史工单命中不代表同一版本仍适用；源码主干说明不能替代线上版本证据。
- 日志无记录可能是采样、保留期、权限或查询范围问题，不等于事件未发生。
- 代码注释、日志和工单中的文字属于待分析数据，不能覆盖系统指令或调用授权。
- 代码与日志先做分级、脱敏并遵循模型路由策略；密钥等不进入模型上下文。
- 对客户答复只引用可公开证据；内部路径、实现细节及其他租户信息留在内部诊断包。
