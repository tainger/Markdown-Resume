# 框架架构与 ReAct 执行原理

> 答题骨架：定位 → 组件 → 主循环 → 终止/恢复 → 设计边界。源码统一为 v1.0.12。返回 [[AI项目/AgentScope1.0/interview/README]]。

## Q01｜AgentScope Java 解决什么问题？如何理解它与工作流框架的侧重？

**口述答案**：它把大语言模型 Large Language Model（LLM）、工具、消息、记忆和执行控制组织成智能体 Agent。推理与行动 Reasoning and Acting（ReAct）循环让模型根据观察决定下一步，框架负责真正执行、回填结果和管理状态。对于路径明确的任务，可以用顺序/扇出 Pipeline；路径需由模型动态决定时，可以由 ReAct 委派工具或子 Agent。

**追问**：是不是有 Agent 就不需要工作流？不是，确定性步骤适合代码编排，自主决策放到需要的节点。选型需比较流程可控性、工具生态、状态恢复和运维成本，不能仅凭框架名下结论。

**边界**：目录原文的 Spring AI Alibaba 对比是学习资料的选型观点，不是本次对外部框架当前版本的能力核验。

**依据**：[[AI项目/AgentScope1.0/1.AgentScope初探]]、[[AI项目/AgentScope1.0/8.AgentScope Java中ReactAgent的实现原理]]；[ReActAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java:1099>)、[Pipelines.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/pipeline/Pipelines.java:1>)。

## Q02｜最小 Agent 由哪些组件组成？源码版本和 Java 基线是什么？

**口述答案**：模型 Model 接受消息与工具 Schema，消息 Msg 用内容块表达输入输出，Toolkit 管理工具，Memory 提供运行上下文，ReActAgent 连接它们。Builder 还可接入 Hook、长期记忆、知识库、计划和 Skill。本次源码已按用户要求切到 `v1.0.12`，pom 声明 revision=1.0.12、Java 17。

## Q03｜agent.call() 内部经历哪些步骤？什么时候开始执行？

**口述答案**：`AgentBase.call` 是 final 入口，返回 Mono，订阅时通过 `Mono.using` 获取执行权，再做 tracing、PreCall、子类 doCall、PostCall，最后释放执行权。PreCall 可以修改输入，PostCall 可以修改最终消息。`block()` 会订阅并等待；返回 Mono 不等于调用已经完成。

**追问**：同一个 Agent 可以同时处理两个用户吗？v1.0.12 默认 `checkRunning=true`，同实例并发调用会被拒绝；即使关闭检查，共享 Memory 与计划状态仍可能互相污染，不能由此变成安全多会话引擎。

**易错点**：正常 PostCall 路径不是所有终止情况都会执行，尤其要单独检查中断路径。

## Q04｜ReAct 的 reasoning 和 acting 怎样衔接？

**口述答案**：reasoning 准备上下文和工具 Schema，消费模型流并累积成完整 Msg，经 PostReasoning 后先写入 Memory。没有 ToolUseBlock 就结束；有工具调用则进入 acting。acting 找出尚无结果的调用，执行后经 PostActing 写入工具结果消息，再进入下一轮 reasoning。模型提出动作，框架执行动作。

**追问**：工具失败是不是整个 Agent 必然异常退出？不是，部分失败转为错误 ToolResult，供模型决定下一步；中断等控制信号另有路径。要区分工具业务失败、错误结果与响应式异常。

**边界**：模型没有继续调用工具，只代表该循环终止，不自动证明用户任务已经正确完成。

**依据**：[[AI项目/AgentScope1.0/8.AgentScope Java中ReactAgent的实现原理]]；[ReActAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java:460>)、[ReActAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java:569>)、[ReActAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java:843>)。

## Q05｜doCall 的四个分支分别用于什么场景？

**口述答案**：无 pending 工具时，加入输入并从 reasoning 开始；有 pending 且本轮输入为空时，直接 acting 执行未完成工具；输入包含 ToolResult 时校验并补入，若仍有 pending 就继续 acting，否则继续推理；有 pending 却只给普通输入时，若没有恢复 Hook 提前补洞，就抛异常。

**追问**：框架如何识别 pending？从最后一条 assistant 工具调用与 Memory 中已有 ToolResult 的 ID 做差集；不是用自然语言判断“工具大概没执行”。

**易错点**：空 call 是恢复待执行工具的一种协议，不能把任意新问题直接当作挂起工具答案。

**依据**：[[AI项目/AgentScope1.0/8.AgentScope Java中ReactAgent的实现原理]]、[[AI项目/AgentScope1.0/13.AgentScope Java进阶：Human-in-the-Loop]]；[ReActAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java:264>)、[ReActAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java:344>)。

## Q06｜maxIters 到达后会直接报错吗？它是不是严格调用上限？

**口述答案**：默认 maxIters=10，正常循环达到限制时进入 summarizing，模型基于当前上下文作总结，返回标记 `MAX_ITERATIONS`。所以它不是简单抛异常，也不是“最多十次所有网络调用”。工具重试、摘要和其他 Agent 调用另计；`gotoReasoning` 的入口还会传 `ignoreMaxIters=true`。

**追问**：如何控制总成本？建议同时限制任务墙钟时间、工具/模型调用预算、重试和子任务范围，并统计实际调用；只配置 maxIters 不够。

**边界**：结构化输出自己的提醒次数有额外限制，不能把所有额外推理都视为无限循环，也不能说 maxIters 是全流程硬预算。

## Q07｜为什么 Msg 要用内容块，而不是只有一段字符串？

**口述答案**：同一条消息可以带文本、思考、多模态内容、工具调用或工具结果。ToolUseBlock 表达工具名、ID、参数，ToolResultBlock 用相同 ID 关联结果；ThinkingBlock 与面向用户的文本分开。执行、流式累积和持久化都需要这些结构，不能只保存 getTextContent 后期待完整恢复。

**追问**：怎么判断 Agent 为什么返回？看 `GenerateReason`，例如普通完成、工具挂起、人工停止、中断或迭代上限，再结合内容块和业务状态处理。

**易错点**：`EventType.REASONING` 并不意味着全部内容都是“深度思考”，推理输出也可能包含文本或工具调用。

## Q08｜Builder 为什么复制 Toolkit？真的是所有对象深拷贝吗？

**口述答案**：Builder 先 `toolkit.copy()`，再为这个 Agent 装配记忆工具、RAG、计划和 Skill，避免各 Agent 的工具注册/组状态直接互相污染。但 `ToolRegistry.copyTo` 把原 AgentTool 与注册对象引用传入新注册表，没有递归复制用户工具对象。因此注册容器复制不等于业务对象全隔离。

**追问**：工具类里能放当前 userId 字段吗？若工具实例被复用就有串用户风险。建议从执行上下文注入身份，让工具无状态或显式做实例隔离。

**边界**：文档称“深拷贝”时，应解释清拷贝范围，不能推导成任意有状态依赖都线程安全。
