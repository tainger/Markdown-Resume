# 工具调用与执行治理

> 答题骨架：定义 → Schema → 参数/上下文 → 激活与执行 → 并发、超时和重试。返回 [[AI项目/AgentScope1.0/interview/README]]。

## Q17｜@Tool 方法如何变成模型能调用的工具？

**口述答案**：Toolkit 注册对象后，从注解和方法签名生成工具描述、参数 JSON Schema 与调用适配。模型返回 ToolUseBlock，工具注册表按名字定位适配器，ToolMethodInvoker 转换参数并反射调用，再把返回值转为 ToolResultBlock。还可以直接实现 AgentTool 控制更复杂的调用行为。

**追问**：工具描述好坏为什么影响效果？模型依赖名称、描述和 Schema 决定何时调用、如何填参数；描述应说清动作、前置条件、参数格式和副作用，但后端仍要校验。

**边界**：Schema 合法不代表订单归属、余额或用户授权合法，业务事实不能靠描述保证。

## Q18｜如何让模型不能伪造 userId？预设参数的优先级是什么？

**口述答案**：模型需要填写的参数标 `@ToolParam`；Agent、ToolEmitter、ToolExecutionContext 和合适的未注解上下文对象由执行层注入，不进入模型参数 Schema。工具从可信业务上下文取身份，再检查资源归属。普通 Toolkit 路径先合并模型输入，再覆盖注册预设参数，因此预设值优先。

**追问**：上下文多个来源冲突怎么办？`ToolExecutionContext.merge` 按传入顺序组成查找链，靠前优先；ToolExecutor 将调用/Agent 上下文放在 Toolkit 默认上下文前。应统一传递同一个身份来源。

**边界**：McpTool 自身的 presetArguments 合并是输入优先，与 Toolkit 层不同；敏感身份不要仅靠 MCP 预设参数保护。

## Q19｜工具组 ToolGroup 是为了省 token，还是权限控制？

**口述答案**：工具组控制一批工具是否激活，未激活工具不应进入当前可用 Schema；执行层也检查 active 状态，拒绝不可用工具调用。这既减少模型选择空间，也提供运行时能力开关。它仍不等于完整业务权限：同一工具被允许调用后，具体资源归属和操作范围还需后端验证。

**追问**：模型还记得之前看到的工具名会怎样？ToolExecutor 不只依赖隐藏 Schema，还做激活检查，因此不能仅因模型知道名字就绕过组状态。

**边界**：不要把全局启用工具当成某个用户已授权执行任意副作用。

## Q20｜parallel=true 具体怎么执行？结果顺序能保证吗？

**口述答案**：ToolExecutor 把每个调用包装为 Mono，并调度到 boundedElastic 或自定义执行器；并行模式用 `Flux.mergeSequential`，可并发订阅但按输入顺序输出结果；顺序模式用 Flux.concat。这样 ReAct 可以按原工具调用顺序与结果配对。

**追问**：所有工具都应该并行吗？只有互不依赖的查询适合。先创建订单再支付、先拿候选 ID 再查详情等要分轮或显式编排；共享可变工具对象也要检查线程安全。

**易错点**：输出有序不代表执行串行；工具并行与多个 Agent 的 fanout 是不同层的并发。

## Q21｜模型调用与工具执行的默认超时/重试相同吗？

**口述答案**：ExecutionConfig 的模型默认超时 5 分钟、最多 3 次尝试，包含首次；初始退避 2 秒、最大退避 30 秒，默认只对限流、服务端错误、超时和网络错误等可重试异常放行。工具默认同为 5 分钟，但最多 1 次尝试，即默认不重试。配置可以被覆盖，不能把常量当每个应用的最终配置。

**追问**：为什么不默认重试工具？工具可能有下单、发信等副作用，失败不等于没执行；在无业务幂等时重试会重复产生结果。

**边界**：最大尝试次数不是重试次数；总耗时还包含退避及多轮调用，不是一个单次 timeout。

**依据**：[[AI项目/AgentScope1.0/2.AgentScope Java特性：流式输出、结构化输出、超时与重试、执行控制]]；[ExecutionConfig.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/model/ExecutionConfig.java:151>)、[ExecutionConfig.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/model/ExecutionConfig.java:169>)。

## Q22｜工具抛 IOException，配了 retryOn 就一定会重试吗？

**口述答案**：不一定，要沿错误信号流核对。v1.0.12 的 `executeCore` 会将普通工具异常转为正常发出的错误 ToolResultBlock；外层 retryWhen 只看异常信号，收到正常错误结果就不会重试。McpTool 也会提前转错误结果；外层调度/超时等异常则可能抵达 retryWhen。

**追问**：超时也会命中 RETRYABLE_ERRORS 吗？工具 applyTimeout 构造的是 RuntimeException，不是 TimeoutException；若谓词仅识别后者/IOException，可能不匹配。不能只看异常文案里的“timeout”。

**建议**：统一错误分类、明确哪些异常应保留到重试层，或显式判断结果码；用假工具计数验证真实尝试次数。以上是静态分析与改进建议，未运行复现。

## Q23｜HTTP 超时、工具超时与 Agent 任务超时怎么区分？

**口述答案**：HTTP 传输层控制连接/读取等等待，ExecutionConfig 控制一次模型或工具执行等待，maxIters 控制推理循环，而整个业务任务还可能包含多轮与多个子 Agent。几层限制互不替代。响应式超时通常会取消上游订阅，但不保证外部系统已经撤销副作用。

**追问**：超时后能直接再次下单吗？应先按业务请求标识查供应商结果，区分成功、失败和未知，再决定是否重试；幂等请求号和状态查询应由业务系统负责。

**边界**：框架没有自动把任意第三方调用变成分布式事务或 exactly-once 执行。

## Q24｜怎样测试一个工具集成，而不依赖真实模型每次都配合？

**口述答案**：分层测。直接构造 ToolUseBlock 测 Schema、参数转换、预设参数与上下文；用假工具测成功、异常、挂起、超时和尝试次数；用固定模型响应验证 ToolUse/ToolResult 配对与 Memory。再对少量关键流程做真实模型集成验证，避免把随机输出当作稳定单测。

**追问**：你会特别测哪些安全场景？缺身份、伪造身份参数、停用组、跨用户资源、重复副作用请求、异常转结果后不重试，以及并行写共享状态。
