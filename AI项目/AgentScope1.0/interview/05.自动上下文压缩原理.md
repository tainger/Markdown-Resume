# 自动上下文压缩原理

> 答题骨架：触发 → 六级策略 → 原文与工作视图 → 重载/持久化 → 成本和质量。返回 [[AI项目/AgentScope1.0/interview/README]]。

## Q33｜AutoContextMemory 如何与 Agent 接上？只换 Memory 就够吗？

**口述答案**：通常同时配置 AutoContextMemory 与 AutoContextHook。Hook 在 PreCall 首次注册 ContextOffloadTool 并关联 PlanNotebook，在 PreReasoning 调用 compressIfNeeded，再用工作记忆构造实际输入，附上需要时调用 context_reload 的说明。只创建 Memory 不等于所有自动集成步骤都已发生。

**追问**：为什么压缩放在推理前？这里能看到即将发送的上下文，并在模型消费前统一更新输入，避免仅压缩内部缓存却继续发送旧消息。

**边界**：该标签 Hook 的 priority 实际为 0，类注释所说的 50 不是运行值；有状态 Hook 不宜跨 Agent 随意复用。

## Q34｜压缩阈值有哪些？字符、消息和 token 怎么区分？

**口述答案**：默认消息数达到 100，或估算 token 达到 `128×1024×0.75=98,304` 时尝试压缩。大负载阈值默认 `5×1024` 字符，卸载预览 200 字符，lastKeep=50 条消息，工具摘要最低 token 阈值 5000。这些都是 v1.0.12 的默认参数，可以被应用覆盖。

**追问**：有一个超长消息就立刻卸载吗？顶层先检查消息数或 token 阈值；未触发时不会只因消息超过 largePayloadThreshold 就直接走整个压缩流程。

**易错点**：50 条消息不等于 50 轮对话，5120 字符不等于 5120 token；默认 128×1024 也不是读取模型真实窗口的自动探测结果。

## Q35｜六级压缩策略按什么顺序执行？

**口述答案**：依次尝试历史工具序列摘要、保护近期消息的大负载卸载、不保护近期消息的大负载卸载、历史轮次摘要、当前轮大消息摘要、当前轮整体摘要。某个策略成功就返回，后续策略这次不再执行。第一级内部最多尝试处理 5 组历史工具消息，不是总共只处理一条消息。

**追问**：是不是始终先用不调用 LLM 的策略？不是，历史工具摘要放在最前，可能调用 LLM；第二、三级卸载才是不调用模型的预览替换。

**边界**：一次策略成功不保证 token 已降到阈值以下，后续推理仍需预算检查；不要把它描述成必然压到安全大小的硬承诺。

## Q36｜摘要与卸载有什么区别？卸载数据默认就在外部数据库吗？

**口述答案**：卸载把原文与 UUID 关联，用预览和标记替代大内容；摘要还调用模型形成语义缩写。AutoContextMemory 的 offloadContext 默认是本实例 HashMap，并不是自动上传外部数据库或对象存储。真正跨重启保存，要把整个 Memory 状态写到 Session。

**追问**：原文还在，为什么模型会忘细节？模型只看到工作视图，不会自动扫描全部原文；它需要发现缺口并用 UUID 重载。因此“可恢复”不等于每次回答无损。

**边界**：卸载能降低模型上下文体积，不保证 JVM 内存更低，因为原始消息和卸载数据仍可能保留。

**依据**：[[AI项目/AgentScope1.0/5.AgentScope Java特性：智能上下文压缩]]、[[AI项目/AgentScope1.0/6.实战：实现AgentScope的三层记忆体系]]；[AutoContextMemory.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/AutoContextMemory.java:97>)、[AutoContextMemory.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/AutoContextMemory.java:807>)、[AutoContextMemory.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/AutoContextMemory.java:812>)。

## Q37｜原始 Memory 和 working Memory 怎样持久化？

**口述答案**：AutoContextMemory 同时维护原始与工作消息，getMessages 返回用于当前推理的工作内容。saveTo 保存 workingMessages、originalMessages，并在存在时保存 offloadContext 和 compressionEvents；loadFrom 对应重建。只保存压缩后的聊天文本，会丢 UUID 对应原文，无法完整重载。

**追问**：有 UUID 标记就能跨节点恢复吗？不够，还需要共享 Session 保存对应内容，并在新节点重建同类 Memory、正确加载这些状态。

**边界**：多个字段的存储操作是否原子由后端/快照设计决定，Memory 的 saveTo 方法本身不能保证分布式一致快照。

**依据**：[[AI项目/AgentScope1.0/3.AgentScope Java特性：多轮会话&会话持久化]]、[[AI项目/AgentScope1.0/5.AgentScope Java特性：智能上下文压缩]]；[AutoContextMemory.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/AutoContextMemory.java:157>)、[AutoContextMemory.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/AutoContextMemory.java:1975>)、[AutoContextMemory.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/AutoContextMemory.java:2084>)。

## Q38｜lastKeep 为什么不能理解为“最近 50 条永远不压缩”？

**口述答案**：它是部分策略选择范围的保护参数。历史工具压缩和第二级大负载卸载会考虑保留近期消息，但第三级会尝试不使用同样的近期保护，后续还可能处理当前轮大消息或整体内容。所以它是渐进降级策略中的偏好，不是永远保留的绝对边界。

**追问**：哪些数据不宜只靠 lastKeep 保证？订单 ID、审批状态、用户确认、精确金额等，应有结构化权威存储；重要原始细节可按需重载，不能仅依赖它留在最近消息里。

**易错点**：`offloadingLargePayload` 某些注释曾说参数未使用，实际代码会按 lastKeep 计算搜索范围，要看实现。

## Q39｜TokenCounterUtil 是模型精确 tokenizer 吗？

**口述答案**：不是，它按文本长度约每 2.5 字符一个 token，再叠加消息、工具调用和结果结构开销作估算；其他内容块多用较小固定开销。它帮助触发压缩，不能代替供应商 usage、账单或对多模态成本的精确计算。

**追问**：模型仍报上下文超限怎么办？要计入系统提示、工具 Schema、多模态内容与输出预算，留安全余量；必要时用对应模型 tokenizer 或更保守估算，再对真实请求验证。

**边界**：该工具传入的是消息列表，不能据它的结果声称已精确统计完整请求和所有外部调用。

**依据**：[[AI项目/AgentScope1.0/5.AgentScope Java特性：智能上下文压缩]]；[TokenCounterUtil.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/TokenCounterUtil.java:47>)、[TokenCounterUtil.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-extensions/agentscope-extensions-autocontext-memory/src/main/java/io/agentscope/core/memory/autocontext/TokenCounterUtil.java:71>)。

## Q40｜如何证明自动压缩有效，又不明显损伤任务质量？

**口述答案**：用相同任务、模型和候选数据，对照压缩前后的输入/输出 token、摘要额外调用、重载次数、总延迟与任务正确率。专门测试压缩前出现的精确事实、工具 ID 结构、长文细节和恢复后 UUID 重载，不能只看文本缩短比例。

**追问**：成本一定下降吗？摘要本身花模型调用，频繁重载还会增加成本；要看整条任务的总 usage 与完成效果。
