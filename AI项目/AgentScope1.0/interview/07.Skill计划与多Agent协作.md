# Skill、计划与多 Agent 协作

> 答题骨架：能力说明与执行工具分开 → 有状态计划 → 委派/流水线 → 权限和恢复范围。返回 [[AI项目/AgentScope1.0/interview/README]]。

## Q49｜Skill、Tool、MCP 与 SubAgent 有什么区别？

**口述答案**：工具 Tool 表达可以执行的动作及其参数契约；技能 Skill 提供完成一类任务的方法、说明与资源，可调用已有工具；MCP 是外部能力的协议适配；子智能体 SubAgent 是独立的 Agent 执行职责。它们可组合，不是四选一：父 Agent 委派子 Agent，子 Agent 加载 Skill，再调用本地或 MCP 工具。

**追问**：写一个 SKILL.md 就能自动下单吗？不能，文档说明不等于可执行能力，仍需注册工具、供应商连接、身份和业务授权。

**边界**：某个 Skill 被模型读过，不等于允许它绕过应用既定的权限与确认流程。

## Q50｜SkillBox 的渐进加载具体怎么工作？

**口述答案**：先注册技能及可发现的名称/描述；SkillHook 在 PreReasoning 向系统提示加入技能目录。模型通过 `load_skill_through_path` 按 skill ID 和资源路径加载正文或资源，SkillToolFactory 执行加载并激活对应技能。Builder 将 SkillBox 绑定到 Agent 的 Toolkit，并注册加载工具和 SkillHook。

**追问**：为什么不把所有正文一次塞入提示词？大多数技能本轮用不到，全文会增加输入成本和选择干扰；先发现再读取更适合大量技能。

**边界**：渐进加载不是无限容量，也不保证模型会选对技能，应检查加载成功、资源路径和工具可用性。

**依据**：[[AI项目/AgentScope1.0/12.AgentScope Java进阶：Skill]]；[ReActAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java:1755>)、[SkillHook.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/skill/SkillHook.java:1>)、[SkillToolFactory.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/AgentScope1.0/repo/agentscope-java/agentscope-core/src/main/java/io/agentscope/core/skill/SkillToolFactory.java:162>)。

## Q51｜Skill 正文加载后会自动从历史中消失吗？

**口述答案**：不能这样保证。加载工具把正文作为工具结果返回并进入运行 Memory，后续推理可能反复携带它。渐进加载主要降低初始注入体积，历史结果是否压缩还取决于配置 AutoContextMemory/Hook 或应用自己的输入折叠方案。

**追问**：deactivateAllSkills 等于删除历史正文吗？不是，技能/工具组激活状态与 Memory 里的旧工具结果是不同数据。需要沿具体 API 看它改变哪个容器。

**建议**：延迟到真正使用前加载，避免全文复制到多条消息；压缩后保留资源定位并支持重载，再评测重复加载与任务正确率。

## Q52｜Skill 的代码执行环境默认就是安全沙箱吗？

**口述答案**：不是。SkillBox 可启用 Shell、读写文件等工具，ShellCommandTool 支持工作目录、命令白名单、审批回调和超时，但这不自动提供操作系统级隔离。未配置白名单时的开放行为也要核对；允许 bash/python 等解释器后，命令名限制不能证明文件和网络都受控。

**追问**：生产怎么收敛？建议优先暴露结构化业务工具；确需执行代码时，配置低权限身份、隔离目录/进程、网络限制、资源预算与审计，并做实际越权和超时测试。

**边界**：这些是部署与应用的建议，不是框架已为任意 Skill 提供了完整多租户安全保证。

## Q53｜Plan-and-Execute 在 v1.0.12 中一定是 Planner/Executor 两个 Agent 吗？

**口述答案**：不是，默认是在同一个 ReActAgent 上挂 PlanNotebook。Builder 注册计划管理工具，再在每轮 PreReasoning 追加当前计划 hint；模型用工具创建、修订和推进计划，执行仍走 reasoning↔acting。它让模型显式跟踪任务，不是另写一个固定 DAG 引擎。

**追问**：hint 是 SYSTEM 消息吗？`getCurrentHint` 返回 USER 角色消息并追加到输入末尾，内部用 system-hint 文本标签组织规则；标签名不改变消息角色。

**边界**：`needUserConfirm=true` 默认会影响计划提示规则，不能据此断言每个业务工具都在服务端验证了用户确认。

## Q54｜PlanNotebook 有哪些状态约束？计划如何保存和展示进度？

**口述答案**：工具涵盖创建/结束计划、修订结构、推进/完成子任务和查询状态。`updateSubtaskState` 会校验索引和状态，标记 IN_PROGRESS 前要求前序任务 done/abandoned，且没有其他进行中任务；标 done 应通过 finish_subtask 带 outcome。状态变化可以触发 change hook，让应用推送进度。

**追问**：默认历史计划能跨进程保存吗？默认 PlanStorage 是内存实现；当前计划可随 Agent 的 Session 状态保存，但历史计划仓库是另一个存储职责，跨重启需明确配置和验证。

**边界**：计划工具中的具体状态校验不等于全业务安全门禁；needUserConfirm 的提示规则也不是一个完整确认凭据系统。

## Q55｜Agent-as-Tool 如何创建子 Agent？会自动永久保存子会话吗？

**口述答案**：SubAgentTool 把子 Agent 包装成 AgentTool，接收 message 与可选 session_id，由 provider 创建实例；继续会话时按配置 Session 加载，执行后保存并返回关联 session ID。可选转发子 Agent 事件给父工具 emitter。

**追问**：默认 Session 是数据库吗？`SubAgentConfig` 未显式配置时使用 InMemorySession，只提供当前配置实例范围内的内存状态，不能声称自动跨节点或跨重启持久化。

**边界**：provider 每次提供什么实例、会话 ID 谁能使用、父子工具权限如何约束仍是应用责任；父 Agent 的业务上下文不会凭空成为子 Agent 的可信身份。

## Q56｜SequentialPipeline 与 FanoutPipeline 的执行/异常语义有什么区别？

**口述答案**：顺序流水线把上一个 Agent 的 Msg 交给下一个，按固定列表串联；Fanout 给多个 Agent 同一输入，可并发或顺序运行。并发实现让各分支完成并收集异常，若有失败最终返回 CompositeAgentException；不能简单当成“自动返回所有部分成功结果”。

**追问**：fanout 返回顺序跟注册顺序相同吗？并发实现用 Flux.merge，结果按到达次序收集；不要按位置盲配评估维度。需要稳定关联就保留来源标识。

**边界**：扇出不自动仲裁冲突、投票或重试；这些应由上层明确实现。原系列没有独立 Pipeline 章节，本题补充底层协作机制。
