> 覆盖 RAG 核心概念、解决的问题、三大经典范式演进、以及业界其他 RAG 范式。

## Q1: 什么是 RAG？它解决了大模型的什么问题？

**难度**: ⭐ 基础

**参考答案**:

RAG = Retrieval-Augmented Generation（检索增强生成），核心是"**先检索、后生成**"——从外部知识库检索相关片段，把检索结果和用户问题一起拼进 prompt，让大模型**基于检索到的资料**来回答。

它主要解决大模型的两大痛点：

1. **幻觉问题**：大模型靠参数记忆知识，可能生成看似合理但事实错误的内容。RAG 为答案提供可核验的依据，但仍可能因检索错误或生成偏离而出错
2. **知识过时/专业领域**：大模型的知识停留在训练截止日，且对垂直领域（企业内部文档、医疗、法律）缺乏覆盖。RAG 让模型"即查即用"

> 来源：[[AI项目/RAG/1.什么是RAG]]

**追问**：RAG 能彻底消除幻觉吗？不能，错误资料、漏召回与生成偏离仍可能导致错误。

## Q2: RAG 和微调（Fine-tuning）有什么区别？各自适合什么场景？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：RAG 主要通过外部资料补充回答依据；微调通过训练调整模型行为。两者可组合，但都不能自动保证事实正确。

| 维度 | RAG | 微调 |
|:---|:---|:---|
| 更新对象 | 文档、索引、检索配置 | 模型参数 |
| 知识更新 | 数据处理并达到查询可见状态后生效 | 重新准备训练数据、训练和验证 |
| 常见目标 | 私有知识、动态信息、可追溯回答 | 领域任务表现、指令遵循、风格与格式 |
| 主要成本 | ETL、索引、检索及生成调用 | 数据标注、训练与部署推理 |
| 来源追溯 | 需要显式保留并校验引用 | 单靠微调难以定位参数知识来源 |

**选型回答**：企业手册经常变更，优先考虑 RAG；回答格式和任务行为需要适配时，再评估微调。不能笼统说 RAG 一定更便宜，也不能把微调只理解为修改语气。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]（本题为系列内容的选型整理）。

**追问**：资料改了就立刻生效吗？需完成处理并达到查询可见状态，再按版本检索。

## Q3: 请描述 RAG 的完整流程

**难度**: ⭐⭐ 中级

**参考答案**:

RAG 分两条链路：**离线索引构建** 和 **在线检索生成**。

**离线链路（ETL）**：
```
原始文档 → 预处理（清洗/标准化）→ 分片 → 向量化（Embedding）→ 存入向量数据库 + 元数据
```

**在线链路（实时）**：
```
用户提问 → 查询改写（可选）→ 向量化 → 向量相似度检索 → Top-K 文档 → 重排序（可选）
→ 构造 prompt（问题 + 检索结果）→ 大模型生成答案 → 返回结果（附引用来源）
```

> 来源：[[AI项目/RAG/2.深入理解RAG技术原理——索引构建]]、[[AI项目/RAG/3.深入理解RAG技术原理——检索生成]]

**追问**：离线与在线如何关联？靠文档版本、片段 ID 和元数据串联索引与来源。

## Q4: Naive RAG、Advanced RAG、Modular RAG 三者有什么区别？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：它们描述基础流程、质量优化和模块化组织方式，不能仅靠检索次数区分，也不必视为互斥类别。

| 范式 | 核心关注 | 示例 |
|:---|:---|:---|
| Naive RAG | 建立检索再生成的基本链路 | 分片、嵌入、检索、拼接上下文 |
| Advanced RAG | 改善检索前、检索中和检索后的质量 | 元数据过滤、改写、混合检索、重排 |
| Modular RAG | 将职责拆为可组合、可替换的组件 | 独立的查询处理、检索器、聚合器、提示增强器 |

同一系统可以按 Modular 方式组织 Advanced 优化；“Advanced 必须写死流程”“Modular 一定检索多次”都不是定义。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]、[[AI项目/RAG/29.Spring AI中的Modular RAG支持]]、[[AI项目/RAG/30.LangChain4J中的Modular RAG支持]]。

**追问**：一个系统能同时属于 Advanced 与 Modular 吗？能，质量优化与组件组织不是互斥分类。

## Q5: Agentic RAG 和 Modular RAG 有什么区别？能否组合？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：Modular 强调组件如何组织，Agentic 强调由谁决定检索动作；两者是不同维度，可以组合。

- **Modular RAG**：查询转换、检索、聚合、上下文注入等职责解耦；可以实现固定顺序，也可以加入路由与分支。
- **Agentic RAG**：Agent 根据任务状态选择是否调用检索、调用哪个数据源、是否继续搜索；其检索工具内部仍可采用模块化流水线。

例如知识客服可采用固定检索流程；跨多个知识源的分析任务可由 Agent 决策后调用不同检索工具。动态决策带来额外调用和流程不确定性，需要限制轮数、总时限与工具权限。

> 来源：[[AI项目/RAG/38.Agentic RAG]]、[[AI项目/RAG/30.LangChain4J中的Modular RAG支持]]。最后的轮数与权限约束为工程设计建议，⚠️ raw 缺失，待补充对应实现。

**深入追问**：

怎样判断证据足够并结束检索？可将问题拆为待核实要点，跟踪已覆盖的证据和仍缺失的条件；达到回答要求则生成，预算耗尽仍缺证据则部分回答、澄清或说明不足。仅由模型说“我很自信”不能证明证据充分。

为查询和已访问来源维护去重状态，检测重复动作或多轮无新增证据；同时限制轮数、总耗时与工具调用。⚠️ raw 缺失，待补充：覆盖判定、循环检测和终止策略实现；此处是对 [[AI项目/RAG/38.Agentic RAG]] 的设计深化。

**追问**：Agent 的检索工具内部能模块化吗？能，Agent 负责决策，工具内部负责执行与证据返回。

## Q6: 什么是 Graph RAG？它和传统向量 RAG 有什么互补性？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：图增强 RAG 利用实体、关系或图结构补充检索。Microsoft GraphRAG 是其中一种具体实现，不能把所有图增强方案都等同于它。

Microsoft GraphRAG 的索引阶段会抽取实体关系、组织社区并生成报告；查询阶段可利用局部实体关联或全局社区信息回答问题。社区检测与报告生成主要属于索引准备，不是每次提问都重新构图。

| 维度 | 向量检索 | 图增强检索 |
|:---|:---|:---|
| 主要线索 | 文本语义相似性 | 实体、关系、社区或图路径 |
| 常见用途 | 局部知识点、操作步骤 | 跨实体关联、语料整体主题 |
| 主要风险 | 证据漏召回 | 抽取错误、图谱更新与构建成本 |

选型先确认问题确实依赖关系或全局聚合；跨文档问题也可能通过多路召回、问题分解解决，并非只有图方案。

> 来源：[[AI项目/RAG/28.RAG优化技术:Graph RAG]]；技术口径校核：[Microsoft GraphRAG](https://microsoft.github.io/graphrag/)（2026-10-20）。

**深入追问**：

固定 Cypher 查询与自动构图的 GraphRAG 有什么区别？前者可能直接使用事先维护的节点、关系和查询模板；后者还需从语料抽取实体关系、组织索引或报告。能回答一个两跳问题，不代表已经完成自动知识图谱构建。应说明图从哪里来、关系是否经过审核、查询如何生成，以及文档变化时如何更新。

可结合 [[AI项目/RAG/28.RAG优化技术:Graph RAG]] 的电影关系示例讲固定图查询；不要把该示例称为已实现 Microsoft GraphRAG 的完整索引与报告流程。

**追问**：图关系一定真实吗？不一定，抽取与消歧错误会影响后续回答。

## Q7: Self-RAG、CRAG、Adaptive RAG 分别解决什么问题？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

三者都涉及按状态调整处理，但机制不同，不能统称为“再加一个提示词自检”。

| 方案 | 关注点 | 核心机制 |
|:---|:---|:---|
| Self-RAG | 按需检索与生成质量控制 | 训练模型生成反思标记，判断检索需求、资料相关性及答案支撑等 |
| CRAG（Corrective RAG） | 检索结果不可靠时如何纠正 | 评估检索质量，结合知识精炼及外部搜索等纠正动作 |
| Adaptive RAG | 根据问题复杂度调整策略 | 选择不检索、单次或迭代检索等路径；具体方式随实现而异 |

**答题边界**：Self-RAG 的反思机制不等于可靠识别所有幻觉；CRAG 的知识精炼也不等于简单做摘要。介绍论文方案时要与自己实现的工程简化版分开。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]；论文校核：[Self-RAG](https://arxiv.org/abs/2310.11511)、[CRAG](https://arxiv.org/abs/2401.15884)（2026-10-20）。

**追问**：提示词让模型自检就等于 Self-RAG 吗？不等于，论文包含训练与反思标记机制。

## Q8: 长上下文（Long Context）模型会取代 RAG 吗？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：选择取决于任务和成本，两者可互补，不能用窗口大小直接判断。

| 维度 | 检索后生成 | 直接使用长上下文 |
|:---|:---|:---|
| 优势 | 在大语料中筛选与当前问题有关的资料 | 减少片段筛选遗漏，便于全文联合阅读 |
| 主要风险 | 漏召回、切片丢失关系 | 无关信息干扰、输入成本和处理时间 |
| 适用判断 | 文档很多、更新频繁、需权限或版本筛选 | 文档有限且可装入窗口，需要通读分析 |

长窗口不保证模型能正确利用每个位置的信息；RAG 也可能因多次模型调用比直接输入更慢。可先检索文档，再把完整章节放入长上下文，用同一评测集比较质量、延迟与费用。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]。

**追问**：长窗口一定更慢吗？不一定，应比较实际输入、缓存、调用链与模型服务。

## Q9: 什么是 RAG-Fusion？

**难度**: ⭐⭐ 中级

**参考答案**:

RAG-Fusion 是**多查询融合**策略：把一个问题用 LLM 改写成多个视角的子问题，每个子问题独立检索，最后用 **RRF（Reciprocal Rank Fusion）** 融合所有结果。

示例：用户问 "R7 续航多少"
```
改写为 3 个子问题：
  - "智界 R7 电池容量"
  - "智界 R7 CLTC 续航里程"
  - "华为 R7 纯电续航"
分别检索 → RRF 融合 → 重排 → 生成
```

**核心公式**：`RRF Score = Σ 1/(k + rank_i)`，k 通常取 60，只依赖排名不依赖原始分数。

**可能收益**：覆盖同一意图的不同表述。保留原查询并限制扩展范围，不能把电池容量、续航和不同车型视为同一个问题；扩展检索可能增加噪声，须通过评测确认。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]、[[AI项目/RAG/27.RAG优化技术：重排序]]

**追问**：多查询一定提升吗？不一定，主题漂移与重复候选可能增加噪声及成本。

## Q10: LLM Wiki 和 RAG 有什么不同？能否组合？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：LLM Wiki 侧重将原始材料预先整理为可维护的知识页；RAG 侧重在回答时检索外部证据。知识整理方式与查询方式可以组合。

| 维度 | 常见 RAG 系统 | LLM Wiki |
|:---|:---|:---|
| 预处理 | 解析、分片、索引，也可做摘要和结构化 | 编译概念、实体、对比和综合页 |
| 查询 | 检索相关内容后生成 | 从索引、双链或页面检索定位知识 |
| 维护风险 | 旧索引、漏召回、版本不一致 | 编译错误、来源丢失、页面未随原文更新 |

不能说 RAG 每次从零处理所有文档，也不能说编译过的知识天然正确。Wiki 页面也可以作为 RAG 的检索语料，同时保留回到原始证据的链接。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]。

**追问**：编译后的知识还要更新吗？要，需随来源变更并保留溯源。

## Q11: 为什么要在基础 RAG 上增加检索优化？如何判断是否值得？

**难度**: ⭐⭐ 中级

**参考答案**:

基础链路可能遇到术语检索不到、版本误召回、候选噪声和上下文不完整。优化应针对错误样本，而不是因为方案名叫 Advanced 就把组件全部打开。

| 问题 | 候选优化 | 验证重点 |
|:---|:---|:---|
| 型号、专有名词漏召回 | 关键词与向量混合检索 | 目标证据是否进入候选集 |
| 版本不匹配 | 元数据过滤 | 错版本样本是否减少 |
| 相关证据排名靠后 | 重排序 | 排名及最终答案质量是否改善 |
| 问题含指代、表达不完整 | 改写或澄清 | 保留原意，避免引入新实体 |
| 上下文冗余 | 去重、抽取或压缩 | 降低输入量时保留关键事实 |

每次先做单项对照，再判断收益是否值得额外延迟、费用和维护成本；没有行业占比数据时，不将“当前生产主流”当作已证实事实。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]、[[AI项目/RAG/interview/06-RAG评测体系]]。

**追问**：一次加上所有模块如何归因？很难，应先做单项和消融对照。

## Q12: 请用一句话 + 类比区分所有主要 RAG 范式

**难度**: ⭐⭐⭐ 高级

**参考答案**:

把 RAG 比作"帮你找资料的助理"：

| 范式 | 一句话 | 类比 |
|:---|:---|:---|
| Naive RAG | 你问 → 助理按问题检索相关资料 → 念给你听 | 实习生助理，只会按流程走 |
| Advanced RAG | 翻之前先查目录关键词、翻完挑最相关的几本 | 有经验的助理，会用工具 |
| Modular RAG | 查目录、翻书、挑书、整理、朗读——每步都可替换 | 团队协作，每个人可以单独换 |
| Agentic RAG | 助理自己判断要不要找、找几次、够不够 | 可决定检索动作的助理 |
| Graph RAG | 助理先画一张知识关联图，顺着图找 | 分析师，看全局关系 |
| Self-RAG | 助理找完念一遍，自己检查念得对不对 | 谨慎的助理，念完自我核对 |
| CRAG | 助理找完先评估资料靠谱不，不靠谱就上网查 | 会辨别资料质量的助理 |
| Adaptive RAG | 先问你是要简单答案还是深度分析，再决定怎么做 | 会区分场景的助理 |
| RAG-Fusion | 助理换 3 个角度各找一遍，合并结果 | 多管齐下 |
| Long-Context | 助理直接把整个书架搬过来给你看 | 通读材料后作答 |

> 来源：[[AI项目/RAG/5.RAG的范式演进]]。

**追问**：这些范式能叠加吗？能，分别说明优化、组件组织、决策和数据结构等维度。
