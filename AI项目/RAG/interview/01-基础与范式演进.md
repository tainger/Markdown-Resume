# 一、基础与范式演进

> 覆盖 RAG 核心概念、解决的问题、三大经典范式演进、以及业界其他 RAG 范式。

---

## Q1: 什么是 RAG？它解决了大模型的什么问题？

**难度**: ⭐ 基础

**参考答案**:

RAG = Retrieval-Augmented Generation（检索增强生成），核心是"**先检索、后生成**"——从外部知识库检索相关片段，把检索结果和用户问题一起拼进 prompt，让大模型**基于检索到的资料**来回答。

它主要解决大模型的两大痛点：

1. **幻觉问题**：大模型靠参数记忆知识，可能生成看似合理但事实错误的内容。RAG 让答案"有依据"
2. **知识过时/专业领域**：大模型的知识停留在训练截止日，且对垂直领域（企业内部文档、医疗、法律）缺乏覆盖。RAG 让模型"即查即用"

> 来源：[[1.什么是RAG]]

## Q2: RAG 和微调（Fine-tuning）有什么区别？各自适合什么场景？

**难度**: ⭐⭐ 中级

**参考答案**:

| 维度 | RAG | 微调 |
|:---|:---|:---|
| 知识来源 | 外部知识库（可随时更新） | 模型参数（改完即固化） |
| 知识更新 | 改文档即可，实时生效 | 需重新训练，成本高、周期长 |
| 可解释性 | 答案有引用来源 | 黑盒，难以追溯知识来源 |
| 适用场景 | 海量动态知识、需要溯源、多领域 | 风格统一、输出格式固定、领域术语内化 |
| 成本 | 低（向量库存储 + 检索计算） | 高（训练算力 + 数据准备） |
| 核心能力 | **知识增强** | **能力增强** |

简单说：**RAG 给模型补充"是什么"的知识，微调给模型植入"怎么说"的风格和格式**。两者不是互斥，实际项目经常组合——先 RAG 补知识，再微调统一语气和输出结构。

## Q3: 请描述 RAG 的完整流程

**难度**: ⭐⭐ 中级

**参考答案**:

RAG 分两条链路：**离线索引构建** 和 **在线检索生成**。

**离线链路（ETL）**：
```
原始文档 → 预处理（清洗/标准化）→ 分片 → 向量化（Embedding）→ 存入向量数据库 + 元数据
```

**在线链路（实时）**：
```
用户提问 → 查询改写（可选）→ 向量化 → 向量相似度检索 → Top-K 文档 → 重排序（可选）
→ 构造 prompt（问题 + 检索结果）→ 大模型生成答案 → 返回结果（附引用来源）
```

> 来源：[[2.深入理解RAG技术原理——索引构建]]、[[3.深入理解RAG技术原理——检索生成]]

## Q4: Naive RAG、Advanced RAG、Modular RAG 三者有什么区别？

**难度**: ⭐⭐ 中级

**参考答案**:

| 范式 | 核心思想 | 检索次数 | 复杂度 | 定位 |
|:---|:---|:---|:---|:---|
| **Naive RAG** | 最朴素的"检索 + 生成"，无优化 | 1 次 | 低 | 入门 Demo、简单 FAQ |
| **Advanced RAG** | Naive + 混合检索/重排序/问题改写/上下文压缩 等优化 | 1-2 次 | 中 | **当前生产环境主流** |
| **Modular RAG** | 各阶段解耦为可独立配置、替换的模块化组件 | 可配置 | 中高 | 企业级、需灵活扩展 |

**演进线**：Naive（能用） → Advanced（好用） → Modular（可扩展）

> 来源：[[5.RAG的范式演进]]

## Q5: Agentic RAG 和 Modular RAG 有什么本质区别？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

关键区别在 **"谁来决定做什么"**：

- **Modular RAG**：预定义流水线（改写→检索→重排→生成），**流程固定**。像装配线，每个工位做什么、顺序是什么，提前写死
- **Agentic RAG**：把 RAG 当作 Agent 的**一个工具**，**Agent 自主决策**——要不要检索？检索几次？结果够不够？不够就改写查询再搜一轮

```
Modular RAG（固定流程）：
  用户提问 → 改写 → 检索 → 重排 → 生成（写死顺序）

Agentic RAG（动态决策）：
  用户提问 → Agent："要检索吗？" → 是 → 检索
  → Agent："结果够吗？" → 不够 → 改写再检索
  → Agent："现在可以生成了吗？" → 是 → 生成
```

Modular RAG 适合**流程明确**的场景（如智能客服），Agentic RAG 适合**复杂多步推理**场景。

> 来源：[[5.RAG的范式演进]]、[[38.Agentic RAG]]

## Q6: 什么是 Graph RAG？它和传统向量 RAG 有什么互补性？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

Graph RAG 是微软 2024 年提出的方案，用**知识图谱**替代/补充向量检索：

```
文档 → LLM 抽取实体 + 关系 → 构建知识图谱
用户提问 → 社区检测 → 社区摘要 → LLM 生成答案
```

| 维度 | 传统向量 RAG | Graph RAG |
|:---|:---|:---|
| 擅长 | 局部细节查询（"XX 怎么做"） | 全局总结（"这篇文档讲了什么"） |
| 能力 | 语义相似度匹配 | 实体关系推理、跨文档关联 |
| 构建成本 | 低（分片+Embedding） | 高（需大量 LLM 调用抽取实体关系） |
| 适合 | 海量 FAQ、搜索类场景 | 长文档总结、法律/医疗知识推理 |

**互补性**：传统 RAG 擅长"点查"，Graph RAG 擅长"面查"。生产中可以组合——先用向量召回局部，再用图谱做全局关系推理。

> 来源：[[5.RAG的范式演进]]、[[28.RAG优化技术:Graph RAG]]

## Q7: Self-RAG、CRAG、Adaptive RAG 分别在解决什么问题？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

三者都是在不同维度上给 RAG 加"智能判断"：

| 范式 | 解决的问题 | 核心机制 |
|:---|:---|:---|
| **Self-RAG** | 模型会不会**自己发现幻觉**？ | 生成过程中模型自我评估（检索结果相关吗？答案有依据吗？），不满足就重新检索/重新生成。需要用反思数据微调模型 |
| **CRAG（Corrective RAG）** | 检索结果**质量不稳定**怎么办？ | 检索结果分"正确/模糊/错误"三档分别处理——错误的丢弃、模糊的摘要提取、实在不行转网页搜索兜底 |
| **Adaptive RAG** | **不同问题应该走不同流程** | 先给问题分类（简单事实/复杂推理/闲聊），再路由到不同 RAG 策略 |

三者都是在 Advanced RAG 基础上加**质量闸门**，让系统更鲁棒。

> 来源：[[5.RAG的范式演进]]

## Q8: Long-Context 模型（如 Claude 3.5 200K）会取代 RAG 吗？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**不会取代，是互补关系**：

| 维度 | 传统 RAG | Long-Context 直接塞 |
|:---|:---|:---|
| 适合 | 文档量大（GB 级） | 文档量小（能塞进窗口） |
| 检索 | 需要（向量/BM25） | 不需要 |
| 延迟 | 低（只给 top-K chunk） | 高（全量 token 推理） |
| 成本 | 低 | 高（token 多，线性增长） |
| 风险 | 召回不全 | 大海捞针（信息密度低时模型可能"看不到"关键片段） |

结论：**小知识库（如一本书）可以跳过检索直接塞**，大知识库（如企业文档库）仍需 RAG。实际工程中两者常组合——先用 RAG 粗筛，再把筛出的多篇文档塞进长窗口做深度分析。

> 来源：[[5.RAG的范式演进]]

## Q9: 什么是 RAG-Fusion？

**难度**: ⭐⭐ 中级

**参考答案**:

RAG-Fusion 是**多查询融合**策略：把一个问题用 LLM 改写成多个视角的子问题，每个子问题独立检索，最后用 **RRF（Reciprocal Rank Fusion）** 融合所有结果。

示例：用户问 "R7 续航多少"
```
改写为 3 个子问题：
  - "智界 R7 电池容量"
  - "智界 R7 CLTC 续航里程"
  - "华为 R7 纯电续航"
分别检索 → RRF 融合 → 重排 → 生成
```

**核心公式**：`RRF Score = Σ 1/(k + rank_i)`，k 通常取 60，只依赖排名不依赖原始分数。

**优势**：比单次检索**召回更全**，尤其适合用户表达模糊/有多种叫法的场景。

> 来源：[[5.RAG的范式演进]]、[[27.RAG优化技术：重排序]]

## Q10: LLM Wiki 和 RAG 有什么本质不同？

**难度**: ⭐⭐ 中级

**参考答案**:

Karpathy 提出的 LLM Wiki 是从**知识编译**角度的另一条路：

| 维度 | 传统 RAG | LLM Wiki |
|:---|:---|:---|
| 知识形态 | 切碎的 chunk（碎片化） | 结构化页面（concept/entity/comparison） |
| 知识处理 | 每次查询时**从零检索** | **编译一次、持续积累**，有答案直接返回 |
| 检索方式 | 向量相似度 | 双链 + 索引 + 结构化导航 |
| 知识积累 | 每次检索独立无状态 | 越用越好（新发现自动写入 wiki） |
| 适合场景 | 海量动态知识库查询 | 个人知识体系、学习笔记、面试复习 |

一句话：**RAG 是"每次都搜"，LLM Wiki 是"编译一次反复用"**。

> 来源：[[5.RAG的范式演进]]

## Q11: 为什么说 Advanced RAG 是当前生产环境主流？

**难度**: ⭐⭐ 中级

**参考答案**:

Naive RAG 太朴素，实际用起来问题很多（召回不全、噪声干扰、用户问题模糊）。Advanced RAG 通过**组合多种优化手段**让系统从"能用"变"好用"：

1. **混合检索**（BM25 + 向量）：取长补短，覆盖关键词精确匹配和语义模糊匹配
2. **重排序**：从几十条候选中精筛选出最相关的 3-5 条，喂给 LLM 的上下文更干净
3. **问题改写**：把用户模糊的表达转换成更适合检索的查询
4. **上下文压缩**：长文档摘要/抽取关键信息，降低 LLM 上下文压力
5. **HyDE / RAG-Fusion**：词汇不匹配、多角度召回

这些优化**各自独立、可以按需组合**，不涉及架构级重构，性价比很高——所以成了生产标配。

> 来源：[[5.RAG的范式演进]]

## Q12: 请用一句话 + 类比区分所有主要 RAG 范式

**难度**: ⭐⭐⭐ 高级

**参考答案**:

把 RAG 比作"帮你找资料的助理"：

| 范式 | 一句话 | 类比 |
|:---|:---|:---|
| Naive RAG | 你问 → 助理去书架随便翻几本 → 念给你听 | 实习生助理，只会按流程走 |
| Advanced RAG | 翻之前先查目录关键词、翻完挑最相关的几本 | 有经验的助理，会用工具 |
| Modular RAG | 查目录、翻书、挑书、整理、朗读——每步都可替换 | 团队协作，每个人可以单独换 |
| Agentic RAG | 助理自己判断要不要找、找几次、够不够 | 高级助理，有独立判断力 |
| Graph RAG | 助理先画一张知识关联图，顺着图找 | 分析师，看全局关系 |
| Self-RAG | 助理找完念一遍，自己检查念得对不对 | 谨慎的助理，念完自我核对 |
| CRAG | 助理找完先评估资料靠谱不，不靠谱就上网查 | 会辨别资料质量的助理 |
| Adaptive RAG | 先问你是要简单答案还是深度分析，再决定怎么做 | 会区分场景的助理 |
| RAG-Fusion | 助理换 3 个角度各找一遍，合并结果 | 多管齐下 |
| Long-Context | 助理直接把整个书架搬过来给你看 | 土豪玩法，简单粗暴 |
