## Q1: 为什么要对文档分片？什么情况下可以直接使用整篇文档？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：分片是为了控制检索粒度与输入预算，不是所有文档都必须切碎。

1. 嵌入模型（Embedding Model）有单条输入上限；超长文本需要切分或其他处理。单条上限与一次批量请求的条数、总 token 限制是不同约束。
2. 整篇文档混合多个主题时，单个向量可能难以突出用户问的细节。
3. 返回完整长文会增加生成输入量，无关段落也可能干扰回答。

短且主题集中的文档可以整篇作为检索单元；需要通读且能装入窗口时，也可直接输入全文。选择应兼顾检索命中率和上下文完整性。

> 来源：[[AI项目/RAG/2.深入理解RAG技术原理——索引构建]]、[[AI项目/RAG/9.什么是父子分片]]。

**追问**：全文很短也必须切吗？不必，可整体索引或直接作为上下文。

## Q2: 文档分片有哪些常见策略？

**难度**: ⭐⭐ 中级

**参考答案**:

| 策略 | 切分依据 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **固定长度切分** | 按固定 token/字符数硬切 | 实现最简单 | 可能切断句子/段落，语义断裂 |
| **TokenTextSplitter** | 按指定 tokenizer 的 token 数切分，重叠行为视实现而定 | 按所选 tokenizer 控制长度，仍需匹配目标模型 | 仍可能切断语义边界 |
| **按标题/段落切分** | 文档自然结构（Markdown 标题、Word 标题） | 保留语义完整性 | 标题下内容长短不一，可能超长 |
| **语义切分** | 按语义相似度阈值分组 | 最符合语义边界 | 实现复杂、开销大 |
| **父子分片** | 父块保留完整结构，子块做检索 | 兼顾检索精度和生成完整性 | 额外存储、父块查询与去重成本 |

可从按标题/段落切分与有限重叠开始，实际收益通过评测确认。

> 来源：[[AI项目/RAG/8文档分片的代码实现]]、[[AI项目/RAG/9.什么是父子分片]]

**追问**：按标题切完超长怎么办？按结构继续拆分并校验目标模型 token 限制。

## Q3: 什么是 Overlap？它是否保证语义完整？

**难度**: ⭐⭐ 中级

**参考答案**:

**重叠切分（Overlap）**让相邻分片重复保留一段内容，以降低边界截断带来的信息损失，但无法保证任意长度的语义单元都落在同一块内。

例：`chunkSize=500`、`overlap=50`，窗口分别为 `[0,500)`、`[450,950)`。对足够长的文本，忽略首尾效应，总切分长度相对原文约为 `500/(500-50)=1.11` 倍；这只是文本重复量，不等于总索引磁盘开销。

重叠越多，向量条数和重复召回通常越多。先尊重标题、段落等边界，再用有限重叠缓解切断；通过检索评测决定大小，不固定背诵一个比例。

> 来源：[[AI项目/RAG/2.深入理解RAG技术原理——索引构建]]、[[AI项目/RAG/9.什么是父子分片]]。公式为固定滑窗的推导。

**追问**：加大重叠就能保证完整吗？不能，长语义单元仍可能跨块且会增加重复。

## Q4: 父子分片（Parent-Child Chunking）的核心思想是什么？为什么需要它？

**难度**: ⭐⭐ 中级

**参考答案**:

核心思想：**检索用小子块、生成用大父块**。

```
文档分片阶段：
  父块（大，如按 Markdown 标题切）→ 存 MySQL（不做 Embedding）
  子块（父块再按 chunkSize 切）→ 做 Embedding → 存向量库（带子块 parentChunkId）

文档检索阶段：
  用户问题 → 向量检索命中子块 → 取子块的 parentChunkId → 查 MySQL 拿父块 → 父块喂给 LLM
```

**为什么需要**：解决两个矛盾
1. Embedding 模型 token 限制 → 子块控制在限制内
2. 大块检索信号稀释 / 小块语义不完整 → 子块负责检索精度，父块负责生成完整性

> 来源：[[AI项目/RAG/9.什么是父子分片]]

**追问**：父块必须存 MySQL 吗？不是，关键是能按稳定标识取回完整内容，存储可替换。

## Q5: 父子分片有哪些工程挑战？是否一定需要手写？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：父子分片用小块匹配与大块回填兼顾检索和阅读，但效果与成本取决于具体实现。

- **额外存储与查询**：保存父内容、子内容及映射，不固定等于两倍存储；通常需要批量查询父块。
- **父块去重与排序**：多个子块指向同一父块时，去重后仍需保留相关性顺序，不能按数据库返回顺序直接拼接。
- **上下文预算**：父块可能很长，回填后仍须选择、截取或压缩；父块不嵌入不代表生成端没有上限。
- **一致性**：更新和删除时，要防止子块仍指向失效父块。具体发布和恢复方案见场景篇 Q3。
- **框架集成**：需按项目版本确认现成检索器与扩展点，不能笼统断言所有框架都没有实现。

> 来源：[[AI项目/RAG/9.什么是父子分片]]。⚠️ raw 缺失，待补充：所用框架版本与一致性实现；本题后两项为设计要求，非已有代码验证结果。

**追问**：为什么回填后还需预算？父块不参与嵌入，但仍占生成模型输入。

## Q6: 文档预处理（ETL 清洗）通常做什么？

**难度**: ⭐⭐ 中级

**参考答案**:

ETL 预处理是分片之前的"清扫工作"，目标是让后续分片和向量化在干净数据上进行：

1. **格式转换**：PDF/Word/PPT → 纯文本或 Markdown
2. **去噪**：页眉页脚、重复的空行、特殊字符、乱码、无意义的装饰性文本
3. **结构化保留**：Markdown 标题层级、表格、代码块——这些是重要的语义边界，不能丢
4. **标准化**：统一换行符、编码、空格处理
5. **元数据提取**：文件名、文档类型、页码、章节位置——用于后续过滤和引用展示

预处理质量直接决定了分片质量和最终检索效果。**垃圾进、垃圾出**。

> 来源：[[AI项目/RAG/2.深入理解RAG技术原理——索引构建]]、[[AI项目/RAG/17.索引构建流程（ETL）总结与查缺补漏]]

**追问**：先调 Embedding 能修复解析丢表头吗？不能，应先检查抽取数据。

## Q7: 按 token 切分和按字符切分有什么区别？是否必须用 TokenTextSplitter？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：关键是使用目标模型的分词规则校验输入长度，并非必须使用某个类。

| 方式 | 优点 | 局限 |
|:---|:---|:---|
| 字符切分 | 实现简单，便于快速估算 | 字符数与 token 数不固定对应 |
| token 切分 | 可结合指定 tokenizer 控制长度 | tokenizer 必须与目标模型匹配，仍可能切断语义 |
| 结构切分后校验 | 保留标题、段落、代码等结构 | 超长单元还需二次切分 |

中文、英文、代码、特殊符号的 token 比例不同，不能用“一个中文字恒等于几个 token”精确推算。可先按结构切，再用模型 tokenizer 校验；只拿另一个模型的 tokenizer 计数也不能保证不超限。

> 来源：[[AI项目/RAG/8文档分片的代码实现]]、[[AI项目/RAG/9.什么是父子分片]]。

**追问**：token 计数器不匹配怎么办？用目标模型规则或保守校验，不能假设其他 tokenizer 精确兼容。

## Q8: 分片时如何处理表格、图片、代码和公式？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：优先保留结构与来源定位，超长时按结构拆分，而不是统一硬切。

| 内容 | 处理思路 | 边界 |
|:---|:---|:---|
| 表格 | 保留表头、单位、行列关系；必要时分行组并重复表头 | 只存摘要可能丢失数值条件 |
| 图片 | 保存原图位置、图片标识和描述，可同时检索关联文本 | 图片描述可能失真，生成时可回看原图 |
| 代码 | 按函数、类或逻辑块切分，保留文件与符号信息 | 代码也可能依赖跨块定义，不能断言不需重叠 |
| 公式 | 公式与符号说明、适用条件一起保留 | 单独抽出公式可能丢失语义 |

父子分片可帮助回填完整章节，但不能修复解析阶段已丢掉的表头或图片；先检查抽取结果，再调分片参数。

> 来源：[[AI项目/RAG/9.什么是父子分片]]、[[AI项目/RAG/33.多模态RAG]]、[[AI项目/RAG/36.多模态文档处理]]。

**追问**：表格一定要整表入模吗？不一定，超长可按行组拆，但须保留表头、单位与来源。

## Q9: chunkSize 和 overlap 怎么调？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：在模型输入约束下，用代表性问题比较不同参数；没有通用最佳数字。

1. 固定解析结果、嵌入模型、检索配置与评测集，先比较几组分片长度。
2. 查看正确证据是否被截断、主题是否混杂、重复片段是否占满结果。
3. 再比较重叠长度或父子分片策略，记录检索与最终答案的变化。
4. 同时比较向量条数、ETL 时间、检索延迟和生成输入量。

预算应满足：`系统指令 + 历史 + 问题 + 检索上下文 + 预留输出 ≤ 模型上下文窗口`。分片还须满足嵌入模型的单条输入约束；父块回填后重新计算生成预算。

例如可将 400/800 token 作为两组实验起点，但它们只是待测参数，不能宣称对应某模型的推荐最优值。

> 来源：[[AI项目/RAG/8文档分片的代码实现]]、[[AI项目/RAG/9.什么是父子分片]]、[[AI项目/RAG/interview/06-RAG评测体系]]。

**追问**：调参只看召回率吗？还看答案质量、重复量、token 成本与延迟。

## Q10: 请描述父子分片在工程实现上的完整链路

**难度**: ⭐⭐⭐ 高级

**参考答案**:

```
写入链路（离线 ETL）：
  1. 原始文档加载 → 预处理
  2. 按 Markdown/Word 标题切分为父块
  3. 父块写入 MySQL（id, content, metadata）
  4. 对每个父块，用 TokenTextSplitter 按 chunkSize 切为子块
  5. 每个子块：加 parentChunkId 元数据 → Embedding → 存向量库

查询链路（在线检索）：
  1. 用户问题 → Embedding → 向量库相似度检索 → 命中子块列表
  2. 提取子块的 parentChunkId 集合（去重）
  3. 批量查询 MySQL → 拿父块完整内容
  4. 按相关性选择父块并校验 token 预算 → 构造 prompt → LLM 生成答案（重排序可在子块或父块阶段按需进行）
  5. 答案附引用来源（父块的文档名、章节）
```

**关键实现细节**：
- 父块查询宜**批量**（例如 `WHERE id IN (...)`），避免每个子块单独查询形成 N+1
- 父块去重：多个子块命中同一父块时只保留一份
- 子块排序后映射回父块，保持语义相关性顺序

> 来源：[[AI项目/RAG/9.什么是父子分片]]

**追问**：批量查父块后顺序乱了怎么办？按检索相关性与稳定 ID 映射恢复顺序。
