# 二、文档处理与分片

> 覆盖 ETL 全流程、分片策略对比、父子分片深度解析。

---

## Q1: 为什么要对文档进行分片？不分片直接把整篇文档塞给大模型不行吗？

**难度**: ⭐ 基础

**参考答案**:

不分片有三个硬伤：

1. **Embedding 模型有 token 上限**：如 text-embedding-v4 单批次最大 8192 token，超过就无法做向量化，也就存不进向量库
2. **检索粒度太粗**：整篇文档向量化后，用户问一个细节，检索回来的是整篇文档——相关性被"稀释"（一篇 50 页的手册，用户问第 3 页的内容，整篇文档的向量相似度反而不如一个 500 token 的 chunk 精确）
3. **上下文窗口浪费**：LLM 的输入是有限的，把整篇塞进去会导致真正相关的信息被大量无关内容淹没

分片的本质是**在"粒度精度"和"语义完整性"之间找平衡**。

> 来源：[[2.深入理解RAG技术原理——索引构建]]、[[9.什么是父子分片]]

## Q2: 文档分片有哪些常见策略？

**难度**: ⭐⭐ 中级

**参考答案**:

| 策略 | 切分依据 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **固定长度切分** | 按固定 token/字符数硬切 | 实现最简单 | 可能切断句子/段落，语义断裂 |
| **TokenTextSplitter** | 按 token 数切分，支持 overlap | 精确控制 token 数，避免 Embedding 超限 | 仍可能切断语义边界 |
| **按标题/段落切分** | 文档自然结构（Markdown 标题、Word 标题） | 保留语义完整性 | 标题下内容长短不一，可能超长 |
| **语义切分** | 按语义相似度阈值分组 | 最符合语义边界 | 实现复杂、开销大 |
| **父子分片** | 父块保留完整结构，子块做检索 | 兼顾检索精度和生成完整性 | 存储翻倍、需多一跳查询 |

实际工程中**按标题切分 + overlap 冗余**是性价比最高的组合。

> 来源：[[8文档分片的代码实现]]、[[9.什么是父子分片]]

## Q3: 什么是 Overlap？为什么要做 Overlap？

**难度**: ⭐⭐ 中级

**参考答案**:

Overlap 就是**相邻分片之间保留一段重叠内容**。

比如按 500 token 切分，overlap 设 50 token，那么 chunk1 覆盖 token[0, 500)，chunk2 覆盖 token[450, 950)，chunk3 覆盖 token[900, 1400)……

**为什么要 Overlap**：因为分片必然会切断完整的语义单元。如果某个概念的解释恰好跨了两个 chunk 的边界，overlap 能保证至少有一个 chunk 包含完整的上下文。

代价是**存储和索引体积增大约 10%-20%**。一般推荐 overlap = chunkSize 的 **10%~20%**。

> 来源：[[2.深入理解RAG技术原理——索引构建]]

## Q4: 父子分片（Parent-Child Chunking）的核心思想是什么？为什么需要它？

**难度**: ⭐⭐ 中级

**参考答案**:

核心思想：**检索用小子块、生成用大父块**。

```
文档分片阶段：
  父块（大，如按 Markdown 标题切）→ 存 MySQL（不做 Embedding）
  子块（父块再按 chunkSize 切）→ 做 Embedding → 存向量库（带子块 parentChunkId）

文档检索阶段：
  用户问题 → 向量检索命中子块 → 取子块的 parentChunkId → 查 MySQL 拿父块 → 父块喂给 LLM
```

**为什么需要**：解决两个矛盾
1. Embedding 模型 token 限制 → 子块控制在限制内
2. 大块检索信号稀释 / 小块语义不完整 → 子块负责检索精度，父块负责生成完整性

> 来源：[[9.什么是父子分片]]

## Q5: 父子分片的优缺点和工程挑战？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**优点**：
- 检索精度高（子块语义聚焦，避免大块信号稀释）
- 生成上下文完整（父块保留完整结构，不会切断表格/图片）
- 绕过 Embedding token 限制（父块太长不嵌入，子块控制在限制内）
- 存储灵活（子块入向量库，父块入 MySQL，不占向量库空间）

**缺点 / 工程挑战**：
- **存储翻倍**：同一段内容存两份
- **检索多一跳**：向量命中 → 查 MySQL 取父块，多一次 DB 查询
- **父块去重**：多个子块命中同一个父块时，需要去重（否则同一父块重复喂 LLM，浪费 token）
- **框架不原生支持**：LangChain / Spring AI / LangChain4j 都没有直接实现，需要手写
- **子块粒度难调**：太小 → 命中率高但父块太大；太大 → 退化为普通分片

> 来源：[[9.什么是父子分片]]

## Q6: 文档预处理（ETL 清洗）通常做什么？

**难度**: ⭐⭐ 中级

**参考答案**:

ETL 预处理是分片之前的"清扫工作"，目标是让后续分片和向量化在干净数据上进行：

1. **格式转换**：PDF/Word/PPT → 纯文本或 Markdown
2. **去噪**：页眉页脚、重复的空行、特殊字符、乱码、无意义的装饰性文本
3. **结构化保留**：Markdown 标题层级、表格、代码块——这些是重要的语义边界，不能丢
4. **标准化**：统一换行符、编码、空格处理
5. **元数据提取**：文件名、文档类型、页码、章节位置——用于后续过滤和引用展示

预处理质量直接决定了分片质量和最终检索效果。**垃圾进、垃圾出**。

> 来源：[[2.深入理解RAG技术原理——索引构建]]、[[17.索引构建流程（ETL）总结与查缺补漏]]

## Q7: TokenTextSplitter 和普通按字符切分有什么区别？

**难度**: ⭐⭐ 中级

**参考答案**:

| 维度 | 按字符切分 | TokenTextSplitter |
|:---|:---|:---|
| 切分单位 | 字符数 | **token 数** |
| Embedding 兼容性 | 可能超 Embedding 模型 token 限制 | 精确控制在限制内 |
| 语义精度 | 字符 ≠ token，中英混合时误差大 | token 才是模型真正理解的单位 |
| overlap 计算 | 按字符 overlap | 按 token overlap，更精准 |

Embedding 模型（如 text-embedding-v4）和 LLM 都是按 token 计费、按 token 限长。用字符切分可能导致：
- 英文 1 字符 ≈ 0.25 token，但中文 1 字符 ≈ 1.5 token
- 同样 800 字符的 chunk，中文可能已经超了 Embedding 的 8192 token 限制

所以**生产环境必须用 TokenTextSplitter**。

> 来源：[[8文档分片的代码实现]]

## Q8: 分片中如何处理表格、图片、代码块这些结构化内容？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

这是分片里最容易踩坑的地方：

| 内容类型 | 问题 | 处理方式 |
|:---|:---|:---|
| **表格** | 按行切断后语义完全丢失 | 父块保留完整表格；或转成 Markdown 表格后用语义切分；或提取表格元数据（表头+行摘要）做独立 chunk |
| **图片** | 被切分成两半完全不可用 | 图片作为独立 chunk，内容为图片描述（通过多模态模型生成），图片本身保留在父块中 |
| **代码块** | 切断后语法错误、无法理解 | 按函数/类为单位切分，overlap 设为 0（代码不需要重叠）；或整段代码作为一个 chunk |
| **公式** | 切断后上下文丢失 | 公式整体作为独立 chunk，周围的解释文本作为另一个 chunk |

这正是**父子分片**能发挥优势的地方——父块保留完整结构，子块做检索。

> 来源：[[9.什么是父子分片]]、[[33.多模态RAG]]

## Q9: 分片粒度（chunkSize）到底设多大合适？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**没有万能数字**，取决于 Embedding 模型、LLM 上下文窗口、以及内容类型：

| 参考基准 | 建议 |
|:---|:---|
| Embedding 模型 token 上限 | chunkSize ≤ 模型上限的 **70%**（留余量） |
| LLM 上下文窗口 | Top-K 个 chunk 的总 token ≤ 窗口的 **30%-50%** |
| 内容类型 | 代码块/Markdown 标题 → 整块；纯文本 → 500-1000 token |
| overlap | chunkSize 的 **10%-20%** |

**经验值**：text-embedding-v4（8192 token 上限）→ chunkSize = 500-800 token，overlap = 50-100 token。

**调优方法**：用 RAGAS 评测不同 chunkSize 下的 Context Recall 和 Faithfulness，找到拐点。

> 来源：[[8文档分片的代码实现]]、[[9.什么是父子分片]]

## Q10: 请描述父子分片在工程实现上的完整链路

**难度**: ⭐⭐⭐ 高级

**参考答案**:

```
写入链路（离线 ETL）：
  1. 原始文档加载 → 预处理
  2. 按 Markdown/Word 标题切分为父块
  3. 父块写入 MySQL（id, content, metadata）
  4. 对每个父块，用 TokenTextSplitter 按 chunkSize 切为子块
  5. 每个子块：加 parentChunkId 元数据 → Embedding → 存向量库

查询链路（在线检索）：
  1. 用户问题 → Embedding → 向量库相似度检索 → 命中子块列表
  2. 提取子块的 parentChunkId 集合（去重）
  3. 批量查询 MySQL → 拿父块完整内容
  4. 父块 → 重排序 → 构造 prompt → LLM 生成答案
  5. 答案附引用来源（父块的文档名、章节）
```

**关键实现细节**：
- MySQL 查询必须**批量**（IN parentChunkId IN (...)），避免 N+1
- 父块去重：多个子块命中同一父块时只保留一份
- 子块排序后映射回父块，保持语义相关性顺序

> 来源：[[9.什么是父子分片]]
