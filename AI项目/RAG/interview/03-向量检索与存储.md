# 三、向量检索与存储

> 覆盖向量模型、相似度算法、ANN 索引原理、向量数据库选型。

## Q1: 什么是 Embedding？它在 RAG 里起什么作用？

**难度**: ⭐ 基础

**参考答案**:

Embedding 就是把一段文本（chunk 或用户问题）**映射成一个固定维度的向量**（如 1024 维浮点数）。

它在 RAG 里的作用是**建立"语义空间"**——语义相近的文本，它们的向量在这个高维空间里也**距离很近**。这样就可以用"算距离"替代"算关键词匹配"，让检索从**字面匹配**升级到**语义匹配**。

```
用户问题 Embedding → 向量库做相似度检索 → 找到语义最接近的 chunk
```

Embedding 模型的质量直接决定 RAG 检索效果——选不好，整个系统的召回率就上不去。

> 来源：[[12.向量模型&向量数据库&向量存储]]

## Q2: 余弦相似度、欧式距离、点积，三者在向量检索里有什么区别？

**难度**: ⭐⭐ 中级

**参考答案**:

| 算法 | 公式核心 | 衡量什么 | 适用场景 |
|:---|:---|:---|:---|
| **余弦相似度** | cos(θ) = (A·B) / (‖A‖×‖B‖) | **方向**有多接近 | Embedding 向量（通常长度归一化过） |
| **欧式距离** | ‖A-B‖₂ = √(Σ(Ai-Bi)²) | 在空间里**离得有多远** | 聚类、非归一化向量 |
| **点积** | A·B = Σ(Ai×Bi) | 方向×长度综合 | 长度有意义时（如 TF-IDF 的权重） |

**实际 RAG 里用余弦相似度最多**——因为 Embedding 模型输出的向量通常经过 L2 归一化（长度恒为 1），此时余弦相似度 = 点积。

**注意**：向量数据库里说的 "cosine distance" 有的实现直接用 `1 - cos(θ)`，有的用真正的欧式距离（归一化后两者等价），要留意具体实现。

## Q3: KNN 和 ANN 有什么区别？为什么生产环境必须用 ANN？

**难度**: ⭐⭐ 中级

**参考答案**:

**KNN（K-Nearest Neighbors）** 是暴力搜索：逐个扫描所有向量，算距离，取 Top-K。时间复杂度 O(N·D)，D 是维度。

- 优点：**100% 精确**（召回率 = 100%）
- 缺点：N 大时**线性变慢**——百万级向量就已经卡了

**ANN（Approximate Nearest Neighbor）** 是近似搜索：牺牲极少量精度，大幅提速。时间复杂度接近 O(log N)。

| 维度 | KNN | ANN |
|:---|:---|:---|
| 精确率 | 100% | 95%-99%（可调） |
| 速度 | O(N·D) | O(log N) ~ O(N^0.5) |
| 适用规模 | 小数据（几千条） | 生产级（百万/亿级） |
| 典型算法 | — | IVF、HNSW、LSH |

生产环境**必须用 ANN**——不然百万级向量检索一次就要几秒，用户体验不可接受。

> 来源：[[16.相似度搜索的常见算法]]

## Q4: HNSW 的原理是什么？为什么它是目前综合性能最好的 ANN 算法？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

HNSW（Hierarchical Navigable Small World）的核心是**分层图结构**，可以理解为**跳表 + 小世界网络**：

```
高层 Layer 2：  o —— o —— o —— o     （节点少、跨距大，像高速公路）
                  ↓    ↓    ↓    ↓
中层 Layer 1： o — o — o — o — o — o  （节点稍多）
                ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓
底层 Layer 0： o-o-o-o-o-o-o-o-o-o-o  （所有数据点，邻居都是就近的）
```

**搜索过程**（跳楼梯）：
1. 从顶层入口点开始
2. 在当前层用**贪婪算法**找比自己近的邻居，直到找不到更近的
3. "下楼梯"到下一层，以刚才的终点为起点继续
4. 到最底层后，继续贪婪搜索，得到 Top-K

**为什么综合性能最好**：
- **速度接近 O(log N)**：高层快速定位区域，底层精确定位
- **召回率极高**：图结构遍历不容易漏
- **支持动态插入**：新数据直接插入，不需要重新聚类（IVF 需要重新聚类）
- **唯一代价**：内存占用高（要存图的边连接）

Milvus、Qdrant、pgvector 都支持 HNSW，是当前**工业界首选**。

> 来源：[[16.相似度搜索的常见算法]]

## Q5: IVF 和 HNSW 怎么选？两者的优缺点？

**难度**: ⭐⭐ 中级

**参考答案**:

| 维度 | IVF（倒排索引） | HNSW（分层小世界图） |
|:---|:---|:---|
| 核心原理 | K-Means 聚类分桶 → 只查最近几个桶 | 分层图导航，高层粗搜 → 底层精搜 |
| 速度 | 快 | **极快** |
| 召回率 | 中/高（可调 `nprobe`） | **极高** |
| 内存占用 | 中（可配合 PQ 压缩） | **高**（存图的边） |
| 动态更新 | 差（新数据可能要重新聚类） | **好**（直接插入） |
| 参数敏感性 | 高（聚类数、nprobe 调不好就漏） | 中（层数、邻居数） |
| 典型场景 | 数据量极大、内存紧张 | **综合最优，生产首选** |

IVF 的进阶版 **IVF_PQ**（配合 Product Quantization 压缩向量）能让内存占用降低几十倍，适合手机端或内存极小的服务器跑亿级数据。

**选型结论**：
- 综合性能优先 → **HNSW**
- 内存极度吃紧 → **IVF_PQ**
- 简单去重/粗筛 → **LSH**

> 来源：[[16.相似度搜索的常见算法]]

## Q6: 向量数据库怎么选？对比 Milvus / Qdrant / pgvector / ElasticSearch

**难度**: ⭐⭐⭐ 高级

**参考答案**:

| 维度 | Milvus | Qdrant | pgvector | ElasticSearch |
|:---|:---|:---|:---|:---|
| 定位 | 专业向量数据库 | 轻量向量数据库 | PostgreSQL 扩展 | 关键词+向量混合 |
| 索引算法 | HNSW/IVF/Annoy | HNSW/IVF/Quantization | HNSW/IVF 有限支持 | 稠密向量 + BM25 |
| 元数据过滤 | ✅ 强 | ✅ 强 | ✅ 原生 SQL | ✅ Query DSL |
| 混合检索 | ❌ 需外部 | ❌ 需外部 | ❌ 需外部 | ✅ **原生支持** |
| 部署复杂度 | 高（分布式） | 低（单机/分布式） | 极低（加个扩展） | 中（已有 ES 就用） |
| 适合规模 | 亿级+ | 千万级 | 百万级 | 千万级+（关键词强） |
| 学习成本 | 高 | 低 | 极低（会 SQL 就行） | 中 |
| 生产案例 | 阿里、小米 | 个人/中小团队 | 快速 MVP | 已有 ES 栈的企业 |

**选型思路**：
1. 已有 PostgreSQL → **pgvector**（零新组件，快速启动）
2. 已有 ElasticSearch → **ES 稠密向量**（混合检索原生支持）
3. 纯向量场景 + 超大规模 → **Milvus**
4. 轻量、自建、千万级 → **Qdrant**

> 来源：[[14.向量是数据库如何选型]]、[[26.使用 ElasticSearch 做关键词检索]]

## Q7: 什么是 Embedding 的维度？维度越高越好吗？

**难度**: ⭐⭐ 中级

**参考答案**:

维度就是向量的长度——text-embedding-v4 是 1024 维，bge-large-zh-v1.5 是 1024 维，text-embedding-3-small 是 1536 维。

**维度不是越高越好**，有几个 trade-off：

1. **维度 ↑ → 表达能力 ↑**：更多维度能编码更丰富的语义信息
2. **维度 ↑ → 存储/计算代价 ↑**：1024 维 vs 1536 维，向量存储体积差 50%，ANN 搜索也慢一截
3. **维度 ↑ → 维度灾难风险**：高维空间里向量间的距离差异变小，区分度下降
4. **维度 ↑ → 模型本身的上限**：如果模型训练时就只输出 512 维，说明它本身就只能压缩到 512 维的语义信息，硬升维度没用

**实践**：用模型**原生输出维度**就行，不要自己调。主流模型都是 768-1536 维。

## Q8: 什么是元数据过滤？为什么它比"加进向量一起搜"更重要？

**难度**: ⭐⭐ 中级

**参考答案**:

元数据过滤 = 在相似度检索**之前或同时**，先按结构化字段做精确过滤：

```
例：用户问"根据 2023 版手册，汽车怎么启动"
1. 元数据过滤：year = 2023 → 只留下 2023 版的 chunk
2. 在过滤结果里做向量相似度检索
→ 避免 2024/2025 版的"旋钮启动""手机启动"被召回
```

**为什么元数据过滤比纯向量搜更重要**：向量相似度检索是**模糊匹配**，它只能找"语义上相似"的内容，但很多场景需要**精确匹配**（版本号、权限隔离、文档类型、时间范围）。

**典型应用**：
- 多版本文档（手册 v2023/v2024）
- 多租户权限隔离（user_id 过滤）
- 按文档类型筛选（只搜 PDF，不搜网页）
- 按时间范围筛选（只搜 2025 年以后的）

向量数据库如果不支持元数据过滤，就要自己在应用层过滤——召回 N 条后再筛，效率极低。**选型时务必确认元数据过滤能力**。

## Q9: 混合检索（Hybrid Retrieval）怎么做？BM25 关键词 + 向量检索

**难度**: ⭐⭐⭐ 高级

**参考答案**:

混合检索 = **BM25/ES 关键词检索 + 向量相似度检索**，两条链路并行跑，然后融合结果。

```
用户问题 ─┬─→ BM25 关键词检索 ──┐
          │                      ├─→ RRF 融合 → Top-K
          └─→ Embedding 向量检索 ─┘
```

**为什么需要**：
- 向量检索擅长**模糊语义匹配**（"怎么启动汽车" 和 "汽车启动方法" 能匹配）
- BM25 擅长**精确关键词匹配**（"iPhone 15" 就是 "iPhone 15"，不会把 "iPhone 14 Pro" 误召回）
- 两者互补，尤其是用户问题里包含**专有名词、产品型号、代码标识符**时，BM25 是关键

**融合方法**：
- **RRF**（最常用）：只看排名位置，不关心原始分数 → `Score = Σ 1/(k + rank_i)`，k 取 60
- **线性加权**：`Score = α × VectorScore + β × BM25Score` → 需要归一化，调参麻烦
- **Cascade**：先用 BM25 粗筛 N 条，再用向量精筛 → 速度优先

ElasticSearch 8.x 原生支持**稠密向量 + BM25 混合检索**，是最方便的方案。

> 来源：[[5.RAG的范式演进]]、[[26.使用 ElasticSearch 做关键词检索]]、[[27.RAG优化技术：重排序]]

## Q10: Embedding 模型怎么选？中文场景有什么特殊考量？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**选型维度**：

| 维度 | 考量 |
|:---|:---|
| **语种** | 中文场景必须选中文 Embedding 模型（bge-large-zh、text2vec-chinese），英文模型在中文上效果差很多 |
| **Token 上限** | 单批次最大 token 数 → 决定 chunkSize 上限。text-embedding-v4 是 8192，bge 系列多是 512 |
| **向量维度** | 768~1536，不要超过模型原生输出 |
| **性能** | 离线 ETL 看吞吐量（docs/sec），在线看延迟（ms） |
| **是否私有化** | 数据敏感时要选本地可部署的模型（bge、text2vec） |

**中文场景的坑**：
- 中文是**表意文字**，一个字可能对应多个概念。Embedding 模型需要足够的中文语料训练
- 中英混合内容（代码注释、API 文档）要选双语模型
- 中文分词影响 Embedding 效果——模型内部的 tokenizer 已经处理了，不用自己再分词

**推荐**：
- 云端：**阿里云百炼 text-embedding-v4**（8192 token 上限，中文效果好）
- 私有化：**bge-large-zh-v1.5** 或 **text2vec-base-chinese**

> 来源：[[12.向量模型&向量数据库&向量存储]]、[[15.如何使用离线向量模型]]

## Q11: 向量检索的"Top-K"到底该设多少？

**难度**: ⭐⭐ 中级

**参考答案**:

Top-K 是一次检索返回多少条候选 chunk。设大了召回全但噪声多，设小了精度高但可能漏。

**经验参考**：

| 阶段 | 建议 Top-K | 原因 |
|:---|:---|:---|
| 混合检索（BM25 + 向量） | 各取 Top-**50** 或 Top-**100** | 先粗召回，后 RRF 融合 + 重排序精筛 |
| 单路向量检索 | Top-**20~30** | 后续有重排序就取多些，没有就取少些 |
| 重排序后 | 保留 Top-**3~5** 给 LLM | LLM 上下文窗口有限，给最精的几条就行 |

**动态策略**：还可以加阈值——如果检索结果的最低分低于阈值（如 cosine < 0.6），说明知识库没有相关内容，直接返回"没找到"，不要硬塞给 LLM 编造。

**核心原则**：**给 LLM 的 3-5 条必须是最相关的，比给 20 条乱七八糟的效果好得多**。

> 来源：[[5.RAG的范式演进]]
