## Q1: 重排序（Reranking）是什么？为什么 Advanced RAG 一定要加重排序？

**难度**: ⭐⭐ 中级

**参考答案**:

重排序 = 在初步检索得到候选 chunk 后，用**更强的模型**（Cross-Encoder 或专用 Reranker）对这些候选重新打分、重新排序，再选出最相关的 3-5 条喂给 LLM。

```
混合检索（BM25 + 向量） → Top-50 候选 → 重排序 → Top-5 最相关 → LLM
```

**为什么一定要加**：

1. **召回和精度是 trade-off**：初步检索取 Top-50 是为了"不漏"，但里面 40+ 条其实是噪声
2. **Embedding 模型是双塔架构**：Query 和 Doc 分别编码，然后点积算相似度——这种"分别编码"天生精度有限
3. **Cross-Encoder 是单塔架构**：Query + Doc 拼一起过 Transformer，直接输出相关性分数——精度比双塔高一大截，但**太慢**，只能处理少量候选

所以生产环境都是**两阶段**：双塔粗召回（快、量大）→ 单塔精重排（慢、量小）。

> 来源：[[27.RAG优化技术：重排序]]

## Q2: Cross-Encoder 和 Bi-Encoder（Embedding）有什么本质区别？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

两者都是句子编码器，但**架构完全不同**：

| 维度 | Bi-Encoder（Embedding） | Cross-Encoder（Reranker） |
|:---|:---|:---|
| 编码方式 | Query / Doc **分别过** Transformer → 各自得到向量 | Query + Doc **拼在一起**过 Transformer |
| 相似度计算 | 两个向量做点积/余弦（快） | 模型直接输出相关性分数（慢） |
| 精度 | 中 | **极高** |
| 速度 | 极快（向量预计算好，检索时只算一次点积） | 很慢（每对 Query-Doc 都要重新跑一遍 Transformer） |
| 适合 | 百万/亿级向量检索 | Top-50 候选精排序 |

```
Bi-Encoder（一次编码 N 个 Doc）：
  Query → Encoder → q_vec
  Doc1  → Encoder → d1_vec ─┐
  Doc2  → Encoder → d2_vec ─┼─→ 向量库预存，查询时只算 q_vec·d_vec
  ...                        │
  DocN  → Encoder → dN_vec ─┘

Cross-Encoder（每次一对）：
  [Query ; Doc1] → Transformer → score1
  [Query ; Doc2] → Transformer → score2
  ...
```

**关键洞察**：Bi-Encoder 快是因为它"先编码再匹配"，Cross-Encoder 准是因为它"边编码边匹配"。

> 来源：[[27.RAG优化技术：重排序]]

## Q3: RRF（Reciprocal Rank Fusion）的原理和用法？

**难度**: ⭐⭐ 中级

**参考答案**:

RRF 是一种**只依赖排名、不依赖原始分数**的融合算法，用来合并多路检索结果（如 BM25 + 向量）。

**公式**：
```
RRF Score(d) = Σ(1 / (k + rank_i(d)))
```
- `rank_i(d)` = 文档 d 在第 i 个检索结果中的排名（从 1 开始）
- `k` = 常数，通常取 **60**（控制低排名文档的权重）
- 文档不在某个列表里 → 该项跳过（视为 rank → ∞，贡献 → 0）

**为什么不用原始分数**：不同检索方法的分数**不可比**——BM25 分数范围是 0~N，余弦相似度是 -1~1，直接加起来会被某一路"量级大"的分数主导。RRF 用排名就避免了这个问题。

**示例**：k=60，某文档在 BM25 排第 2，在向量排第 5
```
RRF Score = 1/(60+2) + 1/(60+5) = 0.0161 + 0.0154 = 0.0315
```

**优势**：
- 实现极简
- 对不同检索器的分数差异鲁棒
- 实证效果在 TREC 等标准评测中优于多数加权融合

> 来源：[[27.RAG优化技术：重排序]]

## Q4: 问题改写（Query Rewriting）有哪些主流策略？

**难度**: ⭐⭐ 中级

**参考答案**:

主流四种（富化、分解、多样化、回溯）：

| 策略 | 做什么 | 示例 |
|:---|:---|:---|
| **富化（Enhancement）** | 用 LLM 把模糊问题补全语义 | "R7 续航多少" → "智界 R7 电动汽车 CLTC 续航里程参数" |
| **分解（Sub-Query）** | 把复杂多跳问题拆成多个子问题 | "iPhone 15 发布时苹果 CEO 是谁" → Q1: iPhone 15 发布时间？Q2: 2023 年 CEO 是谁？ |
| **多样化（Perspective）** | 从多个视角重写，每个视角独立检索 | "R7 续航" → ①电池容量角度 ②CLTC 角度 ③实测用户报告角度 |
| **回溯提示（History）** | 结合对话上下文补全指代 | 用户先问 "R7 续航"，再问 "那 Model Y 呢" → 重写为 "特斯拉 Model Y 的续航里程" |

分解和多样化是**当前生产用得最多**的两种——分解解决多跳问题，多样化解决用户表达模糊（对应 RAG-Fusion）。

> 来源：[[21.RAG优化技术：问题改写]]

## Q5: HyDE（Hypothetical Document Embeddings）的核心思想是什么？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

HyDE 是"让 LLM 先编造一个答案，用编造答案去检索"——听起来反直觉，但效果很好。

**工作流程**：
```
1. 用户提问 "如何给自行车链上油？"
2. LLM 生成假设答案（可能不准确）：
   "首先准备链条油和布，调到中间档位，每个关节滴油同时倒转踏板，最后擦去多余油"
3. 把假设答案做 Embedding → 去向量库检索 → 找到真正的文档
4. 用真正的文档给用户生成最终答案
```

**为什么有效**：
- 用户问题可能**只有几个字**（"R7 续航"），Embedding 向量信息密度低
- 假设答案是**长文本**，包含更多关键词（"链条油""倒转踏板""擦去多余的油"），这些词更可能出现在知识库中
- **"词汇不匹配"问题**：用户说"心情低落"，知识库里写"重度抑郁障碍"，直接检索匹配不上。HyDE 的假设答案大概率会同时出现两种表达，就能桥接

**适用场景**：用户问题简短模糊、用户用语和知识库用语差异大的场景。

> 来源：[[25.RAG优化技术：HyDE]]

## Q6: 元数据过滤有哪些典型应用场景？

**难度**: ⭐⭐ 中级

**参考答案**:

1. **多版本文档**：`metadata.version = "2023"` → 只搜 2023 年版手册，避免召回错误版本
2. **权限隔离**：`metadata.user_id = current_user` → 只搜当前用户有权限看的文档
3. **内容类型**：`metadata.type IN ("PDF", "Doc")` → 排除网页抓取内容
4. **时间范围**：`metadata.publish_date >= "2025-01-01"` → 只搜最新文档
5. **领域分类**：`metadata.domain = "汽车"` → 多知识库时按领域隔离
6. **引用来源展示**：答案附 metadata.file_name + metadata.page → 让用户看到引用来源

**工程要点**：向量数据库必须支持**高效的元数据混合过滤**（先过滤再做向量检索），不要在应用层"先全量召回再过滤"——性能差一大截。

> 来源：[[20.RAG优化技术：元数据过滤]]

## Q7: 查询路由（Query Routing）是什么？

**难度**: ⭐⭐ 中级

**参考答案**:

查询路由 = 根据用户问题的**类型**，动态把请求路由到**不同的检索策略或数据源**。

```
用户提问 "我要出差北京需要准备什么"
    │
    ├─ 路由判定：这是"内部差旅政策"类问题
    │
    ├─→ 路线 A：公司差旅政策知识库（向量检索 + 元数据过滤 department=travel）
    │
    └─→ 路线 B（备用）：外部天气 API + 携程机票查询工具
```

**典型路由维度**：
- **领域路由**：多知识库场景，先判断问题属于哪个领域
- **复杂度路由**：简单问题走单路检索，复杂问题走多跳/Agentic
- **数据源路由**：有的问题走内部知识库，有的走联网搜索
- **语言路由**：中英混合知识库，按语言分流

**实现方式**：用一个**小模型或分类器**先做意图识别，再路由。LlamaIndex、Spring AI 都有 RoutingModule/Router 组件。

> 来源：[[22.RAG优化技术：查询路由]]

## Q8: Graph RAG 和传统向量 RAG 各有什么适用边界？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

| 维度 | 传统向量 RAG | Graph RAG |
|:---|:---|:---|
| 擅长问题类型 | **局部细节查询**（"XX 怎么做""XX 的参数"） | **全局性问题**（"这篇文档讲了什么""A 和 B 什么关系"） |
| 检索方式 | 向量相似度 → Top-K chunk | 知识图谱社区检测 → 社区摘要 |
| 构建成本 | 低（分片 + Embedding） | 高（需大量 LLM 调用抽取实体关系） |
| 跨文档推理 | 弱（只召回各自 chunk） | 强（图谱连接多个文档的实体） |
| 适合规模 | 海量 FAQ、搜索 | 长文档总结、多文档关联分析 |
| 典型框架 | LlamaIndex、LangChain、Spring AI | Graphiti、LlamaIndex Graph RAG |

**互补性**：生产中经常组合——向量 RAG 负责"点查"，Graph RAG 负责"面查"。

> 来源：[[5.RAG的范式演进]]、[[28.RAG优化技术:Graph RAG]]

## Q9: 问题澄清（Question Clarification）在什么场景下需要？

**难度**: ⭐⭐ 中级

**参考答案**:

问题澄清 = 当用户问题**存在歧义、信息缺失**时，系统主动反问用户，让问题更清晰后再检索。

```
用户："我要订机票"
系统："好的，请问您的出发城市、目的地和出发日期是？"

用户："R7 怎么样"
系统："您是想了解智界 R7 的续航？价格？还是配置？"
```

**何时触发澄清**：
1. 指代消解失败（"它怎么样"——"它"指什么？）
2. 关键参数缺失（"帮我查一下"——查什么？）
3. 歧义检测（"苹果"——水果？公司？产品？）
4. 检索结果太少/太多（说明问题可能有问题）

**实现**：用 LLM 做"问题充分性判断"——判断当前问题是否已足够执行检索，不够就生成澄清问题。

> 来源：[[24.RAG优化技术:问题澄清]]

## Q10: 上下文压缩（Context Compression）是什么？

**难度**: ⭐⭐ 中级

**参考答案**:

上下文压缩 = 对检索到的长文本 chunk 做**摘要或关键信息提取**，减少喂给 LLM 的 token 量。

```
检索到 5 个 chunk，总 token = 4000
→ 每个 chunk 做摘要，压缩到核心要点
→ 压缩后总 token = 1200
→ 同样的信息量，占更少的上下文窗口
```

**为什么要压缩**：
- LLM 上下文窗口有限（即使 128K，也不想全给检索结果）
- 长 chunk 里大量是"水分"（过渡句、重复描述、格式信息）
- 压缩后 LLM 有更多空间做推理，同时降低 token 成本

**压缩策略**：
- **LLM 摘要**：用小模型给每个 chunk 生成一句话摘要
- **关键句提取**：用 TextRank/BERTScore 选出最关键的句子
- **Structured Extraction**：提取表格行、代码片段、定义等结构化信息

LlamaIndex 有 ContextCompression/ContextRefine 组件，Spring AI Modular RAG 有 contextBuilder 可定制压缩逻辑。

## Q11: 请设计一个"RAG 召回质量差"时的自动降级/兜底策略

**难度**: ⭐⭐⭐ 高级

**参考答案**:

召回质量差的典型信号：检索结果的**最低相似度分低于阈值**（如 cosine < 0.6），或**Top-K 结果之间相似度差异极小**（说明区分度差）。

**分层兜底策略**：

```
Level 0 正常路径：向量检索 → 重排序 → LLM 生成
    │
    │ 召回分 < 阈值
    ↓
Level 1 CRAG 质量评估：检索结果分档
    ├─ 正确档（高分）→ 直接用
    ├─ 模糊档（中分）→ 对结果做摘要提取再用
    └─ 错误档（低分）→ 丢弃，下一层
    │
    │ 全是低分
    ↓
Level 2 混合检索 + RRF：BM25 关键词 + 向量两路并行，RRF 融合
    │
    │ 还是不行
    ↓
Level 3 HyDE 重新检索：先让 LLM 生成假设答案，用假设答案做 Embedding 再搜
    │
    │ 还是不行
    ↓
Level 4 多视角重写：用 LLM 改写出 3-5 个子问题，分别检索再融合（RAG-Fusion）
    │
    │ 还是不行
    ↓
Level 5 拒绝 + 联网：返回"知识库中未找到相关内容" → 同时尝试联网搜索兜底
```

**工程要点**：每层有超时控制（避免连环调用拖慢响应），每层的结果都做质量评估决定要不要进下一层。

> 来源：[[5.RAG的范式演进]]（CRAG、HyDE、RAG-Fusion）

## Q12: Advanced RAG 的所有优化技术如何组合？画出完整架构

**难度**: ⭐⭐⭐ 高级

**参考答案**:

```
用户提问
    │
    ▼
[问题澄清] ──→ 反问用户补齐信息（可选）
    │
    ▼
[问题改写] ──→ 富化 / 分解 / 多样化
    │
    ▼
[查询路由] ──→ 按领域/复杂度/数据源分流
    │
    ├─→ [HyDE]（假设答案生成 → Embedding）
    │
    ▼
[混合检索] ──┬─→ BM25 / ES 关键词检索
             └─→ 向量相似度检索（HNSW + 元数据过滤）
             │
             ▼
[RRF 融合] ──→ 合并两路结果，只看排名不看分数
    │
    ▼
[重排序] ──→ Cross-Encoder 精排，从 Top-50 选 Top-5
    │
    ▼
[上下文压缩] ──→ 摘要/关键句提取，压缩 token 量
    │
    ▼
[构造 Prompt] ──→ 问题 + 压缩后的文档 + 指令（不编造、引用来源）
    │
    ▼
[LLM 生成] ──→ 答案 + 引用来源（元数据）
```

**实际生产组合建议**：问题改写 + 元数据过滤 + 混合检索 + RRF + 重排序——这五件套是 Advanced RAG 的黄金组合，再加 HyDE/RAG-Fusion 应对特别难召的场景。

> 来源：[[5.RAG的范式演进]]、[[20-27 系列优化文档]]
