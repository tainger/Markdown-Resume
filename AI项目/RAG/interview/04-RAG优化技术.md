## Q1: 重排序（Reranking）解决什么问题？一定要加吗？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：重排序对已召回候选重新判断与问题的相关性，改善排名与上下文选择；不是每个系统都必须增加一次模型调用。

例如先召回 50 个候选，再选择 5 个进入生成，是一种示例配置，不是标准答案。双编码器（Bi-Encoder）便于预计算文档向量；交叉编码器（Cross-Encoder）联合处理问题与文档，能捕捉更细粒度交互，但对每对输入都要计算。

**何时考虑**：正确证据已进入候选集却排名靠后，或噪声占用上下文。若候选本就很少、排序足够好或延迟预算严格，可比较跳过重排的效果。

**边界**：重排不能找回根本没召回的证据；模型也不保证在当前领域一定更准。用相同候选集比较排名指标、最终答案与新增成本。

> 来源：[[AI项目/RAG/27.RAG优化技术：重排序]]、[[AI项目/RAG评测/3.RAG的核心评测指标有哪些]]。

**追问**：没有被召回的证据能靠重排找回吗？不能，重排只作用于候选集合。

## Q2: Cross-Encoder 和 Bi-Encoder（Embedding）有什么本质区别？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

两者的关键差异是问题与文档是否在编码阶段联合交互：

| 维度 | Bi-Encoder（Embedding） | Cross-Encoder（Reranker） |
|:---|:---|:---|
| 编码方式 | Query / Doc **分别过** Transformer → 各自得到向量 | Query + Doc **拼在一起**过 Transformer |
| 相似度计算 | 两个向量做点积/余弦（快） | 模型直接输出相关性分数（慢） |
| 效果 | 取决于表示模型与业务数据 | 联合交互可能改善排序，需领域评测 |
| 速度 | 文档向量可预计算；在线编码查询并搜索候选 | 每对问题与候选需联合计算，成本随候选量增加 |
| 适合 | 百万/亿级向量检索 | Top-50 候选精排序 |

```
Bi-Encoder（文档向量离线预计算）：
  Query → Encoder → q_vec
  Doc1  → Encoder → d1_vec ─┐
  Doc2  → Encoder → d2_vec ─┼─→ 向量库预存，查询时只算 q_vec·d_vec
  ...                        │
  DocN  → Encoder → dN_vec ─┘

Cross-Encoder（每次一对）：
  [Query ; Doc1] → Transformer → score1
  [Query ; Doc2] → Transformer → score2
  ...
```

**关键洞察**：Bi-Encoder 可把文档编码移到离线阶段，Cross-Encoder 则在问题与文档联合输入时建模交互，适用于较小候选集的精细排序。

> 来源：[[AI项目/RAG/27.RAG优化技术：重排序]]

**追问**：Cross-Encoder 的效果一定更好吗？不保证，模型训练领域、截断和候选质量都会影响结果。

## Q3: RRF（Reciprocal Rank Fusion）的原理和用法？

**难度**: ⭐⭐ 中级

**参考答案**:

RRF 是一种**只依赖排名、不依赖原始分数**的融合算法，用来合并多路检索结果（如 BM25 + 向量）。

**公式**：
```
RRF Score(d) = Σ(1 / (k + rank_i(d)))
```
- `rank_i(d)` = 文档 d 在第 i 个检索结果中的排名（从 1 开始）
- `k` = 常数，通常取 **60**（控制低排名文档的权重）
- 文档不在某个列表里 → 该项跳过（视为 rank → ∞，贡献 → 0）

**为什么不用原始分数**：不同检索方法的分数**不可比**——BM25 分数范围是 0~N，余弦相似度是 -1~1，直接加起来会被某一路"量级大"的分数主导。RRF 用排名就避免了这个问题。

**示例**：k=60，某文档在 BM25 排第 2，在向量排第 5
```
RRF Score = 1/(60+2) + 1/(60+5) = 0.0161 + 0.0154 = 0.0315
```

**优势**：
- 实现极简
- 对不同检索器的分数差异鲁棒
- 无需校准不同检索器原始分数；实际收益仍须在业务评测中验证

> 来源：[[AI项目/RAG/27.RAG优化技术：重排序]]

**追问**：多路结果如何去重？先映射统一片段身份，再累加排名贡献；单列表重复项不能重复计权。

## Q4: 问题改写有哪些策略？如何防止改写偏离原意？

**难度**: ⭐⭐ 中级

**参考答案**:

| 策略 | 作用 | 主要风险 |
|:---|:---|:---|
| 指代补全 | 根据对话将“它的续航”补为明确对象 | 沿用错误历史实体 |
| 查询重写 | 去掉冗余，转成适合检索的表达 | 擅自增加年份、型号、限制条件 |
| 问题分解 | 将多跳问题拆成可检索子问题 | 子问题遗漏依赖或引入错误前提 |
| 多查询扩展 | 用不同表述提升覆盖 | 重复结果、成本增加、主题漂移 |
| 回溯抽象（Step-back） | 转向更一般的背景问题 | 只找到背景而没有回答原问题的证据 |

**工程回答**：保留原问题，检查改写前后实体、数值和否定条件；必要时原查询与改写查询分别召回再融合。不确定的关键槽位向用户澄清，不让模型凭空补齐。

对话历史补全不等同于 Step-back。效果应在原问题上评测，不能因改写后句子更通顺就判断更好。

> 来源：[[AI项目/RAG/21.RAG优化技术：问题改写]]、[[AI项目/RAG评测/18.解决问题重写导致的召回不准问题]]。

**深入追问**：

子问题什么时候能并行？相互独立的资料查询可以并行；后一步需要前一步的实体、时间或其他结果时，必须保留依赖。例如先找某事件发生时间，再查询当时负责人，不能让后一步自行猜时间。

可用有向依赖关系组织执行，记录每步输出与证据，并限制展开深度、总调用和重复查询。前序证据不足时，不把猜测当作后续检索的已知事实。来源：[[AI项目/RAG/21.RAG优化技术：问题改写]]。⚠️ raw 缺失，待补充：依赖编排和中间证据验证实现。

**追问**：回溯历史和 Step-back 一样吗？不同，前者补指代，后者抽象成更一般的问题。

## Q5: HyDE 的核心思想是什么？假设答案会不会污染最终回答？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**假设文档嵌入（Hypothetical Document Embeddings，HyDE）**先生成一段可能回答问题的文本，再用其向量检索真实资料，最终根据真实证据回答。

它尝试把简短问题转成更接近文档表达的文本，从而改善问题与文档的表示匹配。收益来自检索表示变化，不是因为假设答案已经正确。

**风险与边界**：假设文档可能编造实体、数值并把检索带偏，还会增加一次生成调用。对精确型号或短事实查询不一定有收益。假设文本必须与真实证据分开，不能冒充引用资料进入最终答案。

可同时保留原问题检索路径，对比证据召回、误召回及总延迟，决定是否启用。

> 来源：[[AI项目/RAG/25.RAG优化技术：HyDE]]、[[AI项目/RAG/5.RAG的范式演进]]。

**追问**：假设文档能当参考来源吗？不能，它只是检索辅助，最终证据来自真实资料。

## Q6: 元数据过滤有哪些应用？权限过滤应由谁生成？

**难度**: ⭐⭐ 中级

**参考答案**:

典型约束包括租户、访问范围、文档版本、有效日期、类型和领域。文件名、页码等元数据还可用于引用定位，但“展示引用”本身不等于过滤。

**权限路径**：服务端根据已认证身份生成访问约束，每个检索数据源都执行；父块回填、引用预览和缓存命中也要遵守相同权限。不能把 `user_id=current_user` 视为覆盖所有共享文档与角色权限的通用模型。

**性能路径**：过滤是查询语义，实际可能在索引扫描前、后或迭代过程中执行；应检查返回不足、过滤选择性和查询计划，而不是断言所有数据库都先过滤再走 ANN。

> 来源：[[AI项目/RAG/20.RAG优化技术：元数据过滤]]；[pgvector Filtering](https://github.com/pgvector/pgvector#filtering)。⚠️ raw 缺失，待补充：端到端权限实现；相关内容为设计要求。

**追问**：用户让系统放宽租户过滤呢？访问范围仍由服务端授权决定。

## Q7: 查询路由是什么？路由失败如何处理？

**难度**: ⭐⭐ 中级

**参考答案**:

**查询路由（Query Routing）**根据问题和请求上下文选择数据源或处理路径，可以走一个或多个检索器。

例如内部差旅制度去制度库，实时天气去外部工具；复杂度不同的请求也可选择单次或多轮检索。路由可用规则、分类器或模型完成，不必须由 LLM 决策。

**边界**：意图路由不负责授予权限。低置信度时可澄清，或在授权范围内搜索多个候选数据源；对多路调用设置并发、超时与费用限制。

框架组件需按文档核对，例如 LangChain4J 的 `QueryRouter`；不要虚构各框架共有的 `RoutingModule` API。

> 来源：[[AI项目/RAG/22.RAG优化技术：查询路由]]；组件校核：[LangChain4J RAG](https://docs.langchain4j.dev/tutorials/rag/)（2026-10-20）。

**追问**：路由置信度低怎么办？澄清或在已授权的多个数据源检索，不能越权兜底。

## Q8: Graph RAG 和向量 RAG 的适用边界是什么？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

| 维度 | 向量 RAG | 图增强 RAG |
|:---|:---|:---|
| 主要检索线索 | 文本语义相似性 | 实体关系、图结构或社区报告 |
| 常见优势 | 局部事实、步骤和语义搜索 | 关系关联、跨实体分析、整体主题 |
| 主要代价 | 分片、嵌入与索引维护 | 额外的抽取、建图、报告与更新成本 |
| 失败风险 | 漏掉互补片段 | 实体消歧或关系抽取错误 |

向量 RAG 也能通过多查询与分解回答跨文档问题，图增强也不自动具备可靠推理能力。Microsoft GraphRAG 的局部与全局查询机制，应与其他图记忆或图检索实现分别介绍。

面试时先给出问题样例与约束，再说明为什么普通检索不足；不要因为文档长就直接选图方案。

> 来源：[[AI项目/RAG/28.RAG优化技术:Graph RAG]]；[Microsoft GraphRAG](https://microsoft.github.io/graphrag/)（2026-10-20）。

**追问**：跨文档问题必须图检索吗？不必，多查询和问题分解也是可选方案。

## Q9: 问题澄清（Question Clarification）在什么场景下需要？

**难度**: ⭐⭐ 中级

**参考答案**:

问题澄清 = 当用户问题**存在歧义、信息缺失**时，系统主动反问用户，让问题更清晰后再检索。

```
用户："我要订机票"
系统："好的，请问您的出发城市、目的地和出发日期是？"

用户："R7 怎么样"
系统："您是想了解智界 R7 的续航？价格？还是配置？"
```

**何时触发澄清**：
1. 指代消解失败（"它怎么样"——"它"指什么？）
2. 关键参数缺失（"帮我查一下"——查什么？）
3. 歧义检测（"苹果"——水果？公司？产品？）
4. 检索结果不足且能归因于关键槽位缺失时，可触发澄清；结果数量本身不证明问题有歧义

**实现**：用 LLM 做"问题充分性判断"——判断当前问题是否已足够执行检索，不够就生成澄清问题。

> 来源：[[AI项目/RAG/24.RAG优化技术:问题澄清]]

**追问**：检索少就必须反问吗？不是，先判断是否缺关键条件以及是否存在系统或资料问题。

## Q10: 上下文压缩怎么做？如何避免压掉关键证据？

**难度**: ⭐⭐ 中级

**参考答案**:

**上下文压缩（Context Compression）**在检索后减少冗余输入，可采用去重、相关句抽取或摘要；压缩不是无损保证。

优先删除重复与明显无关内容；涉及数字、条件、否定、表头与例外规则时保留原始证据片段。若用生成式摘要，应继续保留摘要到原片段的映射，必要时回看全文。

验证不能只看 token 下降，还要比较关键事实覆盖、答案正确性及引用支撑率。为每个 chunk 单独调用模型也可能增加延迟和费用。

框架上可通过检索后处理扩展点实现，不将概念性的 `contextBuilder` 当作通用 API；Spring AI 官方提供 `DocumentPostProcessor` 接口。

> 来源：[[AI项目/RAG/interview/06-RAG评测体系]]；接口校核：[Spring AI RAG](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)（2026-10-20）。⚠️ raw 缺失，待补充：本项目压缩实现与对照结果。

**追问**：摘要更短是否就更好？还需检查关键事实、条件与引用是否保留。

## Q11: 召回质量差时如何设计降级和兜底？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：区分“查询执行失败”“没搜到足够证据”和“系统无权查询”，不能一路降级直到模型编出答案。

1. 空结果先查权限、版本、索引状态和解析是否缺失；不能放宽权限换取召回。
2. 问题不完整则澄清；表达问题可保留原查询并尝试改写或混合召回。
3. 相关候选已有但噪声大，再评估重排、去重或上下文选择。
4. 仍缺证据时说明未知，或在业务允许的公开范围内检索外部来源，并明确其来源不同。
5. 设置总调用预算、每步超时、最大尝试次数与终止条件，防止兜底链不断增加延迟。

**不能使用的判断**：最低一条分数低、排名差距小，都不能单独证明知识库没有答案；阈值需在标注样本上校准。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]、[[AI项目/RAG评测/25.增加分层拒答能力，减少错误回答发生]]。预算和终止条件为设计建议，⚠️ raw 缺失，待补充实现。

**追问**：兜底搜索失败可以让模型凭记忆回答吗？需遵守业务证据策略，并明确无法核实的信息。

## Q12: 如何组合 RAG 优化模块？是否应该全部开启？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**答题骨架**：从能验证的基础链路开始，按错误样本增加模块，并比较每项优化的质量与成本。

```text
身份与授权范围 → 问题解析（必要时澄清/改写）
  → 数据源路由 → 向量/关键词检索（可并行）
  → 统一标识去重与融合 → 可选重排
  → 父块/邻居回填（按需）→ 预算控制与引用映射
  → 基于证据生成 → 质量评估与错误样本回流
```

HyDE、多查询、图检索和压缩都是候选模块，不构成固定“黄金组合”。融合与重排可组合，也可单独使用；父块回填与重排先后应根据候选单位、长度和效果实验决定。

验收用同一评测集做消融对照：基础链路、增加单个模块、组合配置；记录正确性、证据覆盖、误拒、延迟和费用，保留复杂度值得的模块。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]、[[AI项目/RAG/20.RAG优化技术：元数据过滤]]、[[AI项目/RAG/27.RAG优化技术：重排序]]、[[AI项目/RAG/interview/06-RAG评测体系]]。

**追问**：模块如何决定保留？用错误样本和对照评测比较质量增益与成本。
