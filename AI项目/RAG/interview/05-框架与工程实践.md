## Q1: Modular RAG 的模块化与 Advanced RAG 的优化有什么区别？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：Advanced 关注优化什么，Modular 关注如何拆分职责和组织实现，两者可以同时成立。

可将查询转换、检索、融合/重排、上下文注入和生成拆成明确接口；同一检索器可在不同流水线复用，不同场景可选择不同配置。增加某种优化不要求硬编码，模块化也不保证任意交换模块顺序都正确。

**工程价值**：独立替换检索后端、分别评估各阶段、清楚定位职责。接口需约定数据类型、排序、元数据和错误行为；仅把代码拆成几个类还不够。

> 来源：[[AI项目/RAG/5.RAG的范式演进]]、[[AI项目/RAG/29.Spring AI中的Modular RAG支持]]、[[AI项目/RAG/30.LangChain4J中的Modular RAG支持]]。

**追问**：模块任意换顺序都成立吗？不成立，要满足输入输出及证据映射契约。

## Q2: Spring AI 和 LangChain4J 的 RAG 核心组件如何对应？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：两者均提供可组合的检索增强流程，但不是共享一套 Advisor API。

| 职责 | Spring AI | LangChain4J |
|:---|:---|:---|
| 流程入口 | `RetrievalAugmentationAdvisor` | `DefaultRetrievalAugmentor` |
| 查询变换 | `QueryTransformer` | `QueryTransformer` |
| 内容检索 | `DocumentRetriever` | `ContentRetriever` |
| 检索后处理 | `DocumentPostProcessor` | `ContentAggregator`（重排实现可接评分模型） |
| 提示增强 | `QueryAugmenter` | `ContentInjector` |

查询改写发生在检索前，`QueryAugmenter` 负责结合检索内容增强输入，不能将二者混为一谈。上述名称是职责导航；并非每个接口实例都能直接作为 ChatClient Advisor 传入。

**API 边界**：本目录为面试材料，未提供锁定依赖的 Java 工程。这里不把 `RagChain`、`DocumentGrader Advisor` 等示意名称当作已验证 API，也不宣称示例可直接编译。

> 来源：[[AI项目/RAG/29.Spring AI中的Modular RAG支持]]、[[AI项目/RAG/30.LangChain4J中的Modular RAG支持]]；官方校核：[Spring AI RAG](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)、[LangChain4J RAG](https://docs.langchain4j.dev/tutorials/rag/)（2026-10-20；Spring 页面当时标示 2.0.1，LangChain4J 为滚动文档）。

**追问**：QueryAugmenter 是查询改写器吗？不是，此处负责将检索内容与查询组合增强。

## Q3: Spring AI 和 LangChain4J 做 RAG 怎么选？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：按团队生态、目标流程与可验证的集成选择，不能仅凭“哪个框架更新/更成熟”。

| 维度 | 如何评估 |
|:---|:---|
| 现有应用 | Spring Boot 配置、监控、依赖管理的集成成本 |
| 检索流程 | 查询转换、多路检索、过滤、重排和来源返回是否满足需求 |
| 模型与后端 | 目标模型、向量库、认证和部署方式是否有合适集成 |
| 扩展维护 | 自定义接口、异步执行、超时和错误传播是否清楚 |
| 验证方法 | 同一数据和评测集做最小功能验证与压测 |

两者都可实现模块化 RAG；不能由课程旧表推断 Spring AI 无法重排，也不能把 Spring 集成等同于向量库和关系库自动具有跨库事务。

> 来源：[[AI项目/RAG/32.Spring AI 和 LangChain4J的模块化RAG功能对比]]；能力口径以 [Spring AI](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)、[LangChain4J](https://docs.langchain4j.dev/tutorials/rag/) 为准（2026-10-20）。⚠️ raw 缺失，待补充：本项目依赖版本及选型验证结果。

**追问**：Spring 集成等于跨库事务吗？不等于，外部索引与其他存储需另行设计一致性。

## Q4: 固定流程 RAG 与 Agentic RAG 有什么区别？

**难度**: ⭐⭐ 中级

**参考答案**:

| 维度 | 固定流程 RAG（此处对应课程 Generic RAG） | Agentic RAG |
|:---|:---|:---|
| 控制方式 | 应用预先定义路径与条件 | Agent 选择检索工具和后续动作 |
| 检索次数 | 按流程，可含多路或多次检索 | 动态决定，可能零次、一次或多次 |
| 适合任务 | 业务路径清晰、易预测的知识问答 | 需跨来源探索、逐步补充证据的任务 |
| 额外关注 | 各阶段失败处理与可观测性 | 决策正确性、循环终止、总预算和工具权限 |

固定流程不是只允许一次检索，Agentic 也不天然更准确。要明确 Agent 的工具输入、输出、证据来源与终止条件；其工具内部仍可采用模块化 RAG。

> 来源：[[AI项目/RAG/38.Agentic RAG]]。循环和预算要求为工程建议，⚠️ raw 缺失，待补充实现。

**追问**：固定流程只能一次检索吗？不是，也可预定义多路、迭代与条件分支。

## Q5: 多模态 RAG 有哪些实现路线？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：不只“图片转文字”一种实现，应区分检索表示与生成输入。

- **文本代理路线**：图片生成描述、表格提取结构化文本，再走文本嵌入检索；保留原始资源与页码，用于核对和引用。本库主要展示此路线。
- **多模态检索路线**：用适合的模型编码图文等内容，检索图像或页面，再把原始视觉内容交给支持视觉输入的生成模型。

图片描述可能遗漏布局、数值和局部细节；表格转文本也可能丢失行列关系。不能因为检索到了描述就认为原图事实已被完整保留。纯文本检索也可保存表格文本，并不必然丢弃所有表格。

> 来源：[[AI项目/RAG/33.多模态RAG]]、[[AI项目/RAG/36.多模态文档处理]]。⚠️ raw 缺失，待补充：本库多模态向量检索路线的实现与验证；当前仅作选型补充。

**追问**：图片描述能替代原图吗？不能保证，关键视觉细节应可回看原图核验。

## Q6: PDF 文本与图片如何提取并恢复阅读顺序？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**答题骨架**：按页提取文字及位置、图片绘制位置和来源标识 → 进行版面分析 → 必要时 OCR 或图片理解 → 保存原件与定位 → 再分片检索。

PDFBox 的文本提取可使用 `PDFTextStripper`；图片资源与页面绘制指令需要分别处理。仅遍历资源中的图片对象不能完整恢复每次绘制位置；复杂 PDF 还可能包含嵌套对象或矢量图。

**易错点**：
- 多栏、旋转文本、跨页表格不能只用全页按 Y/X 排序保证正确顺序。
- 扫描页可能无文本层，需要 OCR；PDFBox 不是完整的表格语义识别器。
- 页旋转、裁剪框和变换矩阵会影响坐标，不能固定只反转 Y 轴。
- API 有版本差异：PDFBox 3 使用 `Loader.loadPDF(...)` 加载，不沿用 2.x 的 `PDDocument.load(...)`。

> 来源：[[AI项目/RAG/33.多模态RAG]]、[[AI项目/RAG/36.多模态文档处理]]；版本校核：[PDFBox 3 迁移文档](https://pdfbox.apache.org/3.0/migration.html)（2026-10-20）。复杂版面支持程度须用样本验证。

**追问**：按坐标排序能处理所有版面吗？不能，多栏、旋转与跨页表格需额外分析。

## Q7: RAG 工程需要哪些组件？是否都要独立部署？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

| 层次 | 职责 | 可选实现示例 |
|:---|:---|:---|
| 数据处理 | 解析、清洗、分片、向量化 | ETL Worker、解析库、嵌入模型 |
| 检索 | 关键词、向量、结构化过滤 | PostgreSQL/pgvector、搜索引擎、向量服务 |
| 编排 | 改写、路由、融合、重排、上下文组织 | Spring AI、LangChain4J 或自定义流程 |
| 生成 | 基于证据回答和引用 | 满足任务与部署要求的生成模型 |
| 存储 | 原件、元数据、父块及版本 | 对象存储、关系库、检索索引 |
| 评测运维 | 质量、错误样本、调用延迟与费用 | 评测任务、日志、监控 |

**先说结论**：组件职责不等于独立服务数量。小规模可复用已有数据库和存储；需要扩展或隔离时再拆分。应先定义业务约束，再确定技术栈，避免固定套用“MinIO + MySQL + ES + 向量库全家桶”。

> 来源：[[AI项目/RAG/34.实战：多模态RAG智能问答系统]]、[[AI项目/RAG/14.向量是数据库如何选型]]、[[AI项目/RAG/interview/06-RAG评测体系]]。

**追问**：组件越多越适合生产吗？不一定，先满足业务质量与维护成本要求。

## Q8: RAG 文档如何增量更新、删除并保证查询可见？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：区分写入成功、索引准备好与查询可见；不能承诺插入成功后下一次查询一定读到。

1. 根据文档标识和内容版本识别变更，只处理新增、修改和删除的文档。
2. 修改后重新解析、分片和嵌入，维护父子映射与来源元数据。
3. 明确检索后端的写入与刷新语义；使用版本过滤，避免同时返回新旧内容。
4. 删除时覆盖子块、父块、引用访问与相关缓存；跨存储失败需要可重试和对账。
5. 新数据通过完整性检查和回归评测后，再对外提供对应版本。

具体的版本发布与失败恢复设计见场景篇 Q3；仅有文件监听或 MQ 不代表已经解决数据一致性。

> 来源：[[AI项目/RAG/20.RAG优化技术：元数据过滤]]、[[AI项目/RAG/9.什么是父子分片]]。⚠️ raw 缺失，待补充：版本发布、重试及对账实现。

**追问**：写入成功就能立即查询到吗？取决于后端可见性，发布前应验证。

## Q9: 对象存储、关系库与向量库分别保存什么？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：原始资料是重建与追溯的基础，索引是面向检索的派生数据；具体物理存储可合并或拆分。

| 数据 | 常见存放位置 | 用途 |
|:---|:---|:---|
| 原始 PDF、图片等 | 对象存储或受控文件存储 | 重新解析、重新嵌入、预览原件 |
| 文档版本、任务状态、父块 | 关系库或文档存储 | 管理生命周期与内容回填 |
| 向量、检索文本和过滤元数据 | 向量/搜索索引 | 在线相似度与关键词检索 |

用稳定的文档标识、版本、片段标识和位置串联来源。内容 hash 可帮助识别变更，但不是权限标识；引用访问应走授权检查或短期访问链接，不把永久公开 URL 作为默认设计。

> 来源：[[AI项目/RAG/34.实战：多模态RAG智能问答系统]]、[[AI项目/RAG/36.多模态文档处理]]、[[AI项目/RAG/9.什么是父子分片]]。⚠️ raw 缺失，待补充：[[AI项目/RAG/35.MinIO接入]] 当前为空，不能作为已实现接入教程；访问控制为设计建议。

**追问**：向量库能替代原件备份吗？不能，派生片段不保证能重建原始文件。

## Q10: 如何描述在线链路并定位响应慢的环节？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**答题骨架**：鉴权与版本范围 → 问题处理 → 查询嵌入 → 多路检索 → 融合/可选重排 → 内容回填与预算控制 → 模型生成 → 引用返回。

分别记录排队、网络和执行时间；区分首个 token 时间（TTFT）、完整响应时间与生成速度。独立检索分支若并行，等待时间由关键路径决定，不能简单把各分支耗时相加，也不能把某环节延迟分位数相加当作端到端分位数。

**排查**：先从端到端请求追踪找慢阶段，再看模型排队、查询计划、父块 N+1、候选数量和超时重试。比较 p50/p95 与超时率，避免只报平均值。

**证据边界**：本目录没有生产压测记录，不填写固定毫秒数，也不将检索、重排或生成任何一个阶段预先认定为必然最慢。具体故障回答见场景篇 Q7。

> 来源：[[AI项目/RAG/3.深入理解RAG技术原理——检索生成]]、[[AI项目/RAG/27.RAG优化技术：重排序]]。⚠️ raw 缺失，待补充：请求追踪、延迟分布及并发压测。

**追问**：p95 可以逐阶段相加吗？不能作为端到端 p95，应从完整请求分布计算。
