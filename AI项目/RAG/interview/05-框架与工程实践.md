## Q1: Modular RAG 的"模块化"到底是什么意思？和 Advanced RAG 的"多种优化手段"有什么本质区别？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

关键区别在 **"优化手段是硬编码在流程里，还是可以插拔替换"**：

```
Advanced RAG（多种优化，但流程固定）：
  改写 → 混合检索 → RRF → 重排序 → 生成
  ↑ 每种优化是一个固定步骤，你不能跳过或替换顺序

Modular RAG（模块解耦，可自由组合）：
  [QueryTransformer] ──→ [Retriever] ──→ [Reranker] ──→ [ContextBuilder] ──→ [Generator]
      （可替换）            （可替换）        （可替换）         （可替换）          （可替换）
      富化/分解/多种       BM25/向量/混合   Cross-Encoder/   压缩/拼接/         任意 LLM
                          多数据源路由       无               去重
```

**本质区别**：
- Advanced RAG：**"流水线上加了几个工位"**，工位不能换顺序、不能跳过
- Modular RAG：**"每个工位都可以换掉、跳过、重排"**，甚至路由到不同工位链

**为什么要模块化**：
- 不同场景需要不同组合（安全情报要加时效性筛选，法律要加事实校验）
- 每个模块可以**独立优化、独立升级**，不用重构整个系统
- 多人协作时**职责边界清晰**（A 管检索，B 管重排，C 管生成）

> 来源：[[5.RAG的范式演进]]、[[29.Spring AI中的Modular RAG支持]]、[[30.LangChain4J中的Modular RAG支持]]

## Q2: Spring AI 和 LangChain4J 的 Modular RAG 怎么实现？核心组件有哪些？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

两者架构思路类似，都是 **Advisor / RagModule 模式**——在 ChatClient 的执行链上挂可插拔组件：

**Spring AI Modular RAG**：
```
ChatClient.prompt()
  .advisors()
    .advisor(queryAugmenter)      // QueryTransformer：问题改写
    .advisor(documentRetriever)    // Retriever：检索（向量/BM25/混合）
    .advisor(documentGrader)       // Reranker：重排序（可选）
    .advisor(contextBuilder)       // ContextBuilder：拼接/压缩/去重
  .call()
```

**LangChain4J Modular RAG**：
```
ChatLanguageModel chatModel = ...;
ContentRetriever retriever = new VectorStoreContentRetriever(vectorStore);

RagChain chain = RagChain.builder()
  .chatModel(chatModel)
  .contentRetriever(retriever)
  .queryTransformer(queryRewriteTransformer)  // 问题改写
  .contentAggregator(buildContentAggregator()) // 拼接/压缩
  .build();
```

**核心组件对照表**：

| 职责 | Spring AI | LangChain4J |
|:---|:---|:---|
| 查询改写 | QueryAugmenter Advisor | QueryTransformer |
| 检索 | DocumentRetriever Advisor | ContentRetriever |
| 重排序 | DocumentGrader Advisor | 需自定义或用 External |
| 上下文构建 | ContextBuilder | ContentAggregator |
| 生成 | ChatModel | ChatLanguageModel |

> 来源：[[29.Spring AI中的Modular RAG支持]]、[[30.LangChain4J中的Modular RAG支持]]

## Q3: Spring AI 和 LangChain4J 做 RAG 各有什么优缺点？怎么选？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

| 维度 | Spring AI | LangChain4J |
|:---|:---|:---|
| 定位 | Spring 生态扩展，优先与 Spring 体系集成 | 独立 LLM 应用框架，Java 版 LangChain |
| 学习曲线 | 低（Spring Boot + 自动配置） | 中（API 风格与 Spring 不同） |
| Modular RAG | ✅ Advisor 模式，Spring Boot 原生支持 | ✅ RagChain 原生支持 |
| 向量库集成 | Milvus/Qdrant/PostgresML/Elasticsearch | Milvus/Qdrant/Pgvector/ElasticSearch |
| Agent 支持 | 需集成 AgentScope | Agent 原生支持 |
| 生产成熟度 | 较新（1.0 GA 不久） | 较成熟 |
| 团队背景 | Spring 官方 | Dify 作者 + 社区 |

**选型建议**：
- 公司是 **Spring 技术栈** → **Spring AI**（自动配置、事务一致性、与已有服务无缝集成）
- 想要**更灵活、Agent 生态更全** → **LangChain4J**
- 需要和 AgentScope 多智能体框架配合 → 看 AgentScope 对哪个集成更好（LangChain4J 原生支持）

> 来源：[[32.Spring AI 和 LangChain4J的模块化RAG功能对比]]、[[18.Spring AI 和 LangChain4J中文档处理功能对比]]

## Q4: Agentic RAG 和 Generic RAG 到底有什么区别？分别适合什么场景？

**难度**: ⭐⭐ 中级

**参考答案**:

来自 AgentScope 的术语：

| 维度 | Generic RAG | Agentic RAG |
|:---|:---|:---|
| 特点 | 流程固定：**先检索 → 后生成** | 流程动态：**Agent 决定什么时候检索、检索几次** |
| 检索触发 | 每次都检索 | Agent 判断"这个问题需要检索吗？"→ 是才检索 |
| 检索次数 | 固定 1 次 | 动态（可能 0 次、1 次、N 次） |
| 典型实现 | ChatClient + DocumentRetriever Advisor | Agent 把 RAG 当作一个 Tool |
| 适合场景 | 智能客服、固定 FAQ、**检索是核心能力** | 复杂任务、多步推理、**检索只是工具之一** |

**实例**：
- Generic RAG：智能客服收到任何问题都先查知识库再回答
- Agentic RAG：旅行 Agent 先查航班 → 再查酒店 → 再查签证政策，每一步都是 Agent 自己决定要不要调哪个工具

> 来源：[[38.Agentic RAG]]

## Q5: 多模态 RAG 是什么？和纯文本 RAG 有什么区别？

**难度**: ⭐⭐ 中级

**参考答案**:

多模态 RAG = 检索对象不仅是文本，还包括**图片、表格、公式**等多种模态内容。

```
纯文本 RAG：  文档 → 文本分片 → Embedding → 检索
多模态 RAG：  文档 → 文本分片 + 图片描述 + 表格结构化 → Embedding → 检索
```

**关键技术点**：
1. **文档解析**：PDFBox 提取文本 + 定位坐标，识别图片区域
2. **图片处理**：用多模态大模型（qwen-vl-plus）把图片转成**文本描述**
3. **表格处理**：表格转 Markdown 或结构化数据，保持表头-行关系
4. **分片策略**：图片作为独立 chunk（内容是图片描述），或嵌入父块上下文

**典型流程**：
```
PDF 文档 → PDFBox 提取文本/图片/表格（按坐标排序保序）
→ 图片 → 多模态模型 → 图片描述文本
→ 表格 → 结构化处理 → Markdown 表格
→ 统一文本流 → 分片 → Embedding → 检索
```

**为什么重要**：纯文本 RAG 会**丢弃 PDF 里的图片、表格、公式**，这些往往是文档中最关键的信息（如系统架构图、API 参数表）。

> 来源：[[33.多模态RAG]]、[[36.多模态文档处理]]

## Q6: 多模态文档处理的完整链路？PDFBox 怎么同时提取文本和图片？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

```
1. PDDocument.load(pdfFile) → 获取文档对象
2. 逐页遍历，PDPage → PDResources → 遍历 XObject
3. 区分 PDTextStripper（文本）和 PDImageXObject（图片）
4. 每个元素记录：类型 + 坐标 (x0,y0,x1,y1) + 内容
5. 按坐标排序（Y 从上到下，X 从左到右）还原阅读顺序
6. 图片 → processImage() → 多模态模型转描述文本
7. 拼接成统一文本流 → 后续分片/Embedding
```

**核心类**：`UnifiedContentStripper extends PDFTextStripper`
- 重写 `writeString()` 捕获文本 + 坐标
- 重写 `processOperator()` 捕获图片 XObject + 坐标

**坐标转换**：PDF 坐标系原点在左下角，阅读视角从左上到右下 → Y 坐标要反转。

> 来源：[[33.多模态RAG]]

## Q8: RAG 系统上线后怎么维护？增量更新、热更新怎么做？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**增量更新**（新文档入库）：
```
监听新文档（定时轮询 / 消息队列）
  → ETL（预处理 → 分片 → Embedding）
  → 新 chunk 写入向量库 + 关系库
  → 索引构建（HNSW/IVF 动态插入）
```

**热更新**（不重启服务）：
- 向量数据库（Milvus/Qdrant/pgvector）都支持**动态插入**——新向量实时写入，索引在线更新，不影响在线检索
- ElasticSearch 写入后实时可见（refresh interval 默认 1s）
- 应用层**不需要重启**，新数据入库后下一次用户提问就能检索到

**删除/更新**：
- 删除：先删向量库的 chunk，再删关系库的记录。向量库支持按 metadata 批量删除（`WHERE file_name = 'xxx'`）
- 更新：标记旧版本为 inactive → 新版本正常入库 → 下次检索只返回 active 的。或直接覆盖（需要先删后插）

**监听机制**：
- 简单方案：定时扫描目录（每天凌晨）
- 实时方案：MinIO/S3 事件通知 → MQ → ETL Worker
- 手动触发：管理后台 API 主动触发某文件重新索引

## Q9: MinIO / 对象存储在 RAG 里起什么作用？和向量库的关系？

**难度**: ⭐⭐ 中级

**参考答案**:

MinIO 是**原始文档存储**，和向量库是**上下游关系**：

```
原始 PDF/Word/PPT ──→ MinIO（对象存储，长期存档）
                        │
                        │ ETL 读取
                        ↓
                    分片 → Embedding
                        │
                        ↓
                  向量数据库（存储 Embedding + 元数据）
                  + MySQL（存父块完整内容，父子分片场景）
```

**为什么需要对象存储**：
1. **原始文档不可丢**——向量库和关系库只存分片后的内容，原始文档需要长期存档
2. **重新 ETL 的来源**——如果 Embedding 模型升级了，需要重新对所有文档做 Embedding，这时从 MinIO 读原始文档重新处理
3. **引用追溯**——用户点开"参考来源"时，可以从 MinIO 拿到原始文件下载/预览
4. **存储成本低**——对象存储（MinIO/S3）比向量库便宜得多，适合存大量原始文件

**工程要点**：
- MinIO 存原始文件，用**内容 hash**（MD5/SHA256）做文件版本管理——hash 没变就跳过 ETL
- 向量库的 metadata 里要存**MinIO 的文件 URL + hash**，方便追溯

> 来源：[[35.MinIO接入]]

## Q10: 请描述从用户提问到返回答案的完整在线链路，标注每个环节的耗时

**难度**: ⭐⭐⭐ 高级

**参考答案**:

以下是典型生产环境的耗时分布（毫秒级）：

```
用户提问 "R7 续航多少"
    │
    ▼
[1] Query 预处理 / 改写              耗时 50-200ms（LLM 调用，取决于模型大小）
    │
    ▼
[2] 多路检索并行                     耗时 50-150ms
    ├─ BM25/ES 关键词检索            20-50ms
    └─ 向量相似度检索（HNSW）        30-80ms
    │
    ▼
[3] RRF 融合 + 去重                   耗时 <5ms（纯计算）
    │
    ▼
[4] 重排序（Cross-Encoder）           耗时 200-500ms（Top-50 → Top-5，这是最慢的环节）
    │
    ▼
[5] 上下文构建（拼接/压缩）           耗时 10-50ms
    │
    ▼
[6] LLM 生成答案                     耗时 1000-3000ms（取决于答案长度和模型）
    │
    ▼
[7] 返回答案（附引用来源）            -
    
─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
总计：约 1300-3900ms（1.3s ~ 4s）
```

**性能瓶颈**：
1. **重排序**：Cross-Encoder 跑 Top-50 太慢 → 可以用**小模型 Reranker**（如 bge-reranker-base 比 Cross-Encoder 快一个数量级）
2. **LLM 生成**：流式输出可缓解体感延迟
3. **多路检索**：BM25 和向量可以**并行**跑，节省总耗时

**优化方向**：
- 改写/摘要等 LLM 调用用**小模型**（qwen-turbo / gpt-4o-mini）
- 重排序用**专用 Reranker**（不是 Cross-Encoder，是专门做重排的小模型）
- 检索用**向量数据库的 HNSW 索引**（亚毫秒级）
- **避免串行调用**：能并行的都并行（BM25 + 向量、改写 + HyDE）
