## Q1: 用户问“某部门有多少人”，为什么不能直接用向量检索回答？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：检索相似片段不等于对完整业务数据做精确统计。先判断问题需要哪种证据，再选择数据源。

| 需求 | 候选路径 | 回答时说明 |
|:---|:---|:---|
| 当前部门人数、金额汇总 | 关系库聚合查询 | 统计对象、时间、状态和访问范围 |
| 制度解释、操作步骤 | 文档检索 | 生效版本与原文依据 |
| 多个实体的关系路径 | 图查询或关系连接 | 关系方向、路径与证据 |

“人数”还需澄清在职、外包、子部门是否计入；历史时点可能没有可查询快照。若混合问题同时问人数和编制政策，可以分别取证后合成，标明统计时间与政策版本，不能用召回片段数量充当人数。

**验证**：准备同义统计问题、子部门口径和历史时点样本，对照人工确认的查询结果；统计口径不清时应澄清。

**追问**：RAG 只能查向量库吗？不是，外部证据也可来自 SQL、图查询或受控 API。

## Q2: 几百张表时如何选择 schema？如何消除业务术语歧义？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**设计建议**：先缩小授权数据域，再做 schema linking（问题与表、字段的对应），避免把全部 DDL 直接塞进提示。

1. 建立数据字典，包含表和字段说明、连接键、枚举、单位以及受控业务指标定义。
2. 用问题检索候选表列，并补齐连接所需的中间表；相似表名不等于可替代的数据口径。
3. 对“客户数”“有效订单”“最近一个月”等词明确去重键、状态、时区和时间区间；无法确定就澄清。
4. 只把必要 schema 和脱敏示例交给模型，生成后校验字段、连接路径与聚合口径。

例如订单关联明细会放大行数；按客户去重计数与数订单行不同。提示里提供正确字段只是起点，仍需验证业务语义。

**验证**：覆盖同名字段、多条连接路径、空值、重复明细和跨月边界；与审核后的 SQL 比较结果及口径，不只比 SQL 字符串。

**追问**：只检索最相似的两张表够吗？未必，可能漏掉连接表或业务口径说明。

## Q3: 提示词要求“只生成查询 SQL”是否足够？执行前验证什么？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：提示是行为约束，执行权限必须由程序和数据库控制；不能把模型生成的 SQL 原样交给高权限连接。

- 使用匹配目标方言的解析器检查完整语法树，限制单条语句及允许的语法；检查子查询、CTE、表列、函数和操作，而不只判断是否以 `SELECT` 开头。
- 只开放授权视图或表列；数据行访问通过可信执行层或数据库策略落实，不能只相信模型自己添加的租户条件。
- 使用最小权限账号，结合只读事务、语句超时、结果量及并发预算；只读查询也可能消耗大量资源。
- 已验证结构中的值用参数绑定；表列标识符用白名单映射，参数化不能证明整段动态 SQL 安全。
- 拒绝未通过校验的查询；修正应重新走全部检查，并保留审计信息。

`LIMIT` 约束返回量，不保证减少聚合或连接的扫描量；只读配置也不能代替访问授权。

**验证**：检查越权表列、跨租户、嵌套查询、多语句、长耗时及超大结果等用例；查询不得绕过执行策略。

**追问**：只过滤 DROP/DELETE 关键字可以吗？不够，语法嵌套、权限和资源消耗都不是关键词过滤能完整判断的。

## Q4: SQL 返回零行、多行、空值或超时，如何处理？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：先明确查询结果契约，再选择 JDBC 读取方式；没有记录、统计为零、未知和执行失败不能混为一谈。

| 情况 | 处理 |
|:---|:---|
| 单行单列统计 | 明确数值类型；无匹配记录时 `COUNT(*)` 仍可能返回一行零 |
| 预期单行却返回零行或多行 | 区分无匹配、条件不唯一和生成 SQL 错误 |
| 单行值为 SQL NULL | 按业务语义表示未知或缺失，不能自动当零 |
| 明细多行或多列 | 使用列表/行映射，控制分页、返回量与截断提示 |
| 超时、权限或语法错误 | 返回可区分的执行状态；不伪装成“业务没有数据” |

原笔记用 `queryForObject(sql, clazz)`，这个重载期待单行单列，不适合任意自然语言查询。结果交给模型说明时，连同统计条件与执行状态传递，避免凭错误状态编答案。

**验证**：覆盖零行、统计零、单行 NULL、多行、多列、超时和权限失败；检查用户展示不把运行错误变成业务结论。

**追问**：结果为空就扩大查询范围吗？不能自动放宽授权或业务条件，应先区分原因。
