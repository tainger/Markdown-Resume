## Q1: 数据库写入批次设小了，为什么 Embedding 仍可能超限？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：数据库写入批次与嵌入请求批次控制不同阶段，不能把同名或类似配置视为同一限制。

原笔记展示的 `PgVectorStore.doAdd` 先执行嵌入，再对数据库写入分批；因此只调写入批次不能证明嵌入请求已满足服务限制。该示例也传入了 `BatchingStrategy`，不能进一步推断“框架完全不会拆分嵌入”。

排查时确认：实际绑定的 `EmbeddingModel` → 适配器是否拆批 → 分批依据是条数还是 token → 最终请求大小 → 数据库批次。外层主动分组可限制一次提交量，但仍要校验单片段长度与提供商约束。

本库示例的批次 9 是演示配置，不能作为所有模型的通用上限。Spring AI 的 token 批处理策略也需按实际版本与 tokenizer 验证。

**验证**：分别构造条数多但很短、条数少但很长的输入，观察脱敏后的请求计数和 token 估算，区分哪个阶段拒绝请求。

**追问**：外层一次只传一个片段就不会超限吗？不会解决单条超长或并发请求速率超限。

## Q2: 单条 token、批量条数、批量 token 和限流如何分别控制？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**设计建议**：分别控制请求大小与请求速率，任意一项满足不代表其余也满足。

| 约束 | 控制位置 |
|:---|:---|
| 单条 token 上限 | 分片后按目标模型规则检查，超长单独处理 |
| 一次请求最大条数 | 构建嵌入请求时限制列表长度 |
| 一次请求总 token | 装批时累计长度，预留估算误差 |
| 每分钟请求/token 配额 | 全局或租户级速率调度，不能只依赖线程数 |
| 并发与内存 | 有界队列、工作线程和在途请求数 |

一组待发片段应同时满足条数与总 token 约束；无法放入任何批次的片段应明确报错或重切，避免装批循环不前进。具体配额从选定服务和部署获取，不在题库固定。

限流重试采用有上限的等待与退避，并根据服务语义处理；无限增大并发会放大排队、重试与费用。

**验证**：覆盖单条超长、累计超限、并发任务共同耗尽配额及持续限流，检查队列有界、重试可终止并能恢复。

**追问**：并发数限制等于每分钟请求限制吗？不是，相同并发在不同延迟下产生的请求速率不同。

## Q3: 一批只有一个片段失败，如何恢复而不重复处理整批？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**设计建议**：记录每个阶段和片段的状态，区分明确失败、成功与结果未知。

1. 为片段绑定文档版本、稳定片段 ID、内容摘要和嵌入配置版本，保存嵌入/写入阶段状态。
2. 服务支持逐项结果时，只处理失败项；整批报错时按错误类型判断，可隔离坏样本，但限流或网络故障不应一律二分重试。
3. 已获得的向量可在受控保存和版本一致的条件下复用；不要为数据库暂时失败重复计算全部嵌入。
4. 超时后可能“已写入但响应丢失”，先对账或通过稳定 ID 的幂等写入恢复，不能直接追加随机 ID。
5. 永久错误进入可追踪的待处理队列，不能静默跳过后把文档标为完整发布。

批次成功与文档完整入库是不同状态；发布前还需检查应有片段是否齐全。

**验证**：模拟单片段错误、部分成功、写入后超时及进程重启；重跑后应无重复、无漏块，并能追踪隔离项。

**追问**：所有失败都立即重试吗？不是，应区分参数/内容错误、临时故障和限流，设置恢复上限。

## Q4: 保存向量为什么还要保存文本和元数据？列表顺序错位会怎样？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：向量用于定位候选，文本为生成提供证据，元数据为过滤、回填和追溯提供身份；三者必须指向同一片段。

显式调用 `embedAll(segments)` 再调用 `addAll(embeddings, segments)` 时，不能只验证列表长度相同；要按适配器返回契约维护位置或标识映射。并发分批、跳过坏样本后，各自按完成顺序追加，可能把 A 的向量绑定 B 的文本。

建议用携带片段 ID、文本、元数据、向量和状态的记录流转，确认成功返回后再一起写入。若后端只存向量和外部引用，也需能可靠回取对应证据；不是所有向量库都必须物理存一份全文。

顺序错位会让“向量上匹配”返回无关证据，容易被误判为嵌入模型差或生成幻觉。

**验证**：让不同批次乱序完成并注入单条失败，逐 ID 核验输入文本、向量来源与保存记录；用可识别的样本文本回查。

**追问**：两份列表长度相同就正确吗？不够，必须保证每对向量与片段身份一致。
