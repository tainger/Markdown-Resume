## Q1: 索引分词与查询分词有什么区别？为什么可能使用不同策略？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：索引分析器将字段内容转换为入索引的词项，搜索分析器处理查询文本；关键是两者的输出能按预期匹配。

原笔记的 `content` 字段配置 `ik_max` 建索引、`ik_smart` 查询，另有使用不同索引分析器的 `content.smart` 子字段。这是可比较的实验配置，不代表“建库一定细分、查询一定粗分”。

通常先保持分析规则一致，再为具体用途考虑差异；更细的词项可能增加覆盖，也可能带来噪声。只修改查询分析器不会重新生成旧文档的索引词项；需要改变存量词项时，应评估重建索引并验证切换。

分词参数、词典、大小写和停用词处理都纳入版本管理，查询效果不能只由插件名推断。

**验证**：用分析 API 查看同一术语在索引侧、查询侧产生的词项及位置，再比较真实查询召回；覆盖旧数据和新配置切换。

**追问**：换了词典就等于旧文档已重新分词吗？不是，需区分运行时词典变化与已有索引数据。

## Q2: 型号、错误码、英文缩写被切坏时，怎么诊断和修复？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**答题顺序**：先检查原字段和实际词项，再决定改词典、字段或查询。

1. 固定失败查询和目标文档，用分析 API 检查连字符、下划线、大小写、字母数字组合及中文别名。
2. 确认查询实际使用哪个字段与分析器，排除字段选错、存量索引未重建或过滤条件错误。
3. 对业务标识建立专用精确字段，约定大小写与格式归一化；自然语言描述仍放全文字段。
4. 对别名与专业词，可评估自定义词典或同义词配置，注意词项位置、更新方式与版本兼容。
5. 保留词项和查询结果对照，评估是否在找回目标的同时增加近似型号误召回。

不要为追求某一个样本命中，直接移除租户、版本等业务约束。

**验证**：覆盖完整型号、相邻型号、缩写、大小写、符号与中文别名，并统计目标召回和错误型号命中。

**追问**：把所有字段都设成 keyword 可以吗？不合适，完整标识与自然语言检索的需求不同。

## Q3: term、match、match_phrase 与元数据过滤如何配合？

**难度**: ⭐⭐ 中级

**参考答案**:

| 方式 | 用途 | 注意 |
|:---|:---|:---|
| `term` | 匹配精确索引词项，常用于 keyword 字段 | 不是对任意 text 原文做完整字符串相等比较 |
| `match` | 分析查询文本后做全文匹配 | 不自动保证完整型号或全部条件相等 |
| `match_phrase` | 依据分析后的词项及位置做短语匹配 | 不等于原文逐字符相等，行为受分析器与 slop 影响 |
| filter 上下文 | 租户、版本、类型等布尔约束 | 主要用于是否匹配，不贡献相关性评分 |

可将服务端授权条件与明确版本放入过滤，将说明性问题交给全文查询；必要时添加专用型号字段约束。BM25 排名回答“哪些更相关”，不能代替授权或业务条件判断。

**验证**：构造“同说明不同型号”“同型号不同版本”“同词项不同顺序”数据，检查允许范围、匹配类型和排名均符合预期。

**追问**：短语匹配就是精确原文吗？不是，它仍基于分析后的词项和位置。

> 来源：[[AI项目/RAG/26.使用 ElasticSearch 做关键词检索]]、[[AI项目/RAG/20.RAG优化技术：元数据过滤]]；官方：[match](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query)、[match_phrase](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query-phrase)、[查询与过滤上下文](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-filter-context)（2026-10-20）。

## Q4: Bulk 请求完成但部分写入失败，如何恢复并核验？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：传输成功不等于所有条目写入成功；逐项结果、重复执行和搜索可见性要分别处理。

原示例已检查 `response.errors()` 和失败 item，但仅打印日志没有形成恢复闭环。应记录失败条目的 ID、操作与原因，区分参数错误和可重试故障；不能把其余成功项也当失败随意重复提交。

网络超时导致结果未知时，结合操作类型、稳定 ID 和版本策略对账。`index`、`create`、`update` 的重试语义不同，稳定 ID 也不能阻止旧请求覆盖更新版本。

`refresh=true` 会主动刷新以提供搜索可见性，不能解决部分失败；`wait_for` 等待相关刷新，适用时可减少不必要的强制刷新，但仍需预算控制。写入成功、可搜索与整篇文档完整发布是三个条件。

**验证**：模拟部分条目错误、限流、响应丢失和旧版本重试；逐 ID 核对内容与版本，按可见性要求验证查询，再决定文档是否可发布。

**追问**：只看 Bulk HTTP 状态够吗？不够，必须结合 item 结果；批次超时也不能直接认定全部未写入。
