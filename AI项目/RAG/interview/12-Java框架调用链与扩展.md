## Q1: VectorStore.add 与 EmbeddingStore.addAll 有什么区别？如何避免重复向量化？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：根据具体接口契约区分“接收文档并嵌入入库”与“接收已算好的向量”，不能只看方法都叫 add。

本库 Spring AI 示例调用 `VectorStore.add(documents)`，`PgVectorStore` 在内部调用所绑定的嵌入模型；LangChain4J 示例则先 `embedAll`，再将向量与文本片段一起交给 `EmbeddingStore.addAll`。

若先自行嵌入，随后仍调用内部会重新嵌入的文档接口，前一次结果可能根本没被使用。排查时沿调用链统计模型请求次数，而不是只看服务方法名。

同时核对实际绑定的嵌入模型：应用中有多个模型 Bean 时，手动计算与向量存储绑定的模型可能不同。配置、归一化、维度和查询编码需保持兼容。

这些描述针对所列接口与示例实现，不能推广为所有存储 API 都自动嵌入或都不嵌入。

**验证**：用可观测的嵌入适配器记录单次入库的调用次数和模型配置；检查保存向量的来源与在线查询模型一致。

**追问**：向量维度一致就能忽略模型绑定吗？不能，不同模型的同维向量也可能不兼容。

## Q2: EmbeddingStoreIngestor 封装了什么？自定义处理应放在哪？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：它封装文档入库的处理链，不等于替应用完成原件存储、权限设计和任务恢复。

正文示例配置 splitter、embeddingModel 和 embeddingStore，替代手写的分片、嵌入和保存步骤。具体版本可提供文档或片段变换扩展，应按处理对象和执行顺序选择：文档级清洗与统一元数据在切分前，片段级富化在切分后，嵌入在最终检索文本确定后。

关键约定是各阶段保留文档版本、来源、权限和片段身份；有些处理会改变文本或生成新对象，不能假定 metadata 自动完整继承。

不要先手工切完又无意重复切分。无论用封装还是手写，仍需观察片段数、嵌入请求、写入结果与失败状态。

**验证**：用带结构和元数据的样本文档，对比手写流程与 Ingestor 的最终片段、来源映射和嵌入调用，明确有意的差异。

**追问**：用了 Ingestor 就能自动增量恢复吗？不能据此推断，需要额外设计任务状态、幂等和失败恢复。

> 来源：[[AI项目/RAG/17.索引构建流程（ETL）总结与查缺补漏]]、[[AI项目/RAG/31.基于LangChain4J实现简单的RAG检索]]；官方：[LangChain4J RAG](https://docs.langchain4j.dev/tutorials/rag/)。⚠️ raw 缺失，待补充：变换顺序与恢复验证。

## Q3: QuestionAnswerAdvisor 与 RetrievalAugmentationAdvisor 如何选择？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：基础向量检索增强可从前者入手，需要明确组合多个检索阶段时评估后者，不能只用“哪个名字更高级”判断。

| 方式 | 选择时关注 |
|:---|:---|
| `QuestionAnswerAdvisor` | 围绕向量查询与上下文注入的基础使用，检查过滤、模板及来源返回 |
| `RetrievalAugmentationAdvisor` | 通过查询处理、检索、合并/后处理、增强等模块组织流程 |
| 自行编排 | 业务状态、跨源依赖或失败控制超出现有入口适配范围时考虑 |

自行编排仍可复用框架检索接口，不意味着重写全部组件；模块化入口也不意味着必须启用改写、扩展和重排。比较时检查目标版本能力、执行顺序、错误传播和来源获取，避免重复挂载两个 RAG Advisor 导致重复检索或上下文注入。

**验证**：在同一知识库与问题上检查入模上下文、来源返回和模型调用次数，加入空结果与检索异常样本；复杂方案再验证自定义阶段顺序。

**追问**：模块化一定更慢吗？不一定，取决于实际启用了哪些阶段及外部调用。

> 来源：[[AI项目/RAG/19.检索增强生成]]、[[AI项目/RAG/29.Spring AI中的Modular RAG支持]]；官方：[Spring AI RAG](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)。

## Q4: 空上下文配置、提示词拒答与应用返回策略如何保持一致？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：先定义业务可回答性策略，再把它落实到框架、提示与应用层，不把任意一层配置当成保证。

- 区分正常空结果、权限不足、索引不可用和执行异常，不能全部返回“知识库没有答案”。
- `allowEmptyContext` 控制空上下文时的框架处理；允许空上下文并不等于模型必须使用参数知识，也不代表资料足够。
- 严格证据型业务在缺证据时返回明确状态；提示要求说明不足，应用层负责路由和返回格式。
- 可以部分回答时，说明有依据的部分与缺失部分；公开知识兜底需独立的业务策略和来源说明。
- 检查提示是否同时写了“不编造”与“尽量猜测需求后回答”，避免互相冲突。

即使检索非空，内容也可能无法支持答案；是否拒答还须检查证据覆盖，不能只看列表长度。

**验证**：覆盖正常空结果、相关但不足、无关片段、权限不足、后端超时与部分可答；分别核对应用状态、模型输入和最终输出。

**追问**：提示写“不知道就拒答”能代替策略吗？不能，框架配置、应用错误处理和生成表现都需验证。
