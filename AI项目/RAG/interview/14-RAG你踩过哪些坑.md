# 十四、RAG 你踩过哪些坑

[返回题库目录](./README.md) · 更新：2026-10-20

> 一道综合面试题，整理 10 类踩坑素材。这里复盘的是仓库文档记载和代码审阅发现的风险，不代表本人生产经历；面试时只选自己实际处理过的案例。验证项是验收方法，未在本轮执行模型、数据库或故障实验。

## Q1: RAG 项目中你踩过哪些坑？如何定位、修复和防止复发？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

先选两三个能讲清楚的具体案例，按“现象 → 初步假设 → 定位证据 → 根因 → 修复 → 回归与防复发”回答。重点说明为什么判断问题在某一阶段，而不是只报一串优化名词。

优先准备三类：入库阶段的批次与元数据问题；检索阶段的查询污染、版本误召回和融合问题；生成与评测阶段的证据不足、引用错位和指标误读。下面按可追溯的素材展开。

### 坑 1：数据库写入已经分批，向量模型调用仍然报错

- **素材性质**：正文记录的接入问题，具体行为受框架及模型适配器版本影响。
- **现象与根因**：只调整数据库写入批次，却没有确认嵌入请求的条数和 token。正文示例先嵌入，再对数据库写入分批；两个阶段的限制并不相同。
- **定位与处理**：沿实际调用链检查嵌入适配器、批处理策略及最终请求大小，分别控制单条长度、批量条数、总 token 与速率。示例传入了 `BatchingStrategy`，不能反过来断言框架完全不会拆分嵌入。
- **验证与防复发**：用“多条短文本”和“少条长文本”分别验证限制；记录各阶段请求量与失败类型。不要把原文的批次 9 当成所有模型的通用上限。
- **来源**：[[AI项目/RAG/12.向量模型&向量数据库&向量存储]]、[[AI项目/RAG/31.基于LangChain4J实现简单的RAG检索]]；详解见 [[AI项目/RAG/interview/09-离线入库与批处理]] Q1–Q2。

### 坑 2：文本切出来了，页码、文件名和权限元数据却丢了

- **素材性质**：静态代码审阅风险，尚无本轮运行复现。
- **现象与根因**：分片后能看到文本，不代表来源信息完整。正文自定义分片器在 `apply` 中用 `new Document(chunk)` 创建对象，没有显式带上原文档 metadata。
- **定位与处理**：对比切分前后文档对象，检查文档 ID、版本、页码、授权字段和父块映射。创建子块时保留必要元数据，再生成独立片段身份，避免多个子块共用可变对象而互相污染。
- **验证与防复发**：用带页码、版本和权限字段的输入，逐块核验来源与过滤行为；把元数据完整性纳入分片器验收，不只断言块数。
- **来源**：[[AI项目/RAG/8文档分片的代码实现]]；详解见 [[AI项目/RAG/interview/11-自定义分片器代码审阅]] Q4。⚠️ raw 缺失，待补充：修复代码与执行记录。

### 坑 3：名字叫“语义分片”，实际切分效果却不符合预期

- **素材性质**：正文记录了中文句子未按预期拆分、英文缩写被拆开的实验现象。
- **现象与根因**：按句子、按字符、按 token 和依据嵌入相似度切分不是同一机制。类名或方法名不能证明其语言支持与切分质量；字符长度也不能代替目标模型 token 计数。
- **定位与处理**：查看所用版本、调用重载、分隔规则和输出边界。先保留标题、段落与代码结构，再对超长单元二次切分；不能把某次中文实验推广成整个框架永久不支持中文。
- **验证与防复发**：覆盖中文标点、英文缩写、长段落、中英混合及结构化内容，同时检查证据覆盖和目标模型长度限制。
- **来源**：[[AI项目/RAG/8文档分片的代码实现]]、[[AI项目/RAG/9.什么是父子分片]]；详解见 [[AI项目/RAG/interview/02-文档处理与分片]] Q7–Q9。

### 坑 4：召回分很高，却拿错了文档版本

- **素材性质**：正文以不同年份汽车手册演示的错误风险。
- **现象与根因**：不同版本的句子高度相似，但业务规则不同；向量相似不等于满足年份、型号、权限和有效期等条件。
- **定位与处理**：核对用户问题、实际过滤条件和入模片段版本。将明确的业务条件转为结构化约束，授权范围由服务端产生；条件缺失或歧义时澄清，不能自行猜版本。
- **验证与防复发**：同一问题配不同年份、相邻型号和不同用户权限回归；不仅检查命中文档，还检查父块回填、最终答案与引用版本一致。
- **来源**：[[AI项目/RAG/20.RAG优化技术：元数据过滤]]；详解见 [[AI项目/RAG/interview/03-向量检索与存储]] Q8。

### 坑 5：为 SQL 补充的用户信息，污染了所有检索查询

- **素材性质**：评测系列记载的查询改写问题，不将其中效果数字作为个人成绩。
- **现象与根因**：将“用户 ID、当前时间”等信息直接拼到改写后的问题，再广播到向量和全文检索。SQL 所需的执行上下文混入语义查询，可能改变向量表示并引入无关关键词。
- **定位与处理**：同时保存原问题、改写结果和每路实际请求。将问题语义、授权约束与 SQL 业务上下文分开传递；用户明确问到的年份等条件仍应保留，不能机械删除所有时间信息。
- **验证与防复发**：固定问题、语料和配置，比较拆分前后的目标证据排名及错误召回；增加用户身份变化、时间变化和真实时间条件样本。
- **来源**：[[AI项目/RAG评测/18.解决问题重写导致的召回不准问题]]、[[AI项目/RAG/21.RAG优化技术：问题改写]]；详解见 [[AI项目/RAG/interview/04-RAG优化技术]] Q4。

### 坑 6：融合公式没错，结果却重复，引用顺序还乱了

- **素材性质**：评测系列分别记录了内容相等性和引用补全过程中的问题。
- **现象与根因**：同一片段跨检索器构造成不同对象，若身份比较不一致，排名贡献不能正确合并；后续去重或持久化若不保序，又可能破坏重排结果和引用对应。
- **定位与处理**：逐阶段记录片段身份、各路排名、融合分和输出顺序。用明确的文档版本与片段身份统一去重，并保留排序与来源映射；不能只按文本或对象地址推断相同，也不能假设普通 Map 的遍历顺序就是相关性顺序。
- **验证与防复发**：手工构造两路重叠列表验证累加与去重，再核对实际入模顺序和引用展示。原文的框架默认实现分析只作为对应版本案例，不推广为当前版本的固定缺陷。
- **来源**：[[AI项目/RAG评测/19.解决RRF融合乱序和结果重复的问题]]、[[AI项目/RAG评测/20.解决引用信息补全导致参考资料乱序问题]]；详解见 [[AI项目/RAG/interview/07-工程故障与场景设计]] Q5。

### 坑 7：没检索到资料，模型仍然给出流畅答案

- **素材性质**：问题改写正文为了比较效果，展示了无命中但模型仍有回答的情况。
- **现象与根因**：回答可能来自参数知识或推测，语言流畅不能证明答案基于企业资料。允许空上下文和提示词里的“尽量回答”也不能当成有证据的保证。
- **定位与处理**：检查实际入模资料、历史与提示；区分正常空结果、权限不足和后端异常。按业务定义拒答、澄清、部分回答或独立来源兜底，不把执行故障描述成知识库没有答案。
- **验证与防复发**：覆盖相关、无关、部分证据、空结果和检索异常，并检查应用状态、答案与来源支撑；非空资料也可能无法回答问题。
- **来源**：[[AI项目/RAG/21.RAG优化技术：问题改写]]、[[AI项目/RAG/37.检索增强生成]]；详解见 [[AI项目/RAG/interview/12-Java框架调用链与扩展]] Q4。

### 坑 8：Demo 能返回图片，就以为复杂 PDF 已经支持了

- **素材性质**：实战篇明确说明表格、公式和扫描件处理存在局限；图片描述曾使用 mock。
- **现象与根因**：样例中的图片处理成功不代表所有文档元素都被正确解析。描述替代原图后还可能丢失数字、图注和布局，切开图片标签则会破坏资源关联。
- **定位与处理**：先核对原页与解析产物，确认是真实图片理解结果；保留原图、描述、文档位置及稳定资源标识。表格、扫描件等缺口单独设计处理路线，不靠更换生成模型掩盖解析缺失。
- **验证与防复发**：按普通文本、扫描页、多栏、表格和图表建立样本集，分别验收抽取、检索、展示与关键事实；不要只展示一张成功截图。
- **来源**：[[AI项目/RAG/34.实战：多模态RAG智能问答系统]]、[[AI项目/RAG/36.多模态文档处理]]；详解见 [[AI项目/RAG/interview/13-多模态证据处理]]。⚠️ raw 缺失，待补充：复杂版面处理与评测记录。

### 坑 9：改写、多查询和重排都加上了，质量未必涨，耗时先涨了

- **素材性质**：正文提示了组合策略的质量与性能取舍；不是已提供的生产容量结论。
- **现象与根因**：每个模块可能增加调用、候选或 token；多查询还可能重复召回同一证据。把所有优化默认打开，难以判断增益来自哪里，也可能把无关信息塞入上下文。
- **定位与处理**：记录实际调用图、候选数、去重后证据与阶段耗时；做单项和消融对照，再决定启用条件。给多轮调用设置总预算，区分首 token 与完整响应时间。
- **验证与防复发**：固定评测集比较基础链路、单项优化和组合策略，同时报告正确性、误拒、延迟与费用；不能把调用次数增加当作证据覆盖提高。
- **来源**：[[AI项目/RAG/21.RAG优化技术：问题改写]]、[[AI项目/RAG/30.LangChain4J中的Modular RAG支持]]；详解见 [[AI项目/RAG/interview/07-工程故障与场景设计]] Q7。⚠️ raw 缺失，待补充：消融与容量实验。

### 坑 10：评测分涨了，就认为线上问题解决了

- **素材性质**：评测材料的指标口径审校与评测设计提醒，不是已复现的线上事故。
- **现象与根因**：忠实复述错误版本可能忠实度高但答案错；修改裁判、指标、参考答案或样本范围后，分数也不再天然可比。评测执行失败更不能直接丢弃后只报成功样本均分。
- **定位与处理**：固定资料、问题集、指标定义与裁判配置，回看低分和分歧样本；修正错误参考需说明依据，并重跑基线。修正参考不能为了迎合当前答案。
- **验证与防复发**：检查关键类别、误答、误拒、有效样本覆盖及人工一致性。依赖参考数据的召回指标，要在有参考的样本上计算；不能把无标注流量直接当作真实召回率。
- **来源**：[[AI项目/RAG评测/3.RAG的核心评测指标有哪些]]、[[AI项目/RAG评测/7.RAGAS评测时，如何抑制模型幻觉导致的结果不稳定问题？]]；详解见 [[AI项目/RAG/interview/06-RAG评测体系]] Q2–Q3、Q6、Q11。

### 面试时如何选案例

优先选一个有直接错误现象的实现问题，再选一个涉及检索或证据链的问题。每个案例准备原文、输入、阶段输出或实验记录；如果只有代码审阅和设计，没有实际实施，就如实说明。不要把课程作者的日志、模型规格或示例成绩当作自己的经验。

可用下面的表达框架替换为真实材料：

> 在【真实项目】里，一个具体问题是【输入与错误行为】。最初怀疑【原因】，但通过【检查或对照】排除了这个假设，最后定位到【根因】。处理方式是【具体修改】；用【固定样本和指标】复查，并把【反例或完整性检查】加入回归。尚未验证的边界是【局限】。

**追问**：你怎么证明不是模型能力问题？用同一问题逐阶段对照原文、解析、候选、最终上下文和答案，必要时替换为人工确认的证据；给出实验和中间结果，不能只用“换模型后好了一些”归因。

**验证**：本文作为复习入口，以上修复与验证均应回到对应工程执行。⚠️ raw 缺失，待补充：个人负责范围、依赖版本、完整实验日志及优化前后对照；没有记录就不填写性能数字。
