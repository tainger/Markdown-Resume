# ✅RAG 系统的运行指标与容量规划

> 适用对象：know-engine 这类「向量检索 + 重排 + LLM 生成」的企业级 RAG 客服/问答系统。
>
> 一句话总结：**RAG 单次请求比 Agent 短得多（3~10s），但 QPS 比 Agent 高一个数量级；瓶颈从「LLM 长事务并发」转到「向量库 QPS + Embedding 吞吐 + 缓存命中率」，成本仍是 Token，但绝对值比 Agent 低 5~10 倍。**

---

## 一、RAG 与 Agent 的指标差异（面试必答）

| 维度 | AI Agent（ReAct 多轮） | RAG 系统（单轮问答） |
|:---|:---|:---|
| 单次请求耗时 | 15~120s | **3~10s** |
| 入口 QPS（1000 DAU） | ≈2 | **≈10~20**（高一个数量级） |
| 关键容量指标 | 在途并发、LLM RPM | **向量库 QPS、Embedding 吞吐、缓存命中率** |
| LLM 调用次数/请求 | 5~8 次 | **1 次**（仅生成） |
| 成本结构 | Token 占大头（月万元级） | **Token + Embedding 调用**（月千元级） |
| 延迟敏感点 | 首 token（TTFT） | **检索 P95 + 重排 P95** |
| 质量指标 | 意图准确率、工具选择正确率 | **召回率、Faithfulness、Answer Correctness** |
| 失败模式 | 工具级联失败、限流 | **召回漏召、重排噪声、幻觉** |
| 可观测核心 | 链路 trace | **检索召回率、各阶段耗时** |

核心认知：**RAG 比 Agent 更像传统 Web 服务——短请求、中 QPS、强依赖外部存储**。但多了一个维度：**检索质量本身就是运行指标**（召回率低 = 业务失败，不只是慢）。

---

## 二、RAG 指标全景（五层）

```
┌──────────────────────────────────────────────────────────┐
│ L5 业务效果层   DAU/留存/解决率/点踩率/转人工率             │
├──────────────────────────────────────────────────────────┤
│ L4 质量层       召回率/精确率/Faithfulness/Answer Correctness│
├──────────────────────────────────────────────────────────┤
│ L3 检索性能层   向量库 QPS/P95、重排 P95、Embedding 吞吐   │
├──────────────────────────────────────────────────────────┤
│ L2 生成性能层   首 token P95、生成耗时、token/请求         │
├──────────────────────────────────────────────────────────┤
│ L1 系统稳定层   入口 QPS、错误率、缓存命中率、资源利用率   │
└──────────────────────────────────────────────────────────┘
```

| 层 | 指标 | 说明 |
|:---|:---|:---|
| **L1 系统** | 入口 QPS、并发数 | 容量规划基础 |
| | 错误率（向量库超时、LLM 超时、429） | 稳定性 |
| | 缓存命中率（embedding cache、query cache、answer cache） | **RAG 性价比最高的优化** |
| | CPU/内存/网络（向量库常驻内存大） | 向量库是内存大户 |
| **L2 生成** | 首 token 延迟 P50/P95 | 用户体感 |
| | 单请求总耗时 P50/P95 | |
| | Token/请求、Token/天 | 成本核算 |
| **L3 检索** | 向量库 QPS、P95 延迟 | **RAG 独有的关键瓶颈** |
| | Embedding 调用 QPS、吞吐 | Embedding 也是限流对象 |
| | 重排延迟 P95 | 重排模型常走 GPU |
| | 召回 Top-K 数、rerank 输入数 | 漏斗参数 |
| **L4 质量** | 召回率（Recall@K）、精确率（Precision@K） | 见 RAG评测系列 |
| | Faithfulness、Answer Relevancy、Answer Correctness | |
| | 幻觉率、拒答率、引用覆盖率 | |
| **L5 业务** | DAU、解决率（未转人工）、点踩率 | 业务效果 |
| | 转人工率、重问率、平均轮次 | 用户满意度隐式信号 |

## 三、1000 DAU 容量推算

### 3.1 RAG 推算链路

```
DAU
 └─× 人均提问数 = 日 query 数
      └─÷ 活跃窗口 × 峰谷系数 = 峰值 query QPS
           ├─× 0.3~0.5（cache miss 率）= 向量库峰值 QPS
           ├─× 0.3~0.5 = Embedding 峰值 QPS
           └─× 1（每次必走 LLM 生成）= LLM 峰值 QPS → RPM
```

### 3.2 输入参数三档

| 参数 | 保守 | 中等 | 积极 |
|:---|:---|:---|:---|
| DAU | 1000 | 1000 | 1000 |
| 人均提问数/天 | 5 | 10 | 20 |
| **日 query 数** | **5,000** | **10,000** | **20,000** |
| 单 query 耗时 | 3~5s | 5~8s | 8~15s |
| 活跃窗口 | 10h | 同左 | 同左 |
| 峰谷系数 | ×3 | ×4 | ×5 |
| Embedding cache 命中率 | 30% | 50% | 70% |
| 答案 cache 命中率 | 10% | 20% | 30% |

> RAG 的 query 频次比 Agent 高——差旅 Agent 一天 3 会话×6 轮，但 RAG 客服类（手册问答、知识助手）用户问完一个接着问，频次显著更高。

### 3.3 入口 QPS（中等档，10,000 query/天）

| 口径 | 公式 | 结果 |
|:---|:---|:---|
| 全天平均 | $10000/86400$ | ≈ **0.12 QPS** |
| 10h 活跃窗口平均 | $10000/36000$ | ≈ **0.28 QPS** |
| **峰值** | $0.28\times 4$ | **≈ 1.1 QPS（按 1.5 预留）** |

> 看起来很低？**这只是"用户提问"维度的 QPS**。但 RAG 的请求更密集——每次提问必然触发一次完整检索+生成链路，且 cache miss 时下游会被放大。

### 3.4 下游负载（峰值 1.5 query/s，考虑 cache）

| 下游 | 计算（中等档） | 峰值量级 |
|:---|:---|:---|
| **向量库**（miss 率 50%） | $1.5\times 0.5$ | **0.75 QPS**（很低） |
| **Embedding API**（同上） | $1.5\times 0.5$ | **0.75 QPS ≈ 45 RPM** |
| **重排模型**（Top-20 → Top-5） | $1.5\times 1$ | **1.5 QPS** |
| **LLM 生成**（cache 20% 后） | $1.5\times 0.8$ | **1.2 QPS ≈ 72 RPM** |
| **MySQL**（消息日志/反馈） | $1.5\times 5$ | **7.5 QPS** |

> 注意：**积极档（20,000 query/天）下峰值 ≈ 3 QPS**，向量库 ≈ 1.5 QPS，LLM ≈ 2.4 QPS ≈ 144 RPM。仍然不到传统 Web 的零头，但比 Agent 高 5~10 倍。

## 四、并发模型：Little 定律

代入中等档（峰值 1.5 query/s，单 query 6s）：

$$L = \lambda \times W = 1.5 \times 6 = \textbf{9 个在途 query}$$

| 并发资源 | 估算 | 量级 |
|:---|:---|:---|
| 在途 query | 1.5/s × 6s | **≈ 10** |
| 在途 LLM 请求 | 10 × 0.8（cache 后） | **≈ 8 并发** |
| SSE 长连接（同时在线 = DAU×3~8%） | 1000×5% | **30~80 条** |

**对比 Agent**：Agent 在途 60 个、SSE 150 条；RAG 在途 10 个、SSE 80 条。**RAG 容量压力只有 Agent 的 1/6 左右**——这正说明 RAG 的瓶颈不在并发，而在**单次质量**和**检索效率**。

---

## 五、Token 与成本（远低于 Agent）

假设（每 query 输入 5k token = 检索回来的 Top-5 chunk + 用户问题 + system prompt；输出 0.5k）：

| 口径 | 输入 | 输出 |
|:---|:---|:---|
| 日（10,000 query × 80% 经 LLM） | 4000 万 | 400 万 |
| 月 | **≈ 12 亿** | **≈ 1.2 亿** |
| 月费用（混部粗估） | — | **¥1,000~3,000** |
| Embedding 月费用（5000 万 token） | — | **¥50~200** |

**对比 Agent**：Agent 月费 ¥1~5 万，RAG 月费 ¥1~3 千——RAG 便宜 5~10 倍。原因：RAG 每 query 只调 1 次 LLM，输入 token 也少。

### 成本杠杆（按收益排序）

1. **答案 cache 命中率**（20~30%）——热门问题直接返回缓存，省整条链路；
2. **Embedding cache 命中率**（50~70%）——同义问题复用向量；
3. **Top-K 控制**——召回 5 比 20 省 75% 输入 token；
4. **模型分档**——简单 FAQ 用小模型，复杂推理才用强模型；
5. **prompt cache**（system prompt + 知识库前缀缓存）。

## 六、延迟与质量目标（SLO）

| 指标 | 建议目标 |
|:---|:---|
| 检索 P50 / P95 | 50ms / 200ms |
| 重排 P50 / P95 | 100ms / 500ms |
| 首 token（TTFT）P50 / P95 | 0.5~1s / 2~3s |
| 完整响应 P50 / P95 | **3~5s / 8~10s** |
| 端到端错误率 | < 0.5~1% |
| Embedding cache 命中率 | 50~70% |
| 答案 cache 命中率 | 20~30% |
| **召回率（Recall@5）** | **> 85%** |
| **Faithfulness** | **> 0.9** |
| 可用性 | 99.5~99.9% |

> RAG 的 P95 比 Agent 紧——用户对"问答"的耐心比对"复杂任务"短，10 秒不返回就被认为是慢。

## 七、容量配置建议（1000 DAU，中等档）

| 组件 | 配置 | 说明 |
|:---|:---|:---|
| 应用服务 | **1~2 实例 × 2C4G** | 单 query 轻，1 实例够，2 实例做容灾 |
| MySQL | 2C4G 基础版 | 10 QPS 量级，毫无压力 |
| Redis | 512MB~1G | cache + 限流计数 |
| **向量库** | **关键**——见下表 | 与文档量、QPS、召回率强相关 |
| 聊天记录 | ≈ 2KB/query → 20MB/天 → **600MB/月** | 远小于 Agent |

### 向量库选型与规格

| 文档量 | 推荐 | 规格 | 1000 DAU 是否够 |
|:---|:---|:---|:---|
| < 10 万 chunk | Milvus Lite / Qdrant 单机 | 2C4G + 8G 索引 | ✅ 足够 |
| 10 万~100 万 | Milvus 单机 / ES KNN | 4C8G + 16G 索引 | ✅ 足够 |
| 100 万~1000 万 | Milvus 集群 / ES 集群 | 多节点 + HNSW | ✅ 但需调参 |
| > 1000 万 | Milvus 分布式 + 分片 | 多分片 + IVF/HNSW | 需专项设计 |

> know-engine（智界 R7 手册）大概在 1~10 万 chunk 量级，单机 Milvus / ES KNN 足够。

### 上线前必处理的三件事

1. **Embedding API 配额**：峰值 50~150 RPM，DashScope embedding 默认配额通常够，但突发流量仍要预提额；
2. **向量库索引预热**：冷启动时索引加载慢（数十秒），上线前需预热；
3. **重排模型部署**：若自部署 BGE-reranker，需 GPU；若走 API（Cohere/Jina），关注其限流。

## 八、面试问题（运行指标方向）

> 答题骨架：**先纠正认知（RAG 比 Agent 短但 QPS 高）→ 给推算链路 → 给数字 → 落回工程手段**。

### Q1：1000 DAU 的 RAG 系统，QPS 大概多少？需要什么配置？

**答题骨架**：
1. 先算 query：1000 DAU × 10 提问/天 ≈ 1 万 query/天，10h 活跃窗口平均 0.28 QPS，峰值 ×4 ≈ **1.5 QPS**；
2. 下游放大：向量库 0.75 QPS（cache 50%）、LLM 1.2 QPS ≈ 72 RPM、重排 1.5 QPS；
3. 并发用 Little 定律：$1.5\times 6=9$ 个在途 query、8 个在途 LLM 请求、30~80 条 SSE 连接；
4. 配置：1~2 台 2C4G 应用 + 单机向量库（文档 < 10 万 chunk）+ 基础 RDS；
5. **瓶颈不是机器，是向量库索引大小 + Embedding/重排 API 配额**。

### Q2：RAG 和 Agent 的容量规划有什么不同？

| 维度 | RAG | Agent |
|:---|:---|:---|
| 单次耗时 | 3~10s | 15~120s |
| QPS | 高（短请求） | 低（长事务） |
| 关键并发 | 在途 ≈10 | 在途 ≈60 |
| 瓶颈 | 向量库 QPS、Embedding 吞吐 | LLM RPM/TPM |
| 成本 | 月千元级 | 月万元级 |
| 优化重点 | cache 命中率、Top-K | 意图短路、模型分档 |

**关键差异**：RAG 像 Web 服务（短请求、看 QPS），Agent 像工作流引擎（长事务、看在途并发）。

### Q3：RAG 响应慢，怎么定位？

**分层埋点**（必答）：
1. **Embedding 阶段**：query embedding 耗时（cache 命中 vs miss 差异大）；
2. **向量检索阶段**：向量库查询 P95、Top-K 取数；
3. **重排阶段**：rerank 模型调用耗时；
4. **prompt 构造阶段**：chunk 拼接、token 计算；
5. **LLM 生成阶段**：TTFT + 完整生成耗时；
6. **流式传输阶段**：SSE chunk 间隔、网络 RTT。

**优化按收益排序**：
- Embedding cache（最有效，命中率 50~70%）；
- 答案 cache（热门问题直接返回）；
- 向量库索引优化（HNSW M/efConstruction 调参）；
- 重排异步化或降级（高负载时跳过 rerank）；
- LLM 流式输出（首 token 提前）；
- chunk 预取与并行（检索 + 重排流水线）。

### Q4：RAG 的 Token 成本怎么估算？

**骨架**：DAU → 日 query → cache miss 率 → 实际 LLM 调用数 → 平均输入/输出 token → 月量 × 单价。1000 DAU 中等档：1 万 query × 80% miss × 5k 输入 = 4000 万/天，月 ≈ 12 亿输入 + 1.2 亿输出，费用 ¥1~3 千。强调**RAG 比 Agent 便宜 5~10 倍，因为每 query 只调 1 次 LLM**。

### Q5：向量库 QPS 上不去怎么办？

1. **索引选型**：HNSW 召回快但内存大；IVF 召回略低但内存省、可分片；
2. **参数调优**：HNSW 的 `efSearch` 调小（精度换速度）；IVF 的 `nprobe` 调小；
3. **副本与分片**：读多写少 → 加副本；文档量大 → 分片；
4. **缓存层**：query embedding cache + 答案 cache，命中率 50%+ 即减半向量库压力；
5. **降级**：高负载时跳过 rerank 或减少 Top-K；
6. **就近部署**：应用与向量库同 VPC，减少网络 RTT。

### Q6：RAG 的"召回率低"算运行指标还是质量指标？

**两者都是**——这是 RAG 与 Agent 的关键差异：
- **质量维度**：召回率低 = 业务失败（用户问的问题没找到答案）；
- **运行维度**：召回率低往往伴随重试、追问、转人工，拉高 token 成本和延迟。

所以 RAG 的"召回率"既是 L4 质量指标，也是 L1 系统稳定性的间接指标——**召回率低的系统，容量压力会隐性放大**（重试、转人工查询、人工兜底 LLM 调用）。

### Q7：RAG 上线后最重要的三个监控是什么？

1. **召回率在线监控**：定期跑 golden set（100~500 标注问题），每天报召回率/精确率/Faithfulness；
2. **各阶段 P95 延迟**：embedding / 检索 / 重排 / 生成分段埋点，定位慢在哪一层；
3. **cache 命中率 + token 成本**：cache 跌破阈值告警（可能是 query 分布漂移），token 月费异常告警。

### Q8：DAU 涨 10 倍（1 万），RAG 系统最先挂哪里？

按顺序：
1. **向量库**：QPS 从 0.75 → 7.5，单机 Milvus/ES 可能到瓶颈（看索引大小和 efSearch）；
2. **Embedding API**：RPM 从 45 → 450，可能撞 DashScope 默认配额；
3. **LLM Provider**：RPM 从 72 → 720，需提额；
4. **应用层**：CPU/内存/连接池——但通常最后才挂，因为单请求轻；
5. **MySQL**：从 7.5 → 75 QPS，仍不到瓶颈。

应对：向量库加副本/分片、API 提额、应用层水平扩展、cache 命中率优化（这是性价比最高的）。

### Q9：RAG 的 SSE 长连接和 Agent 有什么不同？

- RAG 单次响应快（3~10s），连接生命周期短，断连风险低；
- 但 RAG 用户提问频次高，**连接创建/销毁更频繁**，注意 emitter 复用、连接池；
- RAG 流式生成阶段 chunk 间隔受 LLM 影响，注意 `proxy_read_timeout` 别设太短（≥30s）；
- 答案 cache 命中时无需流式，直接返回完整响应（快路径）。

### Q10：怎么做 RAG 的容量规划？给个方法论。

1. **业务侧**：DAU、人均 query/天、活跃窗口、峰谷系数 → 峰值 QPS；
2. **链路侧**：cache 命中率假设 → 向量库 QPS、Embedding QPS、LLM RPM；
3. **并发侧**：Little 定律 $L=\lambda W$ → 在途并发、SSE 连接数；
4. **资源侧**：向量库规格（看文档量）、应用规格（看并发）、RDS 规格（看 QPS）；
5. **配额侧**：LLM Provider、Embedding Provider、重排 API 的 RPM/TPM；
6. **成本侧**：月 token 量 × 单价 → 预算；
7. **冗余侧**：峰值 ×2~3 留余量，配额按峰值报。

## 九、易错点

1. **拿 Agent 的容量模型套 RAG**——RAG 单次短、QPS 高、并发低，不是长事务；
2. **只看 LLM RPM 不看 Embedding RPM**——Embedding 也会限流，且更易被忽视；
3. **向量库按 QPS 估算，忽略索引大小**——文档量大时单次查询也慢；
4. **cache 命中率假设过高**——上线初期实际命中率常低于预期（10~20%）；
5. **重排模型未做容量评估**——自部署 BGE-reranker 需 GPU，API 版有限流；
6. **向量库冷启动未预热**——首次请求超慢（索引加载数十秒）；
7. **chunk 数量与文档数混为一谈**——1 个文档可能切 10~50 chunk，向量库规模按 chunk 算；
8. **忽略召回率对容量的隐性放大**——召回率低 → 重试 → 下游压力翻倍。

---

## 十、一句话总结

**入口按 QPS 算账（≈1.5）、容量按在途算账（≈9 在途）、配额按 RPM 算账（LLM≈72、Embedding≈45）、成本按 Token 算账（月千元级）、质量按召回率算账（>85%）、性能按 P95 算账（<10s）**——六本账分开，才是 RAG 运行指标的正确打开方式。

**对比 Agent**：RAG 的 QPS 高 5 倍、并发低 1/6、成本便宜 5~10 倍、瓶颈在向量库而非 LLM 配额——**这是两套完全不同的容量模型**。
