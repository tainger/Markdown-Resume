前面我们介绍过了如何获取测评集，有一种方式是通过文档可以生成一些问题和答案。那么ragas就只次，我们介绍下如何使用。

### 基于AI生成数据集


比如我们提前准备一份文档，markdown格式最好，放到docs目录下


![docs 目录示例](./assets/10-docs-directory.png)


运行以下脚本代码：

```python
from langchain_community.document_loaders import DirectoryLoader
from ragas.llms import LangchainLLMWrapper
from ragas.testset import TestsetGenerator
from ragas.embeddings.base import embedding_factory
from openai import OpenAI
from dotenv import load_dotenv
from ragas.llms import llm_factory
import os

# 1. 加载环境变量
load_dotenv()

# 2. 加载文档
path = "docs/"
loader = DirectoryLoader(path, glob="**/*.md")
docs = loader.load()

# 3. 配置 LLM
openai_client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))
llm = llm_factory("qwen3.7-max", client=openai_client)

# 4. 配置 Embeddings
embeddings = embedding_factory("openai", model="text-embedding-v4", client=openai_client)

# 5. 生成测试集
generator = TestsetGenerator(llm=llm, embedding_model=embeddings)
dataset = generator.generate_with_langchain_docs(docs, testset_size=10)

# 6. 导出结果
df = dataset.to_pandas()
print(df)

df.to_csv("rag_testset.csv", index=False)
print("测试集已成功导出为 rag_testset.csv")
```


运行以上代码。可以看到运行进度：

![RAGAS 运行进度](./assets/10-rag-progress.png)


- `Applying HeadlinesExtractor` (提取标题) & `HeadlineSplitter` (按标题切分)：AI 正在通读你的 Markdown 文件，识别出里面的各级标题，理清文档的整体骨架结构。
- `Applying SummaryExtractor` (提取摘要)：AI 对文档的各个部分进行总结概括，以便后续能基于这些摘要来设计问题。
- `Applying CustomNodeFilter` (节点过滤)： AI 正在从文档中筛选出最有价值、信息密度最高的文本片段（Nodes），剔除掉那些无关紧要的内容。
- `Applying EmbeddingExtractor` (向量化处理)：将筛选出来的文本片段转换成计算机能理解的数学向量，方便后续评估检索的准确度。
- `Applying ThemesExtractor` (提取主题) & `NERExtractor` (提取命名实体)：AI 进一步分析文档中的核心话题以及专有名词（如人名、产品名、地名等）。
- `CosineSimilarityBuilder` & `OverlapScoreBuilder`：计算各个文本片段之间的相似度与重叠度，为后续生成需要跨段落推理的复杂问题建立关联。
- `Generating personas` (生成用户画像)：AI 虚拟出了不同类型的提问者角色（比如“新手小白”、“资深专家”），让生成的问题更贴近真实用户的提问习惯。
- `Generating Scenarios` (生成应用场景)：结合刚才提取的知识点和用户画像，构思出具体的提问背景。
- `Generating Samples` (生成最终样本)：最~~后，综合以上所有信息，生成高质量~~测试数据


### 基于 AI 生成评测集的工作原理

上面的进度条看起来是"AI 在读文档然后出题"，但真实机制和大家直觉里想的不太一样：**ragas 并不是把文档丢给 LLM、让它直接写 10 道题**。它的做法是先把你的文档**编译成一张知识图谱（Knowledge Graph）**，让每个知识片段都带上摘要、主题、实体、向量这些标签，再从这张图谱里"反推"出问题。

官方文档把整个流程归为两个大阶段（2 main operations）：**建图** 和 **出题**。


```text
阶段一：建图 KnowledgeGraph Creation
────────────────────────────────────────────
原始文档
  │ ① HeadlinesExtractor + HeadlineSplitter
  │      按标题把文档切成层级节点（DOCUMENT → CHUNK）
  ▼
节点集合
  │ ② Extractors：给节点打标签（全部靠 LLM / Embedding）
  │      SummaryExtractor   → 摘要节点 SUMMARY
  │      EmbeddingExtractor → 节点向量
  │      ThemesExtractor    → 主题节点 THEME
  │      NERExtractor       → 命名实体/关键词节点 KEYPHRASE
  │ ③ CustomNodeFilter：剔掉信息量低、不值得出题的节点
  ▼
带标签的节点集合
  │ ④ Relationship Builder：把节点连成边
  │      CosineSimilarityBuilder / OverlapScoreBuilder
  ▼
KnowledgeGraph（节点 + 关系）


阶段二：出题 Testset Generation
────────────────────────────────────────────
KnowledgeGraph
  │ ⑤ Generating personas：虚拟出不同提问者画像（新手 / 专家 / …）
  ▼
Persona（用户画像）
  │ ⑥ QuerySynthesizer 按"问题类型"挑节点 → generate_scenarios
  ▼
Scenario（画像 + 问题类型 + 一组指定节点）
  │ ⑦ generate_sample：真正落笔，写出问题 + 参考答案
  ▼
Sample = user_input（问题）+ reference（标准答案）+ reference_contexts（出题用的资料）
```


**为什么要多绕一层知识图谱？**

1. **不同类型的问题，需要的上下文不一样。** 单跳问题只要一个 chunk 就够；多跳问题需要把两三个 chunk 串起来。所以必须先有第 ④ 步"节点之间的边"（相似度/重叠），才能凑出跨段落的上下文——这也是进度日志里 `CosineSimilarityBuilder`、`OverlapScoreBuilder` 存在的原因。
2. **控制多样性。** 节点打完主题、实体标签后，才能避免 10 道题全问同一段内容。
3. **成本复用。** 摘要、主题、实体、向量都是一次性算好挂在图谱上的，后面每种问题类型都从同一张图谱取料，不必重复分析文档。


**四种问题类型与默认分布**

ragas 按「单跳/多跳 × 具体/抽象」把问题分成四类，`default_query_distribution()` 的默认配比是：


| 问题类型 | 含义 | 默认占比 |
| --- | --- | --- |
| SingleHopSpecific 单跳-具体 | 一个 chunk 就能回答的事实题（如"某某配置项的默认值是多少"） | 0.5 |
| MultiHopAbstract 多跳-抽象 | 跨多个 chunk，需要归纳、解释的开放题 | 0.25 |
| MultiHopSpecific 多跳-具体 | 跨多个 chunk，把几处事实拼起来才能答 | 0.25 |
| SingleHopAbstract 单跳-抽象 | 单段落上的开放题（不在默认分布里，需自己配） | - |


**进度日志与两个阶段的对应关系**


| 日志 | 所属阶段 | 在干什么 |
| --- | --- | --- |
| HeadlinesExtractor / HeadlineSplitter | 阶段一 ①② | 定文档骨架、切节点 |
| SummaryExtractor / CustomNodeFilter | 阶段一 ②③ | 打摘要标签、筛掉低价值节点 |
| EmbeddingExtractor / ThemesExtractor / NERExtractor | 阶段一 ② | 补向量、主题、实体三类标签 |
| CosineSimilarityBuilder / OverlapScoreBuilder | 阶段一 ④ | 连边，为多跳问题准备"跳板" |
| Generating personas / Scenarios / Samples | 阶段二 ⑤⑥⑦ | 画像 → 场景 → 落笔出题 |


**想干预的话，入口有三个**

- 改问题配比：把 `default_query_distribution(llm)` 换成自己的 `[(Synthesizer(llm), 权重), ...]` 传给 `generator.generate(testset_size=10, query_distribution=...)`。
- 改建图方式：自定义 Transformations（切分器、抽取器、关系构建器）或直接传入现成的 `KnowledgeGraph`。
- 代码上用哪个 API：本文示例的 `generate_with_langchain_docs()` 是"建图 + 出题"一步到位的封装；如果图谱要复用、要分步调试，就用 `KnowledgeGraph` + `generate()` 自己拆开跑。


这也解释了文末那个关键点：`reference_contexts` 里的资料，是**第 ⑦ 步为写出标准答案而挑出来的节点**（也就是"出题时的已知答案出处"），并不是你的 RAG 系统实际检索到的东西。所以这份数据集可以当"题库"，但还不能直接拿去算 Context Precision / Recall。


这个过程根据你的文档的大小，LLM的情况，可能会比较慢。


最终会得到一份csv文档，里面包含了10条数据，分别包含了用户问题、参考内容以及标准答案：

![CSV 结果示例](./assets/10-csv-result.png)


可以看到，上面的数据集中是不包含我们的RAG系统针对问题的回答的，所以，根据上一期我们介绍的各个指标需要的参数，那么有了这份数据集，就可以针对Context Precision、Context Recall两个指标做评测了么？


其实并不是，因为上面的数据集中的参考资料，其实是生成标准答案的参考资料，而我们要对RAG测评，需要拿到RAG实际检索到的参考资料才行。

|  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- |
| 指标 | 问题 | AI回答 | 参考材料 | 标准答案 | LLM | Embedding |
| Context Precision上下文准确率 | ✅ |  | ✅ | ✅ | ✅ |  |
| Context Recall上下文召回率 | ✅ |  | ✅ | ✅ | ✅ |  |
| Answer Relevancy答案相关性 | ✅ | ✅ |  |  | ✅ | ✅ |
| Faithfulness忠诚度 | ✅ | ✅ | ✅ |  | ✅ |  |
| Answer Correctness答案准确性 | ✅ | ✅ |  | ✅ | ✅ | ✅ |


不管是针对Context Precision、Context Recall两个指标做评测，还是要针对另外几个指标做评测，我们还需要基于这份数据集，生成我们自己的RAG问答系统的答案+参考资料才行。
