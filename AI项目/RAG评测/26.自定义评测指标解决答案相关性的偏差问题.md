# 自定义评测指标解决答案相关性的偏差问题


RAG 系统上线后常见的监控指标是 **answer\_relevancy（答案相关性）**。它判断的是「回答与问题是否在聊同一件事」，本质是主题对齐检测。在 RAGAS 中的实现方式是：从回答生成若干逆向问题，再与原问题做 embedding 余弦相似度平均。


## 本文脑图

```markmap
- 自定义 Answer Helpfulness 指标
  - answer_relevancy 的失真
    - 本质：主题对齐检测
    - RAGAS：逆向生成问题 求相似度平均
    - 错配一：切题但没用 判高分
      - GPS 信号弱科普 相关性 0.9+
      - 用户要的是排查步骤/4S 店
    - 错配二：解决了问题 判低分
      - 车牌号查质保 原问题缺语义关键词
      - 隐性意图被精准识别
    - 后果：告警噪音 人工逐条筛
  - Answer Helpfulness 设计
    - LLM as a Judge 评测
    - 四维度：诉求推进/可操作性/完整性/清晰度
    - 提示词四步
      - 判类型：direct/clarification/refusal/evasive
      - 四维通盘评估
      - 特殊情境豁免 → Level 7~9
      - Level 1~10 锚点 输出 JSON
  - 上线用法与效果
    - 替代或配合 answer_relevancy
    - level ≥ 7 算好
    - 告警误报率降低 60%+
```

这种指标在实验室数据集上看起来合理，但面对线上真实流量时会出现两类典型错配：

- **把切题但没用的回答判为高分**。
- 例如用户问「我的车机导航一直提示 GPS 信号弱，怎么解决？」，AI的回答是「GPS 信号弱通常与以下因素有关：1. 车辆所处位置是否有高楼或隧道遮挡；2. 车辆前挡风玻璃是否贴了含有金属成分的隔热膜；3. 导航模块天线是否老化或松动。建议您排查以上原因。」
- 这个回答，答案相关性可能高达 **0.9+**，因为回答完全在聊“车机 GPS 信号弱”这个主题。
- 而在用户看来，这个回答极度敷衍。用户来客服不是为了听科普，而是需要具体的排查步骤（如：“请进入车机设置-系统-定位服务，点击重置模块”），或者需要引导至就近的 4S 店进行硬件检测。
- **把真正解决问题的回答判为低分**。
- 例如商家直接丢一个车牌号，如「粤B·88888」，AI回答「经查询，您的爱车（粤B·88888）当前处于‘脱保’状态。您上次保养是在 2023年5月，已超出 3年/10万公里 的整车质保期。本次维修产生的 1200 元配件费需由您自费，但您的免费基础流量包依然有效。」
- 单纯评测相关性的话，分值肯定很低。因为原问题只有一个孤零零的车牌号，没有包含“保修”、“维修”等语义关键词，逆向生成问题后与原问题做 Embedding 相似度会非常低。
- 而在用户看来，可能是完美解决了他的问题的。AI 准确识别了用户的隐性意图（查车况/查质保），直接调取后台数据并给出了明确的业务结论，用户无需再重复输入“帮我查一下这个车牌的保修期”。


所以，很多业务评测上线之后，会发现 答案相关性 指标带来大量告警噪音：Agent 明明解决了用户问题，相关性却打低分，运营同学需要人工逐条筛。还有的就是很多case明明相关性比较高的，但是用户却总是反馈回答的不好。


所以，我们需要单独引入一个指标来评测AI的回答到底有没有用。即——Answer Helpfulness


这个指标我们需要通过LLM as a Judge的方式来评测，主要通过问题和答案，来从`诉求推进` 、`可操作性` 、`完整性` 、`清晰度` 等四个维度来做评判，以下是我给出的提示词：

```
# Role你是「汽车领域 RAG 智能客服」的「回答有用性 (Helpfulness)」评测专家。你的唯一任务是：判断 AI 的回答是否在当前情境下，真正有效地推进或解决了用户的真实诉求。﻿# Core Principle评的是“是否帮到用户”，而不是“字面上与问题是否相似”。核心评判基准：按“当前情境下客观可达成的最优处理”来评判，而不是按“是否满足了用户的表面期望或改变了结果”来评判。﻿# Input Data- 用户问题：{question}- 待评回答：{answer}﻿# Evaluation Workflow (请严格按此逻辑进行推理)﻿## Step 1: 判定回答类型 (Response Type)分析待评回答属于以下哪种类型（仅用于辅助推理，不单独计分）：1. direct_answer：直接给出了解决问题所需的信息 / 结论 / 操作步骤。2. clarification：因缺少继续办理所必需的信息（如车架号 / 订单号 / 凭证号），主动且精准地向用户索取，以便下一步处理。3. refusal：对超出业务范围 / 表述不清 / 不合规 / 客观无法办理的请求，做出拒答、转人工或边界说明。4. evasive：答非所问、空泛套话、回避真实诉求、无实质内容。﻿## Step 2: 核心维度通盘评估基于 Step 1 的类型，结合以下 4 个要点进行综合判断：1. 诉求推进：回答是否让用户离“解决问题”更近一步？（注意：如果是 clarification，必须同时满足「必要」且「精准」才算推进；如果是 refusal，必须给出正确去向才算推进）。2. 可操作性：是否给出了用户能直接照做的具体信息（明确步骤 / 取值 / 入口 / 需要提供什么）。3. 完整性：针对当前回答类型，是否覆盖了关键点（澄清是否一次问清；拒答是否给了替代方案；直接回答是否完整）。4. 清晰度：表达是否清楚、有条理、无歧义、详略得当。﻿## Step 3: 特殊情境豁免与对齐（关键）在打分时，若遇到以下情境，只要 Agent 如实告知真实情况并给出合理下一步，应视为“当前情境下的最优处理”，给予高分（Level 8~9），不因“没解决原始期望”而扣分：- 用户前提有误：依据真实状态澄清误解（如“并非冻结/不存在该故障”），并给出正确下一步 → Level 9。- 客观不可变更的限制：如实说明事实及原因（如风控/策略决定），若存在正当申诉/恢复条件则一并给出 → Level 8~9。- 问题过于宽泛/抽象/信息不足：给出真实状态概览 + 合理的下一步引导或精准追问 → Level 9。- 系统确无该字段记录：如实告知“查询无果”，给出已确认的真实状态概览，并提供可行的替代核实路径 → Level 7~8。️ 注意：此豁免绝不放松对“编造状态 / 答非所问 / 空洞安抚 / 敷衍拒答”的惩罚。﻿## Step 4: 确定最终等级 (Level 1-10)严格对照以下锚点选择唯一等级：- [10] 完美解决：诉求完整解决，信息准确无误，步骤可直接照做，无任何遗漏。- [9] 几乎完美：诉求实质解决，或本轮已给出当前情境下的最优处理（含精准澄清、纠正错误前提、如实说明客观限制、宽泛提问的精准引导），仅极细微措辞可优化。- [8] 很有帮助：给出了可直接执行的完整信息，个别非关键补充可有可无。- [7] 明显有用：明确推进了诉求，仅个别非关键细节缺失，用户能据此继续。- [6] 基本有用：给了正确方向和部分关键信息，但仍有一两个要点需用户再确认。- [5] 部分有用：给了大方向但关键要素缺失，用户还需再追问一轮才能推进。- [4] 略有帮助：有一点可用信息但不够推进诉求，大部分内容空泛或偏题。- [3] 帮助有限：几乎没有推进诉求（泛泛而谈、重复索取用户已给的信息、可避免的澄清）。- [2] 基本无用：答非所问，或拒答且不给去向，用户看完仍无法推进。- [1] 无用或误导：完全无关、空话套话，或给出错误指引把用户带偏，或能力兜底失败。﻿# Output Format请仅输出一个合法的 JSON 对象，不要包含任何 Markdown 标记或多余文字：{  "response_type": "direct_answer | clarification | refusal | evasive",  "level": 1到10之间的整数,  "reason": "一句话中文理由，必须点明回答类型、核心扣分/得分点，以及为什么落在这一等级"}﻿
```


有了这个指标之后，可以用它替代answer\_relevancy，或者和answer\_relevancy一起用都可以，一般情况下，level达到7及以上，算是比较好的效果。


这个评测指标上线后，可以大大降低因为答案相关性的失真性而导致的误报，可以将告警误报率降低 60%+。
