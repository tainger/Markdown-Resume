# 线上幻觉 Case 的预发回放机制：让"推理日志"变成可复现的取证材料

上一轮我们聊了"怎么排查"，这一轮解决的是更工程化的问题：**线上出了幻觉，怎么把它"搬"到预发环境里原样重放，拿到完整的推理日志。**

ReAct 的推理日志能看，是因为每一步都在当前进程里。但线上环境不一样——你不可能在线上开 `enable_thinking=True` 然后盯着日志等，流量、延迟、成本都不允许。所以需要一套 **"线上只录快照，预发做重放"** 的机制。

## 一、核心思路：线上录"指纹"，预发做"回放"

线上和预发承担不同职责：

|  | 线上环境 | 预发环境 |
| :--- | :--- | :--- |
| **目标** | 正常服务，只做轻量记录 | 复现问题，开启完整日志 |
| **记录内容** | 请求输入 + 关键中间产物指纹（hash） + 版本信息 | 完整推理链、思考过程、每一步输入输出 |
| **推理日志** | 关闭（省 token、降延迟） | 开启（`enable_thinking=True`） |
| **可复现性** | 只记录"发生了什么" | 用相同输入重新执行，对比"为什么发生" |

微软的 Agent Replay 框架就是这个模式：线上捕获完整执行快照（模型部署版本、系统提示词 hash、工具调用响应、trace 时间线），存到 Blob Storage；预发加载快照，用相同的输入重新执行 agent chain，逐步对比输出。


## 二、线上录什么：快照的字段设计

一个 RAG 幻觉 case 要能被预发准确重放，线上快照至少需要记录：

```json
{
  "trace_id": "xxx",
  "timestamp": "2026-09-23T14:30:00",

  "// 1": "请求层：用户原始输入",
  "user_query": "智界R7的行车记录仪视频怎么导出？",

  "// 2": "检索层：模型实际“看到”了什么",
  "retrieved_chunks": [
    {"chunk_id": "...", "content": "...", "rerank_score": 0.72, "source": "..."}
  ],
  "rerank_scores": [0.72, -0.15, 0.68],

  "// 3": "生成层：模型配置（用于复现相同条件）",
  "model_version": "qwen3.6-plus",
  "system_prompt_hash": "sha256:abc123...",
  "generation_params": {"temperature": 0.2, "topP": 0.9, "enable_thinking": false},

  "// 4": "输出层：最终答案 + 引用列表",
  "final_answer": "...",
  "citations": [],

  "// 5": "版本锚点：知识库索引版本",
  "index_version": "v20260923",
  "prompt_version": "v3.2"
}
```

> 注意：上面带 `//` 的键只是为了在示例里标注分组，真实落盘的 JSON 里不要写注释。`rerank_scores` 里的**负分也要原样记录**。

关键点：**`retrieved_chunks` 必须记录实际送入模型的那一批**，而不是"检索系统认为应该返回的"。第 21 篇讲的 `minScore` 过滤后仍有负分 chunk 混入，如果线上只记录"检索到了什么"而不记录"最终喂给模型的是什么"，预发回放时条件就不一致。


## 三、预发回放：从快照到推理日志

拿到线上快照后，预发环境做三件事：

### 1. 用相同输入重新执行 RAG 链路

把快照里的 `user_query` + `retrieved_chunks` + `system_prompt_hash` 对应的完整提示词，喂给**开启了思考模式**的模型：

```java
// 预发环境：排查专用配置
ragChatModel = OpenAiStreamingChatModel.builder()
    .modelName(snapshot.modelVersion)                    // 与线上一致
    .temperature(snapshot.generationParams.temperature)
    .customParameters(Map.of("enable_thinking", true))   // 关键：打开思考模式
    .build();
```

### 2. 捕获完整推理链

开启思考模式后，模型的 `reasoning_content` 就是"推理日志"。行车记录仪那个幻觉 case，如果线上录了快照、预发用 `enable_thinking=True` 重放，大概率能看到模型在思考过程里"补全"了 `/DCIM/100R7/` 目录结构的步骤——这个步骤在参考资料的 chunk 里根本不存在。

### 3. 对比线上输出，定位分歧点

把预发重放的输出与线上快照的 `final_answer` 对比：

- **检索层一致，但输出不同** → 模型采样随机性导致，需要多次重放。
- **检索层一致，输出也一致，但都有幻觉** → 生成层问题（提示词、模型能力）。
- **检索层不一致** → 回放条件不完整，快照缺字段。


## 四、和标准 Tracing 的区别：为什么"回放"不是"看日志"

这里容易混淆：LangSmith / Langfuse / Phoenix 也能看 trace，为什么还需要专门的 replay？

|  | 标准 Tracing | 预发 Replay |
| :--- | :--- | :--- |
| **能力** | 看"当时发生了什么" | 用相同条件**重新执行**，看"如果再来一次会怎样" |
| **推理日志** | 线上没开 `enable_thinking`，就没有 | 预发开启，补上缺失的推理链 |
| **干预能力** | 只能看，不能改 | 可以 fork：改一个 chunk、换提示词，看输出怎么变 |
| **成本** | 线上持续记录 | 只在需要排查时执行，token 成本可控 |

retrace-sdk 的 "cascade replay" 就是这个思路：在 dashboard 里 fork 任意一步，SDK 会用修改后的输入**重新执行整个函数**，所有下游步骤随之分化。对 RAG 来说，就是在"检索完成、生成开始"这个节点 fork，换掉某个 chunk 或改掉提示词，看幻觉是否消失。


## 五、落地检查清单

要让这套机制跑起来，线上需要满足：

- [ ] **每次 RAG 请求生成唯一 `trace_id`**，贯穿检索 → 重排 → 生成全链路。
- [ ] **记录实际送入模型的 `retrieved_chunks` 及其 `rerank_score`**，包括被 `minScore` 过滤掉的和低分残留的。
- [ ] **记录生成参数和系统提示词 hash**，确保预发能复现相同条件。
- [ ] **知识库索引版本随请求记录**，避免"线上用的是 v2 索引，预发用的是 v3"导致回放失真。
- [ ] **预发环境预留"排查模式"开关**，打开 `enable_thinking=True`、提高 `max_tokens`、写完整推理链到独立日志文件。
- [ ] **回放结果与线上输出做 diff**，明确分歧发生在检索层还是生成层。


## 一句话总结

线上幻觉排查的工程化路径是：**线上录快照（输入 + 实际检索结果 + 版本指纹），预发开思考模式做回放（相同输入重新生成，拿到推理日志），对比分歧定位根因。** ReAct 的推理日志之所以好拿，是因为它本来就在跑；RAG 的推理日志需要靠"预发回放"补回来，但补的方式必须是**条件一致的重执行**，而不是简单的日志查看。
