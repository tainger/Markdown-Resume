# 05. 线程模型与 Scheduler

> 目标：能回答每一段代码在哪执行，避免把“返回 Mono”误当成“自动异步”。返回 [[AI项目/Reactor/README]]。

## 1. 默认不凭空创建线程

```java
Mono.just("hello")
        .map(text -> {
            System.out.println(Thread.currentThread().getName());
            return text.toUpperCase();
        })
        .subscribe(System.out::println);
```

若在 main 线程订阅，这个同步链通常就在 main 执行。网络客户端、计时操作符或显式调度可能引入其他线程；要观察具体来源和切换点。

依据：[线程与调度器](https://projectreactor.io/docs/core/release/reference/coreFeatures/schedulers.html)。

## 2. subscribeOn 与 publishOn

```java
Mono.fromCallable(() -> {
            System.out.println("读取：" + Thread.currentThread().getName());
            return "hello";
        })
        .subscribeOn(Schedulers.boundedElastic())
        .map(String::toUpperCase)
        .publishOn(Schedulers.parallel())
        .map(text -> {
            System.out.println("转换：" + Thread.currentThread().getName());
            return text.length();
        })
        .block(Duration.ofSeconds(2)); // 仅在本例同步边界等待
```

| 操作符 | 主要作用 | 阅读规则 |
|:---|:---|:---|
| `subscribeOn(s)` | 调度向上游的订阅及相关请求工作 | 给同步阻塞源使用时紧跟源，意图最清晰 |
| `publishOn(s)` | 将该点收到的信号转交指定 Scheduler 处理 | 后续通常在这里切换，直到下一切换点 |

`subscribeOn` 本身不会发起订阅。异步源自带的回调线程也不必被它“永久接管”；不要把整条复杂链概括成同一个线程。

`publishOn` 通常引入队列与预取；频繁切换会增加调度和缓存成本，不是越多越快。

## 3. 阻塞 SDK 的标准适配

```java
Mono<User> user = Mono.fromCallable(() -> legacyClient.loadUser(id))
        .subscribeOn(Schedulers.boundedElastic());
```

这里做了两件事：`fromCallable` 延后调用并把异常转成信号；`subscribeOn` 把调用安排到适合等待的工作线程。

```java
// 问题：loadUser 在包装之前就执行了
Mono<User> wrong = Mono.just(legacyClient.loadUser(id))
        .subscribeOn(Schedulers.boundedElastic());
```

即使适配后，SDK 调用本身仍是阻塞的，只是放到了其他线程。它是否响应取消、中断或自身超时，仍需核对 SDK。

依据：[包装同步阻塞调用](https://projectreactor.io/docs/core/release/reference/faq.html)。

## 4. Scheduler 怎么选

| Scheduler | 适用 | 边界 |
|:---|:---|:---|
| `immediate()` | 当前线程直接执行 | 不隔离阻塞 |
| `single()` | 共享单工作线程，适合串行的小任务 | 一个阻塞会影响同一工作线程其他任务 |
| `parallel()` | 固定数量的工作线程，适合 CPU 计算 | 不适合等待 JDBC/同步 HTTP |
| `boundedElastic()` | 受限工作线程与排队，适合同步阻塞 I/O | 饱和后仍会排队或拒绝，不是无限容量 |
| `newBoundedElastic(...)` | 为特定阻塞服务建立专属池 | 应用负责生命周期，避免每个请求创建一个池 |

本系列 Java 17 实验使用平台线程；不能因为 Reactor 支持虚拟线程，就说本项目默认运行在虚拟线程上。Java 21+ 的相关配置见 [3.8.2 Schedulers API](https://projectreactor.io/docs/core/3.8.2/api/reactor/core/scheduler/Schedulers.html)。

## 5. CPU 并行与异步 I/O 并发

```java
Flux<Integer> computed = Flux.range(1, 100)
        .parallel(4)
        .runOn(Schedulers.parallel())
        .map(i -> i * i)
        .sequential();
```

`parallel(4)` 先拆成 4 条处理轨道，`runOn` 才为轨道安排执行资源；`sequential` 合并回 Flux，不等于恢复原始全局顺序。

异步远程请求通常优先用带 concurrency 的 `flatMap`；不要把每个轻量操作都拆到线程池。依据：[ParallelFlux](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-parallelizing-parralelflux.html)。

## 6. 线程切换后的状态

- `ThreadLocal` 绑定线程，不能自动等同于一次响应式请求的上下文。
- 同一个订阅内普通信号有顺序约束，但多个内部流、多个订阅和共享对象仍可能并发访问状态。
- `AtomicInteger` 解决一个变量的原子操作，不会让多步骤业务事务自动一致。

项目案例：[[AI项目/gogo-agent/27.基于Reactor Context 实现多智能体之间的会话上下文传递]]；订阅级状态见 [[AI项目/Reactor/09.Context与资源生命周期]]。
