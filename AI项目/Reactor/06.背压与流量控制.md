# 06. 背压与流量控制

> 目标：知道数据快于消费时，压力转移到了哪里。返回 [[AI项目/Reactor/README]]。

## 1. 背压不是 sleep

背压 Backpressure 是下游用 `request(n)` 表达还能接收多少数据。请求沿上游传，数据沿下游传。

```text
消费者 --request(2)--> 上游
消费者 <--onNext(A)-- 上游
消费者 <--onNext(B)-- 上游
消费者 --request(1)--> 上游
消费者 <--onNext(C)-- 上游
```

额度是累计的；它限制发射的数据量，不是“每秒多少条”。完成/错误信号不消耗业务数据额度。`cancel()` 请求停止发送并释放资源，但不保证外部操作立刻停止。

依据：[Reactive Streams Subscription](https://www.reactive-streams.org/reactive-streams-1.0.4-javadoc/org/reactivestreams/Subscription.html)。

## 2. 手动控制需求

```java
Flux.range(1, 5).subscribe(new BaseSubscriber<Integer>() {
    @Override
    protected void hookOnSubscribe(Subscription subscription) {
        request(1);
    }

    @Override
    protected void hookOnNext(Integer value) {
        System.out.println(value);
        request(1); // 同步处理完成后，再要一个
    }
});
```

若回调里启动一个异步操作就立刻 `request(1)`，只说明“已经启动”，不说明“已经处理完成”。更适合把异步工作组合成 `concatMap` 或带并发上限的 `flatMap`。

普通 lambda 形式的 `subscribe` 通常请求无界额度，所以“用了 Flux”不代表应用主动逐条控制了需求。

依据：[BaseSubscriber 与背压](https://projectreactor.io/docs/core/release/reference/coreFeatures/simple-ways-to-create-a-flux-or-mono-and-subscribe-to-it.html)。

## 3. limitRate、prefetch 和 concurrency

```java
Flux<Result> handled = source
        .limitRate(32)
        .flatMap(value -> processAsync(value), 8, 4);
```

| 参数/操作符 | 控制什么 | 不保证什么 |
|:---|:---|:---|
| `limitRate(32)` | 将下游需求分批向上游传递 | 每秒 32 条、最多只有 32 个对象存活 |
| concurrency=8 | 同时订阅的内部 Publisher 数 | 全应用只有 8 个任务 |
| prefetch=4 | 对内部源预先请求的额度 | 整个应用总缓存只有 4 条 |
| `buffer(32)` | 32 条数据形成一个列表 | 过载队列最大长度为 32 |

`publishOn`、合并、网络适配器及业务缓存可能各有队列，必须观察整条链。内存评估至少考虑元素大小、活跃订阅数、队列数量与容量。

依据：[Flux API](https://projectreactor.io/docs/core/3.8.2/api/reactor/core/publisher/Flux.html)。

## 4. 来源不支持减速时怎么办

| 策略 | 适用 | 代价 |
|:---|:---|:---|
| 有界 buffer | 短时突发、允许排队 | 达到容量后必须明确失败/丢弃策略 |
| drop | 某些采样、非关键通知 | 数据丢失，需要统计 |
| latest | 只关心最新状态，如进度百分比 | 中间状态丢失 |
| error | 不能悄悄丢数据，必须显式过载 | 调用方需要重试或降级方案 |

```java
Flux<Event> bounded = source.onBackpressureBuffer(256);
```

这里限制该操作符维护的队列；溢出行为按 API 传播，不能据此推断上游 SDK 也有界。`onBackpressureBuffer` 会主动向上游请求数据，它是将压力暂存进本地队列，不是让生产者自动慢下来。

文本生成的增量 token、财务事件不适合随意 `drop` 或 `latest`，否则会破坏内容或业务记录；进度通知则可能允许只保留最新值。这是业务选型，需要明确语义。

## 5. 外部回调与 Flux.create

```java
// 适配思路，API register/listener 为业务伪代码
Flux<String> events = Flux.create(sink -> {
    Registration registration = api.register(new Listener() {
        public void onData(String text) { sink.next(text); }
        public void onError(Throwable error) { sink.error(error); }
        public void onDone() { sink.complete(); }
    });
    sink.onDispose(registration::close);
}, FluxSink.OverflowStrategy.ERROR);
```

仅适用于接受“没有需求时失败”的桥接方案。生产适配还需核对回调注册竞态、并发发射、终止后回调、资源释放，以及 SDK 能否真正暂停或取消。`Flux.create` 不会把阻塞的 register 方法自动转成异步。

依据：[程序化创建流](https://projectreactor.io/docs/core/release/reference/coreFeatures/programmatically-creating-sequence.html)。

## 6. 在 LLM 流式输出里怎么判断

分四层检查：模型供应商是否支持暂停 → SDK 是否缓存 → Reactor 适配器怎么处理需求 → HTTP 客户端是否消费得动。Flux 类型本身无法保证端到端减速。

本地 AgentScope 1.0.12 的事件桥使用 `Flux.create(..., BUFFER)`，这只是一个实现选择，不能解释成已经具备有界队列或供应商背压。对照 [[AI项目/AgentScope1.0/2.AgentScope Java特性：流式输出、结构化输出、超时与重试、执行控制]]，源码入口见 [[AI项目/Reactor/11.AgentScope与WebFlux实战]]。
