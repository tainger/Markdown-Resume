# 07. 异常处理、超时与重试

> 目标：知道错误会结束哪一段、恢复会替换哪一段、重试会重新执行什么。返回 [[AI项目/Reactor/README]]。

## 1. 错误是终止信号

```java
Flux<Integer> values = Flux.just(1, 0, 2)
        .map(i -> 10 / i)
        .onErrorReturn(-1);
// 发射 10、-1，然后完成；不会接着处理原来的 2
```

恢复是切换到备用值/备用流，不是让原来已经失败的上游从报错处继续运行。

| 操作符 | 用途 |
|:---|:---|
| `doOnError` | 观察错误，不自动恢复 |
| `onErrorReturn` | 用固定值替代失败 |
| `onErrorResume` | 按异常选择备用 Publisher |
| `onErrorMap` | 转换异常，保留失败语义 |
| `doFinally` | 在正常完成、错误或取消后观察结束类型 |

依据：[错误处理](https://projectreactor.io/docs/core/release/reference/coreFeatures/error-handling.html)。

## 2. 恢复放内层还是外层

```java
Flux<Result> perItem = Flux.fromIterable(ids)
        .flatMap(id -> callRemote(id)
                .onErrorResume(error -> fallback(id, error)), 4);
```

这里每项可单独恢复。若把 `onErrorResume` 放到整条 flatMap 后面，一个内部错误可能终止整个合并过程，并取消其他内部订阅，再进入整体备用流程。

是否允许部分成功必须由业务决定；不要用统一 `onErrorResume(e -> Mono.empty())` 把故障隐藏成“查不到”。`onErrorContinue` 也有特定支持范围和上游影响，不作为通用 try/catch 使用。

## 3. timeout 限制什么

```java
Mono<Result> result = Mono.defer(() -> callRemote())
        .timeout(Duration.ofSeconds(2))
        .retryWhen(Retry.backoff(2, Duration.ofMillis(100))
                .filter(error -> error instanceof TimeoutException))
        .timeout(Duration.ofSeconds(7));
```

- 内层 2 秒：每次订阅尝试的期限。
- 重试 2 次：初始一次加最多两次重试，总共最多三次尝试。
- 外层 7 秒：包含重试与退避等待的整体上限。

外层超时不保证底层远程调用立刻终止，也不撤销已经提交的写入。同步阻塞任务如果卡住执行线程，还需 SDK 自身超时及适配层取消支持。

对于 `Flux.timeout(Duration)`，通常检查首条或相邻两条信号的等待间隔，不是整个无限流的总时长。总持续时间可用 `take(Duration)` 控制正常截断，但它与超时错误的业务语义不同。

依据：[Mono API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html)、[Flux API](https://projectreactor.io/docs/core/3.8.2/api/reactor/core/publisher/Flux.html)。

## 4. 重试就是重新订阅

```java
AtomicInteger attempts = new AtomicInteger();
Mono<String> request = Mono.defer(() -> {
    int attempt = attempts.incrementAndGet();
    return attempt < 3
            ? Mono.error(new IOException("临时失败"))
            : Mono.just("成功");
});
Mono<String> recovered = request.retry(2); // 第三次成功
```

冷源的副作用可能重复；Flux 在失败前已发送的值也可能重放。对扣款、订票、发消息等，重试前要有外部幂等键或明确的去重/事务协议。

`retryWhen(Retry.backoff(...))` 支持退避和过滤。默认耗尽后可能包装为重试耗尽异常；确实需要保留最后原异常时可显式设置：

```java
Retry policy = Retry.backoff(2, Duration.ofMillis(100))
        .filter(error -> error instanceof IOException)
        .onRetryExhaustedThrow((spec, signal) -> signal.failure());
```

依据：[Retry 3.8.2 API](https://projectreactor.io/docs/core/3.8.2/api/reactor/util/retry/Retry.html)。

## 5. 操作符顺序决定结果

```java
// 先重试原请求，耗尽后再降级
request.retry(2).onErrorResume(error -> fallback());

// 先降级；若备用流成功，后面已经看不到原请求错误
request.onErrorResume(error -> fallback()).retry(2);
```

对于 eager 创建的 Future，反复订阅同一个已失败 Future 不等于重新调用接口；用 `defer` 或明确的延迟 factory 创建每次尝试。

## 6. AgentScope 的额外边界

如果工具层已把异常转换成普通 `ToolResultBlock` 错误文本，外层 Reactor `retryWhen` 看见的可能是正常 onNext，而不是 onError；它不会因为文字里有“失败”就重试。

来源：[[AI项目/AgentScope1.0/interview/03.工具调用与执行治理]]、[[AI项目/AgentScope1.0/interview/09.版本口径与源码核对]]。同样，流式 HTTP 已输出部分内容后再重试整个 Agent，可能重复内容与工具副作用，需按具体阶段设计恢复。

## 7. 自测

1. `doOnError` 打过日志，下游为什么仍收到错误？它只观察。
2. `retry(2)` 是执行两次吗？最多三次，含初次。
3. 把 timeout 放 retry 前后一样吗？计时范围不同。
