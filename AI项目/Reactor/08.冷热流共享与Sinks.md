# 08. 冷热流、共享与 Sinks

> 目标：判断多次订阅是重新执行，还是消费同一份事件。返回 [[AI项目/Reactor/README]]。

## 1. 冷流与热流

| 类型 | 与订阅的关系 | 例子 |
|:---|:---|:---|
| 冷流 Cold | 每个订阅通常单独生成数据、执行来源 | defer 中创建的 HTTP 请求 |
| 热流 Hot | 来源可独立于当前订阅生产；后来订阅者未必拿到历史 | 实时事件广播 |

```java
AtomicInteger calls = new AtomicInteger();
Mono<Integer> cold = Mono.fromSupplier(calls::incrementAndGet);
cold.block(); // 1
cold.block(); // 2
```

`Mono.just(fetch())` 在组装时已取得值，以后订阅重放该值；“没有订阅就绝对什么都不做”不是所有来源的共同保证。

依据：[冷热流](https://projectreactor.io/docs/core/release/reference/advancedFeatures/reactor-hotCold.html)。

## 2. cache：缓存信号，不只是缓存正常值

```java
AtomicInteger calls = new AtomicInteger();
Mono<Integer> cached = Mono.fromSupplier(calls::incrementAndGet).cache();
cached.block(); // 1
cached.block(); // 仍为 1
```

`Mono.cache()` 可重放值、空完成或错误；没有设置失效策略时，失败也可能被后续订阅者继续看到。TTL、错误缓存和取消行为要按具体重载核对。

缓存作用域同样重要：把与用户身份有关的 Mono 放进单例字段并全局 cache，可能把一个用户的结果复用给其他用户。身份相关缓存必须有正确键、生命周期和权限边界；不要用 cache 草率修补重复订阅。

## 3. publish、replay、share 与连接管理

| 写法 | 关注点 |
|:---|:---|
| `source.publish()` | 得到可显式连接的 ConnectableFlux，默认不重放历史 |
| `.publish().autoConnect(n)` | 达到 n 次订阅后连接；不要当成自动人数归零就取消 |
| `.publish().refCount(n)` | 达到连接条件后共享，订阅生命周期还会影响断开/重连 |
| `source.share()` | 共享活跃上游，重连与终止后的行为依具体类型/API |
| `source.replay(limit)` | 向后来订阅者重放有限历史，可控连接 |

想让两个消费者同时看到同步有限源，不能先让第一个完整消费，再期待第二个收到原来的实时广播；可先注册订阅者，再 connect。

依据：[ConnectableFlux](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-broadcast-multiple-subscribers-connectableflux.html)、[Mono API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html)。

## 4. Sinks：把外部事件手动推入响应式流

```java
Sinks.Many<String> sink = Sinks.many().replay().limit(2);
sink.tryEmitNext("A").orThrow();
sink.tryEmitNext("B").orThrow();
sink.tryEmitNext("C").orThrow();
sink.tryEmitComplete().orThrow();

Flux<String> history = sink.asFlux(); // 新订阅者收到 B、C，然后完成
```

这里用有限重放演示晚订阅；生产应用要按业务决定历史上限、容量和保留时间。

| Sink | 常见用途 | 需要确认 |
|:---|:---|:---|
| `Sinks.one()` | 一个值或一次终止 | 重复完成与错误处理 |
| `many().unicast()` | 单个订阅者消费 | 缓冲边界、取消后的生命周期 |
| `many().multicast()` | 广播给当前订阅者 | 慢订阅者策略、是否允许丢失 |
| `many().replay()` | 新订阅者补收历史 | 时间/条数限制，避免无限历史 |

`tryEmitNext` 返回 `EmitResult`，不等于永远成功；终止、取消、需求不足或并发竞争等可能导致失败。教学示例使用 `orThrow` 暴露问题；生产端应按失败类型设计拒绝、重试或丢弃策略，不能静默忽略。

默认安全 Sink 可检测并发发射冲突，但不保证每个竞争调用自动排队成功；不得因此删除业务侧的并发控制。

依据：[Sinks](https://projectreactor.io/docs/core/release/reference/coreFeatures/sinks.html)。

## 5. create、generate 与 Sinks 怎么选

- `Flux.generate`：同步按需求逐次生成，每次回调最多一个 next。
- `Flux.create`：在每次订阅里接入外部回调，注意注销与需求策略。
- `Sinks`：需要独立持有一个发射端，供多个位置推入事件。

这三个入口都不提供业务消息持久化或“恰好一次”交付；可靠事件系统还需要外部存储、消费确认和幂等设计。

## 6. 自测

1. 两次订阅冷请求与两次订阅 cache 后请求有什么区别？前者一般重新执行，后者可重放缓存信号。
2. cache 是否能充当所有用户共享的会话管理器？不能，需要隔离键与生命周期。
3. Sinks 发射结果能忽略吗？不能，失败意味着该次推送没有按预期接受。
