# 09. Context 与资源生命周期

> 目标：把请求身份、取消、清理与主链绑定起来。返回 [[AI项目/Reactor/README]]。

## 1. 三种上下文必须区分

| 概念 | 保存什么 | 面向谁 |
|:---|:---|:---|
| 模型上下文 | 系统提示、历史、检索结果、工具结果 | 模型请求 |
| Reactor Context | 与订阅关联的元数据，如 userId、traceId | 响应式调用链 |
| AgentScope ToolExecutionContext | 注入工具的业务对象 | 工具执行 |

把 userId 写入 Reactor Context 不会自动增加模型记忆，也不会自动完成权限校验或持久化。

项目来源：[[AI项目/gogo-agent/27.基于Reactor Context 实现多智能体之间的会话上下文传递]]、[[AI项目/AgentScope1.0/9.AgentScope Java特性：工具集成]]。

## 2. contextWrite 写，deferContextual 读

```java
Mono<String> identity = Mono.deferContextual(ctx ->
        Mono.just("当前用户：" + ctx.<String>get("userId")))
        .contextWrite(ctx -> ctx.put("userId", "u-42"));
```

Context 绑定 Subscriber，`contextWrite` 返回新的不可变 Context，并影响它上游的读取。把代码从上到下看时，写入通常放在读取的下面，因为订阅传播从下游向上游进行。

```java
Mono<String> value = Mono.deferContextual(ctx -> Mono.just(ctx.<String>get("k")))
        .contextWrite(ctx -> ctx.put("k", "内层"))
        .contextWrite(ctx -> ctx.put("k", "外层"));
// source 处读取为“内层”
```

依据：[Reactor Context](https://projectreactor.io/docs/core/release/reference/advancedFeatures/context.html)。

## 3. Context 的传播边界

```java
Mono<String> result = Mono.just("开始")
        .flatMap(ignored -> Mono.deferContextual(ctx ->
                Mono.just(ctx.<String>get("traceId"))))
        .contextWrite(ctx -> ctx.put("traceId", "t-1"));
```

这样组合的内部流程可以读取下游传来的 Context；但在回调里裸 `subscribe()` 会创建另一个顶层订阅，不能假定自动继承原 Context。优先组合流程，必要的外部桥接需显式捕获并重新接入。

Context 不可变不意味着其中存放的可变对象变成线程安全，也不意味着用户身份天然可信；身份仍应由认证入口确定，业务层校验资源归属。

原笔记中“ThreadLocal 完全不可用”“独立订阅 Context 必然为空”的表述过强：未配置桥接时不能依赖 ThreadLocal 自动跨线程；新订阅也可能被显式配置 Context 或框架 Hook。应核对实际链与环境，不能扩大成 Reactor 的绝对规则。

## 4. Context 与 ThreadLocal 桥接

Micrometer Context Propagation 提供注册访问器、快照和恢复机制。Reactor 支持有限模式，以及显式启用的自动模式；启用时间、依赖、已注册的 ThreadLocalAccessor 都影响结果。

因此，`contextWrite` 不是自动写 MDC 的通用开关，`contextCapture` 也不是任意对象的全量快照。需要桥接时按应用版本配置，并验证跨线程和清理行为。

依据：[Context Propagation](https://projectreactor.io/docs/core/release/reference/advanced-contextPropagation.html)。

## 5. 结束分为成功、错误与取消

```java
Flux<Long> ticks = Flux.interval(Duration.ofMillis(100))
        .doFinally(signal -> System.out.println("结束：" + signal));
Disposable handle = ticks.subscribe(System.out::println, Throwable::printStackTrace);
// 业务拥有 handle；不再需要时调用 handle.dispose()
```

`doFinally` 可以观察 CANCEL；`doOnComplete` 只针对正常完成。取消是协作协议：链外启动的线程、SDK 调用和外部写入是否停止，需要额外支持。

如果要在流程结束前等待异步清理，不能只在 `doFinally` 里返回一个未消费的 Mono；应使用能够组合清理完成信号的结构。

## 6. 同步资源用 using，异步资源用 usingWhen

```java
// openResource 返回资源；read 返回 Mono<String>；close 为同步方法
Mono<String> read = Mono.using(
        () -> openResource(),
        resource -> read(resource),
        resource -> resource.close());
```

若 open/read/close 阻塞，还需在适当 Scheduler 上执行，资源操作符不会让它们自动非阻塞。

```java
// acquireAsync、readAsync、closeAsync 都为假设的异步业务方法
Mono<String> read = Mono.usingWhen(
        acquireAsync(),
        resource -> readAsync(resource),
        resource -> closeAsync(resource),
        (resource, error) -> closeAsync(resource),
        resource -> closeAsync(resource));
```

三个清理分支分别对应成功、错误、取消；异步清理失败还可能影响下游结果，不能视为绝对不会出错的 finally。事务提交/回滚则应按对应驱动与事务管理器设计。

依据：[资源与 finally](https://projectreactor.io/docs/core/release/reference/coreFeatures/error-handling.html)、[Mono API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html)。

## 7. 自测

1. 为什么切线程后还能通过 deferContextual 取到身份？它不依赖当前线程上的普通 ThreadLocal。
2. 为什么服务层嵌套 subscribe 容易丢失生命周期？它创建独立任务，调用方不再统一等待和取消。
3. 为什么 doFinally 不能充当所有异步关闭操作的等待机制？回调没有组合清理 Publisher。
