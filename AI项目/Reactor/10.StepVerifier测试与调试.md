# 10. StepVerifier 测试与调试

> 目标：验证信号、时序和订阅行为，而不是只看控制台“好像运行了”。返回 [[AI项目/Reactor/README]]。

## 1. StepVerifier 验证信号序列

```java
StepVerifier.create(Flux.range(1, 3).map(i -> i * 10))
        .expectNext(10, 20, 30)
        .expectComplete()
        .verify(Duration.ofSeconds(2));
```

没有最后的 verify，测试脚本没有真正运行。默认无限等待容易让失败测试卡住，应设置验证超时；本系列实验全局设置 3 秒。

```java
StepVerifier.create(Mono.<String>error(new IllegalArgumentException("bad input")))
        .expectErrorMatches(error -> error instanceof IllegalArgumentException
                && error.getMessage().equals("bad input"))
        .verify(Duration.ofSeconds(2));
```

依据：[Reactor 测试](https://projectreactor.io/docs/core/release/reference/testing.html)。

## 2. 用零初始需求验证背压

```java
StepVerifier.create(Flux.range(1, 3), 0)
        .thenRequest(1)
        .expectNext(1)
        .thenRequest(2)
        .expectNext(2, 3)
        .expectComplete()
        .verify(Duration.ofSeconds(2));
```

这能检验按需发射；不能只用默认无界订阅，再声称已经验证了慢消费者。

## 3. 虚拟时间测试

```java
StepVerifier.withVirtualTime(() ->
                Mono.delay(Duration.ofHours(1)).thenReturn("done"))
        .expectSubscription()
        .expectNoEvent(Duration.ofMinutes(59))
        .thenAwait(Duration.ofMinutes(1))
        .expectNext("done")
        .expectComplete()
        .verify(Duration.ofSeconds(2));
```

需要让使用默认 Scheduler 的时间操作符在 Supplier 内延迟创建，以便安装虚拟 Scheduler 后再组装。它不能加速真实 HTTP、`Thread.sleep` 或任意 SDK 的内部时钟；手动指定的 Scheduler 也需另外核对。

## 4. 证明备用分支真的被订阅

```java
PublisherProbe<String> fallback = PublisherProbe.of(Mono.just("备用"));
StepVerifier.create(Mono.<String>empty().switchIfEmpty(fallback.mono()))
        .expectNext("备用")
        .verifyComplete();
fallback.assertWasSubscribed();
fallback.assertWasRequested();
fallback.assertWasNotCancelled();
```

`PublisherProbe` 适合核对无值流程或分支选择；只断言最终完成，可能漏掉错误路径。

`TestPublisher` 则允许测试代码手动发射信号，适合控制来源在指定步骤发值、失败或结束；不必为了验证下游而真的启动模型服务。

## 5. 验证 Context 与取消

```java
StepVerifier.create(Mono.deferContextual(ctx -> Mono.just(ctx.<String>get("uid")))
                .contextWrite(ctx -> ctx.put("uid", "u-1")))
        .expectNext("u-1")
        .verifyComplete();

AtomicBoolean cancelled = new AtomicBoolean();
StepVerifier.create(Flux.never().doOnCancel(() -> cancelled.set(true)))
        .thenCancel()
        .verify(Duration.ofSeconds(2));
assertTrue(cancelled.get());
```

生产桥接还应验证：HTTP 客户端取消后，外部监听器是否注销、SDK 是否停止、资源是否释放。验证 Reactor 内部收到取消不等于验证这些外部效果。

## 6. checkpoint 与信号日志

```java
Mono<Result> result = load(id)
        .checkpoint("load-order")
        .flatMap(this::validate)
        .checkpoint("validate-order");
```

`checkpoint` 提供装配位置线索；需要堆栈的重载会有额外开销。`log()` 可以观察 onSubscribe、request、onNext、cancel 等信号，但生产中应控制级别和敏感内容。

`Hooks.onOperatorDebug()` 会在装配阶段捕获信息，应在可疑链创建前启用；不要未经评估全量长期打开。需要全局诊断时，再按官方方式评估 ReactorDebugAgent。

依据：[Reactor 调试](https://projectreactor.io/docs/core/release/reference/debugging.html)。

## 7. 出错时的检查顺序

| 现象 | 优先定位 |
|:---|:---|
| 没有任何行为 | 是否订阅、是否返回给框架、是否丢弃新链 |
| flatMap 不进入 | 上游是否为空，是否用了 Mono<Void> |
| 重复请求/扣款 | 是否重复订阅、retry、repeat 或共享作用域错误 |
| 卡住 | 上游是否不结束、是否缺需求、是否阻塞、groupBy 是否未消费 |
| 顺序不符合预期 | flatMap/merge 是否允许交错；结果顺序与副作用顺序是否混淆 |
| 身份丢失 | 是否越过裸订阅/外部回调边界，Context 方向是否正确 |
