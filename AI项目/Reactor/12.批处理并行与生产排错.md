# 12. 批处理、并行与生产排错

> 目标：理解进阶操作符的资源代价，形成排查方法。返回 [[AI项目/Reactor/README]]。

## 1. buffer、window 与 groupBy

| 操作符 | 输出 | 用途 |
|:---|:---|:---|
| `buffer(n)` | `Flux<List<T>>` | 攒批写入、批量请求 |
| `window(n)` | `Flux<Flux<T>>` | 每个窗口作为一个独立流继续处理 |
| `groupBy(key)` | `Flux<GroupedFlux<K,T>>` | 按键组织子流 |

```java
Flux<List<Integer>> batches = Flux.range(1, 5).buffer(2);
// [1,2]、[3,4]、[5]

Flux<Integer> sizes = Flux.range(1, 5)
        .window(2)
        .concatMap(window -> window.count().map(Long::intValue));
// 2、2、1
```

缓冲与窗口的某些 size/skip 重载会重叠或跳过数据，不能统一理解成“每条只属于一个批次”。每个窗口/分组也需要被正确消费。

## 2. groupBy 为什么可能卡住

如果按高基数键分出大量组，却只允许很少的内部组被消费，未消费组会填满缓存；上游又被背压，正在消费的组等不到完成，可能形成停滞。

所以不要把所有订单按唯一订单号 groupBy，再对整个分组流随意 concatMap。先判断键数量是否受控、组是否能结束、是否能及时订阅所有组；必要时改变分片方案。

依据：[三种批处理](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-three-sorts-batching.html)。

## 3. CPU 并行要考虑状态和顺序

```java
Flux<Integer> squared = Flux.range(1, 100)
        .parallel(4)
        .runOn(Schedulers.parallel())
        .map(i -> i * i)
        .sequential();
```

并行计算应避免共享可变集合；返回普通 Flux 后再聚合。`sequential` 合并轨道，不承诺原始全局顺序；需要有序结果可按需求选 `flatMapSequential` 或明确排序，后者需要额外缓存。

依据：[ParallelFlux](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-parallelizing-parralelflux.html)。

## 4. 复用操作符配方

```java
Function<Flux<String>, Flux<String>> normalize = flux -> flux
        .map(String::trim)
        .filter(text -> !text.isEmpty());
Flux<String> values = Flux.just(" a ", " ", "b").transform(normalize);
```

`transform` 在组装时应用配方，`transformDeferred` 在每次订阅时应用。需要每订阅独立状态时，用后者或 defer 在相应范围创建状态；不要把一个 StringBuilder 定义在全局并让所有用户共享。

依据：[操作符复用](https://projectreactor.io/docs/core/release/reference/advancedFeatures/advanced-mutualizing-operator-usage.html)。

## 5. 观测哪些指标

至少把总延迟、首条输出延迟、活跃订阅、错误/取消数、重试次数、内部并发、线程池排队、连接池占用和缓冲溢出分开观察。

官方 `reactor-core-micrometer` 提供 Publisher 和 Scheduler 的观测接口，需要显式接入 registry；别用未配置 registry 的旧示例宣称已经有指标。跨用户标签不要直接放无限增长的 userId/sessionId，避免高基数污染指标系统。

依据：[Reactor metrics](https://projectreactor.io/docs/core/release/reference/metrics.html)。

## 6. 六种生产症状的定位

| 症状 | 证据与下一步 |
|:---|:---|
| CPU 不高但延迟增加 | 检查同步 I/O、线程池排队、连接池等待和锁 |
| 内存持续涨 | 检查 collectList、无限 replay/cache、无界 BUFFER、未消费分组 |
| 下游服务被打爆 | 检查每订阅并发 × 活跃请求数、重试放大、全局配额 |
| 用户身份串线 | 检查单例可变字段、缓存键、ThreadLocal 桥接和嵌套订阅 |
| 输出顺序混乱 | 区分 flatMap、merge、并行轨道与副作用顺序 |
| 用户断开仍在执行 | 追踪 cancel 是否越过适配层并真正到达 SDK |

这是排查路径，不是已经定位的故障结论。用线程转储、堆/队列指标、信号日志及故障注入逐项验证。

## 7. 完成这四个综合练习

1. 独立请求并发 4 个，每项 1 秒超时；只对临时失败重试一次，最终按输入顺序输出。
2. 从缓存查不到时调用数据库；证明命中缓存时数据库分支未订阅。
3. 每个请求带独立 Context，线程切换后仍能读到；证明没有复用上一用户的状态。
4. 外部 SDK 推送太快时，明确选择有界队列或过载失败；证明取消会注销监听器。

需要外部服务的部分应单独建集成测试，不能只凭 Reactor 类型或单元测试证明端到端行为。对应原项目入口：[[AI项目/AgentScope1.0/2.AgentScope Java特性：流式输出、结构化输出、超时与重试、执行控制]]、[[AI项目/gogo-agent/27.基于Reactor Context 实现多智能体之间的会话上下文传递]]。
