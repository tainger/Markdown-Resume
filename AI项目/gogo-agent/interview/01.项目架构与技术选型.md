# 项目架构与技术选型

> 答题骨架：业务问题 → 一次请求 → 职责拆分 → 取舍 → 实现边界。返回 [[AI项目/gogo-agent/interview/README]]。

## Q01｜用两分钟介绍 gogo-agent，你会怎么讲？

**口述答案**：这是一个企业差旅助手，把自然语言需求接到差旅申请、审批查询、行程规划和预订执行。主智能体 MasterAgent 负责协调，行程管理、规划、信息查询、预订分别由专业子智能体处理。大语言模型 Large Language Model（LLM）负责理解、拆任务和解释；价格计算、政策比较、业务状态更新由 Java 工具完成。聊天展示记录和 Agent 运行记忆分别保存，前端通过服务器发送事件 Server-Sent Events（SSE）接收进度、方案和交互请求。

**追问**：最值得讲的工程点是什么？选择“跨 Agent 上下文传递”“规划—审核—修复”“跨节点暂停恢复”中的两点，沿调用链展开，别只罗列框架名。

**边界**：报销模块仍是待实现；第三方返回下单号与支付链接不代表支付、出票已经完成。上述是项目介绍模板，个人贡献须按实际经历表述。

## Q02｜为什么采用多智能体 Multi-Agent，而不是一个大 Agent？

**口述答案**：不同环节的工具、提示词和风险不同。管理 Agent 操作差旅单，规划 Agent 搜索比价并修复方案，BookingAgent 执行用户确认后的预订。拆开后每个 Agent 只携带本职责需要的工具和指令，便于控制权限和排查失败。代价是更多模型调用、上下文转交和状态管理，所以不按每个 API 拆一个 Agent。

**追问**：小规模单 Agent 可以吗？可以，若工具少、流程短、上下文可控，单 Agent 更容易实现；本项目用业务职责解释拆分的必要性。

**易错点**：拆 Agent 不自动带来隔离。仍要核对实际注册的工具，例如规划 Agent 也有 Shell 执行能力，职责边界需要代码配合。

## Q03｜一次普通聊天请求的真实执行顺序是什么？

**口述答案**：`ChatController.chat` 从登录态取得用户身份，建立会话上下文、保存用户消息、预中断旧执行并创建 SSE。普通新请求进入 Pipeline：原问题先走 L0 守卫与 L1/L2；快路径命中就交给 Master；未命中则加载近期聊天做问题改写，再走意图识别，最后仍交给 Master。Master 通过子 Agent 工具委派，结果由 Executor 落展示历史并推给前端。

**追问**：所有请求都这样吗？不是。“继续/确认”等续聊信号可能走活跃 Agent；`/respond` 则是挂起工具的恢复入口。不能把三条路径混在一起。

**易错点**：不是每次都“先改写再识别”；也不是 L1/L2 命中后完全没有 LLM 调用。

## Q04｜Master 如何调用子 Agent？是不是 A2A？

**口述答案**：当前是进程内的工具式委派。Master 的 Toolkit 用 `subAgent` 注册四个工具，绑定管理、规划、信息查询和预订 Agent 的 provider。provider 在调用时从 Spring 容器创建实例，任务通过 `message` 等参数转交。Master 自己维护协调上下文和最终输出规则。

**追问**：主观审核也通过 Master 路由吗？不是，审核工具内部创建评估器并用 `Pipelines.fanout` 并发执行，属于另一种协作方式。

**边界**：当前主链路不是跨服务 Agent-to-Agent（A2A）协议集成；报销类中的 A2A 只有 TODO。

## Q05｜Agent 为什么使用 prototype？每次新建怎么记住上轮？

**口述答案**：Agent 内部带 Memory、计划和工具状态；使用 Spring 多例作用域 prototype，避免不同会话共享可变运行状态。`AgentRegistry.getAgent` 每次取新实例；`SessionPersistenceHook` 调用前按 `sessionId:agentName` 加载，调用后保存到 MySQL Session。同节点恢复挂起工具时例外：可直接复用本地缓存实例。

**追问**：多例能保证同一会话并发安全吗？不能。多个请求仍可能加载同一份历史再覆盖写回；需要会话级串行或版本控制，现有预中断也不能等同于分布式锁。

**依据**：[[AI项目/gogo-agent/5.会话与消息的持久化]]、[[AI项目/gogo-agent/115.Human-in-the-Loop在集群模式下的支持]]；[AgentRegistry.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/registry/AgentRegistry.java:58>)、[SessionPersistenceHook.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/hook/SessionPersistenceHook.java:74>)、[TravelAgentConfig.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/config/TravelAgentConfig.java:79>)。

## Q06｜为什么改写、意图识别不用 ReAct？为什么自己编排 Pipeline？

**口述答案**：这两步是输入到结构化文本的单次转换，不需要推理与行动 Reasoning and Acting（ReAct）的工具交互循环。代码直接调用模型流并汇总结果；流水线还需要条件跳过改写、中断检查、注入历史和统一调度，用 `Mono.flatMap` 显式串联更容易表达这些分支。

**追问**：直接模型调用就不能中断了吗？可以，两类 Agent 都继承 AgentBase；流消费中检查中断，返回 `GenerateReason.INTERRUPTED` 后 Pipeline 停止后续步骤。

**易错点**：使用 Reactor 不代表所有代码都非阻塞；向量检索和部分审核实现中仍有 `.block()`，要关注线程位置。

## Q07｜用了哪些模型，为什么有些步骤不开深度思考？

**口述答案**：以当前 `ModelConfig` 为准：`fastModel=qwen-flash`，`strongModel=qwen-plus`，`stableModel=qwen-max`，另有开启思考的 qwen-plus。Master 和管理用 strong，Info 和审核评估用 stable，规划与预订用思考版 strong。规划的 Hook 在未创建计划时保留思考，有计划后执行阶段关闭思考，最终总结设置思考预算。

**追问**：为什么不全开？查询和固定结构转换需要关注延迟与输出稳定性；复杂规划才更可能受益，应通过同一任务集比较。`2048` 是代码里的预算配置，不能说成每次固定消耗。

**边界**：模型名代表本地快照配置；“stable 一定比 strong 更准”需要评测，不能从 Bean 名推出。

## Q08｜项目最重要的技术取舍是什么？

**口述答案**：一是放弃普通请求高置信直跳，保留 Master 的跨 Agent 协调上下文；二是确定性计算落 Java，主观偏好交给模型；三是规划和真正预订拆职责；四是把运行记忆与展示历史分存，让上下文恢复和产品展示各自有合适的数据形态。

**追问**：这些设计有什么代价？Master 与评估器增加调用成本，Redis 中间数据引入过期与覆盖问题，Hook 让主流程简洁但增加时序依赖。回答一个收益时，紧接一个代价和验证办法。

**边界**：当前“审批前能否规划”的提示词仍有冲突，不能讲成已完全收敛的状态机，见 [[AI项目/gogo-agent/interview/09.源码核对与待补证据]]。
