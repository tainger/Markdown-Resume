# 工具设计与预订一致性

> 答题骨架：接口契约 → 服务端身份 → 读写边界 → 外部副作用 → 失败补偿。返回 [[AI项目/gogo-agent/interview/README]]。

## Q17｜项目里 Tool、Skill、MCP、SubAgent 怎么选择？

**口述答案**：本地工具 Tool 适合有明确输入输出和业务约束的操作，例如查差旅单、取消预订、方案算分；技能 Skill 给模型提供执行第三方任务的方法与命令说明；模型上下文协议 Model Context Protocol（MCP）提供外部工具的标准接入；子智能体 SubAgent 适合独立职责、多轮决策和自己的工具上下文。这些维度可以组合：Agent 加载 Skill，再通过 Shell 调第三方 CLI。

**追问**：为什么下单用 Skill、取消用 Java Tool？下单参数多且供应商流程易变，项目复用 CLI 技能；取消更适合收敛为可校验归属、状态与结果的确定性入口。这是当前取舍，不代表下单不能做成 Tool。

**依据**：[[AI项目/gogo-agent/75.预定时，为什么下单用skill，取消用工具]]、[[AI项目/gogo-agent/77.什么时候用Skill，什么时候用SubAgent]]；[BookingAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/BookingAgent.java:108>)、[BookingWriteTools.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/tools/BookingWriteTools.java:65>)。

## Q18｜一个好工具的描述和返回值应该包含什么？

**口述答案**：名称表达单一业务动作，描述写清触发条件、前置条件和副作用；参数给格式、必填性与可选范围，服务端能确定的身份不暴露给模型。结果用明确的成功标志、错误码和必要业务字段，让模型能决定停止、补信息或重试。例如取消入口收内部预订单号，查询后再取得外部单号。

**追问**：JSON 能保证工具正确吗？只能降低格式歧义。还要做业务校验、枚举/范围检查、异常分类和测试；合法 JSON 也可能包含错误订单号。

**易错点**：不要通过返回大量原始供应商 JSON 来弥补模糊契约，也不要把格式修复当业务事实校验。

**依据**：[[AI项目/gogo-agent/31.如果定义一个好的工具]]、[[AI项目/gogo-agent/90.提示词工程-结构化输出约束]]；[BookingWriteTools.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/tools/BookingWriteTools.java:61>)、[ItineraryPlannerTools.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/tools/ItineraryPlannerTools.java:69>)。

## Q19｜如何避免模型幻觉或伪造 userId？

**口述答案**：用户身份从 Sa-Token 登录态获取，创建 `AgentSessionContext`，组装 Agent 时注册进 `ToolExecutionContext`；工具用无 `@ToolParam` 的上下文形参读取 userId，让模型只传业务参数。对订单等资源还要校验其所属用户，`cancel_booking` 已有这一检查。

**追问**：这样就彻底没有越权了吗？没有。上下文注入只确定“请求者是谁”，每个资源入口仍要校验“资源属于谁”；按订单号直接查库、恢复与中断会话尤其要单独审计。

**边界**：`check_travel_order_approval` 当前按单号查到后的代码未见归属校验，不能把所有工具讲成已统一闭环，详见源码核对页。

**依据**：[[AI项目/gogo-agent/34.如何避免模型幻觉导致用户id传错]]、[[AI项目/gogo-agent/35.多智能体上下文参数传递遇到的坑]]；[ChatController.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/controller/ChatController.java:57>)、[BaseSubAgent.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/BaseSubAgent.java:167>)、[BookingWriteTools.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/tools/BookingWriteTools.java:82>)。

## Q20｜天气/签证 MCP 是怎么接入的？

**口述答案**：天气通过 `McpClientBuilder` 创建 Streamable HTTP 客户端，配置请求和初始化超时；Agent 的 Toolkit 注册客户端，并使用 `enableTools` 只暴露需要的工具。签证有独立客户端与白名单配置。把远程服务变化收敛到接入层，模型按工具描述选用能力。

**追问**：远程 MCP 初始化失败怎么办？天气配置捕获异常并返回 null，意图上是降级；但 Agent 构建时继续注册该客户端是否安全，需要结合框架行为和运行测试确认，不能据此宣称全部降级已验证。

**边界**：MCP 解决接入形式，不自动保证工具可信、用户授权、结果正确或所有服务稳定可用。

## Q21｜同一轮里怎样避免反复查询用户和差旅政策？

**口述答案**：多个 Agent/工具共享本次执行的 `AgentSessionContext` 对象，工具可以缓存已查询的用户信息、订单和按城市区分的政策。`PolicyTools` 查询与合规校验共用 `resolvePolicyJson`，命中就省掉重复查库。跨请求的长期偏好缓存则在 Redis，是另一层。

**追问**：这是真正跨会话缓存吗？上下文缓存主要服务本次执行实例，并非持久化数据库。若同一轮写了用户资料或业务状态，还要确认相关缓存是否失效。

**易错点**：“缓存命中”不能取代审批等写操作前的最新状态检查；缓存范围、键和失效点要分别说明。

**依据**：[[AI项目/gogo-agent/37.使用缓存减少工具重复调用]]；[AgentSessionContext.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/context/AgentSessionContext.java:1>)、[PolicyTools.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/tools/PolicyTools.java:57>)、[TravelPreferenceMemoryCache.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/memory/TravelPreferenceMemoryCache.java:1>)。

## Q22｜LLM 下单后为什么用 Hook 自动落库？幂等做到哪里？

**口述答案**：`BookingPersistenceHook` 监听工具执行后事件，识别机/酒/火下单命令，解析结果中的外部单号，绑定用户、会话及差旅单后写 `booking_record`，并推送支付卡片。模型不再负责额外调用“保存记录”，可减少漏记。重复外部订单先查重，数据库还有 `(platform,biz_type,external_order_no)` 唯一索引兜底。

**追问**：能防止重复向供应商下单吗？不能。相同外部单号的本地去重不等于外部请求幂等。超时后供应商可能已成功，盲目重试会生成新的订单号。

**待改进**：建议在调用前保存业务请求号，接入供应商幂等键/按请求号查单，再补偿本地记录。当前 Hook 捕获落库异常后只记日志，未见持久补偿闭环。

**依据**：[[AI项目/gogo-agent/74.行程预订的下单结果持久化方案]]；[BookingPersistenceHook.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/hook/BookingPersistenceHook.java:147>)、[schema.sql](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/resources/db/schema.sql:182>)。

## Q23｜取消预订如何保证不会取消别人的订单？酒店真的退订了吗？

**口述答案**：入口用内部 `booking_id` 查记录，再比较记录 userId 与上下文用户。已取消直接返回；机票和火车票走外部取消接口，失败不更新本地状态，成功才保存。酒店当前没有线上取消通道，只标记内部状态并提示人工联系酒店，返回 `platformCancelled=false`。

**追问**：两次取消同时到达怎么办？“先查状态再更新”不能证明并发一次执行。可引入带期望状态的条件更新、执行中状态与供应商幂等，超时则先查外部结果。

**易错点**：不能把内部 `CANCELLED` 文案解释成供应商退订或退款到账；必须保留 `platformCancelled` 的语义差异。

**依据**：[[AI项目/gogo-agent/76.取消预订工具的定义及开发]]；[BookingWriteTools.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/tools/BookingWriteTools.java:65>)、[BookingWriteTools.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/tools/BookingWriteTools.java:116>)。

## Q24｜差旅单、审批单、预订记录为什么分开？事务管到哪里？

**口述答案**：差旅单描述申请与行程，审批单描述一次审批过程，预订记录描述机酒火的具体外部订单。一张差旅单可能关联多次审批和多条预订。`TravelOrderService` 把本库内的审批决策与差旅单状态同步放在事务中，避免只更新其中一张表。

**追问**：`@Transactional` 能回滚途牛订单吗？不能，本地数据库事务不能自动撤销已经执行的外部副作用。需要业务状态机、查单和补偿；并发审批还要检查状态条件是否在数据库原子更新中表达。

**边界**：当前状态检查体现了顺序调用的幂等意图，不能只凭事务注解就声称所有重复/乱序回调安全。
