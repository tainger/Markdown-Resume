# 规划算法与审核闭环

> 答题骨架：计划和执行 → 候选数据 → 客观算分 → 多维审核 → 有限修复 → 确认后预订。返回 [[AI项目/gogo-agent/interview/README]]。

## Q25｜Plan-and-Execute 和 ReAct 在项目里是什么关系？

**口述答案**：不是另写一个与 ReAct 完全独立的引擎，而是在 `ReActAgent` 上配置 `PlanNotebook`。计划记录子任务及状态，Agent 仍通过工具执行和观察推进。Notebook 的变更 Hook 推送进度；`PlanAwareThinkingHook` 根据当前计划是否存在调整思考配置，兼顾规划质量与执行延迟。

**追问**：计划一旦写出来就不能改吗？可以修订。审核失败后需要调整输入、补搜再规划，而不是机械执行最初计划。

**边界**：`needUserConfirm(false)` 指计划本身不要求逐步确认，不代表允许跳过用户对最终预订方案的确认。

## Q26｜方案为什么交给 Java 算，LLM 负责什么？

**口述答案**：候选交通和酒店来自真实搜索，工具读取候选后计算时间、总价、归一化和组合排序；LLM 负责根据真实用户偏好给候选打分、提供理由，并解释最终方案。这样金额和时间能复算，偏好判断保留语义灵活性。无偏好或快速初稿可用 `scores="auto"`，全部赋中性 50 分。

**追问**：工具会读 preferences 文本自己打分吗？不会。明确传入分数时按候选 id 关联，缺失 id 默认 0；偏好文本不是工具的自然语言推理输入。

**边界**：代码确定性并不保证入参正确；候选数据真实性、ID 对齐和分数范围仍需要验证。

## Q27｜组合、归一化和权重具体怎么算？

**口述答案**：枚举“去程×酒店×返程”，先过滤不能成立的时间组合，再对时间、价格和体验做 min-max 归一化。时间/价格越低越好，公式为 `100×(max-x)/(max-min)`；体验越高越好，方向相反。极差为 0 时当前返回 100。偏好分取去程、住宿、返程三项均值；综合分为 `0.20×时间+0.10×价格+0.40×偏好+0.30×体验`。

**追问**：政策分也加权吗？当前综合公式不包含 policy_score，政策违规单独记录并交给审核，不要沿用旧讲法。

**边界**：枚举规模为 O(去程数×酒店数×返程数)，内存也随组合数增长。若规模扩大，可先做可行性筛选和候选截断；这是优化建议，当前不是全局最优化证明。

## Q28｜为什么不是只给一个最优方案？一定有四个吗？

**口述答案**：代码选综合最佳、时间最短、价格最低、最符合偏好四种代表，使用户看清不同取舍。同一组合若拿到多个标签会合并，所以最多四个不同方案。时间/价格代表还带体验容忍逻辑：极值方案有体验风险时，优先尝试在相应指标约 15% 容忍范围内找无风险替代。

**追问**：为什么“价格最低”可能不是数学最低价？因为有体验替换策略。应在产品标签和解释中说明取舍，不能宣传为无条件全局最低。

**易错点**：归一化分数依赖当前候选池，候选改变后同一方案的分数也可能改变，不能跨批次直接比较。

## Q29｜搜索、规划、审核、预订如何共享方案？

**口述答案**：搜索结果由捕获 Hook 存入 Redis 候选池，按路线和日期精确读取；`plan_itinerary` 存完整方案，只返回简短摘要。规划结果用 `planner:result:{userId}` Hash，field 为出发地、目的地和出发日期，TTL 是整个 Key 的 24 小时。审核自动读取；需要展示或预订时通过 `get_proposals` 取真实数据，减少模型重复转抄。

**追问**：同用户开两个会话安全吗？当前同路线同出发日共享 field，不含会话、返程日和方案版本，可能覆盖；TTL 也不是每个 field 独立过期。

**待改进**：建议引入独立 planId/version，确认与预订绑定同一版本，关键方案另作持久快照，避免用户确认旧方案却执行新结果。

## Q30｜审核为什么做成工具？硬约束如何不被 LLM 覆盖？

**口述答案**：当前 `review_itinerary` 是编排入口：先由 Java 六维审核完整性、时间、出发目的地、预算、舱位和路线；再并发三个模型评估器，评价体验、韧性和偏好；最后模型生成仲裁整改单。若客观结果为 fail，代码强制最终 verdict=fail，并补入硬约束问题，模型不能用主观好评覆盖。

**追问**：仲裁完全由规则写死吗？不是，`ReviewArbitratorService` 仍然调用 LLM。代码负责硬否决以及是否继续整改的判定，不能把整个仲裁称为纯确定性。

**边界**：旧 `ItineraryReviewAgent` 还在源码中，但标为 Deprecated，当前规划配置注册的是审核工具。

## Q31｜审核失败后怎么修复，怎么避免无限循环？

**口述答案**：工具返回 `continue_remediation` 和整改优先级，Agent 重新读取候选/方案，根据问题补搜或调整评分，再真实调用规划和审核。当前代码在 verdict=fail、存在硬约束整改项，或推荐方案/高优先级可修复问题达到条件时要求继续；上一轮报告按 session 保存供下轮参考。提示词要求最多两轮修复，Agent 还有限制总推理迭代次数。

**追问**：两轮是 Java 状态机硬上限吗？不是，当前是提示词规则；`maxIters=30` 是总迭代限制，不能证明恰好限制两轮。若要强保证，需要代码维护修复次数和退出状态。

**边界**：候选打 0 分不等于删除，它仍可能成为最低价/最短时间代表。失败后不能靠生成“修复版文案”冒充重算结果。

## Q32｜为什么规划与预订分开？审批和确认在哪里保证？

**口述答案**：规划允许探索多个候选和调整方案，预订会产生外部订单，风险和工具不同，所以单独设 BookingAgent。规划结束展示真实方案并等待用户确认，Master 再委派预订；预订提示词要求检查指定差旅单审批状态，读取确认方案并执行下单。

**追问**：这些是强制业务门禁吗？当前部分条件依赖提示词顺序，Shell 执行入口本身没有展示出完整的审批/确认校验状态机。应把用户、差旅单、方案版本、确认凭据与审批状态在副作用发生前统一校验。

**边界**：规划提示词允许信息齐全时先规划，Master 提示词仍有“未审批不规划”的表述。现状存在冲突，不宣称已完整覆盖所有状态。
