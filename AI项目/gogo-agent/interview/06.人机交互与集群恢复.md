# 人机交互与集群恢复

> 答题骨架：暂停是什么 → 保存什么 → 在哪里恢复 → 中断与恢复区别 → 一致性边界。返回 [[AI项目/gogo-agent/interview/README]]。

## Q41｜ask_user 是怎么实现人机协同 HITL 的？会占着线程等用户吗？

**口述答案**：人机协同 Human-in-the-Loop（HITL）工具 `ask_user` 携带问题、交互类型和选项，抛出 `ToolSuspendException`。框架返回 `TOOL_SUSPENDED`，Executor 保存本地实例与共享挂起元数据，发送 `user_interaction` 让前端显示表单或确认控件，然后结束本次流。用户之后提交 `/respond` 再启动续跑。

**追问**：只在普通回复里写“请选择”有什么区别？结构化挂起有明确 toolUseId 和恢复位置，前端无需解析自然语言猜输入类型。

**易错点**：挂起不是服务器线程一直阻塞等待，也不是用户回复后从头重跑业务流程。

## Q42｜用户在节点 A 被提问，在节点 B 回复怎么恢复？

**口述答案**：本地 Caffeine 缓存活实例，容量 1024、访问后 30 分钟过期；共享 `PendingToolSessionStore` 保存 agentName、toolUseId、toolName，Key 为 `sessionId:pending_tool`。恢复先找本地匹配的实例，未命中就从共享元数据得知 Agent 类型，再创建新实例、加载 MySQL Session 历史，拼 `ToolResultBlock` 调用续跑。

**追问**：是不是把 Java Agent 整个序列化到 MySQL？不是，共享的是可恢复状态和元数据，运行对象按代码重建。

**边界**：本地缓存 TTL 不是共享 pending 的业务有效期；当前共享存储没有显示相同 TTL，也未看到原子一次消费。

## Q43｜恢复时为什么有时跳过 loadIfExists，有时必须加载？

**口述答案**：本地命中的 Agent 还持有当前 pending 工具状态，重新加载历史可能覆盖正在恢复的内存上下文，因此设置 `resuming=true`，持久化 Hook 跳过历史加载。跨节点是新建空实例，必须从 Session 加载历史，因此不设置这个跳过标志。代码传的是 `!recoveredFromSession`，需要按语义理解这个反转。

**追问**：resume 前为什么只本地中断，不广播？普通广播会清理共享 pending，而恢复依赖它；入口先停止本节点旧流，保留待恢复元数据。

**边界**：这个标志控制当前订阅如何加载 Memory，不等于永久标记会话已恢复，也不能保证完整进程快照恢复。

**依据**：[[AI项目/gogo-agent/115.Human-in-the-Loop在集群模式下的支持]]；[SessionReactorContext.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/context/SessionReactorContext.java:59>)、[SessionPersistenceHook.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/hook/SessionPersistenceHook.java:91>)、[ChatAgentExecutor.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/service/ChatAgentExecutor.java:265>)。

## Q44｜集群中断为什么使用 Redis Pub/Sub？

**口述答案**：实际 Agent 和 SSE 连接活在执行节点，本地注册表按 sessionId 保存一个 Agent 集合，能一起中断 Master 及嵌套子 Agent。显式中断优先处理本地，未命中广播；新请求预中断则本地处理并广播。各节点订阅 `agent:interrupt`，停止本地流、清挂起缓存/元数据，命中执行时通知前端。

**追问**：共享 Session 为什么还不够？数据库存状态，不能直接给另一个进程中正在运行的对象发停止信号，所以需要控制消息。

**边界**：Pub/Sub 不是持久消息队列，指令发送成功不等于每个节点确认执行；重连期间漏消息、并发旧任务等需要额外机制保证。

**依据**：[[AI项目/gogo-agent/116.集群架构下的Agent打断与恢复]]；[ChatAgentExecutor.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/service/ChatAgentExecutor.java:94>)、[AgentInterruptBroadcast.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/session/AgentInterruptBroadcast.java:136>)、[AgentExecutionRegistry.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/registry/AgentExecutionRegistry.java:46>)。

## Q45｜为什么中断后要手动保存 Memory？时间戳解决了什么？

**口述答案**：项目的中断路径可能绕过 PostCall 持久化 Hook，因此注册表调用 `agent.interrupt()` 后，对有 Memory 的 ReActAgent 手动保存当前记忆，避免丢掉被中断轮次。广播带发送时间，本地若发现 Agent 注册时间更晚就跳过中断，减少旧广播回环误停新任务。

**追问**：时间戳彻底解决并发了吗？没有，它依赖节点时钟，且注册时间按 session 记录；清理 pending 的逻辑也不全受同样过滤。更稳妥的建议是为每次执行分配 runId/递增版本，按目标版本停止与清理。

**易错点**：保存 Memory 不代表外部预订已回滚，发出中断也不证明供应商请求被取消。

## Q46｜为什么选择 SSE？浏览器怎么发带鉴权的 POST 流？

**口述答案**：聊天主要是客户端提交一次需求、服务端持续推送结果，单向 SSE 适合这个交互。后端使用 Spring MVC `SseEmitter`，前端使用 fetch POST 携带 JSON 和登录头，通过 ReadableStream 读取，不是原生 EventSource。常规流超时配置 30 分钟；推理片段、工具进度与最终 `message` 是不同事件。

**追问**：网络包边界就是事件边界吗？不是，前端要累积 buffer，按空行结束一个事件，多行 data 合并，再分发。文本解码也要跨块保留状态。

**边界**：当前实现不能据此宣称有自动重连、事件重放、心跳和代理超时完整治理；连接断了也不天然等于业务停止。

**依据**：[[AI项目/gogo-agent/118.实时通信 — SSE 流式推送架构]]；[ChatAgentExecutor.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/service/ChatAgentExecutor.java:56>)、[ChatSseNotifier.java](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/src/main/java/com/gogo/travel/agent/service/ChatSseNotifier.java:1>)、[chat.ts](</Users/rocky/study/profile/Markdown-Resume/AI项目/gogo-agent/repo/gogo-agent/frontend/src/api/chat.ts:15>)。

## Q47｜为什么支付链接和计划进度用结构化事件推送？

**口述答案**：PlanNotebook 变化推送 `plan_update`，工具展示数据推 `travel_data`；下单落库后 Hook 推 `booking_result`，前端据订单号、金额和支付链接渲染卡片。这样关键业务数据直接来自执行结果，减少让 LLM 复述时改写、漏字段或丢链接的风险。

**追问**：`thinking` 事件为什么要有上下文映射？部分 chunk 回调来自框架独立订阅，Reactor Context 可能断开，进度 Hook 用此前记录的 Agent ID→会话映射找到本地 emitter。

**边界**：这些是运行时推送，不是可靠业务事件存储；断线后仍应从数据库查订单，不能依赖一张前端卡片判断成功与否。

## Q48｜跨节点恢复还有哪些不能宣称已解决的问题？

**口述答案**：当前实现给出了本地复用与共享状态重建路径，但不等于可靠工作流引擎。静态阅读可见跨节点分支未先校验请求 toolUseId 与共享 pending 的一致性，也未展示原子抢占/消费；两个节点同时回复可能都尝试续跑。SessionKey 按会话和 Agent 隔离，但没有独立 runId。

**追问**：你会怎么补？建议验证会话归属、pending ID/类型和有效期，以条件更新原子地将 pending 从 WAITING 转为 RESUMING，并绑定 runId；失败再按状态恢复。副作用另用业务幂等键。

**待补**：⚠️ raw 缺失，待补充：节点宕机、重复回复、延迟旧广播、网络断开等故障注入记录。本题属于实现边界与改进建议，未进行攻击或运行复现。
