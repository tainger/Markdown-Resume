# 场景追问与评测复盘

> 答题骨架：现象 → 证据 → 定位层 → 最小处理 → 后续验证。方案未在源码出现时，明确说“我会这样改”。返回 [[AI项目/gogo-agent/interview/README]]。

## Q57｜用户说响应慢，你先查什么？

**口述答案**：先区分等待首个反馈、等待模型正文，还是等待任务真正完成；按 session 关联 Pipeline、Master、子 Agent、工具和审核耗时。原问题是否快路径命中、是否重复改写、外部搜索是否超时重试、审核 fanout 与仲裁耗时，都会影响端到端延迟。进度事件能降低无反馈等待，但不能当成任务计算更快。

**追问**：马上换快模型行不行？先看耗时占比。外部网络占大头时换模型帮助有限；模型轮次多则优先减少重复工具输出和无效调用，再用任务成功率评估模型切换。

**待补**：⚠️ raw 缺失，待补充：统一 tracing、首事件/首正文/任务完成时间的 P50/P95、分阶段基线。当前主要是日志证据，排查步骤是建议。

## Q58｜如何证明上下文优化省钱，而不是只让文本变短？

**口述答案**：对相同模型、提示词版本、初始偏好、候选快照和任务集比较优化前后，统计全流程每次调用的输入/输出 token、缓存命中、重试次数与完成质量。项目 `TokenUsageHook` 逐轮累加 reasoning 和 summary 的 usage；最终返回消息只带最后一次用量，不能当总消耗。

**追问**：当前 Hook 的累计就是全项目成本吗？不是。它随 Agent 实例创建，当前明确挂在规划 Agent；Master、独立评估器和重建后的实例还要合并统计。字符差、压缩率与账单也不是同一指标。

**待补**：⚠️ raw 缺失，待补充：统一 runId 的全调用用量、供应商账单、缓存统计以及同任务质量对照。不能编造“节省 80%”或固定金额。

## Q59｜怎么验证规划方案质量，而不只问模型“好不好”？

**口述答案**：先用固定候选和已知约束验证数学、时间顺序、金额与政策结果，再测试“空候选、去返程缺失、同价同耗时、零/缺失偏好、极端天气、全部不合规”等边界。主观评估与最终任务完成另用人工标注，避免只拿同一模型作为裁判。修复前后检查是否真实重跑、是否减少违规和是否收敛。

**追问**：有个高综合分就说明正确吗？不行，综合分是候选池内的取舍函数，硬约束结果要单列；当前政策分没有加进综合分，打零分也不代表剔除。

**现有与待补**：已有政策与冲突相关测试；本次未运行测试。⚠️ raw 缺失，待补充：完整规划排序/审核闭环回归集与人工验收结果。上述边界样例是建议。

## Q60｜供应商已下单成功，但本地没记录，怎么处理？

**口述答案**：先确认外部事实，不能让模型重复下单。按业务请求标识、外部单号与用户查询供应商结果，再补录本地记录，利用外部订单唯一约束防重复。当前 Hook 对落库异常只记录日志，这个故障窗口确实存在；应把它作为待补能力说明。

**追问**：更完整的方案是什么？建议调用前记录执行意图及幂等请求号，结果进入成功/失败/未知状态；未知进入持久查单任务，成功再对账落库，失败才允许重新执行。多项预订部分成功还需逐项状态与补偿策略。

**边界**：这是改进设计，当前未见 Outbox、持久补偿任务或与供应商对账闭环。单库事务不能解决这个跨系统窗口。

## Q61｜已确认方案，但 Redis 过期或被另一会话覆盖了怎么办？

**口述答案**：先检查方案是否仍存在、版本是否与用户确认相同；缺失时重新搜索/规划并再次确认，不能根据自然语言历史拼出“原方案”继续下单。当前结果按用户和路线/出发日存，存在跨会话覆盖风险；24 小时过期也不保证价格库存仍有效。

**追问**：如何改？建议保存确认时的 planId/version、候选标识和关键价格快照，在预订前向供应商复核价格/库存；发生变化则返回差异并重新确认。订单关联明确方案版本，而非只关联路由文字。

**边界**：价格锁定、库存预占、方案版本确认均需实际供应商能力与代码支持，不能说当前已实现。

## Q62｜两个节点同时收到“确认”，怎么避免双执行？

**口述答案**：先区分普通续聊确认与挂起工具 `/respond`。当前预中断、活跃 Agent 记录和本地缓存并不能组成跨节点互斥；共享 pending 也采用普通读写，未展示一次消费。因此不能宣称并发确认已经严格幂等。

**追问**：你会把幂等键设成 sessionId 吗？建议使用业务动作/确认凭据对应的 requestId，绑定用户、差旅单与方案版本；session 内可能有多个独立动作，不能永久共用一个键。pending 的原子状态转移和外部请求幂等要分别处理。

**验证建议**：同时向两个节点提交相同确认，断开响应后重试，再发旧 toolUseId，检查只有一个有效业务动作、旧回复被拒绝，且失败能查询状态。

## Q63｜项目能扩到多大？生产化你先做哪三件事？

**口述答案**：不能从用了 Redis/MySQL 就推断规模。当前没有给出压测与线上流量证据。我会先补副作用门禁和幂等，保证用户/订单/确认版本正确；再补 pending 原子消费与 runId，减少重复执行；最后打通全链路观测和故障回归，用结果决定并发、资源与限流配置。

**追问**：还有哪些容量点？本地 Caffeine、SSE 连接、阻塞检索线程、外部供应商限额、枚举组合数、每节点内存向量库和启动 embedding 都要分别测。共享存储不代表系统没有节点本地状态。

**待补**：⚠️ raw 缺失，待补充：并发数/QPS、任务成功率、连接与堆内存基线、供应商限流和故障压测。优先级是建议，不是已完成的上线成果。

## Q64｜面试官问“你做过最难的事”，怎么答得有证据？
