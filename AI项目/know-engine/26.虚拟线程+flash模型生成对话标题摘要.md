# 虚拟线程 + flash 模型生成对话标题摘要

在知识库对话系统中，当用户发起新会话时，需要为会话生成一个简洁的标题以便后续识别和管理。由于标题生成依赖 LLM 调用，耗时较长（通常 500ms-2s），为了不阻塞主对话流程，采用**异步生成**策略。

### 同步流程（主线程）

```java
// 1. 生成临时标题（快速、本地计算）
String tempTitle = content.substring(0, Math.min(content.length(), 20));

// 2. 创建会话（DB 写入）
finalConversationId = chatConversationService.createConversation(userId, tempTitle);

// 3. 触发异步标题生成（不等待）
Thread.ofVirtual().name("title-summary-" + finalConversationId).start(() -> { ... });

// 4. 继续主流程：保存消息、启动流式对话
return knowEngineApplicationService.streamingChat(...);
```

**关键设计点**：

- 临时标题截取前 20 字符，保证用户可立即看到会话
- 异步任务启动后立即返回，不阻塞 SSE 流式响应

### 异步流程（虚拟线程）

```java
Thread.ofVirtual().name("title-summary-" + finalConversationId).start(() -> {
    try {
        // 1. 构建轻量级模型实例
        OpenAiChatModel titleChatModel = OpenAiChatModel.builder()
                .apiKey(chatModelApiKey)
                .modelName("qwen3.5-flash")          // 轻量级模型，快速响应
                .temperature(0.7)                     // 适度创造性
                .baseUrl(chatModelBaseUrl)
                .customParameters(Map.of("enable_thinking", false))  // 关闭思考链，加速响应
                .build();

        // 2. 创建 AI Service 代理
        TitleSummaryService titleSummaryService = AiServices.builder(TitleSummaryService.class)
                .chatModel(titleChatModel)
                .build();

        // 3. 调用 LLM 生成标题
        String aiTitle = titleSummaryService.generateTitle(content);

        // 4. 更新数据库
        chatConversationService.updateTitle(finalConversationId, aiTitle);

    } catch (Exception e) {
        // 5. 容错：失败时保留临时标题，不影响主流程
        log.warn("异步标题生成失败, 保留临时标题: conversationId={}", finalConversationId, e);
    }
});
```

### TitleSummaryService 接口定义

```java
public interface TitleSummaryService {

    @SystemMessage("你是一个对话标题生成助手。根据用户的第一句话，生成一个简洁的中文会话标题，要求：不超过20个字，不加引号，直接输出标题内容。")
    @UserMessage("请根据以下用户问题生成会话标题：{{it}}")
    String generateTitle(String userQuestion);
}
```

**Prompt 设计说明**：

- `SystemMessage`：设定角色和约束条件（字数限制、格式要求）
- `UserMessage`：传入用户原始问题，`{{it}}` 为 LangChain4j 占位符
- 要求直接输出标题内容，避免模型返回多余解释

### 为什么选择虚拟线程？

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **虚拟线程**（当前方案） | 轻量、自动调度、代码简洁、无需线程池管理 | 需要 JDK 21+ | IO 密集型异步任务 |
| 平台线程 | 成熟稳定 | 资源占用高，大量任务时内存压力大 | 计算密集型任务 |
| @Async + 线程池 | Spring 集成好 | 需要配置线程池，代码侵入性稍高 | Spring 生态内统一异步管理 |
| CompletableFuture | 函数式编程，可组合 | 代码相对复杂 | 需要链式异步操作 |

### 为什么不用线程池？

不是"不能用"，而是**虚拟线程更合适**这个场景。核心原因有三点：

**1. 任务特征：纯 IO 阻塞，不占 CPU**

标题生成的完整链路是：发 HTTP 请求 → 等模型响应（500ms-2s）→ 写一次 DB。99% 的时间在等网络响应，CPU 基本空闲。平台线程在等待期间被挂起但仍占着栈内存（默认 1MB/线程），虚拟线程在等待时让出载体线程，几乎不占资源。

**2. 并发量不可预测**

每个新会话都触发一个标题生成任务。高峰期可能瞬间来 100+ 个并发请求。线程池要处理 100 个并发，要么配 100 个线程（每线程 1MB 栈 = 100MB 内存），要么排队等待。虚拟线程 100 个并发只占几 MB。

**3. 代码简洁度**

```java
// 虚拟线程：一行搞定，无需管理池
Thread.ofVirtual().name("title-summary-" + id).start(() -> { ... });

// 线程池：需要定义池、配置参数、管理生命周期
@Bean
public ThreadPoolTaskExecutor titleExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(20);
    executor.setQueueCapacity(50);
    executor.setThreadNamePrefix("title-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
    executor.initialize();
    return executor;
}
// 还要在方法上加 @Async("titleExecutor") 或注入 executor
```

对于"启动后不管"的 fire-and-forget 任务，虚拟线程的 `Thread.start()` 更直接。

### 虚拟线程 vs 线程池：完整对比

| 维度 | 虚拟线程 | 线程池 |
| :--- | :--- | :--- |
| JDK 要求 | 21+ | 8+ |
| 内存占用 | 极低（~几 KB/线程） | 高（~1MB 栈/线程） |
| 并发上限 | 百万级 | 受池大小限制 |
| 调度方式 | JVM 自动调度到载体线程 | 手动配 core/max/queue |
| 排队策略 | 无队列，直接启动 | 需选队列类型（有界/无界） |
| 拒绝策略 | 不会拒绝（无上限） | 需配 RejectedExecutionHandler |
| 资源控制 | 弱（无法限制并发数） | 强（可精确控制） |
| 监控 | 弱（JVM 级，粒度粗） | 强（池活跃数、队列深度、完成数） |
| 适合场景 | IO 密集、高并发、短任务 | 需要限流、计算密集、需监控 |
| 不适合 | CPU 密集型、需要限流保护下游 | 超高并发 IO（线程数不够用） |

### 虚拟线程的短板：无法限流

虚拟线程没有"池大小"的概念，来一个任务起一个线程。如果下游 LLM API 有 QPS 限制（比如 50 QPS），虚拟线程不会帮你限流——100 个并发请求直接打过去，可能触发 429 限流。

线程池天然有限流能力：`maxPoolSize=20` 就是最多 20 个并发，剩下的排队。

**如果要用虚拟线程 + 限流**，需要额外加 Semaphore：

```java
private final Semaphore rateLimiter = new Semaphore(20); // 最多 20 并发

Thread.ofVirtual().name("title-summary-" + id).start(() -> {
    if (!rateLimiter.tryAcquire(2, TimeUnit.SECONDS)) {
        log.warn("标题生成限流，跳过: {}", id);
        return;
    }
    try {
        // ... 调用 LLM ...
    } finally {
        rateLimiter.release();
    }
});
```

### 如果用线程池，参数怎么选？

```java
@Bean("titleExecutor")
public ThreadPoolTaskExecutor titleExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);          // 常驻线程
    executor.setMaxPoolSize(20);          // 高峰扩容上限
    executor.setQueueCapacity(50);        // 排队上限
    executor.setThreadNamePrefix("title-");
    executor.setRejectedExecutionHandler(
        new ThreadPoolExecutor.CallerRunsPolicy());  // 拒绝策略
    executor.setKeepAliveSeconds(60);     // 空闲线程回收
    executor.initialize();
    return executor;
}
```

| 参数 | 值 | 为什么 |
| :--- | :--- | :--- |
| corePoolSize | 4 | 平时并发不高，4 个常驻够用。标题生成不是核心链路，不需要太多常驻资源 |
| maxPoolSize | 20 | 高峰期扩容。20 个并发 × 1MB 栈 ≈ 20MB，内存可接受。再多了 LLM API 也会限流 |
| queueCapacity | 50 | 排队缓冲。高峰期 20 个在跑 + 50 个排队 = 70 个任务缓冲。超出走拒绝策略 |
| rejectedPolicy | CallerRunsPolicy | 队列满了让调用线程自己跑（同步降级）。标题生成不是关键路径，同步跑一次最多卡 1-2s，比丢任务好 |
| keepAlive | 60s | 高峰过后回收多余线程，释放内存 |

核心原则：标题生成是**非关键路径的 IO 密集任务**，线程池参数偏保守——不需要太大，丢不了任务就行。如果用 AbortPolicy 直接拒绝，用户会话标题就永远是"前 20 字符"的临时标题。

### 选型决策逻辑

```
能用虚拟线程吗？
  ├─ JDK 21+？ ✅
  ├─ IO 密集？ ✅
  ├─ 需要限流？ ❌（标题生成 QPS 不高，暂不需要）
  ├─ 需要监控线程池？ ❌（fire-and-forget，失败有容错）
  └→ 用虚拟线程，代码最简洁

如果后续 LLM API 加了 QPS 限制？
  └→ 虚拟线程 + Semaphore，或切回线程池
```

### 为什么选择 qwen3.5-flash？

| 模型 | 响应速度 | 生成质量 | 成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| **qwen3.5-flash** | 极快（<1s） | 良好 | 低 | 简单摘要、标题生成 |
| qwen3.5 | 快（1-2s） | 优秀 | 中 | 通用对话 |
| qwen-max | 较慢（2-5s） | 最佳 | 高 | 复杂推理 |

**选择理由**：

1. 标题生成是简单任务，不需要复杂推理能力
2. flash 模型响应速度快，用户体验好
3. 成本低，适合高频调用场景
4. 关闭 `enable_thinking` 进一步加速响应

### 优化措施

1. **模型参数优化**：`enable_thinking=false` 关闭思考链，减少 token 消耗和响应时间
2. **temperature=0.7**：平衡创造性和确定性，避免过度发散
3. **独立模型实例**：异步流程单独构建轻量级模型，不影响主对话模型配置
