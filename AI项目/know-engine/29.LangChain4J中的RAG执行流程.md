# LangChain4J 中的 RAG 执行流程

在下面这篇文章中，我们介绍过了关于 RAG 的模块化 RAG 的支持：

- [LangChain4J中的Modular RAG支持](../RAG/LangChain4J中的Modular RAG支持.md)

我们的这个项目就会围绕着这个机制来实现 RAG 的检索流程。

上一篇文档中，我们介绍了各个组件，我们在这里再来回顾一下它们，并且把整个流程串起来。然后我们基于这些组件逐一展开开始课程的学习。

`RetrievalAugmentor` 是 LangChain4j 中 RAG 检索的核心组件，只有给一个 AIService 配置了 `RetrievalAugmentor` 之后，它才会做检索。

`RetrievalAugmentor` 中包含了以下组件：

| 组件 | 作用 | 默认实现 |
| --- | --- | --- |
| **QueryTransformer** | 将用户的原始查询转换为一个或多个新查询，目的是提升检索质量。 | 直接返回原查询 |
| **QueryRouter** | 根据查询语义，将其路由到最合适的一个或多个 ContentRetriever（内容检索器） | 将查询发到所有检索器 |
| **ContentRetriever** | 接收一个 Query，从底层数据源中检索出相关内容，返回按相关性排序的 `List<Content>`。它是 RAG 流程中唯一必须由用户提供的组件（其他组件都有默认实现）。 | / |
| **ContentAggregator** | 将所有查询从所有检索器检索到的内容进行聚合、去重、排序，确保只返回最相关且不冗余的内容给 LLM | 使用 RRF 融合排序 |
| **ContentInjector** | 将聚合后的检索内容注入到原始用户消息中，构造增强提示词，使 LLM 能基于检索到的内容生成回答。 | 使用模板 `{{userMessage}}\n\nAnswer using the following information:\n{{contents}}` 将内容追加到用户消息末尾 |

用法：

```java
DefaultRetrievalAugmentor.builder()
    .queryRouter(new DefaultQueryRouter(
        List.of(embeddingRetriever, fullTextRetriever, sqlRetriever, neo4jRetriever), chatModel))  // 自定义路由器和检索器
    .queryTransformer(queryTransformer)          // 自定义改写器
    .contentAggregator(contentAggregator)        // 自定义聚合器（多层去重+RRF）
    .contentInjector(contentInjector)            // 自定义注入模板
    .build();
```

实际执行流程：

```java
public AugmentationResult augment(AugmentationRequest augmentationRequest) {
    // 从 UserMessage 提取原始查询
    Query originalQuery = Query.from(queryText, augmentationRequest.metadata());

    // 步骤1: 查询转换
    Collection<Query> queries = queryTransformer.transform(originalQuery);

    // 步骤2+3: 查询路由 + 内容检索（内部并行）
    Map<Query, Collection<List<Content>>> queryToContents = process(queries);

    // 步骤4: 内容聚合
    List<Content> contents = contentAggregator.aggregate(queryToContents);

    // 步骤5: 内容注入
    ChatMessage augmentedChatMessage = contentInjector.inject(contents, chatMessage);

    return AugmentationResult.builder()
        .chatMessage(augmentedChatMessage)
        .contents(contents)
        .build();
}
```

后面，我们就从头开始，以此开始介绍 **QueryTransformer（查询改写）、QueryRouter（查询路由）、ContentRetriever（混合检索）、ContentAggregator（重排序）以及 ContentInjector（内容注入）**。

## 步骤 2+3 的并行执行方案

步骤 2+3 是"查询路由 + 内容检索"，多个 Query 分别路由到多个 ContentRetriever 检索，这些检索互相独立，可以并行执行：

```
用户问题 → QueryTransformer 改写出 3 个 Query
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
     Query1          Query2         Query3
       │                │              │
   ┌───┴───┐        ┌──┴──┐           │
   ▼       ▼        ▼     ▼           ▼
 向量检索  BM25   SQL检索  Neo4j    向量检索
   │       │        │     │           │
   └───┬───┘        └──┬──┘           │
       ▼              ▼              ▼
     结果1           结果2          结果3
       └──────────────┴──────────────┘
                      ▼
              ContentAggregator 聚合
```

每个 Query × 每个 Retriever 的调用都是独立的 IO 操作（查 ES / 查 SQL / 查 Neo4j），串行执行会把延迟叠加，并行能把总耗时压到最慢的那一个。

### 方案 1：CompletableFuture（推荐）

JDK 原生，无需额外依赖，适合"发多个独立请求，等全部完成"的场景。

```java
// 每个 Query × 每个 Retriever 组合成一个异步任务
List<CompletableFuture<List<Content>>> futures = new ArrayList<>();

for (Query query : queries) {
    for (ContentRetriever retriever : routedRetrievers) {
        futures.add(CompletableFuture.supplyAsync(() -> retriever.retrieve(query)));
    }
}

// 等待全部完成
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

// 收集结果
List<List<Content>> results = futures.stream()
    .map(CompletableFuture::join)
    .collect(Collectors.toList());
```

| 优点 | 缺点 |
| :--- | :--- |
| JDK 原生，无依赖 | 嵌套多时代码可读性下降 |
| 可组合（thenCombine / allOf） | 异常处理稍繁琐 |
| 默认用 ForkJoinPool，可自定义线程池 | — |

### 方案 2：虚拟线程 + StructuredTaskScope（JDK 21+）

项目已经用了 JDK 21（虚拟线程生成标题），可以用结构化并发：

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    // 每个检索任务一个子任务
    var subtasks = queries.stream()
        .flatMap(q -> routedRetrievers.stream()
            .map(r -> scope.fork(() -> r.retrieve(q))))
        .toList();

    scope.join();              // 等待全部完成
    scope.throwIfFailed();     // 有一个失败就抛异常

    List<List<Content>> results = subtasks.stream()
        .map(Subtask::get)
        .collect(Collectors.toList());
}
```

| 优点 | 缺点 |
| :--- | :--- |
| 代码最直观，像同步写法 | 需 JDK 21+（预览特性，需 `--enable-preview`） |
| 父子关系明确，自动取消 | 生产环境用了预览特性有风险 |
| 虚拟线程，IO 阻塞不占资源 | — |

### 方案 3：Parallel Stream

```java
List<List<Content>> results = queries.parallelStream()
    .flatMap(q -> routedRetrievers.parallelStream()
        .map(r -> r.retrieve(q)))
    .collect(Collectors.toList());
```

| 优点 | 缺点 |
| :--- | :--- |
| 代码最简短 | **不适合 IO 阻塞任务**，默认用 ForkJoinPool，线程数=CPU 核数 |
| — | 阻塞 IO 会占满公共线程池，影响其他 parallelStream 使用者 |
| — | 无法控制并发数、无法自定义线程池 |

**不推荐用于 RAG 检索**——检索是 IO 密集型，parallelStream 的 CPU 密集设计会适得其反。

### 方案 4：ExecutorService + Future

```java
ExecutorService executor = Executors.newFixedThreadPool(10);

List<Future<List<Content>>> futures = new ArrayList<>();
for (Query query : queries) {
    for (ContentRetriever retriever : routedRetrievers) {
        futures.add(executor.submit(() -> retriever.retrieve(query)));
    }
}

List<List<Content>> results = new ArrayList<>();
for (Future<List<Content>> future : futures) {
    results.add(future.get());  // 阻塞等待每个完成
}
executor.shutdown();
```

| 优点 | 缺点 |
| :--- | :--- |
| 成熟稳定，控制力强 | 代码冗长 |
| 可精确控制线程数 | 需手动管理线程池生命周期 |
| — | `future.get()` 逐个等待，总耗时不如 allOf 高效 |

### 方案 5：Reactor / RxJava 响应式

```java
Flux.fromIterable(queries)
    .flatMap(q -> Flux.fromIterable(routedRetrievers)
        .flatMap(r -> Mono.fromCallable(() -> r.retrieve(q))
            .subscribeOn(Schedulers.boundedElastic())))
    .collectList()
    .block();
```

| 优点 | 缺点 |
| :--- | :--- |
| 背压控制、流式处理强大 | 学习曲线陡，代码可读性差 |
| 可组合 filter / map / merge | 引入额外依赖 |
| 适合流式 SSE 场景 | 对简单并行来说过重 |

### 方案选型对比

| 维度 | CompletableFuture | 虚拟线程+STS | Parallel Stream | ExecutorService | Reactor |
| :--- | :--- | :--- | :--- | :--- | :--- |
| JDK 要求 | 8+ | 21+（预览） | 8+ | 8+ | 额外依赖 |
| 代码简洁度 | 中 | 高 | 最高 | 低 | 低 |
| IO 阻塞友好 | ✅ | ✅ | ❌ | ✅ | ✅ |
| 并发控制 | 自定义线程池 | 自动 | 无 | 精确 | 背压 |
| 异常处理 | handle / exceptionally | throwIfFailed | 难 | try-catch | onError |
| 适合 RAG 检索 | ✅ 推荐 | ✅ 但预览特性 | ❌ | 可用但繁琐 | 过重 |

### 当前项目的建议

项目已经在标题生成中用了虚拟线程（JDK 21），RAG 检索并行有两种推荐路径：

1. **保守方案**：`CompletableFuture` + 自定义线程池——成熟稳定，无预览特性风险
2. **前沿方案**：`StructuredTaskScope`——代码最直观，但需 `--enable-preview`

> **注意**：LangChain4j 内部的 `DefaultRetrievalAugmentor.process()` 已经用 CompletableFuture 做了并行检索，只要把多个 Retriever 配进去，框架会自动并行。通常不需要自己手写并行逻辑，除非你自定义了 RetrievalAugmentor。
