# 问题缓存加速——缓存使用

缓存构建好，经过人工审核上线之后，就可以被使用了。

缓存查询集成在 `ChatApplicationService.chat()` 方法中，作为对话流程的**第一优先级**执行。整体控制流如下：

```
用户提问
   │
   ▼
保存用户消息 + 创建空助手消息
   │
   ▼
┌──────────────────────────────────────────────────┐
│  qaCacheService.lookup()  ── 异步执行              │
│       │                                          │
│       ├── 命中 ──▶ 直接用缓存答案替换助手消息内容    │
│       │            发送 [REFERENCE] 事件（网页端）   │
│       │            发送 [ANSWER_MESSAGE] 事件       │
│       │            发送 [DONE] 事件                 │
│       │                                          │
│       └── 未命中 ──▶ 走正常 RAG 流程               │
│                     （意图识别 → 检索 → LLM 推理）  │
│                     发送 [ANSWER_MESSAGE] 事件      │
│                     发送 [DONE] 事件                │
└──────────────────────────────────────────────────┘
```

## 缓存查询入口：lookup() 方法

`QaCacheService.lookup(question, conversationId, messageId, assistantMessageId)` 是缓存查询的唯一入口，返回 `Optional<CachedAnswer>`。

### 前置条件检查

方法首先进行四项快速检查，任一不满足即返回空（不走缓存）：

| 检查项 | 条件 | 不满足时行为 |
| --- | --- | --- |
| 缓存启用 | `properties.isEnabled() == true` | 返回空，走 RAG |
| 问题非空 | `question != null` | 返回空，走 RAG |
| 问题长度下限 | `question.length() >= 5` | 返回空，走 RAG |
| 问题长度上限 | `question.length() <= 500` | 返回空，走 RAG |

### 首问判断

通过 `entryService.hasHistory(conversationId, messageId)` 判断当前问题是否为该会话的首轮提问。

- **判断方式**：查询同一 `conversationId` 下是否存在 `id` 小于当前 `messageId` 的其他消息
- **仅首问走缓存**：如果当前问题之前已有会话消息（即多轮追问），直接返回空，走 RAG
- **设计理由**：多轮对话的追问高度依赖上下文，缓存答案难以覆盖各种上下文组合

### 向量相似度检索

调用 `QaCacheVectorService.search(question, minScore)` 进行语义匹配：

1. 使用 Embedding 模型将用户问题转换为向量
2. 在独立的 Elasticsearch 索引中进行 KNN 相似度搜索
3. 设置 `minScore = 0.95`（高阈值，宁可漏掉也不误匹配）
4. 返回最多 5 个候选匹配（`maxResults = 5`），每个包含 `id` 和 `score`

### 逐条验证

对向量检索返回的每个候选（按相似度从高到低），依次执行两层验证：

**第一层：`isUsable()` — 状态与有效期检查**

- 条目非空
- 状态为 `ACTIVE`
- 有效期未过期（`expiresAt > now`）
- 答案非空

**第二层：`lifecycle.ensureCurrent()` — 来源有效性检查**

- 加锁读取条目（`SELECT ... FOR UPDATE`）
- 校验有效期（双重检查）
- 如果 `dependencies` 尚未解析，从 `sources` 中解析并保存
- 校验所有依赖的文档和版本仍然存在、状态为已发布、公开可见
- 任一检查失败则调用 `autoDisable()` 下线条目

**容错设计**：整个 lookup 方法被 try-catch 包裹。任何异常都会记录警告日志并返回空，自动回退到 RAG 流程，保证用户体验不受影响。

## 缓存命中时的处理

当找到第一个通过全部验证的候选时，执行以下操作：

### 数据记录

```
recordLookup(questionMessageId, assistantMessageId, entryId)
   │
   ├── 写入 qa_cache_lookup 表（幂等插入）
   │     记录：问题消息ID、助手消息ID、命中的缓存条目ID
   │
   └── 更新 chat_message 表
         设置 cache_hit = 1
         在 metadata 中写入 qaCacheEntryId
```

同时调用 `hit(entryId)` 累加该条目的 `hits` 计数。

### 引用文档解析

调用 `resolveReferences(entryId)` 从缓存条目的 `dependencies` 字段构建引用列表：

1. 反序列化 `dependencies` JSON 数组为 `Dependency(documentId, versionId, chunkId)` 列表
2. 逐个查询 `KnowledgeDocument` 获取文档标题
3. 查询 `KnowledgeDocumentVersion` 获取文档 URL 和版本号
4. 构建 `RagReference(documentId, documentTitle, url, version)` 对象列表

### SSE 响应构建

缓存命中时，`ChatApplicationService.chat()` 通过 SSE 流式返回以下内容：

| 顺序 | SSE 事件 | 说明 |
| --- | --- | --- |
| 1 | 缓存答案文本 | 直接将缓存答案作为 Flux 元素发送 |
| 2 | `[REFERENCE]:{json}` | 引用文档列表（仅网页端发送） |
| 3 | `[ANSWER_MESSAGE]:{assistantMessageId}` | 通知前端答案已完成，附加评价按钮 |
| 4 | `[DONE]:{conversationId}` | 标记对话结束 |

对比 RAG 流程，缓存命中**跳过了所有进度通知**（如"正在识别意图…"、"正在检索…"、"正在生成回答…"），用户几乎瞬间看到完整答案。

### 数据库更新

在发送 SSE 事件之前，后端同步更新数据库：

- `chat_message.content` ← 缓存答案文本
- `chat_message.rag_references` ← 引用文档 JSON
- `chat_message.cache_hit` ← 1（通过 recordLookup 设置）
- 清除会话的内存聊天缓存（`evictCache`），避免缓存答案污染后续 RAG 对话的历史记忆

## 缓存未命中时的处理

当所有候选都未通过验证（或向量检索无结果）时：

1. 调用 `recordLookup(questionMessageId, assistantMessageId, null)` 记录未命中（`entryId` 为 null）
2. 返回 `Optional.empty()`
3. `ChatApplicationService.chat()` 中的 `flatMapMany` 检测到空结果，切换到 `normalAnswer` 流
4. 执行完整的 RAG 流程：意图识别 → 问题改写 → 向量/全文/SQL 检索 → 重排序 → LLM 推理

**未命中记录的作用**：即使未命中也会写入 `qa_cache_lookup` 表（`entryId = null`），用于计算缓存命中率（`hits / total queries`），为准出决策提供数据。

## 前端渲染

### 答案渲染

前端通过 SSE 流式接收数据。当收到普通文本内容时，累积拼接到 `fullContent` 变量，并通过 Markdown 渲染器实时更新消息气泡的内容。

缓存命中的答案是一次性发送的完整文本（非逐 token 流式），因此用户看到的是瞬间出现的完整答案。

### 引用资料渲染

当收到 `[REFERENCE]:{json}` 事件时，前端：

1. 解析 JSON 数组获取引用列表
2. 去重（按 `documentTitle + url` 组合去重）
3. 渲染为可点击的链接列表，格式为 `[1] 文档标题`、`[2] 文档标题`…
4. 插入到消息气泡底部（时间戳之前），标记为"参考来源："

引用资料的展示与 RAG 回答完全一致，用户无法感知答案来自缓存还是 RAG。
