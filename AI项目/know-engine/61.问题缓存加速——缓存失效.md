# 问题缓存加速——缓存失效

缓存建立了，不可能一直都保留下去，一方面如果过时的缓存会影响回答质量，还有就是有些问题长时间没命中，保留下来也是浪费。

缓存条目的可用性由 `status` 字段承载，失效的本质是把条目从 PENDING / APPROVED / ACTIVE 迁入 DISABLED（待审核候选被拒绝则进入 REJECTED）。完整状态机如下：

```
                    ┌──────────┐
                    │ REJECTED │
                    └──────────┘
                         ▲
                         │ 拒绝
┌──────────┐  审核通过  ┌──────────┐  发布成功  ┌──────────┐
│ PENDING  │──────────▶│ APPROVED │──────────▶│  ACTIVE  │
└──────────┘           └──────────┘           └──────────┘
                           │                       │
                           │ 过期/来源失效          │ 自动准出
                           ▼                       ▼
                    ┌──────────┐            ┌──────────┐
                    │ DISABLED │◀───────────│ DISABLED │
                    └──────────┘            └──────────┘
                         │
                         │ 重新激活
                         ▼
                    ┌──────────┐
                    │ APPROVED │（重新发布）
                    └──────────┘
```

进入 DISABLED 的每一条路径都是一次"失效"：可能是**知识变了（文档/分段变更）、质量差了（差评/低命中率）、到期了（超过有效期）、来源追溯不到了，也可能是员工主动下线**。本章按触发时机展开各类失效机制，向量清理则描述失效之后发生的事。

我们设计的失效不依赖单一机制，而是由三道互补的防线构成：

```
防线一：主动失效（事件驱动）
            知识变更发生的那一刻
  DocumentInvalidatedEvent / SegmentEditedEvent
  ──▶ 同步下线受影响条目
                  时效性最好
                │
                │ 若事件遗漏或出现新的变更路径
                ▼
防线二：惰性校验（使用前兜底）
           每次缓存查询、审批、发布前
  ensureCurrent() ──▶ 逐条重新校验有效期与依赖快照
         保证最终正确性
                │
                │ 与知识无关的质量问题
                ▼
防线三：定期准出（定时任务）
             XXL-Job: qaCacheRetire
  evaluateUsage() ──▶ 差评 / 低命中率条目自动下线
          质量退出通道
```

## 主动失效：事件驱动下线

我们的缓存是基于文档构建的，所以当文档发生变化的时候，我们需要把对应的缓存也给失效掉。

在我们的系统中，有文档级的更新，比如文档直接删除、文档增减新版本等，也有分段级别的更新，比如直接修改分段。

### 文档级失效

我们在文档发生变化的时候，会抛出一个 `DocumentInvalidatedEvent` 事件：

| 触发操作 | 事件携带 | 失效范围 |
| --- | --- | --- |
| 版本切换（`currentVersionId`变化） | 文档 ID | 该文档的**全部**条目 |
| 收回公开访问（`VISITOR`→ 其他） | 文档 ID | 该文档的全部条目 |
| 逻辑删除文档 | 文档 ID | 该文档的全部条目 |
| 物理删除文档（单个 / 批量） | 文档 ID 列表 | 这些文档的全部条目 |
| 停用版本（`deactivateVersion`） | 文档 ID + 版本 ID | **仅**依赖该版本的条目 |

这个事件之前一直没用上，现在我们用上了，我们可以监听 `DocumentInvalidatedEvent`，由 `KnowledgeDocumentServiceImpl` 在以下场景发布：

```java
@EventListener
public void onDocumentInvalidated(DocumentInvalidatedEvent event) {
    if (!properties.isEnabled()) {
        return;
    }
    for (Long documentId : event.getDocumentIds()) {
        entryService.invalidateByDocument(documentId, event.getVersionId());
    }
}
```

### 分段级失效

员工在管理后台编辑某个分段文本时（`KnowledgeSegmentServiceImpl.updateById`），系统会删除旧向量、生成新 embeddingId，这时候也会触发一个新的 SegmentEditedEvent 事件。

```java
// 文本变更时，同步更新父分段内容
if (textChanged) {
    syncParentSegmentText(oldSegment, entity.getText());
    // 通知缓存等模块执行分段级精确失效。
    if (oldSegment.getChunkId() != null) {
        log.info("分段内容变更，通知缓存等模块执行分段级精确失效, chunkId: {}", oldSegment.getChunkId());
        eventPublisher.publishEvent(new SegmentEditedEvent(this, oldSegment.getChunkId()));
    }
}
```

同样监听这个事件，触发这个分段有关联的缓存的失效——`invalidateByChunk`，其实最终执行的就是这个 SQL：

```sql
UPDATE qa_cache_entry
SET status='DISABLED', disable_reason='SEGMENT_CHANGED', ...
WHERE status IN ('PENDING','APPROVED','ACTIVE')
  AND JSON_CONTAINS(dependencies, JSON_OBJECT('chunkId', 'chunk-a1b2'))
```

只有依赖快照中**明确记录了该 chunkId** 的条目会被下线，其余条目不受影响。

## 惰性校验：使用前的兜底防线

除了上面的主动失效场景，我们还有一个很关键的兜底场景。

比如，因为缓存生效前需要先发起审批，并且审批是个异步流程，那么我们就需要在最终审批通过的时候，再做一次兜底校验，确保这过程中数据不发生变化（比如文档失效）。

再比如，审批的时候，我们设置的缓存是 30 天有效，但是到了时间了，还没来得及失效掉，这时候检索的时候也需要确保数据是可用的。

所以，任何缓存条目在被真正生效使用之前，都会经过 `ensureCurrent` 的完整校验：

- **缓存查询时**：`lookup()` 对每个向量召回的候选调用；
- **审批 / 发布时**：`approve` 与 `publish` 前调用，阻止已失效条目进入或保持生效。

```
ensureCurrent(id)
   │
   ├── lock(id) 行锁，status ∈ {PENDING, APPROVED, ACTIVE}？
   │        否 ──▶ false（已下线条目无需再处理）
   │
   ├── expires_at ≤ now ？ ──▶ EXPIRED 下线
   │
   ├── dependencies 为空？
   │        ├── 解析 sources 中的 RAG 引用 → 回溯 knowledge_segment
   │        ├── 任一引用无法追溯 ──▶ SOURCE_UNVERIFIABLE 下线
   │        └── 全部可追溯 ──▶ 固化依赖快照（仅首次）
   │
   └── dependenciesCurrent(id)：逐依赖四重校验
            ① documentId / versionId 有效
            ② 文档 current_version_id 仍等于快照版本（未被切换）
            ③ 文档仍对访客公开（accessible_by = VISITOR）
            ④ 版本记录仍为 VECTOR_STORED（未停用）
            任一不满足 ──▶ KNOWLEDGE_CHANGED 下线
```

三个准出原因的语义：

| disable_reason | 含义 |
| --- | --- |
| `EXPIRED` | 超过员工审批时设定的有效期，需要重新审核 |
| `SOURCE_UNVERIFIABLE` | 原始引用已无法追溯到完整文档版本（如引用缺失 embeddingId / version），宁可不用 |
| `KNOWLEDGE_CHANGED` | 依赖快照与当前知识库状态不一致（版本切换、删除、停用、收回公开） |

## 定期准出：基于使用数据的自动下线

前两道防线解决"知识是否还有效"，第三道防线回答"这条缓存**值不值得继续存在**"。XXL-Job 定时任务 `qaCacheRetire` 驱动 `retire()`：

```
retire()（游标分页，每批 100 条）
   │
   ├── 逐条 ensureCurrent()       ── 失效者当场下线（惰性校验的定期巡检版）
   │
   ├── 存活者 evaluateUsage()
   │        ├── 差评准出（无观察窗口限制）
   │        └── 低命中率准出（需激活满 7 天）
   │
   └── 统一执行向量清理（见 4.8 节）
```

**差评准出（NEGATIVE_FEEDBACK）**：`feedbackCounts` 按**用户首次评价**统计（每用户只计一条，避免重复投票），满足差评用户 ≥ 3 且差评占比 ≥ 50% 时下线。

**低命中率准出（LOW_HIT_RATE）**：激活满 7 天（完整观察窗口）且窗口内有效查询 ≥ 100 而命中率 < 1% 时下线。统计基于 `chat_message` 粗口径：

- 分母：窗口内带 RAG 引用的助手回答数（近似"走到检索环节的查询量"）；
- 分子：其中 `cache_hit = 1`、答案非空且 `metadata.qaCacheEntryId` 指向本条目的回答数。

粗口径指的是这个百分比其实并不是非常精准的命中率，因为没考虑比如多轮对话的影响。但是其实影响不大，我们主要是用它来判断一个缓存还是否被经常用，所以不那么准影响也不太大，如果非要很精确，就需要单独维护表和数据，比较麻烦。所以就用了这个折中方案。

## 向量清理：失效之后发生的事

缓存条目下线时**并不删除 ES 向量**，只标记 `vector_deleted = false`，清理交给 `retire()` 的收尾阶段：

```
条目下线（autoDisable）
   │ vector_deleted = false
   ▼
retire() 收尾：查询所有 DISABLED 且未清理的条目（每批 100，按更新时间升序）
   │
   ├── vectors.remove(id) 从 ES 删除 ── 成功 ──▶ vector_deleted = true
   └── 删除失败 ──▶ 保持 false，下轮任务自动重试
```

这样设计的原因：

1. **不阻塞主业务**：文档删除、审批发布等操作不必等待 ES 删除完成；
2. **失败可重试**：ES 抖动不会导致条目"下线成功但清理永久丢失"；
3. **查询安全不依赖清理**：`lookup()` 拿到向量召回的候选后仍要经过 `isUsable()`（强制 `status = ACTIVE`）与 `ensureCurrent` 双重校验——即使向量因清理失败仍留在 ES 中，对应的已下线条目也绝不会被返回。
