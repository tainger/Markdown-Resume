## Q1: know-engine 是一个什么项目？包含哪些核心功能？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：know-engine 是一个基于 RAG 架构的企业知识管理与智能问答系统，实现从文档接入、智能切片、向量化存储到多源检索、意图路由、流式对话的全链路闭环。

核心功能五大块（按项目笔记口径）：

1. **全链路知识接入（Ingestion Pipeline）**：多格式解析（PDF 走 MinerU 深度解析，另支持 Word、Excel、Markdown、TXT 等）；5 种切片策略按工厂模式选择；Spring `ApplicationEvent` 事件驱动串联"文档转换 → 切片 → 向量化"；XXL-Job 定时扫表补偿失败任务，保障最终一致性。
2. **关键检索增强**：查询改写（4 维策略）、父子分段扩展、本地 Reranking（BGE-RERANKER）、三路由查询（ES / MySQL / Neo4j）、Text2SQL、Text2Cypher。
3. **意图识别与动态 Prompt**：6 大意图分类 + 领域相关度判断（不相关问题直接走通用对话，避免 RAG 误检索）+ 结构化实体提取，按识别结果动态加载领域 Prompt。
4. **流式对话体验**：基于 Reactor `Flux` 的 SSE 全链路流式输出，进度推送与 RAG 引用溯源，支持 `[CARD]` 结构化交互卡片与钉钉机器人接入。
5. **知识库管理**：双类型知识库（`DOCUMENT_SEARCH` 语义检索型 / `DATA_QUERY` 数据查询型）、完整文档生命周期（INIT → UPLOADED → CONVERTING → CONVERTED → CHUNKED → VECTOR_STORED）、多版本管理、检索权限体系。

**验证**：脱稿画出"上传 → 解析 → 切片 → 向量化 → 检索 → 生成"链路图，并逐一报出五大功能的关键词（事件驱动、4 维改写、6 大意图、SSE 事件、文档状态机）。

**追问**：它和"上传文档就能问答"的 Demo 区别在哪？——区别在工程化完整度：入库有状态机与补偿、检索有多源路由与精排、交互有进度与溯源，每个环节都有对应容错设计。

> 来源：[2.项目整体架构与核心功能](../2.项目整体架构与核心功能.md)
> 源码：`src/main/java/cn/hollis/llm/mentor/know/engine/document/constant/DocumentStatus.java`、`src/main/java/cn/hollis/llm/mentor/know/engine/document/event/DocumentEventListener.java`、`src/main/java/cn/hollis/llm/mentor/know/engine/document/job/DocumentCompensationJob.java`

## Q2: 项目的技术栈全景是怎样的？各组件分别负责什么？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：以 Java 21 + Spring Boot 3.5 + LangChain4j 1.11.0 为骨架，AI 侧用通义系列模型 + 本地 BGE 重排，存储侧由 ES / MySQL / Neo4j / Redis / MinIO 按数据类型分工。

| 分类 | 技术 | 职责 |
|:---|:---|:---|
| 语言/框架 | Java 21 + Spring Boot 3.5 | 虚拟线程、Record 模式匹配 |
| AI 框架 | LangChain4j 1.11.0 | RAG 管道、AI Services、流式对话 |
| LLM | qwen3-30b-a3b-instruct-2507（主对话/意图/改写/路由）、qwen3.6-plus（RAG 流式生成）、qwen3.5-flash（异步标题）、qwen3-vl-plus（图片描述） | 意图识别、查询改写、路由决策、流式生成、标题与图片描述 |
| 向量存储 | Elasticsearch | KNN / 全文 / 混合检索 |
| 图数据库 | Neo4j + APOC | Text2Cypher 实体关系查询 |
| 关系数据库 | MySQL + MyBatis-Plus | 业务数据 + Text2SQL 结构化查询 |
| 对象存储 | MinIO | 文档文件存储 |
| 缓存 | Redis + Redisson | 分布式锁、父分段缓存 |
| Reranking | BGE-RERANKER（ONNX Runtime） | 进程内本地推理，零网络开销 |
| Embedding | text-embedding-v4（通义） | 1536 维向量 |
| 文件解析 | MinerU（PDF）、Apache Tika（类型检测）、EasyExcel | 多格式文档解析 |
| 任务调度 | XXL-Job 2.4 | 补偿任务定时触发 |
| 响应式 | Project Reactor | SSE 流式推送、非阻塞调度 |
| 连接池 | Druid | SQL 监控、慢查询检测 |

**验证**：随机抽 3 个组件，能说出"它解决什么问题、换掉它影响哪条链路"——例如去掉 XXL-Job 则失败任务失去定时补偿兜底。

**追问**：Reranking 为什么用 ONNX 在本地跑？——进程内推理省去网络往返，BGE-RERANKER 模型以双重检查锁单例加载一次、全生命周期复用。

源码校核：笔记中的 LLM 列表「qwen-max-latest、qwen3.5-flash、qwen-3.6-plus」在源码中实际为 qwen3-30b-a3b-instruct-2507（application.yml 主对话/流式模型）、qwen3.6-plus（ChatApplicationService 中 RAG 生成专用）、qwen3.5-flash（标题生成）、qwen3-vl-plus（MinerU 图片描述）；源码中不存在 qwen-max-latest，「qwen-3.6-plus」在代码中的实际写法为 qwen3.6-plus。

## Q3: 项目源码如何分层与划分模块？这样划分有什么好处？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：系统采用分层架构设计（笔记中架构自上而下分 5 层），源码按职责划分为 7 个核心包，AI 能力、对话编排、文档处理、RAG 检索彼此解耦。

| 模块 | 包路径 | 职责 |
|:---|:---|:---|
| AI 能力层 | `ai/` | 意图识别、通用对话、Prompt 路由、标题摘要生成 |
| 对话管理层 | `chat/` | 对话编排（RAG 管道）、会话管理、消息持久化、多轮记忆 |
| 文档管理层 | `document/` | 文档上传/转换/切片/向量化、知识库管理、事件驱动处理 |
| RAG 检索增强层 | `rag/` | 查询改写、查询路由、多源检索、Reranking、进度感知 |
| 业务数据层 | `business/` | 车辆/订单/用户等业务实体管理、MapStruct 数据转换（Converter/VO） |
| 基础设施层 | `infra/` | 分布式锁注解、雪花 ID 生成器、JSON 修复工具 |
| 全局配置层 | `config/` | 线程池、MyBatis-Plus、XXL-Job、元数据填充 |

RAG 管道核心组件挂在 `rag/modules/` 下：`KnowEngineQueryTransformer`（查询改写）、`KnowEngineQueryRouter`（三源路由）、`KnowEngineElasticsearchContentRetriever`（ES 检索，父子分段扩展）、`ProgressAwareContentAggregator`（进度感知聚合）以及 reranker、splitter 子包。

好处用设计原则回答：Controller 只发布事件、业务逻辑由 EventListener 异步驱动，"事件驱动优于直接调用"让文档处理各阶段独立解耦、Controller 瘦身、职责清晰。

**验证**：给定一个新需求（如新增一种切片策略），能立即说出落在哪个包、通过什么机制接入（`DocumentSplitterFactory` 按策略创建）。

**追问**：document/ 和 rag/ 为什么分开？——入库（转换/切片/向量化）与检索（改写/路由/精排）是两条链路，变更频率和关注点不同，事件驱动把两者解耦。

源码校核：笔记中的「7 个核心包」在源码中实际为 10 个顶层包——除笔记所列 ai/chat/config/document/infra/rag/business 外，还有 `auth/`（Sa-Token 登录认证）、`common/`（通用响应 R）、`dingtalk/`（钉钉机器人接入）；且 business/ 中并无知识库 CRUD（知识库管理在 document/），实际为 CarInfo/CarOrder/MyCar/StaffInfo/UserInfo 等业务实体。rag/modules/ 下另有 KnowEngineSqlDatabaseContentRetriever（Text2SQL）、KnowEngineNeo4jContentRetriever（Text2Cypher）等检索器。

> 来源：[2.项目整体架构与核心功能](../2.项目整体架构与核心功能.md)、[3.项目亮点与设计原则](../3.项目亮点与设计原则.md)
> 源码：`src/main/java/cn/hollis/llm/mentor/know/engine/rag/modules/KnowEngineQueryRouter.java`、`src/main/java/cn/hollis/llm/mentor/know/engine/rag/modules/splitter/DocumentSplitterFactory.java`、`src/main/java/cn/hollis/llm/mentor/know/engine/business/entity/CarInfo.java`

## Q4: 把项目跑起来需要哪些环境依赖和步骤？版本与插件要求背后有什么原因？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：7 项环境依赖 + 两步配置 + 一条构建命令，验证入口是 8009 端口的对话页与上传页。

环境依赖：JDK 21+、MySQL 8.0+、Redis 7.0+、Elasticsearch 8.x（需开启 KNN 向量检索）、Neo4j 5.x（需安装 APOC 插件）、MinIO、XXL-Job Admin 2.4+。

启动步骤：

1. 修改 `application.yml`，填入各中间件连接信息和 LLM API Key；
2. 执行 `sql/tables.sql` 初始化数据库表；
3. `mvn clean package -DskipTests` 后 `java -jar target/know-engine-1.0.0-SNAPSHOT.jar`，或在 IDEA 直接运行 `KnowEngineApplication`；
4. 访问 `http://localhost:8009/chat.html`（对话页）、`http://localhost:8009/upload.html`（文档管理页）。

版本要求的原因（与笔记口径对应）：ES 8.x 开 KNN——ES 在本项目承担向量存储与 KNN 检索，不开则向量检索链路不可用；Neo4j 装 APOC——项目以 "Neo4j + APOC" 做 Text2Cypher 实体关系查询；JDK 21——虚拟线程、Record 模式匹配都依赖它（笔记建议 JDK 21，最低 17+）；XXL-Job Admin 是补偿任务的调度中心。

核心接口速览：`/chat/send`（POST，SSE 流式对话）、`/api/document/upload`（上传）、`/api/document/split/{documentId}`（手动切片；切片完成后由事件驱动自动触发向量化）。

**验证**：先起中间件再起应用；上传一份文档，观察状态从 INIT 依次走到 VECTOR_STORED，再到 chat.html 提问并确认返回携带引用溯源。

**追问**：只装部分中间件能跑吗？——笔记未提供裁剪方案（⚠️ raw 缺失）；从架构看各组件承担独立链路（ES 检索、MySQL 业务、Redis 缓存、MinIO 文件、Neo4j 关系查询），缺一对应功能不可用。源码侧 STARTUP 明确 XXL-Job Admin 为非硬性依赖（未部署不阻塞启动），钉钉配置无效也不影响启动。

源码校核：笔记中的「/api/document/embedding（手动向量化）」接口在源码中不存在——KnowledgeDocumentController 仅有 /upload、/split/{documentId} 等接口，向量化由切片完成事件自动触发；另笔记「JDK 21，最低 17+」在源码 README/STARTUP 中均为 JDK 21+，未提最低 17。

## Q5: RAG 框架为什么选 LangChain4j 而不是 Spring AI？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：两者功能整体差不多、各有优势也各有不足；最终选择 LangChain4j + Python 组合，决定性原因有两条——文档处理两边支持都不够好（干脆都不用，交给 Python），以及 LangChain4J 原生支持混合检索和重排序。

展开：

1. **选型前提**：先从两个维度做过详细对比——文档处理（Splitter / Transformer）与 Modular RAG（查询路由 / 混合检索 / 重排序 / 内容聚合），结论是"功能差不多"。
2. **文档处理**：Spring AI 和 LangChain4j 的支持都不够，决定都不用，改用 Python 生态现成工具做文档处理（后续落地为 MinerU 方案，见 Q7/Q8）。
3. **混合检索 + 重排序**：LangChain4J 支持，Spring AI 不支持，需要自己基于 Advisor 机制实现——自研成本是明确差距。

通用补充：这套选型方法可迁移——先列出系统的必需要素（混合检索、Rerank、结构化输出等），再对框架逐项打分，框架差异常在"生态位细节"而不是名气；框架解决不了的环节（文档解析）要敢于整体外移到更成熟的生态。

**验证**：能脱稿复述两条决定性原因，并回答"如果用 Spring AI，混合检索与重排序要怎么补"（基于 Advisor 机制自行实现）。

**追问**：选了 LangChain4j 就完全不用 Python 了吗？——不是，文档解析仍交给 Python 侧（MinerU），Java 侧专注 RAG 管道与业务编排。

> 来源：[5.技术选型](../5.技术选型.md)、[18.Spring AI 和 LangChain4J中文档处理功能对比](../../RAG/18.Spring AI 和 LangChain4J中文档处理功能对比.md)、[32.Spring AI 和 LangChain4J的模块化RAG功能对比](../../RAG/32.Spring AI 和 LangChain4J的模块化RAG功能对比.md)

## Q6: 向量存储为什么选 Elasticsearch + IK 而不是 pgvector？整体存储方案怎么划分？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：核心诉求是混合检索——ES 本身同时支持语义相似检索（KNN）和关键词检索，一个库就能做混合检索，不必维护两套数据库；pgvector 路线可行但全文检索用得少，本项目换成 ES + IK 分词器。

展开：

- **备选评估**：pgvector 在课程前面章节用过；pgsql 其实也支持全文检索和向量检索，"pg + es" 组合也不是不行。笔记明确：这块影响不算大，实际写简历时可按自己熟悉的或公司主用技术栈来写。
- **存储方案（本项目）**：向量存储 ES；关系型数据 MySQL；文档内存存储 ES（笔记原文口径，即 ES 同时承担向量与文档两块）；缓存 Redis；文件 MinIO。
- **替代组合（pg 路线）**：向量 pg、关系型 pg、文档内存 es、缓存 redis、文件 minio。
- **关系库选 MySQL**：对话信息、用户信息、权限管理等业务数据落 MySQL，理由是用户基数更大、熟悉的人更多、SQL 更简单。
- **图库选 Neo4j**：db-engines 图数据库排名第一。
- **文件选 MinIO**：开源、上手成本低，支持文档、图片等对象存储。

通用补充：IK 分词器在这里的作用是提供中文分词能力，支撑 ES 关键词/全文检索一侧，与 KNN 向量检索共同构成混合检索。

**验证**：能画出 5 类数据的归属（向量/关系/文档/缓存/文件），并回答"为什么不用两个库分别做语义与关键词检索"（ES 一库兼得，降低维护成本）。

**追问**：用 pgvector 会被面试官挑战吗？——不会，笔记口径是可以按熟悉或公司栈来写，关键是讲清"混合检索需要语义 + 关键词两种能力"这一选型依据。

> 来源：[5.技术选型](../5.技术选型.md)

## Q7: 为什么不用 Java 生态（Spring AI / LangChain4J）解析 PDF 文档？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：用一份 46.1 MB、图文并茂、左右分栏带表格的车型手册 PDF 实测，Java 侧两套方案都存在格式乱、空白字符多、图片和表格无法保留等硬伤，且扫描件、表格、LaTeX 公式完全无能为力，因此必须换一种能"一次性解决所有问题"的方案（Python 侧 MinerU）。

展开：

- **Spring AI 路线**：用 `PagePdfDocumentReader` / `ParagraphPdfDocumentReader`（课程中封装过 `PdfReaderStrategy`）实测，四类问题：①左右结构的版式没有区分、格式乱；②大量空白字符；③图片没解析出来甚至没保留；④表格没解析出来甚至没保留。
- **自研补丁也救不回来**：`PdfMultimodalProcessor` 能处理带图片的 PDF，但缺点依旧——需要自己写代码实现、解析出的文字中还有很多空格、文档结构不正确、表格无法处理。
- **LangChain4J 路线**：`langchain4j-document-parser-apache-pdfbox`（`ApachePdfBoxDocumentParser`，基于 PDFBox）实测，结果与 Spring AI 方案差不多，文档结构读取正确，但上述问题依旧存在。
- **共同能力空白**：扫描件 PDF、PDF 中的表格、LaTeX 公式，Java 侧工具"都无能为力"。

**验证**：拿一份"左右分栏 + 图 + 表"的 PDF，分别跑 Spring AI 和 LangChain4J 的解析器，对照笔记四类问题逐项核对复现。

**追问**：Java 侧是不是完全不做解析？——不是一刀切：Java 侧仍用 Apache Tika 做文件类型检测（按文件头魔数而非扩展名）、EasyExcel 处理 Excel，难解析的 PDF 才交给 Python 侧。

## Q8: 文档解析为什么最终选 MinerU？相比 PaddleOCR、Marker 的优势与缺点边界在哪？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：在 MinerU、PaddleOCR + PP-Structure、Marker 三个开源方案中，MinerU 是端到端智能解析，中文支持最好，能正确处理双栏、图文穿插、浮动框，表格与公式还原精度最高，且部署简单、提供开源版/网页版/客户端/在线 API 多种形态，故选它做 PDF → Markdown 的解析入口。

| 维度 | MinerU | PaddleOCR + PP-Structure | Marker |
|:---|:---|:---|:---|
| 类型 | 端到端智能解析 | 分阶段 OCR + 版面分析 | 基于 LLM 的 PDF 转 Markdown |
| 中文支持 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ |
| 公式识别 | ✅ LaTeX（高精度） | ❌ 仅字符级，无公式结构 | ⚠️ 依赖 OCR，公式支持弱 |
| 表格还原 | ✅ 跨页、合并单元格 | ⚠️ 基础表格，跨页易错 | ⚠️ 表格常转为图片或文本 |
| 多栏排版 | ✅ 自动还原阅读顺序 | ⚠️ 易出现"Z 字形"错乱 | ✅ 较好（依赖 layout 模型） |
| OCR 能力 | 内置多语言 OCR（84 种） | 强（中文优化好） | 集成 Donut/OCR |
| 输出格式 | Markdown / JSON / HTML | TXT / HTML（需二次开发） | Markdown |
| 部署难度 | 中等（CLI/WebUI/Docker） | 较高（需拼接模块） | 中等（需 GPU） |
| 适合场景 | 论文、财报、教材、RAG 知识库构建 | 简单票据、证件、固定模板 | 英文论文批量转 Markdown |

MinerU 的 7 条优势可压缩为：版面还原（双栏/图文穿插/浮动框）、LaTeX 高精度、部署简单开源、中文友好、PDF 转 Markdown、表格图片友好、多种使用形态。

缺点与边界（⭐⭐⭐ 考察点）：MinerU 网页版能识别标题，但**无法准确识别多级标题**——所有标题都被转成 `#`（一级标题）。设计建议：know-engine 下游的 `MarkdownHeaderParentTextSplitter` 依赖标题层级构建 Parent-Child 父子分段，标题层级被拍平会直接退化切片质量，落地时要针对这一点做补偿或用 API/客户端版本核对效果；面试中可坦然说明这是已知踩坑点，笔记也提示"使用时的各种问题后续专门讲如何解决"。

**验证**：用一份双栏 PDF 在 MinerU 在线版（mineru.net，GitHub/微信登录免费试用）实测：多栏阅读顺序、表格、公式是否还原，导出 Markdown 并重点检查多级标题是否被拍平。

**追问**：
1. 多级标题问题为什么影响大？——下游按标题层级切片建父子分段，层级丢失会破坏 Parent-Child 结构（设计建议，属推论）。
2. 除了本地开源部署还能怎么用？——网页版、客户端、在线 API 多种方式，验证阶段可先用网页版快速试效果。

## Q9: 为什么需要三源智能路由？ES、MySQL、Neo4j 如何分工，路由失败怎么办？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：企业问答的问题天然分三类——非结构化知识、结构化业务数据、实体关系，单一数据源无法都答好；`KnowEngineQueryRouter` 用 LLM 对用户 Query 做语义分析，输出 `{intent, strategy, confidence}` 结构化决策，自动路由到最合适的数据源。

三源分工：

| 数据源 | 检索方式 | 适用场景 |
|:---|:---|:---|
| Elasticsearch | KNN 向量检索 + 全文检索 + 混合检索 | 语义相似性匹配、非结构化知识 |
| MySQL | Text2SQL（LLM 生成 SQL，JDBC 执行） | 结构化数据查询，如订单、保险、召回信息 |
| Neo4j | Text2Cypher（LLM 生成 Cypher + 降级回退） | 实体关系查询，如车型图谱、零部件供应链、故障影响链 |

关键设计细节：

- **Text2SQL**：基于 `table_meta` 表存储的表结构元数据驱动 Schema 感知，自动注入当前日期等上下文变量，查询结果以自然语言格式返回。
- **Text2Cypher**：LLM 根据图数据库 Schema 自动生成 Cypher，无需预先编写查询模板；**Cypher 查询失败时自动降级回退 ES 检索**，查询结果与 ES 向量检索结果经 `ContentAggregator` 统一聚合，再经 Reranking 参与最终生成。
- **路由容错**：路由决策失败（JSON 解析异常或其他错误）时自动降级为全量检索（返回全部内容检索器），避免直接无结果，保障系统鲁棒性。

边界讨论（设计建议）：路由决策依赖 LLM 判断，confidence 低或判错数据源时要有兜底——本项目已落地"Text2Cypher → ES 降级"与"路由失败降级全量检索"两道防线；更进一步的演进方向是多路召回后统一融合，代价是延迟与成本上升，需按评测数据取舍。

**验证**：构造三类问题各一条（"保养周期怎么规定" / "我的订单什么状态" / "某车型的零部件供应链关系"），观察路由输出的 strategy 是否分别落到 ES / MySQL / Neo4j；再模拟 Neo4j 不可用，确认降级到 ES 仍能返回结果。

**追问**：
1. 路由决策输出什么结构？——`{intent, strategy, confidence}` 三字段的结构化结果，由 LLM 输出并解析。
2. 判错数据源的最坏结果是什么？——拿到空结果或低质量结果；现有兜底是降级与统一聚合精排，彻底解决需多路召回（设计建议）。

源码校核：笔记中的「路由失败自动降级为空结果」在源码中实际为降级为全量检索——KnowEngineQueryRouter 在 JSON 解析异常或路由异常时返回全部 contentRetrievers，注释明确"避免直接无结果"。

## Q10: 一分钟介绍这个项目的设计亮点，并说出背后贯穿的设计原则

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：亮点按"检索质量、流式体验、工程健壮性"三组讲，每条亮点对应一条明确的设计原则，避免流水账式罗列。

**检索质量组**：
- **本地 Reranking**：ONNX Runtime 在 JVM 进程内运行 BGE-RERANKER，双重检查锁单例仅加载一次，无需独立 Reranking 微服务，零网络开销——对应"本地推理优先"。
- **父子分段检索**：命中细粒度子分段后，经 `parentChunkId` 回溯父分段完整文本、`brotherChunkId` 补全兄弟分段，解决"切片后语义截断"这一 RAG 经典痛点；父分段原文标记 `skipEmbedding = 1` 不参与向量检索。
- **查询改写 4 维策略**（简洁改写、抽象概念改写、错别字纠正、车型信息标准化），改写结果用虚拟线程异步回写，对端到端延迟零贡献——对应"虚拟线程优先"。

**流式体验组**：装饰器模式注入 `ProgressAwareContentRetriever` / `ProgressAwareContentAggregator`，SSE 事件扩展为 `[PROGRESS]` / `[REFERENCE]` / `[CARD]` / Token 四类；新会话用虚拟线程 + qwen3.5-flash 异步生成标题（关闭 `enable_thinking` 降延迟，失败保留临时标题）——对应"流式优先"与"容错优先"。

**工程健壮性组**：
- **事件驱动 + XXL-Job 补偿**：Controller 只发布事件，"异步优先，定时兜底"保障最终一致性——对应"事件驱动优于直接调用"与"最终一致性"。
- **`@DistributeLock` 声明式并发控制**：Redisson + AOP，支持 SpEL 动态 Key 与超时自动续期；切片/向量化场景 `waitTime = 0` 直接失败，防止同一文档重复处理。
- **三级缓存**：HashMap → Redis（30 秒 TTL）→ MySQL 回源，父分段回溯场景把数据库压力降低一个量级，空值缓存防击穿。
- **`JsonUtil.fixJson()` 7 步修复管道**：从 Markdown 代码块剥离、引号/尾逗号修复到最终包装兜底，兜住所有 LLM 结构化输出环节的非法 JSON。

设计原则全表（笔记原文）：事件驱动优于直接调用、最终一致性、流式优先、声明式并发控制、本地推理优先、虚拟线程优先、容错优先、分布式 ID 全链路、权限内建。

答题建议：每条亮点用"痛点 → 方案 → 原则"一句话收口，例如"切片语义截断 → 父子分段回溯补全 → 为 LLM 提供完整上下文窗口"。

**验证**：脱稿讲 3 条亮点各不超过 30 秒，每条能落到一条设计原则，并指出对应源码位置（rag/、document/、infra/）。

**追问**：
1. 三级缓存 L2 为什么只设 30 秒 TTL？——父分段回溯是短时高频读，TTL 限制了数据不一致窗口；30 秒已能把库压力降一个量级（设计建议）。
2. 为什么大量用虚拟线程而不是线程池？——设计原则"虚拟线程优先"：LLM 辅助调用（标题生成、改写回写）不占平台线程、不阻塞 SSE 主流程。
