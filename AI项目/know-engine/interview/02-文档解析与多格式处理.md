## Q1: 项目为什么选 MinerU 做文档解析？它有哪两种接入方式？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：MinerU 负责把 PDF 等文档解析成 Markdown（附带 JSON 和图片），是离线入库流程中"解析成 Markdown"这一步的核心工具；接入方式分官方 API 服务和自建服务两种，按数据量、速度要求和数据隐私来选。

| 方式 | 适用场景 |
|:---|:---|
| **官方 API 服务** | 小团队、要处理的 PDF 不多、对处理速度要求不高；个人实验也建议用这种 |
| **自建服务** | 任务量大、对速度有要求；文档含隐私数据或公司内部数据、不想暴露的场景 |

API 方式需要在 MinerU 官网的 token 页面申请 token（需官方审批，审批较快），每个用户每天可解析 10000 份文件、可优先解析 2000 页文档，一般够用。

**验证**：不查资料说出两种方式各自的适用条件，以及 API 方式的每日额度数字。

**追问**：官方 API 对待解析文件有什么前置要求？文件必须放在公网可访问的地址（如 OSS 或有公网域名的 MinIO），接口通过 URL 拉取文件。

## Q2: 描述 MinerU 官方 API 解析一份 PDF 的完整流程？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：申请 token → POST 创建解析任务拿到 task_id → GET 轮询任务状态 → 完成后从 full_zip_url 下载压缩包解压。

1. **创建任务**：`POST https://mineru.net/api/v4/extract/task`，Header 带 `Authorization: Bearer <token>`，请求体传文件 url 和 `model_version`（笔记示例用 `vlm`），响应返回 task_id。
2. **轮询状态**：`GET .../extract/task/{task_id}`，任务状态有 `done`（完成）、`pending`（排队中）、`running`（正在解析）、`failed`（解析失败）、`converting`（格式转换中）。
3. **获取结果**：state 为 done 时，响应里的 `full_zip_url` 指向一个压缩包；下载解压后包含原始 PDF、解析后的 JSON、Markdown，以及 images 目录下的图片。
4. 除了单文件解析，API 还提供批量接口，可批量提交解析任务和批量查看解析结果。

**验证**：按顺序默写三个接口动作，说出五种任务状态和压缩包内的内容构成。

**追问**：API 是同步返回解析结果吗？不是，它是异步任务模式——创建任务后拿 task_id 轮询，完成后才给压缩包地址。

## Q3: 自建 MinerU 有哪些部署要点？后端引擎怎么选？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：装 core 不装 all、版本要 3.0 以上、按有无 GPU 选后端引擎，国内网络记得指定 modelscope 模型源。

- **环境要求**：Python 3.10-3.13，至少 16GB 内存（32GB 建议），20GB 磁盘空间。推荐用 uv 安装：`uv venv` 后 `uv pip install "mineru[core]"`。core 是核心依赖，包含除 `vllm`/`lmdeploy` 外的所有功能模块，不要像官网那样装 `mineru[all]`；vllm/lmdeploy 是 VLM（Vision Language Model）推理加速模块，需要 Volta 及以后架构、8G 及以上显存的显卡。安装慢可配置国内镜像源（如阿里云的 `UV_INDEX_URL`）。
- **版本**：需要 3.0 以上的版本，否则无法处理 doc、docx 等类型文件。
- **命令行使用**：有 GPU 默认使用 `hybrid-auto-engine` 后端；纯 CPU 环境加 `-b pipeline`。首次运行会下载依赖模型；国内网络建议加 `--source modelscope`，否则默认拉 huggingface 模型可能长时间卡住。

| 后端引擎 | 是否需要 GPU | 最低显存 | 适用场景 |
|:---|:---|:---|:---|
| `pipeline` | 否 | 无 | 纯 CPU 环境 |
| `vlm` | 是（Volta 架构+） | 10GB | 最高精度 |
| `hybrid` | 是（Volta 架构+） | 8GB | 多语言 OCR（光学字符识别）+ 高精度 |
| `*-auto-engine` | 可选 | 3GB | 自动选择最佳引擎 |

- **常用参数**：`-p` 输入文件或目录、`-o` 输出目录、`-b` 后端引擎、`-m` 解析方式（auto/txt/ocr）、`-l` 语言（提升 OCR 效果）、`-d` 推理设备（cpu/cuda/npu/mps）、`-f`/`-t` 是否启用公式/表格解析（默认 true）、`--source` 模型源。

**验证**：能默写安装命令并解释为什么不装 `[all]`；给一台纯 CPU 服务器写出完整解析命令。

**追问**：没有 GPU 的服务器用哪个后端？pipeline，它是唯一不需要 GPU 的引擎。

## Q4: 一份文档上传后，系统如何记录并流转它的状态？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：用 knowledge_document、knowledge_segment 两张表加状态机驱动整条异步链路，上传、解析、分块、向量化每个阶段落一个状态。

- **knowledge_document（文档表）**：记录 doc_title、upload_user、doc_url（MinIO 原文件地址）、converted_doc_url（解析后文档地址）、status、accessible_by（按角色控制可见范围）。
- **状态流转**：`INIT → UPLOADED → CONVERTED → CHUNKED → VECTOR_STORED`；不需要进向量库的数据（如父子分段中的父分段、需要通过数据查询而不是文档搜索的数据）走另一条链，最后落 `STORED`（存关系型数据库）。实际代码中转换过程还有 `CONVERTING` 过渡状态。
- **knowledge_segment（片段表）**：chunk_id（向量化存储关联）、text、document_id、chunk_order（文档内排序）、embedding_id（Elasticsearch 中的向量 ID）、status（INIT/VECTOR_STORED）、metadata（含 parent_chunk_id、brother_chunk_id 等关联信息）、skip_embedding（是否跳过嵌入）；文档与片段一对多。
- **上传接口**：接收 file、uploadUser、accessibleBy 三个参数。先上传 MinIO、保存文档记录置 UPLOADED；再判断是否 PDF——先按后缀名判断（`.pdf`），再用 Apache Tika 检测文件内容 MIME 是否为 application/pdf；是 PDF 则异步触发转换处理（转换失败不影响上传结果，仅记录日志），非 PDF 直接置 CONVERTED 并把上传地址写入 convertedDocUrl。

**验证**：白板画出两条状态流转链并说明 STORED 分支针对哪类数据；说出 PDF 判断的"后缀 + Tika 内容检测"双重手段。

**追问**：为什么解析失败不让上传接口失败？文件已落 MinIO、记录已建，转换属于后续阶段可以重试，让用户重复上传没有意义。

## Q5: Java 侧是如何调用 MinerU 的？中途踩过什么性能坑？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：MinerU 自带 FastAPI 服务，Java 通过 HTTP multipart 调用同步接口 `POST /file_parse`；性能坑出在用 RestTemplate 接收返回内容时转换过慢，换成 Apache HttpClient 后明显改善。

- **启动服务**：如需 modelscope 模型先 `export MINERU_MODEL_SOURCE=modelscope`，然后 `mineru-api --host 0.0.0.0 --port 8000`，浏览器访问 `/docs` 查看接口文档。`/file_parse` 是同步解析接口，files 参数支持 PDF 和部分图片格式（如 jpg、png），不支持 Office 文件。
- **Java 调用**：用 Apache HttpClient 5 构造 multipart 请求，关键参数：`files`（二进制流）、`backend=pipeline`、`response_format_zip=false`、`return_images=false`、`return_model_output=false`、`return_middle_json=false`。
- **处理流程**：状态先置 CONVERTING → 文件名拼接 hashCode 避免中文乱码 → 调解析接口 → 从返回 JSON 取 `results.{文件名}.md_content` → Markdown 上传 MinIO 的 converted/ 目录 → 状态置 CONVERTED 并记录 convertedDocUrl；失败回滚为 UPLOADED。
- **性能坑定位**：MinerU 端已正常返回，但 Java 一直拿不到结果；排查发现慢在用 `ResponseEntity<String>` 接收原始数据、把返回内容转成字符串的环节，改用 Apache HttpClient 改造后快了很多。
- **细节**：解析完成后 MinerU 会打印本地输出目录，但可能找不到——它有后台线程自动删除本地文件。控制台进度条含义可挑重点讲：Layout Predict（版面布局预测）、MFD/MFR（公式检测/识别，输出 LaTeX 等格式）、Table-wired/wireless（有线表/无线表预测）、OCR-det/rec（文本检测/识别）。

**验证**：能说出 multipart 关键参数、结果 JSON 的取值路径，以及 RestTemplate 问题的现象与定位过程。

**追问**：为什么传给 MinerU 的文件名要拼接 hashCode？避免中文文件名乱码，同时该名称作为 results 里的 key 用来取 md_content。

## Q6: 项目中多种文档格式分别是怎么处理的？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：PDF/Word 统一走 MinerU 转 Markdown，Excel/CSV 走专门的表格解析器，Markdown/TXT 直接读内容，各格式差异主要在图片处理和分段方式上。

| 格式 | 处理方式 |
|:---|:---|
| PDF | MinerU 解析成 Markdown + 图片 |
| Word（doc/docx） | MinerU 旧版本（如 2.7.6）不支持，调用报 `HTTP 400 Unsupported file type: docx`；升级到 3.0 以后即支持，用法与 PDF 完全一致：转 zip、解压上传处理 |
| Excel / CSV | 参考 RAGFlow 实现 ExcelSplitter，键值对/HTML 表格双模式（见 Q8） |
| Markdown | 分段上不需要特别处理，但图片要处理：用视觉 LLM 生成图片描述并替换原 alt 文本 |
| TXT | 与 Markdown 一样的纯文本处理，只不过不太适合做标题分段 |

Markdown 处理（MarkdownProcessServiceImpl）要点：正则 `!\[(.*?)\]\(([^)]+)\)` 匹配图片标签，逐张调用视觉模型生成描述；描述为空或生成异常时保留原 alt 文本并告警；描述去除换行保证 Markdown 标签单行；处理后上传 MinIO 置 CONVERTED，失败回滚 UPLOADED。此类输入的图片地址通常已是公网可访问 URL（如 MinerU 输出的 cdn 地址）。

**验证**：对每种格式说出入口组件、是否依赖 MinerU、分段上的特殊点。

**追问**：Markdown 本身就是解析目标格式，还需要处理什么？主要是图片描述增强——把 alt 替换成视觉模型生成的描述，让图片内容可检索。

> 来源：[[AI项目/know-engine/23.项目中多种格式的文档处理？]]、[[AI项目/know-engine/11.解决MinerU解析无法获取图片的问题]]

## Q7: MinerU 解析后只拿到 Markdown，图片全丢了，怎么解决？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：调用 `/file_parse` 时加 `response_format_zip=true` 和 `return_images=true`，改拿 ZIP 压缩包而不是纯 JSON；Java 侧解压后把 Markdown 和图片分别上传 MinIO，再把 md 里的相对图片地址替换成 MinIO URL，并用视觉模型生成图片描述。

- **获取 ZIP**：两个关键参数缺一不可；Java 用 HttpClient 5 发请求，`EntityUtils.toByteArray(responseEntity)` 把响应读成 byte[]（HttpClient 5 支持流式下载大文件）。解压后是一个 md 文件加一个图片文件夹。
- **ZIP 的两种用法**：① 直接把 zip 上传 MinIO，后面用的时候再处理；② 下载解压，把 PDF、图片分别上传 MinIO。项目选方案 ②，理由有三：职责上解压属于文档处理阶段，放到分段阶段再做下载解压不合适；图片后面还要用（用户提问时可以把图片返回给用户查看），先传 zip、后期图片再传一次就要保存两份，浪费资源；md 中的图片本来就要做特殊处理——相对地址要替换成网络地址用户才能看到、要生成描述信息图片才能被检索，不如在这个环节一起做完。
- **处理主流程**（processDocumentToMarkdownFromZip）：调接口拿 ZIP → 保存 ZIP 到本地磁盘 → 解压 → 上传 md 和图片到 MinIO → 替换 md 中的图片地址 → 调 LLM 生成图片描述并更新 md → 保存 md 的 MinIO 地址到 convertedUrl → 异步清理本地临时文件。
- **图片标签处理**（processMarkdownImages）：正则匹配 `![alt](path)`，按文件名从 imageUrlMap 找 MinIO URL（找不到保持原样并告警），完成两步替换：`![](images/xxx.jpg)` → `![](http://minio地址/xxx.jpg)`，再把 alt 替换成图片描述。
- **描述生成**：用 LangChain4J 的 OpenAiChatModel 指定 `qwen3-vl-plus`（能理解图片的视觉模型），UserMessage 中同时传 TextContent 提示词（描述场景、对象、布局、颜色、文字信息，直接输出纯文本）和 ImageContent(imageUrl)；ImageContent 还支持 base64、Image 对象等构造方式。注意：用外部模型时图片 URL 必须公网可访问，否则模型需要能与 MinIO 内网通信。

**验证**：能说出两个关键请求参数、选"解压分别上传"的三个理由、图片标签的两步替换；能解释描述生成为什么选 VL 模型而不是纯文本模型。

**追问**：图片描述生成失败怎么办？Markdown 处理分支的既有实现是保留原 alt 文本并告警，不让单张图片失败阻塞整个文档；MinerU 流程可沿用同样策略（设计建议）。

## Q8: Excel 文件怎么处理？为什么不直接丢给 MinerU？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：MinerU 的解析接口不支持 Office 文件；市面"LibreOffice 先转 PDF、再用 MinerU 识别表格区域"的方案（如 RAG-Anything）属于多此一举——Excel 本身就是标准表结构，应按查询目标二选一：入关系型数据库做 SQL 查询，或参考 RAGFlow 转成键值对文本/HTML 分块进向量库。

- **两条路线**：① Excel 是结构化数据，更适合解析后建表写入关系型数据库，用户咨询时用 text2sql 生成 SQL 去查询（百炼的数据查询类型知识库就是这个思路，项目实现类为 ExcelProcessServiceImpl）；② 走向量库则参考 RAGFlow 的 RAGFlowExcelParser。
- **RAGFlow 模式一（默认，键值对文本）**：以表头行做 key，把每行数据拼成"表头：值; 表头：值"的语义化文本，sheet 名不含 "sheet" 时在行尾追加 "——sheet名"。每行都是一个独立语义单元，天然适合作为一个 chunk，检索时直接匹配整行内容即可。
- **模式二（html4excel=true，HTML 表格）**：整表转 HTML 后按 chunk_rows（默认 256 行）分块，且每个分块都会包含表头。必须分块的原因：HTML 是一个完整结构，上千行的表格会让单块超出 LLM 的上下文限制、检索时噪声太多导致匹配精度下降、存储和传输效率低。
- **Java 版 ExcelSplitter 实现要点**：用 EasyExcel 读取且必须 `headRowNumber(0)`，否则第一行被默认当表头、不会通过 ReadListener 回调返回；通过文件头魔数检测类型（`PK\x03\x04` ZIP 头 → xlsx，`D0 CF 11 E0` OLE 头 → xls，含逗号和换行 → CSV）；CSV 做 BOM 编码检测（UTF-8/UTF-16BE/UTF-16LE，默认 UTF-8）；解析后清洗非法控制字符（保留换行符和制表符）；HTML 模式按字符数分块（默认 500），装块时保证同一行不会被拆到不同分块，每个分块都带上表头。

**验证**：能画出 Excel 的两条处理路径；解释 HTML 模式为什么每个分块都要重复表头；说出不设 headRowNumber(0) 会丢什么数据。

**追问**：键值对模式和 HTML 模式各适合什么场景？键值对模式每行独立成块，适合按行语义检索（笔记口径）；HTML 模式保留表格结构、每块带表头，更适合表格类问题，代价是块更大、需控制分块大小（通用补充）。

## Q9: 表格或图片被拆分到多个分块怎么办？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：PDF/Word 统一转成 Markdown 再分段；对 Markdown 采用"标题分段 + 父子分段"组合方案，先靠标题边界保证图表不跨块，超长时靠父分段兜底。

- **危害**：表格被切分到不同分块后，后面的分段会丢失表头信息，既影响检索效果，也影响输出结果——分块里的表格是不完整的，但用户期望拿到一个完整的表格；图片被切开是同类问题。
- **标题分段**：基于 Markdown 标题做分段，同一个标题下的内容会落在同一个分段（没有超过 chunkSize 的情况下）。因为图片和表格不可能跨标题，所以标题分段能保障它们在正常情况下不会被分到不同分段。
- **父子分段兜底**：当同一标题下的内容太长、超过 chunkSize 需要二次切分时，采用父子分段——父分段保留完整内容（含完整图片、表格），子分段保留切分后的部分内容；向量检索时用子分段检索，检索命中后、调用 LLM 之前找到对应的父分段，把父分段（包含完整图片、表格）的内容交给 LLM。

**验证**：先讲清"丢表头"的两层危害，再按"正常情况靠标题分段、超长靠父子分段"的顺序讲方案，并说清父子分段介入的时机（检索后、生成前）。

**追问**：只靠标题分段为什么不够？超长标题段仍要二次切分，切开就会破坏表格图片，只有"子分段检索、父分段生成"能保住完整结构。

## Q10: MinerU 部署和运行你踩过哪些坑？分别怎么解决？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：坑集中在模型源、并发模型、标题层级、Python 版本和系统依赖几类，逐个现象对应原因和处理方式。

| 现象 | 原因 | 处理 |
|:---|:---|:---|
| 长时间卡住不动 | 默认使用 huggingface 的模型，网络可能无法访问 | 加 `--source modelscope` 改用 modelscope 模型源；或先把模型下载到本地再运行 |
| 批量任务"卡住"或"只跑一部分就停" | pipeline 后端（2.x）不支持真正的并发，多个批量任务被自动排队、串行执行 | 用多进程部署（启动多个 MinerU 实例，各自独立处理一个批量任务）；多线程/多协程并发调 OCR/Layout 易引发 GPU 资源冲突或模型线程不安全 |
| 单任务解析慢 | 版本与依赖不匹配 | 升级到 2.1.2 及以上并确保 PyTorch 与 CUDA 匹配（CUDA 11.8 推荐 torch 2.6.0）；环境变量 `MINERU_MIN_BATCH_INFERENCE_SIZE` 可调批量推理 batch size，但只影响单任务性能 |
| Markdown 全是一级标题、无多级层级 | 标题分级依赖"LLM 辅助标题优化"（llm_aided_title），需配置 API Key 并联网，没有内置的版式/字体规则可推断层级 | 在配置 `llm_aided_config` 下启用 `title_aided`；否则只能手动后处理 Markdown 或自定义规则分级（作者认为为此引入 LLM 依赖没什么必要） |
| Python 版本不支持 | 仅支持 3.10-3.13；旧虚拟环境可能还用着升级前的版本 | `uv venv --python python3.11` 重建虚拟环境 |
| 安装报错 | 各类系统依赖缺失（示例缺 pkg-config、ffmpeg） | 逐个按报错解决，如 `brew install pkg-config ffmpeg` |
| 运行报错找不到 libGL.so.1 | opencv-python 依赖系统图形库（OpenGL），极简安装的系统缺共享库 | `yum install -y mesa-libGL libglvnd-glx libSM libXext libXrender` |
| FontBBox 警告连续刷屏 | PDF 字体描述信息不完整（如 Notion 导出的 PDF 触发一百多次） | 只是警告，不影响 MinerU 正常运行和解析结果，可忽略 |

**验证**：遇到"卡住"先确认是不是在拉模型（换 modelscope 源），再确认后端的并发模型；安装/运行报错按缺失的库或头文件定位系统依赖。

**追问**：升级 MinerU 版本能解决并发卡住问题吗？不能根治——单实例本质仍是串行队列，真并发要靠多进程/多实例分批，升级版本和对齐依赖只提升单任务性能。
