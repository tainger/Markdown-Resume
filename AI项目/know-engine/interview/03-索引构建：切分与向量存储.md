## Q1: 文档切分在索引构建流程中处于什么位置？项目中切分一个文档的完整流程是什么？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：切分是把 MinerU 转换出的 Markdown 文档变成一段段 chunk 的环节，处于"文档转换完成（CONVERTED）"与"向量存储"之间，产物落在 KnowledgeSegment 表，文档状态推进为 CHUNKED。

流程（对应 `/split/{documentId}` 接口）：

1. 查询 `KnowledgeDocument`，校验文档存在且 `convertedDocUrl` 非空；若状态已是 CHUNKED，直接返回已切分分段数量（统计 `skipEmbedding=0` 的分段）；状态不是 CONVERTED 则抛异常拒绝切分。
2. 从 MinIO 下载转换后的 Markdown 内容。
3. 按接口传入的 splitType 通过 `DocumentSplitterFactory` 创建分段器（标题切分用自研父子分段器 `MarkdownHeaderParentTextSplitter`），chunkSize、overlap 由 `/split/{documentId}` 接口请求参数传入（如 1000/100；SMART 模式下 overlap 自动取 chunkSize 的 10%），切分得到 `TextSegment` 列表。
4. 逐段转成 `KnowledgeSegment` 保存：text、metadata 中的 chunkId、metadata JSON、documentId、documentVersion、chunkOrder（记录顺序，方便后台像智能体平台一样做分段预览）、status=STORED、skipEmbedding。
5. `saveBatch` 批量保存分段，并把文档状态更新为 CHUNKED。

**验证**：调用切分接口后查 knowledge_segment 表，确认按 document_id 能查到分段、chunkOrder 连续、status=STORED；对同一文档重复调用接口，应直接返回分段数量而不重复切分。

**追问**：切分接口为什么要校验文档状态？——防止对未转换完成的文档切分，同时保证幂等，避免重复切分产生重复分段。

源码校核：笔记中「固定 `MarkdownHeaderParentTextSplitter(1000, 100)`、分段初始状态 status=INIT」在源码中实际为「分段器由 `DocumentSplitterFactory` 按接口入参创建（chunkSize/overlap 来自请求参数），分段初始状态为 `SegmentStatus.STORED`，该枚举仅有 STORED、VECTOR_STORED 两个值」（见 DocumentProcessServiceImpl.split、SegmentStatus）。

## Q2: chunkSize 和 overlap 设置成多少比较合适？过大或过小有什么问题？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：没有绝对的"黄金标准"，核心思想是**从通用推荐值出发，根据文档类型和语言特性调整，并通过实验验证**（类似线程池核心线程数的设定）。注意项目中 chunkSize/overlap 的单位是**字符数**，不是 token 数。

从 token 视角看，chunk_size 建议从 512 或 1024 token 起步（部分模型上限是 512 token，如 bge-small-zh；百炼的 text-embedding-v3/v4 上限是 8192 token）。一个 token 约等于 1.5-2 个汉字、3-4 个英文字符，所以纯中文文档 chunkSize 可设 500-1000 字符，英文文档可设 2000-3000 字符；overlap 按 chunkSize 的 10%-20% 取。

极端值的问题：

- chunkSize 过小（<300 字符）：语义碎片化，丢失关键上下文；父子分片能缓解，但可能带来上下文过长的问题。
- chunkSize 过大（>1024 字符）：包含过多无关信息，稀释核心语义，降低检索精度，还增加大模型的上下文负担和成本。
- overlap 为 0：极易在切分边界丢失信息，相邻块语义断裂。

按文档类型微调：

| 文档类型 | chunk_size（字符） | overlap（字符） | 核心考量 |
|:---|:---|:---|:---|
| 纯文本/文章 | 256-512 | 32-64 | 保持段落连贯，避免信息碎片化 |
| 技术文档/代码 | 384-512 | 64 | 确保函数、类或代码块完整，避免被截断 |
| 法律/合同文件 | 320-512 | 48-64 | 保持条款和推理上下文；中文法律条文 320 左右可能更佳 |
| FAQ/知识库 | 300-600 | 30-60 | 每块聚焦一个独立的问答对或事实 |
| 长文本/论文 | 512-1024 | 100-200 | 需要更大上下文理解复杂论证与证据链 |

**验证**：对照项目配置确认单位是字符；用自己的文档跑一次切分，统计分段数与被二次拆分的分段数（方法见 Q8），再准备一批标注问题做 A/B 对比（如 chunk_size [256, 512, 768] × overlap [10%, 20%]）。

**追问**：直接抄别人的"最佳值"行吗？——不行，参数必须结合文档类型、嵌入模型 token 上限和自己的实验结果确定。

## Q3: 为什么选择基于 Markdown 标题切分？MinerU 把标题都解析成一级标题有什么影响？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：知识库文档主体是 Markdown，按标题切分能利用文档自然结构保留语义边界；MinerU 默认把所有标题解析成一级标题，实测对检索影响不大，可按需升级处理。

一级标题带来的影响：

1. 没有标题层级关系，就没办法做"分块合并"——合并分块需要标题层级信息，只有一级标题做不了。
2. 切出来可能出现"只有标题、没有正文"的分段，这种分段没什么用，工程上可以过滤掉。

处理方式：

- 如果标题真的很重要、重要到影响检索，可以在转换时指定 `llm_aided_title`，让 MinerU 基于大模型做多级标题识别；但实测影响并不大。
- 原因：一般标题内容和正文内容是相关联的，只要有关联，语义相似度就能比较好地检索。如果效果不好，再上其他优化手段，比如重写、多路检索、重排序。

**验证**：检查转换后的 Markdown 标题层级是否全为一级标题；查 knowledge_segment 中是否存在只有标题的空分段，评估其对召回的实际干扰再决定是否启用 llm_aided_title。

**追问**：只有一级标题时父子关系失效怎么办？——做不了分块合并，只能过滤空段、依赖标题与正文的相关性检索，效果不佳时再靠重写、多路检索、重排序弥补。

## Q4: 项目如何接入 ElasticSearch 做向量存储？需要哪些依赖和核心类？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：选 ES 当向量数据库是为了后续基于 ES 做混合检索；接入依赖官方适配模块 `langchain4j-elasticsearch`，核心是 ElasticsearchEmbeddingStore + OpenAiEmbeddingModel 两个 Bean。

1. 引入依赖 `dev.langchain4j:langchain4j-elasticsearch:1.11.0-beta19`。该模块主要提供两个类：
   - **ElasticsearchEmbeddingStore**：`EmbeddingStore` 接口实现，用 ES 存储和检索嵌入向量；
   - **ElasticsearchContentRetriever**：`ContentRetriever` 接口实现，基于向量相似度搜索检索相关文档。
2. 在 `ElasticSearchConfiguration` 中定义 Bean：
   - `RestClient`（`destroyMethod = "close"`，按配置的 host 用 `HttpHost.create` 构建）；
   - `ElasticsearchEmbeddingStore`：`builder().restClient(restClient).indexName("know-engine-vector").build()`；
   - `OpenAiEmbeddingModel`：配置 modelName、dimensions、baseUrl、apiKey，以及 `maxSegmentsPerBatch(9)`。
3. 配置项通过 `ElasticSearchProperties`（prefix 为 `elasticsearch`）读取：host、baseUrl、modelName、apiKey、dimensions。项目示例为 dashscope 兼容模式 + text-embedding-v4 + 1536 维。
4. 之后即可把向量化后的 chunk 存入 ES，也能用 metadata filter（如 `metadataKey("version").isEqualTo("1")`）做带过滤的相似度检索。

**验证**：启动应用确认 RestClient、ElasticsearchEmbeddingStore、OpenAiEmbeddingModel 三个 Bean 正常装配；调一次 embed + add，用 `GET /{index}/_count` 或 `_search` 确认数据写入 ES。

**追问**：为什么选 ES 而不是专用向量库？——项目后续要做混合检索，复用 ES 可以把关键词检索和向量检索放在同一套存储与运维体系里。

## Q5: ES 向量索引的 mapping 里有哪些字段？vector 字段的关键参数怎么理解？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：索引有三个字段 metadata、text、vector；核心是 vector 的 dense_vector 配置——1536 维、cosine 相似度、int8_hnsw 索引。

- **vector（向量字段，最关键）**：`type=dense_vector`；`dims=1536`（与配置的向量维度一致）；`similarity=cosine`（余弦相似度）；`index=true`。`index_options` 指定索引算法：
  - `type=int8_hnsw`：HNSW 近似搜索 + int8 量化。量化可以显著减少内存占用并提高搜索速度，同时保持较高的精度；
  - `m=16`：HNSW 图中每个节点的邻居数量；
  - `ef_construction=100`：添加一个节点时查找的最相邻 doc 构建邻居，默认为 100。
- **text（文本字段）**：`type=text` 并带 `keyword` 子字段，既支持全文检索（分词），也支持精确匹配（如排序、聚合）。
- **metadata（元数据字段）**：对象类型，如 `version` 字段记录数据版本信息。

mapping 可通过 `GET /know-engine/_mapping` 查看。

**验证**：执行 `GET http://host:9200/{index}/_mapping`，核对 `vector.dims` 是否与配置的 dimensions 一致、`similarity` 与 `index_options` 是否符合预期。

**追问**：int8 量化有什么取舍？——以少量精度损失换取内存占用降低和搜索速度提升，属于近似检索方案的通用取舍（通用补充）。

源码校核：笔记示例中索引名 know-engine（`GET /know-engine/_mapping`）在源码中实际为常量 `INDEX_NAME = "know-engine-vector"`（见 ElasticSearchConfiguration）；mapping 本体在源码仓库中没有定义文件，是运行时在 ES 侧创建的（dims=1536 与 application.yml 的 `elasticsearch.dimensions` 一致）。

## Q6: 向量维度如何设置？项目里为什么配 1536？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：维度不是可随意调整的参数，而是由所选 Embedding 模型直接决定，必须与模型输出维度完全一致；不匹配会导致向量无法正确存储和检索，整个系统无法工作。

- 每个模型输出固定长度向量：如 OpenAI 的 text-embedding-ada-002 是 1536 维，BAAI/bge-small-zh-v1.5 是 384 维。创建向量库索引时必须把这个固定维度作为参数传入。
- 很多模型支持多种维度（如 text-embedding-v4 支持多档维度），此时按场景选择：
  - **1024（默认）**：性能与成本的最佳平衡点，适合绝大多数语义检索任务；
  - **1536 / 2048**：追求极致精度，保留最丰富的语义信息，但存储和计算成本最高；
  - **768 及以下**：资源受限场景，显著降低开销，但会损失部分语义信息。
- 项目先设 1536，后面会做评测，在检索效果（精度）与系统成本（性能）之间找平衡点：召回效果较好但性能较差 → 考虑降低维度；性能较好但召回效果很差 → 考虑提升维度。

**验证**：调用 embedding 接口查看返回向量长度是否等于配置的 dimensions；故意把配置维度改错再写 ES，应报维度不匹配错误，反向验证"必须一致"这一原则。

**追问**：维度越高检索一定越准吗？——不一定，更高维度只是保留更丰富语义信息的潜力，同时抬高存储和计算成本，最终以评测结果为准。

## Q7: 向量存储（embeddingAndStore）的流程是什么？如何避免重复向量化？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：分页扫描待嵌入的分段，批量 embedAll → 批量 addAll 到 ES → 回填 embeddingId 并更新状态；靠文档状态与分段状态双重条件实现幂等。

流程：

1. **前置校验**：文档不存在返回 false；状态已是 VECTOR_STORED 直接返回 true，避免重复处理。
2. **分页扫描**：查询该文档版本下 status=STORED、embeddingId 为空、skipEmbedding=0 的分段，每页 100 条，防止一次性加载过多数据导致内存溢出。
3. **循环处理**：每页把 KnowledgeSegment 转成 TextSegment（携带 metadata）→ `openAiEmbeddingModel.embedAll` 批量获取嵌入向量 → `elasticsearchEmbeddingStore.addAll` 批量存储并返回 embeddingId 列表 → 遍历回填 embeddingId、状态置为 VECTOR_STORED → 翻页继续，直到处理完所有符合条件的切片。
4. **收尾**：把文档版本状态更新为 VECTOR_STORED（KnowledgeDocument 状态由 CHUNKED 事件监听器同步推进），标志整个向量化流程结束。

源码现状：`embedAndStore` 已加 `@DistributeLock` 分布式锁（scene=document-embed），且向量化前会 double-check 统计仍为 STORED 的分段数、不为 0 时打日志返回 false——笔记写作时留的三个 todo（增加分布式锁、补充状态校验、最后检查所有 segment 都已转换为 vector）在当前源码中已落地，不再是已知边界。

**验证**：对同一文档连续调两次 embeddingAndStore，第二次应立即返回 true 且不再调用嵌入；查库确认 skipEmbedding=0 的分段全部 status=VECTOR_STORED 且 embeddingId 非空。

**追问**：skipEmbedding=1 的分段会怎样？——向量存储的查询条件限定了 skipEmbedding=0，这些分段不会做嵌入，也不计入已向量化分段数。

源码校核：笔记中「查询条件 status=INIT」在源码中实际为「status=STORED」（KnowledgeDocumentServiceImpl.activateVersion）；笔记所述三个 todo 在源码中已实现为 `@DistributeLock` 分布式锁 + double-check 状态校验（DocumentProcessServiceImpl.embedAndStore）。

## Q8: 项目里 chunkSize=1000 是怎么定下来的？如何低成本验证切分参数？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：先按 Markdown 标题分段并统计总段数，再以"被二次拆分的父分段数量"作为最差召回损失的代理指标，配合单元测试离线验证，最后用 A/B 测试校准。

项目做法：

1. 先按 markdown 标题分段（按段落、特殊符号也可以），跑一下这个 markdown 一共被分成多少段——示例文档是 1894 段。
2. 假设最差情况：一个分段被 chunkSize 拆分后会导致无法召回。若要求召回率 95%，即最多可接受 100 个分段无法召回。
3. 调整 chunkSize，统计有多少 chunk 的 metadata 带 parentChunkId——带这个标记说明它是被二次拆分过的，属于最差情况可能无法召回的部分。
4. 示例文档在 chunkSize=1000 时约 90 个被二次切分的父分段，满足 ≤100 的目标，所以选了 1000。
5. 数据通过运行单元测试获得（如 `MarkdownHeaderParentTextSplitterTest`），不需要实际上线跑。

后续 A/B 测试：准备 50-100 个有代表性的真实用户问题，标注每个问题正确答案所在的文档片段；用测试集对比不同参数组合（如 chunk_size [256, 512, 768] × overlap [10%, 20%]）的检索准确率；分析未命中的查询——是相关片段被切碎了，还是块太大导致关键信息被稀释。

**验证**：跑 `MarkdownHeaderParentTextSplitterTest` 统计带 parentChunkId 的分段数量；换 2-3 组 chunkSize 重复统计，确认都落在可接受阈值内，再用标注测试集复检实际召回率。

**追问**：为什么用"被二次拆分的父分段数"做代理指标？——被 chunkSize 再切分的分段最差情况下可能无法召回，其数量是召回损失的保守上界，可以离线快速算出，不必上线试错。

## Q9: 分段批量插入 MySQL 时遇到过什么性能问题？怎么优化？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：MyBatis-Plus 的 `saveBatch` 看似批量，底层 `executeBatch` 实际是 for 循环逐条调用 save，每条都是独立的 INSERT，分段很多时性能极差；优化手段是 JDBC URL 加 `rewriteBatchedStatements=true`，并按需调整 batchSize。

问题细节：

- `IService#saveBatch` 底层调用 `executeBatch`，在循环中逐条消费，每调一次 save 就向数据库发送一条独立的 `INSERT INTO table VALUES (...)` 语句。
- 事务在所有 insert 都执行完后一次性提交：执行过程中数据库里看不到数据；其中任何一条 SQL 失败，整个事务会回滚。

优化手段：

1. 在 JDBC URL 中添加 `rewriteBatchedStatements=true`（如 `jdbc:mysql://localhost:3306/know-engine?useUnicode=true&characterEncoding=UTF-8&rewriteBatchedStatements=true`）。该参数会指示 MySQL 驱动把多条独立的 INSERT 合并成一条高效的 `INSERT INTO table VALUES (...), (...), ...` 语句，降低数据库的解析和执行开销。
2. `saveBatch` 允许指定 batchSize 参数（默认 1000），根据实际数据量和服务器内存调整此值以获得最佳性能。

**验证**：用同一份大 Markdown 文档（如 840.8 KB 的测试手册）分别在带/不带 rewriteBatchedStatements 的 URL 下跑切分入库，对比耗时；开启 SQL 日志或 MySQL general log，确认 INSERT 是逐条发送还是合并成了多 VALUES 语句。

**追问**：合并成一条大 INSERT 有没有隐患？——单条语句变大，需要结合 max_allowed_packet 与 batchSize 权衡，不能无限调大（通用补充）。

> 来源：[20.分段批量插入性能优化](../20.分段批量插入性能优化.md)

## Q10: 为什么 chunkId 要用雪花算法生成？ID 的结构和实现要点是什么？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：项目需要为文档分段记录 chunkId，尤其 parentChunkId 必须保证唯一，否则会路由错误；雪花算法（Snowflake）能在分布式环境下生成趋势递增的 64 位唯一长整型，所以选它。

**ID 结构（64 位 long）**：

- 1 位符号位（始终为 0）
- 41 位时间戳（毫秒级，可使用约 69 年），EPOCH 取 2024-01-01 00:00:00（1704038400000L）
- 10 位工作机器 ID（0-1023）
- 12 位序列号（毫秒内自增，每毫秒可生成 4096 个 ID）

组装方式：`((timestamp - EPOCH) << TIMESTAMP_SHIFT) | (workerId << WORKER_ID_SHIFT) | sequence`。

**实现要点**（项目中的 SnowflakeIdGenerator）：

- 双重校验锁单例（volatile + synchronized）；workerId 默认取进程 ID 的低 10 位（pid & 1023），取不到时兜底为 1。
- `nextId()` 用 synchronized 保证线程安全；同一毫秒内序列号 +1 并与 4095 掩码，溢出则自旋阻塞到下一毫秒；新的毫秒序列号重置为 0。
- **时钟回拨处理**：若当前时间戳小于上次生成的时间戳，直接抛出异常拒绝生成（"Clock moved backwards"），避免产生重复 ID。

**验证**：并发调用 nextId() 把结果收集进 Set 验证无重复；把系统时钟回拨后调用，应抛出时钟回拨异常；切分入库后检查 knowledge_segment 的 chunkId 及 metadata 中的 parentChunkId 均无冲突。

**追问**：时钟回拨为什么危险？——时间戳回退后，同一 workerId 可能再次生成相同的（时间戳， 序列号）组合导致 ID 重复；本项目选择直接抛异常快速失败。
