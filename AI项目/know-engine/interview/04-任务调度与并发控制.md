## Q1: 文档预处理全流程分哪几个阶段？为什么用事件驱动串联？

**难度**: ⭐（基础记忆）

**参考答案**:

**先说结论**：全流程分为文档上传、文档分段、文档向量保存三个阶段，各阶段之间基于事件驱动串联；事件驱动处理失败时，引入定时任务兜底。

展开：

- 文档上传阶段完成解析转换（调 MinerU）并落库，状态流转为 CONVERTED；
- 文档分段阶段把转换后的文档切分为 segment，完成后状态为 CHUNKED；
- 文档向量保存阶段对 segment 做向量嵌入并存储。
- 多个流程之间基于事件驱动，是为了更好地解耦、提升吞吐量：上一阶段完成后发布事件（如分段完成发布 DocumentChunkedEvent），由监听器异步触发下一阶段，阶段之间不直接同步调用。
- 事件驱动可能失败，因此用 XXL-JOB 定时任务扫描中间状态做兜底补偿。

**验证**：对照笔记 17 的三张阶段流程图，确认"上传→分段→向量保存"的事件衔接关系；在工程中搜索 @EventListener，核对监听的事件类型与阶段一一对应。

**追问**：事件驱动失败了流程会断吗？会停在中间状态，由 XXL-JOB 补偿任务扫描该状态重新触发，见 Q3。

源码校核：笔记中"各阶段之间基于事件驱动串联"在源码中实际为仅"分段完成→向量化"由 DocumentChunkedEvent 事件串联；DocumentConvertedEvent 的发布方法 publishConvertedEvent 已标记 @Deprecated，分段改为用户在前端手动触发。

> 源码：`document/event/DocumentEventListener.java`、`document/service/impl/DocumentProcessServiceImpl.java`、`document/job/DocumentCompensationJob.java`

## Q2: DocumentEventListener 是如何监听分段事件并触发向量化的？

**难度**: ⭐⭐（原理与比较）

**参考答案**:

**先说结论**：在 DocumentEventListener 中用 @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) 接收 DocumentChunkedEvent，方法上加 @Async("eventListenerExecutor") 异步执行，内部按事件的 documentVersionId 查出版本记录后调用 documentProcessService.embedAndStore(documentVersion) 完成向量嵌入和保存，成功后同步 KnowledgeDocument 状态为 VECTOR_STORED。

要点：

- 事件对象 DocumentChunkedEvent 携带 documentId、documentVersionId 和 segmentCount，日志中打印 documentId 与 segmentCount，便于追踪；
- @Async 指定独立线程池 eventListenerExecutor，监听逻辑异步执行，不阻塞事件发布方；
- 用 @TransactionalEventListener(AFTER_COMMIT) 而非 @EventListener，是为了保证发布方 split() 的事务提交后监听器才执行，否则异步线程会读到未提交的旧状态（CONVERTED）导致 embedAndStore 提前返回 false；
- 方法体内 try-catch 全量捕获异常只记 error 日志，不让异常向外传播——异步任务里的异常发布方本来就感知不到，失败后残留的中间状态由兜底任务处理；
- 成功、失败路径都有带 documentId 的日志，方便排查。

**验证**：在工程中定位 DocumentEventListener#onDocumentChunked，确认注解组合为 @Async("eventListenerExecutor") + @TransactionalEventListener(phase = AFTER_COMMIT)、参数为 DocumentChunkedEvent，与笔记 17 的代码片段逐行核对。

**追问**：监听器抛异常会影响发布方吗？不会，异步执行加 try-catch，异常只落日志，残留状态交给补偿任务兜底。

源码校核：笔记中的 "@EventListener + embeddingAndStore(documentId)" 在源码中实际为 "@TransactionalEventListener(phase = AFTER_COMMIT) + embedAndStore(KnowledgeDocumentVersion)"，事件对象还多携带一个 documentVersionId。

> 来源：[[AI项目/know-engine/17.文档预处理阶段全流程讲解（事件驱动）]]。
> 源码：`document/event/DocumentEventListener.java`、`document/event/DocumentChunkedEvent.java`、`config/AsyncConfig.java`

## Q3: XXL-JOB 向量化补偿任务是如何设计的？

**难度**: ⭐⭐（原理与比较）

**参考答案**:

**先说结论**：向量化补偿任务（documentEmbeddingCompensation）扫描 CHUNKED 状态的文档版本记录，对仍是当前版本的记录重新触发 embedAndStore（未向量化 segment 的 double check 内置于 embedAndStore 中），定位是事件驱动失败后的兜底。

执行步骤：

1. 查询 KnowledgeDocumentVersion 表中 status = CHUNKED 的版本记录列表；
2. 对每条版本记录查出对应 KnowledgeDocument，若该版本不是文档的 currentVersionId 则记 warn 并跳过（只补偿当前版本）；
3. 调 documentProcessService.embedAndStore(documentVersion) 执行向量化补偿：内部先校验版本状态（已是 VECTOR_STORED 直接返回成功、非 CHUNKED 返回 false），再 double check 未向量化分段数（status = STORED、skip_embedding = 0 的 segment 计数），为 0 才算成功；
4. 单个文档失败只记 failCount，不影响其他文档；
5. 任务级 try-catch 兜住整体异常，结束后输出"成功/失败"统计日志。

注意：源码中保留了 MAX_RETRY_COUNT = 5 常量，但当前向量化补偿任务并未实现重试次数控制（重试逻辑只存在于已注释掉的分段补偿代码中），存在无限重试的隐患，见 Q4。

另外，文档分段补偿任务（documentSplitCompensation）已注释移除、不再使用，因为分段操作改为由用户在页面上发起（需要用户选择分段方式）。

**验证**：在工程中搜索 @XxlJob("documentEmbeddingCompensation")，对照源码核对查询条件（KnowledgeDocumentVersion 的 status = CHUNKED + 当前版本匹配）与 embedAndStore 内部的 segment double check（STORED + skip_embedding=0）；确认分段补偿任务已整体注释。

**追问**：XXL-JOB 部署要注意什么？初始化 doc/db/tables_xxl_job.sql 建库表，修改 admin 的 application.properties 数据库等配置（1核2G 即可），启动后访问 :8080/xxl-job-admin（默认 admin/123456）；注意 logback.xml 里配置的日志路径必须存在，否则启动报 FileNotFoundException，创建目录即可。

源码校核：笔记中"扫描文档 + 预查 INIT/skipEmbedding=0/embeddingId 为 null 的 segment + 从 extension 解析重试次数 + 成功后更新重试次数"在源码中实际为"扫描 KnowledgeDocumentVersion 的 CHUNKED 记录并校验当前版本，直接调 embedAndStore，segment double check（STORED + skip_embedding=0）内置在 embedAndStore 中，无重试次数控制"；cron 不在代码中，在 xxl-job-admin 控制台配置，工程内只有 config/XxlJobConfig.java 的执行器配置。

> 来源：[[AI项目/know-engine/18.XXL-JOB部署及用任务驱动文档处理流程]]。
> 源码：`document/job/DocumentCompensationJob.java`、`document/service/impl/DocumentProcessServiceImpl.java`、`config/XxlJobConfig.java`

## Q4: 向量化补偿任务当前实现有什么隐患？如何改进？

**难度**: ⭐⭐⭐（边界与排查）

**参考答案**:

**先说结论**：当前查询只有 status = CHUNKED 一个条件、没有时间过滤，会把正在被正常流程处理的文档也捞走；应加 updateTime <= now - 10 分钟的过滤，把补偿任务收窄为"兜底"，而不是抢正常流程的活。

三个问题：

| 问题 | 说明 |
|:---|:---|
| 并发冲突 | 正常流程正在向量化的文档也会被捞走，和正常流程重复执行 |
| 重复空跑 | 每次定时触发都全量扫描同一批文档，即使上次刚补偿成功 |
| 资源浪费 | 正常流程没出问题的文档也被扫描、判断，白白消耗数据库查询和 API 调用 |

改进建议（建议补丁，当前项目代码尚未实现）：

```java
docQueryWrapper.eq(KnowledgeDocumentVersion::getStatus, DocumentStatus.CHUNKED);
docQueryWrapper.le(KnowledgeDocumentVersion::getUpdatedAt,
    LocalDateTime.now().minusMinutes(10));
```

- `status = CHUNKED` 只看切分完还没向量化的；`updatedAt <= now - 10min`（实体字段在 BaseEntity 中，已存在可直接用）排除"刚切分完正在被正常流程处理"的文档；
- 重试次数控制当前尚未落地：源码只保留了 MAX_RETRY_COUNT = 5 常量但向量化补偿中未使用，建议一并补上 `retryCount < MAX_RETRY_COUNT`，防止无限重试；
- 阈值 10 分钟应根据正常向量化流程的平均耗时调整：大文档向量化要 5 分钟就设 10 分钟，小文档 1 分钟搞定就设 5 分钟。

代码中还有其他待改进点（todo）：扫表注意索引问题；segment 计数 double check 已内置在 embedAndStore 中，无需再在任务里预查；retryCount 字段尚未落地（源码中没有从 extension 解析的逻辑，仅遗留未使用的 MAX_RETRY_COUNT 常量），实际项目应在实体和数据库中显式加 retryCount 字段。

**验证**：查看 documentEmbeddingCompensation 当前的查询条件，确认只有 status 单条件；据此核对"并发冲突/重复空跑/资源浪费"三类风险是否成立，并检查时间过滤补丁是否已落地、阈值是否匹配实际向量化耗时。

**追问**：时间阈值设太小会怎样？会把正常流程仍在处理的文档捞走重新补偿，重新引入并发冲突，所以阈值要略大于正常向量化耗时。

源码校核：笔记中补丁用的 KnowledgeDocument::getUpdateTime 在源码中实际为 KnowledgeDocumentVersion::getUpdatedAt（查询对象是版本表，时间字段在 BaseEntity 中）；"retryCount < MAX_RETRY_COUNT 已有"在源码中实际未实现（常量保留但未使用）。

> 来源：[[AI项目/know-engine/18.XXL-JOB部署及用任务驱动文档处理流程]]。
> 源码：`document/job/DocumentCompensationJob.java`、`document/entity/BaseEntity.java`

## Q5: 事件驱动 + 定时任务兜底为什么会引发并发问题？为什么用分布式锁（悲观锁）而不是乐观锁？

**难度**: ⭐⭐⭐（工程设计）

**参考答案**:

**先说结论**：事件驱动和 XXL-JOB 兜底在极端情况下会并发处理同一份文档；又因为文档处理是"先干活、最后才写库"，锁必须加在干活之前，所以选择悲观锁（分布式锁）而不是乐观锁。

并发从哪来：为了解耦和提升吞吐量，文档的转换、切分、嵌入和存储用事件驱动串联；事件驱动可能失败，所以引入 XXL-JOB 定时任务兜底；极端情况下定时任务和 listener 就会并发。即使换成 MQ 也一样，因为 MQ 也可能重投。本质上这是个低并发场景，分布式锁已足够。

为什么悲观锁：

- 悲观锁的特点是**先加锁、后干活**；乐观锁是**先干活、最后再加锁**（写回时校验）；
- 文档处理很多时候先做转换（调 MinerU）、分段、嵌入等操作，最后才操作数据库；
- 如果最后才加乐观锁，前面这些耗费资源的操作在锁生效前就已经并发发生了，资源白白浪费；所以悲观锁更合适。

**验证**：复述并发产生的两个前提（事件可能失败、兜底任务与 listener 的时间窗口重叠）；对照笔记 19 开头关于悲观/乐观锁的引文检查选型理由链；确认工程中锁注解加在 upload、split、embedAndStore 方法入口而非写库处。

**追问**：换成 MQ 能绕开这个问题吗？不能，MQ 存在消息重投，同样会出现并发处理，仍需分布式锁兜住。

## Q6: 自定义 @DistributeLock 注解有哪些参数？锁的 key 如何构成？

**难度**: ⭐⭐（原理与比较）

**参考答案**:

**先说结论**：注解基于 Redisson 的 lock 和 tryLock 封装，核心参数是 scene（锁场景）和 key/keyExpression（二选一），最终锁 key 为 scene + "#" + key。

| 参数 | 说明 |
|:---|:---|
| scene | 锁的场景标识，参与拼接锁 key |
| key | 固定值作为锁 key，默认 NONE_KEY |
| keyExpression | SpEL 表达式（如 #id、#insertResult.id）；key 未指定时生效，二者只能取一个 |
| expireTime | 超时时间（毫秒），默认不设置，此时会自动续期 |
| waitTime | 加锁等待时长（毫秒），默认一直等待直到获取到锁 |

实现要点（DistributeLockAspect，@Aspect + @Around("@annotation(...)")）：

- keyExpression 通过 SpelExpressionParser 解析，用 StandardReflectionParameterNameDiscoverer 获取运行时参数名并绑定到 EvaluationContext，再求值得到 key；
- waitTime 为默认值时走 rLock.lock()（可带 expireTime）；否则走 tryLock(waitTime[, expireTime])；
- 获取锁失败抛 DistributeLockException；finally 中先 isHeldByCurrentThread() 判断再 unlock，避免误解锁；
- 典型用法：@DistributeLock(keyExpression = "#payCreateRequest.bizNo", scene = "GENERATE_PAY_URL")，在方法入口自动加锁、结束后自动解锁。

**验证**：打开 infra.lock 包下的 DistributeLock 注解与 DistributeLockAspect 切面，核对参数默认值和 lockKey 拼接格式（scene + "#" + key）；写一个带 keyExpression 的方法验证 SpEL 能正确取到参数值。

**追问**：key 和 keyExpression 都不设会怎样？切面直接抛 DistributeLockException("no lock key found...")。锁依赖的 Redis 怎么部署？Docker 单实例、开启 AOF 持久化并设置 requirepass（Apple Silicon 上用 redis:alpine 镜像避免拉到 AMD64 架构）。

> 来源：[[AI项目/know-engine/19.引入分布式锁解决文档处理的并发问题]]。
> 源码：`infra/lock/DistributeLock.java`、`infra/lock/DistributeLockAspect.java`、`infra/lock/DistributeLockConstant.java`

## Q7: 文档处理在哪三处加锁、分别锁什么？@Order(Integer.MIN_VALUE) 解决什么问题？

**难度**: ⭐⭐⭐（工程设计）

**参考答案**:

**先说结论**：三处加锁——upload 按 uploadUser 锁，限制同一用户同时上传多份文件；split 按 docId 锁、embedAndStore 按 versionId 锁，分别保证同一份文档的分段、同一个版本的向量化不同时执行；三者都设 waitTime = 0，抢锁失败立即返回不阻塞。@Order(Integer.MIN_VALUE) 让锁切面最早执行（处于最外层），避免"事务未提交但锁已释放"导致并发问题依旧发生。

| 方法 | 注解配置 | 锁粒度 |
|:---|:---|:---|
| upload | scene="document-upload"，keyExpression="#uploadUser"，waitTime=0 | 用户 |
| split（@Transactional） | scene="document-split"，keyExpression="#document.docId"，waitTime=0 | 文档 |
| embedAndStore（即监听器调用的向量化入库方法） | scene="document-embed"，keyExpression="#documentVersion.versionId"，waitTime=0 | 文档版本 |

split 和 embedAndStore 的 scene 与 key 均不同（document-split#docId vs document-embed#versionId），二者之间不互斥；互斥只发生在"同 key 的同类操作"之间——并发 listener 与补偿任务调的是同一个 embedAndStore，锁正是兜住这种并发。另外源码中 uploadNewVersion（document-upload / #uploadUser）与 switchVersion（document-upload / #docId）也加了锁，主流程答题讲清 upload/split/embedAndStore 三处即可。

@Order 的原理：AOP 切面 order 值越小优先级越高、在拦截器链中越靠外。锁切面排到最外层后，执行顺序变成"加锁 → 开启事务 → 业务 → 提交事务 → 解锁"，解锁时事务已提交；如果锁切面落在事务切面内层，方法结束时会先释放锁、事务还没提交，另一个等待锁的线程立刻拿到锁进入流程，读到的仍是未提交/旧数据，等于锁白加。waitTime = 0 则保证失败方不排队等待——文档处理是长任务，等待无意义，直接失败交给兜底。

**验证**：在 DocumentProcessServiceImpl 核对三个方法的注解参数；确认 DistributeLockAspect 上有 @Order(Integer.MIN_VALUE)；用两个线程并发调同一 docId 的 split，观察其中一个立即抛 DistributeLockException 且不阻塞。

**追问**：waitTime=0 抢锁失败后任务丢了吗？没有，当前请求快速失败，残留状态仍由 XXL-JOB 补偿任务兜底。

源码校核：笔记中 embedAndStore 的 "scene=document-split、keyExpression=#document.docId" 在源码中实际为 "scene=document-embed、keyExpression=#documentVersion.versionId"，split 与 embedAndStore 并不共用锁、二者不互斥。

> 来源：[[AI项目/know-engine/19.引入分布式锁解决文档处理的并发问题]]。
> 源码：`document/service/impl/DocumentProcessServiceImpl.java`、`infra/lock/DistributeLockAspect.java`

## Q8: 新会话标题为什么用虚拟线程 + flash 模型异步生成？整体方案是什么？

**难度**: ⭐⭐（原理与比较）

**参考答案**:

**先说结论**：标题生成依赖 LLM 调用，耗时 500ms-2s，为不阻塞主对话流程采用异步生成；该任务是纯 IO 密集的 fire-and-forget，所以选虚拟线程 + 轻量 flash 模型。

同步流程（主线程）：

1. 生成临时标题：截取用户首句前 20 字符，保证用户立即看到会话；
2. 创建会话（DB 写入）；
3. Thread.ofVirtual().name("title-summary-" + conversationId).start(...) 触发异步标题生成，不等待；
4. 立即返回，继续保存消息、启动 SSE 流式对话。

异步流程（虚拟线程）：

- 单独构建轻量级 OpenAiChatModel：modelName=qwen3.5-flash、temperature=0.7、customParameters 设 enable_thinking=false（关闭思考链，减少 token 消耗、加速响应）；独立实例不影响主对话模型配置；
- 用 AiServices 创建 TitleSummaryService 代理：@SystemMessage 约束"不超过 20 字、不加引号、直接输出标题内容"，@UserMessage 用 {{it}} 占位符传入用户问题；
- 调 generateTitle 生成标题后 updateTitle 写库；
- catch 任意异常只记 warn，保留临时标题，失败不影响主流程（容错）。

为什么虚拟线程而不是线程池：

- 任务特征：完整链路是发 HTTP 请求 → 等模型响应（500ms-2s）→ 写一次 DB，99% 时间在等网络、CPU 空闲；平台线程等待期间仍占约 1MB 栈内存，虚拟线程等待时让出载体线程，几乎不占资源；
- 并发量不可预测：高峰期可能瞬间 100+ 个新会话，线程池要么配 100 线程（约 100MB 栈内存）要么排队，虚拟线程只占几 MB；
- 代码简洁：fire-and-forget 一行 Thread.start() 即可，无需定义池、配置参数、管理生命周期。

边界与备用方案（设计建议）：虚拟线程没有池大小概念、无法限流，若下游 LLM API 有 QPS 限制需加 Semaphore（tryAcquire 超时则跳过、finally release），或切回线程池（core=4、max=20、queue=50、CallerRunsPolicy、keepAlive=60s——标题生成是非关键路径 IO 任务，参数偏保守，宁可同步降级也不丢任务）。选 qwen3.5-flash 因为标题生成是简单任务、响应极快（<1s）、成本低。

**验证**：在会话创建代码确认临时标题截取前 20 字符、虚拟线程名前缀为 title-summary-；检查 TitleSummaryService 的 @SystemMessage/@UserMessage 与模型参数（qwen3.5-flash、enable_thinking=false、temperature=0.7）；人为让模型调用失败，确认会话标题回退为临时标题且主流程不受影响。

**追问**：为什么关闭 enable_thinking？减少思考链的 token 消耗和响应时间，标题生成不需要复杂推理。什么情况下放弃虚拟线程？下游 LLM API 加了 QPS 限制需要限流时，用虚拟线程 + Semaphore 或切回线程池。
