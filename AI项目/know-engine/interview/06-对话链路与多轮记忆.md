## Q1: know-engine 的对话模块表结构是怎么设计的？

**难度**: ⭐ 基础

**参考答案**:

**先说结论**：Chat 模块围绕「会话表 chat_conversation + 消息表 chat_message」两张表管理对话全生命周期，消息表用 JSON 字段完整记录改写内容、RAG 引用与扩展元数据，支撑问题改写、成本分析与答案可解释性。

**ChatConversation（会话，表 chat_conversation）**：`id`（自增主键）、`conversationId`（会话唯一标识）、`userId`（关联用户）、`title`（默认"新对话"）、`createTime`/`updateTime`、`status`（枚举 ChatConversationStatus：ACTIVE 活跃 / ARCHIVED 已归档 / DELETED 已删除）。设计要点：

1. **软删除机制**：删除只把 status 置为 DELETED，不做物理删除；
2. **时间追踪**：记录创建/更新时间，便于排序和审计。

**ChatMessage（消息，表 chat_message）**：`messageId`、`conversationId`（外键关联会话）、`type`（ChatMessageType：USER / ASSISTANT）、`content`（原始内容）、`transformContent`（用户问题改写结果，服务 RAG 优化）、`tokenCount`（AI 回复的 Token 统计，便于成本分析）、`modelName`（使用的 LLM）、`ragReferences`（List\<RagReference\>，JSON 存储）、`createTime`、`metadata`（扩展元数据，JSON 存储）。

**RagReference（RAG 引用内部类）**：记录 AI 回复引用的知识库来源——`documentId`、`url`、`documentTitle`、`chunkId`、`chunkContent`、`similarityScore`（相似度分数）、`rerankScore`（重排序分数）、`retrievalSource`（检索来源枚举：VECTOR / KEYWORD / HYBRID / RERANK）、`metadata`。完整记录引用可实现答案可解释性。

JSON 字段（`ragReferences`、`metadata`）通过 MyBatis-Plus 的 `JacksonTypeHandler` 做序列化。

**验证**：脱稿默写两张表的核心字段；能分别说清 `transformContent`（存问题改写结果）、`tokenCount`（成本分析）、`ragReferences`（引用溯源）三个字段各自的用途。

**追问**：删除会话是物理删除吗？——不是，仅把 status 置为 DELETED 做软删除，保留数据。

## Q2: 意图识别有哪些实现方案？项目中如何演进与选型？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：从最简单的提示词工程起步，按「意图数量、表达复杂度、延迟容忍度、是否多轮」逐级演进：提示词工程 → 提示词+槽位 → 意图/槽位分离 → 前置 RAG 召回，多轮场景再叠加历史上下文与问题澄清。

1. **提示词工程**：角色定义 + few-shot + 结构化输出，无需额外算法即可快速具备意图识别能力，适合意图数量少（如 10 个以内）的场景。缺点：意图增多时每个意图都要写 few-shot、CoT，提示词迅速膨胀且识别容易失败；对方言、口语化等特异表达不稳定，出 Bad Case 只能反复改提示词，繁琐且效果难保证。
2. **提示词工程 + 槽位抽取**：在意图识别提示词里直接加关键信息提取（如"订机票"抽出发地/目的地/时间），后置处理更方便。缺点：意图和槽位多了要不断调整提示词，也会影响输出效果。
3. **意图、槽位分离（两个节点）**：意图识别节点只放所有意图的简要描述，快速判断类别；命中后路由到该意图专属的槽位抽取节点，只关注当前意图的槽位。优点：架构清晰、易维护（增改意图只动对应节点），职责单一、不受无关意图干扰。缺点：串联调用两次或多次 LLM，总响应时间变长。适合意图分支较多（如 10-20 个）、业务逻辑复杂、对延迟有一定容忍度的场景，如企业内部业务咨询系统。
4. **前置 RAG 召回**：为每个意图预先构建"意图泛化知识库"（标准问法、同义句、口语化、方言）；用户提问先与知识库做语义相似度检索，把最相似的问法作为 Few-shot 连同原始问题交给 LLM 辅助决策。优点：泛化能力可控——识别不了的表达直接加进知识库即可，无需反复调提示词，修复 Bad Case 快；且可选用性价比更高的小模型，成本与准确率更优。缺点：研发成本高（要单独搞一套 RAG）；主要基于单轮输入检索，不擅长结合历史上下文，多轮能力弱。适用于以单轮为主、大量特异表达的垂直领域（地铁公交查询、地域化客服系统）。
5. **多轮与澄清**：多轮需求（先说"我要打车"再补"去公司"）需要把历史对话、近期操作的文档/数据作为辅助信息输入模型；高阶方案会将意图识别与槽位抽取合并并升级为多轮 RAG 召回。当意图置信度不高或关键槽位缺失时，不猜测而是主动澄清——引导式提问让用户补充（如"安排下周的会议"反问"请问会议的主题和预计时长是？"）。

**验证**：能按"意图数量、表达复杂度、响应延迟容忍度、是否多轮"四个维度，把四个方案的适用场景各配一个例子，并说出每个方案至少一条缺点。

**追问**：泛化不好为什么不直接换更大参数的模型？——大模型泛化更强但成本和响应时长扛不住，笔记明确说这不是长久之计，所以用 RAG 前置召回替代。

## Q3: 项目中意图识别提示词是如何优化的？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：旧版提示词只有宽泛的角色定义和输出格式示例，实测经常识别错误；新版从角色定位、任务流程、CoT、易混淆辨析、Few-shot、输出规范六个维度系统性重写，Bad Case 明显减少。

**旧版的 5 个问题**：

1. 角色定义过于宽泛（"你是一个意图识别专家"），缺汽车领域针对性，模型用通用逻辑处理；
2. 缺乏结构化推理流程（CoT），没有具体步骤，模型推理随意，容易跳过关键辨析环节；
3. 易混淆场景辨析不足（维修 vs 技术咨询、售前 vs 优惠），经常识别错误；
4. 没有 shot 示例——只有输出格式示例，没有输入输出配对示例，模型不知道"好"的输出长什么样，容易格式混乱或推理不充分；
5. 输出格式不规范、要求宽松，可能输出 Markdown 代码块。

**新版的优化（对比维度）**：

| 对比维度 | 旧版 | 新版 |
|:---|:---|:---|
| 角色定位 | 模糊 | 资深汽车行业智能客服意图识别专家，能区分"技术咨询"与"服务需求" |
| 任务流程 | 简单描述 | 5 步明确任务：相关性判断 → CoT 推理 → 意图识别 → 实体提取 → 格式化输出 |
| CoT 思维链 | 无 | 强制显式推理，过程摘要写入 `reasoning` 字段 |
| 辨析指导 | 无 | 覆盖易混淆场景（"雨刮器怎么换"=技术指导，"雨刮器坏了去换"=售后维修等） |
| 字段定义 | 无 | 说明各字段类型与含义 |
| Few-Shot 示例 | 无 | 多组输入输出配对样本 |
| 输出规范 | 简单 | 详细可执行：仅输出一个标准 JSON，严禁 ```json 等 Markdown 标记 |
| 实体描述 | 简单 | 更详细（如"具体的故障现象描述"） |

**对比测评**：通过运行 `IntentRecognitionTest` 单测（数据集 `intent-test-dataset.json`）验证，典型修复的 Bad Case：「这车保修期多长？」旧版误判"售后维修与保养"、新版正确判"售前咨询与购买"；「价格能便宜点吗？」旧版"售前咨询与购买"、新版"汽车营销政策"；「车险怎么买比较划算？」新版"汽车营销政策"；「车是好车，就是售后服务有点慢」新版"其他"；「我的车」旧版判成与汽车无关（related=false）、新版"其他"。

**验证**：打开 `IntentRecognitionTest`，用 `intent-test-dataset.json` 分别跑新旧两版提示词，逐条对比 Bad Case 是否修复；能脱稿说出旧版 5 个问题。

**追问**：为什么加 `reasoning` 字段能提升准确率？——强制模型在输出结论前先做相关性判断、场景定位、易混淆辨析的显式推理（CoT），减少跳过辨析环节导致的误判。

## Q4: 如何解决模型 JSON 格式输出不稳定的问题？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：两层防御——第一层在提示词中给出具体的 JSON 结构；实测仍会失败（最典型的是输出里带 ```json 这样的 Markdown 代码块导致解析出错），所以再加一层代码级兜底：LLM 返回后先跑一个 JSON 修复工具再解析，思想参考 Python 的 `json_repair` 框架。

典型不稳定表现：缺少引号、逗号、括号不匹配、包含多余的解释性文字、输出被 Markdown 代码块包裹。

修复工具 `JsonUtil.fixJson` 的处理步骤：

1. **提取 JSON 内容**：用正则移除 ```json ... ``` 等 Markdown 代码块标记；
2. **移除前后非法字符**：截取第一个 `{`/`[` 到最后一个 `}`/`]` 之间的内容；
3. **修复引号问题**：中文引号转英文引号、单引号转双引号（JSON 标准要求双引号）；
4. **修复尾部逗号**：去掉 `,}` 与 `,]`；
5. **修复缺失引号**：给没有引号的键名补上引号；
6. **修复转义字符问题**：处理字符串中未转义的换行、回车、制表符；
7. **验证**：用 `objectMapper.readTree` 校验；修复后仍无效则兜底 `wrapAsSimpleJson`，把原始文本转义后包装成 `{"content":"..."}` 的简单 JSON 对象返回。

对外提供 `fixAndParse`：修复 + 解析二合一，解析失败时返回空 JsonNode 并记录日志，保证下游拿到的始终是可解析的 JSON。

**验证**：构造带 ```json 包裹、尾部逗号、无引号键名的模型输出，调用 `fixAndParse` 确认能正常解析；能脱稿说出 7 个修复步骤的顺序。

**追问**：修复后仍然无效怎么办？——`wrapAsSimpleJson` 做最后容错，把原文转义包装成 `{"content":"..."}`，避免直接抛异常打断流程。

## Q5: 单轮对话版本中，如何根据不同意图实现定制化提示词？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：链路是「意图识别结果 → 意图枚举 → 提示词文件（带缓存加载）→ ContentInjector 拼接」。非客服相关问题路由给通用 LLM 做通用回答；客服相关问题按意图定制——技术类问题专业性优先（严谨、术语准确），售前类问题热情度优先（亲切、激发购买兴趣）。

1. **提示词文件**：`resources/prompts/` 下按意图放置 6 个文件：`car-before-sales-query-prompt.txt`、`car-complaints-query-prompt.txt`、`car-maintenance-query-prompt.txt`、`car-marketing-query-prompt.txt`、`car-other-query-prompt.txt`、`car-tech-support-query-prompt.txt`。每份提示词都带角色定位（如售前=专业汽车销售顾问、技术支持=资深汽车技术工程师）与关键约束（严禁出现"根据参考资料"等字眼、不编造上下文不存在的事实）。
2. **意图枚举 KnowEngineIntent**：每个枚举项关联一个提示词文件名，并提供 `getIntent(IntentRecognitionResult)` 方法用 switch 把识别结果映射到枚举项（"售前咨询与购买"→CAR_BEFORE_SALES_QUERY……default→CAR_OTHER_QUERY）。
3. **PromptService**：用 `ConcurrentHashMap` 缓存 + `computeIfAbsent` 懒加载，首次从 `classpath:/prompts/` 读文件；指定意图的文件不存在时回退到默认提示词（CAR_OTHER_QUERY），默认文件也缺失才抛异常。
4. **拼接**：在意图识别之后调用 `getPrompt` 拿到提示词，交给 `DefaultContentInjector.builder().promptTemplate(new PromptTemplate(...))` 完成提示词与检索文档的拼接。

**关键约束**：默认提示词支持的占位符只有 `{{userMessage}}` 和 `{{contents}}`，自定义提示词也必须用这两个，不能换成其他的。

**版本性质**：这一版是把整个定制提示词（含占位符）当作用户提示词给 LLM 的，单轮对话没问题——多轮对话下的隐患见下一题。

**验证**：脱稿画出"意图 → 枚举项 → 文件名 → PromptService 缓存 → ContentInjector"链路；能解释为什么占位符不能自定义。

**追问**：提示词文件缺失怎么办？——PromptService 回退加载 CAR_OTHER_QUERY 的默认提示词；默认文件也缺失才抛"默认提示词文件缺失"异常。

源码校核：笔记中的枚举常量名 CAR_BEFORE_SALES_QUERY、CAR_OTHER_QUERY 等带 _QUERY 后缀，在当前源码中实际为 CAR_BEFORE_SALES、CAR_COMPLAINTS、CAR_MAINTENANCE、CAR_MARKETING、CAR_TECH_SUPPORT、CAR_OTHER（无 _QUERY 后缀，默认提示词对应 CAR_OTHER）。

## Q6: 多轮对话下，单轮版定制化提示词为什么会失效？如何改造？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：根因是 LangChain4j 在多轮对话中，如果本轮没有给 AiService 设置系统提示词，就会默认沿用上一轮的系统提示词；而项目中意图识别和 RAG 问答共享同一个 conversationId，历史记忆里混着意图识别的系统提示词，导致明明调用的是 RAG 检索和回答，返回的却是意图识别的结果。

**踩坑过程**：旧版实现把定制提示词当作用户提示词，构建 `knowEngineChatAiService` 时没有调用 `.systemMessage(...)`（被注释掉）。由于意图识别和 RAG 问答共享同一 conversationId，对话历史中包含了意图识别那一步的系统提示词（"你要帮我做意图识别XXXX"）；RAG 对话侧没设系统提示词，LangChain4j 就拿历史里的意图识别系统提示词来用，最终 RAG 问答返回意图识别结果。

**改造方案**：

1. 构建 AiService 时显式设置系统提示词：`String prompt = promptService.getPrompt(chatParam.intentRecognitionResult());` 然后 `.systemMessage(prompt)`；
2. 提示词同步改造：移除中间的 `{{userMessage}}`、`{{contents}}` 占位符，只保留系统级的人设与约束内容（角色定位 + 关键约束）；
3. 占位符替换交回默认实现——`DefaultContentInjector` 的默认模板 `DEFAULT_PROMPT_TEMPLATE`：`{{userMessage}}` + `Answer using the following information:` + `{{contents}}`。

**验证**：故意注释掉 `.systemMessage(prompt)` 后连续多轮对话，观察 RAG 问答是否退化为输出意图识别 JSON；恢复后再验证恢复正常。能说清"单轮为什么没事、多轮为什么出事"。

**追问**：为什么单轮版本没有这个问题？——单轮没有共享的上一轮系统提示词，用户提示词里自带完整指令；问题只会在"共享 conversationId 的多轮记忆 + 未设置系统提示词"同时出现时触发。

## Q7: DatabaseChatMemoryStore 如何设计 Redis+MySQL 两级记忆架构？为什么 updateMessages 只写 Redis？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：自定义 `DatabaseChatMemoryStore` 实现 LangChain4j 的 `ChatMemoryStore`，采用 Redis 缓存 + MySQL 持久化的两级架构，并做读写分离：读路径 getMessages 走「Redis → 未命中再 DB（只读）并回写 Redis」；写路径的最终持久化由业务层直接写 DB，`updateMessages` 只截断后写 Redis。

**核心设计**：常量包括 Redis key 前缀 `know-engine:chat-memory:`、`MAX_MESSAGES = 10`、缓存 TTL 1 小时。

- **getMessages（读）**：优先从 Redis 读（`ChatMessageDeserializer.messagesFromJson` 反序列化）；未命中则 `loadFromDatabase`——通过 `chatMessageService.getRecentMessages(conversationId, MAX_MESSAGES)` 取最近 10 条，过滤空消息（如预创建的 assistant 占位记录），USER → `UserMessage.from(content)`、ASSISTANT → `AiMessage.from(content)`，再回写 Redis。
- **updateMessages（写）**：截断保留最近 10 条（`trimMessages`）后写入 Redis，不直接写 DB。原因有二：①消息的最终持久化由业务层 `ChatMessageService.saveUserMessage()` 和 `updateContent()` 负责，这样可以控制在对话过程中更新记忆内容（比如引用的文档、改写后的问题等）；②LangChain4j 的 `updateMessages()` 在一次 LLM 调用中会被调用多次（加用户消息后一次、加 AI 回复后一次），每次都写 DB 会产生不必要的频繁 IO。
- **evictCache（失效）**：直接删除 Redis 中的会话 key，用于隔离意图识别等中间环节的记忆污染。
- **业务层写路径**（与流式保存配套）：对话开始时先 `saveUserMessage` + `saveAssistantMessage`（先建 Assistant 占位消息）；流式输出在 `doOnNext` 中累计 token，`doOnComplete` 时 `updateContent(assistantMessageId, 全量内容)` 落库（用户取消时 dispose 同步取消内部订阅）；引用文档通过 `chatMessageService.updateRagReferences(chatMessageId, ragReferences)` 更新。

**为什么必须实现 updateMessages**：LangChain4j 在运行时会调用这个方法把 systemPrompt 也放进 list——如果不实现，会导致 `@SystemPrompt` 注解失效。

**一次对话的生命周期**（两个 AiService——意图识别 + RAG 对话——共享同一个 DatabaseChatMemoryStore）：① saveUserMessage / saveAssistantMessage 写 DB → ② 意图识别 AiService：getMessages → Redis miss → 从 DB 加载 → add SystemMessage + UserMessage → 调 LLM → add AiMessage → updateMessages 把意图识别结果写入 Redis → ③ **evictCache 清 Redis**（隔离意图识别的 AI 响应，避免污染后续对话记忆）→ ④ RAG 对话：getMessages → Redis miss → 从 DB 加载干净历史 → 更新改写后的问题、检索文本到 DB 的 UserMessage → add SystemMessage + UserMessage + RAG 上下文 → 流式调 LLM → updateMessages 完整记忆写入 Redis → ⑤ doOnComplete → updateContent 把 AI 回复持久化到 DB。

**验证**：脱稿画出上面 5 步生命周期图，标注哪几步写 Redis、哪几步写 DB；能回答"为什么 updateMessages 只写 Redis 的两个原因"和"不实现 updateMessages 的后果"。

**追问**：从 DB 加载历史时为什么要过滤空消息？——对话开始会预创建 assistant 占位记录，content 为空，放进对话记忆会干扰 LLM 对上下文的理解。

## Q8: ChatMemoryStore 的 Redis 缓存为什么用 String 存 JSON，而不是 List 结构？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：`updateMessages(memoryId, List<ChatMessage>)` 的语义是"全量覆盖"——第二个参数是 LangChain4j 经过内存管理器（如 MessageWindowChatMemory）计算后、当前这一时刻应保留的所有有效消息的全集；Redis List 只能追加、不支持覆盖保存，用 String 存整个 JSON 一次 SET 就能语义对齐。

**窗口淘汰的例子**：假设窗口限制保留最近 3 条，Redis 里已有 `[消息A, 消息B, 消息C]`；用户发来消息 D 后，LangChain4j 在内存中先把 D 加进去变成 `[A, B, C, D]`，发现超出 3 条就自动淘汰最早的 A，此时调用 `updateMessages` 传给你的列表是 **[B, C, D]**——它的潜台词是"存储器，请把这个会话的状态**更新**为 [B, C, D]"。

**如果用 List 直接 RPUSH 追加**，又不先删旧数据，Redis 里会变成 `[A, B, C, B, C, D]`，产生重复脏数据。

要用 List 只有两种补救办法：一是先从 Redis 取出内容、去重后再保存；二是先整体删除 Redis 再更新（List 不支持覆盖保存）。两个方案都很复杂，还不如直接存一个 JSON 字符串（opsForValue）来得简单。

**验证**：能复述"窗口 3 条时 [A,B,C] 收到 D 后传参变成 [B,C,D]"的例子，并说清 RPUSH 会产生什么后果、为什么 String 一次 SET 就没这个问题。

**追问**：Redis List 为什么不能覆盖保存？——List 的写入语义是追加/按位置操作，没有按 key 整体覆盖的命令，只能删了再写或逐条处理，与 updateMessages 的全量覆盖语义不匹配。

## Q9: 问题重写如何支持多轮对话？

**难度**: ⭐⭐ 中级

**参考答案**:

**先说结论**：把历史对话通过 `{{chatMemory}}` 占位符注入改写提示词，让 LLM 结合上下文做指代消除与信息补全，把最新提问重组为独立完整的检索查询；不需要改写时直接输出原问题。

原有的基础改写策略（简洁改写、抽象概念改写、错别字改写等）只支持单轮，多轮对话场景下会失效——比如先问"我的车打不着火怎么回事"、下一轮才补充"我的车辆是：宝马 3系"，改写时必须结合历史对话才能把车型信息补全。为此在 `KnowEngineQueryTransformer` 实现中做两件事：

1. **改提示词**：在原有改写策略（简洁改写、抽象概念改写、错别字改写、车型信息提取等）基础上，新增第 5 条上下文融合策略——"结合历史对话和最新提问，识别出所有相关的细节、术语和上下文信息。最后，将这条提问重新组织成一个清晰、简洁且独立完整的格式，以便于进行信息检索"；并约定 5 种改写策略需逐一使用、最终给出一个统一的改写结果，直接输出改写后的结果、不需要输出思考过程及额外的多余内容，如果不需要改写则直接输出原问题。提示词新增两个占位符：`{{chatMemory}}`（历史对话内容）与 `{{query}}`（用户问题），并强调"非常重要的一点是：你只需要提供重新组织后的提问，不要包含任何其他内容！绝对不要在提问前添加任何多余的文字！"。
2. **改代码**：从 `query.metadata().chatMemory()` 取出 `List<ChatMessage>` 历史记忆，格式化后放进变量表——`variables.put("query", query.text())`、`variables.put("chatMemory", chatMemory)`，通过 `promptTemplate.apply(variables)` 生成 Prompt，再交给 `chatModel.chat(...)` 执行改写。

**验证**：能说出两个占位符的名字与来源（chatMemory 来自 `query.metadata().chatMemory()`）；设计一个两轮用例（先问故障、下一轮补车型）验证改写结果是否把车型信息补全。

**追问**：改写结果里混入了不相关内容怎么办？——提示词要求删除无关信息、确保查询简洁明了且独立完整，无需改写时直接输出原问题。

## Q10: 支持多轮对话后，问题重写踩了什么坑？为什么最终选择"二次删除 Redis"而不是换模型？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：坑是一次对话本应做两次 Redis 记忆删除，最初实现只删了第一次——意图识别的内容（结构化输出的 JSON 格式要求 + 意图识别结果）留在记忆里污染了问题重写；先尝试换模型但无法彻底解决，最终采用"二次删除 Redis"做上下文隔离。

**污染的表现**：问题重写时会从内存（Redis）取出对话记忆做指代消除和上下文补全，结果历史对话里混入了两类内容：①意图识别的系统提示词尾部要求"You must answer strictly in the following JSON format: {...IntentRecognitionResult...}"；②AI 的意图识别 JSON 输出。改写后的提示词把意图识别的格式要求和 JSON 结果全带进去了，导致默认使用的 LLM 改写结果完全错误——用户问"打不着火"，常被改写成"车辆信息查询"。

**LLM 对比（ChatModelBenchmarkTest / benchmarkDifferentModels）**：用污染后的提示词对多个模型做测试——

| 模型 | 表现 | 耗时（关闭思考） |
|:---|:---|:---|
| qwen-max-latest（默认使用） | 不稳定：两次回答一次"无法启动故障排查"、一次"车辆信息查询"，经常把意图识别成查车辆信息 | 2238 / 5691 |
| qwen3.6-max-preview | 仍是车辆信息类错误 | 3066 / 7847 |
| qwen3.6-flash | 直接输出了 JSON | 8322 / 1607 |
| qwen3-30b-a3b-instruct-2507 | 正确："车辆打不着火故障排查" | 470 / 1518 |
| qwen3.5-27b | 车辆信息类错误 | 1072 / 4318 |
| deepseek-r1-distill-qwen-7b / 32b | 输出 JSON / 不稳定 | 4619-8730 |

对效果最好的 `qwen3-30b-a3b-instruct-2507` 单独做 20 轮测试（benchmarkSameModelMultipleCalls）：**正确率 90%、平均耗时 1564ms、最小 437ms、最大 5375ms**。即使最好的模型也有 10% 概率出错，错误结果主要是输出了一个 JSON（像 deepseek-r1-distill-qwen-7b 那样，被历史里的 JSON 示例带偏）。

**为什么放弃换模型**：换参数量更大、更新的模型会更稳定，但耗时太长；qwen-max-latest 这类古早模型速度还行但输出不稳定——换模型无法彻底解决问题。

**最终方案**：采用二次删除 Redis——在意图识别之后、RAG 检索 + LLM 对话之前，先把 Redis 中的对话记忆删掉，这样后续读取记忆时从数据库读取，而数据库中的内容是干净的（没存意图识别的结果；就算存了也可以过滤）。这本质上是一种**多 agent 之间的上下文隔离**手段。

**验证**：跑 `ChatModelBenchmarkTest` 的 benchmarkDifferentModels，用污染提示词复现各模型差异；或临时注释掉意图识别后的 evictCache，观察问题重写是否退化为"车辆信息查询"。能脱稿说出"两次删除分别删在哪一步、各自防什么污染"。

**追问**：为什么最好的模型也会输出 JSON？——历史对话里混入了意图识别的 JSON 格式要求与 JSON 输出示例，诱导部分模型模仿该格式输出，所以治本要隔离上下文而不是换模型。

源码校核：笔记中"一次对话做两次 Redis 记忆删除（对话开始时一次 + 意图识别后一次）"，在当前源码中实际只有一处 evictCache 调用——位于 `ChatApplicationService.chat()` 内意图识别完成后、RAG 流程之前，即笔记所说的"第二次删除"；对话开始时的第一次删除在当前源码中已不存在。

## Q11: RAG 问题澄清的对话卡片是怎么实现的？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：当意图识别发现用户问题缺少必要信息（如车辆信息）时，不直接拒绝也不猜测，而是通过 SSE 消息约定前缀返回卡片数据，前端渲染成可选卡片，用户点选后携带实体重新走一遍完整对话流程。

**整体流程**：用户发问 → 意图识别 → 信息完备性检查 → 缺信息则返回卡片 → 前端渲染卡片 → 用户选择 → 携带选择重新提问。

**后端实现**：

1. **意图识别**：`IntentRecognitionService` 接口方法上通过 `@SystemMessage(fromResource = "prompts/intent-recognition-new-prompt.txt")` 挂系统提示词，AiService 实例在 `ChatApplicationService.init()` 中用 `AiServices.builder(...)` 编程式构建（并挂载基于 DatabaseChatMemoryStore 的 chatMemoryProvider），由 LLM 对用户问题做意图分类，输出结构化的 IntentRecognitionResult——`related`（是否与汽车领域相关）、`intent`（售前、售后、技术支持、营销等分类）、`entities`（从问题中提取的实体，如 car_id、car_model）。
2. **信息完备性判断**（核心逻辑在 `ChatApplicationService.ragChat()`）：
   - 场景 1：维保/技术支持（CAR_MAINTENANCE / CAR_TECH_SUPPORT）→ 需要 car_id；为 null 时查用户已添加的车辆（`myCarService.getCarByUserId(userId)`），无车辆则返回 `[WARN]:您还没有添加车辆信息，请先添加车辆信息`，有车辆则返回 `[CARD]:请先选择车辆` + `[CARD_CHOICE_MYCAR]:` + 车辆 JSON；
   - 场景 2：营销政策（CAR_MARKETING）→ 需要 car_model；为 null 时返回 `[CARD]:请先选择您要咨询的车辆` + `[CARD_CHOICE_CAR]:` + 车型 JSON；
   - 信息充足则走 `doChat` 进入正常 RAG 流程。
3. **SSE 消息前缀约定**：`[WARN]:`（警告提示）、`[CARD]:`（卡片提示文字）、`[CARD_CHOICE_MYCAR]:`（"我的车辆"选择卡片，JSON 数据）、`[CARD_CHOICE_CAR]:`（车型选择卡片，JSON 数据）、`[PROGRESS]:`（进度通知）、`[DONE]:`（流结束标记）。

**前端实现**：解析 SSE 流时按 `data:` 前缀匹配分发——`renderCardPrompt()` 渲染提示文字，`renderMyCarChoices()` 渲染用户已绑定车辆的卡片网格，`renderCarInfoChoices()` 渲染可选车型网格；卡片用 CSS Grid 布局（.card-choice-grid），每张卡片展示车辆图片、名称、车牌/颜色等信息。

**用户选择回调**：`handleMyCarSelect()` 选中自己的车辆后，自动填入"我的车辆是：xxx"并携带 myCarId、carId 重新发送；`handleCarInfoSelect()` 选中车型后填入"我想咨询的车辆是：xxx"并携带 carId 重新发送。重新走一遍完整对话流程后，意图识别会从用户消息中提取到 car_id/car_model 实体，完备性检查通过，进入正常 RAG 对话。

**验证**：脱稿说出 6 个 SSE 前缀的含义；完整描述一次"维保问题缺 car_id → 返回选车卡片 → 点选车辆 → 重新提问 → 进入 RAG"的闭环。

**追问**：为什么缺关键信息时不让 LLM 直接猜？——笔记的口径是"与其猜测，不如主动询问"：置信度不高或关键槽位缺失时用引导式提问让用户补充，避免答非所问。

源码校核：笔记中"信息完备性判断核心逻辑在 ChatApplicationService.chat()"在源码中实际位于 `ChatApplicationService.ragChat()`（由 chat() 调用）；笔记中"IntentRecognitionService 使用 @SystemMessage + @AiService 注解"在源码中实际为方法级 @SystemMessage 注解 + AiServices.builder 编程式构建，未使用 @AiService 注解。

## Q12: 如何接入登录并实现用户级对话隔离？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

**先说结论**：采用 **sa-token + Redis** 的双轨登录体系——网页端客户（手机号+密码）与钉钉员工（不通过网页登录，直接通过钉钉机器人提问、系统自动识别身份）用不同登录入口和不同的 loginId 标识隔离；Controller 不再接受前端传入的 userId，统一从 session 中读取，实现用户只能访问自己的对话数据。

**核心架构**：两套体系共享同一套认证服务接口（AuthController / AuthServiceImpl），底层由 sa-token（StpUtil）管理会话，Redis 存储 session 与 token 映射关系。

1. **依赖与配置**：`sa-token-spring-boot3-starter` + `sa-token-redis-jackson`（1.39.0，Jackson 序列化）+ `commons-pool2` 连接池；application.yml 中配置 token-name 为 satoken、有效期 30 天、`is-concurrent: true`（允许并发登录）、`is-share: true`（多人登录共用 token）、token 风格 uuid、同时从 cookie 和 header 读取 token。
2. **客户登录**：AuthServiceImpl.login 依次做参数校验 → 手机号查 UserInfo → 密码校验（当前明文比对，生产环境建议 BCrypt）→ 账号状态校验 → `StpUtil.login(userInfo.getId())`，loginId = user_info.id。
3. **员工登录**：loginId 使用 `staff_` 前缀 + 工号 empId（如 `staff_TEST001`），设备标识为 "staff"；钉钉员工不通过网页登录，直接通过钉钉机器人提问，系统自动识别身份。
4. **全局拦截**（SaTokenConfig）：对所有接口做登录校验，白名单为 `/auth/**`（认证接口）、`/dingtalk/**`（钉钉回调）、`/druid/**`（数据库监控）及静态资源；文档管理路由（`/api/document/**`、`/api/segment/**`）额外要求 loginId 以 `staff_` 开头，否则抛 NotLoginException。
5. **身份识别**：`getCurrentUserId()` 从 `StpUtil.getLoginIdAsString()` 取；`getCurrentUser()` 按 `staff_` 前缀判断身份、查询不同的数据表（员工表/客户表）；`isStaffLogin()` 判断是否员工登录。

**对话隔离的应用**：Controller 中不再接受前端传入的 userId——前端只传登录后保存的 token，服务端通过 token 去 session 中查已保存的用户 id。没登录的用户进来无法获取用户 id，也无法获取其他人的 id，更加安全。查询对话列表时做了权限隔离：`getConversationsByUserId(authService.getCurrentUserId())`，用户只能查到自己的对话列表。

**验证**：未登录状态直接调用对话接口确认被拦截；用 A 用户的 token 请求 B 用户的会话列表，验证拿不到数据；检查 `/api/document/**` 用客户身份访问是否被 staff_ 前缀校验拒绝。

**追问**：客户和员工在同一套体系里怎么区分？——靠 loginId 的 `staff_` 前缀识别员工身份：同一套认证服务接口，不同的登录入口与 loginId 标识做隔离。

源码校核：笔记中员工 loginId 为"staff_ 前缀 + id（如 staff_12345）"，在源码中实际为 staff_ 前缀 + 工号 empId（`StpUtil.login(STAFF_LOGIN_PREFIX + staffInfo.getEmpId(), "staff")`）。
