## Q1: 请完整讲述 know-engine 中一次用户提问的回答全流程

**难度**: ⭐

**参考答案**:

**先说结论**：入口是 `ChatController.send`，共四个阶段：会话管理 → 消息持久化 & 意图识别 → RAG 增强检索 → 流式生成回复。

1. **阶段一：会话管理**。接收 content（用户问题）、conversationId（可选），userId 从 sa-token session 获取（`authService.getCurrentUserId()`）；若 conversationId 为空则创建新会话，用用户问题前 20 字符作为临时标题同步写入数据库，再异步（虚拟线程）调用 LLM 生成摘要标题，完成后回写更新；已有 conversationId 则直接使用。
2. **阶段二：消息持久化 & 意图识别**。先分别保存用户消息与占位的 assistant 消息（`saveUserMessage` / `saveAssistantMessage`）；再调用 `IntentRecognitionService` 做意图识别（基于 LLM + 结构化输出），判断问题是否与汽车领域相关并提取实体（车型、订单号、故障描述等）；若 related=false 走 `CommonChatService` 通用对话分支直接返回流式结果，related=true 进入 RAG 增强检索分支。
3. **阶段三：RAG 增强检索**（`ChatApplicationService.chat`）：
   - **查询改写**（`KnowEngineQueryTransformer`）：用 LLM 做简洁改写、抽象改写、错别字纠正、车型标准化，返回改写后的单个 Query，并异步（虚拟线程）回写改写结果到数据库；
   - **查询路由**（`KnowEngineQueryRouter`）：用 LLM 判断走哪个数据源——relational_db → `SqlDatabaseContentRetriever`（关系库，Text2SQL）、graph_db → `Neo4jText2CypherRetriever`（图库，Text2Cypher）、knowledge_base → `ElasticsearchContentRetriever`（ES 向量检索 + 全文检索）；
   - **内容检索**：被路由到的 Retriever 执行检索，获取相关 Content 列表；
   - **内容聚合 + 重排序**（`KnowEngineReRankingContentAggregator`，外层依次包装 `KnowEngineHybridContentAggregator` 与 `ProgressAwareContentAggregator`）：用 BGE-RERANKER ONNX 模型重排序，选取第一个查询作为重排序参考；
   - **内容注入**（`DefaultContentInjector`）：根据意图识别结果选择对应 Prompt 模板，把检索内容注入 Prompt。
4. **阶段四：流式生成回复**。构建 `KnowEngineChatAiService`（含 ChatMemory，窗口 10 条），调用 `streamChat` 流式对话，返回 `Flux<String>` 给前端（SSE 流式推送）。

**验证**：对照笔记流程图自查四阶段顺序与每阶段关键类名（IntentRecognitionService、KnowEngineQueryTransformer、KnowEngineQueryRouter、KnowEngineReRankingContentAggregator、DefaultContentInjector、KnowEngineChatAiService），并确认分支分叉点在意图识别的 related 字段。

**追问**：非汽车相关问题怎么处理？意图识别 related=false，直接走 `CommonChatService` 通用对话分支流式返回，不进 RAG 链路。

源码校核：笔记中"接收前端传入的 userId"在源码中实际为从 sa-token session 获取；笔记中查询改写"返回改写查询 + 原始查询两个 Query"实际只返回改写后的单个 Query（返回两个 Query 的代码已被注释）；笔记中的 `ReRankingContentAggregator` 在源码中实际为 `KnowEngineReRankingContentAggregator`（外层再包装 `KnowEngineHybridContentAggregator` 与 `ProgressAwareContentAggregator`）。

## Q2: 为什么要给用户展示 RAG 的执行过程？技术上如何实现？

**难度**: ⭐⭐

**参考答案**:

**先说结论**：一是建立信任与认知共识——普通聊天像"开卷考试"，用户不知道模型有没有"一本正经地胡说八道"，展示"分析意图 → 问题优化 → 问题路由 → 文档检索 → 排序优化"的过程更像工程师在透明地干活；二是缓解等待焦虑——RAG 回答可能需要几十秒甚至几分钟，一直转圈用户会以为程序卡死。技术实现是把各阶段的 `[PROGRESS]` 进度消息与 LLM 流式 token 桥接到同一个 Flux。

1. **入口与编排层**：流式编排在 `ChatApplicationService.chat`（`ChatController#send` 仅做委托）——从意图识别处开始做流式过程输出：`Flux.just("[PROGRESS]:正在识别您的意图...")`，`.concatWith(Mono.fromCallable(意图识别).subscribeOn(Schedulers.boundedElastic()).flatMapMany(...))`；flatMapMany 根据意图结果动态切换两条异步管道（不相关 → 通用对话；相关 → RAG 流程），最后 `.concatWith(Mono.just("[DONE]:" + conversationId))` 收尾。
2. **Service 层**：`ChatApplicationService.doChat` 用 `Flux.create(sink)` 把 RAG 管道各阶段进度与 LLM 流式输出桥接到同一个 Flux，各组件对应：`KnowEngineQueryTransformer` → 正在优化您的问题；`KnowEngineQueryRouter` → 正在路由您的问题；`ProgressAwareContentRetriever` → 按委托检索器类型区分发送：ES → 正在检索知识库内容、SQL → 正在检索数据库内容、Neo4j → 正在检索图数据库内容、其他 → 正在检索文档内容；`ProgressAwareContentAggregator` → 正在排序筛选结果 → 正在生成回答。组件内执行 `sink.next(msg)` 发出进度。
3. **代理模式**：对不能改动的第三方组件（如 `ElasticsearchContentRetriever`、`ReRankingContentAggregator`），用装饰器实现——`ProgressAwareContentAggregator` 持有 delegate 和 progressCallback，在 `aggregate` 执行前后发送进度消息。
4. **线程模型**：`Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())` 把阻塞任务从 WebFlux 事件循环（EventLoop）剥离到弹性线程池，保证 AI 响应慢时不卡请求处理线程；`.publishOn(Schedulers.parallel())` 引入异步边界，让 boundedElastic 专心执行阻塞的 RAG 操作，parallel 线程负责推送数据到前端，确保进度消息及时 flush。

**验证**：前端观察 SSE 消息序列是否符合 `[PROGRESS]`×N → token 流 → `[DONE]:conversationId` 的顺序；代码上核对每个 RAG 组件是否都经 progressCallback 或 ProgressAware 代理发出进度。

**追问**：为什么意图识别要 subscribeOn(boundedElastic)？它是阻塞的 LLM 调用，直接在 EventLoop 上执行会卡住整个 WebFlux 服务的事件循环。

源码校核：笔记中流式过程输出编排归于 `ChatController#send`，源码中该编排已下沉至 `ChatApplicationService.chat`（Controller 仅委托调用）；笔记中检索进度只有"正在检索知识库内容"一种，源码中 `ProgressAwareContentRetriever` 按委托检索器类型分别发送"正在检索知识库/数据库/图数据库/文档内容"。

> 源码：`src/main/java/cn/hollis/llm/mentor/know/engine/chat/service/ChatApplicationService.java`、`src/main/java/cn/hollis/llm/mentor/know/engine/rag/modules/ProgressAwareContentAggregator.java`、`src/main/java/cn/hollis/llm/mentor/know/engine/rag/modules/ProgressAwareContentRetriever.java`

## Q3: 如何把引用文档内容（参考来源）返回给用户？

**难度**: ⭐⭐

**参考答案**:

**先说结论**：引用来源的价值是增加回答可信度，并让用户直接查看完整文档。实现分两步——分段时给每个 Chunk 写入来源 metadata；检索后在重排序精筛后按 DOC_ID 去重构造 RagReference，回写消息表并以 `[REFERENCE]` 前缀推给前端。

1. **分段时**：`DocumentProcessServiceImpl#split` 中统一给每个分段 put metadata：`DOC_ID`（document.getDocId()）、`FILE_NAME`（document.getDocTitle()）、`URL`（document.getDocUrl()），再 `JSON.toJSONString(metadata.toMap())` 存到 knowledgeSegment。
2. **检索时**：在 `ProgressAwareContentAggregator#aggregate` 中，对重排序精筛后的 results 用 `Collectors.toMap` 按 DOC_ID 去重（重复时保留 existing），再从每个 content 的 metadata 构造 `ChatMessage.RagReference`：documentId、chunkId、url、documentTitle、chunkContent、rerankScore。
3. **持久化**：`chatMessageService.updateRagReferences(chatMessageId, ragReferences)` 把引用保存到消息记录——注意这里传入的 messageId 是 **assistantMessage**（模型回答那条消息）的 id，不是用户提问消息的 id，因此构造 Aggregator 时要传入 assistantMessageId 和 chatMessageService。
4. **推送前端**：通过 `progressCallback.accept("[REFERENCE]:" + JSON.toJSONString(ragReferences))` 返回；用 `[REFERENCE]` 特殊前缀方便前端识别，正文不展示，用特殊引用样式渲染。
5. **异常兜底**：引用回写失败只 `log.warn`，不影响主回答流程。

**验证**：前端确认引用区展示的是去重后的文档列表且能点开 URL；数据库中 assistant 消息记录包含 ragReferences；构造多个分块同属一个文档的场景验证去重。

**追问**：为什么在重排序精筛之后才构造引用？精筛后候选已收敛，避免为即将被过滤掉的检索结果白白构造引用与去重。

源码校核：笔记中"在 `DocumentProcessServiceImpl#split` 中 put metadata"，源码中实际由该类的 `enrichMetadata` 方法在分段保存时统一写入（DOC_ID/FILE_NAME/URL 之外还写入 VERSION 与 ACCESSIBLE_BY）；引用构造除按 DOC_ID 去重的文档维度外，源码还会按 CHUNK_ID 去重生成 chunk 维度引用用于持久化。

## Q4: Chunk 的 metadata 是怎么设计的？有哪些用途？

**难度**: ⭐⭐

**参考答案**:

**先说结论**：metadata 承担两大作用——记录扩展信息（标记分段的归属）和用于数据过滤（如权限控制，即元数据过滤）。项目用常量类 `MetadataKeyConstant` 统一定义所有 key，写入与过滤两侧共用同一份定义。

按用途分组：

- **归属与引用**：`FILE_NAME`（文件名称）、`DOC_ID`、`URL`（文件地址）——在分段时统一写入，支撑"引用文档内容返回给用户"（来源名称与地址）。
- **父子分块结构**：`CHUNK_ID`、`PARENT_CHUNK_ID`（父块ID）、`BROTHER_CHUNK_ID`（同级块ID）、`BROTHER_CHUNK_INDEX`、`BROTHER_CHUNK_TOTAL`、`HEADER_LEVEL`（头级别）——支撑父子分块的切分与检索（父块回填、兄弟块定位）。
- **权限控制**：`ACCESSIBLE_BY`（访问权限）——检索时做权限过滤（详见文档检索权限体系实现）。
- **版本与内容增强**：`VERSION`（文件版本）、`CATEGORY`（分类）、`SUMMARY`（摘要）、`KEYWORDS`（关键字）。
- **处理控制**：`SKIP_EMBEDDING`——true 表示该分段不需要做 embedding。

**验证**：能按"归属引用 / 父子分块 / 权限 / 版本 / 处理控制"五组默写 key 并说明各服务哪条链路；对照 `MetadataKeyConstant` 源码核对拼写。

**追问**：为什么要用常量类而不是直接写字符串 key？（通用补充）分段写入、检索过滤、引用回填多处共用同一 key，常量类统一约束，避免拼写不一致导致过滤条件静默失效。

## Q5: 如何实现图片的召回和渲染？

**难度**: ⭐⭐

**参考答案**:

**先说结论**：核心思路是"图片描述文本入库参与检索 + Markdown 图片标签回流到回答中渲染"，需要改三处：内容提示词、图片描述生成提示词、页面渲染支持。

1. **内容提示词修改**：在 RAG 最终生成提示词中增加格式要求——
   - 所有回答必须使用 Markdown 格式排版；
   - 如果上下文信息中包含图片描述标签 `![图片](URL)`，则返回包含图片的内容；
   - 仅在必要时包含图片，千万不要输出重复的内容和图片，确保最终生成的 URL 不重复。
   目的是让模型输出更稳定，并把图片正常带出来。
2. **图片描述生成提示词优化**：描述要求包含场景、对象、布局、颜色、文字信息，直接输出纯文本描述，并特别加上"不要增加任何特殊符号，特别是换行符"——因为图片描述一旦带多行，会导致 Markdown 图片标签 `![xxx](http://xxx.com)` 失效。
3. **页面优化**：在 chat.html 中增加针对 Markdown 的渲染支持，让回答中的图片标签能正常展示。

**验证**：入库一张带图片描述的资料，提问命中该图片后检查：回答中出现正确的图片 URL、页面能渲染、URL 无重复；再构造多行描述的旧版本验证标签失效问题已被提示词规避。

**追问**：为什么图片描述里不能有换行符？Markdown 行内图片语法 `![alt](url)` 必须单行完整，描述换行后标签会被拆断而失效。

## Q6: 如何基于 Text2SQL 实现关系型数据库查询？

**难度**: ⭐⭐

**参考答案**:

**先说结论**：智能客服中并非所有问题都靠知识库检索——用户问"我的保险什么时候到期"这类个人信息，必须查数据库。know-engine 采用三路由检索架构，SQL 检索是 relational_db 分支，核心链路：用户提问 → 查询改写 → 意图路由 → text2sql → SQL 检索 → LLM 生成回答。

1. **查询改写**（`KnowEngineQueryTransformer`）：LLM 完成简洁/抽象/错别字等改写；进入 SQL 分支后，由 `KnowEngineSqlDatabaseContentRetriever.retrieve` 给查询附加上下文——`"我的问题是：" + 查询文本 + ", 我的用户Id是: " + userId + ", 现在是：" + LocalDateTime.now()`。userId 和当前时间对后续 SQL 生成非常重要（"我的保险还有多少天到期"需要 user_id 过滤，时间比较需要当前日期）。
2. **意图路由**（`KnowEngineQueryRouter`）：LLM 判断意图，当查询涉及结构化数据（车辆信息、保险信息、订单信息、数值比较、聚合操作等）时 strategy 为 relational_db，路由到 SQL 检索器。
3. **检索器构建**：`KnowEngineSqlDatabaseContentRetriever` 是对 LangChain4j 原生 `SqlDatabaseContentRetriever` 的增强封装，builder 参数包括：`dataSource`（JDBC 数据源，执行生成的 SQL）、`promptTemplate`（text-to-sql-prompt.txt）、`databaseStructure`（静态 retrieve_tables.sql 与 table_meta 表中动态建表 SQL 合并后的表结构 Schema）、`chatModel`、`fallbackRetriever`（向量检索兜底）。
4. **Text2SQL Prompt 设计**：角色是 SQL 专家，只能查询不能修改删除；注入 `{{databaseStructure}}`；要求只返回 SQL 语句不带解释、确保语法正确、使用上下文提供的表名和字段名、无法查询时返回空字符串；并注入"今天是:{today}"。
5. **Schema**：提供 3 张业务表——car_info（车型信息：品牌、型号、续航、价格等）、my_car（用户车辆：车牌号、VIN码、保险到期日、里程等）、car_order（车辆订单：订单状态、金额、交付日期等），每个字段带详细 comment 帮助 LLM 理解字段含义。
6. SQL 检索结果被标记 skipRerank 后直接透传（`KnowEngineHybridContentAggregator` 对结构化结果不做 RRF 融合与 BGE 重排序）→ LLM 生成最终回答。

**验证**：问"我的保险什么时候到期"，核对日志：路由 strategy 为 relational_db、生成的 SQL 带 user_id 过滤条件、回答内容来自 SQL 执行结果而非编造。

**追问**：为什么把 userId 和时间拼进查询文本？让 LLM 在一次生成中就能拿到过滤用户和时间比较所需的变量，无需额外传参通道。

源码校核：笔记中"改写后的查询附加上下文（我的问题/userId/当前时间）"在源码中实际发生在 `KnowEngineSqlDatabaseContentRetriever.retrieve` 内（不在 `KnowEngineQueryTransformer`），且用户Id为硬编码示例值 "123321"；笔记中 databaseStructure 仅提 retrieve_tables.sql，源码中实际为静态 SQL 与 table_meta 表动态建表语句的合并；笔记中"SQL 结果再经 BGE 重排序"，源码中 SQL 结果标记 skipRerank 后由混合聚合器直接透传、不参与重排序。

> 来源：[[AI项目/know-engine/50.如何基于text2sql实现关系型数据查询]]

## Q7: SQL 检索异常或查不到数据怎么办？为什么判空要自己实现？

**难度**: ⭐⭐⭐

**参考答案**:

**先说结论**：降级策略是"SQL 异常或结果为空 → fallbackRetriever 向量检索兜底"；但 LangChain4j 原生 `SqlDatabaseContentRetriever` 查询无数据时**不会返回空 list**，而是返回包含列名但无数据行的文本，所以必须自定义判空逻辑。

1. **降级策略**（`KnowEngineSqlDatabaseContentRetriever.retrieve`）：先调用原生 `sqlDatabaseContentRetriever.retrieve(query)`；执行异常 → log.warn 后 `return fallbackRetriever.retrieve(query)`；结果为 null/空或 `isSqlResultEmpty` 判空 → 降级向量检索；正常则直接返回 SQL 查询结果。
2. **空结果长什么样**：有结果时文本形如 `Result of executing 'SELECT ...':\nplate_number,insurance_expire_date\n沪A12345,2025-06-20`；无结果时只有列名行，没有数据行。
3. **判空逻辑**（`isSqlResultEmpty`）：仅当 results.size()==1 且文本以 `Result of executing '` 开头时继续判断；用 `":\n"` 定位列名行开始，再找列名行之后的第一个 `\n`（数据开始位置）；该位置不存在或其后内容 trim 后为空，则判定结果为空。

**验证**：构造三类输入分别验证：诱导生成非法 SQL（触发异常降级）、查询条件无匹配行（只有列名，触发判空降级）、正常返回多行数据（直接透传）；确认三种情况下用户都不会看到原始 SQL 报错。（通用补充）生产上建议对降级事件打点，区分"数据真没有"与"SQL 生成错误"，便于持续优化。

**追问**：只判 `results.isEmpty()` 够吗？不够——原生实现无数据时返回的是包含列名头的非空 list，必须解析文本判空。

## Q8: 如何基于 Text2Cypher 实现图数据库查询？与 Text2SQL 有什么差异？

**难度**: ⭐⭐⭐

**参考答案**:

**先说结论**：graph_db 分支与 SQL 分支链路同构（改写 → 路由 → text2cypher → 图检索 → LLM 生成），本质是 GraphRAG 实践；核心差异有两点：检索器内部用 `Neo4jText2CypherRetriever` 生成并执行 Cypher，且成功结果要标记 skipRerank 跳过重排序。

1. **检索器封装**：`KnowEngineNeo4jContentRetriever` 封装 `langchain4j-community-neo4j-retriever` 提供的 `Neo4jText2CypherRetriever`，builder 配置：`graph`（Neo4jGraph + neo4jDriver）、`chatModel`、`promptTemplate`（text-to-cypher-prompt.txt）、`fallbackRetriever`（向量检索降级）。封装的主要目的就是做兜底。
2. **retrieve 流程**：先给查询补充用户上下文与时间信息辅助生成 Cypher → 调用 `Neo4jText2CypherRetriever.retrieve` → 异常降级知识库检索 → 空结果降级（`isCypherResultEmpty` 判定逻辑与 SQL 一致：`Result of executing '...'` 只有列名头、没有数据行）→ 成功结果用 `ContentUtil::markAsSkipRerank` 标记后直接透传。
3. **Prompt 设计**：`{{schema}}` 动态注入 Neo4j Schema；`{{examples}}` 提供 few-shot 示例（BMW 有哪些车型、宝马3系有哪些版本、哪些车是纯电动、哪些车和 Model 3 长续航版用相同轮胎等多跳遍历样例）；要求只返回 Cypher、只使用 Schema 中提供的节点标签/关系类型/属性、无法查询返回空字符串、**禁止写操作（CREATE、MERGE、SET、DELETE、REMOVE 等）**。
4. **数据模型**：节点 Brand、CarModel、CarVersion、Part、EnergyType；关系 HAS_MODEL、HAS_VERSION、USES_PART、HAS_ENERGY_TYPE；Brand 节点同时有 `name` 和 `englishName` 支持中英文查询。
5. **为什么 skipRerank**：图数据库和关系型数据库的检索结果不需要重排序——结构化查询结果进入 `KnowEngineReRankingContentAggregator` 做 RRF 融合和 BGE 重排序时，会导致重排序失败或效果异常。

**验证**：问"哪些车配置了空气悬架系统？"，核对生成的 Cypher 是否为 `(CarVersion)-[:USES_PART]->(Part)` 方式反查（Part 名为空气悬架系统），且结果带 skipRerank 标记未被重排序。

**追问**：结构化结果为什么不能进 BGE 重排序？BGE 重排序面向自然语言文本相关性打分，结构化查询结果与其语义不匹配，会导致重排序失败或效果异常。

## Q9: 为什么要引入多数据源查询？三种数据源如何协同？

**难度**: ⭐⭐⭐

**参考答案**:

**先说结论**：不是所有问题都适合向量检索——知识库回答制度/方法类问题；个人数据（我的保险、我的订单）要查关系库；实体关系类（哪些车配置了空气悬架）要查图库。know-engine 用一个查询路由器按意图分流三种数据源，结构化分支各自再兜底回知识库。

1. **路由分发**：`KnowEngineQueryRouter` 用 LLM 判断 strategy 并按类型过滤检索器——relational_db → `SqlDatabaseContentRetriever` 系、graph_db → `Neo4jText2CypherRetriever` 系、knowledge_base → `ElasticsearchContentRetriever`（向量检索 + 全文检索）。
2. **两条结构化分支的共同设计**：检索器内在查询中注入用户上下文与当前时间（源码中用户Id为硬编码示例值）；各自持有 fallbackRetriever（向量检索）做异常/空结果降级；自定义判空逻辑；检索成功后 skipRerank 直接透传，不做 BGE 重排序。
3. **知识库分支**走标准 RAG 链路：检索 → `KnowEngineReRankingContentAggregator`（BGE-RERANKER ONNX，选第一个查询作为重排序参考）→ `DefaultContentInjector` 注入 Prompt。
4. **统一出口**：无论哪个分支，结果都作为 Content 走聚合、注入，最终由同一个 LLM 生成回答，对前端协议透明（[PROGRESS]/[REFERENCE]/[DONE]）。

（设计建议）路由依赖 LLM 输出 strategy 字符串，建议对解析结果做白名单校验，未识别时默认 knowledge_base，避免异常输出导致检索器选择失败。

**验证**：三类问题各测一例（个人数据查 SQL、配置关系查图库、制度问题查知识库），核对日志中路由策略与实际命中的检索器；再测 LLM 返回非法 strategy 的边界场景确认默认分支。

**追问**：一个问题既要查库又要查知识库怎么办？主干路由按意图选一个分支，但各结构化分支都带向量检索兜底；混合口径问题应分别取证后合成，并标明各自依据。

源码校核：笔记中"改写时注入 userId 与当前时间"，源码中实际在 `KnowEngineSqlDatabaseContentRetriever` / `KnowEngineNeo4jContentRetriever` 的 retrieve 内拼接，且用户Id为硬编码示例值 "123321"；笔记（设计建议）中"未识别 strategy 默认 knowledge_base"，源码中未识别 strategy 或路由异常时实际降级为返回全部检索器做全量检索（设计建议仍保留）。

## Q10: 如何把 RAG 系统接入钉钉机器人做客服答疑？

**难度**: ⭐⭐⭐

**参考答案**:

**先说结论**：企业内部答疑不必单独做网页，用钉钉机器人集成即可。采用 Stream 模式（WebSocket 长连接，无需公网服务器、IP、域名，只需集成 SDK），在回调里复用 `ChatApplicationService` 完整对话链路，并把 SSE 流聚合为一次性消息回复。

1. **接入步骤**：钉钉开发者平台创建应用 → 添加【机器人】能力，消息接收模式选 **Stream 模式** → 申请【企业内机器人发送消息权限】→ 版本管理与发布。配置 dingtalk 的 appKey/appSecret/robotCode（企业内部应用机器人的 robotCode 通常与 appKey 相同）。
2. **实现原理**：用官方 SDK `OpenDingTalkStreamClientBuilder` 创建长连接客户端，配置 appKey/appSecret 鉴权，注册 `ChatBotCallbackListener` 回调监听器，`@Bean(initMethod = "start")` 在应用启动时自动建连；有回调时开放平台通过 WebSocket 把数据推给应用。
3. **回调处理流程**（`ChatBotCallbackListener`）：从 ChatbotMessage 取文本内容、会话类型、发送者 StaffId → 先给发送方回"已接到您的请求，正在思考中..."降低等待焦虑 → 拼 `dingtalk_` 前缀作为内部 userId，调用 `chatApplicationService.chat(userId, content, null, ChatSource.STAFF_DING)` → 因钉钉机器人为请求-响应模型、无法直接消费 SSE 流，用 `aggregateChatResult` 把 `Flux<String>` 阻塞聚合为结构化结果（设 120 秒超时避免回调线程无限阻塞；跳过 [PROGRESS]/[DONE]，收集 [WARN]、[REFERENCE]、[CARD] 等类型）→ 按会话类型调用群聊或单聊发送服务，有引用时拼成 Markdown"参考来源"列表。
4. **复用设计**：`ChatController.send()` 和钉钉回调共用同一个 `chat(...)` 方法，通过 `ChatSource` 区分来源——USER_WEB 需要车辆信息时返回 `[CARD_CHOICE_MYCAR]`/`[CARD_CHOICE_CAR]` 交互卡片；STAFF_DING 跳过车辆选择卡片分支，直接走 RAG 检索或返回 [WARN] 提示。
5. **关键坑**：官方文档说 conversationType 0 是单聊、1 是群聊，但实测 1 为单聊、2 为群聊，代码按实测值处理；官方 demo 默认只有群聊模式代码，单聊需自行实现 `RobotPrivateMessageService`（batchSendOTO 接口发送）。
6. **消息模板**：`DingTalkMessageBuilder` 统一封装 sampleText（文本）、sampleMarkdown（Markdown）、sampleLink（链接）、sampleActionCard（单按钮卡片）四类 msgKey/msgParam。

单聊方便查找、不需要 at，适合企业内部通用 AI 助手；群聊需要 at 机器人，适合单产品的客服答疑群。

**验证**：群聊 at 机器人与单聊各测一轮，确认"正在思考"提示、RAG 回答、参考来源 Markdown 列表均正常；构造超长耗时问题验证 120 秒超时兜底生效；用实测 conversationType 值核对单聊/群聊分支。

**追问**：为什么不直接把 SSE 流转发给钉钉？钉钉机器人为请求-响应模型，只能发送完整消息，所以必须把 Flux 聚合后再按消息模板发送。
