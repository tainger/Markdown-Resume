## Q1: 说说你在 RAG 项目中踩过的坑？如何定位、修复和避免复发？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

先给复盘表达框架，再选两三个能讲透的案例展开。每个案例都按同一条线组织，避免只报一串优化名词：

> **现象**：说清具体输入与错误行为（哪个文档、哪条链路、什么表现），不说笼统的「效果不好」。
> **定位**：沿链路逐阶段取证据——提示词原文、各阶段产物、日志，先验证最容易怀疑的假设。
> **根因**：区分四类——接口/参数没用对、框架语义理解错、模型能力上限、架构设计缺陷。
> **修复**：优先选确定性手段（改参数、改代码、改架构）；涉及模型的先做 benchmark 对比，再决定换模型还是改架构。
> **回归**：固定样本与配置复测，把踩坑反例纳入验收，防止复发。

下面 8 个案例覆盖入库、检索、对话三条链路，按链路顺序展开。

### 案例1：MinerU 解析 PDF 拿不到图片

- **现象**：通过 MinerU 解析接口把 PDF 转成 Markdown，只返回 Markdown 文本，文档里的图片全部丢失。
- **根因**：不是解析能力问题，而是解析接口的默认响应只含 Markdown，必须显式要求 ZIP 模式的返回才能拿到图片。
- **修复**：以 ZIP 模式拿回 Markdown + 图片文件夹——源码走 MinerU 官方 v4 异步批量接口：POST `/file-urls/batch` 申请上传链接、PUT 预签名 URL 上传文件、轮询 `/extract-results/batch/{batchId}` 后从 `full_zip_url` 下载 ZIP；Java 侧用 Apache HttpClient 5、`EntityUtils.toByteArray` 读 ZIP 字节流。解压后不整包上传，而是把图片与处理后的 Markdown 分别上传 MinIO，再用正则 `!\[(.*?)\]\(([^)]+)\)` 把 Markdown 里的图片相对地址替换成 MinIO 网络地址，并用 qwen3-vl-plus（`ImageContent` 传图）生成图片描述写进 alt 文本，让图片可检索。选「解压分别上传」而非「整包上传」，因为后续分段、用户问答展示、描述生成都要用图片，整包上传会导致图片存两份。
- **一句话要点**：图片丢失先查接口参数而不是急着换解析方案；ZIP 模式 + 解压上传 + 地址替换 + 描述生成应在文档处理阶段一次做完。
- **源码校核**：笔记中的「fast api `/file_parse` 接口 + `response_format_zip=true`/`return_images=true` 参数 + multipart 请求」在源码中实际为 MinerU 官方 v4 异步批量接口（`/file-urls/batch` 申请上传链接 → PUT 预签名 URL 上传 → 轮询 `/extract-results/batch/{batchId}` → 下载 `full_zip_url`），见 `MinerUProcessBaseServiceImpl.parseDocumentToZip`。
- **来源**：[[AI项目/know-engine/11.解决MinerU解析无法获取图片的问题]]

### 案例2：saveBatch 看似批量，实则逐条 INSERT

- **现象**：一个文档分段很多时，批量保存知识片段（MyBatis-Plus `IService#saveBatch`）性能极差。
- **根因**：`saveBatch` 底层 `executeBatch` 是 for 循环逐条调 `save()`，每条都向数据库发一条独立 INSERT；且事务在全部 INSERT 执行完才一次性提交，中途任一条失败整个事务回滚。名为批量，实为逐条。
- **修复**：在 JDBC URL 加 `rewriteBatchedStatements=true`，让 MySQL 驱动把多条 `INSERT INTO table VALUES (...)` 合并成一条多 VALUES 的 INSERT，降低解析与执行开销；再按数据量与内存调整 `saveBatch` 的 `batchSize`（默认 1000）。
- **一句话要点**：不要被方法名里的 batch 麻痹，MyBatis-Plus 默认是逐条 flush；`rewriteBatchedStatements` 才让驱动真正合并 INSERT。
- **来源**：[[AI项目/know-engine/20.分段批量插入性能优化]]

### 案例3：表格与图片被切分到多个分块

- **现象**：文档中的表格或图片在分段时被切到不同 chunk，后半段丢失表头，既影响检索效果，也影响输出——表格不完整，但用户期望看到完整表格。
- **根因**：按长度机械切分不感知 Markdown 中表格、图片的结构边界。
- **修复**：PDF/Word 统一先转 Markdown 再分段；对 Markdown 用「标题分段 + 父子分段」组合——标题分段保证同一标题下内容落在一个分段（图片和表格不可能跨标题，未超 chunkSize 时天然完整）；同一标题下内容超长需二次切分时用父子分段：父分段保留完整内容，子分段用于向量检索，命中后、调用 LLM 前回填父分段，把完整表格/图片交给模型。
- **一句话要点**：结构化元素不能靠文本长度保护，「标题分段兜边界 + 父子分段做回填」才能保证进 LLM 的表格和图片完整。
- **来源**：[[AI项目/know-engine/24.表格&图片被拆分到多个分块如何解决？]]

### 案例4：模型 JSON 输出不稳定导致解析失败

- **现象**：意图识别等要求 JSON 输出的场景，模型输出经常解析失败：缺引号、逗号、括号不匹配、夹带解释性文字，最典型的是 JSON 外面包了一层 \`\`\` Markdown 代码块。
- **根因**：即使提示词里给出具体 JSON 结构约束，模型输出仍存在不稳定，这是模型行为问题，无法只靠提示词彻底消除。
- **修复**：两手准备——提示词中给出 JSON 结构约束；LLM 返回后先过一遍手写的 JSON fix 工具（思想参考 Python 的 json_repair 框架）：提取 Markdown 代码块内的 JSON、裁掉首个 `{`/`[` 之前的垃圾字符、修中文引号与单引号、去尾部逗号、补缺失键名引号、修非法转义，再 `readTree` 验证；仍无效就转义后包装成 `{"content": ...}` 兜底。
- **一句话要点**：对模型的结构化输出要有确定性的程序化修复兜底，提示词约束只是第一道防线。
- **来源**：[[AI项目/know-engine/43.如何解决模型json格式输出不稳定问题？]]

### 案例5：意图识别结果污染问题重写（多轮对话）

- **现象**：支持多轮对话后，RAG 阶段的问题重写结果完全错误——用户明确问「打不着火怎么办」，改写结果却是「车辆信息查询」；部分模型还会原样输出意图识别的 JSON。
- **根因**：一次对话中本应做两次 Redis 记忆删除，最初实现只删了第一次；意图识别 AiService 的输入输出（含 JSON 格式约束与识别结果）经 `updateMessages()` 写入 Redis，问题重写从 Redis 读对话记忆时把这些内容当成「历史对话」，整体注入改写提示词，污染了改写结果。
- **修复**：先写 `ChatModelBenchmarkTest` 做模型对比：qwen-max-latest 速度可以但输出不稳定，常把「打不着火」识别成查询车辆信息；qwen3-30b-a3b-instruct-2507 效果最好，20 轮测试正确率 90%、平均耗时 1564ms（最小 437ms、最大 5375ms），但仍有 10% 错误——输出了 JSON 而非改写结果；qwen3.6-flash、deepseek-r1-distill-qwen-7b 直接复述 JSON。换更大更新的模型更稳但耗时不可接受，换模型无法根治。最终方案：意图识别之后、RAG 检索之前调用 `evictCache()` 删除 Redis 记忆，让 RAG 阶段从 DB 加载干净历史（DB 只保存用户消息与 AI 回复，没存意图识别结果；若存了也可过滤）——本质是多 agent 之间的上下文隔离。
- **一句话要点**：多个 AiService 共享同一 ChatMemoryStore 时必须主动隔离上下文；换模型只能缓解污染，删缓存隔离才是根治。
- **来源**：[[AI项目/know-engine/47.支持多轮对话后的问题重写踩坑与LLM对比]]、[[AI项目/know-engine/44.基于langchain4j的多轮对话的实现]]

### 案例6：Redis 记忆用 List 导致消息重复

- **现象**：如果对话记忆存 Redis List 并用 RPUSH 追加，会话历史会出现 `[A, B, C, B, C, D]` 这类重复。
- **根因**：误解了 `updateMessages(memoryId, messages)` 的参数语义——LangChain4j 的 MessageWindowChatMemory 先加入新消息、淘汰超窗旧消息，再把「当前时刻应保留的全部消息全集」（如 `[B, C, D]`）整体传入，是覆盖语义而非追加语义。
- **修复**：「先取出去重再保存」和「先整体删除再更新」两个方案都复杂，最终改用 String 结构（`opsForValue`）存整份 JSON 整体覆盖；窗口截断保留最近 10 条、缓存 TTL 1 小时。注意 `updateMessages()` 不能省略不实现，否则 LangChain4j 运行时写入 systemMessage 的动作丢失，`@SystemPrompt` 注解会失效。
- **一句话要点**：接框架回调前先确认参数语义（全集覆盖还是增量追加），Redis 用 String 存 JSON 覆盖写是最简单的正确方案。
- **来源**：[[AI项目/know-engine/44.基于langchain4j的多轮对话的实现]]

### 案例7：路由错误导致问答失败

- **现象**：查询路由根据用户问题把检索导向关系型数据库、图数据库或知识库，模型有幻觉时会路由错——应到知识库的问题被路由到 SQL，检索为空或报错，问答失败。
- **根因**：路由决策由 LLM 完成，幻觉导致路由不可能 100% 正确，需要按「路由一定会错」来设计。
- **修复**：在 `KnowEngineSqlDatabaseContentRetriever` 和 `KnowEngineNeo4jContentRetriever` 中做兜底：检索异常时 catch 降级调用 fallbackRetriever（走知识库检索）；结果为空（null、empty 或空结果判定）同样降级再检索一次，尽量减少拒答。
- **一句话要点**：把「LLM 路由可能错」当成默认假设，结构化检索器内做「异常 + 空结果」双兜底降级到知识库。
- **来源**：[[AI项目/know-engine/57.解决路由错误导致问答失败问题]]

### 案例8：结构化检索结果导致重排序失败

- **现象**：混合检索场景中，SQL/Cypher 返回的结构化表格结果进入 `KnowEngineReRankingContentAggregator` 做 RRF 融合 + BGE 重排序时失败或效果异常；按 chunk 的 embedding_id 去重时还会报错。
- **根因**：三个不兼容——BGE scoring model 为文本相似度设计，对结构化表格数据评分不准；RRF 倒数秩融合对精确匹配结果不合理；代码基于 chunk 的 embedding_id 字段去重，结构化结果没有该字段。
- **修复**：设计基于元数据标记的混合聚合架构：定义 `skipRerank` 标记常量，SQL/Cypher 检索器成功时给 Content 打上标记（异常/空结果仍降级向量检索、不打标记）；新增 `KnowEngineHybridContentAggregator` 先按标记分离两类结果——非结构化走原 RRF + BGE 重排序聚合器，结构化直接透传，最后合并（结构化在前、非结构化在后）交给 LLM。
- **一句话要点**：重排序通道只服务非结构化文本，用元数据标记把结构化结果隔离出融合/重排链路。
- **来源**：[[AI项目/know-engine/58.解决针对非向量检索导致重排序失败问题]]

### 面试时如何选案例

优先选一个「有直接错误现象、修复手段确定」的案例（如案例2 的批量插入、案例4 的 JSON 修复），再配一个「涉及架构设计」的案例（如案例5 的记忆隔离、案例8 的重排序隔离）。每个案例都要能讲出提示词原文、阶段产物或 benchmark 数据；如果只是跟随课程实现、没有亲手排查，就如实说明，不要把作者的日志和成绩当成自己的经验。

**验证**：本文作为复习入口，以上修复与验证均应回到对应工程执行。案例5 的 benchmark 数字来自仓库笔记的测试记录，复述时说明口径（20 轮测试、关闭思考的耗时）；没有亲手复测就不把数字当成个人成绩。

**追问**：你怎么证明问题出在链路而不是模型能力？——用案例5 的做法：固定提示词与输入，跑多模型、同模型多轮 benchmark，用数据区分「模型不稳定」和「上下文被污染」两个假设；再说明为什么最终不选换模型（耗时不可接受）而选架构隔离。

## Q2: 如何向面试官陈述这个项目的整体设计？

**难度**: ⭐⭐⭐ 高级

**参考答案**:

按「业务目标 → 架构分层 → 文档处理链路 → 检索链路 → 对话链路 → 工程化保障」六段陈述，每段 30 秒左右，总长控制在 3~5 分钟，讲完主动停住等面试官选方向下钻。

1. **业务目标**：面向汽车场景的企业知识库智能客服——购车咨询、车型信息、保养维修、保险年检等；核心是让回答基于企业私有知识（知识库文档 + 结构化数据）而不是模型参数知识，支持多轮对话。
2. **架构分层**：Java + LangChain4J 技术栈；MinerU 负责文档解析（PDF 转 Markdown）；Elasticsearch 承担向量 + 全文检索；MySQL 存业务数据并做对话记忆持久化；Redis 做记忆缓存；MinIO 存文档与图片；XXL-JOB 调度异步任务。
3. **文档处理链路**：上传 → MinerU 以 ZIP 模式解析出 Markdown + 图片 → 解压、图片上传 MinIO、替换 Markdown 内图片地址、VLM（qwen3-vl-plus）生成图片描述 → 标题分段 + 父子分段切分 → 向量化入库 ES。
4. **检索链路**：意图识别 → 查询路由（知识库 / SQL / Cypher 图查询）→ 混合检索（ES 向量 + 全文）→ 混合聚合：结构化结果打 skipRerank 标记直接透传，非结构化走 RRF 融合 + BGE 重排序（minScore 0.6、maxResults 5）→ SQL/Cypher 检索异常或为空时兜底降级知识库。
5. **对话链路**：自定义 `DatabaseChatMemoryStore`（Redis 缓存 + MySQL 持久化两级，读写分离：Store 写 Redis、业务层写 DB）→ 意图识别 → `evictCache()` 隔离意图识别记忆 → 问题重写（指代消除 + 上下文补全）→ RAG 问答流式输出（token 逐个推送）→ AI 回复落库。
6. **工程化保障**：文档分段加分布式锁（`@DistributeLock`）、批量插入优化（`rewriteBatchedStatements`）、JSON 输出修复工具、路由双兜底、重排序隔离、模型 benchmark 对比。

哪些点要结合自己实际做的部分讲：

- **明确归属**：只把亲手实现或排查过的模块说成「我做的」（例如批量插入优化、JSON 修复、Redis 记忆隔离这类在 Q1 里能展开的案例）；其余如实说「项目采用的方案是……」，避免面试官一追问实现细节就露馅。
- **每条链路备一个下钻点**：文档链路备「图片为什么解压分别上传」、检索链路备「skipRerank 聚合器怎么分离两类结果」、对话链路备「为什么 `updateMessages()` 只写 Redis 不写 DB」（避免一次 LLM 调用中多次写 DB 的频繁 IO，同时保留在过程中更新引用文档、改写后问题的能力）。
- **主动连接踩坑案例**：陈述到某段链路时，若面试官感兴趣，直接引到 Q1 对应案例，把「设计取舍」讲成「踩坑后的改进」，比背架构图更有说服力。

**验证**：本文作为复习入口，陈述中每个链路都应能在仓库笔记中找到依据（见下方来源）；XXL-JOB 的具体调度任务、ES 选型理由等未在已读笔记中展开的内容，⚠️ raw 缺失，待补充后再作答，不要临场编造。

**追问**：面试官常追问选型题，如「为什么用 ES 同时做向量与全文检索」「为什么记忆要 Redis + MySQL 两级」「为什么结构化结果不参与重排」。前者的完整论证 raw 缺失，待补充；后两者可分别用 Q1 案例6（覆盖语义决定用 String 整体覆盖）和 Q1 案例8（BGE 对表格数据评分不准）回答。
