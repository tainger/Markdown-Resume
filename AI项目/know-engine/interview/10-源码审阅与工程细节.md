## Q1: 请 review 下面这段 SQL 检索器代码，说说有什么问题？

**难度**: ⭐⭐

`src/main/java/cn/hollis/llm/mentor/know/engine/rag/modules/KnowEngineSqlDatabaseContentRetriever.java`

```java
    @Override
    public List<Content> retrieve(Query query) {
        List<Content> results;
        try {
            String newQuery = "我的问题是：" + query.text() + ", 我的用户Id是: 123321" + ", 现在是：" + LocalDateTime.now();
            query = new Query(newQuery, query.metadata());
            results = sqlDatabaseContentRetriever.retrieve(query);
        } catch (Exception e) {
            log.warn("SQL 检索异常，降级使用知识库检索, query: {}", query.text(), e);
            return fallbackRetriever.retrieve(query);
        }

        if (results == null || results.isEmpty() || isSqlResultEmpty(results)) {
            log.info("SQL 检索结果为空，降级使用知识库检索, query: {}", query.text());
            return fallbackRetriever.retrieve(query);
        }

        // SQL 结构化查询结果直接透传，不参与后续重排序/融合
        return results.stream()
                .map(ContentUtil::markAsSkipRerank)
                .collect(Collectors.toList());
    }
```

**参考答案**:

结论先行：这段代码的降级与空结果兜底逻辑是好的（对应路由错误的容错设计），但第 48 行把用户身份**硬编码**进了检索器，是一个必须修的多租户隐患。

- **考察什么**：能否从一段看似正常的代码里发现「硬编码 + 职责错位」两个坏味道，并意识到它在多租户场景下的数据越权后果——这是纯背笔记背不出来的。
- **答题要点**：
  1. `userId = "123321"` 写死在 `retrieve()` 内部，所有用户共用同一个身份去查 text2sql——线上只要接了真实用户，A 用户的问题会带着 B 用户的 ID 拼进 SQL 生成提示词，轻则查错数据，重则把 123321 用户的车辆/订单信息返回给别人（数据越权）。
  2. 注入位置错：`retrieve()` 是 LangChain4j 的框架回调，检索器是「无状态组件」，用户上下文属于会话级信息，应该在对话链路里由调用方从登录态取出来（项目已接入 Sa-Token 登录，见笔记 56），放进 `Query.metadata()` 或提示词变量传进来，而不是在检索器里就地拼字符串。
  3. 降级分支 return 的 `query` 已经是被改写过的对象（第 49 行重新赋值），fallback 拿到的是拼了 userId 和时间戳的问题——读代码时要能注意到变量被重新赋值后的流向。
- **加分项**：能指出同一个硬编码在 `KnowEngineNeo4jContentRetriever` 里复制了一份（两处必须一起修）；能给出修法——检索器构造时注入「用户上下文解析器」或在 `ChatApplicationService` 组装 RAG 时把 userId 塞进 `Query.metadata`；能提到 `LocalDateTime.now()` 是为了让 LLM 生成带时间条件的 SQL，属于有意设计，但拼接进 query 文本会让「问题改写结果回写」「查询缓存」等以文本为键的机制需要确认键的稳定性。

**验证**：`grep -rn "123321" src/` 可确认硬编码出现在 SQL 检索器、Neo4j 检索器两处主代码及测试断言中（`KnowEngineQueryTransformerTest` 三处断言 `contains("我的用户Id是: 123321")`，说明该写法已被测试固化，修复时需同步改测试）。

**追问**：如果让你改成多租户，最小改动方案是什么？——检索器加一个 `userId` 构造参数由调用方传入，或从 Query metadata 读取；拒绝「在检索器里自己查登录态」的方案（保持组件可测试、可复用）。

**参考答案**:

结论先行：`MAX_RETRY_COUNT` 是死常量（活代码中零引用），而活跃的向量化补偿任务恰恰缺重试上限——两者对照正说明「写了上限却没接上」。

- **考察什么**：能否识别死代码并推导其来历；能否发现「注释说更新重试次数、实际只打日志」这种注释与实现不符的坏味道；能否补出完整方案。
- **答题要点**：
  1. 两个常量在活代码中没有任何引用——`MAX_RETRY_COUNT` 唯一的使用点在被整段注释掉的 `documentSplitCompensation` 方法里，IDE 会灰显。类 Javadoc 写了 `@Deprecated`，但真正的注解也被注释掉了（`//    @Deprecated`），并未正式标记过时。
  2. 活跃的 `documentEmbeddingCompensation` 每个调度周期无条件重扫全部 CHUNKED 文档并重试 `embedAndStore`：持久失败的文档会被**无限重试**（每个周期一次），没有任何计数、跳过或上限——反复调用 embedding API 产生费用与限流风险，日志噪音持续增长。
  3. 补齐方案：把 `retry_count` 持久化（加表字段或复用 extension JSON），补偿时先读取、`>= MAX_RETRY_COUNT` 则跳过并告警/置为待人工状态；用 `COMPENSATION_THRESHOLD_MINUTES` 配合 `updatedAt` 做「超过 N 分钟才补偿」的时间窗，避免把刚进入 CHUNKED、正常处理中的文档误补偿。
- **加分项**：指出被注释的整段方法应该删除（git 历史已留痕，注释代码不是文档）；指出 `if (!document.getCurrentVersionId().equals(...))` 前没有对 `document` 判空，文档被物理删除时会 NPE；能把「补偿任务」与「事件驱动改前端手动触发分段」的演进（笔记 17→分段参数前端选择）串起来解释死代码的成因。

**验证**：对 `MAX_RETRY_COUNT`、`COMPENSATION_THRESHOLD_MINUTES` 做 IDE Find Usages 或全库搜索，确认仅出现在注释块内；跑一次 XXL-Job 调度观察重复失败文档每周期被重试的日志。

**追问**：为什么补偿任务必须做幂等？——`embedAndStore` 重跑前需先清理旧分段/向量（或以 versionId 幂等覆盖），否则重试会产生重复 chunk；这一点可以引申到分布式锁配合（见笔记 19）。

## Q3: 下面是一条被 @Deprecated 标记的事件链路。请评估它当前的存活状态，并说说如果要安全下线，你会怎么做？

**难度**: ⭐⭐

```java
    private void publishConvertedEvent(KnowledgeDocument document) {
        log.info("发送文档CONVERTED事件，documentId: {}", document.getDocId());
```

**参考答案**:

结论先行：这条链路已经是「全链路死代码」——发布方法是 private 且全库无任何调用点，事件类也没有任何监听器引用，但文件还在仓库里误导读者。

- **考察什么**：能否用「引用分析」确认死代码的实际存活状态，而不是只看注解；能否给出有序、可回滚的下线步骤。
- **答题要点**：
  1. 状态判定：`publishConvertedEvent` 是 private 方法且全库搜索无调用点（连定义所在的类里都没人调它），`DocumentConvertedEvent` 的全部引用只有自身与这个死方法——没有 `@EventListener`/`ApplicationListener` 在消费它。背景是产品决策变化：文档解析完成后改为用户在前端手动触发分段（因为分段方式需要用户选择），事件驱动的自动分段被废弃。
  2. 危害：代码能编译、能运行，但读者会误以为「解析完成自动分段」仍生效；`publishChunkedEvent`（CHUNKED 事件）还在同一文件里活跃使用，说明事件机制本身没废，只有 CONVERTED 这一段废了——review 时要能区分。
  3. 安全下线步骤：① 全库引用确认（IDE Find Usages + grep，覆盖事件类/发布方法/监听器三类对象）；② 若仍有监听器先下线监听器再删发布点；③ 确认零引用后删除 `publishConvertedEvent`、`DocumentConvertedEvent` 类及对应 import（注意 `eventPublisher` 被 CHUNKED 事件使用，必须保留）；④ 编译 + 启动 + 核心回归（上传→解析→手动分段→向量化）；⑤ 下线决策写入变更记录。
- **加分项**：肯定 `@Deprecated` 的 Javadoc 写了「为什么」（需要用户选择分段方式）——决策上下文值得留，但应留在提交信息或设计文档里而不是死代码上；能说出 private 未调用方法可被 IDE 的「unused declaration」检查批量发现；能结合笔记 17（事件驱动全流程）讲清这条链路当初的设计。

**验证**：`grep -rn "DocumentConvertedEvent" src/` 只有事件类自身与 `publishConvertedEvent` 方法内的构造，共 5 处、无监听器；删除后 `mvn compile` 通过即为零引用佐证。

**追问**：为什么不直接删，还要走确认流程？——Spring 事件是隐式契约，监听器可能通过 `@TransactionalEventListener`、XML 或反射注册；删除是单向操作，先确认引用再动手是评审习惯。

## Q4: 从这份 application.yml 里，你能读出「文档解析接口的超时设计」和哪些排障线索？

```yaml
elasticsearch:

  base-url: https://dashscope.aliyuncs.com/compatible-mode/v1
  model-name: text-embedding-v4
  api-key: @dashscope.api.key@

```

```yaml
# 文件解析服务配置（MinerU 官方精准解析 API，异步协议）
file:
  parse:
    api:
      url: https://mineru.net/api/v4 # MinerU 官方 API 地址（本地自建 mineru-open-api 则改为 http://host:port）
```

**参考答案**:

结论先行：解析类接口的超时要远大于普通接口，因为它走的是「提交任务 + 轮询结果」的异步协议，超时预算覆盖的是整个解析生命周期，而不是单次 HTTP 往返。

- **考察什么**：能否从两个数字（30s / 600s）反推接口的工作方式，以及是否具备「拿配置当排障地图」的意识。
- **答题要点**：
  1. `connect-timeout: 30000` 是单次 HTTP 连接/读取超时——申请上传链接、PUT 上传、每次轮询各自受它约束；`response-timeout: 600000` 是异步轮询的**整体**超时，注释写明「大文档解析耗时较长」。大 PDF 的 MinerU 解析是分钟级任务，600s ≈ 10 分钟的预算是合理的；如果误把整体预算配成 30s，就会出现「解析明明在正常进行、客户端却提前报超时」的假故障。
  2. 排障线索：看到这两个值就知道「解析任务跑了 8 分钟还没结果」在预算内属正常，该查的是 MinerU 侧任务状态而不是重试；`model-version: pipeline` 说明当前用的解析模型档位（注释提示 vlm 推荐）；ES 段的 `dimensions: 1536` 与 `text-embedding-v4` 是检索链路的第一排查项——维度不匹配会直接导致向量写入/检索报错。
  3. 对比记忆：普通业务接口超时通常秒级（如 druid `max-wait: 60000` 是连接池等连接的上限），与解析类分钟级预算属于不同量级，配置时要按接口形态分类，不能一套超时全站复用。
- **加分项**：指出同一文件里 `token` 是明文提交的真实密钥（本文摘录时隐去）——安全坏味道，应改用环境变量或配置中心注入；对比 `api-key: @dashscope.api.key@` 是 Maven resource filtering 占位符，key 不在仓库里，这是正面做法，两者形成鲜明对照；能说出自建 mineru-open-api 时只需改 `url`，超时参数语义不变。

**验证**：对照 `MinerUProcessBaseServiceImpl` 的实现确认两个超时分别作用于单次请求与轮询总时长；将 `response-timeout` 临时调小可复现「大文档解析超时」故障，验证预算语义。

**追问**：轮询整体超时到了之后代码应该做什么？——记录任务终态、释放上传的中间资源、给用户失败反馈；不能默默吞掉，否则文档会停在 CONVERTING 状态（这正是补偿任务与状态机的价值）。

## Q5: JDBC URL 里的 rewriteBatchedStatements=true 到底改变了什么？没有它，saveBatch 的表现是什么？

**难度**: ⭐⭐⭐

`src/main/resources/application.yml`

```yaml
  datasource:
    type: com.alibaba.druid.pool.DruidDataSource
    url: jdbc:mysql://127.0.0.1:3306/know_engine?rewriteBatchedStatements=true
    username: know_engine
    password: know_engine
    driver-class-name: com.mysql.cj.jdbc.Driver
```

`src/main/java/cn/hollis/llm/mentor/know/engine/document/service/impl/DocumentProcessServiceImpl.java`

```java
        // 5. 批量保存片段
        Stopwatch stopwatch = Stopwatch.createStarted();
        boolean saveResult = knowledgeSegmentService.saveBatch(knowledgeSegments);
        Assert.isTrue(saveResult, "保存知识片段失败");
        log.info("保存知识片段耗时: {}", stopwatch.elapsed().toMillis());
```

**参考答案**:

结论先行：MySQL 批量写真正的开关在 JDBC 驱动层，不在 MyBatis-Plus——`rewriteBatchedStatements=true` 才让驱动把一批 INSERT 合并重写，没有它 `saveBatch` 名为批量、实为逐条。

- **考察什么**：能否分清「应用层的 batch API」「MyBatis-Plus 的 executeBatch」「MySQL 驱动的重写开关」三层各自做什么——这是只背过「加了 rewriteBatchedStatements 就快了」的人答不出的。
- **答题要点**：
  1. 三层分工：MyBatis-Plus 的 `IService#saveBatch` 底层 `executeBatch` 是 for 循环逐条 flush，每条片段发一条独立 `INSERT INTO ... VALUES (...)`，事务在全部执行完才统一提交；MySQL 驱动默认收到 batch 也是逐条发送；`rewriteBatchedStatements=true` 让驱动在发送前把多条同结构 INSERT 合并成一条多 VALUES 的 INSERT（`INSERT INTO t VALUES (...),(...),(...)`），网络往返从 N 次降到 ⌈N/批⌉ 次，解析与执行开销大幅下降。
  2. 没有它的表现：一个几百段的文档入库时每段一条 INSERT + 一次往返，总耗时随段数线性增长且事务变长（长事务持锁时间久）；代码里专门用 `Stopwatch` 记录保存耗时并打日志，就是当年定位这个问题的痕迹。
  3. 该开关只对 MySQL 驱动生效，写在 URL 参数里（本例是 URL 里唯一的参数），与连接池（druid）、ORM 层配置无关——换数据库方言时不能照搬。

结论先行：按 `lockKey`（`scene#key` 格式）grep 日志，用五个关键字还原每个锁的生命周期时间线：`lock for key` → `lock success for key` → `unlock for key`，失败路径是 `try lock for key` → `lock failed for key`。

- **考察什么**：能否把日志语句与锁的真实行为一一对应，从时间线推断竞争、阻塞、异常三类问题——这是运维排障的读码功夫。
- **答题要点**：
  1. 竞争/阻塞：同一 key 连续多条 `lock for key`（无 wait 参数）却迟迟没有对应的 `lock success`，说明线程阻塞在无上限的 `rLock.lock()` 上——这是最危险的分支（`waitTime` 用默认值时直接 lock()，不设等待上限）；有 `try lock for key ... wait` 后跟 `lock failed for key`，则是等待超时的正常竞争失败，随后业务抛 `acquire lock failed`。

  3. 读代码时还应发现的坏味道：`catch (Throwable e) { throw new Exception(e); }` 把包括 Error 在内的一切异常包成 checked Exception，破坏了异常类型语义；日志用 `String.format` 而非 `{}` 占位符，且 `lock failed` 只在 tryLock 分支可能走到。`@Order(Integer.MIN_VALUE)` 保证锁切面最先进、最后出，锁覆盖整个业务方法。
- **加分项**：能说出「对比同一 key 的 `lock success` 到 `unlock` 的时差即临界区耗时」，用连续调度周期的时间线判断是竞争还是临界区过长；能建议给 `lock()` 无等待分支补 `waitTime` 或至少告警，作为 review 产出。

**验证**：在 dev 环境并发触发同一文档的分段接口，观察日志出现「lock for key」→「try lock」/「lock failed」序列；用 `redis-cli` 的 `KEYS *scene#*` 确认锁键命名与代码一致。

**追问**：为什么解锁前必须 `isHeldByCurrentThread()`？——Redisson 的看门狗续期下锁可能已过期易主，无条件 unlock 会抛异常或误删他人锁；这是分布式锁实现的经典考点。

```java
        if (jsonString == null || jsonString.trim().isEmpty()) {
            return "{}";
        }

        String fixed = jsonString.trim();

        // 1. 提取 JSON 内容（移除 markdown 代码块标记）

        fixed = removeLeadingTrailingGarbage(fixed);

        fixed = fixTrailingCommas(fixed);

        fixed = fixMissingQuotes(fixed);

        fixed = fixEscapeChars(fixed);

        }
    }
```

**参考答案**:

结论先行：先补 `JsonUtil`——它是纯函数、零外部依赖、输入输出确定，是性价比最高的单测对象；而且它修的每一个坏 JSON 形态都是线上真实发生过的故障样本，fixture 现成。

- **考察什么**：测试策略的优先级判断（纯函数优先、风险与成本权衡）与 fixture 工程化能力，而不是「补测」的口号。
- **答题要点**：
  1. 选择理由：`fixJson` 是 static 工具方法，不需要 Spring 容器、不碰网络与数据库，测试可以毫秒级跑进 CI；它是意图识别、问题重写等所有 Structured Output 链路的公共兜底，坏了是全局故障——高风险 × 低成本，第一优先级。现有 `src/test` 下只有切分器、Neo4j、RAG 管道类测试，`JsonUtil` 零覆盖。
  2. fixture 造法：把踩坑笔记（43）里枚举的坏样本逐一固化为用例——```json 代码块包裹、首个 `{` 前有解释性文字、中文引号/单引号、尾部逗号、键名缺引号、字符串内裸换行；用 `@ParameterizedTest` + `@MethodSource` 建立「输入 → 期望」表。断言两层：结构层（`objectMapper.readTree(fixJson(input))` 不抛异常）+ 语义层（解析后关键字段值正确，如 `intent == "车辆保养周期规定"`），只断言「能读」不校验内容等于没测。

**追问**：为什么不优先给 AI 链路补单测？——链路的不确定性来自模型，单测只能验证确定性代码（参数组装、降级分支、解析逻辑）；模型行为用 Q7/Q8 的 benchmark 与数据集回归覆盖，两层测试各管各的确定性。

结论先行：被注释的 `List.of(compressedQuery, query)` 说明这里曾是「改写后 Query + 原始 Query」双路下发，现在收敛为 `singletonList(compressedQuery)`——只检索改写后的问题，演进动因是下游聚合复杂度与收益不成正比。

- **考察什么**：能否解释双 Query 方案为什么被放弃，以及是否掌握从注释代码、git 历史做演进考古的方法与边界。
- **答题要点**：
  1. 双 Query 的代价：LangChain4j 的 QueryTransformer 支持一对多，`List.of(改写, 原始)` 会让所有检索器（ES 向量、全文、SQL、Cypher）各跑两次，随后 RRF 融合的输入列表翻倍、BGE 重排候选翻倍——检索与重排成本近乎 ×2；而问题改写本身已经做了上下文补全与指代消除，原始问题对多轮场景反而是噪音（「它多少钱」这种指代问题原样检索必空），多路收益很低。这与 LangChain4j 官方 `CompressingQueryTransformer` 返回单个压缩 Query 的设计一致。
  2. 收敛收益：单路检索让下游聚合器逻辑简单（Q1 片段里结构化结果打 skipRerank 标记透传、非结构化走 RRF+BGE 的混合聚合，输入翻倍会把分类合并逻辑复杂化），token 成本与时延可预期；改写质量由提示词 + benchmark（Q7）保障，而不是靠多路冗余兜底。
  3. 考古方法：读注释代码与 Javadoc 的措辞变化 → `git log -p` / `git blame` 看这行的提交时间点与关联提交信息 → 对照笔记（30 单轮版改写、46 多轮版改写）确认演进动机。考古结论要标注证据等级：注释代码只能证明「曾经存在」，动因必须以提交信息或笔记为准，不能脑补。
- **加分项**：指出注释代码的正确归宿是删除（git 已留史）；能注意到该组件还做了虚拟线程异步回写 `transform_content`（把改写前后问题留给前端展示与排障），说明单 Query 并没有丢信息——原始与改写后的问题都落库可查，这解释了为什么放弃双路检索是安全的。

**验证**：`git log -p -- src/main/java/.../KnowEngineQueryTransformer.java` 查找 `List.of(compressedQuery, query)` 的增删记录；对照笔记 30/46 与 09 题库 Q2 的链路陈述。

**追问**：什么场景下双 Query 反而值得？——改写置信度低（改写可能引入幻觉）且下游是廉价检索（如纯 ES）时，多路召回 + 去重融合能提高容错；本项目的痛点恰在重排与结构化链路的成本，所以收敛。

## Q11: 记忆缓存这段代码里 evictCache 只有 Redis 删除。结合调用点说说：上下文隔离为什么从「两次删除」演进到「一次删除」？当前的隔离口径是什么？

**难度**: ⭐⭐⭐

`src/main/java/cn/hollis/llm/mentor/know/engine/chat/memory/DatabaseChatMemoryStore.java`

```java
    /**
     * 清除指定会话的缓存（在新一轮对话开始前调用，确保从DB重新加载最新消息）
     */

        try {
            stringRedisTemplate.delete(buildKey(memoryId));
        } catch (Exception e) {
            log.warn("Redis 清除聊天记忆缓存失败, memoryId={}", memoryId, e);
        }
    }
```

`src/main/java/cn/hollis/llm/mentor/know/engine/chat/service/ChatApplicationService.java`

```java
                                .flatMapMany(intentRecognitionResult -> {
                                    // 意图识别完成后清除缓存，避免意图识别的AI响应污染后续RAG对话的历史记忆
                                    databaseChatMemoryStore.evictCache(finalConversationId);
```

**参考答案**:

结论先行：全库只有这一处 `evictCache` 调用——意图识别完成后删一次 Redis 记忆。从「本应两次删除」收敛为「一次删除 + DB 侧过滤」的双保险，本质是把多 AiService 的上下文隔离从「删得多」改为「写的时候就分干净」。

- **考察什么**：能否讲清多 Agent 共享 ChatMemoryStore 的污染机理、两次/一次删除的差异，以及当前隔离口径的完整边界——这题答对细节只能靠读过这两个类。
- **答题要点**：
  1. 污染机理：意图识别 AiService 的输入输出（含 JSON 格式约束和识别结果）会经 `updateMessages()` 写入 Redis；问题重写从同一 store 读记忆时把 JSON 当成历史对话注入改写提示词，产生「打不着火 → 改写成查询车辆信息」的错误——这是踩坑笔记 47 的原始案例。
  2. 一次删除的口径：`evictCache` 只删 `know-engine:chat-memory:{conversationId}` 这一个 Redis key（TTL 1 小时），**不动 DB**；删除后 RAG 阶段 `getMessages` 未命中缓存、走 `loadFromDatabase` 从 MySQL 重载——而 DB 只保存用户消息与 AI 回复（`saveUserMessage`/`updateContent`），意图识别的中间产物从未落库，所以一次删除即恢复干净上下文。与 `deleteMessages`（连 DB 的 `deleteMessagesByConversationId` 一起删，会话级销毁）职责不同，不能混用。
  3. 演进逻辑：最初设计里一轮对话要做两次记忆删除，但第一处删除一直缺失导致事故；修复时发现 DB 侧本来就没有脏数据，于是在意图识别后（`flatMapMany` 回调里、RAG 之前）删一次即可，`loadFromDatabase` 里再按消息类型只装配 USER/ASSISTANT 做第二道保险——隔离职责从「事后删干净」前移到「写入时分干净」。
- **加分项**：能说出缓存重载的代价可控（一次 DB 查询最近 10 条）且换来正确性；能指出 `evictCache` 的 try-catch 让 Redis 故障时降级为直接读 DB，不阻断对话；能把它与 09 题库 Q1 案例5 的 benchmark 决策（换模型 vs 架构隔离）串成完整故事。

**验证**：`grep -rn "evictCache" src/main/java` 确认仅 `DatabaseChatMemoryStore` 定义 + `ChatApplicationService` 一处调用；人工对话一轮后检查 Redis key 与 `chat_message` 表内容，验证意图识别 JSON 只进缓存不进 DB。

**追问**：如果意图识别结果将来也要持久化用于分析，隔离方案要怎么改？——落库时打独立类型标记，`loadFromDatabase` 按类型过滤；同时 `evictCache` 的时机不变——读侧过滤 + 写侧分类是可持续的口径，不能依赖「恰好没写」。

## Q12: 实体基类上有一个 @Version 字段。它防的是什么并发问题？和项目里的分布式锁是怎么分工的？

**难度**: ⭐⭐⭐

`src/main/java/cn/hollis/llm/mentor/know/engine/document/entity/BaseEntity.java`

```java
    /**
     * 乐观锁版本号
     */
    @Version
    protected Integer lockVersion;

    /**
     * 是否删除：0-未删除，1-已删除
     */
    @TableLogic
    protected Integer deleted;
```

`src/main/java/cn/hollis/llm/mentor/know/engine/config/MybatisPlusConfig.java`

```java
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        //乐观锁插件
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
        //防全表更新与删除插件
        interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());
        //分页插件
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
```

`src/main/java/cn/hollis/llm/mentor/know/engine/document/service/impl/DocumentProcessServiceImpl.java`

```java
        // 更新文档版本
        document.setCurrentVersionId(versionId);
        boolean docUpdateResult = knowledgeDocumentService.updateById(document);
        Assert.isTrue(docUpdateResult, "更新文档版本失败");
```

**参考答案**:

结论先行：`@Version` + `OptimisticLockerInnerInterceptor` 实现行级乐观锁，防的是「读-改-写」之间的丢失更新（Lost Update）；分布式锁拦大部分并发于门外，乐观锁兜住最后一行写入的竞态，两者是粗粒度与细粒度的互补分工。

- **考察什么**：能否把注解、插件配置、调用点三段代码串成完整机制——`updateById` 生成 `UPDATE ... SET ..., lock_version = lock_version + 1 WHERE id = ? AND lock_version = ?`，受影响行数为 0 即并发冲突，这正是第三段代码 `Assert.isTrue(docUpdateResult, ...)` 存在的原因。
- **答题要点**：
  1. 防什么：多版本文档场景下，同一 `knowledge_document` 行会被多处并发修改——版本切换（`switchVersion` 改 `currentVersionId`）、状态机流转、清理任务回写状态。两个事务都基于旧快照做 update 时，没有版本号则后写覆盖先写（先提交的状态变更被静默丢掉）；有 `@Version` 后只有携带最新版本号的事务能写成功，失败方拿到 false 走断言报错、由调用方重读重试。
  2. 前提条件：乐观锁插件必须注册（第二段代码），否则 `@Version` 注解不生效——只贴实体不说插件是半懂；`lockVersion` 必须随实体一起查出再更新（新 new 的实体没有版本值时插件不拦截）。
  3. 分工：`@DistributeLock`（Redisson）保护**跨进程的长临界区**——文档分段、向量化整条流程要防止同一文档被两个节点同时处理（见笔记 19），这是锁的领域；`@Version` 保护**单行最终写入**——不需要长持锁的短更新，或作为锁范围之外的兜底（如补偿任务与人工操作同时更新一行）。无锁无阻塞、失败即知，代价是调用方必须处理失败分支——代码里 `Assert.isTrue` 就是失败分支的体现。
- **加分项**：能对比三者适用层：分布式锁（进程间互斥、可保护多表多步骤）、数据库行锁 `SELECT ... FOR UPDATE`（悲观、阻塞、本仓库未用）、`@Version`（乐观、无阻塞、失败重试）；能指出 `@TableLogic deleted` 与乐观锁共存时逻辑删除也会带版本条件；能说出乐观锁适合「冲突概率低」的写场景，高冲突时应改用锁或队列——本项目的分段流程冲突概率被分布式锁压低，乐观锁兜底成本才划算。

**验证**：并发两个线程对同一文档执行 `switchVersion`，观察其中一个 `updateById` 返回 false 并抛出断言异常；看 SQL 日志（`log-impl: StdOutImpl`）确认 UPDATE 语句携带 `lock_version` 条件。

**追问**：为什么文档状态机用乐观锁而不是状态条件更新（`UPDATE ... WHERE status = 'CONVERTED'`）？——两者都能防竞态；版本号是通用机制不需要为每种状态流转写专门 SQL，状态条件更新则语义更显式，能讲出 trade-off 而不是站队即可。
