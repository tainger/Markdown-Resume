# ✅如何做好 Agent 评测

> 一句话总结：**Agent 评测 = 分层评什么（模型/组件/轨迹/端到端）× 四种手段（规则断言/LLM-as-a-Judge/人工/在线 A/B）× 固定数据集回归**。没有回归数据集的 Agent 评测，都是"抽卡看运气"。

---

## 1. 为什么 Agent 评测比传统软件测试难

传统软件测试：输入确定 → 输出确定 → `assert(output == expected)`。

Agent 评测的四个难点：

| 难点 | 具体表现 | 应对思路 |
|:---|:---|:---|
| **非确定性** | 同一输入两次运行，走的路径、给的说法都不同 | 不比"逐字输出"，比"结构化结果/最终效果" |
| **路径不确定** | 达成目标可以走 N 条不同的工具调用序列 | 评轨迹（trajectory）质量而非死磕单一路径 |
| **错误会级联** | 意图识别错 → 后面全错；中间某步幻觉 → 结果污染 | 分层评测 + 逐层归因（先定位哪层坏了） |
| **环境依赖** | 工具返回的真实数据随时间变化（票价、天气） | 测试环境用 mock/录制回放（record-replay） |

核心认知转变：**传统测试测的是"代码逻辑"，Agent 评测测的是"概率系统的统计行为"**。单次通过/失败意义有限，要看 N 次运行的通过率和分布。

---

## 2. 分层评测体系（评什么）

不要一上来就测端到端——那样失败了你不知道是谁的锅。按分层归因：

```
┌─────────────────────────────────────────────────┐
│  L4 端到端：任务完成率（用户视角，最贵最慢）        │
│    "帮我规划上海到杭州的出差行程" → 方案合规可执行？ │
├─────────────────────────────────────────────────┤
│  L3 轨迹评测：中间步骤对不对（排障视角）            │
│    工具选择序列、参数正确性、循环/死锁检测          │
├─────────────────────────────────────────────────┤
│  L2 组件评测：单个模块的召回/准确率                 │
│    意图识别、问题改写、RAG 检索、工具参数生成        │
├─────────────────────────────────────────────────┤
│  L1 模型评测：底层 LLM 能力（换模型时才跑）          │
│    指令遵循、JSON 输出稳定性、函数调用能力           │
└─────────────────────────────────────────────────┘
```

| 层级 | 评什么 | 典型指标 | 成本 | 跑的频率 |
|:---|:---|:---|:---|:---|
| **L1 模型层** | 换模型/升版本时的能力基线 | MMLU、函数调用 bench、JSON 合法率 | 低（公开数据集） | 换模型时 |
| **L2 组件层** | 意图识别/RAG/改写/工具参数 | 准确率、召回率、F1、Top-k 命中率 | 中 | 每次 prompt/代码变更 |
| **L3 轨迹层** | 工具调用序列是否合理 | 轨迹匹配率、多余调用数、死循环率 | 中高 | 核心流程变更 |
| **L4 端到端** | 任务最终完成情况 | 任务完成率、人工满意度、合规通过率 | 高 | 发布前 + 每日巡检 |

**落地建议**：L2 组件评测是性价比最高的投入点，因为它可断言、可回归、可归因。比如三层意图识别的 L1/L2/L3 各自命中率，天然就是组件级评测指标。

## 3. 四种评测手段（怎么评）

### 3.1 规则断言（最便宜，优先用）

凡是**结构可预期**的输出，全部用代码断言，不要用大模型评：

```java
// 意图识别输出：结构固定，直接断言
assertThat(result.getIntents()).hasSize(1);
assertThat(result.getPrimary()).isEqualTo(IntentCategory.REIMBURSEMENT);
assertThat(result.getConfidence()).isIn(List.of(Confidence.HIGH, Confidence.MEDIUM));

// 工具参数：格式可校验
assertThat(dateStr).matches("^\\d{4}-\\d{2}-\\d{2}$");

// 政策合规：规则明确（4 职级 × 3 城市等级）
assertThat(plan.getHotelPrice()).isLessThanOrEqualTo(policyLimit);
```

适用：意图分类、参数格式、状态机流转、政策硬约束、错误码。

### 3.2 LLM-as-a-Judge（评"好不不好"，不能断言的部分）

凡是**开放式生成**的内容——方案描述质量、回答的语气、摘要是否遗漏要点——用 LLM 当裁判。

**三种裁判模式**：

| 模式 | 做法 | 适用 |
|:---|:---|:---|
| **逐点评分** | 给输出按 rubric 打 1-5 分 | 单答案质量 |
| **成对比较** | A/B 两个答案，裁判选优 | 版本对比、模型选型 |
| **参考对照** | 有参考答案，裁判评相似度/覆盖度 | 有标注数据时 |

**Rubric 拆解示例**（行程方案评测）：

```
从以下 5 个维度各打 1-5 分，输出 JSON：
1. 完整性：去程/返程/住宿是否都覆盖？缺一项扣分
2. 合规性：总价是否超差旅标准？舱位/酒店星级是否符合职级？
3. 合理性：时间衔接是否可行（去程落地时间 < 酒店入住 < 返程）？
4. 优化性：给出的方案是否是候选中综合分较高的？
5. 表达性：Markdown 结构清晰、无内部名词泄露？
```

**Judge 的四个关键纪律**：

1. **定义越细越好**："打分"不可靠，"如果缺少返程信息则完整性 ≤ 3"才可靠
2. **裁判模型 ≠ 被测模型**：避免自我偏好（同源模型给自己打高分）
3. **位置偏差**：成对比较时交换 A/B 顺序跑两次，结果一致才可信
4. **抽检校准**：定期抽 5% 用人工复核 Judge 的打分，计算 Judge 与人的一致率（一般 ≥ 80% 才可用）

### 3.3 人工评测（最贵，用在对的地方）

只在三个地方用人工：

- **建基准集**：初期标注 100-200 条golden 数据，之后 Judge 才有对照
- **校准 Judge**：验证 LLM 裁判靠不靠谱
- **灰度抽检**：上线后按比例抽样人工复核（如 1%）

人工标注也要有纪律：写标注规范（每条含输入、期望行为、判分标准）、双人标注算一致性（Cohen's Kappa ≥ 0.7）、分歧仲裁。

### 3.4 在线评测（生产环境的真相）

离线数据集再好也是"考卷"，线上才是"实战"：

- **隐式反馈**：用户重试率、会话放弃率、多轮追问率（追问多 = 首答没满足）、thumbs up/down
- **显式反馈**：点赞点踩 + 用户自由文本反馈
- **Human-in-the-Loop 转化率**：Agent 中途 ask_user 的频率（过高说明自主能力差）
- **A/B 实验**：新旧版本各分 5% 流量，比核心指标

## 4. 核心指标体系

### 4.1 效果类

| 指标 | 定义 | 采集方式 |
|:---|:---|:---|
| **任务完成率** | 端到端跑通目标任务的比率 | 人工判定 + Judge |
| **意图准确率** | 分类正确的比例 | 断言 |
| **工具选择正确率** | 该调的工具调了、不该调的没调 | 轨迹比对 |
| **参数正确率** | 传参格式/取值正确 | 断言 + Judge |
| **轨迹效率** | 完成任务的实际步数 / 理论最少步数 | 轨迹统计 |
| **幻觉率** | 编造了不存在的事实/数据的比例 | 参考对照 + 抽检 |

### 4.2 成本与性能类

| 指标 | 为什么重要 |
|:---|:---|
| **单任务 token 成本** | 多智能体架构下容易被子 Agent 放大 |
| **P50/P95 端到端延迟** | 用户体感；多 Agent 串行是延迟大头 |
| **工具调用次数** | 次数多 = token 贵 + 慢 + 出错概率大 |
| **缓存命中率** | prompt cache 命中率直接影响成本 |
| **熔断触发次数** | 工具健康度的间接指标 |

### 4.3 稳定性类

| 指标 | 定义 |
|:---|:---|
| **同一用例 N 次运行通过率** | 10 次里通过几次？< 10/10 说明有随机性问题 |
| **输出格式合法率** | JSON 解析成功率、字段齐全率 |
| **死循环/超 maxIters 率** | 保险丝触发频率 |

**关键实践：Pass@k 与 Pass^k**
- Pass@k：跑 k 次至少 1 次成功的概率（乐观，适合有重试的场景）
- Pass^k：跑 k 次全部成功的概率（严格，适合不可重试的写操作如下单）
- **下单、支付这类写操作必须用 Pass^k 评估**，一次失败就是真实事故。

## 5. 评测数据集怎么建

### 5.1 来源（按优先级）

1. **真实线上 case**（最值钱）：从生产日志里捞，特别是**失败的、被重试的、被点踩的**
2. **边界构造**：故意造对抗样本——空参数、超长输入、日期格式错、多意图混杂、口语化改写
3. **人工编写**：覆盖每个意图类别 × 每种表达变体
4. **模型生成 + 人工审核**：让 LLM 变换问法扩量，人只做审核

### 5.2 数据集设计原则

| 原则 | 说明 |
|:---|:---|
| **分层覆盖** | 每个 L2 组件都要有独立测试集（意图集、改写集、RAG 问答集） |
| **难度梯度** | simple / medium / hard 分档，防止"只会做简单题"的虚高指标 |
| **对抗样本占比 ≥ 20%** | 全是正常样本测不出问题 |
| **golden 轨迹** | 端到端 case 不只存最终答案，还存期望的工具调用骨架（宽松匹配） |
| **版本化** | 数据集进 Git，指标可以跨版本对比，新增 case 只增不删 |

### 5.3 mock 与录制回放

评测环境的两大坑：外部工具数据会变、调真实工具又慢又贵又不可重复。

**解法：录制回放（Record & Replay）**

```
录制阶段：真实环境跑一遍 → 录下每次工具调用的 请求/响应 对
评测阶段：Agent 跑到工具调用时 → 命中录制库直接回放 → 不真实出网
```

- 优点：可重复、快、便宜；对 Agent 的推理路径零干扰
- 缺点：录制数据会过期 → 定期重录；新工具调用没命中 → 走 mock 兜底并标记

## 6. 端到端评测的两种打分法

### 6.1 最终状态打分（End State）

只看最终产物是否达标，不关心中间怎么走的：

```
输入："下周去杭州出差3天，帮我规划"
通过条件（全部满足）：
  ✓ 包含往返交通方案且日期与"下周"匹配
  ✓ 包含酒店且总价不超该职级差旅标准
  ✓ 行程无时间冲突
  ✓ 有明确的确认引导（没擅自下单）
```

适合：写操作类任务（提交差旅单、生成报销单）。

### 6.2 轨迹打分（Trajectory）

看中间步骤是否合理。两种匹配强度：

| 模式 | 判定方式 | 适用 |
|:---|:---|:---|
| **精确轨迹匹配** | 工具序列与 golden 完全一致 | 流程固定性强的场景（太严，慎用） |
| **子集/顺序匹配** | 必调的工具都调了、顺序对、无多余危险调用 | 大多数场景 |
| **LLM 评轨迹** | Judge 看 tool call 序列判断合理性 | 开放性任务 |

**特别要评的两类轨迹失败**：

1. **多余调用**：反复查同一个工具（结果没用上）→ token 浪费
2. **危险调用**：查询场景误触写工具 → 最小权限没兜住

## 7. 常用评测框架速查

| 工具 | 定位 | 适合 |
|:---|:---|:---|
| **LangSmith** | LangChain 官方，trace + 数据集 + 评测一体 | LangChain 系项目 |
| **Ragas** | RAG 专项指标（faithfulness / context recall） | RAG 组件评测 |
| **DeepEval** | pytest 风格的 LLM 单测（assert_test） | 想把评测嵌进 CI |
| **promptfoo** | 声明式 YAML 配置多模型对比 | 模型/prompt 横评 |
| **τ-bench（tau-bench）** | Agent 工具调用 + 用户模拟 + 规则校验 | 端到端 Agent bench |
| **AgentBench** | 多环境通用 Agent 能力基准 | 模型层选型 |
| **自研** | 业务强绑定（意图集、政策合规校验） | **最终一定走到这** |

现实建议：**公开基准用于模型选型，业务评测一定自研**——你的差旅政策、意图体系，公开数据集根本不覆盖。

## 8. 在 CI 里跑起来（工程化落地）

评测不做进 CI 就会腐化。建议的流水线位置：

```
PR 提交
  │
  ├─ 单元测试（纯逻辑，秒级）
  ├─ L2 组件评测（意图集 300 条，断言为主，~2 分钟，阻断合并）
  │     └─ 指标：意图准确率 ≥ 基线-1%，否则 fail
  │
发布前（手动/每日定时）
  ├─ L4 端到端评测（录制回放，50 条核心 case，~10 分钟）
  │     ├─ 任务完成率 ≥ 90%
  │     └─ Pass^10 ≥ 95%（写操作 case）
  └─ Judge 评分报告 + 与上版本 diff 报告（人工过目）
```

**核心纪律：每次 prompt/模型/框架的变更都必须跑回归**。Agent 系统最典型的退化就是——改了意图识别的 prompt，端到端某条链路悄悄坏了，两周后才发现。

## 9. 以 gogo-agent 为例的评测清单

对照多智能体差旅系统，各层该建什么评测：

| 层 | 评测对象 | 数据集 | 手段 | 核心指标 |
|:---|:---|:---|:---|:---|
| L2 | 三层意图识别 | 每类意图 20+ 条 + 口语化改写 + 多意图混合 | 断言 | L1/L2/L3 分层命中率、整体准确率、误路由率 |
| L2 | 问题改写 | 多轮指代对话对（"那个酒店改一下"） | 参考对照 | 指代消解正确率 |
| L2 | RAG 检索 | 政策/景点问答对 | Ragas 指标 | context recall、faithfulness |
| L3 | 工具选择 | golden 轨迹（如规划必查差旅单→查偏好→搜交通） | 子集匹配 | 工具选择正确率、多余调用数 |
| L3 | 工具参数 | 边界参数用例（错日期格式、超 3 天天气查询） | 断言（beyond_range 信号是否触发） | 参数正确率、信号引导正确率 |
| L4 | 行程规划端到端 | 50 条核心 case（不同城市/职级/预算） | End State + Judge | 完成率、政策合规率、Pass^10 |
| L4 | 写操作（提交差旅单/下单） | 幂等重复 case | 断言 + 写后验证 | 重复创建率、Pass^k |
| 在线 | 全链路 | 生产流量 | 隐式反馈 | 重试率、追问率、点踩率、熔断次数 |

**优先级建议**：先把「意图识别断言集」+「端到端录制回放 50 条」建起来，这两块投入产出比最高——前者拦住 80% 的路由级退化，后者兜住发布质量。

## 10. 常见反模式

| 反模式 | 问题 | 纠正 |
|:---|:---|:---|
| 只跑端到端 | 失败无法归因，修复靠猜 | 先建 L2 组件评测 |
| 用 LLM 评一切 | 慢、贵、Judge 本身不稳定 | 能断言的先断言 |
| 数据集一成不变 | 过拟合测试集，线上照样翻车 | 持续从线上失败 case 回流 |
| 单次运行下结论 | 非确定性系统单次无意义 | N 次统计 + Pass^k |
| 指标只有准确率 | 忽略了成本/延迟/安全 | 效果×成本×稳定性三维权衡 |
| 评测集即训练集 | prompt 是照着评测集调的 | 评测集与开发集分离，评测集只增不改 |

---

## 一句话总结

**评测左移（组件级断言进 CI）、失败回流（线上 badcase 进数据集）、写操作用 Pass^k、Judge 要校准**——做到这四条，Agent 才从"demo 能跑"进化到"敢上线"。
