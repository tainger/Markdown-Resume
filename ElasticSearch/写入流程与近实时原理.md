# 写入流程与近实时原理

高频追问链：「一条文档怎么写进去的 → **为什么是近实时** → 宕机了数据丢不丢 → 更新删除为什么贵」。一条主线：**内存 buffer + translog，refresh 可搜，flush 落盘**。

---

## 一、单文档写入全链路（必背，能白板画）

```
Client ──► ① Coordinating Node（协调节点）
              │ 按 routing 计算目标分片: shard = hash(routing) % primary_count
              ▼
           ② Primary Shard（主分片所在节点）
              │ 校验 Mapping → 写入内存 buffer → 追加 translog
              ▼
           ③ 并行同步到所有 In-Sync 副本分片
              │
              ▼ 达到 wait_for_active_shards（默认 quorum：主+过半副本）
           ④ Primary 返回 → 协调节点响应 Client
```

| 步骤 | 关键点 |
|:---|:---|
| ① 路由 | 不指定 `routing` 就用 `_id`；**相同 routing 必落同一分片**（业务可用它做本地化join） |
| ② 主分片写入 | 只写内存 + translog，**此时尚不可搜索** |
| ③ 副本同步 | 主分片**串行定序**后并行转发副本，保证副本顺序一致 |
| ④ 响应条件 | `wait_for_active_shards=quorum`：过半分片组活着才允许写，兼顾可用性与不丢数据 |

## 二、为什么是「近实时」（NRT）而不是实时

写入只是进了**内存 buffer**，要等 **refresh** 把 buffer 生成一个**新 segment** 后，这个 segment 才能被搜索（Lucene 的 segment 一旦生成就是不可变且可读的）。`index.refresh_interval` 默认 **1s**——所以 ES 是「**1 秒内可见**」的近实时。

> 面试话术：**「不是不能更快，是 trade-off：refresh 越频繁，小 segment 越多，merge 压力越大，写入吞吐越低。1s 是检索时效与写入吞吐的平衡点。」**

## 三、refresh / flush / translog 三件套（最高频）

| 操作 | 做什么 | 频率 | 关键词 |
|:---|:---|:---|:---|
| **refresh** | buffer → **新 segment**（进文件系统缓存），此时**可搜但未落盘** | 默认 1s | 近实时、可搜索 |
| **flush** | Lucene commit：segment **fsync 真正落盘** + 清空 translog + 生成 commit point | translog ≥512MB 或 30 分钟 | 持久化、丢数据恢复点 |
| **translog** | 每次写操作追加的事务日志（7.x 起默认 `request` 级别即写即 fsync） | 每次写入追加 | 宕机恢复、防丢数据 |

**宕机恢复流程**：从 commit point 加载已 fsync 的 segment → 重放 translog 中未 flush 的操作 → 数据不丢（前提 durability=request；若设为 `async` 则可能丢最近几百毫秒）。

```
时间线： write ──► [refresh +1s 可搜] ──► [flush 落盘+清日志]
                  ↑ 此区间宕机 → translog 重放恢复
```

## 四、Segment 不可变性（一切设计的根）

| 好处 | 代价 |
|:---|:---|
| 并发读**无需加锁**，只读结构可无限共享 | 删除**只能标记**（.live docs 位图），空间不立即释放 |
| 可深度压缩，OS 文件缓存命中率高 | 更新 = **删旧 + 写新**（版本号+1），更新比插入贵一倍 |
| 写入=纯顺序追加，磁盘友好 | 小 segment 不断累积，需后台 **merge** 回收 |

**删除/更新原理**：每个 commit point 附带 `.live docs` 位图，删除只是把 doc id 标记为不可见；查询时命中已标记文档直接跳过。被标记的空间要等 **merge**（多段合并成新段时物理丢弃死文档）才真正释放。

**段合并 merge**：后台线程按策略把小段合并为大段（回收删除空间、减少段数量）。`force_merge` 可强制合并到单段（常用于不再写入的索引），**但它是重 IO 操作，必须在业务低峰执行**。

## 五、并发控制：乐观锁

ES 用 **`if_seq_no` + `if_primary_term`** 实现单文档 CAS（6.7+ 替代旧 version/外部版本号）：

```json
PUT orders/_doc/1001?if_seq_no=17&if_primary_term=1
{ "status": "PAID" }
```

- `seq_no`：该文档在分片内的操作序号；`primary_term`：主分片的代数（主分片切换后 +1）。
- 版本冲突返回 409，客户端重读再改——与数据库乐观锁（version 字段）同构，面试可以类比。

---

## 易错点

1. **refresh ≠ flush**：把 refresh 答成「落盘」是致命错误。refresh 只是「可搜索」，数据真正安全要等 flush fsync，中间靠 translog 兜底。
2. **translog 不是可关的日志**：`durability: async` 确实能提速，但宕机会丢最近写入——日志类索引可以权衡，交易类绝不能开。
3. **写入完成 ≠ 可搜索**：默认 1 秒延迟，测试脚本写完立刻查不到不是 bug，可用 `?refresh=wait_for` 强制等刷新。
4. **merge 会抢 IO**：写入毛刺常来自段合并；大量删除后空间不释放也别慌，等 merge 或 force_merge。
5. **副本同步失败不是写失败**：只要满足 quorum 就成功，落后副本之后通过 **seq_no + 主分片恢复**补齐。

## 一句话总结

> 写入 = 「**内存 buffer 顺序写 + translog 兜底**」，refresh 让它 1 秒内可搜（近实时），flush 才真正落盘；**segment 不可变**是根基——换来无锁并发读，代价是删除打标、更新翻倍、merge 回收。
