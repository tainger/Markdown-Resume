# 搜索流程与相关性评分

高频追问链：「一次搜索在集群里发生了什么 → **为什么要两阶段** → 相关性分怎么算的 → match 和 term 什么区别」。核心：**Query Then Fetch + BM25**。

---

## 一、Query Then Fetch 两阶段（必背，能白板画）

```
Client ──► Coordinating Node
              │ 广播到索引的每个分片(各选一个副本)
   ── Query Phase ────────────────────────────────────────
              │ 各分片本地执行查询，只返回「top N 的 docId + 排序值」(N=from+size)
              │ ◄── 分片1: [doc5:9.2, doc1:8.7 ...]
              │ ◄── 分片2: [doc8:9.5, doc2:8.1 ...]
              │ 协调节点归并排序，选出全局 top N 的 docId
   ── Fetch Phase ────────────────────────────────────────
              │ 按最终 docId 回对应分片拉取 _source/高亮/聚合外的字段
              │ ◄── 返回完整文档
              ▼ 给 Client
```

**为什么分两阶段**：若一步拉全文档，每个分片要传 `from+size` 条**完整文档**，网络传输巨大。两阶段把「排序」与「取回」拆开，Query 阶段只传轻量的 docId+score，Fetch 只拉最终命中的几条。

**两种搜索类型**：

| 类型 | 评分依据 | 特点 |
|:---|:---|:---|
| `query_then_fetch`（默认） | 分片**本地**词频 | 快；但高频词分布不均时分数可能轻微失真 |
| `dfs_query_then_fetch` | 先收集**全局**词频再评分 | 更准；多一次往返，只在分片数少、对排序敏感时用 |

## 二、query context vs filter context

| 维度 | query context（must/should） | filter context（filter/must_not） |
|:---|:---|:---|
| 是否算分 | 计算 `_score`（BM25） | 只回答「是/否」，不算分 |
| 缓存 | 不缓存 | **结果 bitset 被节点缓存复用** |
| 适用 | 相关性排序场景（搜商品标题） | 精确条件（状态、时间范围、类目） |

> 铁律：**能用 filter 的条件一律放 filter**，又快（不算分）又省（可缓存），还能提升 must 部分的相对区分度。

## 三、相关性评分：BM25

演进：**TF-IDF → BM25**（5.x 起默认）。TF-IDF 的问题：词频无饱和——一个词出现 100 次，分数线性暴涨，长文档被过度偏爱。BM25 引入两个参数：

| 参数 | 含义 | 调整效果 |
|:---|:---|:---|
| `k1`（默认 1.2） | **词频饱和度** | 越大，高频词继续加分的空间越大 |
| `b`（默认 0.75） | **文档长度归一** | 越大，越压制长文档；b=0 退化为不考虑长度 |

> 一句话：**BM25 = 会饱和的 TF-IDF**——词出现次数越多加分越少，长文档按比例被「打折」。

## 四、分词器（Analyzer）

三件套流水线：**Character Filter（预处理，如去 HTML 标签）→ Tokenizer（切词）→ Token Filter（小写/去停用词/同义词）**。

- 内置 `standard` 按字切英文单词但对中文只能**逐字切**——中文必须用 **IK**：
  - `ik_max_word`：**索引用**，最细粒度（「中华人民共和国」→ 多种组合），提高召回；
  - `ik_smart`：**搜索用**，粗粒度切分，减少噪音。
- 自定义词库：扩展词典（产品名、人名）+ 同义词过滤，热更新需 reload（或用远程词库接口）。
- 铁律：**索引与搜索的分词方式要匹配**，一边 max_word 一边 standard 会导致词条对不上、查不到。

## 五、DSL 核心查询

| 需求 | 用法 | 说明 |
|:---|:---|:---|
| 全文检索 | `match` | 先分词再查（text 字段） |
| 精确匹配 | `term` | **不分词整值匹配**（keyword/数字/日期） |
| 多条件组合 | `bool`: must / should / filter / must_not | 算分与不算分分层组合 |
| 范围 | `range` | 时间、数值区间，放 filter |
| 短语 | `match_phrase` | 保序且相邻（slop 控制容错距离） |

**经典坑**：对 `text` 字段用 `term` 查整句查不到——因为 text 已被切成小写词条；要么查词条，要么用它的 `.keyword` 子字段。

## 六、聚合（Aggregation）

```
桶聚合 bucket： terms(类目) / date_histogram(按天) / nested   → 分组
指标聚合 metric： avg / max / sum / cardinality(去重计数)      → 算数
管道聚合 pipeline：derivative / moving_avg                     → 对结果再算
```

- 聚合排序与分组依赖 **doc_values（列存，默认开启、磁盘）**；`text` 字段默认不能聚合，强开 `fielddata` 会把词条装进**堆内存**，极易 OOM——生产禁用。
- `cardinality` 去重计数是 **HyperLogLog++ 近似算法**，误差可控、内存极省，面试答「精确去重请回数据库或用 terms 暴力桶」。

---

## 易错点

1. **分片词频偏差**：被追问「为什么搜索分数看起来不对」时，答出 query_then_fetch 用本地词频 + `dfs_query_then_fetch` 修复，是加分项。
2. **text vs keyword**：`match` 对 text、`term` 对 keyword 混用是最高频翻车点，答题先报字段类型。
3. **两阶段 ≠ 两次全文扫描**：Query 阶段只传 docId+score，别把 Fetch 说成「每个分片都返回完整文档」。
4. **fielddata 是堆内、doc_values 是堆外列存**——说反了等于告诉面试官没查过线上 OOM。
5. **from+size 会传递到每个分片**（详见下篇深分页），别在两阶段描述里漏掉 `from+size` 这个 N。

## 一句话总结

> 搜索 = 「**Query 阶段各分片只交 top N 的 docId，Fetch 阶段再回源取文档**」的两阶段设计；相关性用 **BM25（饱和词频 + 长度归一）**，精确条件进 **filter context** 白拿缓存，中文检索靠 **IK 双粒度分词**。
