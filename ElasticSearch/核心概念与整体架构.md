# 核心概念与整体架构

ES 的面试第一题永远是「**为什么用 ES 而不用 MySQL LIKE？讲讲倒排索引**」。答好的关键：定位与适用场景 → 倒排索引三层结构 → 与 MySQL 对比 → 概念层级与分片路由 → 选主与脑裂。

---

## 一、定位与适用场景（先答"为什么用"）

| 适合 ES | 不适合 ES |
|:---|:---|
| 全文检索（分词、相关性排序、高亮） | **强事务**（无 ACID，多文档写不保证原子） |
| 多维过滤 + 聚合分析（日志、监控、BI） | **频繁更新**（更新=删旧+写新，代价高） |
| 海量写入 + 近实时查询（日志平台、APM） | 多表关联（join 弱，靠宽表/反范式冗余） |
| 结构化+非结构化混合检索 | 深分页遍历全量数据 |

> 面试话术：**「MySQL 解决『怎么把一行数据准确存取』，ES 解决『怎么在一亿条数据里秒级找到相关的那批』，两者互补而非替代。」**

## 二、倒排索引（最高频，必须画图）

正排：`文档 ID → 内容`；倒排：`关键词 → 文档 ID 列表`。写入时对字段分词，建立「词项 → 出现该词的文档集合」映射：

```
文档1: "Java 并发编程"        词项(Term)      倒排列表(Posting List)
文档2: "Java 虚拟机"    ──►   Java      ──►   [1, 2, 4, 7]        ← Roaring Bitmap 压缩
文档3: "MySQL 索引"           并发      ──►   [1]
文档4: "Java 高并发"          虚拟机    ──►   [2]
                              高并发    ──►   [4]
```

查询 `Java AND 并发` 时对两个 posting list **求交集**，而不是扫全表——这是 ES 快的根本原因。

**三层结构（必背）**：

| 层 | 位置 | 数据结构 | 作用 |
|:---|:---|:---|:---|
| Term Index | **内存** | **FST（有限状态转换机）** | 前缀匹配，定位 term 在词典中的 block 位置，省内存 |
| Term Dictionary | 磁盘 | 分 block 排序存储 | 所有词项有序存放 |
| Posting List | 磁盘 | **Roaring Bitmap + skip list** | 压缩文档 ID；skip list 让 AND/OR 交集可跳步加速 |

> 一句话：**FST 在内存里当「目录的目录」，磁盘上是排好序的词典 + 压缩的倒排列表，类似「字典的部首目录 → 正文页码 → 压缩的页码列表」。**

## 三、与 MySQL 的对比

| 维度 | MySQL | ElasticSearch |
|:---|:---|:---|
| 索引模型 | B+ 树（聚簇索引+二级索引） | **倒排索引 + doc_values 列存** |
| 检索能力 | LIKE 前缀可用索引，`%xx%` 全表扫 | 分词、模糊、相关性排序、高亮 |
| 事务 | ACID，完整隔离级别 | 无事务，靠版本号做单文档 CAS |
| 写入 | 随机写（页分裂） | **顺序写 segment**，吞吐高 |
| 更新/删除 | 原地更新 | 标记删除 + merge 回收，代价高 |
| 深分页 | 优化后尚可（延迟关联） | 天然受限（`max_result_window=10000`） |
| 典型组合 | 主存储、事实来源（Source of Truth） | 查询视图层，由 binlog/CDC/MQ 同步 |

## 四、概念层级与分片路由

```
Cluster 集群
└── Node 节点（master-eligible / data / ingest / coordinating）
    └── Index 索引（≈ MySQL 的表）
        ├── Shard 主分片（数据水平拆分单元，创建后数量不可改）
        │   └── Replica 副本（主分片的拷贝，容灾+分担读）
        │       └── Document 文档（JSON，≈ 一行；7.x 起无 _type）
        │           └── Field 字段（Mapping 定义类型与是否分词）
```

- **分片路由公式（必背）**：`shard = hash(routing) % number_of_primary_shards`，`routing` 默认为 `_id`。这就是**主分片数创建后不能改**的原因——改了公式结果全错，历史数据找不到分片。
- 单分片建议 **20~50GB 以内**；分片总数别无脑堆（每个分片是一个 Lucene 实例，有固定堆开销），经验：**每 GB 堆 ≤ 20 个分片**。
- 副本可随时动态调整；副本数 = 节点数 - 1 起步，兼顾容灾与读吞吐。

## 五、节点角色

| 角色 | 职责 | 面试考点 |
|:---|:---|:---|
| master-eligible | 参与选主、维护集群状态（轻量元数据） | **≥3 个奇数**部署，防止脑裂 |
| data | 存数据、执行 CRUD/搜索/聚合 | 可再分 hot/warm/cold（见高可用篇） |
| coordinating | 接收请求、路由分发、归并结果 | **每个节点都自动充当**协调角色 |
| ingest | 写入前预处理（pipeline：富化、脱敏） | 替代部分 Logstash 场景 |

小集群可混合部署；生产中大集群通常把 master 与 data **分离**，避免重负载节点拖垮集群状态管理。

## 六、选主与脑裂

```
正常: 所有 master-eligible 互 ping → 投票 → 得票超半数(quorum)者成为 Master
故障: Master 失联 → 幸存 eligible 节点发现"当前 epoch 无主" → 重新发起选举(仍需 quorum)
```

- **6.x 时代**：手工配置 `discovery.zen.minimum_master_nodes = eligible数/2+1`。配错（比如节点扩容后没改）就会脑裂——网络分区时两边各自选主，数据分裂。
- **7.x 之后**：引入 **voting configuration 自动仲裁**，集群自动维护投票配置，选主/元数据变更都需要过半票数，**不再需要手工配 minimum_master_nodes**。分区中拿不到 quorum 的一侧自动降级、拒绝写入，脑裂从机制上避免。
- 落地铁律：master-eligible 用 **3 或 5 台奇数**，且不要与重负载 data 节点混部。

---

## 易错点

1. **倒排 ≠ 只有一张倒排表**：漏答 FST/Roaring Bitmap/skip list 三件套是最大的失分点，被追问「posting list 太长怎么办」要能接住。
2. **主分片数不可改 ≠ 不能扩容**：扩节点不加分片也能再平衡；确要加主分片只能 reindex 或 split，别答「分片数随时可改」。
3. **ES 不是数据库**：答成「可以直接替代 MySQL」直接扣分；它无事务、更新贵、深分页弱，是检索/分析层。
4. **coordinating 不是独立节点类型**：所有节点都是协调者，别答「专门买协调节点」（大集群可以这么部署，但角色本身人人都有）。
5. **7.x 起没有 `_type`**，面试举例用 `_doc`，别再暴露老版本习惯。

## 一句话总结

> ES 用「**FST 内存词索引 + 磁盘倒排 + 压缩 posting list**」换来了秒级全文检索，用「**主分片路由公式**」做数据分片、用「**quorum 选主**」防脑裂——它天生是为**读多写少的检索分析**而生，与 MySQL 是互补关系。
