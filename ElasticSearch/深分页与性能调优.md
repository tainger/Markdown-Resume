# 深分页与性能调优

高频追问链：「分页查到 10 万条怎么办 → **为什么默认限制 10000** → scroll 和 search_after 选哪个 → 线上怎么调优」。核心：**深分页三方案 + 写入/查询/JVM 三层调优**。

---

## 一、from+size 深分页陷阱（必背）

两阶段搜索中，**每个分片**都要返回「from+size」条 docId 参与归并：

```
from=9990, size=10, 5个主分片
→ 每个分片排序并返回 10000 条 docId
→ 协调节点在 50000 条里归并出 9990~10000 这 10 条
→ 大部分排序计算与传输全是浪费
```

所以 ES 默认 `max_result_window = 10000`，超过直接报错。这不是「限制功能」，而是**保护集群**：翻得越深，每分片的排序成本越大，还可能打爆协调节点内存。

| 方案 | 原理 | 实时性 | 适用 | 缺点 |
|:---|:---|:---|:---|:---|
| **from+size** | 每分片取 from+size 归并 | 实时 | 翻页浅（前几页） | 深翻页代价指数增长 |
| **scroll** | 首次查询生成**快照视图**，游标逐批拉取 | **快照，不实时** | 离线全量导出/重建索引 | 占用搜索上下文资源；上下文有上限（默认 500 个） |
| **search_after (+PIT)** | 用**上一页最后一条的排序值**做游标续查 | **实时** | 业务深翻页、导出、Feed 流 | 只能「下一页」不能跳页；排序值必须唯一（末位加 `_id`） |

> 面试话术：**「业务跳页用 from+size 到 1 万为止；无限下拉用 search_after + PIT；全量搬运用 scroll——三者是『浅翻页 / 实时游标 / 离线快照』的分野。」**

## 二、写入调优

| 手段 | 做法 | 说明 |
|:---|:---|:---|
| **bulk 批量写** | 单请求 5~15MB、千条级 | 减少请求往返与连接开销，最立竿见影 |
| **调大 refresh** | 大导入期 `refresh_interval: -1`，导完恢复 30s/1s | 减少小 segment 生成与 merge 压力 |
| **临时去副本** | 导入期 `replicas: 0`，导完调回 | 副本同步是写入的主要放大器 |
| translog 异步 | `durability: async` | **仅日志类可接受**，交易类禁用 |
| 索引瘦身 | 不检索的字段 `index: false`；不需 `_source` 的场景关闭 | 少建倒排、少存原文 |
| 用自动 id | 让 ES 生成 `_id` | 自定义 id 需先查重（GET），多一次点查 |

## 三、查询调优

1. **能用 filter 就不放 must**（不算分 + bitset 缓存）。
2. **禁前导通配符** `*abc`——倒排是按前缀组织的，前导通配符等于扫全词表；用 `wildcard`/`ngram` 重建索引替代。
3. **只要 id/排序值时**用 `_source: false` 或 `docvalue_fields`，别整行 `_source` 拉 JSON。
4. **冷热数据分索引**，查询带日期条件命中少数索引，避免广播到全部分片。
5. **分片别过量**：分片越多，Query 阶段扇出与归并成本越高；也不是越少越好（单机成为瓶颈），按数据量 20~50GB/片规划。
6. 聚合用 **doc_values**；`terms` 聚合桶数（`size`）与 `search.max_buckets` 控制内存。

## 四、JVM 与内存模型（P7 必考）

```
机器内存
├── ≤ 50%：JVM 堆（Xms=Xmx，≤ 31G 保留压缩指针）
│     ├── 查询/聚合的临时对象、请求队列
│     └── 各类 Circuit Breaker 守护
└── ≥ 50%：留给 OS 文件系统缓存
      └── Lucene segment 常驻 → 顺序读接近内存速度
```

- **堆越大越好是误区**：堆超过 32G 会失去压缩指针（对象引用膨胀），且挤压 Lucene 缓存。**多加节点 > 换大内存机器**。
- **断路器（Circuit Breaker）**：parent 95%、request 60%、fielddata 40%——查询预估内存超限直接拒绝请求，**宁可报错也不 OOM 整机**。线上「circuit_breaking_exception」先查 fielddata 与聚合桶数。
- 铁律 `Xms = Xmx`：避免运行期堆伸缩抖动。

---

## 易错点

1. **scroll 不是业务分页方案**：它是快照（开启后写入对新查询不可见），且长期不关闭会泄漏搜索上下文；业务列表用 search_after。
2. **max_result_window 不是 bug**：「能不能把 10000 调大」——能，但面试要答出**为什么不该调**（每分片 from+size 归并）。
3. **search_after 排序值必须唯一**：同分文档会导致游标丢数据，末位拼 `_id` 是标准做法。
4. **调大 refresh 只该在导入期**：常态 `-1` 会让用户看到分钟级延迟，还堆积大 buffer。
5. **堆 50% 铁律**：把 64G 全给 JVM 是经典事故，Lucene 缓存被挤掉后性能断崖下跌。

## 一句话总结

> 深分页的本质是「**每个分片都要陪跑 from+size**」，所以浅翻页 from+size、实时游标 search_after+PIT、离线快照 scroll；调优三板斧 = **写入 bulk+关 refresh+去副本、查询 filter+禁前导通配、内存对半分（堆≤32G，剩给 Lucene）**。
