# 高可用与集群治理

高频追问链：「一台节点挂了数据丢吗 → **脑裂到底怎么防的** → 节点恢复时为什么集群变慢 → 索引越滚越大怎么办」。核心：**副本容灾 + 分片分配 + 冷热分离 ILM**。

---

## 一、副本与容灾

```
索引: 3 主分片 × 2 副本（任意一个分片组 = 1主2副）
Node1: P0 P1        Node2: R0 P2        Node3: R1 R2
     ↓ Node1 宕机
集群检测 node_left → 主分片缺失的组内，把副本 R0/R1 **提升为主**
     → 集群状态 yellow→恢复（补齐副本后回 green）
```

- **写读分流**：主分片处理写，主/副本都处理读（默认轮询）。
- **in-sync 副本列表**：只有跟上主分片进度的副本才有资格提升；落后副本靠 seq_no 增量补齐或从主分片拷贝。
- 副本数规划：**节点数 - 1** 起步；单副本的索引在单节点故障时会出现「无副本裸奔期」。

## 二、脑裂防范的演进（必考）

| 版本 | 机制 | 隐患 |
|:---|:---|:---|
| 6.x 及以前 | 手工 `minimum_master_nodes = n/2 + 1` | 扩缩容忘改配置 → 网络分区两边各自选主 → **数据分裂** |
| 7.x+ | **voting configuration 自动维护**，元数据变更需过半投票 | 拿不到 quorum 的一侧自动停止服务（拒绝写），**机制上杜绝脑裂** |

落地铁律：

1. master-eligible **3 或 5 个奇数**（7.9+ 可用专门的 voting-only 节点补票）。
2. master 节点与重负载 data **分离**，防止 GC 长暂停触发误判掉线。
3. `discovery.zen.fd` 心跳超时别调得过小，网络抖动频繁误选主比慢选主更伤。

## 三、分片分配与恢复（线上经验密集区）

- **节点掉线延迟分配**：节点离开后，其分片默认 1 分钟就开始向其他节点**全量复制**恢复——日志集群节点重启会引发**恢复 IO 风暴**。生产必配：

```json
"index.unassigned.node_left.delayed_timeout": "5m"
```

  节点 5 分钟内回来 → 未分配副本直接**原地复用本地数据**（synced flush 标记），秒级恢复，不做全量拷贝。
- **机架/可用区感知**（allocation awareness）：把主/副本强制分散到不同机架，防止「一个机柜断电，主副本全灭」。
- **quota 限流**：`cluster.routing.allocation.disk.watermark`（low 85% / high 90% / flood 95%）——磁盘水位线，flood stage 会把索引**只读**，线上报警最常见原因之一。

## 四、扩容与主分片扩容

- **水平扩容**：加节点 → 分片自动再平衡（副本自动迁移，无需人工）。**主分片数不变**，所以扩容提升的是「吞吐与存储上限」，不改单分片检索性能上限。
- 确需增加主分片：**split**（按倍数拆分，需建索引时预留 `number_of_shards` 可整除）或 **reindex** 到新索引。split 前提是 `_shards` 数量可整除，规划期就写好。

## 五、冷热分离与 ILM（日志/时序场景标配）

```
            ┌── hot 节点(SSD, 高配) ──► 新数据，读写都在这
索引按天滚动 │
            └── warm 节点(大磁盘) ──► 7天后：索引只读
                                      ├─ shrink/force_merge（合并成单段省内存）
                                      └─ 30天后：delete 或迁冷存
```

ILM（Index Lifecycle Management）策略示例：

```json
PUT _ilm/policy/logs_policy
{
  "policy": {
    "phases": {
      "hot":    { "actions": { "rollover": { "max_size": "50gb", "max_age": "1d" } } },
      "warm":   { "min_age": "7d",  "actions": { "allocate": { "require": { "data": "warm" } } } },
      "delete": { "min_age": "30d", "actions": { "delete": {} } }
    }
  }
}
```

- rollover 要求索引名 `logs-000001` 递增且设 `is_write_index`；配合**索引模板**自动挂 policy。
- 收益：hot 集群始终小而快，warm 大盘低价磁盘，老数据自动过期——**存储成本与查询性能同时可控**。

## 六、生产实战案例（讲述模板：现象 → 排查 → 处理 → 预防）

| 事故 | 现象 | 根因 | 处理/预防 |
|:---|:---|:---|:---|
| **写入积压** | 写入延迟飙升、bulk 429 | refresh 过频 + 副本同步放大 + merge 抢 IO | bulk 增大、导入期 refresh=-1 + replicas=0；区分峰值常态容量 |
| **协调节点 OOM** | 查询偶发 circuit breaker | 业务方 from+size 拉全量 + fielddata 聚合 text 字段 | 推 search_after；禁 fielddata；断路器阈值告警 |
| **节点重启集群卡死** | 一次重启，全集群 IO 打满 | 副本立即全量恢复 | delayed_timeout=5m；分批滚动重启（禁用分配→重启→恢复） |
| **索引变只读** | 写入报 FORBIDDEN | 磁盘过 flood 水位 95% | 清理/扩盘 → 释放只读锁；水位告警前置 |

## 易错点

1. **副本提升是自动的**：别答「要人工切换主分片」；但 in-sync 之外的落后副本**不能**直接提升。
2. **yellow ≠ 故障**：yellow = 主分片齐、副本未分配（单节点集群天然 yellow）；red = 有主分片缺失，数据不可查。
3. **7.x 答脑裂还在背 minimum_master_nodes** 是过时答案，要答「已自动化，但奇数 eligible 的部署纪律仍在」。
4. **delayed_timeout 不是不用副本**：只是延迟分配决策，超时后照常恢复；别和副本数混为一谈。
5. **force_merge 低峰执行**：它是全段重写级 IO，高峰执行等于自造事故。

## 一句话总结

> 高可用三板斧：**副本容灾（主挂副本自动升主）+ quorum 选主（7.x 机制性防脑裂）+ 分配策略（延迟恢复防 IO 风暴、机架感知防同柜全灭）**；治理三板斧 = **冷热分离 + ILM 自动滚动过期 + 磁盘水位线**。
