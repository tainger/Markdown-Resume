## 一、一分钟回顾：Profile 与 Bundle 是什么

只铺垫读代码必需的最小概念：

- **Profile**：`$DSH_HOME/profiles/<name>/` 下的一个目录，含 `package.json`（其中 `dsh.profile.bundles` 是有序 bundle 名单）和用户自己的 `cordis.patch.yml`。
- **Bundle**：一个 npm 包，`package.json` 声明 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`，patch 文件就是它贡献的配置行。
- **根配置永远是空数组**：profile 目录下的 `cordis.yml` 内容固定为 `[]`，整棵树完全由 patch 层堆叠而成，任何一行都能被上层按 `id` 覆盖。

```
加载顺序（后者覆盖前者，按配置行 id 寻址）：
  bundle1.patch → bundle2.patch → …（dsh.profile.bundles 顺序）
  → profile 自己的 cordis.patch.yml
  → $DSH_HOME/cordis.patch.yml（home 层，机器级偏好）
  → --patch a.yml --patch b.yml（命令行 overlay，按 argv 顺序）
  → 标志位派生 patch（如 DSH_TELEMETRY_DISABLED）
```

下面从入口代码开始走。

## 二、CLI 入口：launcher 只解析自己认识的旗标

### 2.1 bin.ts：三模式分派

`dsh` 的可执行入口极薄，解析参数后按 mode 动态 import，避免不相关模式互相拖累启动路径：

```ts
// apps/cli/src/bin.ts
const invocation = parseDshArgs(process.argv.slice(2), readVersion())

switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({
      environment: loadLayeredEnv('dsh'),
      profile: invocation.profile,
      patchFiles: invocation.patches,
      args: invocation.args,
    })
    break
  }
  case 'plugin': {
    const { runPlugin } = await import('./plugin.ts')
    process.exit(runPlugin(invocation.profile, invocation.args))
    break
  }
  case 'dump-config': {
    const { runDumpConfig } = await import('./dump-config.ts')
    runDumpConfig(invocation.profile, invocation.defaultOnly, invocation.patches)
    break
  }
}
```

注意 `loadLayeredEnv('dsh')` 在任何插件挂载前运行：它读入「继承的进程环境 > cwd 的 `.env` > `$DSH_HOME/.env`」快照，且两层文件先全部校验通过才统一应用（避免一个生效一个被拒）。`.env` 里出现 `PATH`、`NODE_OPTIONS`、`DSH_*` 前缀等 bootstrap-only 变量会直接报错——这些只能由启动进程决定。

### 2.2 args.ts：launcher flags 与 app 参数的切分

参数解析基于 commander，设计上有一个关键分界：

```ts
// apps/cli/src/args.ts
// launcher 只认：--profile / --patch / --dump-config / --dump-default-config
// 第一个不认识的 token 之后，全部原样交给被 boot 的 app 自己解析
program
  .allowUnknownOption()
  .passThroughOptions()
  .enablePositionalOptions()
  .argument('[args...]', 'arguments for the booted profile\'s app')
  .option('--profile <name>', 'the profile under $DSH_HOME/profiles to boot')
  .option('--patch <path>', 'extra patch-list overlay ... (repeatable)', collect)
```

所以 `dsh --profile tui --resume abc` 中 `--resume abc` 不属于 launcher，而 `dsh --profile web -h` 打印的是 web app 自己的 help。`--patch` 用单值重复收集器而不是 variadic，否则会吞掉后面的 inner args：

```ts
// apps/cli/src/args.ts
const collect = (value: string, previous: string[] = []): string[] => [...previous, value]
```

三种 mode 的类型定义也在此文件：`ProfileInvocation`（启动）、`DumpConfigInvocation`（打印配置树，boot-free）、`PluginInvocation`（转发 pnpm 管插件）。另外 `dsh web` 是硬编码的 `--profile web` 别名。

### 2.3 完整调用链

```

        │
```

## 三、Profile 解析：磁盘上的组合关系

### 3.1 loadProfile：模板自愈 + bundle 双锚点解析

profile 第一次使用会按内置模板自动建目录：

```ts
// packages/boot/app-boot/src/profile.ts
export const PROFILE_TEMPLATES: Record<string, readonly string[]> = {
  web: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app'],
  headless: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-headless'],
}
```

每个 bundle 的定位是**双锚点**：先从 dsh 安装目录解析，再从 profile 目录解析。in-box 插件保证永远来自运行中的 dsh 同一份安装：

```ts
// packages/boot/app-boot/src/profile.ts
export function resolveBundleDir(binName, packageName, installAnchor, profileDir) {
  for (const anchor of [installAnchor, join(profileDir, 'package.json')]) {
    const dir = packageDirFromAnchor(anchor, packageName)
    if (dir !== undefined) return dir
  }
  throw new Error(`${binName}: cannot resolve profile bundle ...`)
}
```

bundle 包必须在自己的 `package.json` 声明 `dsh.bundle.patch`，否则 fail loud——「名字写进 bundles 却不是 bundle」属于配置错误，不允许静默跳过。

### 3.2 profiles/node_modules 软链接兜底

out-of-tree 插件装在 profile 自己的 `node_modules`（pnpm hoisted），而 in-box 插件靠 `healProfilesModuleFallback()` 维护的扁平兜底目录：它从 app 的 package.json 出发对 `dependencies + peerDependencies` 做 BFS，把依赖闭包里每个包**各建一个符号链接**到 `$DSH_HOME/profiles/node_modules/<pkg>`。Node 从任意 profile 向上查找时必然经过该目录，于是所有 in-box 插件无需 profile 安装即可解析，且 peer 依赖（服务定义包如 `dsh-compaction`）也在闭包中，不会出现两份 cordis 实例。

### 3.3 空根为什么每次都要重写

```ts
// apps/cli/src/profile-boot.ts
export function prepareProfile(name: string, userLayer = true): Profile {
  healProfilesModuleFallback(INSTALL_ANCHOR)
  const profile = loadProfile(NAME, name, INSTALL_ANCHOR, undefined, { userLayer })
  writeFileSync(join(profile.dir, PROFILE_ROOT_FILENAME), PROFILE_ROOT_CONFIG)
  return profile
}
```

根文件内容是注释加 `[]`，每次 boot 重写。注释解释了原因：vendored Loader 有 tree write-back（插件自卸载会把当前树持久化进配置文件），不重写的话组合出来的行会被烤进根文件，下次启动就把每个 bundle 的 insert 重复一遍。根文件存在的唯一理由是 Loader 需要一个真实的 include 锚点来定 `baseUrl`。

## 四、Patch 行格式与覆盖语义（整条链的核心）

### 4.1 两种 patch 行

bundle/patch 文件是顶层 YAML 数组，每个元素是 `PatchOptions`。语义在 vendored include 里只有一份实现，boot 和 dump-config 都调它：

```ts
// vendor/include/src/index.ts
export function applyEntryPatches(data: EntryOptions[], patches: PatchOptions[] | undefined, warn) {
  data = structuredClone(data)                       // 输入永不被改，结果恒为 detached
  const entryMap = new Map<string, EntryOptions>()
  const buildMap = (entries) => {
    for (const entry of entries) {
      if (entry.id) entryMap.set(entry.id, entry)
      if (entry.group && Array.isArray(entry.config)) buildMap(entry.config)
    }
  }
  buildMap(data)

  for (const patch of patches) {
    const { id, insert, name, ...overrides } = patch
    if (insert) {
      if (id) {                                      // 往某个 group 行里插
        const target = entryMap.get(id)
        if (!target) { warn('patch insert: entry %C not found', id); continue }
        target.config.push(...insert)
      } else {
        data.push(...insert)                         // 无 id：顶层插入
      }
      buildMap(insert)                               // 同层后续 patch 可以覆盖刚插入的行
      continue
    }
    const target = entryMap.get(id)
    if (!target) { warn('patch: entry %C not found', id); continue }
    if (name && name !== target.name) { warn('name mismatch ...'); continue }
    for (const [key, value] of Object.entries(overrides)) {
      if (key === 'id') continue
      target[key] = value                            // 整字段替换：config 是整体替换，不是 merge
    }
  }
  return data
}
```

要点（面试高频）：

1. **`insert`**：无 `id` 时顶层追加一批行；有 `id` 时要求目标是 group，插入其 `config`。
2. **id 寻址覆盖**：`{ id: 'tools', config: {...} }` 直接整字段替换——**config 整体替换而非深合并**，所以上层 patch 必须重述它要拥有的全部键。`disabled: true` 是同样的字段替换。
3. **后写赢**：patch 按扁平化后的顺序逐条 apply；刚 insert 的行立刻进 `entryMap`，所以后一个 bundle 能配置/禁用前一个 bundle 插入的行。
4. 匹配不到行只告警不致命——同一个 overlay 可以跨 surface 使用，不必匹配每棵树。

base bundle 的头部注释把这条纪律写得很直白：

```yaml
# packages/bundle/base/cordis.patch.yml
# A patch replaces the targeted row's whole `config` rather than merging into it,
# so a row whose value differs by mode does NOT live here: it belongs to each
# mode bundle ...
- insert:
    - id: timer
      name: '@deepseek-ai/cordis-plugin-timer'
    - id: llm
      name: '@deepseek-ai/dsh-llm'
    ...
```

### 4.2 `!!js` 表达式：配置即代码

行内可以用 `!!js`，由 include 的 YAML dialect 解析成表达式节点，Loader 在每个 entry 的注入就绪上下文上插值：

```yaml
# packages/bundle/base/cordis.patch.yml
- id: sandbox-policy
  name: '@deepseek-ai/dsh-sandbox-policy'
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    workspaceRoot: !!js process.cwd()

- id: session-persistence-jsonl
  name: '@deepseek-ai/dsh-session-persistence-jsonl'
  config:
    root: !!js dshHomePath('sessions')
```

web bundle 更进一步：配置表达式引用一个**尚不存在的服务**，Loader 会把该行的激活推迟到服务发布：

```yaml
# packages/bundle/web-app/cordis.patch.yml
- id: webserver
  name: '@deepseek-ai/dsh-host-webserver'
  inject: [webStartup]
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'
    port: !!js ctx.webStartup.port ?? 3080
```

`webStartup` 是一个普通插件（`web-app/src/startup.ts`）解析 commander 后 `ctx.provide` 出来的。旗标→服务→惰性配置表达式，这就是「命令行参数如何变成插件配置」的全部机制，没有任何特权行。

### 4.3 堆叠的实际组装代码

```ts
// apps/cli/src/profile-boot.ts
function composeProfile(name, patchFiles): ComposedProfile {
  const profile = prepareProfile(name)
  const homePatches = loadOptionalPatches(NAME, homePatchPath()) ?? []
  const overlays = patchFiles.flatMap(file => loadOverlayPatches(NAME, resolve(file)))
  const bundlePatches = profile.layers.flatMap(layer => layer.patches)
  const rows = new Map<string, EntryOptions>()
  for (const row of composeEntries([bundlePatches, profile.patches, homePatches, overlays])) {
    if (typeof row.id === 'string') rows.set(row.id, row)
  }
  const composedOverlays = [...overlays]
  if (rows.has('agent-presets')) {                  // 装配 shipped preset 目录
    composedOverlays.push({
      id: 'agent-presets',
      config: { ...rows.get('agent-presets')?.config, roots: [{ path: SHIPPED_PRESET_ROOT, trust: 'system' }] },
    })
  }
  const telemetryPatch = resolveTelemetryPatch(process.env.DSH_TELEMETRY_DISABLED, rows.has(TELEMETRY_ROW_ID))
  if (telemetryPatch !== undefined) composedOverlays.push(telemetryPatch)
  return { profile, bundlePatches, homePatches, overlays: composedOverlays, rows }
}
```

两个工程坑在注释里写得很精彩：

- **live reload 的重组必须 `structuredClone`**：include 把 insert 行按引用推进挂载树，id 覆盖会原地改这些对象；复用同一个解析对象会把用户覆盖烤进 bundle 的 insert 行，删掉覆盖后再也回不到默认值。
- **home 层高于 profile 层**：`$DSH_HOME/cordis.patch.yml` 是机器级偏好，对所有 profile 生效，所以排在 profile 自己的 patch 之后。

## 五、boot()：从空 Context 到树沉淀

### 5.1 挂载主流程

```ts
// packages/boot/app-boot/src/index.ts
export async function boot(binName, absoluteConfigPath, patches?, prepare?, bareModuleBaseUrl?) {
  const ctx = new Context()
  let stage = 'host preparation failed'
  try {
    ctx.baseUrl = pathToFileURL(dirname(absoluteConfigPath)).href + '/'
    ctx.provide('dshHomePath', dshHomePath)
    await ctx.plugin(Loader)
    await prepare?.(ctx)                            // host 预置：env 快照 + cmdline
    stage = 'plugin tree failed to load'
    await mountRootInclude(ctx, absoluteConfigPath, patches, bareModuleBaseUrl)
    await ctx.get('loader')?.await()                // 并发挂载，等全部 settle
    if (ctx.get('loader') === undefined) return ctx // 启动途中被 dispose（fast one-shot）
    await assertEntriesActivated(ctx, binName)
    return ctx
  } catch (cause) {
    await ctx.fiber.dispose()                       // 失败也要把部分树回滚干净
    throw new Error(`${binName}: ${stage}: ${detail}...`, { cause })
  }
}
```

根 Include 以固定 id 挂载，builtin 直接给类而非包名（外部 preset 无法按名解析 group 包）：

```ts
// packages/boot/app-boot/src/index.ts
ctx.loader.builtins.include = Include
ctx.loader.builtins.group = Group
const rootInclude: EntryOptions = { id: 'include', name: 'cordis:include', config: { path: ..., patches: [...] } }
const includeId = await ctx.loader.create(rootInclude)
```

### 5.2 fail-loud：两条失败防线

Loader 并发挂 entry，一个晚到的插件 init rejection 可能变成 unhandledRejection。dsh 的做法：

1. `installFailLoud()` 在 boot 前注册 `unhandledRejection`：打印一行带堆栈的诊断后 `exit(1)`，若 surface 持有终端（TUI），先 await 最长 2s 的 release 钩子恢复终端，再退。
2. settle 后 `assertEntriesActivated()` 主动审计：无 fiber 且未 disabled → 失败；fiber FAILED → await 出原始 rejection 并保留插件自身堆栈；fiber PENDING → 报出它在等哪些服务：

```ts
// packages/boot/app-boot/src/index.ts
if (state === FIBER_PENDING) {
  const missing = Object.keys(fiber.inject).filter(service => fiber.ctx.get(service) === undefined)
  failures.push(`${entry.options.name}: pending (waiting for ${...}: ${missing.join(', ')})`)
}
```

### 5.3 信号与有界关停

```ts
// apps/cli/src/profile-boot.ts
const shutdown = createProcessShutdown(async () => { await app.current?.fiber.dispose() })
process.on('SIGTERM', () => { interrupt(0) })    // 监管方普通停止，统一 0
process.on('SIGINT',  () => { interrupt(130) })  // 用户中断，130
```

关停控制器（`apps/cli/src/process-shutdown.ts`）的语义：正常 `shutdown(code)` dispose 后只设置 `process.exitCode`（允许事件循环自然排空）；信号 `interrupt(code)` dispose 后真退出，5s 宽限内没排完就强退，重复信号立即强退。

### 5.4 patch 热更新

settle 后挂两个文件 watcher（profile 层 + home 层），编辑即通过 HMR 事务性地重新 apply 根 Include：

```ts
// apps/cli/src/profile-boot.ts
const composeLive = (): PatchOptions[] => structuredClone([
  ...composed.bundlePatches,                                  // bundle 永远在最底
  ...loadOptionalPatches(NAME, composed.profile.patchPath) ?? [],
  ...loadOptionalPatches(NAME, homePatchPath()) ?? [],
  ...composed.overlays,                                       // overlay 永远在最顶
])
await watchUserPatches(ctx, { binName: NAME, filename: composed.profile.patchPath, compose: composeLive })
```

层级顺序在 live reload 时保持不变：用户编辑永远挤不走 bundle 和 overlay。web/headless 两个 bundle 都把共享 HMR 行 `disabled: true`，此时 launcher 会补一个 watch-only 的 HMR 实例（`root: []`，不重载模块只盯配置），保证「patch 热改生效」的契约不破。

### 5.5 cmdline：内层参数如何到达插件

launcher 在任何 entry 挂载前把两个事实 provide 到 host ctx：

```ts
// packages/boot/cmdline/src/index.ts
export function provideCmdline(ctx: Context, host: CmdlineHost): void {
  const snapshot: readonly string[] = Object.freeze([...host.args])
  ctx.provide('cmdlineArgs', { get: () => snapshot })
  ctx.provide('appExit', host.exit)
}
```

app 插件（如 headless 的 startup）注入 `cmdlineArgs`，用**自己的 commander program** 解析，再把结果 provide 成普通服务：

```ts
// packages/bundle/headless/src/startup.ts
export const inject = ['cmdlineArgs']
export function apply(ctx: Context): void {
  const program = headlessCommand()
  program.action(() => {
    const task = program.args.join(' ')
    if (task.trim() === '') program.error('error: a task is required ...')
    ctx.provide(HEADLESS_STARTUP_SERVICE, { task })
  })
  parseCmdline(ctx, program)
}
```

`parseCmdline` 还处理了一个坑：必须递归给每个子命令都装 `exitOverride`，否则子命令的 `--help`/parse error 会直接 `process.exit` 绕过 `appExit`；commander 错误用结构化特征（`code.startsWith('commander.')`）而非 `instanceof` 识别，以防 out-of-tree 插件带第二份 commander 副本。

## 六、Cordis 模型：Context / Plugin / effect 在代码里的样子

dsh 把 cordis vendor 在 `vendor/cordis/`。这一节只讲与装配强相关的机制。

### 6.1 Context 是一个 Proxy

```ts
// vendor/cordis/src/context.ts
export class Context {
  [symbols.isolate]: Dict<symbol>      // 服务名 → 隔离域 label
  [symbols.intercept]: Dict            // 服务名 → 合并进插件的 config
  constructor() {
    this[symbols.isolate] = Object.create(null)
    const self = new Proxy<this>(this, ReflectService.handler)  // 属性读走服务解析
    this.root = self
    this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])
    ...
    return self
  }
  extend(meta = {}) { /* Object.create 原型链子上下文，父不被改 */ }
  isolate(name, label?) {
    const shadow = Object.create(this[symbols.isolate])
    shadow[name] = label ?? Symbol(name)
    return this.extend({ [symbols.isolate]: shadow })
  }
}
```

- `extend(meta)`：原型继承出子 ctx，服务查找沿原型链向上，注册只挂在子 fiber 上——**父子作用域**的物理基础。
- `isolate(name)`：给某个服务换一个私有 store label。传给两个 isolate 调用同一个 label 则共享同一域。group 行（`cordis:group`）就是「给一个 provider 和它的消费者同一个 isolate realm」的组合手段。
- `intercept(name, config)`：把配置合并进该服务在子树内每个插件解析出的 config。

### 6.2 ctx.plugin()：注册 = 开一个 Fiber

```ts
// vendor/cordis/src/registry.ts
plugin(plugin: Plugin, config?: any) {
  const callback = this.resolve(plugin)          // 函数 / class / {apply} 三种形态
  this.ctx.fiber.assertActive()
  let runtime = this._internal.get(callback)
  if (!runtime) {
    runtime = { name: plugin.name, callback, fibers: new DisposableList(), Config: plugin.Config }
    this._internal.set(callback, runtime)
  }
  const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, ...)
  const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
  wrapped.then = (onFulfilled, onRejected) => fiber.await().then(onFulfilled, onRejected)
  return wrapped                                 // 既是 fiber 又可 await
}
```

插件不立刻跑：Fiber 进入 PENDING，等 `inject` 声明的服务全部可用才激活。这解释了为什么「行顺序不带加载语义」（base patch 里的原话）——激活由服务可用性驱动，`inject: [webStartup]` 的行可以物理排在 provider 行前面。

### 6.3 effect：注册即可逆

一切注册（事件监听、服务绑定、自定义资源）都经由 `fiber.effect()`：execute 立即执行，返回的 disposer 在**手动 dispose 或 fiber unload 时逆序执行**：

```ts
// vendor/cordis/src/fiber.ts
effect(execute: () => Effect, label = 'anonymous') {
  this.assertActive()                                 // uid 清空 → INACTIVE_EFFECT
  ...
  const dispose = () => {
    for (const disposable of disposables.splice(0).reverse()) { ... }  // 逆序回滚
  }
  removeWrapper = this._disposables.push(wrapper)
  task = this._execute(runner)                        // 同步/thenable/iterator 都收
}
```

事件注册就是一个 effect，所以监听器随插件卸载自动注销：

```ts
// vendor/cordis/src/events.ts
register(label, hooks, callback, options) {
  return this.ctx.fiber.effect(() => {
    hooks[method]({ ctx: this.ctx, callback, ...options })
    return () => this.unregister(hooks, callback)
  }, label)
}
```

dsh 业务代码里随处可见这个范式。persona 插件整个本体就一个 effect：

```ts
// packages/preset/persona/src/index.ts
export function apply(ctx: Context, config: Config): void {
  ctx.effect(() => ctx.systemPrompt.section({
    name: PERSONA_SECTION, order: PERSONA_ORDER, text: config.text,
    ...(config.complete ? { complete: true } : {}),
  }), 'persona.section()')
}
```

### 6.4 事件五分派与 waterfall 的 next 链

```ts
// vendor/cordis/src/events.ts
type DispatchMode = 'emit' | 'parallel' | 'serial' | 'bail' | 'waterfall'

waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)
  const inner = args.pop()                    // 最后一个参数是最内层 next（默认行为）
  const next = () => {
    const cb = cbs.shift() ?? inner
    return cb(...args)                        // 每个 listener 包在其余链之外
  }
  args.push(next)
  return next()
}

async serial(...args: any[]) {
  for (const cb of this.dispatch('serial', args)) {
    const result = await cb(...args)
    if (isBailed(result)) return result       // 非 null/false/undefined 即 bail
  }
}
```

即：waterfall 的每个 listener 收到同一个 `next`，**调了才往里走，不调就是否决**；serial 没有 next，按序 await，靠返回值决定是否短路。dispatch 时还会过一次 context filter（scope 路由就挂在这里，见 6.5）。

### 6.5 scope：per-agent 作用域与事件路由

`core/scope` 在 Cordis 之上提供不透明身份的作用域原语。铸一个 scope 本质是挂一个无操作插件 fiber，再 extend 出带符号 tag 的 ctx：

```ts
// packages/core/scope/src/index.ts
const kScope = Symbol('dsh.scope')

export function createScope(ctx: Context, key: ScopeKey, options?): Scope {
  if (options?.parent !== undefined) bindScopeParent(key, options.parent)
  const fiber = ctx.plugin(scope)                       // scope() 是空函数插件
  const scoped: Context = fiber.ctx.extend({ [kScope]: key })
  return {
    ctx: scoped,
    rawDispose: fiber.dispose,
    dispose: () => (disposing ??= quiesceFiber(fiber)), // 并发 dispose 共享同一次沉淀
  }
}
```

路由载体 `scopeTarget(base, key)` 包出一个只改 filter 的对象：无 tag 的 listener 全局收；有 tag 的只在「dispatch key 或其祖先」命中时收——**事件沿 scope 链向上流，不向下**：

```ts
// packages/core/scope/src/index.ts
[CordisContext.filter](ctx: Context): boolean {
  if (baseFilter !== undefined && !baseFilter.call(base, ctx)) return false
  const tag = scopeOf(ctx)
  if (tag === undefined) return true
  for (let cursor = key; cursor !== undefined; cursor = scopeParents.get(cursor)) {
    if (cursor === tag) return true
  }
  return false
}
```

另一方向是注册表分层：`ScopedLayers` / `NamedEntries`（`core/scope/src/store.ts`）让子 scope 的视图向下合并祖先层，而插入按层归属、随 scope dispose 撤销。工具表、prompt section、skill 目录都是这套 host+per-scope 分层。

agent preset 直接利用该机制，并且做了两道硬审计：preset 子树里任何 pending 行拒绝挂载；任何往 **root realm** 发布服务的行也拒绝（否则第二个 session 挂同一 preset 必然撞服务）：

```ts
// packages/preset/agent-presets/src/mount.ts
export async function mountPreset(agentCtx: Context, preset: AgentPreset): Promise<void> {
  const scope = scopeOf(agentCtx)
  if (scope === undefined) throw new Error('refusing to mount preset ... into an unscoped context')
  const handle = agentCtx.plugin(PresetTree, config)    // 直接插子树，不经 Loader entry
  await handle.await()
  const unusable = inactiveRows(tree)
  if (unusable.length > 0) throw new Error(`${...} row(s) did not activate:\n${unusable.join('\n')}`)
  const leaked = leakedServices(agentCtx, fiber)
  if (leaked.length > 0) throw new Error('row(s) published process-global service(s) ...')
}
```

`PresetTree` 还重写了两个继承行为：bare import 改从 harness 安装目录解析（用户 home 下的 preset 找不到 `@deepseek-ai/dsh-*`）；`write()` 置空——preset 是输入不是持久化目标，禁止 Loader 把树回写进 preset 文件。

## 七、settings：分层配置与加载校验

### 7.1 三层 resolve 顺序

`ctx.settings` 是能力缝（Service Definition 在 `packages/settings/settings`，文件 Provider 在 `settings-file`）。每个命名 namespace 的值按固定三层合成：**schemastery schema 默认值 → 注册方的 composition `base`（entry config 子集）→ 用户文档段**，拿到的结果递归冻结：

```ts
// packages/settings/settings/src/index.ts（SettingsScope 契约注释）
export interface SettingsScope<T> {
  /** Current resolved value: schema defaults, then `base`, then the user layer. */
  get(): T
  watch(callback: (next: T, prev: T) => void | Promise<void>): () => void
  update(patch: object): Promise<void>     // 稀疏 merge 进用户层
  replace(section: object): Promise<void>  // 整体替换；{} 回到 base/默认
}
```

注册时可给 `validate`（schema 表达不了的跨字段约束），它拦的是**写**；外部改文档导致校验失败时保留「last good value」并告警，正在运行的 owner 不会被坏文档挂起。写入还带 `expectedRevision` 乐观锁，过期写入抛 `SettingsConflictError`。

### 7.2 文件 Provider：热发布 + 注释保留

```ts
// packages/settings/settings-file/src/index.ts
/**
 * One YAML or JSON document under the user's harness home carries every
 * namespace section; external edits hot-publish through the seam, and every
 * write re-reads the document under a cross-process writer lock before
 * patching it as a comment-preserving leaf-level diff.
 */
```

即：`$DSH_HOME/settings.yaml` 单文档承载所有 namespace；chokidar 监听外部编辑并热发布；写入走跨进程文件锁 + 原子写，YAML 以叶子级 diff 打补丁保留注释。base bundle 的注释也印证：`llm-deepseek:` 段就是 Web Models 页写入、免重启覆盖 adapter 行的载体。

### 7.3 插件如何接 settings

agent-loop 把「最大并行工具调用数」开放为用户可写项，而 `agents` 启动数组刻意不开放（改了也只像生效）：

```ts
// packages/core/agent-loop/src/index.ts
installSettingsSection(ctx, AGENT_LOOP_SETTINGS_NAMESPACE, AGENT_LOOP_SETTINGS_SCHEMA, entry, {
  validate: value => void resolveMaxParallelToolCalls(value.maxParallelToolCalls),
  setSource: (current) => { source = current },
  onChange: () => {},
})
// config 里用 getter，每个调度组决策时现读，热改只影响下一组
get maxParallelToolCalls() { return source().maxParallelToolCalls }
```

### 7.4 preset/persona 如何装配

- **persona**（`packages/preset/persona`）：一个 scope-only 行。全局 persona 由 `system-prompt` 注册无条件注册，persona 行挂在 preset 的 agent scope 里就**遮蔽**部署级 persona；挂全局则与注册表自身的注册碰撞并 fail loud。`complete: true` 可把 persona 变成完整 system prompt（抑制其他所有 section）。
- **agent-presets**（`packages/preset/agent-presets`）：roster 服务，roots 配置只读 shipped 目录（`trust: system`）加默认追加的 `$DSH_HOME/.agent-presets`（等同 shell 信任，因为 preset 本身就是一份组合）；默认 preset 名本身也存 settings namespace `agent-presets`。web bundle 用一行 `- id: agent-presets` insert 进树，launcher 再用 overlay 把 shipped root 路径补进去。

### 8.2 dsh-headless：一次性任务模式

patch 做三件事：覆盖 persona、关掉共享 HMR、覆盖 tools 的 mode；再 insert 三行：

```yaml
# packages/bundle/headless/cordis.patch.yml
- insert:
    - id: code-runtime
      name: '@deepseek-ai/dsh-code-runtime-worker-thread'
    - id: headless-startup
      name: '@deepseek-ai/dsh-headless/startup'
    - id: headless-runner
      name: '@deepseek-ai/dsh-headless'
      inject: [headlessStartup]
      config:
        task: !!js ctx.headlessStartup.task
```

runner 是「直接驱动 Agent」的最小范例：等整树沉淀 → 从 default-model 服务取路由 → `agents.create` → 先 `whenIdle` 取首 seq → `followup(task)` → 再 `whenIdle` → flush session → 汇总最后一条 assistant 文本打印 → 请求退出码：

```ts
// packages/bundle/headless/src/index.ts
export const inject = ['agentDefaultModel', 'agents', 'sessions']
async function run(ctx, task, io) {
  await ctx.get('loader')?.await()
  const selection = ctx.get('agentDefaultModel').currentSelection()
  const { agent } = await agents.create({
    sessionId: SessionId(`session-${randomUUID()}`),
    meta: { cwd: process.cwd() },
    agentOptions: { provider: selection.provider, model: selection.model },
    setup: (agentCtx) => installModelSelection(agentCtx, { current: selection, assembled: undefined }),
  })
  await agent.whenIdle()
  const firstSeq = agent.session.seq
  agent.followup(createUserMessage({ content: [{ type: 'text', text: task }], source: { kind: 'user' } }))
  await agent.whenIdle()
  await sessions.flush(agent.session)
  const outcome = summarize(agent.session.events, firstSeq)
  io.stdout.write(outcome.text + '\n')
  io.exit(outcome.reason?.kind === 'completed' ? 0 : 1)
}
```

### 8.3 dsh-web-app：浏览器 surface

web bundle 在 base 之上做两类动作：

1. **覆盖 base 行**：persona、hmr 关闭、tools.mode、session-query 配置（patch 整 config 替换，所以逐键重述）。
2. **insert 一大批 web 专属行**，分两层：
   - host/transport：`storage*`、`workspace`、`api-gateway`（`host-apiproxy`）、`cordis-host-runner`、`web-startup`（旗标 provider）、`webserver`（`inject: [webStartup]`）、`web-runtime`（解析 dist、挂载静态资源、注册 web prompt section、打印 URL、开浏览器，bind 后 provide `webRuntime`）、`client-hmr`；
   - browser roster（`dsh.client` 行，node 半边扫树拼成 `window.__DSH_BOOT__`）：`modules`、`connection`、`ui-theme/layout/sidebar/settings*/conversation/tool/...` 几十个客户端插件。

3. **把 agent 平面整体挪到 preset 之后**：显式 `disabled` 掉 base 的 `tool-bash`、`tool-fs`、`tool-skill`、`compaction-basic`、`tool-subagent*` 等模型可见行，改由每个 session 挂载的 agent preset 提供；而 jobs/skill/subagent **注册表**、token-meter、goal 服务等保留 host 平面（Remote RPC 在 session 存在之前就要解析它们）。注释里反复强调「disable 而不是删除」：base 是共享的，行缺席会在组合重排那天悄悄复活。

## 九、调试能力：--dump-config 与其他观测口

### 9.1 boot-free 配置转储

`dsh --profile web --dump-config` 不启动任何 app 插件、不求值 `!!js`，只用**同一个** `applyEntryPatches` 把各层拍成最终行列表，并逐层 diff 标注每行的来源与修改者：

```ts
// packages/boot/app-boot/src/index.ts
// snapshot_k = 对 layers 1..k 的一次扁平化 apply；snapshot_N 即实际挂载的组合
const snapshot = (count, warnings) => {
  const flattened = structuredClone(layers.slice(0, count).flatMap(l => l.patches))
  return applyEntryPatches(base, flattened, ...)
}
```

输出用 `# == <file>, patched by <layer>` 注释把连续同源行分组，仍是可加载的 YAML。`--dump-default-config` 是修复诊断：跳过用户层和 overlay（坏掉的 `cordis.patch.yml` 不会被解析），只打 bundle 层。

### 9.2 其他装配期观测手段

- **activation 审计错误**：pending 行会直接列出缺失服务名，是排查「插件为什么没起来」的第一现场。
- **preset 挂载审计**：`inactiveRows` / `leakedServices` 的报错会逐行点名。
- **HMR 日志**：根 Include 可配 `enableLogs` 观察 apply/reload/unload。
- **patch miss 告警**：boot 时 include 对匹配不到 id 的 patch 走 logger（dump 时走 stderr），跨 surface 共用 overlay 不致命但可见。

## 十、面试高频 Q&A

**Q1：执行 `dsh --profile web --port 8080` 后到插件树就绪，经过哪些步骤？**

A：bin 用 commander 只切出 launcher 自己的旗标（profile/repeatable patch/dump），其余参数原样保留；`loadLayeredEnv` 固化三层环境快照；`composeProfile` 解析 profile 目录、按 `dsh.profile.bundles` 双锚点定位每个 bundle 的 patch 文件，按「bundle 堆叠 → profile patch → home patch → --patch overlay → 标志位 patch」用 include 的 `applyEntryPatches` 合成（不落盘）；`boot()` 新建 Context、挂 Loader、在 prepare 里 provide 环境快照和 cmdline 服务，然后以固定 id `include` 挂载根 Include（配置是那个内容为 `[]` 的 cordis.yml + patches）；Loader 并发拉取所有 entry，按 inject 服务可用性激活；`loader.await()` 沉淀后 `assertEntriesActivated` 审计失败/pending 行；最后挂两个 patch 文件 watcher 支持热重组。`--port 8080` 由 web-startup 插件自己解析后 provide 成 `webStartup`，webserver 行通过 `!!js ctx.webStartup.port` 惰性读取。

**Q2：patch 为什么能覆盖任意配置行？config 是深合并吗？**

A：根配置是空数组，整棵树是 patch apply 的产物。patch 分两类：无 id 的 `insert` 追加行；带 id 的 patch 对 entryMap 中的目标行做逐字段赋值（`target[key] = value`），所以 `config` 是**整体替换**，上层必须重述全部自有键，`disabled` 也是同理。同层中新插入的行会立即建索引，后续 patch 立刻可覆盖。匹配不到 id 只告警不报错。

**Q3：Cordis 的插件卸载为什么能自动回滚注册？**

A：`ctx.plugin()` 为每次调用开一个 Fiber；插件体内所有注册（`ctx.on`、服务绑定、自定义资源）都走 `fiber.effect(execute)`，execute 同步执行并收集返回的 disposer。Fiber unload 时把该 fiber 的 disposer **逆序**执行；插件因 inject 未满足处于 PENDING 时根本不执行，卸载即无副作用。在已 dispose 的 fiber 上注册直接抛 `INACTIVE_EFFECT`。

**Q4：isolate / scope / group 分别解决什么问题？**

A：`ctx.isolate(name)` 给某个服务换私有 store symbol，同一 label 共享、不同 label 隔离，解决「一份组合里要两套同名服务」；group 行（`cordis:group`）是给 provider 和消费者同发一个 isolate realm 的组合语法。dsh 的 `core/scope` 在其上加了不透明对象身份（ScopeKey）与父子链：`createScope` 用一个空插件 fiber + extend 符号 tag 铸出 agent 级 ctx，事件经 `scopeTarget` 的 filter 只向祖先链传播，注册表视图向下合并，agent 销毁即整层撤销。preset 还额外禁止子树向 root realm 漏服务，避免多 session 撞全局单例。

**Q5：settings 的三层配置和 bundle patch 是什么关系？**

A：两者正交。patch 层解决「组合时挂哪些行、行的启动 config 是什么」（组合期事实，热重组靠 HMR）；settings 是运行期单文档（`$DSH_HOME/settings.yaml`），插件注册 namespace schema 后，值按「schema 默认 → composition base → 用户文档」合成，外部编辑热发布，写入带乐观锁和跨进程文件锁。需要进程启动前定结构的（如 agent-loop 的 `agents` 数组）只走 patch；运行期可改的策略（默认模型、并行度、adapter 凭据段）走 settings。

**Q6：为什么根 cordis.yml 每次启动都重写成 `[]`？**

A：Loader 存在 tree write-back（插件自卸载等场景会把当前树持久化进它读的配置文件）。根文件若保留组合结果，下次启动会把所有 bundle insert 重复一遍。它在磁盘上存在只是因为 Loader 需要一个真实文件锚定 `baseUrl`（dump-config 也锚定同一文件以保证同源），所以 dsh 选择每次重写空根，组合真相只存在于 patch 层。

**Q7：`dsh plugin add <pkg>` 做了什么？**

A：转发给 profile 目录下的 pnpm（相对路径规格先锚定到调用者 cwd，防止 `.` 自连），完成后按**安装实况**对账 `dsh.profile.bundles`：任何声明了 `dsh.bundle` 的依赖自动加入层栈（追加），失去该声明或被移除的依赖退出层栈。这样 `pnpm update` 让一个旧版本没有 bundle 声明的包在新版本自动生效。

## 十一、易错点

1. **以为 patch 的 config 是合并**：实际整字段替换。在 profile patch 里只写一个想改的键，其余键会全部丢失（除非 schema 补默认）。正确做法是重述该行完整 config。
2. **以为行顺序决定启动顺序**：激活由 `inject` 服务可用性驱动，与 YAML 行序无关；`inject: [webStartup]` 可以排在 provider 之前。
3. **waterfall 监听忘记调 `next()` 当成 bug**：在 Cordis 语义里不调 next 是否决（veto），`agent/pre-step` 不调 next 就不会进入 step；而 `agent/turn-stopping` 是 serial，根本没有 next 参数。
4. **在 preset/agent scope 里 provide 全局服务**：会被 `leakedServices` 审计拒绝；跨 session 共享的服务必须放 host 平面或 isolate realm。
5. **直接改根 cordis.yml**：下次启动必被重写覆盖；自定义只能写 profile 的 `cordis.patch.yml`、home patch 或 `--patch` overlay。
6. **误以为 `.env` 能覆盖一切**：`PATH`、`NODE_OPTIONS`、`DSH_*`、代理等 bootstrap-only 名只能由启动环境提供，写进 `.env` 直接拒绝启动；且 `.env` 不替换已继承的同名变量。

## 十三、一句话总结

> dsh 的启动本质是「**空根 + 有序 patch 层在 Cordis Loader 上的一次纯函数组合**」：launcher 只负责切旗标、堆 patch、做失败审计与有界关停；bundle 用 insert/id 覆盖两种行声明整棵树，Cordis 用 Fiber+effect 让每个注册可逆、用 inject 驱动激活、用 isolate/scope 实现按 agent 的隔离与撤销——配置可逐行覆盖、插件可整树热重组、挂载失败逐行点名，是这套装配体系最值得借鉴的三个工程决策。
