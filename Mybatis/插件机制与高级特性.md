# 插件机制与高级特性

MyBatis 的「原理分」主要在这里：**插件 = 责任链 + 动态代理**（PageHelper 就靠它）、**延迟加载 = 代理对象**、**Spring 整合 = SqlSessionTemplate 代理**。三处代理思想一以贯之。

---

## 一、插件原理：四大拦截点 + 责任链

MyBatis 允许在四个对象的创建处「包一层」动态代理：

| 拦截点 | 拦什么 | 典型插件 |
|:---|:---|:---|
| `Executor` | 执行器（update/query/commit/rollback） | **PageHelper 分页**、慢 SQL 监控 |
| `StatementHandler` | Statement 构建与执行 | SQL 打印、DataPermission 行级权限 |
| `ParameterHandler` | 参数设置 | 脱敏/加密参数 |
| `ResultSetHandler` | 结果映射 | 结果解密、敏感字段脱敏 |

```java
// 自定义插件三件套：@Intercepts 声明拦截签名 + implement Interceptor
@Intercepts({
    @Signature(type = StatementHandler.class, method = "prepare",
               args = {Connection.class, Integer.class})
})
public class SqlCostPlugin implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return invocation.proceed();      // 放行：调用下一个插件或原对象
        } finally {
            System.out.println("SQL cost: " + (System.currentTimeMillis() - start) + "ms");
        }
    }
}
```

### 底层机制（面试要能画出来）

```
 Configuration.newStatementHandler()
   └ interceptorChain.pluginAll(handler)          ← 责任链逐层包装
        plugin1 → plugin2 → ... → 原 StatementHandler

 每个插件的 plugin() 里调用 Plugin.wrap(target, this)：
   → JDK 动态代理（Proxy.newProxyInstance）
   → invoke() 里比对 @Signature 方法签名
        ├─ 匹配 → 走 intercept()
        └─ 不匹配 → 直接反射调用原方法
```

- **注册**：`mybatis-config.xml` 或 Spring 配置里声明插件 → 存入 `InterceptorChain`（List）。
- **包装顺序**：pluginAll 按注册顺序**层层代理**，执行时 `proceed()` 是**责任链**往后传。
- 一个插件可用多个 `@Signature` 同时拦截多个点。

## 二、分页：逻辑分页 vs 物理分页 vs PageHelper

| 方案 | 原理 | 评价 |
|:---|:---|:---|
| `RowBounds` | MyBatis 自带：把**全部结果查回内存**再截取 | ❌ 逻辑分页，数据量大直接 OOM，别用 |
| **手写 LIMIT** | SQL 里 `LIMIT #{offset}, #{size}` | 简单可控，但每处都要写 |
| **PageHelper** | 拦截 `Executor.query`，自动改写成 `count(*)` + `LIMIT` | 主流方案 |

PageHelper 工作原理（结合插件机制背）：

1. `PageHelper.startPage(pageNum, pageSize)` 把分页参数放进 **ThreadLocal（Page 对象）**；
2. 插件拦截 `Executor.query` → 检查 ThreadLocal 有分页参数：
   - 先执行改写后的 `SELECT count(*)` 求总数；
   - 再给原 SQL 追加 `LIMIT offset, size` 执行；
3. 用完（查询返回后）**清除 ThreadLocal**。

**ThreadLocal 泄漏坑（必考）**：`startPage()` 之后必须**紧跟一次查询**；若中间抛异常或没执行查询，分页参数残留在 ThreadLocal，会「污染」**线程池里下一个任务**的下一次查询（Tomcat/线程池线程复用）。防御：startPage 与查询放同一 try 块，或用 `PageMethod.startPage` 后立即消费。

```java
// 正确姿势：参数清晰、随用随清
PageHelper.startPage(pageNum, pageSize);
try {
    List<User> list = userMapper.search(params);
    PageInfo<User> page = new PageInfo<>(list);
} finally {
    PageHelper.clearPage();   // 兜底（startPage 内部也会在查询后自动清）
}
```

## 三、延迟加载原理

| 配置 | 含义 |
|:---|:---|
| `lazyLoadingEnabled=true` | 开启延迟加载（默认 false） |
| `aggressiveLazyLoading` | 3.4.1+ 默认 false：调用对象任意方法都触发加载（旧行为） |
| `fetchType=lazy/eager` | 单条映射覆盖全局配置 |

原理（和 Mapper 代理同一思想）：**查询返回的关联对象是运行时生成的代理**（CGLIB/Javassist），内部持有一个 `ResultLoader`；第一次真正访问关联对象的非 `hashCode/equals` 等方法时，才触发 SQL 查询并回填属性。

- 价值：嵌套查询模式下避免「永远用不到的关联查询」→ 缓解 N+1。
- 局限：**延迟不等于免费**——用到了照样发 SQL；且序列化/`toString` 意外触发加载是经典 bug。

## 四、Spring 整合原理（SqlSessionTemplate）

手工用 MyBatis 要自己 `openSession/close`，Spring 整合后这些全部消失：

| 组件 | 职责 |
|:---|:---|
| `SqlSessionFactoryBean` | 把 SqlSessionFactory 作为一个 Spring Bean 构建 |
| `@MapperScan` / `MapperScannerConfigurer` | 扫描 Mapper 接口 → 注册 **MapperFactoryBean**（每个接口一个 Bean） |
| `SqlSessionTemplate` | **线程安全**的 SqlSession 门面（替代手工 session） |
| `SqlSessionInterceptor` | Template 内部的动态代理：方法级 get/release session |
| `SqlSessionHolder` | 事务同步器：把当前 SqlSession 绑到线程（TransactionSynchronizationManager） |

```
 mapper.search()
   → SqlSessionTemplate（单例，无状态）
     → SqlSessionInterceptor.invoke()
          ├─ 事务中？→ 从 ThreadLocal 取已绑定的 DefaultSqlSession（一级缓存生效）
          └─ 无事务？→ 新开 SqlSession → 执行 → 立即 close（查询间一级缓存不共享）
```

两个必考结论：

1. **SqlSessionTemplate 为什么线程安全**——它本身不持有会话状态，每个方法调用都通过代理临时获取/归还 SqlSession。
2. **一级缓存与事务的关系**——`@Transactional` 内多次查询共享同一 SqlSession → 一级缓存命中；非事务查询每次新 session → 看似失效。详见 [缓存机制.md](缓存机制.md)。

## 五、MyBatis-Plus 速览

| 能力 | 说明 |
|:---|:---|
| `BaseMapper<T>` | 通用 CRUD/分页，启动时注入 `MappedStatement`（复用 MyBatis 代理体系） |
| 条件构造器 `LambdaQueryWrapper` | 类型安全的动态条件，替代手写 XML `if` |
| 分页插件 `PaginationInnerInterceptor` | 同 PageHelper 思路：拦截改写 LIMIT |
| 自动填充/逻辑删除/乐观锁插件 | `@TableField(fill)`、`@TableLogic`、`@Version` |
| 代码生成器 | 表 → Entity/Mapper/Service 一键生成 |

> 定位一句话：**MP = MyBatis 的语法糖增强，单表不写 SQL，复杂 SQL 仍回 XML**；两者共存于同一套架构。

## 六、易错点

| 易错点 | 澄清 |
|:---|:---|
| **插件能拦截所有方法** | 只能拦截 `@Signature` 声明的四大对象的方法，其余直接放行 |
| **多个插件顺序无所谓** | 有序：责任链按注册顺序层层代理，执行顺序=逆序 proceed |
| **RowBounds 分页好用** | 内存分页（逻辑分页），大数据量 OOM，生产一律物理分页 |
| **startPage 后忘记查询没关系** | ThreadLocal 残留分页参数，线程复用下污染下一次查询 |
| **延迟加载 = 少执行 SQL 一定快** | 只是把查询时机后移；`toString`/序列化可能意外触发全量加载 |
| **SqlSessionTemplate 需要手动 close** | 不需要，代理方法结束自动归还/关闭 |
| **@MapperScan 扫到接口就能注入** | 需要 SqlSessionFactory（多数据源时要 `sqlSessionTemplateRef` 对应指定） |
| **多数据源共用一个 SqlSessionFactory** | 不行，每套数据源独立 Factory + 扫描路径隔离 |

---

## 七、一句话总结

MyBatis 的高级特性全是**代理**：插件用「JDK 动态代理 + 责任链」在四大对象方法上做 AOP（PageHelper 拦改 SQL + ThreadLocal 传分页参数）；延迟加载用 CGLIB 代理把关联查询推迟到首次访问；Spring 整合用 SqlSessionTemplate 代理实现线程安全与事务内 SqlSession 复用——记「四大拦截点、PageHelper 的 ThreadLocal 生命周期、一级缓存随事务」三个点即可拿下这一篇。
