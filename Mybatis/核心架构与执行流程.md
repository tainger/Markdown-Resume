# 核心架构与执行流程

MyBatis 的面试第一题永远是「**说说 MyBatis 的工作原理**」。答好的关键：三层架构 → 核心组件 → 一条 SQL 的完整旅程 → **Mapper 接口为什么不用写实现类**（动态代理）。

---

## 一、三层架构

```
┌───────────────────────────────────────────────────────────┐
│ 接口层    SqlSession / Mapper 接口（使用者唯一入口）           │
├───────────────────────────────────────────────────────────┤
│ 核心处理层                                                 │
│   配置解析：XMLConfigBuilder → Configuration                │
│   参数映射：ParameterHandler                                │
│   SQL执行：Executor → StatementHandler → JDBC              │
│   结果映射：ResultSetHandler（resultMap 自动/手动映射）       │
│   插件体系：InterceptorChain（四大拦截点）                    │
├───────────────────────────────────────────────────────────┤
│ 基础支撑层  数据源/事务工厂、TypeHandler、反射工具、日志、缓存   │
└───────────────────────────────────────────────────────────┘
```

核心组件一句话职责：

| 组件 | 职责 | 生命周期 |
|:---|:---|:---|
| `SqlSessionFactoryBuilder` | 解析配置，建工厂 | 方法局部变量（用完即弃） |
| `SqlSessionFactory` | 生产 SqlSession，持有 `Configuration` | **应用级单例** |
| `SqlSession` | 一次数据库会话的门面：CRUD + 事务边界 | **请求/方法级**，非线程安全 |
| `Executor` | 真正的执行器：缓存判断、事务提交、SQL 发放 | 随 SqlSession |
| `StatementHandler` | 封装 `Statement`、设置参数、执行 | 随 Executor |
| `ParameterHandler` | Java 参数 → JDBC 占位符（配合 TypeHandler） | 随 StatementHandler |
| `ResultSetHandler` | ResultSet → Java 对象（映射、关联嵌套） | 随 StatementHandler |
| `MappedStatement` | 一条 SQL 的全部元信息（id、SQL、入参/出参映射） | Configuration 持有，全局 |

> 「Executor → StatementHandler → Parameter/ResultSetHandler」这条链就是**插件系统的四大拦截点**，详见 [插件机制与高级特性.md](插件机制与高级特性.md)。

---

## 二、一条 SQL 的完整旅程（必背）

```
UserMapper.selectById(1)                    ← 接口方法调用
  │
  ├─ MapperProxy.invoke()                   ← 动态代理接住调用
  │    └ MapperMethod → SqlSession.selectOne()
  │
  ├─ Executor.query()
  │    ├─ 二级缓存（CachingExecutor 装饰）→ 命中直接返回
  │    ├─ 一级缓存（PerpetualCache）→ 命中直接返回
  │    └─ 未命中 → doQuery()
  │
  ├─ StatementHandler
  │    ├─ 创建 PreparedStatement
  │    ├─ ParameterHandler 设参（#{} 占位符赋值）
  │    └─ execute() → JDBC 执行
  │
  ├─ ResultSetHandler
  │    └─ 按 resultMap/resultType 映射成 List<User>
  │
  └─ 写入一级缓存 → 返回
```

配置解析阶段（应用启动）做的事：`XMLConfigBuilder` 解析 mybatis-config + Mapper XML/注解，把**每条 SQL 包装成 `MappedStatement`**，以 `namespace + "." + id` 为 key 存进 `Configuration`——这就是 Mapper 接口能找到 SQL 的根本原因。

## 三、Mapper 接口为什么不用写实现类（必考）

**答案：JDK 动态代理。** `SqlSession.getMapper()` 返回的是运行时生成的代理对象：

```java
// 1. 入口：DefaultSqlSession.getMapper
public <T> T getMapper(Class<T> type) {
    return configuration.<T>getMapper(type, this);
    // → MapperRegistry： knownMappers.get(type) → MapperProxyFactory
}

// 2. 工厂：每次 new 一个 MapperProxy（JDK 动态代理的 InvocationHandler）
public T newInstance(SqlSession sqlSession) {
    MapperProxy<T> mapperProxy = new MapperProxy<>(sqlSession, mapperInterface, methodCache);
    return (T) Proxy.newProxyInterface(...);  // Proxy.newProxyInstance 创建代理
}

// 3. 核心拦截逻辑：MapperProxy.invoke()
public Object invoke(Object proxy, Method method, Object[] args) {
    if (Object.class.equals(method.getDeclaringClass()))
        return method.invoke(this, args);      // toString/hashCode 直接放行
    return cachedInvoker(method).invoke(proxy, method, args, sqlSession);
    // → MapperMethod：把「接口方法」翻译成「MappedStatement 执行」
}

// 4. MapperMethod：解析方法 → 找到 SQL
//    接口全限定名 = XML 的 namespace，方法名 = SQL 的 id
final String statementId = mapperInterface.getName() + "." + method.getName();
```

要点（面试逐条讲）：

1. **接口全限定名 ↔ namespace、方法名 ↔ id**，两者对上就能从 `Configuration` 拿到 `MappedStatement`（含 SQL 类型 INSERT/UPDATE/SELECT）。
2. `MapperProxy` 用 `ConcurrentHashMap<Method, MapperMethodInvoker>` **缓存方法解析结果**，避免每次反射解析。
3. 为什么用接口不用类：代理只能实现接口方法；接口约定即「SQL 的签名」，参数/返回值由 `MapperMethod` 解析成 `SqlCommand` + `MethodSignature`。
4. MyBatis-Plus 的 `BaseMapper` 通用 CRUD 也是同一套：启动时把通用方法以 `MappedStatement` 形式**注入** Configuration。

## 四、Executor 三种执行器

| 类型 | 特点 | 场景 |
|:---|:---|:---|
| `SIMPLE`（默认） | 每条 SQL 都新建 `PreparedStatement` | 常规 CRUD |
| `REUSE` | 以 SQL 字符串为 key 复用 `Statement` | 同一批大量相似 SQL，减少预编译开销 |
| `BATCH` | 攒一批后统一 `executeBatch()` | **批量插入/更新**（万级数据首选），不回传自增主键 |

```java
// 批量插入的正确姿势（千~万级）
try (SqlSession session = factory.openSession(ExecutorType.BATCH)) {
    UserMapper mapper = session.getMapper(UserMapper.class);
    for (int i = 0; i < 100000; i++) {
        mapper.insert(userList.get(i));
        if (i % 1000 == 999) session.flushStatements(); // 分批刷，防内存涨
    }
    session.commit();
}
```

> 与 `foreach` 拼大 SQL 批量插入的取舍：foreach 一条超长 SQL 快但受 `max_allowed_packet`/参数上限约束；BATCH 稳定可控。详见 [动态SQL与参数绑定.md](动态SQL与参数绑定.md)。

## 五、MyBatis vs Hibernate/JPA（高频对比题）

| 对比项 | MyBatis | Hibernate/JPA |
|:---|:---|:---|
| 定位 | **SQL Mapper**（SQL 写在手） | **ORM**（对象自动映射，屏蔽 SQL） |
| SQL 控制权 | 完全自控，可写复杂 SQL/优化 | 自动生成，复杂查询要 HQL/原生 SQL 兜底 |
| 学习/上手 | 快，门槛低 | 重，概念多（一级/二级缓存、脏检查、懒加载陷阱） |
| 性能调优 | 直接改 SQL，DBA 友好 | 难（生成 SQL 不可控） |
| 数据库移植 | 弱（SQL 绑方言） | 强（方言抽象） |
| 适用 | 互联网业务（复杂查询、极致优化） | 传统企业系统（领域模型稳定） |

一句话：**MyBatis = 半自动 ORM，要灵活找它；Hibernate = 全自动，要省心找它**。国内互联网主流是 MyBatis / MyBatis-Plus。

## 六、易错点

| 易错点 | 澄清 |
|:---|:---|
| **SqlSession 线程安全，可以单例** | ❌ 每次 `openSession()` 新建，用完 close；Spring 里由 SqlSessionTemplate 帮你管理（见 [插件机制与高级特性.md](插件机制与高级特性.md)） |
| **SqlSessionFactory 每次 new** | 应**应用级单例**，重复创建浪费解析开销 |
| **Mapper 接口有实现类** | 没有实现类，是 **JDK 动态代理**（MapperProxy） |
| **接口方法重载** | 一个 namespace 下 id 必须唯一，接口方法**不能重载**（同名方法映射不到唯一 SQL） |
| **XML 与注解同时定义同一 SQL** | 同一方法只能有一种定义，否则启动报 `MappedStatement` 重复 |
| **Executor 默认是 BATCH** | 默认 `SIMPLE`；BATCH 要显式 `openSession(ExecutorType.BATCH)` |

---

## 七、一句话总结

MyBatis = **启动时**把每条 SQL 解析成 `MappedStatement` 存进 Configuration；**运行时**由 `SqlSession → Executor → StatementHandler → JDBC` 四级流水执行，缓存先于 DB 判断；Mapper 接口靠 **JDK 动态代理**（namespace=接口名、id=方法名）把方法调用翻译成 SQL 执行——这就是「没写实现类却能跑」的全部秘密。
