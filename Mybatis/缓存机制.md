# 缓存机制：一级缓存与二级缓存

MyBatis 缓存是「**SqlSession 一级 + namespace 二级**」的两级结构。面试三连：区别、失效场景、**生产上为什么建议关二级缓存**。

---

## 一、缓存体系全景

```
 查询请求
   │
   ▼
 CachingExecutor（二级缓存壳，默认不开启时就是个透传）
   │  ← namespace 级缓存：跨 SqlSession 共享
   ▼
 BaseExecutor
   ├─ PerpetualCache（一级缓存）  ← SqlSession 级：同一会话内共享
   │    └ 本质就是 HashMap<String, Object>
   ├─ 缓存未命中 → QueryFromDatabase → StatementHandler → JDBC
   └─ 事务缓存 TransactionalCacheManager（二级缓存真正写入的时机管理）
```

**查询顺序：二级 → 一级 → 数据库**（开启二级后）。

---

## 二、一级缓存（默认开启）

| 属性 | 说明 |
|:---|:---|
| 作用域 | **SqlSession** 级（JDBC 连接级） |
| 底层 | `PerpetualCache` → 一个 `HashMap`（`BaseExecutor.localCache`） |
| key | `MappedStatement id + offset + limit + SQL + 参数 + 环境` |
| 开关 | 默认 `localCacheScope=SESSION`；可设 `STATEMENT` 每条语句执行完即清 |

**失效场景（必背）**：

1. 同一 SqlSession 内执行 `insert/update/delete`（flushCache=true）→ 清空一级缓存；
2. `sqlSession.clearCache()` / `commit()` / `close()`；
3. 查询不同的 `MappedStatement`（不同 SQL）；
4. `flushCache=true` 的查询配置；
5. **不同的 SqlSession**（各自有各自的缓存，天然隔离）。

经典并发安全题：一级缓存导致**脏读**——两个 SqlSession，A 查了一次缓存住，B 更新了库并提交，A 再查还是旧值。单请求内通常无害；但**开启事务**时要清楚「事务内重复读可能来自缓存」。

**Spring 整合下的真相（高频追问）**：没有事务时，`SqlSessionTemplate` 每次查询都 **新建并立即关闭** SqlSession → 一级缓存「看似失效」（命不中跨查询）；**同一个事务内**（`@Transactional`），SqlSession 被绑定到线程（`SqlSessionHolder`）复用 → 一级缓存生效。所以「一级缓存在 Spring 里失效」这句话不严谨，准确说法是**非事务查询间不共享**。

---

## 三、二级缓存（namespace 级，默认关闭）

| 属性 | 说明 |
|:---|:---|
| 作用域 | **namespace（Mapper）** 级，跨 SqlSession 共享 |
| 开启方式 | 全局 `cacheEnabled=true`（默认 true，但还需 Mapper 上声明才真正生效）+ XML `<cache/>` 或注解 `@CacheNamespace` |
| 结构 | `CachingExecutor` 包装 `Executor`，命中则不走数据库 |
| 存储 | 装饰器链：`PerpetualCache` + `LruCache/FifoCache` + `SoftCache/WeakCache` + `BlockingCache`… |
| 写入时机 | **事务提交时**才真正写入（`TransactionalCacheManager` 管理，防未提交数据被别人读到） |
| 失效 | 该 namespace 的增删改会清空其二级缓存；`flushCache=true` |

```xml
<!-- Mapper.xml -->
<cache eviction="LRU" flushInterval="60000" size="1024" readOnly="false"/>
```

### 二级缓存的三大坑（面试深挖点）

1. **多表 join 脏读**：A namespace 的 SQL 关联了 B 表，B namespace 更新数据**只会清 B 的缓存**，A 的缓存照旧 → 返回旧数据。根因：缓存以 namespace 为单位，**失效粒度和数据关联粒度不一致**。补救：`<cache-ref namespace="B"/>` 让多个 namespace 共享同一份缓存（牺牲隔离换正确性）。
2. **分布式失效**：缓存是**本地**的，多实例部署时实例 1 更新只清自己的缓存，实例 2 还拿着旧值 → 必须换 Redis 等集中式缓存（MyBatis 二级缓存基本不用于生产集群）。
3. **序列化要求**：`readOnly=false` 时所有对象必须可序列化（深拷贝隔离），有性能成本。

> **生产建议（背下来）**：MyBatis 自带二级缓存适用面太窄（单表、单实例、读极多写极少），互联网生产普遍**关闭二级缓存，用 Redis/Caffeine 做应用层缓存**——失效策略由业务自己控制，粒度清晰。

---

## 四、一级 vs 二级 对比表（面试直接背）

| 对比项 | 一级缓存 | 二级缓存 |
|:---|:---|:---|
| 作用域 | SqlSession | namespace（Mapper） |
| 默认 | **开启** | 关闭（需 `<cache/>` 声明） |
| 共享范围 | 会话内 | 跨会话、跨线程 |
| 底层 | PerpetualCache（HashMap） | 装饰器链（LRU 等）+ 事务提交才写入 |
| 开关粒度 | `localCacheScope` | `cacheEnabled` + Mapper 声明 |
| 生产态度 | 无害保留 | **建议关闭**，用 Redis/Caffeine 替代 |

---

## 五、易错点

| 易错点 | 澄清 |
|:---|:---|
| **二级缓存全局 cacheEnabled=true 就生效** | 还必须在该 Mapper 上声明 `<cache/>`，两者是「总开关 + 分开关」 |
| **二级缓存在事务提交前可读** | 不能，事务提交（或语句 flush）后才写入，防止脏读 |
| **Spring 里一级缓存完全失效** | 只是**非事务**查询间不共享；同事务内依然命中 |
| **update 只清自己 namespace** | 二级缓存按 namespace 失效，**关联表不会连带清** → 脏读根源 |
| **分布式部署用 MyBatis 二级缓存** | 它是 JVM 本地缓存，多实例各存一份，必须换集中式缓存 |
| **缓存存的是结果对象引用** | `readOnly=false` 时返回序列化拷贝；`true` 是共享引用（只读约定） |

---

## 六、一句话总结

MyBatis 缓存两级：**一级是 SqlSession 内的 HashMap（默认开、会话内共享、增删改即失效）**；**二级是 namespace 级的共享缓存（默认关、事务提交才写、多表/分布式两大坑）**。生产结论一句话：**一级缓存放心用，二级缓存改用 Redis/Caffeine**。
