## 二、逐题详解

### Q1：@Transactional 加在类 / 方法 / 接口上的行为差异？多方法调用时事务边界怎么走？

**注解位置行为表**：

| 位置 | 行为 | 生产建议 |
|:---|:---|:---|
| **类上** | 该类所有 public 方法都加事务 | 小工具类可用；业务类慎用（只读方法被无意义开事务） |
| **方法上** | 仅该方法（最细粒度） | **生产首选** |
| **接口上** | JDK 代理生效，CGLIB 不一定生效（版本相关） | 一律不推荐 |
| private / protected | 不生效（代理默认只代理 public） | 详见 [AOP与事务](AOP与事务.md) 失效场景 1 |

**多方法调用的事务边界**（默认 REQUIRED 加入外层，详见 [AOP与事务](AOP与事务.md) 传播行为章节）：

```java
// 同类自调用 —— 走 this 绕过代理，@Transactional 不生效
@Service
public class OrderService {
    @Transactional public void create() { this.detail(); }   // this 走原对象，detail 的 @Transactional 不生效
    @Transactional public void detail() { ... }
}
// Controller 调 orderService.create():
//   ├─ 进入 create 代理：开事务 T1
//   ├─ create 内部 this.detail()：不走代理，detail 在 T1 里跑（detail 的 @Transactional 等同没加）
//   └─ create 返回：T1 提交
```

```java
// 跨类调用 —— 走代理能感知外层
@Service public class A {
    @Autowired private B b;
    @Transactional public void a() { b.b(); }   // 开 T1
}
@Service public class B {
    @Transactional public void b() { ... }      // 默认 REQUIRED：加入 T1，不新开
}
```

> **口诀**：跨类调用走代理能感知外层 → 默认 REQUIRED 加入；同类自调用走 this → 代理失效，连"加入"都没机会谈。自调用失效的 3 种解决办法（注入自己 / AopContext.currentProxy / 拆类）见 [AOP与事务](AOP与事务.md) 代理陷阱章节。

### Q2：@Transactional 注解的 7 个属性在生产怎么配？只用默认值会踩什么坑？

```java
@Transactional(
    propagation = Propagation.REQUIRED,                  // 传播行为（详见 AOP与事务.md）
    isolation   = Isolation.DEFAULT,                     // 隔离级别（继承 DB 默认）
    timeout     = -1,                                     // 超时秒数（-1 不超时）
    readOnly    = false,                                  // 只读标记
    rollbackFor       = {},                              // 触发回滚的异常类型
    noRollbackFor     = {},                              // 不触发回滚的异常类型
    value / transactionManager = "transactionManager"     // 用哪个事务管理器
)
```

**生产配置模板与坑表**：

| 属性 | 默认值 | 坑 | 生产模板 |
|:---|:---|:---|:---|
| `propagation` | REQUIRED | 90% 场景就够；日志/审计也用 REQUIRED 会让主流程失败时日志一起回滚 | 业务方法 REQUIRED；日志审计 REQUIRES_NEW |
| `isolation` | DEFAULT（继承 DB） | MySQL 默认 RR，高并发热点行更新场景下 RR 行锁竞争激烈 | 通常 DEFAULT；秒杀等场景显式 READ_COMMITTED 减锁竞争 |
| `timeout` | -1（不超时） | 没超时保护，长事务一直占着连接 | 查询方法设 3~5s；写方法设 30s |
| `readOnly` | false | 不打标优化器走只读路径没机会 | **只 select 的方法必加 `readOnly=true`**（语义清晰 + Hint） |
| `rollbackFor` | RuntimeException + Error | **SQL 异常不回滚**——生产事故第一坑 | **永远写 `rollbackFor = Exception.class`** |
| `noRollbackFor` | 空 | 某些"友好异常"不想让整单事务回滚 | 极少用；如 `noRollbackFor = BizSkipException.class` |
| `value` | "transactionManager" | 多数据源忘切，写了主库事务管理器但 SQL 走从库 → 失效（见 Q4） | 多数据源每个 @Transactional 显式指定 value |

**最容易翻车的两条**：

1. **rollbackFor 默认值**——Spring 默认只回 RuntimeException，所有受检异常（IOException / SQLException）都不回滚。生产必须显式 `rollbackFor = Exception.class`。详见 [AOP与事务](AOP与事务.md) 失效场景 8。
2. **readOnly 不写**——纯查询方法不开 readOnly，MySQL 不会路由到从库、Hibernate 也不会跳 FlushMode；写 `readOnly=true` 是免费的优化。

### Q3：编程式事务 vs 声明式事务，什么场景选哪个？

| 维度 | 声明式 @Transactional | 编程式 TransactionTemplate |
|:---|:---|:---|
| **灵活度** | 整个方法一个事务边界 | 可在方法内部任意粒度开 / 提交 |
| **侵入性** | 0（注解） | 中（需写 lambda） |
| **性能** | 走 AOP 代理切面 | 直调事务管理器，无代理开销 |
| **局部回滚** | 不支持（事务整体回滚） | 配合 savepoint 可局部回滚 |
| **适用场景** | 90% CRUD、Service 标准方法 | 复杂流程：批量任务、循环内独立事务、嵌套子事务 |

**编程式两种写法对比**：

```java
// 1) TransactionTemplate（推荐，lambda 风格）
@Autowired private TransactionTemplate txTemplate;

public void batchInsert(List<Order> orders) {
    for (List<Order> chunk : Lists.partition(orders, 500)) {
        txTemplate.execute(status -> {       // 每个分片独立事务
            chunk.forEach(dao::insert);
            return null;
        });
    }
}

// 2) PlatformTransactionManager（更底层，更少用）
@Autowired private PlatformTransactionManager txManager;

public void manual() {
    TransactionStatus status = txManager.getTransaction(new DefaultTransactionDefinition());
    try {
        dao.insert(...);
        txManager.commit(status);
    } catch (Exception e) {
        txManager.rollback(status);
    }
}
```

**选型决策树**：

```
方法整体一个事务边界？
├─ 是 → @Transactional（默认选这个）
└─ 否 → 方法内需要多次独立事务 / 局部回滚 / 批量分片
        └─ 用 TransactionTemplate
```

> 编程式事务的两个典型场景：① 批量导入 100 万行分批 500 一事务（避免长事务）；② 主流程异常后还要写审计表（用 REQUIRES_NEW 在主流程 catch 后单独开事务）。

### Q4：多数据源场景 @Transactional 怎么走？为什么"明明配了主库事务管理器，写从库不回滚"？

**经典坑场景**：

```java
@Configuration
public class DataSourceConfig {
    @Bean(name = "masterTxManager")
    public DataSourceTransactionManager master(@Qualifier("masterDataSource") DataSource ds) { ... }

    @Bean(name = "slaveTxManager")
    public DataSourceTransactionManager slave(@Qualifier("slaveDataSource") DataSource ds) { ... }
}

@Service
public class OrderService {
    @Transactional                            // ❌ 没指定 value，默认按主事务管理器
    @DS("slave")                              // 但 SQL 被自定义 AOP 路由到从库 DataSource
    public void query() {
        // 事务管理器从 masterTxManager 的 DataSource 拿 Connection → 走主库
        // 但 SQL 被 @DS AOP 切到了从库 DataSource → 不在事务里！
        // 现象：异常不回滚，且事务管理器误以为事务已开（实际是另一个 DS 的连接）
    }
}
```

**根因**：Spring 事务 = 事务管理器 + DataSource。事务管理器只管它自己 DataSource 的 Connection；如果业务 SQL 走另一个 DataSource，事务对它无能为力。原理见 [AOP与事务](AOP与事务.md) ThreadLocal 章节。

**解决对照表**：

| 方案 | 做法 | 局限 |
|:---|:---|:---|
| 显式指定事务管理器 | `@Transactional(value = "slaveTxManager")` | 必须每个方法手写，容易漏 |
| 自定义切面自动选 | 拦截 @DS 注解，自动给 @Transactional 设置对应 txManager | 实现复杂 |
| 多数据源中间件 | dynamic-datasource-spring-boot-starter 等开箱即用 | 引入依赖 |
| **跨库事务** | 单机 @Transactional **无法保证**，必须 Seata 等 | 见 Q9 |

> **生产铁律**：跨 DataSource 的操作，本地 @Transactional **保证不了**原子性。要么单库内闭环，要么上分布式事务。

### Q5：线上一段 SQL 在事务里执行太久，把连接池占爆，怎么排查与治理？

**排查骨架（三步）**：

```text
① 现象定性：HikariCP 报 "Connection is not available, request timed out after 30000ms"
② 看谁占着连接：jstack 抓线程 → 找 WAITING 在 HikariPool.getConnection 的业务线程
   → 看它的栈顶在干什么（DB 等待？外部 RPC？文件 I/O？）
③ 找源头：日志按 traceId 串起来 → 看哪个 @Transactional 方法耗时最长
```

**长事务 4 大典型元凶**：

| 元凶 | 例子 | 修复 |
|:---|:---|:---|
| **事务内做远程调用** | `@Transactional` 方法内调 RPC、HTTP、发邮件 | RPC 移出事务外，只把 DB 操作留在事务里 |
| **大批量循环** | `for (i..10000) dao.insert()` | 改批量 insert / 分片编程式事务（Q3） |
| **等用户输入 / 文件上传** | `@Transactional` 方法读 MultipartFile 流 | 移到事务外读完，再传字节进事务 |
| **索引差导致 SQL 慢** | 事务里一句 update 扫表 5s | 加索引治本（见 [mysql/SQL优化的实际场景](../mysql/SQL优化的实际场景.md)） |

**HikariCP 配置层面的兜底**：

```yaml
spring:
  datasource:
    hikari:
      connection-timeout: 3000      # 拿不到连接 3s 就失败（默认 30s 太长）
      max-lifetime: 600000          # 连接最长生命周期 10min，防止 DB 端 idle 断开
      maximum-pool-size: 20         # 别一味调大，连接数 > CPU 核数 × 2 + 磁盘数 后反而降速
```

> **治理心法**：@Transactional 方法体里只放 DB 操作；所有 RPC、文件、睡眠、外部资源访问一律移出去。事务越短越好——连接池是公共资源。

### Q6：事务方法里写了 Redis，事务回滚但缓存脏写怎么办？

**问题场景**：

```java
@Transactional(rollbackFor = Exception.class)
public void pay(Order order) {
    dao.updateStatus(order);                       // DB 写
    redis.set("order:" + order.getId(), order);   // Redis 写
    dao.deductStock(order);                        // DB 写
    // 异常 → DB 回滚
    // ❌ 但 Redis 已经写了，缓存与 DB 不一致！
}
```

**4 种解法对比**：

| 方案 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| 双写不删，依赖 TTL | Redis 写时带过期时间 | 简单 | TTL 内一直脏，业务可感知 |
| 事务提交后再写缓存 | `@TransactionalEventListener` 监听提交事件 | 100% 一致 | 多 1 次同步调用（详见 Q7） |
| 延迟双删 | 提交后 + sleep 500ms 再删一次缓存 | 应对并发 | 加复杂度，sleep 不优雅 |
| **可靠消息最终一致** | 事务内只发 MQ 消息，消费者异步刷缓存 | 解耦 + 性能好 | 引入 MQ，复杂度上升 |

**最常用：事务事件钩子（见 Q7 详解）**

```java
@Component
public class OrderCacheRefresher {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onPay(PayEvent event) {
        redis.set("order:" + event.getOrderId(), event.getOrder());
    }
}
```

> **原则**：DB 是事务边界；Redis / ES 等其他存储都不在事务边界内 → 必须用"事务提交后置钩子"或"可靠消息"做最终一致。

### Q7：@TransactionalEventListener 比 @EventListener 强在哪？事务提交后置钩子解决什么场景？

**两者执行时机对比**：

```text
@Transactional 方法体执行
    ├─ 1. 业务代码
    ├─ 2. applicationEventPublisher.publishEvent(event)   ← 事件发布
    │      ├─ @EventListener         ← 立即同步执行（事务还没提交！）
    │      └─ @TransactionalEventListener(phase = BEFORE_COMMIT)  ← 提交前同步
    ├─ 3. 事务提交 commit()
    └─ 4. @TransactionalEventListener(phase = AFTER_COMMIT)  ← 提交后异步/同步执行 ✅
```

**4 个 Phase 速查**：

| Phase | 时机 | 典型用途 |
|:---|:---|:---|
| BEFORE_COMMIT | 事务提交前（同步） | 同事务内做额外 DB 校验 |
| AFTER_COMMIT | 提交成功后（默认） | **缓存刷新、MQ 发送、外部通知** ← 最常用 |
| AFTER_ROLLBACK | 回滚后 | 回滚补偿：发告警、清缓存 |
| AFTER_COMPLETION | 提交或回滚后 | 通用清理 |

**生产场景**：

| 场景 | 解法 |
|:---|:---|
| 事务提交后刷 Redis（见 Q6） | AFTER_COMMIT 同步刷缓存 |
| 事务提交后发 MQ | AFTER_COMMIT 发可靠消息（提交了再发，避免回滚但消息已发） |
| 事务回滚后清缓存 | AFTER_ROLLBACK 删 Redis key |
| 事务回滚后告警 | AFTER_ROLLBACK 发钉钉/邮件 |

> **核心收益**：把"事务外的副作用"挪到事务提交后，避免事务回滚后还要补救（如发出去的 MQ 撤不回来）。这是 Spring 4.2+ 给的事务边界友好工具，比手写 `TransactionSynchronizationManager.registerSynchronization` 优雅得多。

### Q8：库存扣减的批量接口：REQUIRES_NEW 嵌套 5 层把 HikariCP 打爆，怎么救？

**事故复盘（STAR 结构）**：

- **Situation**：秒杀批量扣减库存接口，Controller → Service → 库存子服务，每层都 `@Transactional(REQUIRES_NEW)`，业务还嵌套 5 层 Service。
- **Task**：单机 50 并发就把 HikariCP 10 连接打爆，前端大量超时。
- **Action**：
  1. jstack 抓 50 个线程都在 `getConnection` WAITING
  2. 沿调用链看：5 层 REQUIRES_NEW = 单请求占 5 个连接
  3. 50 并发 × 5 = 250 个连接需求 vs 池里 10 个 → 必爆
- **Result**：去掉中间层 REQUIRES_NEW，只在最外层保留事务；内层改默认 REQUIRED 加入外层。50 并发只用 50 个连接，过 HikariCP 20 配置毫无压力。

**REQUIRES_NEW 的代价表**：

| 维度 | REQUIRED（默认） | REQUIRES_NEW |
|:---|:---|:---|
| 连接占用 | 加入外层，复用外层 Connection | **新拿一个 Connection**，外层 Connection **挂起暂存** |
| 嵌套 N 层占连接数 | 1 | **N** |
| 适合场景 | 90% CRUD | 日志、审计、必须独立提交的子操作 |

> **铁律**：REQUIRES_NEW 不是"事务更安全"，而是"我要独立提交/回滚"。N 层 REQUIRES_NEW = N 个连接，慎用。原理见 [AOP与事务](AOP与事务.md) 易错点「REQUIRES_NEW 连接泄漏风险」。

### Q9：本地 @Transactional 解决不了的边界在哪？Seata AT/TCC/可靠消息怎么选？

**本地事务的边界**：

```text
单库（同 JVM 同 DataSource）：  @Transactional ✅ 100% 保证
跨库（同 JVM 多 DataSource）： 本地 @Transactional ❌ 无法保证原子
跨服务（不同 JVM）：           本地 @Transactional ❌ 完全无能为力
跨消息中间件：                 本地 @Transactional ❌（DB 提交 + MQ 发送无法原子）
```

**分布式事务 4 种选型对比**：

| 方案 | 一致性 | 侵入性 | 性能 | 典型场景 |
|:---|:---|:---|:---|:---|
| **Seata AT** | 强（最终） | 低（注解） | 中 | 单体应用跨库（undo_log 自动补偿） |
| **Seata TCC** | 强（最终） | 高（写 Try/Confirm/Cancel） | 高 | 资金类、需要业务级回滚 |
| **本地消息表 + MQ** | 最终一致 | 中（消息表 + 重试） | 高 | 跨服务异步通知、可靠消息 |
| **最大努力通知** | 弱 | 低 | 高 | 对账、短信通知（容忍短期不一致） |

**选型决策树**：

```text
跨库（同 JVM）？
├─ 是 → Seata AT（无侵入，自动 undo_log）
└─ 否 → 跨服务
        ├─ 资金 / 库存等关键业务 → Seata TCC（业务级回滚）
        ├─ 异步通知 / 跨服务消息 → 本地消息表 + MQ 最终一致
        └─ 容忍短期不一致       → 最大努力通知
```

> Seata AT/TCC 模式细节见 [SpringCloud微服务.md](SpringCloud微服务.md)；本地消息表实现见 [MySQL/存储引擎与架构.md](../mysql/存储引擎与架构.md) 的两阶段提交思路。

### Q10：Spring 6 WebFlux 里 @Transactional 为什么不生效？TransactionalOperator 怎么写？

**根因**：Spring 事务基于 ThreadLocal 绑定 Connection（见 [AOP与事务](AOP与事务.md) ThreadLocal 章节）；WebFlux 是响应式流（Reactor），跨线程切换，ThreadLocal 失效。

**@Transactional 在响应式栈的失效场景**：

```java
@Service
public class OrderService {
    @Transactional   // ❌ 在 WebFlux 项目里完全不生效！
    public Mono<Void> pay(Order o) {
        return dao.save(o).then(redisSet(o));   // 多次切换线程，事务 ThreadLocal 全程摸不到
    }
}
```

**响应式事务：TransactionalOperator**：

```java
@Service
public class OrderService {
    @Autowired private TransactionalOperator txOperator;
    @Autowired private R2dbcRepository dao;

    public Mono<Void> pay(Order o) {
        return Mono.from(dao.save(o))
            .then(redisSet(o))
            .as(txOperator::transactional)   // ← 把整个 Mono 包装成事务
            .doOnError(e -> log.error("pay failed", e));
    }
}

// 或者类级别注解（Spring 6+）
@Transactional
@Service
public class OrderService {
    @Transactional
    public Mono<Void> pay(Order o) {   // 响应式栈下的 @Transactional 等价于 TransactionalOperator
        return dao.save(o).then(redisSet(o));
    }
}
```

**两者的本质区别**：

| 维度 | @Transactional（传统） | TransactionalOperator（响应式） |
|:---|:---|:---|
| 绑定方式 | ThreadLocal | Reactor Context（流上下文） |
| 线程模型 | 同步，单线程 | 异步，多线程切换 |
| 数据访问 | JDBC（Connection） | R2DBC（ConnectionFactory） |
| 事务管理器 | DataSourceTransactionManager | R2dbcTransactionManager |
| 适合栈 | Spring MVC + JDBC | Spring WebFlux + R2DBC |

> **迁移要点**：传统同步栈 → @Transactional；响应式栈 → TransactionalOperator 或 Spring 6 的响应式 @Transactional（但底层走 R2dbcTransactionManager，不再走 ThreadLocal）。

---

## 三、一句话总结

Spring 事务面试**场景题**核心就 3 件事：**① 注解属性生产配置必背**（`rollbackFor = Exception.class`、只读查询必加 `readOnly=true`、`timeout` 兜底）；**② 事务边界 + 连接池思维**（@Transactional 方法只做 DB 操作、REQUIRES_NEW 慎用因为占连接、多 DataSource 跨库本地事务保证不了）；**③ 事务外的副作用用提交后钩子**（`@TransactionalEventListener AFTER_COMMIT`）替代事务内同步刷缓存 / 发 MQ。分布式事务是 Spring 事务的边界，跨库跨服务用 Seata 或本地消息表；响应式栈用 TransactionalOperator 替代 @Transactional。
