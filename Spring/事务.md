# Spring 事务

Spring 事务 = 「AOP 动态代理 + 事务管理器 + ThreadLocal 绑定 Connection」三件套。本文是**原理层 + 场景层**一体笔记：上半部分讲原理，下半部分讲 11 道面试场景题；AOP 代理机制 / Advice 执行顺序等公共底层见 [AOP.md](AOP.md)。

---

# 第一部分 · 原理层

## 一、事务管理器 PlatformTransactionManager

Spring 事务本质是「把 JDBC Connection 的提交/回滚封装成声明式」。核心接口：

```java
public interface PlatformTransactionManager {
    TransactionStatus getTransaction(TransactionDefinition definition);
    void commit(TransactionStatus status);
    void rollback(TransactionStatus status);
}
```

常见实现：

| 实现类 | 对应场景 |
|:---|:---|
| **DataSourceTransactionManager** | 纯 JDBC / MyBatis / Spring JdbcTemplate —— **生产 90% 用这个** |
| JpaTransactionManager | Hibernate / JPA |
| HibernateTransactionManager | Hibernate（较老） |
| WebSphereUowTransactionManager | WebSphere 应用服务器事务（极少见） |
| R2dbcTransactionManager | Spring 6 响应式栈（R2DBC + WebFlux，见场景题 Q10） |

## 二、Connection 绑定到线程 —— ThreadLocal 机制

Spring 事务保证一个事务里的多次操作共用同一个 Connection，靠的是 `TransactionSynchronizationManager` 的 ThreadLocal：

```
@Transactional 方法开始:
  PlatformTransactionManager.getTransaction():
    ↓
  DataSourceTransactionManager.doBegin():
    1. 从 DataSource.getConnection() 拿新连接
    2. conn.setAutoCommit(false)  ← 关闭 JDBC 自动提交
    3. 把 conn 放入 TransactionSynchronizationManager.resources
       └─ key=DataSource，value=ConnectionHolder
       └─ `ThreadLocal(Map(Object, Object))`  ← 保证同线程同事务同连接

MyBatis/JdbcTemplate 执行 SQL 时:
  DataSourceUtils.getConnection(dataSource):
    1. 先查 TransactionSynchronizationManager.resources 有没有绑定的 conn
    2. 有 → 复用它（在事务里）
    3. 没有 → 临时 new Connection（非事务，每句 SQL 一个连接）

方法正常 return:
  PlatformTransactionManager.commit():
    connection.commit() → connection.setAutoCommit(true) → 从 ThreadLocal 解绑
方法抛 RuntimeException / Error:
  PlatformTransactionManager.rollback():
    connection.rollback() → ... 同上解绑
```

> 这套机制的核心约束：**事务 = ThreadLocal 绑定**。一切破坏线程一致性的场景都会让事务失效：多线程异步方法、@Async 切面切到另一个线程、WebFlux 响应式跨线程切换（见失效场景 6 与场景题 Q10）。

## 三、回滚规则

默认只回滚：

- **`RuntimeException` 及其子类**（空指针、索引越界、业务运行时异常）
- **`Error`**（OOM 等系统错误）

**不回滚**：

- `Exception`（非 RuntimeException，如 IOException、SQLException）
- 受检异常

自定义回滚规则：

```java
// 受检异常也回滚
@Transactional(rollbackFor = {SQLException.class, IOException.class})
// 指定异常不回滚（只回滚 RuntimeException，不回滚 BizException）
@Transactional(noRollbackFor = BizException.class)
```

> **口诀**：默认**跑（RuntimeException）错（Error）回**，受检不回。生产建议**永远显式写 `rollbackFor = Exception.class`**——这是场景题 Q2 第 1 大坑。

## 四、7 种事务传播行为（Propagation）

这是 Spring 事务最精华的部分。**面试官喜欢画场景题让你选传播行为**，先把 7 种的定义和效果理清楚。

### 快速分类

| 行为 | 代码 | 一句话解释 |
|:---|:---|:---|
| **REQUIRED**（默认） | `Propagation.REQUIRED` | **有事务加入、无事务新建** — 最常用 |
| **SUPPORTS** | `SUPPORTS` | 有事务加入，没事务就非事务跑 |
| **MANDATORY** | `MANDATORY` | 强制必须在已有事务里，没事务直接抛异常 |
| **REQUIRES_NEW** | `REQUIRES_NEW` | **挂起外层事务，我新建自己的** — 次常用 |
| **NOT_SUPPORTED** | `NOT_SUPPORTED` | 挂起外层事务，我**非事务**跑（适合不想被事务拖的查询） |
| **NEVER** | `NEVER` | 不能在事务里，有事务抛异常 |
| **NESTED** | `NESTED` | **外层事务的嵌套事务**（savepoint 机制） |

### 场景化对比 —— REQUIRED vs REQUIRES_NEW vs NESTED

假设 ServiceA.methodA() 有事务，里面调用 ServiceB.methodB()：

```java
@Service
public class ServiceA {
    @Transactional(propagation = REQUIRED)  // 外层事务 Tx1
    public void methodA() {
        dao.saveA();
        serviceB.methodB();   // 决定用哪种传播行为
        dao.saveA2();
        // methodA 最后 throw RuntimeException
    }
}
```

**三种传播行为的结果对比：**

| 场景 | 传播行为 | methodB 有无新事务 | methodB 内部异常时 methodB 的 DB 操作 | methodA 异常时 methodB 的 DB 操作 |
|:---|:---|:---:|:---|:---|
| 1 | REQUIRED | ❌（加入 Tx1） | **都回滚**（和 methodA 共享事务） | 回滚 |
| 2 | REQUIRES_NEW | ✅（新事务 Tx2，挂起 Tx1） | **只回滚自己 Tx2**（Tx1 不感知） | **不回滚**（Tx2 已独立提交）✅ |
| 3 | NESTED | 部分：savepoint，不新建物理事务 | **只回滚到 savepoint**（Tx1 本身还在） | **跟着外层回滚**（savepoint 是同一事务） |

### 生产实战选型

| 业务场景 | 推荐传播行为 | 理由 |
|:---|:---|:---|
| **普通 CRUD Service 方法**（默认） | **REQUIRED** | 被上层事务包进去，不单独开事务；自己单独调用时自动开一个 |
| **写日志、审计、埋点**（失败不能影响主流程） | **REQUIRES_NEW** | 即使主流程炸了，日志也要提交进去 |
| **批量发通知、发消息**（可以在事务外） | **NOT_SUPPORTED** | 不让长事务把数据库连接占住 |
| **校验配置是否存在**（只读） | **SUPPORTS** | 有事务就读一致快照，没事务也不额外开 |
| **Dao 层更新，必须要有外层事务调用** | **MANDATORY** | 防止有人在非事务里调用导致脏数据 |
| **子流程：主流程成功了才提交，子流程自己失败回滚不影响主流程** | **NESTED** | 典型：主订单 + 子订单；子订单校验失败不影响主订单但主订单失败子订单一起回滚 |

> **NESTED 的前提条件**：需要用的是 **JDBC 3.0+ savepoint 支持**的 DataSource（HikariCP、Tomcat JDBC Pool 都支持）+ **DataSourceTransactionManager** 作为事务管理器。JTA 分布式事务通常不支持 NESTED。

## 五、@Transactional 失效的 8 大场景（高频中的高频）

这是面试必问 Top 3，背 8 条按套路口述 + 1 条项目真实坑 STAR 结构讲：

### 场景 1：非 public 方法

```java
@Service
public class OrderService {
    @Transactional
    void save(Order o) { ... }  // ❌ 包访问级别！
}
```

**原因**：Spring AOP（CGLIB/JDK 代理）默认只代理 public 方法。protected / package / private 不代理 → 调用直接走到原对象。

> **Spring 版本特殊**：Spring 5.3 加了 `exposeProxy` / CGLIB 有 `protected` 代理支持，但生产代码永远写 **public** 最安全。

### 场景 2：类内部自调用（this.xxx / super.xxx）

代理陷阱：this 调用绕过代理。**90% 的事务失效场景都是这个**。3 种解决办法（注入自己 / AopContext.currentProxy / 拆类）详见 [AOP.md](AOP.md) 代理陷阱章节。

### 场景 3：捕获异常没重新抛出

```java
@Transactional(rollbackFor = Exception.class)
public void save(Order o) {
    try {
        dao.insert(o);
        int a = 1 / 0;
    } catch (Exception e) {
        log.error("出错啦", e);
        // ❌ 吞掉了！Spring 不知道发生了异常 → 居然 commit 成功了！
    }
}
```

**原因**：Spring 事务切面靠 catch RuntimeException 才触发 rollback。你把异常吃了，切面以为方法正常 return 了 → 提交。

**正确写法**：catch 后要么 `throw e;` 要么手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();`

### 场景 4：数据库引擎不支持事务

```java
@Transactional
public void save() { ... }  // 业务代码看似没问题
```

但如果 `create table xxx engine=MyISAM;` —— MyISAM **根本没有事务**。Spring 切面会成功 commit / rollback，但 MySQL 层静默忽略 rollback，数据已经写进去了。

> 现在 MySQL 8.0 默认 InnoDB，不会遇到；但如果接手老库或者迁移过的库先确认存储引擎：`show create table xxx;`

### 场景 5：方法被 final 修饰（只有 CGLIB 场景）

```java
@Transactional
public final void save(Order o) { ... }  // ❌ CGLIB 子类无法覆盖 final 方法
```

JDK 代理不受影响（接口方法不能 final）。但 Spring Boot 默认 CGLIB，final 方法直接忽略代理逻辑。

### 场景 6：多线程 / 异步方法

```java
@Service
public class OrderService {
    @Transactional
    public void save(Order o) {
        new Thread(() -> dao.insertDetail(o)).start();  // 新线程不在事务 ThreadLocal 里
    }

    @Async
    @Transactional
    public void saveAsync(Order o) {
        // @Async 在另一个线程池线程执行，事务切面和异步切面顺序也会出错
    }
}
```

**原因**：事务 Connection 绑定的是 ThreadLocal。新线程 → 没有绑定 Connection → 要么每句 SQL 单独开连接/单独事务，要么拿不到 Connection NPE。

### 场景 7：Bean 没有被 Spring 管理

```java
// 没有 @Service / 没有 @Component 注解，或者是 new 出来的
public class OrderService {
    @Transactional public void save() {}
}

// 外部调用
OrderService service = new OrderService();  // 自己 new 的，Spring 根本不知道这个类
service.save();  // ❌ 不可能有代理
```

### 场景 8：rollbackFor 配置错误（默认只回 RuntimeException）

```java
@Transactional // 默认不回滚 SQLException！
public void save() throws SQLException {
    jdbcTemplate.update("INSERT ...");
    throw new SQLException("出错");  // ❌ 不回滚！
}
```

生产最佳实践：`@Transactional(rollbackFor = Exception.class)` 当模板用。

## 六、易错点（事务相关）

| 易错点 | 说明 |
|:---|:---|
| **REQUIRES_NEW 连接泄漏风险** | 挂起外层事务时外层的 Connection 被暂存在 stack，内层拿新 Connection。如果 ServiceA 嵌套 REQUIRES_NEW 调用 5 层，瞬间占用 5 个 Connection。HikariCP 连接池默认只有 10 个，并发 3 个请求就打爆了。注意层级不要太深（完整事故复盘见场景题 Q8） |
| **@Transactional 方法内调外部 RPC** | 事务持有 Connection 期间阻塞等 HTTP 响应 → 连接池被占。事务内不要做远程调用。正确做法：先 RPC 拿数据，再在事务里只做纯 DB 操作（治理心法见场景题 Q5） |
| **只读事务 readOnly=true 的作用** | Hibernate 会刷 FlushMode.MANUAL，JdbcTemplate 会给 Connection 设置 readonly 标记（MySQL 路由到从库读）。性能没传说中那么大，但语义清晰——所有只做 select 的方法都加 readOnly |
| **NESTED 外层没事务** | NESTED 要求外层必须有事务，否则等价于 REQUIRED（新建事务）。和 REQUIRES_NEW 语义完全不同 |

## 二、逐题详解

### Q1：@Transactional 加在类 / 方法 / 接口上的行为差异？多方法调用时事务边界怎么走？

**注解位置行为表**：

| 位置 | 行为 | 生产建议 |
|:---|:---|:---|
| **类上** | 该类所有 public 方法都加事务 | 小工具类可用；业务类慎用（只读方法被无意义开事务） |
| **方法上** | 仅该方法（最细粒度） | **生产首选** |
| **接口上** | JDK 代理生效，CGLIB 不一定生效（版本相关） | 一律不推荐 |
| private / protected | 不生效（代理默认只代理 public） | 详见上文失效场景 1 |

**多方法调用的事务边界**（默认 REQUIRED 加入外层，详见上文「四、7 种事务传播行为」）：

```java
// 同类自调用 —— 走 this 绕过代理，@Transactional 不生效
@Service
public class OrderService {
    @Transactional public void create() { this.detail(); }   // this 走原对象，detail 的 @Transactional 不生效
    @Transactional public void detail() { ... }
}
// Controller 调 orderService.create():
//   ├─ 进入 create 代理：开事务 T1
//   ├─ create 内部 this.detail()：不走代理，detail 在 T1 里跑（detail 的 @Transactional 等同没加）
//   └─ create 返回：T1 提交
```

```java
// 跨类调用 —— 走代理能感知外层
@Service public class A {
    @Autowired private B b;
    @Transactional public void a() { b.b(); }   // 开 T1
}
@Service public class B {
    @Transactional public void b() { ... }      // 默认 REQUIRED：加入 T1，不新开
}
```

> **口诀**：跨类调用走代理能感知外层 → 默认 REQUIRED 加入；同类自调用走 this → 代理失效，连"加入"都没机会谈。自调用失效的 3 种解决办法（注入自己 / AopContext.currentProxy / 拆类）见 [AOP.md](AOP.md) 代理陷阱章节。

### Q2：@Transactional 注解的 7 个属性在生产怎么配？只用默认值会踩什么坑？

```java
@Transactional(
    propagation = Propagation.REQUIRED,                  // 传播行为（详见上文「四、7 种事务传播行为」）
    isolation   = Isolation.DEFAULT,                     // 隔离级别（继承 DB 默认）
    timeout     = -1,                                     // 超时秒数（-1 不超时）
    readOnly    = false,                                  // 只读标记
    rollbackFor       = {},                              // 触发回滚的异常类型
    noRollbackFor     = {},                              // 不触发回滚的异常类型
    value / transactionManager = "transactionManager"     // 用哪个事务管理器
)
```

**生产配置模板与坑表**：

| 属性 | 默认值 | 坑 | 生产模板 |
|:---|:---|:---|:---|
| `propagation` | REQUIRED | 90% 场景就够；日志/审计也用 REQUIRED 会让主流程失败时日志一起回滚 | 业务方法 REQUIRED；日志审计 REQUIRES_NEW |
| `isolation` | DEFAULT（继承 DB） | MySQL 默认 RR，高并发热点行更新场景下 RR 行锁竞争激烈 | 通常 DEFAULT；秒杀等场景显式 READ_COMMITTED 减锁竞争 |
| `timeout` | -1（不超时） | 没超时保护，长事务一直占着连接 | 查询方法设 3~5s；写方法设 30s |
| `readOnly` | false | 不打标优化器走只读路径没机会 | **只 select 的方法必加 `readOnly=true`**（语义清晰 + Hint） |
| `rollbackFor` | RuntimeException + Error | **SQL 异常不回滚**——生产事故第一坑 | **永远写 `rollbackFor = Exception.class`** |
| `noRollbackFor` | 空 | 某些"友好异常"不想让整单事务回滚 | 极少用；如 `noRollbackFor = BizSkipException.class` |
| `value` | "transactionManager" | 多数据源忘切，写了主库事务管理器但 SQL 走从库 → 失效（见 Q4） | 多数据源每个 @Transactional 显式指定 value |

**最容易翻车的两条**：

1. **rollbackFor 默认值**——Spring 默认只回 RuntimeException，所有受检异常（IOException / SQLException）都不回滚。生产必须显式 `rollbackFor = Exception.class`。详见上文失效场景 8。
2. **readOnly 不写**——纯查询方法不开 readOnly，MySQL 不会路由到从库、Hibernate 也不会跳 FlushMode；写 `readOnly=true` 是免费的优化。

### Q3：编程式事务 vs 声明式事务，什么场景选哪个？

| 维度 | 声明式 @Transactional | 编程式 TransactionTemplate |
|:---|:---|:---|
| **灵活度** | 整个方法一个事务边界 | 可在方法内部任意粒度开 / 提交 |
| **侵入性** | 0（注解） | 中（需写 lambda） |
| **性能** | 走 AOP 代理切面 | 直调事务管理器，无代理开销 |
| **局部回滚** | 不支持（事务整体回滚） | 配合 savepoint 可局部回滚 |
| **适用场景** | 90% CRUD、Service 标准方法 | 复杂流程：批量任务、循环内独立事务、嵌套子事务 |

**编程式两种写法对比**：

```java
// 1) TransactionTemplate（推荐，lambda 风格）
@Autowired private TransactionTemplate txTemplate;

public void batchInsert(List<Order> orders) {
    for (List<Order> chunk : Lists.partition(orders, 500)) {
        txTemplate.execute(status -> {       // 每个分片独立事务
            chunk.forEach(dao::insert);
            return null;
        });
    }
}

// 2) PlatformTransactionManager（更底层，更少用）
@Autowired private PlatformTransactionManager txManager;

public void manual() {
    TransactionStatus status = txManager.getTransaction(new DefaultTransactionDefinition());
    try {
        dao.insert(...);
        txManager.commit(status);
    } catch (Exception e) {
        txManager.rollback(status);
    }
}
```

**选型决策树**：

```
方法整体一个事务边界？
├─ 是 → @Transactional（默认选这个）
└─ 否 → 方法内需要多次独立事务 / 局部回滚 / 批量分片
        └─ 用 TransactionTemplate
```

> 编程式事务的两个典型场景：① 批量导入 100 万行分批 500 一事务（避免长事务）；② 主流程异常后还要写审计表（用 REQUIRES_NEW 在主流程 catch 后单独开事务）。

### Q4：多数据源场景 @Transactional 怎么走？为什么"明明配了主库事务管理器，写从库不回滚"？

**经典坑场景**：

```java
@Configuration
public class DataSourceConfig {
    @Bean(name = "masterTxManager")
    public DataSourceTransactionManager master(@Qualifier("masterDataSource") DataSource ds) { ... }

    @Bean(name = "slaveTxManager")
    public DataSourceTransactionManager slave(@Qualifier("slaveDataSource") DataSource ds) { ... }
}

@Service
public class OrderService {
    @Transactional                            // ❌ 没指定 value，默认按主事务管理器
    @DS("slave")                              // 但 SQL 被自定义 AOP 路由到从库 DataSource
    public void query() {
        // 事务管理器从 masterTxManager 的 DataSource 拿 Connection → 走主库
        // 但 SQL 被 @DS AOP 切到了从库 DataSource → 不在事务里！
        // 现象：异常不回滚，且事务管理器误以为事务已开（实际是另一个 DS 的连接）
    }
}
```

**根因**：Spring 事务 = 事务管理器 + DataSource。事务管理器只管它自己 DataSource 的 Connection；如果业务 SQL 走另一个 DataSource，事务对它无能为力。原理见上文「二、Connection 绑定到线程 —— ThreadLocal 机制」。

**解决对照表**：

| 方案 | 做法 | 局限 |
|:---|:---|:---|
| 显式指定事务管理器 | `@Transactional(value = "slaveTxManager")` | 必须每个方法手写，容易漏 |
| 自定义切面自动选 | 拦截 @DS 注解，自动给 @Transactional 设置对应 txManager | 实现复杂 |
| 多数据源中间件 | dynamic-datasource-spring-boot-starter 等开箱即用 | 引入依赖 |
| **跨库事务** | 单机 @Transactional **无法保证**，必须 Seata 等 | 见 Q9 |

> **生产铁律**：跨 DataSource 的操作，本地 @Transactional **保证不了**原子性。要么单库内闭环，要么上分布式事务。

### Q5：线上一段 SQL 在事务里执行太久，把连接池占爆，怎么排查与治理？

**排查骨架（三步）**：

```text
① 现象定性：HikariCP 报 "Connection is not available, request timed out after 30000ms"
② 看谁占着连接：jstack 抓线程 → 找 WAITING 在 HikariPool.getConnection 的业务线程
   → 看它的栈顶在干什么（DB 等待？外部 RPC？文件 I/O？）
③ 找源头：日志按 traceId 串起来 → 看哪个 @Transactional 方法耗时最长
```

**长事务 4 大典型元凶**：

| 元凶 | 例子 | 修复 |
|:---|:---|:---|
| **事务内做远程调用** | `@Transactional` 方法内调 RPC、HTTP、发邮件 | RPC 移出事务外，只把 DB 操作留在事务里 |
| **大批量循环** | `for (i..10000) dao.insert()` | 改批量 insert / 分片编程式事务（Q3） |
| **等用户输入 / 文件上传** | `@Transactional` 方法读 MultipartFile 流 | 移到事务外读完，再传字节进事务 |
| **索引差导致 SQL 慢** | 事务里一句 update 扫表 5s | 加索引治本（见 [mysql/SQL优化的实际场景](../mysql/11.%20SQL优化的实际场景.md)） |

**HikariCP 配置层面的兜底**：

```yaml
spring:
  datasource:
    hikari:
      connection-timeout: 3000      # 拿不到连接 3s 就失败（默认 30s 太长）
      max-lifetime: 600000          # 连接最长生命周期 10min，防止 DB 端 idle 断开
      maximum-pool-size: 20         # 别一味调大，连接数 > CPU 核数 × 2 + 磁盘数 后反而降速
```

> **治理心法**：@Transactional 方法体里只放 DB 操作；所有 RPC、文件、睡眠、外部资源访问一律移出去。事务越短越好——连接池是公共资源。

### Q6：事务方法里写了 Redis，事务回滚但缓存脏写怎么办？

**问题场景**：

```java
@Transactional(rollbackFor = Exception.class)
public void pay(Order order) {
    dao.updateStatus(order);                       // DB 写
    redis.set("order:" + order.getId(), order);   // Redis 写
    dao.deductStock(order);                        // DB 写
    // 异常 → DB 回滚
    // ❌ 但 Redis 已经写了，缓存与 DB 不一致！
}
```

**4 种解法对比**：

| 方案 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| 双写不删，依赖 TTL | Redis 写时带过期时间 | 简单 | TTL 内一直脏，业务可感知 |
| 事务提交后再写缓存 | `@TransactionalEventListener` 监听提交事件 | 100% 一致 | 多 1 次同步调用（详见 Q7） |
| 延迟双删 | 提交后 + sleep 500ms 再删一次缓存 | 应对并发 | 加复杂度，sleep 不优雅 |
| **可靠消息最终一致** | 事务内只发 MQ 消息，消费者异步刷缓存 | 解耦 + 性能好 | 引入 MQ，复杂度上升 |

**最常用：事务事件钩子（见 Q7 详解）**

```java
@Component
public class OrderCacheRefresher {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onPay(PayEvent event) {
        redis.set("order:" + event.getOrderId(), event.getOrder());
    }
}
```

> **原则**：DB 是事务边界；Redis / ES 等其他存储都不在事务边界内 → 必须用"事务提交后置钩子"或"可靠消息"做最终一致。

### Q7：@TransactionalEventListener 比 @EventListener 强在哪？事务提交后置钩子解决什么场景？

**两者执行时机对比**：

```text
@Transactional 方法体执行
    ├─ 1. 业务代码
    ├─ 2. applicationEventPublisher.publishEvent(event)   ← 事件发布
    │      ├─ @EventListener         ← 立即同步执行（事务还没提交！）
    │      └─ @TransactionalEventListener(phase = BEFORE_COMMIT)  ← 提交前同步
    ├─ 3. 事务提交 commit()
    └─ 4. @TransactionalEventListener(phase = AFTER_COMMIT)  ← 提交后异步/同步执行 ✅
```

**4 个 Phase 速查**：

| Phase | 时机 | 典型用途 |
|:---|:---|:---|
| BEFORE_COMMIT | 事务提交前（同步） | 同事务内做额外 DB 校验 |
| AFTER_COMMIT | 提交成功后（默认） | **缓存刷新、MQ 发送、外部通知** ← 最常用 |
| AFTER_ROLLBACK | 回滚后 | 回滚补偿：发告警、清缓存 |
| AFTER_COMPLETION | 提交或回滚后 | 通用清理 |

**生产场景**：

| 场景 | 解法 |
|:---|:---|
| 事务提交后刷 Redis（见 Q6） | AFTER_COMMIT 同步刷缓存 |
| 事务提交后发 MQ | AFTER_COMMIT 发可靠消息（提交了再发，避免回滚但消息已发） |
| 事务回滚后清缓存 | AFTER_ROLLBACK 删 Redis key |
| 事务回滚后告警 | AFTER_ROLLBACK 发钉钉/邮件 |

> **核心收益**：把"事务外的副作用"挪到事务提交后，避免事务回滚后还要补救（如发出去的 MQ 撤不回来）。这是 Spring 4.2+ 给的事务边界友好工具，比手写 `TransactionSynchronizationManager.registerSynchronization` 优雅得多。

### Q8：库存扣减的批量接口：REQUIRES_NEW 嵌套 5 层把 HikariCP 打爆，怎么救？

**事故复盘（STAR 结构）**：

- **Situation**：秒杀批量扣减库存接口，Controller → Service → 库存子服务，每层都 `@Transactional(REQUIRES_NEW)`，业务还嵌套 5 层 Service。
- **Task**：单机 50 并发就把 HikariCP 10 连接打爆，前端大量超时。
- **Action**：
  1. jstack 抓 50 个线程都在 `getConnection` WAITING
  2. 沿调用链看：5 层 REQUIRES_NEW = 单请求占 5 个连接
  3. 50 并发 × 5 = 250 个连接需求 vs 池里 10 个 → 必爆
- **Result**：去掉中间层 REQUIRES_NEW，只在最外层保留事务；内层改默认 REQUIRED 加入外层。50 并发只用 50 个连接，过 HikariCP 20 配置毫无压力。

**REQUIRES_NEW 的代价表**：

| 维度 | REQUIRED（默认） | REQUIRES_NEW |
|:---|:---|:---|
| 连接占用 | 加入外层，复用外层 Connection | **新拿一个 Connection**，外层 Connection **挂起暂存** |
| 嵌套 N 层占连接数 | 1 | **N** |
| 适合场景 | 90% CRUD | 日志、审计、必须独立提交的子操作 |

> **铁律**：REQUIRES_NEW 不是"事务更安全"，而是"我要独立提交/回滚"。N 层 REQUIRES_NEW = N 个连接，慎用。原理见上文「六、易错点」第 1 条「REQUIRES_NEW 连接泄漏风险」。

### Q9：本地 @Transactional 解决不了的边界在哪？Seata AT/TCC/可靠消息怎么选？

**本地事务的边界**：

```text
单库（同 JVM 同 DataSource）：  @Transactional ✅ 100% 保证
跨库（同 JVM 多 DataSource）： 本地 @Transactional ❌ 无法保证原子
跨服务（不同 JVM）：           本地 @Transactional ❌ 完全无能为力
跨消息中间件：                 本地 @Transactional ❌（DB 提交 + MQ 发送无法原子）
```

**分布式事务 4 种选型对比**：

| 方案 | 一致性 | 侵入性 | 性能 | 典型场景 |
|:---|:---|:---|:---|:---|
| **Seata AT** | 强（最终） | 低（注解） | 中 | 单体应用跨库（undo_log 自动补偿） |
| **Seata TCC** | 强（最终） | 高（写 Try/Confirm/Cancel） | 高 | 资金类、需要业务级回滚 |
| **本地消息表 + MQ** | 最终一致 | 中（消息表 + 重试） | 高 | 跨服务异步通知、可靠消息 |
| **最大努力通知** | 弱 | 低 | 高 | 对账、短信通知（容忍短期不一致） |

**选型决策树**：

```text
跨库（同 JVM）？
├─ 是 → Seata AT（无侵入，自动 undo_log）
└─ 否 → 跨服务
        ├─ 资金 / 库存等关键业务 → Seata TCC（业务级回滚）
        ├─ 异步通知 / 跨服务消息 → 本地消息表 + MQ 最终一致
        └─ 容忍短期不一致       → 最大努力通知
```

> Seata AT/TCC 模式细节见 [SpringCloud微服务.md](SpringCloud微服务.md)；本地消息表实现见 [MySQL/存储引擎与架构.md](../mysql/3.%20存储引擎与架构.md) 的两阶段提交思路。

### Q10：Spring 6 WebFlux 里 @Transactional 为什么不生效？TransactionalOperator 怎么写？

**根因**：Spring 事务基于 ThreadLocal 绑定 Connection（见上文「二、Connection 绑定到线程 —— ThreadLocal 机制」）；WebFlux 是响应式流（Reactor），跨线程切换，ThreadLocal 失效。

**@Transactional 在响应式栈的失效场景**：

```java
@Service
public class OrderService {
    @Transactional   // ❌ 在 WebFlux 项目里完全不生效！
    public Mono<Void> pay(Order o) {
        return dao.save(o).then(redisSet(o));   // 多次切换线程，事务 ThreadLocal 全程摸不到
    }
}
```

**响应式事务：TransactionalOperator**：

```java
@Service
public class OrderService {
    @Autowired private TransactionalOperator txOperator;
    @Autowired private R2dbcRepository dao;

    public Mono<Void> pay(Order o) {
        return Mono.from(dao.save(o))
            .then(redisSet(o))
            .as(txOperator::transactional)   // ← 把整个 Mono 包装成事务
            .doOnError(e -> log.error("pay failed", e));
    }
}

// 或者类级别注解（Spring 6+）
@Transactional
@Service
public class OrderService {
    @Transactional
    public Mono<Void> pay(Order o) {   // 响应式栈下的 @Transactional 等价于 TransactionalOperator
        return dao.save(o).then(redisSet(o));
    }
}
```

**两者的本质区别**：

| 维度 | @Transactional（传统） | TransactionalOperator（响应式） |
|:---|:---|:---|
| 绑定方式 | ThreadLocal | Reactor Context（流上下文） |
| 线程模型 | 同步，单线程 | 异步，多线程切换 |
| 数据访问 | JDBC（Connection） | R2DBC（ConnectionFactory） |
| 事务管理器 | DataSourceTransactionManager | R2dbcTransactionManager |
| 适合栈 | Spring MVC + JDBC | Spring WebFlux + R2DBC |

> **迁移要点**：传统同步栈 → @Transactional；响应式栈 → TransactionalOperator 或 Spring 6 的响应式 @Transactional（但底层走 R2dbcTransactionManager，不再走 ThreadLocal）。

### Q11：分布式锁 + @Transactional 混用为什么会导致超卖？锁包事务还是事务包锁？

这是 Spring 事务里**最经典也最隐蔽的实战 bug**——根因是「锁释放早于事务提交」。

**错误写法（事务包锁）**：

```java
@Service
public class OrderService {
    @Autowired private RedissonClient redisson;

    @Transactional(rollbackFor = Exception.class)   // 事务边界
    public void deduct(Long skuId, int qty) {
        RLock lock = redisson.getLock("stock:" + skuId);
        try {
            lock.lock();                       // 1. 加锁
            int stock = dao.getStock(skuId);   // 2. 查库存 = 100
            if (stock < qty) throw new BizException("库存不足");
            dao.deduct(skuId, qty);            // 3. 扣减到 50（未提交）
        } finally {
            lock.unlock();                     // 4. ❌ 解锁！但事务还没 commit
        }
        // 5. 方法返回 → AOP 切面才 commit
    }
}
```

**超卖时序图**：

```text
T1：lock → 查 100 → 扣 50(未提交) → unlock → [commit 窗口期]
                                                  ↑ T2 在此期间拿到锁
T2：              lock → 查库存 ❌读到 100(T1 未提交) → 扣 50 → 超卖！
```

**根因**：`@Transactional` 的 commit 发生在**方法返回后**（AOP 切面后置），而 `lock.unlock()` 在 **finally 块里、方法返回前**。实际顺序变成 `lock → 业务 → unlock → commit`，unlock 与 commit 之间出现「锁已释放但事务未提交」的窗口期，其他线程在此期间拿到锁但读不到未提交数据。

**4 种解法对比**：

| 方案 | 做法 | 评价 |
|:---|:---|:---|
| **锁包事务（外置锁）** | Controller / 非 @Transactional 方法里 lock → 调事务方法 → unlock | ✅ 最推荐 |
| AOP 注解 + @Order | 自定义 `@DistributedLock` 切面，`@Order` 比事务切面更外层 | 注解优雅，要懂 AOP 顺序（见 [AOP.md](AOP.md) 多切面执行顺序） |
| 编程式事务 | 锁内用 TransactionTemplate 手动开事务，commit 后再 unlock | 灵活但侵入 |
| 延迟双释放 | unlock 前 sleep 500ms | 治标不治本，不优雅 |

**正确写法 1：锁包事务（最推荐）**

```java
@RestController
public class OrderController {
    @Autowired private RedissonClient redisson;
    @Autowired private OrderService orderService;

    @PostMapping("/order")
    public R order(Long skuId, int qty) {
        RLock lock = redisson.getLock("stock:" + skuId);
        try {
            lock.lock();                        // 1. 加锁（事务外）
            orderService.deduct(skuId, qty);    // 2. 调事务方法 → 内部 commit
        } finally {
            lock.unlock();                      // 3. 解锁（commit 后）
        }
        return R.ok();
    }
}
// 顺序：lock → 进入代理 → 开事务 → 业务 → commit → unlock ✅
```

**正确写法 2：AOP 注解化（团队复用）**

```java
@Aspect
@Component
@Order(0)   // ⚠️ 必须 < @Transactional 的 Ordered.LOWEST_PRECEDENCE
public class DistributedLockAspect {
    @Around("@annotation(lock)")
    public Object around(ProceedingJoinPoint pjp, DistributedLock lock) throws Throwable {
        RLock rLock = redisson.getLock(lock.key());
        try {
            if (!rLock.tryLock(lock.waitTime(), lock.leaseTime(), TimeUnit.SECONDS)) {
                throw new BizException("操作过于频繁");
            }
            return pjp.proceed();   // 内层才是 @Transactional 切面
        } finally {
            rLock.unlock();
        }
    }
    // 切面顺序：@Order(0) 锁外层 → @Transactional 内层
    //   → lock → 开事务 → 业务 → commit → unlock ✅
}

@Service
public class OrderService {
    @DistributedLock(key = "'stock:' + #skuId")
    @Transactional(rollbackFor = Exception.class)
    public void deduct(Long skuId, int qty) { ... }
}
```

> **铁律与延伸**：
> 1. **锁包事务，不要事务包锁**——同样适用于本地 `synchronized + @Transactional`，原理相同（synchronized 释放在 monitor exit，事务 commit 在 AOP 后置）。
> 2. **验证方法**：开 2 个线程并发调，看是否超卖/重复。
> 3. **生产高频踩坑场景**：秒杀扣库存、订单防重复提交、Token 幂等校验——只要"锁 + 写 DB"组合都可能踩。

## 三、一句话总结

Spring 事务 = **「事务管理器 + ThreadLocal 绑定 Connection + 7 种传播行为」**。生产实战 4 件事必背：**① 注解属性生产配置**（`rollbackFor = Exception.class` 必写、只读查询必加 `readOnly=true`、`timeout` 兜底）；**② 事务边界 + 连接池思维**（@Transactional 方法只做 DB 操作、REQUIRES_NEW 慎用因为占连接、多 DataSource 跨库本地事务保证不了）；**③ 事务外的副作用用提交后钩子**（`@TransactionalEventListener AFTER_COMMIT`）替代事务内同步刷缓存 / 发 MQ；**④ 锁包事务而非事务包锁**（分布式锁 / synchronized 必须放在 @Transactional 外层，否则 unlock 早于 commit 出现超卖窗口期）。本地事务的边界：跨库跨服务用 Seata 或本地消息表；响应式栈用 TransactionalOperator 替代 @Transactional（ThreadLocal 失效）。
