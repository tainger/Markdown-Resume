# Spring Boot 自动配置与启动流程

Spring Boot 的「开箱即用」本质是两个魔法：**自动装配（Auto-Configuration）** 替你注册一堆你大概率需要的 Bean，**约定大于配置（Convention over Configuration）** 按默认值起服务。

---

## 一、@SpringBootApplication 拆成三件套

```java
@SpringBootApplication
public class App { public static void main(String[] args) { SpringApplication.run(App.class, args); } }
```

等价于：

```java
@Configuration                    // 1. 表明这是一个配置类（等价于 beans XML 标签）
@EnableAutoConfiguration          // 2. ★ 开启自动装配（核心魔法所在）
@ComponentScan                    // 3. 扫描当前包及子包下 @Component/@Service 等注解（等价 context:component-scan 标签）
public class App { ... }
```

不是三个「加起来」这么简单，每层都有深意：

### 1.1 @Configuration — 配置类（Full Lite 模式）

Spring 5.2 后 `@Configuration` 默认带 `proxyBeanMethods = true`，又叫** Full 模式**：

```java
@Configuration(proxyBeanMethods = true)  // Full 模式（默认）
public class MyConfig {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); }  // ✅ a() 不会 new 两次，而是从容器拿 a 单例
}
```

`proxyBeanMethods = false`（**Lite 模式**，SpringBoot 2.2+ 官方推荐 starter 用这个）：
- 不生成 CGLIB 子类代理，启动更快
- 方法间直接调用会**真的 new 两次**，不能保证单例

> **生产建议**：自己业务项目的配置类用默认 Full（省得出坑）；写公共 starter 给别人用的配置类写 `@Configuration(proxyBeanMethods = false)`，加快别人的启动速度。

### 1.2 @ComponentScan — 扫包范围

默认扫描的是 `@SpringBootApplication` 所在类的**包及所有子包**。这就是为什么启动类必须放在**顶层包**的原因。

```
com.example.project
├── ProjectApplication.java   // ← @SpringBootApplication 在这里 → 扫 com.example.project 下所有
├── controller/               // ✅ 在子包，扫得到
├── service/                  // ✅ 扫得到
└── dao/                      // ✅ 扫得到

com.example.other             // ❌ 兄弟包，不在扫描范围内！
└── SomeService.java          //     就算加了 @Service 也不生效
```

如果非要扫启动类外的包：

```java
@SpringBootApplication(scanBasePackages = {"com.example.project", "com.example.other"})
// 或者
@ComponentScans({
  @ComponentScan("com.example.project"),
  @ComponentScan("com.example.other")
})
```

### 1.3 @EnableAutoConfiguration — ★ 自动装配的入口

```java
@Import(AutoConfigurationImportSelector.class)  // ★ 这是真正自动装配的引擎
public @interface EnableAutoConfiguration { ... }
```

`@Import` 可以直接把类导入为 Spring Bean。`AutoConfigurationImportSelector` 实现了 `DeferredImportSelector` 接口，**它会扫描 ClassPath 下所有 META-INF 里写好的自动配置类清单，批量 Import 进容器**。

## 二、自动配置的加载机制（版本差异是面试陷阱）

### 2.1 两个版本的不同文件路径

| | Spring Boot 2.7 及以前 | **Spring Boot 3.0+（当前主流）** |
|:---|:---|:---|
| **自动配置清单文件路径** | `META-INF/spring.factories` | `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` |
| **格式** | `properties` 格式，一行键值：`org.springframework.boot.autoconfigure.EnableAutoConfiguration=\` 换行写 `com.example.MyAutoConfig1,...`（多值逗号分隔 + 反斜杠换行续行） | 纯文本，一行一个全限定类名：`com.example.MyAutoConfig1` 换行 `com.example.MyAutoConfig2` |
| **3.0 还读 spring.factories 吗？** | 读 | 只读部分（如 `ApplicationContextInitializer`、`ApplicationListener`）；**自动配置类不再读 spring.factories 的 EnableAutoConfiguration 段** |
| **自定义 starter 怎么办？** | 写 `META-INF/spring.factories` | 写 `AutoConfiguration.imports`，或在 `@AutoConfiguration` 类上加 `@AutoConfigurationPackage` |

> **P7 级细节**：SpringBoot 3.0 把自动配置从 spring.factories 拆出来单独放，是为了更快的启动——spring.factories 里还有很多其他类型的 key，以前每次加载都要读全文件再过滤；现在 AutoConfiguration 有了独立文件可以 mmap 直接按行读。

### 2.2 加载流程简化图

```
SpringApplication.run()
  │
  ▼
ApplicationContext 创建 → refresh()
  │
  ▼
@EnableAutoConfiguration 解析 → 触发 AutoConfigurationImportSelector
  │
  ▼
ImportCandidates.load(AutoConfiguration.class, classLoader):
  │  读取 META-INF/spring/...AutoConfiguration.imports（3.0+）
  │  + spring.factories 中的其他扩展
  ▼
  得到 100~200 个自动配置类全限定名列表（如 DataSourceAutoConfiguration 等）
  │
  ▼
条件筛选 @ConditionalOnXxx（本节后面详细讲）：
  ├─ @ConditionalOnClass：有没有对应类？（如 HikariCP 在 classpath 才启 DataSource）
  ├─ @ConditionalOnMissingBean：容器里有没有同名 Bean？（你自己注册了就不覆盖）
  ├─ @ConditionalOnProperty：`spring.datasource.enabled=true`？
  └─ 其他一堆条件
  │
  ▼
最终通过条件的 20~50 个自动配置类真正被 @Import 进容器
  │
  ▼
每个自动配置类的 @Bean 方法按条件注册到 BeanFactory
```

### 2.3 条件注解大全（高频）

| 条件注解 | 触发条件 | 典型应用 |
|:---|:---|:---|
| `@ConditionalOnClass` | classpath 有这个类 | HikariCP 存在才注册 HikariDataSource；Mybatis 存在才注册 SqlSessionFactory |
| `@ConditionalOnMissingClass` | classpath **没有**这个类 | 没 HikariCP 时试试 Tomcat JDBC Pool |
| `@ConditionalOnBean` | 容器里有这个 Bean | 已有 TransactionManager 才注册事务注解驱动 |
| `@ConditionalOnMissingBean` | 容器里**没有**这个 Bean（用户自己配了就用用户的） | **90% starter 自动配置用这个**——"用户优先"原则 |
| `@ConditionalOnProperty` | `application.yml` 里某属性 = 特定值 | `mybatis.mapper-locations` 才生效 |
| `@ConditionalOnWebApplication` | 当前是 Web 应用（Servlet / Reactive） | DispatcherServlet 自动配置、WebMvc 自动配置 |
| `@ConditionalOnNotWebApplication` | 非 Web 应用 | 纯批处理、Job 类的自动配置 |
| `@ConditionalOnExpression` | SpEL 表达式为 true | 复杂条件组合，少用 |
| `@ConditionalOnJava` | JDK 版本满足 | 一些用到 JDK 17 新特性的自动配置 |
| `@ConditionalOnSingleCandidate` | 容器里这个类型的 Bean 只有 1 个 | 避免多数据源时歧义 |

> 核心设计思想：**starter 是默认兜底方案，用户永远可以覆盖**。`@ConditionalOnMissingBean` 是这个思想的关键实现——用户自定义 Bean 优先级永远比自动配置高。

## 三、自定义 Starter 的标准结构（P7 级加分项）

面试官经常问「写过自定义 starter 吗？怎么做的？」。回答时按**结构 + 两个模块 + 3 步实现**讲：

### 3.1 为什么要分两个 Maven 模块

```
myproject-common-spring-boot-starter/    ← 用户依赖这个就行，空 jar，只有 pom.xml 依赖
└── pom.xml → 依赖 myproject-common-spring-boot-autoconfigure

myproject-common-spring-boot-autoconfigure/  ← 真正写自动配置逻辑的模块
├── src/main/java
│   └── com.example.common.autoconfigure
│       ├── MyCommonAutoConfiguration.java   // @AutoConfiguration + @Conditional + @Bean
│       ├── MyCommonProperties.java          // @ConfigurationProperties 绑定配置文件
│       └── MyCommonService.java             // 自动配置类注册的核心 Service
└── src/main/resources/META-INF/spring/
    └── org.springframework.boot.autoconfigure.AutoConfiguration.imports  // 一行全限定名
```

**为什么分两个模块？**——这是 Spring 官方 starter 的约定：
- `starter`（后缀是 `-spring-boot-starter`）：用户侧 artifact，纯 POM，不含代码。它的职责只有"把 autoconfigure + 其他必要依赖拉进来"。
- `autoconfigure`（前缀是 `-spring-boot-autoconfigure`）：真正的自动配置实现，用户不用直接依赖。
- 分模块的好处：**后续可以独立升级 autoconfigure 版本，不影响 starter 版本**；也方便被其他 starter 依赖。

### 3.2 三步实现一个 starter

假设有一个「接口访问限流」starter：`ratelimit-spring-boot-starter`

**Step 1：Properties 类绑定配置**
```java
@ConfigurationProperties(prefix = "ratelimit")
@ConstructorBinding   // Spring Boot 3.0+ 推荐构造器绑定，@Data 也可以
public class RateLimitProperties {
    public enum Mode { GUAVA, REDIS }
    private boolean enabled = true;
    private Mode mode = Mode.GUAVA;        // 默认本地 Guava 限流
    private long defaultPermitsPerSecond = 100;
    // getter / all args constructor
}
```

**Step 2：AutoConfiguration 类 + 条件装配**
```java
@AutoConfiguration                                    // 新注解，等价 @Configuration
@EnableConfigurationProperties(RateLimitProperties.class)  // 开启配置绑定
@ConditionalOnProperty(prefix = "ratelimit", name = "enabled", havingValue = "true", matchIfMissing = true)
public class RateLimitAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    @ConditionalOnClass(name = "com.google.common.util.concurrent.RateLimiter")  // Guava 才注册
    public RateLimitService guavaRateLimitService(RateLimitProperties p) {
        return new GuavaRateLimitServiceImpl(p.getDefaultPermitsPerSecond());
    }

    @Bean
    @ConditionalOnMissingBean
    @ConditionalOnClass(name = "org.redisson.api.RedissonClient")  // 有 Redisson 才注册
    public RateLimitService redisRateLimitService(RateLimitProperties p) {
        return new RedisRateLimitServiceImpl(p.getDefaultPermitsPerSecond());
    }
}
```

**Step 3：AutoConfiguration.imports 注册文件**

文件：`autoconfigure/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`

内容（一行一个全限定名）：
```
com.example.ratelimit.autoconfigure.RateLimitAutoConfiguration
```

> 最后：starter 模块的 pom.xml 依赖 autoconfigure。用户 pom.xml 里添加 starter 依赖（以 `groupId=com.example, artifactId=ratelimit-spring-boot-starter, version=1.0.0` 为例）即可，不需要任何额外配置就能开功能。

### 3.3 扩展：`spring.factories` 其他 key（非自动配置）

即使 Spring Boot 3.0 把自动配置移出来了，`META-INF/spring.factories` 仍然用于以下扩展点：

```properties
# ApplicationContext 初始化器 —— refresh 前触发（常用：注册自定义 PropertySource）
org.springframework.context.ApplicationContextInitializer=\
  com.example.MyApplicationContextInitializer

# SpringApplication 启动监听器 —— 比 refresh 更早
org.springframework.boot.SpringApplicationRunListener=\
  com.example.MyRunListener

# 失败分析器 —— 启动报错时输出更友好的错误提示（例如端口被占用，输出 "try server.port=xxx"）
org.springframework.boot.diagnostics.FailureAnalyzer=\
  com.example.MyFailureAnalyzer

# 环境后处理器 —— 读取自定义配置源（比如从 Apollo / Nacos 拉配置放 Environment 里）
org.springframework.boot.env.EnvironmentPostProcessor=\
  com.example.MyEnvPostProcessor
```

## 四、SpringApplication.run() 完整启动流程

从 `main` 开始到 `Started xxxApplication in 5.2 seconds` 这 5 秒里 Spring Boot 干了什么。按 9 个阶段讲：

```
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 1: SpringApplication 实例化（构造方法）                       │
│  - 推断 Web 类型：Servlet / Reactive / None（看 classpath 有没依赖） │
│  - 加载 META-INF/spring.factories 里的                             │
│    ApplicationContextInitializer、ApplicationListener              │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 2: 启动监听器 starting                                        │
│  - SpringApplicationRunListener.starting() —— 最早的 hook，甚至      │
│    Environment 还没创建。用于：打印 banner 开始、埋点启动耗时        │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 3: 准备 Environment（配置加载阶段）                          │
│  - 创建 Environment（Web 就 StandardServletEnvironment）           │
│  - 加载配置源，优先级从高到低：                                    │
│    命令行 args → SPRING_APPLICATION_JSON → ServletConfig/InitParam │
│    → System.getProperties() → 系统环境变量                         │
│    → random.* → application.yml → application-{profile}.yml       │
│  - @PropertySources → @ConfigurationPropertiesScan                │
│  - 触发 EnvironmentPostProcessor（Nacos/Apollo 在这里注入配置）    │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 4: 打印 Banner（Spring 大字 LOGO）                          │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 5: 创建 ApplicationContext                                  │
│  - Servlet Web → AnnotationConfigServletWebServerApplicationContext │
│  - 内部会实例化 DefaultListableBeanFactory（IOC 核心容器）         │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 6: 准备 Context，执行初始化器                               │
│  - 把 Environment 注入到 Context                                   │
│  - ApplicationContextInitializer.initialize() 跑（用户自定义扩展）│
│  - resourceLoader / 配置注册                                       │
│  - 触发 BeanFactoryPostProcessors：                               │
│     ↳ ConfigurationClassPostProcessor：扫描 @ComponentScan 注册 BD │
│     ↳ AutoConfigurationImportSelector：批量 import 自动配置类      │
│     ★  所有自动配置在这里完成条件判断，真正注册到 BeanFactory        │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 7: refresh Context —— ★ 最核心（IOC 的全部流程在这里）      │
│  AbstractApplicationContext.refresh():
│   1) prepareRefresh() 元数据 + PropertySource 校验
│   2) obtainFreshBeanFactory() 拿 BeanFactory
│   3) prepareBeanFactory() 配置 BeanFactory（ClassLoader/BeanPostProcessors）
│   4) postProcessBeanFactory() 子类扩展
│   5) invokeBeanFactoryPostProcessors() ★ 执行所有 BeanFactoryPostProcessors
│      → ConfigurationClassPostProcessor 扫 @Configuration/@Import
│   6) registerBeanPostProcessors() ★ 注册所有 BeanPostProcessors（AOP 链路）
│   7) initMessageSource() 国际化
│   8) initApplicationEventMulticaster() 事件广播
│   9) onRefresh() ★ ServletWebServerApplicationContext 在这里创建 Tomcat/Jetty
│  10) registerListeners() 注册所有 ApplicationListener
│  11) finishBeanFactoryInitialization() ★ 实例化所有非懒加载 singleton Bean
│      → createBean → 循环依赖 → AOP 代理 → 放入单例池
│  12) finishRefresh()：发布 ContextRefreshedEvent + 启动生命周期处理器
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 8: afterRefresh，启动监听器 started                          │
│  - 调用所有 CommandLineRunner / ApplicationRunner 接口实现         │
│    ★  这是「启动后立即执行一些初始化工作」的标准扩展点：            │
│       缓存预热、连接预热、启动检查、任务调度注册                   │
│  - 打印 Banner "Started App in 5.234 seconds"                     │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 9: 运行态 → 接收请求 → 优雅关闭                              │
│  - 收到 SIGTERM / kill pid → 发布 ContextClosedEvent              │
│    → SmartLifecycle.stop() → DisposableBean.destroy() → close()   │
└─────────────────────────────────────────────────────────────────────┘
```

### P7 必会的扩展点选择场景

面试官问：「**想在启动阶段做 X，应该用什么扩展点？**」——按时间点匹配：

| 想做的事 | 推荐扩展点 | 触发阶段 |
|:---|:---|:---|
| **自定义配置源**（从 Nacos/Apollo/Consul 远程拉配置） | `EnvironmentPostProcessor` + spring.factories 注册 | Phase 3（Environment 创建完、refresh 前） |
| **程序参数 / 配置校验**（启动参数必须有 `--env=prod`，否则 fail-fast） | `ApplicationContextInitializer` | Phase 6（Context 创建完、refresh 前） |
| **启动失败时打印人类可读的错误提示**（如"端口 8080 被占用，建议换 8081"） | `FailureAnalyzer` + spring.factories 注册 | 失败时随时触发 |
| **启动后初始化缓存 / 预热连接 / 启动定时任务** | `ApplicationRunner` / `CommandLineRunner` | Phase 8（refresh 完、Bean 都实例化后） |
| **动态注册自定义 BeanDefinition**（MyBatis Mapper 批量扫包生成） | `BeanDefinitionRegistryPostProcessor`（或 ImportBeanDefinitionRegistrar） | Phase 7 step 5 |
| **Bean 实例化前替换 BeanClass**（如加 Mock） | `InstantiationAwareBeanPostProcessor#postProcessBeforeInstantiation` | Phase 7 step 11 每次实例化前 |
| **Bean 初始化后包代理 / 加增强**（AOP 通用切面） | `BeanPostProcessor#postProcessAfterInitialization` | Phase 7 step 11 每次初始化后 |
| **优雅停机前释放资源**（关闭线程池 / 注销 Nacos 服务） | `SmartLifecycle#stop()` 或 `@PreDestroy` 或 `DisposableBean` | Phase 9 关闭时 |

## 五、易错点

| 易错点 | 说明 |
|:---|:---|
| **以为 Spring Boot 3.0 自动配置还读 spring.factories** | 3.0 自动配置移到 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`；但 spring.factories 仍用在 ApplicationContextInitializer、ApplicationListener 等扩展。面试先问版本再答 |
| **以为 @ComponentScan 只扫 @Component** | `@Service @Repository @Controller @RestController @Configuration @ControllerAdvice` 这些本质都是 @Component 的元注解，都能被扫到 |
| **starter 只一个模块，没分 starter/autoconfigure** | 不遵守官方约定虽然不影响运行，但面试答出来分就有了 |
| **`@ConditionalOnMissingBean` 以为是"有则替换"** | 正好相反：**没有 Bean 才注册**（用户优先级最高）。如果想"有 Bean 才生效"用 `@ConditionalOnBean` |
| **ApplicationRunner 有多个时执行顺序不确定** | 要加 `@Order` 或实现 Ordered 接口，否则依赖加载顺序 |
| **生产打印了 Started 日志但服务其实还没好** | Tomcat 创建在 Phase 7 step 9 onRefresh 里，finishBeanFactoryInitialization（step 11）要实例化所有 Bean。如果在这之前用户请求进来会 404 / 超时。K8s readiness probe 建议加 `/actuator/health/readiness` 等 SpringBoot Actuator 信号 |
| **`proxyBeanMethods = true` 性能损耗无所谓** | 大型项目配置类多 + Bean 之间互相引用多的话，CGLIB 代理成本可观。SpringBoot 3.1+ 有 `spring.main.allow-circular-references=false` 默认关闭，循环依赖现在都是显式报错，不再默认开启 |

## 六、一句话总结

`@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`；**自动装配的引擎是 `AutoConfigurationImportSelector`**，Spring Boot 3.0+ 从 `META-INF/spring/...AutoConfiguration.imports` 加载自动配置清单（2.7 及前在 spring.factories），每个自动配置类靠**条件注解**控制生效，核心原则是「用户 Bean 优先（@ConditionalOnMissingBean）」；自定义 starter 官方约定「starter POM 模块 + autoconfigure 真实实现模块」两模结构，三步写好（Properties → @AutoConfiguration + 条件 Bean → 注册文件）；`SpringApplication.run()` 9 阶段按「实例化 → 监听器 → 环境 → Banner → Context 创建 → 准备 → refresh（IOC） → afterRefresh（Runner） → 运行」流程，每个阶段对应不同的扩展点选择场景。
