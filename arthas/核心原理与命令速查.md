# Arthas 核心原理与命令速查

面试问 Arthas，**用法决定会不会用，原理决定能不能聊深**。这一篇先讲清两件事：Arthas 为什么能「不重启、不改代码」就诊断线上 JVM；再给一张命令地图，后续两篇分别展开命令详解和排障实战。

---

## 一、Arthas 是什么

阿里巴巴开源的 **Java 在线诊断工具**（JDK 6+），通过 attach 到目标 JVM，对**已加载的类做运行时字节码增强**，解决四类线上痛点：

| 痛点 | 传统方式 | Arthas 方式 |
|:---|:---|:---|
| 线上跑的是不是我改的代码？ | 重新发包确认 | `jad` 反编译直接看 |
| CPU 飙高 / 接口 RT 高 | top -Hp + jstack 手工映射 | `thread -n 3`、`trace` 一条命令 |
| 方法入参出参是什么、异常是什么 | 加日志、重启、复现 | `watch` 实时观测 |
| 紧急 bug 要热修 | 打包发布、重启 | `jad → mc → redefine` 在线替换 |

> 核心特点：**无侵入**（不改业务代码）、**不重启**（运行时 attach）、**可回退**（退出时还原增强）。

## 二、整体架构与工作原理

### 1. 三个关键技术底座

| 技术 | 作用 |
|:---|:---|
| **Attach API**（`com.sun.tools.attach.VirtualMachine`） | 让一个进程附着到另一个运行中的 JVM，JDK 6+ 提供 |
| **Java Agent**（动态 agentmain） | attach 后在目标 JVM 内执行 agent 代码，能访问目标进程所有类 / ClassLoader |
| **Instrumentation API**（`java.lang.instrument`） | JVM 官方提供的「运行时修改已加载类字节码」机制，注册 `ClassFileTransformer` + `retransformClasses` |

> 对比：静态 agent 是 `-javaagent` 启动参数（premain，main 之前加载，如 SkyWalking 探针）；**Arthas 用的是动态 agent（agentmain）**，进程跑起来后再注入，这是「不重启」的前提。

### 2. 启动与注入流程

```bash
# 启动 arthas-boot，列出本机 Java 进程，选序号 attach
java -jar arthas-boot.jar
# 或直接指定 pid
java -jar arthas-boot.jar <pid>
```

```
  你的终端                    目标 JVM (pid=12345)
 ┌──────────────┐            ┌─────────────────────────────┐
 │ arthas-boot  │  attach()  │ JVM 进程                     │
 │              │───────────▶│                             │
 │              │ loadAgent  │  加载 arthas-agent.jar       │
 │              │            │  └─ agentmain() 入口         │
 │              │            │     └─ ArthasBootstrap      │
 │  telnet 3658 │◀──────────▶│        ├─ Telnet Server     │
 │  http   8563 │◀──────────▶│        └─ HTTP/Web Console  │
 └──────────────┘            └──────────┬──────────────────┘
                                        │ 执行 watch/trace 等命令
                                        ▼
                        Instrumentation.addTransformer(...)
                        Instrumentation.retransformClasses(目标类)
                                        │ ByteBuddy(ASM) 织入
                                        ▼
                        方法进入/退出处插入 AdviceListener 回调
                        → 采集 params / returnObj / #cost / 调用链
```

要点：

1. `arthas-boot` 只是个启动器，真正的诊断逻辑（Arthas server）**运行在目标 JVM 进程内部**，所以能直接看到目标进程的类和对象。
2. 一个 JVM 只会被注入一次：重复 attach 时提示 `The target process already loaded arthas-agent`，直接连已有 server。
3. 命令通道是 **Telnet（默认 3658）+ HTTP/Web Console（默认 8563）**，默认只监听 127.0.0.1。

### 3. 字节码增强：命令为什么能观测方法

`watch` / `trace` / `stack` / `monitor` / `tt` 这类「方法观测」命令，底层是同一件事：

1. 通过 `Instrumentation` 注册一个 `ClassFileTransformer`；
2. 调用 `retransformClasses(目标类)` 触发 JVM 重新走类转换流程；
3. transformer 用 **ByteBuddy（底层 ASM，访问者模式操作字节码）** 在目标方法的**进入点和退出点**织入回调（类似 AOP 的 before/after，但织在字节码层）；
4. 方法被调用时，回调里拿到参数、返回值、异常、耗时，再通过 Telnet 通道输出给你。

```java
// 伪代码：增强后的方法长这样
public Order createOrder(OrderRequest req) {
    Advice.before(clazz, method, new Object[]{req});   // 织入的前置通知
    try {
        Order result = 原始方法体;
        Advice.afterReturning(result);                 // 织入的正常返回通知
        return result;
    } catch (Throwable t) {
        Advice.afterThrowing(t);                      // 织入的异常通知
        throw t;
    }
}
```

> **retransform 的限制**（JVM 规范，面试常问）：只能改方法体，**不能增删字段、方法，不能改方法签名和继承结构**，否则报 `attempted to change the schema (add/remove fields)`。这就是 `redefine` 热更新只能改方法内部逻辑的原因。

## 三、命令地图（速查表）

| 分类 | 命令 | 一句话用途 |
|:---|:---|:---|
| **总览** | `dashboard` | 实时面板：线程、内存分代、GC、CPU、Runtime 信息 |
| **线程** | `thread` | 线程栈；`-n 3` 最忙线程、`-b` 死锁/阻塞源、`--state BLOCKED` 按状态过滤 |
| **类查找** | `sc`（search class） | 查已加载的类：`sc -d *OrderService`（ClassLoaderHash、来源 jar） |
| **方法查找** | `sm`（search method） | 查类的方法：`sm -d 类 方法` |
| **反编译** | `jad` | 反编译线上类，确认实际运行的代码版本 |
| **方法观测** | `watch` | 看方法入参 / 返回值 / 异常 / 成员变量（最常用） |
| | `trace` | 方法内部调用链 + 每段耗时（定位慢点） |
| | `stack` | 方法被谁调用（输出调用栈） |
| | `monitor` | 周期统计：调用次数、成功/失败、平均 RT、失败率 |
| | `tt`（TimeTunnel） | 录制每次调用现场，事后查看、重放（`-p`） |
| **表达式** | `ognl` | 执行 OGNL 表达式：调静态方法、读静态字段、拿 Spring Bean |
| | `getstatic` | 快速看静态字段 |
| | `vmtool` | JVMTI 能力：`getInstances` 查堆内实例、`forceGc` 强制 GC |
| **内存** | `heapdump` | 导出堆 dump（`--live` 只导存活对象），再用 MAT 分析 |
| **日志** | `logger` | 查看 / 动态修改日志级别，不用重启 |
| **热更新** | `mc` | Memory Compiler，在线编译 .java |
| | `redefine` / `retransform` | 用新 .class 替换线上类（只能改方法体） |
| **火焰图** | `profiler` | 内置 async-profiler：`start` / `stop --format html` |
| **JVM 信息** | `jvm` / `sysprop` / `sysenv` / `vmoption` | JVM 详情、系统属性、环境变量、VM 参数 |
| **类加载器** | `classloader` | 查看 ClassLoader 树、加载的 jar |

## 四、启动、连接与退出

```bash
# 安装（单机）
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar            # 选进程序号

# 退出方式（面试常考区别）
quit / q / Ctrl+C   # 只断开当前连接；Arthas server 还在目标 JVM 里，增强仍在
stop                # 完全退出：关闭 server、reset 所有增强类、恢复原样
reset 类名           # 手动还原某个类的增强（不退出 Arthas）
```

| 操作 | 增强是否保留 | server 是否停止 |
|:---|:---|:---|
| `quit` / `q` / Ctrl+C | 保留（开销持续） | 否 |
| `stop` | 全部 reset | 是 |
| `reset 类名` | 指定类还原 | 否 |

> **生产红线**：排查完必须 `stop`（或至少 `reset`）。增强是有插桩开销的，`quit` 断开后增强仍在目标方法里，高频方法上可能一直吃掉性能。

## 五、易错点

| 易错点 | 澄清 |
|:---|:---|
| Arthas 需要改应用代码 / 加启动参数 | 不需要。运行时 attach，动态 agentmain 注入 |
| 增强是 Arthas 自己实现了一套 AOP | 走 JVM 标准 `Instrumentation` + `ClassFileTransformer` + ByteBuddy/ASM 织字码节码 |
| `redefine` 能随便改类 | JVM 限制：只能改方法体，不能加方法/字段、改签名 |
| `quit` 就是退出 Arthas | quit 只断连接，增强还在；**`stop` 才是真退出并还原** |
| attach 后诊断代码跑在 arthas-boot 进程里 | 错。agent 注入后逻辑运行在**目标 JVM 内部** |
| 一台机多次 attach 会重复注入 | 不会，检测到已加载 agent 直接复用 3658 server |
| Telnet 端口可以随便开放远程访问 | 默认只监听 127.0.0.1；开 0.0.0.0 等于把线上 JVM 的操作权裸奔 |

---

## 六、一句话总结

Arthas 靠 **Attach API + 动态 Java Agent（agentmain）** 注入目标 JVM，用 **Instrumentation 的 `retransformClasses` + ByteBuddy 字节码增强**在方法前后织入回调，从而实现不改代码、不重启的线上观测；观测类命令（watch/trace/stack/monitor/tt）共用这一套增强底座，`redefine` 热更新也走同一条路但受 JVM 限制只能改方法体；用完记得 **`stop` 还原增强**。
