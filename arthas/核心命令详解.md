# Arthas 核心命令详解

面试实操题基本围绕「**观测四件套（watch / trace / stack / monitor）+ tt + 反编译三件套（sc / sm / jad）**」展开。本篇按使用频率讲每个命令的参数、表达式和坑。

---

## 一、watch：方法观测（最高频）

实时观测一个方法的**入参、返回值、异常、对象成员、耗时**，不用加日志、不用重启。

```bash
# 基本用法：观测入参 + 返回值，展开 2 层，只执行 3 次
watch com.demo.OrderService createOrder '{params, returnObj}' -x 2 -n 3

# 只看异常：方法抛异常时打印入参和异常对象
watch com.demo.OrderService createOrder '{params, throwExp}' -e -x 3

# 方法调用前就打印（拿不到返回值，适合看入参是否被上游传错）
watch com.demo.OrderService createOrder '{params}' -b

# 观测当前对象的成员变量（target = this）
watch com.demo.OrderService createOrder 'target' -x 2
```

### 四个观测时点

| 参数 | 时点 | 能拿到什么 |
|:---|:---|:---|
| `-b` | 方法调用前 | params、target |
| `-e` | 方法异常退出后 | params、throwExp |
| `-s` | 方法正常返回后 | params、returnObj |
| `-f` | 方法结束后（**默认**，正常/异常都触发） | params、returnObj（异常时为 null）、throwExp |

### 表达式里的内置变量（OGNL）

| 变量 | 含义 |
|:---|:---|
| `params` | 入参数组，`params[0]`、`params.length` |
| `returnObj` | 返回值 |
| `throwExp` | 抛出的异常对象 |
| `target` | 当前对象（this），可看成员变量 `target.cacheMap` |
| `clazz` | 当前类的 Class 对象 |
| `#cost` | 方法执行耗时（**毫秒**） |

### 条件表达式（第二个参数）

```bash
# 只看耗时 > 100ms 的调用
watch com.demo.OrderService createOrder '{params, returnObj, #cost}' '#cost > 100'

# 只看第一个参数的 userId == 123 的调用
watch com.demo.OrderService createOrder '{params}' 'params[0].userId == 123'

# 展开深度 -x：默认 1 层，嵌套对象要看清就 -x 2/3
```

> `-n 3` 表示命中 3 次后自动退出增强，**生产环境必加**，避免高频方法持续插桩。

## 二、trace：调用链耗时（定位慢点）

输出方法内部的**调用树和每一级的耗时占比**，接口慢时第一个用它。

```bash
# 追踪 createOrder 内部调用链
trace com.demo.OrderService createOrder

# 只看总耗时 > 500ms 的请求，逐层下钻
trace com.demo.OrderService createOrder '#cost > 500' -n 3

# 正则匹配类/方法（-E 开启正则）
trace -E com.demo.service.*Service '.*Order.*'

# 默认跳过 JDK 方法，想连 JDK 内部一起看
trace com.demo.OrderService createOrder --skipJDKMethod false
```

输出示意：

```
`---[2345ms] com.demo.OrderService:createOrder()
    +---[10ms]   com.demo.dao.OrderDao:insert()
    +---[2200ms] com.demo.client.InventoryClient:deduct()   # 慢点在这
    `---[80ms]   com.demo.MQProducer:send()
```

关键限制（面试高频）：

1. **只追一层**：trace 只展示目标方法的**直接子调用**。发现 `deduct()` 慢，要再 `trace InventoryClient deduct` 继续往下钻。
2. **不跨线程**：子调用在异步线程 / 线程池里执行时追不到（trace 沿当前线程栈走）。
3. trace 也是字节码增强，高频接口记得加 `#cost` 过滤和 `-n` 限制。

---

## 三、stack：方法被谁调用

输出「谁调用了这个方法」的完整调用栈，适合排查**某个方法在什么入口/场景下被意外触发**。

```bash
# 谁在调用 pay 方法
stack com.demo.PayService pay

# 只看耗时 > 50ms 的调用栈
stack com.demo.PayService pay '#cost > 50' -n 5
```

> trace 是「**往下**看方法内部」，stack 是「**往上**看调用来源」，watch 是「**看这一点**的数据」。

---

## 四、monitor：方法执行统计

按周期（默认 60s，`-c` 指定秒数）聚合统计方法的调用情况：

```bash
# 每 10 秒输出一次统计
monitor -c 10 com.demo.OrderService createOrder
```

```
 timestamp            class          method      total  success  fail  avg-rt(ms)  fail-rate
 2026-09-08 10:00:00  OrderService   createOrder 120    115      5     42.36       4.17%
```

| 指标 | 含义 |
|:---|:---|
| total / success / fail | 周期内总调用 / 成功 / 失败次数 |
| avg-rt | 平均响应时间 |
| fail-rate | 失败率（抛异常算失败） |

> monitor 适合**宏观量化**：「这个接口最近是不是失败率涨了 / RT 涨了」；微观根因还得靠 trace/watch。

## 五、tt（TimeTunnel）：时间隧道

把方法的**每一次调用现场**（入参、返回值、异常）录下来，事后回放。偶现问题的神器。

```bash
tt -t com.demo.OrderService createOrder -n 10   # 录制 10 次调用
tt -l                                           # 列出所有录制片段（INDEX）
tt -i 1000                                      # 查看 INDEX=1000 片段的详细现场
tt -i 1000 -p                                   # 用当时的入参重放（replay）这次调用
tt -d 1000                                      # 删除片段
```

| 参数 | 作用 |
|:---|:---|
| `-t` | 记录调用现场 |
| `-i <INDEX>` | 查看指定片段 |
| `-p` | **重放**：用录制的入参重新调用一次（注意写操作会重复执行！） |
| `-n` | 限制录制次数 |

> `-p` 重放是真的重新执行方法，**下单、扣款这类写操作慎用**，可能造成重复数据。

## 六、sc / sm / jad：类信息与反编译

```bash
# sc：查类是否加载、被哪个 ClassLoader 加载、来自哪个 jar
sc -d *OrderService
# 关键输出：classLoaderHash（mc 编译时要用）、code-source（jar 路径）

# sm：查类有哪些方法
sm com.demo.OrderService
sm -d com.demo.OrderService createOrder     # 方法详情

# jad：反编译线上实际运行的字节码
jad com.demo.OrderService
jad --source-only com.demo.OrderService > /tmp/OrderService.java   # 只导出源码
```

典型用途：

- **「我改的代码上线了吗？」** → jad 反编译看逻辑是不是新的；
- **「类怎么没生效？」** → sc -d 看 `code-source`，发现是旧 jar / 多个 ClassLoader 加载了两份；
- 热修复第一步：jad 导出源码作为修改基础。

## 七、thread / dashboard：线程与总览

```bash
dashboard                          # 实时总览：线程、内存分代、GC 次数、CPU
thread                             # 所有线程概览（ID、状态、CPU%、daemon）
thread 42                          # 看 ID=42 线程的栈
thread -n 3                        # CPU 最忙的 3 个线程 + 栈（CPU 飙高首选）
thread -b                          # 找出阻塞其他线程的线程（死锁定位）
thread --state BLOCKED             # 列出所有 BLOCKED 状态线程
thread -i 1000                     # 按 1000ms 采样统计线程 CPU 占用
```

## 八、ognl / vmtool / heapdump：表达式与内存

### ognl：直接执行 OGNL 表达式

```bash
# 调静态方法 / 读静态字段
ognl '@java.lang.System@getProperty("user.dir")'
ognl '@com.demo.Constants@SWITCH'

# 线上紧急改开关（读出来、set 回去）
ognl '@com.demo.Config@getInstance().setSwitch(false)'
```

### vmtool：JVMTI 能力（查堆内实例）

```bash
# 堆里找某个类的实例（查缓存里到底放了什么、实例数异常增长）
vmtool --action getInstances --className com.demo.OrderVO --limit 10 -x 2

# 强制 GC（配合观察堆是否回落，判断内存泄漏）
vmtool --action forceGc
```

### heapdump：导出堆快照

```bash
heapdump /tmp/dump.hprof              # 导出全量
heapdump --live /tmp/dump.hprof       # 只导存活对象（会先触发 Full GC）
```

> `--live` 会先 Full GC，生产上有 STW 成本；dump 大堆期间也有停顿，低峰期操作。导出后用 MAT 分析（支配树、Leak Suspects）。

---

## 九、logger：动态日志级别

```bash
logger                                          # 查看所有 logger 及级别
logger --name com.demo.service --level DEBUG    # 临时开 DEBUG，不用重启
logger --name com.demo.service --level INFO     # 排查完改回去
```

> 比 redefine 热改日志配置更轻：线上偶现问题时先把级别调到 DEBUG，复现后立刻调回。

## 十、mc / redefine：热更新

```bash
# 1. 反编译出源码
jad --source-only com.demo.OrderService > /tmp/OrderService.java
# 2. 修改 /tmp/OrderService.java（vim 改方法体逻辑）
# 3. mc 内存编译：-c 指定 ClassLoaderHash（sc -d 拿到），-d 输出目录
mc -c 19469ea2 /tmp/OrderService.java -d /tmp
# 4. 加载新 class
redefine /tmp/com/demo/OrderService.class
#    或 retransform（支持 -l 查看、-d 回滚，更推荐）
retransform /tmp/com/demo/OrderService.class
```

**限制（JVM retransform 规范）**：

- ✅ 能改：方法体内部逻辑（if 判断、赋值、计算）；
- ❌ 不能改：新增/删除方法或字段、修改方法签名、修改继承结构、改注解。
- Spring Bean 不会重新初始化，替换的是类的方法字节码，原 Bean 实例不变。

## 十一、profiler：火焰图

内置 async-profiler，**采样式、低开销**，适合定位 CPU 热点和内存分配热点。

```bash
profiler start                              # 开始采样 CPU
profiler stop --format html --file /tmp/cpu.html   # 停止并生成火焰图

profiler start --event alloc                # 采样内存分配
profiler stop --format html --file /tmp/alloc.html
```

## 十二、易错点

| 易错点 | 澄清 |
|:---|:---|
| watch 默认方法调用前触发 | 默认是 `-f`（结束后）；想看入参到达时机要显式 `-b` |
| 方法异常时 returnObj 有值 | 异常时 returnObj 为 null，异常信息要用 `-e` + `throwExp` |
| `-x` 默认展开全部 | 默认只展开 **1 层**，嵌套对象看到的是 `@xxx` 引用，要 `-x 2/3` |
| trace 能追整条分布式/异步链路 | 只追**当前线程一层直接调用**；跨线程、跨服务追不到 |
| trace 慢就多开几个 | trace 也有插桩开销，高频接口加 `#cost` 过滤 + `-n` 限制 |
| tt `-p` 重放没有副作用 | 重放是真实调用，写操作（下单/扣款）会重复执行 |
| redefine 能加新方法 | 不能，JVM 限制 schema 不能变（字段/方法/签名） |
| `mc` 不用指定 ClassLoader | 多模块/多 ClassLoader 环境必须 `-c <hash>`，否则编译加载失败 |
| heapdump --live 无成本 | 会先 Full GC + dump 期间 STW，大堆低峰操作 |
| ognl 可以随便线上执行 | ognl 能调任意静态方法，等于开放执行权，生产慎用 + 用完 stop |

---

## 十三、一句话总结

观测类命令分工：**watch 看一个点的入参出参异常**（`-b/-e/-s/-f` + `params/returnObj/throwExp/#cost`，条件过滤 + `-n` 限次）、**trace 往下看一层调用链耗时**、**stack 往上看谁调的**、**monitor 周期统计成功率与 RT**、**tt 录制现场并可重放**；确认线上代码用 **jad/sc/sm**，查实例与内存用 **vmtool/heapdump**，临时开日志用 **logger**，热修走 **jad → mc(-c classLoaderHash) → retransform**，全程记住：高频方法必加条件和次数限制，用完 `stop`。
