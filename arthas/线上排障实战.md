# Arthas 线上排障实战

命令背得再熟，面试最终落在「**给你一个现象，你怎么用 Arthas 定位**」。本篇按线上高频故障场景组织，每个场景给出：现象 → 命令组合 → 定位思路。建议把 2~3 个场景准备成 STAR 案例。

---

## 场景 1：CPU 突然飙高

```bash
thread -n 3          # 直接列出 CPU 最忙的 3 个线程及其栈
thread -i 1000       # 按 1s 采样统计，避免瞬时抖动误判
```

定位分支：

| 栈顶特征 | 根因方向 |
|:---|:---|
| 业务方法（死循环、复杂计算、正则回溯） | 代码问题，继续 `trace`/`watch` 下钻 |
| 大量 GC 线程（`VM Thread`、`GC task`） | 频繁 GC，转内存方向（见场景 8） |
| `Object.wait` / 锁相关 | 锁竞争，转场景 5 |
| JIT 编译线程持续高 | 热点编译，一般短暂观察即可 |

> 对比传统三板斧：`top → top -Hp <pid> → printf %x → jstack grep nid`，Arthas `thread -n 3` 一步到位，底层是同一套线程栈数据。

## 场景 2：接口 RT 高 / 超时

思路：**trace 自顶向下逐层下钻**，每一层只追慢请求。

```bash
# 第 1 层：只追 > 500ms 的请求
trace com.demo.OrderController createOrder '#cost > 500' -n 3

# 输出发现 InventoryClient.deduct() 占了 2200ms → 继续追
trace com.demo.client.InventoryClient deduct '#cost > 1000' -n 3

# 再往下是 HttpClient.execute 慢 → 怀疑下游，或用 watch 看参数
watch com.demo.client.InventoryClient deduct '{params, #cost}' '#cost > 1000' -x 2 -n 3
```

常见根因：下游 RPC 慢（trace 终点在 client）、慢 SQL（终点在 MyBatis Mapper）、锁等待（栈中 park/lock）、大对象序列化。

> trace 不跨线程：异步调用在 trace 里看不到耗时，要对异步线程里执行的方法**单独 trace**。

## 场景 3：接口报错 / 返回结果不对

```bash
# 异常：直接抓抛异常时的入参和异常栈
watch com.demo.OrderService createOrder '{params, throwExp}' -e -x 3 -n 3

# 结果不对：对比入参和返回值，怀疑哪层看哪层
watch com.demo.OrderService createOrder '{params, returnObj}' -f -x 2 -n 3

# 偶发特定用户出问题：用条件表达式精确过滤
watch com.demo.OrderService createOrder '{params, returnObj}' 'params[0].userId == 12345' -x 2 -n 1
```

定位思路：先确认**入参是不是被上游传错**（-b 看入口参数），再确认**返回值在哪一层开始变错**（对链路各层分别 watch），最后看**异常类型和 message**（throwExp）。

## 场景 4：怀疑线上跑的代码不是最新版本

```bash
# 类来自哪个 jar、被哪个 ClassLoader 加载
sc -d com.demo.OrderService
# 关注：code-source（jar 路径）、classLoaderHash

# 直接反编译看逻辑
jad com.demo.OrderService
```

常见结论：发布平台没发成功、多实例灰度只发了部分、多 ClassLoader 加载了新旧两份类、依赖 jar 版本没升级。

---

## 场景 5：死锁 / 线程大量 BLOCKED

```bash
thread -b                 # 直接找出「阻塞其他线程」的线程，死锁会明确标出来
thread --state BLOCKED    # 看所有阻塞线程在等哪把锁
```

拿到阻塞源头线程的栈后：看它持有锁在干什么（慢查询？外部调用？sleep？），对症优化锁粒度。

## 场景 6：紧急 bug 热修复（不重启）

适用：**方法体内的逻辑错误**（判断条件、赋值、计算），不涉及类结构变更。

```bash
# 1. 确认类已加载，拿 classLoaderHash
sc -d com.demo.OrderService
# 2. 反编译导出源码
jad --source-only com.demo.OrderService > /tmp/OrderService.java
# 3. 修改源码（vim /tmp/OrderService.java）
# 4. 内存编译，-c 指定 ClassLoaderHash
mc -c 19469ea2 /tmp/OrderService.java -d /tmp
# 5. 重新加载
retransform /tmp/com/demo/OrderService.class
```

边界：

- ❌ 不能加方法/字段、改签名、改继承；
- Spring Bean 不重新初始化，换的是方法字节码；
- **retransform 只是应急，正式修复必须走发布流程**（重启后热更失效）；
- 操作前在测试环境验证 class 文件。

## 场景 7：临时调整日志级别排查偶现问题

```bash
logger                                          # 找到目标 logger 名
logger --name com.demo.service --level DEBUG    # 开 DEBUG 等复现
logger --name com.demo.service --level INFO     # 完事后立刻改回
```

比加日志发版快得多，也避免热更新改代码的风险。

## 场景 8：内存泄漏 / OOM / 频繁 Full GC

```bash
dashboard                              # 看堆各代占用、GC 次数增速
vmtool --action forceGc                # 强制 GC 后看占用是否回落（不回落 = 泄漏嫌疑）
vmtool --action getInstances --className com.demo.OrderVO --limit 10 -x 2  # 看实例内容
heapdump --live /tmp/dump.hprof        # 导堆，MAT 分析引用链
```

配合 jvm 笔记里的 MAT 套路（Histogram → Dominator Tree → Leak Suspects → GC Roots 引用链），常见泄漏源：静态集合只增不减、ThreadLocal 未 remove、缓存无淘汰、连接未关。

> 也可用 `ognl` 读静态缓存字段验证猜测，如 `ognl '@com.demo.CacheHolder@userOrderCache.size()'`。

## 场景 9：某方法被意外调用 / 想知道调用入口

```bash
stack com.demo.PayService refund -n 5     # 谁触发了退款方法
```

适合排查：定时任务意外触发、MQ 重复消费、接口被未知方调用、循环调用放大。

## 场景 10：偶现问题，事后想看现场

```bash
tt -t com.demo.OrderService createOrder -n 20   # 先挂上录制
# ……问题复现后……
tt -l                                           # 找到异常片段 INDEX
tt -i 1003                                      # 查看当时入参/返回/异常
# tt -i 1003 -p                                 # 确认后再重放（写操作慎用）
```

## 生产环境使用规范（面试加分项）

1. **权限**：用与目标进程相同的系统用户 attach；Telnet 默认 127.0.0.1，不要绑 0.0.0.0 暴露公网。
2. **控开销**：观测高频方法必须带条件表达式（`#cost > n`、参数过滤）+ `-n` 限制次数；`profiler` 采样开销低可稍长开，watch/trace 命中即收。
3. **收尾**：排查完执行 `stop`（不是 quit），或 `reset` 还原增强，避免插桩长期存在。
4. **危险操作分级**：logger < watch/trace < heapdump（有 STW）< retransform/ognl 写操作 < tt 重放；写操作前先在测试环境验证。
5. **Arthas 不能替代监控**：它是「现场显微镜」，常态监控靠日志/metrics/APM；Arthas 解决的是监控覆盖不到的临时深挖。

## 易错点

| 易错点 | 澄清 |
|:---|:---|
| CPU 高直接看业务栈 | 先排除 GC 线程（`thread -n 3` 栈顶是 GC task 说明根因在内存） |
| trace 一次就能看到底 | 只追一层，慢点子调用要再 trace；异步线程追不到 |
| 热更新当发布手段 | retransform 重启即失效，只能应急，正式修复必须发版 |
| heapdump 随手导 | dump 期间 STW，`--live` 还会先 Full GC，大堆低峰操作 |
| tt 重放随便点 | `-p` 是真实调用，写接口会产生脏数据 |
| 用完 quit 就完事 | quit 不断增强，必须 stop/reset |
| Arthas 能追跨服务调用 | 只能观测单 JVM 内，分布式链路还得靠 SkyWalking/Arms 等 APM |

---

## 一句话总结

排障套路：**CPU 高**用 `thread -n 3`（先分清业务线程还是 GC 线程）；**接口慢**用 `trace '#cost>n'` 逐层下钻（不跨线程、只追一层）；**结果错/异常**用 `watch -e/-f` + 条件表达式抓出入参和 throwExp；**版本疑问**用 `sc -d + jad`；**死锁**用 `thread -b`；**偶现**用 `tt` 录现场、`logger` 开 DEBUG；**内存**用 `dashboard + forceGc + heapdump → MAT`；**应急止血**用 `jad → mc → retransform`（只能改方法体）。生产上记住：条件 + 限次 + 用完 `stop`，热更必须补发版。
