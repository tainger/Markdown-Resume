# 服务注册发现与配置

注册中心是 Dubbo 的大脑。面试三板斧：**URL 统一模型 → 注册中心选型（ZK vs Nacos）→ 服务订阅与推送**；P7 加分项：**Dubbo3 应用级发现**与**配置优先级**。

---

## 一、URL：Dubbo 的统一数据总线（必背）

Dubbo 里**一切配置、协议、注册信息都是 URL**，一条服务提供方的注册 URL：

```
dubbo://192.168.1.10:20880/com.foo.UserService?
    application=user-provider&
    group=pay&
    version=1.0.0&
    timeout=3000&
    retries=2&
    loadbalance=roundrobin&
    methods=getUser,createOrder
```

| 段 | 含义 | 作用 |
|:---|:---|:---|
| `dubbo://` | 协议 | `@Adaptive` 按它选 Protocol 扩展 |
| `host:port` | 地址 | 网络层连接目标 |
| `path` | 接口全限定名 | 服务定位 |
| `?参数` | 全部配置 | 方法级/接口级/全局配置都在这 |

> 注册中心、路由规则、动态配置本质上都是**对 URL 的增删改**——理解了 URL 就理解了 Dubbo 的一切流转。

## 二、注册中心选型（必考对比）

| 维度 | ZooKeeper | Nacos | Redis |
|:---|:---|:---|:---|
| 一致性 | **CP**（ZAB） | **AP**（可切 CP/Distro+Raft） | AP 弱一致 |
| 健康检查 | 会话 Session（心跳+临时节点） | 客户端心跳 + 服务端主动探测 | 心跳 TTL |
| 推送方式 | Watch 一次性触发（需重注册） | **UDP/长轮询/长连接推送** | 发布订阅 |
| 结构 | 树形 ZNode /dubbo/…/providers | 服务-集群-实例模型 | hash 结构 |
| 典型问题 | ZK 集群脑裂时**不可用**（牺牲可用性） | 极端分区返回旧列表（可接受） | 数据易丢，主流不用 |
| 选型建议 | 强一致诉求、老架构 | **主流首选**（阿里系+云原生） | 仅限小型自建 |

> 经典追问「注册中心挂了还能调用吗」：**能**。Consumer 本地缓存了 providers 列表（`RegistryDirectory` 内存态），注册中心只影响**新上线下线感知**，不影响存量调用——这体现 AP 设计的务实：**宁可短暂不一致，不能不可用**。

## 三、服务订阅与推送流程

```
Consumer 启动
  ├─ 订阅 /dubbo/com.foo.UserService/providers   （ZNode 目录）
  ├─ RegistryDirectory 收到全量 provider URL 列表
  │    └─ toInvokers()：按协议分组 → 生成远程 Invoker → 刷新本地缓存列表
  ├─ 订阅 routers / configurators（路由与动态配置）
  │
  ▼ 运行期 Provider 上下线
  ZK 临时节点消失 / Nacos 实例剔除
  → 推送给 RegistryDirectory
  → 本地 Invoker 列表增删（不加锁全量重建，copy-on-write）
  → 后续调用自动避开失效节点
```

要点：
- **Directory 是活的**：它不是快照，是持续接收通知刷新的动态列表（Cluster 层每次调用 `list()` 取最新）。
- **ZK Watch 是一次性的**：触发后要重新注册 Watcher，Dubbo 内部已封装。
- **消费端本地缓存文件**：`dubbo.consumer.cache` 可持久化列表，注册中心全挂也能用旧文件冷启动（容灾）。

## 四、配置覆盖关系（必背顺序）

同一配置在四处出现时，**优先级从高到低**：

```
① 方法级 provider 指定      > ② 接口级 provider      > ③ Consumer 端方法/接口级
> ④ Consumer 全局           > ⑤ Provider 全局（provider 的配置更懂自己）
```

- 经典考点：**timeout 谁说了算？** Provider 端优先——提供方最了解自己的接口该多久超时，防止消费方乱设导致资源挂死。
- 动态配置中心（Nacos 配置/Dubbo Admin）可运行时改 URL 参数 → 触发 configurators 通知 → **不重启调整超时/权重/禁用**。

---

## 五、启动检查与多注册中心

| 特性 | 说明 | 关键参数 |
|:---|:---|:---|
| 启动检查 | 默认启动时若 provider 不可用直接抛异常（fail-fast） | `check=false` 关闭（测试环境/依赖松耦合场景） |
| 多注册中心 | 一个服务可同时注册到 ZK + Nacos（双注册迁移方案） | `register=true/false` 指定注册到哪几个 |
| 多协议 | 同一服务可同时以 dubbo + rest 暴露 | `<dubbo:protocol type="dubbo,rest">` |
| 分组/版本 | group 隔离环境/业务线；version 控制接口升级（新旧并存） | `group`、`version`；只订阅不注册 `register=false` |

> **版本迁移话术**：灰度期新版本接口 `version=2.0` 与旧版并存 → 消费方按需切换 → 全量后下线 1.0。配合 `register=false` 还能实现「只订阅不注册」（直连压测）。

---

## 易错点

1. **注册中心挂 ≠ 不可用**（高频追问）：存量调用靠本地缓存继续，只是丧失动态感知。
2. **ZK 临时节点**：Provider 会话断开节点自动删除——所以 ZK 心跳由 **session** 保证，不是靠子节点 TTL。
3. **Consumer 本地列表刷新是 copy-on-write 全量替换**，不是增量改——保证无锁并发安全。
4. **check=false 只关闭「启动检查」**，运行期掉线照样走容错（Failover 换机器），别答成「彻底不检查」。
5. 配置优先级答题别背反：**方法级 > 接口级 > 全局级；Provider > Consumer**（timeout 场景）。

---

## 一句话总结

**一切皆 URL**：Provider `export` 后把 URL 写进注册中心，Consumer 订阅目录由 `RegistryDirectory` 维护活列表；注册中心挂了靠本地缓存照常调用（AP 取向）；配置优先级「方法>接口>全局、Provider>Consumer」；Dubbo3 应用级发现把接口级注册数据降一个数量级。
