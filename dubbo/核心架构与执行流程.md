# 核心架构与执行流程

Dubbo 的面试第一题永远是「**说说 Dubbo 的架构和一次 RPC 调用的完整流程**」。答好的关键：分层架构 → 核心组件与 Invoker 模型 → 服务暴露/引用 → 一次调用全链路 → **Dubbo3 应用级服务发现**。

---

## 一、分层架构（必背）

Dubbo 采用**分层 + 可扩展**的架构，每层都是一个 SPI 扩展点，层与层之间通过 `Invoker` 解耦：

```
┌─────────────────────────────────────────────────────────────┐
│ Service 业务层   接口实现类（Provider）/ 接口引用（Consumer）      │
├─────────────────────────────────────────────────────────────┤
│ Proxy 代理层    透明代理：消费端生成代理stub，服务端包装skeleton  │
│ Registry 注册层  服务注册与发现（ZooKeeper/Nacos）               │
│ Cluster 集群层   容错（Directory+Router+LoadBalance）、伪装成    │
│                一个 Invoker                                   │
│ Protocol 协议层  RPC 调用封装：dubbo/三协议，Invoker ↔ Exporter │
├─────────────────────────────────────────────────────────────┤
│ Remoting 远程通信层                                             │
│   Exchange 信息交换层：Request/Response 语义                    │
│   Transport 网络传输层：Netty/Mina 抽象                         │
│   Serialize 序列化层：hessian2/kryo/protobuf                   │
└─────────────────────────────────────────────────────────────┘
```

核心组件一句话职责：

| 组件 | 职责 | 面试考点 |
|:---|:---|:---|
| `Invoker` | **Dubbo 的核心模型**：一个「可执行的本地/远程对象」，掩盖网络细节 | 分层解耦的关键抽象 |
| `Proxy` | 消费端动态代理（Javassist/JDK），把接口调用转成 `Invoker.invoke()` | 为什么无感知 RPC |
| `Protocol` | 通信协议扩展点：`export(Invoker)` 暴露、`refer()` 引用 | `dubbo://` 默认协议 |
| `Exporter` | 暴露后的句柄，`unexport()` 可注销服务；存入 `ExporterMap`（key=接口+版本+分组） | 服务下线 |
| `Registry` | 注册中心客户端：注册、订阅、通知 | ZK/Nacos 对比 |
| `Cluster` | 把多个 Provider 的 Invoker **伪装成一个**：内部 Directory→Router→LB | 容错与负载均衡入口 |
| `Directory` | 动态的 Invoker 目录：从注册中心拿实时列表 | 与 Router/LB 的链路 |
| `Router` | 路由规则过滤（如黑白名单、同机房优先、灰度） | 服务治理 |
| `LoadBalance` | 从路由后的列表选一个 Invoker | 四种负载均衡 |
| `URL` | **Dubbo 的统一数据总线**：配置、协议、注册信息都以 URL 承载 | 一切皆 URL |

## 二、服务暴露（Provider 启动）流程

```
Spring 容器启动 → 解析 @DubboService / <dubbo:service>
  │
  ├─ ① ServiceConfig.export()
  │     本地暴露 injvm（可选）→ 远程暴露
  │
  ├─ ② Proxy 层：把实现类 ref 包装成 AbstractProxyInvoker
  │     （消费端调它 = 反射调真实实现）
  │
  ├─ ③ Protocol 层：dubbo 协议 export(invoker)
  │     ├─ 启动 Netty Server，监听 20880 端口
  │     └─ 存入 ProtocolExporterMap：key = 服务接口+group+version
  │
  ├─ ④ Registry 层：register(URL)
  │     把服务 URL 写入注册中心（如 /dubbo/com.foo.BarService/providers/...）
  │
  └─ ⑤ 订阅 configurators/routers 动态配置
```

## 三、服务引用（Consumer 启动）流程

```
@DubboReference 注入 → ReferenceConfig.get()
  │
  ├─ ① 拉取注册中心 providers/consumers/routers/configurators 目录
  ├─ ② Cluster 层：把 providers 列表包装成 ClusterInvoker（伪装成一个）
  ├─ ③ Proxy 层：Javassist/JDK 生成接口代理
  └─ ④ 代理注入到业务字段 → 调用即 RPC
```

## 四、一次 RPC 调用的完整旅程（必背，能白板画）

```
Consumer                                              Provider
────────────────────────────────────────────────────────────────
userService.getUser(id)                    ← 业务代码调用接口
  │
  ├─ Proxy（Javassist 代理）
  │    └ 封装 RpcInvocation（方法名/参数类型/实参/attachments）
  │
  ├─ Cluster（默认 FailoverClusterInvoker）
  │    ├─ Directory.list() → 拿可用 Invoker 列表
  │    ├─ Router 链过滤（如 ip 路由、同机房优先）
  │    └─ LoadBalance 选中一个 Invoker（默认 Random）
  │
  ├─ Protocol 客户端（DubboInvoker）
  │    ├─ 默认异步发送：当前 Invoker 占用计数 +1（配合 LeastActive）
  │    └─ Netty Client → 长连接写出（16 字节协议头 + hessian2 body）
  │                                     ──────────────────────────►
  │                                                Netty Server IO 线程解码
  │                                                  │
  │                                            Dispatcher 派发到业务线程池
  │                                                  │
  │                                            Handler 定位 Exporter
  │                                                  │
  │                                            反射调用实现类方法
  │                                                  │
  │         id 配对异步响应 ◄────────────  结果 hessian2 序列化回写
  │
  ├─ DefaultFuture：按请求 id 匹配 Response（2.7+ 可直接 CompletableFuture）
  └─ 反序列化结果 → 返回给业务代码
```

> 面试话术：**「代理接住调用 → 集群容错选机器 → 协议序列化 → Netty 发送 → 服务端线程池反射执行 → id 配对异步回包」**，一条链说清。

## 五、Dubbo3 的关键升级：应用级服务发现（高频新考点）

| 对比 | Dubbo 2.x 接口级 | Dubbo 3.x 应用级 |
|:---|:---|:---|
| 注册中心存什么 | **每个接口**一条注册数据（接口级 URL） | **每个应用实例**一条（ip:port + 元数据） |
| 数据规模 | 接口数 × 实例数，万级应用时推送风暴 | 与实例数线性相关，**数量级下降** |
| 接口 → 应用映射 | 注册中心天然携带 | 存到**元数据中心**，消费端本地查 |
| 兼容性 | — | 双注册双订阅平滑迁移 |

一句话：**「接口级发现是把路由表放注册中心，应用级发现是把路由表移到消费端 + 元数据中心」**——解决云原生时代注册中心存储与推送压力。

## 六、Dubbo vs Spring Cloud vs gRPC（选型对比）

| 维度 | Dubbo | Spring Cloud | gRPC |
|:---|:---|:---|:---|
| 定位 | 高性能 RPC + 服务治理全家桶 | 微服务全家桶（HTTP 生态） | 高性能跨语言 RPC |
| 通信 | 默认 TCP 长连接 + hessian2 | HTTP/1.1 REST（Feign） | HTTP/2 + protobuf |
| 性能 | 高 | 一般（HTTP 开销） | 高 |
| 跨语言 | 弱（多语言客户端有限） | 弱 | **强** |
| 服务治理 | 内置（容错/路由/动态配置） | 依赖组件拼装（Ribbon/Hystrix 等） | 无，需搭配其他框架 |
| 社区/生态 | 国内微服务主流之一 | 国际主流 | CNCF 主推 |

> 选型话术：内部 Java 技术栈 + 高并发内网调用选 Dubbo；跨语言或对外 API 选 gRPC/REST；需要完整 Spring 生态整合选 Spring Cloud。

## 易错点

1. **Invoker ≠ 实现类对象**：它是「可执行抽象」，消费端是远程 Invoker，服务端是包装实现类的 AbstractProxyInvoker——一句话讲清才算懂 Dubbo 模型。
2. **Cluster 层是「伪装」**：`ClusterInvoker` 把整个集群伪装成一个 Invoker，所以上层 Proxy 感知不到多机器。
3. **Dubbo3 的应用级发现不是「不注册接口」**：接口与应用映射移到了元数据中心，别答成「不再需要元数据」。
4. **暴露 ≠ 注册**：先 `export`（起 Netty Server）再 `register`（写注册中心），顺序反了会出现「注册中心有、服务不可用」的窗口。

---

## 一句话总结

**Dubbo = 分层 SPI 架构 + Invoker 核心模型 + 一切皆 URL**：服务暴露是「起服务 + 写注册中心」，调用是「代理 → 集群选机器 → 协议 → Netty → 线程池反射」，Dubbo3 用应用级服务发现解决云原生下的注册中心膨胀。
