# 通信协议与线程模型

「dubbo 协议为什么要设计成单一长连接？」「请求和响应怎么对上的？」「IO 线程和业务线程怎么分工？」——这一篇覆盖 RPC 通信层全部高频题：协议设计、Netty 线程模型、Dispatcher 派发、序列化选型。

---

## 一、dubbo 协议：为什么是「单一长连接 + NIO」（必考）

| 特性 | 设计 | 原因 |
|:---|:---|:---|
| **单一长连接** | Consumer 与每个 Provider 默认**一条 TCP 长连接**（可配 connections 扩展） | 小数据量大并发的内网 RPC：省去握手开销，复用连接 |
| **异步 NIO** | Netty 事件驱动，请求不阻塞线程 | 一条连接支撑高 QPS（靠请求 id 异步配对，见下） |
| **适合小报文** | 默认报文上限 8MB | 传大文件/大 list 会挤占连接，拖慢所有请求 |

> 经典追问「为什么不用短连接？」——TCP 三次握手 + 慢启动的开销在内网高频调用下不可接受；「为什么连接数少反而快？」——线程/句柄/上下文切换省资源，NIO 让一条连接跑出高并发。

### 协议头 16 字节（能画出来就是加分）

```
 0 ─ 15bit   Magic（0xdabb，识别 dubbo 协议）
16 ─ 23bit   Flag：请求/响应、是否事件、序列化类型 id
24 ─ 31bit   Response 状态码（20=OK）
32 ─ 95bit   请求 id（8 字节 long）★ 异步配对的关键
96 ─127bit   body 长度（4 字节）
─────────────
 body：hessian2 序列化的 DubboInvocation（方法名/参数类型/实参/attachments）
```

**粘包/拆包怎么解**：定长头部里的 body 长度 → Netty `LengthFieldBasedFrameDecoder` 按长度切帧，无粘包问题。

## 二、请求 id 与异步转同步（本篇最核心的原理题）

```
Consumer 线程                              Netty IO 线程
   │ 发请求：Request{id=100}
   ├─ 创建 DefaultFuture（静态 ConcurrentHashMap<Long, Future>）
   ├─ future.get(timeout) 挂起等待 ─┐
   │                                │        Netty 收到 Response{id=100}
   │                                │        ├─ 按 id 从 Map 找到 Future
   │                                │        └─ future.complete(result)
   ├─ get() 醒来，拿到结果 ◄─────────┘
   └─ 业务线程没被网络阻塞过（等待由 JUC Condition 实现，不占 IO 线程）
```

- **单连接多并发**的本质：靠 8 字节请求 id 把「异步网络收发」和「同步业务等待」解耦。
- Dubbo 2.7+ 直接暴露 `CompletableFutureRpcContext`，支持原生异步调用。

## 三、线程模型：IO 线程 vs 业务线程池（必考）

```
Provider 端
  Netty EventLoopGroup（boss 1 + worker CPU核数）      ← IO 线程：只做编解码
        │ 解码出 Request
        ▼
  Dispatcher 线程派发策略（SPI 扩展点）
        ├─ all（默认）：全部请求派发到 DubboServerHandler 线程池
        ├─ message：只有请求/响应派发，连接事件留在 IO 线程
        ├─ direct：全在 IO 线程执行（业务重了会阻塞 IO，禁用）
        ├─ execution：只有请求派发，响应在 IO 线程
        └─ connection：连接事件派发，其余 IO 线程
        ▼
  业务线程池（默认 fixed，200 线程 + SynchronousQueue 队列）
        └─ Handler 定位 Exporter → 反射调用实现类
```

| 考点 | 答案 |
|:---|:---|
| 默认线程池类型 | `fixed`：200 线程 + **SynchronousQueue**（不排队，满了直接抛拒绝 → 快速失败暴露问题） |
| 为什么 IO 线程不放业务 | 业务慢会阻塞 EventLoop，**同 EventLoop 上所有连接全部卡死** |
| IO 线程做什么 | 编解码 + 心跳 + 建连断连（默认 `all` 策略下连事件也派发出去） |
| 线程池打满现象 | `Thread pool is EXHAUSTED` 日志；排查下游慢调用/超时设置过大 |

## 四、序列化选型（对比题）

| 序列化 | 特点 | 状态 |
|:---|:---|:---|
| **hessian2**（默认） | 自描述、跨语言、性能与体积均衡 | Dubbo 传统默认 |
| Kryo / FST | Java 专用，更快更小 | 需注册类，性能敏感场景 |
| Protobuf | 强 schema、体积最小、跨语言最好 | gRPC 标配；Dubbo3 Triple 协议 |
| JDK 序列化 | 慢、体积大、**反序列化漏洞多** | 被禁用，面试说出「不安全」是加分 |

> 追问「为什么 body 用 hessian2 而不用 JDK 序列化」：JDK 序列化要求实现 Serializable、记录类元数据体积膨胀、性能差、历史漏洞（反序列化 RCE）频出。

## 五、协议扩展与 Dubbo3 Triple

| 协议 | 场景 |
|:---|:---|
| `dubbo`（默认） | 内网 Java 高并发 RPC |
| `rest` | 对外 HTTP API / 跨语言 |
| `hessian` / `rmi` / `webservice` | 兼容遗留系统 |
| **triple（Dubbo3）** | 基于 HTTP/2 + Protobuf，兼容 gRPC，支持流式（客户端/服务端/双向流） |

> Dubbo3 迁移话术：`dubbo` 协议解决内部性能，`triple` 解决云原生跨语言与网关穿透（HTTP/2 天然过 LB），两者共存由 URL 驱动选择。

## 易错点

1. **「单一长连接」是每个 Provider 一条**，不是全局一条：消费端对 10 台 Provider 是 10 条连接；`connections=N` 可每机多条（配合多 IO 线程）。
2. **业务等待不占 IO 线程**：`future.get` 挂起的是调用线程（如 DubboClientHandler 或业务线程），别答「阻塞 Netty worker」。
3. **默认线程池队列是 SynchronousQueue**：没有排队缓冲，打满立刻拒绝——这是设计而非缺陷（快速失败），对比 JVM 笔记里 `Executors.newFixedThreadPool` 的无界队列陷阱。
4. **Provider 拒绝 ≠ Consumer 失败**：线程池满抛的异常会以错误响应回传，Failover 会换机器重试，放大效应要心里有数。
5. **报文上限 8MB**：大对象传输先分页/压缩，别改协议默认值硬扛。

---

## 一句话总结

**dubbo 协议 = 单一长连接 + NIO + 16 字节定长头**：靠请求 id 实现异步配对（单连接撑高并发），靠 body 长度解决粘包；线程模型「IO 线程只编解码 + Dispatcher 派发 + fixed 业务线程池快速失败」；序列化默认 hessian2，Dubbo3 用 triple（HTTP/2 + protobuf）拥抱云原生。
