# 集群容错与负载均衡

一次远程调用前，Cluster 层要完成「**拿列表 → 路由过滤 → 负载均衡选一个 → 失败了怎么办**」。容错策略与负载均衡是 Dubbo 面试的高频对比题，超时重试与 Mock 降级是生产事故复盘的常客。

---

## 一、Cluster 调用链（先立框架）

```
ClusterInvoker（伪装成一个 Invoker）
  │
  ├─ Directory.list()        动态 Invoker 列表（实时推送刷新）
  ├─ Router 链过滤           脚本路由/标签灰度/同机房优先/黑白名单
  ├─ LoadBalance 选择        从候选中选 1 个（Forking 选 N 个）
  │
  └─ invoke → 失败？→ 按容错策略：换机重试 / 快速抛错 / 忽略 / 并行…
```

---

## 二、六大集群容错策略（必背表格）

| 策略 | 行为 | 适用场景 | 关键参数 |
|:---|:---|:---|:---|
| **Failover**（默认） | 失败**换一台**重试，默认 `retries=2`（共 3 次） | **幂等读操作**；重试带来更长响应时间 | `retries`、`cluster=failover` |
| **Failfast** | 只发起一次，失败**立即抛异常** | **非幂等写操作**（新增记录），重试会重复插入 | — |
| **Failsafe** | 失败**忽略**，仅记日志 | 写审计日志等旁路操作，失败无伤大雅 | — |
| **Failback** | 失败**定时重发**（后台任务） | 消息通知类，允许最终成功 | `failbackTasks` |
| **Forking** | **并行调多个**服务器，取最快返回 | 实时性要求高、读操作，浪费更多资源 | `forks=2` |
| **Broadcast** | 逐个**全部调一遍**，任一台异常则报错 | 通知所有节点更新缓存/日志 | — |

> 面试话术：**「读用 Failover 换机重试，写用 Failfast 防重复，旁路用 Failsafe，通知用 Broadcast，追求极速用 Forking」**——按场景反推策略，比干背六名词高一个档次。

## 三、四种负载均衡（必背 + 加分原理）

| 算法 | 原理 | 加权细节 | 适用 |
|:---|:---|:---|:---|
| **Random**（默认） | 按权重随机 | 权重越大命中概率越高；「按权重随机」收敛后即权重分布 | 通用首选，无需状态 |
| **RoundRobin** | 加权平滑轮询 | **平滑加权**（Nginx 同款）：避免 「a a a b b c」 的瞬时密集，输出 「a b a c b a」 | 请求需均匀摊开 |
| **LeastActive** | 选中**活跃数最少**的 Invoker（活跃数=发起未返回的请求数） | 活跃数相同再按权重随机 | **慢机器自动少接活**，性能差异大的集群 |
| **ConsistentHash** | 哈希环 + 虚拟节点（默认 160 个/节点） | 默认**只用第一个参数**做 hash | 同一请求始终落同一机器（有状态/缓存亲和） |

**LeastActive 的底层配合**：`RpcStatus.beginCount/endCount` 维护每台机器的并发计数——发起 +1、返回 -1。这也是「自适应负载均衡」的思想雏形。

**ConsistentHash 追问链**：
1. 为什么虚拟节点？→ 节点少时哈希环分布不均，虚拟节点让负载更均匀；
2. 为什么默认取第一参数？→ 参数复用对象 hash 不稳定，第一参数通常是业务主键；
3. 节点宕机流量会怎样？→ 只迁移到相邻节点，其余映射不变（这是相对取模的最大优势）。

## 四、超时与重试：生产事故第一现场（必考）

```
默认：timeout = 1000ms，retries = 2（Failover 下总共最多 3 次请求）
```

| 坑 | 现象 | 正确姿势 |
|:---|:---|:---|
| **超时小于接口真实耗时** | 1s 超时 + 2 次重试 = **同一写操作被执行 3 次**，库存多扣、订单重复 | 写接口 `retries=0` 或保证幂等（唯一键/状态机） |
| 重试放大故障 | 下游已过载，重试流量翻三倍 → 雪崩 | 重试要配**限流/熔断**（Sentinel），或退避 |
| timeout 设置随意 | 消费方设 10s，把下游线程池挂死 | Provider 侧明确声明合理 timeout（配置优先级 Provider 优先） |
| 长任务 + Failover | 报表类 30s 任务超时后重试，服务器上同时跑多份 | 长任务异步化 / `cluster=failfast` |

> **幂等设计三件套**：数据库唯一键兜底、状态机校验、token 去重——面试把「重试必配幂等」讲成条件反射。

## 五、Mock 与服务降级

| 手段 | 配置 | 行为 |
|:---|:---|:---|
| **Mock 降级** | `mock=fail:return null` | 失败后返回兜底值；`force:return` 强制降级（踢掉熔断测试） |
| 本地伪装类 | 接口名 + `Mock` 后缀类（`UserServiceMock`） | 失败走自定义逻辑（如返回默认推荐列表） |
| 屏蔽/容错 | Dubbo Admin 动态下发 | `override://` 协议动态改 URL，不重启生效 |
| 直连 | `url=dubbo://ip:port` | 绕过注册中心直连，联调用 |

配合限流熔断（Sentinel/Dubbo Filter）构成完整的**服务自愈**方案：**超时→重试→熔断→降级→告警**。

## 六、优雅上下线与灰度（服务治理补充）

- **优雅停机**：先从注册中心反注册 → 等 `shutdown.timeout` 让在途请求跑完 → 关 Netty Server（`kill` 触发 QUIT 信号）。
- **标签路由**：`tag=vip` 的消费端只调同 tag 的 Provider（金丝雀发布）；无 tag 的回落 `force=false` 默认组。
- **条件路由**：`host = 10.20.* => host = 10.30.*` 读写分离式引流，动态下发。

---

## 易错点

1. **retries 是「额外重试次数」**：默认 2 表示最多请求 3 次，答成「总共 2 次」直接露馅。
2. **Failover 重试不保证负载均衡参与**：重试会跳过已失败节点，但不重跑 Router 全链（行为按版本有差异，别把细节说死）。
3. **LeastActive 不是「响应时间最少」**：是「正在处理中的请求数最少」，别混入 RT 概念。
4. **ConsistentHash 默认哈希第一参数**：参数是对象时 hash 不稳定，要指定 `hash.arguments`。
5. **Mock 的 `force` 与 `fail` 区别**：force 强制走 Mock（不看结果），fail 失败才走。

---

## 一句话总结

**Cluster = Directory（活列表）+ Router（过滤）+ LoadBalance（选机器）+ 容错策略（失败善后）**：读 Failover、写 Failfast、旁路 Failsafe、极速 Forking；负载均衡默认 Random 加权，LeastActive 让慢机少干活，一致性哈希做亲和；**重试必须配幂等**，Mock + 动态配置构成降级逃生门。
