**3、增加get\_candidates方法**

  

增加 get\_candidates 的核心原因是解决审核修复循环中上下文压缩导致候选数据丢失的问题。尤其是在review过后，需要重新规划的时候，需要让LLM感知到这些备选方案，这样模型才能更好的基于审核建议做优化。

  

在多维审核架构中，Plan Agent 需要多轮修复审核不通过的方案。但使我们因为用了搜索结果自动持久化的方案，所以导致LLM其实并不知道具体的航班/火车/酒店候选。所以我们需要提供一个方法可以供LLM调用来获取这些备选项。

  

LLM在拿到审核意见和备选项之后，会根据意见重新给这些备选项打分，进而影响最终的方案设计结果。

  

**4、舱位/席别等级比较 Bug 修复**

  

数据库 schema 中 flight\_class / train\_seat\_class 字段表示的是允许的最高舱位等级（≤ 关系），即政策允许"头等舱"时，坐"经济舱"也应合规。

但原代码用的是字符串匹配，导致低等级舱位被判为不合规：

  

```
// ❌ 旧代码 — 机票：字符串包含匹配if (!policy.getFlightClass().contains(flightClass)) { ... }﻿// ❌ 旧代码 — 火车：精确字符串匹配if (!seatClass.equalsIgnoreCase(policy.getTrainSeatClass())) { ... }
```

  

于是我们新增 CabinRankUtil.java — 舱位等级归一化工具，将各类舱位名称映射为数值等级，用 actual ≤ allowed 判断合规：

  

```
飞机：经济舱/Economy = 1，商务舱/Business = 2，头等舱/First = 3高铁：二等座/Second = 1，一等座 = 2，商务座 = 3
```

  

核心方法 isCabinCompliant(actual, allowedSpec)：

- 将 actual 和 allowed 都转为等级数值
- actualRank <= allowedRank → 合规
- 未知舱位名称 → 回退字符串匹配（向后兼容）

  

**5、增加出行体验分的权重**

  

我们之前的方案设计时，并没有考虑到红眼航班、恶劣天气、通勤时间长、到达时间过晚等影响体验的方案设计。而这些内容其实我们在行程审核的时候也会审核到，这样就会导致多余的审核-修复。如果我们能把这些提前考虑到方案设计中，则可以减少这些问题的发生。

  

于是我定义了ExperienceScorer方法，用来做以下事情：

![](https://cdn.nlark.com/yuque/0/2026/png/5378072/1787060958710-c4519b5b-f7de-4a30-bf6d-4457e7054441.png)

  

```
    /**     * 计算组合的出行体验评分。     */    public double computeScore(JSONObject ob, JSONObject rb, String weatherSummary) {        double score = 100.0;﻿        // 1. 红眼航班惩罚        if (isRedEye(ob)) {            score -= RED_EYE_PENALTY;        }        if (isRedEye(rb)) {            score -= RED_EYE_PENALTY;        }﻿        // 2. 去程到达时间过晚（> 21:00）        LocalDateTime obArr = PlannerUtils.parseDt(PlannerUtils.getStr(ob, "arrival_time"));        if (obArr != null && obArr.getHour() >= LATE_ARRIVAL_HOUR) {            score -= LATE_ARRIVAL_PENALTY;        }﻿        // 3. 返程为当天末班交通（出发时间最晚的候选）——简化判断：返程出发 >= 21:00 且为飞机        LocalDateTime rbDep = PlannerUtils.parseDt(PlannerUtils.getStr(rb, "departure_time"));        if (rbDep != null && rbDep.getHour() >= LATE_ARRIVAL_HOUR && "flight".equals(PlannerUtils.getStr(rb, "type"))) {            score -= LAST_TRANSPORT_PENALTY;        }﻿        // 4. 单程通勤过长        score = applyCommutePenalty(score, PlannerUtils.getInt(ob, "_transit_min"));        score = applyCommutePenalty(score, PlannerUtils.getInt(rb, "_transit_min"));﻿        // 5. 恶劣天气选飞机        if (hasSevereWeather(weatherSummary)) {            if ("flight".equals(PlannerUtils.getStr(ob, "type"))) {                score -= BAD_WEATHER_FLIGHT_PENALTY;            }            if ("flight".equals(PlannerUtils.getStr(rb, "type"))) {                score -= BAD_WEATHER_FLIGHT_PENALTY;            }        }﻿        return PlannerUtils.round2(Math.max(0.0, score));    }﻿
```

  

引入了体验这个新维度之后，我们之前的时间、价格、偏好之外就需要再加一个这个维度，于是我们设计了以下权重：

  

> 偏好 0.40 \> 体验 0.30 \> 时间 0.20 \> 价格 0.10

  

因为出差是为了工作，不是穷游。（当然也可以根据实际情况调整，比如有的公司就想省差旅费）

  

- 偏好最高（0.40）：用户个人喜好（舱位/品牌/时段）是软性需求，权重最大
- 体验第二（0.30）：到达后的精神状态直接影响工作质量，是差旅的核心质量指标
- 时间第三（0.20）：时间重要但不是唯一，不能为了快牺牲健康
- 价格最低（0.10）：差旅费用由公司承担，省钱不应以牺牲体验为代价
