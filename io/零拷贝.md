# 零拷贝

> 「零拷贝」不是没有拷贝，而是**没有 CPU 拷贝**（或没有用户态拷贝）——它是 Kafka、RocketMQ、Netty 高吞吐的共同底牌。

按「**传统 IO 的 4 拷贝 4 切换 → mmap / sendfile 两条优化路 → 谁在用零拷贝 → 零拷贝的边界**」组织，要求能把路径图白板画出来。

---

## 一、传统 IO：read + write 的代价（必背，能画图）

把磁盘文件发到网卡，传统做法是「读文件 + 写 socket」：

```
read()                                          write()
────────────────────────────────────────────────────────────
① DMA 拷贝：   磁盘 ──────► 内核页缓存（PageCache）
② CPU 拷贝：   页缓存 ────► 用户缓冲区      ← 此时用户程序才拿到数据
───────────────────── read 返回，write 开始 ─────────────────
③ CPU 拷贝：   用户缓冲区 ─► Socket 缓冲区
④ DMA 拷贝：   Socket 缓冲区 ► 网卡
────────────────────────────────────────────────────────────
合计：4 次拷贝（2 次 DMA + 2 次 CPU）+ 4 次用户态/内核态上下文切换
```

- read 两次切换（用户→内核→用户），write 再两次，共 **4 次切换**；
- ②③ 两次 **CPU 拷贝**纯粹是「搬运工」，还要占 CPU——这就是优化目标。

---

## 二、三条优化路径

### 1. mmap + write：省一次 CPU 拷贝

`mmap` 把内核页缓存**映射到用户空间**，用户程序直接操作页缓存，跳过「页缓存 → 用户缓冲区」：

| 指标 | 值 |
|:---|:---|
| 上下文切换 | 4 次（read/write 仍在） |
| 拷贝 | **3 次**（1 DMA + 2 CPU） |
| 优点 | 用户态能看见/修改数据 |
| 代价 | 大文件映射开销、缺页中断、映射管理复杂 |

**使用者：RocketMQ**——CommitLog 用 mmap 写消息（读写混合场景）。

### 2. sendfile：全程内核态，真正的「零拷贝」

一次系统调用替代 read+write，数据**不再进出用户空间**：

```
Linux 2.1 sendfile：
① DMA 拷贝：磁盘 → 页缓存
② CPU 拷贝：页缓存 → Socket 缓冲区
③ DMA 拷贝：Socket 缓冲区 → 网卡
   （2 次切换 + 3 次拷贝）

Linux 2.4 + DMA gather：
① DMA 拷贝：磁盘 → 页缓存
② 仅把「fd + 长度」描述符附加到 Socket 缓冲区（数据不搬）
③ DMA 直接从页缓存 → 网卡
   （2 次切换 + 2 次拷贝 + 0 次 CPU 拷贝 ← 这才是「零拷贝」）
```

**限制**：数据不经过用户态 → **不能在用户程序里修改/加密/校验内容**。

### 3. Java 层对应的 API

```java
// sendfile 的 Java 封装：文件 → 网络通道
FileChannel file = FileChannel.open(Paths.get("data.log"), StandardOpenOption.READ);
SocketChannel socket = ...;
file.transferTo(0, file.size(), socket);   // 底层调 sendfile

// mmap 的 Java 封装：文件映射为直接内存
MappedByteBuffer mbb = file.map(FileChannel.MapMode.READ_WRITE, 0, file.size());
mbb.put(0, (byte) 9);                      // 直接读写页缓存
```

Netty 在框架层延续同一思想：

- `FileRegion`：包装 `transferTo` 做文件传输（sendfile）；
- `CompositeByteBuf` / `Unpooled.wrappedBuffer()`：多个 Buffer **逻辑组合**，避免合并时的真实拷贝；
- 堆外直接内存：避免「JVM 堆内 → 堆外」那次拷贝。

## 三、谁在用零拷贝（必背对照表）

| 组件 | 技术 | 场景原因 |
|:---|:---|:---|
| **Kafka** | sendfile（`transferTo`） | 消费者拉日志：整段读整段发，不改数据 |
| **RocketMQ** | mmap | CommitLog 读写混合，需要用户态操作 |
| **Netty** | FileRegion / CompositeByteBuf / 堆外 | 文件传输、协议头+包体逻辑聚合 |
| **Nginx** | `sendfile on;` | 静态文件下发 |

> 面试话术：**「Kafka 快 = 顺序写 + 零拷贝 + 批量 + 页缓存」；零拷贝选型一句话——不改数据用 sendfile，要改数据用 mmap**。

---

## 四、零拷贝的边界（追问防身）

1. 需要在用户态**加密 / 压缩 / 校验 / 改写** → 必须回用户态，sendfile 失效（Kafka 开 SSL 后就用不了零拷贝）；
2. 数据要被**多个消费者分别处理/广播** → sendfile 一条管道直发，不合适；
3. 小文件场景收益有限——切换和拷贝本身开销占比小。

---

## 易错点

1. **零拷贝 ≠ 0 次拷贝**：DMA 拷贝依然存在，零的是 **CPU 拷贝**（更严格说：零用户态拷贝）。
2. **mmap 省的是拷贝不是切换**：mmap+write 仍是 4 次上下文切换，答「省切换」就错了。
3. **「epoll 用 mmap」是错误答案**：epoll 快靠回调 + 就绪链表，与 mmap 无关——两道题别互相污染。
4. **transferTo 的目标只能是 Channel**：不能边发边改内容；要改就老老实实 read 回用户态。
5. **堆外内存泄漏**：Netty Direct Buffer 不受 GC 直接管理，用 `-Dio.netty.leakDetection.level` 排查、`-XX:MaxDirectMemorySize` 限流。

---

## 一句话总结

**传统 IO 4 拷贝 4 切换 → mmap 省一次 CPU 拷贝（RocketMQ）→ sendfile 全程内核态，DMA gather 后 0 次 CPU 拷贝（Kafka/Netty/Nginx）**；选型口诀：数据不改用 sendfile，数据要改用 mmap——所有零拷贝优化的本质都是「让数据别进用户空间瞎折腾」。
