# 异常体系面试题

异常是 Java 的错误处理模型。面试考三块：**体系分类与设计哲学、finally/try-with-resources 的执行语义、工程实践与性能**。

---

## 一、体系结构（先立框架）

```
Throwable
 ├─ Error                 系统级错误，不应捕获
 │    ├─ OutOfMemoryError            堆/元空间耗尽
 │    ├─ StackOverflowError          栈深超限（无限递归）
 │    └─ NoClassDefFoundError        编译期有、运行期缺类（与 ClassNotFoundException 区分）
 └─ Exception
      ├─ RuntimeException (unchecked)  NPE、ClassCastException、IndexOutOfBounds、
      │                                ArithmeticException、IllegalStateException…
      └─ 受检异常 (checked)            IOException、SQLException、ClassNotFoundException、
                                       InterruptedException…
```

| 对比 | checked | unchecked |
|:---|:---|:---|
| 编译器 | 强制 try/catch 或 throws 声明 | 不强制 |
| 设计意图 | **可恢复**的外部故障（文件缺失、网络失败） | **编程 bug**（空指针、越界），改代码而非捕获 |
| 典型争议 | lambda 与 Stream 中书写繁琐；调用链层层声明污染签名 | 容易被悄悄吞掉 |

> 追问「为什么 Java 有 checked 异常而 C#/Kotlin 没有」：答「强制显式处理外调用失败 vs 签名污染的取舍」，再落到工程实践——**业务代码内部异常多转 unchecked + 全局处理器**。

## 二、finally 的执行语义（必考细节题）

### finally 一定执行吗？

不。以下情况不执行：`System.exit()`、JVM 崩溃、当前线程被杀死、finally 前无限循环。

### 两个经典代码题

```java
// ① finally 中 return：覆盖 try 的返回值（反模式，别写）
static int f() {
    try { return 1; }
    finally { return 2; }   // 返回 2，try 的 return 1 被丢弃
}

// ② finally 修改返回变量：基本类型改的是「已拷贝的副本」，无效
static int g() {
    int x = 1;
    try { return x; }        // 返回值在 return 时已拷贝到操作数栈
    finally { x = 99; }      // 改局部变量 x，不影响返回值 → 仍返回 1
}
static StringBuilder h() {
    StringBuilder sb = new StringBuilder("a");
    try { return sb; }
    finally { sb.append("b"); }  // 引用类型：内容可变 → 返回 "ab"
}
```

> 原理一句话：**return 时先把返回值压栈暂存**，finally 改局部变量改不到已暂存的值；但引用指向的对象内容仍可变。

### try-with-resources（JDK 7+，标准答案）

```java
try (var in = new FileInputStream(src);
     var out = new FileOutputStream(dst)) {   // 实现了 AutoCloseable
    in.transferTo(out);
}
// ① 自动按声明逆序 close；② 编译器生成抑制异常逻辑
// ③ close 抛的异常不会吞掉业务异常，挂在主异常的 suppressed：
catch (Exception e) { for (Throwable t : e.getSuppressed()) ... }
```

对比手写 finally 关闭：不用嵌套判空、不丢主异常、代码减半——**面试答 finally 关流直接判定过时**。

## 三、异常与性能（区分度考点）

| 点 | 说明 |
|:---|:---|
| 构造成本 | `new Exception` 会 **fillInStackTrace**（抓全栈，微秒级）；高频路径禁用异常控流程 |
| 优化 | 覆写 `fillInStackTrace()` 返回 this 可省栈（如 Netty 内部信号异常），但堆栈失真需权衡 |
| 捕获范围 | catch 具体异常优于 Throwable；**catch 里别再抛原始异常给上层循环重试** |
| 异常日志 | 捕获后**必须处理或带上下文重抛**；`e.printStackTrace()` 到 stdout 等于没记 |
| 抛谁的异常 | 接口声明受检异常 = 对实现方的强约束，优先业务异常体系 + 全局处理（Spring `@RestControllerAdvice`） |

### 异常链（保留根因）

```java
catch (IOException e) {
    throw new ServiceException("订单导出失败", e);   // 传 e 保留 cause，别 new 完不带根因
}
```

## 易错点

| 坑 | 说明 |
|:---|:---|
| finally 写 return | 覆盖返回值 + 吞异常，IDE 直接告警 |
| catch 后什么都不做 | 异常被吞，线上排查灾难 |
| `finally { return }` 吞掉 try 里抛出的异常 | 异常被 return 取代，直接丢失 |
| NoClassDefFoundError vs ClassNotFoundException | 前者是 Error（运行期类缺失/初始化失败），后者是 checked Exception（反射按名加载失败） |
| 用异常做业务分支 | 性能差 + 可读性差（如靠 NumberFormatException 判断是否数字） |
| 多 catch 的继承顺序 | 子类在前父类在后，父类在前编译不过（unreachable） |

---

## 一句话总结

**Error 不接、runtime 不声明、受检要显式**；finally 除 JVM 退出外必执行但**改不了已暂存的基本类型返回值**；资源关闭标准答案是 try-with-resources（逆序关闭 + suppressed 异常）；异常的性能成本在**构造时的全栈抓取**，高频路径别拿异常当流程控制。
