## 二、逐题详解

### Q1：LinkedBlockingQueue vs ArrayBlockingQueue vs SynchronousQueue，在线程池里用哪个？

**先看在线程池任务队列中的行为差异**（关键在于「队列满没满」直接影响线程池是走入队还是走扩线程）：

| 队列 | 容量 | 线程池行为 | 典型场景 |
|:---|:---|:---|:---|
| **ArrayBlockingQueue** | 有界，构造时指定 | 队列满 → 扩最大线程数 → 拒绝 | 已知任务量上限、需要精确限流 |
| **LinkedBlockingQueue** | 默认 `Integer.MAX_VALUE`（≈无界） | 队列**永远不满** → 最大线程数**永远用不上** → 永不拒绝但可能 OOM | Executors 三个工厂方法都用它，但**阿里规约禁用** |
| **SynchronousQueue** | 容量 0（不存任务，直接交给线程） | 有任务立即找核心线程，核心满了**直接扩最大线程**，不进队列 | `newCachedThreadPool` 用它，适合短生命周期、数量不确定的任务 |

**选型核心矛盾**：队列越大 → 线程越不容易扩（大量任务堆积在队列里等少数核心线程慢慢处理）→ 延迟变高但线程数少；队列越小 → 线程越容易扩 → 并发高但线程数多（上下文切换开销）。

| 场景 | 推荐队列 | 理由 |
|:---|:---|:---|
| **固定并发 IO 任务**（如固定 100 个 DB 查询） | `ArrayBlockingQueue`（容量略大于并发数） | 队列有界保证不会 OOM；核心线程数顶得住就不扩 |
| **短生命周期、数量波动大的任务**（如 HTTP 请求） | `SynchronousQueue` + 合理的最大线程数 | 直接转线程处理，低延迟；最大线程数不能设 `MAX_VALUE`（`newCachedThreadPool` 坑点） |
| **CPU 密集任务** | `ArrayBlockingQueue`（小容量）+ 核心=最大=N<sub>cpu</sub>+1 | CPU 密集不需要太多线程，核心=最大意味着队列满就拒绝，不扩线程 |

> **阿里规约精神**：**队列必须有界**，最大线程数要合理，拒绝策略要明确。`newFixedThreadPool` 用无界队列 → OOM；`newCachedThreadPool` 用 `MAX_VALUE` 最大线程 → 线程爆炸。正确做法是 `new ThreadPoolExecutor(core, max, keepAlive, N, ArrayBQ(有界), 命名工厂, 明确拒绝策略)`。

### Q2：生产上线程池核心参数怎么定？IO 密集和 CPU 密集的经验值？

**先记公式，再谈经验**：

\[
N_{threads} = N_{cpu} \times U_{cpu} \times (1 + \frac{W}{C})
\]

- \(N_{cpu}\)：CPU 核数，`Runtime.getRuntime().availableProcessors()`
- \(U_{cpu}\)：目标 CPU 使用率（0~1，通常 0.8）
- \(W/C\)：等待时间 / 计算时间（IO 密集 ≫ 1，CPU 密集 ≈ 0）

**经验值速查表**：

| 任务类型 | W/C 比 | 核心线程数 | 最大线程数 | 队列 |
|:---|:---|:---|:---|:---|
| **CPU 密集**（计算、加密、视频编解码） | ≈ 0 | \(N_{cpu} + 1\) | = core（不扩） | 小容量 ArrayBQ |
| **IO 密集**（DB/RPC/文件操作） | 5~10 | \(N_{cpu} \times (1 + W/C)\) ≈ 2×~5× \(N_{cpu}\) | = core 或略大 | 有界 ArrayBQ |
| **混合型** | 2~5 | 按 IO 密集算 | 按 IO 密集算 | 有界 ArrayBQ |

**关键参数避坑**：

| 参数 | 避坑 |
|:---|:---|
| **corePoolSize** | 生产上通常设为 2~5 倍 N<sub>cpu</sub>；核心线程默认不销毁（allowCoreThreadTimeOut=false） |
| **maximumPoolSize** | IO 密集可设得比 core 大（2~3 倍），CPU 密集建议 = core（不扩） |
| **keepAliveTime** | 非核心线程空闲存活时间，IO 密集建议 60s（避免频繁创建销毁） |
| **allowCoreThreadTimeOut** | **默认 false**，核心线程永不超时销毁；低负载场景可开 true 省资源 |

> **生产实战**：参数不是一次定死的——先用经验值 + 监控指标（活跃线程数、队列堆积、任务耗时）反馈调整，大促前压测迭代。

### Q3：线程池能动态调参吗？哪些参数能热更新？哪些不能？

**ThreadPoolExecutor 提供了运行时热更新的方法**：

| 参数 | 热更方法 | 效果 | 注意 |
|:---|:---|:---|:---|
| **corePoolSize** | `setCorePoolSize(int)` | 立即生效：若新值 > 当前核心数，会立刻补建新线程；若 <，空闲核心线程会等 keepAliveTime 后销毁 | 不能设为 0（除非同时开了 allowCoreThreadTimeOut） |
| **maximumPoolSize** | `setMaximumPoolSize(int)` | 立即生效：设小了，如果当前线程数 > 新 max，多余的空闲线程会被回收 | 设小了会触发拒绝（如果队列也满） |
| **keepAliveTime** | `setKeepAliveTime(long, TimeUnit)` | 立即生效，影响所有线程的空闲超时 | — |
| **allowCoreThreadTimeOut** | `allowCoreThreadTimeOut(boolean)` | 立即生效 | — |
| **handler（拒绝策略）** | `setRejectedExecutionHandler(RejectedExecutionHandler)` | 立即生效 | — |
| **threadFactory** | `setThreadFactory(ThreadFactory)` | 只影响**新创建的线程**，已有线程的名字/守护状态不变 | — |
| **workQueue（任务队列）** | ❌ 没有 setter | **不能运行时替换队列** | 想换队列只能重建线程池 |

> **动态线程池框架**：携程的 `dynamic-tp`、美团的 `ttl-thread-pool` 在原生热更之上加了 Nacos 配置中心 + 监控指标自动反馈，参数可在运行时从配置中心推送变更，大促前可临时扩容核心线程数。

### Q4：怎么监控线程池健康？核心告警指标有哪些？

**ThreadPoolExecutor 内置了一堆 getter 方法**，直接打指标就能用：

| 指标 | getter | 含义 | 告警阈值建议 |
|:---|:---|:---|:---|
| **活跃线程数** | `getActiveCount()` | 正在执行任务的线程数 | > corePoolSize × 0.8 且持续 5min → 可能要扩容 |
| **已完成任务数** | `getCompletedTaskCount()` | 累计完成 | 趋势性下降 + 活跃线程高 → 线程泄漏或任务卡住 |
| **总任务数** | `getTaskCount()` | 累计提交 | — |
| **队列长度** | `getQueue().size()` | 当前排队任务数 | 队列满 + 拒绝次数 > 0 → 必须介入 |
| **队列容量** | `getQueue().remainingCapacity()` | 剩余容量 | — |
| **当前线程数** | `getPoolSize()` | 池内线程总数（核心+非核心） | > maximumPoolSize 是 bug |
| **拒绝次数** | 需要自实现 | 调用次数/时间窗口内 | **任何拒绝都该告警**（说明参数不够或任务堆积） |

**拒绝次数怎么统计**：自定义 `RejectedExecutionHandler`，在 `rejectedExecution` 里打 Counter 指标：

```java
public class MonitoredRejectedHandler implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        Metrics.counter("threadpool.rejected", "pool", executor.toString()).increment();
        // 可选：记录详细参数、告警、或降级处理
        throw new RejectedExecutionException("Task rejected");
    }
}
```

**Spring Boot Actuator 集成**：注册 `ThreadPoolTaskExecutor` 为 Bean 后，Actuator 自动暴露 `thread.pool.executor.active` / `thread.pool.executor.queue.size` / `thread.pool.executor.completed` 等 Micrometer 指标，Grafana 画个面板就能实时看。

### Q5：Spring Boot @Async 用的是什么线程池？有哪些坑？

**默认是 `SimpleAsyncTaskExecutor`——它不是真的线程池，而是每次提交都 `new Thread()`！**

```java
// Spring Boot 2.x 的默认行为
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {
    // 如果不重写 getAsyncExecutor()，Spring Boot 用 SimpleAsyncTaskExecutor
    // 这货内部是 ThreadPoolTaskExecutor，默认核心线程数 = 1，队列无界（LinkedBlockingQueue）
}
```

| 版本 | 默认实现 | 核心问题 |
|:---|:---|:---|
| Spring Boot 1.x | `SimpleAsyncTaskExecutor` | 每次 `new Thread()` → 线程爆炸 |
| Spring Boot 2.x+ | `ThreadPoolTaskExecutor`（自动配置） | 默认核心=8、队列无界 → 任务堆积 OOM |

**正确配置**（生产必做）：

```java
@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean("bizExecutor")
    public ThreadPoolTaskExecutor bizExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(200);          // 有界队列！
        executor.setKeepAliveSeconds(60);
        executor.setThreadNamePrefix("biz-async-");  // 命名！日志里能看到
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.setWaitForTasksToCompleteOnShutdown(true);  // 优雅关闭
        executor.setAwaitTerminationSeconds(60);
        executor.initialize();
        return executor;
    }
}

// 使用时指定线程池
@Async("bizExecutor")
public void sendEmail(long userId) { ... }
```

**其他 @Async 坑**：

| 坑 | 原因 | 解法 |
|:---|:---|:---|
| **自调用不生效** | `this.sendEmail()` 绕过 Spring AOP 代理 | 注入自身 Bean 或 `AopContext.currentProxy()` |
| **void 返回值吞异常** | 异常在线程池子线程里抛，主线程看不到 | 改 `CompletableFuture` 返回值 + `exceptionally()` 处理 |
| **Transaction 失效** | @Async 开新线程，事务上下文不传播 | `@TransactionalEventListener(phase = AFTER_COMMIT)` 或手动传 TransactionTemplate |

### Q6：ForkJoinPool vs ThreadPoolExecutor 怎么选？

| 维度 | ForkJoinPool | ThreadPoolExecutor |
|:---|:---|:---|
| **设计目标** | 并行分治任务（递归拆分子任务并行执行） | 通用任务（IO/RPC/定时） |
| **核心机制** | Work-Stealing：空闲线程从忙碌线程的**双端队列尾部**偷任务 | 单队列共享，所有线程从同一个队列取 |
| **适用任务** | CPU 密集 + 可拆分（归并排序、并行流、`CompletableFuture`） | IO 密集 + 任务独立（HTTP 请求、DB 查询） |
| **默认线程数** | CPU 核数 | 自定义 |
| **嵌套提交** | 支持：子任务 `fork()` + `join()`，比 `submit` 更高效 | 嵌套 submit 可能导致死锁（外层等内层，内层等外层线程空闲） |
| **CompletableFuture** | `ForkJoinPool.commonPool()` 是默认线程池 | 可通过 `thenApplyAsync(..., customPool)` 切换 |

**选型口诀**：
- **任务可以递归拆分、CPU 密集** → ForkJoinPool（并行流、归并排序）；
- **任务独立、IO 密集** → ThreadPoolExecutor；
- **CompletableFuture** 默认走 commonPool，IO 任务**一定要传自定义 ThreadPoolExecutor**，不然 commonPool 被 IO 阻塞后整个 JVM 里所有并行流都慢。

### Q7：什么是线程池隔离（舱壁模式）？怎么做？

**问题**：一个 JVM 里所有业务共用一个线程池 → 某个业务任务堆积把队列填满 → 其他业务也被拒绝 → **故障扩散**。

**舱壁模式（Bulkhead Pattern）**：不同业务用**独立的线程池 + 独立的队列容量**，一个业务炸了不影响其他。

```
┌─────────────────────────────────────────────┐
│                 JVM                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ 订单线程池 │  │ 支付线程池 │  │ 通知线程池 │   │
│  │ core=8   │  │ core=4   │  │ core=2   │   │
│  │ max=16   │  │ max=8    │  │ max=4    │   │
│  │ queue=50 │  │ queue=20 │  │ queue=10 │   │
│  └──────────┘  └──────────┘  └──────────┘   │
│                                               │
│  订单池炸了 → 队列满 → 拒绝订单                │
│  支付/通知池正常工作 ✅                         │
└─────────────────────────────────────────────┘
```

**实现要点**：
1. **每个线程池独立配置**：core/max/queue/拒绝策略按业务重要性定；
2. **拒绝策略差异化**：核心业务（订单）用 `CallerRunsPolicy`（降级但不丢），非核心（通知）用 `DiscardOldestPolicy`（丢旧的保新的）；
3. **监控隔离**：每个线程池打独立的监控指标，告警互不干扰；
4. **线程数总量控制**：隔离后每个池的 max 加起来可能超 CPU 核数太多 → 全局限流（Sentinel）或容器级资源限制。

### Q8：线程池任务堆积 OOM 怎么排查和预防？

**典型现场**：线上报 OOM → jmap dump → 堆里大量 `TaskQueue`（LinkedBlockingQueue 的 Node 对象）→ 队列里堆了几万/几十万个 Runnable 任务，每个任务还持有业务对象引用 → GC Root 无法回收。

**根因链**：

```
任务提交速度 > 任务消费速度
  │
  ├─ 队列是 LinkedBlockingQueue（无界）→ 永不拒绝，越堆越多
  │
  └─ 消费慢：核心线程数不够 / 任务耗时暴涨（DB 慢查询 / RPC 超时）
```

**排查步骤**：

```
① 看监控：队列长度 getQueue().size() 是否持续增长？活跃线程数 getActiveCount() 是否接近 maxPoolSize？
② jstack：线程池线程是否全部 WAITING（等锁/等 RPC 响应）？还是 RUNNABLE（忙不过来）？
③ 看任务耗时：P99 耗时是否突然跳涨？（通常是 DB/RPC 超时导致任务卡住，线程被占住释放不出来）
④ dump 堆：队列里的 Runnable 持有什么大对象？
```

**预防清单**：

| 预防手段 | 做法 |
|:---|:---|
| **队列必须有界** | `ArrayBlockingQueue` + 合理容量，永不 `LinkedBlockingQueue` |
| **拒绝策略要明确** | 核心业务用 `CallerRunsPolicy`（降级），非核心用丢弃策略 |
| **任务超时控制** | `Future.get(timeout)` + 取消；RPC 客户端设超时；DB 设 statement_timeout |
| **监控告警** | 队列长度 / 拒绝次数 / P99 任务耗时 |
| **动态调参** | 接入 dynamic-tp，大促前临时扩容 |
| **线程池隔离** | 舱壁模式，一个业务炸不拖全局 |

### Q9：线程池 submit 后调用 get() 超时，线程池会怎样？

```java
Future<?> future = executor.submit(() -> {
    Thread.sleep(10000);
    return "done";
});
try {
    future.get(1, TimeUnit.SECONDS);   // 超时
} catch (TimeoutException e) {
    // 超时后线程池还在跑那个任务！
    future.cancel(true);                // ★ 必须主动 cancel，传 true 会 interrupt 执行线程
}
```

**三个关键细节**：

| 问题 | 答案 |
|:---|:---|
| get() 超时后任务还在跑吗？ | **是的**，`TimeoutException` 只是客户端等不及了，线程池那边任务继续执行 |
| cancel(true) 会发生什么？ | 给执行任务的线程发中断信号 → 如果任务里有 `sleep/wait/Condition.await` 会抛 `InterruptedException`；如果是纯计算代码，**中断标志位会被置位但没人检查，任务继续跑完** |
| 没 cancel 会怎样？ | 任务继续跑完，结果存在 Future 里占内存直到 GC；如果任务持有大对象 → 内存泄漏风险 |

> **生产必做**：get() 超时后必须 `cancel(true)`；任务代码里要检查中断标志（`Thread.currentThread().isInterrupted()`），及时响应中断退出长循环。

### Q10：生产上线程池必配的 5 个参数是什么？

**答这 5 个，比列 7 个核心参数更聚焦**：

| # | 参数 | 必配原因 |
|:---|:---|:---|
| ① | **corePoolSize + maximumPoolSize** | 决定并发上限，CPU 密集 = N<sub>cpu</sub>+1，IO 密集 = 2~5×N<sub>cpu</sub> |
| ② | **有界 workQueue** | 无界队列 = 潜在 OOM，必须 `ArrayBlockingQueue` + 合理容量 |
| ③ | **命名 ThreadFactory** | 线程名里带业务前缀，jstack 能一眼认出哪个线程池的线程；排查必用 |
| ④ | **明确的拒绝策略** | 默认 AbortPolicy 抛异常可能炸业务；CallerRunsPolicy 是降级兜底；不能 DiscardPolicy 静默丢任务 |
| ⑤ | **allowCoreThreadTimeOut + keepAliveTime** | 默认核心线程永不超时，低负载时空占内存；IO 密集建议开 true + keepAlive 60s |

**额外加分**：`waitForTasksToCompleteOnShutdown(true)` + `awaitTerminationSeconds(60)`——JVM 关闭时优雅等正在执行的任务跑完，不硬杀。

## 三、易错点

| 易错点 | 说明 |
|:---|:---|
| **LinkedBlockingQueue 容量** | 默认 `Integer.MAX_VALUE`，不是「没容量」是「容量≈无限」——Executors 三个工厂方法坑点根源 |
| **`newCachedThreadPool` 最大线程数** | `MAX_VALUE`，并发上来直接线程爆炸 OOM |
| **submit 超时后任务还在跑** | `TimeoutException` 只是客户端等不及，线程池那边继续执行——必须 `cancel(true)` |
| **cancel(true) ≠ 立刻终止** | 中断只是发信号，任务代码必须检查 `isInterrupted()` 才能响应；纯计算代码可能一直跑 |
| **Spring Boot @Async 默认线程池** | 2.x 默认 ThreadPoolTaskExecutor 核心=8、队列无界；1.x 默认 SimpleAsyncTaskExecutor 每次 new Thread |
| **CompletableFuture 默认池** | `ForkJoinPool.commonPool()` 是全局共享的，被 IO 任务阻塞后并行流也跟着慢 |
| **动态调参不能换队列** | 没有 `setWorkQueue()`，想换队列只能重建线程池 |
| **核心线程默认不销毁** | `allowCoreThreadTimeOut=false` 时 keepAliveTime 对核心线程无效，只有非核心线程超时才会销毁 |

## 四、一句话总结

**线程池面试 P7 分水岭**：能背七大参数是 P5，能说清队列选型对线程池行为的影响 + 监控告警 + 拒绝策略选型是 P7。**生产上线程池必做三件事**：队列必须有界、线程必须命名、拒绝策略必须明确。
