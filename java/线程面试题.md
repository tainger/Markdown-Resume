## 二、逐题详解

### Q1：创建线程有哪几种方式？本质区别是什么？

**标准答案：三种，本质都是创建 `Thread` 对象。**

| 方式 | 写法 | 本质 |
|:---|:---|:---|
| **继承 Thread** | `class MyThread extends Thread { run() {...} }` | 重写 `Thread.run()`，启动后 JVM 回调这个 `run` |
| **实现 Runnable** | `new Thread(() -> {...}).start()` | `Runnable` 是任务，`Thread` 是执行器；`Thread` 内部持有 `target`（Runnable），`run()` 里调 `target.run()` |
| **实现 Callable + FutureTask** | `new Thread(new FutureTask<>(callable)).start()` | 有返回值 + 可抛异常；`FutureTask` 同时实现 `Runnable` 和 `Future` |

**选型建议**：
- 继承 Thread：简单但耦合（Java 单继承），任务与执行器绑定；
- **实现 Runnable/Callable**：任务与执行器解耦，推荐；
- Callable：需要返回值时才用，否则 Runnable 更轻。

> JDK21 虚拟线程（`Thread.ofVirtual().start()`）本质还是 Thread 对象，但由 JVM 调度而非 OS 线程，百万级并发的关键。详见 [jdk21增加了哪些新内容？](jdk21增加了哪些新内容？.md)。

### Q2：线程有哪些状态？状态之间怎么转换？

**Java 6 种状态**（`Thread.State` 枚举）：

```
         ┌─────────────────────── NEW（新建）
         │  Thread t = new Thread(...)
         └───────────┬───────────┘
                     │ t.start()
                     ▼
              ┌─────────────── RUNNABLE（可运行/运行中）
              │  包含 Running + Ready（等待 CPU 时间片）
              ├───▶ 阻塞态（BLOCKED / WAITING / TIMED_WAITING）
              │     被抢占/IO 阻塞 → 操作系统层的 Runnable 队列
              │
              │   ┌─ BLOCKED ─┐  ┌─ WAITING ─┐  ┌─ TIMED_WAITING ─┐
              │   │ 等锁      │  │ wait/join │  │ sleep/带超时wait│
              │   │ IO 等     │  │ 无超时     │  │ 带超时           │
              │   └───────────┘  └───────────┘  └──────────────────┘
              │         │               │              │
              │         └── 被唤醒/获锁 ────────────────┘
              │                            │
              │                            ▼
              └───────────────────── RUNNABLE
                     │
              正常结束 / 抛异常
                     ▼
              ┌─────────────── TERMINATED（已终止）
              └───────────────┘
```

**三种阻塞态的区别**（面试高频追问）：

| 状态 | 触发方式 | 唤醒条件 | 是否释放锁 |
|:---|:---|:---|:---:|
| **BLOCKED** | 等待 synchronized 锁、IO 阻塞 | 获取锁 / IO 完成 | 不适用（没持锁） |
| **WAITING** | `wait()`、`join()` 无超时 | `notify()/notifyAll()`、被中断、join 目标结束 | ✅ wait 必须在 synchronized 内，调用后**立即释放锁** |
| **TIMED_WAITING** | `sleep()`、带超时的 `wait()/join()`、parkNanos | 超时 / 被唤醒 / 被中断 | ❌ sleep **不释放锁**；wait 释放 |

### Q3：wait / notify / notifyAll 的原理？为什么必须在 synchronized 中调用？

**原理**：每个 Java 对象都有一个 `Monitor`（监视器，synchronized 的底层实现）。`wait/notify` 就是操作这个 Monitor 的 **WaitSet（等待队列）**：

```
synchronized(lock) {
    while (条件不满足) {
        lock.wait();          // ① 把当前线程放入 lock 的 WaitSet
                              // ② 释放 lock 的 Monitor 锁（其他线程可进入 synchronized 块）
                              // ③ 线程进入 WAITING 状态，不再竞争 CPU
    }
    // 条件满足了，继续干活
}

// 另一个线程：
synchronized(lock) {
    // 改变条件
    lock.notify();            // 从 WaitSet 随机捞 1 个线程，放回 Monitor 的 EntryList
                              // （但线程此时还没获锁，要等当前线程退出 synchronized 后再竞争）
    // notifyAll() 是捞 WaitSet 全部线程，逐个放入 EntryList
}
```

**为什么必须在 synchronized 中？**（三句话答完）

1. **规范层**：`wait` 要「释放锁」，前提是你**正在持锁**——不持锁就没得放；
2. **一致性层**：`while (条件不满足) wait()` 这组操作必须原子——如果不在 synchronized 内，两个线程可能同时检查条件同时进入 wait → 丢失唤醒（lost wakeup）；
3. **JVM 层**：`wait/notify` 本质是操作**Monitor**，每个对象只有持锁的线程才能访问它的 WaitSet——JVM 用 `ObjectMonitor` 校验，不在 synchronized 内调用直接抛 `IllegalMonitorStateException`。

**notify vs notifyAll 怎么选？**

| 场景 | 推荐 | 原因 |
|:---|:---|:---|
| 多个线程等同一个条件 | `notifyAll` | `notify` 只捞一个，但被捞的线程可能不是你需要唤醒的（比如生产者/消费者模式中，消费者等「有货」，生产者等「有空」，两者共用一个锁的 WaitSet） |
| 只有一个消费者 | `notify` | 性能更好，避免无意义的唤醒竞争 |
| 不确定 | **`notifyAll` 优先** | 宁可多唤醒几个线程空转，也不能漏唤醒 |

### Q4：sleep / wait / yield / join 四者的区别？

| 维度 | `Thread.sleep` | `Object.wait` | `Thread.yield` | `Thread.join` |
|:---|:---|:---|:---|:---|
| **所属** | Thread 静态方法 | Object 方法 | Thread 静态方法 | Thread 实例方法 |
| **前提** | 无 | 必须在 synchronized 内 | 无 | 无 |
| **锁** | ❌ **不释放** | ✅ 释放当前 Monitor 锁 | 不涉及锁 | 内部可能用 wait，会释放 |
| **状态** | TIMED_WAITING | WAITING / TIMED_WAITING | RUNNABLE（让出 CPU 时间片，立即回到就绪队列） | WAITING / TIMED_WAITING |
| **唤醒** | 超时 / `interrupt` | `notify/notifyAll` / 超时 / `interrupt` | 立刻被调度器选回 RUNNABLE | 目标线程结束 / 超时 / `interrupt` |
| **典型用途** | 定时、轮询间隔 | 生产者-消费者、条件等待 | 调试/测试时让出 CPU | 等子线程完成后主线程再继续 |
| **是否异常** | 抛 `InterruptedException` | 抛 `InterruptedException` | 不抛 | 抛 `InterruptedException` |

**面试陷阱**：
- `yield` 不是阻塞！它让当前线程**让出 CPU 时间片**，但线程仍处于 RUNNABLE 状态，调度器下一轮可能立刻又把它选上；
- `sleep(0)` ≠ `yield()`：sleep(0) 在某些 JVM 实现中仍会走 timed_waiting → runnable 的完整状态转换，而 yield 是直接回到 runnable；
- `join` 底层是 `while(isAlive()) wait(0)`，所以它会**释放锁**（和 wait 一样）——很多人漏掉这点。

### Q5：synchronized 的底层原理？锁升级链路？

> **分工声明**：锁升级的底层实现（Mark Word 位布局、偏向锁判定条件、轻量级锁 CAS 自旋细节）见 [JUC 并发包](JUC并发包.md) 第二节「synchronized vs Lock」+ 锁升级链路；本文聚焦**面试怎么答**——给一张 ASCII 图 + 三句话说清 + 重入实现。

**synchronized 的底层 = 对象头 Mark Word + Monitor**

```
┌───────────────────────────────────────────┐
│                对象头 (64 位 JVM)            │
│  Mark Word (64位)  │  Klass Point(64位)    │
│  ┌────────────────┐ │  ┌───────────────────┐│
│  │ hashcode/GC分代 │ │  │ 指向 Klass 元数据  ││
│  │ age(4) │ 状态(2)│ │  │                    ││
│  └────────────────┘ │  └───────────────────┘│
└───────────────────────────────────────────┘

状态位 (2位)：
  01 = 无锁 / 偏向锁  10 = 轻量级锁  11 = 重量级锁
偏向锁额外有：线程ID（54位）+ 偏向标志位(1位)
```

**锁升级链路**（JDK6 引入，优化 synchronized 在低竞争场景的性能）：

```
无锁
  │ 单线程首次进入 synchronized
  ▼
偏向锁（Mark Word 存线程ID，同一线程重入无开销）
  │ 另一个线程来竞争
  ▼
轻量级锁（CAS 自旋：Mark Word 存指向栈中锁记录的指针）
  │ 自旋失败（或多线程持续竞争，CPU 空转浪费）
  ▼
重量级锁（Mark Word 存指向 Monitor 的指针，Monitor 管 EntryList+WaitSet）
```

**Monitor 核心结构**：

```
ObjectMonitor {
    _owner: Thread        // 当前持锁线程
    _EntryList: Node      // 等待获取锁的线程队列（BLOCKED）
    _WaitSet: Node        // 调用了 wait() 的线程队列（WAITING）
    _count: int           // 重入计数
    _recursions: int      // 重入层数（配合 count）
}
```

**重入是怎么实现的**：同一个线程重入 synchronized 方法时，JVM 检查 `_owner == 当前线程`，是的话 `_count++`；退出时 `_count--`，减到 0 才真的释放锁。

### Q6：死锁的四个必要条件？怎么预防？

**四个必要条件（缺一不可）**：

| 条件 | 含义 | 比喻 |
|:---|:---|:---|
| **互斥** | 资源只能被一个线程持有 | 一把椅子只能坐一个人 |
| **请求与保持** | 持有已获资源的同时，又请求新资源 | 拿着碗去接第二碗汤但不放下第一碗 |
| **不可剥夺** | 已持有的资源不能被强制拿走 | 别人不能从你手里把碗抢走 |
| **循环等待** | 线程 A 等 B 的资源，B 等 A 的资源 | 两个人互相等对方先放碗 |

**预防策略**（对应破坏条件）：

| 破坏条件 | 具体做法 | 例子 |
|:---|:---|:---|
| 请求与保持 | **资源预分配**：一次性拿齐所有需要的锁 | 转账前同时锁住两个账号 |
| 不可剥夺 | **超时拿锁 + 主动释放** | `ReentrantLock.tryLock(timeout)` 超时后放弃并释放已持锁 |
| **循环等待** | **统一加锁顺序** | 所有涉及账户 A、B 的操作，都先锁 ID 小的那个 |

> 面试必说：**预防循环等待最实用的手段是统一加锁顺序**，代码层面可维护。资源预分配在多锁场景难以做到（比如嵌套调用、框架内部加锁）。

### Q7：volatile 写后读发生了什么？

**一句话版**：volatile 写会把工作内存中值刷回主存 + 禁止写之前的操作重排到写之后；volatile 读会把主存中值重新加载到工作内存 + 禁止读之后的操作重排到读之前。

**详细链路**（基于 JMM happens-before 规则）：

```
线程 A                              主存                         线程 B
───────────────────────────────────────────────────────────────────
① 普通写 x = 1
② volatile写 flag = true
   ├── StoreStore屏障：保证①不会重排到②之后
   └── StoreLoad屏障 + 刷主存 → flag 最新值回主存

                                ────────────── 主存 flag 更新

③ volatile读 flag（命中 true）
   ├── LoadLoad屏障 + LoadStore屏障
   └── 从主存读 flag → 本地工作内存

④ 普通读 x
   └── 因为 ② hb ③（volatile 变量规则）
       所以 ① hb ③（传递性）
       所以 ① hb ④（传递性）
       → B 线程一定看到 x == 1
```

**三个关键规则**（happen-before）：
1. **volatile 变量规则**：volatile 写 hb 后续对该变量的 volatile 读；
2. **程序次序规则**：同一线程内前面的操作 hb 后面的操作；
3. **传递性**：A hb B，B hb C → A hb C。

> 详情 + 内存屏障四类型见 [../jvm/JMM内存模型.md](../jvm/JMM内存模型.md)，本文只讲面试口径。

### Q8：什么是守护线程（daemon）？和用户线程的区别？

| 维度 | 用户线程（默认） | 守护线程（daemon） |
|:---|:---|:---|
| 创建 | `new Thread()` | `new Thread(); t.setDaemon(true)` |
| 生命周期 | JVM 中**只要有一个**用户线程活着，JVM 就不退出 | 用户线程**全挂**后，守护线程会被 JVM 强制终止 |
| 典型用途 | 业务线程、异步任务线程 | 后台辅助：垃圾回收器、JIT 编译器、监控线程 |
| 代码时机 | 必须在 `start()` 之前调 `setDaemon()` | 同左 |
| finally | 守护线程的 finally **不保证执行** | —（但用户线程如果被中断，finally 照常） |

```java
// 守护线程示例：主线程结束后，daemon 自动被终止
Thread daemon = new Thread(() -> {
    while (true) {
        System.out.println("daemon running...");
        try { Thread.sleep(1000); } catch (InterruptedException e) {}
    }
});
daemon.setDaemon(true);   // 必须在 start 前设
daemon.start();
// 主线程结束 → daemon 立刻被 JVM 杀掉，不会再打印
```

### Q9：中断机制是怎么回事？为什么 `Thread.stop` 被废弃？

**中断 = 协作式通知，不是强制终止**

```java
// 三个 interrupt 相关方法的区别
t.interrupt();                    // 给线程 t 发中断请求（设置中断标志位）
                                  // 若 t 正在 wait/sleep/join → 立刻抛出 InterruptedException
                                  // 若 t 正在跑普通代码 → 什么都不发生，标志位置位

Thread.interrupted();             // 静态方法：返回当前线程的中断标志位 + 清除标志位（读一次就没了）

t.isInterrupted();                // 实例方法：只查询 t 的中断标志位，不清除
```

**正确的中断响应模式**：

```java
while (!Thread.currentThread().isInterrupted()) {
    try {
        doSomeWork();                    // 可能执行很久的任务
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();  // ★ 必须重新设置中断标志（catch 会清掉）
        break;                                // 然后根据需要退出循环
    }
}
```

**为什么 `Thread.stop()` 被废弃**：
- 它会**直接杀掉线程**，不管线程在干什么——可能持有锁时杀掉 → 其他线程永远拿不到锁；可能正在写数据 → 数据部分更新一半；
- 没有任何清理机会（finally 也不一定能执行到）；
- 中断机制让**被中断的线程自己决定怎么退出**，保证了状态完整性。

### Q10：多线程单例模式怎么写？

| 实现 | 代码 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **饿汉式** | `private static final Singleton INSTANCE = new Singleton();` | 天然线程安全（类加载时就创建，JVM 类加载机制保证类只加载一次） | 不管用不用都创建，浪费内存 |
| **懒汉式（同步）** | `public static synchronized Singleton get() { if (INSTANCE==null) INSTANCE = new Singleton(); return INSTANCE; }` | 按需创建、线程安全 | 每次 get 都争锁，性能差 |
| **DCL（双重检查锁）** | 见下 | 按需创建 + 只在首次创建时争锁 | 必须加 `volatile` 禁止重排 |
| **静态内部类** | 见下 | 懒加载 + 线程安全 + 无锁 | —（推荐） |
| **枚举单例** | `enum Singleton { INSTANCE }` | JVM 保证绝对安全、序列化安全、防反射 | 不能有懒加载 |

**DCL 为什么必须加 volatile？**

```java
// ❌ 错误版：没有 volatile
Singleton s = new Singleton();   // JVM 可能重排为：
                                  // ① 分配内存
                                  // ② s 指向这块内存（此时 s 非 null，但 Singleton() 还没执行！）
                                  // ③ 执行 Singleton() 初始化

// 线程 A 执行到 ②（还没到 ③），线程 B 进来发现 s != null，直接用了「半初始化」的对象 → 崩溃

// ✅ 正确版：加 volatile
private static volatile Singleton INSTANCE;   // volatile 禁止 ①②③ 之间重排
```

**静态内部类为什么好用？**

```java
public class Singleton {
    private Singleton() {}

    private static class Holder {
        // 类加载机制保证：Holder 只在首次被引用时加载一次，且加载过程线程安全
        static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;   // 首次调用才加载 Holder，触发 INSTANCE 创建
    }
}
```

> 选型：**简单场景饿汉式、需要懒加载就静态内部类、框架里用枚举**。DCL 适合面试答题，但实际代码推荐静态内部类。

## 三、易错点

| 易错点 | 说明 |
|:---|:---|
| **sleep 释放锁** ❌ | sleep **不释放** synchronized 锁；wait 才释放。面试高频坑 |
| **wait 在哪里调用** | 必须在 synchronized 内调用**持锁对象**的 wait（`lock.wait()`），不是 `this.wait()` 随便调 |
| **notifyAll = 全部通知** | 是把 WaitSet 里**所有**线程都捞出来，不区分条件——如果两个线程等不同条件，可能全部被唤醒但只有一个能继续 |
| **yield 不是阻塞** | 让出 CPU 时间片，线程仍在 RUNNABLE 状态，调度器可能立刻又选上 |
| **interrupt 清除标志位** | `catch (InterruptedException)` 时中断标志位会被**自动清除**，必须在 catch 内重新 `interrupt()` |
| **守护线程 finally 不保证执行** | JVM 关闭时守护线程可能被硬杀，finally 块不保证跑到 |
| **synchronized 重入计数** | 同一线程重入时 `_count++`，不是覆盖。退出时减到 0 才真正释放 |

---

## 四、一句话总结

**线程面试三层塔**：基础层（Thread 类 + synchronized + wait/notify + 生命周期 + 中断）→ 工具层（JUC 并发包）→ 轻量可见性层（volatile）。**必须在 synchronized 内调 wait**（否则 Monitor 校验不过）、**sleep 不释放锁**、**中断是协作不是强制**、**synchronized 锁升级从偏向到轻量到重量**——这四个是高频追问点。
