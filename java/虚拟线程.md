# 虚拟线程（Virtual Thread）

> 基础特性见 [jdk21增加了哪些新内容？](jdk21增加了哪些新内容？.md)，本篇深挖 carrier 调度、continuation 机制、pinned 问题、Go goroutine 对比与生产实战。

---

## 一、虚拟线程是什么

虚拟线程（Virtual Thread）是 JDK 21 正式发布的**轻量级线程实现**（JEP 444），本质是 **JVM 调度的协程**。

- 创建成本极低（几 KB 栈 vs 平台线程 ~1MB）
- 可以创建**百万级**虚拟线程
- 用**同步阻塞的代码写法**实现异步高并发
- 底层通过 **Continuation（续体）** + **Carrier Thread（载体线程）** 实现 M:N 调度

```java
// 创建一个虚拟线程
Thread vt = Thread.ofVirtual().start(() -> {
    System.out.println("Hello from virtual thread!");
});

// 用 ExecutorService 批量创建
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 1_000_000).forEach(i ->
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));
            return i;
        }));
}  // try-with-resources 自动等待所有任务完成
```

## 二、核心架构：Carrier + Continuation

### 2.1 M:N 调度模型

```
┌─────────────────────────────────────────────┐
│             ForkJoinPool (调度器)             │
│          (parallelism = CPU 核数)            │
│                                               │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ Carrier   │  │ Carrier   │  │ Carrier   │   │  ← 平台线程
│  │ Thread #1 │  │ Thread #2 │  │ Thread #3 │   │     (OS 线程)
│  └─────┬────┘  └─────┬────┘  └─────┬────┘   │
│        │              │              │        │
│   ┌────▼────┐   ┌────▼────┐   ┌────▼────┐    │
│   │ 虚拟线程 │   │ 虚拟线程 │   │ 虚拟线程 │    │  ← JVM 管理
│   │  #1     │   │  #2     │   │  #3     │    │
│   └─────────┘   └─────────┘   └─────────┘    │
│        ...（百万个虚拟线程）                    │
└─────────────────────────────────────────────┘
```

- **Carrier Thread（载体线程）**：从 `ForkJoinPool` 调度器池中获取的平台线程，负责执行虚拟线程的代码
- **Continuation（续体）**：虚拟线程的执行状态（栈），可以被**挂起（unmount）** 和 **恢复（mount）**

### 2.2 Unmount / Mount 机制

```
虚拟线程执行 IO 操作（如 Thread.sleep / Socket.read）
        │
        ▼
检测到阻塞点（JVM 增强的 I/O 方法）
        │
        ▼
┌─────────────────────────────────┐
│  unmount：                        │
│  1. 保存当前栈状态到 Continuation  │
│  2. 释放 carrier 线程回调度池      │
│  3. 虚拟线程进入 PARKED 状态       │
└─────────────────────────────────┘
        │
        │  ... IO 完成（epoll 通知）...
        │
        ▼
┌─────────────────────────────────┐
│  mount：                          │
│  1. 从调度池取一个 carrier 线程    │
│  2. 恢复 Continuation 栈状态      │
│  3. 继续执行虚拟线程代码           │
└─────────────────────────────────┘
```

**关键点**：
- 虚拟线程**阻塞时不阻塞 carrier 线程**，carrier 可以去执行其他虚拟线程
- 这就是"同步代码 + 异步性能"的秘密
- 调度器是共享的 `ForkJoinPool`，**所有虚拟线程共用一个调度池**

### 2.3 阻塞点检测（Loom 增强）

JDK 21 对常见阻塞方法做了增强，能识别阻塞点并触发 unmount：

| 方法 | 触发 unmount |
|:---|:---:|
| `Thread.sleep()` | ✅ |
| `Socket.read() / Socket.write()` | ✅ |
| `ServerSocket.accept()` | ✅ |
| `BlockingQueue.take() / put()` | ✅ |
| `LockSupport.park()` | ✅ |
| `synchronized` 块内的操作 | ❌（Pinned 问题） |
| `Object.wait()` | ❌（Pinned 问题） |

## 三、Pinned 问题（面试高频）

### 3.1 什么是 Pinned

当虚拟线程在 **synchronized 块** 或 **native 方法** 中阻塞时，**无法 unmount**，carrier 线程会被"钉住"（pinned），其他虚拟线程无法使用这个 carrier。

```java
// ❌ Pinned：synchronized 块内阻塞
synchronized (lock) {
    Thread.sleep(1000);  // 不会 unmount，carrier 被钉住 1 秒
}

// ✅ 不 Pinned：用 ReentrantLock
lock.lock();
try {
    Thread.sleep(1000);  // 会 unmount，carrier 可以执行其他任务
} finally {
    lock.unlock();
}
```

### 3.2 为什么 synchronized 会 Pinned

synchronized 的锁实现深度耦合 OS 线程（monitor 与 OS 线程绑定），JVM 无法在不持有锁的情况下 unmount 虚拟线程。而 `ReentrantLock` 是纯 Java 实现，JVM 可以在 `LockSupport.park()` 时 unmount。

### 3.3 Pinned 的影响

- 少量 Pinned 影响不大（carrier 池会自动扩容）
- 大量 Pinned 会**降低虚拟线程吞吐**（carrier 不够用）
- 生产环境建议**将 `synchronized` 替换为 `ReentrantLock`**

### 3.4 检测 Pinned

启动时加 JVM 参数（JDK 21+）：

```bash
java -Djdk.tracePinnedThreads=full -jar app.jar
```

Pinned 时会打印完整堆栈，方便定位。

## 四、ThreadLocal 与 ScopedValue

### 4.1 ThreadLocal 在虚拟线程中的问题

虚拟线程可以有百万个，**每个虚拟线程都有自己的 ThreadLocal 副本**：

- 内存占用大（百万个虚拟线程 × ThreadLocal 对象）
- `InheritableThreadLocal` 继承开销大
- 线程池场景下 ThreadLocal 泄漏问题依然存在

### 4.2 ScopedValue（JDK 21 + JEP 446）

`ScopedValue` 是专为虚拟线程设计的**不可变、显式传递**的上下文方案：

```java
private static final ScopedValue<String> USER_ID = ScopedValue.newInstance();

// 绑定作用域
ScopedValue.where(USER_ID, "user-123").run(() -> {
    String userId = USER_ID.get();  // 在作用域内访问
    System.out.println("Processing for " + userId);
});
```

| 维度 | ThreadLocal | ScopedValue |
|:---|:---|:---|
| 可变性 | 可变（set/get/remove） | 不可变（只能在作用域内读） |
| 生命周期 | 随线程存在 | 显式作用域（where.run） |
| 继承 | InheritableThreadLocal | 自动传递给子作用域 |
| 虚拟线程友好 | 内存开销大 | 轻量、无泄漏风险 |
| 推荐场景 | 传统平台线程 | 虚拟线程 + 不可变上下文 |

## 五、虚拟线程 vs Go Goroutine

| 维度 | 虚拟线程（Java） | Goroutine（Go） |
|:---|:---|:---|
| 调度器 | JVM ForkJoinPool（work-stealing） | Go runtime（per-P run queue + global queue） |
| 阻塞点 | JVM 增强检测（sleep/IO/LockSupport） | 语言级（所有 syscall 都走 runtime） |
| Pinned 问题 | 有（synchronized/native） | 无（syscall 自动 handoff） |
| 栈大小 | 初始几 KB，可动态扩展 | 初始 2KB，可动态扩展 |
| 调试 | jstack/JFR 支持（JDK 21+） | pprof + trace |
| 生态 | 渐进式迁移（旧代码不动） | 原生支持 |
| M:N 实现 | Continuation + carrier | g-m-p 模型 |

> **面试加分**：Go 的 goroutine 从语言层面就设计为协程，所有系统调用都经过 runtime；Java 是在 JVM 层后加的，所以有 Pinned 历史包袱，但优势是**存量代码不用改，逐步迁移**。

## 六、应用场景

### 6.1 高并发 IO 密集型（最适合）

```java
// HTTP 客户端并发请求（传统写法，同步阻塞）
List<CompletableFuture<String>> futures = urls.stream()
    .map(url -> CompletableFuture.supplyAsync(() -> {
        try { return HttpClient.newHttpClient()
                .send(HttpRequest.newBuilder(URI.create(url)).build(),
                      HttpResponse.BodyHandlers.ofString()).body();
        } catch (Exception e) { return null; }
    }))
    .toList();

// 虚拟线程写法（更简单，直接同步）
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = urls.stream()
        .map(url -> executor.submit(() ->
            HttpClient.newHttpClient()
                .send(HttpRequest.newBuilder(URI.create(url)).build(),
                      HttpResponse.BodyHandlers.ofString()).body()))
        .toList();
}
```

### 6.2 AgentMate 实战：LLM 回归测试批量执行

简历中 AgentMate 项目用虚拟线程做 LLM 回归测试的**异步批量执行**：

```java
// 伪代码：回归测试场景，几百个 case 并发执行
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<TestCaseResult>> futures = testCases.stream()
        .map(tc -> executor.submit(() -> {
            // 每个 case：调 LLM + 真实接口校验，耗时几秒到几十秒
            String llmOutput = callLLM(tc.getPrompt());
            String actualResult = callRealApi(tc.getRequest());
            return judge(tc, llmOutput, actualResult);
        }))
        .toList();

    // 实时回写进度
    for (int i = 0; i < futures.size(); i++) {
        TestCaseResult result = futures.get(i).get();  // 阻塞等单个完成
        reportProgress(i, result);
    }
}
```

**为什么用虚拟线程**：
- 传统平台线程池：50 个 case 并发需要 50 个线程，每个阻塞等 LLM 响应，线程池排队慢
- 虚拟线程：500 个 case 也只要几十个 carrier，虚拟线程阻塞时自动让出，吞吐量高 10 倍
- 代码保持同步写法，无需 `CompletableFuture` 链式地狱

### 6.3 不适合的场景

| 场景 | 原因 |
|:---|:---|
| CPU 密集型计算 | 虚拟线程不会并行更快，反而增加调度开销（用平台线程池 + 多核） |
| 大量 synchronized 代码 | Pinned 问题降低吞吐 |
| native 方法密集 | Pinned 问题 |
| 仍用 JDK 11/8 | 虚拟线程是 JDK 21 LTS 特性 |

## 七、面试问答

### Q1：虚拟线程的底层原理是什么？

虚拟线程是 JVM 实现的 M:N 协程调度。虚拟线程在阻塞点（sleep/IO/LockSupport）会触发 **Continuation unmount**，将栈状态保存，释放 carrier 线程回 `ForkJoinPool` 调度器执行其他虚拟线程。IO 完成后通过 `mount` 恢复栈状态继续执行，实现"同步代码 + 异步性能"。

### Q2：虚拟线程和平台线程有什么区别？

| 维度 | 平台线程 | 虚拟线程 |
|:---|:---|:---|
| 映射 | 1:1 OS 线程 | M:N（虚拟线程 : carrier） |
| 创建成本 | ~1MB 栈 + OS 资源 | ~几 KB |
| 数量 | 几百个就很多了 | 百万级 |
| 阻塞代价 | 阻塞 OS 线程 | 自动 unmount，不占 carrier |
| 适用 | CPU 密集 | IO 密集（高并发） |

### Q3：虚拟线程有什么坑？

1. **Pinned 问题**：synchronized/native 中阻塞会钉住 carrier，建议用 `ReentrantLock`
2. **ThreadLocal 内存**：百万虚拟线程 × ThreadLocal = 内存爆炸，推荐 `ScopedValue`
3. **调试差异**：jstack 输出大量虚拟线程，需配合 JFR 分析
4. **不是银弹**：CPU 密集型没有提升，甚至更慢
5. **版本依赖**：JDK 21 LTS 才稳定，需升级 JDK

### Q4：虚拟线程和 CompletableFuture 怎么选？

- **虚拟线程**：逻辑清晰、同步写法、适合大量短任务并发
- **CompletableFuture**：已有异步框架、需要复杂编排（thenCombine/thenCompose）
- **趋势**：新项目优先虚拟线程，存量渐进迁移

### Q5：Spring Boot 支持虚拟线程吗？

Spring Boot 3.2+ 支持虚拟线程：

```yaml
# application.yml
spring:
  threads:
    virtual:
      enabled: true
```

启用后 Tomcat 的请求处理线程全部换成虚拟线程，IO 密集型应用吞吐大幅提升。

### Q6：虚拟线程会替代线程池吗？

**不会完全替代**：
- 虚拟线程池适合 IO 密集、每任务一个虚拟线程
- 平台线程池适合 CPU 密集、限制并发数保护下游
- 生产中混用：CPU 密集用平台池，IO 密集用虚拟线程

## 八、一句话总结

> 虚拟线程 = **JVM 版协程**，用 Continuation + carrier 实现 M:N 调度，同步写法享受异步性能，IO 密集高并发的银弹，但 Pinned 和 ThreadLocal 两个坑要当心。
