# 垃圾回收算法

GC 要回答三个问题：**哪些对象该回收（判活）→ 用什么算法回收（策略）→ 什么时候停顿（安全点）**。本篇讲算法与机制，具体收集器见 [垃圾收集器.md](垃圾收集器.md)。

---

## 一、如何判断对象已死？

### 1. 引用计数法（Java 未采用）

给对象加计数器，被引用 +1、失效 -1，为 0 即可回收。

- 优点：实现简单、实时性好。
- **致命缺点：无法解决循环引用**（A 引 B、B 引 A，计数都不为 0，却已无用）。

### 2. 可达性分析（Reachability Analysis）✅ Java 采用

从一组 **GC Roots** 出发向下搜索，走过的路径叫**引用链**；不在任何引用链上的对象判定为「可回收」。

**哪些能作为 GC Roots？**（高频）

| GC Roots | 举例 |
|:---|:---|
| 虚拟机栈中引用的对象 | 方法里的局部变量、参数 |
| 方法区中**静态属性**引用的对象 | `static` 变量指向的对象 |
| 方法区中**常量**引用的对象 | 字符串常量池里的引用 |
| 本地方法栈中 JNI 引用的对象 | native 方法引用 |
| 活跃线程、同步锁持有的对象 | Thread、被 synchronized 锁住的对象 |

> 循环引用只要整体不与 GC Roots 相连，就会被判死——这是可达性分析优于引用计数的核心。

## 二、四种引用强度

回收行为不止「回收/不回收」，引用强度决定对象在内存紧张时的命运：

| 引用类型 | 回收时机 | 典型用途 |
|:---|:---|:---|
| **强引用** `Object o = new ...` | 永不回收（只要可达） | 普通对象 |
| **软引用** `SoftReference` | **内存不足时**才回收 | 内存敏感的缓存 |
| **弱引用** `WeakReference` | **下次 GC 必回收** | `WeakHashMap`、ThreadLocal 的 key |
| **虚引用** `PhantomReference` | 随时可能回收，无法通过它取对象 | 跟踪对象被回收、管理堆外内存（DirectByteBuffer 的 Cleaner） |

> ThreadLocal 内存泄漏就源于此：ThreadLocalMap 的 key 是弱引用、value 是强引用，key 被回收后 value 仍在 → 用完要 `remove()`。

## 三、三种基础回收算法

| 算法 | 过程 | 优点 | 缺点 | 适用区域 |
|:---|:---|:---|:---|:---|
| **标记-清除** Mark-Sweep | 标记存活 → 清除未标记 | 简单 | **内存碎片**、效率随对象增多下降 | 老年代（CMS） |
| **标记-复制** Copying | 内存分两半，存活对象复制到另一半，清空旧半区 | 无碎片、分配快 | 浪费一半空间 | **新生代** |
| **标记-整理** Mark-Compact | 标记存活 → 把存活对象向一端移动 → 清理边界外 | 无碎片、不浪费空间 | 移动对象成本高、需更新引用 | 老年代（Serial Old、Parallel Old） |

```
标记-复制（新生代）：
回收前  [ A  垃圾 B  垃圾 C ]  空闲区
回收后    空闲区            [ A B C ]   ← 存活对象紧凑复制过去
```

## 四、分代收集理论（GC 的总纲）

基于两条经验假说：

| 假说 | 含义 | 推论 |
|:---|:---|:---|
| **弱分代假说** | 绝大多数对象**朝生夕灭** | 新生代用复制算法（存活少，复制成本低） |
| **强分代假说** | 熬过越多次 GC 的对象越难死 | 老年代用标记-清除/整理（回收频率低） |

于是把堆分代，**各代用最合适的算法**：

```
新生代（Young）  ← 复制算法（Eden : S0 : S1 = 8:1:1）  → Minor GC，频繁、快
老年代（Old）    ← 标记-整理 / 标记-清除                → Major/Full GC，慢
```

### GC 类型术语（别混）

| 术语 | 回收范围 | 触发 |
|:---|:---|:---|
| **Minor GC / Young GC** | 只回收新生代 | Eden 满 |
| **Major GC / Old GC** | 只回收老年代（CMS 等有此概念） | 老年代空间不足 |
| **Full GC** | 整个堆 + 方法区 | 老年代满、元空间满、`System.gc()` 等 |
| **Mixed GC** | 新生代 + 部分老年代 | G1 特有 |

## 五、跨代引用与记忆集（P7 深度）

**问题**：Minor GC 只扫新生代，但**老年代对象可能引用新生代对象**，若不处理会误判新生代对象已死。全扫老年代又太慢。

**解法**：
- **记忆集（Remembered Set）**：记录「老年代到新生代」的跨代引用，Minor GC 时把它也当作 GC Roots 的一部分，无需全扫老年代。
- **卡表（Card Table）**：记忆集的具体实现，把老年代按「卡页」分块，某块有跨代引用就标记为 **Dirty**。
- **写屏障（Write Barrier）**：在引用赋值时插入一小段逻辑，维护卡表（把对应卡页标脏）。

> G1 更进一步用 Region 级记忆集；ZGC 用染色指针 + 读屏障。这类问题能答出「记忆集/卡表/写屏障」就已到 P7 深度。

## 六、安全点与安全区域

GC（尤其涉及移动对象）需要**所有用户线程停下来**——即 **STW（Stop The World）**。但不能随时停，得停在状态一致的位置：

| 概念 | 含义 |
|:---|:---|
| **安全点（Safepoint）** | 代码中特定位置（方法调用、循环回边、异常跳转等），线程只能在此暂停 |
| **安全区域（Safe Region）** | 一段引用不变的代码区，线程处于其中（如 sleep/blocked）时可随时被 GC |
| **主动式中断** | GC 时设标志位，各线程跑到安全点主动轮询并挂起 |

> 为什么循环里要设安全点？长循环若中间不设安全点，GC 要等它跑完，导致「进入安全点耗时过长」。可通过 `-XX:+SafepointTimeout` 等诊断。

## 七、三色标记与并发标记问题（P7 高阶）

CMS、G1 的并发标记用**三色标记法**：

| 颜色 | 含义 |
|:---|:---|
| 白 | 未访问（最终仍白 = 垃圾） |
| 灰 | 自己被访问，但引用的对象还没扫完 |
| 黑 | 自己和引用都扫完（存活） |

**并发标记的漏标问题**：标记与用户线程并发时，若同时满足两条件会误删活对象：
1. 一个黑对象新增了对某白对象的引用；
2. 所有灰对象都断开了对该白对象的引用。

**两种解法**：

| 方案 | 破坏哪个条件 | 用于 |
|:---|:---|:---|
| **增量更新（Incremental Update）** | 记录黑对象新增的引用，重新扫黑对象 | CMS |
| **原始快照 SATB（Snapshot At The Beginning）** | 记录被删除的引用，按标记开始时的快照处理 | G1、ZGC |

## 八、易错点

| 易错点 | 澄清 |
|:---|:---|
| **Java 用引用计数** | Java 用**可达性分析**，正因引用计数解决不了循环引用 |
| **对象不可达立即回收** | 还可能在 `finalize()` 中「自救」一次；且回收由 GC 决定时机 |
| **Minor GC 要扫全堆** | 只扫新生代 + 记忆集里的跨代引用，不全扫老年代 |
| **软/弱引用分不清** | 软引用内存不足才回收（缓存）；弱引用下次 GC 必回收 |
| **`System.gc()` 立即回收** | 只是**建议** JVM 做 Full GC，不保证立即执行 |

---

## 九、一句话总结

GC 用**可达性分析 + GC Roots** 判活（解决循环引用）；按**分代假说**给新生代用**复制**、老年代用**标记-整理/清除**；靠**记忆集/卡表/写屏障**处理跨代引用，靠**安全点 + STW** 保证一致性；并发收集器用**三色标记 + 增量更新/SATB** 解决漏标。这套机制是理解各款收集器的通用语言。
