# 垃圾收集器

收集器是 GC 算法的**具体实现**。面试的核心是：**每款收集器用在哪代、什么算法、STW 特点、怎么选、怎么调**。P7 尤其要能讲清 CMS → G1 → ZGC 的演进动机。

---

## 一、收集器全景与搭配

```
新生代收集器            老年代收集器
┌──────────┐          ┌──────────────┐
│ Serial   │──────────│ Serial Old   │   单线程，client 模式
│ ParNew   │──────────│ CMS          │   并发低停顿（已废弃）
│ Parallel │──────────│ Parallel Old │   吞吐量优先
│  Scavenge│          └──────────────┘
└──────────┘
        G1        —— 整堆，Region 化，JDK 9+ 默认
        ZGC / Shenandoah —— 超低停顿，超大堆
```

> 连线表示可搭配使用。CMS 的新生代搭档是 ParNew。

---

## 二、经典收集器逐个看

| 收集器 | 代 | 算法 | 线程 | STW | 关注点 | 备注 |
|:---|:---|:---|:---|:---|:---|:---|
| **Serial** | 新生代 | 复制 | 单线程 | 全程 STW | — | 简单高效，client / 小堆 |
| **Serial Old** | 老年代 | 标记-整理 | 单线程 | 全程 STW | — | CMS 失败时的后备 |
| **ParNew** | 新生代 | 复制 | 多线程 | 全程 STW | — | Serial 的多线程版，配 CMS |
| **Parallel Scavenge** | 新生代 | 复制 | 多线程 | 全程 STW | **吞吐量** | 可自适应调节 `-XX:+UseAdaptiveSizePolicy` |
| **Parallel Old** | 老年代 | 标记-整理 | 多线程 | 全程 STW | **吞吐量** | Parallel Scavenge 的老年代搭档 |
| **CMS** | 老年代 | 标记-清除 | 并发 | **部分并发** | **低延迟** | JDK 9 弃用、14 移除 |
| **G1** | 整堆 | 复制 + 标记-整理 | 并发 | 可控停顿 | **可预测停顿** | JDK 9+ 默认 |
| **ZGC** | 整堆 | 染色指针 + 读屏障 | 几乎全并发 | **<1ms** | **超低延迟** | JDK 15 正式可用 |

> **吞吐量 vs 延迟**：吞吐量优先（Parallel）适合后台计算/批处理；低延迟优先（CMS/G1/ZGC）适合在线服务、对响应敏感的系统。

---

## 三、CMS（Concurrent Mark Sweep）—— 理解并发 GC 的经典

**目标**：最短回收停顿，适合响应优先的 Web 服务。四个阶段：

| 阶段 | 是否 STW | 做什么 |
|:---|:---:|:---|
| 1. 初始标记 Initial Mark | **STW（短）** | 只标记 GC Roots 直接关联的对象 |
| 2. 并发标记 Concurrent Mark | 并发 | 从 Roots 遍历整个引用链（与用户线程同时跑） |
| 3. 重新标记 Remark | **STW（短）** | 修正并发期间变动的标记（增量更新） |
| 4. 并发清除 Concurrent Sweep | 并发 | 清除死对象 |

**三大缺陷（面试必答）**：

| 缺陷 | 原因 |
|:---|:---|
| **内存碎片** | 用标记-清除，不整理，长期运行产生碎片 → 可能提前 Full GC |
| **CPU 敏感** | 并发阶段占用 CPU，吞吐量下降 |
| **浮动垃圾 & Concurrent Mode Failure** | 并发清除时用户线程仍在产生垃圾（浮动垃圾）；若预留空间不够就退化为 Serial Old 单线程 Full GC，停顿反而变长 |

> CMS 被淘汰的根本原因：碎片问题 + 无法与更大堆和可预测停顿的需求匹配，被 G1 取代。

---

## 四、G1（Garbage First）—— 当前主流

**核心思想**：把堆划分成大量**大小相等的 Region**，不再固定分代，每个 Region 动态扮演 Eden/Survivor/Old/Humongous 角色。

```
┌──┬──┬──┬──┬──┬──┬──┐
│E │O │S │E │H │O │E │   每个方块是一个 Region（1~32MB）
├──┼──┼──┼──┼──┼──┼──┤   E=Eden S=Survivor O=Old H=大对象
│O │E │O │S │E │O │H │
└──┴──┴──┴──┴──┴──┴──┘
   优先回收「垃圾最多」的 Region → Garbage First
```

**关键特性**：

| 特性 | 说明 |
|:---|:---|
| **可预测停顿** | `-XX:MaxGCPauseMillis` 设目标停顿（如 200ms），G1 据此挑选回收的 Region 数 |
| **Region 化** | 局部用复制算法，整体看是标记-整理 → **无碎片** |
| **Mixed GC** | 回收全部新生代 + 部分收益高的老年代 Region |
| **SATB** | 并发标记用原始快照解决漏标 |
| **不要求整堆连续回收** | 按「性价比」优先回收垃圾多的 Region |

**G1 的 GC 过程**：Young GC（STW）→ 并发标记周期 → Mixed GC。回收失败时同样退化为 Full GC（早期单线程，JDK 10+ 并行）。

> G1 适合大堆（6GB+）、要求停顿可控的场景，是 JDK 9 起的默认收集器。

## 五、ZGC / Shenandoah —— 超低延迟前沿（P7 加分）

面向**超大堆（TB 级）+ 亚毫秒停顿**：

| 收集器 | 关键技术 | 停顿 |
|:---|:---|:---|
| **ZGC** | **染色指针（Colored Pointers）** + **读屏障** + 并发整理 | 目标 <1ms，几乎与堆大小无关 |
| **Shenandoah** | **Brooks 转发指针** + 读屏障 + 并发整理 | 与 ZGC 类似，OpenJDK 出品 |

**ZGC 为何这么快？**
- 把 GC 信息**染色**存进指针的高位（标记、重映射等），配合读屏障在访问时按需修正引用。
- 几乎所有阶段（标记、转移、重映射）都**与用户线程并发**，只留极短的 STW 做根扫描。
- 停顿时间**不随堆增大而增长**——这是与 CMS/G1 的本质区别。

## 六、收集器选型（面试怎么答）

| 场景 | 推荐 | 理由 |
|:---|:---|:---|
| 小内存 / 客户端 | Serial | 简单、无线程切换开销 |
| 后台计算 / 批处理，吞吐优先 | Parallel Scavenge + Parallel Old | 最大化吞吐量 |
| 一般在线服务，堆中等 | G1 | 停顿可控，默认选择 |
| 大堆（几十 GB+）、低延迟苛刻 | ZGC / Shenandoah | 亚毫秒停顿，停顿与堆无关 |
| 老系统 | CMS（已淘汰，不建议新用） | — |

> P7 回答框架：先问**吞吐量还是延迟优先**、**堆多大**、**能接受多长停顿**，再给出收集器 + 关键参数，最后说怎么用 GC 日志验证。

## 七、常用参数速查

```bash
# 选择收集器
-XX:+UseSerialGC          # Serial + Serial Old
-XX:+UseParallelGC        # Parallel Scavenge + Parallel Old（吞吐）
-XX:+UseConcMarkSweepGC   # CMS（JDK 9 起弃用）
-XX:+UseG1GC              # G1（JDK 9+ 默认）
-XX:+UseZGC               # ZGC

# G1 关键参数
-XX:MaxGCPauseMillis=200      # 目标最大停顿
-XX:G1HeapRegionSize=16m      # Region 大小
-XX:InitiatingHeapOccupancyPercent=45  # 触发并发标记的堆占用阈值

# 通用堆参数
-Xms4g -Xmx4g                 # 初始/最大堆，生产建议相等
-Xmn2g                        # 新生代大小
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=256m
```

## 八、易错点

| 易错点 | 澄清 |
|:---|:---|
| **CMS 用标记-整理** | CMS 用**标记-清除**，所以有碎片问题 |
| **G1 没有分代** | G1 **保留逻辑分代**，只是物理上 Region 化、动态分配角色 |
| **G1/ZGC 完全没 STW** | 仍有短暂 STW（如根扫描），只是极短且可控 |
| **Parallel 就是低延迟** | Parallel 系列追求**吞吐量**，全程 STW，不是低延迟 |
| **`MaxGCPauseMillis` 越小越好** | 设太小会导致每次回收 Region 变少、GC 更频繁，吞吐反降 |

---

## 九、一句话总结

收集器是 GC 算法的落地：**Serial/Parallel** 全程 STW（分别偏简单/吞吐），**CMS** 首次实现老年代并发但受碎片和 Concurrent Mode Failure 拖累，**G1** 用 Region 化 + 可预测停顿成为主流默认，**ZGC/Shenandoah** 靠染色指针/转发指针 + 读屏障做到与堆大小无关的亚毫秒停顿。选型先定「吞吐 vs 延迟 + 堆大小」，再配参数并用 GC 日志验证。
