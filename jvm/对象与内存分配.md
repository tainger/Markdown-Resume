# 对象与内存分配

从「一个 `new` 到底发生了什么」到「对象在内存里长什么样、分配到哪」，是连接内存结构与 GC 的关键一环，也是 P7 面试区分深度的地方。

---

## 一、对象的创建过程（一个 new 的旅程）

```java
Object obj = new Object();
```

背后执行五步：

| 步骤 | 做什么 | 关键点 |
|:---|:---|:---|
| 1. **类加载检查** | 检查 `new` 指令的类是否已加载、解析、初始化 | 没有则先触发类加载（见 [类加载机制.md](类加载机制.md)） |
| 2. **分配内存** | 从堆划出一块确定大小的内存 | 指针碰撞 vs 空闲列表（见下） |
| 3. **初始化零值** | 分配的内存全置为零值 | 所以字段不赋值也有默认值（0/null/false） |
| 4. **设置对象头** | 填 Mark Word、类型指针、（数组则长度） | 见第三节对象布局 |
| 5. **执行 `<init>`** | 调构造方法，按代码给字段赋值 | 此时对象才真正「可用」 |

### 内存分配的两种方式

| 方式 | 适用场景 | 说明 |
|:---|:---|:---|
| **指针碰撞** | 堆内存规整（有整理的收集器，如 Serial、G1） | 用过的在一边，空闲在另一边，指针挪一下 |
| **空闲列表** | 堆内存不规整（标记-清除，如 CMS） | 维护一张空闲块列表，找一块够大的划出 |

### 并发安全：CAS + TLAB

多线程同时分配会冲突，两种解决：
- **CAS + 失败重试**：保证指针更新原子性。
- **TLAB（Thread Local Allocation Buffer）**：每个线程在 Eden 预先分一小块**私有缓冲区**，线程内分配无需同步，快用完了再走 CAS 申请新的。默认开启（`-XX:+UseTLAB`）。

## 二、对象的内存分配策略（对象去哪了）

对象**优先在 Eden 分配**，但有若干规则决定它可能直接进老年代。

| 策略 | 规则 | 相关参数 |
|:---|:---|:---|
| **优先 Eden** | 新对象先放 Eden，满了触发 Minor GC | — |
| **大对象直接进老年代** | 超过阈值的大对象（如长数组）直接进老年代，避免在 Eden/Survivor 间反复复制 | `-XX:PretenureSizeThreshold` |
| **长期存活进老年代** | 对象每熬过一次 Minor GC 年龄 +1，达到阈值晋升 | `-XX:MaxTenuringThreshold`（默认 15） |
| **动态年龄判定** | Survivor 中同龄对象总大小 > S 区一半，则 ≥ 该年龄的直接晋升 | 不必等到 15 |
| **空间分配担保** | Minor GC 前检查老年代剩余空间是否够，不够可能提前 Full GC | `-XX:+HandlePromotionFailure` |

> 面试高频：**为什么要有两个 Survivor 区（S0/S1）？** 采用复制算法，每次只用一个，回收时把 Eden + 存活 Survivor 的活对象复制到另一个空 Survivor，避免了标记-清除产生的内存碎片，也保证复制目标区始终是空的。

## 三、对象的内存布局

HotSpot 中对象在堆里分三部分：

```
┌─────────────────────────────────────┐
│  对象头 Header                        │
│   ├─ Mark Word（运行时数据）           │  → 8 字节（64 位）
│   │   哈希码、GC 分代年龄、锁状态、       │
│   │   偏向锁线程ID、指向锁记录/monitor  │
│   └─ 类型指针 Klass Pointer            │  → 4 字节（开启压缩指针）
│       指向方法区/元空间的类元数据        │
│   （数组还有一段：数组长度）             │
├─────────────────────────────────────┤
│  实例数据 Instance Data               │  → 真正的字段值
├─────────────────────────────────────┤
│  对齐填充 Padding                     │  → 补齐到 8 字节的整数倍
└─────────────────────────────────────┘
```

| 组成 | 作用 |
|:---|:---|
| **Mark Word** | 存哈希码、GC 年龄、**锁状态标志**（无锁/偏向/轻量级/重量级），锁升级就改这里 |
| **类型指针** | 指向类元数据，告诉 JVM「这是哪个类的实例」 |
| **实例数据** | 各字段的值，会按类型重排以节省空间 |
| **对齐填充** | HotSpot 要求对象大小是 8 字节整数倍 |

> Mark Word 是理解 **synchronized 锁升级**（无锁→偏向→轻量→重量）的基础，属于并发与 JVM 的交叉考点。

## 四、对象的访问定位

引用（reference）如何找到堆里的对象？两种方式：

| 方式 | 机制 | 优点 | 缺点 | HotSpot 选择 |
|:---|:---|:---|:---|:---:|
| **句柄访问** | 堆中划出句柄池，引用存句柄地址，句柄含「对象实例指针 + 类型指针」 | 对象移动（GC）时只改句柄，reference 不变 | 多一次间接寻址，慢 | — |
| **直接指针** | 引用直接存对象地址 | 少一次寻址，快 | 对象移动要改 reference | ✅ **HotSpot 用这种** |

## 五、逃逸分析与优化（P7 加分项）

**逃逸分析（Escape Analysis）**：JIT 编译期分析一个对象的作用域是否「逃逸」出方法/线程。据此做三种优化：

| 逃逸程度 | 优化 | 效果 |
|:---|:---|:---|
| **不逃逸**（只在方法内用） | **栈上分配** | 对象随栈帧出栈自动销毁，减轻 GC 压力 |
| **不逃逸** | **标量替换** | 把对象拆成一个个基本类型标量，甚至不创建对象 |
| **不逃逸出线程** | **锁消除** | 去掉不可能竞争的 synchronized（如局部 StringBuffer） |

```java
// sb 不逃逸出方法 → 锁消除 + 可能标量替换
public String concat(String a, String b) {
    StringBuffer sb = new StringBuffer(); // StringBuffer 内部 synchronized
    sb.append(a).append(b);               // 锁被消除，等价 StringBuilder
    return sb.toString();
}
```

> 结论：**并非所有对象都在堆上分配**。逃逸分析（`-XX:+DoEscapeAnalysis`，默认开）让不逃逸对象可能栈上分配或被标量替换。这是「Java 对象一定在堆上」这一说法的重要反例。

## 六、易错点

| 易错点 | 澄清 |
|:---|:---|
| **对象一定在堆分配** | 逃逸分析后可能栈上分配 / 标量替换 |
| **`new` 完对象就能用** | 要到 `<init>` 执行完字段才被正确赋值；分配后只是零值 |
| **年龄到 15 才晋升** | 还有大对象直进老年代、动态年龄判定等提前晋升规则 |
| **句柄和直接指针混淆** | HotSpot 用**直接指针**，句柄是另一种可选实现 |
| **Mark Word 存类信息** | 类信息在**类型指针**里；Mark Word 存运行时数据（锁、GC 年龄等） |

---

## 七、一句话总结

一个 `new` 要经历「类加载检查 → 分配内存（指针碰撞/空闲列表 + TLAB）→ 零值 → 设对象头 → `<init>`」；对象在堆里由**对象头（Mark Word + 类型指针）+ 实例数据 + 对齐填充**组成；分配上**优先 Eden**，大对象/长寿对象进老年代；而**逃逸分析**让不逃逸对象可以栈上分配、标量替换、锁消除——所以对象未必都在堆上。
