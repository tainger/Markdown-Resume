# 性能调优与诊断

P7 面试最看重「能不能落地」：知道 JIT 怎么让 Java 变快、会用工具定位问题、有过真实的 OOM/CPU 高/GC 频繁排查经验。这一篇把执行引擎、调优参数、诊断工具和实战套路串起来。

---

## 一、执行引擎：解释执行 + JIT 编译

Java「一次编译，到处运行」靠字节码；运行时字节码有两条路：

| 方式 | 谁执行 | 特点 |
|:---|:---|:---|
| **解释执行** | 解释器逐条翻译字节码 | 启动快、峰值性能低 |
| **JIT 编译** | 把热点代码编译成本地机器码 | 启动慢、峰值性能高 |

HotSpot 采用**混合模式**：先解释执行，探测到**热点代码**再 JIT 编译，兼顾启动速度和长期性能。

### 热点探测与分层编译

- **热点判定**：基于计数器——方法调用计数器 + 回边计数器（循环），超阈值即热点。
- **分层编译（Tiered Compilation）**：

| 层级 | 编译器 | 说明 |
|:---|:---|:---|
| 0 | 解释器 | 纯解释 |
| 1~3 | **C1（Client）** | 编译快、优化少，带性能监控 |
| 4 | **C2（Server）** | 编译慢、深度优化，用于最热的代码 |

> **OSR（On-Stack Replacement，栈上替换）**：一个正在执行的长循环，可以在不退出方法的情况下，把循环体替换成编译后的机器码。

### JIT 的关键优化

| 优化 | 说明 |
|:---|:---|
| **方法内联（Inlining）** | 把被调方法体直接嵌入调用处，消除调用开销，是最重要的优化 |
| **逃逸分析** | 栈上分配 / 标量替换 / 锁消除（见 [对象与内存分配.md](对象与内存分配.md)） |
| **循环优化** | 循环展开、边界检查消除 |
| **去虚拟化** | 单实现的虚方法调用优化成直接调用 |

> **为什么 Java 长跑后反而比 C 慢不了多少？** 就是 JIT + 内联 + 逃逸分析在运行期基于**实际热点**做了深度优化，甚至能做静态编译做不到的激进优化（失败可去优化回退解释执行）。

## 二、核心调优参数

### 堆与元空间

```bash
-Xms4g -Xmx4g                # 初始/最大堆，生产设相等，避免动态扩容抖动
-Xmn2g                       # 新生代大小（或用 -XX:NewRatio）
-XX:SurvivorRatio=8          # Eden:Survivor = 8:1
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=256m    # 限制元空间，防类加载器泄漏拖垮机器
-Xss512k                     # 每线程栈大小
```

### GC 与日志

```bash
-XX:+UseG1GC                 # 选收集器
-XX:MaxGCPauseMillis=200     # G1 目标停顿

# GC 日志（JDK 9+ 统一日志）
-Xlog:gc*:file=gc.log:time,uptime,level,tags
# JDK 8 写法
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log
```

### OOM 现场保留（生产必配）

```bash
-XX:+HeapDumpOnOutOfMemoryError          # OOM 时自动 dump 堆
-XX:HeapDumpPath=/data/dumps/            # dump 文件路径
-XX:+ExitOnOutOfMemoryError              # OOM 后退出，配合重启（可选）
```

> 生产环境**必开** `HeapDumpOnOutOfMemoryError`——OOM 往往难复现，没有现场 dump 就无从分析。

## 三、诊断工具箱

### JDK 自带命令行（面试要能说出用途）

| 工具 | 用途 | 典型命令 |
|:---|:---|:---|
| **jps** | 列出 Java 进程和 PID | `jps -l` |
| **jstat** | 看 GC 统计、各代占用 | `jstat -gcutil <pid> 1000`（每秒一次） |
| **jmap** | 看内存、导出堆 dump | `jmap -dump:format=b,file=heap.bin <pid>` |
| **jstack** | 打印线程栈（**查死锁、CPU 高**） | `jstack <pid>` |
| **jinfo** | 查看/修改 JVM 参数 | `jinfo -flags <pid>` |
| **jcmd** | 万能命令，整合上述功能 | `jcmd <pid> GC.heap_info` |

### 可视化 / 增强工具

| 工具 | 用途 |
|:---|:---|
| **JVisualVM / JMC** | 图形化监控内存、线程、CPU 采样 |
| **MAT（Memory Analyzer）** | 分析堆 dump，找内存泄漏（Leak Suspects、支配树、GC Roots 引用链） |
| **Arthas**（阿里开源，强推） | 线上诊断利器：`dashboard` 看总览、`thread` 查繁忙线程、`trace/watch` 追方法耗时/参数、`jad` 反编译、`heapdump` |
| **async-profiler** | 低开销火焰图，定位 CPU/内存热点 |

## 四、实战排查套路（P7 必备）

### 场景 1：CPU 飙高

```bash
# 1. 找到最耗 CPU 的 Java 进程
top                              # 记下 PID
# 2. 找到该进程里最耗 CPU 的线程
top -Hp <pid>                    # 记下线程 TID（十进制）
# 3. TID 转十六进制
printf "%x\n" <tid>              # 得到 nid
# 4. 在线程栈里定位这个线程在干什么
jstack <pid> | grep <nid> -A 30
```

用 Arthas 更快：`thread -n 3`（直接列出最忙的 3 个线程栈）。

> 常见原因：死循环、频繁 GC（此时栈里多是 GC 线程）、正则回溯爆炸、锁竞争激烈。

### 场景 2：内存溢出 OOM / 内存泄漏

```
1. 现场：靠 -XX:+HeapDumpOnOutOfMemoryError 拿到 heap.bin
   （或 jmap -dump 主动导出，注意会 STW，生产慎用）
2. 用 MAT 打开 dump：
   - 看 Histogram：哪个类实例最多/占用最大
   - 看 Dominator Tree：谁支配了大块内存
   - 看 Leak Suspects：自动报告可疑泄漏点
   - 顺 GC Roots 引用链找到「谁在强引用它导致回收不了」
3. 定位代码：常见泄漏源——静态集合只增不减、ThreadLocal 未 remove、
   连接/流未关闭、缓存无淘汰策略、监听器未注销
```

### 场景 3：频繁 Full GC / GC 停顿长

```bash
jstat -gcutil <pid> 1000 10      # 观察 YGC/FGC 次数和耗时增长
# 结合 GC 日志看：是老年代满了？元空间满了？还是晋升失败？
```

排查方向：

| 现象 | 可能原因 |
|:---|:---|
| Full GC 频繁、老年代回收后仍很满 | 内存泄漏 / 堆太小 / 大对象过多 |
| YGC 频繁 | 新生代太小 / 短命对象产生过快 |
| 单次停顿长 | 收集器选型不当 / 堆过大 / 未用并发收集器 |
| Metaspace 触发 Full GC | 类加载器泄漏（热部署、动态代理） |

## 五、调优的基本原则（回答框架）

1. **先定目标**：吞吐量优先，还是延迟（停顿）优先？可接受的停顿是多少？
2. **先测量再优化**：用 GC 日志 / 监控拿数据，别拍脑袋改参数。
3. **一次只改一个变量**：改完对比指标，确认因果。
4. **优先解决代码问题**：多数「GC 问题」其实是代码问题（内存泄漏、对象创建过多），调参数只是治标。
5. **合理设置堆**：`-Xms = -Xmx` 避免抖动；新生代不宜过小（短命对象多时）。

> P7 加分：不要一上来背参数，而是「**目标 → 观测 → 假设 → 验证**」的科学方法，参数是手段不是目的。

## 六、易错点

| 易错点 | 澄清 |
|:---|:---|
| **JIT 一开始就编译** | 先解释执行，热点代码才 JIT（分层编译） |
| **生产随便 jmap -dump** | dump 会 STW，大堆可能卡住服务，优先靠自动 dump |
| **CPU 高就是死循环** | 也可能是频繁 GC，要先看线程栈里是不是 GC 线程 |
| **调大堆就能解决 OOM** | 内存泄漏时调大只是推迟 OOM，必须找到泄漏点 |
| **`System.gc()` 手动救急** | 触发 Full GC 加剧停顿；但**无脑 `-XX:+DisableExplicitGC` 禁用有坑**——Netty/NIO 堆外内存靠它兜底回收，禁用可能 `Direct buffer memory` OOM。推荐 `-XX:+ExplicitGCInvokesConcurrent` 让它走并发 GC |

---

## 七、一句话总结

Java 靠**解释执行 + JIT 分层编译（C1/C2）+ 内联/逃逸分析**兼顾启动速度与峰值性能。调优要**先定目标（吞吐 vs 延迟）、用数据说话、一次改一个变量**；生产必配 `HeapDumpOnOutOfMemoryError` + GC 日志。排查三板斧：**CPU 高**（top -Hp + jstack/Arthas thread）、**OOM**（heap dump + MAT 找引用链）、**频繁 GC**（jstat + GC 日志）。多数「JVM 问题」根子在代码。

## 九、性能调优参数速查

第二节是「必配核心参数」，本节按类别给全量速查（默认值 + 生产建议），面试问参数时按分类答，不要东拼西凑。

### 1. 堆与内存

| 参数 | 默认值 | 作用 | 生产建议 |
|:---|:---|:---|:---|
| `-Xms` / `-Xmx` | 物理内存 1/64 ~ 1/4 | 初始 / 最大堆 | **设相等**，取容器内存的 50%~75% |
| `-Xmn` | 由 NewRatio 推导 | 新生代大小 | 吞吐量收集器可设；**G1 不要设**（破坏自适应） |
| `-XX:NewRatio=2` | 2 | 老年代:新生代 = 2:1 | 与 `-Xmn` 二选一 |
| `-XX:SurvivorRatio=8` | 8 | Eden:单个 Survivor = 8:1 | 即 Eden:S0:S1 = 8:1:1 |
| `-XX:MaxTenuringThreshold=15` | Parallel=15 / CMS=6 | 对象晋升老年代的年龄上限 | 最大就是 **15**（对象头年龄字段 4 bit） |
| `-XX:PretenureSizeThreshold` | 无 | 大对象直接进老年代 | **仅 Serial/ParNew 生效**；G1 用 Humongous 对象（超 Region 一半） |
| `-XX:MetaspaceSize` | ~20MB | 触发元空间首次 GC 的**高水位**（不是预分配大小） | 类多的应用显式设 256m，避免启动早期反复 Full GC |
| `-XX:MaxMetaspaceSize` | 不限（受物理内存约束） | 元空间上限 | **必须设**，防类加载器泄漏拖垮机器 |
| `-XX:MaxDirectMemorySize` | ≈ `-Xmx` | 堆外直接内存上限 | Netty/NIO 应用显式设，防堆外 OOM |
| `-Xss512k` | 512k~1M（平台相关） | **每个线程**的栈大小 | 线程多的服务可调小 256k~512k，换更多线程 |
| `-XX:+AlwaysPreTouch` | 关 | 启动时把堆内存页全部 touch 一遍 | 大堆 / 低延迟服务开：启动变慢，运行期无缺页中断抖动 |

### 2. 收集器选型（参数互斥，选一个）

| 参数 | 收集器组合 | 适用 |
|:---|:---|:---|
| `-XX:+UseSerialGC` | Serial + Serial Old | 客户端、小堆（几百 MB） |
| `-XX:+UseParallelGC` | Parallel Scavenge + Parallel Old | **JDK 8 默认**，吞吐量优先（批处理、计算） |
| `-XX:+UseConcMarkSweepGC` | ParNew + CMS | 低延迟（JDK 9 废弃、14 移除，遗留系统） |
| `-XX:+UseG1GC` | G1 | **JDK 9+ 默认**，延迟可控，堆 4G~32G 首选 |
| `-XX:+UseZGC` | ZGC | JDK 15 转正（11 需 `-XX:+UnlockExperimentalVMOptions`），JDK 21 分代 ZGC，亚毫秒停顿 |

### 3. G1 专项参数

| 参数 | 默认 | 作用 |
|:---|:---|:---|
| `-XX:MaxGCPauseMillis=200` | 200ms | 停顿时间**软目标**（不是硬保证）；设太小 → 新生代变小、GC 更频繁 |
| `-XX:G1HeapRegionSize` | 堆/2048 向上取 2 的幂（1~32MB） | Region 大小 |
| `-XX:InitiatingHeapOccupancyPercent=45` | 45（JDK9+ 默认自适应） | 堆占用超水位触发并发标记 |
| `-XX:G1ReservePercent=10` | 10 | 保留内存，防 evacuation（转移）失败 |
| `-XX:G1NewSizePercent=5` / `G1MaxNewSizePercent=60` | 5 / 60 | 新生代占堆比例上下限 |
| `-XX:+ParallelRefProcEnabled` | 关（JDK8） | 并行处理 Reference（Final/Soft/Weak），建议开 |

### 4. CMS 专项参数（遗留系统）

```bash
-XX:+UseConcMarkSweepGC
-XX:CMSInitiatingOccupancyFraction=70          # 老年代占 70% 触发 CMS GC
-XX:+UseCMSInitiatingOccupancyOnly             # 只用上面设定的水位，不让 JVM 自适应
-XX:+UseCMSCompactAtFullCollection             # Full GC 时整理碎片（标记-清除的补偿）
-XX:CMSFullGCsBeforeCompaction=0               # 每次 Full GC 都压缩
-XX:+CMSScavengeBeforeRemark                   # remark 前先 YGC，减少并发标记根扫描开销
```

### 5. GC 线程数

| 参数 | 默认 | 作用 |
|:---|:---|:---|
| `-XX:ParallelGCThreads` | 核数 ≤8 取核数，否则 8+(核-8)×5/8 | STW 阶段并行线程数 |
| `-XX:ConcGCThreads` | ParallelGCThreads 的 1/4 | 并发标记线程数 |

### 6. GC 日志（JDK 8 与 JDK 9+ 两套写法）

```bash
# ---- JDK 8 ----
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-XX:+PrintGCApplicationStoppedTime     # 打印每次 STW 停顿时长（排查 safepoint）
-XX:+PrintTenuringDistribution         # 打印对象晋升年龄分布（调 Survivor/晋升阈值）
-Xloggc:/data/logs/gc.log
-XX:+UseGCLogFileRotation              # 日志滚动
-XX:NumberOfGCLogFiles=5
-XX:GCLogFileSize=20M

# ---- JDK 9+ 统一日志（-Xlog）----
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m
# safepoint 停顿
-Xlog:safepoint:file=safepoint.log:time,uptime
```

### 7. OOM 现场与 System.gc

```bash
-XX:+HeapDumpOnOutOfMemoryError        # OOM 自动 dump（生产必开）
-XX:HeapDumpPath=/data/dumps/
-XX:+ExitOnOutOfMemoryError            # OOM 后退出，交给 K8s/守护进程重启
-XX:OnOutOfMemoryError="sh /data/script/oom-kill.sh"   # OOM 时执行脚本（告警+自杀）

# System.gc() 处理（二选一）：
-XX:+DisableExplicitGC                 # 直接忽略 System.gc()
-XX:+ExplicitGCInvokesConcurrent       # System.gc() 走并发 GC（推荐，见易错点）
```

**`OnOutOfMemoryError` 脚本的意义（面试常问「配了 dump 为什么还要脚本」）**：

JVM 抛 OOM 后、进程退出前，会 `fork()` 一个**独立进程**执行该 shell 脚本，做三件事：补轻量现场、发告警、自杀重启。

```bash
#!/bin/bash
# /data/script/oom-kill.sh
PID=$(pgrep -f my-app.jar)
# 1. 补系统级 / 轻量现场（heap dump 又大又慢，这些几秒出结果）
jstack -l $PID  > /data/dumps/oom-jstack.log 2>&1   # 线程栈：死锁/阻塞现场
jmap   -histo $PID > /data/dumps/oom-histo.log 2>&1 # 对象直方图：哪个类实例最多
top -b -n1 -p $PID > /data/dumps/oom-top.log        # CPU/内存快照
dmesg -T | tail -50 > /data/dumps/oom-dmesg.log     # 内核日志：容器 OOMKilled 的关键证据
# 2. 发告警（JVM 挂了 K8s 会重启，但没人主动喊，运维要等用户投诉）
curl -X POST "https://oapi.dingtalk.com/robot/xxx" \
  -d '{"msgtype":"text","text":{"content":"订单服务 OOM，请查 /data/dumps"}}'
# 3. 自杀，交给 K8s / 守护进程拉新实例
kill -9 $PID
```

| 参数 | 行为 | 定位 |
|:---|:---|:---|
| `HeapDumpOnOutOfMemoryError` | 自动 dump 完整堆（GB 级，给 MAT 事后分析） | 重现场，慢 |
| `ExitOnOutOfMemoryError` | OOM 后 JVM **直接退出**（兜底防僵死：OOM 发生在非主线程时，进程可能端口还占着但不服务） | 保证死透 |
| `OnOutOfMemoryError` | 执行自定义脚本：补轻量证据 + 告警 + `kill -9` | 死前留遗言、喊人、确认重启 |

> 三者是**组合拳**不是三选一。坑：脚本是**同步执行**的，JDK 8 部分版本有脚本阻塞导致退出流程卡住的问题（JDK-8157025），脚本末尾务必兜底 `kill -9`。

### 8. JIT 编译

| 参数 | 默认 | 作用 |
|:---|:---|:---|
| `-Xmixed` / `-Xint` / `-Xcomp` | `-Xmixed` | 混合（解释+JIT）/ 纯解释 / 纯编译；生产永远默认 |
| `-XX:+TieredCompilation` | JDK8+ 默认开 | 分层编译（C1+C2） |
| `-XX:CompileThreshold=10000` | 10000 | 方法调用计数热点阈值（开启分层后由多层阈值接管，一般不调） |
| `-XX:CICompilerCount` | 按 CPU 核数自适应 | JIT 编译线程数 |

### 9. 容器环境（JDK 10+ / JDK 8u191+）

```bash
-XX:+UseContainerSupport               # 默认开：JVM 能识别 cgroup 的 CPU/内存限制
-XX:MaxRAMPercentage=75.0              # 堆占容器内存上限的 75%（替代写死 -Xmx）
-XX:InitialRAMPercentage=75.0          # -Xms 同理
```

> 容器里写死 `-Xmx` 容易和容器 limit 不一致（OOMKilled）；`MaxRAMPercentage` 让堆随 limit 自适应，剩余内存留给元空间、堆外、栈和 JVM 自身。

### 10. 生产配置模板

```bash
# ---- JDK 8，4C8G 容器，G1（8u 也推荐 G1）----
-server -Xms4g -Xmx4g
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=256m
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
-XX:+ParallelRefProcEnabled
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dumps/
-XX:+ExitOnOutOfMemoryError
-XX:+ExplicitGCInvokesConcurrent
-Xloggc:/data/logs/gc.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps
-XX:+PrintGCApplicationStoppedTime
-XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=5 -XX:GCLogFileSize=20M

# ---- JDK 17/21，低延迟，ZGC ----
-Xms8g -Xmx8g -XX:+UseZGC
-XX:MaxMetaspaceSize=256m
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dumps/
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m
```

### 11. 易错点

| 易错点 | 澄清 |
|:---|:---|
| **`MetaspaceSize` 是预分配大小** | 是触发元空间 GC 的**高水位**；达到就 Full GC 并尝试上调，类多的应用要显式设大 |
| **`MaxGCPauseMillis` 越小越好** | 软目标；设太小会压缩新生代、GC 次数暴增，总吞吐反降 |
| **G1 也设 `-Xmn` / `NewRatio`** | G1 靠 Region 动态调整新生代，硬编码会让自适应失效 |
| **`DisableExplicitGC` 无脑开** | Netty/NIO 的堆外内存回收靠 `System.gc()` 兜底（Cleaner 需 GC 才回收）；直接禁用可能 `Direct buffer memory` OOM。用 **`ExplicitGCInvokesConcurrent`** 让它走并发 GC 更稳 |
| **`SurvivorRatio=8` 是 Eden:S0:S1** | 是 Eden:**单个** Survivor = 8:1，总比例 8:1:1 |
| **晋升年龄随便调大** | 上限 15（对象头 4 bit）；调大让短命对象滞留 Survivor，可能触发 Survivor 溢出提前晋升 |
| **堆设得越满越好** | 容器内堆建议只占 limit 的 50%~75%，其余给元空间、堆外、线程栈、CodeCache，否则容器 OOMKilled |
| **参数越多越好** | 默认值经过充分验证，90% 的场景只需「堆大小 + 收集器 + GC 日志 + dump」四类 |

### 12. 一句话总结

参数按「**堆内存（-Xms=-Xmx、元空间上限、Xss）→ 收集器（8 用 Parallel/G1，9+ 默认 G1，低延迟 ZGC）→ GC 日志（JDK8 PrintGC* / JDK9 -Xlog）→ OOM 现场（dump + 退出重启）**」四类记忆；G1 不设 -Xmn、停顿目标是软指标；容器环境用 `MaxRAMPercentage` 替代写死堆；`System.gc()` 用 `ExplicitGCInvokesConcurrent` 而非简单禁用。**先观测（GC 日志 + jstat）再调参，一次只改一个变量。**
