# 类加载机制

类加载解决「一个 `.class` 文件如何变成 JVM 中可用的 Class 对象」。核心考点是**类加载的七个阶段**、**双亲委派模型**，以及 P7 层面的**如何/为何打破双亲委派**。

---

## 一、类的生命周期（七个阶段）

```
加载 → [ 验证 → 准备 → 解析 ] → 初始化 → 使用 → 卸载
 Load    ─────── 连接 Linking ──────   Init   Use   Unload
```

| 阶段 | 做什么 | 关键点 |
|:---|:---|:---|
| **加载 Loading** | 读取 `.class` 字节流 → 生成 `Class` 对象 | 来源可以是文件、网络、动态生成（代理）、jar |
| **验证 Verification** | 校验字节码格式、语义、符号引用合法性 | 保证不危害 JVM 安全 |
| **准备 Preparation** | 为**静态变量**分配内存并设**零值** | `static int a = 5` 此阶段 a=0（不是 5！） |
| **解析 Resolution** | 把常量池的**符号引用**换成**直接引用** | 可能延迟到初始化后（动态绑定） |
| **初始化 Initialization** | 执行 `<clinit>()`，真正给静态变量赋值、跑静态块 | `a` 此时才 = 5 |
| **使用 Using** | 正常运行 | — |
| **卸载 Unloading** | 回收 Class | 需类加载器被回收，条件苛刻 |

> **准备 vs 初始化** 的区别是高频陷阱：准备阶段 `static int a = 5` 只把 a 置为**零值 0**；到初始化阶段执行 `<clinit>` 才赋成 **5**。（`static final` 常量在准备阶段就直接赋值。）

### 类初始化的触发时机（主动引用，会触发 `<clinit>`）

| 场景 | 举例 |
|:---|:---|
| `new` 对象、访问静态字段、调用静态方法 | `new A()`、`A.staticField` |
| 反射调用 | `Class.forName("A")` |
| 初始化子类时父类未初始化 | 先初始化父类 |
| 启动类（含 main 的类） | JVM 启动 |

**被动引用**不触发初始化：通过子类访问父类静态字段、`A[] arr = new A[10]`（只初始化数组类型）、引用 `static final` 常量（编译期已入常量池）。

## 二、类加载器与双亲委派模型

### 三层类加载器（JDK 8 及以前）

| 加载器 | 加载范围 | 实现 |
|:---|:---|:---|
| **启动类加载器 Bootstrap** | `<JAVA_HOME>/lib`、核心类库（`rt.jar`） | C++ 实现，Java 中显示为 null |
| **扩展类加载器 Extension** | `<JAVA_HOME>/lib/ext` | Java 实现 |
| **应用类加载器 Application** | classpath 下用户类 | 默认的系统类加载器 |
| （自定义） | 自定义路径/来源 | 继承 `ClassLoader` |

> JDK 9+ 模块化后，扩展类加载器被 **Platform ClassLoader** 取代，但双亲委派思想不变。

### 双亲委派模型（Parents Delegation）

```
      收到加载请求
          │
          ▼
   ┌─────────────┐  先委派给父加载器 ↑
   │ Application  │───────────────┐
   └─────────────┘                │
   ┌─────────────┐                ▼
   │ Extension    │───────────► 一路向上委派
   └─────────────┘                │
   ┌─────────────┐                ▼
   │ Bootstrap    │  父加载不了，才由子加载器自己加载 ↓
   └─────────────┘
```

**工作流程**：一个类加载请求先**逐级向上委派**给父加载器，父加载器能加载就加载；只有父加载器加载不了（找不到），子加载器才自己尝试。

**为什么要双亲委派？（面试必答）**

| 好处 | 说明 |
|:---|:---|
| **避免类重复加载** | 同一个类只被最顶层能加载它的加载器加载一次 |
| **保证核心类安全** | 用户自己写 `java.lang.Object` 也不会被加载，因为 Bootstrap 已加载了正版，防止核心 API 被篡改 |

> 类的「唯一性」由**类加载器 + 全限定名**共同决定：同一个类被两个不同加载器加载，是**两个不同的类**，`instanceof`、`equals` 都不成立。

## 三、打破双亲委派（P7 深度）

双亲委派不是强制的，很多框架**主动打破**它。三个经典案例：

| 案例 | 为什么打破 | 怎么打破 |
|:---|:---|:---|
| **JDBC / SPI**（`java.sql.Driver`） | 核心接口在 rt.jar（Bootstrap 加载），但实现是第三方 jar（Application 加载），父加载器加载不了子类实现 | **线程上下文类加载器（TCCL）**：父加载器「反向」委托子加载器加载实现 |
| **Tomcat** | 每个 Web 应用要**隔离**（不同应用可用同名不同版本的库），还要能加载共享库 | 每个 webapp 一个 `WebappClassLoader`，**优先自己加载**（打破向上委派），再委派父加载器 |
| **OSGi / 热部署** | 模块化、可动态替换类 | 网状类加载器结构，按需委派 |

### SPI 与 ServiceLoader

```java
// JDBC 4.0 起：DriverManager 用 ServiceLoader 自动发现驱动
ServiceLoader<Driver> loaders = ServiceLoader.load(Driver.class);
// 内部用 Thread.currentThread().getContextClassLoader() 加载实现类
```

> 线程上下文类加载器（TCCL）是打破双亲委派、实现 SPI 的关键机制：它让处于上层的 Bootstrap 加载的代码，能「借用」下层的 Application 加载器去加载实现类。

## 四、字节码文件结构（了解即可，P7 偶尔问）

`.class` 文件是一组以 8 字节为基础单位的二进制流，固定结构：

| 部分 | 内容 |
|:---|:---|
| 魔数 Magic | `0xCAFEBABE`，标识这是 class 文件 |
| 版本号 | 主/次版本，决定能否被当前 JVM 加载 |
| **常量池** | 字面量 + 符号引用（类/方法/字段名） |
| 访问标志 | public/final/abstract 等 |
| 类/父类/接口索引 | 继承关系 |
| 字段表、方法表 | 字段和方法定义（方法体在 Code 属性里） |
| 属性表 | Code、LineNumberTable、注解等 |

> 常见工具：`javap -c -v XXX.class` 反编译看字节码指令；ASM / Javassist / ByteBuddy 做字节码增强（AOP、Mock、Agent 都靠它）。

## 五、易错点

| 易错点 | 澄清 |
|:---|:---|
| **准备阶段就赋初值** | 准备阶段只给**零值**，初始化阶段 `<clinit>` 才赋真实值 |
| **双亲委派是强制的** | 只是「推荐」实现，Tomcat/SPI 都可打破 |
| **同名类一定相等** | 不同类加载器加载的同名类是**不同的类** |
| **`Class.forName` 与 `loadClass` 一样** | `forName` 默认会**初始化**类；`loadClass` 只加载不初始化 |
| **Bootstrap 是 Java 类** | Bootstrap 由 C++ 实现，`getClassLoader()` 返回 null |
| **访问 static final 常量会初始化类** | 编译期常量已进调用方常量池，不触发目标类初始化 |

---

## 六、一句话总结

类加载经历**加载→验证→准备→解析→初始化**五步（准备给零值、初始化才赋真值）；**双亲委派**让加载请求逐级上抛，保证核心类唯一且安全；但框架常主动打破它——SPI 靠**线程上下文类加载器**反向委派、Tomcat 靠**应用私有加载器**做隔离。类的唯一性由「类加载器 + 全限定名」共同决定。
