## 二、逐题详解

### Q1：线上一条 SQL 突然变慢，完整排查链路怎么走？（P7 开局）

**答题骨架（万能五步）**：

```text
① 复现定性：多慢？何时开始？与发布/数据量增长/大事务有无时间关联？
② 抓现场：show processlist 看线程 State
③ explain 定位：type / key / rows / Extra 四列
④ 根因分诊（见 Q3 分诊表）
⑤ 解决 → 复盘：加监控、写事故报告防再犯
```

**show processlist 关键 State 速查**：

| State | 含义 | 指向 |
|:---|:---|:---|
| `Sending data` | 在扫描和传输大量行 | 缺索引 / 索引失效（Q2） |
| `Copying to tmp table` | 临时表（排序/分组） | order by / group by 优化 |
| `Waiting for table metadata lock` | 等 MDL 锁 | 有长事务阻塞 DDL（见 Q6） |
| `Waiting for lock` | 等行锁 | 锁冲突（见 Q6） |

### Q2：建了索引却不走，哪些实际场景会导致索引失效？

每个失效场景背后都是一个「生产故事」（原理详见 [索引](4.%20索引.md)）：

| 场景 | 反例 | 根因 |
|:---|:---|:---|
| 索引列做函数/运算 | `WHERE DATE(create_time)='2026-08-30'` | B+ 树存的是原始值，被加工后有序性用不上 |
| 隐式类型转换 | phone 是 varchar，`WHERE phone=13800001111` | 等价于对列套 CAST，同上 |
| 最左前缀断裂 | 联合索引(a,b,c)，`WHERE b=1` | 跳过 a 无法定位 |
| like 左模糊 | `LIKE '%abc'` | 前缀未知，无法走有序树 |
| OR 混入无索引列 | `WHERE a=1 OR d=2`（d 无索引） | 优化器放弃索引走全表 |
| **优化器主动弃用** | 回表行数太多，估算全表扫更快 | 这不是失效，是代价决策——`force index` 可验证 |

**加分点**：能区分「写法导致的失效」和「优化器基于代价的弃用」，并说出验证手段（`explain` + 对比 `force index` 的代价）。

### Q3：同一条 SQL 时快时慢，什么原因？（区分度题）

| 层 | 根因 | 机制 |
|:---|:---|:---|
| 缓存冷热 | Buffer Pool 命中 vs 落盘 | 快时数据全在内存，慢时冷页要磁盘 I/O；刚重启/大扫描会冲掉热页 |
| 执行计划漂移 | 统计信息过期 / 数据量增长跨临界点 | rows 估算变了，优化器换计划：之前 ref 现在全表；`analyze table` 重新收集 |
| 刷脏干扰 | redo log 接近满 | MySQL 主动刷脏页，读写都抖动（见 [存储引擎与架构](3.%20存储引擎与架构.md)） |
| 锁等待 | 同一行被长事务持锁 | 快慢取决于别人的事务何时提交（见 [事务与锁](5.%20事务与锁.md)） |
| 环境差异 | 走了不同从库 | 数据分布/统计信息不同；或主从配置差异（见 [分库分表](12.%20分库分表.md)） |

### Q4：往千万级大表批量导入 100 万数据，怎么优化？

**写入慢在哪**：一条 insert ≈ 一次事务（redo + binlog 双 fsync）+ 索引维护 + 唯一性检查。

| 手段 | 做法 | 原理 |
|:---|:---|:---|
| **手动事务批量提交** | 500~1000 行一个事务 | 关掉自动提交，1 次刷盘代替 100 万次 |
| **多值插入** | `INSERT INTO t VALUES (...),(...)` | 一条语句一次解析/一次事务 |
| **load data** | `load data infile` | MySQL 最快的导入路径，直接跳过 SQL 解析层 |
| 容忍丢 1 秒的场景 | `innodb_flush_log_at_trx_commit=2` | redo 写 OS 缓存，每秒刷盘 |
| 会话级加速 | `unique_checks=0`、`foreign_key_checks=0` | 数据自洽时关校验 |
| **先删二级索引，导完重建** | | 维护 N 个二级索引 = 每行 N 次额外写 |

### Q5：线上 MySQL CPU 飙到 100%，怎么定位到具体 SQL？

```text
① top 确认是 mysqld 进程吃 CPU（排除备份/监控进程）
② show full processlist：Time 长的、State 异常的线程
③ 拿到嫌疑 SQL → explain 看 rows / type（多半是 type=ALL 大扫描）
④ sys 库兜底聚合视图：
   sys.statements_with_full_table_scans（全表扫描排行）
⑤ 止血：kill <id>；优化 SQL；加慢日志告警防复发
```

**加分点**：说出「CPU 100% 多半是**扫描行数暴涨**——单条慢 SQL 或多条 SQL 叠加」，并主动关联大促前的压测容量评估。

### Q6：业务报 Lock wait timeout exceeded，怎么排查？

```sql
-- ① 当前所有事务（找 trx_started 很久之前的长事务）
SELECT * FROM information_schema.innodb_trx ORDER BY trx_started;

-- ② 8.0 直接给出阻塞对（谁等谁、blocking_pid）
SELECT * FROM sys.innodb_lock_waits;   -- 5.7 用 information_schema.innodb_lock_waits

-- ③ 处理：kill 阻塞源会话 → 业务恢复 → 根因回溯
```

**根因回溯四问**：大事务没拆？循环里单条 update？交互式会话改了数据没提交？**update 条件没走索引导致行锁膨胀成大范围扫描加锁**（见 [事务与锁](5.%20事务与锁.md)）。

**预防**：事务尽量小、DML 必带索引条件、监控事务运行时长超 10s 告警。

### Q7：订单页多条件动态筛选，联合索引怎么设计？

**场景**：订单表按 user_id / status / create_time 任意组合查，不可能每个组合建一个索引。

**设计权衡（实战原则）**：

1. **等值列在前，范围列在后**：`(user_id, status, create_time)`——范围列之后的索引列失效；
2. **找公共前缀**：所有查询都带的列做最左列（如 tenant_id / user_id）；
3. 排序列并入联合索引尾部，避免 `Using filesort`；
4. 高频查询字段追加到索引尾部做**覆盖索引**，避免回表；
5. 实在覆盖不了的长尾组合：**异步走 ES / 宽表**（多维查询见 [分库分表](12.%20分库分表.md)），主库只保核心链路。

**一句话**：联合索引设计 = **把「最常等值过滤」的列放前面，范围与排序列放后面，长尾组合交给旁路系统**。

### Q8：报表聚合 SQL 扫全表很慢，业务又要实时看，怎么办？

**分层解法（从便宜到贵）**：

| 层 | 手段 |
|:---|:---|
| SQL 层 | 聚合列建索引走覆盖；JOIN 聚合先收敛再放大（见 [笛卡尔积](10.%20笛卡尔积.md) Q7） |
| **预聚合** | 维护汇总表：定时任务/增量聚合，查询打汇总表——**报表场景性价比之王** |
| 计数外置 | count 类 → Redis 计数器/计数表，binlog 订阅异步校准 |
| 读写分离 | 报表走从库，不冲击主库写入（延迟敏感型报表除外） |
| 存储分离 | 数据量大、维度多 → ES / ClickHouse，**OLTP 与 OLAP 分离** |

### Q9：一条查询要扫 2000 万行，从 SQL 到架构逐层怎么优化？（综合必考）

**答题顺序体现优化意识（先穷尽便宜的，再上贵的）**：

```text
① SQL/索引层：覆盖索引？深分页改书签法（见 深分页优化）？只查需要的列？
② 表结构层：冷热分离（历史归档表）、适度冗余减少 JOIN、大字段拆表
③ 缓存层：热点结果放 Redis，挡住读流量
④ 架构层：读写分离 → 分库分表（分片键选择见 分库分表）
⑤ 仍不行：换存储——ES（检索）/ ClickHouse（分析）
```

**收束**：面试官在考「**优化顺序意识**」——一上来就说分库分表 = 不会优化（对应 [SQL优化与调优](8.%20SQL优化与调优.md) 易错点）。

### Q10：团队怎么系统性治理慢 SQL？（P7 工程化）

| 阶段 | 手段 |
|:---|:---|
| **事前约定** | 建表评审考虑查询模式；SQL 规范（禁 select *、update 必带索引条件）；上线前 explain 门禁/审核 |
| **事中监控** | 慢查询日志 + pt-query-digest 周报；APM 打 SQL 耗时分位数（P95/P99）；连接数、长事务告警 |
| **事后治理** | TOP N 慢 SQL 排行 → 责任到人 → 优化前后耗时对比闭环；大促前全量压测；定期清理无用索引 |

**P7 收束句**：慢 SQL 治理的本质是**把个人优化能力沉淀成流程和门禁**，而不是等出事故再救火。

## 三、易错点

| 易错点 | 说明 |
|:---|:---|
| 只背「索引失效口诀」 | 面试官追问「为什么 OR 不走索引」要答到**代价估算**层：两个条件必须都取回才能并集，不如全表扫 |
| 时快时慢只答「缓存」 | 至少说出执行计划漂移（统计信息）和刷脏干扰才算完整 |
| 批量导入不提事务粒度 | 逐条自动提交是最大杀手，先答「合事务」再答参数调优 |
| 锁超时只会 kill | kill 是止血，面试要给出根因回溯（长事务/无索引 update） |
| 优化顺序颠倒 | 先分库分表再索引 = 大忌；架构手段永远是最后一步 |

---

## 四、一句话总结

场景题的万能骨架 = **现象定性 → show processlist 抓现场 → explain 定位 → 按「索引 → 改写 → 缓存 → 架构」顺序分诊解决 → 复盘防再犯**。所有场景殊途同归：**减少扫描行数，把计算挪到数据写入时（预聚合）而不是查询时**。
