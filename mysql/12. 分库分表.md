# 分库分表

> 数据量突破单机极限后的必答题。面试主线：**要不要拆 → 怎么拆 → 分片键怎么选 → 拆完的新问题 → 怎么平滑扩容**——P7 会把它当系统设计题深挖。

---

## 一、先问要不要拆（避免过早优化）

单表行数不是硬性标准，本质是 **B+ 树层数与缓冲命中率**：3 层 B+ 树约可承载 **2000 万行**（与行宽有关），配合 Buffer Pool 仍能跑得很快（原理见 [索引.md](4.%20索引.md)）。

| 拆分信号 | 说明 |
|:---|:---|
| 单表数据量/增速 | 千万级且持续增长，DDL 变更超小时级 |
| 单库容量/IO | 磁盘、内存装不下热数据，QPS/连接数逼近上限 |
| 锁与备份 | 锁竞争严重、备份恢复时长不可接受 |

**拆之前先榨单机**：索引优化 → 读写分离 → 冷热/归档分离 → 缓存抗读 → 最后才是分库分表。

---

## 二、四种拆分方式

```
垂直分库：按业务域拆                    垂直分表：按字段冷热/大小拆
┌─────┐ ┌─────┐ ┌─────┐               spu 表                    spu_detail 表
│订单库│ │商品库│ │用户库│        id|name|price|detail(TEXT) →  id|name|price    id|spu_id|detail
└─────┘ └─────┘ └─────┘               （热点列）                  （大字段，按需查）

水平分库分表：同一张表按分片键散到 N 库 × M 表
order_0 ──> order_00, order_01      （分片键 = buyer_id hash）
order_1 ──> order_10, order_11
```

| 方式 | 解决什么 | 代价 |
|:---|:---|:---|
| 垂直分库 | 业务解耦、微服务化 | 跨库 JOIN/事务 |
| 垂直分表 | 行宽过大拖慢页读取、大字段 IO | 多一次关联查询 |
| **水平分库分表** | **容量与并发的根本扩展** | 全套分布式问题（本文主角） |

## 三、分片键与路由策略（核心）

### 路由算法对比

| 算法 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **范围分片** | 按 ID/时间区间（如每月一张表） | 扩容只加新片、范围查询友好 | **热点集中**（新数据全打最新片） |
| **哈希取模** | `hash(shardKey) % N` | 数据均匀 | **扩容全量迁移**；N 固定 |
| **一致性哈希/预分槽** | 4096 个槽 → 槽映射到库表；扩容只搬槽 | 均匀 + **扩容只迁部分** | 实现稍复杂（推荐默认选择） |
| 查表法 | 映射表记录 key→分片 | 最灵活（可按租户/地区调整） | 路由表本身要高可用、多一次查询 |

### 分片键选择原则（必答）

1. **高频查询条件优先**：绝大多数 SQL 都带的字段（订单按 buyer_id 查 ≠ 按 seller_id 查）；
2. 数据均匀：防大客户倾斜；
3. **避免没有分片键的查询**：缺分片键 = 广播全部分片聚合，性能灾难。

**经典两难解法——基因法**：订单既要按 buyer_id 查又要按 order_id 查 →

```
order_id 生成时嵌入 buyer_id 的分片基因：
order_id = 雪花算法比特位 | buyer_id.hashCode() % 1024（低 10 位作基因）
路由：按 order_id 查 → 取低 10 位定位分片；按 buyer_id 查 → 同样基因定位
一条数据同时满足两类查询，不落广播。
```

卖家维度的高频查询则**冗余一份按 seller_id 分片的表**（或异构到 ES），用最终一致对齐。

## 四、拆完之后的四大新问题（必考）

### 1. 跨分片查询

| 方案 | 说明 |
|:---|:---|
| 广播 + 归并 | 中间件把 SQL 发到全部分片，汇总排序聚合——能用但慢，控制使用频率 |
| **异构索引** | 同步到 ES（binlog→Canal→ES），复杂查询走 ES 拿 ID 回查——CQRS 思路（见 [../系统设计/README.md](../系统设计/README.md)） |
| 字段冗余 | 订单表冗余商品名/用户名，免跨库 JOIN |

### 2. 跨分片分页（深分页放大）

`limit 1000000, 10` 在分片下 = 每片都要取前 1000010 条归并。对策：
- **禁跳页**：游标翻页 `where id > last_id limit 10`（每片各取 10 条归并即可）；
- 必须跳页用二次查询/延迟关联（原理见 [SQL优化与调优.md](8.%20SQL优化与调优.md)）。

### 3. 全局唯一 ID

自增主键在分片下会冲突。方案：**雪花算法（时间戳+机器ID+序列）**、号段模式、数据库步长分段——详见 [../系统设计/ID生成器.md](../系统设计/ID生成器.md)。注意**趋势递增**避免页分裂（呼应 [索引.md](4.%20索引.md)）。

### 4. 分布式事务

跨库写无法用本地事务：单体大事务 → **本地消息表/事务消息 + 最终一致**（见 [../分布式/README.md](../分布式/README.md)）；能用「同一分片内完成」的设计（基因法把相关数据聚到一个分片）就避免跨片。

## 五、平滑扩容（数据迁移，P7 必问）

```
① 双写开启：新库与旧库同时写（写旧为主，写新容错）
② 全量迁移：存量数据按分片规则搬到新集群（大表分批，限速）
③ 增量同步：binlog（Canal）追平迁移期间的新变更
④ 数据校验：行数 + 抽样字段比对（或 checksum），差异修复
⑤ 灰度切读：按百分比/租户维度逐步把读流量切到新库，观察
⑥ 切写与收尾：写主切到新库 → 停旧库双写 → 旧库降级为备份
```

| 方案 | 适用 |
|:---|:---|
| 停机迁移 | 业务允许停写窗口（最简单可靠） |
| **双写 + binlog 追平 + 灰度切流** | 不停机标准方案，注意双写不一致的补偿与幂等 |
| 取模翻倍扩容 | N → 2N 时只迁一半数据（hash 高位不变），是取模方案少有的扩容优点 |

## 六、中间件选型

| 维度 | ShardingSphere-JDBC | ShardingSphere-Proxy | MyCat |
|:---|:---|:---|:---|
| 形态 | 客户端 JAR，增强 JDBC | 独立代理进程（伪 MySQL） | 代理层 |
| 性能 | **无中转损耗** | 多一跳网络 | 同左 |
| 侵入性 | 需引入依赖（Spring Boot starter 顺滑） | **语言无关**、DBA 友好 | — |
| 现状 | **主流首选** | 异构语言/运维治理场景 | 逐渐淘汰 |

## 易错点

| 坑 | 说明 |
|:---|:---|
| 分片键没选对 | 非分片键查询全表广播；选完再改成本极高——先梳理 Top 查询 |
| 自增 ID 直接入库 | 集中写到一个分片（尾部热点）+ 全局冲突；用雪花/号段 |
| 取模 N 直接用实例数 | 扩容全量迁移；预分槽（4096 slots）留余量 |
| 分片下还写 `limit 深跳页` | 归并代价爆炸，改游标翻页 |
| 以为分库分表解决事务 | 它**制造**分布式事务问题；设计时尽量把强一致路径圈在单分片 |
| 二维分片先分库再分表混乱 | 固定套路：`db = slot / 每库表数; table = slot % 每库表数` |

---

## 一句话总结

**先榨单机再拆**：垂直按业务/冷热、水平解决容量并发；分片键选「高频查询字段」，用**预分槽/一致性哈希**留扩容余量、**基因法/冗余**对抗多维度查询；拆完必配「全局 ID + 异构索引/游标翻页 + 最终一致」；扩容走「双写 → 全量+binlog 追平 → 校验 → 灰度切流」。
