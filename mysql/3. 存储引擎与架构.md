# MySQL 存储引擎与架构面试题

理解 MySQL 的整体架构和 InnoDB 的日志系统，是回答「一条 SQL 怎么执行」「数据怎么不丢」这类深度问题的基础。

---

## 一、MySQL 整体架构（一条 SQL 的旅程）

MySQL 逻辑上分为 **Server 层** 和 **存储引擎层**。

```
客户端
  │
┌─────────────── Server 层 ───────────────┐
│ 连接器   → 管理连接、权限校验            │
│ 查询缓存 → 命中直接返回（8.0 已移除）     │
│ 分析器   → 词法/语法分析，生成语法树      │
│ 优化器   → 选索引、定 join 顺序、生成执行计划│
│ 执行器   → 调用存储引擎接口，逐行处理      │
└──────────────────┬──────────────────────┘
                   │
        ┌── 存储引擎层（InnoDB / MyISAM）──┐
        │  负责数据的存储与提取             │
        └───────────────────────────────┘
```

| 组件 | 职责 |
|:---|:---|
| 连接器 | 建立连接、校验账号密码和权限，长连接内存问题 |
| 查询缓存 | 缓存 SQL 与结果（**8.0 已彻底删除**，因表更新即失效、命中率低） |
| 分析器 | 词法分析（认识关键字）、语法分析（检查语法） |
| 优化器 | **基于成本**选择索引、决定表 join 顺序，生成执行计划 |
| 执行器 | 校验权限，调用引擎接口读写数据 |

## 二、InnoDB vs MyISAM（高频对比）

| 维度 | InnoDB ✅ 默认 | MyISAM |
|:---|:---|:---|
| **事务** | 支持（ACID） | 不支持 |
| **外键** | 支持 | 不支持 |
| **锁粒度** | 行锁 + 表锁 | 只有表锁 |
| **崩溃恢复** | 支持（redo log） | 不支持，需修复表 |
| **聚簇索引** | 是（叶子存整行） | 否（索引和数据分离） |
| **count(\*)** | 需实时统计（慢） | 存了行数，`count(*)` 极快 |
| **适用场景** | 增删改多、要事务（绝大多数场景） | 读多写少、不要事务（如日志、报表归档） |

> 结论：**几乎所有场景都用 InnoDB**。MySQL 5.5 起 InnoDB 就是默认引擎。

```sql
show engines;                          -- 查看支持的引擎
show table status like 'user';         -- 查看某表用的引擎
```

## 三、InnoDB 内部架构

在讨论三大日志之前，先把 InnoDB 存储引擎的内部组件梳理一遍——三大日志正是这套架构里「内存改页 → 顺序记日志 → 异步刷脏」的关键环节。

```text
┌───────────────────── InnoDB 存储引擎内部架构 ─────────────────────┐
│                                                                   │
│  内存层（Buffer Pool 主导）                                        │
│  ┌──────────────┐  ┌──────────────┐  ┌────────────────────────┐  │
│  │  Buffer Pool │  │ Change Buffer │  │ Adaptive Hash Index    │  │
│  │ 数据页+索引页│  │ 非唯一索引DML │  │ 热点页等值查询加速     │  │
│  └──────────────┘  └──────────────┘  └────────────────────────┘  │
│                            ┌──────────────┐                       │
│                            │  Log Buffer  │  ← redo log 缓冲     │
│                            └──────────────┘                       │
│                                                                   │
│  后台线程                                                          │
│  ┌──────────┐ ┌─────────┐ ┌──────────┐ ┌──────────────────┐    │
│  │ Master   │ │ IO Thread│ │ Purge    │ │ Page Cleaner     │    │
│  │ Thread   │ │ 4读4写   │ │ Thread   │ │ Thread（刷脏页）  │    │
│  └──────────┘ └─────────┘ └──────────┘ └──────────────────┘    │
│                                                                   │
│  磁盘层                                                           │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐             │
│  │  表空间 ibd  │ │  redo log    │ │  undo log    │             │
│  │ 数据+索引页  │ │ ib_logfile   │ │ 回滚+MVCC    │             │
│  └──────────────┘ └──────────────┘ └──────────────┘             │
└───────────────────────────────────────────────────────────────────┘
```

| 组件 | 所在层 | 职责 |
|:---|:---|:---|
| **Buffer Pool** | 内存 | 缓存数据页和索引页（默认 128MB），减少磁盘 I/O；脏页在此产生 |
| **Change Buffer** | 内存 | 对**非唯一二级索引**的 DML 操作先记内存，等读时再合并，避免随机 I/O |
| **Adaptive Hash Index** | 内存 | 自动为热点页建立哈希索引，加速等值查询（只读的 B+ 树页才有） |
| **Log Buffer** | 内存 | redo log 写磁盘前的缓冲，默认 16MB，满了或事务提交时刷盘 |
| **Master Thread** | 后台 | 核心调度，周期性触发刷脏、合并 Change Buffer、purge undo |
| **IO Thread** | 后台 | 处理读写请求（4 个 read + 4 个 write），异步 I/O 的主力 |
| **Purge Thread** | 后台 | 回收事务不再需要的 undo log，防止版本链过长 |
| **Page Cleaner Thread** | 后台 | 把 Buffer Pool 里的脏页异步刷回磁盘，配合 redo log |
| **表空间 .ibd** | 磁盘 | 表的数据页 + 索引页（聚簇+二级），段→区→页三级结构 |
| **redo log** | 磁盘 | 物理日志，循环写，崩溃恢复靠它 |
| **undo log** | 磁盘 | 回滚日志，MVCC 版本链靠它 |

> 一句话串起架构：**写操作先改 Buffer Pool 里的数据页（脏页），同时写 Log Buffer → redo log（保证不丢），后台 Page Cleaner 异步把脏页刷回 .ibd 表空间；Purge Thread 回收 undo；读操作命中 Buffer Pool 直接返回，未命中从磁盘加载**。这套流程正是下一节「WAL + 两阶段提交」的基础。

## 四、InnoDB 三大日志

这是「持久性」「原子性」「崩溃恢复」的底层保障，务必分清。

| 日志 | 层 | 作用 | 保证 |
|:---|:---|:---|:---|
| **redo log**（重做日志） | InnoDB 引擎层 | 记录**物理修改**（某页做了什么改动），崩溃后重放 | **持久性** |
| **undo log**（回滚日志） | InnoDB 引擎层 | 记录**旧值**，用于回滚和 MVCC 版本链 | **原子性** + MVCC |
| **binlog**（归档日志） | Server 层 | 记录**逻辑操作**（语句或行变更），用于主从复制、数据恢复 | 复制 / 备份 |

### redo log vs binlog 区别（常考）

| 维度 | redo log | binlog |
|:---|:---|:---|
| 层次 | InnoDB 引擎特有 | Server 层，所有引擎通用 |
| 内容 | 物理日志（页的改动） | 逻辑日志（SQL / 行变化） |
| 写入方式 | 循环写，空间固定，写满覆盖 | 追加写，写满换新文件，不覆盖 |
| 用途 | 崩溃恢复（crash-safe） | 主从复制、数据归档恢复 |

## 五、WAL 与两阶段提交（2PC）—— 面试深水区

### WAL（Write-Ahead Logging，预写日志）

**先写日志，再写磁盘数据**。修改数据时先改内存 Buffer Pool 并顺序写 redo log（顺序 I/O 快），脏页稍后再刷盘（随机 I/O 慢）。即使宕机，也能靠 redo log 恢复。

> 核心：把「随机写数据」变成「顺序写日志」，大幅提升性能，还保证不丢数据。

### 两阶段提交（保证 redo log 与 binlog 一致）

一条 `update` 语句的提交流程：

```
1. 执行器改内存中的数据页
2. 写 redo log，状态置为 prepare（准备）   ← 阶段一
3. 写 binlog
4. 提交事务，redo log 状态改为 commit      ← 阶段二
```

**为什么要两阶段？** 让两个日志的写入具备原子性，避免主从 / 恢复数据不一致：
- 若只写完 redo 就崩溃（还没写 binlog）：redo 是 prepare 态且无对应 binlog → **回滚**
- 若 redo prepare + binlog 都写完才崩溃：→ **提交**（数据完整）

> 没有 2PC，可能出现「主库用 redo 恢复了数据，但 binlog 没记录，从库同步不到」的不一致。

## 六、Buffer Pool（缓冲池）

InnoDB 在内存里开辟的一块缓存区，缓存数据页和索引页，减少磁盘 I/O。

| 概念 | 说明 |
|:---|:---|
| **缓存页** | 读数据先看 Buffer Pool，没有再从磁盘加载（以页 16KB 为单位） |
| **脏页** | 内存中被修改但还没刷到磁盘的页 |
| **改进版 LRU** | 分 young / old 区，防止全表扫描把热点数据挤出缓存 |
| **刷脏** | 后台线程异步把脏页写回磁盘（配合 redo log） |

> 写数据流程：改 Buffer Pool（内存）→ 写 redo log → 后台异步刷脏页。所以写操作很快。

## 七、常见字段类型与建表规范

| 问题 | 建议 |
|:---|:---|
| `char` vs `varchar` | char 定长（适合固定长度如身份证），varchar 变长（省空间） |
| 存金额 | 用 `decimal`，不要用 `float`/`double`（精度丢失） |
| 存时间 | `datetime`（与时区无关）vs `timestamp`（带时区、范围到 2038） |
| 主键 | 建议**自增 bigint**，避免用 UUID（无序导致页分裂、索引大） |
| `null` | 尽量 `not null` 给默认值，null 影响索引和统计 |

> 为什么主键推荐自增？自增主键顺序写入，B+ 树叶子**顺序追加**，避免页分裂和数据移动；UUID 无序会导致频繁页分裂、索引变大。

## 八、易错点

| 易错点 | 说明 |
|:---|:---|
| **redo log 和 binlog 搞混** | redo 是引擎层物理日志（循环写），binlog 是 Server 层逻辑日志（追加写） |
| **以为查询缓存还在** | MySQL 8.0 已彻底移除查询缓存 |
| **认为写数据就是直接写磁盘** | 先改 Buffer Pool + 写 redo log，脏页异步刷盘（WAL） |
| **不知道 count(\*) 为何 InnoDB 慢** | InnoDB 支持事务/MVCC，行数不固定，需实时算 |
| **UUID 当主键** | 无序导致页分裂、聚簇索引膨胀 |

---

## 九、一句话总结

MySQL 分 **Server 层**（连接器/分析器/优化器/执行器）和**存储引擎层**；默认引擎 **InnoDB** 支持事务、行锁、聚簇索引。InnoDB 内部以 **Buffer Pool** 为核心（缓存页 + Change Buffer + 自适应哈希 + Log Buffer），配合 **Master/IO/Purge/Page Cleaner** 后台线程，实现「内存改页 → 顺序记日志 → 异步刷脏」。靠 **redo log（物理/持久性）+ undo log（回滚/MVCC）+ binlog（复制）** 三大日志，配合 **WAL** 和**两阶段提交**，做到高性能且崩溃不丢数据。
