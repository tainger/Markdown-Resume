## 一、InnoDB 锁体系总览

```
InnoDB 锁
├─ 表级锁
│   ├─ 表锁（LOCK_TABLE）：显式 lock tables / 上 DDL
│   ├─ 意向锁（Intention Lock）：IS / IX  ← 提升加锁效率
│   ├─ AUTO-INC 锁（自增主键分配）
│   └─ MDL 元数据锁（Metadata Lock）：保护表结构
│
└─ 行级锁（InnoDB 真正的精华）
    ├─ 记录锁（Record Lock）：锁单行索引
    ├─ 间隙锁（Gap Lock）：锁索引间隙（开区间）
    ├─ 临键锁（Next-Key Lock）：左开右闭区间（RR 默认）
    └─ 插入意向锁（Insert Intention Lock）：插入时的间隙锁变体
```

> [事务与锁.md](5.%20事务与锁.md) 第六节讲了「按粒度 + 兼容性 + InnoDB 三种形态」入门，本文重点补其余 4 类表锁 + 行锁的细节 + 加锁规则深度。

## 二、表级锁层

### 1. 意向锁（Intention Lock）—— IS / IX

**作用**：表锁与行锁的**协调机制**。当事务想加**表锁**时，不必逐行检查是否有行锁，只要看表上有没有意向锁即可，**O(1) 判断兼容性**。

| 意向锁 | 含义 | 触发场景 |
|:---|:---|:---|
| **IS（Intention Shared）** | 准备加行 S 锁前先加 IS | `select ... lock in share mode` |
| **IX（Intention Exclusive）** | 准备加行 X 锁前先加 IX | `select ... for update` / `update` / `delete` / `insert` |

```
事务 A：select * from t where id = 1 for update;
  1. 表上加 IX
  2. 行 id=1 上加 X 记录锁

事务 B：lock tables t write;   ← 要加表 X 锁
  → 先看表上意向锁：有 IX → 与表 X 互斥 → 阻塞
  → 不必扫所有行判断有没有行锁（O(1) 拒绝）
```

> **口诀**：意向锁只与表锁竞争，**意向锁之间互不冲突**（IS/IX 之间兼容），意向锁只表达"我想加行锁"的意图，不阻塞任何行操作。

### 2. AUTO-INC 锁（自增主键分配）

`innodb_autoinc_lock_mode` 三种模式：

| 模式 | 名称 | 行为 | 适用 |
|:---|:---|:---|:---|
| 0 | 传统 | 整个 SQL 持有表级 AUTO-INC 锁，结束才释放 | 兼容老版本，并发差 |
| **1** | **连续**（MySQL 5.7 默认） | Simple insert 用轻量级 mutex；bulk insert 仍用表锁 | 平衡 |
| **2** | **交叉**（MySQL 8.0 默认） | 全用轻量级 mutex，不持表锁；bulk 也并发分配 | 并发最好，但自增值可能不连续 |

> MySQL 8.0 默认 2，性能最佳；缺点是同 SQL 内自增值可能跳跃，业务不能依赖连续 ID。

### 3. MDL 元数据锁（Metadata Lock）

**作用**：保护**表结构**不被并发修改。5.5.3+ 引入。

```
事务 A：select * from user;          （长事务一直没提交）
       → 隐式持有 user 的 MDL 共享读锁

事务 B：alter table user add column; （DDL）
       → 要 MDL 排他写锁 → 阻塞在 A 后面

事务 C：select * from user;          （后续所有查询都阻塞！）
       → 阻塞在 B 后面 → 整表雪崩
```

> **生产高频事故**：长事务 + DDL = 雪崩。排查命令见下文第十节。解决办法：① DDL 前先 `kill` 长事务；② 用 pt-online-schema-change / gh-ost 工具做在线 DDL。

### 4. 显式表锁

```sql
lock tables t read;       -- 表 S 锁，自己和其他事务只能读
lock tables t write;       -- 表 X 锁，独占
unlock tables;
```

> 业务几乎不用，运维 / 备份偶尔用。

## 三、行级锁层

[事务与锁.md](5.%20事务与锁.md) 第六节已讲 Record/Gap/Next-Key 三种形态，这里补**插入意向锁**和锁的具体实现细节。

### 1. 插入意向锁（Insert Intention Lock）

**作用**：插入新行时**不阻塞其他事务往同一间隙插入不同值**——并发插入友好。

```
表 t 有 id=5、id=10，间隙 (5,10)

事务 A：insert into t values (7);   ← 在间隙 (5,10) 加插入意向锁
事务 B：insert into t values (9);  ← 同间隙插入意向锁 ✅ 兼容
                                  → A、B 都能插入（不阻塞）

但如果事务 C：select * from t where id=7 for update;
                                  ← 间隙上已有 X 间隙锁 → 阻塞 A 的插入
```

| 场景 | A 的插入意向锁 与 B 的什么锁冲突 |
|:---|:---|
| B 的**插入意向锁**（不同值） | ✅ 兼容 |
| B 的**间隙锁**（Gap Lock） | ❌ 冲突 |
| B 的**临键锁** | ❌ 冲突 |

> 这就是为什么**并发插入**很高效——插入意向锁之间兼容，不会互相等。

### 2. 锁的实现：锁的不是数据行，是索引

```
InnoDB 行锁锁在索引上：
  ┌─ 走索引（聚簇 / 二级） → 锁索引项（精确行）
  └─ 不走索引 → 退化全表扫 → 锁所有行 → 等于表锁
```

> [事务与锁.md](5.%20事务与锁.md) 易错点提过这条，这里强调：**无索引 = 行锁退化为表锁**，所有并发写全堵在表锁上。加索引治本。

### 3. 锁的存储：锁内存

- 锁信息存在**锁池（Lock Sys）**内存结构，不写入数据文件
- 5.7 单 Lock Sys 全局锁池，8.0 按 Lock Partition 分片（128 个），减少全局锁竞争

## 四、锁兼容矩阵

### 表级锁兼容矩阵（IS/IX 之间）

| | IS | IX |
|:---|:---:|:---:|
| **IS** | ✅ | ✅ |
| **IX** | ✅ | ✅ |

> **意向锁之间全兼容**——IS/IX 表达"我要加行锁"，不影响别人加不同的行锁。

### 表级锁 vs 行级锁的兼容

| 表 \ 行 | 行 S | 行 X |
|:---|:---:|:---:|
| 表 S | ✅ | ❌ |
| 表 X | ❌ | ❌ |

### 行级锁兼容矩阵

| | Record S | Record X | Gap | Insert Intention |
|:---|:---:|:---:|:---:|:---:|
| **Record S** | ✅ | ❌ | ✅ | ✅ |
| **Record X** | ❌ | ❌ | ✅ | ✅ |
| **Gap** | ✅ | ✅ | ❌ | ❌ |
| **Insert Intention** | ✅ | ✅ | ❌ | ✅ |

**两个关键规律**：

1. **Gap 与 Gap 不兼容**：两个事务同时锁一个间隙 = 阻塞
2. **Insert Intention 之间兼容**：同间隙插入不同值不冲突

## 五、加锁规则深度（必考）——「两原则、两优化」

这是 InnoDB RR 级别加锁的核心规律，背熟它就能口算任何 SQL 的加锁范围。

### 原则 1：加锁的基本单位是 Next-Key Lock（左开右闭）

```
表 t 有 id=5,10,15,20
默认加锁 = (前一行, 当前行] 的 Next-Key Lock

查询 id=10 命中 → 默认加 (5,10] Next-Key Lock
```

### 原则 2：查找过程中访问到的对象才加锁

```
select * from t where id > 7 and id < 12 for update;
  ↑ 查找过程中扫了 id=10 → 给 (5,10] (10,15] 加锁
  ↑ 实际加锁范围 = (5,15]
```

### 优化 1：唯一索引等值命中 → Next-Key 退化为 Record Lock

```
表 t 有 id=5,10,15,20（id 是唯一索引）
select * from t where id = 10 for update;
  ↑ Next-Key (5,10] 退化为 Record Lock 只锁 id=10
  ↑ 别人能 insert id=6,7,8 ✅（间隙不锁）
```

> **优化 1 只对唯一索引生效**。非唯一索引等值命中，仍加 Next-Key，前后间隙都锁。

### 优化 2：向右遍历时最后一个不满足条件的值 → Next-Key 退化为 Gap Lock

```
表 t 有 id=5,10,15,20（id 是普通索引，非唯一）
select * from t where id = 10 for update;
  ↑ 加锁：(5,10] Next-Key + (10,15] Next-Key
  ↑ 遍历到 id=15 时 id=15≠10 不满足条件 → 退化为 Gap Lock
  ↑ 实际加锁：(5,15]（即 (5,10] + (10,15) Gap）
```

> **Gap Lock 只在 RR 级别出现**，RC 几乎不加 Gap（除外键 / 唯一约束检查）。

### bug：唯一索引范围查询会"多锁一个"

```
表 t 有 id=5,10,15,20（id 是唯一索引）
select * from t where id > 10 and id <= 15 for update;
  ↑ 理论应锁 (10,15]
  ↑ 但实际加锁到 (10,20]   ← 多锁了一个间隙 (15,20)
```

> 这是 InnoDB 的已知行为：唯一索引**范围**查询时，第一个不满足条件的值会加上临键锁而不是间隙锁。

## 六、不同 SQL 的加锁分析

### 索引类型对照矩阵

| SQL | 索引类型 | 加锁范围（RR） |
|:---|:---|:---|
| `where id = 10 for update` | **唯一索引**命中 | Record Lock on id=10（优化 1） |
| `where id = 10 for update` | **非唯一索引**命中 | Next-Key (前,10] + Gap (10,后]（优化 2） |
| `where id > 10 for update` | 唯一索引 | Next-Key (10,+∞] 直到表末 |
| `where id > 10 for update` | 非唯一索引 | Next-Key (10,+∞] 直到表末 |
| `where id > 10 and id < 20 for update` | 唯一索引 | Next-Key (10,20] + bug 多一个 (20,后] |
| `where id > 10 and id < 20 for update` | 非唯一索引 | Next-Key (10,后] 直到表末 |
| **无索引** `where name='x' for update` | 无索引 | **锁全表**（每行 Next-Key） |

### 实战案例：行锁退化为表锁

```sql
create table t (id int primary key, name varchar(20));
insert into t values (1,'a'),(2,'b'),(3,'c');

-- ❌ 没给 name 加索引
select * from t where name = 'a' for update;
-- → 全表扫，给所有行加 X Next-Key → 等于表锁

-- 给 name 加索引后
create index idx_name on t(name);
select * from t where name = 'a' for update;
-- → 走 idx_name，只锁命中的行（加在二级索引 + 聚簇索引上）
```

### 命中行锁 + 回表锁聚簇索引

```sql
-- 命中二级索引回表时，聚簇索引对应行也加锁
select * from t where name = 'a' for update;
-- 1. 二级索引 idx_name 上加 X Record Lock on 'a'
-- 2. 回表 → 聚簇索引上加 X Record Lock on id=1
-- ↑ 别的事务 update id=1 也会阻塞
```

## 七、不同隔离级别下的加锁差异

| 隔离级别 | 当前读加锁 | 快照读 |
|:---|:---|:---|
| **RC** | 只加 Record Lock，**几乎不加 Gap Lock** | MVCC（每次 select 新 ReadView） |
| **RR**（默认） | Next-Key Lock（Record + Gap） | MVCC（首次 select 固定 ReadView） |
| **Serializable** | 所有 select 隐式加 `lock in share mode` | 退化为当前读 |

### RC 不加 Gap Lock 的实战影响

```sql
-- 表 t 有 id=5,10,15,20，RC 级别
-- 事务 A：
select * from t where id > 10 and id < 15 for update;
-- 只锁 id=10 范围的行（如果有），不加 (10,15) Gap

-- 事务 B：
insert into t values (12);
-- ✅ 可以插入！RR 下会被 Gap Lock 阻塞，RC 下不会

-- → RC 不防幻读；但并发性更好
```

> **生产调优**：高并发热点行更新场景，可以考虑把单库隔离级别从 RR 调到 RC，减少间隙锁竞争（牺牲防幻读能力换并发）。

## 八、死锁深度

[事务与锁.md](5.%20事务与锁.md) 第七节讲过死锁基础，这里补**触发条件 + 算法 + 排查**。

### 触发条件

1. **互斥**：锁不能共享
2. **持有等待**：持有锁的同时等待别人的锁
3. **不剥夺**：不能强行剥夺别人持有的锁
4. **循环等待**：A 等 B，B 等 A

### InnoDB 死锁检测：Wait-for Graph

```
事务节点 + 等待边构成有向图
检测是否有环 = 死锁
回滚环上"undo 量最小"的事务（释放锁让另一个继续）
```

- **默认开启**：`innodb_deadlock_detect = ON`（8.0 默认）
- **关闭代价大**：高并发下死锁靠超时回滚，业务延迟
- **超时兜底**：`innodb_lock_wait_timeout = 50`（秒）

### 经典死锁场景

**场景 1：交叉加锁顺序**

```
A：update t set ... where id=1 → 锁 1，等 2
B：update t set ... where id=2 → 锁 2，等 1   → 死锁
解决：所有事务按相同顺序加锁
```

**场景 2：Gap Lock 互锁**

```
A：select ... where id between 10 and 20 for update  → 加 (10,20] Gap
B：select ... where id between 15 and 25 for update  → 加 (15,25] Gap
   B 等 A 释放 (15,20]，A 等 B 释放 (20,25]   → 死锁
解决：降级到 RC；或缩小事务范围
```

**场景 3：唯一索引插入冲突**

```
A：insert values (10);   → 唯一冲突等待 → 持有 S 锁等待 X
B：insert values (10);   → 同样冲突等待
   互相等待对方释放 → 死锁
```

### 排查命令

```sql
-- 1) 最近一次死锁详情
show engine innodb status;
-- 在输出里找 LATEST DETECTED DEADLOCK 段

-- 2) 当前所有事务
select * from information_schema.innodb_trx;
-- 字段：trx_id / trx_state / trx_started / trx_rows_locked / trx_rows_modified / trx_query

-- 3) 当前所有锁（8.0 用 Performance Schema）
-- 8.0.13+ 推荐：
select * from performance_schema.data_locks;
select * from performance_schema.data_lock_waits;
-- 5.7 旧版：
select * from information_schema.innodb_locks;
select * from information_schema.innodb_lock_waits;

-- 4) 谁阻塞谁
select
    r.trx_id waiting_trx,
    r.trx_mysql_thread_id waiting_thread,
    b.trx_id blocking_trx,
    b.trx_mysql_thread_id blocking_thread,
    r.trx_query waiting_query,
    b.trx_query blocking_query
from information_schema.innodb_lock_waits w
join information_schema.innodb_trx b on b.trx_id = w.blocking_trx_id
join information_schema.innodb_trx r on r.trx_id = w.requesting_trx_id;

-- 5) 杀掉阻塞的事务
kill <thread_id>;
```

> **生产排查模板**：① `show engine innodb status` 看死锁详情；② `innodb_trx` 找未提交事务；③ `data_locks/waits` 找锁等待链；④ `kill` 阻塞源头事务。

## 九、乐观锁 vs 悲观锁

| 维度 | 悲观锁 | 乐观锁 |
|:---|:---|:---|
| **思路** | 先加锁，独占访问 | 不加锁，提交时检测冲突 |
| **数据库支持** | `select ... for update` / `lock in share mode` | 无原生支持，应用层实现 |
| **适用** | 高竞争写 | 低竞争写，读多写少 |
| **失败代价** | 阻塞等待 | 整个事务回滚重试 |
| **性能** | 持有锁占用连接 | 不持有锁，但冲突时回滚成本高 |

### 乐观锁实现：版本号

```sql
-- 1) 表加版本号字段
alter table account add version int default 0;

-- 2) 业务读取时带版本号
select id, balance, version from account where id = 1;
-- 返回 version=5

-- 3) 提交时检查版本号
update account
   set balance = balance - 100, version = version + 1
 where id = 1 and version = 5;
-- affected rows = 0 → 被人改过 → 重试 / 报错
-- affected rows = 1 → 成功
```

### 悲观锁实现

```sql
-- 显式加行 X 锁
select * from account where id = 1 for update;
-- 整个事务期间别人无法 update / for update 这一行
```

> **选型**：竞争激烈（如秒杀扣库存）→ 悲观锁；竞争稀疏（如订单更新）→ 乐观锁；分布式锁包事务另说，详见 [Spring/事务.md](../Spring/事务.md) Q11。

## 十、锁监控与排查

### 锁等待排查五步

```text
1) 应用报错：Lock wait timeout exceeded
2) show processlist;              ← 看 State=updating 的事务
3) select * from innodb_trx;      ← 看 trx_started 最早的事务（疑似源头）
4) data_locks / data_lock_waits  ← 找锁等待链
5) kill <源头事务 thread_id>
```

### 关键监控指标

| 指标 | 来源 | 关注点 |
|:---|:---|:---|
| 活跃事务数 | `innodb_trx` count | 长时间运行的事务 |
| 锁等待数 | `data_lock_waits` count | >0 说明有竞争 |
| 行锁等待时间 | `innodb_metrics` 的 `lock_wait_timeouts` | 累计超时次数 |
| 死锁次数 | `show engine innodb status` 的 LATEST DETECTED DEADLOCK | 高频死锁 = 业务加锁顺序乱 |
| 行锁等待时间均值 | Performance Schema `events_waits_summary_global_by_event_name` | wait/synch/cond/... |

### 主要参数

```ini
innodb_lock_wait_timeout = 50        # 行锁等待超时 50s
innodb_deadlock_detect = ON          # 死锁检测（默认开）
innodb_print_all_deadlocks = ON      # 死锁全打错误日志（默认关）
innodb_status_output_locks = ON      # show engine innodb status 显示锁
```

> **生产设置**：`innodb_print_all_deadlocks = ON` 必开——死锁日志默认只保留最后一次，全量打错误日志便于回溯历史死锁。

## 十一、易错点

| 易错点 | 说明 |
|:---|:---|
| **以为意向锁之间互斥** | IS/IX 之间全兼容，意向锁只与表锁竞争 |
| **以为 InnoDB 行锁锁的是数据行** | 锁的是索引项；无索引退化为表锁（详见 [事务与锁.md](5.%20事务与锁.md) 易错点） |
| **以为 Gap Lock 在所有级别都有** | RC 不加 Gap Lock（除唯一约束 / 外键检查），RR 才默认加 |
| **以为唯一索引等值查询加 Next-Key** | 唯一索引等值命中 → 优化 1 退化为 Record Lock，前后间隙不锁 |
| **以为乐观锁有 DB 原生支持** | 必须自己在表加 version 字段，应用层判断 |
| **以为死锁只发生在并发 update** | insert 唯一冲突、Gap Lock 互锁都可能死锁 |
| **以为 MDL 只在 DDL 时持有** | select / DML 也隐式持有 MDL 共享读锁；长事务持有 MDL → DDL 雪崩 |
| **以为不显式 for update 就不加锁** | 普通 select 不加锁（快照读）；但 update / delete / insert 都隐式加 X 锁 |
| **以为 AUTO-INC 锁一定持表锁** | 8.0 默认 `mode=2` 用轻量级 mutex，不持表锁 |
| **以为加锁规则只看 SQL** | 还要看索引类型（唯一/非唯一）、隔离级别（RC/RR）、是否命中 |

---

## 十二、一句话总结

InnoDB 锁分**表级**（意向锁 IS/IX、AUTO-INC、MDL 元数据锁）+ **行级**（Record/Gap/Next-Key/Insert Intention），行锁锁的是**索引**而非数据行。**RR 默认加锁 = Next-Key Lock（左开右闭）**，遵循「**两原则两优化**」：原则 1 基本单位是 Next-Key、原则 2 访问到的对象才加锁、优化 1 唯一索引等值命中退化为 Record Lock、优化 2 非唯一索引向右遍历最后一个不满足值退化为 Gap Lock。**RC 不加 Gap**（除唯一约束 / 外键检查），高并发热点场景可降级到 RC 换并发。死锁检测靠 wait-for graph 算法，回滚 undo 量最小的事务。生产排查走 `show engine innodb status` + `innodb_trx` + `data_locks/waits` 五步定位源头事务。秒杀等竞争激烈用悲观锁 `for update`，订单更新等稀疏冲突用乐观锁版本号。
