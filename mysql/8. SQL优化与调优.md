# MySQL SQL 优化与调优面试题

SQL 优化的目标是**减少磁盘 I/O 和扫描行数**。核心手段是「让查询走上合适的索引」，配套还有分页、count、大表等场景的专项优化。

---

## 一、优化的整体思路（自顶向下）

| 层次 | 手段 |
|:---|:---|
| **SQL 与索引** | 用 explain 分析、加合适索引、避免索引失效、覆盖索引 |
| **表结构** | 合理字段类型、适度冗余（反范式）、垂直/水平拆分 |
| **架构** | 读写分离、主从复制、缓存（Redis）、分库分表 |
| **配置/硬件** | Buffer Pool 大小、连接数、SSD |

> 面试回答顺序：先定位慢 SQL（慢查询日志）→ explain 分析 → 优化索引/改写 SQL → 再考虑架构层。

---

## 二、explain —— 分析执行计划（必考）

`explain select ...` 输出每一行的执行细节，重点看这几列：

| 列 | 含义 | 关注点 |
|:---|:---|:---|
| **type** | 访问类型（性能等级） | 最重要，见下表 |
| **key** | 实际用到的索引 | 为 null 说明没走索引 |
| **rows** | 预估扫描行数 | 越小越好 |
| **Extra** | 额外信息 | 看有无 `Using filesort`、`Using temporary` |
| possible_keys | 可能用到的索引 | 有但 key 为空 → 索引失效 |
| key_len | 用到索引的字节数 | 判断联合索引用了几列 |

### type 从好到差（要背）

```
system > const > eq_ref > ref > range > index > ALL
```

| type | 含义 | 好坏 |
|:---|:---|:---:|
| const | 主键/唯一索引等值查询，最多一行 | 极好 |
| eq_ref | join 时用主键/唯一索引关联 | 很好 |
| ref | 普通索引等值查询 | 好 |
| range | 索引范围扫描（`>`、`between`、`in`） | 尚可 |
| index | 扫描整个索引树 | 较差 |
| **ALL** | **全表扫描** | **最差，需优化** |

> 优化目标：至少到 **range**，理想到 **ref / const**。看到 `type=ALL` 且 rows 很大，重点优化。

**Extra 里的危险信号**：

| Extra | 含义 | 优化方向 |
|:---|:---|:---|
| `Using filesort` | 用了额外排序（没走索引排序） | 给 order by 列加索引 |
| `Using temporary` | 用了临时表（常见于 group by / distinct） | 优化分组字段索引 |
| `Using index` | ✅ 覆盖索引，不回表 | 好现象 |
| `Using where` | 用 where 过滤 | 正常 |

## 三、慢查询日志

定位「哪些 SQL 慢」的第一手段。

```sql
show variables like 'slow_query_log';        -- 是否开启
set global slow_query_log = on;              -- 开启
set global long_query_time = 1;              -- 超过 1 秒记为慢查询
show variables like 'slow_query_log_file';   -- 日志文件位置
```

> 配合 `mysqldumpslow` 或 `pt-query-digest` 工具分析慢日志，找出最耗时的 SQL。

## 四、SQL 改写常见优化

### 1. 避免 `select *`

只查需要的列，减少网络传输，还可能触发**覆盖索引**避免回表。

### 2. 分页优化（深分页问题）

```sql
-- ❌ 慢：offset 100000 要先扫描并丢弃前 10 万行
select * from user order by id limit 100000, 10;

-- ✅ 优化一：延迟关联（子查询先在覆盖索引上定位主键）
select * from user u
join (select id from user order by id limit 100000, 10) t
on u.id = t.id;

-- ✅ 优化二：书签记录法（记住上一页最后的 id）
select * from user where id > 100000 order by id limit 10;
```

> 深分页慢在于 `offset` 要扫描并丢弃大量行。书签法把「跳过 N 行」变成「按索引定位」，最快。

### 3. count 优化

```sql
count(*)  -- 推荐，优化器会选最小的索引统计，语义是「统计行数」
count(1)  -- 与 count(*) 性能基本一致
count(字段) -- 会跳过该字段为 null 的行，且可能不走最优索引
```

> InnoDB 无法像 MyISAM 那样直接返回行数（因 MVCC 行数不定）。海量数据要精确 count 可维护一张计数表或用 Redis。

### 4. join 优化

- 小表驱动大表（`in` 用于小表，`exists` 用于大表）
- 被驱动表的关联字段**要有索引**（否则 join 变慢）
- 关联字段类型保持一致，避免隐式转换

### 5. order by / group by 优化

- 让排序/分组字段能利用索引的**有序性**，避免 `Using filesort` / `Using temporary`
- 联合索引顺序与 `order by` 一致时可省去排序

## 五、大表优化方案（架构层）

数据量到千万/亿级时，单表优化到极限后走架构手段。

| 方案 | 说明 | 代价 |
|:---|:---|:---|
| **读写分离** | 主库写、从库读，binlog 主从复制 | 有主从延迟 |
| **加缓存** | 热点数据放 Redis，挡住大部分读 | 缓存一致性问题 |
| **分区表** | 单表按范围/哈希分成多个物理分区 | 仍是单库 |
| **垂直分表** | 把大字段/冷字段拆到另一张表 | join 变多 |
| **水平分表** | 按 id / 时间把数据分散到多张表 | 跨表查询复杂 |
| **分库分表** | 数据分散到多个库多张表（如 ShardingSphere） | 分布式事务、跨库 join、扩容麻烦 |

> 分库分表的核心难点：**分片键选择**、**全局唯一 ID**（雪花算法）、**跨库 join / 分页 / 事务**。能不拆就不拆，先用缓存和读写分离扛。

## 六、主从复制原理

读写分离的基础，基于 **binlog**。

```
主库：写操作 → 记录 binlog
从库：IO 线程拉取主库 binlog → 写入 relay log（中继日志）
       SQL 线程重放 relay log → 数据同步
```

| 问题 | 说明 |
|:---|:---|
| **主从延迟** | 从库单线程重放跟不上主库，导致刚写完读不到 |
| 解决延迟 | 强一致读走主库、并行复制、半同步复制 |

## 七、易错点

| 易错点 | 说明 |
|:---|:---|
| **不看 explain 盲目加索引** | 索引是否生效、够不够，都要以 explain 为准 |
| **深分页直接加 limit** | offset 大时极慢，用延迟关联或书签法 |
| **count(字段) 当 count(\*)** | count(字段) 会忽略 null 且可能不走最优索引 |
| **join 被驱动表无索引** | 会导致嵌套循环全表扫，性能骤降 |
| **一上来就分库分表** | 应先穷尽索引/缓存/读写分离，分表引入巨大复杂度 |
| **索引建太多** | 拖慢写入、占空间、可能误导优化器 |

---

## 八、一句话总结

SQL 优化 = **减少扫描行数和 I/O**。流程是「**慢查询日志定位 → explain 分析（看 type/key/rows/Extra）→ 优化索引 + 改写 SQL（覆盖索引、深分页、count、join）→ 架构层（缓存、读写分离、分库分表）**」。核心永远是**让查询走上合适的索引**。
