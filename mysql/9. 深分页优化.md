# 深分页优化

> `limit 1000000, 10` 为什么慢、怎么救。速记版见 [SQL优化与调优.md](8.%20SQL优化与调优.md)，本文展开原理、多列排序变体与选型。

---

## 一、为什么深分页慢

```sql
select * from user order by id limit 1000000, 10;
```

MySQL 的执行逻辑是**「扫够 offset + size 行，再丢掉前 offset 行」**：

```
主键索引（顺序扫描）
 [1][2][3]...[999999][1000000][1000001]...[1000010]
  └──────────读出后全部丢弃──────────┘ └──返回这10行──┘
                扫 100 万行 = 白读                    扫 10 行 = 有效
```

| 慢的放大因素 | 说明 |
|:---|:---|
| 扫描量与 offset 成正比 | 第 100 页和第 10000 页成本差百倍 |
| **二级索引排序 + 回表** | `order by create_time limit ...`：先在二级索引上找偏移，**每一行都要回表**再丢弃（回表原理见 [索引.md](4.%20索引.md)），100 万次随机 I/O |
| filesort | 排序列无索引时，还要先全量排序再偏移 |

## 二、方案一：游标 / 书签记录法（连续翻页最优）

**思路：把「跳过 N 行」换成「从上页末尾的定位点继续」**——用索引定位代替扫描偏移。

```sql
-- 上一页最后一条 id = 1000000，下一页：
select * from user where id > 1000000 order by id limit 10;
```

- 主键索引直接定位到 1000001，**扫 10 行返回 10 行**，与页深无关；
- 局限：**只能连续翻页（上一页/下一页）**，不能跳到第 N 页——把「页码」改成「游标」传给前端（现代产品的主流交互：Feed 流、聊天记录、ES 的 `search_after` 同思想）。

### 变体：多列排序的游标

按 `(create_time, id)` 排序时，游标要**两列组合比较**，否则同一秒多条数据会丢/重：

```sql
-- 上页末尾：create_time='2026-08-29 10:00:00', id=88
select * from orders
where create_time < '2026-08-29 10:00:00'
   or (create_time = '2026-08-29 10:00:00' and id < 88)
order by create_time desc, id desc
limit 10;
```

> **排序键必须带唯一列兜底**（时间戳不唯一，永远拼上 id），且排序键建联合索引 `(create_time, id)` 才能走索引序。

## 三、方案二：延迟关联（必须支持跳页时）

**思路：先用覆盖索引把 offset 的开销压在「只扫主键」上，最后只回表 10 次。**

```sql
select * from user u
join (select id from user order by id limit 1000000, 10) t   -- ① 覆盖索引：只扫 id，不回表
on u.id = t.id;                                              -- ② 拿 10 个 id 才回表
```

为什么快：

| 版本 | offset 100 万的开销 |
|:---|:---|
| 直接 `select *` | 扫 100 万行**每行回表**（随机 I/O × 100 万） |
| 延迟关联 | 子查询在主键索引上**顺序扫 100 万个 id**（无回表），再回表 10 次 |

仍是 O(offset) 扫描，但把最贵的随机回表砍到只剩 10 次，通常快一个数量级。

### 变体：子查询定位法（offset 可先算出来）

```sql
select * from user
where id >= (select id from user order by id limit 1000000, 1)  -- 先拿起点 id
order by id limit 10;
```

## 四、方案三：业务侧约束（治本）

| 手段 | 说明 |
|:---|:---|
| **限制最大页深** | 只开放前 100/500 页（Google、ES 默认 `from+size ≤ 10000` 都这么干）；深需求引导到筛选条件缩小范围 |
| 跳页 → 改游标交互 | 产品层面把「跳页」改成「下一页/无限下拉」，全部走游标法 |
| 默认排序 + 强制过滤 | 高基数筛选条件（时间窗/类目）让结果集天然变小 |
| count 同步优化 | 页码导航需要总数时：近似值/单独缓存 count，别每页 `count(*)` |

> 面试观点：**深分页大多是伪需求**——用户不会翻到 10 万条，把跳页改成游标是产品和性能的双赢。

## 五、特殊场景

| 场景 | 对策 |
|:---|:---|
| **分库分表下翻页** | 各分片都要取 `offset+size` 条归并，深页代价 × 分片数 → 业务层限深 + 游标（见 [分库分表.md](12.%20分库分表.md)） |
| ES 深分页 | `from+size` 性能差 → `search_after`（游标思想）；跨分片全局排序用 `scroll`/PIT |
| 导出全量数据 | 别用分页循环，按游标分批（`where id > last`）或读 binlog |

## 六、选型对比

| 方案 | 复杂度 | 支持跳页 | 适用 |
|:---|:---:|:---:|:---|
| 游标/书签法 | 低 | ❌ | **首选**：Feed 流、连续翻页 |
| 延迟关联 | 低 | ✅ | 后台管理「必须跳页」的列表 |
| 子查询定位法 | 低 | ✅ | 同上，单列主键排序时更直观 |
| 业务限深 | 零开发 | — | 所有方案的保底搭配 |

---

## 易错点

| 坑 | 说明 |
|:---|:---|
| 游标排序键不唯一 | 按 create_time 翻页丢数据/重复——**永远拼上 id 兜底** |
| 游标列没索引 | 书签法的前提是定位列有索引，否则 `where id > ?` 变全表扫 |
| 延迟关联写反 | `select * from (select * from user limit ...) t`——子查询里就 `select *`，回表照样 100 万次 |
| offset 放在回表之后 | 延迟关联的核心是**覆盖索引内完成 offset**，别破坏这个前提 |
| count 和分页一起全查 | 列表页每页都 `count(*)`，深表直接拖垮——总数走缓存/估算 |
| 分库分表下照用 limit | 归并放大，见第五节 |

---

## 一句话总结

深分页慢在「**扫 offset 行再丢弃**」，二级索引下还乘上回表：**连续翻页用游标法**（定位代替偏移，O(logN)+10），**必须跳页用延迟关联**（覆盖索引内完成 offset，只回表 10 次），**兜底靠业务限深**——排序键永远带唯一列。
