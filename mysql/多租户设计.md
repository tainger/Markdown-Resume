# 多租户设计

> SaaS 的核心架构题：**一套系统服务 N 家客户，数据怎么隔离、请求怎么路由、和分库分表怎么结合**。面试常与分库分表、权限体系连着问。

---

## 一、三种隔离方案（必考对比）

| 方案 | 做法 | 隔离性 | 成本 | 适用 |
|:---|:---|:---:|:---:|:---|
| **独立数据库** | 一租户一个 DB 实例/schema | ★★★ | ★★★ | 金融/医疗等强合规、大客户 |
| **独立 Schema** | 共享实例，一租户一个 schema | ★★ | ★★ | 中等隔离需求，迁移恢复方便 |
| **共享表 + tenant_id** | 所有表加租户列，行级隔离 | ★ | ★ | **主流**：海量小租户、成本敏感 |

**决策不是三选一，而是分池**：

```
                  ┌─ VIP/合规租户 ──> 独立库池（独立实例，随便定制）
租户接入路由 ──按等级──┤
                  └─ 普通租户 ────> 共享库池（共享表 + tenant_id，内部再分片）
```

> 判断依据：**租户数量 × 合规要求 × 客户单价**。小租户独立库 = 连接数与运维成本爆炸；大客户共享表 = 串库事故与合规风险。

## 二、租户识别与路由（请求怎么知道是谁）

| 载体 | 例子 | 说明 |
|:---|:---|:---|
| 子域名 | `tenant-a.app.com` | 天然隔离，SaaS 最常见 |
| JWT claim | `{"tenant_id": "t1001"}` | 认证时写入，网关解析 |
| Header / 路径 | `X-Tenant-Id`、`/t1001/api` | 内部调用常用 |

**关键：租户 ID 一旦从网关解析出，就要全链路传递**——Java 标准做法是 ThreadLocal 上下文：

```java
public class TenantContext {
    private static final ThreadLocal<String> CURRENT = new ThreadLocal<>();

    public static void set(String tenantId) { CURRENT.set(tenantId); }
    public static String get()               { return CURRENT.get(); }
    public static void clear()               { CURRENT.remove(); }   // ★ 线程复用必须清理
}
```

### SQL 自动注入租户条件（别靠手写）

手写 `where tenant_id = ?` 必有漏网，标准方案是 **MyBatis 拦截器自动改写 SQL**：

```java
// MyBatis-Plus 提供TenantLineInnerInterceptor，原理见 Mybatis 插件机制
// SELECT * FROM orders WHERE user_id = ?
//   ↓ 拦截器改写（不需要开发者感知）
// SELECT * FROM orders WHERE user_id = ? AND tenant_id = 't1001'
```

- 拦截器从 `TenantContext` 取租户 ID 拼进所有 DML；
- 字典等共享表加入**忽略名单**；
- 完整原理 → [../Mybatis/插件机制与高级特性.md](../Mybatis/插件机制与高级特性.md)。

> 多租户 + 异步/线程池：ThreadLocal 会断，需用装饰器包装 Runnable 或阿里 TTL 传递上下文（坑见 [ThreadLocal 源码分析](../java/ThreadLocal源码分析.md)）。

## 三、多租户 × 分库分表（P7 组合题）

| 设计点 | 方案 |
|:---|:---|
| 分片键 | **tenant_id 优先**（天然按客户聚合，租户内查询不广播） |
| 大租户倾斜 | **分片键 = tenant_id + 实体 ID** 组合 hash；或大租户数据按时间二次分片 |
| 混合池路由 | 元数据表维护 `tenant → 数据源/分片` 映射，路由层按查表法分发（见 [分库分表.md](分库分表.md)） |
| Noisy Neighbor | 共享池里一个大租户拖垮大家 → 连接数/QPS 配额限流，超标租户**搬去独立池** |
| 租户迁移 | 按租户粒度搬迁（数据天然以 tenant_id 聚簇），比按行迁移简单得多 |

```
共享分片池（tenant_id hash 分片）
┌──────────┬──────────┬──────────┐
│ shard_0  │ shard_1  │ shard_2  │   t1001 太大 → 摘出迁到独立库
│ 小租户们  │ 小租户们  │ t1001⚠️  │   元数据改指向 → 按租户整体搬迁
└──────────┴──────────┴──────────┘
```

## 四、配套设计清单

| 维度 | 要点 |
|:---|:---|
| **唯一索引** | 所有业务唯一键**必须含 tenant_id**：`(tenant_id, username)`——否则 A 租户注册了同名用户 B 就注册不了 |
| **缓存** | Redis key 加租户前缀：`t1001:user:5`，防串数据；配置类缓存按租户隔离 |
| **全局数据** | 字典/配置分「平台级（共享表）」与「租户级（带 tenant_id）」两张表 |
| **计费计量** | 用量事件（调用量/存储量）打点 → 聚合出账，通常落独立计量库 |
| **数据安全** | 逻辑删除条件带 tenant_id；导出/备份按租户粒度可提取（退租返还数据） |
| **可观测** | 日志/Metrics/Trace 全部带租户维度，问题可按租户定位 |
| **定时任务** | 批处理按租户分组执行并传递上下文，防止串租户写库 |

---

## 易错点

| 坑 | 事故现场 |
|:---|:---|
| 唯一索引漏 tenant_id | 租户间数据互斥，A 创建成功 B 永远创建失败 |
| **ThreadLocal 不清理** | 线程复用后下个请求**沿用上个租户 ID** → 跨租户写入（最经典串库事故） |
| 异步/线程池丢上下文 | 定时任务、@Async 里的查询没有租户条件，全表扫或查错库 |
| 缓存 key 不带租户 | 热点用户数据互相覆盖，读出别人家的数据 |
| 手写 SQL 漏 where 条件 | 依赖拦截器兜底 + 测试用「双租户比对」用例卡点 |
| 所有租户共用连接池 | Noisy Neighbor：一个大客户把连接耗尽 → 分池 + 配额 |
| 共享表方案无逃生通道 | 大客户要独立库时才发现无处可迁——设计期就预留 tenant→池 的元数据路由 |

---

## 一句话总结

**隔离按成本分层：合规大客户独立库、普通租户共享表 + tenant_id**；请求靠「网关解析租户 → ThreadLocal 上下文 → MyBatis 拦截器自动拼条件」全链路兜住；与分库分表结合时**分片键选 tenant_id、大租户摘池独立部署**；三条保命线——**唯一索引含 tenant_id、缓存 key 带租户、ThreadLocal 用完必清理**。
