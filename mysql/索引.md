# MySQL 索引面试题

索引是**帮助 MySQL 高效获取数据的排好序的数据结构**。它以额外的写入和存储空间为代价，换取查询时的加速——本质是「用空间换时间」，和「减少磁盘 I/O 次数」。

---

## 一、为什么索引用 B+ 树，不用别的结构？

| 结构 | 为什么不选 |
|:---|:---|
| **哈希表** | 只能等值查询 `=`，不支持范围 `>`、`<`、`between` 和排序 `order by` |
| **二叉搜索树 / AVL / 红黑树** | 树太高（每层一次磁盘 I/O），数据量大时高度爆炸 |
| **B 树** | 非叶子节点也存数据，导致每个节点能放的 key 变少 → 树更高；且叶子间无链表，范围查询要回中序遍历 |
| **B+ 树** ✅ | 非叶子只存索引、叶子存全部数据且用**双向链表**串联，树矮（3~4 层存千万级数据）、范围查询快 |

> 核心口诀：**B+ 树矮胖、叶子有序且链表相连**，既减少磁盘 I/O，又天然支持范围查询和排序。

**为什么 B+ 树只有 3~4 层就能存千万数据？**

InnoDB 一个节点（一页）默认 16KB = 16384 字节。分别算非叶子节点和叶子节点能放多少东西：

**非叶子节点**（存索引项 = 主键值 + 子页指针）：

| 组成 | 字节数 |
|:---|---:|
| 主键值（bigint） | 8 |
| 子页指针（page number） | 6 |
| **合计一项** | **14** |

一页存多少项 = `16384 / 14 ≈ 1170` 项 → 每个非叶子节点最多指向 1170 个子节点

**叶子节点**（存整行数据）：

假设一行数据约 1KB = 1024 字节（粗略估算，实际取决于列数和列类型）

一页存多少行 = `16384 / 1024 = 16` 行

**三层 B+ 树总容量（连乘）**：

```
第 1 层（根）：   1 个节点 × 1170 个指针        = 1170 个第 2 层节点
第 2 层：      1170 个节点 × 1170 个指针        = 1170 × 1170 个第 3 层节点
第 3 层（叶子）：1170 × 1170 个叶子 × 每叶 16 行 = 1170 × 1170 × 16 ≈ 2190 万行
```

| 层数 | 公式 | 容量 |
|:---:|:---|:---|
| 2 层 | `1170 × 16` | ≈ 1.8 万 |
| 3 层 | `1170 × 1170 × 16` | ≈ 2000 万 |

所以三层 B+ 树就能撑起千万级表，查一次数据最多 3 次磁盘 I/O（根节点常驻内存，实际更少）。

> `1KB/行`是假设——实际行 100B 时一页存 160 行、4KB 时一页存 4 行。取 1KB 是为了让结果落在「千万级」这个常见量级，面试好记。

## 二、聚簇索引 vs 二级索引（非聚簇索引）

这是 InnoDB 最核心的概念，几乎必考。

| 维度 | 聚簇索引（主键索引） | 二级索引（辅助索引） |
|:---|:---|:---|
| 叶子节点存什么 | **整行数据** | **主键值** |
| 一张表有几个 | 只有 1 个 | 可以有多个 |
| 如何确定 | 有主键用主键；无主键用第一个唯一非空索引；再无则隐式生成 `rowid` | 普通 `index` / `unique` |

**回表（Back to Table）**：通过二级索引查到主键值后，还要再拿主键去聚簇索引查一次完整行数据，这个过程叫「回表」。

```
select * from user where name = 'Tom';
-- 1. 在 name 二级索引上找到 name='Tom' → 得到主键 id=5
-- 2. 拿 id=5 回聚簇索引查出整行  ← 这一步就是回表
```

> 回表 = 走了两棵 B+ 树。能用**覆盖索引**避免回表就尽量避免。

## 三、覆盖索引与最左前缀

### 覆盖索引（Covering Index）

如果一个查询**所需的所有列都在同一个索引里**，就不用回表，直接在二级索引上返回，这叫覆盖索引。`explain` 的 `Extra` 会显示 `Using index`。

```sql
-- 建立联合索引 (name, age)
select name, age from user where name = 'Tom';  -- 覆盖索引，不回表 ✅
select * from user where name = 'Tom';           -- 要 * 里的其他列，回表 ❌
```

> 优化技巧：`select *` 改成只查需要的列，让索引「覆盖」查询。

### 最左前缀原则（Leftmost Prefix）

联合索引 `(a, b, c)` 相当于建了 `(a)`、`(a,b)`、`(a,b,c)` 三个索引。查询必须**从最左列开始、且不跳列**，才能命中索引。

| 查询条件 | 能否用索引 | 说明 |
|:---|:---:|:---|
| `where a = 1` | ✅ | 用到 a |
| `where a = 1 and b = 2` | ✅ | 用到 a、b |
| `where a = 1 and b = 2 and c = 3` | ✅ | 全用上 |
| `where b = 2` | ❌ | 跳过了 a |
| `where a = 1 and c = 3` | ⚠️ | 只用到 a，c 用不上（b 断了） |
| `where a > 1 and b = 2` | ⚠️ | a 是范围，b 用不上（范围列后失效） |

> 记忆：**从左往右连续匹配，遇到范围查询（`>`、`<`、`like 'xx%'`）就停**。

### 索引跳跃扫描（Index Skip Scan，MySQL 8.0.13+）

8.0 之前，`where b = 2`（跳过 a）严格不走索引。8.0.13 引入了 **Index Skip Scan**，优化器在某些条件下可以**部分绕过最左前缀**。

**原理**：联合索引 `(a, b, c)` 的第一列 `a` 取值很少时（低基数），优化器把查询拆成多个等值子查询：

```sql
-- 联合索引 (a, b, c)，a 只有 ['M', 'F'] 两个值
-- 原 query：select * from t where b = 2 and c = 3
-- 优化器内部拆成：
select * from t where a = 'M' and b = 2 and c = 3   -- 满足最左前缀 ✅
union
select * from t where a = 'F' and b = 2 and c = 3   -- 满足最左前缀 ✅
```

每个子查询都满足最左前缀，分别走索引再合并——所以叫「跳跃扫描」。

**适用条件与局限**：

| 条件 | 说明 |
|:---|:---|
| 第一列取值少（低基数） | `a` 只有 2~几十种值时才有意义；取值多了拆出的子查询太多，优化器放弃 |
| `explain` 看法 | `type = range`、`Extra = Using index for skip scan` |
| 版本 | MySQL 8.0.13+，低版本不支持 |
| 不适用的场景 | 第一列是高基数列（如 user_id），拆不开 → 还是全表扫 |

> 面试口径：「最左前缀是**规则**，但 8.0 的 Skip Scan 是**优化器的补偿**——第一列取值少时能跳过。但生产里联合索引还是应该把高频查询列放最左，不能指望 Skip Scan 兜底。」

## 四、索引失效的常见场景（高频）

| 场景 | 示例 | 原因 |
|:---|:---|:---|
| **在索引列上做运算 / 函数** | `where age + 1 = 10`、`where date(t) = '2024'` | 索引存的是原值，算完就对不上 B+ 树 |
| **隐式类型转换** | `phone` 是 varchar，写 `where phone = 138xxx`（数字） | MySQL 把列转 number，等于在列上加函数 |
| **`like` 以 `%` 开头** | `where name like '%Tom'` | 无法用有序前缀定位，`'Tom%'` 才行 |
| **`or` 连接非索引列** | `where a = 1 or b = 2`（b 无索引） | 有一个没索引就全表扫 |
| **不满足最左前缀** | 联合索引跳列 | 见上一节 |
| **`!=`、`not in`、`is not null`**（视情况） | `where age != 10` | 优化器可能判断走索引不如全表扫 |

> 判断依据始终以 `explain` 为准，优化器会基于**成本估算**决定用不用索引，上面是常见规律而非绝对。

## 五、索引的分类

| 分类维度 | 类型 | 说明 |
|:---|:---|:---|
| 按功能 | 主键索引 / 唯一索引 / 普通索引 / 全文索引 | 主键唯一非空；唯一索引允许一个 null |
| 按列数 | 单列索引 / 联合（复合）索引 | 联合索引遵循最左前缀 |
| 按存储 | 聚簇索引 / 二级索引 | 见第二节 |
| 特殊 | 前缀索引 | 对长字符串取前 N 个字符建索引，省空间 |

```sql
-- 前缀索引：只对 email 前 10 个字符建索引
create index idx_email on user(email(10));
```

## 六、什么时候该建 / 不该建索引？

| 适合建索引 | 不适合建索引 |
|:---|:---|
| 经常出现在 `where` / `order by` / `group by` / `join on` 的列 | 很少查询的列 |
| 区分度高的列（如身份证号） | 区分度低的列（如性别，只有男女） |
| 数据量大的表 | 数据量很小的表（全表扫更快） |
| — | 频繁增删改的列（维护索引有代价） |

> 区分度 = `count(distinct col) / count(*)`，越接近 1 越适合建索引。

## 七、易错点

| 易错点 | 说明 |
|:---|:---|
| **以为主键索引和聚簇索引是两个东西** | InnoDB 里主键索引就是聚簇索引，叶子直接存整行 |
| **联合索引顺序随便建** | 应把**区分度高**、**最常单独查询**的列放最左 |
| **索引越多越好** | 索引会拖慢写入、占空间，且可能误导优化器 |
| **对 null 的误解** | 唯一索引允许多个 null（MySQL 里）；`is null` 有时能走索引 |
| **忘记覆盖索引可去回表** | 大幅提升性能的常见手段 |

---

## 八、一句话总结

MySQL 索引用 **B+ 树**实现「矮胖 + 叶子有序链表」，减少磁盘 I/O 并支持范围查询；InnoDB 的**聚簇索引**叶子存整行、**二级索引**叶子存主键（查非索引列要**回表**）；用好**覆盖索引**和**最左前缀**、避开**索引失效**场景，是 SQL 优化的核心。
