# Redis 持久化面试题

Redis 是内存数据库，一旦宕机数据就会丢失。**持久化**就是把内存中的数据写到磁盘，重启后能恢复。Redis 提供两种方式：**RDB（快照）** 和 **AOF（日志）**，以及 4.0 后的**混合持久化**。

---

## 一、RDB（Redis DataBase）快照

把某一时刻的**全量数据**以二进制形式写入磁盘（默认文件 `dump.rdb`），是**紧凑的全量快照**。

### 触发方式

| 方式 | 说明 | 是否阻塞主线程 |
|:---|:---|:---|
| **save** | 主线程同步生成快照 | ⚠️ **阻塞**，生产禁用 |
| **bgsave** | fork 子进程后台生成 | 仅 fork 瞬间短暂阻塞 |
| **自动触发** | 配置 `save` 规则满足时自动 bgsave | fork 瞬间阻塞 |

```
# redis.conf：900秒内至少1次修改，或300秒内10次，或60秒内1万次
save 900 1
save 300 10
save 60  10000
```

### bgsave 与写时复制（Copy-On-Write）

`bgsave` 靠 `fork` 出子进程来写盘，同时**主进程还能继续处理写请求**，靠的就是 COW：

```
1. fork 子进程，父子共享同一份物理内存页（只读）
2. 子进程负责把这些页写入 RDB 文件
3. 主进程若要修改某页数据，OS 复制一份该页出来再改（写时复制）
   → 子进程看到的仍是 fork 那一刻的旧数据，保证快照一致性
```

> **注意**：fork 时会复制父进程的**页表**，内存越大 fork 越慢（短暂阻塞）；如果 bgsave 期间父进程写入频繁，会产生大量页复制，内存可能瞬间翻倍。

### 优缺点

| 优点 | 缺点 |
|:---|:---|
| 文件紧凑、体积小 | **可能丢数据**：两次快照之间宕机，这期间的数据全丢 |
| 恢复速度快（直接加载二进制） | fork 子进程有开销，大内存时卡顿 |
| 适合备份、灾难恢复 | 快照频率难权衡（太频繁 fork 开销大） |

## 二、AOF（Append Only File）

以**追加**的方式记录每一条**写命令**（以 Redis 协议格式），恢复时重新执行一遍命令即可。默认关闭，需 `appendonly yes` 开启。

### 写回策略（appendfsync）

写命令先进 AOF 缓冲区，再由策略决定何时 `fsync` 刷盘：

| 策略 | 刷盘时机 | 性能 | 安全性 |
|:---|:---|:---|:---|
| **always** | 每条写命令都刷盘 | 最差 | 最高，几乎不丢 |
| **everysec**（默认） | 每秒刷一次 | 折中 | 最多丢 1 秒 |
| **no** | 交给操作系统决定 | 最好 | 最差，可能丢很多 |

> **关键顺序**：AOF 是**先执行命令、成功后再写日志**（写后日志），MySQL 的 redolog 是先写日志后执行（WAL）。好处是不会记录错误命令；坏处是命令执行后、写日志前宕机会丢这条。

### AOF 重写（rewrite）

AOF 会越来越大，需要"瘦身"。重写会**根据当前内存数据**生成一份最精简的等价命令集，而不是简单压缩旧文件。

```
# 对同一个 key 的多次操作
set num 1
incr num        →  重写后只保留一条：
incr num             set num 3
```

- 由 `bgrewriteaof` fork 子进程完成，同样用 COW。
- 重写期间的新写命令会同时写入 **AOF 缓冲区**和 **AOF 重写缓冲区**，重写完成后把重写缓冲区内容追加到新文件，保证数据不丢。

## 三、混合持久化（Redis 4.0+，推荐）

单用 RDB 会丢数据，单用 AOF 恢复慢、文件大。**混合持久化**结合两者优点：

```
AOF 重写时：
  ┌─────────────────┬──────────────────────┐
  │  RDB 格式全量快照  │  AOF 格式的增量写命令   │
  └─────────────────┴──────────────────────┘
       (前半段)              (重写期间的新命令)
```

- 前半部分是 RDB 二进制全量（**恢复快**），后半部分是 AOF 增量命令（**丢数据少**）。
- 开启：`aof-use-rdb-preamble yes`（4.0 后默认开启）。

---

## 四、RDB vs AOF 对比

| 维度 | RDB | AOF |
|:---|:---|:---|
| 数据形式 | 二进制全量快照 | 文本写命令日志 |
| 文件体积 | 小 | 大（重写可缓解） |
| 数据安全 | 丢数据多（两次快照间） | 丢数据少（最多 1 秒） |
| 恢复速度 | 快 | 慢（重放命令） |
| 对性能影响 | fork 时卡顿 | everysec 影响小 |
| 适用场景 | 备份、可容忍分钟级丢失 | 数据完整性要求高 |

> **如何选？** 生产环境推荐 **RDB + AOF 混合**：RDB 定期做冷备，AOF 保证丢数据少。若只做缓存、可容忍丢失，用 RDB 即可。

---

## 五、数据恢复优先级

Redis 重启加载数据时：

```
如果开启了 AOF：优先用 AOF 恢复（数据更全）
否则：用 RDB 恢复
```

---

## 六、易错点

| 易错点 | 说明 |
|:---|:---|
| **以为 AOF 是先写日志** | AOF 是**写后日志**（先执行再记），与 MySQL WAL 相反 |
| **everysec 就绝对不丢** | 仍可能丢**最多 1 秒**的数据 |
| **AOF 重写是压缩旧文件** | 是根据**当前内存状态**重新生成，不读旧 AOF |
| **fork 不阻塞** | fork 瞬间会复制页表，大内存时有明显阻塞 |
| **RDB 恢复用 AOF 校验** | 重启优先级 AOF > RDB（若两者都开） |
| **主从复制不用持久化** | 从库全量同步靠的就是 RDB 文件传输 |

---

## 七、一句话总结

Redis 持久化两条路：**RDB** 是二进制全量快照，靠 `bgsave` + **写时复制**在后台生成，体积小、恢复快，但两次快照间宕机会丢数据；**AOF** 是追加写命令的日志（**写后日志**），`everysec` 策略下最多丢 1 秒，但文件大、恢复慢，靠**重写**瘦身。生产推荐 **4.0 的混合持久化**：RDB 全量打底 + AOF 增量兜底，兼顾恢复速度和数据安全。
