# Redis 生产问题与排查手册面试题

Redis 生产事故不是考「背命令」，而是考**排查思路**：看到现象 → 定位故障域 → 用对命令 → 找到根因 → 止血 + 根治。本手册汇总 7 大故障域的高频生产问题，每个统一「现象 → 排查命令 → 根因 → 解决方案」格式，机制细节链回对应专题笔记。

---

## 零、生产问题总览

| 故障域 | 典型现象 | 首查命令 | 详细笔记 |
|:---|:---|:---|:---|
| **阻塞类** | RT 飙升、请求超时、CPU 低但响应慢 | `SLOWLOG GET`、`CLIENT LIST` | 本手册第一章 |
| **内存类** | OOM 报错、内存碎片高、淘汰频繁 | `INFO memory`、`MEMORY USAGE` | 本手册第二章 |
| **连接类** | `maxclients reached`、连接数突增 | `INFO clients`、`CLIENT LIST` | 本手册第三章 |
| **持久化类** | fork 卡顿、AOF 损坏、磁盘满 | `INFO persistence`、`LASTSAVE` | 本手册第四章 |
| **高可用类** | 主从延迟大、脑裂、集群迁移卡顿 | `INFO replication`、`CLUSTER INFO` | 本手册第五章 |
| **一致性类** | 读到旧数据、缓存脏、主从不一致 | `get` 对比、`INFO replication` | 本手册第六章 |
| **性能类** | CPU 打满、网络丢包、热 key 倾斜 | `INFO stats`、`--hotkeys` | 本手册第七章 |

## 一、阻塞类问题（最常见）

### 1.1 慢命令阻塞主线程

**现象**：Redis CPU 不高但 RT 飙升，所有请求排队；`SLOWLOG` 记录慢命令。

**排查命令**：
```bash
SLOWLOG GET 20                    # 最近 20 条慢命令
SLOWLOG LEN                       # 慢日志条数
INFO commandstats                 # 各命令调用次数与耗时
CLIENT LIST                       # 看当前阻塞命令
MONITOR                           # 临时看实时命令（生产慎用）
```

**根因**：Redis 单线程模型，任何 O(N) 命令或耗时操作都会阻塞所有请求。高频元凶：

| 危险命令 | 复杂度 | 替代方案 |
|:---|:---|:---|
| `KEYS *` | O(N) 全库扫描 | `SCAN 0 COUNT 1000` 渐进式 |
| `HGETALL` / `SMEMBERS` | O(N) 全量拉 | `HSCAN` / `SSCAN` 分批 |
| `LRANGE 0 -1` | O(N) 全量取 | 分页 `LRANGE start end` |
| `DEL 大key` | O(N) 同步释放 | `UNLINK` 异步删 |
| `SORT` 大集合 | O(N log N) | 客户端排序或 ZSet |
| `FLUSHALL` | O(N) 清空 | 禁用，用 DBSIZE 验证 |

**解决方案**：
1. 生产环境**禁用 KEYS / FLUSHALL / CONFIG** 等危险命令（`rename-command` 重命名）
2. 大容器命令改 SCAN 系列渐进式
3. 大 key 删改 UNLINK
4. 开启 `latency-monitor-threshold 100` 自动记录 >100ms 事件

```text
# 危险命令防护配置（redis.conf）
rename-command KEYS ""
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command CONFIG "CONFIG_B8f3d2"   # 重命名而非禁用，便于应急
latency-monitor-threshold 100
```

### 1.2 大 Key 阻塞

**现象**：`HGETALL big_hash` 直接把 Redis 打挂；`DEL big_list` 阻塞数十秒。

**排查**：见 [7. 大Key与数据倾斜.md](7. 大Key与数据倾斜.md) 第一章识别工具（`--bigkeys` / SCAN 巡检）。

**根因**：大 key 命令复杂度 O(N) 或释放 O(N)，单线程下阻塞全部请求。

**解决方案**：
- 拆大 key（Hash 分桶、List 按时间段）
- 删大 key 用 `UNLINK` 替代 `DEL`
- 容器大 key 用 `HSCAN` / `SSCAN` 分批拉取

### 1.3 fork 阻塞（持久化触发）

**现象**：bgsave/bgrewriteaof 时 Redis 卡顿数百毫秒到数秒，大内存实例更明显。

**排查**：
```bash
INFO persistence   # latest_fork_usec 显示最近 fork 耗时
INFO memory        # mem_fragmentation_ratio 看碎片
```

**根因**：fork 时复制**页表**（不是复制数据），内存越大页表越大，fork 瞬间阻塞主线程；fork 后子进程靠 COW（写时复制）共享物理页。

**解决方案**：
1. **控制实例内存**：单实例 < 10GB 是 fork 友好区，超过用 Cluster 分片
2. **降低 fork 频率**：AOF 重写触发条件调高（`auto-aof-rewrite-percentage 100`、`auto-aof-rewrite-min-size 64mb`）
3. **避开高峰期**：bgsave 调度到业务低峰
4. **Linux 配置**：`vm.overcommit_memory=1` 允许超量分配，避免 fork 失败；`echo 1 > /proc/sys/vm/dirty_ratio` 调整脏页刷写
5. **关闭透明大页**：`echo never > /sys/kernel/mm/transparent_hugepage/enabled`（THP 会让 fork 时页表膨胀）

### 1.4 Lua 脚本阻塞

**现象**：`EVAL` 执行后 Redis 卡住，其他命令排队。

**排查**：`SLOWLOG` 看到 EVAL 慢记录；`INFO commandstats` 看 eval 耗时。

**根因**：Lua 脚本在 Redis 主进程**原子执行**，默认无超时会一直跑到结束；脚本里循环大量 key 或调用慢命令直接阻塞。

**解决方案**：
1. 设置超时：`lua-time-limit 5000`（5s），超时后脚本标记为 busy
2. **脚本必须短小精悍**，禁止在 Lua 里做循环全量操作
3. 超时后用 `SCRIPT KILL` 终止（仅在脚本未写数据时可用）
4. 复杂计算移到客户端，Lua 只做简单原子判断

## 二、内存类问题

### 2.1 OOM（Out of Memory）

**现象**：写报 `OOM command not allowed when used memory > maxmemory`；或容器被 OOM Kill 杀掉。

**排查**：
```bash
INFO memory          # used_memory / maxmemory / mem_fragmentation_ratio
INFO stats           # evicted_keys 淘汰数
MEMORY DOCTOR        # 7.0+ 自动诊断内存问题
```

**根因**：
- 业务数据量超过 `maxmemory`
- 大 key 占满内存
- 内存碎片高（实际可用 < 配置值）
- 淘汰策略 `noeviction`（默认）写直接报错

**解决方案**：
1. 临时止血：调大 `maxmemory` 或重启释放碎片
2. 治本：拆大 key、加节点扩容、热 key 本地缓存卸压
3. 淘汰策略按场景选：缓存场景用 `allkeys-lru`，持久化场景用 `noeviction` + 告警
4. 告警：`used_memory` 达 `maxmemory` 80% 时触发

### 2.2 内存碎片率高

**现象**：`mem_fragmentation_ratio > 1.5`，实际内存使用远大于数据量。

**排查**：
```bash
INFO memory    # mem_fragmentation_ratio = used_memory_rss / used_memory
```

**根因**：Redis 用 jemalloc 分配器，频繁增删不同大小 key 导致内存碎片；jemalloc 会自动归还部分空闲页，但碎片严重时仍需手动处理。

**解决方案**：
1. **启用碎片整理**（4.0+）：
   ```text
   activedefrag yes
   active-defrag-ignore-bytes 100mb
   active-defrag-threshold-lower 10
   ```
2. 临时：`DEBUG MEMORY PURGE`（4.0+）主动归还空闲页
3. 终极：低峰期重启实例（碎片清空，从 RDB/AOF 恢复）

### 2.3 淘汰频繁

**现象**：`evicted_keys` 持续增长，缓存命中率下降。

**排查**：`INFO stats` 看 `evicted_keys`、`keyspace_hits/misses` 算命中率。

**根因**：内存不足 + 淘汰策略配置不当；大 key 淘汰困难（见 [4. 过期与内存淘汰.md](4. 过期与内存淘汰.md) 第四章）。

**解决方案**：扩容内存 / 拆大 key / 优化淘汰策略；淘汰困难的大 key 提前用 UNLINK 清理。

## 三、连接类问题

### 3.1 连接数打满（maxclients reached）

**现象**：客户端报错 `ERR max number of clients reached`；业务大量超时。

**排查**：
```bash
INFO clients          # connected_clients / maxclients
CLIENT LIST           # 看连接来源、空闲时间
```

**根因**：
- 客户端连接池配置过大
- 连接泄漏（建连不释放）
- 慢命令导致连接堆积（命令不返回，连接不释放）
- 短连接循环创建（高并发下 TIME_WAIT 堆积）

**解决方案**：
1. 临时：调大 `maxclients`（默认 10000），但治标不治本
2. 排查泄漏：`CLIENT LIST` 看 `idle` 字段，对长时间 idle 的连接检查客户端连接池
3. 修复连接池：设最大连接数、空闲超时（Lettuce 默认 60s）
4. 用长连接 + 连接池，禁用短连接高频创建
5. 慢命令根因解决后连接堆积自然消失

### 3.2 连接超时

**现象**：客户端 `connect timeout` 或 `read timeout`。

**排查**：
```bash
INFO stats        # total_connections_received 趋势
ping              # Redis 响应延迟
```

**根因**：
- Redis 阻塞（见第一章）→ 命令不返回 → read timeout
- 网络问题 → connect timeout
- 防火墙/安全组限制

**解决方案**：先定位是 connect 还是 read 超时；read 超时优先查慢命令阻塞，connect 超时查网络和安全组。

## 四、持久化类问题

### 4.1 AOF 文件损坏

**现象**：Redis 启动失败报 AOF 损坏；数据丢失。

**排查**：检查 AOF 文件末尾是否截断（异常退出导致）。

**根因**：宕机时 AOF 写入不完整，末尾残留半截命令。

**解决方案**：
1. **自动修复**（7.0+）：`redis-server --aof-fix ./appendonly.aof`
2. **手动修复**：用 `redis-check-aof --fix appendonly.aof`
3. 数据恢复：AOF 修复后重启，或用 RDB 兜底 + AOF 增量（混合持久化推荐，见 [3. 持久化.md](3. 持久化.md) 第三章）

### 4.2 RDB 失败

**现象**：`bgsave` 失败，`INFO persistence` 显示 `rdb_last_bgsave_status:err`。

**排查**：
```bash
INFO persistence   # rdb_last_bgsave_status / rdb_last_bgsave_time_sec
tail -f redis.log  # 看 fork / 写入错误
df -h              # 磁盘空间
```

**根因**：磁盘满、fork 失败（内存超量分配）、临时目录无权限。

**解决方案**：
1. 磁盘满：清理日志 / 扩容磁盘
2. fork 失败：`vm.overcommit_memory=1`
3. 无权限：`dir` 和 `dbfilename` 配置正确，Redis 用户有写权限

### 4.3 磁盘 IO 瓶颈

**现象**：AOF `appendfsync everysec` 仍卡；bgsave 期间 RT 飙升。

**排查**：
```bash
iostat -x 1        # %util 看磁盘利用率
vmstat 1           # bi/bo 块设备 IO
```

**根因**：磁盘 IOPS 不足，机械盘随机写慢；云盘 IOPS 限流。

**解决方案**：
1. 换 SSD 或本地 NVMe
2. AOF 策略调优：`appendfsync everysec`（每秒刷盘，折中）而非 `always`
3. 持久化与数据盘分离
4. 云盘选 IOPS 更高的规格

## 五、高可用类问题

### 5.1 主从同步延迟大

**现象**：从库读到旧数据；`INFO replication` 显示 `slave_repl_offset` 落后主库 `master_repl_offset` 数秒。

**排查**：
```bash
INFO replication   # master_repl_offset vs slave_repl_offset
redis-cli -p 从库 INFO replication
```

**根因**：
- 主库写 QPS 高，从库单线程回放命令跟不上
- 大 key 同步（主库写大 value，从库重放耗时）
- 网络带宽不足
- 从库机器性能弱

**解决方案**：
1. 读写分离场景对延迟敏感的请求走主库
2. 拆大 key 降低回放耗时
3. 提升从库配置 / 增加从库分摊读压力
4. 监控延迟，超阈值告警
5. 用半同步复制（`min-replicas-to-write` + `min-replicas-max-lag`）保证至少一个从库同步

### 5.2 脑裂（Split-Brain）

**现象**：主从切换后两个主库同时写入；数据丢失。

**排查**：切换后检查是否有两个 master 实例。

**根因**：哨兵网络分区时，原主库未下线但新主已选出；原主继续接受写入，分区恢复后数据冲突。

**解决方案**：
1. 哨兵配置 `min-replicas-to-write 1` + `min-replicas-max-lag 10`：主库发现从库不足时拒绝写入
2. 客户端用哨兵统一路由，禁止直连主库
3. 切换后做数据校验与修复

### 5.3 Cluster slot 迁移卡顿

**现象**：集群扩容 / 重分片时 RT 飙升，`CLUSTER INFO` 显示迁移中。

**排查**：
```bash
CLUSTER INFO
CLUSTER SLOTS
redis-cli --cluster check 127.0.0.1:7000
```

**根因**：迁移 slot 时单 key 迁移阻塞；大 key 迁移尤其慢（见 [7. 大Key与数据倾斜.md](7. 大Key与数据倾斜.md)）。

**解决方案**：
1. 低峰期迁移
2. 拆大 key 后再迁移
3. 用 `redis-cli --cluster reshard` 控制迁移速率

## 六、数据一致性问题

### 6.1 缓存与数据库双写不一致

**现象**：DB 已更新但缓存读到旧值；或缓存删了但又被旧数据回填。

**排查**：对比 DB 与缓存值；看更新时序。

**根因**：详见 [6. 缓存问题与实战.md](6. 缓存问题与实战.md) 第二章，无法强一致，只能最终一致。

**解决方案**：
- 常规：**先更新 DB，再删缓存** + 缓存过期兜底
- 高要求：Canal 订阅 binlog 异步删缓存
- 禁止：先删缓存再更新 DB（并发读会回填旧值）

### 6.2 异步复制丢数据

**现象**：主库写入成功，宕机后从库缺数据。

**根因**：Redis 复制是**异步**的，主库写完立即返回不等待从库确认（见 [5. 高可用与集群.md](5. 高可用与集群.md) 第一章）。

**解决方案**：
1. 半同步复制：主库等待至少一个从库 ACK 才返回（`WAIT numreplicas timeout` 命令）
2. 强一致场景（金融）：Redis 不适合，用 ZooKeeper / etcd
3. 持久化 `appendfsync everysec` 减少丢数据窗口

### 6.3 缓存穿透 / 击穿 / 雪崩

详见 [6. 缓存问题与实战.md](6. 缓存问题与实战.md) 第一章，速查：

| 问题 | 根因 | 止血方案 |
|:---|:---|:---|
| 穿透 | 查 DB 不存在数据 | 布隆过滤器 / 缓存空值 |
| 击穿 | 单个热点 key 过期 | 互斥锁重建 / 逻辑过期 |
| 雪崩 | 大量 key 同时过期 / Redis 宕 | 过期加随机值 + 集群高可用 |

## 七、网络与性能问题

### 7.1 CPU 打满

**现象**：Redis CPU 100%，RT 飙升。

**排查**：
```bash
top -p $(pidof redis-server)
INFO commandstats    # 看哪条命令调用最频繁
redis-cli --hotkeys  # 4.0+ 看热点 key
```

**根因**：
- 大 key 命令（HGETALL / KEYS）
- 热点 key 高 QPS 集中在单节点（Cluster 倾斜）
- Lua 脚本循环
- 压缩 / 解压开销

**解决方案**：
1. 定位危险命令并禁用 / 拆分
2. 热 key 本地缓存兜底（见 [7. 大Key与数据倾斜.md](7. 大Key与数据倾斜.md) 第二章）
3. Cluster 倾斜治理
4. 大 value 改压缩存储（Protobuf）

### 7.2 网络慢 / 丢包

**现象**：RT 不稳定，ping 延迟抖动。

**排查**：
```bash
ping redis-host
mtr redis-host         # 路由追踪 + 丢包
tcpdump -i any port 6379
```

**根因**：跨机房部署、网络拥塞、云网卡限流。

**解决方案**：同机房部署；开启 TCP_NODELAY；调整 `tcp-backlog`。

### 7.3 热 key 流量倾斜

详见 [7. 大Key与数据倾斜.md](7. 大Key与数据倾斜.md) 第二章，治理优先级：本地缓存兜底 → 多副本打散 → 读写分离 → 独立小集群。

```bash

# === 阻塞排查 ===

CLIENT LIST             # 客户端连接详情

# === 内存排查 ===
MEMORY USAGE key SAMPLES 0   # 精确字节
MEMORY DOCTOR                # 7.0+ 自动诊断
redis-cli --bigkeys          # 快速找大 key
redis-cli --memkeys          # 6.0+ 找内存大的 key

# === 持久化排查 ===
INFO persistence        # fork 耗时 / RDB/AOF 状态

# === 高可用排查 ===
INFO replication        # 主从 offset / 延迟

# === 客户端工具 ===
redis-benchmark -q -n 100000 -c 50 -t get,set   # 压测
redis-cli --stat        # 实时 QPS / 内存监控
```

## 九、易错点

| 易错点 | 说明 |
|:---|:---|
| **Redis 是多线程所以不会阻塞** | 命令执行**仍单线程**，6.0 只是网络 IO 多线程；慢命令照样阻塞全部 |
| **KEYS 只在测试用没事** | KEYS O(N) 全库扫描，生产哪怕一次大库也会阻塞数十秒；必须 SCAN |
| **DEL 大 key 比 UNLINK 快** | DEL 同步释放阻塞主线程；UNLINK 后台释放，大 key 必须用 UNLINK |
| **fork 是复制数据** | fork 只复制**页表**（只读共享），写时 COW 才复制页；大内存 fork 慢是页表大 |
| **aof always 最安全** | always 每次写都 fsync，性能极差；everysec 折中且基本不丢 |
| **主从不一致一定是 bug** | 异步复制最终一致是设计；强一致用半同步或别的组件 |
| **调大 maxclients 能解决连接问题** | 治标不治本；根因是连接泄漏 / 慢命令堆积 |
| **Cluster 扩容能解决所有问题** | 扩容只迁槽；大 key / 热 key 不拆，倾斜依旧 |
| **生产可以跑 MONITOR** | MONITOR 记录所有命令，CPU 飙升 50%+，只能临时排查 |
| **OOM 时重启就没事** | 重启从 RDB/AOF 恢复，若数据量不变照样 OOM；必须扩容或拆 key |

---

## 十、一句话总结

Redis 生产问题排查遵循**「现象→故障域→命令→根因→止血+根治」**闭环：阻塞类首查 `SLOWLOG` + `CLIENT LIST`（禁 KEYS/大命令/Lua 阻塞，删大 key 用 UNLINK）；内存类首查 `INFO memory` + `MEMORY USAGE`（OOM 扩容拆 key、碎片率高开 activedefrag、淘汰频繁调策略）；连接类首查 `INFO clients` + `CLIENT LIST`（根因是泄漏/慢命令堆积，调大 maxclients 只治标）；持久化类首查 `INFO persistence`（fork 阻塞控内存/关 THP、AOF 损坏 `--fix`、磁盘满扩容）；高可用类首查 `INFO replication` + `CLUSTER INFO`（主从延迟拆大 key、脑裂用半同步防护、迁移拆大 key）；一致性类记住**双写只能最终一致**、**异步复制会丢数据**；性能类 CPU 打满查危险命令+热 key 倾斜。全程靠监控告警前置，避免被动救火。
