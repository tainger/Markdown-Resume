# 热点 Key 问题与解决方案

> 大 Key 与数据倾斜中已覆盖热 key 基础成因与治理三板斧，本篇深挖**发现定位（4 种探测方法对比）→ 选型决策树 → 生产级实现细节 → 完整实战案例**，解决「线上热 key 怎么发现、发现了怎么选方案、方案落地有哪些坑」三个核心问题。
> 关联基础篇：[7. 大Key与数据倾斜.md](7.%20大Key与数据倾斜.md) 第二章。

## 一、什么是热点 Key

热点 Key（Hot Key）是指**访问频率远高于其他 key 的少量 key**，在集群模式下会导致流量集中到单个节点，引发 QPS 倾斜。

```
正常流量分布：          热点 key 流量分布：
节点 A: 25% QPS          节点 A: 95% QPS  ← 热点 key 全压这里
节点 B: 25% QPS          节点 B: 2% QPS
节点 C: 25% QPS          节点 C: 2% QPS
节点 D: 25% QPS          节点 D: 1% QPS
```

**典型场景**：
- 秒杀活动的库存 key（`stock:item:1001`）
- 微博热搜 / 明星超话的热度 key
- 电商首页商品详情 key
- 配置中心的全局配置 key
- 排行榜的榜单 key

**危害链**：热 key → 单节点 QPS 打满 → CPU 飙高 → RT 飙升 → 连接数打满 → 影响该节点上的其他 key → 集群整体性能被单节点拖累

## 二、热点 Key 发现与定位

> 这是面试高频追问：「你怎么知道哪个 key 是热点？」——不能只说 `--hotkeys`，要讲清每种方法的适用场景和局限性。

### 2.1 四种探测方法对比

| 方法 | 实时性 | 精度 | 侵入性 | 适用场景 | 局限性 |
|:---|:---:|:---:|:---:|:---|:---|
| **redis-cli --hotkeys** | 准实时 | 中 | 无 | 快速排查已有 LFU 策略的实例 | 必须开启 `maxmemory-policy` 含 LFU；只给 TOP，漏掉次热点 |
| **客户端埋点** | 实时 | 高 | 低 | 生产环境持续监控 | 需要改 SDK，统计上报有开销 |
| **代理层统计** | 实时 | 高 | 无 | Codis/Predixy/Twemproxy 架构 | 需要代理层支持，直连 Redis 不适用 |
| **MONITOR 采样** | 实时 | 低 | 高 | 临时深度排查 | MONITOR 极耗 CPU，生产慎用；只采样部分 |

### 2.2 方法一：redis-cli --hotkeys（最快但有条件）

```bash
# 前提：淘汰策略必须是 LFU（volatile-lfu / allkeys-lfu）
redis-cli CONFIG SET maxmemory-policy allkeys-lfu

# 查看热点 key TOP N
redis-cli --hotkeys
```

**原理**：LFU 淘汰策略下，Redis 会在 `redisObject` 中维护 key 的访问计数器（lru 字段复用为 LFU counter），`--hotkeys` 扫描所有 key 按 counter 排序。

**坑**：
- 必须开 LFU，LRU 策略下 hotkeys 不准
- `--hotkeys` 本身会扫描全库，大实例上慢
- 只统计当前内存中的 key，已过期/淘汰的不计入

### 2.3 方法二：客户端埋点（生产推荐）

在 Redis 客户端 SDK 层埋点，统计 key 访问频率：

```java
// 装饰器模式包装 Jedis/Lettuce
public class HotKeyDetector {
    // SlidingWindow 计数器：每分钟统计 key 访问次数
    private final Map<String, SlidingWindowCounter> counters = new ConcurrentHashMap<>();
    private static final int HOT_KEY_THRESHOLD = 1000;  // 单 key 分钟访问 >1000 视为热点

    public void record(String key) {
        counters.computeIfAbsent(key, k -> new SlidingWindowCounter(60, 1))
                .increment();
    }

    public List<String> getHotKeys() {
        return counters.entrySet().stream()
                .filter(e -> e.getValue().getCount() > HOT_KEY_THRESHOLD)
                .map(Map.Entry::getKey)
                .toList();
    }
}

// 使用：在 Jedis 拦截器中
public class HotKeyInterceptor implements CommandInterceptor {
    public Object execute(Command command) {
        if (command.getKey() != null) {
            hotKeyDetector.record(command.getKey());
        }
        return command.execute();
    }
}
```

**上报 Prometheus**：

```java
// Micrometer 统计
MeterRegistry registry;
registry.gauge("redis_hot_key_qps", List.of("key", key), key -> hotKeyDetector.getQps(key));
```

**优点**：精度高、可设阈值、持续监控、可告警
**缺点**：需要改 SDK，统计本身有微量内存开销（可设上限淘汰冷 key）

### 2.4 方法三：代理层统计（无侵入）

如果用 Codis / Predixy / Twemproxy 代理，代理层天然能统计每个 key 的 QPS：

```
客户端 → Codis Proxy（统计 key 访问次数）→ Codis Group → Redis
              │
              └─ 上报 Prometheus: redis_proxy_key_qps{key="xxx", node="xxx"}
```

Predixy 内置 hotkey 统计：

```conf
# predixy.conf
HotKeyMark true
HotKeyMarkTypes string hash list set zset
HotKeyMarkThreshold 10000
```

### 2.5 方法四：MONITOR 采样（临时深度排查）

```bash
# MONITOR 实时打印所有命令（极耗 CPU，生产慎用，限制 10s）
timeout 10 redis-cli MONITOR | awk '{print $NF}' | sort | uniq -c | sort -rn | head -20

# 配合 SLOWLOG 看慢命令
redis-cli SLOWLOG GET 20
```

**注意**：MONITOR 会显著降低 Redis 性能（每条命令都要写日志），生产环境只能短时间用，不能常开。

## 三、解决方案选型决策树

> 核心追问：「热 key 有好几种解法，你怎么选？」——不能全背，要讲决策逻辑。

```
┌─────────────────────────────────────────────────────────────────┐
│                  热点 Key 治理决策树                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Step 1：热 key 是读多写少还是写多读少？                          │
│    │                                                            │
│    ├─ 读多写少（90% 场景：商品详情/配置/榜单）                    │
│    │    │                                                       │
│    │    ├─ 对一致性要求不高（允许秒级延迟）？                     │
│    │    │    ├─ 是 → ✅ 方案 A：本地缓存兜底（Caffeine 短 TTL）   │
│    │    │    │        实现简单、效果立竿见影、多实例天然分散       │
│    │    │    │                                                  │
│    │    │    └─ 否（强一致，如库存）→ ⬇️ 继续判断                │
│    │    │                                                       │
│    │    ├─ 读 QPS 极高（>10w）单 key 撑不住？                     │
│    │    │    ├─ 是 → ✅ 方案 B：多副本打散（key 加随机后缀）      │
│    │    │    │        同一热 key 存 N 份，读时随机选一份          │
│    │    │    │                                                  │
│    │    │    └─ 否 → ✅ 方案 D：读写分离（读走从库）             │
│    │    │           简单但有复制延迟，一致性要求高的不能用         │
│    │    │                                                       │
│    │    └─ 热 key 数量多（TOP10 都很热）？                        │
│    │         └─ 是 → ✅ 方案 E：整体分片（拆 sub-key 到不同槽）   │
│    │                治本，但改造成本高                           │
│    │                                                            │
│    └─ 写多读少（10% 场景：计数器/排行榜）                         │
│         │                                                       │
│         ├─ 写 QPS 不高（<1w）→ ✅ 不需要特殊处理                  │
│         │                                                       │
│         └─ 写 QPS 极高（>1w）→ ✅ 方案 E：分片 + 本地聚合         │
│                写操作先本地聚合，定期批量 flush 到 Redis           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 方案对比速查表

| 方案 | 适用场景 | 一致性 | 改造成本 | 效果 | 坑 |
|:---|:---|:---:|:---:|:---:|:---|
| **A. 本地缓存兜底** | 读多写少、允许秒级延迟 | 弱（TTL 期间脏读） | 低 | ⭐⭐⭐⭐ | 多实例数据不一致；缓存雪崩 |
| **B. 多副本打散** | 读 QPS 极高、key 数量少 | 强（写同步更新所有副本） | 中 | ⭐⭐⭐⭐⭐ | 写放大 N 倍；副本一致性维护 |
| **C. 拆分子 Key** | 大 key + 热点、需要治本 | 强 | 高 | ⭐⭐⭐⭐⭐ | 改造量大；跨子 key 操作复杂 |
| **D. 读写分离** | 读多写少、有从库 | 弱（复制延迟） | 低 | ⭐⭐⭐ | 从库延迟；一致性要求高的不能用 |
| **E. 分片 + 聚合** | 写多读少、写 QPS 极高 | 最终一致 | 高 | ⭐⭐⭐⭐ | 本地聚合丢失风险；flush 时机 |

## 四、生产级实现细节

### 4.1 方案 A 生产级实现：本地缓存兜底（Caffeine）

#### 基础版（已有，见大Key篇）

```java
Caffeine<String, String> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(1, TimeUnit.SECONDS)
    .build();
```

#### 生产级增强版（5 个关键优化）

```java
public class HotKeyLocalCache {
    // 1. 热点 key 自动识别 + 提升：不是所有 key 都放本地，只放访问 >阈值的
    private final Caffeine<String, CacheEntry> localCache = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(2, TimeUnit.SECONDS)        // 短 TTL 控制一致性窗口
            .recordStats()                                  // 命中率监控
            .removalListener((key, value, cause) -> {
                // 2. 淘汰时记录日志 + 上报监控
                log.debug("Local cache evicted: {}, cause: {}", key, cause);
            })
            .build();

    // 3. 热点 key 阈值计数器：只有访问 >3 次的 key 才提升到本地缓存
    private final Map<String, Integer> accessCounter = new ConcurrentHashMap<>();
    private static final int HOT_THRESHOLD = 3;

    public String get(String key) {
        // 4. 先查本地缓存
        CacheEntry entry = localCache.getIfPresent(key);
        if (entry != null && !entry.isExpired()) {
            return entry.getValue();
        }

        // 5. 本地 miss → 查 Redis
        String value = redisClient.get(key);
        if (value != null) {
            // 热点 key 才回填本地（避免冷 key 占用本地缓存）
            int count = accessCounter.merge(key, 1, Integer::sum);
            if (count >= HOT_THRESHOLD) {
                localCache.put(key, new CacheEntry(value, System.currentTimeMillis()));
            }
        }
        return value;
    }

    // 写操作：删除本地缓存 + 删除 Redis（双删）
    public void set(String key, String value) {
        redisClient.set(key, value);
        localCache.invalidate(key);  // 先删本地，避免脏读
    }
}
```

**5 个关键优化点**：

| 优化 | 原因 |
|:---|:---|
| 热点 key 自动提升（阈值计数） | 不是所有 key 都放本地，冷 key 会污染本地缓存 |
| 短 TTL（1-2s） | 控制一致性窗口，TTL 越短越一致但回源越多 |
| `recordStats()` 命中率监控 | 知道本地缓存效果，命中率 <50% 说明配置有问题 |
| 双删（写后删本地） | 防止本地读到旧值 |
| 淘汰监听日志 | 排查缓存穿透/雪崩时需要知道淘汰行为 |

### 4.2 方案 B 生产级实现：多副本打散

#### 核心思路

```
原始 key: product:1001:detail
                │
                ├─ 写时同步写 N 份副本
                │    product:1001:detail:replica:0
                │    product:1001:detail:replica:1
                │    product:1001:detail:replica:2
                │
                └─ 读时随机选一份
                     GET product:1001:detail:replica:<random 0..2>
```

#### 生产级实现

```java
public class HotKeyReplicaCache {
    private static final int REPLICA_COUNT = 5;  // 副本数，根据 QPS 倾斜程度调

    // 写：同步写所有副本（保证一致性）
    public void set(String key, String value, long ttlSeconds) {
        // 用 Pipeline 批量写，减少网络开销
        try (Pipeline pipeline = redisClient.pipelined()) {
            for (int i = 0; i < REPLICA_COUNT; i++) {
                pipeline.setex(key + ":replica:" + i, ttlSeconds, value);
            }
            pipeline.sync();
        }
    }

    // 读：随机选一份
    public String get(String key) {
        int replica = ThreadLocalRandom.current().nextInt(REPLICA_COUNT);
        return redisClient.get(key + ":replica:" + replica);
    }

    // 删除：同步删所有副本
    public void delete(String key) {
        try (Pipeline pipeline = redisClient.pipelined()) {
            for (int i = 0; i < REPLICA_COUNT; i++) {
                pipeline.del(key + ":replica:" + i);
            }
            pipeline.sync();
        }
    }
}
```

#### 副本数怎么定

| 单 key QPS | 建议副本数 | 说明 |
|:---|:---:|:---|
| < 5000 | 1 | 不需要打散，读写分离即可 |
| 5000-20000 | 3 | 平衡写放大和读分散 |
| 20000-50000 | 5 | 常见配置 |
| > 50000 | 8-10 | 写放大严重，考虑其他方案 |

**坑**：
- 写放大 N 倍：副本越多写压力越大，副本数要平衡
- 副本一致性：写时必须同步写所有副本，不能异步（否则读到旧值）
- 内存放大 N 倍：每个副本占一份内存，大 value 不适合多副本

### 4.3 方案 D 实现：读写分离

```java
// Lettuce 配置读写分离
LettuceClientConfiguration config = LettuceClientConfiguration.builder()
    .readFrom(ReadFrom.REPLICA_PREFERRED)  // 优先从库读，从库不可用走主库
    .build();

// 关键：热 key 读走从库，写走主库
StatefulRedisMasterSlaveConnection<String, String> connection =
    MasterSlave.connect(client, config, "redis://master:6379");
connection.setReadFrom(ReadFrom.REPLICA_PREFERRED);
```

**适用判断**：
- ✅ 读多写少（读:写 > 10:1）
- ✅ 允许秒级复制延迟
- ❌ 强一致场景（库存扣减、余额查询）

## 五、生产实战案例

### 案例：EasyBI 报表查询热点 Key 治理

**背景**：
EasyBI 仪表板图表查询结果缓存到 Redis，热门报表（如「昨日 GMV 总览」）的缓存 key 被大量访问，导致 Redis 单节点 QPS 倾斜，RT 从 2ms 飙到 50ms。

**发现过程**：
1. 监控告警：某 Redis 节点 CPU 80%+，其他节点 <20%
2. `redis-cli --hotkeys` 发现 TOP1 key：`chart:result:dashboard:home:gmv_overview`，分钟访问 5w+
3. 客户端埋点确认：该 key 占单节点 70% QPS

**治理决策**（走决策树）：
```
读多写少？→ 是（报表缓存 99% 是读）
允许秒级延迟？→ 是（报表数据本身 TTL 300s）
读 QPS 极高？→ 是（5w+/min = 800+/s，单节点可扛但有风险）
→ 选方案 A（本地缓存兜底）+ 方案 D（读写分离）组合
```

**实施**：
```java
// 1. Caffeine 本地缓存，短 TTL 3s（报表 TTL 300s，本地 3s 足够）
private final Cache<String, String> localCache = Caffeine.newBuilder()
    .maximumSize(500)  // 热点报表 key 数量不多
    .expireAfterWrite(3, TimeUnit.SECONDS)
    .recordStats()
    .build();

// 2. 两级读取
public String getChartResult(String chartId) {
    String cacheKey = "chart:result:" + chartId;

    // L1: 本地缓存
    String local = localCache.getIfPresent(cacheKey);
    if (local != null) return local;

    // L2: Redis（走从库读）
    String redis = slaveRedisClient.get(cacheKey);
    if (redis != null) {
        localCache.put(cacheKey, redis);
    }
    return redis;
}

// 3. 报表更新时删除本地 + Redis
public void updateChartResult(String chartId, String result) {
    String cacheKey = "chart:result:" + chartId;
    masterRedisClient.setex(cacheKey, 300, result);
    localCache.invalidate(cacheKey);  // 删本地
}
```

**效果**：
| 指标 | 治理前 | 治理后 |
|:---|:---|:---|
| 热 key 所在节点 CPU | 80% | 25% |
| 平均 RT | 50ms | 3ms |
| 本地缓存命中率 | - | 92% |
| Redis 集群 QPS | 8w | 1.2w |

**踩过的坑**：
1. 一开始本地缓存 TTL 设 30s，导致报表更新后 30s 内用户看到旧数据 → 改 3s
2. 所有 chart key 都放本地，冷 key 占用 80% 本地缓存 → 改热点 key 阈值提升
3. 本地缓存没有监控，不知道命中率 → 加 `recordStats()` + Prometheus 上报

## 六、面试高频问答

### Q1：线上怎么发现热点 key？

四步法：
1. **先看监控**：集群各节点 QPS/CPU 是否均匀，倾斜了大概率有热 key
2. **再用 --hotkeys**：前提开了 LFU 策略，快速定位 TOP 热 key
3. **客户端埋点确认**：在 SDK 层统计 key 访问频率，设阈值告警
4. **代理层统计**：如果有 Codis/Predixy，代理层天然统计 key QPS

### Q2：热 key 有哪些解决方案，怎么选？

按决策树选：
- **读多写少 + 允许秒级延迟** → 本地缓存兜底（Caffeine 短 TTL）
- **读 QPS 极高 + key 数量少** → 多副本打散（随机后缀）
- **读多写少 + 有从库 + 允许延迟** → 读写分离
- **大 key + 热点 + 需要治本** → 拆分子 key 到不同槽
- **写多读少 + 写 QPS 极高** → 分片 + 本地聚合

### Q3：本地缓存兜底有什么坑？怎么解决？

| 坑 | 解决方案 |
|:---|:---|
| 多实例数据不一致 | 接受秒级延迟（短 TTL）；强一致场景不用本地缓存 |
| 冷 key 污染本地缓存 | 热点 key 阈值提升（访问 >N 次才放本地） |
| 缓存雪崩（本地缓存同时过期） | 本地 TTL 加随机抖动 ±10% |
| 写后本地脏读 | 写操作双删（删 Redis + 删本地） |
| 命中率低不知道 | `recordStats()` + Prometheus 监控 |

### Q4：多副本打散的副本数怎么定？

根据单 key QPS：
- <5000：1 份（不需要）
- 5000-2w：3 份
- 2w-5w：5 份（常见）
- >5w：8-10 份

副本数 = 写放大倍数，要平衡读分散和写压力。副本越多读越分散，但写压力和内存占用线性增长。

### Q5：热 key 治理和缓存击穿有什么区别？

| 维度 | 缓存击穿 | 热点 Key |
|:---|:---|:---|
| 触发 | 单个热点 key **过期瞬间**，大量请求同时回源 | 单个 key **持续**高 QPS，不管过没过期 |
| 本质 | 时间维度的瞬时冲击 | 空间维度的流量倾斜 |
| 解法 | 互斥锁重建 / 逻辑过期 / 永不过期 | 本地缓存 / 多副本 / 读写分离 |
| 关系 | 热 key 如果设了 TTL，过期瞬间会演变成击穿 | 热 key 是常态问题，击穿是热 key 的瞬时爆发 |

> **面试加分**：热 key 是缓存击穿的前提——正因为 key 很热，过期瞬间大量请求同时回源才叫击穿。治理热 key 用本地缓存，天然也能缓解击穿（本地命中了就不会回源）。

---

## 七、易错点

1. **❌ --hotkeys 随时能用** → ✅ 必须开启 LFU 淘汰策略，LRU 下不准
2. **❌ 本地缓存 TTL 越长越好** → ✅ TTL 越长一致性窗口越大，热 key 场景建议 1-3s
3. **❌ 多副本异步写就行** → ✅ 必须同步写所有副本，否则读到旧值
4. **❌ 读写分离适合所有热 key** → ✅ 强一致场景（库存/余额）不能用，有复制延迟
5. **❌ 热 key 只有读场景** → ✅ 写热 key 也有（计数器/排行榜），解法是分片 + 本地聚合
6. **❌ MONITOR 可以常开** → ✅ MONITOR 极耗 CPU，生产只能短时间用（10s）

## 九、一句话总结

> 热点 Key 治理 = **发现（监控倾斜 → --hotkeys → 客户端埋点）→ 选方案（决策树：读多写少→本地缓存，QPS 极高→多副本，有从库→读写分离）→ 落地（短 TTL 本地缓存 + 双删 + 热点提升 + 命中率监控）**，核心是用空间（本地缓存/多副本）换时间（Redis 单节点压力），在一致性和性能之间找平衡。
