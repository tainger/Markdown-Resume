# 一条 Redis 命令的执行过程

> 这是 Redis 知识体系的**枢纽篇**——把 IO 多路复用、单线程执行、数据结构查找、持久化触发、主从复制、过期删除全部串成一条线。
> 面试价值：90% 的 Redis 面试题最终都能落到这条链路上，理解了它就理解了 Redis 的全部设计哲学。

---

## 一、全链路总览

以执行一条 `SET user:1 zhaozhiyuan EX 3600` 为例，从客户端到服务端再到返回，完整经历 **7 个阶段**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    一条 Redis 命令执行全链路                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [1] 客户端发送                                                   │
│      SET user:1 zhaozhiyuan EX 3600                              │
│      ↓ TCP 连接（长连接 / connect 池）                           │
│                                                                 │
│  [2] 服务端接收                                                   │
│      数据到达内核 socket 缓冲区                                   │
│      ↓ epoll 检测到 EPOLLIN 事件                                 │
│                                                                 │
│  [3] IO 线程读取（Redis 6.0+ 多线程）                            │
│      从内核缓冲区读数据到应用层协议解析缓冲区                      │
│      ↓ 解析 RESP 协议 → 命令对象                                  │
│                                                                 │
│  [4] 命令分发（主线程）                                           │
│      查 redisCommand 命令表 → 找到 setCommand                    │
│      ↓ 路由到对应数据库 dbDict                                    │
│                                                                 │
│  [5] 命令执行（主线程单线程）                                      │
│      写入 dictEntry(key=user:1, value=SDS"zhaozhiyuan")         │
│      设置过期字典 expireDict[user:1] = now+3600s                 │
│      ↓ 记录到 AOF 缓冲区 / 复制缓冲区（后置动作）                  │
│                                                                 │
│  [6] 写回响应                                                    │
│      OK → 写入客户端输出缓冲区                                    │
│      ↓ epoll 检测到 EPOLLOUT → IO 线程写回 socket                │
│                                                                 │
│  [7] 后置动作（异步/定时）                                        │
│      ├─ 持久化：aof_buffer → flush（appendfsync 策略）           │
│      ├─ 复制：写入 repl_backlog → 异步发给从库                   │
│      └─ 过期：惰性删除（下次访问检查）+ 定期删除                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 二、阶段详解

### 阶段 1：客户端发送命令

```java
// Jedis / Lettuce / Redisson 客户端
try (Jedis jedis = new Jedis("127.0.0.1", 6379)) {
    String result = jedis.set("user:1", "zhaozhiyuan", "EX", 3600);
}
```

**关键细节**：

| 项 | 说明 |
|:---|:---|
| 连接方式 | TCP 长连接（默认 6379），客户端连接池复用 |
| 通信协议 | RESP（Redis Serialization Protocol），文本协议，人类可读 |
| 序列化 | RESP 协议自带类型前缀（`+`简单字符串 `-`错误 `:`整数 `$`bulk `*`数组） |
| 编码 | 命令按 RESP 编码：`*5\r\n$3\r\nSET\r\n$6\r\nuser:1\r\n$12\r\nzhaozhiyuan\r\n$2\r\nEX\r\n$4\r\n3600\r\n` |

**RESP 协议示例**：

```
客户端发送：
*5\r\n           ← 数组，5 个元素
$3\r\nSET\r\n    ← bulk string，长度 3，内容 SET
$6\r\nuser:1\r\n ← bulk string，长度 6，内容 user:1
$12\r\nzhaozhiyuan\r\n
$2\r\nEX\r\n
$4\r\n3600\r\n

服务端返回：
+OK\r\n          ← 简单字符串
```

---

### 阶段 2：服务端接收 + epoll 事件循环

#### 2.1 epoll 多路复用（Reactor 模型）

Redis 服务端启动后，创建一个 `aeEventLoop` 事件循环，用 **epoll** 管理所有 socket：

```
Redis 服务端事件循环（aeEventLoop）
│
├─ 注册监听 socket（accept 新连接）
│   └─ epoll_ctl(ADD, listen_fd, EPOLLIN)
│
├─ 注册客户端 socket
│   └─ 新连接 accept 后，epoll_ctl(ADD, client_fd, EPOLLIN)
│
└─ 事件循环（aeMain）
    └─ while(true):
        ├─ epoll_wait() 等待事件
        ├─ 处理就绪事件（accept / read / write）
        ├─ 处理定时任务（过期删除、AOF flush、集群心跳）
        └─ 执行 pending 命令队列
```

**为什么用 epoll 而不是 select/poll**：

| 模型 | 连接数限制 | 时间复杂度 | 原理 |
|:---|:---:|:---:|:---|
| select | 1024 | O(n) | 每次遍历所有 fd |
| poll | 无硬限制 | O(n) | 同上，用链表 |
| **epoll** | 无限制 | **O(就绪数)** | 内核维护红黑树+就绪链表，只返回就绪 fd |

Redis 单线程能扛 10w+ QPS 的核心就是 epoll——**只处理就绪的 fd，不用遍历全部连接**。

#### 2.2 Redis 6.0 多线程 IO 革命

Redis 6.0 之前，**网络读写也是单线程**的。6.0 引入多线程 IO：

```
Redis 6.0+ 架构
│
├─ 主线程（Main Thread）
│   ├─ accept 新连接
│   ├─ 命令执行（仍然严格单线程！）
│   └─ 写回响应（也可以多线程）
│
└─ IO 线程池（io_threads，默认 1，可配 2~128）
    ├─ 读 socket 数据
    ├─ 解析 RESP 协议
    └─ 写 socket 响应
```

**关键点（面试必问）**：
- 多线程只做**网络 IO**（读 socket、协议解析、写 socket）
- **命令执行仍然严格单线程**，不需要锁
- 配置：`io-threads 4` + `io-threads-do-reads yes`

---

### 阶段 3：命令解析

IO 线程从 socket 读出字节流，按 RESP 协议解析：

```
字节流：*5\r\n$3\r\nSET\r\n$6\r\nuser:1\r\n$12\r\nzhaozhiyuan\r\n$2\r\nEX\r\n$4\r\n3600\r\n

解析过程：
1. 遇到 '*' → 数组，5 个元素
2. 依次解析每个 bulk string：["SET", "user:1", "zhaozhiyuan", "EX", "3600"]
3. 封装为 redisCommandArgv 结构，交给主线程执行
```

**协议解析的坑**：
- 粘包/半包：TCP 是流式协议，一个命令可能被拆成多个包，或多个命令合成一个包
- Redis 用 `readQueryBuffer` 累积读取，解析完整命令后才处理
- 不完整的命令留在缓冲区，等下次 epoll 事件继续读

---

### 阶段 4：命令分发

主线程拿到解析好的命令后，查 `redisCommand` 全局命令表：

```c
// server.c 中的命令表（简化）
struct redisCommand redisCommandTable[] = {
    {"set", setCommand, -3, "write", 0, 0, 0, 0, 0},
    {"get", getCommand, 2, "readonly", 0, 0, 0, 0, 0},
    {"del", delCommand, -2, "write", 0, 0, 0, 0, 0},
    // ... 200+ 命令
};

// 查找到 setCommand 处理函数
```

**分发逻辑**：

```
命令名 "SET"
    │
    ▼
查 redisCommandTable（字典 O(1) 查找）
    │
    ▼
找到 setCommand 处理函数 + 命令标志位
    │
    ├─ 权限校验（CLIENT 认证？SELECT db？）
    ├─ 命令类型判断（readonly / write / admin）
    ├─ 慢查询日志记录（SLOWLOG）
    └─ 调用 setCommand(c) 执行
```

---

### 阶段 5：命令执行（单线程核心）

```c
// setCommand 简化逻辑
void setCommand(client *c) {
    // 1. 解析参数：SET key value [EX seconds | PX milliseconds] [NX | XX]
    // 2. 查找目标 DB：db = c->db
    // 3. 检查 key 是否存在
    dictEntry *de = dictFind(db->dict, key);
    if (de) {
        // 覆盖旧值，处理 EX/PX/NX/XX 选项
        dictReplace(db->dict, key, value);
    } else {
        // 新增
        dictAdd(db->dict, key, value);
    }
    // 4. 设置过期时间（如果有 EX/PX）
    if (expire) {
        dictAdd(db->expires, key, now + expire);
    }
    // 5. 记录到 AOF 缓冲区
    feedAppendOnlyFile(c->cmd, c->argv, c->argc);
    // 6. 记录到复制缓冲区
    replicationFeedSlaves(c->cmd, c->argv, c->argc);
}
```

**执行阶段的关键设计**：

| 设计 | 说明 |
|:---|:---|
| **单线程无锁** | 所有命令在主线程顺序执行，无需加锁，天然线程安全 |
| **O(1) 字典查找** | dictFind 用哈希表，平均 O(1) |
| **SDS 优化** | value 用 SDS 存储，O(1) 取长度、二进制安全 |
| **惰性空间释放** | 覆盖旧值时不立即 free，等 GC 或下次分配复用 |
| **过期字典分离** | 过期时间单独存 `expires` 字典，不污染主字典 |

---

### 阶段 6：写回响应

命令执行完，结果写入客户端输出缓冲区：

```
执行结果 "OK"
    │
    ▼
写入 client->buf 输出缓冲区（或 client->reply 链表）
    │
    ▼
注册 EPOLLOUT 事件到 epoll
    │
    ▼
IO 线程检测到可写 → 写回 socket
    │
    ▼
客户端收到 "+OK\r\n"
```

**输出缓冲区的两种模式**：

| 模式 | 场景 | 说明 |
|:---|:---|:---|
| 静态缓冲 | 小响应（< 16KB） | 直接写固定数组 `client->buf` |
| 动态缓冲 | 大响应 / 大量数据 | 用链表 `client->reply`，避免单次分配过大内存 |

**背压机制**：如果客户端读取慢，输出缓冲区超过 `client-output-buffer-limit`（默认 256mb 硬限），Redis 会主动断开连接，防止 OOM。

---

### 阶段 7：后置动作

命令执行完不是结束，还有三个关键后置动作：

#### 7.1 持久化（AOF / RDB）

```
命令执行成功
    │
    ▼
feedAppendOnlyFile() 写入 aof_buf 内存缓冲区
    │
    ▼
什么时候刷盘？取决于 appendfsync 策略：
    ├─ always：每次命令都 fsync（最安全，最慢）
    ├─ everysec：每秒 fsync 一次（默认，折中）
    └─ no：由 OS 决定（最快，可能丢 30s 数据）
```

> ⚠️ AOF 是**写后日志**：先执行命令成功，再写缓冲区。如果写日志前宕机，丢这条命令。
> 详见 [持久化.md](持久化.md)

#### 7.2 主从复制

```
命令执行成功
    │
    ▼
replicationFeedSlaves() 写入 repl_backlog 复制积压缓冲区
    │
    ▼
异步发给所有从库（不阻塞主库返回）
    │
    ▼
从库收到命令 → 同样走阶段 4-6 执行 + 写回
```

> 主从是**最终一致**，主库写完立即返回，不等从库 ACK。
> 详见 [高可用与集群.md](高可用与集群.md)

#### 7.3 过期处理

```
SET user:1 ... EX 3600
    │
    ▼
写入 db->expires 过期字典
    │
    ├─ 惰性删除：下次访问 user:1 时检查是否过期，过期则删除
    └─ 定期删除：每秒 10 次，随机抽 20 个 key，过期占比 >25% 继续抽
```

> 详见 [过期与内存淘汰.md](过期与内存淘汰.md)

## 四、面试高频问答

### Q1：Redis 为什么单线程还这么快？

**四个核心原因**：
1. **纯内存操作**：数据在内存中，读写速度纳秒级
2. **单线程命令执行**：无锁竞争、无上下文切换、无线程调度开销
3. **epoll IO 多路复用**：一个线程管理数万连接，只处理就绪 fd
4. **高效数据结构**：SDS（O(1) 取长度）、哈希表（O(1) 查找）、跳表（O(log n) 范围查询）

### Q2：Redis 6.0 多线程后，命令执行还是单线程吗？

**是的，命令执行仍然严格单线程**。多线程只用于：
- 网络 IO 读取（读 socket）
- RESP 协议解析
- 网络 IO 写入（写 socket）

这样设计的原因：避免多线程并发执行命令带来的锁竞争和复杂性，保持 Redis 的简单和高性能。

### Q3：一条 SET 命令的完整过程？

```
1. 客户端按 RESP 编码 SET 命令 → TCP 发送
2. 服务端 epoll 检测到 EPOLLIN → IO 线程读 socket
3. IO 线程解析 RESP 协议 → ["SET", "user:1", "value"]
4. 主线程查 redisCommand 表 → setCommand
5. setCommand 写入 db->dict（哈希表 O(1)）+ 设置过期字典
6. 写入 aof_buf + repl_buf（后置动作）
7. 结果 "OK" 写入输出缓冲区
8. epoll 检测到 EPOLLOUT → IO 线程写回 socket
```

### Q4：为什么 Redis 不用多线程执行命令？

| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| 单线程 | 无锁、无竞争、实现简单、性能稳定 | 无法利用多核 |
| 多线程执行 | 利用多核 | 需要锁（dict 操作、过期字典、AOF buffer）、上下文切换、复杂度过高 |

Redis 的选择是**网络 IO 多线程 + 命令执行单线程**——IO 是瓶颈时用多线程加速，执行保持简单。

### Q5：命令执行过程中会阻塞吗？

**会，慢命令会阻塞整个事件循环**：
- `KEYS *`：遍历所有 key，O(N)，阻塞期间所有命令排队
- `HGETALL` 大 Hash：O(N)，同样阻塞
- 大 key 的 `DEL`：内存释放阻塞

**治理**：禁用 KEYS，改 SCAN 渐进式扫描；大 Hash 拆分；删大 key 用 UNLINK（4.0+ 异步释放）。

### Q6：一条命令的延迟由哪些部分组成？

```
命令延迟 = 网络传输（RTT）
        + 排队等待（如果主线程在执行慢命令）
        + IO 解析（RESP 解码）
        + 命令执行（O(1)~O(N) 取决于命令）
        + 写回响应（网络传输）
```

优化方向：**Pipeline 减少 RTT**、**避免慢命令减少排队**、**多线程 IO 减少解析开销**。

### Q7：RESP 协议为什么设计成文本的？

- **简单**：人类可读，调试方便（telnet 就能测）
- **快速解析**：以 `\r\n` 分隔，按行扫描即可，不用复杂解析器
- **二进制安全**：bulk string 用长度前缀，能传输二进制数据（不用 `\0` 判结尾）

### Q8：如何让多条命令批量执行减少网络开销？

三种方式：

| 方式 | 原理 | 原子性 |
|:---|:---|:---:|
| Pipeline | 客户端批量发送，服务端批量处理，减少 RTT | ❌ 非原子 |
| MULTI/EXEC | 事务，命令入队，EXEC 时一次性执行 | ✅ 原子（不保证隔离） |
| Lua 脚本 | EVAL 执行 Lua 脚本，服务端原子执行 | ✅ 完全原子 |

## 五、易错点

1. **❌ Redis 是单线程的** → ✅ 命令执行是单线程，Redis 6.0+ 网络 IO 是多线程的，且有多个后台线程（BIO：close/file/flush）
2. **❌ AOF 是写前日志** → ✅ AOF 是**写后日志**（先执行成功再写），与 MySQL WAL 相反
3. **❌ 主从复制是同步的** → ✅ 异步复制，主库写完立即返回，不等从库 ACK
4. **❌ 命令执行会被 epoll 事件打断** → ✅ 不会。Redis 事件循环是「先处理完当前事件，再处理下一个」，命令执行期间不会被打断（除非慢命令阻塞）
5. **❌ RESP 协议是二进制协议** → ✅ RESP 是**文本协议**，但支持二进制安全（长度前缀）
6. **❌ 多线程 IO 可以让所有命令变快** → ✅ 多线程只加速网络 IO 部分，命令执行仍是单线程，CPU 密集型命令不会变快

## 七、一句话总结

> 一条 Redis 命令的旅程：**客户端按 RESP 编码 → TCP 到达 → epoll 唤醒 → IO 线程读+解析 → 主线程查命令表单线程执行 → 写回输出缓冲区 → IO 线程写 socket → 异步触发持久化/复制/过期**。理解这条链路，就理解了 Redis「纯内存 + 单线程执行 + epoll 多路复用」三位一体的设计哲学。
