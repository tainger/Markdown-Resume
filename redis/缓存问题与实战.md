# Redis 缓存问题与实战面试题

Redis 最常见的用途是给数据库做**缓存**。缓存用得好能扛住高并发，用不好反而会拖垮数据库。这部分是面试的重中之重，主要有：**三大缓存问题（穿透/击穿/雪崩）**、**双写一致性**、**分布式锁**。

---

## 一、缓存三大问题

先看正常缓存读流程（Cache Aside 旁路缓存）：

```
读请求 → 查缓存
  ├─ 命中  → 直接返回
  └─ 未命中 → 查数据库 → 写回缓存 → 返回
```

三大问题都出在"缓存没起作用、请求打到数据库"这一环。

### 1. 缓存穿透

**查一个数据库里根本不存在的数据**（如 id = -1）。缓存和数据库都没有，每次都穿透缓存打到数据库。常见于恶意攻击。

| 解决方案 | 做法 | 优缺点 |
|:---|:---|:---|
| **缓存空值** | 查不到也缓存一个 null（设短过期，如 5 分钟） | 简单，但占内存、可能短暂不一致 |
| **布隆过滤器** | 请求前先过滤，不存在的直接拦掉 | 高效省内存，但有误判、删除麻烦 |
| **接口校验** | 对明显非法的参数（如负数 id）直接拦截 | 基础防护 |

> **布隆过滤器**：用一个位数组 + 多个哈希函数，判断元素"**一定不存在**"或"**可能存在**"。有误判（说存在但实际不存在），但不会漏判（说不存在就一定不存在）。适合前置拦截。

### 2. 缓存击穿（热点 key 失效）

**某个热点 key 突然过期**，此刻大量并发请求同时打到数据库（一根针捅穿）。区别于穿透：数据是**存在**的，只是缓存刚好失效。

| 解决方案 | 做法 |
|:---|:---|
| **互斥锁** | 只让一个线程去查库重建缓存，其他线程等待/重试 |
| **逻辑过期** | key 不设物理过期，存一个逻辑过期字段，过期后异步重建，期间返回旧值 |
| **热点数据永不过期** | 后台定时更新 |

```
# 互斥锁重建缓存（伪代码）
查缓存 miss → 尝试获取分布式锁 setnx lock
  ├─ 拿到锁 → 查库 → 写缓存 → 释放锁
  └─ 没拿到 → sleep 后重试查缓存
```

### 3. 缓存雪崩

**大量 key 在同一时间集体失效**，或 **Redis 宕机**，导致海量请求同时打到数据库，数据库被压垮（雪崩）。

| 场景 | 解决方案 |
|:---|:---|
| **大量 key 同时过期** | 过期时间加**随机值**（如基础 30min + 随机 0~5min），错开失效 |
| **Redis 宕机** | 搭建**集群**（主从 + 哨兵）保证高可用；服务端加**熔断降级、限流** |
| **通用兜底** | 多级缓存（本地缓存 + Redis）、缓存预热 |

### 三者对比

| 问题 | 数据是否存在 | 根因 | 核心解法 |
|:---|:---|:---|:---|
| **穿透** | 数据库也没有 | 查不存在的数据 | 布隆过滤器 / 缓存空值 |
| **击穿** | 存在 | 单个热点 key 过期 | 互斥锁 / 逻辑过期 |
| **雪崩** | 存在 | 大量 key 同时过期 / Redis 挂 | 过期时间加随机 / 集群高可用 |

## 二、缓存与数据库双写一致性

缓存和数据库是两份数据，更新时如何保证一致？核心讨论的是 **Cache Aside 模式**下"删缓存"还是"更新缓存"、以及顺序问题。

### 为什么是删缓存而不是更新缓存？

- 更新缓存：并发更新时缓存可能被旧值覆盖；且很多缓存是计算结果，更新代价大。
- **删缓存**（懒加载）：下次读时再从库加载，简单且不易出错。

### 先删缓存还是先更新数据库？

| 方案 | 问题 |
|:---|:---|
| **先删缓存，再更新库** | 删完还没更新时，读请求把**旧值**又写回缓存 → 不一致 |
| **先更新库，再删缓存**（推荐） | 大多数情况正确；极端并发下仍有小概率不一致 |

### 延迟双删

为缓解"先更新库再删缓存"的极端不一致：

```
1. 先删缓存
2. 更新数据库
3. 延迟一小段时间（如 500ms，覆盖读请求写回的时间）
4. 再删一次缓存  ← 第二次删，清掉可能被写回的旧值
```

### 更可靠：借助 binlog（最终一致）

用 **Canal 订阅 MySQL binlog**，数据库一变更就发消息，由消费者去删/更新缓存，解耦且可靠。达到**最终一致**。

> **结论**：缓存一致性无法做到强一致，只能追求**最终一致**。常规用「**先更新库，再删缓存** + 给缓存设过期时间兜底」，要求高就上 binlog 订阅。

## 三、分布式锁

多个服务实例并发访问共享资源时，需要跨进程的锁。Redis 常被用来实现分布式锁。

### 基础版：SETNX + 过期时间

```
# 加锁：原子地"不存在才设置" + 过期时间（防死锁）
SET lock_key unique_value NX EX 10

# 解锁：Lua 脚本保证"判断是自己的锁 + 删除"原子
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**三个关键点：**

| 要点 | 为什么 |
|:---|:---|
| **NX**（不存在才设） | 保证互斥，只有一个客户端能加锁 |
| **EX 过期时间** | 防止持锁客户端崩溃导致**死锁** |
| **value 存唯一标识** | 解锁时校验，防止**误删别人的锁** |
| **Lua 脚本解锁** | 保证"判断 + 删除"的原子性 |

### 锁提前过期怎么办？——看门狗（Watchdog）

业务没执行完锁就过期了，别人就能拿锁 → 并发问题。解决：**自动续期**。

- **Redisson** 的看门狗机制：加锁后启动后台线程，默认每 10 秒检查一次，若业务还没结束就把锁续期到 30 秒，避免提前释放。

### 主从架构下的锁失效

主库加锁成功但还没同步到从库时主库挂了，从库升主后锁丢失 → 两个客户端同时持锁。

- 解决方案：**RedLock（红锁）** 算法，向多个独立 Redis 节点加锁，多数成功才算加锁成功。但 RedLock 有争议（时钟漂移等），对强一致场景更推荐 **ZooKeeper/etcd**。

## 四、Redis 其他实战场景

| 场景 | 用到的类型/命令 | 说明 |
|:---|:---|:---|
| **分布式锁** | String（SET NX EX） | 见上 |
| **限流** | String（incr + expire）/ Lua | 固定/滑动窗口限流 |
| **排行榜** | ZSet（zadd/zrevrange） | 实时榜单 |
| **点赞/去重** | Set / Bitmap | 用户唯一性 |
| **签到** | Bitmap（setbit） | 一天一位，省内存 |
| **UV 统计** | HyperLogLog | 海量去重计数 |
| **消息队列** | List / Stream | Stream 支持消费组、ACK |
| **延迟队列** | ZSet（score 存执行时间） | 到点弹出 |

## 五、易错点

| 易错点 | 说明 |
|:---|:---|
| **穿透和击穿混淆** | 穿透=数据不存在；击穿=单个热点 key 过期 |
| **雪崩只想到宕机** | 还有"大量 key 同时过期"，解法是过期时间加随机 |
| **双写能做强一致** | 只能**最终一致**，常规「先更新库再删缓存」 |
| **分布式锁不设过期** | 必须设过期防死锁，并用看门狗续期防提前释放 |
| **解锁直接 del** | 要先校验 value 是不是自己的，且用 Lua 保证原子 |
| **加锁没设唯一 value** | 会误删别人的锁 |
| **布隆过滤器能精确判断** | 有误判（可能存在），但不漏判（说没有就没有） |

---

## 六、一句话总结

缓存三大问题：**穿透**（查不存在的数据 → 布隆过滤器/缓存空值）、**击穿**（热点 key 过期 → 互斥锁/逻辑过期）、**雪崩**（大量 key 同时失效或 Redis 宕机 → 过期加随机 + 集群高可用）。双写一致性只能做**最终一致**，常规用「**先更新库，再删缓存** + 过期兜底」，要求高上 **binlog 订阅**。分布式锁用 **`SET NX EX` + 唯一 value + Lua 解锁**，靠 **Redisson 看门狗**续期，跨节点强一致场景考虑 **RedLock 或 ZooKeeper**。
