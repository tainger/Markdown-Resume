# Redis 过期删除与内存淘汰面试题

Redis 是内存数据库，内存有限，必须解决两个问题：
1. **过期删除**：设置了过期时间（`expire`）的 key 到期后如何删除？
2. **内存淘汰**：内存写满了（达到 `maxmemory`）该淘汰谁？

这两个是不同层面的机制，容易混淆，是高频考点。

---

## 一、过期时间怎么存的？

Redis 用一个独立的**过期字典（expires dict）**保存每个设置了过期时间的 key 及其过期时间戳：

```
expires: { key1 → 时间戳t1, key2 → 时间戳t2, ... }
```

判断一个 key 是否过期，就是拿它的时间戳和当前时间比较。

---

## 二、过期删除策略

删除过期 key 有三种理论策略，Redis 采用**惰性删除 + 定期删除**的组合：

| 策略 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **定时删除** | 设置过期时给每个 key 建定时器，到点就删 | 内存释放及时 | 定时器消耗大量 CPU，不采用 |
| **惰性删除** | 访问 key 时才检查是否过期，过期才删 | 省 CPU | key 不被访问就一直占内存（内存不友好） |
| **定期删除** | 每隔一段时间随机抽查一批 key，删掉其中过期的 | CPU/内存折中 | 抽查有随机性，可能漏删 |

### Redis 的实际做法：惰性删除 + 定期删除

**1. 惰性删除**
访问 key 时检查过期时间，过期则删除并返回 nil。

**2. 定期删除**
默认每秒运行 10 次（`hz 10`），每次流程：

```
1. 从过期字典中随机抽取 20 个 key
2. 删除其中已过期的 key
3. 如果过期比例 > 25%，重复步骤 1（继续抽）
4. 有单次时长上限，避免长时间阻塞主线程
```

> 两者结合：定期删除兜底（防止大量过期 key 堆积），惰性删除补漏（访问时清理）。仍有一部分"永不访问 + 定期没抽到"的 key 残留，靠**内存淘汰**机制最终处理。

---

## 三、内存淘汰策略（maxmemory-policy）

当内存达到 `maxmemory` 时，Redis 按配置的策略淘汰 key，共 **8 种**：

### 不淘汰

| 策略 | 行为 |
|:---|:---|
| **noeviction**（默认） | 不淘汰，写操作直接报错（读和删可以） |

### 在"设置了过期时间"的 key 中淘汰

| 策略 | 淘汰依据 |
|:---|:---|
| **volatile-lru** | 最近最少使用（LRU） |
| **volatile-lfu** | 最不经常使用（LFU，4.0+） |
| **volatile-ttl** | 剩余存活时间最短（越快过期越先删） |
| **volatile-random** | 随机 |

### 在"所有" key 中淘汰

| 策略 | 淘汰依据 |
|:---|:---|
| **allkeys-lru** | 最近最少使用（**最常用**） |
| **allkeys-lfu** | 最不经常使用（4.0+） |
| **allkeys-random** | 随机 |

> **记忆**：前缀 `volatile-` = 只在设了过期时间的 key 里选；`allkeys-` = 所有 key 里选。后缀 = 淘汰算法（lru / lfu / random / ttl）。

---

## 四、LRU vs LFU

| 算法 | 全称 | 淘汰谁 | 缺陷 |
|:---|:---|:---|:---|
| **LRU** | Least Recently Used 最近最少使用 | 最久没被访问的 | **偶发的大批量访问**会污染缓存（如全表扫描把热点挤掉） |
| **LFU** | Least Frequently Used 最不经常使用 | 访问次数最少的 | 解决了 LRU 的缓存污染问题（4.0 引入） |

### Redis 的近似 LRU

标准 LRU 要维护一个链表，成本高。Redis 用**近似 LRU**：

```
1. 每个 key 的 redisObject 里记录一个 lru 字段（最后访问时间戳）
2. 淘汰时随机采样 N 个 key（默认 maxmemory-samples 5）
3. 淘汰这批里 lru 最旧的那个
```

> 用采样近似代替全局链表，**省内存、够用**。采样数越大越接近真实 LRU，但更耗 CPU。

### Redis 的 LFU 实现

LFU 的计数器不是简单累加，而是**基于概率递增 + 随时间衰减**，避免"早期热点永久霸榜"的问题。

---

## 五、易错点

| 易错点 | 说明 |
|:---|:---|
| **过期删除 ≠ 内存淘汰** | 过期删除针对设了 TTL 的 key；内存淘汰是内存满时的兜底，可能删没设 TTL 的 key |
| **定期删除是全量扫描** | 是**随机抽样**，不是遍历所有 key |
| **noeviction 完全不能用** | 只是写报错，读和 del 仍可用 |
| **默认策略是 allkeys-lru** | 默认是 **noeviction**（不淘汰、写报错） |
| **Redis 是标准 LRU** | 是**近似 LRU**（采样实现），省内存 |
| **主从下从库自己删过期 key** | 从库不主动删，等主库发 del 命令同步过来（保证一致性） |

---

## 六、一句话总结

Redis 靠**过期字典**记录 key 的过期时间，用**惰性删除 + 定期删除（随机抽样 + 25% 阈值）**清理过期 key。内存写满时用 **8 种淘汰策略**兜底：`volatile-` 只淘汰有 TTL 的、`allkeys-` 淘汰所有，后缀是 **LRU / LFU / random / ttl** 算法（默认 noeviction 写报错，最常用 allkeys-lru）。为省内存，Redis 用**采样近似 LRU**；4.0 引入 **LFU** 解决偶发大流量导致的缓存污染。
