# Redis 高可用与集群面试题

单机 Redis 有两个问题：**宕机后数据不可用**（可用性）和**单机内存/性能有上限**（扩展性）。Redis 用三层方案逐步解决：

1. **主从复制**：数据冗余 + 读写分离，是高可用的基础
2. **哨兵（Sentinel）**：主从的自动故障转移
3. **Cluster 集群**：数据分片，突破单机容量上限

---

## 一、主从复制（Replication）

一主多从，主库负责写，从库负责读（读写分离），主库数据同步给从库。

### 同步流程（全量复制）

从库第一次连主库，走**全量复制**：

```
1. 从库发 psync 命令，请求同步
2. 主库执行 bgsave 生成 RDB 快照，发给从库
3. 主库把生成 RDB 期间的新写命令，记到「复制缓冲区（repl buffer）」
4. 从库加载 RDB，再执行复制缓冲区的命令，追上主库
```

### 增量复制（断线重连，2.8+）

如果从库只是短暂断连，不必全量。靠三个东西实现增量：

| 组件 | 作用 |
|:---|:---|
| **复制积压缓冲区（repl_backlog）** | 一个环形缓冲区，主库把写命令也写一份进去 |
| **主库 offset** | 主库写到的位置 |
| **从库 offset** | 从库已复制到的位置 |

```
从库重连 → 上报自己的 offset
  ├─ offset 还在积压缓冲区内 → 增量复制（只补差的那部分）
  └─ offset 已被覆盖（断太久） → 退化为全量复制
```

### 命令传播（正常运行时）

全量同步完成后，主库每执行一条写命令，就**异步**传播给从库，保持持续同步。

> **主从数据一致性是最终一致**：命令异步传播，主库写完立即返回，不等从库确认。所以从库读到的可能是旧数据。

## 二、哨兵（Sentinel）

主从复制解决了数据冗余，但主库挂了需要**人工**切换。哨兵实现**自动故障转移**。

### 哨兵的四大职责

| 职责 | 说明 |
|:---|:---|
| **监控** | 定期给主从发 ping，判断是否存活 |
| **主观下线（SDOWN）** | 单个哨兵认为某节点挂了 |
| **客观下线（ODOWN）** | 超过法定数量（quorum）的哨兵都认为主库挂了 → 确认下线 |
| **故障转移** | 选新主库、让其他从库改跟新主、通知客户端 |

### 为什么哨兵要集群部署？

单个哨兵可能误判（自己网络问题）。哨兵集群通过**投票**判断（客观下线），避免单点误判和单点故障。

### 故障转移流程

```
1. 哨兵们判定主库「客观下线」
2. 从哨兵中选出一个 Leader（Raft 算法）来主持转移
3. Leader 从从库中挑一个"最优"的升为新主库
   挑选依据：优先级 → 复制 offset 最大（数据最全）→ runid 最小
4. 让其他从库改为复制新主库
5. 通知客户端新主库地址；旧主库恢复后降为从库
```

> **quorum 与 majority**：判客观下线要 `quorum` 个哨兵同意；但真正执行故障转移的 Leader 选举需要 `majority`（多数）哨兵同意授权。所以哨兵数量建议**奇数且 ≥ 3**。

---

## 三、Cluster 集群（分片，3.0+）

哨兵只是主从的高可用，数据还是全量在每个节点上，**单机内存仍是瓶颈**。Cluster 把数据**分片**存到多个主节点，实现水平扩展。

### 哈希槽（Hash Slot）

Cluster 不用一致性哈希，而是引入 **16384 个哈希槽**：

```
计算 key 属于哪个槽：
    slot = CRC16(key) % 16384

每个主节点负责一部分槽，例如 3 主：
    节点A: 槽 0     ~ 5460
    节点B: 槽 5461  ~ 10922
    节点C: 槽 10923 ~ 16383
```

- **为什么是 16384（2^14）而不是更多？** 心跳包要携带槽位图，16384 位 = 2KB，大小合适；且集群节点数一般不会超过 1000，16384 够分。
- **数据定位**：客户端算出 slot → 找到负责该 slot 的节点 → 直接访问。若访问错节点，节点返回 `MOVED` 重定向。

### 扩容/缩容

增删节点时，只需**迁移部分槽**及其数据到新节点，不影响其他槽（比一致性哈希更可控）。迁移中访问会返回 `ASK` 重定向。

### 集群的多 key 操作限制

不同 key 可能在不同槽/节点，`mset`、事务、Lua 脚本涉及多 key 时可能失败。解决办法用 **hash tag**：

```
# 用 {} 括起来的部分参与 CRC16，强制路由到同一个槽
mset {user1}:name Tom {user1}:age 18   # 都按 user1 算槽，落同一节点
```

> ⚠️ hash tag 解决了多 key 同槽问题，但 tag 分布不均会引发**数据倾斜**；大 key 占满单槽也是倾斜的核心成因——治理方案见 [大Key与数据倾斜.md](大Key与数据倾斜.md)。

## 四、三种方案对比

| 方案 | 解决什么 | 局限 |
|:---|:---|:---|
| **主从复制** | 数据冗余、读写分离 | 主库挂了要**手动**切换 |
| **哨兵** | 主从的**自动故障转移** | 数据不分片，**单机内存仍是上限** |
| **Cluster** | **数据分片** + 高可用（每个分片自带主从） | 多 key 操作受限、运维复杂 |

---

## 五、易错点

| 易错点 | 说明 |
|:---|:---|
| **主从是强一致** | 是**最终一致**，命令异步传播，从库可能读到旧值 |
| **哨兵负责存数据** | 哨兵不存数据，只监控和转移；数据在主从节点 |
| **Cluster 用一致性哈希** | 用的是 **16384 个哈希槽**，不是一致性哈希 |
| **主观下线就切换** | 要**客观下线**（quorum 个哨兵同意）才触发转移 |
| **哈希槽数量记成 65536** | 是 **16384（2^14）** |
| **哨兵部署 2 个够了** | 至少 **3 个且奇数**，否则选举可能选不出 Leader |
| **主从复制会阻塞主库** | 全量复制时 bgsave 是 fork 子进程，主库仍可服务 |

---

## 六、一句话总结

Redis 高可用三级火箭：**主从复制**做数据冗余（全量用 RDB + 复制缓冲区、断线用复制积压缓冲区做增量，命令异步传播是**最终一致**）；**哨兵**集群靠投票判断**客观下线**并自动**故障转移**（Raft 选 Leader 主持切换）；**Cluster** 用 **16384 个哈希槽**（`CRC16(key)%16384`）做数据分片，突破单机内存上限，多 key 操作用 **hash tag** 保证同槽。
