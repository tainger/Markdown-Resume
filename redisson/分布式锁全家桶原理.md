# Redisson 分布式锁全家桶原理面试题

Redisson 最核心的面试价值，就是它实现了**一整套分布式锁全家桶**——从最常用的 RLock 可重入互斥锁，到公平锁、读写锁、联锁、红锁、信号量、闭锁，一共 7+ 种。每种锁的底层 Redis 数据结构 + Lua 脚本 + 场景，都是 P7 面试连环追问的重点。

> 前置知识：`分布式/分布式锁.md` 已经讲了「简陋 SETNX 三坑 → 正确手写版 → RLock 可重入锁 Hash 结构 Lua → 看门狗基本原理」。**本篇在此基础上，深入源码级细节（看门狗时间轮、公平锁 List、联锁循环等）+ 扩展 6 种锁。**

---

## 一、7 种锁一览（先背表格 ⭐）

| 锁 | Java 接口 | 核心 Redis 结构 | 典型场景 |
|:---|:---|:---|:---|
| **① 可重入互斥锁**（最常用） | `RLock` | **Hash**（field=线程标识，value=重入次数）+ Pub/Sub 通知 | 90% 场景：扣库存、接口防并发、任务互斥 |
| **② 公平锁** | `RFairLock` | **Hash + List（等待队列）+ Hash 排队次序** | 严格先到先得：避免低优先级线程饥饿（如批量任务排队） |
| **③ 读写锁** | `RReadWriteLock` → `RReadLock / RWriteLock` | **Hash 两个 field 分别记读/写计数** | 读多写少：商品详情读多，更新商品是写；读读并发、读写互斥、写写互斥 |
| **④ 联锁** | `RMultiLock` | 多个独立 RLock 依次 tryLock | 多资源联动：扣库存+扣余额+写订单，三把锁同时拿才能做 |
| **⑤ 红锁** | `RRedLock`（extends RMultiLock） | N 个独立 Redis Master + 多数节点策略 | 理论上解决主从切换锁丢失（生产少用，见争议） |
| **⑥ 信号量** | `RSemaphore` | **String 计数** + Pub/Sub | 限流控制并发数：同时最多 100 个请求处理 |
| **⑦ 闭锁（倒计时门闩）** | `RCountDownLatch` | **Hash 计数** + Pub/Sub | 多任务汇合：5 个子任务全部做完，主线程才继续 |

## 二、RLock 可重入锁（⭐⭐⭐⭐⭐ 皇冠级，源码级必背）

### 2.1 加锁 Lua 脚本（Hash 可重入）

对应源码位置：`RedissonLock#tryLockInnerAsync`

```lua
-- KEYS[1] = 锁名（如 "stock:1001"）
-- ARGV[1] = 锁 TTL 毫秒（默认 30000）
-- ARGV[2] = 线程唯一标识（UUID:ThreadId，如 "3a1b...-abcd:98"）

if (redis.call('exists', KEYS[1]) == 0) then           -- ① 锁根本不存在
    redis.call('hincrby', KEYS[1], ARGV[2], 1);         -- ② Hash field=线程标识 计数=1
    redis.call('pexpire', KEYS[1], ARGV[1]);              -- ③ TTL 30s
    return nil;                                          -- ④ nil=加锁成功（无阻塞）
end;

if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then  -- ⑤ 锁存在 且 持有者就是我（重入）
    redis.call('hincrby', KEYS[1], ARGV[2], 1);         -- ⑥ 计数 +1（入了几层就记几次）
    redis.call('pexpire', KEYS[1], ARGV[1]);              -- ⑦ 刷新 TTL
    return nil;                                          -- ⑧ 重入成功
end;

return redis.call('pttl', KEYS[1]);                      -- ⑨ 被别人持有 → 返回剩余 TTL（ms）
```

### 2.2 解锁 Lua 脚本（计数递减 + Pub/Sub 通知）

对应源码位置：`RedissonLock#unlockInnerAsync`

```lua
-- KEYS[1] = 锁名，KEYS[2] = Pub/Sub 频道名（redisson_lock__channel:{锁名}）
-- ARGV[1] = 解锁消息体（0=释放），ARGV[2] = TTL 30000，ARGV[3] = 线程标识

if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then   -- ① 我不是持有者？
    return nil;                                            -- ② 非法解锁 → 返回 nil
end;

local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1);  -- ③ 计数 -1

if (counter > 0) then                                     -- ④ 还有重入没解锁（减完 > 0）
    redis.call('pexpire', KEYS[1], ARGV[2]);              -- ⑤ 刷新 TTL，不删锁
    return 0;
else                                                       -- ⑥ 减完 = 0，最外层解锁
    redis.call('del', KEYS[1]);                            -- ⑦ 删除锁 key
    redis.call('publish', KEYS[2], ARGV[1]);              -- ⑧ PUBLISH：锁释放了！别人可以来抢
    return 1;
end;
```

> 💡 **为什么用 Pub/Sub 通知，而不是自旋 sleep？** 没有锁的线程，执行 tryLock 失败后会 **SUBSCRIBE 这个锁的释放频道**，然后 park 休眠。锁被释放时 PUBLISH，订阅的线程被唤醒去抢。CPU 消耗比 while(true)+sleep 低一个数量级。

### 2.3 ⭐ 看门狗（Watchdog）自动续期机制——源码级解读

入口：`RedissonLock#scheduleExpirationRenewal`

```
调用链：
  tryAcquireAsync()
    → 加锁成功（Lua 返回 nil）
    → 如果 leaseTime == -1（即调用方没显式传过期时间）
       → scheduleExpirationRenewal(threadId)
          → internalLockLeaseTime / 3 之后，跑一个 Timeout
             = 默认 30000ms / 3 = 每 10 秒一次
```

续期任务的核心 Lua（`renewExpirationAsync`）：
```lua
-- 其实就是：如果这个线程还在持有锁，就把 TTL 重新设为 30s
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    redis.call('pexpire', KEYS[1], ARGV[1]);   -- ARGV[1]=30000
    return 1;
end;
return 0;
```

**看门狗三条铁律**：

| 铁律 | 说明 |
|:---|:---|
| **① leaseTime ≠ -1 → 不开看门狗** | 你显式传了 `tryLock(..., 15, SECONDS)` → Redisson 认为你知道业务多久执行完，它不帮你续；只有传 `-1`（或 `lock()` 无参方法，内部 leaseTime 就是 -1）才启动 |
| **② 周期 = lockWatchdogTimeout / 3** | 默认 30s / 3 = 10s；留出网络抖动缓冲，也不会续得太频繁 |
| **③ 线程/实例死了就停** | 续期任务是跑在「持锁客户端」的 Netty 时间轮上的；如果客户端进程崩 / JVM OOM 卡死，任务线程也没了，就不会再续 → 30s 后锁自动过期（正确行为）|

> **面试加分点（说出来证明读过源码）**：看门狗的调度用的是 Netty 的 **`HashedWheelTimer` 时间轮**，不是 `ScheduledThreadPoolExecutor`。时间轮适合大量短周期定时任务、精度稍低但并发高，不占用线程池。

## 三、公平锁 RFairLock（FIFO 排队，避免饥饿）

RLock 是非公平的（谁先抢到就是谁的，后到的线程运气好也能插队）。公平锁保证**先请求的先拿到**。

**新增了两个 Redis 结构做排队：**
```
Hash Key: {锁名}:threadsQueue    ← 存储「线程标识 → 排队序号」
List Key: {锁名}:timeoutSet      ← 存所有排队线程（按入队顺序）
```

**加锁流程（简化）：**

```
1. 如果锁没人持有 且 等待队列为空
   → 正常加锁（Hash），把当前线程登记为「第一个」，返回成功

2. 如果锁被持有 或 已经有人在排队
   a. 当前线程没入队 → RPUSH 进等待队列 List、登记序号 → 没拿到 → 订阅 + 等
   b. 已经在队里 → 检查自己是不是队头（LINDEX 0）
      ├─ 是队头 + 锁空着 → 拿锁 + LPOP 出队
      └─ 不是队头 或 锁还被人持有 → 等（订阅前一个线程的解锁通知）
```

**适用场景**：资源紧张、大量线程抢一把锁的场景。典型是「批量任务按提交顺序执行」「不希望小请求被大请求长期插队饿死」。一般场景默认非公平 RLock 就够（性能比公平锁快 30%+，因为少了 List 操作）。

## 四、读写锁 RReadWriteLock（读多写少神器）

和 JUC ReentrantReadWriteLock 语义一模一样：**读读共享、读写互斥、写写互斥**。

```
两个独立的锁对象：
  RReadWriteLock rw = redisson.getReadWriteLock("product:1001");
  RLock readLock  = rw.readLock();    ← 读锁（共享）
  RLock writeLock = rw.writeLock();   ← 写锁（排他）

读读并发：Thread-A 读锁持有，Thread-B 也能拿读锁 ✅
读写互斥：Thread-A 读锁持有，Thread-B 拿写锁 → 阻塞 ❌
写写互斥：Thread-A 写锁持有，Thread-B 拿写锁 → 阻塞 ❌
```

**底层怎么实现（面试能讲到这点 = P7）**：
- 同一个 Redis Hash key，**两个独立的 field 分别计数**
  - `mode` 字段：记录当前是「读模式」还是「写模式」（无=0，写=1，读=2）
  - 读锁：每个读线程有自己的 field 记数重入次数
  - 写锁：和 RLock 一样，每个写线程 field 记数重入次数
- **加写锁前**：检查 mode 是不是 0 或者已经是写模式且是自己
- **加读锁前**：检查 mode 是不是 0 或者已经是读模式（不能有写锁存在）

## 五、联锁 RMultiLock（多锁联动）

**语义：同时对 N 把独立锁加锁，全部拿到才算成功，一把失败就全部退回。**

```java
RLock lock1 = redisson.getLock("stock:1001");
RLock lock2 = redisson.getLock("balance:u9527");
RLock lock3 = redisson.getLock("order:lock");

RMultiLock multiLock = new RedissonMultiLock(lock1, lock2, lock3);

// 拿 3 把锁：全部成功才返回 true
boolean ok = multiLock.tryLock(3, 10, TimeUnit.SECONDS);
```

**底层实现**：for 循环每把锁调用 tryLock，有任何一把失败 → 反向遍历已经拿到的那些 → 全部 unlock → 再重试（或超时返回 false）。

## 六、红锁 RRedLock（N/2+1 节点，解决主从丢失锁）**｜争议点，P7 要答务实**

extends `RedissonMultiLock`，使用方式和 MultiLock 几乎一样，差别：
- **传进去的 N 个 RLock，应该对应 N 个独立 Redis 集群**（无主从/复制关系，完全独立）
- **加锁成功条件 = N/2 + 1 把锁拿到 且 总耗时 < TTL**

```java
// 5 个独立 Redis Master（5 套，互不复制）
Config c1 = ..., c2 = ..., c3 = ..., c4 = ..., c5 = ...;
RedissonClient r1 = Redisson.create(c1);
...
RLock lock1 = r1.getLock("order:lock"),
      lock2 = r2.getLock("order:lock"), ...;

RRedLock redLock = new RedissonRedLock(lock1, lock2, lock3, lock4, lock5);
redLock.lock();  // 要拿到 5/2+1=3 把才算成功
```

### Martin Kleppmann 对 RedLock 的质疑（背下来，面试加分）
Redis 作者 Salvatore 提出 RedLock 后，分布式系统专家 Martin Kleppmann 发博客质疑：
1. **时钟漂移**：Redis 各节点时钟不一致，可能导致某节点锁提前过期
2. **GC STW / 网络长时间延迟**：Client 拿了锁后发生长时间 GC STW，锁过期了，Client 还以为自己持有 → 另一 Client 也拿到 → 双持
3. **需要 N 套独立集群运维成本太高**

> 💡 **P7 正确回答**：「我知道 RedLock 算法，但**项目上不会用**。它牺牲了一半性能+需要维护 N 套独立 Redis，且理论上在时钟漂移/GC STW 下仍不安全。工程上更务实的做法是 **「Redisson 单集群 RLock + 幂等 + 乐观锁」三层兜底**：锁是第一道防线防并发，幂等（DB 唯一键/状态机）是第二道防线防脏数据，极端情况都能兜住。性价比远高于 RedLock。」——这个回答体现你追求的是「工程可靠性」而不是「理论完美」，P7 味道拉满。

## 七、信号量 RSemaphore

和 JUC Semaphore 语义一致：控制「同时最多 N 个线程并发」。底层 Redis **String 存剩余许可数**。

```java
RSemaphore sem = redisson.getSemaphore("api:concurrent:100");
sem.trySetPermits(100);  // 初始化 100 个许可（只执行一次）

sem.acquire(5);          // 拿 5 个许可，没就阻塞（-5）
// ... 执行高消耗逻辑 ...
sem.release(5);          // 归还 5 个许可（+5）
```

## 八、闭锁 RCountDownLatch

和 JUC CountDownLatch 语义一致：主任务等 N 个子任务完成。**底层 Hash 存剩余计数**。

```java
RCountDownLatch latch = redisson.getCountDownLatch("job:batch:20260902");
latch.trySetCount(5);                // 设置需要等 5 个子任务（只初始化一次）

// ===== 子任务（5 个实例各自执行）=====
latch.countDown();                    // 做完后减 1

// ===== 汇总任务（等所有人做完）=====
latch.await(30, TimeUnit.MINUTES);    // 阻塞到 count=0 或超时
// 到这里就可以做汇总、发通知了
```

## 九、易错点

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「不管 leaseTime 传什么都会有看门狗帮我续期」 | ❌ 只有 `leaseTime=-1`（不传 或 显式 -1）才开；显式传 15s 就只给 15s，到点直接过期，不会续 |
| 2 | 「公平锁比非公平锁好，所以全用公平锁」 | ❌ 公平锁有 List 排队开销，性能比非公平低 30%~50%；只有「明确需要 FIFO、防止饥饿」才用 |
| 3 | 「读写锁读多写少能无限读并发」 | ✅ 对，但前提是 Redis 本身是单线程命令执行；太多并发读会压满 Redis 主线程，建议配合 RLocalCachedMap 本地缓存 |
| 4 | 「RedLock 能 100% 防主从锁丢失」 | ❌ 时钟漂移/GC STW 仍可能双持；工程正确答案是「单集群 + 幂等兜底」 |
| 5 | 「联锁 MultiLock 和 红锁 RedLock 一样」 | ❌ MultiLock 是**拿全部 N 把**才成功；RedLock 是 **≥N/2+1 把**就成功，且节点必须是独立的无复制关系 |
| 6 | 「信号量 trySetPermits 每次调用都重置」 | ❌ trySetPermits 只有「许可数为 0 且从未设置过」才生效；已经有值了调用它无效。动态改许可数要用 `addPermits(n)` / `reducePermits(n)` |
| 7 | 「闭锁可以重置计数重用」 | ❌ RCountDownLatch 和 JUC 一样，计数到 0 就没法重置了（JUC 本来就这样设计）。要重复用的场景应该用 RCyclesSemaphore 或自己做一层封装。 |
| 8 | 「lock() 无参是安全的，反正看门狗兜底」 | ❌ lock() 是**永久阻塞等待**拿锁（无 wait 超时）；如果某个锁长期被人持有，调用方会一直 park。生产必须用 `tryLock(wait, lease, unit)` 带 wait 超时，避免线程永久挂起。 |

## 十、一句话总结

> Redisson 7 种锁 = **「RLock（Hash+可重入）+ 看门狗（HashedWheelTimer 每 10s PEXPIRE 续到 30s）」是基础**，公平锁加了**List 等待队列**，读写锁加了**双模式计数**，MultiLock 全拿、**RedLock ≥N/2+1 但工程少用**，信号量 String 记数、闭锁 Hash 记数；P7 面试的核心不是背 API，而是**讲清「RLock 三坑演进→可重入 Lua→看门狗源码→主从丢失→RedLock 争议→务实方案（锁+幂等兜底）」这条追问链**。
