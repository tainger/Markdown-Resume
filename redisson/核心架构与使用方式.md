# Redisson 核心架构与使用方式面试题

Redisson 是一个**Java Redis 高级客户端**，但它的定位远不止「客户端」这么简单：它基于 **Netty NIO** 实现非阻塞通信，并且把 JUC 里 40+ 种并发工具（ReentrantLock、ReadWriteLock、Semaphore、BlockingQueue、ConcurrentHashMap…）**在 Redis 上做了分布式实现**，让 Java 开发者用熟悉的 API 写分布式代码。

---

## 一、定位：Jedis vs Lettuce vs Redisson（⭐ P7 开场第一问）

Java 生态连接 Redis 主流有三驾马车，面试必问选型。

| 维度 | **Jedis** | **Lettuce** | **Redisson ⭐** |
|:---|:---|:---|:---|
| **作者/出身** | 老牌社区，Redis Labs 维护 | Pivotal（Spring 团队），Spring Data Redis 2.x 默认 | 俄罗斯开源项目，现被 Redis Labs 官方赞助 |
| **通信模型** | **同步阻塞 BIO**（一个 Jedis 实例同一时刻只能被一个线程用） | **异步响应式（Netty NIO）**，支持 Reactor Flux/Mono | **异步响应式（Netty NIO）**，同时提供同步/异步/RxJava 三套 API |
| **线程安全** | ❌ 非线程安全，必须配合 **JedisPool 连接池** | ✅ 一个连接实例多线程共享（基于 Netty Channel 多路复用） | ✅ 一个 RedissonClient 实例全局单例即可 |
| **连接池** | 必须 Apache Commons Pool2，默认 8 个连接；高并发下连接瓶颈明显 | 默认不需要池（一个 TCP 连接多路复用），可开连接池 | 每个 Redis 节点维护 **Netty Channel 池**（默认 64 条连接），空闲有心跳 |
| **集群/哨兵支持** | 支持（JedisCluster / JedisSentinelPool） | 支持 | 支持（自动发现节点、自动拓扑刷新） |
| **高级功能** | ❌ 几乎 0，只有基础命令封装 | ⚠️ 有响应式 API，但没有**分布式并发对象** | ✅ **40+ 分布式 JUC 对象**（可重入锁/公平锁/读写锁/信号量/闭锁/延迟队列/本地缓存Map/限流器…） |
| **Spring 整合** | Spring Data Redis 支持 | Spring Data Redis 默认推荐 | **Spring Cache 默认实现（Spring Boot 3.x+）**，有独立 Starter |
| **序列化** | 自己配（常见 GenericJackson2JsonRedisSerializer） | 同上 | **内置 10+ 编码器**：Kryo5/Jackson/JSONB/Avro/Smile/FST/Protobuf/JDK…默认 JDK（建议切 Kryo） |
| **适用场景** | 旧项目迁移、并发不高 | 纯基础 CRUD 命令、响应式编程 | **企业级 90% 场景首选**：分布式锁、缓存、分布式工具 |
| **一句话** | 够用但老、性能差 | 轻但薄、没高级货 | **「瑞士军刀」，P7 面试默认你会这个** |

> 💡 **P7 标准回答**：「我们项目统一用 Redisson，主要三个原因：① 性能比 Jedis 高（Netty NIO vs BIO）；② Spring Cache 官方默认实现、整合最顺；③ 40+ 分布式工具开箱即用，不用自己手写 Lua 实现锁/队列/限流器，工程效率和可靠性都高。」

## 二、Redisson 线程模型与架构分层

```
┌────────────────────────────────────────────────────────────┐
│                  应用层 (业务代码)                           │
│   RLock rLock = redisson.getLock("myLock"); rLock.lock();   │
│        RMap / RQueue / RBloomFilter / RRateLimiter ...      │
└───────────────────────────────┬────────────────────────────┘
                                │ 接口调用（同步/异步/Rx）
┌───────────────────────────────▼────────────────────────────┐
│                  命令对象层 (CommandExecutor)                │
│   把业务操作翻译为 Redis 命令 / Lua 脚本                     │
│   可重入锁 → Hash 结构 + Lua；信号量 → String + Lua          │
└───────────────────────────────┬────────────────────────────┘
                                │ 封装为 Command 对象进队列
┌───────────────────────────────▼────────────────────────────┐
│                  连接 & 拓扑管理层                           │
│  单/哨兵/Cluster 模式；定期 PING 做拓扑刷新；                │
│  每个节点独立的 Channel 池；MOVED/ASK 自动重定向              │
└───────────────────────────────┬────────────────────────────┘
                                │ 写出/读入字节
┌───────────────────────────────▼────────────────────────────┐
│          Netty NIO 事件循环组 (EventLoopGroup)              │
│          线程数 = 默认 CPU 核数 × 2                          │
│   ├─ Boss NIO：连接建立（TCP 三次握手）                      │
│   └─ Worker NIO：真正 socket 读写、pipeline 批量发送         │
└───────────────────────────────┬────────────────────────────┘
                                │ TCP 长连接
┌───────────────────────────────▼────────────────────────────┐
│              Redis 服务端（单机/哨兵/Cluster）                │
└────────────────────────────────────────────────────────────┘
```

**核心特点：**

| 点 | 说明 |
|:---|:---|
| **全局一个 RedissonClient 实例** | 重量级对象，Spring 容器中单例 Bean 即可；别每次 new 一个（会反复建 Netty 线程池和连接） |
| **Netty NIO 非阻塞** | 业务线程发命令不是直接阻塞等响应，而是把命令对象放进队列立即返回；Netty Worker 线程负责真正 socket 读写，读到响应后把结果回调给业务线程的 Future |
| **Pipeline 自动批处理** | 同一个业务线程连续发多条命令，Redisson 会自动合并 pipeline 发出，减少网络 RTT |
| **看门狗用的时间轮** | 续期/超时等调度任务走 Netty 的 `HashedWheelTimer`（时间轮），比 `ScheduledExecutorService` 更省线程 |

## 三、连接池（Netty Channel 池）

Redisson 的「连接池」和 Jedis 的 Commons Pool2 **不是一回事**：

```
每个 Redis 节点（Cluster 模式下每个主节点）：
  Channel Pool 1（64 条 Netty Channel，默认）
    ├── Channel-1 (TCP 连接)
    ├── Channel-2 (TCP 连接)
    ├── ...
    └── Channel-64 (TCP 连接)
```

| 配置项（Config） | 默认值 | 说明 |
|:---|:---|:---|
| `connectionPoolSize` | 64 | 每个节点连接池**上限**（64 条 Channel/连接，一般够了别乱调） |
| `connectionMinimumIdleSize` | 24（集群）/10（单） | 每个节点**最小空闲连接数**，冷启动时已备好，避免临时建连接延迟 |
| `idleConnectionTimeout` | 10000ms（10s） | 空闲连接超过此时间没被使用就关闭 |
| `connectTimeout` | 10000ms | 建立 TCP 连接超时 |
| `timeout` | 3000ms | 命令执行响应超时（3s 没收到结果就抛异常） |
| `retryAttempts` | 3 | 命令失败重试次数（MOVED/ASK 场景、网络抖动） |
| `retryInterval` | 1500ms | 重试间隔 |

> 💡 **调优建议**：大部分场景默认值够用。如果是 Redis 集群 + 万级 QPS，把 `connectionPoolSize` 调到 128，`connectionMinimumIdleSize` 调到 48，保证高峰期不用临时建连接。

## 四、4 种部署模式配置（⭐ 必会写）

Redisson 支持 4 种模式，用 YAML 或 Java Config 配置，Spring Boot 中直接写在 `application.yml` 的 `spring.redis.redisson.config:` 下。

### 1️⃣ 单机模式（开发/本地测试）

```yaml
# singleServerConfig：单节点
singleServerConfig:
  address: "redis://127.0.0.1:6379"
  password: null            # 没密码就 null
  database: 0               # 哪个 DB（0~15，默认 0）
  connectionPoolSize: 64
  connectionMinimumIdleSize: 10
  connectTimeout: 10000
  timeout: 3000
threads: 16                 # Netty 线程数（默认 CPU*2）
nettyThreads: 16
codec: !<org.redisson.codec.Kryo5Codec> {}   # Kryo5 序列化（生产推荐）
```

### 2️⃣ 哨兵模式（Sentinel，生产常用高可用）

```yaml
sentinelServersConfig:
  masterName: "mymaster"    # 哨兵配置的主节点名称（sentinel.conf 里的 sentinel monitor）
  sentinelAddresses:
    - "redis://sentinel1:26379"
    - "redis://sentinel2:26379"
    - "redis://sentinel3:26379"
  password: "redis密码"
  database: 0
  # 连接池：对每个实际 Redis 主/从节点生效
  masterConnectionPoolSize: 64
  masterConnectionMinimumIdleSize: 24
  slaveConnectionPoolSize: 64
  slaveConnectionMinimumIdleSize: 24
  readMode: "SLAVE"         # 读请求发从库（读写分离，SLAVE/MASTER/MASTER_SLAVE）
  subscriptionMode: "SLAVE" # Pub/Sub 订阅用从库
threads: 16
codec: !<org.redisson.codec.Kryo5Codec> {}
```

### 3️⃣ Cluster 模式（生产大规模分片，推荐 ≥ 3 主 3 从）

```yaml
clusterServersConfig:
  nodeAddresses:
    - "redis://node1:6379"
    - "redis://node2:6379"
    - "redis://node3:6379"
    - "redis://node4:6379"
    - "redis://node5:6379"
    - "redis://node6:6379"
  password: "redis密码"
  scanInterval: 2000        # 每 2s 扫描一次集群拓扑（自动感知节点增删/槽迁移）
  slots:
    - 0-16383               # 全槽位（一般不写默认全）
  masterConnectionPoolSize: 64
  masterConnectionMinimumIdleSize: 32
  slaveConnectionPoolSize: 64
  slaveConnectionMinimumIdleSize: 32
  readMode: "SLAVE"
threads: 16
codec: !<org.redisson.codec.Kryo5Codec> {}
```

### 4️⃣ 主从模式（手动指定主从地址，不常用）

```yaml
masterSlaveServersConfig:
  masterAddress: "redis://master:6379"
  slaveAddresses:
    - "redis://slave1:6379"
    - "redis://slave2:6379"
  password: "xxx"
  readMode: "SLAVE"
```

## 五、Java 快速上手：3 行初始化 RedissonClient

```java
import org.redisson.Redisson;
import org.redisson.api.RedissonClient;
import org.redisson.config.Config;

public class RedissonDemo {

    public static void main(String[] args) {
        // ===== 方式一：代码里写 Config =====
        Config config = new Config();
        config.useSingleServer()
              .setAddress("redis://127.0.0.1:6379")
              .setConnectionPoolSize(64);
        // Kryo5 序列化（体积比 JDK 小 5~10 倍，速度快 10+ 倍）
        config.setCodec(new org.redisson.codec.Kryo5Codec());

        RedissonClient redisson = Redisson.create(config);  // 单例，全局就这一个

        // 拿到各种分布式对象（接口名和 JUC 几乎一样，前面加 R）
        RLock lock = redisson.getLock("stock:1001");       // 可重入锁
        RMap<String, User> map = redisson.getMap("user");   // 分布式 Map
        RBlockingQueue<Order> queue = redisson.getBlockingQueue("orderQueue");

        redisson.shutdown();  // 应用关闭时关（Spring 容器销毁自动调）
    }

    // ===== 方式二：读 YAML 文件 =====
    public static RedissonClient fromYaml() throws IOException {
        Config config = Config.fromYAML(new File("redisson-config.yml"));
        return Redisson.create(config);
    }
}
```

> **Spring Boot 中怎么用？** 直接加依赖 `redisson-spring-boot-starter`，application.yml 里配地址就能 `@Autowired RedissonClient` 用。[Spring集成与生产调优.md](Spring集成与生产调优.md) 详解。

## 六、易错点

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「Redisson 和 Jedis 都是 Redis Java 客户端，没什么区别」 | ❌ 差远了！Jedis 只是「基础命令封装」+ BIO；Redisson 是 Netty NIO + 40+ 分布式并发工具的「高级框架」，定位层级不同 |
| 2 | 「每执行一次操作 new 一个 RedissonClient」 | ❌ 绝对禁止！RedissonClient 是重量级对象（建 Netty 线程池、建连接池），应该是全局单例（Spring 容器一个 Bean 即可） |
| 3 | 「Lettuce 和 Redisson 都走 Netty，选哪个都行」 | 看需求：只做简单 CRUD 命令 + 响应式 → Lettuce；要分布式锁/队列/本地缓存/限流 → **Redisson** |
| 4 | 「哨兵模式只需要填 sentinel 地址，不用 masterName」 | ❌ 必须填 `masterName`，不然哨兵不知道你要找哪组主从 |
| 5 | 「默认序列化就够用了」 | ❌ 默认是 JDK 序列化（`SerializationCodec`），要类实现 Serializable、体积大、慢、类版本兼容差；**生产必切 Kryo5Codec 或 JacksonJsonCodec** |
| 6 | 「Cluster 模式要写所有 6 个节点地址」 | 写任意几个就行（一般写全更稳）；Redisson 会自动通过 `CLUSTER SLOTS` 发现所有节点和槽位分布 |
| 7 | 「readMode=SLAVE 就完全读写分离强一致」 | 主从异步复制，从库读到的可能是旧数据（最终一致），和 Redis 服务端本身一致性是一个意思 |

---

## 七、一句话总结

> Redisson 的核心价值是**把「单机 JUC 并发工具」搬到 Redis 集群上**，让 Java 开发者用和本地 Lock/Map/Queue 几乎一样的 API 写分布式代码。架构分层是「业务 API → 命令对象/Lua 翻译 → 连接拓扑管理 → Netty NIO 事件循环」，全局一个 RedissonClient 单例。选型方面：**Jedis=老（BIO+无工具）、Lettuce=轻（响应式但无工具）、Redisson=全（Netty NIO+40+分布式工具，P7 默认会）**。生产配置四模式（单/哨兵/集群/主从），序列化切 Kryo5，连接池默认值基本够用，Spring Boot 用 Starter 自动装配。
