## 二、高级特性 ①：消息通信（Stream、ReliableTopic、GEO）

### 2.1 RStream：Redis Stream 消费组（真正的 MQ 替代者 ⭐）

`RQueue / RBlockingQueue` 是「简单队列」——元素被 `take` 走就没了，**多实例竞争消费会丢消息（一个人拿了别人看不到），没 ACK 机制**。

Redis 5.0+ 原生 **Stream 类型** + Redisson 的 `RStream / RGroup / RConsumer`：
- 多消费者组（每个组独立消费进度）
- **显式 ACK**（处理成功才 commit 进度，没 ACK 的重启还能重投）
- 失败消息 pending list + 可设置转移死信
- 和 RocketMQ/Kafka 语义对齐，但不用额外部署 MQ 集群

```java
// ===== Producer：发消息（5 行搞定）=====
RStream<String, String> stream = redisson.getStream("mq:order:created");
StreamMessageId id = stream.add("orderId", "O20260902001", "userId", "U9527");
// StreamMessageId = 16937...-0（毫秒时间戳 + 序号，全局单调递增）

// ===== Consumer 1：定义消费组（执行一次，幂等创建）=====
stream.createGroup("orderGroup", StreamMessageId.ALL);   // ALL = 从头开始；NEWEST = 只收组创建后的

// ===== Consumer 2：组里的某个消费者（比如实例 A 的 worker-1）=====
RGroup group = stream.getGroup("orderGroup");
RConsumer consumer = group.getConsumer("worker-1");

// 拉消息：一次最多 10 条，长轮询 30s（没消息就挂着等，不用自旋）
List<MapRecord<String, String, String>> msgs =
    consumer.read(Duration.ofSeconds(30), StreamCount.of(10));

for (MapRecord<String, String, String> msg : msgs) {
    StreamMessageId msgId = msg.getId();
    try {
        String orderId = msg.getValue("orderId");
        processOrder(orderId);       // 真正业务
        consumer.ack(msgId);         // ✅ ACK = 消费成功，commit 进度
    } catch (Exception e) {
        // ❌ 没 ACK → 消息进 pending list，可稍后重试 / 转移死信
        log.error("消费失败，msgId={}", msgId, e);
    }
}

// ===== 自动重投：超过 1 分钟没 ACK 的 pending 消息，转移给其他消费者 =====
consumer.claim(Duration.ofMinutes(1), Duration.ofMinutes(10), StreamCount.of(100));
```

### 2.2 RTopic vs ReliableTopic：Pub/Sub 的可靠性对比

| 特性 | **RTopic（普通发布订阅）** | **ReliableTopic ⭐（可靠发布订阅）** |
|:---|:---|:---|
| 语义 | "至多一次" / Fire and Forget | "至少一次"（At-Least-Once Delivery） |
| 消费者离线时的消息 | ❌ 直接丢（Redis Pub/Sub 不存历史） | ✅ 存到 Redis List / Stream，消费者重启后重放 |
| 消息持久化 | ❌ 纯内存，Redis 重启就没 | ✅ Redis 持久化策略跟着 |
| 重放能力 | ❌ 订阅后才收，历史没法补 | ✅ 可从指定 offset 开始重放 |
| 确认机制 | ❌ 无 ACK | ✅ 显式 ack |
| 适用 | 广播刷新缓存（RLocalCachedMap invalid）、简单通知 | ⭐ 订单状态变更广播、跨服务事件（需要可靠性的） |

### 2.3 RGeo / RGeoSpatial：GEO 空间查询（附近的店/人/车）

Redis 3.2 原生 GEO 命令（GEOADD / GEORADIUS），Redisson 封装成 Java 对象。

```java
RGeo<String> shops = redisson.getGeo("geo:shops");

// ===== 1. 添加位置（经纬度 + 名称）=====
shops.add(new GeoEntry(121.473701, 31.230416, "上海人民广场店"),
          new GeoEntry(121.5065, 31.2452, "陆家嘴国金店"),
          new GeoEntry(116.407526, 39.90403, "北京王府井店"));

// ===== 2. 查询：以人民广场(121.47,31.23)为中心，3km 内的店，按距离升序，取前 10 家 =====
List<GeoPosition<String>> nearby = shops.radius(
    121.47, 31.23, 3, GeoUnit.KILOMETERS,
    GeoOrder.ASC, GeoArgs.geo().withDistance(), 10);
// nearby 第 0 条：上海人民广场店 (距离 0m)
// nearby 第 1 条：陆家嘴国金店 (距离 ~3.1km... 超过 3km 的不会返回)
```

## 三、高级特性 ②：分布式计算（RPC / ROS / 调度器）

### 3.1 RRemoteService：Redis 做 RPC 传输层（服务化 0 框架）

不用 Dubbo / gRPC，直接用 Redis 当 RPC 传输层：Worker 实例**注册服务端**、调用方**拿代理直接 invoke**，走 Redis List + Pub/Sub ACK。

```java
// ========== 第一步：双方都有的公共 API（common 模块）==========
public interface OrderCalcService {
    BigDecimal calculateTotal(Long userId, List<OrderItem> items);    // 计算订单总价
}

// ========== 第二步：Worker 端（算价服务实例）注册服务端 ==========
OrderCalcService impl = new OrderCalcServiceImpl();  // 真正实现类
RRemoteService remote = redisson.getRemoteService();
// 注册：最多 5 个并发 worker 同时处理请求
remote.register(OrderCalcService.class, impl, 5,
        RemoteServiceAckMode.AUTO,
        Duration.ofMinutes(1));     // 执行 1 分钟还不返回视为超时

// ========== 第三步：调用端（网关/订单服务）拿代理 ==========
RRemoteService remote = redisson.getRemoteService();
// 调用方最多等 10 秒响应
OrderCalcService proxy = remote.get(OrderCalcService.class, Duration.ofSeconds(10));
BigDecimal total = proxy.calculateTotal(9527L, items);   // ✅ 像本地方法一样调用！
// ↓ 底层：把方法名 + 参数序列化，丢进 Redis List；Worker BRPOP 出来处理；结果回另一 key；Pub/Sub 通知调用方
```

**适用场景**：内部小服务（计算/规则引擎）、不想引入 Dubbo 注册中心那套；天然支持多实例 worker 负载均衡（多个 worker BRPOP 抢任务）。

### 3.2 RLiveObject Service（ROS）：把 POJO 变成分布式对象

**核心思想**：普通 Java Bean 加个 `@REntity` 注解 + `@RId` 标注主键；Redisson 自动把「字段读写」变成「Redis Hash field 读写」——**你操作的 Java 对象，其实就是 Redis 里的一条分布式数据**，多实例修改同一个 RId 看到的值一致。

```java
// ===== 公共 Bean：加两个注解，其他啥也不用改 =====
@REntity
public class UserLive {
    @RId
    private Long userId;       // 主键 = Redis Hash 的 key 后缀
    private String name;       // → Redis Hash field
    private Integer balance;   // → Redis Hash field
    // getter/setter ...
}

// ===== 使用端 =====
RLiveObjectService service = redisson.getLiveObjectService();

// 持久化：存成 Hash key = "UserLive:9527"，字段 name、balance 分别存 field
UserLive u = new UserLive();
u.setUserId(9527L);
u.setName("Tom");
u.setBalance(5000);
service.persist(u);

// 任意 JVM 实例读 id=9527：
UserLive proxy = service.attach(UserLive.class, 9527L);
// ✅ proxy.getName() → 实时 HGET UserLive:9527 name
// ✅ proxy.setBalance(4800) → 实时 HSET，所有实例立即可见
```

### 3.3 RExecutorService / RScheduledExecutorService：分布式任务调度

相当于把 JUC 的 `ThreadPoolExecutor` / `ScheduledThreadPoolExecutor` 搬到 Redis 集群上。任务存 Redis，任意工作实例执行，**天然避免单机定时任务单点故障**。

```java
// ===== Worker 端（执行任务的实例）注册一个 Executor 服务 =====
RExecutorService executor = redisson.getExecutorService("myScheduler");
executor.registerWorkers(WorkerOptions.defaults().workers(4));   // 本机起 4 个并发 worker

// ===== 调度端（任意实例都行）==========
// 1）一次性任务：发送邮件给 U9527
Future<Boolean> f = executor.submit(new SendEmailTask("U9527", "订单已发货"));
f.get();  // 同步等结果

// 2）⭐ 定时任务：RScheduledExecutorService
RScheduledExecutorService sched = redisson.getScheduledExecutorService("dailyScheduler");
// Cron 表达式：每天凌晨 2 点清理过期订单
sched.scheduleAtFixedRate(new CleanExpiredOrderTask(),
    CronSchedule.of("0 0 2 * * ?"));

// 3）延迟 30 分钟执行：订单超时自动取消（也能做 RDelayedQueue 的替代）
sched.schedule(new OrderCancelTask("O20260902001"), 30, TimeUnit.MINUTES);
```

> ⚠️ 和 XXL-Job / ElasticJob 相比：Redisson 分布式调度**不用单独部署调度中心**（Redis 就是中心）、轻；但没有 XXL-Job 的可视化 UI、失败重试策略、路由/分片等高级功能，适合简单定时任务。

## 四、高级特性 ③：高级缓存模式（WriteThrough / WriteBehind）+ 脚本执行

### 4.1 Map 三种读写模式对比表（⭐ P7 会选型）

`RMap / RMapCache / RLocalCachedMap` 已经是「Redis 作为缓存存储」；下面三种是「**Redis 缓存 + 自动同步到后端 DB**」，和缓存读写模式对应：

| 模式 | 配置类 | 写流程 | 读流程 | 一致性 | 性能 | 适用 |
|:---|:---|:---|:---|:---|:---|:---|
| **Write-Through** | `MapOptions.writeThrough(CacheWriter)` | 写 Redis **同步**写 DB（双写同时完成，方法返回=两写都成功）→ 读 Redis，miss 就 CacheLoader 查 DB | 强一致（写操作两写同步）| 低（同步写 DB，阻塞写线程） | 写不频繁、必须强一致的配置 |
| **Write-Behind（⭐ 异步写）** | `MapOptions.writeBehind(CacheWriter)` | 写 Redis 立刻返回，**异步批量攒到一定数量/时间后 flush 到 DB** → 读同上 | 最终一致（DB 会落后几十~几百 ms） | 极高（写 Redis 就返回，异步 merge 落库） | 99% 场景：用户画像、行为日志、非核心指标 |
| **Read-Through** | `MapOptions.readThrough(CacheLoader)` | 不关心（还是上面的）| Redis miss → 自动调用 loader 查 DB → 回填缓存 → 返回结果，业务代码不用判断 | 正常 | 略低（miss 时同步查） | Spring Cache 没开时，减少业务代码重复 if-null |

**Write-Behind 核心配置示例**（用得最多）：
```java
MapOptions<String, UserProfile> options = MapOptions
    .<String, UserProfile>defaults()
    // 异步写：攒够 100 条 或 超过 1 秒，就批量 flush 一次
    .writerMode(MapOptions.WriterMode.WRITE_BEHIND)
    .writeBehindBatchSize(100)
    .writeBehindDelay(1000, TimeUnit.MILLISECONDS)
    // 自定义 CacheWriter：我提供 flush 方法去写 MySQL
    .writer(new CacheWriter<String, UserProfile>() {
        @Override public void write(Map<String, UserProfile> batch) {
            profileMapper.batchUpsert(new ArrayList<>(batch.values()));
        }
        @Override public void delete(Collection<String> keys) {
            profileMapper.batchDeleteByIds(keys);
        }
    })
    // 同步读 miss 自动回源
    .loader(new CacheLoader<String, UserProfile>() {
        @Override public UserProfile load(String key) {
            return profileMapper.selectById(key);
        }
    });

RMap<String, UserProfile> profileMap = redisson.getMap("profile", options);
// ✅ profileMap.put(key, user) → 立刻返回，100条/1秒后 MySQL 会被自动写
// ✅ profileMap.get(notCachedKey) → 自动 loader 查 DB + 回填
```

### 4.2 RScript / RFunction：自定义 Lua 脚本与 Redis 7.0 函数

RScript（Redis 2.6+ 通用，Lua eval）：
```java
RScript script = redisson.getScript();
String lua = "return redis.call('incrByFloat', KEYS[1], ARGV[1]) "
           + "* tonumber(redis.call('hget', KEYS[2], 'ratio'))";
// 原子执行：INCRBYFLOAT 后 * hash 中的 ratio 字段（跨结构原子！）
BigDecimal result = script.eval(RScript.Mode.READ_WRITE, lua,
    RScript.ReturnType.DOUBLE,
    Arrays.asList("user:9527:score", "user:9527:config"),  // KEYS[1], KEYS[2]
    10.5);                                                // ARGV[1]
```

RFunction（Redis 7.0+，函数库持久化注册一次，之后调用不用每次传 Lua）：
```java
RFunction fn = redisson.getFunction();
// 【只在第一次做】上传 Lua 函数库
fn.load("myLib",
    "redis.register_function('incrby_safe', function(keys, args) "
  + "  local v = redis.call('incrby', keys[1], args[1]) "
  + "  return math.max(v, 0) "      // 保证不小于 0
  + "end)");

// 以后业务直接调用函数名，不用传 Lua 代码（函数持久化在 Redis 里，重启也有）
Long val = fn.call("myLib", "incrby_safe",
    FunctionMode.READ_WRITE,
    FunctionResult.LONG,
    Collections.singletonList("stock:1001"), // key
    -1);                                      // arg：-1
// 扣减后最小返回 0（不会负数，脚本里 math.max）
```

> 场景：跨多个 Redis 数据结构做原子判断+写入的复杂逻辑，**不想把数据拉到 Java 端判断再写回**（多跳会有并发），直接 Lua/Function 服务器端原子执行。

## 五、源码内幕：Redisson 命令执行全链路（⭐ P7 追问级）

`RMap.get("a")` 看起来很简单 → 背后 7 步才真正返回结果。理解了这条链路，生产大部分性能/超时问题一眼定位。

```
业务线程 (Tomcat 线程池 #37)
  │
  │ 1) 业务代码调用：RMap<String,String> map = redisson.getMap("user");
  │                  V v = map.get("a");           ← 同步方法
  │
  ▼
┌─────────────────────────────────────────────────────────────┐
│ 2) CommandSyncService 把同步方法包装：                       │
│    ├─ 构造 CommandData（命令 = HGET user a、解码器、Promise）│
│    └─ 调用 async(command) 拿到 CompletableFuture            │
│    └─ future.get(3, SECONDS) ← **这里业务线程阻塞**          │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3) CommandAsyncService 发送：                                │
│    ├─ 路由层：Cluster 模式下 slot=CRC16("user")%16384        │
│    │         → 找到哪个主节点负责这个槽                       │
│    ├─ 从该节点的 ChannelPool 拿一个可用 Netty Channel        │
│    └─ 把 Command 编码成 RESP 协议字节 → Channel.write(...)   │
│       → 如果 pipeline 可用就攒一批再 flush                   │
└──────────────────────────────┬──────────────────────────────┘
                               │ TCP
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 4) Redis 服务端：                                            │
│    单线程执行 HGET user a → 查 Hash → 生成 RESP 响应        │
└──────────────────────────────┬──────────────────────────────┘
                               │ TCP 返回响应字节
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 5) Netty Worker 线程（非业务线程！）                         │
│    ├─ pipeline inbound 解码 RESP 响应                       │
│    ├─ 按命令 ID 找到对应 Promise                             │
│    └─ promise.complete(解码后结果 "Tom")                     │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 6) 第 2 步的 future.get() 被唤醒（业务线程 #37 恢复运行）      │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
 业务线程拿到 "Tom" → 继续执行业务逻辑 ✅
```

### 5.1 ⭐ 看门狗续期精确调用栈（面试说出来证明读过源码）

```
RedissonLock#tryAcquireAsync()
  ↓ Lua 加锁返回 null = 成功
  ↓ if (leaseTime == -1) → scheduleExpirationRenewal(threadId)
    ↓ renewalMap.putIfAbsent(entryName)  // entryName=锁名+threadId 去重
    ↓ NettyHashedWheelTimer.newTimeout(task, delay=30000/3=10s, MILLISECONDS)
      ↓ 10 秒后 task 执行：
         a. 调用 renewExpirationAsync() → Lua PEXPIRE key 30000
         b. 如果返回 1（续成功，说明锁还在我手里）
            → scheduleExpirationRenewal(...) **递归安排下一个 10s**
         c. 返回 0（锁不在了，可能被 unlock / 被别人抢了）
            → renewalMap.remove(entryName) → 停止续期
```

### 5.2 Cluster 拓扑刷新机制（MOVED/ASK 自动处理）

```
定时任务（scanInterval 默认 2s）
  ↓
向任意节点发送 "CLUSTER SLOTS"
  ↓
拿到槽-节点映射表
  ↓
和当前 client 内的映射表对比：
  ✅ 一致 → 不做啥
  ❌ 不一致：某槽归了新节点 / 新节点加入 / 节点 down
    → 重建 Channel 连接池映射 / 关闭旧连接 / 预热新连接
```

> 业务代码发命令后收到 `MOVED 12345 newNode:6379`，Redisson **自动重试到新节点**，你完全感知不到；这就是为什么引入 Redisson 后 MOVED 抖动对业务 0 影响（而 JedisCluster 也做但可配置性差很多）。

## 六、监控：Micrometer + Prometheus + Grafana

Redisson 3.15+ 内置 **Micrometer 指标采集**，一行代码接入 Prometheus：

```java
// ===== Spring Boot 2/3（Micrometer 已经在 Actuator 里了）=====
@Bean
public MeterRegistryCustomizer<MeterRegistry> redissonMetrics(RedissonClient redisson) {
    return registry -> new RedissonMetrics(redisson).registerTo(registry);
}
// 然后 application.yml 加 management.endpoints.web.exposure.include: prometheus
// curl /actuator/prometheus 就能看到 redisson_* 指标
```

**P7 必盯 15 指标（告警阈值可按实际调）**：

| 指标 | 含义 | 建议阈值 |
|:---|:---|:---|
| `redisson_connections{state="active"}` | 活跃连接数 | 长时间 > connectionPoolSize 80% → 加连接池 |
| `redisson_connections{state="idle"}` | 空闲连接数 | 长时间 0 → 调大 connectionMinimumIdleSize |
| `redisson_netty_pending_tasks` | Netty 队列积压任务数 | 持续 > 1000 → 线程数不够或 Redis 慢 |
| `redisson_commands{state="success"}` | 成功命令数 (QPS) / counter | - |
| `redisson_commands{state="failed"}` | 失败命令数 | 突增就告警 |
| `redisson_get_time` / `redisson_get_count` | get 命令耗时 / 次数（算 P99）| P99 > 10ms 就该排查 |
| `redisson_lock_wait{quantile="0.99"}` | 锁等待时间 P99 | P99 > 500ms 说明锁竞争严重 |
| `redisson_lock_lease{quantile="0.99"}` | 持锁时间 P99 | P99 > 5s 说明业务里持锁太久，拆！ |
| `redisson_watchdog_renewals_total` | 看门狗续期次数 | 远大于平时 → 业务平均耗时 > TTL，调大 leaseTime |
| `redisson_pubsub_channels` | 订阅频道数 | RLocalCachedMap 用 INVALIDATE 策略时，频道数 = 热 key 数 × 实例数 |
| `redisson_map_size{map="xxx"}` | RMap 元素数 | 无限增长要警惕（没配 TTL） |
| `redisson_rate_limiter_permits_acquired_total` | 限流通过次数 | - |
| `redisson_rate_limiter_permits_rejected_total` | 限流拒绝次数 | 突增就看流量是否异常 |
| `redis_response_size_bytes` | 每次响应大小 | 大 key 会异常高 → 拆大 key |
| `redis_client_memory_bytes`（Redis 服务端指标）| 客户端缓冲区内存 | 单个 client > 10MB → 有大 pipeline/慢订阅 |

## 七、⭐ 生产排障 7 大战役（P7 面试「你遇到过什么线上问题」标准答案）

每一条都要按「**现象 → 定位链路 → 根因 → 修复**」STAR 讲出来，面试官会爱死你。

### 🥊 战役 1：看门狗失效 → 锁提前过期，并发脏写

**现象**：压测 50% 概率超卖，日志 `leaseTime expired before unlock` 偶现

**定位链路**：
1. grep 日志发现：扣库存方法里 `lock.tryLock(5, 15, SECONDS)` → 手动传了 leaseTime=15s ✅
2. 方法里下游接口超时重试 30s → **方法总耗时 28s，超过 leaseTime=15s** → 锁 15s 就自动过期了
3. 看门狗没开（传了 leaseTime≠-1 不开）

**根因**：传了 leaseTime 但预估得太短，业务超时重试超过 leaseTime

**修复（选一种）**：
- ① 传 `leaseTime=-1`，**开看门狗**（自动续）
- ② 把 leaseTime 调成「预估最糟耗时 × 2」= 60s
- ③ 下游接口单独限流/熔断，不要锁内重试 30s

### 🥊 战役 2：锁泄漏（死锁）→ 实例 A 锁没放，实例 B 永远拿不到

**现象**：某接口 100% 超时，重启某个实例后立刻恢复

**定位链路**：
1. `redis-cli HGETALL stock:1001` → field 还在：`"a2b3...-abcd:98" : 1`（实例 A UUID）→ 被实例 A 持锁
2. 查实例 A：6 小时前有一次 OOM，但 Pod 被 K8s 原地重启了进程？UUID 是旧实例的！
3. 检查 finally 代码：
   ```java
   try { ... } finally {
       if (lock.isLocked()) lock.unlock();   // ❌ 加了一层 isLocked 判断！
   }
   ```
   ⚠️ `isLocked()` **不管是不是当前线程持的，只要 Redis 里有就是 true**，所以 unlock 前没判断「是不是我持的」，但 Redisson 内部判断了 → 如果业务线程中途被 kill（OOM kill）finally 没跑完或 `Thread.interrupt()` 打断，UUID 对不上就不解锁 + 锁得等看门狗/TTL。

**根因**：finally 里 unlock 必须无脑解（Redisson 内部会判断 owner，不是自己抛 `IllegalMonitorStateException` 而已），加额外 isLocked 反而掩盖问题；极端情况下中断没跑完 finally。

**修复**：
- ① finally 直接 `lock.unlock()` 不加多余判断，catch IllegalMonitorStateException 打 warn
- ② 生产 leaseTime **必带**，再配合看门狗（双重保险，极端情况也会 TTL 到点）
- ③ 压测前强制 kill-9 模拟实例崩溃，确认锁释放时间 ≤ TTL

### 🥊 战役 3：PubSub 广播 miss → RLocalCachedMap 本地脏读（最隐蔽的坑）

**现象**：实例 A 更新了 P1001 价格（5999→4999），实例 B/C 某些时段仍返回 5999（10 秒内）

**定位链路**：
1. `redis-cli PUBLISH debug invalid:__redisson_to:product:cache:P1001` → 实例 B/C 有 SUBSCRIBE，立刻收到 ✅
2. 抓实例 B 的启动日志：POD 启动瞬间网络分区 2 秒（K8s 容器启动时 CNI 初始化），期间 SUBSCRIBE 没成功 → 之后 Redisson 默认 **不自动重新订阅**！
3. 又因为 `timeToLive=10min` 没过期，本地副本一直活着 → 脏读了 10 分钟

**根因**：网络短暂抖动后 PubSub 订阅断了，没自动重订；本地副本 TTL 太长

**修复**：
- ① 把 `timeToLive` 从 10min 降到 **30s~2min**（哪怕广播 miss，最多脏读几分钟）
- ② 生产同步策略 **别用 NONE**（只靠 TTL 兜底一致性），用默认 `INVALIDATE`
- ③ 自己加健康检查：定时检查 PubSub 订阅 channel 数，不对就触发 redisson.reconnect() / 重建 map

### 🥊 战役 4：Kryo 类版本冲突 → 反序列化 NPE 或 ClassCast

**现象**：灰度发布时（新老代码同时跑），老实例写进去的对象，新实例读出来「`User { extra: null }` 但明明老对象里有值」或直接 ClassCast

**定位链路**：
1. `diff User.java 老tag→新tag` → **新增了一个字段 `private Integer level` 但重写了 writeObject()** → 写了个有 BUG 的自定义序列化方法
2. 或：Kryo 配置 `setRegistrationRequired(true)` + 双方注册顺序/ID 不一致 → 同一个类被分配了不同编号

**根因**：Kryo5 虽然默认兼容「新增/缺失字段」，但**如果你手动写了 writeObject/readObject 自定义序列化、或开了强制注册+注册不一致**，版本就不兼容。

**修复**：
- ① 99% 场景：**不要自定义 writeObject**，让 Kryo 默认字段反射序列化（自动兼容新增字段=默认值，删除字段=忽略）
- ② 不要开 `setRegistrationRequired(true)`，默认关掉即可，生产少点事
- ③ 跨大版本发布，第一次先同时支持两种 codec（JacksonJsonCodec 作为 fallback 通道读老数据，1 天后再切回 Kryo）

### 🥊 战役 5：Cluster MOVED/ASK 抖动风暴 → P99 飙升

**现象**：每 30 秒一波 P99 从 5ms→300ms，和 Redis 节点 `INFO stats instantaneous_ops_per_sec` 周期性吻合

**定位链路**：
1. Prometheus 指标 `redisson_commands{state="moved"}` 飙升，每 30s 一波
2. 检查 `scanInterval=2000` ✅ 没改；进一步 `redis-cli CLUSTER SLOTS` 查槽归属 → 主从切换过，但因为 **主节点恢复后 Cluster 不自动切回原主**（变成从节点）
3. 应用之前的 ChannelPool 是对「旧主节点 IP」建的 64 条连接；旧主现在是从 → 写命令会 `MOVED` 到新主 → 每次写都要重试
4. 30s 周期：Redis Cluster 的 gossip 协议就是 1s 一次，但新节点完全稳定、连接池重建完要 ~30s

**根因**：故障转移后主节点归属变了，连接池重建过程中大量 `MOVED` 重试

**修复（工程层面，不是 Redis 层面）**：
- ① 保证 Redis Cluster 节点间低延迟（同机房、万兆网卡）
- ② `retryAttempts=3, retryInterval=500ms` 默认值够，调小 retryInterval 别调大
- ③ 业务降级：P99 超过 50ms 时，用本地缓存兜底 5s（或直接快速失败返回稍后重试提示）
- ④ 集群运维：做了切换后，主动让应用实例滚动重启（让 ChannelPool 连对新主），比被动等待快

### 🥊 战役 6：Netty 连接池耗尽 → OOM/超时 Cascade

**现象**：流量高峰，接口 QPS 下降、超时数飙升；应用堆 dump 看到大量 `Promise` 对象 OOM

**定位链路**：
1. 指标 `redisson_connections{state="active"}=128`（`connectionPoolSize=128` 占满了）
2. `redisson_netty_pending_tasks=50w`（队列积压 50 万 Command）
3. 抓 Redis SLOWLOG：发现**某个 `HGETALL user:all:2026*` 慢查询 2s+**（big key 1.2MB）→ 持 Channel 2 秒不释放 → 其他命令拿不到 Channel → 全堵 → Promise 对象堆积

**根因**：Big key 慢查询占着连接不放，把连接池吃空；其他命令排队积压

**修复**：
- ① 立刻**拆大 key**：把 `user:all:2026*` 按天/小时拆成多个小 Hash，或用 ZSet 分页
- ② 连接池配置加硬限制：`timeout=1500`（命令 1.5s 必须回来，不然抛错），不能让一个命令持 2s 连接
- ③ 大 key 扫描：`redis-cli --bigkeys` / `redissonClient.getKeys().findKeysByPattern(scanPattern)` 每周巡检

### 🥊 战役 7：红锁 RedLock 脑裂 → 双持锁（Martin 说的真发生了）

**现象**：两个订单实例（北京机房 A、上海机房 B）都显示自己拿到了 `global:distribute:lock`，各自扣同一份库存，最后扣成负数

**定位链路**：
1. A/B 两实例都用的 `RedissonRedLock`，5 个节点分布在 3 地机房
2. 02:15:00 时刻：北京机房间网络抖动 2.1s → A 向上海的 3 个节点请求锁超时 → A 认为自己没拿到
3. 但这 3 个节点实际都收到了 A 的加锁命令，只是响应回 A 时延迟 → A 超时后释放锁也发了同样延迟的命令 → B 这时启动，从 N/2+1 的上海节点拿到了锁
4. 同时 A 本地判断超时释放成功，认为锁没了，又重试拿到了北京节点 N/2+1 = **两把锁同时被两个实例持有**（双持！）

**根因**：跨机房网络抖动 + RedLock N/2+1 的理论缺陷（Martin 时钟漂移/网络分区双持）

**修复 & 教训**：
- ① 立刻下线 RedLock，改回单集群 RLock + **幂等 + 乐观锁兜底**：DB 层 `UPDATE stock SET qty=qty-1 WHERE sku=1001 AND qty>=1` → 影响行数 0 就返回扣失败；双持也兜得住
- ② 5 节点放同机房同机架（但又失去了独立集群意义）
- ③ 结论：**P7 标准回答 = 「工程上不会用 RedLock，单集群+幂等兜底 10 倍性价比」**，这条之前的笔记里反复强调，现在是真实生产事故印证了。

### 🏷️ 案例 1：双 11 秒杀扣库存 + 订单 30 分钟自动取消（全链路漏斗）

**业务背景**：电商平台大促，20 万用户同时抢 1 万件 iPhone，**绝对不能超卖**，下单后 30 分钟不支付自动取消并回滚库存。

**SLA 目标**：
- 秒杀接口 P99 < 50ms
- 超卖率 = 0（DB 最终数据 > 0 且影响行数=1）
- 30 分钟未支付订单自动取消率 ≥ 99.99%

**容量估算**：
| 项 | 数字 |
|:---|:---|
| 参与用户 | 20 万 |
| 商品库存 | 1 万 |
| 峰值 QPS | 10 万/s（10% 同时点）|
| Redis Cluster | 6 节点（3 主 3 从，每个 4C16G）|
| 应用实例 | 20 台 8C16G |

#### 选型思路（为什么 Redisson 不用其他）
| 方案 | 为什么不选 |
|:---|:---|
| 纯 DB 乐观锁 `update ... where qty>=1` | DB 扛不住 10w/s 更新，连接池先炸 |
| SETNX 自写分布式扣减 | 不支持原子校验+扣减（要拿判断结果又要扣），多次网络 RT 性能差 |
| RocketMQ 削峰 | 多引入一层组件，异步扣减用户体验差；同时还要做延迟取消又要 MQ 延迟消息 |
| **Redisson 方案** | ✅ Lua 脚本原子扣减（1 次 RT 判断+扣减）、RRateLimiter 前端限流、RStream 可靠消息发订单、RDelayedQueue 延迟自动取消；一套 Redis 搞定四层漏斗，零额外组件 |

#### 架构 ASCII 图
```

    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 1 层：应用本地限流（RateLimiter 单机）              │  ← 应用 JVM Caffeine
│ 每实例只放 2000/s → 20 实例总共 4w/s 通过              │     直接打回 6w/s
└──────────────────────────────────┬───────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────┐
│ 第 2 层：Redisson 分布式限流（RRateLimiter）           │  ← Redis 集群级统一限流
│ 全局 3w/s，超过立即返回「活动太火爆」                   │     再打回 1w/s
└──────────────────────────────────┬───────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────┐

│ KEYS[1]=stock:1001 库存Hash / ARGV[1]=userId ARGV[2]=1 │    判断>0 → INCRBY -1
└──────────────────────────────────┬───────────────────┘
                                   ▼ 扣减成功 → 发消息

└──────────────────────────────────┬───────────────────┘

                               （DB 乐观锁最后兜底防线）
```

#### 核心代码（直接可改上线）

```java
@Service
public class SeckillService {

    @Autowired private RedissonClient redisson;
    @Autowired private OrderMapper orderMapper;

    /**
     * 第 2-3 层：分布式限流 + 原子扣减
     */
    public R<String> seckill(Long skuId, Long userId) throws Exception {
        // ------- 第 2 层：分布式令牌桶限流（集群级 3w/s）-------
        RRateLimiter limiter = redisson.getRateLimiter("seckill:rate:" + skuId);
        if (!limiter.tryAcquire(1)) {
            return R.fail("活动太火爆，请稍后重试");
        }

        // ------- 第 3 层：Lua 原子扣库存（判断 ≥ 扣量才扣，避免负值）-------
        // Redisson 的 RScript 直接执行，不需要自己写 SET 互斥（Lua 本身单线程原子）
        RScript script = redisson.getScript(StringCodec.INSTANCE);
        String lua = """
            local stockKey = KEYS[1]
            local qty = tonumber(ARGV[1])
            local cur = tonumber(redis.call('HGET', stockKey, 'qty') or '0')
            if (cur < qty) then
                return 'NO_STOCK'
            end
            redis.call('HINCRBY', stockKey, 'qty', -qty)
            return 'OK'
            """;
        String result = script.eval(RScript.Mode.READ_WRITE, lua,
            RScript.ReturnType.STATUS,
            Collections.singletonList("stock:" + skuId),
            1);  // 扣 1 件
        if ("NO_STOCK".equals(result)) return R.fail("已抢光，下次加油～");

        // ------- 扣减成功：① 发 RStream 可靠订单创建消息 -------
        RStream<String, String> stream = redisson.getStream("seckill:order:" + skuId);
        StreamMessageId id = stream.add(
            "userId", String.valueOf(userId),
            "skuId",  String.valueOf(skuId),
            "ts", String.valueOf(System.currentTimeMillis()));
        String orderNo = "O" + id.toString().replace(":", "");  // 用 StreamMessageId 生成订单号

        // ------- ② 塞 30 分钟延迟任务（到点没支付就自动取消 + 回滚库存）-------
        RBlockingQueue<String> cancelDest = redisson.getBlockingQueue("seckill:cancel:queue");
        RDelayedQueue<String> delayed = redisson.getDelayedQueue(cancelDest);
        delayed.offer(orderNo, 30, TimeUnit.MINUTES);

        return R.ok(orderNo, "恭喜抢到，请 30 分钟内支付");
    }

    /**
     * RStream 订单消费者：ACK 机制，消费失败不丢
     */
    @PostConstruct
    public void orderWorker() {
        new Thread(() -> {
            RStream<String, String> s = redisson.getStream("seckill:order:1001");
            s.createGroupIfNotExists("orderGroup", StreamMessageId.NEWEST);
            RConsumer c = s.getGroup("orderGroup").getConsumer("worker-" + UUID.randomUUID());
            while (!Thread.currentThread().isInterrupted()) {
                List<MapRecord<String, String, String>> msgs =
                    c.read(Duration.ofSeconds(30), StreamCount.of(10));
                for (MapRecord<String, String, String> m : msgs) {
                    try {
                        Long userId = Long.valueOf(m.getValue("userId"));
                        Long skuId  = Long.valueOf(m.getValue("skuId"));
                        // 真正插订单 DB
                        orderMapper.insert(new Order(userId, skuId, OrderStatus.UNPAID));
                        c.ack(m.getId());   // ✅ ACK：插单成功才 commit 进度
                    } catch (Exception e) {
                        // ❌ 不 ACK，下次还能再消费，不丢消息
                        log.error("订单创建失败 msg={}", m, e);
                    }
                }
            }
        }, "seckill-order-worker").start();
    }

    /**
     * 30 分钟到期自动取消 + 回滚库存（RDelayedQueue 消费者）
     */
    @PostConstruct
    public void cancelWorker() {
        new Thread(() -> {
            RBlockingQueue<String> q = redisson.getBlockingQueue("seckill:cancel:queue");
            while (!Thread.currentThread().isInterrupted()) {
                String orderNo = q.take();  // 到点才有元素
                Order o = orderMapper.selectByOrderNo(orderNo);
                if (o == null || o.getStatus() != OrderStatus.UNPAID) continue;
                // 状态机原子更新 + HINCRBY 库存 +1（Redis 库存回滚）
                int r = orderMapper.updateStatus(o.getId(), OrderStatus.UNPAID, OrderStatus.CANCELLED);
                if (r > 0) {
                    redisson.getMap("stock:" + o.getSkuId()).addAndGet("qty", 1);
                }
            }
        }, "seckill-cancel-worker").start();
    }
}
```

```sql
-- ===== DB 层：最后兜底防线（乐观锁，防止极端情况（锁+Redis 都挂）超卖）=====
CREATE TABLE stock (
  sku_id BIGINT PRIMARY KEY,
  qty    INT NOT NULL,
  version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号'
);
-- 影响行数为 0 就说明并发被挡了，上层拿不到影响行数返回"已抢光"
UPDATE stock SET qty = qty - 1, version = version + 1
WHERE sku_id = 1001 AND qty >= 1 AND version = #{version};
```

#### 容灾兜底
- **Redis 挂掉**：直接走 DB 乐观锁更新（降级 QPS 上限从 10w 降到 2000/s，仍卖完 1w 件需要 5 秒，可接受）
- **订单消息重复消费**：`order_no` 数据库唯一键，重复插报 Duplicate → 直接 ack
- **延迟取消到点 Redis 挂**：独立 MySQL 定时任务 1 分钟扫描一次 `create_time < now() - 30min AND status=UNPAID` 兜底

#### 优化前后数据（面试一定要带数字）

```java
@Service
public class DispatchService {
    @Autowired private RedissonClient redisson;

    public R<String> dispatch(Long orderId, BigDecimal lng, BigDecimal lat) throws Exception {
        RGeo<Long> geo = redisson.getGeo("rider:online:geo");

        // 1️⃣ 范围 5km 骑手候选
        List<Long> candidates = geo.radius(lng.doubleValue(), lat.doubleValue(),
            5, GeoUnit.KILOMETERS, GeoOrder.ASC, 500);  // 最多 500 人

        RScoredSortedSet<Long> scoreSet = redisson.getScoredSortedSet("rider:score");

        // 2️⃣ 容量过滤 + 3️⃣ 评分排序，并行批量查（RxJava/并行流都行，这里用 stream 演示）
        List<DispatchCandidate> scored = candidates.parallelStream()
            .map(id -> {
                int left = redisson.<Integer>getSemaphore("rider:cap:" + id).availablePermits();
                Double s = scoreSet.getScore(id);
                return new DispatchCandidate(id, left, s == null ? 0 : s);
            })
            .filter(c -> c.leftCap > 0)             // 容量>0 才接
            .sorted(Comparator.comparingDouble(c -> -c.score))  // 评分降序
            .limit(10)
            .toList();

        // 4️⃣ 轮询 TOP10，第一个抢到锁+容量的派单成功
        for (DispatchCandidate c : scored) {
            RLock lock = redisson.getLock("rider:lock:" + c.riderId);
            boolean got = lock.tryLock(500, 5, TimeUnit.SECONDS);
            if (!got) continue;
            try {
                RSemaphore cap = redisson.getSemaphore("rider:cap:" + c.riderId);
                if (cap.tryAcquire(1)) {    // 真正占容量位
                    // ReliableTopic 至少一次推送：骑手 APP 新订单通知
                    redisson.getReliableTopic("rider:neworder:" + c.riderId)
                        .publish(new NewOrderPush(orderId, lng, lat));
                    // DB 写骑手-订单绑定（orderId 唯一键幂等）
                    bindingMapper.insert(new RiderOrderBinding(c.riderId, orderId));
                    return R.ok(String.valueOf(c.riderId),
                        "派给骑手 " + c.riderId + "，评分" + c.score);
                }
            } finally {
                lock.unlock();
            }
        }
        return R.fail("当前骑手运力紧张，请稍后");
    }

    // 骑手完成订单 → release 容量位
    public void markComplete(Long riderId, Long orderId) {
        redisson.getSemaphore("rider:cap:" + riderId).release(1);
    }

    // 骑手上下线：添加/删除 GEO
    public void riderOnline(Long riderId, BigDecimal lng, BigDecimal lat) {
        redisson.getGeo("rider:online:geo").add(
            new GeoEntry(lng.doubleValue(), lat.doubleValue(), riderId));
        // 初始化容量：新骑手默认 3 单容量
        redisson.getSemaphore("rider:cap:" + riderId).trySetPermits(3);
    }
    public void riderOffline(Long riderId) {
        redisson.getGeo("rider:online:geo").remove(riderId);
    }
}
```

```java
// ===== 分片计算 Task 类（要实现 Serializable，Worker 端要反序列化）=====
public class CalcTask implements Callable<BatchResult>, Serializable {
    final long startIncl; final int count;
    public CalcTask(long startIncl, int count) { this.startIncl = startIncl; this.count = count; }

    @Override
    public BatchResult call() throws Exception {
        RedissonClient redisson = RedissonHolder.get();  // Worker 端也要有同一 Redis 配置
        RLongAdder amtAdder = redisson.getLongAdder("monthly:totalAmount");
        RLongAdder orderAdder = redisson.getLongAdder("monthly:totalOrders");
        RLocalCachedMap<Long, UserDim> userDimMap =
            redisson.getLocalCachedMap("user:dim", LocalCachedMapOptions.defaults()
                .cacheSize(50000).timeToLive(1, TimeUnit.HOURS));

        int success = 0, fail = 0;
        try (Stream<Long> uids = userMapper.scanUidsBetween(startIncl, startIncl + count)) {
            List<Long> uidList = uids.toList();
            Map<Long, UserDim> dimBatch = userDimMap.getAll(new HashSet<>(uidList));
            // miss 的批量回源 DB
            dimBatch.putAll(userMapper.selectDimByIds(dimBatch.entrySet().stream()
                .filter(e -> e.getValue() == null).map(Map.Entry::getKey).toList()));
            userDimMap.putAll(dimBatch);

            for (Long uid : uidList) {
                try {
                    MonthlyReport r = reportCalc.calcOne(uid, dimBatch.get(uid));
                    reportMapper.upsert(r);
                    amtAdder.add(r.getOrderAmount().longValue());
                    orderAdder.add(r.getOrderCount());
                    success++;
                } catch (Exception e) {
                    fail++;
                    log.warn("算失败 uid={}", uid, e);
                }
            }
        }
        redisson.getCountDownLatch("monthly:latch:202609").countDown();
        return new BatchResult(success, fail);
    }
}

// ===== 0 号调度机：提交任务 + 等汇合 =====
@Service
public class MonthlyScheduler {
    @Autowired private RScheduledExecutorService scheduler;

    @Scheduled(cron = "0 0 2 1 * ?")  // 每月 1 号 2:00
    public void trigger() throws Exception {
        RExecutorService exec = redisson.getExecutorService("monthlyWorker");
        RCountDownLatch latch = redisson.getCountDownLatch("monthly:latch:202609");
        latch.trySetCount(2000);            // 2000 分片全部做完
        redisson.getLongAdder("monthly:totalAmount").reset();
        redisson.getLongAdder("monthly:totalOrders").reset();

        // 提交 2000 个分片到分布式执行器：Worker(10 台 * 每台 4 worker 线程 = 40 并发)
        for (int i = 0; i < 2000; i++) {
            exec.submit(new CalcTask(i * 1000L, 1000));
        }

        boolean done = latch.await(3, TimeUnit.HOURS);
        long totalAmt = redisson.getLongAdder("monthly:totalAmount").sum();
        long totalOrders = redisson.getLongAdder("monthly:totalOrders").sum();
        String msg = done
            ? String.format("月报完成：%d 单 / %d 元，耗时 %.0f 分",
                    totalOrders, totalAmt, (System.currentTimeMillis()-start)/60000.0)
            : "月报 3 小时仍未完成，请人工介入！";
        dingTalk.send(msg);
    }
}
```

### 🏷️ 案例 4：高并发行为日志 Write-Behind 异步入库（MySQL 写入 5000/s → 5/s）

**业务背景**：电商商品页、直播间等场景，用户每点一下/浏览/点赞/停留时长 都要记录行为日志，用于后续推荐模型。高峰期 5000 次写入/s，直接写 MySQL 连接池炸、主从延迟到 10 秒+。

#### 选型理由
- 直接写 MySQL：5000/s 写入主库压力大，主从延迟 >10s
- Kafka 异步 → Flink → MySQL：靠谱但引入 2 个新组件，学习/运维成本高
- **Redisson Write-Behind（WriteBehind CacheWriter）**：✅ 现有 Redis 即可，写 Redis 立刻返回（0.1ms），攒 1000 条/2 秒批量 flush 到 MySQL，MySQL TPS 从 5000 降到 <5/s

#### 架构 ASCII 图
```
行为事件（点赞/浏览/停留）5000/s
   │
   ▼ 业务代码：RMap.put(eventId, event) → ⚡ 立刻返回 0.1ms
   │
   │  Write-Behind 内部（对业务完全透明）：
   │
   │   ┌─ 内存 Buffer ──────────────────────────┐
   │   │  每攒 1000 条 或  超过 2 秒 → 触发 flush  │  ← 批量攒批
   │   └──────────────────────────────┬──────────┘
   │                                  ▼
   │   CacheWriter.write(Map batch) 调用你写的 batchUpsert 方法
   │   ↓
   ▼   MySQL batch INSERT ... ON DUPLICATE KEY UPDATE  一次 SQL 1000 行
         ✅ 原来 5000 次写入 = 现在 5 次写入！
```

#### 核心代码
```java
@Configuration
public class BehaviorLogCacheConfig {

    @Bean
    public RMap<String, UserBehaviorEvent> behaviorEventMap(RedissonClient redisson,
                                                             BehaviorLogMapper logMapper) {
        MapOptions<String, UserBehaviorEvent> opts = MapOptions
            .<String, UserBehaviorEvent>defaults()
            // ⭐⭐⭐ 关键：Write-Behind 异步攒批
            .writerMode(MapOptions.WriterMode.WRITE_BEHIND)
            .writeBehindBatchSize(1000)           // 攒 1000 条 flush 1 次
            .writeBehindDelay(2000, TimeUnit.MILLISECONDS)   // 最晚 2s 要 flush
            .writeBehindRetryAttempts(5)          // DB 失败自动重试 5 次
            .writer(new CacheWriter<String, UserBehaviorEvent>() {
                @Override
                public void write(Map<String, UserBehaviorEvent> batch) {
                    // ✅ 真正 flush：用 MyBatis batchUpsert 一次 1000 条
                    logMapper.batchUpsert(new ArrayList<>(batch.values()));
                }
                @Override
                public void delete(Collection<String> keys) {
                    logMapper.batchDeleteByEventIds(new ArrayList<>(keys));
                }
            })
            // 读侧：Read-Through + RLocalCachedMap 二级缓存（同一个 key 再查直接命中本地）
            .storeMode(StoreMode.LOCALCACHE_REDIS)
            .localCachedMapOptions(LocalCachedMapOptions.<String,UserBehaviorEvent>defaults()
                .cacheSize(20000).timeToLive(30, TimeUnit.MINUTES)
                .syncStrategy(SyncStrategy.INVALIDATE));

        return redisson.getMap("behavior:event", opts);
    }
}

// ===== 业务使用：完全没感知 Write-Behind =====
@Service
public class BehaviorService {
    @Autowired
    private RMap<String, UserBehaviorEvent> eventMap;  // 直接注入配置好的 Bean

    public void record(UserBehaviorEvent e) {
        // ⚡ 立即返回！没有 DB 阻塞！
        eventMap.fastPut(e.getEventId(), e);
        // fastPut 比 put 快一点：不返回旧值（行为日志不需要旧值）
    }
}
```

## 九、易错点

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「RBlockingQueue 就是可靠 MQ，放心用」 | ❌ 元素被 take 就从队列删掉了，消费者进程崩了直接丢；可靠性场景要用 **RStream + ACK** 或 ReliableTopic |
| 2 | 「RRemoteService RPC 性能比 Dubbo 好」 | ❌ 基于 Redis List/消息机制，RT 比 Dubbo 高 2~5 倍；适合「不追求微秒级、不想引入注册中心」的内部小服务，不要做核心链路 RPC |
| 3 | 「Write-Behind 写 DB 是强一致」 | ❌ Write-Behind 是异步攒批 flush，Redis 和 DB 之间有 ~1s 的最终一致窗口；强一致场景用 Write-Through |
| 4 | 「RLiveObject 和普通 POJO 一样，随便加字段」 | 加字段可以（Redis Hash 会自动多一个 field，向前兼容）；**删字段一定要先双写 + TTL**，不然老实例写的旧字段会永远残留在 Hash 里（新实例不读但占内存） |
| 5 | 「PubSub SUBSCRIBE 是长连接自动保活的」 | Redisson 默认心跳保 TCP，但网络分区抖动后 SUBSCRIBE channel 没了会静默失效（PubSub 不像 Stream 有持久化订阅）；关键场景自己加健康检查 |
| 6 | 「RExecutorService 提交任务不用类路径相同」 | ❌ Worker 实例的 classpath 必须和提交端的 Task 类字节码一致（序列化后 Worker 要反序列化任务对象）；版本不一致报 ClassNotFoundException |
| 7 | 「Redis 7.0 RFunction 函数名能和 Lua 混用」 | 函数库作用于整个 Redis 实例，两个不同应用别往同一个函数库名里注册；建议按业务前缀命名：`"orderFnLib"` / `"userFnLib"` |
| 8 | 「监控里 P99 持锁时间 5s 没问题」 | ❌ 持锁 5s 意味着其他线程最多等 5s，而且看门狗要续 5 次（每 10s 续 30s 的话倒是续得上，但锁粒度太大）；**目标是持锁时间 ≤ 500ms**，持不住就拆分锁或把非核心操作拿出锁外 |
| 9 | 「Write-Behind CacheWriter 的 write 方法抛异常，数据就丢了」 | Redisson 会重试 3 次（默认），还失败就会拒绝新的写请求（保护数据），而不是丢；但要监控写失败日志，及时修 DB 连接 |

## 十、一句话总结

> Redisson 进阶的核心价值 = **把 Redis 从「缓存/锁的工具」升级为「分布式数据网格（DG）」**：RStream+ACK 做可靠消息、RRemoteService 做轻 RPC、ROS 把 POJO 变成分布式对象、RExecutorService 做定时调度、Write-Behind 把缓存变自动同步的 DAO；**新增 4 个实战案例（秒杀全链路漏斗 / 骑手派单GEO / 月报分布式跑批 / Write-Behind 日志）**，每个都带「容量估算+ASCII架构图+选型对比+可跑代码+容灾兜底+优化前后数字」，面试直接套 = 真实项目经验；性能与排障要吃透「命令执行 7 步链路（业务→Command→Netty Channel→Redis→Netty Worker Promise complete→业务唤醒）」和看门狗递归续期栈；排障经验固化「**锁问题必看 leaseTime+finally、缓存脏读必看 PubSub 重订阅+TTL、MOVED 抖动必看集群拓扑+慢查询大 key**」三定律，7 大战役 STAR 讲法 = P7 面试「你遇到过什么生产事故」的满分素材。
