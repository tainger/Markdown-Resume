# RocketMQ 可靠性与高可用面试题

这是 RocketMQ 面试的**终极综合题**：消息如何做到不丢、不重复、如何应对堆积、集群如何高可用。答好这四个问题，需要把前面几篇的知识串起来。

---

## 一、消息如何保证不丢失？（三段论）

消息从发送到消费经过三个阶段，**每个阶段都可能丢**，要逐段保证：

```
Producer ──① 发送阶段──▶ Broker ──② 存储阶段──▶ Consumer
                          ③ 消费阶段
```

### ① 发送阶段（Producer → Broker）

| 手段 | 说明 |
|:---|:---|
| **同步发送 + 确认** | 用 sync send，收到 Broker ack 才算成功 |
| **发送重试** | 发送失败自动重试（默认重试 2 次），可切换其他 Broker/队列 |
| **事务消息** | 保证本地事务与消息发送的原子性 |

### ② 存储阶段（Broker 持久化）

| 手段 | 说明 |
|:---|:---|
| **同步刷盘** | 消息刷到磁盘才返回，避免 PageCache 中断电丢失 |
| **主从同步复制** | Master 写入后同步给 Slave，双份持久化 |

> 存储阶段要真正不丢，需 **同步刷盘 + 同步复制** 双管齐下：单同步刷盘防单机断电，单同步复制防单机磁盘损坏。

### ③ 消费阶段（Broker → Consumer）

| 手段 | 说明 |
|:---|:---|
| **消费成功才提交 offset** | 消费完业务逻辑再返回 `CONSUME_SUCCESS`，未成功不提交 offset |
| **消费重试 + 死信队列** | 失败自动重试 16 次，仍失败进 DLQ 人工处理 |

> **关键**：绝不能「先提交 offset 再处理业务」，否则处理失败消息就丢了。要「先处理业务，成功后再提交 offset」。

## 二、重复消费从哪来？如何幂等？

### 重复消费的来源

RocketMQ 只保证 **at least once（至少一次）**，以下情况必然产生重复：

| 来源 | 说明 |
|:---|:---|
| **发送重试** | Producer 发送成功但 ack 丢失 → 重发 → Broker 存了两条 |
| **消费 offset 未提交** | 消费成功但宕机，offset 未提交 → 重启重新消费 |
| **Rebalance** | 队列转移时未提交 offset → 新消费者重新拉取 |

### 幂等方案（业务侧兜底）

既然无法从根源杜绝重复，**消费端必须做幂等**：

| 方案 | 说明 | 适用 |
|:---|:---|:---|
| **业务唯一键 + 去重表** | 用订单号做唯一索引，重复插入报错则跳过 | DB 落库场景 |
| **Redis SETNX** | 用消息唯一 ID 做 key，`setnx` 成功才处理 | 高并发去重 |
| **状态机** | 判断业务状态，如订单已支付则忽略重复的支付消息 | 有状态流转的业务 |

```java
// 示例：Redis 幂等去重
String key = "msg:" + msg.getKeys();       // 消息唯一标识
if (redis.setnx(key, "1", 24, HOURS)) {    // 首次消费
    doBusiness(msg);                       // 处理业务
} else {
    // 重复消息，直接跳过
}
```

> **面试标准答**：RocketMQ 天然不保证 exactly once，靠**生产端消息唯一 ID + 消费端幂等（去重表/Redis/状态机）**实现业务层的「精确一次」。

## 三、消息堆积怎么办？

消费速度 < 生产速度，消息在队列中大量积压。

### 排查思路

```
1. 定位原因：消费者宕机？消费逻辑变慢（慢 SQL/外部调用）？流量突增？
2. 看堆积在哪：某几个队列还是全部队列？（可能是热点 key 顺序消息导致单队列堆积）
```

### 解决方案

| 方案 | 说明 | 注意 |
|:---|:---|:---|
| **增加消费者实例** | 扩容消费者，最多到**队列数**（多了也无队列可分） | 受队列数量上限约束 |
| **增加队列数** | 队列不够时先扩队列，再扩消费者 | 顺序消息扩队列会破坏顺序 |
| **提升单机并发** | 调大 `consumeThreadMax` 消费线程数 | 受下游（DB）承受能力约束 |
| **批量消费** | 一次拉多条批量处理，减少往返 | 需业务支持批处理 |
| **临时转存** | 极端堆积时，先快速拉取消息转存到其他 Topic/DB，再慢慢处理 | 应急兜底 |

> **核心约束**：**消费者数量 ≤ 队列数量**。如果 Topic 只有 4 个队列，加到第 5 个消费者也分不到队列，会空闲。所以扩容消费者前要先确认队列数够。

## 四、Broker 高可用：主从与 DLedger

### 传统主从（Master-Slave）

| 复制方式 | 说明 | 可靠性/性能 |
|:---|:---|:---|
| **同步复制（SYNC_MASTER）** | Master 写入后等 Slave 复制成功才返回 | 可靠高，性能低 |
| **异步复制（ASYNC_MASTER）** | Master 写入立即返回，异步复制给 Slave | 性能高，Master 挂可能丢 |

**传统主从的痛点**：Master 宕机后，**不能自动切换**（Slave 只能读，无法自动升为 Master），需人工介入 → 可用性不足。

### DLedger 模式（4.5+，自动主从切换）

基于 **Raft** 协议实现，解决自动故障转移：

```
DLedger 组（至少 3 个节点）
  → Raft 选举出 Leader（相当于 Master）
  → 消息写入需多数派（majority）节点确认才算成功
  → Leader 宕机 → 剩余节点自动重新选举新 Leader → 自动故障转移
```

| 对比 | 传统主从 | DLedger |
|:---|:---|:---|
| **故障切换** | 手动 | **自动**（Raft 选举） |
| **数据一致性** | 主从异步/同步 | **多数派确认**，更强 |
| **节点数** | 1 主 N 从 | 至少 **3 个**（Raft 需多数派） |
| **代价** | 简单 | 至少 3 节点、写入需多数派确认，成本更高 |

> **面试点**：DLedger 用 Raft 让 CommitLog 本身具备多副本一致性和自动选主能力，是 RocketMQ 实现**金融级高可用**的方案，代价是至少 3 节点起步。

## 五、RocketMQ vs Kafka（高频对比）

| 维度 | RocketMQ | Kafka |
|:---|:---|:---|
| **存储** | 单 CommitLog 顺序写，海量 Topic 稳定 | 每分区一文件，分区多时退化随机写 |
| **消息类型** | 顺序/延迟/事务消息**完善** | 事务较弱，无延迟消息（需额外实现） |
| **吞吐** | 十万级 | **百万级**（更高） |
| **延迟** | 低（ms 级） | 低 |
| **适用场景** | 业务消息（订单、事务）、金融 | 日志采集、大数据流处理 |

> 一句话选型：**业务/事务消息选 RocketMQ，日志/大数据吞吐选 Kafka**。

## 六、易错点

| 易错点 | 说明 |
|:---|:---|
| **消息绝对不会丢** | 需发送重试 + 同步刷盘 + 同步复制 + 消费成功才提交 offset，全链路配合 |
| **RocketMQ 保证不重复** | 只保证 at least once，重复需业务幂等 |
| **先提交 offset 再消费** | 必须先消费成功再提交 offset，否则丢消息 |
| **消费者越多消费越快** | 消费者数 ≤ 队列数，超出部分空闲 |
| **传统主从自动切换** | 传统主从**不能自动切换**，DLedger 才能自动选主 |
| **DLedger 用 2 个节点** | Raft 需多数派，至少 **3 个**节点 |

---

## 七、一句话总结

RocketMQ 可靠性全链路：**不丢**靠「发送重试 + 同步刷盘 + 同步复制 + 消费成功才提交 offset」三段防护；**不重复**做不到（只保证 at least once），靠消费端**幂等**（唯一键去重表 / Redis setnx / 状态机）兜底；**消息堆积**先扩队列再扩消费者（消费者数 ≤ 队列数）或提并发/批量/临时转存；**高可用**传统主从不能自动切换，**DLedger 模式**用 Raft 多数派确认 + 自动选主实现金融级高可用（至少 3 节点）。
