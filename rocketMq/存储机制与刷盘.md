# RocketMQ 存储机制与刷盘面试题

RocketMQ 单机能扛 **10 万级 TPS**，核心秘密全在存储设计：**顺序写 CommitLog + mmap 零拷贝 + 页缓存 + 异步刷盘**。这是「RocketMQ 为什么快」的标准答案，也是与 Kafka 对比的高频考点。

---

## 一、三大核心存储文件

| 文件 | 作用 | 类比 |
|:---|:---|:---|
| **CommitLog** | **所有消息**顺序写入的物理文件（不区分 Topic） | 流水账总账本 |
| **ConsumeQueue** | 消费队列的**逻辑索引**，指向 CommitLog 中的消息 | 目录/索引卡片 |
| **IndexFile** | 按 Message Key / 时间的**哈希索引**，用于消息查询 | 字典的拼音索引 |

### 三者关系

```
Producer 发消息
   │
   ▼
① 消息统一顺序追加到 CommitLog（单机所有 Topic 共用，顺序写）
   │   每个文件默认 1GB，写满换下一个，文件名=起始偏移量
   │
   ▼（异步分发线程 ReputMessageService）
② 为每条消息在对应 ConsumeQueue 写一条索引（20 字节）
   ConsumeQueue 项 = [CommitLog offset(8) + msgSize(4) + tagHashCode(8)]
   │
   ▼
③ 若消息带 Key，在 IndexFile 建哈希索引，支持按 Key 查询
```

**消费时的读取路径**：

```
Consumer 拉消息
  → 先读 ConsumeQueue 拿到 CommitLog 的 offset（顺序读小文件，快）
  → 再按 offset 去 CommitLog 读实际消息内容
```

## 二、为什么 CommitLog 不按 Topic 分开存？

这是 RocketMQ 与 **Kafka 最大的设计差异**：

| 对比 | Kafka | RocketMQ |
|:---|:---|:---|
| **存储粒度** | 每个 Partition 一个文件 | **全部消息写一个 CommitLog** |
| **写入方式** | 分区多时变成**多文件随机写** | 始终**单文件顺序写** |
| **Topic/分区多时** | 分区一多，磁盘退化为随机写，性能骤降 | 不受 Topic/队列数量影响，始终顺序写 |

> **核心原因**：把所有消息集中到一个 CommitLog **顺序写**，无论多少 Topic、多少队列，磁盘 IO 始终是**顺序写**（磁盘顺序写速度接近内存）。代价是消费时要多一层 ConsumeQueue 索引跳转，但索引文件小、可缓存，得大于失。所以 RocketMQ 在**海量 Topic** 场景下比 Kafka 更稳。

## 三、mmap 与零拷贝

RocketMQ 用 **mmap（内存映射文件）** 实现零拷贝，减少数据拷贝次数和用户态/内核态切换。

### 传统 IO vs mmap

```
传统读文件（4 次拷贝 + 4 次上下文切换）：
  磁盘 → 内核页缓存 → 用户缓冲区 → Socket 缓冲区 → 网卡

mmap（减少一次拷贝）：
  把文件直接映射到进程虚拟内存，读写内存即读写文件
  磁盘 → 内核页缓存(与用户空间共享映射) → Socket 缓冲区 → 网卡
```

| 技术 | 说明 | RocketMQ 用途 |
|:---|:---|:---|
| **mmap** | 文件映射到内存，读写文件像读写内存，省一次内核→用户拷贝 | CommitLog、ConsumeQueue 读写 |
| **页缓存（PageCache）** | 操作系统对文件的内存缓存，读写先走 PageCache | 消息读写都命中 PageCache 时极快 |

> **mmap 的限制**：单次映射文件大小有限（这也是 CommitLog 定为 **1GB** 一个文件的原因之一），且 mmap 首次访问会触发缺页中断。RocketMQ 用**文件预热（warmup）**：启动时给每个 page 写个 0，提前把文件加载进 PageCache，避免消费时缺页抖动。

## 四、刷盘机制（Flush）

消息写入先到 **PageCache**（内存），何时真正落盘由刷盘策略决定：

| 刷盘方式 | 说明 | 可靠性 | 性能 |
|:---|:---|:---|:---|
| **同步刷盘（SYNC_FLUSH）** | 消息写入后**立即刷盘**，刷完才返回成功 | 高（不丢） | 低 |
| **异步刷盘（ASYNC_FLUSH，默认）** | 消息先写 PageCache 就返回，后台线程批量刷盘 | 中（宕机可能丢） | 高 |

```
同步刷盘：写 PageCache → 强制 flush 到磁盘 → 返回 ack   （金融级，慢）
异步刷盘：写 PageCache → 立即返回 ack → 后台定时 flush   （默认，快）
```

> **权衡**：异步刷盘性能高但机器**断电/宕机**时 PageCache 中未刷盘的消息会丢；同步刷盘保证不丢但吞吐低。金融支付类用同步刷盘，一般业务用异步刷盘 + 主从复制兜底。

---

## 五、过期文件清理

CommitLog 会不断增长，RocketMQ 定时清理过期文件：

- 默认消息保留 **72 小时**，过期文件删除；
- 触发条件：到达清理时间点（默认凌晨 4 点）、磁盘使用率超阈值（默认 75%）；
- **按文件整体删除**（一个 1GB 文件），不是删单条消息——顺序存储的必然选择。

## 六、易错点

| 易错点 | 说明 |
|:---|:---|
| **CommitLog 按 Topic 分文件** | 所有 Topic 消息写**同一个** CommitLog，靠顺序写保证性能 |
| **消费直接读 CommitLog** | 先读 ConsumeQueue 索引拿 offset，再读 CommitLog |
| **mmap 是真正零拷贝** | mmap 减少一次拷贝，真正的 sendfile 零拷贝是另一回事；RocketMQ 主要用 mmap |
| **默认同步刷盘** | 默认是**异步刷盘**（性能优先），同步刷盘需手动配置 |
| **异步刷盘一定不丢** | 异步刷盘宕机会丢 PageCache 未落盘的消息，靠主从复制降低风险 |
| **ConsumeQueue 存消息体** | 只存索引（offset + size + tagHash 共 20 字节），消息体在 CommitLog |

---

## 七、一句话总结

RocketMQ 高性能存储：所有消息顺序追加写入**同一个 CommitLog**（1GB/文件，不按 Topic 分，磁盘始终顺序写，海量 Topic 下比 Kafka 稳），异步为每条消息在 **ConsumeQueue** 建 20 字节索引、按 Key 在 **IndexFile** 建哈希索引；用 **mmap + PageCache** 减少拷贝（启动预热避免缺页）；刷盘分**同步**（不丢慢）和**异步**（默认快，宕机可能丢），配合主从复制兜底。
