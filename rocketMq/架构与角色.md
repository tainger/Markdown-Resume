# RocketMQ 架构与角色面试题

RocketMQ 是阿里开源、后捐给 Apache 的分布式消息中间件，主打**高吞吐、高可用、金融级可靠**。它的整体架构由四大角色组成，理解这四个角色的职责与交互是所有面试题的基础。

---

## 一、四大核心角色

| 角色 | 职责 | 类比 |
|:---|:---|:---|
| **NameServer** | 轻量级注册中心，管理 Broker 路由信息 | 通讯录 / DNS |
| **Broker** | 消息存储与转发的核心，负责收发消息、持久化 | 邮局 |
| **Producer** | 消息生产者，发送消息到 Broker | 寄信人 |
| **Consumer** | 消息消费者，从 Broker 拉取消息消费 | 收信人 |

### 交互流程

```
1. Broker 启动 → 向所有 NameServer 注册自己（Topic、队列、地址等路由信息）
2. Broker 每 30s 向 NameServer 发心跳；NameServer 每 10s 扫描，120s 无心跳则剔除
3. Producer/Consumer 启动 → 从 NameServer 拉取 Topic 路由（每 30s 更新一次）
4. Producer 按路由直连 Broker 发消息；Consumer 按路由直连 Broker 拉消息
```

> **关键点**：NameServer 只做路由发现，**不参与消息收发**。真正的数据流是 Producer/Consumer 与 Broker 直连，NameServer 不在数据链路上，所以它可以做得非常轻量。

---

## 二、NameServer 为什么不用 ZooKeeper？

早期 Kafka 用 ZooKeeper 做元数据管理，RocketMQ 却自研了 NameServer。核心原因是**去中心化、够用就好**：

| 对比点 | ZooKeeper | NameServer |
|:---|:---|:---|
| **一致性** | 强一致（ZAB 协议，有 Leader 选举） | **弱一致 / 最终一致**（各节点独立，不互相通信） |
| **节点关系** | 集群内节点互相同步 | **节点间完全独立**，无通信 |
| **复杂度** | 重，需维护选举、脑裂 | 极轻量，无状态 |
| **CAP 取向** | CP | **AP**（可用性优先） |

- **NameServer 各节点互不通信**：Broker 要向**每一个** NameServer 都注册。这样即使部分 NameServer 挂了，其他节点仍有全量路由。
- **为什么弱一致就够**：路由信息短暂不一致（如某 Broker 刚下线还没被剔除）问题不大——Producer 发送失败会自动重试其他队列/Broker，容错机制兜底。用强一致的 ZK 反而是过度设计，还引入选举、脑裂等复杂度。

## 三、Topic、Queue（MessageQueue）与 Broker 的关系

这是 RocketMQ 数据模型的核心，也是**高吞吐**和**顺序消息**的基础。

```
Topic（逻辑概念，一类消息）
  └── 分布在多个 Broker 上
        └── 每个 Broker 上有多个 MessageQueue（队列，物理分片）

例：Topic "OrderTopic" 有 8 个队列，分布在 2 个 Broker 上（每个 Broker 4 个队列）
```

| 概念 | 说明 |
|:---|:---|
| **Topic** | 消息的逻辑分类，生产/消费的基本单位（一级分类） |
| **Tag** | Topic 下的二级分类，消费时可按 Tag 过滤 |
| **MessageQueue** | Topic 的物理分片，一个 Topic 分成多个 Queue 分布到多 Broker，是**并行消费**和**顺序消息**的关键 |

- **为什么分队列**：多个 Queue 分布在多个 Broker，Producer 轮询写入不同 Queue、Consumer 并行消费不同 Queue → 突破单机瓶颈，实现**水平扩展和高吞吐**。
- **队列与顺序**：单个 Queue 内消息**先进先出有序**，跨 Queue 无序。所以「顺序消息」要把同一业务的消息发到同一个 Queue（见[消息类型与发送.md](消息类型与发送.md)）。

## 四、Broker 的主从架构（简述）

Broker 分 **Master** 和 **Slave**，用 `BrokerName` 相同、`BrokerId` 区分（`0` 为 Master，`>0` 为 Slave）：

- Master 负责读写，Slave 只负责读（分担读压力）+ 数据备份；
- Master 挂了，消息仍可从 Slave 读，但**默认不能自动切换**（老版本），需 DLedger 模式实现自动主从切换。
- 详见[可靠性与高可用.md](可靠性与高可用.md)。

## 五、易错点

| 易错点 | 说明 |
|:---|:---|
| **NameServer 参与消息转发** | 不参与，只做路由注册与发现，数据流是 Producer/Consumer 直连 Broker |
| **NameServer 节点互相同步** | 各节点**完全独立不通信**，Broker 向每个 NameServer 都注册 |
| **RocketMQ 依赖 ZooKeeper** | 早期版本不依赖，自研 NameServer；ZK 是 Kafka 老版本的方案 |
| **一个 Topic 只在一个 Broker** | Topic 的队列可分布在多个 Broker 上，实现负载均衡 |
| **Queue 跨队列也有序** | 只有**单个 Queue 内**有序，全局无序 |
| **Broker 挂了消息就丢** | 有主从备份 + 刷盘机制，配置得当可保证不丢 |

---

## 六、一句话总结

RocketMQ 四大角色：**NameServer** 是轻量无状态的路由注册中心（各节点独立不通信、AP 弱一致，故不用 ZK），**Broker** 是消息存储转发核心（分 Master/Slave），**Producer/Consumer** 从 NameServer 拿路由后**直连 Broker** 收发消息。数据模型上，**Topic** 逻辑分类 → 拆成多个 **MessageQueue** 物理分片 → 分布到多 Broker，靠分队列实现高吞吐与顺序消息。
