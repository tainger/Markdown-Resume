# RocketMQ 消息类型与发送面试题

RocketMQ 提供了丰富的消息类型，覆盖绝大多数业务场景。面试高频：**顺序消息、延迟消息、事务消息**这三类，尤其是事务消息的两阶段提交。

---

## 一、消息类型全景

| 类型 | 说明 | 典型场景 |
|:---|:---|:---|
| **普通消息** | 无序、并发发送，吞吐最高 | 日志、通知 |
| **顺序消息** | 保证同一分区内先进先出 | 订单状态流转（下单→付款→发货） |
| **延迟消息** | 消息延迟一段时间后才可被消费 | 订单超时未支付自动取消 |
| **事务消息** | 保证本地事务与消息发送的最终一致 | 分布式事务（下单扣库存） |
| **批量消息** | 一次发送多条，减少网络开销 | 批量数据同步 |

---

## 二、三种发送方式

| 方式 | 说明 | 可靠性 | 性能 |
|:---|:---|:---|:---|
| **同步（sync）** | 发完等 Broker 返回确认 | 高 | 低 |
| **异步（async）** | 发完不等，通过回调拿结果 | 中 | 高 |
| **单向（oneway）** | 只管发，不关心结果 | 低（可能丢） | 最高 |

> 选型：重要消息（订单）用**同步**；实时性高但可容忍偶尔失败用**异步**；日志类海量场景用**单向**。

---

## 三、顺序消息

### 全局顺序 vs 分区顺序

| 类型 | 实现 | 吞吐 |
|:---|:---|:---|
| **全局顺序** | Topic 只设 **1 个队列**，所有消息串行 | 极低（无并发） |
| **分区顺序** | 同一业务 key 的消息发到**同一队列** | 高（多队列并行） |

实际几乎都用**分区顺序**：例如同一订单的所有消息发到同一个 Queue，不同订单散落到不同 Queue 并行。

### 实现原理

顺序性需要**发送端 + 存储 + 消费端**三方配合：

```
1. 发送端：用 MessageQueueSelector，按订单ID % 队列数 选队列
           → 保证同一订单消息进同一 Queue（Queue 内 FIFO）
2. 存储：  单个 Queue 内消息顺序存储、顺序消费
3. 消费端：用 MessageListenerOrderly（顺序消费监听器）
           → 对同一 Queue 加锁，保证单线程串行消费
```

```java
// 发送：同一订单ID路由到同一队列
producer.send(msg, new MessageQueueSelector() {
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        int index = (int) ((long) arg % mqs.size());   // arg = 订单ID
        return mqs.get(index);
    }
}, orderId);

// 消费：顺序消费监听器（并发消费会破坏顺序）
consumer.registerMessageListener(new MessageListenerOrderly() { ... });
```

> **顺序消息的坑**：① 若某条消息消费失败，为保证顺序**不能跳过**，会阻塞后面消息（返回 `SUSPEND_CURRENT_QUEUE_A_MOMENT` 稍后重试）；② 队列扩容会打破原有顺序，顺序 Topic 应避免动态扩容。

## 四、延迟消息

### 实现原理（固定延迟级别）

开源版 RocketMQ **不支持任意时间延迟**，只支持 **18 个固定延迟级别**：

```
1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
（level 1 ~ 18）
```

```java
msg.setDelayTimeLevel(3);   // level 3 = 延迟 10 秒
```

**内部机制**：

```
1. 发送延迟消息 → Broker 发现有 delayLevel，不直接投递到目标 Topic
2. 而是暂存到内部 Topic「SCHEDULE_TOPIC_XXXX」，按 level 分成 18 个队列
3. 定时任务扫描到期消息 → 重新投递回原目标 Topic → 消费者才可见
```

> RocketMQ 5.x 已支持**任意精度的定时消息**（基于时间轮）。面试问「为什么只有固定级别」答：早期用固定级别是为了避免为每条消息单独排序的开销，18 级队列各自有序，扫描成本低。

## 五、事务消息（重点）

解决「**本地事务**与**消息发送**」的原子性问题。经典场景：下单后要扣库存，本地下单成功但消息发失败，或消息发了本地却回滚 → 数据不一致。

### 两阶段提交 + 事务回查

```
【阶段一】发送 half（半）消息
  1. Producer 发送 half 消息到 Broker
  2. half 消息对消费者「不可见」（存到内部 Topic RMQ_SYS_TRANS_HALF_TOPIC）
  3. Broker 返回 ack，Producer 收到后执行本地事务

【阶段二】提交或回滚
  4. 本地事务成功 → Producer 发 COMMIT → Broker 把 half 消息转为正常消息，消费者可见
     本地事务失败 → Producer 发 ROLLBACK → Broker 丢弃 half 消息

【事务回查】兜底（关键）
  5. 若 Producer 迟迟没发 commit/rollback（如宕机）
     → Broker 定时回查 Producer 的本地事务状态（checkLocalTransaction）
     → 根据回查结果决定提交或回滚
```

```
Producer                    Broker                     Consumer
   │──① half 消息──────────────▶│  (存 half，不可见)
   │◀─② ack────────────────────│
   │ ③ 执行本地事务             │
   │──④ commit/rollback────────▶│  commit → 转正常消息 ─▶│ (可见)
   │                            │  rollback → 丢弃
   │◀─⑤ 回查本地事务状态────────│  (④ 超时未达时的兜底)
```

> **事务消息保证的是最终一致**，不是强一致。它确保「本地事务成功 ⟺ 消息最终被消费」，中间有短暂延迟（回查间隔）。

## 六、消息过滤：Tag vs SQL92

| 方式 | 说明 | 过滤位置 |
|:---|:---|:---|
| **Tag 过滤** | Consumer 订阅时指定 Tag，最常用 | Broker 端按 Tag 的 hashcode 粗筛 + Consumer 端精筛 |
| **SQL92 过滤** | 按消息属性写 SQL 表达式（如 `age > 18`） | Broker 端，更灵活但需开启配置 |

```java
consumer.subscribe("OrderTopic", "TagA || TagB");        // Tag 过滤
consumer.subscribe("OrderTopic", MessageSelector.bySql("age > 18"));  // SQL 过滤
```

## 七、易错点

| 易错点 | 说明 |
|:---|:---|
| **顺序消息用并发消费** | 必须用 `MessageListenerOrderly`，用并发监听器会乱序 |
| **全局顺序高吞吐** | 全局顺序只能 1 个队列，吞吐极低，业务几乎都用分区顺序 |
| **延迟消息支持任意时间** | 开源 4.x 只有 18 个固定级别；5.x 才支持任意精度定时 |
| **事务消息是强一致** | 是**最终一致**，靠事务回查兜底 |
| **half 消息消费者能看到** | half 消息对消费者不可见，commit 后才可见 |
| **Tag 过滤在 Consumer 端完成** | Broker 先按 Tag hashcode 粗筛（减少网络传输），Consumer 端再精确比对 |

---

## 八、一句话总结

RocketMQ 消息类型：**顺序消息**靠「同 key 发同队列 + 顺序消费监听器」实现分区有序；**延迟消息**开源版只支持 18 个固定级别（先存内部 SCHEDULE Topic，定时投递回原 Topic），5.x 支持任意定时；**事务消息**用「half 消息（不可见）→ 本地事务 → commit/rollback → 事务回查兜底」两阶段提交保证**最终一致**；过滤用 **Tag**（最常用）或 **SQL92**。
