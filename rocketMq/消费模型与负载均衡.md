# RocketMQ 消费模型与负载均衡面试题

消费端是 RocketMQ 面试的重灾区：**推拉模式、消费者组、集群/广播、Rebalance、offset 管理**环环相扣。理解这些才能答好「消息堆积怎么办」「重复消费怎么来的」。

---

## 一、Push vs Pull

RocketMQ 提供两种消费方式，但**本质都是 Pull**：

| 模式 | 说明 | 实时性 |
|:---|:---|:---|
| **Push（推）** | Consumer 注册监听器，消息到了「推」给消费者 | 高 |
| **Pull（拉）** | Consumer 主动调用接口拉取，自己控制节奏 | 由业务控制 |

> **关键点**：Push 模式底层其实是 **长轮询（Long Polling）** 实现的「伪推」——Consumer 发起拉取请求，若 Broker 没有新消息，**不立即返回**，而是 hold 住请求（默认 15s），期间有新消息就立即返回。这样既有 Push 的实时性，又避免了 Pull 频繁空轮询的开销。

---

## 二、消费者组（Consumer Group）

同一个 Consumer Group 下的多个消费者实例，**共同分担**一个 Topic 的消费。这是消费端扩展和高可用的基础。

```
Topic（8 个队列） + ConsumerGroup（4 个消费者实例）
  → 每个消费者分到 2 个队列（负载均衡）
  → 某个消费者挂了 → 触发 Rebalance，队列重新分配给存活的消费者
```

---

## 三、集群消费 vs 广播消费

| 模式 | 说明 | 一条消息被消费几次 | offset 存储 |
|:---|:---|:---|:---|
| **集群消费（默认）** | 组内消费者**分摊**消息 | 组内**只消费一次** | **Broker 端** |
| **广播消费** | 组内**每个**消费者都收全量消息 | 每个实例都消费一次 | **Consumer 本地** |

```java
consumer.setMessageModel(MessageModel.CLUSTERING);  // 集群（默认）
consumer.setMessageModel(MessageModel.BROADCASTING); // 广播
```

- **集群消费**：适合分布式任务分摊，一条订单只需处理一次。offset 存 Broker，实例重启不影响。
- **广播消费**：适合每个实例都要更新的场景（如本地缓存刷新）。offset 存本地文件，重启后可能重复消费。

---

## 四、Rebalance（重平衡）

当消费者组内**实例数量变化**（新增/下线）或 **Topic 队列数变化**时，触发队列的重新分配。

### 触发时机

- 消费者实例上线 / 下线（宕机、扩缩容）；
- Topic 的队列数量变化；
- 消费者订阅的 Topic 变化。

### 分配策略（AllocateMessageQueueStrategy）

| 策略 | 说明 |
|:---|:---|
| **平均分配（默认）** | 队列数 ÷ 消费者数，按序均分 |
| **环形平均** | 环形轮流分配 |
| **一致性哈希** | 队列变动时影响范围小 |
| **机房就近** | 按机房 IDC 分配，减少跨机房 |

### Rebalance 的问题

```
Rebalance 期间会有短暂的「消费暂停」和「重复消费」：
  - 队列从消费者A转移到消费者B时
  - A 可能已消费但 offset 未提交 → B 重新拉取 → 重复消费
```

> **面试点**：Rebalance 是**重复消费的重要来源之一**，所以消费端必须做**幂等**（见[可靠性与高可用.md](可靠性与高可用.md)）。频繁 Rebalance 会导致消费抖动，应避免消费者频繁上下线。

## 五、Offset（消费位点）管理

offset 记录「消费到哪了」，是消息不重不漏的关键。

| 概念 | 说明 |
|:---|:---|
| **消费进度 offset** | 每个 Queue 一个，记录已消费到的位置 |
| **集群模式** | offset 存 **Broker**（`consumerOffset.json`），多实例共享 |
| **广播模式** | offset 存 **Consumer 本地**（`offsets.json`） |

### offset 提交时机（重复消费根源）

```
Push 模式下，消费成功后才提交 offset：
  1. Consumer 拉一批消息
  2. 消费成功 → 提交 offset（并非每条都立即提交，是定时批量提交，默认 5s）
  3. 若消费到一半宕机 → offset 未提交 → 重启后从上次 offset 重新拉 → 重复消费
```

> **为什么会重复消费**：offset 是**批量异步提交**的，宕机/Rebalance 时未提交的 offset 会导致消息被重新消费。RocketMQ 保证 **at least once（至少一次）**，不保证 exactly once，所以业务必须**幂等**。

---

## 六、消费重试与死信队列

集群模式下消费失败会**自动重试**：

```
消费失败（返回 RECONSUME_LATER 或抛异常）
  → 消息进入「重试队列」（%RETRY%ConsumerGroup）
  → 按延迟级别递增重试（10s, 30s, 1m ... 最多 16 次）
  → 16 次仍失败 → 进入「死信队列」（%DLQ%ConsumerGroup）
```

| 队列 | 命名 | 说明 |
|:---|:---|:---|
| **重试队列** | `%RETRY%消费者组名` | 每个消费者组一个，失败消息暂存重试 |
| **死信队列（DLQ）** | `%DLQ%消费者组名` | 重试 16 次仍失败的消息，需人工介入 |

> **注意**：① 广播模式**不重试**（失败就跳过）；② 顺序消息失败不进重试队列，而是阻塞当前队列稍后重试（避免乱序）。

## 七、易错点

| 易错点 | 说明 |
|:---|:---|
| **Push 是服务端主动推** | 底层是**长轮询**实现的伪推，本质仍是 Consumer 拉 |
| **一条消息组内消费多次** | 集群模式组内**只消费一次**；广播模式才每实例一次 |
| **集群模式 offset 存本地** | 集群模式存 **Broker**；广播模式才存本地 |
| **RocketMQ 保证 exactly once** | 只保证 **at least once**，重复消费需业务幂等 |
| **Rebalance 不影响消费** | Rebalance 期间有短暂暂停 + 可能重复消费 |
| **重试队列是全局一个** | 每个**消费者组**一个重试队列，默认重试 16 次进 DLQ |

---

## 八、一句话总结

RocketMQ 消费端：Push 模式底层是**长轮询伪推**；同一 **Consumer Group** 分摊消费，**集群模式**组内只消费一次（offset 存 Broker）、**广播模式**每实例都消费（offset 存本地）；实例增减触发 **Rebalance** 重新分配队列，期间可能重复消费；offset **批量异步提交**导致只能保证 **at least once**，业务需幂等；消费失败自动重试（`%RETRY%`），重试 16 次进**死信队列**（`%DLQ%`）。
