# 一致性协议

> **P7 面试核心**：CAP 不是选择题而是 trade-off；Raft 是 P7 系统设计「集群选主/高可用」的基础。背流程 + 能讲清「为什么注册中心选 AP、分布式锁选 CP」= 过关。

---

## 一、CAP 定理（分布式绕不开的基石）

### 1.1 定义

分布式系统中，**三个指标最多只能同时满足两个，不可能三个都要**：

| 指标 | 全称 | 含义 | 人话解释 |
|:---:|:---|:---|:---|
| **C** | Consistency（一致性） | 所有节点在同一时刻看到**相同的数据** | 写了之后马上读，任何节点都能读到刚写的新值 |
| **A** | Availability（可用性） | 每个请求都能收到**非错误的响应**（不保证是最新值）| 集群任何时候能正常响应请求，不会超时/拒绝 |
| **P** | Partition Tolerance（分区容错性）| 集群出现**网络分区**（节点间通信断了）时，仍能对外服务 | 网络断了分成几伙，各伙还能单独工作，不整个挂 |

### 1.2 为什么「3 选 2」是骗人的 —— 实际是 CP / AP 二选一

```
真实世界的网络：
  机房 A ────(光缆断了/路由器挂了/防火墙抽风)──── 机房 B
  ┌─────────┐                                  ┌─────────┐
  │ 节点1~5 │                                  │ 节点6~10│
  └─────────┘                                  └─────────┘
       ▲                                            ▲
       └──────── 中间断了，两边互相收不到消息 ────────┘
               → 这就是网络分区（Partition）
```

**关键点：P 在分布式系统中是「必然存在」的客观现实**，不是你选不选的问题。只要跨机器跨机房，网络就可能出问题。所以真正的选择是：

- **保留 C，舍弃 A → CP 系统**：网络分区时，为了保证数据一致，**拒绝对外服务**（返回错误/超时）
- **保留 A，舍弃 C → AP 系统**：网络分区时，继续对外服务，**允许暂时返回旧数据**（最终一致）

### 1.3 CP vs AP 选型对比表

| 维度 | CP（强一致） | AP（高可用） |
|:---|:---|:---|
| **网络分区时表现** | 少数派节点不响应（只读 or 直接报错），多数派维持一致 | 两边各自继续工作，可能返回不一致的旧数据 |
| **牺牲什么** | 可用性（服务可能短暂不可用） | 一致性（短暂不一致，最终一致） |
| **典型场景** | 分布式锁、分布式事务协调者、配置中心、数据库集群 | 服务注册与发现、缓存集群、消息队列、搜索引擎 |
| **代表系统** | Zookeeper、Etcd、Consul（注册默认）、HBase | Nacos（默认 AP）、Eureka、Cassandra、Redis Cluster |
| **一句话口诀** | 「宁可不可用，也不能错」 | 「宁可返回旧的，也不能不返回」 |

### 1.4 P7 高频场景题：为什么注册中心默认选 AP（Nacos/Eureka）

```
注册中心挂了/分区了，影响什么？
  ├── CP（ZK 模式）：注册中心不可用 → 服务没法注册/发现 → 所有服务互相找不到 → 全站雪崩
  │                        ↑ 这代价太大了，注册信息 1 分钟前的旧数据也能凑合用啊！
  │
  └── AP（Nacos/Eureka）：注册中心分区 → 两边各自返回旧注册信息 → 服务发现还能用
                            只是可能把请求发到已经下线的旧实例 → 重试 + 超时容错就兜住了
```

> **核心结论**：注册中心「**有旧信息（可用）比没信息（全挂）好一万倍**」→ 铁定选 AP。Nacos 默认 AP 就是这个道理，Eureka 纯 AP，ZK 当注册中心是 CP（所以 Dubbo 3.0 之后不推荐用 ZK 做注册中心了，推荐 Nacos）。

## 二、BASE 理论（CAP 的务实妥协）

BASE 是对 CAP 中「一致性和可用性不可兼得」的**工程化答案**——大多数业务不追求「每时每刻强一致」，而愿意接受「**最终一致**」来换取高可用。

| 缩写 | 全称 | 含义 |
|:---:|:---|:---|
| **BA** | Basically Available（基本可用） | 分布式系统出故障时，允许损失**部分可用性**（比如降级、响应变慢），但保证核心功能可用 |
| **S** | Soft State（软状态） | 允许系统存在**中间态**（比如 Saga 的正向流程走了一半），这个中间态不影响系统整体可用性 |
| **E** | Eventually Consistent（最终一致） | 经过一段时间后，所有节点数据最终会达成一致（不需要实时强一致）|

> **BASE vs ACID 对比**：ACID 是数据库强一致的保守派（宁慢不可错），BASE 是分布式高可用的激进派（宁错不可挂，通过补偿最终拉齐）。两者没有对错，只有场景匹配。

## 四、Raft 协议（⭐⭐⭐⭐⭐ P7 必考）

Raft = Paxos 的「可理解、可实现」简化版，把复杂的一致性问题拆成 **3 个独立子问题**：**Leader 选举 → 日志复制 → 安全性保障**。

### 4.1 Raft 三角色 & 生命周期

```
        超时没收到 Leader 心跳
   Follower ──────────────────────────▶ Candidate
      ▲                                   │
      │                                   │ 投票给它自己
      │                                   │ + 向其他节点求票
      │  收到选举结果（自己败选）          │
      │◀──────────────────────────────────┤
      │                                   │
      │                                   │ 拿到 >半数选票
      │          成为新 Leader            │
      └───────────────────────────────────┘
                        │
                        ▼
                    Leader（处理所有读写请求，
                           靠心跳维持权威）
```

| 角色 | 行为 |
|:---|:---|
| **Follower（追随者）** | 被动接收 Leader 的日志复制请求和心跳；超时没心跳就变身 Candidate |
| **Candidate（候选人）** | 选举中间态：自增任期 term、投自己一票、并发发 RequestVote RPC 给所有节点 |
| **Leader（领袖）** | 唯一处理写请求的角色；向所有 Follower 发心跳（空 AppendEntries）和日志复制请求 |

> **选举关键：随机超时打散冲突**。每个 Follower 超时时间是**随机的**（150~300ms），谁先超时谁先当 Candidate 去拉票，避免多个 Candidate 同时抢票导致死锁。

### 4.2 核心概念

| 概念 | 含义 |
|:---|:---|
| **Term（任期号）** | 逻辑时钟，单调递增；每个 Leader 对应一个 term；新选举产生 term+1；用来鉴别「谁的信息更新」 |
| **Log Index（日志索引）** | 每条日志在节点日志数组中的位置编号，单调递增 |
| **已提交（Committed）** | Leader 把日志复制到 **>半数节点**后就标记「已提交」，提交的日志保证不丢且最终会被所有节点执行 |
| **已应用（Applied）** | 节点把日志真正写到状态机（比如 DB 更新）的过程，提交后异步应用 |

### 4.3 流程一：Leader 选举 ASCII

```
初始态：3 节点都是 Follower，term=0

  Node-A(150ms) 先超时 → 变 Candidate，term=1，投自己，发 RequestVote 给 B、C
     │
     ├──▶ Node-B：A 的日志 ≥ 我本地？是 → 投 A，更新 term=1
     ├──▶ Node-C：A 的日志 ≥ 我本地？是 → 投 A，更新 term=1
     │
     └── A 拿到 3 票（A+B+C）> 半数(2) → 变 Leader term=1
         立即开始发 AppendEntries 心跳给 B、C（每 100ms 一次）

             Leader(A, term=1)
                │ 心跳/日志
        ┌───────┴───────┐
        ▼               ▼
  Follower(B)      Follower(C)

关键规则：收到 RequestVote，投票条件 = 「对方 term ≥ 我 term」 AND「对方日志 ≥ 我本地日志」
         → 保证选出来的 Leader 一定拥有「所有已提交日志」（安全性核心）
```

### 4.4 流程二：日志复制 ASCII

```
Client 写请求 → Leader(A, term=1)
                    │
                    ├── 1. 本地追加一条日志（index=5, term=1, 内容=SET X=1）
                    │
                    ├── 2. 并发发 AppendEntries(index=5) 给 B、C
                    │       │
                    │       ├──▶ Node-B：收到 → 追加日志 → 返回 OK
                    │       └──▶ Node-C：超时丢了 → 稍后 Leader 重试 AppendEntries
                    │
                    ├── 3. 等 >半数节点返回 OK（A 本地+B = 2 个 ≥ 半数 2）
                    │       → 标记日志 index=5 为「已提交 Committed」
                    │
                    ├── 4. 回应 Client：写成功！
                    │
                    └── 5. 下一次心跳时，把「提交到 index=5」通知给 B、C
                            B、C 收到后把 index=5 标记为已提交并应用到状态机
```

> 💡 **为什么「>半数」就算提交**？因为下一次选举时，只要是 >半数节点选出来的新 Leader，里面**必然有至少一个节点持有了已提交的日志**（鸽巢原理：2N+1 个节点，提交了 N+1 个；下次选举任何 N+1 个节点的集合里，至少有一个是之前提交过的那个，所以新 Leader 不会丢日志）。

### 4.5 安全性 5 条保证（面试能说 2~3 条就够）

| 规则 | 说明 |
|:---|:---|
| **选举安全** | 一个 term 内最多选 1 个 Leader（投票权一人一张，半数票才当选） |
| **Leader 只追加** | Leader 只能追加日志，不能删/改已有日志（Follower 的不一致日志由 Leader 覆盖）|
| **日志匹配** | 如果两个节点某条日志的 index 和 term 都相同 → 这条日志之前的所有日志也必然完全相同 |
| **Leader 提交完整性** | 某条日志在某个 term 提交了 → 它会出现在所有更高 term 的 Leader 日志里 |
| **状态机安全** | 如果某节点把 index=i 的日志应用到状态机了 → 其他节点不会在相同 index 应用不同日志 |

### 4.6 Raft vs Paxos（知道区别就行）

| 维度 | Paxos | Raft |
|:---|:---|:---|
| 谁更容易懂/实现 | 极难（论文出名的晦涩），工业界实现差异大 | **非常易懂**（教学友好，工业界事实标准）|
| 角色划分 | 不强制分 Leader/Follower，各节点平等协商 | 明确 Leader/Follower 分工，**一切 Leader 说了算** |
| 选主方式 | Multi-Paxos 可以有 Leader，但非必须 | **必须选 Leader**，没有 Leader 无法写 |
| 工业落地 | Chubby、Google Megastore（很少有开源完整实现） | **Etcd、Nacos CP 模式、TiKV、Redpanda、RQLite**（遍地都是）|
| 日志复制方向 | 可以互相发 | Leader → Follower 单向发 |

> 一句话：**Raft 就是 Paxos 的「工业可落地简化版」**，现在新做 CP 系统全用 Raft，没人从零写 Paxos。

## 五、ZAB 协议（ZooKeeper 用的）

ZAB = ZK Atomic Broadcast，是 **Raft 的「同期竞品」**，思路几乎一样（也是选主 + 日志复制），只是细节术语不同：

| 对比项 | Raft | ZAB（ZK） |
|:---|:---|:---|
| 选主 | Candidate 拉票 → Leader | Looking 状态 → 投票算法 → Leader |
| 日志复制 | Leader AppendEntries → Follower | Leader propose → Follower ACK → Leader commit |
| 事务编号 | (term, index) | (zxid.epoch, zxid.counter) |
| 一致性 | 最终一致（Leader 读可线性化） | 最终一致（sync 读可线性化） |

不用细扣差异，知道「**ZK 用 ZAB，和 Raft 本质一样都是「选主+过半提交」的 CP 协议**」就行。

## 六、Gossip 协议（AP 场景：谣言传播）

### 6.1 核心思想

一群节点像「**办公室传八卦**」一样，每个节点定期随机挑几个邻居，把自己知道的信息告诉对方，经过几轮后全网信息就一致了。

```
第 0 轮：  Node-A 知道「X=1」，其他不知道
           [X=1]   [X=?]   [X=?]   [X=?]   [X=?]
             A       B       C       D       E

第 1 轮：  A 随机挑 2 个，告诉 B、D
           [X=1]──▶[X=1]   [X=?]──◀[X=1]   [X=?]
             A       B       C       D       E

第 2 轮：  A/B/D 各自随机挑邻居扩散
           [X=1]   [X=1]──▶[X=1]   [X=1]──▶[X=1]
             A       B       C       D       E   ← 全知道了！
```

### 6.2 两种传播模式

| 模式 | 流程 | 收敛速度 | 网络流量 |
|:---|:---|:---:|:---:|
| **Anti-Entropy（反熵）** | 每轮节点和邻居**全量比对数据**，有差异就同步 | 慢（全量比） | 大 |
| **Rumor-Mongering（谣言 mongering）⭐** | 收到新信息的节点，随机挑 k 个邻居转发，直到所有节点都知道 | 快（指数扩散） | 小 |

### 6.3 典型应用

- **Cassandra / Redis Cluster 节点发现**：新节点加入时，通过 Gossip 全网扩散它的存在
- **Consul 服务健康状态传播**：节点健康状态变化靠 Gossip 扩散
- **IPFS / BitTorrent 节点发现**

> **Gossip 优缺点**：✅ 去中心化完全 AP，节点越多越稳；❌ 收敛速度不确定，只保证「最终一致」，不保证多久后一致。

## 七、拜占庭容错（了解概念就行）

前面的协议都有一个**默认前提（非拜占庭模型）**：「节点只会宕机/断网，不会故意作恶发假消息」。但在区块链、加密货币场景下，节点可以恶意撒谎——这时候需要拜占庭容错。

| 算法 | 容错恶意节点数 | 典型应用 |
|:---|:---:|:---|
| **PBFT（实用拜占庭容错）** | 总节点数 ≥ 3f+1 能容错 f 个恶意节点 | 联盟链（Hyperledger Fabric）|
| **PoW（工作量证明）** | 容错 51% 以下算力作恶 | 比特币、以太坊（经典） |
| **PoS（权益证明）** | 容错 1/3 以下质押作恶 | 以太坊（当前）、其他新公链 |

后端面试（非区块链方向）基本不考，知道「PBFT 需要 3f+1 节点」就够了。

## 八、一致性级别总结（从轻到重排序）

```
弱（最轻）                                                          强（最重）
 │                                                                   │
 ▼                                                                   ▼
最终一致   →   会话一致   →   读己之写   →   单调读   →   因果一致   →   线性一致（强一致）
 │             │             │            │            │               │
 ▼             ▼             ▼            ▼            ▼               ▼
Gossip         同一个会话里  写完马       同一个Client  有因果关系      就像只有单节点
Redis 副本     读最新保证    上读自己    读到的数据    的写操作        一样，写了马上
Cassandra      不读回旧值    写过的东西  不会越来越旧   顺序能被保证    任何节点都能读
                                                                   到新值
                                                                   ZK sync读
                                                                   Raft 写
```

> **99% 的后端业务只需要「最终一致」或「读己之写」**，真的需要线性一致的场景极少（分布式锁、全局唯一发号器、数据库主从复制...）。

## 九、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「CAP 三个里我可以放弃 P 选 CA」 | ❌ 错！分布式系统跨机器就一定有网络分区可能，P 是客观前提不是选项，**实际只能 CP/AP 二选一** |
| 2 | 「CP 系统任何时候都强一致」 | ❌ 错！网络分区时 CP 系统直接拒绝服务（A 没了），**只有分区恢复后**才重新回到强一致 |
| 3 | 「Raft Leader 处理读请求一定强一致」 | ❌ 错！Leader 可能是分区后的少数派旧 Leader（term 已落后），所以**线性一致读要加 ReadIndex：Leader 先确认自己仍是最新 Leader（过半心跳响应）再回数据** |
| 4 | 「Nacos 是纯 AP 没 CP」 | ❌ 错！Nacos 默认 AP（注册中心），但临时实例/持久化实例切换后，**持久化实例是 CP（Raft 协议）**，一套系统两种模式 |
| 5 | 「Gossip 会在 N 轮内收敛」 | ❌ 错！Gossip 只保证「概率上最终收敛」，**不保证确定时间收敛**，所以不能拿来当强一致同步用 |
| 6 | 「Etcd 是强一致数据库，所有读都线性一致」 | ❌ 错！Etcd 默认读是 Leader 本地读，串行化但不线性；要线性一致读得加 `--consistency=s`（ReadIndex 机制，过半确认）|

## 十、一句话总结

> 一致性的本质是「**分布式系统中，跨节点的数据什么时候对谁可见**」。CAP 告诉我们鱼和熊掌不可兼得，工程上绝大多数场景选 AP+BASE（最终一致）换取高可用，只有对「数据不能错」有执念的场景才上 CP（Raft/PBFT）。P7 面试考察的不是背 Raft 流程，而是**根据业务场景在 CP/AP 之间做 trade-off，并能讲清 Nacos 为什么默认选 AP 这类真实决策背后的逻辑**。
