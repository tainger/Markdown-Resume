# 分布式事务

> **P7 面试核心**：不仅背 2PC/TCC/Saga 是什么，更要能讲「**你的项目里选了哪种方案，为什么，踩过什么坑**」。选型对比表 + 适用场景 = P7 过关钥匙。

---

## 一、为什么需要分布式事务？本地事务为什么不行？

**本地事务**（MySQL `@Transactional`）只能管「一个服务 + 一个数据源」，一旦业务跨了服务、跨了库（微服务常态），本地事务就失效了：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  订单服务     │────▶│  库存服务     │────▶│  支付服务     │
│  DB-Order    │     │  DB-Stock    │     │  DB-Pay      │
└──────────────┘     └──────────────┘     └──────────────┘
       本地事务管得住      ↑     ↑      本地事务管不住
                           └─────┘
                        跨服务/跨库 → 需要分布式事务
```

**核心矛盾**：多个独立数据源，各自 ACID 各自为政，怎么保证「**要么全成功，要么全回滚**」？

## 二、6 种分布式事务方案全景对比

| # | 方案 | 核心思想 | 一致性 | 侵入性 | 性能 | 适用场景 |
|:---:|:---|:---|:---:|:---:|:---:|:---|
| 1 | **2PC（两阶段提交）** | TM 协调者分 Prepare → Commit 两步，全部 Prepare 好才 Commit | 强一致（CP） | 低（XA 协议） | 差（阻塞+锁） | 传统银行/对一致性极致要求、并发不高 |
| 2 | **3PC（三阶段提交）** | 2PC 加 CanPreCommit 阶段 + 超时自动 Commit 决议 | 强一致（仍可能不一致） | 低 | 更差（多一轮 RTT） | 几乎没人用（理论价值 > 落地价值） |
| 3 | **TCC（Try-Confirm-Cancel）** | 业务层拆三步：Try 预留资源 → Confirm 确认提交 → Cancel 回滚补偿 | 最终一致 | 极高（每接口写 3 个方法） | 好（无长锁） | 核心资金/库存/扣减场景、性能敏感 |
| 4 | **Saga（长事务）** | 正向调用 + 每步配「反向补偿操作」，失败按顺序逆序回滚 | 最终一致 | 中（每步写补偿） | 好（无锁） | 长链路跨多服务业务流（出行/电商下单全链路）、允许中间态 |
| 5 | **本地消息表（可靠事件）⭐ 首选 | 本地事务 = 业务更新 + 插事件消息表 → MQ 投递 → 消费方幂等处理 | 最终一致 | 低（通用框架） | 好（本地事务） | 90% 的业务场景都适用；**生产首选方案** |
| 6 | **最大努力通知** | MQ 发通知 + 定时查 + 多级别重试退避，消费方接不到就算了 | 弱一致（允许丢） | 低 | 好 | 短信/邮件/微信通知等非核心副产品场景 |

> 💡 **选型速记口诀**：强一致 2PC、性能+核心 TCC、长链路 Saga、**通用首选本地消息表**、非核心通知最大努力。

## 三、方案一：2PC（两阶段提交）/ XA

### 3.1 流程（ASCII 图）

```
阶段一：Prepare（投票）
  TM(协调者)          RM-库A          RM-库B
      │   Prepare?       │                │
      │─────────────────▶│                │
      │                  │ 本地事务+锁     │
      │   Yes(Ready)     │                │
      │◀─────────────────│                │
      │   Prepare?       │                │
      │──────────────────────────────────▶│
      │                  │                │ 本地事务+锁
      │   Yes(Ready)     │                │
      │◀──────────────────────────────────│
      │                  │                │
      │  ⭐ 全部 Yes → 进入 Commit        │
      │  有任何 No/超时 → 进入 Rollback   │

阶段二：Commit/Rollback（执行）
  TM(协调者)          RM-库A          RM-库B
      │   Commit!        │                │
      │─────────────────▶│                │
      │                  │ 提交+释放锁     │
      │   Done           │                │
      │◀─────────────────│                │
      │   Commit!        │                │
      │──────────────────────────────────▶│
      │                  │                │ 提交+释放锁
      │   Done           │                │
      │◀──────────────────────────────────│
```

### 3.2 致命缺陷（为什么没人用）

| 缺陷 | 说明 |
|:---|:---|
| **同步阻塞** | Prepare 后 RM 要一直持有数据库锁，直到 Commit/Rollback，高并发下直接 DB 打满 |
| **单点故障** | TM 挂了 = 所有 RM 一直傻等锁 → 服务雪崩 |
| **数据不一致** | 极端：Commit 阶段网络分区，部分 RM 收到 Commit 部分没收到 → 永久不一致（3PC 也没彻底解决） |
| **性能差** | 2 轮额外 RTT + 锁持有时长翻倍，吞吐暴跌 |

### 3.3 MySQL XA 支持

InnoDB 支持 XA 协议，但**生产基本不开**，性能损耗 5~10 倍。

## 四、方案二：3PC（三阶段提交）—— 了解即可

2PC 的「改进版」，加了 `CanCommit`（软投票，不占锁）+ 超时策略，实际更慢更复杂，**工业界几乎不用**，面试知道有这么个东西就行。

## 五、方案三：TCC（Try-Confirm-Cancel）⭐ 核心资金场景

### 5.1 核心思想

把「**一个大业务操作**」拆成三个接口，由 TM 协调调用：

```
        Try（预留资源，不提交）          Confirm（确认提交）/ Cancel（撤销回滚）
业务 ───┼───────────────────────────────▶  Confirm 全成功 = 结束
  │     │                                │
  │     │  Try 全成功 ─── TM 记录 ──────▶│  有失败 → 调所有 Cancel 反向补偿
  │     │                                │
  │     │  有任何 Try 失败 ─────────────▶│  直接调已成功部分的 Cancel
```

### 5.2 扣库存 TCC 案例

```java
// ===== Try 接口：预留资源，冻结库存 =====
@TwoPhaseBusinessAction(name = "stockTcc", commitMethod = "confirm", rollbackMethod = "cancel")
public boolean tryDeduct(@BusinessActionContextParameter(paramName = "skuId") String skuId,
                         @BusinessActionContextParameter(paramName = "num") int num) {
    // 检查：库存 ≥ num？
    // 动作：把可用库存 -num，把「冻结库存」+num（不是真扣，是冻结）
    stockService.freeze(skuId, num);   // freezed_stock = freezed_stock + num
    return true;
}

// ===== Confirm 接口：真正扣减（Try 全 OK 才会调）=====
public boolean confirm(BusinessActionContext ctx) {
    String skuId = ctx.getActionContext("skuId");
    int num = (int) ctx.getActionContext("num");
    // 动作：冻结库存 -num（真扣完成，冻结变已扣）
    stockService.deductFreezed(skuId, num);
    return true;
}

// ===== Cancel 接口：回滚补偿（有任何失败调已成功服务的 Cancel）=====
public boolean cancel(BusinessActionContext ctx) {
    String skuId = ctx.getActionContext("skuId");
    int num = (int) ctx.getActionContext("num");
    // 动作：冻结库存 -num，可用库存 +num（解冻回去）
    stockService.unfreeze(skuId, num);
    return true;
}
```

### 5.3 TCC 三大坑 ⚠️

| 坑 | 说明 | 解法 |
|:---|:---|:---|
| **空回滚** | Try 没收到（丢包），TM 却直接调了 Cancel → Cancel 无事可做 | Cancel 里先查「是否存在 Try 记录」，无则直接返回成功（不报错） |
| **幂等** | Confirm/Cancel 可能因网络重试被调多次 | 每张 TCC 日志表加唯一键（txId+branchId），重复调直接返回成功 |
| **悬挂** | Cancel 先执行完了（网络乱序），然后迟到的 Try 才到 → 资源被冻结后永远没人解冻 | Try 执行前先查「该事务是否已 Cancel 过」，已取消则直接拒绝 Try |

### 5.4 优缺点

| ✅ 优点 | ❌ 缺点 |
|:---|:---|
| **性能好**：无数据库长锁，Try/Confirm/Cancel 都是短事务 | **侵入性极高**：每个参与接口写 3 个方法，改造量巨大 |
| **最终一致**：靠 Cancel 补偿兜底 | **开发成本高**：3 个接口都要考虑幂等/空回滚/悬挂 |
| **柔性可控**：业务层自定义逻辑 | **不适合复杂链路**：服务一多，TCC 关系能把人绕晕 |

## 六、方案四：Saga（长事务补偿）⭐ 长链路业务流

### 6.1 核心思想

**正向流程** + **每步配一个反向补偿操作**。失败时，**逆序执行已成功步骤的补偿**：

```
下订单 → 扣库存 → 用优惠券 → 扣余额 → 创建物流单 （正向5步）
  OK      OK       OK       失败（余额不够）×
                  │
                  └──▶ 逆序补偿：退优惠券 → 退库存 → 取消订单
```

### 6.2 两种执行模式

| 模式 | 流程 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **协同式（Choreography）** | 每步服务执行完发事件 → 下一步监听事件触发 | 去中心化，无单点 | 链路散、难追踪、出了问题不知道走到哪步 |
| **编排式（Orchestration）⭐ 推荐** | 中央「编排器/状态机」统一调度每一步的调用与补偿 | 链路清晰、好监控、易排错 | 编排器要高可用（有状态需持久化） |

### 6.3 编排式 Saga 状态机 ASCII

```
        ┌─────────────────────────────────────────────────────┐
        │              Saga 编排器（状态机持久化）              │
        └─────────────────────────────────────────────────────┘
                          │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
    Step1:订单        Step2:库存       Step3:支付
    补偿:取消订单      补偿:退库存      补偿:退款
         │                │                │
         └────────────────┼────────────────┘
                          ▼
               执行日志表（持久化每步状态）
```

### 6.4 优缺点

| ✅ 优点 | ❌ 缺点 |
|:---|:---|
| **无长锁**：每步独立短事务，并发性能好 | **不隔离**：中间态对外可见（下单后到支付前，别人看到订单已创建但没支付）|
| **长链路友好**：跨 10+ 服务也能清晰管理 | **补偿写起来麻烦**：每步一个反向操作，有些操作天然不可逆（发了短信没法撤回） |
| **一阶段提交**：性能比 2PC 好太多 | **幂等+重试**：补偿和正向都要防重 |

## 七、方案五：本地消息表（可靠事件模式）⭐⭐⭐ 生产首选

### 7.1 核心思想

利用「**本地事务能同时保证业务更新 + 事件入库**」的原子性，把分布式一致性问题**降维**成两个本地事务 + MQ + 幂等：

```
┌────────────── 服务 A（发件方）───────────────┐
│  本地事务（原子！同时成功或失败）            │
│    ① 业务更新（如扣库存）──────┐             │
│    ② 插一条「待投递事件」到消息表│ ← 同事务   │
│                              ┘             │
│  ┌──────────────────────────┐              │
│  │  后台定时任务（或MQ立即发）│：轮询 NEW 事件│
│  │  → 投 MQ → 成功后标记 SENT│              │
│  │  → 失败重试（含退避）    │              │
│  └──────────────────────────┘              │
└────────────────────────────────────────────┘
                       │
                       ▼ MQ
┌────────────── 服务 B（消费方）───────────────┐
│  消费消息（at-least-once → 可能重复）         │
│  ↓                                           │
│  ① 查「消费去重表」：消息ID 是否已处理？       │
│  ② 未处理 → 本地事务（业务更新 + 去重表插入）│
│  ③ 已处理 → 直接 ACK（丢重复）                │
└────────────────────────────────────────────┘
```

### 7.2 为什么这是「首选」

| 优势 | 说明 |
|:---|:---|
| **90% 业务场景适用** | 只要能容忍「几秒级」最终一致，都能上 |
| **改造量极小** | 加两张表（事件表+去重表），不需要 TCC 改 3 个接口 |
| **性能好** | 全是本地短事务，无长锁无阻塞 |
| **靠 MQ 解耦** | 下游挂了不影响上游，MQ 堆着等恢复即可 |

### 7.3 消息表 Schema 参考

```sql
-- 发件方：本地消息表
CREATE TABLE reliable_event (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_type    VARCHAR(64)  NOT NULL COMMENT '事件类型：ORDER_CREATED...',
    payload       TEXT         NOT NULL COMMENT '消息体 JSON',
    status        TINYINT      NOT NULL DEFAULT 0 COMMENT '0=NEW待投递 1=SENT已投递 2=FAILED',
    retry_count   INT          NOT NULL DEFAULT 0,
    next_retry_at DATETIME     NOT NULL,
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status_time (status, next_retry_at)
);

-- 消费方：消费去重表
CREATE TABLE idempotent_consume (
    msg_id     VARCHAR(128) PRIMARY KEY COMMENT 'MQ消息ID或业务唯一键',
    consume_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## 八、方案六：最大努力通知

**最轻量方案**，适合「丢了也无伤大雅的非核心通知」：

1. 服务 A 完成业务 → 发 MQ 通知 B（比如短信、邮件、钉钉）
2. 服务 B 消费失败 → MQ 自动重试（1 分/5 分/30 分/1 小时/5 小时...退避）
3. 达到最大重试次数 → **放弃，不再通知**
4. 兜底：服务 B 提供「主动校对查询接口」，业务方如果特别在意就主动查

典型场景：订单完成发短信通知 → 用户没收到短信不会真的影响订单状态，只是体验稍差。

## 九、Seata 四大模式对比（实战落地框架）

Seata 是阿里开源的分布式事务框架，支持以下 4 种模式：

| 模式 | 对应上面哪种方案 | 核心 | 代码侵入 | 一致性 | 推荐场景 |
|:---|:---|:---|:---:|:---:|:---|
| **AT 模式 ⭐** | 自动版 2PC + 补偿 | 自动生成前后镜像 → 一阶段本地提交 → 二阶段异步删日志/补偿回滚 | **几乎0** | 最终一致 | **业务首选**，90% 场景无脑用 |
| **TCC 模式** | TCC | Try/Confirm/Cancel 业务三接口，手动写 | 极高 | 最终一致 | 核心资金/性能敏感且要自定义逻辑 |
| **Saga 模式** | Saga 编排式 | 状态机编排 + 每步补偿（Seata 1.4+ 支持）| 中 | 最终一致 | 长链路跨多服务、步骤多的大业务流 |
| **XA 模式** | 2PC XA | 基于数据库 XA 协议的两阶段提交 | 低 | 强一致 | 对一致性极致要求、并发不高的核心资金 |

### 9.1 Seata AT 核心机制（为什么能做到「0 侵入」）

```
一阶段：业务 SQL 执行（同本地事务，只是被 Seata 代理的 DataSource 拦截）
  ① Seata 拦截 SQL → 自动查询「前镜像」（修改前的数据，用于回滚）
  ② 执行业务 SQL（比如 update 扣库存）
  ③ 自动查询「后镜像」（修改后的数据）
  ④ 前后镜像 + 业务 SQL → 插入 undo_log 表（和业务同一个本地事务）
  ⑤ 获取「全局锁」（防止其他全局事务改这行）
  ⑥ 本地事务提交（不阻塞！和 2PC 的区别）

二阶段（异步，不影响主流程性能）：
  ├── 分支全成功 → TM 通知所有 RM Commit → RM 异步删 undo_log + 释放全局锁
  └── 有分支失败 → TM 通知所有 RM Rollback → RM 用「前镜像」+ undo_log 生成反向 SQL 补偿回滚
```

> 💡 **AT vs TCC 的本质区别**：AT 是「**框架自动补偿**」（拿前镜像拼反向 SQL），TCC 是「**人工手写补偿**」（Confirm/Cancel 方法）。AT 省了 80% 工作量，只有 AT 兜不住的特殊逻辑才上 TCC。

## 十一、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「TCC 的 Confirm 不会失败」 | ❌ 错！Confirm 也可能失败，所以 Confirm 本身也要幂等 + 重试，不能假设 Try 成功 Confirm 就一定 OK |
| 2 | 「本地消息表用了 MQ 就不会丢」 | ❌ 错！MQ 是 at-least-once，消费端必须靠去重表防重复，不能依赖 MQ「恰好一次」（不存在） |
| 3 | 「Saga 的补偿一定能成功」 | ❌ 错！补偿也可能失败，需要人工介入兜底，所以 Saga 一定要有「补偿失败告警 + 后台手动补偿台」 |
| 4 | 「Seata AT 是强一致」 | ❌ 错！一阶段本地提交后，其他事务就能读到更新了，是**最终一致**（短暂中间态）|
| 5 | 「2PC 能保证绝对一致」 | ❌ 错！Commit 阶段网络分区部分收到部分没收到，会永久不一致，只能人工对账修复 |
| 6 | 「TCC 比 Saga 好」 | ❌ 错！场景不同——短链路、高性能扣减选 TCC；长链路多步骤、每步能反向补偿选 Saga |

---

## 十二、一句话总结

> 分布式事务的本质是「**没有银弹**」：一致性越强，性能越差、侵入性越高。P7 面试考察的不是背概念，而是 **根据业务的一致性容忍度、性能要求、开发成本，在 6 种方案里选一个最合适的，并能讲清 trade-off 和兜底策略**。
