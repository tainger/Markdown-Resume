# 分布式锁

> **P7 面试开场白常客**：「现在多实例部署，怎么保证同一时间只有一个线程执行某段代码？」从单机锁（synchronized/ReentrantLock）为什么不行讲起 → 三种实现方案对比 → Redis Redisson 看门狗原理 → 选型决策 = 满分回答。

---

## 一、为什么需要分布式锁？单机锁为什么不行？

```
单机 JVM 场景：
  JVM 进程（1 个实例）
    ├── Thread-1 ──▶ synchronized(user_123) ──▶ 拿到锁，执行扣余额
    ├── Thread-2 ──▶ 等待 Thread-1 释放锁
    └── Thread-3 ──▶ 等待
    ↑ 没问题！JVM 内共享监视器，能拦住并发

分布式多实例场景：
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │ 实例 A (JVM) │   │ 实例 B (JVM) │   │ 实例 C (JVM) │
  │ Thread-1 抢锁│   │ Thread-2 抢锁│   │ Thread-3 抢锁│
  └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
         │ 3 个线程          │ 分别在 3 个        │ 不同的 JVM
         ▼ 互相感知不到！    ▼ JVM 里各自抢       ▼
     单机锁各自都拿到 → 3 个线程同时执行扣余额 → 扣了 3 次，超扣 ❌
```

**一句话**：单机锁只能管「同一个 JVM 内的线程」，跨 JVM/跨进程/跨机器就需要一把「全局共享」的锁 = 分布式锁。

### 分布式锁的 6 个基本要求（判断一个锁靠不靠谱）

| # | 要求 | 含义 |
|:---:|:---|:---|
| 1 | **互斥性（最核心）** | 任意时刻，只能有一个客户端持有锁 |
| 2 | **无死锁** | 某个客户端挂了没释放锁，锁最终也能被别人拿到（靠 TTL/会话失效兜底）|
| 3 | **解铃还须系铃人** | 只有加锁的那个客户端（线程）自己能释放锁，不能被别人释放 |
| 4 | **容错性** | 只要锁服务（Redis/ZK）大多数节点活着，客户端就能加解锁 |
| 5 | **可重入性** | 同一个客户端 + 同一个线程，已经持有锁了，再调用一次加锁应该能直接成功（计数 +1） |
| 6 | **可中断/可超时** | 加锁时不能一直傻等，支持「等 N 毫秒拿不到就放弃」，也支持持有锁的线程被打断释放 |

> 💡 面试开场 30 秒：把上面 6 条快速报一遍，说明你「知道分布式锁不是 SETNX 就完事了，是有严格标准的」，好感度直接拉满。

## 二、三种主流方案选型矩阵（⭐⭐⭐⭐⭐ P7 必背）

| 维度 | **① Redis 分布式锁（Redisson ⭐）** | **② ZooKeeper 分布式锁（Curator）** | **③ MySQL 分布式锁（乐观/悲观）** |
|:---|:---|:---|:---|
| **核心原理** | `SET key value NX EX ttl`（原子命令抢锁）+ 续约 | 创建「临时有序节点」+ 判断自己是不是最小序号 | 悲观：`SELECT ... FOR UPDATE`；乐观：version+WHERE 条件 |
| **互斥性** | ✅ 好（单线程命令执行天然互斥） | ✅ 很好（ZK 天然强一致 CP）| ✅ 可以（DB 行锁/唯一键）|
| **无死锁** | ✅ 靠 TTL（30s 默认）自动过期；**Redisson 看门狗自动续期** | ✅ 会话断开 → 临时节点自动删除（最靠谱）| ⚠️ 悲观锁：事务提交/回滚自动释放；乐观锁：无死锁（只是更新失败）|
| **解铃还须系铃人** | ✅ value = 唯一线程标识（UUID+threadId），释放时 Lua 脚本比对相等才 DEL | ✅ 临时节点只能被「创建它的那个会话」删，别人删不了 | ✅ 悲观锁随事务走，天然隔离；乐观锁靠版本号匹配 |
| **可重入** | ✅ Redisson 内置哈希结构计数（Hash key=锁名 field=线程标识 value=重入次数） | ✅ Curator InterProcessMutex 可重入 | ❌ 行锁事务内可重入（同连接），跨方法不行；乐观锁天然无「重入」概念 |
| **性能（QPS）** | ⭐⭐⭐⭐⭐ 极高（Redis 纯内存 10w+/s） | ⭐⭐ 中（ZK ZXID 持久化写磁盘 ~1k/s）| ⭐ 低（DB 连接池 ~几百/s） |
| **可靠性** | ⭐⭐⭐ 较好（AP 系统，主从切换极端场景丢锁 → 要 RedLock） | ⭐⭐⭐⭐⭐ 极高（CP 系统，ZAB 过半提交绝不丢） | ⭐⭐⭐ 还行（DB 本身高可用） |
| **实现复杂度** | 低（手写 SETNX+Lua 10 行搞定；生产用 Redisson 0 代码） | 中（要会写 Curator 监听器） | 极低（写 SQL 就行）|
| **运维成本** | 低（一般已有 Redis 集群） | 高（要额外维护 ZK 集群） | 无（已有 DB） |
| **一致性模型** | 最终一致（AP，主从异步复制 → 主挂了可能有锁丢失窗口） | 线性一致（CP，ZAB 强一致，绝不可能俩客户端都以为自己拿到锁）| 线性一致（CP，DB 事务） |
| **推荐场景** | **90% 业务首选**：秒杀扣库存、任务调度互斥、接口防并发（性能优先） | 金融级核心扣减、分布式事务协调（可靠性优先、并发不高） | 临时方案、并发低到没 Redis/ZK 的小项目、DB 乐观锁更新 |

> 💡 **选型口诀**：性能选 Redis、可靠选 ZK、临时凑合用 DB。**P7 面试回答**：「我们项目用的 Redisson 分布式锁，因为并发高、需要好性能，同时业务场景是允许极小概率锁丢失的（幂等兜底）。如果是资金核心场景我会选 ZK Curator，CP 强一致锁不丢。」

## 三、方案一：Redis 分布式锁（从手写简陋版 → Redisson 工业版）

### 3.1 简陋版：SETNX + DEL（❌ 坑死人版，千万别写）

```java
// ❌ 这样写会被面试官直接挂
public boolean badLock(String key, long ttl) {
    Boolean ok = redisTemplate.opsForValue()
        .setIfAbsent(key, "1", ttl, TimeUnit.SECONDS);  // SETNX + EX
    return Boolean.TRUE.equals(ok);
}
public void badUnlock(String key) {
    redisTemplate.delete(key);  // ❌ 谁都能删！Thread-A 的锁 Thread-B 也能 DEL
}
```

**至少 3 个致命坑**：
1. ❌ **不区分加锁者**：Thread-A 加的锁，Thread-B 也能 DEL 删掉（解铃还须系铃人 不满足）
2. ❌ **业务执行 > TTL**：锁 TTL=30s，业务执行了 60s，锁 30s 时自动失效 → Thread-B 拿到锁 → Thread-A 执行完 DEL 把 Thread-B 的锁删了
3. ❌ **不可重入**：同一个线程已经持有锁，再调一次 `badLock` 会把自己堵在外面

### 3.2 正确手写版（⭐ 面试能写出来这个 = 及格）

解决上面 3 个坑：**唯一 value + Lua 原子释放 + 判断线程标识**

```java
// 线程唯一标识：JVM UUID(区分不同实例) + ThreadId(区分同JVM内线程)
private static final String WORKER_ID = UUID.randomUUID().toString();

public String tryLock(String lockKey, long waitMs, long leaseMs) {
    long start = System.currentTimeMillis();
    String requestId = WORKER_ID + ":" + Thread.currentThread().getId();  // ⭐ 唯一标识
    do {
        // 加锁：SET key requestId NX EX leaseMs （Redis 2.6.12+ 单命令原子）
        Boolean ok = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, requestId, leaseMs, TimeUnit.MILLISECONDS);
        if (Boolean.TRUE.equals(ok)) return requestId;  // 拿到了：返回 requestId（解锁要用）
        
        // 没拿到：等一下再试（自旋 + 睡眠，避免 CPU 空转）
        Thread.sleep(50);
    } while (System.currentTimeMillis() - start < waitMs);
    return null;  // 超时了拿不到
}

// 解锁必须用 Lua 脚本（GET + 判断 + DEL 合成一个原子操作，避免并发下误删）
private static final String UNLOCK_LUA =
    "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
    "  return redis.call('DEL', KEYS[1]) " +
    "else return 0 end";

public boolean unlock(String lockKey, String requestId) {
    Long result = redisTemplate.execute(
        (RedisCallback<Long>) conn -> conn.eval(
            UNLOCK_LUA.getBytes(StandardCharsets.UTF_8),
            ReturnType.INTEGER,
            1,
            lockKey.getBytes(StandardCharsets.UTF_8),
            requestId.getBytes(StandardCharsets.UTF_8)
        ));
    return Long.valueOf(1).equals(result);
}
```

**面试加分话术**：「上面手写版虽然能用，但还有两个解决不了的问题 → **① 锁过期了业务没执行完（没续期机制）② 不可重入**。所以生产环境直接用 Redisson，它把这俩问题都完美解决了。」

### 3.3 Redisson 工业版（⭐⭐⭐⭐⭐ P7 必考原理细节）

#### 3.3.1 加锁 Lua 脚本（可重入 + 互斥）

Redisson 加锁不是简单 `SET NX`，而是用了 **Hash 结构做可重入计数**：

```lua
-- KEYS[1] = 锁名，ARGV[1] = 锁TTL(30000ms)，ARGV[2] = 线程唯一标识(UUID:ThreadId)
if (redis.call('exists', KEYS[1]) == 0) then           -- 1. 锁不存在
  redis.call('hincrby', KEYS[1], ARGV[2], 1);           -- 2. 第一次加锁：Hash field=线程标识 计数=1
  redis.call('pexpire', KEYS[1], ARGV[1]);              -- 3. 设置 TTL 30s
  return nil;                                           -- 4. 返回nil=加锁成功
end;
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then  -- 5. 锁已存在，且持有者就是我自己（重入）
  redis.call('hincrby', KEYS[1], ARGV[2], 1);           -- 6. 计数+1（可重入计数）
  redis.call('pexpire', KEYS[1], ARGV[1]);              -- 7. 重新续 TTL 30s
  return nil;                                           -- 8. 重入成功
end;
return redis.call('pttl', KEYS[1]);                     -- 9. 别人持有的锁 → 返回剩余TTL（让调用方知道要等多久）
```

加锁后 Redis 结构长这样：
```
Hash Key: myLock
  ├── field: 3a1b2c3d-1234-5678:98   ← 线程标识（Worker UUID + ThreadId:98）
  │         value: 2                  ← 重入次数：这个线程加了 2 次锁（嵌套调用）
  └── TTL: 30000ms（30s，默认看门狗超时时间）
```

#### 3.3.2 解锁 Lua 脚本（重入计数递减 + 过期到 0 才删）

```lua
if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then  -- 1. 我不是锁持有者？
  return nil;                                            -- 2. 非法解锁，直接返回null(0)
end;
local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1);  -- 3. 是持有者，计数-1
if (counter > 0) then                                   -- 4. 减完还 > 0（还有其他重入没解锁）
  redis.call('pexpire', KEYS[1], ARGV[2]);              -- 5. 续一下TTL，返回 0（不删锁）
  return 0;
else                                                     -- 6. 减完 = 0（最外层解锁了）
  redis.call('del', KEYS[1]);                            -- 7. 真正删锁 key
  redis.call('publish', KEYS[2], ARGV[1]);              -- 8. 发 Pub/Sub 通知：锁释放了！等锁的人可以来抢了
  return 1;
end;
```

#### 3.3.3 ⭐⭐⭐ 看门狗（Watchdog）自动续期机制 —— P7 面试皇冠上的珍珠

**背景问题**：业务执行 60s，锁默认 TTL 30s，30s 时锁自动过期 → Thread-B 拿到锁 → 数据并发。

**Redisson 看门狗解法**：

```
加锁成功的那个客户端线程：
  ├── 启动一个「定时任务」（延迟队列，默认 1/3 TTL 周期跑一次 = 每 10s 一次）
  │
  └── 每 10s 检查一次：「我还持有这把锁吗？」
        ├── 是 → 把 TTL 重新续回 30s（就像狗儿到点了就喂粮，不让锁饿死过期）
        └── 否 → 取消这个定时任务，不再续期
```

ASCII 时间线：
```
时间：  0s         10s        20s        30s        40s        50s        60s
TTL:  30s→20s  续到30s   30→20s   续到30s   30→20s   续到30s   30→20s→...
        │         ▲         ▲         ▲         ▲         ▲
        │         └看门狗到点续期─────────────────┘
        │
   业务开始执行(预计60s) ──────────────────────────────────────────▶ 60s执行完，unlock
                                                                  └→ 删锁 + 停看门狗
```

**为什么是 1/3 TTL 周期**？
- 提前 1/3 周期续，留出「网络抖动/Redis 慢」的余量（万一某次续期网络卡了 5 秒，还有 5+ 秒的 TTL 缓冲不会过期）
- 也不会续得太频繁（每 10s 一次 Redis PEXPIRE 操作，对 Redis 压力几乎为 0）

**看门狗默认配置**：
- `lockWatchdogTimeout = 30000ms`（30s，可配置）
- 只有「加锁时没显式指定 leaseTime（即 leaseTime=-1）」才会启看门狗。如果你自己传了 `leaseTime=10s`，Redisson 认为你知道你在干嘛，不会自动续期。

### 3.4 Redis 主从切换的锁丢失问题（极端场景）→ 红锁 RedLock

```
Redis 主从（异步复制）场景的著名问题：
  1. Client-A 向 Master 加锁 → OK（SET key NX EX 30）
  2. Master 把锁命令复制给 Slave...（异步复制，有延迟）
  3. 还没复制完，Master 挂了（断电/崩了）
  4. 哨兵/Sentinel 故障转移：Slave 升为新 Master
  5. ❌ 新 Master 上根本没那条锁记录（复制不及时）
  6. Client-B 此时加锁 → 也成功了！→ A 和 B 都以为自己有锁 → 数据并发错误！
```

**解法：RedLock（红锁）**：N 个（建议 5 个）互相独立的 Redis Master（无主从/集群关系，不复制），加锁要拿到 >N/2（即 ≥3）个节点的锁才算加锁成功：
```
Client 加锁：并行发 SET NX 给 Redis-1、Redis-2、Redis-3、Redis-4、Redis-5
  → 拿到 3/5 且总耗时 < TTL → 加锁成功
  → 只拿到 <3 个 → 向所有节点 DEL 释放（不管刚才有没有拿到），再重试
解锁：对 5 个节点全部 DEL 一遍
```

> 💡 **P7 面试诚实回答**：「我知道 RedLock，但实际生产很少用（性能下降一半、运维复杂 N 套独立集群）。一般我们用**『锁 + 幂等』双层兜底**：即使极端情况下锁丢了，幂等也会防住重复写入，不会真的出故障。」这个答案比「我用红锁」更务实，更像 P7 的工程思维。

## 四、方案二：ZooKeeper 分布式锁（Curator InterProcessMutex）

### 4.1 核心原理：临时有序节点 + 最小序号判断

```
锁路径：/locks/myLock

Client-A 加锁 → 在 /locks/myLock 下创建临时有序子节点：/locks/myLock/00000000001
Client-B 加锁 → 同上创建：                                    /locks/myLock/00000000002
Client-C 加锁 → 同上创建：                                    /locks/myLock/00000000003

加锁判断：
  A 看自己节点序号 000001 = 最小的？是 → 拿到锁 ✅
  B 看自己节点序号 000002 ≠ 最小（最小是 000001）→ 没拿到，
    注册一个 Watcher 监听「自己前一个节点（000001）是否被删除」
  C 看自己 000003，监听自己前一个（000002）

A 解锁 → 删 /locks/myLock/00000000001（因为是临时节点，A 会话断了也会自动删）
  → ZK 通知 B：你监听的那个节点删了！
  → B 醒来，再看自己序号 000002 = 当前最小？是 → 拿到锁 ✅
```

**完美满足 6 个要求**：
1. ✅ 互斥：最小编号唯一
2. ✅ 无死锁：客户端挂了 → 会话断 → 临时节点自动删（**比 Redis TTL 靠谱多了，没有「业务没跑完锁过期」的问题**）
3. ✅ 解铃还须系铃人：临时节点只能自己会话删
4. ✅ 容错性：只要过半 ZK 节点活着
5. ✅ 可重入：Curator InterProcessMutex 有计数
6. ✅ 可中断：支持 `lockInterruptibly()`

**唯一缺点：性能比 Redis 差两个数量级（~1k vs ~10w QPS）**。ZooKeeper 每次写都要 ZAB 协议过半持久化写磁盘，这是硬伤。

### 4.2 Curator 代码示例（几行搞定，不用手写 ZK）

```java
// 1. 创建 Curator 客户端（连接 ZK 集群）
CuratorFramework client = CuratorFrameworkFactory.newClient(
    "zk1:2181,zk2:2181,zk3:2181", new ExponentialBackoffRetry(1000, 3));
client.start();

// 2. 获取分布式锁（InterProcessMutex = 可重入互斥锁）
InterProcessMutex lock = new InterProcessMutex(client, "/locks/myLock");

// 3. 加锁（支持超时 + 可中断）
boolean acquired = lock.acquire(5, TimeUnit.SECONDS);
if (acquired) {
    try {
        // 执行业务逻辑
        doBusiness();
    } finally {
        lock.release();  // 4. 解锁
    }
}
```

> Curator 是 ZK 的「瑞士军刀」客户端，除了可重入互斥锁，还内置了：
> - `InterProcessSemaphoreMutex`（不可重入互斥锁）
> - `InterProcessReadWriteLock`（读写锁）
> - `InterProcessSemaphoreV2`（信号量，限 N 个并发）
> - `LeaderSelector`（主节点选举，集群中选 1 个 Leader 跑任务）

## 五、方案三：MySQL 分布式锁（凑合用）

### 5.1 悲观锁：`SELECT ... FOR UPDATE`（行锁）

```java
// ⚠️ 必须在事务里（@Transactional），行锁随事务提交才释放
@Transactional
public void dbLockBiz(String orderNo) {
    // 1. 用主键/唯一键查 + FOR UPDATE → 对这行加排他锁
    // 注：WHERE 条件一定要命中索引（主键/唯一键），否则会锁全表！
    Order order = orderMapper.selectOne(
        "SELECT * FROM t_order WHERE order_no = #{orderNo} FOR UPDATE",
        orderNo
    );
    // 2. 其他线程执行上面这行会被 BLOCK，直到我事务提交/回滚
    // 3. 这里执行扣库存、改状态等业务
    processOrder(order);
}   // 4. 事务提交 → 自动释放行锁
```

**坑**：
- ❌ 不能设置超时时间（InnoDB 锁等待超时 `innodb_lock_wait_timeout` 全局配置，默认 50s，太长）
- ❌ 一个连接一个事务，连接池耗尽 = 锁死全部线程
- ❌ 性能最差（DB 成瓶颈），几百并发就顶不住
- ✅ **优点是不需要额外组件**，DB 有就直接用，适用于「并发极低 + 临时应急」

### 5.2 乐观锁：版本号字段（其实不是「锁」，是无锁并发控制）

前面「幂等性 10 法」里已经讲过，这里不再重复：
```sql
UPDATE t_stock SET stock = stock - 1, version = version + 1 
WHERE sku_id = ? AND version = ?;   -- version 对上才更新成功，否则被别人改过了
```

## 六、常见锁粒度与锁优化（P7 加分）

### 6.1 锁粒度设计（不要一上来就大锁）

```
反例 ❌：整个订单系统就一把锁 key=lock:order
  → 1 万个用户各下各的单，互相之间没关系，结果大家全排队等一把锁，QPS 暴跌

正例 ✅：按「业务维度 + 唯一键」加细粒度锁
  扣库存 → key=lock:stock:{skuId}     （同一 SKU 才互斥，不同 SKU 并发）
  用户提现 → key=lock:withdraw:{userId} （同一用户才互斥，不同用户各提各的）
  定时任务集群抢跑 → key=lock:job:orderClose （全局一把锁没问题，本来就只要跑一个）
```

### 6.2 锁优化 5 条口诀

| # | 优化点 | 说明 |
|:---:|:---|:---|
| 1 | **能不用锁就不用锁** | 能用 DB 乐观锁/状态机/唯一键幂等解决的场景，别上分布式锁（锁 = 性能瓶颈 + 死锁风险） |
| 2 | **锁内代码块尽量短** | 锁里别放 RPC 调用、DB 慢查询；先把数据查好再上锁，锁内只做核心判断+更新 |
| 3 | **超时时间一定要设** | tryLock(waitMs, leaseMs)，不要 `lock()` 永久等；**持有锁时间 < leaseMs**（或开看门狗） |
| 4 | **finally 必须解锁** | 不管业务抛什么异常，一定要进 finally release，不然锁只能等 TTL 过期（这期间别人都进不来） |
| 5 | **锁 + 幂等双层兜底** | 锁只是「防并发的第一道防线」，DB 层还要有唯一键/状态机幂等兜底。哪怕锁丢了（极端情况），幂等也能防住脏数据 |

## 七、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「Redis SETNX 加了 EX TTL，就没有死锁问题了」 | ❌ 错！业务执行 > TTL 锁自动过期，其他线程拿到锁，第一个线程执行完误删别人的锁。要 Redisson 看门狗续期 + value 匹配才能避免。 |
| 2 | 「释放锁只要 DEL key 就行」 | ❌ 错！必须 GET + 判断 value + DEL 用 Lua 合成原子操作。先 GET 判断再 DEL 是两步，中间会被其他线程钻空子（A GET 完是自己，B 插进来加锁写了新 value，A 接着 DEL 就把 B 的锁删了）。 |
| 3 | 「ZK 锁比 Redis 锁好，所以全用 ZK」 | ❌ 错！可靠性是好，但性能差 100 倍。金融核心选 ZK，普通业务选 Redisson，别拿大炮打蚊子。 |
| 4 | 「Redisson 看门狗能续到天荒地老，所以业务死循环也没事」 | ❌ 错！看门狗只在「持有锁的那个线程还活着」才续。如果 JVM 整个 OOM 卡住/进程被杀，线程也没了 → 看门狗不续了 → 30s 后锁正常过期（正确行为）。但业务自己死循环 = 业务 bug，不是锁的问题。 |
| 5 | 「RedLock 能 100% 解决 Redis 锁丢失问题」 | ❌ 错！RedLock 也有理论漏洞（时钟漂移/长时间 GC STW 导致锁过期）。工程上的正确做法是「锁 + 幂等」双保险，而不是追求锁本身 100% 完美。 |
| 6 | 「DB FOR UPDATE 只要加了就全表锁」 | ❌ 错！WHERE 条件**必须命中索引**（主键/唯一键/普通索引），InnoDB 是行级锁；不命中索引就升级为表锁，瞬间把并发降到 0。 |

## 八、一句话总结

> 分布式锁的本质是「**在多个 JVM 之外，找一个全局共享的地方做互斥标记**」。Redis 靠内存高性能但要靠看门狗续期，ZK 靠 CP 强一致但性能差。P7 面试考察的不是写 `SET NX` 那一行代码，而是**从 6 个判断标准出发，对比三种方案的优缺点，讲清 Redisson 看门狗的自动续期原理、可重入计数的 Hash 结构实现，以及最后落脚到「锁 + 幂等」双保险的工程化思维**。
