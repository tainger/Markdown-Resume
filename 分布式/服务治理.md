# 服务治理

> **P7 面试核心**：微服务 10+ 个服务互相调用之后，出了问题怎么快速定位？MQ 重试/用户重复提交/重复扣款怎么防？接口老版本能不能兼容不发通知？这三个核心问题 = 链路追踪 + 幂等性 + 版本兼容 = 服务治理三大基石。

---

## 一、服务治理是什么？一张图搞清楚

```
微服务没有服务治理的噩梦场景：
  页面报错「系统异常」
    → 问前端：我收到 500，是哪个接口？ → 不知道
    → 问网关：转发给 A 服务了，日志没打 traceId
    → 问 A 服务：我调 B 超时了
    → 问 B 服务：我调 C 返回参数解析失败
    → 问 C 服务：我 DB 查了 null 没判空 → 终于找到根因！
    整个排查花 2 小时，用户已经投诉 10 次了 😭

有服务治理的理想场景：
  页面报错「系统异常」，带上 traceId=abc123
    → 工程师打开 SkyWalking，搜 abc123
    → 看到完整调用链：Gateway → A(300ms) → B(1200ms) → C(1100ms) 
    → 直接定位 C 里第 3 个 SQL 超时 1100ms，还附了 SQL 和参数
    → 1 分钟定位根因，5 分钟修复发布 ✅
```

**服务治理四大块**：
1. **链路追踪**（出问题秒定位）
2. **幂等性设计**（防重复提交、重复扣款——所有写接口必备）
3. **服务注册与发现/路由/负载均衡**（你 Spring Cloud 笔记里已有）
4. **接口版本兼容与灰度路由**（发版不炸老客户端）

## 二、服务治理第一块：分布式链路追踪（APM）

### 2.1 核心概念（3 个术语，先背下来）

| 概念 | 含义 | 例子 |
|:---|:---|:---|
| **Trace（追踪链）** | 一次完整请求的**全链路调用**，用唯一 `TraceID` 标识 | 一次「下单」请求经过 Gateway → Order → Stock → Pay，4 个服务共享同一个 TraceID |
| **Span（跨度）** | 链路中的**一跳**（一次调用），用 `SpanID` 标识；有父子关系形成树 | Gateway → Order 是 Span1（父），Order → Stock 是 Span2（子）|
| **Annotation（标注）** | Span 中的**关键事件打点**，记录时间点 | cs=Client Send（客户端发请求）、sr=Server Receive（服务端收到）、ss=Server Send（服务端回）、cr=Client Receive（客户端收到）|

> **RT 计算**：Span 的 RT = ss - sr（服务端处理耗时）；全链路 RT = 最顶层 Span 的 cr - cs

### 2.2 调用关系 ASCII 树

```
TraceID = abc123（全链路一个）
├── Span0: Gateway（根 Span，SpanID=0，ParentSpanID=null）
│     cs=0ms ───────────────────────────────── cr=1500ms  ← 全链路 1.5s
│     │
│     └── Span1: OrderService（HTTP 调用，SpanID=1，ParentSpanID=0）
│           cs=10ms ─── sr=12ms ───────────────── ss=612ms ── cr=615ms  ← 这段 605ms
│             │
│             ├── Span2: StockService（Dubbo 调用，SpanID=2，ParentSpanID=1）
│             │     cs=20ms ─ sr=22ms ─── ss=122ms ─ cr=124ms  ← Stock 耗时 102ms
│             │
│             └── Span3: PayService（RocketMQ 异步调用，SpanID=3，ParentSpanID=1）
│                   cs=200ms ─ sr=210ms ─── ss=600ms ─ cr=602ms  ← Pay 耗时 402ms
│
▲ Span 之间父子关系通过 SpanID ↔ ParentSpanID 连起来，就是一棵调用树
```

### 2.5 采样率策略（避免全量采样打爆存储）

全链路 100% 采样存储成本极高（每秒 1 万请求，单请求 1KB Trace = 每天 80GB+），要按策略采样：

| 采样策略 | 做法 | 适用 |
|:---|:---|:---|
| **按比例采样** | 默认 10%（每 10 条采 1 条）| 非核心链路，够用就行 |
| **错误全采** | 正常请求按 10% 采，抛异常/慢调用的请求 **100% 采** | **推荐组合**：既省存储又不会漏故障案例 |
| **业务按等级采** | 核心交易接口 100% 采，非核心查询 1% 采 | 核心与非核心差异大的系统 |
| **按用户采样** | VIP 用户/内部员工请求 100% 采，普通用户 1% | 高价值用户优先保障体验 |

## 三、服务治理第二块：幂等性设计（⭐⭐⭐⭐⭐ 所有写接口必备）

### 3.1 为什么一定要做幂等？

分布式三大现实：
1. **MQ 是 at-least-once**（消息至少一次投递，网络重试就会重复消费）
2. **用户会手滑重复点击**（提交按钮连点 3 次 → 后端收 3 次请求）
3. **调用方会超时重试**（Feign/RestTemplate 默认重试策略 → 一个请求发 N 次）

```
没有幂等 = 灾难现场：
  用户点一次下单 → 生成 3 个订单号 ×
  扣库存消息重试 3 次 → 库存被扣 3 次，负库存 ×
  支付回调重试 → 一张订单被标记「支付成功」3 次，发 3 次权益 ×
```

**幂等定义**：同一个请求执行 1 次和执行 N 次，**结果完全相同**（副作用相同）。注意：返回值可以不同（比如第一次返回「成功」第二次返回「已处理」）。

### 3.2 幂等 10 种方案总览（分类记忆）

| 分类 | 方案 | 核心原理 | 代码改造成本 | 一致性强度 | 推荐场景 |
|:---:|:---|:---|:---:|:---:|:---|
| **① 唯一约束型** | 1. DB 唯一索引/唯一键 | 数据库层硬性防重，重复插入直接抛 DuplicateKey | 极低 | 强一致（CP）| **所有写操作通用首选**，最靠谱最简单 |
| | 2. Redis SETNX | `SET key NX EX ttl` 原子命令抢锁，抢到才算「第一次」 | 低 | 最终一致 | 防前端重复提交（短 TTL 场景） |
| | 3. ZK 临时节点/有序节点 | 相同 path 只能建一个；异常会话断了自动删 | 高（引入 ZK）| 强一致（CP）| 对可靠性极致要求的分布式锁+幂等场景（极少用）|
| **② 去重表型** | 4. 独立幂等去重表 | 专门建 `t_idempotent_record` 表，tx 内业务 + 插记录同时成功失败 | 中 | 强一致 | 核心资金场景（支付/结算），**最通用的工业方案** |
| | 5. 状态机幂等 | 业务状态流转设计：`待支付 → 已支付 → 已发货`，逆向事件直接拒绝 | 低（设计阶段就要想）| 强一致 | 所有有状态流转的业务（订单/合同/工单）**必备** |
| **③ Token 型** | 6. 防重 Token（一次性令牌）| 前端进入页面先拿 Token → 提交时带 Token → 后端用后删 Token | 中（前后端配合）| 强一致 | **防前端页面重复提交**（浏览器手滑/刷新） |
| **④ 多版本型** | 7. 乐观锁（版本号）| `update ... set version=version+1 where id=? and version=?` | 极低 | 强一致 | 「并发更新」场景（扣库存、改状态 + 要防并发覆盖）|
| | 8. CAS 原子更新 | Redis `SET key value NX` / Java `AtomicInteger.compareAndSet` | 极低 | 最终一致 | 计数器/配置更新类并发写 |
| **⑤ 下游自身保证** | 9. 下游天然幂等设计 | 自己写接口时就保证重复调不炸（比如 INSERT ... ON DUPLICATE KEY UPDATE）| 低（设计习惯）| 视实现而定 | 所有对外暴露的写接口「默认就该幂等」 |
| | 10. 过滤+重复请求直接返回 | 先查「该业务是否处理过」，处理过直接返回上次成功结果 | 低 | 强一致 | 和 3/4/5 配合用，是所有方案的前置检查 |

### 3.3 方案详解 1：DB 唯一索引（最常用、最靠谱）

```sql
-- 每个幂等场景设计一个「业务唯一键」
-- 例：扣库存 = 业务类型(DEDUCT_STOCK) + 订单号 + SKU 三者组合唯一
CREATE TABLE t_stock_log (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no    VARCHAR(64)  NOT NULL COMMENT '订单号',
    sku_id      VARCHAR(32)  NOT NULL,
    deduct_num  INT          NOT NULL,
    -- 业务唯一键！同一个订单号+SKU 只能有一条扣减记录
    UNIQUE KEY uk_order_sku (order_no, sku_id)
);

-- Java 代码处理
try {
    stockMapper.insert(log);  // 第一次：OK
    stockMapper.deduct(skuId, num);
} catch (DuplicateKeyException e) {
    // 第二次：抛唯一键冲突 → 说明已经处理过了
    log.warn("幂等触发：订单{} SKU{} 已扣过库存", orderNo, skuId);
    return Result.success("已处理");  // 不是报错！是返回成功
}
```

> ⚠️ **误区**：唯一键冲突了不能回前端「系统繁忙」，要**返回「已处理/成功」**。对调用方来说，他要的是结果是「库存被扣了」，不管第一次还是第二次，扣过了就是满足他的诉求。

### 3.4 方案详解 2：独立幂等去重表（资金核心场景首选）

比上面更通用，一张表管**所有**场景的幂等：

```sql
CREATE TABLE t_idempotent_record (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    biz_type    VARCHAR(32)  NOT NULL COMMENT '业务类型：PAY/STOCK_DEDUCT/COUPON_USE...',
    biz_key     VARCHAR(128) NOT NULL COMMENT '业务唯一键：支付号/订单号+SKU...',
    status      TINYINT      NOT NULL COMMENT '0=处理中 1=成功 2=失败',
    request     TEXT COMMENT '请求参数快照（排查用）',
    response    TEXT COMMENT '响应结果快照（重复调用直接返回这个）',
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    -- ⭐ 核心：业务类型+业务键唯一
    UNIQUE KEY uk_type_key (biz_type, biz_key)
);

-- 伪代码：幂等处理器模板（可以用 AOP + 注解自动实现）
Result idempotentProcess(String bizType, String bizKey, Supplier<Result> realLogic) {
    // 1. 先查：处理过没？
    IdempotentRecord record = mapper.selectOne(bizType, bizKey);
    if (record != null && record.getStatus() == 1) {
        return Result.fromJson(record.getResponse());  // 重复请求：直接返回上次成功结果
    }
    // 2. 抢幂等记录（利用唯一键插入）
    try {
        mapper.insertNew(bizType, bizKey, 0);  // 0=处理中
    } catch (DuplicateKeyException e) {
        // 并发插入：另一个线程在处理，等它处理完再读
        Thread.sleep(500);
        return idempotentProcess(bizType, bizKey, realLogic);  // 自旋重试几次
    }
    // 3. 真的执行业务逻辑
    try {
        Result result = realLogic.get();
        mapper.updateSuccess(bizType, bizKey, 1, result.toJson());  // 标记成功 + 存响应
        return result;
    } catch (Exception e) {
        mapper.updateFail(bizType, bizKey, 2, e.getMessage());
        throw e;
    }
}
```

### 3.5 方案详解 3：状态机幂等（所有订单类业务必备）

把业务状态「画死」，非法状态流转直接拒绝：

```
订单状态机（箭头表示允许的流转方向）：
  PENDING(待支付) ──▶ PAID(已支付) ──▶ SHIPPED(已发货) ──▶ DONE(已完成)
       │                  │
       └──▶ CANCELED      └──▶ REFUNDING(退款中) ──▶ REFUNDED(已退款)

-- 更新状态时，用 WHERE 条件卡死「只能从什么状态到什么状态」
UPDATE t_order 
SET status = 'PAID', pay_no = ?, pay_time = NOW()
WHERE order_no = ? 
  AND status = 'PENDING';   -- ⭐ 必须是待支付的才能改成已支付！

-- Java 层判断影响行数
int rows = orderMapper.paySuccess(orderNo, payNo);
if (rows == 0) {
    // 0 行被改 = 要么订单不存在，要么状态不是待支付（已经付过了）→ 幂等：返回成功
    Order order = orderMapper.selectByOrderNo(orderNo);
    if (order != null && "PAID".equals(order.getStatus())) {
        log.warn("订单 {} 已支付，幂等返回", orderNo);
        return Result.success("支付成功");
    }
    throw new BizException("订单状态非法");
}
```

> 💡 **最保险的做法 = 上面三个叠加**：业务状态机（从逻辑上拒绝乱序）+ 幂等去重表（从数据库层保证唯一性）+ 前端 Token（从用户侧防手抖）。

### 3.6 Redis SETNX 防前端重复提交

```java
// 1. 前端进入「提交页」时，调后端 GET /api/token 拿一个一次性 token 存到页面隐藏域
String token = UUID.randomUUID().toString();
redisTemplate.opsForValue().set("submit:token:" + token, "1", 5, TimeUnit.MINUTES);  // 5分钟有效

// 2. 前端提交时把 token 放 Header: X-Idempotent-Token
// 3. 后端拦截器校验
boolean firstTime = redisTemplate.delete("submit:token:" + token);  // DEL 原子操作：删成功=第一次
if (!firstTime) {
    throw new BizException("请勿重复提交");
}
// 删成功了才放行去执行业务
```

> ⚠️ **为什么用 DELETE 不用 GET+DEL？** 因为 GET 和 DEL 分开两步在并发下会有竞争，必须用 Lua 脚本把 GET+DEL 合成一个原子操作（或直接用 DEL，Redis 2.6+ 单线程本身原子）。

## 四、服务治理第三块：接口版本兼容策略

### 4.1 为什么会有版本问题？

微服务下，服务调用方（Consumer）和服务提供方（Provider）是不同团队不同节奏发布的：

```
A 团队 周一 发布 OrderService v2.0：把 createOrder(UserDTO user) 改成 createOrder(Long userId, String userName)
B 团队（调用方 StockService）还在用旧签名，周三才发布升级 → 周二这 2 天，StockService 调 OrderService 全报错 MethodNotFound！
```

### 4.2 接口兼容 6 条铁律（设计阶段就要遵守）

| # | 铁律 | 说明 | ❌ 错误示例 | ✅ 正确示例 |
|:---:|:---|:---|:---|:---|
| 1 | **只加不减** | 新版本只能加字段/加方法，不能删老字段老方法 | v1 有 `name` 字段，v2 直接删了 → 老调用方拿不到 name 报错 | v2 新增 `age` 字段，`name` 字段继续保留并返回默认值 |
| 2 | **接口只能向下兼容** | 新客户端能调老服务端吗？不一定；**老客户端必须能调新服务端** | 新服务端要求必填字段 `age`，老客户端没传 → 400 | 新字段全是可选 + 默认值，老客户端不传也正常跑 |
| 3 | **参数扩展用对象，不用多个基础类型** | 方法签名用 DTO 封装，不要 `f(a,b,c,d,e)` | `createOrder(Long uid, String addr, String phone, String remark)` → 加参数要改方法签名 | `createOrder(CreateOrderReq req)` → 加字段只改 DTO 类，签名不变 |
| 4 | **枚举不要按顺序用** | 不要依赖枚举的 `ordinal()` 做存储/传输 | 存数据库存 `enum.ordinal()` → 中间插入新枚举 = 全错位 | 存数据库存 `enum.name()`（名称字符串）或 `enum.getCode()`（自定义 code）|
| 5 | **DB 字段默认值 + 允许 NULL** | 新增表字段必须有默认值或允许 NULL | `ALTER TABLE t_order ADD COLUMN pay_channel TINYINT NOT NULL` → 老数据全报错 | `ADD COLUMN pay_channel TINYINT DEFAULT 0 COMMENT '0=未知 1=微信 2=支付宝'` |
| 6 | **版本号显式化 + 灰度路由** | URL/Header 带版本，网关按版本路由 | `POST /createOrder` → 分不清 v1/v2 混合流量 | `POST /v1/createOrder` 或 Header `X-API-Version: 1.0` → 灰度可定向切流 |

### 4.3 三种版本路由方案对比

| 方案 | 做法 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **① URL 版本（推荐简单场景）** | `/api/v1/order`、`/api/v2/order` | 直观，调试简单，网关路由好配 | URL 会越来越乱；不支持「内部 dubbo 调用」 |
| **② Header 版本（推荐复杂场景）** | 请求头 `X-API-Version: 1.0.0`，网关/Nacos Dubbo 按 metadata 路由 | URL 始终干净；支持多粒度（用户/租户级切版本）| 工具链要求高，网关要写自定义路由；调试麻烦点 |
| **③ 服务名版本隔离** | Nacos 注册成 `order-service-v1`、`order-service-v2`，调用方直接调不同服务名 | 最简单好实现，零额外框架 | 服务注册越来越多；不支持「同一调用代码按用户切不同版本」 |

## 六、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「幂等就是接口返回相同结果」 | ❌ 错！是「**副作用**相同」。第一次返回「创建成功 ID=1」，第二次返回「已存在 ID=1」没问题。关键是数据库里不能插两条。 |
| 2 | 「DB 唯一键冲突了就返回错误给前端」 | ❌ 错！**冲突 = 已经处理过了 = 成功**。应该查一下处理结果，返回「已处理/成功」。返回错误会让用户误以为失败再试一次，死循环。 |
| 3 | 「Redis SETNX 做幂等和做分布式锁是一回事」 | ❌ 错！幂等的 Key 永不释放（业务永久唯一），分布式锁的 Key 有 TTL，用完要释放。用途完全不同。 |
| 4 | 「SkyWalking 开了全链路，100% 采样性能损耗可以忽略」 | ❌ 错！全量采样 CPU/内存/网络损耗 10%+，ES 存储也爆炸。一定要开采样策略（正常 10% + 错误/慢调用 100%）。 |
| 5 | 「接口加新字段 = 兼容，不用通知调用方」 | ❌ 错！字段是加了，但如果新字段是「后续流程的必填」，老调用方不传新字段 → 后续走到某个分支还是会炸。发版一定要通知所有 Consumer 团队。 |
| 6 | 「乐观锁 where version=? 失败了就报错」 | ❌ 错！乐观锁失败 = 有并发更新，应该**重试几次**（带上 sleep 退避），而不是直接返回失败。重试 3 次还失败再报错。 |

## 七、一句话总结

> 服务治理的本质是「**微服务多了之后，怎么保证系统可观测、不出错、能演进**」。链路追踪解决「出了问题秒定位」，幂等性解决「重复请求不炸库」，版本兼容解决「多团队多节奏发版不互相打架」。P7 面试考察的不是背 SkyWalking 组件，而是**能从服务设计初期（状态机/接口兼容）到运行期（SkyWalking/Sentinel/限流）再到发布期（灰度/版本路由），讲一套贯穿全生命周期的服务治理落地体系**。
