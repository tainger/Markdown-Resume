# 高可用设计

> **P7 面试核心**：系统设计题几乎 100% 会问到「怎么保证系统高可用？」。从**限流→熔断降级→发布策略→异地多活**四个层级由小到大讲清楚，再结合 Sentinel/Hystrix 的原理细节 = P7 过关。

---

## 一、高可用到底是什么？量化指标

**高可用 HA（High Availability）**：系统能「**尽量长时间**」不中断地对外提供服务的能力。

| 几个9 | 年停机时间 | 月停机时间 | 场景 |
|:---:|:---:|:---:|:---|
| 99%（2 个 9）| 3.65 天 | 7.2 小时 | 内部非核心系统 |
| 99.9%（3 个 9）| 8.76 小时 | 43.2 分钟 | 普通 B 端产品（你做的大部分业务）|
| 99.99%（4 个 9）| 52.6 分钟 | 4.3 分钟 | 电商交易/支付核心 |
| 99.999%（5 个 9）| 5.26 分钟 | 25.9 秒 | 公有云核心服务/电信级 |
| 99.9999%（6 个 9）| 31.5 秒 | 2.5 秒 | 几乎是工程极限，极难达到 |

**SLA/SLO 术语**：
- **SLA（服务等级协议）**：对外签的合同，比如云厂商承诺 99.95%，低于这个就赔钱
- **SLO（服务等级目标）**：内部 KPI，通常比 SLA 更严（比如对外承诺 99.9%，内部定 SLO=99.95% 留缓冲）
- **SLI（服务等级指标）**：用来量化 SLO 的指标，比如 P99 延迟、成功率

> 面试时如果被问「你们系统几个 9？」，先报 SLI 数字，再讲怎么达到的——就是下面这四大块。

## 二、第一层：限流（防自己被打死）

### 2.1 限流是什么

当系统 QPS 超过容量上限时，**主动拒绝一部分请求**（返回「系统繁忙请稍后再试」），保护系统不被打死 = 「丢车保帅」。

```
正常情况：每秒 1000 请求 → 系统容量 2000 → 全处理 ✅
突发流量：每秒 5000 请求 → 系统容量 2000 → 处理到内存爆/DB挂 → 全站不可用 ❌
限流后  ：每秒 5000 请求 → 系统接收 2000 → 拒绝 3000 → 核心功能可用 ✅
```

### 2.2 四种限流算法对比（⭐⭐⭐ P7 必背）

| 算法 | 原理示意图 | 优点 | 缺点 | 适用场景 |
|:---|:---|:---|:---|:---|
| **① 固定窗口计数器** | 1 分钟内计请求数，到阈值就拒绝；到点计数器清零 | 最简单最好实现 | **突刺问题严重**：窗口临界点瞬间 2 倍流量 | 非精准、能容忍突刺的粗粒度限流 |
| **② 滑动窗口计数器 ⭐ 默认** | 把 1 分钟切成 6 个 10 秒小窗口，总量 = 近 6 个小窗口之和；随时间「滑」走旧窗口 | **平滑，无突刺问题** | 实现比固定窗口略复杂 | **Sentinel/Hystrix 默认算法，绝大多数场景首选** |
| **③ 漏桶 Leaky Bucket** | 请求先进桶里排队，桶以**匀速**出水处理；桶满了就拒绝（像漏桶匀速漏水）| **强制匀速输出**，保护下游不被突刺打穿 | 桶会增加延迟；**不允许突发流量**（即使系统闲也不能瞬间用满容量） | 调用外部第三方接口（对方有严格限速）、保护下游 DB/缓存不被打穿 |
| **④ 令牌桶 Token Bucket ⭐** | 桶里按速率放 token（每秒放 2000 个），请求来先拿 token，拿到才放行；桶满 token 不超上限 | **允许一定程度突发**（系统空闲时 token 攒满，瞬间能处理桶大小的请求）| 实现比漏桶稍复杂 | **入口网关/接入层限流**（既能防过载，又能容忍瞬间尖峰）|

### 2.3 四种算法 ASCII 对比

```
① 固定窗口计数器（坑：临界点 2 倍流量）
 时间：  │ 0~59 秒      │ 60~119 秒   │
 请求数：│ 1999（通过） │ 2000（通过）│  ← 实际 59~60 秒这一秒内过了 1999+2000=3999！
         └──────────────┴──────────────┘
                          ↑ 临界点突刺

② 滑动窗口（平滑）
 时间窗：[0][10][20][30][40][50]   每 10 秒一小格
         到第 60 秒时：滑走 [0]，补 [60]
         总量 = 最新 6 格之和 ≤ 2000  → 永远不会出现双倍突刺

③ 漏桶（匀速，防下游）
   请求 ▼▼▼▼▼▼▼▼  (瞬时大量涌入)
      ┌─────────┐
      │ 桶(队列) │ → 匀速 10ms 一个出去 → 下游（不会被打穿）
      └─────────┘

④ 令牌桶（允许突发，防自身）
   ┌─────────────────┐   token 按速率放，满了就不堆了
   │  Token Bucket   │─── 拿到 token → 放行（闲时攒满，瞬间能 burst）
   └─────────────────┘   拿不到 → 拒绝
```

### 2.4 分布式限流 vs 单机限流

| 维度 | 单机限流 | 分布式限流 |
|:---|:---|:---|
| 实现 | 单机内存计数器 / Guava RateLimiter | Redis + Lua / Sentinel 集群模式 / Nginx 层 limit_req |
| 精度 | 单实例精确，全集群总量不准 | 全集群精确到总量 |
| 成本 | 极低（无额外组件） | 高（Redis/集群协调） |
| 选型 | 实例数固定、每实例均衡 → 直接单机限流 | 实例数动态、要严格控制全局 QPS → 分布式限流 |

### 2.5 限流粒度与分级策略（P7 加分项）

不是一个阈值用到死，而是**分级限流**：

```
全局限流 20000 QPS
  ├── 用户级限流：每个用户 ID 每秒最多 100 次（防刷）
  │      └── VIP 用户：单独更高阈值（白名单）
  ├── 接口级限流：订单创建接口 5000，订单查询 10000
  └── IP 级限流：同一个 IP 每秒 50 次（防爬虫/攻击）
```

## 三、第二层：熔断降级（防下游故障拖死自己）

### 3.1 熔断 vs 降级，别再搞混

| 概念 | 目的 | 手段 | 比喻 |
|:---|:---|:---|:---|
| **熔断（Circuit Breaking）** | 保护自己不被**下游故障**拖死 | 下游挂了/慢了 → 直接短路，不调用下游，快速失败 | 家里保险丝：电流过大 → 自动断电，防止火烧房子 |
| **降级（Degradation）** | 保护系统整体不崩 → **主动砍掉非核心功能** | 大促时，商品推荐、用户评论功能暂时关掉，保障下单支付核心链 | 春运火车票：非核心功能（选座/餐车）关了，先保证核心「能买到票」 |

### 3.2 熔断器三种状态（Sentinel/Hystrix 核心）ASCII

```
              成功比例达标/半开放探测成功
          ┌───────────────────────────────────────┐
          │                                       │
          ▼                                       │
     ┌─────────┐   错误率/慢调用比例达标    ┌──────────┐
     │  CLOSED  │ ─────────────────────────▶│   OPEN   │
     │ (闭合)  │◀─────────────────────────│ (熔断打开)│
     └─────────┘   熔断超时到了 → 转半开放  └──────────┘
          ▲                                       │
          │                                       │
          │            半开放试探 1 次              │
          │         ┌───────────────┐              │
          └─────────│  HALF_OPEN   │◀─────────────┘
        探测成功 ──▶│  (半开放)    │──▶ 探测失败 → 回 OPEN
                    └───────────────┘
```

| 状态 | 行为 |
|:---|:---|
| **CLOSED 闭合** | 正常调用下游，同时统计错误率/RT；不达标 → 转 OPEN |
| **OPEN 熔断打开** | 接下来的 N 秒（熔断窗口）**完全不调用下游**，直接走 fallback 快速失败 |
| **HALF_OPEN 半开放** | 熔断超时后，放**少量（1 个）请求**试探下游：成功 → 回 CLOSED；失败 → 继续 OPEN |

### 3.3 触发熔断的 3 个条件（Sentinel 支持的）

| 熔断策略 | 说明 | 典型阈值 |
|:---|:---|:---|
| **慢调用比例** | 1 秒内 RT > 阈值（如 500ms）的请求占比超过 X%，就熔断 | RT>500ms 占比 > 50%，熔断 10 秒 |
| **异常比例** | 1 秒内异常请求（抛 Exception）占比超过 X%，就熔断 | 异常占比 > 40%，熔断 10 秒 |
| **异常数** | 1 分钟内异常个数超过阈值，就熔断 | 1 分钟异常 ≥ 20 个，熔断 10 秒 |

### 3.4 Sentinel vs Hystrix（Spring Cloud 原框架对比）

| 维度 | Hystrix（已停更） | Sentinel ⭐ 推荐 |
|:---|:---|:---|
| 隔离策略 | 线程池隔离（默认）/ 信号量隔离 | **信号量隔离**（轻量，无线程切换开销）|
| 熔断触发 | 异常比例 + 滚动窗口 | 慢调用 / 异常比例 / 异常数 + 滑动窗口 |
| 限流算法 | 令牌桶（RxJava） | **滑动窗口计数器**（默认）+ 漏桶 + 令牌桶 多种可选 |
| 控制台 | 简陋（1.x 有 Dashboard，停更后无） | **丰富**：实时监控、规则动态配置推送、集群限流 |
| 扩展性 | 注解 + HystrixCommand | 注解 + SPI 多扩展点 + 规则可持久化 |
| 现状 | 2018 年官宣停更（进入维护模式） | **阿里开源活跃维护，Spring Cloud Alibaba 默认组件** |

> 选型：新项目直接上 Sentinel，不要再用 Hystrix 了（面试官会问为什么选 Sentinel 不用 Hystrix，就答上面这张表）。

### 3.5 降级策略（怎么「优雅降级」）

| 降级方案 | 说明 | 适用场景 |
|:---|:---|:---|
| **返回兜底数据（Fallback）** | 下游挂了，返回本地缓存/默认值/托底静态页 | 商品详情的推荐位挂了 → 返回一组「热门推荐」兜底 |
| **开关降级** | 配置中心总开关，关掉非核心流程的代码分支 | 大促前手动关评论/优惠券/搜索推荐，保障下单 |
| **读降级（缓存兜底）** | DB 挂了 → 直接读 Redis 缓存，哪怕是旧数据 | 订单详情查询：DB 超时 → 读 30 分钟内 TTL 的订单缓存 |
| **写降级（异步化）** | 同步写链路 → 改发 MQ 异步写，先返回「受理中」 | 大促时，下单日志、用户积分 → 不实时落库，先写 MQ 慢慢落 |
| **限流降级** | 非核心接口直接限流拒绝，资源留给核心 | 日志上报/行为采集接口：限流了直接丢，不影响主流程 |

## 四、第三层：发布策略（防发布引入故障）

发布是线上故障的**第一大来源**（统计占 40%+）。好的发布策略 = 「出了问题能秒级回滚 + 最小化爆炸半径」。

### 4.1 三种发布策略对比（⭐⭐⭐ P7 必背）

| 策略 | 做法 ASCII | 流量切换 | 回滚速度 | 成本 | 适用场景 |
|:---|:---|:---:|:---:|:---:|:---|
| **蓝绿发布 Blue/Green** | 2 套完整集群（蓝=旧版本，绿=新版本）→ 全量切流量 | 一次性 0→100% | **秒级**（切流量回去） | 极高（2 倍服务器）| 关键核心系统 + 机器资源充足 + 要最快回滚 |
| **滚动发布 Rolling** | 一台/一批一台地替换：停旧实例→启新实例→健康检查→下一批 | 1 台→2 台→N 台 渐进 | **慢**（要重新滚回去每台） | 低（只多 1~几台缓冲）| 非核心 + 机器少 + 对回滚速度不敏感 |
| **⭐ 金丝雀发布 Canary / 灰度 ⭐** | 先放 1%/5%/10%/20%/50%/100% 小比例流量到新版本，观察无误再逐步放大 | 分 N 批 逐步放大 | **快**（把小比例流量切回旧版）| 中（只多少量灰度节点）| **生产首选标准方案**，兼顾安全+成本 |

### 4.2 金丝雀（灰度）发布详细流程 ASCII

```
初始态：所有 100% 流量 → v1.0（100 台）
                │
                ├─ 准备工作：先启 2 台 v2.0 金丝雀节点
                │
                ▼
第 1 批：  1% 流量 → v2.0（2 台）     99% → v1.0（观察 30 分钟）
                │  监控：错误率、RT、核心业务指标（下单成功率、支付成功率）
                │  ├── 指标异常 → 立即把 1% 切回 v1.0，排查问题
                │  └── 指标正常 → 放大
                ▼
第 2 批：  5% 流量 → v2.0             95% → v1.0（观察 15 分钟）
                ▼
第 3 批： 20% 流量 → v2.0             80% → v1.0
                ▼
第 4 批： 50% 流量 → v2.0             50% → v1.0
                ▼
第 5 批：100% 流量 → v2.0 → v1 全部下线（发布完成 ✅）
```

### 4.3 灰度策略细分（P7 加分）

不是只能按「流量比例」灰度，还可以：
- **用户维度灰度**：只有内部员工 / 白名单用户 / 某地域用户能看到新版本
- **灰度 + 开关**：新版本代码提前全量上，但功能用配置中心开关，只给灰度用户开开关 → **秒级回滚**（比切流量还快）
- **AB 测试型灰度**：两个版本同时跑，拿 50%/50% 对比业务指标（点击率、转化率），数据好的版本保留

> 💡 **生产环境最佳实践 = 灰度发布（多批）+ 配置中心功能开关（秒级回滚兜底）+ 可观测性监控（P99/错误率/核心业务大盘 + 告警秒级通知）**。

## 五、第四层：异地多活（机房级故障的终极保障）

### 5.1 多活等级（从低到高）

| 等级 | 架构 | 机房挂了怎么办 | RTO（恢复时间） | RPO（数据丢失量）|
|:---:|:---|:---|:---:|:---:|
| 0 | 单机单机房 | 挂了就全没了，只能祈祷备份 | 几小时~几天 | 几小时~1天 |
| 1 | **同城主备** | 主挂了 → 人工/自动切备机房 | 分钟级~30 分钟 | 秒级（同步/半同步复制）|
| 2 | **同城双活** ⭐ 中厂标配 | 两边都能读写，任一边挂了 → 流量切另一边 | 秒级~分钟级 | 0~秒级 |
| 3 | **两地三中心** | 同城双活 + 异地灾备，城市级灾难（地震/断电）也顶住 | 分钟级~小时级 | 秒级~分钟级 |
| 4 | **异地多活** ⭐ 大厂追求 | 北上广深每个城市都能读写，用户就近接入 | 秒级 | 秒级（最终一致）|

### 5.2 同城双活 ASCII 图（P7 常考）

```
┌─────────────── 同城双活机房（光纤互联延迟 < 1ms）───────────────┐
│                                                                │
│   ┌──────── 机房 A（活）────────┐   ┌──────── 机房 B（活）────────┐
│   │  APP × 50 台  ←──┐          │   │  APP × 50 台  ←──┐          │
│   │                   │  SLB 同时 │   │                   │  SLB 同时 │
│   │  DB-Master(读写)  │  分流量   │   │  DB-Slave(只读)  │  分流量   │
│   │      │            │          │   │      ▲            │          │
│   │      └───半同步复制──────────┘   │     半同步复制    │          │
│   │      ┌───反向复制（异步）────────┘                    │          │
│   │      ▼                                                │          │
│   │  DB-Slave(只读)                                        │          │
│   └─────────────────────────────────┘   └─────────────────────────────┘
```

**核心要点**：
- 两边 APP 都对外提供服务（所以叫「双活」不是主备）
- DB 只能有一个真正的 Master（A 写 B 读，或者反过来，**双写会有冲突问题**）
- 任一机房全挂：SLB 把全流量切另一机房，DB 那边 Slave 升 Master（自动切换）

### 5.3 异地多活的 3 大挑战（P7 加分深度）

| 挑战 | 问题 | 解法 |
|:---|:---|:---|
| **数据同步延迟** | 北京→上海 1500km ≈ 50ms RTT，跨城同步天然有延迟 | 「单元化」按用户分片，北京用户数据只在北京读写，跨城只读；同步用异步 MQ + 最终一致 |
| **数据一致性冲突** | 用户同时在北京和上海修改同一条数据（双写） | **避免双写**：按用户 ID/地域做 hash 分片，同一数据只在 1 个「单元」写；冲突检测按最后写入时间（LWW）兜底 |
| **流量切换与路由** | 机房故障时，怎么秒级把用户流量切到其他城市 | 全局 GSLB（智能 DNS/HTTPDNS）+ 多活流量调度中心，拨测健康状态实时切 DNS |

## 六、高可用设计通用原则（5 条口诀）

| # | 原则 | 说明 |
|:---:|:---|:---|
| 1 | **无单点原则** | 任何组件都至少 2 份部署（Nginx/APP/DB/MQ/Redis...），别留单点故障点 |
| 2 | **超时 + 重试 + 幂等 三件套** | 任何外部调用必须设超时；重试要指数退避（1s→2s→4s）；重试必然带来重复 → 所有写接口必须幂等 |
| 3 | **降级为常，开关兜底** | 每个非核心功能都要有降级开关；大促/故障时一键关闭，资源留核心 |
| 4 | **故障隔离/舱壁模式** | 线程池/连接池按依赖隔离，一个下游慢了只占自己那点资源，不会全池耗尽拖死全部 |
| 5 | **可观测 + 告警先行** | 没监控的系统 = 瞎跑。P7 面试讲高可用，最后一定要落脚到「**怎么观察到系统健康，怎么秒级告警出问题**」 |

## 七、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「限流就是拒绝请求，让系统越少处理越好」 | ❌ 错！限流是「**处理能力上限内尽可能多处理**」，不是越少越好。阈值要基于压测定真实容量，拍脑袋要么拒太多浪费资源，要么拒太少防不住 |
| 2 | 「令牌桶比漏桶好，所以全用令牌桶」 | ❌ 错！保护**下游**（防打穿第三方/DB）用漏桶（强制匀速）；保护**自身**（允许突发）用令牌桶。场景不同，选算法不同 |
| 3 | 「熔断半开放只放一个请求太保守了，多放几个更好」 | ❌ 错！半开放的目的是「**最小代价试探**」，放一个失败了损失最小；放多了万一探测失败等于没熔断 |
| 4 | 「灰度发布能保证不引入故障」 | ❌ 错！灰度只是**降低爆炸半径**（出问题只有 1% 用户受影响），不是不出问题。不做监控告警，灰度白做 |
| 5 | 「异地多活就是 3 个机房都能读写同一份数据」 | ❌ 错！工程上极少做同一份数据多写（冲突解决不了），一般是「**按用户分片单元化，每个单元唯一写 + 全局只读副本**」 |
| 6 | 「Sentinel 线程池隔离比信号量隔离好」 | ❌ 错！线程池隔离：额外线程+队列+上下文切换，重但有超时/排队能力；信号量隔离：轻量但无排队能力。**Sentinel 默认选信号量（性能优先）**，老的 Hystrix 默认线程池（兜底优先） |

---

## 八、一句话总结

> 高可用不是「多买几台机器」，而是从**限流（防自己被打死）→ 熔断降级（防下游拖死）→ 发布策略（防自己引入故障）→ 异地多活（防灾级故障）** 四层立体防御。P7 面试考察的不是背四个限流算法，而是**从接入层网关到核心服务再到基础设施，层层递进讲一套完整的高可用设计方案，并能结合 Sentinel、灰度发布这些具体工具讲落地实践和踩坑经验**。
