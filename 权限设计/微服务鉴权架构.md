# 微服务鉴权架构（网关统一鉴权 / 服务间认证 / 零信任）

> **P7 面试核心**：单体时代的注解鉴权搬不进微服务——面试必问三连：「**鉴权放网关还是放各服务？服务之间怎么互相信任？内网是不是就不用鉴权了？**」本文按「鉴权位置之争 → 网关统一鉴权全流程 → 服务间认证三种方案 → 内网真的安全吗（零信任）」主线展开。

---

## 一、鉴权放哪：网关统一 vs 各服务自治

### 1.1 两种架构

```
【网关统一鉴权】                        【各服务自鉴权】
Client ──▶ ┌─────────┐                 Client ──▶ ┌────────┐──▶ ┌────────┐
           │ Gateway  │ 认证+粗粒度授权  │           │ Service│    │ Service│
           │ ①验签    │ ──转发(带身份头)──▶            │  自验签 │    │  自验签 │
           │ ②路由级权限                          └────────┘    └────────┘
           └─────────┘                 每个服务都集成认证逻辑
```

| 维度 | 网关统一 | 各服务自治 |
|:---|:---|:---|
| 认证（你是谁）| **网关做**：验签、Token 有效性、限流、灰度 | 重复实现 N 遍 |
| 功能授权（能不能调） | 网关做**路由/租户级**粗粒度；细粒度留给服务 | — |
| 数据授权 | 只能服务内做（要查业务数据/部门）| 服务内注解 |
| 优点 | 集中收口、职责单一、服务零信任成本 | 服务可独立对外、精细 |
| 缺点 | 网关是单点瓶颈；细粒度授权塞网关会爆炸 | 逻辑重复、策略漂移 |

### 1.2 结论（背）

> **认证统一在网关（或独立认证服务），授权分两层：网关做粗粒度（路由白名单/租户/限流），服务内做细粒度（权限点注解 + 数据权限）**。转发时网关把解析好的身份放**可信请求头**传给下游，服务不再解析 Token（性能 + 一致性）。

```yaml
# 网关转发身份头示例
X-User-Id: 1001
X-User-Roles: order_admin,audit
X-Tenant-Id: t_88
```

## 二、Spring Cloud Gateway 统一鉴权全流程（实战）

```
请求 ─▶ GlobalFilter 链：
  ① AuthFilter（核心）
     ├─ 白名单路由（/login /public/**）直接放行
     ├─ 解析 JWT：验签(RS256) → 验 exp → 查黑名单(jti)
     ├─ 组装可信头 X-User-Id / X-Tenant-Id，**剔除客户端伪造的同名头**
     └─ 失败 → 401（未认证）/ 403（无权限）
  ② Route 级权限：path ↔ 权限点映射表（网关侧粗粒度）
  ③ 限流/熔断 → 转发下游
```

```java
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {

    private static final Set<String> WHITE_LIST = Set.of("/api/auth/login", "/api/public");

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getPath().value();
        if (WHITE_LIST.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }
        String token = exchange.getRequest().getHeaders().getFirst(HttpHeaders.AUTHORIZATION);
        Claims claims;
        try {
            claims = jwtUtil.parse(stripBearer(token));   // 验签 + exp
        } catch (JwtException e) {
            return unauthorized(exchange);                 // 401
        }
        // 防伪造：先删客户端可能带来的身份头，再写可信头
        var mutated = exchange.getRequest().mutate()
                .headers(h -> { h.remove("X-User-Id"); h.remove("X-Tenant-Id"); })
                .header("X-User-Id", claims.getSubject())
                .header("X-Tenant-Id", String.valueOf(claims.get("tenantId")))
                .build();
        return chain.filter(exchange.mutate().request(mutated).build());
    }

    @Override
    public int getOrder() { return -100; }   // 最早执行
}
```

> 下游服务侧：加一个**防御性 Filter 校验可信头来自网关**（K8s NetworkPolicy / 入口 IP 白名单保证流量必经网关），否则内网直连服务 = 绕过网关（见第四节）。

## 三、服务间认证（M2M：Server-to-Server）

用户态的身份头不够——服务 A 调服务 B，A 说「这是用户张三」，B 信吗？**服务自己的身份先解决，用户身份只是透传**。

### 3.1 三种方案对比

| 方案 | 机制 | 优点 | 缺点 | 适用 |
|:---|:---|:---|:---|:---|
| **内网 Token（客户端凭证）** | 服务用 `client_id/secret` 向认证中心换 access_token（OAuth2 Client Credentials），调用时带上 | 标准化、短时效、可审计回收 | 每服务维护凭证 + token 刷新 | 主流选择（Dubbo/SpringCloud 均可包一层 RPC Filter）|
| **mTLS 双向证书** | 调用双方互验证书，链路加密 | 身份 + 加密一体，**零信任标配**（Istio 服务网格自动处理）| 证书管理复杂 | 金融级 / 服务网格环境 |
| **内网信任 + 网络隔离** | 不认证，靠 K8s NetworkPolicy/VPC 隔离内网 | 零成本 | 内网一破全线裸奔；日志无法区分调用方 | 小团队过渡期 |

### 3.2 熔断组件鉴权链路（结合 Dubbo/Sentinel）

```
服务A ──RPC──▶ 服务B
  │ ①A 的 RPC Filter：附加 内网token + 用户上下文（traceId 同透传）
  │ ②B 的 RPC Filter：验内网token → 提取用户上下文 → ThreadLocal
  ▼ ③B 业务代码：@PreAuthorize 权限点 + 数据权限拦截器（与单体一致复用）
```

> 要点：**透传链路必须全**（userId/tenantId/traceId），任一环丢失 → 下游数据权限失效或日志断链。Dubbo 用 `RpcContext.attach(...)`，Feign 用 `RequestInterceptor`。

## 四、内网真的安全吗？（零信任 Zero Trust）

### 4.1 传统「城堡护城河」模型失效

```
旧假设：内网 = 可信                     现实：
┌───────────────┐                     ① 一个服务被打穿（SSRF/RCE）→ 横向移动如入无人之境
│  防火墙（外硬内软）│                     ② 内部员工/离职人员摸鱼扫描
│   内网随便跑    │                     ③ 第三方接入（供应链攻击）
└───────────────┘                     ④ 服务器被挂挖矿木马后内网扩散
```

### 4.2 零信任原则（BeyondCorp / Google）

| 原则 | 微服务落地 |
|:---|:---|
| **永不信任，始终验证** | 服务间也要认证（mTLS / 内网 token），不因「在内网」而豁免 |
| 最小权限 | 每个服务只能调它需要的接口（服务级 ACL：Dubbo 黑白名单 / Istio AuthorizationPolicy）|
| 假设已被入侵 | 服务间调用全加密（mTLS）、全审计（谁在何时调了什么）|
| 动态策略 | 按「服务身份 + 环境（补丁状态/异常行为）」实时决定放行，而非静态 IP 白名单 |

> 面试话术：「我们没上完整服务网格，但做了**四件事**：入口强制网关（NetworkPolicy 禁直连）、服务间内网 token + 身份头透传、敏感服务 mTLS、全链路审计日志——零信任的核心是**把内网当外网防**。」

## 五、全链路鉴权检查清单

| 层 | 检查项 |
|:---|:---|
| 接入层 | WAF / 限流（IP+用户+接口三维）/ 灰度路由鉴权 |
| 网关 | 验签、exp、黑名单、路由级权限、**剔除伪造身份头** |
| 服务内 | 权限点注解 + 数据权限拦截器（复用单体方案）|
| 服务间 | 内网 token / mTLS、上下文透传完整性 |
| 存储 | 行级数据权限（见 [数据权限与多租户](数据权限与多租户.md)）、敏感列加密 |
| 审计 | 全链路 traceId、敏感操作落审计表（谁/何时/做了什么/结果）|

## 六、易错点

1. **网关验了签名，下游裸奔**：内网直连服务端口绕过一切鉴权 → NetworkPolicy/安全组限制只有网关能访问业务端口。
2. **身份头可伪造**：客户端直接带 `X-User-Id: 1` 调网关转发头被原样透传 → 网关必须**先删后写**。
3. **细粒度授权塞网关**：「订单 id=1001 能不能删」要查业务库，网关做不了也不该做 → 数据授权归服务内。
4. **内网 token 永不过期**：形同虚设；与用户 JWT 同等强度管理（短时效 + 轮换）。
5. **异步/MQ 链路丢身份**：用户发起消息投递后，消费者侧 ThreadLocal 是空的 → 消息体携带用户上下文，消费时重建（且要重新鉴权）。
6. **定时任务/开放接口无用户态**：系统任务用系统身份（system/system），审计单独标记，别复用真实用户。

---

## 七、一句话总结

> **微服务鉴权 = 网关统一认证（验签 + 组可信头）+ 网关粗授权 / 服务内细授权（注解 + 数据权限）+ 服务间显式认证（Client Credentials 内网 token 或 mTLS）+ 上下文全链路透传；零信任的本质是把内网当外网防，入口收口 + 最小权限 + 全链路审计。**
