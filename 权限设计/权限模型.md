# 权限模型（ACL / DAC / MAC / RBAC / ABAC / ReBAC）

> **P7 面试核心**：权限设计第一题永远是「你们用什么权限模型，为什么不用 XXX」。本文把 6 大模型一次讲透：每个模型的**核心思想 → 一张图 → 优缺点 → 适用场景**，最后给出选型决策表。记住主线：**ACL 是点对点 → DAC/MAC 是策略归属 → RBAC 是角色批量化 → ABAC 是属性动态化 → ReBAC 是关系图谱化**。

---

## 一、认证 vs 授权（先把概念立正）

面试第一坑：把认证（Authentication）和授权（Authorization）混为一谈。

| 概念 | 英文 | 回答的问题 | 例子 |
|:---|:---|:---|:---|
| **认证** | Authentication（AuthN） | 你是谁？ | 账号密码登录、扫码、指纹 |
| **授权** | Authorization（AuthZ） | 你能干什么？ | 这个用户能不能删订单 |
| **鉴权** | — | 实时校验「能不能干」的过程 | 拦截器里查权限点 |

> 一句话：**认证发身份，授权发权利，鉴权做校验**。认证是授权的前提。JWT/Session/OAuth 解决的是认证（和凭证传递），RBAC/ABAC 解决的是授权。

---

## 二、ACL（访问控制列表）

### 2.1 核心思想

**把权限直接挂在资源上**：每个资源维护一张「谁能对我做什么」的列表。

```
资源：订单 #1001
┌──────────────┬────────────┐
│ 主体         │ 权限       │
├──────────────┼────────────┤
│ 用户 Alice   │ 读/写      │
│ 用户 Bob     │ 读         │
│ 运维组       │ 读         │
└──────────────┴────────────┘
```

### 2.2 优缺点与场景

| 优点 | 缺点 |
|:---|:---|
| 粒度极细，直接到单个资源 | 资源 × 用户 爆炸：1 亿资源 × 1 亿用户无法维护 |
| 直观，谁能动这个资源一目了然 | 权限分散在各资源上，全局审计困难 |
| — | 授权动作重：新建用户要挨个资源授权 |

**适用**：资源数量少、主体固定——文件系统 NTFS/POSIX ACL、Git 仓库协作者、网盘分享链接。**不适合**做业务系统的主体模型，但常作为**附属机制**（如「文档所有者额外可分享」）。

---

## 三、DAC 与 MAC（策略归属的两大流派）

### 3.1 DAC（自主访问控制，Discretionary Access Control）

- 权限由**资源所有者自主决定**授予/收回——Unix 文件 `rwx` 三段位、网盘「把文件分享给某人」都是 DAC。
- 优点：灵活、去中心化；缺点：**权限可被层层扩散**，A 授权给 B，B 再转授给 C，最终失控（恶意软件放大、越权链）。

### 3.2 MAC（强制访问控制，Mandatory Access Control）

- 系统按**全局安全策略强制裁决**，所有者和用户都改不了：主体和资源都打**密级标签**，规则是「不上读、不下写」。

```
主体（人/进程）              资源（文件）
绝密 ──────┐          ┌────── 绝密   ✅ 可读可写
机密 ──────┼─ 规则 ──┼────── 机密   ✅
秘密 ──────┘          └────── 绝密   ❌ 不上读：低密级不可读高密级
                                     ❌ 不下写：高密级不可写低密级（防泄密）
```

**适用**：军事、政府、强合规行业（SELinux、鸿蒙/国防系统）。互联网业务系统几乎不用——太僵化，等级是全局静态的。

> 面试金句：**DAC 是「我的地盘我做主」，MAC 是「国家规定说了算」**。

---

## 四、RBAC（基于角色的访问控制）★ 重点

### 4.1 核心思想

**在用户和权限之间加一层「角色」**：权限不直接授予用户，而是授予角色；用户通过扮演角色获得权限。把 `M × N` 的用户-权限关系降为 `M × K + K × N`（K = 角色数，通常几十）。

```
用户 ──多对多──▶ 角色 ──多对多──▶ 权限 ──▶ 资源/操作

张三 ─┐                ┌─ 「订单管理员」─┐
      ├─ 归属 ──▶ ┌────┴────┐           ├─ order:list
李四 ─┘           │  角色   │           ├─ order:delete
                  └─「审计员」┘          └─ order:export
```

### 4.2 RBAC 四级演进（面试高频：说出 96 模型）

| 级别 | 名称 | 新增概念 | 解决的问题 | 一句话 |
|:---:|:---|:---|:---|:---|
| **RBAC0** | 基础版 | 用户/角色/权限 + 两个多对多 | 权限批量授予 | 及格线，90% 系统够用 |
| **RBAC1** | 角色分级 | 角色继承树（ junior ▶ senior）| 上级自动拥有下级权限，避免重复配置 | 董事长隐含拥有经理权限 |
| **RBAC2** | 角色约束 | 互斥（SSD）/ 基数约束 | 职责分离（SoD）防舞弊 | 「会计 + 出纳」不能同一个人 |
| **RBAC3** | 完整版 | RBAC1 + RBAC2 | 大型组织治理 | 银行/ERP 级别 |

```sql
-- RBAC2 互斥约束落地：申请「付款审批」角色时校验
-- 若该用户已持有「付款发起」角色则拒绝（互斥角色集）
SELECT COUNT(*) FROM user_role ur
JOIN role_mutex m ON m.role_a = ur.role_id OR m.role_b = ur.role_id
WHERE ur.user_id = #{userId} AND (m.role_a = #{roleId} OR m.role_b = #{roleId});
-- 结果 > 0 → 拒绝授予
```

### 4.3 优缺点

| 优点 | 缺点 |
|:---|:---|
| 授权成本 O(1)：新员工配几个角色即可 | 角色爆炸：细分场景组合出上万角色（「华东区-华东仓-退货-初级审核员」）|
| 权限回收干净：离职摘角色即可 | 粒度粗：难以表达「只能看自己部门的订单」这类**条件** |
| 符合组织架构，审计友好 | 角色语义漂移：同一个「管理员」各系统定义不同 |

### 4.4 适用

绝大多数**中后台/ToB 管理系统**（权限跟着「岗位」走）。一旦出现大量「因人而异」的规则（跟数据、跟上下文有关），就要升级 ABAC 或「RBAC + 数据权限」混合。

## 五、ABAC（基于属性的访问控制）

### 5.1 核心思想

**用属性 + 规则表达式动态判定**，不再枚举「谁有什么权限」。四要素：

```
S（Subject 主体属性：部门=华东、职级≥5）
A（Action 动作属性：read / approve）
R（Resource 资源属性：订单.归属部门、订单.金额）
E（Environment 环境属性：当前时间 9~18 点、访问 IP 属办公网）
        │
        ▼
策略引擎：user.dept == order.dept && order.amount <= 10000 && work_hours
        │
        ▼
    ALLOW / DENY
```

### 5.2 优缺点与场景

| 优点 | 缺点 |
|:---|:---|
| 表达力极强：一条规则覆盖 n 个「角色」| 规则难审计：出事了说不清「为什么拒绝」|
| 免角色爆炸：条件驱动，天然支持数据权限 | 属性治理难：属性从哪来、谁维护、可信吗 |
| 运行时动态：随时改规则即时生效 | 性能成本：每次请求都要算规则 + 查属性 |

**适用**：云平台 IAM（AWS IAM Policy 就是 ABAC 风格）、风控（「异地登录禁止转账」）、零信任网络（Google BeyondCorp）。常见落地是 **OPA（Open Policy Agent）/ Casbin** 作为策略引擎，策略与业务代码解耦。

---

## 六、ReBAC（基于关系的访问控制）

**核心思想**：权限由「主体与资源之间的关系图」推导。典型问题——「我不是文档协作者，但我是协作者的上级，我能看吗？」RBAC/ABAC 都难表达，关系图一行搞定。

- 代表：Google Zanzibar 论文（全球统一授权系统），开源实现 **SpiceDB / OpenFGA（Auth0 FGA）**。
- 模型：`元组 = (对象, 关系, 用户)`，如 `(doc:123, editor, user:alice)`；支持关系传递（`parent` 继承、`viewer` implies ` commenter`）。
- **适用**：资源间有天然层级/共享关系——网盘（文件夹继承）、协作产品（Notion/飞书文档）、社交（好友可见）。

---

## 七、六大模型对比与选型（背这张表）

| 模型 | 权限挂在哪 | 判定方式 | 粒度 | 代表 | 典型场景 |
|:---|:---|:---|:---:|:---|:---|
| ACL | 资源上 | 查资源 ACL 表 | 资源级 | NTFS、Git | 少量资源共享 |
| DAC | 资源上 | 所有者自定 | 资源级 | Unix rwx | 文件系统 |
| MAC | 全局策略 | 密级标签比对 | 系统级 | SELinux | 军工/强合规 |
| **RBAC** | 角色上 | 查用户→角色→权限 | 功能级 | 全行业中后台 | 管理后台标配 |
| ABAC | 策略引擎 | 属性表达式实时算 | 条件级 | AWS IAM、OPA | 云平台、风控、零信任 |
| ReBAC | 关系图上 | 图遍历/关系推导 | 关系级 | Zanzibar、OpenFGA | 网盘、协作文档、社交 |

### 选型决策（面试这么答）

1. **默认 RBAC0**：中后台管理系统，权限跟岗位走 → 5 张表搞定。
2. **RBAC + 数据权限**：出现「只看自己/本部门/本分公司数据」→ 功能权限 RBAC 管，数据权限用「数据范围字段 + SQL 拼接/拦截器」补（见 [数据权限与多租户](数据权限与多租户.md)）。
3. **规则复杂且动态**（按金额/时间/地域/风控）→ 引入 ABAC 策略引擎，功能权限仍用 RBAC，**混合模型**是工业界主流。
4. **资源有共享/继承关系**（文档协作、网盘）→ ReBAC（OpenFGA）。
5. 万能收尾：「我们生产上是 **RBAC 做功能权限 + ABAC 思想做数据权限 + 关键资源用 ACL 补充**，没有银弹，按问题域组合。」

## 八、易错点

1. **把认证当授权**：JWT 只证明「你是谁」，不解决「你能干什么」——把权限塞进 JWT 还会导致**改权限不生效**（Token 未过期前权限是旧快照）。
2. **角色爆炸不自知**：一开始 RBAC 很香，半年后出现 3000 个角色 → 信号：角色名里开始带「部门 + 地域 + 等级」组合词，说明需要数据权限/ABAC 了。
3. **前端隐藏 ≠ 权限控制**：按钮置灰、菜单隐藏只是 UI 体验，**后端接口必须独立鉴权**（否则拿接口直接 curl 就绕过了）。
4. **MAC/DAC 概念颠倒**：MAC 的 M 是 Mandatory（强制，管理员定），不是 Management；DAC 的 D 是 Discretionary（自主，所有者定）。
5. **RBAC2 互斥只做一半**：授角色时校验互斥，但用户**同时改两个角色**也要校验（并发场景加唯一约束或锁）。
6. **ABAC 全盘推翻 RBAC**：ABAC 成本高（属性治理 + 引擎 + 审计），正确姿势是 RBAC 打底、ABAC 补充条件维度。

---

## 九、一句话总结

> **ACL 挂资源、DAC 自主放、MAC 强制管、RBAC 靠角色、ABAC 看属性、ReBAC 讲关系；工业界主流 = RBAC 打底 + 数据权限/ABAC 补条件，认证归认证、授权归授权，后端鉴权不可省。**
