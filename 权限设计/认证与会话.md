# 认证与会话（Session / JWT / OAuth2 / SSO）

> **P7 面试核心**：认证是权限设计的前置题，必考三连——「**Session 和 JWT 怎么选？JWT 怎么注销？OAuth2 四种模式各用在哪？**」。本文按「凭证演进 → Session vs JWT → JWT 安全治理 → OAuth2.0 → 单点登录 SSO → 二次验证 2FA」主线讲透。

---

## 一、凭证演进：从 Cookie 到 Token

```
HTTP 无状态 → 服务器怎么记住「你是你」？

① 1995 Cookie/Session   服务器存会话，浏览器只带 sessionId
② 2010 Token/JWT        签名令牌放客户端，服务器无状态校验
③ 云时代 OAuth2/OIDC    第三方授权 + 联合登录（微信/GitHub 登录）
④ 零信任时代            短时令牌 + mTLS + 持续验证（BeyondCorp）
```

---

## 二、Session vs JWT（必考对比）

### 2.1 流程图

```
【Session 集群模式】                     【JWT 无状态模式】
Client ──登录──▶ Server                 Client ──登录──▶ Server
        ◀─Set-Cookie: JSESSIONID─              ◀─签名 JWT（Header.Payload.Signature）─
Client ──带 sessionId──▶ 查 Session 存储 Client ──带 JWT──▶ 校验签名（不查库）
                          (Redis/内存)                    ▼
                                                    信任 Payload 声明
```

### 2.2 对比表（背）

| 维度 | Session | JWT |
|:---|:---|:---|
| 状态存储 | **服务端**（Redis/内存） | **客户端**（签名防篡改） |
| 服务端开销 | 每请求查会话存储 | 只验签，CPU 换 IO |
| 注销/封禁 | 删 Session 即时生效 | **难**：Token 到期前一直有效（需黑名单补救）|
| 水平扩展 | 天然支持（Session 集中存 Redis） | 天然支持（无状态）|
| 跨域/多端 | Cookie 受同源限制，App 端不友好 | Header 携带，多端友好 |
| Token 大小 | sessionId 十几字节 | 数百字节起（每请求都带）|
| 敏感信息 | 不暴露 | Payload 仅 Base64 **不是加密**，别放敏感数据 |

### 2.3 选型结论

- **纯 Web 中后台、需要强会话控制** → Session + Redis（注销简单、权限即时生效）。
- **多端（App/小程序）、微服务间传递身份、网关无状态** → JWT。
- 工业折中：**短时 JWT（access 15min）+ 刷新令牌（refresh 7d）+ Redis 黑名单/版本号**，兼顾无状态与可控性。

## 三、JWT 安全治理（面试追问重灾区）

### 3.1 结构与签名

```
Header.Payload.Signature
 {"alg":"HS256"}   {"sub":"1001","exp":1719...}   HMAC-SHA256(header+"."+payload, secret)
①Base64 编码，②只签名不加密（可解码阅读），③篡改任何一位签名校验必失败
```

### 3.2 JWT 三大痛点与解法

| 痛点 | 问题 | 解法 |
|:---|:---|:---|
| **无法主动注销** | 登出后 Token 仍有效至 exp | ① Redis 黑名单（logout 时记 jti，TTL = 剩余有效期）② **版本号/会话版本**：用户表存 `token_version`，JWT 带版本，改密码/封禁时 +1，旧 Token 全部失效（推荐）|
| **续签难题** | exp 到了重新登录体验差 | access(15min) + refresh(7d)：access 过期用 refresh 换新；refresh 一次性使用 + 轮换（rotation），被盗可检测 |
| **密钥泄露** | HS256 对称密钥泄露 = 全线失守 | 服务间用 **RS256/ES256 非对称**：认证中心持私钥签发，各服务只持公钥验签，泄露也伪造不了令牌 |

```java
// 退出登录：黑名单方案（jti = JWT ID）
public void logout(String token) {
    Claims c = jwtParser.parse(token);
    long ttl = c.getExpiration().getTime() - System.currentTimeMillis();
    if (ttl > 0) redis.set("jwt:deny:" + c.getId(), "1", ttl, MILLISECONDS);
}
boolean isDenied = redis.hasKey("jwt:deny:" + jti);  // 校验链：验签 → 验 exp → 查黑名单
```

### 3.3 JWT 易错点

1. **alg:none 攻击**：早期库允许攻击者把 alg 改成 none 绕过验签 → 显式固定算法，拒绝 none。
2. **Payload 放敏感信息**：Base64 一解码就泄露（手机号/角色全集）。
3. **Token 放 localStorage**：XSS 可窃取；HttpOnly Cookie 更安全（但需防 CSRF，SameSite=Strict/Lax + CSRF Token）。
4. **没有 exp / exp 过长**：exp 必须 15~30 分钟级。

## 四、OAuth2.0（授权框架，不是认证协议）

### 4.1 四种授权模式

| 模式 | 流程 | 适用 | 现状 |
|:---|:---|:---|:---|
| **授权码 Authorization Code** | 跳授权页 → 回调拿 code → 后端换 token | 有后端的 Web 应用 | ★ 标准首选；**+PKCE** 后也适用 App/SPA |
| 简化 Implicit | 直接返回 access_token | 纯前端旧 SPA | ❌ 已废弃（token 暴露在 URL）|
| 密码 Resource Owner Password | 用户把账号密码给客户端 | 自己家第一方 App | ⚠️ 不推荐（密码暴露给客户端）|
| 客户端凭证 Client Credentials | 服务用 client_id/secret 换 token | **服务间（M2M）调用** | ★ 微服务内部调用标准做法 |

### 4.2 授权码流程（必须能画）

```
┌────────┐  1.跳转授权页   ┌────────┐  2.用户登录+同意  ┌──────────┐
│ 客户端  │───────────────▶│ 授权页  │─────────────────▶│ 认证服务器│
│(第三方) │◀───────────────└────────┘                  └────┬─────┘
│        │  3.重定向回调 ?code=abc        4.后端 code+secret 换 token
│        │◀─────────────────────────────────────────────────┘
└────┬───┘        5.带 access_token 调资源服务器
     ▼
 资源服务器（拿用户资料）       核心思想：密码只给认证服务器，客户端只拿 code
                              → 临时凭据 → access_token，全程不见密码
```

### 4.3 三个高频追问

1. **为什么要 code 中转，不直接发 token？** 回调 URL 经浏览器（不可信信道），token 直接暴露；code 一次性 + 短时效（10min），且换 token 走**后端对认证服务器的服务端调用**（带 secret），安全信道完成。
2. **PKCE 是干嘛的？** App/SPA 存不了 secret → 客户端先生成随机 `code_verifier`，把 `code_challenge=hash(verifier)` 随授权请求发出；换 token 时出示 verifier，认证服务验证哈希一致 → 防**授权码被拦截重放**。
3. **OAuth2 和 OIDC 什么关系？** OAuth2 管授权（拿 token 访问资源），**OIDC 在其上加 `id_token`（JWT，含用户身份）** 才是认证协议；「用微信登录」= OIDC。只有 access_token ≠ 登录成功。

## 五、单点登录 SSO（一个系统登录，处处通行）

### 5.1 三种实现

| 方案 | 机制 | 场景 |
|:---|:---|:---|
| **共享 Session** | 同域下 Session 存 Redis 共享 | 同一域名下子系统（最简单）|
| **CAS / OIDC（主流）** | 统一认证中心发 ticket/token，各子系统回验 | 跨域多系统 |
| SAML | XML 断言 | 传统企业 / ToB 大客户（SaaS 对接企业 IdP）|

### 5.2 CAS 流程（同 OAuth2 授权码形似）

```
访问子系统A → 未登录 → 跳认证中心 ?service=A
→ 中心登录 → 回调 A?ticket=ST-xxx → A 拿 ticket 回中心验证 → 建立本地会话
再访问子系统B → 跳中心（中心已有会话）→ 直接发 ticket 免登录 ✓
```

> 面试话术：「**OIDC 本质是 OAuth2 + 身份层，CAS 是经典.ticket 模式，二者流程同构：跳中心 → 回调票据 → 后端验证 → 本地会话**。我们选 OIDC 因为生态新、JWT 自包含、支持前端 Logout/Back-channel。」

### 5.3 统一登出

常被忽略：A 登出后 B 还在登录态。解法：**Back-Channel Logout**（中心向各子系统注册的回调推登出通知）或前端心跳校验（各系统定期向中心问会话有效性）。

## 六、二次验证与会话加固（2FA / MFA）

| 机制 | 说明 | 强度 |
|:---|:---|:---|
| 短信/邮箱验证码 | 知识+持有双因子，但 SIM 卡劫持风险 | ★★ |
| TOTP（Google Authenticator） | 时间窗 30s 的 HOTP 算法，离线可用 | ★★★ |
| Passkey/WebAuthn | 设备生物认证（指纹/FaceID），抗钓鱼 | ★★★★ |
| 异常检测 | 新设备/异地登录触发二次验证 | 风控层 |

后台系统标配：**密码 + TOTP**；支付场景再加交易密码/短信确认。

---

## 七、易错点

1. **OAuth2 当登录用**：只有 access_token 无法证明用户身份（可伪造资源响应）→ 必须 OIDC id_token 或资源服务器返回权威身份。
2. **JWT 当 Session 用**：把权限全集塞 Payload，降权不生效；Token 只放身份标识，权限查缓存（见 [RBAC表设计与落地](RBAC表设计与落地.md)）。
3. **refresh_token 不轮换**：长期有效且可重复用，泄露即灾难；每次使用后作废旧 refresh 并检测重放。
4. **回调整 forgot 校验 referer/state**：OAuth2 授权码请求必须带 `state` 随机值防 CSRF，回调时校验。
5. **同域名误用 JWT**：同域 Web 用 Session 更简单可控，别为了「潮流」上 JWT 徒增注销复杂度。
6. **CORS 与 Cookie 组合配错**：跨域携带 Cookie 必须 `Access-Control-Allow-Credentials: true` 且 origin 不能是 `*`。

---

## 八、一句话总结

> **认证解决「你是谁」：内部 Web 用 Session+Redis 强管控，多端/微服务用短时 JWT + refresh 轮换 + 版本号注销；对外授权走 OAuth2 授权码 + PKCE，联合登录上 OIDC，多系统免登用 CAS/OIDC 统一认证中心；高危操作叠 TOTP/Passkey 双因子。**
