## 第一批：修 3 个风险点（必须做）

### 1.1 EasyBI — Caffeine L1 两级缓存

**现状**：代码中只有 Redisson RMapCache，简历写了 "Redis + Caffeine 两级缓存"
**目标**：在 RMapCache 之上加 Caffeine L1 本地缓存层，实现真实两级缓存

#### 实现方案

```
┌─────────────────────────────────────────┐
│           EasybiCacheManager            │
├─────────────────────────────────────────┤
│  L1: Caffeine（本地，热点 key 缓存）     │
│    - maximumSize: 1000                  │
│    - expireAfterWrite: 60s              │
│    - 热点 key 自动提升（访问 > 3 次）    │
├─────────────────────────────────────────┤
│  L2: Redisson RMapCache（分布式）        │
│    - 已有实现，保持不变                   │
│    - TTL + maxIdleTime + LRU            │
└─────────────────────────────────────────┘
```

**核心类**：
- `TwoLevelCacheManager`：包装现有 `EasybiCacheManager`，先查 L1 miss 查 L2
- `CacheEntry`：缓存值 + 元数据（来源、过期时间）
- `CacheWriteStrategy`：写操作双删（先删 L1 再删 L2）

**面试可聊深度**：
- 缓存一致性：双删 vs 延迟双删 vs Canal 订阅 binlog
- 缓存击穿：get(key, valueLoader) 加锁防穿透（Redisson 已有）
- 缓存雪崩：随机 TTL + 多级降级
- 热点 key 自动发现与提升

**简历描述更新**：
> 设计 Redis + Caffeine 两级缓存方案（L1 本地 Caffeine 热点 key + L2 Redisson 分布式缓存），支持实时失效与惰性刷新两种策略，L1 miss 查 L2 并回填，写操作双删保证一致性，基于 LRU 算法做缓存淘汰，图表渲染效率提升 300%。

### 1.2 EasyBI — 流量计费预扣 + 定时结算

**现状**：代码中只有配额统计（easybi-monitor），无支付/预扣/结算
**目标**：实现流量包购买 → 预扣 → 定时对账结算 → 过期回收全流程

#### 实现方案

```
用户购买流量包
    │
    ▼
[1] 创建流量包订单（MySQL）
    │
    ▼
[2] 支付回调 → 流量包生效（Redis 原子加额度）
    │
    ▼
[3] API 调用 → Lua 脚本原子预扣
    │    ┌─ 检查额度 > 0
    │    ├─ 额度 - N
    │    └─ 记录预扣日志（Redis）
    │
    ▼
[4] XXL-Job 定时任务（每小时）
    │    ┌─ 对账：预扣日志 vs 实际调用记录
    │    ├─ 结算：确认扣减 or 回滚
    │    └─ 过期回收：扫描过期流量包，退还剩余额度
    │
    ▼
[5] 结算完成，生成账单
```

**核心类**：
- `TrafficPackageService`：流量包生命周期管理
- `TrafficDeductLuaScript`：预扣原子脚本（额度检查 + 扣减 + 日志记录，单线程执行）
- `TrafficSettlementJob`：XXL-Job 定时对账结算
- `TrafficPackageExpireJob`：过期回收

**面试可聊深度**：
- Redis Lua 脚本保证原子性（为什么不用分布式锁，性能差异）
- 预扣 + 结算的一致性（中间态怎么处理，对账策略）
- 幂等结算（重复执行不重复扣减）
- 高并发下的额度超卖问题

**简历描述更新**：
> 设计流量包的购买、分发、生效、过期全生命周期管理，基于 Redis Lua 脚本实现原子预扣防超卖，XXL-Job 定时对账结算保证最终一致性，过期流量包自动回收退还。

### 1.3 connector — ES 日志存储替换

**现状**：代码中 TracingLogServiceImpl 用 JPA + MySQL，简历写了 "引入 ElasticSearch 替代原有存储"
**目标**：引入 spring-data-elasticsearch，TracingLog 双写过渡，查询走 ES

#### 实现方案

```
流程执行产生日志
    │
    ▼
┌─────────────────────────────┐
│  TracingLogService           │
│  双写模式（可配置）           │
│    ├─ 写 MySQL（JPA，保底）  │
│    └─ 写 ElasticSearch（主） │
└─────────────────────────────┘
    │
    ▼
查询请求
    │
    ├─ 精确查询 → MySQL
    └─ 全文检索/聚合 → ES（毫秒级）
```

**核心类**：
- `TracingLogESRepository`：ElasticSearch 文档操作
- `TracingLogDocument`：ES 索引实体（自定义分词器适配业务字段）
- `ESMigrationService`：历史数据迁移
- `DualWriteTracingLogService`：双写过渡，可配置切换

**ES 索引设计**：
- 索引名：`tracing_log_{yyyyMM}`（按月分片）
- mapping：`flowId`、`traceId`、`stepId`、`level`、`timestamp`、`message`（分词）、`businessFields`（动态 mapping）
- 分词器：`ik_max_word` + 自定义业务词典（产品名词、组件名）

**面试可聊深度**：
- ES 索引设计（分片/副本、mapping 优化、动态 mapping 陷阱）
- 双写一致性（写失败怎么处理，数据补偿）
- MySQL → ES 数据迁移（全量 + 增量）
- 查询性能对比（MySQL LIKE %xxx% vs ES match）
- 日志保存策略（全量/采样，基于 flowId 哈希）

**简历描述更新**：
> 对日志模块进行全面重构，引入 ElasticSearch 替代原有 MySQL 存储方案，自定义 IK 分词库适配业务字段，支持全量/采样两种保存策略，双写过渡保证迁移零中断，全文检索查询性能从秒级提升到毫秒级。

## 第二批：新增高 ROI 亮点（选 1-2 个）

### 方向 A：EasyBI — Presto SQL 安全网关 ⭐推荐

**做什么**：在 EasyBI 的 SQL 执行链路上加安全网关层

```
用户提交 SQL
    │
    ▼
┌──────────────────────────────────┐
│        SQL Security Gateway      │
├──────────────────────────────────┤
│  1. AST 解析（JSqlParser）        │
│     ├─ 识别表名/字段名             │
│     ├─ 检测 SQL 注入（UNION/OR 1=1│
│     │   /--/;DROP 等）           │
│     └─ 检测危险函数（sleep/benchmark│
│        /load_file 等）            │
│                                  │
│  2. 权限注入                      │
│     └─ 基于用户角色自动在 WHERE   │
│        加数据权限条件（行列权限）  │
│                                  │
│  3. 慢查询熔断                    │
│     ├─ 执行前：SQL 预估复杂度      │
│     │  （JOIN 数量/子查询/全表扫描）│
│     └─ 执行中：超时自动 kill      │
│        （通过 Presto queryId）     │
└──────────────────────────────────┘
    │
    ▼
  安全 SQL → Presto 执行
```

**已有基础**：`EasybiSqlExecutorCacheServiceImpl` 里已有 `PrestoGrammarModifier` SQL 改写逻辑

**面试可聊深度**：
- SQL 注入防御（AST vs 正则，为什么 AST 更可靠）
- SQL 改写的性能影响
- Presto 超时 kill 的实现（需要 Presto REST API）
- 行级权限的 SQL 自动注入（MyBatis 拦截器 vs 网关层）
