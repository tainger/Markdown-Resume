## 🔴 高风险问题（必须修复）

### 问题 1：EasyBI "Redis + Caffeine 两级缓存" 与代码不符

| 项 | 内容 |
|:---|:---|
| **位置** | [resume.md 第 92 行](resume.md#L92) |
| **简历原文** | 设计 Redis + Caffeine 两级缓存方案，支持实时失效与惰性刷新两种策略，基于 LRU 算法做缓存淘汰，图表渲染效率提升 300% |
| **代码实际** | `easybi-core/cache/EasybiCacheManager.java` 使用 **Redisson RMapCache**，不是 Caffeine。pom.xml 中无 Caffeine 依赖 |
| **代码证据** | `EasybiQueryCache.java`：`RMapCache<String, Object>` + `maxIdleTime` + `EvictionMode.LRU` + `get(key, valueLoader)` 加锁按需加载 |
| **风险** | 面试官问「Caffeine 的淘汰策略配置了什么？L1 和 L2 的一致性怎么保证？」→ 答不上来 |

**修复方案（二选一）**：

#### 方案 A：二次开发补代码（推荐，让简历变真实）

在 EasyBI 中增加 Caffeine L1 缓存层，包装现有 Redisson RMapCache：

```
L1: Caffeine（本地缓存，热点 key，LRU + 短 TTL）
L2: Redisson RMapCache（分布式缓存，LRU + TTL + maxIdleTime）

读路径：L1 hit → 直接返回
        L1 miss → 查 L2 → 回填 L1 → 返回
写路径：更新 L2 + 删除 L1（双删策略）
```

- 工作量：半天
- 面试可聊深度：缓存一致性（双删 vs 延迟双删）、缓存击穿/穿透/雪崩、Caffeine W-TinyLFU vs Redis LRU、热点 key 自动提升
- 对应计划：[简历二次开发计划 1.1 节](简历二次开发计划.md)

#### 方案 B：改简历文字

```
设计基于 Redisson RMapCache 的分布式缓存方案，支持 LRU 淘汰、TTL + maxIdleTime 空闲过期、
get(key, valueLoader) 加锁按需加载防穿透，图表渲染效率提升 300%
```

- 工作量：5 分钟
- 缺点：少了 Caffeine 这个技术亮点

**状态**：⬜ 待确认方案

### 问题 3：APASS "引入 ElasticSearch 替代原有存储" 与代码不符

| 项 | 内容 |
|:---|:---|
| **位置** | [resume.md 第 105 行](resume.md#L105) |
| **简历原文** | 对日志模块进行全面重构，引入 ElasticSearch 替代原有存储方案，支持两种日志保存策略（全量/采样），实现动态更新分词库以适配业务字段变化，查询性能大幅提升 |
| **代码实际** | `connector` 仓库当前分支 pom.xml 中**无 elasticsearch 依赖**，`TracingLogServiceImpl` 使用 **Spring Data JPA + MySQL**（`TracingLogRepository`） |
| **代码证据** | `console/service/impl/TracingLogServiceImpl.java` import `org.springframework.data.jpa.domain.Specification`，继承 `TracingLogRepository extends JpaRepository` |
| **风险** | 面试官问「ES 的索引设计是怎样的？分词器怎么配的？双写一致性怎么保证？」→ 答不上来 |

**修复方案（二选一）**：

#### 方案 A：二次开发补代码（推荐）

在 connector 中引入 spring-data-elasticsearch，实现日志双写（JPA + ES），查询走 ES：

```
迁移策略：双写过渡
  ├─ 写入：同时写 MySQL + ES（保证数据安全）
  ├─ 查询：切换到 ES（利用 ES 全文检索 + 聚合）
  ├─ 一致性：异步重试 + 对账补偿
  └─ 分词器：自定义 IK 分词 + 业务字段词典动态更新
```

- 工作量：1 天
- 面试可聊深度：ES 索引设计、分词器定制、双写一致性、查询性能对比（MySQL LIKE vs ES match）
- 对应计划：[简历二次开发计划 1.3 节](简历二次开发计划.md)

#### 方案 B：改简历文字

```
对日志模块进行全面重构，优化 JPA 查询性能（Specification 动态条件 + 索引优化），
支持两种日志保存策略（全量/采样），引入 LogRetentionPolicy 日志保留策略自动清理过期日志
```

- 工作量：5 分钟
- 缺点：少了 ES 这个技术亮点

**状态**：⬜ 待确认方案
