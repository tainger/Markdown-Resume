# 短链系统

> **P7 面试核心**：短链是系统设计的「Hello World」——题面简单但能挖出**发号器、缓存击穿、分片路由、301/302 选型、统计链路**五个深坑。面试官用它做暖场题，30 分钟讲不完说明基础不扎实。本文按 SDD 七步法完整走一遍。

---

## 一、需求澄清（先问再画）

系统设计题第一坑：**没问清楚就开画**。先和面试官对齐三类需求。

### 1.1 功能性需求

| # | 需求 | 说明 | 是否必做 |
|:---:|:---|:---|:---:|
| 1 | 长链 → 短链 | 用户输入 `https://very.long.url/...`，返回 `https://t.cn/abc123` | ✅ 必做 |
| 2 | 短链 → 长链重定向 | 访问短链，30x 跳转到原长链 | ✅ 必做 |
| 3 | 自定义短码 | 用户可指定短码（如 `t.cn/my-promo`）| 选做 |
| 4 | 点击统计 | PV/UV、地域、来源、设备 | 选做（面试常追问）|
| 5 | 过期与删除 | 短码可设过期时间，到期失效 | 选做 |

### 1.2 非功能性需求

| 维度 | 目标 | 说明 |
|:---|:---|:---|
| **读多写少** | 读 QPS ≫ 写 QPS | 重定向（读）次数 ≫ 生成（写）次数，比例约 100:1 |
| **高可用** | 99.99% | 短链挂了 = 所有营销短信失效，影响范围大 |
| **低延迟** | 重定向 P99 < 50ms | 用户点短链 1 秒不跳转就关了 |
| **不可预测** | 短码防遍历 | 不能让人 `t.cn/aaa`、`t.cn/aab` 顺序爬完全部长链 |

### 1.3 范围澄清（边界）

- 是否支持批量生成？→ 先 P0 不做，扩展性留口
- 自定义短码是否限制长度？→ 限制 6~16 字符
- 短链是否长期永久？→ 默认 1 年过期，可续期
- 重定向协议？→ HTTP 302（见 §6.4）

## 二、容量估算（先粗后细）

### 2.1 假设条件

- 日均生成短链 1 亿条，读（重定向）100 亿次（10:1 读，营销短信推送场景）
- 单条短链记录 ≤ 500 字节（含长链 URL、元数据、统计字段）
- 保留 10 年 = 3650 天

### 2.2 写入量

- 写 QPS = 1 亿 / 86400 ≈ **1200 QPS**（峰值估 6000 QPS）
- 10 年存储 = 1 亿 × 3650 × 500B ≈ **182 TB**（用 1KB 留余量 = 365 TB）

### 2.3 读取量

- 读 QPS = 100 亿 / 86400 ≈ **12 万 QPS**（峰值估 60 万）
- 峰值带宽 = 60 万 × 1KB（响应体+头）≈ **600 MB/s**

### 2.4 关键结论

> 写入压力低（单 MySQL 撑得住），**读压力高（必须 Redis 缓存 + 多副本）**，存储量级 TB（必须分库分表）。这是后面所有架构决策的依据。

```
Response:
{
  "short_code": "abc123",
  "short_url": "https://t.cn/abc123",
  "expire_at": "2026-12-31"
}
```

```
GET /{short_code}
→ 302 Location: https://example.com/very/long/path?utm_source=x
（异步）→ 写入点击日志：ip / ua / referer / ts
```

## 四、数据模型与存储选型

### 4.1 表结构

```sql
-- 短链主表（按 short_code hash 分 64 库 × 64 表）
CREATE TABLE short_link (
    id            BIGINT UNSIGNED PRIMARY KEY COMMENT '自增主键，发号器分配',
    short_code    VARCHAR(16)  NOT NULL UNIQUE COMMENT 'Base62 短码',
    long_url      TEXT         NOT NULL        COMMENT '原始长链',
    user_id       BIGINT       NOT NULL        COMMENT '创建者',
    custom_alias  TINYINT      NOT NULL DEFAULT 0 COMMENT '是否自定义短码 0/1',
    expire_at     DATETIME     NULL            COMMENT '过期时间',
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user (user_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 长链去重表（避免同一长链生成多个短码，按业务策略可选）
CREATE TABLE long_url_dedup (
    long_url_md5  CHAR(32)  PRIMARY KEY,        -- 长链 md5 做 key
    short_code    VARCHAR(16) NOT NULL UNIQUE,
    UNIQUE INDEX uk_md5 (long_url_md5)
);
```

### 4.2 存储选型

| 数据 | 选型 | 原因 |
|:---|:---|:---|
| 短链主表 | MySQL 分库分表 | 强一致 + 唯一索引防重；TB 级靠分库分表横向扩 |
| 热点缓存 | Redis Cluster | 12 万读 QPS，单 Redis 撑不住，3 主 3 从集群 |
| 点击日志 | Kafka → HDFS/ClickHouse | 异步落库，OLAP 查询走列存 |
| 防爬布隆 | Redis Bitmap | 拦截不存在的短码，不打 DB |

## 六、核心深挖（面试官追问区）

### 6.1 短码生成：三种方案对比 ⭐⭐⭐

| # | 方案 | 原理 | 优点 | 缺点 | 用谁 |
|:---:|:---|:---|:---|:---|:---|
| 1 | **Hash 截断**（MD5/SHA256） | `md5(long_url)` 取前 6/7 位 | 无需中心发号器，分布式友好 | **冲突率高**（生日攻击：6 位 Base62 ≈ 568 亿容量，5000 条就 50% 冲突）| ❌ 几乎没人用 |
| 2 | **自增 ID + Base62** ⭐ | 全局发号器取 ID → Base62 编码 | **零冲突**、短码有序（防爬差但可加扰） | 依赖发号器高可用 | ✅ 主流（微博/知乎）|
| 3 | **随机生成 + DB 查重** | 随机 6 位 Base62，DB 查是否存在 | 无需发号器 | 高并发下查重率高、性能差 | ❌ 不推荐 |

> 💡 **为什么主流选自增 ID + Base62**：唯一性靠发号器保证（DB 唯一索引兜底），短码长度固定（6~7 位），实现简单。**短码有序是个安全缺点**（可被遍历），生产会做「**ID 加扰/异或盐值**」让短码看起来无序。

### 6.2 Base62 编码原理

把「数字 ID」转成「62 进制字符串」：

```
62 进制字符表（顺序固定）：
0 1 2 ... 9 a b c ... z A B C ... Z   （共 62 个字符）

示例：ID = 123456789
123456789 / 62 = 1991237 ... 55 → 第 55 位 = 's'
1991237   / 62 = 32116   ... 45 → 第 45 位 = 'J'
32116     / 62 = 518     ...  0 → 第 0 位 = '0'
518       / 62 = 8       ... 22 → 第 22 位 = 'm'
8         / 62 = 0       ...  8 → 第 8 位 = '8'
→ 反转：'8mJ0s'（5 位，左侧补 0 到 6 位 = '08mJ0s'）
```

**容量速记**：

| 短码长度 | Base62 容量 | 够用场景 |
|:---:|:---|:---|
| 6 位 | 62⁶ ≈ **568 亿** | 国内主流短链平台（t.cn）|
| 7 位 | 62⁷ ≈ **3.5 万亿** | bit.ly 等全球服务 |
| 8 位 | 62⁸ ≈ 218 万亿 | 极端长期 |

### 6.3 Base62 编码 Java 实现

```java
public class Base62 {
    // 字符表顺序固定，编码与解码必须一致
    private static final char[] CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ".toCharArray();
    private static final int RADIX = 62;

    // 数字 ID → Base62 字符串（左侧不补 0，由调用方决定是否补齐到 6 位）
    public static String encode(long id) {
        if (id == 0) return "0";
        StringBuilder sb = new StringBuilder();
        while (id > 0) {
            sb.append(CHARS[(int)(id % RADIX)]);
            id /= RADIX;
        }
        return sb.reverse().toString();
    }

    // Base62 字符串 → 数字 ID（用于重定向时反查也可以，但通常直接按短码查 DB）
    public static long decode(String code) {
        long id = 0;
        for (char c : code.toCharArray()) {
            int idx = indexOf(c);
            if (idx < 0) throw new IllegalArgumentException("非法字符: " + c);
            id = id * RADIX + idx;
        }
        return id;
    }

    private static int indexOf(char c) {
        // 实际生产用 Map<Character,Integer> 反查更优，这里展示逻辑
        for (int i = 0; i < CHARS.length; i++) if (CHARS[i] == c) return i;
        return -1;
    }
}
```

### 6.4 发号器选型（决定短码唯一性）

详见 [ID生成器.md](ID生成器.md)，这里只列结论：

| 方案 | 唯一性 | 有序性 | 性能 | 时钟回拨 | 用谁 |
|:---|:---|:---|:---|:---|:---|
| UUID | 全局唯一 | **无序**（不适合做 DB 主键和短码源）| 高 | 无 | ❌ 短码场景不用 |
| DB 自增 | 唯一 | 严格递增 | 低（DB 瓶颈）| 无 | 小流量可 |
| **Snowflake** ⭐ | 全局唯一 | **趋势递增** | 单机 4M ID/s | **有时钟回拨** | ✅ 主流（需处理回拨）|
| **号段模式（Leaf）** ⭐ | 全局唯一 | 趋势递增 | DB 批量分配极高 | 无 | ✅ 推荐（与 Snowflake 二选一）|

> 生产首选：**Snowflake（主）+ 号段（兜底）双轨**。发号器高可用 = 服务可横向扩 + 时钟回拨兜底。

### 6.5 缓存设计：三道防线防 DB 打穿 ⭐⭐⭐

读 QPS 12 万，MySQL 单实例 ~3 千 QPS，**必须靠缓存撑住 99% 流量**。但缓存本身有三个坑：

```
请求短链 abc123
   │
   ▼
① 布隆过滤器（Redis Bitmap）── 短码 abc123 是否存在？
   │   存在可能误判 → 进 ②
   │   不存在 → 100% 不存在，直接返回 404（防缓存穿透）
   ▼
② Redis 缓存 long_url ── 命中？
   │   命中 → 直接 302（99% 走这条）
   │   未命中 → 进 ③（可能是缓存击穿，热点 key 失效）
   ▼
③ DB 查询（带互斥锁，防击穿雪崩）
   │   查到 → 回填 Redis + 布隆 → 302
   │   查不到 → 返回 404（短码非法）
```

| 坑 | 现象 | 解法 |
|:---|:---|:---|
| **缓存穿透** | 大量请求查**不存在的短码**，布隆和缓存都拦不住，直打 DB | **布隆过滤器**（启动加载全量短码；新增时同步写入布隆）|
| **缓存击穿** | 热点短码过期瞬间，几万请求同时查 DB | **互斥锁**（Redis SETNX，只放一个请求查 DB 回填）或**热点永不过期 + 异步刷新**|
| **缓存雪崩** | 大量短码同时过期 | **过期时间加随机抖动**（1~7 天随机），避免同时失效 |

### 6.6 互斥锁防击穿 Java 伪代码

```java
public String getLongUrlWithCache(String shortCode) {
    // 1. 布隆过滤（防穿透）
    if (!bloomFilter.mightContain(shortCode)) {
        return null;  // 100% 不存在，直接返回 404
    }

    // 2. Redis 缓存
    String longUrl = redis.get("sl:" + shortCode);
    if (longUrl != null) {
        return longUrl;  // 99% 走这里
    }

    // 3. 缓存未命中，加互斥锁防击穿（只让一个请求查 DB，其他等）
    String lockKey = "lock:sl:" + shortCode;
    try {
        // SETNX + 过期时间，避免锁泄漏
        boolean locked = redis.setIfAbsent(lockKey, "1", 3, SECONDS);
        if (!locked) {
            // 等一下再读缓存（别人查到了会回填）
            Thread.sleep(50);
            return redis.get("sl:" + shortCode);
        }
        // 双重检查：拿到锁后再查一次缓存（可能别人刚回填）
        longUrl = redis.get("sl:" + shortCode);
        if (longUrl != null) return longUrl;

        // 查 DB
        longUrl = shortLinkMapper.selectLongUrlByCode(shortCode);
        if (longUrl != null) {
            // 回填缓存（过期时间加随机抖动防雪崩）
            int ttl = 86400 + ThreadLocalRandom.current().nextInt(0, 3600);
            redis.setex("sl:" + shortCode, ttl, longUrl);
        }
        return longUrl;
    } finally {
        redis.del(lockKey);
    }
}
```

### 6.7 301 vs 302 重定向选型 ⭐

| HTTP 状态 | 含义 | 浏览器行为 | 优点 | 缺点 |
|:---|:---|:---|:---|:---|
| **301** | 永久重定向 | **缓存到本地**，下次直接跳，不再请求短链服务 | 服务端压力极小 | **统计不到后续点击**；长链改了，用户被锁死在旧长链 |
| **302** ⭐ | 临时重定向 | **每次都回短链服务**再跳 | **能统计点击 + 防预缓存长链失效** | 服务端压力大（但缓存方案能扛住）|

> 💡 **生产首选 302**：短链核心价值之一是「点击统计」（PV/UV/来源），301 会丢失这个数据。服务端压力靠 Redis 缓存解决。bit.ly、t.cn、dwz.cn 全部用 302。

### 6.8 分库分表与路由

写 QPS 仅 1200，单库能扛，但 10 年 365 TB 存储**必须分库分表**：

- **分片键**：`short_code`（重定向时只带短码，必须按短码路由）
- **分片算法**：`hash(short_code) % 64`（64 库 × 64 表 = 4096 张表，每张 ~90GB）
- **自定义短码**：直接按 hash 路由到对应分片
- **按 ID 查询**（用户查自己生成的）：维护 `user_id → short_code` 索引表（ES 或 Redis ZSet）

> 注意：`id` 是发号器分配的趋势递增 ID，**不能作为分片键**（按 ID 范围分片会导致短码分布不均）。

## 七、扩展性与容错

### 7.1 多机房与异地多活

- 短链是**强读多写少**场景，**读多机房 + 写单机房**（写主机房 → binlog 同步到从机房）
- 营销短信场景：短信发出到用户点击有「分钟级延迟」，从机房同步延迟 1 秒可接受
- 跨机房发号器：Snowflake 的 workerId 段做机房位（10 位机房 ID 段），保证全局唯一

### 7.2 热点短码专项处理

营销大促时某条短链 QPS 突然 10 万+：

| 方案 | 实现 | 适用 |
|:---|:---|:---|
| 本地缓存（Caffeine）| 网关每实例缓存热点短码 1~3 秒 | **首选**，把 10 万 QPS 降到几百 |
| 多副本 key | `sl:abc123:0` ~ `sl:abc123:9`，随机读副本 | 单 key 击穿 Redis 集群单分片 |
| CDN | 把 302 响应推到 CDN 边缘节点 | 短码固定 + 跳转目标固定时可用 |

### 7.3 监控告警

- **核心 SLI**：重定向 P99 延迟、缓存命中率（应 > 99%）、DB QPS（应 < 1000）
- **告警**：缓存命中率 < 95% 立刻告警（可能布隆失效或大量新短码未预热）
- **链路追踪**：每个短链生成/重定向打 TraceID，方便排障

## 八、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「Hash 截断做短码最简单」 | ❌ 生日攻击冲突率高，6 位 Base62 在 5000 条就 50% 冲突。要么自增 ID + Base62，要么用更长的短码（7~8 位）+ DB 唯一索引兜底 |
| 2 | 「短码长度 6 位够用了」 | ⚠️ 视场景：自增 ID 6 位 Base62 容量 568 亿「够用」但 ID 递增会被遍历爬取，需加扰；随机短码 6 位冲突率高，建议 7~8 位 |
| 3 | 「布隆过滤器 100% 准确」 | ❌ 布隆有假阳性（说存在可能不存在），但假阴性 0%（说不存在一定不存在）。所以只能用来「挡掉不存在的」，挡不住「假存在的」|
| 4 | 「缓存设置 1 小时过期最简单」 | ❌ 大量短码同时过期 = 雪崩。必须**过期时间加随机抖动**（基础 TTL + 随机 0~1 小时）|
| 5 | 「301 性能更好，生产应该用 301」 | ❌ 301 会缓存到浏览器，**后续点击统计全丢**，长链改了用户跳错。短链业务的核心价值之一就是统计，**必须 302** |
| 6 | 「自定义短码也走 Base62」 | ❌ 自定义短码是用户输入的字符串，不走编码流程，直接入库（唯一索引兜底）。但要做**敏感词过滤 + 长度限制**（6~16 字符）|
| 7 | 「发号器用 UUID 最简单」 | ❌ UUID 无序 + 36 字符，做 DB 主键会让 InnoDB 主键索引频繁页分裂（写放大 3~5 倍），**不适合做短码源** |
| 8 | 「分片键选 id」 | ❌ 重定向请求只带 short_code，按 id 分片要额外查一次映射表。必须按 `short_code` 分片，让重定向一次路由到位 |
