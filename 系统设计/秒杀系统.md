# 秒杀系统

> **P7 面试核心**：秒杀是系统设计综合题——**限流、缓存、MQ、锁、库存、防刷**六大主题全部用上。一道题考完 P7 的所有基本功。核心口诀：「**流量层层削减，绝不直接打 DB**」。

## 二、容量估算

### 2.1 假设条件

- 单品库存 10 万件
- 商品详情页 PV 1 亿次（首页 + 详情 + 分享）
- 抢购按钮点击 1000 万次（10% 用户点击）
- 实际成单 10 万单（=库存数）

### 2.2 流量漏斗（核心）

```
首页流量      ：1 亿次 PV / 30 分钟 ≈ 5.5 万 QPS
   │
   ▼ 详情页
详情页请求    ：1 亿次 PV / 30 分钟 ≈ 5.5 万 QPS
   │
   ▼ 抢购按钮
抢购点击      ：1000 万次 / 1 分钟 ≈ 16.7 万 QPS  ← 峰值！
   │
   ▼ 库存校验（Redis 预减）
有效下单请求  ：10 万次（库存售罄后拦截 990 万次）
   │
   ▼ MQ 异步落库
实际 DB 写入  ：10 万次 / 1 分钟 ≈ 1700 QPS  ← DB 撑得住
```

> **核心结论**：1000 万次抢购 → 10 万次下单 → DB 只承受 1700 QPS。**层层削减是秒杀架构的灵魂**。

## 六、核心深挖

### 6.1 防超卖三道闸 ⭐⭐⭐（最高频考点）

> 「不能超卖」是秒杀的红线。三道闸从轻到重，任何一道挡住都不会超卖：

| 闸 | 位置 | 原子操作 | 失败兜底 |
|:---:|:---|:---|:---|
| **第一道** | Redis 预减库存 | `DECR stock:actId` 返回值 < 0 → 拦截 | Redis 挂了？走第二道 |
| **第二道** | MQ 串行化下单 | 单 partition 单消费者 = 顺序消费 | DB 写入冲突？走第三道 |
| **第三道** | DB 乐观锁 | `UPDATE ... SET stock = stock - 1 WHERE stock > 0` | 影响行数 = 0 → 抛异常回滚 |

#### 第一道：Redis 原子预减库存

```lua
-- eval 这个 Lua 脚本，保证「判断+扣减」原子
-- KEYS[1] = stock:actId, ARGV[1] = userId, ARGV[2] = limit
local stock = tonumber(redis.call('GET', KEYS[1]))
local bought = tonumber(redis.call('SISMEMBER', KEYS[1]..':bought', ARGV[1]))
if bought == 1 then return -2 end                  -- 已抢过（限购1）
if stock == nil or stock <= 0 then return -1 end  -- 售罄
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[1]..':bought', ARGV[1])
return 1                                           -- 抢购成功，进入MQ
```

```java
public BuyResult tryBuy(Long activityId, Long userId) {
    String stockKey = "stock:" + activityId;
    String boughtKey = stockKey + ":bought";
    // 执行 Lua 脚本：检查 + 扣减 + 标记，原子操作
    Long ret = redisTemplate.execute(SECKILL_LUA, List.of(stockKey, boughtKey),
                                     String.valueOf(userId), "1");
    if (ret == -2) return BuyResult.repeatBuy();   // 已抢过
    if (ret == -1) return BuyResult.stockOut();    // 售罄
    // 抢购成功，发 MQ（异步落库，削峰）
    mqTemplate.send("seckill-order", new OrderMsg(activityId, userId));
    return BuyResult.queued("下单中，请稍候");
}
```

#### 第二道：MQ 串行化下单

- 同一 `activityId` 的订单消息路由到**同一 Kafka partition**（key = activityId）
- 单消费者单线程消费 = **同一活动的下单完全串行**
- 即使 Redis 异常让两个用户都进了 MQ，DB 写时也只有一条能成功

#### 第三道：DB 兜底

```java
// 用行级条件更新做乐观锁，影响行数=0 说明库存不足
int rows = activityMapper.deductStock(activityId, quantity);
if (rows == 0) {
    // DB 也售罄（理论上不该到这里，兜底）
    throw new StockOutException();
}
// 唯一索引 uk_user_sku_act 防重复下单（重复直接抛异常）
seckillOrderMapper.insert(order);
```

### 6.2 库存预热（开抢前把库存推到 Redis）

活动开始前 30 分钟，把 DB 库存同步到 Redis：

```java
@Scheduled(cron = "0 */5 * * * ?")  // 每 5 分钟扫描即将开始的活动
public void preheatStock() {
    List<SeckillActivity> startingSoon = activityMapper.listStartingWithin(30, TimeUnit.MINUTES);
    for (SeckillActivity act : startingSoon) {
        String stockKey = "stock:" + act.getId();
        // 用 set NX，避免覆盖已扣减的库存（活动开始后不预热）
        redisTemplate.opsForValue().setIfAbsent(stockKey, act.getAvailable());
        // 加载限购用户集合（活动期间用 SET 标记）
        redisTemplate.opsForSet().add(stockKey + ":bought");  // 空集合
    }
}
```

> 注意：库存预热**必须用 SETNX 而不是 SET**，否则活动开始后再次预热会重置已扣减的库存。

### 6.3 热 key 打散（防单 key 击穿 Redis 集群）

10 万件库存的 `stock:actId` 单 key QPS 16 万，**全部打到 Redis 集群同一分片**，单分片被打爆 = 全站雪崩。

| 方案 | 实现 | 适用 |
|:---|:---|:---|
| **多副本 key**（推荐）| 库存拆 10 份：`stock:act:0`~`:9` 各 1 万；用户随机路由到某副本 DECR | **首选**，分片均衡 |
| **本地缓存标记** | 副本售罄后用 Caffeine 标记「已售罄」，本地拦截 | 进一步挡 Redis |
| **读主从分离** | 库存查询走从库，扣减走主库 | 减少主库读压力 |

```
库存 100000 → 10 个副本各 10000
   stock:act:0  stock:act:1  ...  stock:act:9
       10000      10000             10000

用户 A → hash(userId) % 10 = 3 → DECR stock:act:3
   副本 3 售罄（值=0）→ 重新路由到副本 4（兜底重试 1~2 次后报售罄）
```

### 6.4 异步下单与超时回滚

```
Redis 抢购成功 ──MQ──► 异步下单服务
                          │
                          ▼
                  DB 扣库存 + 创建订单（待支付）
                          │
                          ▼ 发送「订单创建」事件
                  Push 通知 → 用户跳支付页
                          │
                  ┌───────┴────────┐
                  ▼ 15min 内支付     ▼ 15min 超时未支付
              订单已支付          定时任务扫超时订单
              库存变「已售」      → 取消订单
                                → 回滚 Redis 库存（INCR）
                                → 回滚 DB 库存
                                → 删除用户限购标记
```

**超时回滚 Java 伪代码**：

```java
// 用 RocketMQ 延迟消息做超时（也可用 Redis ZSet 定时扫描）
@RocketMQMessageListener(topic = "order-timeout-check", delayLevel = 14)  // 15min
public class OrderTimeoutListener {
    public void onMessage(OrderMsg msg) {
        SeckillOrder order = orderMapper.selectByNo(msg.getOrderNo());
        if (order == null || order.getStatus() != STATUS_UNPAID) return;
        // 1. DB 取消订单 + 回滚库存（同事务）
        orderMapper.cancelWithStockRollback(order);  // UPDATE stock = stock + qty
        // 2. Redis 回滚库存 + 删除限购标记（保证最终一致）
        redisTemplate.opsForValue().increment("stock:" + order.getActivityId());
        redisTemplate.opsForSet().remove("stock:" + order.getActivityId() + ":bought",
                                         String.valueOf(order.getUserId()));
    }
}
```

> 注意：Redis 回滚必须**幂等**——重复消费 MQ 会导致库存被多 INCR。用 `stock_log` 表唯一键 + Redis SETNX 标记回滚已完成。

### 6.5 接入层限流与防刷

```
用户 ─► Nginx 限流（IP/UA 维度，令牌桶）
       │   ─ 5w IP 限流，超出返回 429
       │   ─ 异常 UA 拦截（curl/scrapy）
       ▼
       验证码 ── 人机校验 + 拉平流量尖峰
       │   ─ 开抢前 5 秒发验证码，避免 0 秒瞬时尖峰
       ▼
       预约 token 校验（必须先预约才能抢）
       │   ─ 没预约直接 403
       ▼
       应用层 Sentinel 集群限流
       │   ─ 每用户每秒最多 1 次（防连点）
       │   ─ 全局每秒 N 万（保护下游）
       ▼
       Redis 预减库存（核心逻辑）
```

### 6.6 防黄牛（业务层）

| 手段 | 实现 | 效果 |
|:---|:---|:---|
| **预约制** | 提前 24h 预约 + 实名认证，发 token 才能抢 | 拦截机器批量注册 |
| **限购 1 件** | DB 唯一索引 `(user_id, sku_id, activity_id)` 兜底 | 防同一用户多次抢 |
| **设备指纹** | 同设备指纹限 1 次（fingerprint.js）| 防同一设备换账号 |
| **IP 频控** | 同 IP/网段每秒限 N 次 | 防机房刷 |
| **风控黑名单** | 历史违规账号/IP 进黑名单 | 长期治理 |

## 七、扩展性与容错

### 7.1 Redis 集群全挂的兜底

极端情况 Redis Cluster 整个挂了：

| 方案 | 实现 | 代价 |
|:---|:---|:---|
| **降级到 DB 乐观锁** | 直接走 DB `WHERE stock > 0` | QPS 降到 DB 承受范围（~3000），大量用户失败 |
| **暂停抢购** | 返回「活动异常，正在恢复」 | 防超卖但影响体验 |

> 生产策略：Redis 主从 + 集群（3 主 3 从），挂一半仍可用；全挂时降级到 DB 兜底 + 风控暂停。

### 7.2 MQ 削峰后积压

抢购峰值 16 万 QPS，下单消费能力 1.7 万 QPS，**积压 14 万消息/秒**：

- 活动持续 1 分钟 = 积压 840 万消息
- 用 RocketMQ/Kafka，单 partition 消费能力 ~1 万 QPS
- **扩容 partition 数 + 消费者实例**（注意 partition 数 = 消费者并发上限）
- **降级策略**：积压超过 100w → 告诉用户「排队中」，前端轮询订单状态

### 7.3 监控告警

| SLI | 告警阈值 | 处置 |
|:---|:---|:---|
| Redis DECR 成功率 | < 95% | 检查是否预热失败 |
| MQ 积压 | > 100w | 扩容消费者 |
| DB QPS | > 5000 | 限流降级 |
| 下单 P99 延迟 | > 500ms | 排查消费瓶颈 |
| 库存对账差异 | > 0 | **立即人工介入**（可能超卖）|

### 7.4 库存对账（防资损）

每分钟对账 Redis 剩余 + DB 剩余 + 订单数：

```
理论剩余 = 初始库存 - 已支付订单 - 待支付订单
Redis 剩余 ≈ 理论剩余（允许秒级延迟）
DB 剩余   ≈ 理论剩余

不一致告警 → 立即排查 → 必要时暂停活动
```

## 八、易错点 ⚠️

| # | 易错点 | 正确理解 |
|:---:|:---|:---|
| 1 | 「Redis DECR 防超卖就稳了」 | ❌ Redis 挂了或 Lua 脚本写错都可能漏。**必须三道闸**（Redis + MQ 串行 + DB 乐观锁），DB 是最后兜底 |
| 2 | 「库存预热用 SET 就行」 | ❌ SET 会覆盖已扣减的库存！活动开始后再次预热会把剩余库存重置成全量。**必须用 SETNX**（不存在才设置）|
| 3 | 「Redis 库存回滚用 INCR 就行」 | ❌ MQ 重复消费会让 INCR 被执行多次，库存凭空变多。回滚必须**幂等**（用 stock_log 唯一键 + SETNX 标记）|
| 4 | 「下单成功立刻扣 DB 库存」 | ❌ 高并发下 DB 行锁竞争激烈（同一行 UPDATE）。**MQ 削峰 + 串行消费** = DB QPS 从 16w 降到 1.7w |
| 5 | 「热 key 用多副本 key 就完美」 | ⚠️ 副本售罄后路由到其他副本的重试逻辑要小心，**避免无限重试**（最多重试 2 次后报售罄）|
| 6 | 「用户连点会重复下单」 | ❌ 用 Redis SET 标记已抢 + DB 唯一索引 `(user_id, sku_id, activity_id)` 双重兜底 |
| 7 | 「订单超时回滚库存就行」 | ⚠️ 回滚后用户又来抢，会触发「限购已抢」标记拦住。**回滚要同时删 Redis 限购标记**，否则用户没库存也没法再抢 |
| 8 | 「秒杀用本地缓存标记售罄就够」 | ❌ 多实例本地缓存不一致，某实例标记售罄但实际还有。**本地标记只能挡住「全局已确认售罄」**，必须由 Redis 全局确认售罄后再写到本地 |
| 9 | 「详情页库存实时查 Redis」 | ❌ 100w QPS 查 Redis 也是压力。库存展示用**本地缓存 1 秒过期**，不要求绝对精确（用户看到「还有 100 件」实际可能 80 件，不影响下单校验）|
| 10 | 「支付完才扣 DB 库存」 | ❌ 下单时就扣 DB 库存（待支付状态），超时回滚。否则支付时再扣会撞行锁。下单扣 = 把锁竞争分散到下单时（已被 MQ 削峰）|

## 九、一句话总结

> 秒杀的本质是「**流量层层削减 + 库存三道闸防超卖 + 异步削峰保护 DB + 库存对账防资损**」。面试核心讲清三件事：①为什么不打 DB（MQ 削峰）②怎么不超卖（Redis + MQ 串行 + DB 三道闸）③怎么防黄牛（预约 + 限购 + 风控）。
