# AI Agent 设计哲学：从「会聊天的模型」到「会做事的系统」

>
> 这两年，几乎每个人都用过大模型对话。但从「能对话」到「能替你把一件事从头做完」，中间隔着一整套工程哲学。本文想聊聊：一个真正可用的 AI Agent，背后到底在坚持哪些设计原则。文中会结合开源框架 [AgentScope](https://github.com/agentscope-ai) 的模块设计做印证——不是讲某个 API 怎么调，而是想说清楚**「为什么这样设计」**。

## 一、先厘清：Agent 到底和「聊天机器人」差在哪

很多人把 Agent 理解成「更聪明的聊天框」，这是最大的误解。

一个聊天机器人做的是**单轮映射**：你问一句，它答一句，答完就结束。而 Agent 做的是**带目标的循环**：

```
        ┌─────────────────────────────────────┐
        │                                     │
   目标 → 观察环境 → 思考(LLM) → 决定动作 → 执行工具 → 观察结果
        │                                     │
        └──────────── 未达成目标则继续 ──────────┘
                              ↓
                          目标达成 → 输出
```

关键差别就一个词：**自主循环（agentic loop）**。模型不再是「一次性给出答案」，而是「反复地感知—决策—行动，直到目标完成」。这个循环带来了 Agent 全部的能力，也带来了它全部的工程难题。

> 一句话概括：**大模型是大脑，Agent 是让这个大脑长出手脚、记忆和分寸的完整身体。**

下面这些设计原则，本质上都在回答同一个问题——**如何让这个自主循环既强大，又可控**。

---

## 二、原则一：模型是「推理引擎」，不是「万能黑盒」

第一个哲学转变：**不要指望模型什么都会，而要把它当成一个只擅长「推理和语言」的引擎，把其余能力用工程手段补齐。**

模型天生有三个短板：

| 短板 | 表现 | 工程补法 |
|:---|:---|:---|
| **没有记忆** | 关掉窗口就忘光，上下文有长度上限 | 外挂记忆系统（memory / RAG） |
| **不能行动** | 只会输出文本，碰不到真实世界 | 工具调用（tool / MCP） |
| **会一本正经胡说** | 幻觉、算错数、编造事实 | 让它用工具查证，而非凭空回答 |

好的 Agent 框架不会试图「让模型更聪明」，而是**围绕模型的短板搭脚手架**。在 AgentScope 的模块划分里，这一点体现得很直白——`model` 只负责对接推理引擎，`memory`、`tool`、`rag` 各自成模块补足短板。**职责分离，各修各的短板**，这就是第一条哲学。

---

## 三、原则二：记忆要「分层」，而不是「全塞进去」

新手常犯的错：把所有历史对话一股脑塞进上下文，塞到模型报错为止。

这行不通。上下文窗口是有限且昂贵的资源，真正的记忆设计是**分层**的：

```
┌────────────────────────────────────────────┐
│  短期记忆（当前对话上下文）  ← 塞进 prompt      │
├────────────────────────────────────────────┤
│  长期记忆（跨会话的用户偏好、事实）← 需要时检索    │
├────────────────────────────────────────────┤
│  外部知识（文档/数据库）← RAG 按需召回          │
└────────────────────────────────────────────┘
```

- **短期记忆**：本轮任务的上下文，直接进 prompt，但要有淘汰/摘要策略防止爆窗口；
- **长期记忆**：用户是谁、之前做过什么决定，存在外部存储，**用到才捞**；
- **外部知识**：海量文档不可能全进上下文，靠 RAG（检索增强）按相关度召回片段。

这也是为什么成熟框架会把 `memory` 和 `rag` 拆成两个独立模块——它们解决的是不同时间尺度、不同来源的「记住」。

> 设计哲学：**上下文是稀缺资源，记忆的艺术不是「记住一切」，而是「在合适的时机，只召回此刻需要的那部分」。**

---

## 四、原则三：工具是 Agent 的手脚，而边界是它的分寸

让模型「能做事」，靠的是**工具调用**——模型输出「我要调用 `search(query)`」，框架执行后把结果喂回去。这一步让 Agent 从「嘴强王者」变成「真能干活」。

但工具一旦能碰真实世界（删文件、发消息、花钱调 API），**风险也随之而来**。所以工具设计有两条并行的哲学：

**1）标准化接入 —— 让工具可插拔。** 与其为每个工具写一套胶水代码，不如定义统一协议。业界的 **MCP（Model Context Protocol）** 就是干这个的：把「工具」抽象成标准接口，Agent 可以像插 U 盘一样接入任意工具。AgentScope 的 `tool/mcp` 模块正是这个思路。

**2）权限与确认 —— 让工具有边界。** 危险操作必须有闸门。这就是为什么框架里会有 `permission`（权限）模块：

```
模型想执行 rm -rf /data
        ↓
  权限系统拦截 → 判定为高危
        ↓
  要么需要人工确认，要么直接拒绝
```

> 设计哲学：**给 Agent 手脚的同时，必须给它分寸。一个能删库的 Agent，如果没有权限边界，就是一颗定时炸弹。** 好的框架把「能力」和「授权」分开设计——工具提供能力，权限系统决定这个能力此刻能不能用。

---

## 五、原则四：复杂任务要「分而治之」——子代理与技能

当任务复杂到一个 Agent 扛不动时，哲学是**分解**，而非「造一个更大的 prompt」。

两种典型分解方式：

- **子代理（Subagent）**：主 Agent 把一个独立子任务（比如「去把这十个文件都搜一遍」）派给一个专门的子 Agent，子 Agent 干完只回报**结论**，不把一路的中间垃圾塞回主上下文。这既省 token，又让主 Agent 的「注意力」保持聚焦。AgentScope 的 `tool/subagent` 就是这个模式。
- **技能（Skill）**：把「某类任务的标准打法」封装成可复用的指令包。遇到匹配的任务，直接加载这套打法，而不是每次让模型从零现想。对应 `skill` 模块。

```
              主 Agent（规划全局）
             /        |         \
      子Agent:搜索  子Agent:分析  子Agent:测试
         （各自独立上下文，只回报结论）
```

> 设计哲学：**单个 Agent 的上下文和注意力是有限的。与其造一个无所不能的巨型 Agent，不如让它学会「委派」和「复用套路」——这和人类团队协作、沉淀方法论，是同一个智慧。**

## 六、原则五：过程必须「可中断、可观测、可回放」

这是最容易被初学者忽略、却最能区分「玩具」和「产品」的一条。

Agent 是个长时间自主运行的循环，一旦跑起来，你会立刻面临三个现实问题：

| 问题 | 需要的能力 | 对应设计 |
|:---|:---|:---|
| 它跑偏了，我想喊停 | **可中断（interruption）** | 随时能安全打断循环，而非等它跑完 |
| 它到底在干嘛？为什么这么决策？ | **可观测（tracing / hook）** | 全链路埋点，每一步决策可追溯 |
| 它崩了，能不能从断点继续？ | **可恢复（state）** | 状态可持久化、可回放 |

AgentScope 里有 `interruption`、`tracing`、`hook`、`state` 一整组模块专门伺候这件事——它们不增加 Agent 的「聪明」，但决定了它能不能**真正上生产**。

> 设计哲学：**一个不能被打断、不能被观察、崩了就得从头再来的 Agent，无论多聪明，都只是 Demo。生产级 Agent 的一半工程量，都花在「让这个黑盒变得透明、可控、可救」上。**

## 七、把这些原则串起来：一次完整的 Agent 运行

把前面的原则落到一次真实运行，大概长这样：

```
用户目标：「帮我把这个仓库里所有 TODO 整理成一份报告」
   │
   ├─ 记忆：调出用户偏好的报告格式（长期记忆）
   │
   ├─ 循环开始 ────────────────────────────┐
   │    思考：需要先搜索所有 TODO             │
   │    工具：调用搜索工具（权限校验通过）      │
   │    观察：拿到 200 处 TODO               │
   │    分解：派子 Agent 分类汇总（省主上下文） │
   │    思考：套用报告技能，生成结构           │
   │  （全程 tracing 记录每一步，可随时中断）   │
   └────────────────────────────────────────┘
   │
   └─ 目标达成，输出报告；状态落盘，可回放
```

你会发现，**没有一步是「模型独自完成」的**——模型只负责「思考下一步做什么」，而记忆、工具、权限、子代理、可观测性这些工程能力，共同把这个「思考」兜成了一件真正办成的事。

---

## 八、写在最后：Agent 设计的三条底层信念

如果把上面所有原则再往下压，我认为 AI Agent 的设计哲学最终只剩三条信念：

1. **模型负责「想」，工程负责「成」。** 别指望模型变全能，要用系统把它的短板补齐、把它的长板放大。
2. **能力越大，边界越重要。** 给 Agent 手脚的同时给它分寸，权限、确认、可中断不是可选项，是及格线。
3. **透明胜过聪明。** 一个可观察、可回放、可救的 Agent，远比一个更聪明但完全黑盒的 Agent 有价值。

大模型给了我们一个前所未有的「大脑」，但决定这个大脑能否真正为人所用的，从来不是参数量，而是我们围绕它建立的这套**克制而周密的工程哲学**。
