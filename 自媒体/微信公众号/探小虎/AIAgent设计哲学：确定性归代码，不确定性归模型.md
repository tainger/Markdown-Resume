# AI Agent 设计哲学：确定性归代码，不确定性归模型

过去一年，我们团队做了两个看起来很像、本质却很不一样的 AI 功能：一个是定时周报，每天自动拉取 Aone 迭代数据生成 Markdown 报告并推送到钉钉；另一个是 CodingAgent，接受自然语言需求，完成理解、规划、编码到分支提交的全流程。

一开始，我们对这两个功能都采用了 ReActAgent 方案。结果周报上线后问题不断，CodingAgent 却越走越顺。复盘下来，我们发现差距不在模型能力，而在一个更底层的问题：**这个任务的不确定性，到底是任务本身固有的，还是我们引入模型之后才产生的？**

不确定性来自哪里？

- 任务本身固有
- 模型引入的

```
任务本身固有  →  交给模型 / ReActAgent
模型引入的    →  交给代码 / 过程式
```

一旦把这个问题想清楚，Agent 的架构选型就不再是 "要不要用模型" 的二选一，而是 "哪里该用模型、哪里该写死" 的边界设计。

这篇文章就想聊聊我们沉淀下来的 AI Agent 设计哲学，以及纯过程式、纯 ReActAgent、混合方案三种路线在真实 case 中的取舍。

## 一、一个朴素判断标准

在设计 AI Agent 时，我们给自己一个判断标准：

> 如果这个任务的不确定性是任务本身固有的，交给模型；如果不确定性是引入模型之后才产生的，交给代码。

听起来像句废话，但落到工程里非常锋利。

CodingAgent 的不确定性来自需求本身：用户说「帮我改一下这个接口的错误处理」，模型必须判断改哪里、怎么改、改哪些文件。这种不确定性无法通过硬编码消除，模型是唯一能消化它的组件。

定时周报则完全相反：输入固定、输出 schema 固定、统计口径固定、推送时间固定。它原本没有任何不确定性，一旦交给 ReActAgent，反而每天都会冒出字段遗漏、格式漂移、日期算错的新问题。

这两个 case 成了我们理解 Agent 边界的最佳教材。

## 二、三种方案对比

| 维度 | 纯过程式 | 纯 ReActAgent | 混合方案 |
| --- | --- | --- | --- |
| 核心思想 | 步骤硬编码、顺序固定 | 完全由 Agent 自主推理、循环执行 | 过程式兜底边界，Agent 处理推理决策 |
| 可控性 | 高 | 中 | 高 |
| 灵活性/扩展性 | 低，新增能力要改核心代码 | 高，加入工具即可扩展 | 中高 |
| 容错/自适应 | 弱，异常处理靠手动覆盖 | 强，自动推理重试 | 中，边界内自适应 |
| 自由对话能力 | 不支持 | 原生支持 | 受限支持 |
| 延迟/成本 | 低 | 高 | 中 |
| 调试难度 | 低 | 高 | 中 |
| 适合场景 | 流程固定、步骤少、对延迟敏感 | 探索性任务、流程不确定 | 生产级确定性任务 + 局部智能决策 |

## 三、反面案例：把定时周报交给 ReActAgent，我们踩了哪些坑

### 3.1 最初的「Agent 化」思路

定时周报的需求很简单：每天固定时间查询 Aone 迭代工作项，统计进度，生成 Markdown 报告，推送到钉钉 AI 卡片。

最初实现时「Agent 化」：创建一个 ReActAgent，注册 Aone MCP 工具，写一份提示词描述查询范围和输出格式，让大模型自己调用 MCP 查询工作项，统计进度，生成报告，最后推送卡片。

从表面看，这确实是个典型 Agent 场景：有工具调用，有数据加工，有内容生成。但上线之后，问题接连暴露。

### 3.2 踩坑一：执行结果偶发误差，且无法根治

同样的提示词、同样的数据，模型每次生成的报告偶现字段遗漏、统计口径漂移、格式偏离预期 schema。为了兜底，代码里不得不加上 JSON 提取容错和「无响应就重试一次」的补丁。

但补丁只能缓解，不能消除不确定性。因为问题根源不在提示词写得不够好，而在于**我们用了一个不确定性的技术去解决一个确定性问题**。

### 3.3 踩坑二：提示词变成了没有编译器的代码

上线后每次报错，排查方式不是看代码分支，而是翻出模型的执行轨迹，反推它在哪一步「想歪了」，再回头调整提示词措辞。

> 提示词事实上变成了一段用自然语言写的程序，但没有编译器、没有类型检查、没有单元测试。

原本指望 Agent 降低研发成本，结果提示词的成本反而超过了直接写代码。

### 3.4 踩坑三：Token 大量浪费

一份周报的内容和结构完全固定，但 ReAct 循环意味着每天都要经历多轮「推理 → 调工具 → 观察」。Token 消耗是一次确定性 API 调用加字符串拼接的几十倍。

为一个每天输出几乎相同结构的报表付出这样的推理成本，性价比极低。

### 3.5 踩坑四：模型心算时间不可靠

报告涉及「近 7 天」「迭代剩余 N 天」这类时间计算，模型心算日期经常出现 off-by-one 甚至跨月错误。

最终的解法是：**时间全部由 Java 代码计算好**（今天日期、迭代名称、剩余天数），以占位符形式注入提示词，模型只负责「引用」而不允许「计算」。

走到这一步其实已经说明：凡是要求精确的环节，都在被一点点从模型手里收回来。

### 3.6 演进结果：整体回归过程式

后续同类的进度提醒任务最终整体回归过程式——锚点时间用 `TemporalAdjusters` 在代码里计算，MCP 数据查询仅引入到独立的 DataProvider，过滤、按人分组、模糊筛选全部由 Java 完成。模型仅在个别真正需要语义判断的单点被调用，甚至完全不用。

改造后结果稳定可复现，可单测，可精确排障，运行成本也降到原来的零头。

> 这个案例的教训：定时报表类任务的输入固定、输出 schema 固定、流程固定，是纯过程式的主场。把它交给 ReActAgent，本质上是用不确定性的技术去解决确定性的问题——不确定性不会消失，只会转化为线上偶发故障和无法预测的提示词调优。

## 四、正面案例：CodingAgent 如何用混合方案围住模型的不确定性

### 4.1 为什么 CodingAgent 必须用模型

与周报不同，CodingAgent 接受自然语言需求，完成理解、规划、编码、分支提交的全流程。

「如何理解需求、怎么改代码、改哪些文件」是真正的开放性问题，不用模型根本做不了；但「工作区在哪、分支叫什么、状态怎么流转」又必须绝对精确。

所以它天然适合混合方案：**用过程式保证确定性骨架，用 Agent 处理不确定性决策**。

### 4.2 严格分工

**过程式状态机负责基建：**

- 任务状态按固定顺序推进
- 入参校验、工作区目录解析（绝对路径配置 + 相对名称拼接配置的 repos 根目录）
- 编码完成后将分支名持久化到任务表
- 执行结果按 schema 落库
- 每一步都是确定性代码，可预测、可回溯

**EnhancedReActAgent 负责核心决策：**

- 需求拆解、编码策略
- 工具调用编排
- 异常自适应重试
- 全部在受 Toolkit 约束的工具集合内进行
- 通过 Hook 机制记录关键事件并外部追踪

**副作用统一收口：**

- Agent 的产出先作为中间产物，支持多次优化
- 状态变更等不可逆操作由过程式层在确定的时机统一执行
- 下游的部署环节直接读取任务表中的分支字段，而不是再问一次模型——正因为这个字段是过程式代码写入的，下游才敢直接信任它

### 4.3 效果

模型的不确定性被限制在「编码决策」这个隔间里，即使某次推理路径不同，对外暴露的状态流转和数据契约始终一致。

排障时先看状态机日志定位到环节，再看该环节内的 Agent 推理日志，问题定位路径清晰。

## 五、两个案例合起来看

| 维度 | 定时周报 | CodingAgent |
| --- | --- | --- |
| 任务性质 | 输入/输出/流程全固定 | 需求开放，方案不确定 |
| 不确定性来源 | 模型引入的（非固有） | 任务本身固有的 |
| 最终方案 | 纯过程式 | 混合方案（过程式骨架 + Agent 决策） |
| 结果 | 稳定、可测、低成本 | 灵活、可控、可排障 |

核心结论：

- 定时周报的问题：把一个确定性问题交给 ReActAgent → 不确定性被凭空引入 → 不可控
- CodingAgent 的成功：承认任务本身不确定 → 用过程式围住边界 → Agent 在笼子里跳舞

## 六、核心设计原则

### 原则一：模型做它擅长的事，代码做代码擅长的事

模型擅长推理、规划、生成和语义理解；代码擅长精确计算、状态管理、格式校验和可复用执行。不要让模型做日期计算，也不要让 if/else 去猜用户需求。

### 原则二：先判断不确定性来源，再选架构方案

不要上来就 ReAct，也不要上来就写死。先回答：**这个任务的不确定性是固有的吗？** 如果是，交给 Agent；如果不是，交给代码。

### 原则三：过程式框架是 Agent 的护城河，不是对立面

很多人把过程式和 Agent 看成二选一，其实它们应该是搭档。过程式负责兜底和边界，Agent 负责灵活和推理。没有护城河的 Agent 注定失控。

## 七、落地经验

- **边界划分要早于实现。** 动手写代码之前，先明确哪些环节必须可控，哪些环节可以放松。边界一旦模糊，后期会不断拉扯「这里交给 Agent 还是写死」。
- **日志和回溯能力要一体化设计。** Agent 的推理循环天然容易产生分岔，必须在架构层面统一收集日志、工具调用参数和中间状态，否则排障时会很痛苦。
- **从混合方案开始，而不是从纯 Agent 开始。** 对于大多数生产级任务，纯 Agent 的自由度是奢侈品，过程式的实现是必需品。先搭起可扩展的框架，再逐步放权，是更务实的路径。
- **提示词不是代码的替代品，而是代码的延伸。** 当你发现自己在提示词里写了大量分支判断、格式约束和异常处理时，很可能说明这部分逻辑本该用代码实现。

## 八、写在最后

回顾这两个案例，最大的收获不是某个技术方案本身，而是一种思考习惯：

> 在面对 AI Agent 时，先问自己——这个不确定性，是任务本来就有的，还是我用模型之后才有的？

这个问题的答案，决定了模型应该扮演主角、配角，还是干脆不上场。

定时周报的教训是：不要把确定性问题交给不确定性技术。CodingAgent 的经验是：把模型关进过程式的笼子里，它才能安全地跳舞。

确定性归代码，不确定性归模型。边界清晰了，Agent 才能真正成为可信赖的生产力工具，而不是一个需要人盯着才能不闯祸的黑盒。
