# Context Engineering:给 AI 编码助手喂上下文的工程化方法

> 探小虎 · 技术分享

用 AI 编码助手久了,你会发现一件事:**输出质量的天花板,不是模型,是你喂的上下文。**

同样一个模型,有人用它写代码惊艳,有人用它写出来全是错的——区别往往不在模型,而在**有没有把正确的上下文在正确的时机喂进去**。这件事有个新名字叫 **Context Engineering(上下文工程)**,它正在取代「prompt engineering」成为 AI 编码的核心技能。

![Context Engineering 示意](images/context-engineering.jpg)

---

## 一、为什么上下文是 AI 编码的「真天花板」

prompt engineering 时代的核心是「怎么问问题」,Context engineering 时代的核心是「**喂什么进去**」。原因有三:

| 趋势 | 影响 |
|:---|:---|
| 模型能力趋同 | 顶级模型差距收窄,上下文质量决定胜负 |
| 任务越来越长 | 长任务里,上下文管理比单次问法更关键 |
| 上下文是稀缺资源 | 窗口有限、注意力衰减、按 token 计费 |

> 一句话概括:**模型负责「想」,你负责「喂」。喂得准,它想得对;喂得乱,它再聪明也跑偏。**

---

## 二、上下文工程的两个目标

上下文工程不是「把所有信息都塞进去」,而是同时服务两个目标:

1. **精准**:此刻这一步,模型需要的最小信息,都齐了。
2. **克制**:此刻不需要的,一律不进上下文。

这两个目标经常打架——精准容易喂多,克制容易喂少。**好的上下文工程,是在两者之间找平衡:最小够用。**

---

## 三、三种记忆注入文件

让 AI 编码助手「记住」项目约定,主流是靠几类约定文件:

| 文件 | 谁用 | 作用 |
|:---|:---|:---|
| `CLAUDE.md` | Claude Code | 项目级指令,启动时自动加载 |
| `.cursorrules` / `.cursor/rules/` | Cursor | 项目规则,影响生成风格与约定 |
| `AGENTS.md` | 通用标准(多家工具支持) | 跨工具通用的项目说明 |

**形式在演进,核心逻辑一致**:这些文件都是**把项目约定从「会话里口头说」变成「文件里白纸黑字」**。它们的写法有几个通用要点:

- **写约定,不写废话。** 「用 Java 17、4 空格缩进、不允许 System.out」这种约束;别写「要写好代码」这种空话。
- **写边界,不写步骤。** 告诉模型「不要碰 /legacy 目录」「DB 改动要审 migrations」;别事无巨细写流程。
- **分层。** 全局约定放 `AGENTS.md`,工具特有约定放对应文件,避免重复冲突。

> 设计哲学:**这些文件是「给 AI 看的项目宪法」。写得好,模型每次都自动遵守;写得差,等于没写。**

---

## 四、最小够用原则

新手最容易犯的错:**把整个仓库喂进去**。结果上下文爆炸,模型反而抓不准。

最小够用的意思是——**只喂此刻这一步需要的**:

| 该不该喂 | 判断标准 |
|:---|:---|
| **喂** | 这一步要改的文件、相关的接口定义、明确的约定 |
| **不喂** | 整个仓库、没直接关联的模块、过时的历史代码 |

操作上,精准引用(`@file`、`#function`)比「全量索引」更管用——**主动选你需要的,比被动塞所有,效果好得多。**

> 设计哲学:**上下文的精准度,比上下文的体量重要十倍。**

---

## 五、清上下文的时机

长任务里,上下文会**越来越脏**:错误尝试的痕迹、无关工具返回、模型跑偏的中间状态,都会污染。这时最该做的不是继续喂,而是**清空重来**:

```
[干净上下文] → 跑了几轮 → [污染上下文,模型开始跑偏]
                              ↓
                     清上下文 + 重喂关键约定
                              ↓
                     [干净上下文] 接着跑
```

什么信号说明该清了?

- 模型开始重复犯同一错(被旧上下文带偏);
- 输出质量明显下降,但任务本身没变难;
- 上下文里堆了大量无关的工具返回;

> OpenSpec 官方都有提醒:**干净上下文 + 高推理模型,效果最好**。不清上下文,模型再强也被脏数据拖垮。

---

## 六、一个上下文工程的工作流

把上面串起来,日常 AI 编码的工作流大概是这样:

```
   写好 CLAUDE.md / AGENTS.md(项目约定)
              ↓
   开任务:精准喂此刻需要的文件(@引用)
              ↓
   跑 → 上下文脏了? → 清 + 重喂约定 → 接着跑
              ↓
   任务完成 → 把新约定沉淀回 AGENTS.md(下次自动加载)
```

这是一个**闭环**:约定沉淀进文件 → 任务里精准喂 → 跑脏了就清 → 新经验再沉淀。好的上下文工程,就是把这个闭环转起来。

---

## 七、常见踩坑

| 坑 | 后果 | 解法 |
|:---|:---|:---|
| **全量喂仓库** | 上下文爆炸,模型抓不准 | 精准引用,最小够用 |
| **约定文件写空话** | 模型当没看见,照样瞎写 | 写约束不写废话,给边界 |
| **从不清上下文** | 越跑越偏,后期崩盘 | 出现污染信号就清+重喂 |
| **约定文件不更新** | 项目变了模型还在守老规矩 | 新约定及时沉淀回文件 |
| **多工具约定冲突** | 不同工具行为不一致 | 通用约定放 AGENTS.md,工具特有的单独写 |

---

## 八、写在最后

1. **上下文是 AI 编码的真天花板。** 模型趋同,喂得准的赢。
2. **最小够用,不是越多越好。** 精准度比体量重要十倍。
3. **沉淀 + 重喂的闭环。** 约定进文件,任务精准喂,脏了就清,新经验再沉淀。

prompt engineering 教你怎么问,context engineering 教你怎么喂。前者是**对话技巧**,后者是**工程纪律**——AI 编码越深入,后者越值钱。
