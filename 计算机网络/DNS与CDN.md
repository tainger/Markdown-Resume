# DNS 与 CDN：域名解析与内容分发

DNS 把人类可读的域名翻译成 IP；CDN 把静态内容搬到离用户最近的边缘节点。两者合起来决定「用户访问的第一个 RTT 花在哪」。面试重点：递归 vs 迭代查询、缓存层级、DNS 负载均衡/HTTPDNS、CDN 命中与回源。

---

## 一、DNS 是什么：分布式分层数据库

域名从右往左层级递减：`www.example.com` → 根(`.`) → 顶级域 `com` → 权威域 `example.com`。全球 13 组根域名服务器（靠任播部署了几百个节点）。

| 服务器角色 | 职责 | 类比 |
|:---|:---|:---|
| 本地 DNS（递归解析器） | 替客户端跑腿，最终给出答案 | 114 查号台 |
| 根域名服务器 | 告诉你「.com 归谁管」 | 总服务台 |
| 顶级域（TLD）服务器 | 告诉你「example.com 的权威在哪」 | 二级前台 |
| 权威域名服务器 | 存最终 A/CNAME 记录，给出答案 | 公司前台 |

## 二、解析流程：递归查询 vs 迭代查询（必考）

```
 浏览器 ──①查缓存──┐
   │  缓存未命中   │
   ↓              └→ 浏览器缓存 → OS缓存 → hosts 文件
 本地DNS(如运营商/8.8.8.8)
   │ ── ②递归查询 ────────────  客户端只问一次，等着拿最终结果
   │    ┌─ ③迭代查询（本地DNS 逐级问）─┐
   │    │  根:   「去问 com 的 TLD」    │
   │    │  TLD:  「去问 ns.example.com」│
   │    │  权威: 「A 记录 = 1.2.3.4」   │
   │    └──────────────────────────────┘
   │ ←── ④返回 1.2.3.4（并缓存 TTL 时长）
   ↓
 浏览器拿到 IP，开始建 TCP 连接
```

| 对比项 | 递归查询 | 迭代查询 |
|:---|:---|:---|
| 谁跑腿 | 被查询方负责**查到底** | 被查询方**只指路**，问的人自己继续 |
| 发生在 | 客户端 → 本地 DNS | 本地 DNS → 根/TLD/权威 |

**缓存与 TTL**：每级结果都带 TTL，缓存在浏览器/OS/本地 DNS。TTL 权衡——调小迁移/切换快但查询量大，调大缓存省查询但切换慢（业务上做 DNS 切换会先调小 TTL 预热）。

## 三、DNS 记录类型与 DNS 负载均衡

| 记录 | 含义 | 场景 |
|:---|:---|:---|
| A / AAAA | 域名 → IPv4 / IPv6 | 最基本 |
| **CNAME** | 域名 → 另一个域名（别名） | CDN 接入标配：`cdn.xx.com → xx.kunlun.com` |
| NS | 该域的权威服务器是谁 | 委派子域 |
| MX | 邮件交换 | 邮件路由 |
| TXT | 附加文本 | SPF/域名校验 |

**DNS 轮询做负载均衡**（简单但不完美）：

- 优点：零成本、天然地理就近/分流、可按运营商线路（智能 DNS）。
- 缺点：**无健康检查**（挂了照样解析）、DNS 缓存让下线/切换不及时、流量分配不均。
- 生产常见组合：DNS 做入口分流 → 下接 LVS/Nginx/网关做真正的负载均衡（与 [系统设计](../系统设计/README.md) 的接入层呼应）。

**HTTPDNS**：绕过运营商 DNS，客户端直接 HTTP 请求云厂商解析服务——解决**DNS 劫持**（运营商插广告）、解析跨网/跨域漂移问题，App 场景常用。

## 四、CDN：内容分发网络

目标：让用户**就近**拿到静态资源（图片/JS/CSS/视频），同时给源站分流抗量。

```
 用户 ── DNS 解析(CNAME 到 CDN GSLB) ──→ 全局调度：选最近的边缘节点
  │
  └──→ 边缘节点（Edge）
         ├─ 缓存命中 → 直接返回（X-Cache: HIT）
         └─ 未命中/过期 → 回源（回 origin 拉取，回源链路可用中间层缓存）
```

核心机制：

| 机制 | 说明 |
|:---|:---|
| **GSLB 全局调度** | 依托 DNS/HTTPDNS + 用户 IP/运营商，调度到最优边缘节点 |
| **边缘缓存** | 按 `Cache-Control` 等策略缓存；命中返回快且省回源带宽 |
| **回源** | 未命中时回源站取；配合预热（主动推送热点）、穿透防护（合并回源/加锁，避免缓存击穿打爆源站） |
| **刷新/预热接口** | 改版后主动 PURGE 删缓存、PUSH 预推，与 [HTTP 缓存](HTTP.md) 协同 |

追问点：

- **动态内容能用 CDN 吗？** 纯静态直接缓存；动态走「全链路加速/DSA」（复用 CDN 边缘网络优化路由，不缓存内容）。
- **CDN 缓存层级**：浏览器缓存 → CDN 边缘 → 源站，逐层兜底（与浏览器强/协商缓存的 `Cache-Control` 语义一致）。
- **怎么判断请求打到了 CDN？** 响应头 `X-Cache: HIT/MISS`、`X-Swift-Cache-Time` 等；DNS 解析结果是否为 CDN CNAME。

## 五、易错点

| 易错点 | 澄清 |
|:---|:---|
| **浏览器直接问根域名服务器** | 只问**本地 DNS**（递归），根/TLD/权威由本地 DNS 迭代访问 |
| **递归和迭代混着用无所谓** | 标准答案：客户端→本地DNS 是递归，本地DNS→各级是迭代 |
| **改了 DNS 记录立即全网生效** | 受各级缓存 TTL 影响，迁移前先调小 TTL |
| **CNAME 指向 IP** | CNAME 指向**另一个域名**；指向 IP 的是 A 记录 |
| **CDN 什么都加速** | 默认只对**静态可缓存**内容；动态请求走全链路加速而非缓存 |
| **13 个根服务器是 13 台机器** | 是 13 组身份（A~M），任播部署成几百个节点 |

---

## 六、一句话总结

DNS 是**分层缓存**体系：客户端只发一次**递归**查询，本地 DNS 逐级**迭代**问根/TLD/权威，结果按 TTL 层层缓存。CDN 靠「DNS 调度到最近边缘 + 命中即返回、未命中回源」让静态资源就近可得——DNS 管调度，CDN 管分发，HTTP 缓存管浏览器侧，三层缓存各司其职。
