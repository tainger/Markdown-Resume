# HTTPS：HTTP + TLS 加密层

HTTPS = HTTP over TLS。它解决 HTTP 明文传输的三大风险：**窃听**（机密性）、**篡改**（完整性）、**冒充**（身份认证）。面试核心：为什么「对称 + 非对称」混合加密、TLS 握手流程、证书链验证、TLS 1.3 的改进。

---

## 一、为什么需要：HTTP 的三大风险

| 风险 | 场景 | HTTPS 对策 |
|:---|:---|:---|
| **窃听** | 明文密码在 WiFi 上被抓包 | 对称加密（机密性） |
| **篡改** | 运营商注入广告、修改内容 | MAC/AEAD 校验（完整性） |
| **冒充** | 假基站/假网关返回假页面 | CA 数字证书（身份认证） |

> 注意：单纯加密不等于安全——如果密钥协商被中间人截胡（MITM），加密形同虚设。所以**身份认证（证书）是 HTTPS 的灵魂**。

---

## 二、对称 vs 非对称加密（为什么混着用）

| 对比项 | 对称加密（AES） | 非对称加密（RSA / ECDHE） |
|:---|:---|:---|
| 密钥 | 一把，双方共用 | 公钥加密、私钥解密（成对） |
| 速度 | **快**（千倍级差距） | 慢 |
| 密钥分发 | 致命弱点：怎么安全地把钥匙给对方？ | 公钥可公开，天然解决分发 |
| 典型用途 | 数据传输加密 | 密钥交换、签名 |

**结论（面试标准话术）**：用非对称加密**协商出对称密钥**，之后的海量数据用对称密钥加密——安全与性能兼得。

> 「只非对称行不行？」——性能扛不住：TLS 记录每个连接都在传海量数据，全用 RSA/ECDHE 加解密 CPU 直接打爆。「只对称行不行？」——密钥没安全保障，第一次分发就被窃听。

## 三、TLS 1.2 握手流程（RSA 版，经典 2-RTT）

```
 Client                                Server
   │ ── ① ClientHello ────────────────→  │
   │     支持的TLS版本、随机数CR、密码套件    │
   │ ←─ ② ServerHello + 证书 ──────────  │
   │     随机数SR、选定套件、Server证书      │
   │（握手明文阶段结束，之后用协商密钥加密）    │
   │ ── ③ ClientKeyExchange ──────────→  │
   │     预主密钥PMS（用服务器公钥加密）      │
   │ ── ④ ChangeCipherSpec/Finished ──→  │
   │ ←─ ⑤ ChangeCipherSpec/Finished ───  │
   │                                     │
  双方各自计算对称密钥 = f(CR, SR, PMS)      │
   │ ←═════════ 应用数据（对称加密）═══════→ │
```

要点：

- 两个随机数（CR/SR）+ 预主密钥（PMS）→ 双方独立算出**相同的对称会话密钥**。
- **两个随机数的作用**：保证每次会话密钥不同（防重放），不能只靠客户端单方面生成。
- **证书在 ② 里下发**，客户端随后验证证书链（见第五节），确认「公钥真是对方的」。
- RSA 握手的缺陷：私钥一旦泄露，历史抓包可被**回溯解密**（无前向安全）→ 改用 ECDHE。

> ECDHE 握手差异（常追问）：③ 换成「双方各自发送 DH 公开参数」，用椭圆曲线 Diffie-Hellman **临时**算出共享密钥——每次会话密钥独立，私钥泄露也解不开历史流量（**前向安全**）。抓包工具不导入私钥也解不开 ECDHE 流量。

## 四、TLS 1.3 的改进

| 改进 | 说明 |
|:---|:---|
| **1-RTT 握手**（甚至 0-RTT 恢复） | 合并密钥交换与 Finished，比 1.2 少一个 RTT；复用会话时 0-RTT 直接带数据 |
| **只保留前向安全套件** | 砍掉 RSA 密钥传输、CBC 等弱算法，只留 ECDHE + AEAD（AES-GCM/ChaCha20） |
| **握手更大部分加密** | ServerHello 之后全部加密，减少明文暴露 |
| 单轮签名算法协商 | 简化密码套件数量（1.2 十几套 → 1.3 几套） |

> 0-RTT 的风险：早期数据**无防重放保护**，只适合幂等请求。

## 五、数字证书与 CA 证书链（防中间人的关键）

证书 = 「**域名 + 公钥 + 颁发者 + 有效期**」等信息，由 CA 用**自己的私钥**签名。

验证流程（浏览器拿到服务器证书后）：

1. 用**上级 CA 的公钥**验证证书签名 → 逐级向上直到**内置根证书**（操作系统/浏览器预装的 Root CA）。
2. 检查：域名是否匹配（SAN）、是否在有效期、是否被吊销（CRL/OCSP）。

```
 根证书（预装在系统，自签名）
   └── 签发 → 中间 CA 证书
          └── 签发 → 站点证书（example.com 的公钥）
```

**为什么中间人攻击行不通？** 攻击者可以给假证书，但签名需要 CA 私钥——它没有；自签证书不在信任链里，浏览器直接红牌警告。

- **抓包工具（Charles/Fiddler）为什么能解密 HTTPS？** 需要手动安装它的根证书到信任列表——本质就是「自愿信任一个中间 CA」，与中间人攻击同构。
- 免费证书：Let's Encrypt（ACME 协议自动签发续期）。

## 六、性能与部署速查

| 手段 | 说明 |
|:---|:---|
| 会话复用（Session ID / Ticket） | 恢复会话免重复密钥协商，1.3 的 PSK 更进一步 |
| TLS 1.3 | 握手 1-RTT，配合 TCP Fast Open / QUIC 0-RTT |
| OCSP Stapling | 服务器代为获取吊销状态并「装订」到握手，客户端不用另查 OCSP |
| 证书链完整 | 少发中间证书会导致部分客户端握手失败 |
| 硬件加速 | AES-NI 指令集，AES-GCM 开销很低 |

TLS 1.2 vs 1.3 对比：

| 对比项 | TLS 1.2 | TLS 1.3 |
|:---|:---|:---|
| 握手 RTT | 2-RTT（RSA）/ 1-RTT（ECDHE 简化场景） | **1-RTT / 0-RTT** |
| 密钥交换 | RSA 传输 + ECDHE | **仅 ECDHE（前向安全）** |
| 对称算法 | AES-CBC、RC4 等均有 | 仅 AEAD（GCM / ChaCha20） |
| 安全性 | 历史包袱多 | 砍掉全部已知弱算法 |

## 七、易错点

| 易错点 | 澄清 |
|:---|:---|
| **HTTPS 用非对称加密传数据** | 非对称只用于**协商密钥**，数据是**对称加密** |
| **有加密就不需要证书** | 证书解决「对面是谁」，防中间人换公钥，加密替代不了 |
| **JWT/HTTPS 之后密码明文可见** | HTTPS 只保护**传输中**数据；日志、数据库里的存储安全是另一层（需哈希加盐） |
| **TLS 1.2 的 RSA 握手是前向安全的** | 不是；私钥泄露可回溯解密历史流量，ECDHE 才有前向安全 |
| **抓包工具解密是「破解」了 HTTPS** | 是用户主动信任其根证书，走的是中间人路径，不是破解 |
| **HTTP/3 = HTTP over 新加密协议** | HTTP/3 = HTTP over QUIC over UDP，加密（TLS1.3）内嵌在 QUIC 里 |

---

## 八、一句话总结

HTTPS = **对称加密**保机密 + **非对称（ECDHE）**换密钥 + **CA 证书链**保身份 + **签名/AEAD**保完整。握手本质是「安全地商量出一把对称钥匙」，TLS 1.3 把这步压到 1-RTT 并只留前向安全算法。
