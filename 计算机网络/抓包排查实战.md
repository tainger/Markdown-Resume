# 抓包与网络问题排查实战

> 网络排查是 P6→P7 的分水岭能力：不背协议字段，而是**用 tcpdump/Wireshark 从真实流量里读出答案**。本文 = 方法论 + 工具速查 + 8 个生产级 Case，每个 Case 按「现象 → 抓包结论 → 根因 → 命令」组织，可直接改编成面试故事。

---

## 一、排查方法论：分层定位（先立框架）

```
连不上？慢？断？错？
   │
   ├─ ① 链路层/网络层：ping（ICMP 通不通）、traceroute/mtr（哪一跳丢）
   ├─ ② 传输层：telnet/nc（端口通不通）、ss -s（连接状态统计）
   ├─ ③ 应用层：curl -v（HTTP 状态）、openssl s_client（TLS 握手）
   └─ ④ 都不对劲 → tcpdump 抓包看真实报文（唯一「不说谎」的证据）
```

| 问题类型 | 典型症状 | 优先怀疑 |
|:---|:---|:---|
| **连不上** | connect timeout / connection refused | 端口未监听、防火墙、路由 |
| **慢** | TTFB 高、偶发超时 | 丢包重传、zero window、DNS 慢、RTT 大 |
| **断** | Connection reset by peer、偶发断连 | 对端 RST、NAT 超时、keepalive |
| **错** | 400/502、TLS alert | 代理篡改、证书链、协议不兼容 |

**工具箱速查**：`ping` / `mtr`（丢包路径）/ `nc -zv`（端口）/ `curl -v -w`（时延分解）/ `ss -s`（状态统计）/ `dig +trace`（DNS）/ `tcpdump`（抓包）/ `Wireshark`（分析 pcap）/ `openssl s_client`（TLS）。

## 二、tcpdump 必背命令（每天用一遍就熟）

```bash
# 基础组合拳：抓 8080 端口，存文件（-s0 不截断报文）
tcpdump -i any -nn -s0 -w app.pcap port 8080

# 只看 TCP 建立/终止：握手与挥手
tcpdump -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

# 抓某主机的 HTTP（BPF 过滤语法：and/or/not 组合）
tcpdump -nn host 10.0.0.5 and port 443

# 容器/K8s：宿主机抓 veth 或 -i any 兜底；抓不到就走 nodeport 链路
```

| 参数 | 作用 | 坑 |
|:---|:---|:---|
| `-i any` | 所有网卡 | 抓到重复报文（bond/bridge 双份），必要时指定网卡 |
| `-n` / `-nn` | 不解析主机名/端口名 | **必加**：DNS 反查会拖慢甚至污染抓包 |
| `-s0` | 抓完整包 | 默认 262144（新版）；老版默认 96 字节会截断 HTTP 头 |
| `-w file.pcap` | 存原始包 | 生产排查首选：抓下来离线用 Wireshark 分析 |
| `-c 1000` | 抓够 N 个包自动停 | 防止生产磁盘写爆 |

**输出关键字段**：`Flags [S]=SYN [S.]=SYN+ACK [P]=push [F]=FIN [R]=RST`；`seq/ack`（相对序号，Wireshark 自动换算）；`win`（接收窗口）；`length`（payload 长度）。

**Wireshark 高频显示过滤器**：`tcp.analysis.retransmission`（重传）、`tcp.flags.reset==1`（RST）、`tcp.analysis.zero_window`（接收方扛不住）、`http.request.uri contains "api"`、`tls.handshake.type==1`（ClientHello）。

## 三、经典 Case 实录（面试可直接讲）

### Case 1：服务「连不上」——先分辨 DROP 还是 REJECT

- **现象**：客户端 connect 超时（约 75s/2min）或秒报 `Connection refused`。
- **抓包**：
  - 只见 `[SYN]` 反复重传、无任何响应 → **防火墙 DROP**（请求被丢弃）；
  - 收到 `[R]`（RST）→ **端口没人监听**（或 REJECT 规则）。
- **根因排查**：服务端 `ss -lntp | grep 8080` 确认监听 → `iptables -L -n` 看规则 → 云安全组。
- **面试点**：**timeout 是被丢弃，refused 是被明确拒绝**——两者排查方向完全不同。

### Case 2：大量 TIME_WAIT vs CLOSE_WAIT（最高频）

```bash
ss -s   # 一行看出各种状态的数量
```

- **TIME_WAIT 堆积**：**本端主动关闭**才会进 TIME_WAIT。爬虫/网关高频短连接调下游 → 每次请求都由本端 FIN。
  - 对策：连接池复用长连接（根治）、`tcp_tw_reuse`（仅出方向、要时间戳）、别开 `tcp_tw_recycle`（NAT 下灾难，新版内核已删）。
- **CLOSE_WAIT 堆积**：对端已 FIN，**本端代码一直没 close**——九成是连接泄漏（异常分支没走 finally close、连接池配置错）。
- **抓包确认**：看最后几个报文谁发的 FIN、本端是否回 FIN——状态机不会骗人。

### Case 3：偶发 Connection reset by peer

- **抓包**：正常数据流中突现 `[R]`。
- **四种常见根因**：
  1. 对端进程重启/崩溃，内核清理连接回 RST；
  2. 对端连接已被回收（keepalive 超时、LB 空闲超时如 SLB 900s），本端还在用「死连接」发数据 → 收 RST；
  3. 防火墙/安全设备注入 RST；
  4. 接收缓冲区被 RST（SO_RCVBUF 满且开了强制选项，少见）。
- **对策**：客户端配置**重试 + 连接有效性检测**（连接池 testOnBorrow/keepalive），LB 侧调大 idle timeout。

### Case 4：接口偶发变慢——重传与 zero window

- **抓包/Wireshark**：`tcp.analysis.retransmission` 密集 → 网络丢包（配合 `mtr` 定位哪一跳丢）；
  - **快速重传**（3 个 dup ack 后重传）链路轻微丢包；**超时重传**（RTO，1s 起指数退避）丢得狠——一次 RTO 直接让 P99 飙升；
- `tcp.analysis.zero_window` → **接收方应用读得慢**（业务线程池打满、GC 停顿），TCP 流量控制生效拖住发送方——这是「应用慢」在网络层的表现；
- **面试点**：重传/零窗口是「网络症状」，根因常在应用层（线程池/GC/下游），抓包打通了这条证据链。

### Case 5：大包断小包通——MTU / 分片问题（经典！

- **现象**：ping 正常、SSH 能登录，但 HTTPS 握手卡死、传大文件断——**握手小包通、数据大包挂**。
- **抓包**：本端发大包后无 ACK；更典型的是收到 `ICMP fragmentation needed (type 3, code 4)`，但该 ICMP 被 firewall 丢弃 → 发送方不知道要缩小包，死等（PMTUD 黑洞）。
- **根因**：链路存在更小 MTU（VPN/隧道 GRE 加封装头），DF 位分片被禁。
- **对策**：`ping -M do -s 1472` 逐跳测路径 MTU；调小接口 MTU 或开启 MSS clamping。
- **面试点**：**「握手成功但数据卡死」的第一反应就是 MTU/PMTUD**——高区分度案例。

### Case 6：HTTPS 请求有问题——两步排查 SOP

> HTTPS 数据载荷加密，但**握手过程与证书是明文**——定位 TLS/网络问题完全够用。打法：先分段定位，再抓包取证。

**第一步：curl 定位问题阶段（不用抓包）**

```bash
curl -v -o /dev/null -s -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n' https://example.com/api
```

| 卡在哪 | 结论与下一步 |
|:---|:---|
| `dns` 大/失败 | DNS 问题 → `dig` 逐层查（见 Case 7） |
| `connect` 失败/超时 | TCP 层：防火墙 DROP 或端口未监听 → `nc -zv`、见 Case 1 |
| `tls` 失败 / 与 connect 差值大 | TLS 握手问题 → **走第二步抓包** |
| `ttfb` 差值大 | TLS 已通，**服务端处理慢** → 查后端，别再抓包 |

**第二步：tcpdump + Wireshark 看握手明文骨架**

```bash
tcpdump -i any -nn -s0 -w tls.pcap host <client_ip> and port 443
```

Wireshark 过滤器链（按握手顺序点检）：

| 过滤器 | 看什么 |
|:---|:---|
| `tls.handshake.type == 1` | ClientHello：SNI、支持的 TLS 版本与 cipher suites |
| `tls.handshake.type == 2` | ServerHello：服务端选定的版本/套件 |
| `tls.handshake.type == 11` | Certificate：证书链是否完整、是否过期 |
| `tls.alert_message.desc` | **失败点在这里**：40=handshake_failure、证书类 alert |

| 现象 | 结论 |
|:---|:---|
| 有 ClientHello 无 ServerHello | 中间设备丢弃 / 服务端无响应 |
| `alert handshake_failure` (40) | 版本/套件协商不上（老客户端 TLS1.0 vs 服务端仅 1.2+） |
| 证书链缺中间证书 | **浏览器正常、curl/程序失败**的经典坑（浏览器缓存补链）、过期、SNI 配错 |

命令行交叉验证：

```bash
openssl s_client -connect host:443 -servername host   # 看 Verify return code 与证书链
```

**补充：需要看「加密内容」时**

载荷加密抓包不可见，两条路：
1. **服务端侧**：问题多半在处理逻辑，用日志/APM 定位（别指望抓包）；
2. **客户端侧代理抓包**（mitmproxy/Charles）：客户端信任其 CA，走中间人代理看到解密后的完整请求/响应——适合 App/前端问题，**不适用于生产服务器间调用**。

**面试点**：HTTPS 抓包 = curl -v 定位阶段 + tcpdump 抓 443 + Wireshark 看握手明文骨架；能定位「协商/证书/网络」，定位不了「加密内容」——那是代理抓包或日志的活。

### Case 7：解析到旧 IP——DNS 缓存链

- **现象**：迁移后部分机器仍连旧 IP。
- **排查链**：应用缓存（JVM DNS cache）→ 本地解析器缓存 → 企业 DNS TTL → 权威记录。`dig @dns target` 逐层对比答案与 TTL。
- **抓包**：UDP 53 或 DoH（443，抓不到明文——HTTPDNS 化的直接动机，呼应 [DNS与CDN](DNS与CDN.md)）。
- **对策**：合理 TTL、发布期双存活、JVM `networkaddress.cache.ttl` 调整。

### Case 8：HTTP 时延到底慢在哪——curl 时延分解

```bash
curl -o /dev/null -s -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com/api
```

| 指标大 | 结论 |
|:---|:---|
| `dns` 大 | 解析慢/超时重试 |
| `connect` 大且 dns 正常 | TCP 建连慢（丢包/远距离/安全组 DROP） |
| `tls` 与 `connect` 差值大 | TLS 握手慢（CPU/证书链/版本回退） |
| `ttfb` 与 `tls` 差值大 | **服务端处理慢**（查后端，别再看网络） |

> 这条命令是面试讲「性能排查」最便宜的武器：一次请求把四段时延拆干净。

## 四、生产抓包的注意事项

| 事项 | 说明 |
|:---|:---|
| 敏感数据 | pcap 里是明文 HTTP/登录态，**别上传外网**，用完即删 |
| 性能影响 | 高 QPS 全量抓包有 CPU/磁盘成本：用端口过滤 + `-c` 限量 + `snaplen` 截断 |
| 容器环境 | 流量经 veth/NAT，`-i any` + 宿主机抓；K8s 里注意 Service 的 DNAT 已发生（看到的是 Pod IP） |
| 证据思维 | 抓包结论 > 日志猜测；截图保留 seq/ack 与 flags 上下文，复盘有据 |

## 易错点

| 坑 | 说明 |
|:---|:---|
| 忘加 `-nn` | tcpdump 做反向 DNS，抓包变慢且结果被污染 |
| tcpdump 与 Wireshark 语法混用 | BPF：`port 80`；Wireshark 显示过滤器：`tcp.port == 80` |
| 只抓一个方向 | `host x and port y` 默认双向，但 `src/dst` 写死后单向；对比请求响应用 `tcpdump -nn 'src host A or dst host A'` |
| 把 timeout 与 refused 混为一谈 | DROP（超时）查防火墙，REJECT/RST（拒绝）查端口与进程 |
| CLOSE_WAIT 想靠内核参数解决 | 参数救不了代码不 close；先查泄漏 |
| 重传只怪网络 | zero window 的「网络慢」是应用读得慢，先看下游线程池/GC |

---

## 一句话总结

**排查 = 分层收缩 + 抓包定案**：ping/mtr 定链路、nc/ss 定端口与连接状态、curl -w 拆时延、tcpdump/Wireshark 拿最终证据；八个经典 Case 记住四个「第一反应」——**超时查 DROP、refused 查监听、TIME_WAIT 主动关/CLOSE_WAIT 代码漏、大包断查 MTU、reset 查对端与空闲超时**；HTTPS 请求两步走：**curl -v 分段定位 → 抓 443 看握手明文骨架**。
