# 系统架构设计

> 系统架构设计师考试的**核心知识域**，综合知识占比约 25%，案例分析必考，论文高频方向。

---

## 一、软件架构风格

### 1.1 架构风格分类（必考）

| 大类 | 具体风格 | 核心特征 | 典型应用 |
|:---|:---|:---|:---|
| **数据流风格** | 批处理 | 顺序、串行、无交互 | ETL 数据处理 |
| | 管道-过滤器 | 数据流经多个处理节点，过滤器无状态 | Unix Shell、ETL 管道 |
| **调用-返回风格** | 主程序-子程序 | 层次化调用 | 传统 C 程序 |
| | 面向对象 | 对象封装 + 继承 + 多态 | Java/C# 应用 |
| | 分层架构 | 每层只依赖下一层，单向依赖 | Spring Boot（Controller→Service→DAO） |
| **独立构件风格** | 进程通信 | 独立进程通过消息/共享内存通信 | Kafka 消费者组 |
| | 事件驱动（隐式调用） | 构件不直接调用，发布事件由总线调度 | GUI 事件、Spring Event |
| **虚拟机风格** | 解释器 | 自定义语法解释执行 | 规则引擎、脚本引擎 |
| | 规则系统 | if-then 规则匹配 | Drools 规则引擎 |
| **仓库风格** | 数据库系统 | 共享数据库作为交互媒介 | 传统 CRUD 系统 |
| | 超文本系统 | 非线性链接组织信息 | Web 系统、维基 |
| | 黑板系统 | 共享黑板 + 知识源协作 | 专家系统、语音识别 |

### 1.2 分层架构

```
┌─────────────────────────┐
│      表现层 (UI)          │  ← 用户交互
├─────────────────────────┤
│    业务逻辑层 (Service)   │  ← 业务规则
├─────────────────────────┤
│    数据访问层 (DAO)       │  ← 数据持久化
├─────────────────────────┤
│      数据层 (DB)          │  ← 数据存储
└─────────────────────────┘
```

- **优点**：关注点分离、可维护性强、易于测试
- **缺点**：性能损耗（层层传递）、改动可能贯穿多层
- **变体**：DDD 四层（用户接口层 → 应用层 → 领域层 → 基础设施层）

### 1.3 微服务架构

```
                    ┌──────────┐
                    │  API Gateway │
                    └─────┬────┘
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ 用户服务  │    │ 订单服务  │    │ 支付服务  │
    │ (独立DB) │    │ (独立DB) │    │ (独立DB) │
    └────┬─────┘    └────┬─────┘    └────┬─────┘
         │                │                │
         └────────┬───────┘                │
                  ▼                        ▼
           ┌──────────┐           ┌──────────┐
           │ 注册中心  │           │ 配置中心  │
           └──────────┘           └──────────┘
```

- **核心特征**：服务独立部署、去中心化数据、轻量通信（REST/gRPC）、自动化运维
- **挑战**：分布式事务、服务发现、链路追踪、数据一致性、网络分区
- **对比 SOA**：

| 维度 | SOA | 微服务 |
|:---|:---|:---|
| 通信 | ESB（重） | REST/gRPC（轻） |
| 部署 | 常整体/大模块 | 完全独立 |
| 数据 | 常共享数据库 | 每服务独立 DB |
| 粒度 | 粗粒度 | 细粒度 |
| 治理 | 集中式治理 | 去中心化 |

### 1.4 事件驱动架构

- **核心组件**：事件生产者、事件通道（消息队列）、事件消费者
- **模式**：发布/订阅、事件溯源（Event Sourcing）、CQRS
- **优势**：松耦合、高可扩展、天然异步
- **挑战**：最终一致性、事件顺序、幂等处理、可观测性

## 二、4+1 视图模型（必考）

Kruchten 4+1 视图，从 5 个视角描述软件架构：

| 视图 | 描述对象 | UML 图 | 关注点 |
|:---|:---|:---|:---|
| **逻辑视图** | 最终用户/功能 | 类图、对象图、状态图 | 系统功能 |
| **开发视图** | 程序员/软件管理 | 包图、组件图 | 代码组织 |
| **进程视图** | 系统集成/性能 | 活动图、顺序图、部署图 | 并发、同步、通信 |
| **物理视图** | 系统工程师/运维 | 部署图 | 拓扑、节点、网络 |
| **场景（+1）** | 所有干系人 | 用例图 | 验证其他视图 |

> **记忆口诀**：逻辑看功能、开发看代码、进程看并发、物理看部署、场景串全局。

## 三、架构评估方法

### 3.1 ATAM（Architecture Tradeoff Analysis Method）

- **属性驱动**，从质量属性需求出发评估
- **9 步流程**：描述 ATAM → 描述业务动机 → 描述架构 → 识别架构方法 → 生成质量属性效用树 → 分析架构方法 → 头脑风暴和确定场景优先级 → 分析架构方法 → 结果汇报
- **核心概念**：敏感点（单个属性影响最大的决策）、权衡点（一个决策影响多个属性）

### 3.2 SAAM（Software Architecture Analysis Method）

- **场景驱动**，通过构造场景评估单个架构
- **步骤**：场景开发 → 场景分类（直接/间接）→ 架构描述 → 场景评估 → 结果分析
- **vs ATAM**：SAAM 更简单、单方案；ATAM 更系统、多方案权衡

### 3.3 其他方法

- **ARID**：活动审查法，面向可重用资产
- **CBAM**：成本效益分析，量化架构投资回报
- **SAAMCS**：考虑组织支持的 SAAM 变体

## 四、软件产品线（SPL）

- **核心思想**：一组相关产品共享核心资产，通过变体制服差异
- **三层结构**：
  - 核心资产库（Core Assets）：架构、可复用组件、需求、测试用例
  - 产品（Product）：基于核心资产定制
  - 产品线（Product Line）：产品集合
- **两个关键活动**：
  - 领域工程（Domain Engineering）：建立核心资产
  - 应用工程（Application Engineering）：基于核心资产构建产品
- **优点**：缩短交付周期、降低成本、提高质量
- **缺点**：前期投入大、领域分析要求高

## 五、ADL（架构描述语言）

- **作用**：形式化描述软件架构的构件、连接件、配置
- **常见 ADL**：Wright、Darwin、ACME、C2、UniCon
- **ADL 与 UML 区别**：ADL 更形式化、支持架构级推理；UML 更通用、支持全生命周期

## 六、架构文档

### 6.1 架构文档 6 要素

1. 系统概述（背景、目标、约束）
2. 架构决策记录（ADR：背景、决策、后果）
3. 架构视图（4+1 视图）
4. 质量属性设计（性能、安全、可用性、可维护性）
5. 架构接口（对外 API、内部接口）
6. 架构演化计划

### 6.2 ADR（Architecture Decision Record）模板

```markdown
# ADR-001: 采用微服务架构

## 状态
已接受

## 背景
系统用户量增长，单体架构发布困难、扩展受限

## 决策
采用 Spring Cloud 微服务架构，按业务域拆分

## 后果
+ 独立部署、弹性扩展、技术异构
- 分布式复杂度、运维成本增加、数据一致性挑战
```

## 七、质量属性设计（论文高频）

| 质量属性 | 策略 | 技术手段 |
|:---|:---|:---|
| **性能** | 减少计算、并行、缓存 | CDN、多级缓存、读写分离、异步化 |
| **可用性** | 冗余、故障隔离、降级 | 主从复制、服务熔断、限流降级 |
| **可维护性** | 模块化、分层、文档 | DDD、SOLID、架构文档、CI/CD |
| **可扩展性** | 无状态、插件化 | 水平扩展、SPI、插件机制 |
| **安全性** | 认证、授权、加密 | JWT、RBAC、TLS、审计日志 |
| **可测试性** | 依赖注入、Mock | IoC、容器化、自动化测试 |

## 八、案例分析答题套路

### 架构风格选择题

1. **看数据流**：有明确的输入→处理→输出流 → 管道-过滤器
2. **看调用方式**：上层调下层、不跨层 → 分层架构；有事件发布 → 事件驱动
3. **看共享状态**：有共享数据库/黑板 → 仓库风格
4. **看独立性**：构件独立运行、进程通信 → 独立构件风格

### 架构图绘制

- 用例图：参与者 + 用例 + 关系
- 类图：类 + 属性 + 方法 + 关联/依赖/继承/聚合/组合
- 部署图：节点 + 构件 + 通信路径
- 时序图：对象 + 生命线 + 消息
