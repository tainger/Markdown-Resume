### 职责2 · 建立日亏熔断、仓位限制、持仓托管、数据异常保护与应急机制
**这是最「资金」的一条，务必讲透。**
**熔断（Circuit Breaker）**：
- 定义：当下游（券商/交易所/行情源）连续失败达到阈值，不再继续调用，直接走降级或快速失败，保护系统不被拖垮，并留出恢复窗口。
- 量化里常配合**风控熔断**：当日亏损超过限额 → 停止开新仓甚至全部平仓。
**仓位限制**：
- 单品种最大仓位、单日最大开仓次数、总杠杆上限。用**仓位状态机** + 风控拦截（下单前检查，不满足就拒绝）。
**持仓托管**：
- 持仓以券商为最终真相，系统内做「影子账本」，定期对账，防止「本地持仓 ≠ 券商持仓」。
**数据异常保护**：
- 行情数据严重滞后/停更 → 停止发单（防止用旧价成交）；数据缺口检测 → 告警。
**应急机制**：
- 一键停单（圈单/单边停）、一键平仓、行情源切换、风控降级预案。

**考点高分回答模板**：
> 我会把「风控」放在下单链路的最前面，做成一个**前置守卫**：所有订单先过风控状态机（检查日亏额度、仓位上限、冻结比例），任一不满足就拒绝并留审计记录。同时熔断有两个维度——**技术熔断**（券商连接挂了自动降级）和**风控熔断**（亏到线强制停止开仓）。数据侧，行情源异常时我宁可暂停下单也不拿脏数据去成交，因为资金场景里「少赚」远好于「做错」。

### 职责3 · 建设统一CI/CD、不可变发布、版本清单、灰度发布和快速回滚
**这条是「把工程化做干净」。**
- **CI/CD**：代码合入 → 自动打镜像/构建 → 自动跑测试 → 发布到环境。
- **不可变发布**：环境不直接在服务器上改改改（那叫雪人配置），而是每次发布出一个**全新的镜像/版本**，旧版本保留。这样「一句话指向新版本，一句话回到旧版本」。
- **版本清单（image/behavior manifest）**：记录「这个版本 = 哪个 commit + 哪个镜像 + 哪些配置 + 依赖版本」，可追溯。
- **灰度发布（canary）**：先放 5% 流量/一个小账户跑一阵，观察指标正常，再全量。量化里可以「用影子账户先跑策略」。
- **快速回滚**：版本清单让回滚变成「一条 git tag / 一条 k8s rollout undo」，秒级回到上一个健康版本。

**案例表述**：
> 我有过一次教训——直接在服务器上改配置改崩了，没法回退。后来所有发布都走镜像，每次打 tag，配置全部外部化（configmap/env），可追溯能回滚。这种「不可变发布 + 版本清单」的做法，正是资金系统最需要的——**你永远不会出现「我不知道线上到底跑的是哪版代码」**。

### 职责4 · 建设行情、策略、订单、成交、持仓、PnL及系统健康的监控告警体系
**关键是「监控哪些 + 报警怎么分页」。**
**监控分层**：
- 行情：Tick 时延、更新频率、缺数。
- 策略：信号频率、计算耗时、异常退出。
- 订单/成交：下单耗时、成交率、拒单率、撤单率。
- 持仓/PnL：实时盈亏、敞口、与券商对账差异。
- 系统健康：CPU/内存/线程池/队列积压/连接池、进程重启。
**工具**：Prometheus（指标）+ Grafana（大盘）+ 告警规则 + OpenTelemetry（链路）+ Sentry（异常聚合）。
**告警分页（分级）**：
- P0 资金风险（亏超限、对账不平）→ 立即电话/关键通道。
- P1 功能故障（行情停更、下单失败）→ 尽快。
- P2 性能退化（时延升高）→ 观察。
- **高分红话术**：**「告警的价值不是『报得多』，而是『报得对』。我宁可少而精，每条告警都对应一个明确的处理动作，否则就是告警疲劳。」**

### 职责5 · 将分散的研究/复盘脚本整合为标准任务和自动流水线
**这条是「把研究员的野路子变成工程」。**
- 现状：研究员写一堆脚本，`ctrl+c` 能跑，但没人管、没参数化、没版控、结果不可复现。
- 目标：抽成**标准任务（标准输入/输出模板）+ 自动流水线（数据取数 → 回测 → 指标 → 报告）**。
- 好处：可复现（换数据重跑结论一致）、可参数化、可自动化（每日/每周自动跑）、可版本管理（进 git）。
**关键点**：定义**契约（契约测试）**——规定输入数据 schema、输出指标 schema，防止「脚本今天能跑明天就崩」。

### 职责6 · 建立券商成交、系统账本和持仓的自动对账机制
**这是第二条资金命脉，重点中的重点。**
**为什么需要对账**：系统本地记录的是「你认为的持仓/成交」，券商记录的是「真实发生的」。两者会因为网络超时、重复下单、订单状态丢失、部分成交、撤单失败而**不一致**。资金场景下，账对不上是会亏钱的。
**对账机制设计**：
1. **三方对账**：券商成交回报 ↔ 系统账本 ↔ 交易所持仓。
2. **对账维度**：按天/按小时/实时，按合约、按订单ID、按数量、按价格、按盈亏。
3. **对账方式**：
   - 逐笔核对：每笔成交有唯一外部订单ID，逐条匹配。
   - 总值核对：持仓数量、可用资金、浮动盈亏的总额对比。
   - 差额稽核：找出「系统有券商无」「券商有系统无」「数量不一致」三类差异。
4. **差异处理**：差异明细出来后，人工/自动生成「调账单」，修复后再核对，闭环。
5. **幂等关键**：每次对账任务要能**重复跑不重复计**——用对账批次ID做幂等，跑 N 次结论一致。
**对账的本质**：**它是「最后一道防线」。即使前面的幂等、状态机、审计都漏了，只要每天对账能跑平，钱就不会错。** 这句话面试时讲出来非常加分。

### 职责7 · 完善数据质量检查、容量规划、备份归档和恢复演练
**「数据」这条偏数据平台。**
- **数据质量检查**：完整性（无缺数）、一致性（时间对齐）、准确性（价格合理性/跳变校验）、时效性（未过期）。可以做成**校验任务**挂到流水线里，不合格就告警/阻断后续任务。
- **容量规划**：历史行情是增长型数据，需要预判表大小、分区数量、磁盘/对象存储用量、带宽，提前扩容。
- **备份归档**：冷数据从热库（PG）归档到对象存储/Parquet；热数据保留最近 N 个月。
- **恢复演练（DR drill）**：定期从备份里恢复并验证能查、能算——**不能只备份不验证**。演练要有 RPO（最多丢多少）/RTO（多久恢复）目标。

### 职责8 · 参与生产事故处理、复盘及不变量测试建设
**「事故处理 + 复盘 + 不变量测试」是很高级的考点。**
- **事故处理**：第一时间止损（熔断/停单）→ 定性（能复现吗、影响面多大）→ 定位（日志/链路/对账差）→ 修复 → 恢复。
- **复盘（blameless postmortem）**：不追责个人，追「为什么会系统性发生」。5Whys，找出流程/工具/设计的失败。
- **不变量测试（invariant testing）**：这是非常加分的高阶概念。**定义系统的「必须永远成立」的性质，写自动化测试持续验证。**
  例子：
  - 订单状态机：`new → submitted → partially_filled → filled`，**不允许**从 `filled` 回到 `pending`。
  - 持仓恒等式：`总持仓 = Σ 成交 - Σ 平仓`，任何时刻成立。
  - 市值恒等式：`买入金额 = 卖出金额 + 已实现盈亏`。
  - 资金恒等式：`账户可用 = 净资产 - 占用保证金`。
  - 对账恒等式：`系统持仓 = 券商持仓`（容差内）。
- **为什么重要**：交易系统里有大量「状态流转」和「账务恒等式」，**用不变量测试把这些性质固化下来，比人工盯着强得多，也是防止回归的最佳手段。** 这是你区别于普通后端的加分亮点。

### 职责9 · 与策略分析师、AI Harness工程师共同定义稳定数据和调用契约
**「契约」是后端很熟的概念，直接迁移。**
- **数据契约**：定义行情/成交/持仓的结构（schema）、字段类型、单位、精度、空值约定、版本。
- **调用契约**：定义接口的入参/出参、错误码、限流、幂等键、超时语义。
- **契约测试**：用 schema 校验数据，防止「今天传 int 明天传 string」；接口用契约测试保证兼容。
- **版本管理**：契约升级要向后兼容（加字段不加必填），避免下游/研究脚本崩掉。
- **AI Harness 工程师**：说明团队有「用 AI 做策略/自动化」的同事，你要给他们稳定、确定的数据和接口，让他们能调。这是「人机协作」的定义者角色。

## 第 3 章 · 硬性要求考点深度讲解（这是你最容易丢分/最能拉开差距的部分）

### 3.1 幂等（Idempotency）—— 资金场景第一原则
**概念**：同一个操作执行一次和执行 N 次，结果一样。**「重复调用不会产生副作用」**。
**为什么交易必须要**：网络超时后客户端重发一条「下单」请求，如果服务端不幂等，就会下出两笔单——**多出来的那笔就是亏损**。
**实现手段（按层级）**：
1. **唯一业务键**：每条请求带一个 `order_id`（客户端生成），服务端以它为唯一约束，已存在就返回原结果，不重复下单。这是最常用、最可靠的。
2. **数据库唯一约束 / 幂等表**：`orders` 表对 `(client_order_id, account)` 加唯一索引，重复插入被拒绝。
3. **分布式锁 / 去重**：同一个 `client_order_id` 同时只有一个在跑。
4. **乐观/悲观锁**：更新持仓时加行锁或版本号，防止并发覆盖。
**代码感（FastAPI + SQLAlchemy 示例思路）**：
```python
# 伪代码：按 client_order_id 幂等
async def create_order(payload):
    order = await db.get(Order, client_order_id=payload.client_order_id)
    if order:
        return order  # 已存在，直接返回，不重复下单
    # 插入时用唯一约束兜底，捕获 IntegrityError 当作「已处理过」
    try:
        order = Order(client_order_id=..., status="pending")
        db.add(order); await db.commit()
    except IntegrityError:
        await db.rollback()
        order = await db.get(Order, client_order_id=payload.client_order_id)
    return order
```
**面试一句话**：**「我在所有会产生副作用的下单/撤单/调账接口上，都强制用客户端生成的唯一单号做幂等键，配合数据库唯一约束兜底，确保网络重试永远只落一笔。」**

### 3.2 超时（Timeout）与 重试（Retry）
**超时**：一次调用最长等多久。不设超时 = 一个下游挂了，整条链路卡死拖垮线程/连接池。
**重试**：失败后过一会儿再试，但要**有前提**：
- 只在**幂等**操作上重试（读、重试安全的写）。**下单绝不能盲目重试**（否则重复下单），用「查订单状态」代替「重新下单」。
- 用**退避（backoff）**：指数退避 `1s, 2s, 4s, 8s` + 抖动（jitter），避免雪崩。
- 设**最大重试次数** + 熔断兜底，别无限重试。
- **区分错误类型**：`timeout`（可重试）、`5xx`（可重试）、`4xx`（业务错误，重试也没用，别重试）。
**考点话术**：
> 超时和重试一定是**成对设计**的。对只读查询我用「小超时 + 指数退避重试」；对下单这类有副作用的操作，我不用『重发下单』，而是**超时后去查订单状态**——如果已成功就返回成功，如果失败才真正重发。这就是『重试查询而非重试动作』。

---

### 3.3 熔断（Circuit Breaker）
**概念**：把调用包装成状态机：`CLOSED（正常）→ OPEN（熔断，直接失败）→ HALF_OPEN（试探恢复）→ CLOSED`。
- 失败率超过阈值 → 打开熔断，一段时间内直接拒绝调用（快速失败），不再累垮下游。
- 冷却后进入 HALF_OPEN，放少量请求试探，成功则闭合，失败则继续打开。
**交易场景的两种熔断**（前面提过）：
- **技术熔断**：券商/行情源连接故障 → 停止调用，降级。
- **风控熔断**：日亏超限 → 停止开仓（可保留平仓，这叫「只平不开」）。
**面试话术**：
> 熔断我分技术层和风控层。技术层用标准熔断器防雪崩；风控层是交易特有的——当日亏损触线时，策略层进入「只平不开」状态。这里特别注意熔断打开后要有**半开试探**，否则券商恢复了熔断还卡在打开就永远起不来。而且**熔断本身要可观测**，打开要告警，不然就是个静默的坑。

### 3.4 状态机（State Machine）—— 订单/持仓的精髓
**为什么交易系统离不开状态机**：订单不是简单的一个「布尔」或数字，它有一整套**合法流转**，必须用一个显式状态机管住，不变量测试守护。
**订单状态机（期货/证券典型）**：
```
pending → submitted → partially_filled → filled
              │           │
              └→ rejected ┘
              └→ canceled (只能从 pending/submitted/partially_filled 撤，不能撤已成交)
```
**核心规则**：
- 状态**只能按边迁移**（合法迁移表），非法迁移直接抛错。
- **已成交的不能撤单**（这是最常见的事故根源）。
- **部分成交**（partially_filled）可以继续成交或撤剩余。
- 每次迁移都留**审计日志**（谁、何时、什么触发、前后状态）。
**设计落地**：
- 用枚举 + 迁移表（dict: `{from_state: {allowed_to: [...]}}`）。
- 更新用 `WHERE status = old_status` 的乐观锁（所谓 CAS），防止并发把已成交的单又改成 pending。
- **不变量**：`filled 单向，永远回不去 pending`。
**面试话术**：
> 订单我实现成显式状态机，用「合法迁移表 + 乐观锁更新（`UPDATE ... WHERE status=旧值`）」保证并发下状态绝不回退。最关键的一个不变量是「已成交的单不可撤」。所有迁移写审计日志，这样出问题时能精确回放「这张单是怎么走到 filled 的」。

---

### 3.5 审计（Audit）与 权限控制（AuthZ）
**审计**：所有影响资金/持仓/配置的操作，都记录「谁、何时、做了什么、改了哪个值、从什么状态到什么状态、用什么触发的」。**audit log 只追加不改**（append-only），能回放。
**权限控制**：
- 角色分离：交易员能下单，但不能改风控配置；风控能改配置，但不能下单（**职责分离**，防止一个人既能下单又能绕过限额）。
- 双人复核：大额下单/调账需要审批（4-eyes）。
- 最小权限：每个服务/人只拿到它需要的权限。
**面试话术**：
> 我会把「能下单的」和「能改风控规则的」分开，这是资金系统的职责分离，防止单点失守。审计日志只追加不改，能精确重放每一次资金变更。关键操作做双人复核，比如调账、超限单。

### 3.6 PostgreSQL · SQL调优 与 数据建模（对后端是强项，突出它）
**数据建模（交易数据）**：
- 订单表：`order_id`（PK）、`client_order_id`（唯一，幂等）、`account_id`、`symbol`、`side`、`price`、`qty`、`status`、`created/updated`。
- 成交表：`trade_id`、`order_id`（FK）、`symbol`、`price`、`qty`、`time`。
- 持仓表：`account_id + symbol` 联合唯一，`qty`、`avg_price`、`position_type`（多/空）。
- 资金表：可用、占用、保证金、浮盈。
**核心索引经验**：
- 查询频繁的健建索引：`(account_id, symbol)`、`(symbol, time)`、`(status)`。
- 订单状态变更极高，注意别让一个表无限膨胀——**分区**或归档。
**时序数据（行情）建模**：
- 用 **partition by range（按时间分区）**：`tick` 表按 `date/月` 分区，老分区快速 drop。
- 索引：`(symbol, ts)` 组合索引查某期货某时间段的行情。
- **BRIN 索引** vs **B-tree**：时间序列上 BRIN 很适合（块级范围索引，省空间），尤其只按时间查询。
**SQL调优步骤（面试要能踩）**：
1. `EXPLAIN (ANALYZE, BUFFERS)` 看执行计划 → 确认走没走索引、有没有 Seq Scan、join 方式。
2. 看扫了多少行 vs 返回多少行（选择性差就要加索引或改查询）。
3. 避免 `SELECT *`、避免大回表、避免函数套在索引列上（`WHERE date(ts)=...` 走不了索引，改 `WHERE ts >= ... AND ts < ...`）。
4. 分页用键集分页（`WHERE id > last_id` 而非 `OFFSET`）。
5. 事务里锁的粒度：尽量缩小事务范围，避免长事务持有锁。
**事务隔离 / 并发**：
- 读已提交（Read Committed）足够大多数场景。
- `SELECT ... FOR UPDATE` 做行级锁，扣减/更新账户余额时防并发覆盖（或乐观锁 `WHERE balance >= cost`）。
- **余额扣减的经典并发问题**：两个请求同时扣同一账户 → 用条件更新 `UPDATE account SET balance = balance - x WHERE id=? AND balance >= x`，靠行锁+条件保证不超扣，或悲观锁。
**面试话术**：
> 我对 PostgreSQL 很熟，会用 `EXPLAIN ANALYZE` 定位慢查询。交易场景我特别重视两点：**一是用唯一约束做幂等和用条件更新防止并发超扣余额；二是行情历史我用按时间分区 + (symbol, ts) 组合索引，老分区冷数据归档，查询用范围谓词而不是函数包裹。**

### 4.1 CTP / 期货 / 证券系统经验（这是关键加分，重点把概念讲准）
**CTP（综合交易平台，上期技术）**：国内主流期货交易 API/柜台。核心概念：
- **行情**：`Tick`（一档快照，含最新价、买一卖一、量、时间戳）；有些是 `DepthMarketData`（多档）、`Notice`（公告）。还有**合约信息**、**交易所行情**。
- **交易**：`ReqOrderInsert`（下单）、`ReqOrderAction`（撤单）、回报（`OnRtnOrder` 订单、`OnRtnTrade` 成交）。
- **账户/持仓**：`QryInvestorPosition`（投资者持仓，含多空、今昨仓、可用）、`QryTradingAccount`（资金）、`QryInstrument`（合约信息，含合约乘数、保证金率、交割月）。
- **期货特点**：**保证金 + 杠杆 + 强制平仓（追保/强平）**；**多空双向**；**T+0**；**涨跌停**；**夜盘/日盘交易时段**。
- **期货 vs 证券**：期货是保证金、带杠杆、双向、可能被强平；证券通常是现货、T+1、不能做空（部分市场除外）。
**面试表现**：只要你能口述「CTP 的下单/撤单/持仓回报回调、期货的保证金和强平、多空持仓区分」，就足够证明你有真实语感。可结合你 howtrader 项目讲。

### 4.2 Tick行情 / 合约 / 订单管理 / 仓位与风控系统
- **Tick 行情**：高频、量大（一秒钟每合约几十笔），需要低时延处理和存储。
- **合约（Instrument）**：代码（如 `rb2510`）、乘数、最小变动价位、保证金、交易时段、交割月。
- **订单管理（OMS）**：下单->回报->状态机->撤单->部分成交，全套管理。
- **仓位与风控**：仓位状态的实时计算、风控拦截、敞口监控。

### 4.3 FastAPI / asyncio / SQLAlchemy / Redis（技术组件，后端必修）
- **FastAPI**：异步 + Pydantic 数据校验 + 自动文档（OpenAPI）。很适合做订单/风控/查询接口。
- **asyncio**：事件循环，处理高并发 I/O（行情/下单/回调）。注意**别在 async 里跑阻塞代码**（要 `asyncio.to_thread` 或 `run_in_executor`），否则阻塞循环。
- **SQLAlchemy**：ORM + 异步（`AsyncSession`）+ 事务管理；可配合 Alembic 做 DDL 迁移。
- **Redis**：缓存（热点行情/持仓）、分布式锁（下单防重）、pub/sub（事件广播）、排行榜/实时数据。

**何时用 asyncio 的并发模型**：行情/订单这类 I/O 密集（网络回调）适合 asyncio；纯 CPU 计算（策略回测）不适合，要用多进程。这个 diu 别绕晕。

### 4.4 Prometheus / Grafana / OpenTelemetry / Sentry
- **Prometheus**：拉取式指标采集，Exporter 暴露 `/metrics`，支持自定义指标（Counter/Gauge/Histogram）。
- **Grafana**：可视化大盘 + 告警。
- **OpenTelemetry**：分布式追踪（trace）+ 指标 + 日志，跨服务定位问题。
- **Sentry**：异常聚合、堆栈、崩溃监控。
**监听什么**（交易平台）：下单时延、成交率、拒单率、行情更新时间、对账差异、PnL、订单状态机异常。

### 4.5 时间序列分区 / Parquet / 对象存储 / 大规模行情管理
- **时间序列数据**：Tick 行情是典型时序，量大且只增不改。
- **分区**：按时间（月/日）range 分区，查询只扫相关分区，老分区可 drop/归档；索引用 `(symbol, ts)`。
- **Parquet**：列式存储，压缩率高、适合 OLAP 分析（回测、统计）。查询比行式（CSV/JSON）快很多。
- **对象存储**（S3/MinIO/OSS）：存放冷数据、历史行情、备份；成本低、容量大。
- **架构**：热数据在 PG/时序库 + 冷数据在 Parquet/对象存储；回测时从 Parquet 加载。可提到 **ClickHouse/TimescaleDB/DuckDB**（能讲出来更加分）。

## 第 5 章 · 高频系统设计 / 场景题（面试官会当场考你设计）

### 场景1 · 设计一个「下单」服务，怎么保证不重复下单、不丢、能对账？
**回答框架（分模块）**：
1. **幂等**：`client_order_id` 客户端生成，服务端唯一约束。重复请求返回原结果。
2. **分步 + 状态机**：避免「下单成功但本地没记」——先落一个 `pending` 本地单，再调券商，回报回来更新状态，任何一步中断都可通过状态机恢复/对账发现。
3. **超时与查询**：下单超时 → **查券商订单状态**，不盲目重发。
4. **异步与队列**：下单放异步任务，落库后异步执行，避免接口阻塞；失败重试（幂等）。
5. **审计**：每次下单/状态迁移写审计。
6. **对账**：每日/每小时和券商成交、持仓对账，找出不一致。

### 场景2 · 行情源突然停了 / 数据延迟，策略还在发单怎么办？
**回答**：
- **数据熔断**：检测行情更新时间戳，滞后超过阈值 → 标记该合约数据「不可用」→ **策略暂停该合约开仓**（可保留平仓）。
- **降级**：切换备行情源（若有多源），或通知人工。
- **告警**：P0 级告警，触发应急。
- **不变量**：一条「行情新鲜度」不变量，持续监控，违规就阻断新单。
**核心原则**：**「数据不可信时，宁可少交易，也不做错。」**

### 场景3 · 怎么设计对账系统？
**回答**：前面第 2 章职责6 + 这里加一个「数据流」。
- 数据源：券商成交/持仓接口 + 系统本地账本 + 交易所持仓。
- 核对维度：按账户/合约/订单/数量/价格/盈亏。
- 差异分类：系统有券商无、券商有系统无、数量价格不符、顺序不一致。
- 处理流程：差异 → 生成调账 → 修复 → 再对账闭环。
- **幂等**：对账批次以「日期+来源」为幂等键，重复跑不重复计。
- **增量**：大表按天增量对，历史定期全量抽。

### 场景4 · 线上事故：某合约持仓和券商对不上，怎么排查？
**回答**：
1. 先**止损**：确认是否影响真实资金，需要的话先停单/熔断。
2. 看**审计日志**回放该合约的所有订单/成交/状态迁移，找出从哪一步开始偏差。
3. 核对**成交回报** vs **系统记录**：是不是有 `filled` 但没记、或重复记。
4. 看**状态机**是否被非法回退（比如已成交被改回 pending）。
5. **对账差异明细**定位具体是数量多/少、方向反、还是价格错。
6. **根因**分析：网络超时丢回报、重复下单、并发覆盖、回调顺序错乱。
7. **修复 + 复盘**：修数据 → 修复代码/加防护 → 写复盘 + 补不变量测试。

### 场景5 · 一个慢查询，你一般从哪开始调优？
**回答**：`EXPLAIN ANALYZE` → 看全表扫描/是否走索引 → 看扫描行数 vs 返回行数 → 建索引/优化 join/改谓词避免函数包裹 → 考虑分区/归档冷数据 → 必要时物化视图/缓存。注意别一头扎进「加索引」，先看执行计划。

2. 「**对账**现在是怎么做的？是每日批式还是实时？目前遇到过最棘手的一次数据不一致是什么？」
3. 「你们如何做**发布**？有没有灰度 + 回滚的机制，还是直接替换？」
4. 「**风控熔断**哪些是引擎内置、哪些是平台强制的？比如日亏熔断是不是平台层统一做的，还是每个策略自己写？」
5. 「团队里策略研究员和平台工程师怎么分工？**数据/接口契约**谁来定义？」
6. 「岗位更偏**交易执行**、**数据平台**还是**SRE治理**？我目前的侧重更匹配哪个方向？」

## 附 · 高频「一句话金句」（面试直接甩，非常加分）

- 「**幂等是资金系统的第一原则**，重复执行结果必须一致。」
- 「网络超时后我**重试查询，而不是重试动作**——尤其下单。」
- 「**熔断分技术层和风控层**，风控熔断是交易特有的『只平不开』。」
- 「订单是**状态机**，已成交的单**永远回不去** pending，靠乐观锁守护。」
- 「前面的机制让错误**不发生**，对账让错误**藏不住**。」
- 「**数据不可信时，宁可少交易，也不做错。**」
- 「告警的价值不是报得多，而是**报得对**——每条都有明确动作。」
- 「**不可变发布 + 版本清单** = 我可以一句话回到上一个健康版本。」
- 「**不变量测试**把『必须永远成立』的性质固化下来，防止回归。」
- 「**职责分离**：能下单的不能改风控规则，防止单点失守。」
- 「文档不是负担，是**防止『我走了系统就没人懂』**的投资。」
