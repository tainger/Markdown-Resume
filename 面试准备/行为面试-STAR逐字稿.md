## 故事一：从0到1架构设计 ⭐核心

> **阿里云 MSE — AgentMate AutoDev 多智能体自动开发流水线**

---

我在阿里云 MSE 微服务团队负责 AgentMate 智能体平台，其中最核心的模块是 AutoDev——自动开发流水线。团队的诉求是把研发运维动作沉淀为可编排的 Agent，降低一线研发成本。但当时市面上没有现成的多智能体协作框架能直接套用，我需要从0到1设计一条从「一句需求描述」到「代码提交、上线」的端到端自动化链路。

我的任务是从0设计这套多智能体流水线的整体架构。

我做的第一件事是拆解研发流程。把一次需求交付抽象成五个阶段：建工单 → 写 Spec → 编码 → 单测 → 部署，然后用一个顺序状态机串起来。每个阶段对应一个智能体：SpecAgent 负责把需求拆成结构化 spec，CodingAgent 负责按 spec 生成代码，DeployAgent 负责走发布流水线。三个智能体分工协作，前一个的输出是后一个的输入。

第二件事是执行器封装。智能体本身不会写代码、也不会发版，它需要调用外部工具。我把 Qoder CLI 进程封装成编码执行器，把 OP2 平台流水线封装成发布执行器，收敛成 Agent 可调用的原子操作。这样 Agent 的职责是「决策调度」，执行器负责「落地动作」，边界清晰。

第三个也是最难的是并发隔离。多个任务并发跑时，如果共享同一个 git 工作目录，会出现提交落错分支、AI 生成的文件互相覆盖等竞态问题。我设计了 WorktreeManager，给每个任务分配独立的 git worktree，从物理上隔离工作空间。但加锁粒度很关键——我只对 worktree 元数据操作加仓库级锁，耗时的编码过程运行在锁外，这样既保证安全又保留了并行度。同时还做了兜底：配置开关支持异常时降级回退共享目录。

最后补充了幂等判定——判断分支上是否已存在本任务提交，让重复触发的任务能安全重跑。

效果上，这条流水线实现了从需求描述到代码上线端到端自动化，成为 AgentMate 平台的核心能力，也是我后续做过程式重构、回归测试守门的基础。

### 💡 面试官可能追问 & 你的回答

| 追问 | 回答要点 |
|:---|:---|
| 多智能体为什么用顺序状态机而不是并行/DAG？ | 研发流程本身是强顺序依赖的，spec 没出来编码无从开始；DAG 适合可并行的子任务，但会引入调度复杂度，当前阶段顺序状态机最可控 |

| Agent 和执行器边界怎么定？ | Agent 只做「决策调度」——拆解、选择工具、判断下一步；执行器只做「落地动作」——跑 CLI、触发流水线。边界清晰才能分别做回归和降级 |

## 故事二：技术选型 Trade-off ⭐核心

> **国际物流平台 — 多租户数据隔离方案选型**

---

在奥克斯做国际物流平台的时候，我需要从零设计多租户体系。平台要同时支撑马来西亚、泰国、美国、迪拜四个国家的业务，总计 16 个承运商，每个都是独立租户。

当时面临的核心决策是：**数据怎么隔离？**

业界常用的三种方案：一是**独立数据库**，每个租户一个库，隔离性最强但运维成本最高；二是**共享数据库 + Schema 隔离**，每个租户一个 schema；三是**共享数据库 + 共享表 + 字段隔离**，所有租户的数据在同一张表里，通过 `tenant_id` 区分。

我分析了我们实际情况后选了第三种方案，原因有三个：

第一，租户数量不多，只有 16 个，独立库每个库都要建表、维护、备份，DBA 的工作量翻 16 倍，划不来。

第二，Schema 隔离看起来折中，但我们用的是 JPA，schema 切换在 JPA 层面支持得不好，需要改很多底层代码。

第三，字段隔离虽然隔离性最弱，但可以通过**租户上下文拦截器**在 DAO 层统一注入 `tenant_id` 过滤条件，代码改动最小，而且不容易出现「忘记加租户过滤」的安全问题。

实现上，我设计了一个 `TenantContext` 持有当前请求的租户 ID，在网关层从请求头解析出来后放到 ThreadLocal 里。Mybatis 层面写了一个拦截器，自动给所有 SQL 拼上 `tenant_id = ?` 条件。这样业务代码完全不需要感知租户逻辑。

当然这个方案也有局限。我说了隔离性最弱，所以后来我们又加了一条规则——涉及财务结算的核心表单独走独立 Schema，普通业务表走字段隔离。这样在安全性和成本之间做了平衡。

如果未来租户涨到 100+，我考虑的方向是：按地域或业务量做**分库**——比如亚太区一个库、欧美区一个库——然后再在每个库内继续用字段隔离。这样既能控制单库压力，也不会让运维成本失控。

## 故事三：最有挑战的技术问题

> **EasyBI — 多源异构数据查询的性能优化**

---

我当时在乐其电商负责 EasyBI 数据分析平台的开发。这个平台有个核心功能是仪表板，用户可以在上面拖拽配置图表，后端会实时查询数据回来渲染。

我们的数据源比较复杂，一个图表可能同时查 MySQL 和 Hive，通过 Presto 做跨源 join。早期数据量小的时候没什么问题，后来随着业务增长，有些图表单次查询就耗时 10 秒以上，仪表板打开要等十几秒，用户反馈很差。

我的任务是在不改变底层数据源的前提下，把首屏渲染优化到 2 秒以内。

我做的第一件事是分析慢查询。发现两个问题：一是很多图表的数据其实不需要每次都查底层引擎，因为底层数据的更新频率是 T+1；二是 Presto 的跨源 join 没有做谓词下推，导致大量无关数据被拉取到 Presto 层再过滤。

针对第一个问题，我设计了一个**两级缓存方案**。一级是 Caffeine 本地缓存，二级是 Redis 分布式缓存。缓存更新策略上，我做了两条路径：对于实时性要求高的图表，底层数据变更时通过 RocketMQ 发消息主动失效缓存；对于可以容忍延迟的图表，采用定时惰性刷新。淘汰策略选了 LRU，因为我们的访问模式是最近看过的图表更可能被重复访问。

这里有个比较 tricky 的点是一致性。因为我们有多实例部署，一个实例更新了数据，怎么保证其他实例的本地缓存也同步失效？我的方案是：数据变更时发一条 MQ 广播消息，所有实例收到后把自己本地 Caffeine 里对应的 key 清掉，下次请求时会穿透到 Redis 重新加载。

效果上，仪表板图表渲染效率提升了 300%，P99 从 12 秒降到了 3 秒左右。这个优化后来也成了 EasyBI 其他查询场景的标准缓存方案。

---

### 💡 面试官可能追问 & 你的回答

| 追问 | 回答要点 |
|:---|:---|
| LRU 具体怎么实现的？ | Caffeine 内置了 W-TinyLFU，比纯 LRU 命中率更高；Redis 我用的是 `allkeys-lru` 策略 |
| 为什么 Caffeine 而不是 Guava？ | Caffeine 是 Guava Cache 的继任者，基于 W-TinyLFU 算法，命中率和内存效率都更优；Guava 太久没维护了 |
| 缓存击穿怎么防？ | 对热点 key 加了互斥锁，第一个请求去加载数据，后续请求等待结果；同时设了合理的 TTL 兜底 |

## 故事四：一次生产事故及复盘

> **APASS — 集成平台流程日志模块 ES OOM 故障**

---

这个事故发生在端点科技的 APASS 集成平台上。当时我刚把流程日志模块从 MySQL 迁移到 ElasticSearch 不久。

那天下午运维群里突然炸了，业务方反馈所有流程都跑不起来了，报超时。我登录看日志，发现大量流程在记录执行日志的时候卡住了，再去看 ES 集群，三个节点有两个 OOM 重启，集群变成 yellow 状态，写入基本瘫痪。

因为集成平台是低代码流程引擎的核心，流程挂了意味着整个业务方所有的数据同步、接口编排都在受影响。事态比较紧急。

**止血阶段**：我先把日志保存策略临时切到了「采样模式」——只记录流程入口和出口，中间节点暂时不记录，这样可以快速降压。大概 5 分钟后流程恢复执行。同时运维那边重启了宕掉的 ES 节点。

**根因分析**：恢复之后我开始查原因。翻 ES 的 slow log，发现分词的 terms 数量异常高。原来我们的业务字段里有很长的 JSON 字符串，ES 默认的 standard 分词器把这个字段切成了上百个 term，加上流程并发量高，倒排索引迅速膨胀，最终把堆内存撑爆了。

**长期修复**：我做了三件事——第一，给这类业务字段设置 `index: false`，不让 ES 做分词索引，只保留 keyword 类型做精确匹配；第二，引入 IK 分词器并配置了自定义词库，只对真正需要做全文检索的中文字段分词；第三，在日志模块加了个监控，当索引写入延迟超过阈值时触发钉钉告警。

**复盘沉淀**：事后我写了事故复盘文档，梳理了 ES 在日志场景下的最佳实践——包括字段 mapping 规范、分词策略、堆内存配置和监控指标。这份文档后来成了团队的 ES 使用规范，之后类似的问题没有再出现过。

---

## 故事五：跨团队协作与推动落地

> **阿里云 MSE — AgentMate 需求协同与研发度量自动化**

---

在 AgentMate 平台里有一个场景：MSE 和云原生网关两个团队，原先靠研发同学人工逐条巡检 Aone（内部研发平台），做值班需求反馈收集、迭代进度催办、安全分透出。这种活儿琐碎、容易漏，而且催办时还得 @ 到具体责任人，人工做效率很低。

我的任务是用 Agent 把这些跨团队的协同工作自动化，把「人工巡检」变成「自动汇总 + 精准触达」。

我基于 SchedulerX2 定时调度和 Aone MCP 工具，开发了十余个定时智能卡片，覆盖值班需求反馈、迭代进度收集与催办、安全分透出等场景。每个卡片的链路是：Agent 按调度触发 → 调用 Aone MCP 拉数据 → 大模型汇总分析 → 生成钉钉 AI 卡片 → @ 到责任人推送。

这里有个 tricky 的点是长耗时任务。比如周报技能要扫描多个仓库的 commit 和 release 生成结构化周报，大概要 4 分钟。如果同步等，钉钉会话会超时。所以我设计了「立即受理 + 后台生成 + 完成后私信/群卡片推送」的异步模式——先回复一句「已受理」，后台跑完再推结果。

另一个坑是重复触发。同一个责任人、同一个仓库可能被多次调度命中，我用「同人同仓库分布式锁」防止重复生成。还有一个问题是模型会编造仓库名，所以我做了一个仓库清单查询工具，让 Agent 先查真实清单再操作，既避免幻觉又不会因为同步阻塞卡住链路。

效果上，这套智能卡片替代了原先人工逐条巡检 Aone 的工作，迭代进度催办和安全分透出都实现了自动触达责任人，推动两个团队的研发度量透明化。

## 故事六：意见冲突与说服他人

> **阿里云 MSE — AutoDev 执行链路过程式化重构**

---

AutoDev 流水线早期我设计的是「主管 Agent + 执行 Agent」双层 ReAct 架构——主管 Agent 负责拆任务、调度，执行 Agent 负责具体动作，两层都跑 ReAct 循环（思考-行动-观察）。听起来很优雅，但上线后问题很大：双层 ReAct 推理容易发散，链路经常超时，结果不可控。

我的判断是：执行层应该从 ReAct 改成过程式线性流水线——把编码、单测、部署这些确定步骤写死成流水线，只在自由对话入口保留 ReAct。但团队有同事反对，理由是：过程式会牺牲 Agent 的灵活性，而且改造成本不小。

我没有硬推。第一步先拿数据：把双层 ReAct 下链路超时的 case、推理跑偏的日志整理出来，量化超时率和失败率，让大家看到问题不是偶发的。第二步做折中方案：不是把 ReAct 全砍掉，而是分层——自由对话入口（用户问问题）保留 ReAct 发挥大模型推理能力，执行链路（确定性的研发动作）改过程式保证可控。第三步补充了幂等判定（分支是否已有本任务提交），用健壮性增强来对冲「过程式不够灵活」的担忧。

最终说服了团队完成重构。重构后链路稳定性明显提升，超时问题基本消失。这件事让我学到：技术分歧不要靠「谁资深」定，要用数据和折中方案说话，而且要区分场景——该灵活的地方灵活，该确定的地方确定。

## 故事七：失败经历与反思

> **CyberLoRA — SDXL 人物 LoRA 训练踩坑（过拟合与 NaN 黑图）**

---

这是我的个人项目 CyberLoRA，目标是用户给 20-30 张生活照就能训练专属人物 LoRA，生成高质量写真。核心要求是「看不出是 AI 生成的」——人物要像、不能有五官畸形和塑料感。

我第一次训练完出图，结果全是黑图。排查后发现是 fp16 的问题：T4 显卡只有 fp16 有 Tensor Core 加速，但 SDXL 的 VAE 在 fp16 下会算出 NaN 导致黑图。解决办法是用 `no_half_vae` 把 VAE 保留成 fp32，其他部分还是 fp16——在显存和稳定性之间做了取舍。

第二个坑是过拟合。权重调高后，出图出现典型的 AI 痕迹：五官变形、油腻塑料感。我意识到「像不像」不能靠肉眼看，于是引入 ArcFace 人脸 embedding 余弦相似度，把主观感受变成可复现的数值。用多 seed 重复评测报均值 ± 标准差（实测 0.792±0.018，而无身份注入的对照组只有 -0.019，证明指标不会误报）。基于数据我建立了权重分档策略：远景/背影 0.5~0.65、常规场景 0.7~0.85、特写不超过 0.95，配合负向词抑制畸形。

这件事让我学到：主观问题一定要先建立量化指标，否则你不知道改了是变好还是变坏；而且调参不能拍脑袋，要看「权重 vs 相似度」曲线的拐点来选档。

最终形成了可复现的出图质量基线，相似度 0.792±0.018，工具链沉淀成三条可跑路线（零 GPU 工程化 + Colab 训练 + 本地 MPS 推理），他人 clone 后一键可复现。

| 追问 | 回答要点 |
|:---|:---|
| 为什么用 ArcFace 而不是 CLIP 相似度？ | ArcFace 是人脸身份 embedding，专门衡量「是不是同一个人」；CLIP 衡量的是图文语义相似度，会被画面风格干扰，不适合做身份一致性评测 |
| fp16 为什么 VAE 出 NaN 而 UNet 不出？ | VAE 解码涉及高精度数值运算，fp16 动态范围小容易溢出；UNet 有 normalization 兜底相对稳定，所以单独把 VAE 保 fp32 |
| 这个项目对工程能力有什么提升？ | 建立了「量化闭环」思维——评测指标 → 数据驱动选型 → 回归基线，这套思路后来在 AgentMate 的 LLM-as-Judge 回归测试里也用上了 |
| 对照组为什么是负的？ | 无身份注入的对照组（不喂人物照片）相似度 -0.019 接近 0，说明指标不会被画面巧合误报，验证了指标有效性 |

## 故事八：主动担责与超出本职

> **端点科技 APASS — Mule IDEA 插件独立开发**

---

在端点科技做 APASS 集成平台时，平台支持多租户，团队同学日常开发要频繁切换租户登录、手写模板代码、去仓库里翻组件看，这些重复操作很耗时。这其实不是分配给我的任务，我的本职是后端业务开发，但我自己被这些重复操作烦到了，就主动承担下来。

我独立开发了一个 IntelliJ IDEA 插件——Mule Plugin。功能包括：多租户登录（插件里直接切租户，不用每次去网页登录）、模板代码生成（选中组件一键生成调用模板）、当前仓库组件展示（直观看到有哪些可用组件）。

开发过程我没用团队额外资源，业余时间研究 IntelliJ Platform SDK，从 Action、Tool Window 到 PSI 文件操作一点点啃下来。插件做好后团队同学都用上了，模板代码生成那块尤其受欢迎，省了大量重复敲键盘的时间。

这件事让我学到：超出本职的贡献往往来自「自己被痛点烦到」——你不是在完成 KPI，而是在解决自己和团队真实的不爽。这种主动性反而更容易被认可，后来这套插件也成了团队的标准开发工具。
