# 向量化模型选型（Embedding Model Selection）

> AgentMate 项目技术选型文档：向量化模型的概念、作用、主流模型对比、阿里云百炼模型清单、选型决策树与项目落地建议。
> 更新时间：2026-09-06

---

## 一、什么是向量化模型？

### 1.1 定义

向量化模型（Embedding Model）是将**文本/图像/视频等非结构化数据转换为固定维度数值向量**的深度模型。转换后的向量能表达语义信息，语义相近的文本在向量空间中距离更近。

```
文本: "Redis 分布式锁怎么实现？"
        │
        ▼ Embedding Model
向量: [0.023, -0.145, 0.891, ...]  ← 1024 维浮点数

语义空间：
  "Redis 分布式锁" ↔ "SETNX 实现互斥锁"  距离近（cosine ~0.85）
  "Redis 分布式锁" ↔ "MySQL 行锁"       距离远（cosine ~0.30）
```

### 1.2 核心特性

| 特性 | 说明 |
|:---|:---|
| **固定维度** | 不同模型输出维度不同（256/512/768/1024/1536/3072） |
| **语义保持** | 相似语义的文本向量距离近 |
| **归一化** | 通常 L2 归一化后用 cosine similarity = dot product |
| **不可互换** | 查询和文档必须用**同一模型** + 同一预处理，否则向量空间不一致 |

## 二、向量化模型的作用

### 2.1 RAG 系统的核心组件

```
RAG 查询链路中 Embedding 的位置：

用户提问 → Query Embedding → 向量检索 → Reranking → Context → LLM 生成
                ↑                                        ↑
                └─────── Document Embedding ─────────────┘
                         （入库时执行一次）

Embedding 质量直接决定检索召回率，是 RAG 系统 70% 问题的根源。
```

### 2.2 下游任务全景

| 任务 | 说明 | 对 Embedding 的要求 |
|:---|:---|:---|
| **语义搜索** | 最相似的 Top-K 文档召回 | 高召回率，中英文均衡 |
| **RAG 检索** | 知识库问答的知识供给 | 长文本支持 + 领域适应性 |
| **聚类** | 文档自动分组 | 向量空间可分性 |
| **分类** | 文本自动打标签 | 语义区分度 |
| **推荐** | 基于内容推荐 | 用户/物品向量匹配 |
| **异常检测** | 离群点发现 | 密度分布均匀 |

### 2.3 为什么选型重要？

```
Embedding 模型选错的后果：
  ├─ 检索召回率低 → RAG 答非所问
  ├─ 中文效果差 → 英文模型在中文场景水土不服
  ├─ 维度选错 → 存储空间浪费或精度不足
  ├─ 成本失控 → 高频调用 API 费用暴增
  └─ 迁移困难 → 换模型需重新向量化全量文档
```

### 3.4 选型关键维度

| 维度 | 考量 |
|:---|:---|
| **语言** | 中文为主 → bge-m3 / Qwen3-Embedding；英文为主 → text-embedding-3-large |
| **成本** | 低流量 → API 按量付费；高流量 → 自部署开源模型 |
| **数据安全** | 敏感数据 → 自部署；通用场景 → API 可接受 |
| **输入长度** | 长文档 → bge-m3（8K）/ Qwen3-Embedding（32K） |
| **维度** | 大规模存储 → 256/512；通用 → 1024；高精度 → 1536/2048/3072 |
| **多模态** | 跨模态检索 → qwen3-vl-embedding / tongyi-embedding-vision-plus |

## 五、技术选型决策树

```
开始选型
  │
  ├─ 数据敏感？（金融/医疗/政企）
  │   ├─ 是 → 自部署开源模型（bge-m3 / Qwen3-Embedding）
  │   │       ├─ 中文为主 → bge-m3（MIT，开箱即用）
  │   │       └─ 中英混合 + 长文本 → Qwen3-Embedding-0.6B（32K 输入）
  │   │
  │   └─ 否 → 使用 API 服务
  │           │
  │           ├─ 阿里云生态？
  │           │   ├─ 是 → 百炼 DashScope
  │           │   │       ├─ 最新旗舰 + 超长文本 → qwen3.7-text-embedding
  │           │   │       ├─ 高性价比 → qwen3.7-text-embedding-flash
  │           │   │       ├─ 灵活降维 → text-embedding-v4
  │           │   │       └─ 存量迁移 → text-embedding-v3
  │           │   │
  │           │   └─ 否 → OpenAI / Cohere
  │           │           ├─ 英文为主 + 高精度 → text-embedding-3-large
  │           │           └─ 成本敏感 → text-embedding-3-small
  │           │
  │           └─ 多模态需求？
  │               ├─ 是 → qwen3-vl-embedding（融合向量）/ tongyi-embedding-vision-plus
  │               └─ 否 → 文本模型（见上）
  │
  └─ 维度选择
      ├─ 大规模存储（千万级）→ 256/512
      ├─ 通用场景 → 1024（默认）
      └─ 高精度要求 → 1536/2048
```

## 六、AgentMate 项目选型建议

### 6.1 项目场景分析

| 维度 | AgentMate 现状 |
|:---|:---|
| 主要语言 | 中文为主，少量英文技术文档 |
| 数据规模 | 知识库百万级 chunk（持续增长） |
| 调用频率 | 在线问答，实时性要求高 |
| 部署环境 | 阿里云生态（MSE 团队） |
| 成本约束 | 中等，需平衡成本与效果 |
| 已有技术栈 | Spring AI + Milvus 向量数据库 |

### 6.2 推荐方案

**首选：`text-embedding-v4`（1024 维）+ `qwen3-rerank` 精排**

```
理由：
  1. 阿里生态集成顺畅，Spring AI 原生支持 DashScope
  2. v4 属于 Qwen3-Embedding 系列，中文效果第一梯队
  3. 1024 维平衡精度与存储成本
  4. 支持灵活降维（可按需降到 512 节省存储）
  5. 配合 qwen3-rerank 两阶段检索，精度有保障
```

**备选（极致成本）：`qwen3.7-text-embedding-flash`（1024 维）**

```
理由：
  1. 价格仅为 v4 的 1/4（¥0.000125 vs ¥0.0005 /千tokens）
  2. 支持 128K 超长文本，比 v4 的 8K 大 16 倍
  3. 201 种语言支持，多语言能力更强
  4. 适合大规模知识库 + 高 QPS 场景
```

**备选（数据敏感）：自部署 `bge-m3` + `bge-reranker-v2-m3`**

```
理由：
  1. MIT 许可证，商用无忧
  2. 中文效果开源第一梯队（MTEB 中文 ~70.2）
  3. 支持 dense/sparse/multi-vector 三种检索模式
  4. 数据不出内网，满足安全要求
```

### 6.3 Spring AI 集成示例

```yaml
# application.yml
spring:
  ai:
    openai:
      api-key: ${DASHSCOPE_API_KEY}
      base-url: https://dashscope.aliyuncs.com/compatible-mode
      embedding:
        options:
          model: text-embedding-v4  # 或 qwen3.7-text-embedding-flash
          dimensions: 1024
    milvus:
      enabled: true
      host: ${MILVUS_HOST}
      port: 19530
      collection-name: agentmate_knowledge
      embedding-dimension: 1024
```

```java
// 文档向量化 + 存储
@Service
public class DocumentService {
    
    private final EmbeddingModel embeddingModel;
    private final VectorStore vectorStore;
    
    public void importDocument(String content) {
        // 1. 切片
        List<String> chunks = splitContent(content, 300);
        // 2. 向量化（自动调用 DashScope text-embedding-v4）
        // 3. 存入 Milvus
        vectorStore.add(chunks);
    }
    
    // 检索
    public List<Document> search(String query) {
        return vectorStore.similaritySearch(
            SearchRequest.builder()
                .query(query)
                .topK(20)           // 粗召回
                .build()
        );
        // 后续用 qwen3-rerank 精排到 Top-5
    }
}
```

### 6.4 迁移注意事项

| 注意点 | 说明 |
|:---|:---|
| **模型不可混用** | 换模型需重新向量化全量文档 + 重建索引 |
| **维度固定** | 同一 collection 内维度必须一致，降维需新建 collection |
| **Batch 调用** | 文档入库用 Batch API（价格减半），查询用实时 API |
| **归一化** | cosine similarity 需确保向量已 L2 归一化 |
| **监控** | 关注 API 限流（RPM/TPM），高频调用需做队列削峰 |

## 七、常见问题

**Q1：为什么中文场景推荐 bge-m3 而不是 OpenAI？**

A：bge-m3 在 MTEB 中文评测 ~70.2，优于 text-embedding-3-large（~64.6）。且开源免费、可自部署、无数据泄露风险。OpenAI 优势在多语言均衡和生态完善，但中文性价比不如 bge-m3。

**Q2：text-embedding-v4 和 v3 怎么选？**

A：v4 属于 Qwen3-Embedding 系列，效果更好且支持灵活降维（64-2048），是新项目首选。v3 主要用于已有 v3 索引的存量迁移，维度兼容（512/768/1024）。

**Q3：维度是不是越小越好？**

A：不是。维度越小存储越省但精度损失。经验值：256 维精度损失 ~5%，512 维 ~2%，1024 维基本无损。大规模存储可降到 512，通用场景用 1024。

**Q4：为什么需要 Rerank？向量检索不够吗？**

A：向量检索用双塔模型，query 和 doc 独立编码，无法细粒度交互。Rerank 用 Cross-Encoder 拼接 query+doc 过模型，精度更高。两阶段架构（向量粗召回 Top-20 + Rerank 精排 Top-5）兼顾速度和精度。

**Q5：API 调用和自部署怎么选？**

A：年调用量 < 1000 万 tokens → API 便宜（不用维护 GPU）；> 1 亿 tokens → 自部署更经济（GPU 月租可覆盖）。数据敏感场景必须自部署。
